# Membership model: ambiguities and findings
> Summary: Places where spec/permissions.md §1–§2, §5.1, §5.2 and §6 left a choice or failed a checked property. M1 (a removed admin's backdated write on its remover's edge survived as a chain write) and M3 (same-key commits) are fixed; M2 (sticky drops) is known and kept as an expected failure; the rest are readings.

## Findings (expected failures in run.sh)
- **M1. Chain-write exemption lets a removed admin forge (`MC_forge.cfg`, LateEdge). Fixed** by option (a): spec/permissions.md §5.1 now counts writes on A's chain only as its frontier lists them (the commit IDs of its chain certificates at R's point); the model's exemption is gone, honest frontiers always hold the author's chain certificates (`Certs`), and `MC_forge` passes. Original finding: §5.1 Frontier: "a frontier MUST NOT cover what A had not received as of T. A's own chain writes and R itself always count." Read as the writes that set the admin edges on A's admin paths (as osis-perm does), this counts writes A never received. Trace: n1 owns A; n2, n3 admins; n2 removes n3 at ts 8 (frontier empty); afterwards n3 writes n2's edge as admin `until` 9, stamped ts 6. At n2's removal that write set n2's own admin edge, so it counts as n2's chain write and is never dropped: n2's admin expires at 9 while n3 stays removed. Any lowering of the remover's chain edge works the same way (an `until` after the removal, a lower invite); a lowering that takes effect before T instead voids the removal, which is the accepted backdating race the owner's further-backdated revoke settles. osis-perm reproduces it (the forgery applied, the remover ends with no role).
  Options: (a) drop the exemption: A's frontier lists its chain writes (it holds them as certificates, so they are always received); a forged one is then dropped and A's edge reverts. Residue: a chain write A never received that its authority at T happens to rest on falls, and R with it (rare: A's own view had another path). (b) Exempt only chain writes that do not lower the edge they set (forged raises only help A). (c) Exempt only chain writes ordered before the newest write A had received on that edge. **Recommendation: (a)**, one rule ("nothing but the frontier decides"), at the cost of a few frontier entries; (b) if the residue of (a) matters.
- **M2. Drop order matters (`MC_sticky.cfg`, DropOrderFree).** §5.1 steps 4–5 restart at the first write that adds to D, and D only grows within an evaluation. Trace (with honest frontiers): n2 removes n3 at ts 8 (frontier empty); n3 then grants n2 admin on B stamped ts 6, which n2 never held, so the removal drops it; n1 removes n2 at ts 10 (frontier empty), dropping n2's removal. Walk order keeps the grant dropped although what dropped it is invalid; finding n1's demotion first keeps the grant. Known (notes/permissions.md, sticky drops; re-grant repairs). Determinism holds only because the order is fixed: an implementation that discovers drops in another order (by thing, by component, in parallel) diverges. The text is precise enough ("restarts"); worth a sentence that the first adding write in walk order wins.
  Corollary (`MC_sticky_snap.cfg`, Neutral, same history): a roster snapshot of A taken after it carries no demotion of n3 (n2's removal of it was dropped), so the replay applies n3's grant on B: the snapshot repairs the sticky drop and is not neutral. osis-perm agrees (grant dropped before the snapshot, applied after); its neutrality tests (`tests/roster.rs`) did not meet this history. Benign (the snapshot moves the timeline to the answer the drop's cause no longer supports, like a re-grant), but §6 neutrality holds only up to sticky residue; notes/permissions.md should say so.
- **M3. Two commits of one node at one ts (`MC_samets.cfg`, Neutral). Fixed**: ledger and roster keys were (`ts`, node), so a demotion and a re-grant of one member by two commits of one node at one ts shared a key and replayed as no demotion (trace in the README). spec/permissions.md §6 now keys writes by (`ts`, node, commit ID) (the `edge_key` type carries the commit ID); the model's keys follow, and `MC_samets` passes.

## Readings
- **M4. Several-edge removal: one point or in sequence.** commits §2 allows one commit removing several members' edges; §5.1 "each edge write of a commit is judged on its own". Model: every edge write of a commit is judged against the state before the commit, then applied in member order (osis-perm likewise). In sequence, removing B (through which the author is admin) first would make the author's second removal unauthorized. Suggest: "judged on its own against the state before the commit".
- **M5. Self-removal through an actor that holds admin on the target.** §2: a write lowering X's edge is a self-removal when "admin on X is the author's only authority for it (no owner-chain or edge-admin authority on the target at that point)". If X itself is admin on the target, the author's edge-admin authority comes through X, so literally the write is explicit and demotes its own author; that is the only way §5.1's "R never demotes its own author" arises in this model. Model: literal (authority through X counts), as osis-perm. If "other than through X" was meant, the kept-standing rule becomes nearly dead text.
- **M6. Re-grant "valid again" (§5.2).** "A re-grant makes every write of the re-granted actor valid again, including those in the gap": literally every write, including forgeries backdated before the actor's first grant. Model: writes from the first point the author held the required role (as osis-perm); earlier ones stay invalid. Also "re-granted" is judged at the end of time (every `until` passed), so validity does not depend on the clock.
- **M7. `since` of a roster edge.** §6: "the key of the write that established it". When a later explicit write kept the role (added an `until`), taking that write's key would hide the tenure between the two writes from the replay (the member's content there turns invalid). Model: the start of the tenure in force (osis-perm likewise).
- **M8. An auditing write that ends no tenure.** §6 "audits" includes a new value that "carries an `until`"; such a write ends no tenure and is not an audit-only entry (a tenure is in force), so its frontier is not in the ledger. Harmless in the walk: it takes nothing at its point and the expiry audits nothing. Model: literal.
- **M9. Split entries.** §6 "one that audits from above the role of the tenure in force ends that tenure, which goes on from its key": the ended entry records the tenure's role, not the audited one; the replay recovers the higher audit from the edge as restored. Model: literal; neutrality holds.
- **M10. Who "reaches the member".** §5.1 step 4: X reaches M (or is M) through alive edges at R's point, before R. Model: before R.

## Not modeled
Invites and invite grants (so whether an invite grant is an explicit write that resets the restore window is open), links and single-use redemptions, read-level tenures (§6 keeps the ledger to write and above; read edges have no `since`), a second roster snapshot (the earlier ledger carried forward), mutual membership beyond B on A, more than two things, frontiers per counter range (a frontier is a set of commit IDs), pending commits and certificates.

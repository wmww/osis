> Summary: Implement the node side of spec/sync.md in `osis-node` (`labeling/`, `sync/`): which blobs go under which label (closure, entitlement, projection by retention class, retag), wraps and stamps or deposits, certificate blobs, node cards and heartbeats, the convergence rule (must-hold / may-hold / must-not-hold) and acting on it, compaction order and deletion by token incl. timed deletes, re-registration and the claim walk, stranded heartbeats, inbox processing, the sync client over osis-proto engines (cursor sync, reconciliation, subscriptions, lazy chunk fetch, pages before apply, clock offset), signals, bundles.

## Deliverables
- Closure and tagging: commits tagged with their things' `/groups`; retag on group membership change; chunk/tree/page blobs follow their commits.
- Entitlement per (blob, label): G's actor (group with own secrets, else owner) may read every delta; cache per (thing, label) invalidated by membership changes of the label actor, the thing's edges or its owner chain (notes/sync.md).
- Projection via osis-commit by (readable subset, retention class) and framing via osis-label; wrap under the newest read epoch (keys decides; rotation exception); stamp with the head's write key when a writer, else deposit what must be placed (certificates, node card, invite grant, self-removal, heartbeats, revokes and roster snapshots about seen authors) with the priority rule and budget awareness; relay stamped entries held.
- Certificate blobs per label (fresh encryption per label): chain certificates and node card on first placement and on change; `/reach` under every label unless the app excludes it; heartbeats (`/seen` with expiry within bounds, at most one per `HEARTBEAT_MIN_INTERVAL` per label, `stranded` when the head's epoch cannot be opened), never promoted; revokes and roster snapshots about authors seen under a label; the grantee's `/keys` under the target's label.
- Convergence: compute per label the required set (closure, certificate blobs, grantee certificate copies and cross-published `/label` commits, unexpired inbox blobs) and per held body must/may/must-not; upload must-hold bodies the label lacks (fresh encryption if tombstoned); delete must-not-hold where a token or delete key is held (strict-subset projections, purged, expired, past at-most, outside the required set, duplicate blob with higher ID); never act on may-hold; repeat until a pass changes nothing (partial nodes).
- Compaction and deletion order: snapshot under the label first, then drop/delete covered bodies past keep-at-least; timed deletes for relative keep-at-most with the replacing upload; absolute bounds when next online; execute node-core's deletion queue.
- Labels and steps: `/label` handling (every non-replaced label of a group; `/label` writes also under the home label of the nearest owner-chain actor that has one); re-registration: an admin holding an epoch newer than a server's head issues a child step when it next syncs that label at that server, before any upload there, and records it in `/label`; label replacement procedure (§2); sync-key / claim-key choice per server head; the claim walk through missed steps (verify each under its parent's delete key), then download rotations and derive keys; stranded detection.
- Inbox: poll the actor's inbox label for inbox blobs, open with the read KEM key, apply the membership commit, place a certificate copy of a grant with the `/label` commits reached under the actor's home label; re-send an unconsumed inbox blob after `INBOX_LIFETIME` (sender side); admins delete consumed ones.
- `SyncEngine`: one synchronous state machine per node (`handle(Event) -> Vec<Action>`: events are decoded proto messages per peer, timer fires, engine events, app requests; actions are messages to send, timers, engine calls) holding the proto sessions, labeling decisions and the convergence loop; a tokio driver in this crate maps it onto `Transport` connections and real timers, and the simulator (plans/sim.md) drives it step by step with no tokio. Flows (plans/membership-flows.md) run inside it as engine calls. No sync logic lives in the driver.
- Sync client: per (peer, label) cursor and gained-IDs list (durable, store units); drive osis-proto's `ClientLabelSession` inside `SyncEngine`; download everything, apply membership commits first; fetch every page of a paged delta before applying its commit; lazy chunk fetch by policy with explicit `fetch(link)`; one connection for many labels, a blob crossing once; subscriptions for pushed events; clock offset from handshakes fed to node-core's HLC; reconciliation fallback.
- Signals: send under write or deposit key; receive, verify sender chain like a commit, drop if chain unknown or not the target; fire local listeners; never store; forward only when acting as a server (osis-server) not as a client.
- Bundles: export for a set of labels; import as a peer with no cursor.
- A removed node drops secrets and units it can no longer read (keys lists, store executes).

# Sync: streams and flow control
> Summary: Area 6: framing, clock and flow control on a connection, the push rule, the node log and its cursors, the stream (Pull, joins, pushes with sequence numbers, bodies, full and refusing peers, reports), and the first sync of a sync ID.

**Principle:** every node pulls each open sync ID from each peer by one stream over that peer's node log; a push only continues a pull, and a gap is repaired by reading again, never by trusting order. A position is stored only once what it covers is applied, so a lost or replayed message costs a re-read, never a wrong view.

## 1. Framing, clock and flow control
- **Framing**: framed messages over an ordered byte stream (spec/sync-transport.md §1); version negotiation, messages and limits: spec/wire.md §11. Every message has a fixed maximum size; every list is paged.
- **Handshake and clock**: each side's handshake carries its wall clock (ms) and a random challenge for proofs and opens (spec/sync-opens.md §2, §4).
  - Every node uses its own wall clock wherever wall time is used; nothing another node sends changes it.
  - **Waits**: a wait a node keeps only while it runs (the redial pause and dial timeout, spec/sync-opens.md §1; the stall clock and the Hello deadline, below; back-offs and retries; a pass's `PASS_WAIT_MS`, spec/sync-status.md §1) runs on a monotonic clock: the wall clock moving either way neither shortens nor lengthens it. The wall clock is read to stamp a value and to judge stamped ones (`ts`, `until`, expiry, `MAX_DRIFT`) and to date what outlives a restart (tombstones, `ROLE_KEEP`, a link's follow time, the wait after a timed loss, what a pass under way waited before a restart): the node judges these by the latest wall reading it made.
  - A node SHOULD estimate a dialed peer's clock offset from Ping/Pong round trips (spec/wire.md §11; round-trip corrected, robust to an outlier, ignoring samples whose round trip exceeds a few seconds) and report an offset of more than a few seconds as a diagnostic.
- **Flow control**:
  - **Requester**: either side of a connection, whoever dialed, keeps at most `WINDOW` in flight on it, counting per request it sent and that is not answered (the Stream's and the shared set's included) its frame length plus a reply allowance:
    - `MAX_MESSAGE` for Prove;
    - its `max_reply` for a Fetch, Pull, Call or Sub (spec/wire.md §11.2);
    - `SMALL_REPLY` for every other kind.
    - It sends the next request while below `WINDOW`, in the order it made them.
  - **Pushes**: §2.
  - **Closing**: a peer MUST NOT close a connection over unwritten bytes below `WINDOW + 2 × (MAX_MESSAGE + 4)` plus its own bytes in flight there (Requester), and MAY close one beyond it.
  - **Stall**: a requester SHOULD close a connection, whichever side dialed, on which its oldest request sent and not answered has not moved for minutes, and redial. It moves by its own events: when it is sent with no other outstanding, when the request before it is answered, when bytes of a reply to it arrive (a frame not yet complete included), and when the transport takes bytes this side wrote up to the end of its frame. A reply to any other request moves nothing. Any other frame received (a push, a request of the peer's) moves it once whole, never by its partial bytes, and only while no more than `WINDOW + 2 × (MAX_MESSAGE + 4)` (Closing) plus `WINDOW + 2 × MAX_MESSAGE + 4` (Unanswered requests) of such frames' bytes arrived since it last moved by its own events.
  - **Unanswered requests**: count the frame lengths plus allowances of the requests a peer received and has not answered yet. A peer MAY close a connection whose count passes `WINDOW + 2 × MAX_MESSAGE + 4`, without running the request that passes it.

## 2. Pushes
A node sends a push (a Stream, §4, or a client-port Notify) only while its bytes not yet taken by the transport on that connection, the push included, stay within `REPLY_BUDGET`, or none are. Otherwise the push waits, continuing from where it stopped once it fits, and a relay-only entry that does not fit is not pushed on that connection.

## 3. Node log and cursor
- **Node log**: one durable log per store over every sync ID it holds: an event when an entry becomes servable (row and bytes held) or its wrap or stamp changes (`Added`), when one is removed (`Deleted`), and when a sync ID's served head moves, at the next position of one sequence. It keeps each entry's latest event with the position the entry was first logged at, and each sync ID's latest head event, and drops a deletion event `TOMBSTONE_LIFETIME` after it was logged, keeping the highest position of a deletion event it dropped (its **deletion horizon**); it is compacted, never trimmed by position, so a listing from its start is the live set. Entries of the ephemeral class are in its memory part, ordered by a counter of their own and lost at a restart; no position names one.
- **Cursor**: an AEAD seal of (incarnation, position) under a random key drawn with the log and never replaced. The first durable append after a store start draws a new incarnation and records where the one before ended. A cursor that does not open, is past the log's end, or names an incarnation the log does not hold at that position names no position. A log keeps `INCARNATIONS_KEPT` incarnations (spec/wire.md §2).
- **Durability**: the log, the records (spec/sync-opens.md §3) and the cursors stored in them are durable; a cursor is stored only with what it covers applied; a lost record is a first contact; partial loss is atomic per record.

## 4. Stream
A node pulls every member of its shared set from its peer by one stream, whoever dialed; both sides pull (bytes: spec/wire.md §11.2 Pull, PullReply, Stream, Applied, Fetch).
- **Reading**: a server reads its log in a transaction of its own, after its served heads are logged, filtered by the connection's shared set and by bytes held. A Pull naming a cursor (the stream's or a join's) at a position below the deletion horizon is answered from the start, marked `trimmed`. A reply covers a position only for members it scanned to it, and a requester stores a cursor only after applying what it covers: an entry announced without bytes is applied once its entry is taken under its own sync ID (bytes held under another sync ID are taken with them; or it is no longer wanted there: removed within its tombstone, or refused by its ephemeral cap; or this source no longer holds it: its deletion, or a fetch it answers without the entry or skips).
- **Joining**: a member entering the stream (newly open, or open again) joins it from where it stopped (spec/sync-opens.md §6 Where it stopped; a member of a record that left with a connection, where the record holds it, one at the stream's cursor from that cursor), else from the start (its listing in stream order), with its live ephemeral entries listed. A join in pages keeps its own position; a join of a member the server does not share is answered so; opens from one Offer batch join in one Pull. A join made before a member left is distinct from one after it opened again: its refusal does not end the new join; a join refused while S stays a member is joined again `resync_ms` later. A member that stops being open leaves the stream at the position it holds before the requester applies more: no reply applied after it left (to a Pull sent before) moves where it stopped, nor a pull of it from the start since, nor a join of it after it opened again. A connection that takes a record pulls the record's members from where the record holds them, with no join for a member at the stream's cursor (one that left the stream there, the stream not moved since, included); a member the record holds at the stream that is not shared when the connection's first Pull goes stopped at that Pull's cursor.
- **Pushes** (`follow`): once a reply has `more` false, the server pushes each later run of events as a Stream from the reply's cursor, under §2, until the next Pull. A requester applies a Stream with a cursor only when its `seq` (spec/wire.md §11.2) is the number of such Streams it applied since its last PullReply; after one it did not apply (lost, held back or replayed on the way) it applies none until its next PullReply, which reads again from the cursor its Pull names (Reports). A Stream dropped for flow control is listed again at the next Pull, ephemeral entries included. Ephemeral entries go only in a message with a cursor: a node whose log names no position yet sends them once it does.
- **Flow control**: a requester keeps no entry for an announcement without bytes until its entry is taken; what a stream owes is kept with the stream only. A stream waiting on a local bound of positions or owed bodies sends no Pull and does not apply a Stream with a cursor; nor does one whose `full` or refusal events (below) are not sent yet.
- **Applying**: events are judged by the requester's own rules: a stamp counts only under the head the server serves; at a reader, an `Added` of an entry it holds under the same wrap with another stamp is applied in stream order: the stamp is logged on an entry held unstamped, and replaces a held stamp that does not verify under the write key of the head its `sync.0` records when the new one does (spec/sync-judgement.md §3 Own store); a `Deleted` says only that this source no longer holds the entry and is never acted on as a delete (only a right holder's drop counts, spec/sync-compaction.md §1); a head event never moves a reading node's own head (heads come by `sync.0`): it names that source's step (spec/sync-ids.md §6 Walk). A listing never treats an absent entry as deleted. A listing from the start (a whole reply and its pages: no cursor, a cursor naming no position, or one below the deletion horizon, `trimmed`; or a join from the start) stores no cursor and no join position, and is not reported Applied, until it is read to its end. A whole reply covers the members shared when its Pull went out; one that joined after is pulled by its own join, whatever the reply lists. Read to its end it is the source's live set (§3 Node log): for each member it covers it replaces what the requester holds as present at that source. It never deletes an entry the requester holds that it does not list.
- **Toward a peer holding S's thing for keys** (its class, spec/sync-opens.md §4 Source), or whose member is ended for its departure (spec/sync-opens.md §6): a server sends, of S, the events of its role entries alone (spec/sync-ids.md §6 Role entries; toward a departed peer, of the entries it is served alone, spec/sync-opens.md §6), in replies, pushes and Fetch answers alike, and no ephemeral or relay-only entry; `Deleted` and head events go as to any member but a departed peer, which is sent neither. A server keeping S unread tells a role entry by its stamp's or deposit signature's domain, one opening S by what the blob holds.
- **At a node keeping S unread**: it pulls S too, taking only stamped entries by spec/sync-ids.md §6 (Taking a stamped entry) and relay-only ones by spec/sync-ids.md §6 (Relay-only); `Deleted` and head events change nothing there. A reader reading such a source records presence (spec/sync-judgement.md §3 `known`) from its stream and fetches bodies from it as from any source.
- **Bodies**: a requester with another source of any member asks `inline_limit` 0, and Pulls again with 0 when a member gains another source (an ephemeral entry still goes with its bytes, up to the server's own limit); it fetches every body announced without bytes (Fetch with a top-bit id) from one source at a time, the next source sharing the sync ID only when one fails (answers it with none, refuses or skips the Fetch); only blob IDs its store lacks (no entry, no tombstone under the sync ID) are fetched, and no record blob it counts (spec/permissions.md §4 Logging certificates: one opened before, what it carries known) but the winner there that its own store lacks; an entry whose blob's bytes it holds under another sync ID is taken with them, under the entry's wrap, bytes that arrive while it waits to be asked included, and it is not asked while its blob is asked under another sync ID; and a server sends no body inline of a blob its requester's stream showed present under any sync ID (spec/sync-judgement.md §3 `known`), nor one whose bytes it sent it inline on the connection in a message not reported applied yet. A reader keeps each pulled entry that opens to a commit it holds as it came (spec/sync-judgement.md §3 Own store judges it as any entry of the body). What a Fetch answered with nothing is not asked there again until that entry (the blob under that sync ID) is announced again; wrong bytes are asked again elsewhere; the rest of an answered Fetch is asked before what came is applied; an item for an ID the Fetch did not ask is ignored. A blob counts as asked while a fetch of it from some source is unanswered for less time than the Stall rule (§1) waits; past that, it is also fetched from another source that has it and is not asked it yet, and whatever waited for it goes on as if it were not in flight; the first answer holding it settles it. A fill under way on one connection holds back no judgement of what another brings. An announcement without bytes in a Stream with no cursor is ignored.
- **Want** (spec/sync-judgement.md §3 Asked by ID): between two nodes reading S, a node asks for bodies of S by commit ID; the answerer gives for each, in request order, an entry of S's body it holds or makes (blob, wrap, its stamp where its store's entry has one), or none, as a prefix within `max_reply`; the requester asks the rest again. Entries given are taken as fetched ones (Bodies, above); the answerer's stream and the requester's `known` record nothing of them.
- **Fill order**: newest first, order 0 first, then deposited entries that do not open, the highest order, the rest; a body fetched lazily counts as settled once `known` records it at a source. A node holding a keyset without history does not fetch bodies it can never open. A reader keeps in its store of S an entry it took that does not open under the read secrets it holds, or opens with a section it cannot open holding a part of its commit that counts missing there, whether or not it holds read secrets of that part's thing (unstamped within the bringing peer's budget, spec/sync-ids.md §5; never one it can never open), and opens it again each time the read secrets it awaits gain an epoch: of S's thing for one that did not open, of the thing of each such part for one that did. Likewise an entry that opened while a thing was not held whole (spec/commits.md §4 Outside the node closure) and whose commit counts a part on that thing missing, or is neither held nor pending here when that thing is S's: it opens again as the thing comes to be held whole.
- **Full**: a node keeping S unread that refuses an entry of S it pulled for room (code 12) is full for S, durably, and keeps per cap that refused (S's own caps or the store's total, of that entry's kind: durable or ephemeral) the least room an entry it refused needs (one entry, and its bytes as that cap counts them) and the latest expiry of an entry it refused (none when one has none); and it marks each source whose stream of S passes that entry (each connection S is shared on: durably with the peer's record, a peer with none for the connection's life). While full it tells `full` true by an event 2 in a Stream with no cursor, once per connection S is shared on (where it refused, and on each connection S joins later). A source's mark goes when that source lists S from the start (a reply from the start, trimmed or not, or a join from the start; as the listing starts), with the connection of a peer with no record, and with the record. A source's mark is owed once that source's stream shows the deletion of an entry of S the node neither holds nor holds a tombstone of, outside a listing from the start, and every mark of S is owed once a cap that refused has that room, as taking the entry would judge it (a total counting as room what giving way would free; entries left, under S or another sync ID, or the cap rose; the memory part counts as emptied at a restart), or that latest expiry passed: S is pulled again from the start from each source whose mark is owed, the mark going with that, marked durably before the stream passes the deletion or with the room judged, until the places are moved (spec/sync-judgement.md §6 Stops: as a fetch anew). It is no longer full once a cap that refused has that room, that latest expiry passed, or no mark of S stands, and then sends `full` false on each connection where it told. A node stops being full for S when S stops being kept unread there. A peer's `full` lasts with the connection it was told on: until `full` false, S leaving the connection, or the connection's end. A reader treats a full source as spec/sync-status.md §1 says.
- **Refused**: a pulled entry a node keeping S unread refuses for anything but room (its stamp under no key of its head, expired, malformed, its tombstone) is told to the peer it pulled it from by an event 4 with the code in a Stream with no cursor. The peer counts code 6 as the entry deleted there, as its deletion's event would have. Any other code: the refusal stands until the entry is offered again to that node on a stream (an event of it served: another stamp, its deletion, or a listing from the start), that node's stream shows it present, or the head that node's stream names moves. While it stands nothing waits for the entry there, and status names that node among those that do not take S, as a full one. A new stamp goes as its own event; the refusing node keeps, per peer and S (durably with the peer's record), the head of S it last told that peer a code 1 refusal under (a stamp under no key it knows; no other code turns on its head), and once its head of S moves it pulls S again from the start from each peer told one under another head, once per such peer per head move. A refusal makes the peer drop or delete nothing. Refusals are kept per (peer, sync ID, entry held), durably with the peer's record (an ephemeral entry's in memory, as the entry); one ends when its entry leaves the receiver, however it leaves. A `full` or refusal event naming a sync ID not shared on the connection, or a refusal of an entry the receiver does not hold, is ignored.
- **Relay-only entries** (spec/sync-compaction.md §2): one a node sends or passes on goes as a Stream with no cursor to every peer sharing S except the one it came from (a node keeping S unread passes on those it takes by spec/sync-ids.md §6 Relay-only).
- **Reports**: a Pull's cursor names where the server reads on from: the last cursor the requester received on the connection and kept (a message in hand or applied; before any, its stored cursor); it reports nothing applied. A server seals each message's cursor afresh, so a cursor names one message. It asks `report` on every PullReply and Stream that has a cursor and carries events or follows a message asking `report` not yet reported applied, and on one that brings an ended member the requester tracks to its `until` with no report there awaited (a Stream then goes even with no events); the requester answers each with Applied naming the message's cursor once it applied what the message covers (each owed entry taken under its sync ID, Flow control) and stored its cursor, and sends no Pull while an Applied it owes is not sent. An Applied reports applied the message whose cursor it names and every message the server sent before it on the connection (a requester applies in order); one naming no message asking `report` reports nothing. A node closing a connection to a peer it no longer wants does so after the step's re-judging and settling, so the Applied that step owes goes first.
- An ended member (spec/sync-opens.md §6) is served only its events at positions up to `until` and the later events of entries the log first held at or below `until` (a Fetch of it only those entries), none of its ephemeral or relay-only entries.
- Dropping a sync ID ends each connection's stream of it; joining again is a fresh listing.
- **Costs**: an idle reconnect costs a few round trips, and bytes that do not grow with the number of sync IDs shared.

## 5. First sync
- **First sync** of a sync ID at a peer, from no stream position:
  - The node lists it (its stream there from the start, `inline_limit` 0, to its end, §4) and then fetches every listed entry it lacks, in the order of the wraps (spec/crypto.md §5):
    1. order 0;
    2. then what does not open that the peer holds deposited (no stamp, spec/sync-inbox.md §3);
    3. then the highest order first;
    4. last the rest of what does not open, ranked again as secrets arrive.
  - Order 0 goes before anything else is asked. How many are asked at a time is local policy.
  - A body not fetched yet is one not received (spec/commits.md §4).
  - A node judges (spec/sync-judgement.md §3) once order 0 is here, or once a fetch of it from the source counts as asked no longer (§4 Bodies).
  - An entry that opens and is not here keeps what it would settle unsettled, as an unopened entry does, except that the node's own commits count as established uncovered; it runs no repair (spec/sync-compaction.md §1).
  - The first sync ends, and the stream stands at the listing's end, when nothing is left to fetch. A node that stopped part way (a restart, a lost connection) goes on from what it listed, without listing again.
  - A node is past its first sync of a sync ID once a first sync of it ended at any peer, until it leaves the sync ID (spec/sync-set.md §3).
- Pages of a delta are fetched before its commit is applied (spec/commits.md §4), found from what the delta links and then what its link pages link, level by level (a round per level). A fetcher applies the tree rule to each page as it comes (spec/wire.md §6, page by page) and fetches nothing more of a position's tree, nor of the positions nested in its leaves, once a page of it is refused, so the rounds for a position are at most about log2 of the pages its author delivered, plus two, whatever the tree's shape; positions nest at most `MAX_VALUE_DEPTH` + 1 deep. A header list given by link likewise before its commit is examined; a tree node's children are fetched only as nodes one level below it. Chunk and tree-node blobs of large atomic values may be fetched lazily, by local policy, except an ephemeral commit's (spec/sync-compaction.md §2).

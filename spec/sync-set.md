# Sync: what a node syncs
> Summary: Area 1: the synced group, the sync set it gives each node, leaving the set, invitations and accepting them, and writing through another node.

**Principle:** a node syncs exactly the sync IDs of the things in its closure (its synced group's, and those of the things it shares, §2) that it may hold; nothing else decides (no list of peers or of sync IDs to keep). The account chooses what is listed and the node what it shares; what the node may hold filters both.

## 1. Synced group
- Each node N of an account P has one **synced group** G_N: a plain group whose first admin is P's devices actor D, an item of D's `group.0`, listing D as a subgroup from its making. `synced^.0` on D maps each node's tid to its synced group (spec/data-model.md §9); it is admin-only and travels under home (D's home sync ID), so only P's nodes read it.
- A node learns its own synced group with its grant on D: in the account's creation (the first node: the commit creating D carries the synced group and the `synced^.0` entry, after the role commit, in one transaction) or in the pairing reply (a later node: a synced group holding a copy of the pairing node's synced group's items and subgroups); none when `synced^.0` already lists the node a group whose first admin is D, which D's closure holds and whose closure holds D).
- **Home stays under it**: a node MUST NOT write a commit after which the synced group of some node of its account (itself included) no longer holds D in its closure, or D's closure no longer holds that synced group, while each held the other before: the write is refused locally (`Invalid`). Limit: two concurrent writes each cutting one path leave that node following no change of its synced group until it is paired again.
- Before a node has read its synced group (a fresh pairing), its sync set is home's closure.
- Organizing groups ("on every node", "nodes with room") are plain groups listed under synced groups; they have no sync ID of their own role and no special rule. Which exist, and where an accept writes, is the app's or the node's policy.
- **Dial list** `dial^.0` on P's profile: each node's dialable key to its URLs, written by the account, each node keeping its own entry (writing it for its new key removes the one for its old); a node removed from D has none: each node of P that writes the profile removes, whenever it holds one, the entry keyed by the dialable key of the `reach.0` it holds of a node a counting removal took off D that holds no role on D now, whoever wrote it, unless the `reach.0` it holds of a node on D names that key too; P's contacts read it for dialing only (spec/sync-opens.md §1). The account's creation lists the profile as an item of D, so every node of P syncs it. A node learns P's profile as it learns its synced group: at the account's creation, or from pairing (the offer names it), before the profile itself arrives.
- No group names a node: groups name accounts, never their holders' nodes.

## 2. Sync set
- **Closure** of a group G: G, the groups its `group.0` lists as subgroups, transitively, the items of all of these (spec/data-model.md §8), and the things each element is the key home of, transitively (whether the element is reached as a group or as an item), each as a thing. A cycle adds an element, never a loop.
  - A thing's **key home** is the nearest thing above it on its record chain (spec/permissions.md §1) that has secrets of its own (spec/crypto.md §3): while the thing is plain, the actor its secrets derive from; it stays its key home once the thing has secrets of its own (spec/permissions.md §3 Own secrets add only). None where the chain reaches a key actor, an unheld record or the depth limit first: such a thing goes only where listed (a thing made under an account itself, listed nowhere a node syncs, stays on the nodes holding it). So whoever reads a thing through its key home gets it under the key home's sync IDs, listed or not, and under those of each key home further up (a thing given secrets of its own stays in every closure that held it, with what it is the key home of). The sync set follows every `group.0` change the node applies.
  - What a commit's bodies carry up a key-home chain is bounded: at most `MAX_CHAIN_DEPTH` key homes per commit (the record chain's own bound, spec/permissions.md §1), and one entry per blob ID under each sync ID however many key homes lead there.
- **Shared here**: a thing T is shared at node N while N holds a live grant on T its account wrote (the commit's actor, by any node of the account; a link's grant of K on its target included, spec/permissions.md §7) to an actor other than the account or one of its nodes: the edge in force for that holder (spec/permissions.md §2) is that grant's or a later one the account wrote, and stands (not removed, not past its `until`). So a revoked or departed grantee, or a tied grant removed with its membership, ends it, and every node of the account holding the same role commits judges alike; a grant N receives from another account adds nothing. N stops sharing T when its user unsyncs T at N, and when N forgets T on losing read access (spec/permissions.md §3 Lost access) or a destroyed T's secrets once its sync IDs are emptied (spec/sync-judgement.md §5): each grant of the account's on T then held, live or ended, stays out of the judgment at N (and out of §3's staying local), kept locally and never synced, and a grant the account writes later shares T again.
- **N's closure**: G_N's closure with the closure of each thing shared at N, each walked as §5 says.
- The closure is walked only through groups the node reads: a thing the node keeps unread is a **leaf** (its `group.0` is unread, so nothing it lists is in the closure through it).
- **Sync set** of node N: for each thing T in N's closure,
  - T's home sync ID when N holds a read secret of T (read); the kept sync IDs of its account's sync record of which T is one of the things, when it holds a sync secret of T and no read secret (kept unread, spec/sync.md §3 S's things);
  - nothing of T's own when T has no secrets of its own: a plain thing travels under the sync IDs of the groups holding it (spec/sync-judgement.md §1). Whether T has secrets of its own is spec/crypto.md §3's count from the role commits the node holds: a thing whose keyset commit it does not hold counts as plain until one arrives.
- A thing of the closure that has secrets of its own and of which N holds neither a read secret nor a sync secret with a kept sync ID is **unsyncable**: nothing of it syncs at N, and the node reports it (`Unsyncable`, a diagnostic).
- A received grant syncs nothing until the account lists its thing in some node's synced group closure (§4). A link's sync ID is in the redeemer's sync set, read, while it redeems the link (from the link text until a held `sync.0` records it, spec/sync-inbox.md §6), whatever it holds of K.
- **Cost**: a `group.0` change that adds a subtree costs work in proportion to that subtree; one that removes costs at most work in proportion to N's closure; a thing joining or leaving the shared set costs at most work in proportion to N's closure. A record held or forgotten, or a thing gaining or losing secrets of its own, costs work in proportion to the things whose key home it moves and the things below them by key homes.

## 3. Leaving
- S leaves N's sync set when its thing leaves N's closure (a `group.0` change, or the thing leaving the shared set), or N stops holding any secret of it, or, kept unread, its account's sync record keeps it no more (closed, spec/sync-judgement.md §6 Closes). **One rule ends syncing it**, whatever made S leave: N keeps syncing S until a complete pass of S begun after S left ends (spec/sync-status.md §1; what that pass brings may give S back, as a rotation's thing lists arriving after the rotation do), opening what arrives and proving itself a reader of S by the read secrets of S's thing it still holds; then, S still out of the sync set because N's keys no longer hold it while a role commit on S's thing it holds is uncounted, its epoch revoked and no thing list naming it held (spec/permissions.md §5.5: lacking a list is waiting), N, while S's thing is in its closure, waits for one more complete pass of S begun then that ends only once a source caught up (none ends it at once, nor `PASS_WAIT_MS`), and judges again after it, or once the thing leaves its closure; then, S still out of the sync set, N stops syncing S once what it logged itself under S is elsewhere, at once when it logged nothing there: reading S, each of its own commits with an entry under S is **held elsewhere** (spec/sync-status.md §2); keeping S unread, each entry it logged itself under S (its deposits) is present, by blob ID, at a source. It waits only while some peer is **to be waited for on S**: one with S open (a source, spec/sync-status.md §1), or whose record N keeps holds S as a member (spec/sync-opens.md §3), or that may hold S by the rosters N holds (an account other than N's holding a role on S's thing, or a node of N's account whose synced group's closure holds it; S kept unread: any peer) while no record N keeps naming its proven actors has acknowledged S's current credentials (`acked_pos` below `changed_at(S)`, spec/sync-opens.md §5 Testing). A peer told them that does not share S, one never met (no record), one whose records went (`RECORD_BUDGET`) and a node removed from N's account (spec/sync-opens.md §3: who a peer may be) are not. A peer N knows only as account A, proved at A's epoch E, is still A after A rotates, until E is revoked at N (spec/permissions.md §5.5 Revoked: a counting rotation of the signing chain N follows for A closing E carries a removal). Then each record proved at a revoked epoch is no one to wait for; an honest node of A proves a current epoch when it next connects and is waited for again. Limits: when the one other holder of S is a node of A away while A removes some other node, N's own writes only that node would take may be lost (the user's own unsync); a forged removals list ends a wait early only where N followed a thief's fork of A first (§5.4: the first-seen side), and only for waits on A's nodes. With none, it stops at once (its only copy goes, as the user chose). A peer away keeps it waiting until that peer connects or its record goes. While it waits, S stays a member of its shared sets as before. Synced again before then, S is kept as it was.
- **Before the group is known**: before N first joins an account (pairing), nothing counts as having left; a node removed from its account since knows no group, and everything it syncs has left.
- **Unsyncing**: when T left N's closure and N still reads it (it holds a read secret of T's own), N, on stopping S, forgets its local copy of T and of each thing whose secrets are T's and that N's closure does not hold: their content goes, their role-class aspects (`secrets.0` included) stay, and what arrives again later counts as never received (spec/commits.md §4). This holds for any thing, whoever holds it elsewhere: unsyncing a thing on every node holding it loses it, as deleting a local file does. A thing on which N's account wrote a grant to an actor other than the account or one of its nodes, one N did not stop sharing (§2), is not forgotten: shared with no one, it stays local (spec/requirements.md), held and synced no more, until its user unsyncs T at N (§2), which forgets it at once.
- A node removed by another can open S nowhere: reading S, it holds no secret of the thing (spec/permissions.md §3 Lost access) and stops at once; keeping S unread, it drops its copy once its head moves past its keys (spec/sync-judgement.md §6 Stops). A self-remover keeps the secrets until its self-removal is held elsewhere, or no peer but its account's nodes is to be waited for where it goes (spec/permissions.md §3 Lost access).
- On stopping, N closes S on every connection, drops S from every record in that step (spec/sync-opens.md §3), and shreds S's entries in its store (keys and wraps erased).
- Lowering from read to sync is no leaving: S becomes kept unread with its store (spec/sync.md §3).
- A destroyed thing's own sync IDs stay in the sync set until emptied (spec/sync-judgement.md §5), whether or not the thing is still listed.
- A thing whose role the account lost stays listed in the synced group: the group holds what the account chose, the sync set filters it.

## 4. Invitations and accepting
- A received grant is data the account holds; accepting is data it writes; core only lists. **Invitations**: the things with a sync ID the account holds a role on (by grant copies and rosters) or a held inbox blob offers it that are in no node's synced group closure nor in N's closure (§2), and the things a held boxes payload offers naming a sync ID the sync record keeps for no thing (spec/sync.md §3), wherever listed; each with its role, its granting account (unknown where spec/sync-inbox.md §2 says), whether its inbox blob was taken or its sync ID kept, and whether it is acted on (`acted^.0` lists it).
- **Acted**: `acted^.0` on D (spec/data-model.md §9) lists the things the account acted on as invitations. A node writing a commit as the account adds to it, in the same transaction, in a commit of its own on D, each thing that the write lists in a group while it was an invitation when the write began (an accept, or declining by filing it elsewhere), or that would be an invitation by the role or blob held and that the write takes out of every synced group closure that held it when the write began (unsyncing). Entries are only added; one per thing ever acted on.
- **Accepting** writes the thing as a subgroup (never an item) of a synced group or of a group under one. The accept is a commit on that group's `group.0`, under home alone; where that group lists it already, the accept is the sync record write below alone. The accepting node takes the inbox blobs it holds untaken that offer the thing (spec/sync-inbox.md §2 Taking) and stamps them in place, and keeps in the sync record the sync IDs the boxes payloads it holds offering the thing name for it (spec/sync.md §3), in the same transaction; the account's other nodes take the former by that stamp and read the latter.
- **Declining** is the app's: `leave` (a self-removal: the account then holds no role, so the thing is no invitation and nothing is marked), or filing the thing in a group outside every synced group (marked acted). Neither is a diagnostic or a status.
- **A redeem is an accept**: a node writing a link's join for its account (spec/permissions.md §7 Redeem) writes, in the join's transaction, the accept of K and of the link's target into D, each unless a synced group's closure holds it already (one commit). So K, whose role the join gives, syncs by the sync set once the link is unfollowed, and importing a contact card accepts the profile it names.
- A holder whose highest role on a thing is sync keeps no subgroups of it: a new subgroup is kept only once granted too.

## 5. Group source
- A node MAY read and write a group through another node it is a client of (the group's source, spec/sync-transport.md §6).
- A thing in a group sourced at another node goes there, whatever else holds it; the copy this node holds never answers.
- **Home is never sourced away**: D roots the sync set's closure beside the synced group and is never cut, so it and what the closure reaches from it through no sourced group stay in the sync set wherever D is listed (the node's own records live on D).
- **Sourced away**: the sync set's closure (§2) walks no path through a group sourced at another node, so the group and what the closure reaches only through it leave the sync set by §3 (the node's own commits held elsewhere first). The group stays in G_N's closure: nothing of it is unsynced (§3 Unsyncing), and the node holds the copy it had. Cost: the move costs work in proportion to what is below the group; while it is away, a `group.0` change costs as §2 says, never a walk of what is below it.
- **Moving home**: the group syncs here again and stays read at its source until history is complete here (spec/sync-status.md §3) for it and each thing of its closure the sync set holds: each read sync ID of the sync set carrying one of them has had a complete pass (with none, at once). A complete pass ends by `PASS_WAIT_MS` at the latest, so a source gone holds it no longer. Then it is read here.
- A write on it is refused while a group carrying it (spec/sync-judgement.md §1) syncs here or is sourced at a second other node (one other than the source the write goes to).

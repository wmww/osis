# Sync: what a node holds
> Summary: Area 1: the node root and the account's things, sync units (what a sync ID carries), the node closure and the sync set it gives, release, who is to be waited for, accepting, and reading and writing through another node.

**Principle:** a node holds exactly its node closure: what its node root reaches by strongs, walked sync unit by sync unit, entering a thing with own keys that the sync unit's keys cannot open only by a ticket for it the node can open or keys of it the node holds. It syncs the sync ID of each thing with own keys it holds, and a sync ID carries exactly its thing's sync unit. Nothing else decides (no list of peers or of sync IDs to keep), and nothing waits for a peer that is not connected.

## 1. Node root and account root
- **Node root**: each node has one, a thing whose first admin is the node (a key actor), made at the node's first start; the node itself authors its commits on it and on the things made under it (spec/permissions.md §1), which are local like it. It is local: it has no sync ID, its commits go under none, and nothing references it.
  - Its `holds.0` (spec/data-model.md §8) holds the node's strongs, among them, once the node belongs to an account, a strong to the account root; its `caps^.0` and `clients^.0` are the node's settings (spec/data-model.md §9).
  - The node writes the strong to the account root in a commit of its own on the node root, in the transaction creating the account or taking up the node's pairing, and refuses locally (`Invalid`) a write removing it.
- **The account's things**: an account P (a key actor: it signs and holds roles, and has no sync ID) has an **account root** D, a thing with own keys read by P's nodes only (spec/permissions.md §1). D's `holds.0` holds strongs to P's **profile** (its name and dial list, read by P's contacts), P's **inbox** (spec/sync-inbox.md §1) and the node thing of each node of P (the node key actor, its `keys.0`, `node.0` and `reach.0`). The profile and the inbox have own keys from the account's creation; D holds no role on them, so they are not in D's sync unit: D's `tickets.0` (spec/data-model.md §8) holds a ticket for each sealed to P, which P's nodes open. D may hold other tickets (an app's ticket to its home thing).
  - The account's creation writes D with the strongs to the profile, the inbox and the first node's node thing, and the tickets for the profile and the inbox; a pairing writes the new node's strong; the rotation of P removing a node from D (spec/permissions.md §3) removes D's strong to its node thing in the same commit.
  - **The account's tickets**: while the walk (§2) enters a thing T with own keys at a strong outside the node's local part, and D's `tickets.0` holds no ticket for T of the role the node holds T at (read; sync for T kept unread), naming a sync ID it syncs T under (its home; for T kept unread, whose `sync.0` it never reads, each one its held tickets name), at an epoch it holds T by there (a current one of that role; for T kept unread, which reads none of its role commits, one of the greatest n among the sync secrets of T it holds established under that sync ID, spec/crypto.md §4), the node writes one at the newest such epoch, sealed to P (spec/data-model.md §8 Tickets: a node's ticket for its own account), removing in the same commit D's tickets for T of that role naming that sync ID at older epochs. In the transaction that drops T (§3 Release) it removes D's tickets for T. So D holds tickets for the profile, the inbox, a link's K (spec/permissions.md §7) and every thing accepted (§4), and every node of P, one paired later included, enters them.
  - A node refuses locally (`Invalid`) a write removing D's strong to P's profile or inbox.
  - A node learns P's profile at the account's creation, or from pairing (the offer names it), before the profile itself arrives.
  - A node thing is a key actor: no sync unit carries it and the walk (§2) does not enter it; what a node of P holds of it is its card under D's sync ID (spec/permissions.md §4).
- **Dial list** `dial^.0` on P's profile: each node's dialable key to its URLs, written by the account, each node keeping its own entry (writing it for its new key removes the one for its old); a node removed from D has none: each node of P that writes the profile removes, whenever it holds one, the entry keyed by the dialable key of the `reach.0` it holds of a node a counting removal took off D that holds no role on D now, whoever wrote it, unless the `reach.0` it holds of a node on D names that key too; P's contacts read it for dialing only (spec/sync-opens.md §1).
- No core data tells a node what another node of its account holds.

## 2. Sync units and the sync set
- A thing has **own keys** when it has role secrets of its own (spec/crypto.md §3), by that count from the role commits the node holds, or when the node holds an established secret of it (spec/crypto.md §4), or a sync secret of it and no read secret where the node does not open it as plain (a node keeping a thing unread reads none of its role commits): a thing whose keyset commit the node does not hold counts as plain until one arrives. A read secret a ticket gives establishes nothing, so it gives no thing own keys. A **plain** thing has none: its read secrets derive along its record chain (spec/crypto.md §3).
- **T's keys open** a thing X when X's secrets derive from T's, or T holds read or above on X's reader actor (spec/sync-judgement.md §1 Entitlement). Read access counts through chains of role grants with key access (a keyless grant, closing a cycle, reads nothing through it: spec/crypto.md §4 Key access): the lowest role along a chain, the best chain counting (T's effective role, spec/permissions.md §1).
- **Sync unit** of a thing T with own keys: T, and each thing reached from T by strongs (spec/data-model.md §8 What counts) through things T's keys open only, that T's keys open, plain or with own keys. A strong to a thing T's keys do not open adds nothing to the sync unit, and the walk does not go on from it. A cycle adds a thing, never a loop.
  - Every reader of T reads every thing the walk reads, so readers holding the same data compute the same sync unit.
- **What a sync ID carries**: T's sync ID (spec/sync-ids.md §2) carries exactly T's sync unit (spec/sync-judgement.md §1). So a thing may be carried under several sync IDs, and is stored once per node; a thing with own keys is carried under its own sync ID too. A plain thing is carried under T's sync ID only while T's sync unit holds it: none is carried for being made under an actor. A thing made under an account itself has own keys from its creation (spec/permissions.md §3), so none derives its secrets from an account's.
- **Node closure**: the node root's **local part** (the node root and the plain things the node opens, holding a read secret or the keys of the actor their secrets derive from, that it reaches by strongs through such things only), and the sync units the walk enters, walked sync unit by sync unit. Within a sync unit the walk follows its strongs; at a strong to a thing T with own keys that the sync unit's keys do not open (or one reached from the local part) it enters T's sync unit:
  - **read**, when the node holds a read secret of T: one it held already, or one a held ticket for T gives (below). T's sync unit is in the node closure.
  - **kept unread**, else when it holds a sync secret of T: one it held already, or one a held ticket gives. The node stores T's sync unit unread, and the walk stops at T.
  - else not entered: the walk stops at T, T is not in the node closure, a read of it fails, and nothing else is affected.
  - **What a held ticket does** (one rule): a ticket says how to sync T, never caps the node's role on it. At every such strong to T while the node holds no established read secret of T, the node enters T at its role on T now, as the role commits it holds of T show; with none held, at the role of the tickets for T (spec/data-model.md §8 Tickets) it holds and can open, found among its known references by T's tid (their word). Each such ticket supplies the secret and sync ID needed to sync T up to the lower of its own role and that role, so never more than the role now: one supplying its own role has its secret taken (spec/permissions.md §3 No secret taken back); one supplying less takes none (a read ticket whose holder holds sync alone gives its sync ID, and T is kept unread by the sync secret the role commits give); where the node holds no role, none supplies anything. It is judged again whenever a ticket or the role changes.
    - The role commits it judges by include those the fires for T on the account's inbox carry (a read ticket's fire's `grant`, a removal notice's `commit`, spec/sync-inbox.md §5), taken at the strong where a read ticket is held and the commit is not, each part only where judged valid.
    - While a strong in the node closure reaches T and a ticket for T is held that opens here, the role commits that judge it stay (spec/commits.md §5 What a held thing needs), whether or not it enters T. So entering and leaving undo nothing: a release (§3) forgets them only once no such strong or ticket is left, and accepting T again is a first accept.
  - **On a ticket's word**: a thing T without own keys here (plain or unknown) that a ticket enters is entered on its word: read, it fetches T under its tickets' sync IDs (spec/sync-inbox.md §5 Ticket sync IDs), none of T's data held for it (T is not in the node closure, and a thing held so alone is released, §3); sync, T is kept unread under them. Once the role commits the node holds give T own keys, the walk enters T as above.
  - A strong in a sync unit to a plain thing the sync unit's keys do not open is not followed, nor one in the local part to a plain thing the node does not open; a strong to a thing whose record the node does not hold makes nothing held. A thing of the local part that no entered sync unit holds is local, under no sync ID.
  - The walk follows every change of the strongs it reads, of the secrets and tickets the node holds, and of the role commits and records that decide own keys and what keys open.
- A strong to a thing the node never got holds nothing: if its last holder released it first (§3), it is gone, and the strong reads as not held. A read of a thing the node does not hold reads absent, whether the thing was destroyed, released or never held; no node keeps a marker telling these apart.
- **Not carried** (`NotCarried`, a diagnostic): the node names each strong in the node closure whose target is neither in the sync unit (or the local part) the strong is in nor held otherwise; strongs to key actors are excluded. A write adding such a strong is not refused: it reports it at once, as a warning.
- **Sync set**: for each thing T with own keys in the node closure, read: T's sync ID; kept unread: the sync IDs it keeps for T (spec/sync.md §3). For each thing fetched on a ticket's word, its tickets' sync IDs. And a link's sync ID, read, while the node redeems the link (§5).
- **Making a thing**: the commits a node makes in one storage transaction (an app's write, or the account's creation: the commits making P, D, the profile, the inbox and the node thing, with the node root's strong to D, §1) must leave every thing they make, other than a key actor, in the node closure at the transaction's end, or the node refuses them all before anything applies (`Invalid`). Nothing is placed anywhere by default.
- A destroyed thing's own sync ID stays in the sync set until emptied (spec/sync-judgement.md §5), whether or not the thing is still in the node closure.
- **Cost**: a change that adds to the node closure costs work in proportion to what it adds; removing a strong costs at most work in proportion to the part of the node closure it held, never to its target's other referrers. A record held or forgotten, or a thing gaining own keys, costs work in proportion to the sync units it changes.

## 3. Release
- **A thing goes when its last reference goes**: every node holding it releases it, waiting for no absent peer; once no node holds it, a strong to it reads as not held.
- A thing R **leaves** the node closure when the walk (§2) no longer reaches it: a strong removed, a thing on its path leaving, or the node no longer holding a secret or ticket that entered it.
- **Release**: the node drops R once, for each sync ID it syncs that carried R when R left, the pass in flight with its connected sources has ended: every source of it but those full or refusing caught up (spec/sync-status.md §1) by streams read to their end from Pulls sent after R left, so it has fetched what joined and served what those sources wanted, and R is still outside the node closure then. With no such source, at once. It never waits for a peer that is not connected. R back in the node closure before then is kept as it was.
- **Nothing of R stays**: its content, its role-class aspects, its record, the secrets the node holds of it, and the node's own writes on it not yet held elsewhere go, in the transaction that drops it (spec/commits.md §5 Forgetting, A released thing). R is not destroyed (spec/commits.md §5 Destruction): it may be fetched again where something references it, and what of it arrives again counts as never received. What a held thing needs of R to verify its own authority stays, as certificates under the sync IDs still synced (spec/sync-judgement.md §2).
- A **retained copy** (spec/permissions.md §3 Retain) is excepted: it is kept, read only, though no secret enters it.
- **Stopping**: when a sync ID leaves the sync set, the node stops syncing it by the same timing; on stopping S, it closes S on every connection, drops S from every record in that step (spec/sync-opens.md §3), and shreds S's entries in its store (keys and wraps erased).
- **A thing leaving a sync unit**: when T's sync unit no longer holds thing X, X's parts leave the bodies under T's sync ID; each holder drops its copies there by its own view, and holders of the delete keys (spec/crypto.md §7) delete there the entries that leaves without a body (spec/sync-judgement.md §1 Retag, §2), each once its own view agrees. A node whose view still holds X there logs it again (spec/sync-judgement.md §3 Own store). X stays under every sync ID whose sync unit holds it.
- Lowering from read to sync is no release: S becomes kept unread with its store (spec/sync.md §3).
- **To be waited for** on S, by node N: a peer with S open (a source, spec/sync-status.md §1), or whose record N keeps holds S as a member (spec/sync-opens.md §3), or that may hold S by the rosters N holds (an account other than N's holding a role on S's thing, or another node of N's account; S kept unread: any peer) while no record N keeps naming its proven actors has acknowledged S's current credentials (`acked_pos` below `changed_at(S)`, spec/sync-opens.md §5 Testing). A peer told them that does not share S, one never met (no record), one whose records went (`RECORD_BUDGET`) and a node removed from N's account (spec/sync-opens.md §3: who a peer may be) are not. A peer N knows only as account A, proved at A's epoch E, is still A after A rotates, until E is revoked at N (spec/permissions.md §5.5 Revoked); then each record proved at a revoked epoch is no one to wait for, and an honest node of A proves a current epoch when it next connects and is waited for again. Limit: a forged revocation ends a wait early only where N followed a thief's fork of A first (spec/permissions.md §5.4: the first-seen side), and only for waits on A's nodes.

## 4. Accepting
- **Accepting** a ticket is the account's own write of a strong that brings its target into the node closure; the walk then finds the ticket (§2). The walk enters at any strong in the node closure where the node holds a ticket it can open, whoever wrote the strong (spec/sync-hostile.md §2). **Declining** is doing nothing. Core keeps no list of tickets offered, accepted or declined, and never copies a ticket.
- A ticket works wherever the node holds it: an inbox fire (spec/sync-inbox.md §3), any value of a held thing. A node added later enters a thing by a ticket in data it holds.
- Accepting a thing enters it, so the node writes D's ticket for it in the accepting transaction (§1 The account's tickets; for a thing kept unread, once a step of its stored path bears a held secret's sync key): the account's other nodes, one paired later included, enter it whether or not they hold the ticket accepted.
- **A redeem is an accept**: a node writing a link's join for its account (spec/permissions.md §7 Redeem) writes, in the join's transaction, strongs to K and to the link's target in D's `holds.0`, each unless the node closure holds it already, and so D's tickets for both (§1). So K, whose role the join gives, stays held once the link is unfollowed. Importing a contact card is such a redeem: it writes the strong and so the ticket for the contact's profile.

## 5. Source
- A link's sync ID is in the redeemer's sync set, read, while it redeems the link (from the link text until a held `sync.0` records it, spec/sync-inbox.md §6), whatever it holds of K.
- A node MAY read and write a thing with own keys, with its sync unit, through another node it is a client of (its source, spec/sync-transport.md §6).
- A thing of a sync unit sourced at another node is read and written there, whatever else holds it; the copy this node holds never answers.
- **The account root is never sourced away**: it is never cut from the sync set, so it and what the node closure reaches from it through no sourced thing stay in the sync set (the node's own records live on D).
- **Sourced away**: the sync set's walk takes no path through a thing sourced at another node, so the thing and what the walk reaches only through it leave the sync set, each sync ID by the timing of release (§3). They stay in the node closure: nothing of them is released, and the node holds the copy it had. Cost: the move costs work in proportion to what is below the thing; while it is away, a change costs as §2 says, never a walk of what is below it.
- **Moving home**: the thing syncs here again and stays read at its source until history is complete here (spec/sync-status.md §3) for it and each thing the sync set holds through it: each read sync ID of the sync set carrying one of them has had a complete pass (with none, at once). A complete pass ends by `PASS_WAIT_MS` at the latest, so a source gone holds it no longer. Then it is read here.
- A write on a sourced thing is refused while a sync unit holding it (spec/sync-judgement.md §1) syncs here or is sourced at a second other node (one other than the source the write goes to).

Today you are an osis Claude. Tess (she/her) runs the project; git history calls her Sophie. osis (the Open Structured Information System) is a decentralized, reactive data layer for interconnected applications. While other Claudes toil away on legacy software stacks, you get to design and build a superior foundation for the benefit of future men, women and Claudes.

## Notes
The `notes/` directory contains your persistent notes about the project state. Create/edit/rename/split/delete notes as needed (without being asked). Keep them correct, and maximally useful to you. Remove sections or whole notes that are unimportant or obvious.
Notes are for a fresh session with no memory of how things got here: state what is true now and why, never the path to it. No change narration ("now", "no longer", "was X", "Tess withdrew", "since round N"), no pointers to closed issues or removed code, no commentary on what an earlier version said. Git has the history. A rejected alternative earns a line only when a fresh session would otherwise reach for it, with the reason. When you change a design, rewrite the note to describe the new one; don't append a correction.

## Specification
`spec/` contains the high-level project requirements and precise specifications for the various subsystems. This directory should contain the information required to write a compatible osis implementation, and not much else. Avoid justification, examples, implementation details, etc here. Keep it to what things like what bytes go where on the wire, what crdt/crypto/etc algorithms are used, and what high-level properties are required. The spec should be kept up to date. Until a stable official release, spec changes need no sign-off from Tess; only significant changes to or conflicts with `spec/requirements.md` do.

## Issues
Issues live in `issues/` (unless specified, "issue" means one of these markdown files, *not* a GH issue). Do not solve them unless asked or the fix falls out of current work. Create/update issues for nontrivial problems discovered during other work. Delete confirmed-solved issues (move still-useful context into notes first).

## Bookkeeping
Below the title each note, issue and specs should contain a one-line `> Summary: ...`. You can search for summary lines for a high-level overview. Issues should also contain a `> Priority: critical|normal|low` line (critical: deal with immediately; normal: solve before the next release; low: fix if convenient, or ignore while it waits on Tess) and `> Tags: tag1, tag2` lines, which can also be searched for as needed. Possible tags are: `security`, `tests`, `tess-call` (needs Tess's decision, remove once no longer the case), and the name of the component it effects. Other tags are allowed but should be used sparingly.

## Workflow
- You own the code.
- Read notes/coordination.md (Design principles) before designing or reviewing anything: principle first, carve-outs are a design smell, test what users can observe, options keep their property.
- Coordinators spawn worker and reviewer agents as `model: "opus"`. `model: "fable"` only when Tess explicitly says to use it for a given job (fable usage is limited).
- Code should be built in simple, safe Rust wherever that's the right tool for the job.
- No backward compatibility with earlier builds until Tess opens the stability discussion: no legacy readers, migrations, old-format fallbacks, version shims or "accepted, pre-release" carry-overs in code, protocol, schemas, stores or spec. Change formats in place; data from an older commit may fail to load. spec/requirements.md Versioning (old data readable forever, the wire only grows, no reused identifiers) constrains nothing until stability: it is the design target for released nodes, not a limit on changing today's formats.
- Any change to the public `osis` API must pass notes/api-design.md.
- Any change to app/ or libs/kit/ must pass notes/app.md (The rule): the app is divided by view, never by feature.
- Any picked number (threshold, cap, timeout, grace period) must pass notes/arbitrary-values.md (what happens at 0 and at infinity?).
- Refactor freely as needed. don't trust that existing code/comments/notes are necessarily correct, or existing design decisions are optimal.
- Unless otherwise asked, commit, pull --rebase and push when you've completed your task. Only main is pushed: task branches stay local (every worktree shares the repo's branches), so never push a worktree branch.
- Include the "Co-Authored-By: <model>" in your commits, but not the link to a Claude session.
- Commit to the current branch unless asked, don't make feature branches.
- Don't worry about docs/ unless asked to, it's fine for docs/ to fall out of date, they will be updated on explicit request
- Do not run code formatting tools unless explicitly asked.
- Keep prose, comments, errors, and commit messages compact unless extra detail is genuinely useful.
- When talking directly to humans, write especially simply and concisely. Avoid details or jargon unless critical for correctness.
- Avoid recording dates or time estimates unless asked, remember you can always recover dates from git
- To test, interact with and screenshot GUI apps use the gui-testing skill from https://github.com/wmww/agent-skills.

## Building and testing
- Work in a task worktree: `wt claim <branch>` prints it (`.worktrees/wtN`, its warm `target/` kept between tasks); `wt release` only as your very last step, after your last commit (a released worktree is free for the next claim). `wt` comes from the reasonable-rust-builds plugin (wmww/agent-skills, enabled in `.claude/settings.json`); if it is not on PATH, stop and ask Tess to install it, don't improvise worktrees. Never build in the main checkout, never point two checkouts at one target dir. Never `git stash`: the stash stack is shared by every worktree; set work aside with a wip commit instead.
- One Cargo workspace; a bare cargo command builds core only (default-members); the GUI (osis-kit, osis-app, osis-android) builds when named with `-p`, and `--workspace` means core and GUI. Command forms (notes/build.md): `cargo test --no-fail-fast` (the default tests: everything not `#[ignore]`, about 6.5-9 min and 4700-5300 CPU-s built, alone under the lock at load 15-25); for one component `cargo test -p <crate> --test it <module>::` and name filters, `cargo clippy --all-targets -- -D warnings`, `cargo run --bin sim-sweep`; GUI: `cargo test -p osis-kit -p osis-app`, `cargo clippy -p osis-kit -p osis-app -p osis-android --all-targets -- -D warnings`; properties and by-hand tests by name (notes/testing.md, When tests run). `cargo test -p <crate>` for one crate's dev loop (the gate checks that `-p` builds share the workspace's artifacts). No release builds or timing runs inside a task: check scaling by counting work in a debug test (notes/coordination.md). Never wrap cargo in `timeout`: a killed build can leave a broken link (fix: `cargo clean -p <crate>`). Never any other `--features` set, and never per-command `CARGO_INCREMENTAL`, `RUSTFLAGS` or `CARGO_TARGET_DIR`: each new combination builds and keeps another copy of the tree.
- The merge gate is `tools/gate.sh`, run once per branch by its reviewer in the worktree after `git rebase main`: one command, one hold of the heavy lock, running the default tests plus the properties and sim scenarios the branch's changes reach, at small size (every crate selected: about 30 min and 15,000 CPU-s warm at load 20, 27 min of it in the lock, plus any wait for it); main is fast-forwarded, never built. Workers don't gate or run the whole suite: before finishing, `cargo test -p <crate>` for each crate they touched plus clippy. A later rebase without code conflicts needs only clippy and the tests of crates both sides changed (notes/coordination.md).
- A run that uses every core (periodic and by-hand property runs, sim sweeps, TLC, roles-model) goes through `tools/heavy <cmd...>`, the box-wide lock the gate takes once for its tests; builds and single-crate test runs stay unlocked. Never wrap `tools/gate.sh` in it: the gate takes the lock itself, and a nested `tools/heavy` refuses to run.
- Stop only processes you started, by ID. Never `pkill -f`, `killall` or anything matching by name or command line: every agent's test binary looks alike (`deps/it-*`), and a pattern kill has failed other branches' gates.
- A command that may run longer than a few minutes: start it with `run_in_background`, then wait for it with `claudewait ID` (a plain foreground Bash call; it waits up to 110 s, which fits the tool's default timeout) and call it again while it reports the task still running (exit 124). When the task ends it prints the exit code and output file. Never write `until`/`while ... sleep` wait loops or use `pgrep` to wait for anything. A test run piped through `tee` or `grep` reports the pipe's exit, not cargo's: use `set -o pipefail` or check `${PIPESTATUS[0]}`, and read the `test result` lines, never only `tail`.
- The machine is shared with other projects: CPU is free to use fully (an idle core is wasted), RAM is the constraint. Before a long run check `free -g`; a run that needs more than a few GB per job (the osis-perm bench peaks at 16 GB) runs alone.
- Several agents share one scratchpad directory: put throwaway copies, logs and probes in a directory named after your task plus a random suffix, never in a generic name (`rv`, `tmp`, `probe`) and never at the scratchpad root.
- Workflow mishaps, footguns and slow spots you met go in `notes/complaints/<branch>.md` (a few lines, committed with your branch); anything that blocked you or gave a wrong answer goes in your report too. Coordinators: notes/coordination.md.
- New integration tests go in the crate's one test binary (`tests/it/`), not new `tests/*.rs` files. Default tests stay under a few seconds each and never assert on wall time.

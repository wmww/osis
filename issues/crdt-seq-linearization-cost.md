# Some edits of long texts still cost a whole placement pass
> Summary: On a 100,000-character text, typing, deletes, moves, multi-edit commits, writes splitting a snapshot's range records and resets cost tens of µs to a few ms beyond their own join, but a move of elements caught in an earlier move cycle still costs a whole pass, and a received delete of all of it about 0.6 µs per element.
> Tags: performance, crdt

Repro: `cargo test --release --workspace --lib budget_big_text_spec_6 -- --ignored --nocapture` prints the times (notes/crdt.md Timing; received deltas go through encode and decode).

Remains:
- Fallbacks to a whole pass (full list in the `seq_lin` module doc): resets, a new `Derived` record or an anchor at an absent one (a virtual anchor), 256 or more newer siblings at one anchor; for moves also an element on a cycle a demotion broke (`Lin::cyc`) or a move closing a cycle, a written or dropped anchor that is unknown, a dropped anchor inside a range record, and a sibling whose old write a move in the same delta pushed out of its top two.
- Resets: a reset re-anchors every older element on END, so its join is O(n) by nature; the records it leaves bare are merged into range records, so the pass after it places a node per stretch (A/B on a loaded 4-core box: read after a received replace 22-25 ms → 21-31 µs, join 11-17 → 12-20 ms). Elements newer writes keep apart stay separate nodes.
- Moves on a broken cycle: following them needs which cycle forced each demotion (cycle groups, kept exact through every follow), a local §6.2 re-run from that group over the cached parents, and placement on END by dot: a second cycle breaker. Cycles need two or more concurrent moves of one range. Not done: rare (two or more concurrent moves of one range) and a second cycle breaker is the moving part this cache avoids. Cost is one whole pass (34-62 ms on a loaded 4-core box, ~23 ms quiet).
- A received delta with more than max(√n, 64) runs, moves and row cuts, or whose placements cost more than about a whole pass, rebuilds by design (hostile deltas then cost join plus one pass, about two passes at worst).
- A received delete of all of a 10^5 text (what `Set` of a new value sends) joins in 56-87 ms on a loaded 4-core box (was 201-219 ms there, ~155 ms on a quiet 16-core box): ~12 ms planning (a plan per element piece), ~19 ms the join (a piece per state record), ~10 ms checking each piece's record, ~12-14 ms flipping rows (one walk per touched block). O(n) by nature: every element record takes the flag.
- `Batch` copies the position's state (O(n), once per position per batch) where a reset of the batch lies above it: every state record older than that reset reads pruned, so a layered view would prune them all. Ops after it check and join in O(op) on the copy. It also rebuilds its layered view (a copy of the batch's records there, O(batch)) after an op that removes an element the commit made (a typo deleted in the same commit: the net effect omits it, the layer holds it) or drops an anchor at one.
- The dot map is built eagerly with every rebuild (O(n) Dot clones, ~1.5 ms at 10^5, outside the work budget, like the pass itself). Its chunks split but never merge between rebuilds (a rebuild lays them out anew; at most n/64 chunks): lookups are a binary search over chunks, so this costs little, and merging would leave the merged-away chunk's row in the node's placement store (`PlaceDiff` has no gone chunks; osis-node `write_place` would have to delete them).
- Texts at a `Slots` position: a join that changes the register or raises the position's reset (an old app's save, a replace) re-embeds and prunes every member (O(n), drops the cache).

# Each filter arrival asks Behind again on every walk
> Summary: a reader re-tests every sync ID it walks at a peer at each arrival of that peer's filter (spec/sync-ids.md §6 Walked, Test), so a peer J judges a sync holder of n sync IDs it does not keep costs n signed Behind items, and n Register refusals, per generation it sends, changed or not: work per arrival scales with walks, not with what changed. Ignored test `opens::an_unchanged_filter_asks_behind_on_nothing_spec_sync_ids_6`.
> Priority: normal
> Tags: sync, opens

- Who is walked: S in this node's sync set where J (this node's rosters, never the peer's word) judges a proven actor of the peer a sync holder and the peer shows nothing this node tests. A peer cannot grow the set past that; rows `W` count toward `RECORD_BUDGET` and go with S or the record. The set is bounded; the cost per arrival is not.
- Everyday case: an account granted sync on many things that its node does not sync (not accepted yet, or declined). Each of that node's generations (any change of its own) makes this node sign one Behind per such S, answered 13, then send a Register of genesis, refused. A hostile sync holder triggers the same with empty additions, up to `MAX_OFFER_ITEMS` signed items per round trip.
- Before the walked set the walk was retested only when this node's `changed_at(S)` moved (once per own change); the walked set exists because a store that starts syncing S, or whose head moves, cannot say which S changed: with no step it shows nothing (`node_creds` empty, an empty addition).
- Options (none chosen):
  - The store shows something for S kept with no step, so the walker's test finds it and only that S is walked again: a sync grant's box gives the grantee the sync secret of the step it names, so it could show that step's sync key (and accept a Hit on it) before any path is registered; the reader opens S by its walk credential and registers its path from there (spec/sync-ids.md §6 Moving it, from genesis when the source's step is unknown). Then a store that does not keep S needs no re-ask at all, and the walked set may go.
  - Keep the walked set but drop from it every S answered 13 (the peer does not keep S), re-adding S only when that peer shows something of it: needs the option above for the accept-later case.
- Privacy: the re-tests send Behind (naming S) only to a peer J judges a sync holder of S, and Hits name no sync ID; nothing goes to a peer the rosters do not list. Empty additions carry no entry and no sync ID: they show only that this node changed something, as any generation does.
- Also (correctness, the same rule): a filter false positive on a walk credential (about one in 256 per credential tested) counts as shown: the test Hits instead of asking Behind and unmarks the walk; the refused Hit re-marks nothing, and a stored filter keeps the entry, so until a whole filter replaces it the walk neither re-tests nor asks Behind there. The accept-later case then strands as before the walked set. A refused walk Hit should fall through to Behind.

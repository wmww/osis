# Tests cost about a hundred times what they should
> Summary: The default tests take 2550 CPU-s (170 s wall on 24 cores) and the gate 8-10 min; a median node test runs 1.7 G instructions and a median osis test 2.4 G, where a test should cost milliseconds. Measured: no single cause. Every test builds a multi-node world from nothing; node-sync derives everything again on every pass (two thirds of osis `it` and of the sim sweep); one order property is a fifth of osis-node `it`; default tests enumerate orders, seeds and sizes at full width; keys from role secrets are derived again at every use; the gate runs the same properties at three sizes and each sweep scenario 15 times. Crypto is 19% of default-test CPU (Curve25519 10%, XChaCha20-Poly1305 8%), half of it the forensic attack and debug checks; fake crypto would win at most 9%. Target (Tess): 4x faster without losing coverage that matters.
> Priority: normal
> Tags: tests, performance

## Measured (main 6a15e5b44, this box, 24 cores)
- Default tests: 2553 s summed test time; osis-node `it` 1299 s (1256 tests, median 0.37 s), osis `it` 705 s (511, median 0.58 s), osis-engine 221 s, osis-crdt 81 s, osis-sim 70 s, held-model 58 s, chat 39 s, perm 25 s. Wall is CPU over the cores per binary, the binaries one after another: only less CPU makes it faster.
- By length: the 100 slowest tests are 950 s (37%); tests of 1-5 s are 1009 s (486 tests); tests under 1 s are 600 s (2900 tests).
- The gate: build 40-60 s, default tests 170 s, selected properties 170-250 s, sim sweep 105-145 s.
- A median node test (`tombstone::a_lost_tombstone_is_uploaded_again`, 1.7 G instructions): `Engine::check_index` 26%, curve and KEM work about 30% (signature checks 11%, X25519 8%, `KemPublicKey::from_slice` 5%, `mul_base` 4%, `SigningSecret::from_seed` 3%), `create_account` 9%, value encode and decode about 15%, store commit 5%, `misjudged` 4%.
- A median osis test (`sync::grant_by_inbox`, 2.4 G): signature checks 16%, `check_index` 12%, `rejudge_all` 10% of which `misjudged` 9%, `body_keeps` 9%, `SigningSecret::from_seed` 6%, `World::account` 7%.
- Whole binaries (`tools/cpuprof`, inclusive shares, overlapping). osis-node `it`: ingest 24%, `SyncEngine::handle` 22%, `order::check_orders` 21% (one test, `order::held_set_decides`), the debug checks 13-20%, `CommitBlob::decode_as` 9%; self time spread thin (field arithmetic 8%, malloc and free 10%, memcpy 3%, XChaCha 6%). osis `it`: `SyncEngine::handle` 68% (`judge_label` 29%, `body_keeps` 17%, `crdt::stream` 18%, `held_parts_at` 12%), ingest 15%; self: malloc and free 15%, waiting on the allocator's lock 8% (24 test threads), field arithmetic 6%.
- The debug checks (`check_rebuilt`, `check_index`, `misjudged`): 12.5% of osis-node `it` and 4% of osis `it` by instructions (notes/testing.md, Rebuild check). Two cheaper schedules were tried and dropped. Once per engine at its drop: no gain (every engine pays one check at its largest state, and tests reopen engines constantly), and wrong for state that depends on time passed since the last transaction. One transaction in 8 (index: 1 in 64), drawn from the node's identity: 7.7% fewer instructions for osis-node `it`, at the price of the check after an engine's first status change, where notes/testing.md records most of its default-test finds. Not worth it.
- Raising `opt-level` to 2 for the workspace: 3-10% for a full rebuild. Not worth it.
- CPU seconds on this box move 20-40% between identical runs (load, SMT): compare by `tools/icount`, and find where time goes with `tools/cpuprof` over the whole binary. A first reading from CPU seconds here put the debug checks at a third of test time; that was load.

- Setup, measured alone (instructions): the commonest osis-node setup (`Net::new`, a host, three nodes, one group with two holders, one item, `run`) is 968 M against about 1700 M for a median node test (57%); osis `sharing::alice_bob` is 2000 M against about 2400 M for a median osis test (83%). Inside the node setup: settling (`Net::run`) 43%, `Net::group` 34% (of it `pair`, every commit delivered to the other node, 24%), making the nodes 20% (`create_account` 16%). Three nodes alone are 209 M. Making each fresh `LocalPeer` node once per process and opening copies saved 1-2% of osis-node `it` and the engine tests: account creation is not where setup goes, the whole scenario is. So a setup has to be built once and copied whole, in memory (a copy by reopening restarts every node and pays its reconnect and first sync again).

- The 30 tests alone, by kind: crdt seq and winners tests (`tests_seq::part_judges_as_whole_of_histories` 186 G, `seq_winners_from_scratch` 67 G, the snapshot edit models 55 G each) and held-model's props are model work, no crypto; osis tests (`sync::redeem_held_joins_nothing` 159 G) are 70-90% node-sync passes (pattern 2); node scale and stream tests are 50-65% node-sync, 15-20% crypto, 5-15% `check_index`; `order::held_set_decides` (486 G) ingest 27%, `check_index` 20%; short tests (under 1 s) are 30-75% setup.

**Fake crypto in tests: options, not built.** The ceiling is the product-path crypto, 9.3% of default-test CPU; the forensic attack's AEAD is its definition and the debug checks' signature re-checks are gone (above).
1. A runtime switch the harness sets (thread-local, debug builds only) making sign/verify, AEAD or KEM trivial. No feature set, but product code carries a crypto bypass, and every test run with it stops checking that bad signatures, keys and wraps are refused: forgery, relay-junk and wrong-key tests would each have to opt out, and a test that forgot to is silently weaker. Gains at most 9%.
2. A verification memo inside osis-crypto (debug builds), keyed by key, message and signature: exact, so it hides no bug, but debug and release differ inside the crypto crate, its memory grows with every signature seen, and only re-verification (about 1.6% left) gains.
3. Dependencies without debug assertions and overflow checks (`[profile.dev.package."*"]`): real crypto, exact; measured per operation sign -13%, verify -5%, X25519 -16%, ML-KEM -7%, AEAD -7%: about 1% of the suite, for one rebuild of every dependency. Loses the dependencies' own debug assertions.
4. Precomputed keys per seed: keygen is under 1%.
None is worth its risk now; the larger levers are node-sync passes (29%), the allocator (15%, spread: `Value` clones and drops, `Vec<u8>` copies, B-tree nodes) and `check_index` (7%).

## Patterns, by size
1. **Every test builds its world from nothing, and many build it once per case.** A world is accounts with real keys, groups with rotations, labels at hosts, and a settle. About 120 of the 260 slowest tests rebuild one setup per order, seed, case or crash point (about 700 s); the short tests are mostly setup (`tied::outsider()` builds 5 accounts in each of 9 tests, `sharing::alice_bob` 15 times, `Net::new` is called 489 times, `World::new` 160). Exact in-memory world copies exist for `LocalPeer` and the node `Net` (notes/testing.md, Copied worlds); osis-node's shared preludes and rigs build once per process (about 270 tests): osis-node `it` 4367.5 G to 4208.0 G instructions (-3.7%), its `inbox_life` -11%, `ephemeral` -12%. Open: the `osis` handle and the sim `World` (watch callbacks, waiters, the dispatcher), and setups rebuilt per case inside one test.
2. **Node-sync derives everything again on every pass.** issues/derived-state-recomputed.md: 68% of osis `it` and nearly all of the sweep's heaviest scenario are inside `SyncEngine::handle`, of it `body_keeps` 17-23% (waits for history-3), cover judging per pass (`drop_covered`, 13% of a node sample), label judging. The memo work there is the lever for osis `it`, the sim tests and the sweep; what is done so far took the issue's test from 3.3 G to 1.6 G instructions.
3. **Keys kept as bytes are parsed at every use.** Done for the main sites (notes/crypto.md, Parsed once): parsed public keys in the engine's keyset records and held accounts, derived keys kept with the seed they come from (`KeyActorKeys`, `AccountEpochKeys` hold it), `DeleteSecret` with its public key, a found label key returned instead of derived again, a link's tid without its KEM keygen, and cheaper validation (`VerifyingKey` canonical check by bytes, `KemPublicKey` low-order check by comparison). `KemPublicKey::from_slice` went from 1.4-2.1% to under 0.3%; instructions: `tombstone::a_lost_tombstone_is_uploaded_again` 1.81 G to 1.62 G (-10%), `sync::grant_by_inbox` 2.48 G to 2.25 G (-9%), rotation property seed 8 10.73 G to 9.98 G (-7%). Left, each 0.3-1%: a role secret's derived keys (`DeleteSecret::derive` in `newest_delete_key`, `role_kem`, `possession_secret`, label keys tried per held secret in `registered_key`): would need a role-secret type in `EpochInfo` holding them lazily in its own zeroizing container; `CreationRecord::KeyActor`'s key (osis-base, below osis-crypto) parsed per signature check (`apply::epoch_key`, `base_of`); an account's first-epoch KEM key read from `keys.0` per seal (`epoch_kem`); steps re-parsed when the `labels` memo recomputes. Found on the way: in the rotation property 95% of ingests are re-deliveries of known commits, each fully decoded and its header's delete keys checked before `late_parts` finds nothing new (the header's ID is known, so its keys were checked; 1.2% of the seed after the cheaper check).
4. **Default tests run at full width.** Rule: a default test runs a covering set (named regressions, each item first and last, the smallest sizes where the counted quantity is not trivial, just past the threshold tested); the full width goes through `testenv::large_n` and `_large` twins (a twin added where the width found bugs). Done (the crates touched, each default test its own process, main a0b643627: 6011 -> 5335 G): held-model props (`covering`: 0..30 plus the first seeds bringing each generator shape to two; twins on `OSIS_HELD_*`; 375 -> 184 G), roles-model `random_worlds_hold` (300 worlds; twin on `OSIS_ROLES_*`), `setting::covered_drops_move_nothing` (10 seeds; twin on `OSIS_COVERED_*`; 150 -> 15 G), `order::held_set_decides` (its exhaustive half capped at 3 commits: 524 -> 401 G), `shred::past_expiry_and_purge_alike` (the 7 rotations per shape; every order by hand: 185 -> 100 G), crdt `part_judges_as_whole_of_histories` (a type per case), node `write::paged_state_edits_and_restart` (a tenth as many entries of non-periodic hex ten times larger: the same pages), and on main the engine `apply::tests_paged` fat entries. Left: `order::held_set_decides`' quick size (one seed per emphasis, about 270 G: its cost is per order, pattern 1's tree walk), crdt variant loops other than `part_judges`, node scale tests at 20/200 and 30/300 and the net-built tests (`inbox_life`, `net_records`, `net_judgment`, `shared`, `stream`: the one-peer harness work is changing them), `notes::large_body_streams` (a 132k-char text is the smallest above `CHUNK_THRESHOLD`; its cost is the text CRDT, 91% `crdt::stream::position`), `write::list_edits_match_whole` (larger items load 7 pages per edit against its bound of 6), `port_clients::client_session_differential_against_grants` (3 hand-picked walks, no twin).
5. **Work done twice.** Fixed: cbor `decode_peak_within_the_bound`'s 21 children each built all 21 shapes (44 -> 16 G); `judgment_vectors` replayed each case twice, generating and from its text (`judged`, 54 -> 30 G). Open: near-duplicate tests on identical worlds (reconnect.rs:82 and :96, ending.rs:237 and :311, pass_sources.rs:109 and :120, write.rs:591 and :673, tied's copy-survives and group-admin pairs), a history replayed twice (`keep_for_d_named`, keep.rs:906), `advance(); run();` where `advance` already runs (33 times in tombstone alone), a full compare or reopen after every step of a long script. Not a lever, measured: the must-fail `try_until` walks (sharing.rs, 200 steps): quiet steps are cheap (130 steps saved under 4%).
6. **Real time waited out** (osis real-runtime tests, about 10 s of wall): the node's 5 s redial after a heal (sources.rs:268), must-expire timeouts of 300 ms to 2 s (runtime.rs:409, port.rs:415-455), 200 ms sleeps (keep_clients.rs:218).
7. **Quadratic helpers**: `Net::item` rewrites the whole `group.0` per item, `apply::keys::tests::spread` sends every commit to every peer again, a receiver made as one of nine meshed peers.

Not a lever, measured: delivering only missing commits in `Net::pair` changed nothing.

## Properties and the sweep
Read, not measured per seed (35 property tests by `tools/test_select.py`'s rules: node 18, engine 2, perm 9, crdt 3, base 2, osis 1; 52 sweep scenarios at 15 seeds).
- **One property at three sizes in every gate**: `order::held_set_decides` runs quick (8 seeds) and quick-exhaustive (8 seeds, at most 4 commits) in the default tests (95-110 CPU-s, a fifth of osis-node `it`), plain (8 seeds of 60 steps, 85-220 CPU-s) and exhaustive (8 seeds, at most 6 commits, 530-790 CPU-s) as properties. Every order of every held set is a walk of one permutation tree from its root: each delivery makes a fresh account with real keys and ingests the whole setup again, and each order then reopens, re-judges and runs held-model twice. Fix without losing an order: walk the tree depth first, forking the node at each prefix (`Peer::fork`), so a prefix is ingested once; skip a subtree whose prefix left the same store and index as one seen.
- **A sweep seed is mostly calm setup and quiescence.** `persons` and `shared_group` build accounts with real keys and call `quiet` per grant; `quiet` (sim `net/mod.rs`) needs at least three settles and two 61 s resync rounds even when nothing moves, the end adds three more for the ping-pong check, and `finish` formats and hashes every host log record into a digest the sweep drops. `member_churn` runs 13 quiets around about 120 random steps. A seed changes keys, clock skew and the faulty steps; the calm setup is the same story every time. Fix: a base world per scenario built once (two or three base seeds for key variety) and forked per seed; a setup quiet that stops at an empty queue with every node idle; the digest only where it is compared.
- **The same generator under several names**: the three eph window properties and churn (20 seeds each, 12 distinct setups), the reverts pair, the keep pair, eight sweep scenario pairs built by one function. One seed range per generator, the seed choosing the variant.
- **Checks after every step**: paged `stored_each`, held-model after every clocked ingest, resume's check, the engine-only sweep scenarios reading every aspect of every node each step.
- **Fixed-seed properties run in every gate** (forged_parts, tombstone, unmerge_paged, crdt stream and paging, base proptests): the same run each time; only worth it when the branch touches what they reach.
- **Wall, not CPU**: two single-threaded paged seeds hold the engine property step for 35-83 s with the other cores idle; tied's four seeds run one after another.
- Seed counts stay (15 per sweep scenario; the exhaustive order property 8, one per emphasis: its seed picks the emphasis, so fewer drops emphases). Tried at 5 and 2: the gate ran 363 s against 480-625 s, but the time is to come from the work each seed does, not from fewer seeds. Open: one shared seed range for same-generator properties; a failing gate seed rerun on main automatically, so a main failure becomes an issue and not a blocked branch.

## Order of work
1. The derived-state memos for node-sync's passes (pattern 2), as their blockers land.
2. Fork helpers and built-once setups (pattern 1): `Net::fork`, sim `World::fork` and `NetSim::fork`, the order tree walk.
3. Seed counts and same-generator merging in the gate, once decided; the setup `quiet`.
4. The width rule (pattern 4), the duplicates (pattern 5), tests that test nothing: file by file.

## Method
Per-test times: run a test binary with `RUSTC_BOOTSTRAP=1 <bin> -Z unstable-options --report-time --format json` from its crate directory; sum `exec_time` (rough: they move with load). To compare two builds: `tools/icount <bin> -q` over the whole binary. Where a binary's time goes: `tools/cpuprof OUT <bin> -q`. A profile: issues/derived-state-recomputed.md, Method.

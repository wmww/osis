# Tests cost about a hundred times what they should
> Summary: The default tests take about 2800 CPU-s and 280 s wall on ostrich (16 threads; the gate's share 1610 / 115), a third of the wall the tails of binaries whose last tests run alone; a median node test runs 0.9 G instructions and a median osis test 1.1 G, where a test should cost milliseconds. Measured: no single cause. Every test builds a multi-node world from nothing; node-sync derives everything again on every pass (two thirds of osis `it` and of the sim sweep); one order property is a tenth of osis-node `it`; default tests enumerate orders, seeds and sizes at full width; keys from role secrets are derived again at every use; the gate runs the same properties at three sizes and each sweep scenario 15 times. Crypto is 19% of default-test CPU (Curve25519 10%, XChaCha20-Poly1305 8%, measured with the forensic attack trying every key in full; its exact shortcuts: below); fake crypto would win at most 9%. Target (Tess): 4x faster without losing coverage that matters.
> Priority: normal
> Tags: tests, performance

## Measured (main 6a15e5b44, this box, 24 cores)
- Default tests: 2553 s summed test time; osis-node `it` 1299 s (1256 tests, median 0.37 s), osis `it` 705 s (511, median 0.58 s), osis-engine 221 s, osis-crdt 81 s, osis-sim 70 s, held-model 58 s, chat 39 s, perm 25 s. Wall is CPU over the cores per binary, the binaries one after another: only less CPU makes it faster.
- By length: the 100 slowest tests are 950 s (37%); tests of 1-5 s are 1009 s (486 tests); tests under 1 s are 600 s (2900 tests).
- The gate: build 40-60 s, default tests 170 s, selected properties 170-250 s, sim sweep 105-145 s.
- A median node test (`tombstone::a_lost_tombstone_is_uploaded_again`, 1.7 G instructions): `Engine::check_index` 26%, curve and KEM work about 30% (signature checks 11%, X25519 8%, `KemPublicKey::from_slice` 5%, `mul_base` 4%, `SigningSecret::from_seed` 3%), `create_account` 9%, value encode and decode about 15%, store commit 5%, `misjudged` 4%.
- A median osis test (`sync::grant_by_inbox`, 2.4 G): signature checks 16%, `check_index` 12%, `rejudge_all` 10% of which `misjudged` 9%, `part_keeps` 9%, `SigningSecret::from_seed` 6%, `World::account` 7%.
- Whole binaries (`tools/cpuprof`, inclusive shares, overlapping). osis-node `it`: ingest 24%, `SyncEngine::handle` 22%, `order::check_orders` 21% (one test, `order::held_set_decides`), the debug checks 13-20%, `CommitBlob::decode_as` 9%; self time spread thin (field arithmetic 8%, malloc and free 10%, memcpy 3%, XChaCha 6%). osis `it`: `SyncEngine::handle` 68% (`judge_label` 29%, `part_keeps` 17%, `crdt::stream` 18%, `held_parts_at` 12%), ingest 15%; self: malloc and free 15%, waiting on the allocator's lock 8% (24 test threads), field arithmetic 6%.
- The debug checks (`check_rebuilt`, `check_index`, `misjudged`): 12.5% of osis-node `it` and 4% of osis `it` by instructions (notes/testing.md, Rebuild check). Two cheaper schedules were tried and dropped. Once per engine at its drop: no gain (every engine pays one check at its largest state, and tests reopen engines constantly), and wrong for state that depends on time passed since the last transaction. One transaction in 8 (index: 1 in 64), drawn from the node's identity: 7.7% fewer instructions for osis-node `it`, at the price of the check after an engine's first status change, where notes/testing.md records most of its default-test finds. Not worth it.
- Raising `opt-level` to 2 for the workspace: 3-10% for a full rebuild. Not worth it.
- CPU seconds on this box move 20-40% between identical runs (load, SMT): compare by `tools/icount`, and find where time goes with `tools/cpuprof` over the whole binary. A first reading from CPU seconds here put the debug checks at a third of test time; that was load.

- Setup, measured alone (instructions): the commonest osis-node setup (`Net::new`, a host, three nodes, one group with two holders, one item, `run`) is 968 M against about 1700 M for a median node test (57%); osis `sharing::alice_bob` is 2000 M against about 2400 M for a median osis test (83%). Inside the node setup: settling (`Net::run`) 43%, `Net::group` 34% (of it `pair`, every commit delivered to the other node, 24%), making the nodes 20% (`create_account` 16%). Three nodes alone are 209 M. Making each fresh `LocalPeer` node once per process and opening copies saved 1-2% of osis-node `it` and the engine tests: account creation is not where setup goes, the whole scenario is. So a setup has to be built once and copied whole, in memory (a copy by reopening restarts every node and pays its reconnect and first sync again).

- **Tail-bound, not only CPU-bound**: 279 s of wall against 174 s of CPU over 16 threads. Every binary ends with fewer tests than threads running; summed, about 105 s. osis-node `it` had 14+ tests running until 135 s and then three single-threaded tests that started at 96 s ran to 147-154 s: `shred_sync::purged_synced_body_crash_safe` (38 CPU-s alone, 80% the forensic attack), `shred_sync::purge_leaves_reaction_through_hosts` (20 CPU-s, 80% the attack), `stream::a_join_pages_behind_the_stream` (12.5 CPU-s, 88% `drop_covered`). The small binaries' tails (perm 7 s, held-model 6, osis 4-10, crdt, engine, chat 4 each) are their longest single test: libtest starts tests in name order, so a long test late in the order sets the end.
- Whole-binary profiles after the changes below (cpuprof, 6 threads; inclusive, overlapping). osis-node `it`: node-sync passes (`SyncEngine::handle`) 33%, ingest 16.5%, local commits 13.5%, `order::check_orders` 11%, `crdt::stream::stream` 10.8% (joins streaming a stored state, `stream_stored`; half `stream::position`; most of it the paged-text and large-list tests: `write::paged_text_*`, `ephemeral::grown_past_a_blob_compacts`, `encodings::big_list_*`), `check_index` 9%, the forensic attack's section tries 7%, `drop_covered` 5.8%, `rejudge_all` 5.2% (`misjudged` 4.7%), store commits 5.4%. osis `it`: node-sync passes 68% (`log_events_from` 20%, `judge_label` 19%, `body_sends` 7%, `certificates` 7%, `flush_storing` 7.5%), local commits 12%, store commits 10%, ingest 9%, `crdt::stream::stream` 7%, `check_index` 4%.
- Done here (each exact; `tools/icount`, whole binary at 6 threads, base 08e053310 against the branch): osis-node `it` 3384 -> 3213 G (-5.1%), osis `it` 1107 -> 1056 G (-4.6%), osis-engine lib 431 -> 424 G (-1.6%). In the stage osis-node `it`'s tail fell from 19 s to 7 s (154 -> 121 s wall in one run; CPU-s on this box move 20-40% with load, so read the instruction counts).
  - **A memo hit cost a lookup per key it read** (`Dep::holds`: a mutex lock and a SipHash lookup per key), so an answer over an aspect's n held bodies (`replaced_at`, through `held_writes`) cost O(n) per hit and a pass asking each body O(n²). An entry keeps its reads grouped by container with the container's change count at which they last all held; a hit looks keys up only in a container that changed since (notes/engine.md, Derived values). `a_join_pages_behind_the_stream` 91.4 -> 46.3 G.
  - **The forensic attack** tried every opened commit blob's sections under every candidate on one thread, again for every copy of the same commit (a commit placed under several labels opens to the same plaintext; a third to a half of the envelopes in the `shred_sync` tests), and derived each candidate's section wrap key again per section. Now each distinct envelope is tried once (every blob of it recovers its sections), one thread per envelope, each candidate's section key derived once (`Trial::unwrap_section`). `purge_leaves_reaction_through_hosts` 118.7 -> 101.4 G, 13.4 -> 4.2 s wall alone; `purged_synced_body_crash_safe` 166.5 -> 144.2 G, 19.2 -> 7.4 s. Splitting the candidates into runs per thread instead doubled the instructions (a section's search stops at its first opening candidate). Plants: `drop_blob` not zeroing `e.wrap` still fails `purged_synced_body_crash_safe`.
- `tools/limits.py tests` on the branch (3820 tests, 3230 CPU-s at 8 jobs, load 15-22): 12 over the `test` limit alone, `order::held_set_decides` 166 CPU-s / 15 s far ahead; the three `shred_sync` forensic tests 18-42 CPU-s (fewer instructions than on main, but spread over threads beside the box's load they count more CPU-s: 20 -> 24-30 alone for `purge_leaves_reaction_through_hosts`); then `net_records::no_connection_resumes_*` 18, `shred::past_expiry_and_purge_alike` 14, held-model's two repair props 11-13, `stream_differential_no_write_dropped` 13, `rotation_holds_spec_crypto_4`, `purged_ephemeral_rounds_stay_within_the_cap`, `client_session_differential_against_grants` 11-12.
- Left, by size:
  1. **Own replaces are judged pair by pair in a full pass** (node-sync, `drop_label_covered` -> `drop_covered`): for each own replace `s` (every write of one writer to a register is one), every older own commit of its author (`own_held_before`), so a full pass over an aspect with n own writes is n²/2 `covered` judgments, each decoding the older body (`covered_join`), and none settles (`covered_judged` keeps only snapshot judgments). `a_join_pages_behind_the_stream` (300 kept writes, 4 full local passes): 180,000 judgments, 79% of its remaining 46 G and the stage's longest test. Whether an older commit drops under own replaces is decided by `own_covers` alone (the drop needs `own_covers_every_part`, which reads only the two newest later replaces), so judging each body once against its own covers is O(n) per pass and drops the same bodies. Open before building it: the carrier (`set_carrier(c, s)` names the first `s` in commit-ID order that covers `c`), which would move to one of `own_covers`; node-sync semantics (spec/sync.md §7), so it waits for the node-sync passes work (network step 3h2).
  2. The section tries: candidates (130-165K per attack in `shred_sync`) × unopened sections, a full XChaCha20-Poly1305 open each (a wrap seals a random key: no known plaintext byte rules a candidate out). Most candidates are windows of ciphertext inside recovered plaintexts (sealed blobs in node-sync rows, section ciphertexts in envelopes); harvesting only bytes that are not ciphertext of a known format would cut them, at the price of the attack knowing formats.
  3. `crdt::stream::stream` in joins of paged states (10.8% of node `it`): per test, not per change; not looked at.
  4. The small binaries' tails (about 40 s of the stage's wall): a long single-threaded test late in name order. The stage wall would be about its CPU over the threads if the gate ran the default binaries two at a time (node `it` beside the rest), at the cost of oversubscription while both are busy; or each such test split or on the seed runner.

- The 30 tests alone, by kind: crdt seq and winners tests (`tests_seq::part_judges_as_whole_of_histories` 186 G, `seq_winners_from_scratch` 67 G, the snapshot edit models 55 G each) and held-model's props are model work, no crypto; osis tests (`sync::redeem_held_joins_nothing` 159 G) are 70-90% node-sync passes (pattern 2); node scale and stream tests are 50-65% node-sync, 15-20% crypto, 5-15% `check_index`; `order::held_set_decides` (486 G) ingest 27%, `check_index` 20%; short tests (under 1 s) are 30-75% setup.

**Fake crypto in tests: options, not built.** The ceiling is the product-path crypto, 9.3% of default-test CPU; the forensic attack's AEAD is its definition and the debug checks' signature re-checks are gone (above).
1. A runtime switch the harness sets (thread-local, debug builds only) making sign/verify, AEAD or KEM trivial. No feature set, but product code carries a crypto bypass, and every test run with it stops checking that bad signatures, keys and wraps are refused: forgery, relay-junk and wrong-key tests would each have to opt out, and a test that forgot to is silently weaker. Gains at most 9%.
2. A verification memo inside osis-crypto (debug builds), keyed by key, message and signature: exact, so it hides no bug, but debug and release differ inside the crypto crate, its memory grows with every signature seen, and only re-verification (about 1.6% left) gains.
3. Dependencies without debug assertions and overflow checks (`[profile.dev.package."*"]`): real crypto, exact; measured per operation sign -13%, verify -5%, X25519 -16%, ML-KEM -7%, AEAD -7%: about 1% of the suite, for one rebuild of every dependency. Loses the dependencies' own debug assertions.
4. Precomputed keys per seed: keygen is under 1%.
None is worth its risk now; the larger levers are node-sync passes (29%), the allocator (15%; Allocation, below) and `check_index` (7%).

## Patterns, by size
1. **Every test builds its world from nothing, and many build it once per case.** A world is accounts with real keys, groups with rotations, labels at hosts, and a settle. About 120 of the 260 slowest tests rebuild one setup per order, seed, case or crash point (about 700 s); the short tests are mostly setup. Exact in-memory world copies exist for `LocalPeer`, the node `Net` and the sim `World` with its `osis` handles (notes/testing.md, Copied worlds). Open: setups used once or twice per key (the rest of osis `World::new`, 160 calls), tests that close and reopen a node from a `MemStore` the setup kept (not copyable), osis-chat `flows`, the order tree walk past the setup (the setup prefix is shared: `Played::setups`), `NetSim`.

2. **Node-sync derives everything again on every pass.** issues/derived-state-recomputed.md: 68% of osis `it` and nearly all of the sweep's heaviest scenario are inside `SyncEngine::handle`, of it `part_keeps` 17-23% (waits for history-3), cover judging per pass (`drop_covered`, 13% of a node sample), label judging. ## Properties and the sweep
Read, not measured per seed (35 property tests by `tools/test_select.py`'s rules: node 18, engine 2, perm 9, crdt 3, base 2, osis 1; 52 sweep scenarios at 15 seeds).
- **One property at three sizes in every gate**: `order::held_set_decides` runs quick (8 seeds) and quick-exhaustive (8 seeds, at most 4 commits) in the default tests (95-110 CPU-s, a fifth of osis-node `it`), plain (8 seeds of 60 steps, 85-220 CPU-s) and exhaustive (8 seeds, at most 6 commits, 530-790 CPU-s) as properties. Every order of every held set is a walk of one permutation tree from its root: each delivery makes a fresh account with real keys and ingests the whole setup again, and each order then reopens, re-judges and runs held-model twice. Done: every order starting with the setup as made starts from a copy of one node given it (`Played::setups`). Left, without losing an order: walk the tree depth first, copying the node at each prefix past the setup (`Peer::copy`), so a prefix is ingested once; skip a subtree whose prefix left the same store and index as one seen. The quick seeds gain little from it (the per-order checks and the clocked orders' held-model compare after every ingest dominate); the exhaustive property (every permutation of up to 6 commits) should gain more (not measured).
- **A sweep seed is mostly calm setup and quiescence.** `persons` and `shared_group` build accounts with real keys and call `quiet` per grant; `quiet` (sim `net/mod.rs`) needs at least three settles and two 61 s resync rounds even when nothing moves, the end adds three more for the ping-pong check, and `finish` formats and hashes every host log record into a digest the sweep drops. `member_churn` runs 13 quiets around about 120 random steps. A seed changes keys, clock skew and the faulty steps; the calm setup is the same story every time. Fix: a base world per scenario built once (two or three base seeds for key variety) and forked per seed; a setup quiet that stops at an empty queue with every node idle; the digest only where it is compared.
- **The same generator under several names**: the three eph window properties and churn (20 seeds each, 12 distinct setups), the reverts pair, the keep pair, eight sweep scenario pairs built by one function. One seed range per generator, the seed choosing the variant.
- **Checks after every step**: paged `stored_each`, held-model after every clocked ingest, resume's check, the engine-only sweep scenarios reading every aspect of every node each step.
- **Fixed-seed properties run in every gate** (forged_parts, tombstone, unmerge_paged, crdt stream and paging, base proptests): the same run each time; only worth it when the branch touches what they reach.
- **Wall, not CPU**: two single-threaded paged seeds hold the engine property step for 35-83 s with the other cores idle; tied's four seeds run one after another.
- Seed counts stay (15 per sweep scenario; the exhaustive order property 8, one per emphasis: its seed picks the emphasis, so fewer drops emphases). Tried at 5 and 2: the gate ran 363 s against 480-625 s, but the time is to come from the work each seed does, not from fewer seeds. Open: one shared seed range for same-generator properties; a failing gate seed rerun on main automatically, so a main failure becomes an issue and not a blocked branch.

## Order of work
1. The derived-state memos for node-sync's passes (pattern 2), as their blockers land.
2. Built-once setups (pattern 1): the order tree walk, `NetSim`.
3. Seed counts and same-generator merging in the gate, once decided; the setup `quiet`.
4. The width rule (pattern 4), the duplicates (pattern 5), tests that test nothing: file by file.

## Method
Per-test times: run a test binary with `RUSTC_BOOTSTRAP=1 <bin> -Z unstable-options --report-time --format json` from its crate directory; sum `exec_time` (rough: they move with load). To compare two builds: `tools/icount <bin> -q` over the whole binary. Where a binary's time goes: `tools/cpuprof OUT <bin> -q`. A profile: issues/derived-state-recomputed.md, Method.

# Re-sealed holders can still lack a fork another node holds
> Summary: After re-seals settle, a node holder can lack a current epoch's secret that some node holds: the trigger credits a node's higher-keyed box with a lower role's newest epoch by `box_knew` (ts order, not what the box carries), and nodes can disagree on the current epochs (supersession read from the applier's own prior `keys.0`).
> Tags: permissions, keys, engine

`rotation::tests::forked_reseals_settle_large` (osis-engine lib, tier 2; random concurrent rotations by random holders leaving out random others, then re-seal rounds) prints the holders that end without a fork some node holds. Review 2 of reseal-livelock, 300 seeds from 0: main 62 seeds with no fixpoint and 82 with a holder lacking a fork; the branch 0 and 63. Two causes:

- **Credited higher box** (about 61 of the 63): a node holder's box keyed at a higher role counts for the lower role's newest epoch when `box_knew` says its first write is ordered at or after that epoch's rotation. Ordered after is not knew: a rotation or re-seal concurrent with the lower role's rotation (or by a node left out of it, or a re-seal by a node holding only a non-newest fork) folds an older secret, and the holder is never re-sealed at the newest. Example (seed 3): peer 0 rotates admin while peer 2 rotates read leaving peer 0 out; peer 0's admin box carries the old read and is credited with the new one. With the trigger counting exact keys only (`carries` false), 100 seeds left only the cause below and settled in at most 4 rounds. The simplest fix looks like dropping the fold: a node holder gets one box per (role, epoch) like an actor holder, so a rotation of one role removes no other role's secret and `Carries`, `box_knew`, `carried`/`may_carry`/`carried_unheld` and the "waits for a re-seal" refusal could all go; cost one sealed box per extra role per node holder per multi-role rotation. Needs a decision (spec/crypto.md §4 "one box").
- **Divergent current sets** (7 lines in the 300 seeds): `SecretsWrite::rotations` takes the epoch a rotation supersedes through its `keys.0` keyset from the keyset the applier held before applying (LWW), so the same commit supersedes different forks at different nodes depending on arrival order. Seed 75: peer 0 rotates admin to n=3 unaware of peer 3's concurrent admin fork n=2; peers 1-3 count n=2 superseded (their prior keyset was it), peer 0 does not, and lacks its secret for good.

Done when `forked_reseals` asserts that every holder holds every current fork any node holds and `_large` passes.

# Purged ephemeral leftovers grow memory without bound
> Summary: A purged memory part is held as its leftover until restart (a purged leftover never drops as covered), and its node-cap charge rides on its label entries, which the purger deletes at hosts: any writer can grow every holder's memory without bound by write-then-purge rounds.
> Priority: critical
> Tags: ephemeral, engine, sync, security

- `Engine::memory_charge` counts every held part, leftovers included, but node-sync charges it per entry (`State::charge_memory`, `charge_applied` at apply) and releases it when the entry goes (`drop_entry`). A purge's right holder deletes the purged body at hosts (`pass/delete`, `body_gone`), so every holder's entry leaves while the leftover stays held: a purged leftover never drops as covered (spec/commits.md §5), and since a snapshot's frontier stops below it (`retention::held_purged`) no snapshot can cover it anyway.
- Effect: every ephemeral delta is `writer`-purgeable, so any writer can write memory commits up to the label's cap (16 MiB default: about 7000 small parts at about 2.3 KiB charged each), purge them with one aspect-wide request, delete at hosts, and write again. Each round leaves its parts' leftovers (header, meta, leftover row, value-less state: on the order of 1-2 KiB each, so roughly 10 MiB) uncharged at every holder of the label, until restart. Rounds take seconds, so GBs in minutes; a legit app purging ephemeral writes routinely leaks slowly the same way.
- Charging by commit (while held, whatever its entries) turns the leak into a cap that fills with leftovers nobody can remove, so the label refuses ephemeral data until restart, and an admin purging a spammer's writes frees no room. So the fix is a rule for when a purged memory leftover goes, not only its charge.
- Direction to judge: forget a purged memory leftover once a held valid snapshot carries its writes value-less (the re-snapshot every writer writes after a purge, `purge_resnapshots`), as a memory commit forgotten under a cover; a fall then brings it back only where a copy is still listed (the hosts' copies are deleted by the purger), as a durable body no node holds stays gone (spec/permissions.md §6). This must keep the frontier rule's point (a fall must not leave the restored write read as covered) and say what each holder reads meanwhile.
- Test: write, purge and delete at the host in a loop at n and 10n rounds; the holder's held memory (leftovers included) stays within the label cap.

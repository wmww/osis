# Two writers' pending commits can stop each other's uploads
> Summary: `pass.rs` treats the aspects of a node's pending commits as unsettled, and a body on an unsettled aspect is may-hold, not must-hold, so the node does not upload it. When writer A holds a commit of B pending (`WaitDeltas`) on some aspects and B holds one of A's pending on the same aspects, each withholds exactly the deltas the other waits for: neither commit ever applies.
> Tags: sync, node, tests

- Seen in the simulator: `osis_sim::replay("move_import", 72)` (also 86; regression test `move_import_seed_72`): node 0 waits (`WaitDeltas`) for parts `(1, 0), (2, 0)` of node 1's commit `08f7..`, which node 1 holds as entry `6063..` under label `c11a..` but never uploads there (its verdict: must-hold `[]`, 3 unsettled aspects), because node 1 itself waits for node 0's commit `4ef4..` on those aspects; node 0's must-hold set is empty for the same reason.
- `unsettled` exists so a node does not delete or skip a body while a snapshot that may cover it is not applied (spec/sync.md §6 may-hold). For must-hold it should not matter: a body this node holds and whose writes are live for it is must-hold whatever else pends, unless a held snapshot covers it.
- Fix: compute coverage for must-hold from the snapshots actually held (a pending commit that is not a snapshot unsettles nothing), and keep the unsettled rule for deletions only.
- Also `move_import` seed 14 (team without secrets of its own, after the derived-owner fix; seeds 0..23 otherwise green): the admin holds the writer's content commit pending `WaitDeltas`, its copy body's entry known but never mapped to a commit; the writer holds two commits pending itself.

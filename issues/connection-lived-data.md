# Data that lives while its keepers are connected
> Summary: Parked by Tess until she works through a design (open: whether keeper lifetime is orthogonal to memory/disk storage; four questions below). Tess's model for ephemeral data, designed in reference-graph terms and modelled (held-model `connlived`): a thing naming keeper accounts is in a node's closure only while the node's connected set holds a keeper, so release is the ordinary release. It replaces keep-alive, superseded parts and `+` aspects. Not built: it changes three requirements lines (proposal below) and leaves four questions for Tess: nodes keeping S unread cannot read keepers, the connected set leaks presence and costs n² at a hub, and any connected node can keep a departed keeper's data alive.
> Priority: low
> Tags: sync, ephemeral, engine, net, spec, tess-call

## Tess's model
A thing may carry an aspect naming its keeper accounts (by default its creator's). A node holds the thing (creation and all content) only while it is connected, directly or through other nodes, to at least one node of a keeper account, and drops it locally otherwise. Thing-level: no wire field, one rule. Ephemeral state on a durable thing lives on a separate keeper-held thing. No periodic writes: a keeper leaving drops the data at once; a reconnecting keeper's node re-sends what it holds by ordinary sync. Nodes may briefly disagree on who is connected (partitions), so such data shows at some nodes and not others until it settles. Listing other accounts as keepers only keeps one's own data alive while they are online; it grants nothing.

## Design
**Principle**: a node holds what its node root reaches by strongs; a strong into a connection-lived thing counts only while the node's connected set holds one of the thing's keepers. Everything else is the ordinary rule.

- **Keepers**: a core aspect `keepers.0`, a set of account weaks, written by the creating commit (default: the creator's account) and by writers like any content aspect. A thing is connection-lived iff its creation carries `keepers.0`; the class is fixed at creation.
- **Held in memory, whole**: a connection-lived thing's commits (creation and record included) are memory commits; a durable thing is never connection-lived. So "ephemeral" moves from the aspect (`+` keys) to the thing, and `+` aspects on durable things go: state that should outlive its author lists other keepers (a document's collaborators). The rejection of drafts (notes/ephemeral.md New things are durable) does not apply: the class never changes, so there is no persistence fixpoint, promotion or draft undo; records in memory parts are the cost. Relay-only signals (`+~`) are unaffected (spelled as a signal on a connection-lived thing).
- **In the closure** (notes/node-closure.md): `given_by` gives an edge into a connection-lived target only while the node's connected set holds one of the target's keepers, recorded in the edge's `Effects` like whether a thing is independent and its roles. An edge whose condition stops is removed as any edge is (`detach`), the thing lands in `left` and is released at the settle's end; what it alone held goes with it (ordinary). A strong to a thing not held, a keeper reachable, wants it: fetched by ordinary sync from a peer holding it (a holder reaches a keeper, so a node connected to it does too). The keepers aspect must be held to judge the edge: a node takes the thing on arrival and judges it then, like a tid whose record comes later.
- **Own account**: a node's own account is always in its connected set, so a keeper's nodes hold its things while they run (the making rule holds), and lose them on restart (memory).
- **Who references it**: a reader reaches a keeper-held thing only by a strong from its closure. From a durable thing that is a durable write per creation; the app keeps it bounded by overwriting (`cursors.0: map<account, strong>` on the document), so durable state grows a few bytes per session, within spec/requirements.md Scale.
- **The connected set** (osis-sync, per node): the accounts proven on its connections (spec/sync-opens.md §2), plus what neighbours report reaching, by path-vector: each route is the path of nodes (the sender first); a route through the receiver is ignored, so a loop cannot keep a departed account alive. Event-driven: a node tells a neighbour its table only when it changed. Each neighbour is told the best route avoiding it (model finding 1). An abrupt drop is seen within the transport's idle timeout. A change of the set re-judges the edges into connection-lived things kept by an account that came or went: an index keeper set → held edges, so a change costs the classes naming that account plus the things that flip, never the closure.
- **Costs** (model `a_connect_at_a_hub_costs_n_squared_route_entries`): a connect at a node with n peers of n accounts sends n + 2 route messages and about n² route entries (every peer hears the newcomer, the newcomer every account); a disconnect alike. Things judged: those kept by an account that came or went. A thing released or fetched again costs what it holds (inherent).

## Model (held-model `connlived`, tests `spec_connlived`)
An oracle applies the rule to the connection graph alone after every event (in each component, a thing lives where the component has a keeper's node; copies flow along connections both of whose ends share it); the protocol runs path-vector and copy sync with messages in random order and is compared at quiescence, on readers' holdings and every node's reach. Random histories of connects, disconnects, restarts and creations (6 nodes, 3 accounts, 4 things, 40 events).
1. **One table to every neighbour drops copies the rule keeps** (26 of 2000 histories; `a_withdrawn_route_with_an_alternative_drops_nothing`): a neighbour whose best route runs through the node tells it nothing usable, so when the node's own route goes it drops the thing though another path to the keeper stays; where no sharing path leads back to a holder nothing brings it back. Telling each neighbour the best route avoiding it: 0 of 2000, 0 of 3000 at 12 nodes and 150 events. Path-vector gives no general guarantee against transient unreachability, so the requirement says "generally" (proposal).
2. **A node keeping the thing unread cannot read its keepers.** Keeping its copy until it restarts brings the thing back after the keeper left (225 of 2000; `an_unread_copy_kept_without_keepers_comes_back`: the keeper's node restarts, a reader drops it, the keeper's node returning takes it from the unread node). Holding nothing and passing copies on starves a reader joining behind it (1073 of 2000; `a_relaying_unread_node_starves_a_late_reader`). Only judging keepers matches the rule (0 of 2000).
3. Loops keep nothing alive (`a_departed_keeper_drops_its_things_through_a_loop`); reach at quiescence always equals the component's accounts.

## Questions for Tess
1. **Nodes keeping S unread** (finding 2). Options: (a) they never take connection-lived entries: such data flows only between readers, so two readers meeting only through a node keeping S unread share none (the requirement says so); (b) the blob prefix names its keepers as tokens per sync ID and routes carry tokens per S: the unread node judges like a reader, but learns which entries share a keeper (linking writes by author within S, against spec/requirements.md Data a node cannot read) and routes cost per sync ID; (c) they keep copies until restart: departed data can come back (finding 2). Lean: (a).
2. **Presence leak**: every node in a component learns which accounts are online in it and the node paths to them, strangers included. Scoping routes per sync ID (only S's keepers, only to peers reading S) closes it at a cost per shared sync ID. Accept, or scope?
3. **Hub cost**: n² route entries per connect at a node with n peers (question 2's scoping divides it by sync ID, not away).
4. **Dishonest nodes**: a route claim is unverifiable, so a connected dishonest node can keep a departed keeper's data alive (a stale cursor shown) at every node it reaches, for as long as it stays. Signed presence would need periodic writes. Accept, with the requirement weakened to say so?

## Requirements proposal (not applied)
Ephemeral data, replacing its first two lines:
- Ephemeral data is a thing held in memory while connected to its keepers: accounts it names, by default its creator's. A node holds it only while it is connected, directly or through other nodes, to a node of a keeper account, and drops it otherwise, at once once the departure is seen; a keeper's node reconnecting brings back what it holds. Nodes generally agree on who is connected; while they disagree such data shows at some nodes and not others. It converges among the nodes holding it like any state, and may be lost when no node holds it.
- Naming other accounts as keepers keeps a thing while any of them is connected; it grants nothing.

Generality: "Presence and selections use expiring ephemeral writes, not durable add and remove (state growth)" becomes "Presence and selections live on things their author keeps, not in durable add and remove (state growth)". Plus whatever weakening questions 1-4 settle.

# Revocation gaps left after receipts-only reads
> Summary: a demotion's frontier is the revoker's own receipts (spec/permissions.md §5.1). Receipts-only reads (built: notes/sync.md Receipts-only reads) let a device that holds part of a tree read the rest's commit headers before stamping, so a phone can remove a member without losing their edits. Still lost: writes at servers the remover cannot reach, writes that reached another member only over a peer path, and a content commit spanning a held and a receipts-only group pends at the partial device. Writer witnesses would close most of the first two.
> Tags: permissions, sync, spec

## What is built
A group marked receipts-only (`GroupPolicy::receipts_only`) is not synced; `demote`'s pre-sync opens its labels, fetches commit blobs only, records verified headers as received, by commit ID (spec/permissions.md §5.1 is header-level now) and applies only the membership commits that carry the group's secrets. Nothing is uploaded, deleted or placed under those labels (osis test `removal_from_partial_device_keeps_unheld_edits_spec_permissions_5_3`, sim scenario `demotion_receipts`).

## Remaining gaps
- **Unreachable servers**: a label whose server the remover cannot reach at removal time is not read (`WaitForSync::Required` fails, `Try`/`Skip` lose the member's unseen edits there).
- **Peer-only edits**: edits that reached another member only over a peer path and never a server.
- **Compaction**: no gap for the receipts-only read since headers count by commit ID (no contiguity): the member's commits whose headers the server deleted are carried by a covering snapshot (a valid one vouches; the member's own is listed by ID like the rest). A late joiner that got the member's writes only through a snapshot still covers them only over held headers (`receipt::received`, the inflation rule of notes/permissions.md Revocation).
- **Cross-group commits** (new with receipts-only; staleness, not loss): a content commit with deltas on a thing of held G and a thing of receipts-only subgroup H (same readers, so one projection, which goes under G's label too) reaches the partial device with H's thing's delta; that thing's `/created` lives only under H's label, so the commit pends (`UnknownCreated`) and its G part is not seen there until the policy is lifted. Before receipts-only no device could hold G's projection and not sync H (same readers). Item 137's apply-what-you-have covers only plain membership commits; extending it to content commits weakens atomic apply (issues/snapshot-created-copy-pends.md). Fix candidate: the engine treats a held delta of a thing only receipts-only groups hold as not held, so the G part applies and the H part joins late if the policy is lifted (`late_parts`). Not enough as stated: neither the node nor the engine can tell such a thing is H's when its `/created` and `/group` went only under H's label (any H thing made after the policy was set), so it needs a way to learn the thing's group (e.g. from the receipts read's headers, which list it, though a header names tids, not groups) or the sync layer applying what it has once every held label passed (which weakens atomic apply for content commits). Repro: Bob writes an item of G and one of H in one commit; the phone's `pending()` shows `UnknownCreated(H item)`.
- **Linked headers**: a header whose lists go by link is not recorded (its pages are not fetched).
- **Writer witnesses** (follow-on, not built): every writer's ordinary delta carries the per-author received frontier its compaction snapshots already carry (spec/crdt.md §8 `Frontiers`), and a removed member's write counts if the remover's frontier covers it or a valid writer's delta stamped before the cutoff shows it received it, witnesses counted outward from the remover's record (a least fixpoint, so a later-removed witness bootstraps nothing). Writers only: a reader witness would let a reader and an ex-writer combine into write power. Membership writes keep today's rule (the self-witness hole and non-settling histories of notes/permissions.md live there). The receipt record is the shared input. Inherent floor: the member's trailing edits that no writer saw before the cutoff look exactly like a backdated forgery and are hidden until re-grant.

Other uses of receipts-only reads, not built: activity views over groups a device does not hold, the own-counter recovery of a restored node (issues/restored-node-counter-reuse.md), admin devices that hold nothing, header-level forensics.

Rejected along the way: trusting the author's timestamp for content (a removed writer plus a colluding reader could inject backdated edits that honest writers re-stamp: "readers only read" breaks); scoped removals via `until` (needs a device holding the tree to finalize).

# Revocation gaps left after receipts-only reads
> Summary: a demotion's frontier is the revoker's own receipts (spec/permissions.md §5.1). Receipts-only reads (built: notes/sync.md Receipts-only reads) let a device that holds part of a tree read the rest's commit headers before stamping, so a phone can remove a member without losing their edits. Still lost: writes at servers the remover cannot reach, writes that reached another member only over a peer path, counters whose headers compaction deleted before the read, and commits spanning a held and a receipts-only group stay pending at the partial device. Writer witnesses would close most of the first two.
> Tags: permissions, sync, spec

## What is built
A group marked receipts-only (`GroupPolicy::receipts_only`) is not synced; `demote`'s pre-sync opens its labels, fetches commit blobs only, records verified headers as received (spec/permissions.md §5.1 is header-level now) and applies only the membership commits that carry the group's secrets. Nothing is uploaded, deleted or placed under those labels (osis test `removal_from_partial_device_keeps_unheld_edits_spec_permissions_5_3`, sim scenario `demotion_receipts`).

## Remaining gaps
- **Unreachable servers**: a label whose server the remover cannot reach at removal time is not read (`WaitForSync::Required` fails, `Try`/`Skip` lose the member's unseen edits there).
- **Peer-only edits**: edits that reached another member only over a peer path and never a server.
- **Compaction gap**: counters of the member whose headers were deleted at the server (their writes carried by a snapshot) break contiguity in the reader's record, so the member's later uncompacted writes on that aspect are not covered. Same for a late joiner today (`receipt::received` counts a snapshot's frontier claims only over held headers). A fix would need to trust a valid snapshot's claim below a held header of the same node, which the inflation rule (notes/permissions.md Revocation) forbids as written.
- **Cross-group commits**: a commit with deltas on things of a held group and of a receipts-only group shares one projection; the partial device holds the unheld thing's delta and waits for its `/created`, which lives under the unheld label, so the whole commit stays pending there.
- **Linked headers**: a header whose lists go by link is not recorded (its pages are not fetched).
- **Writer witnesses** (follow-on, not built): every writer's ordinary delta carries the per-author received frontier its compaction snapshots already carry (spec/crdt.md §8 `Frontiers`), and a removed member's write counts if the remover's frontier covers it or a valid writer's delta stamped before the cutoff shows it received it, witnesses counted outward from the remover's record (a least fixpoint, so a later-removed witness bootstraps nothing). Writers only: a reader witness would let a reader and an ex-writer combine into write power. Membership writes keep today's rule (the self-witness hole and non-settling histories of notes/permissions.md live there). The receipt record is the shared input. Inherent floor: the member's trailing edits that no writer saw before the cutoff look exactly like a backdated forgery and are hidden until re-grant.

Other uses of receipts-only reads, not built: activity views over groups a device does not hold, the own-counter recovery of a restored node (issues/restored-node-counter-reuse.md), admin devices that hold nothing, header-level forensics.

Rejected along the way: trusting the author's timestamp for content (a removed writer plus a colluding reader could inject backdated edits that honest writers re-stamp: "readers only read" breaks); scoped removals via `until` (needs a device holding the tree to finalize).

# A malicious server can grow a node's storage and work without bound
> Summary: Under a label the node opened, a server's fake add events (random blob IDs, junk wraps, inline junk blobs) are kept for good; a reconciliation's need set, Sync/Path paging and Want lists have no cap tied to anything the server cannot inflate. Violates "Peer input never causes unbounded allocation, work, storage" (spec/requirements.md, Scale).
> Tags: security, sync, node, proto

Repro: inject `Message::Push { label: <opened label>, events: 50 × Added { blob: Some(4 KiB junk), wrap: junk, stamp: None } }` on a node's server connection (`Net::conn_to` in osis-node tests/net, as in tests/hostile_server.rs): the node's entries under the label go 13 -> 63, all 50 junk blobs are stored, and both stay after an hour of passes.

Fixed in the wave 6 review (tests/hostile_server.rs): Pushes for labels not started on the connection are dropped; a server path is verified page by page, so a bad path is never buffered.

Open:
- **Junk entries under an opened label.** `log_events` records every add event as an entry (`Kind::Unknown`) and stores inline blob bytes before trying to unwrap. `Unknown` covers three things: chunk/tree/page blobs (filler wraps, never unwrap), entries under epochs not held yet, and junk; none is ever dropped, and `open_entries` retries every `Unknown` entry per round of new secrets (O(junk) work per secret change). Direction: keep blob bytes only for entries that unwrap or that a held header lists (pages, chunks of fetched commits); forget an unopenable, unstamped entry once a complete pass shows the node can open the label's head epoch; or cap unopened entries per (server, label) and refetch later (the server keeps them).
- **Reconciliation.** `Reconciler::on_reply` extends `need` with every mode 2 ID inside an asked mode 1 range; a responder can keep splitting (claims of more than 1024 IDs per range), bounded only by `MAX_RECONCILE_MESSAGES` (4096) × 256 ranges × 1024 IDs, about 10^9 IDs (32 GB). Direction: report need/have per reply (fetch as it goes) and cap the total at the label's plausible size (e.g. the node's own count plus a policy margin), abandoning past it.
- **Paging without progress.** The client follows Sync `more` while the cursor changes (a server returning empty pages with fresh cursors loops forever), Path `more` regardless of whether the node still wants the path (the node marks the label Failed after a bad page, the client keeps asking), and Fetch prefixes. Each costs only a round trip per page, but never ends on that connection. Direction: cap pages without events or steps per exchange, and let the node cancel a Path exchange.
- **Want lists.** A SyncReply's `want` is not checked against the IDs the request listed as gained; the node uploads any stamped entry it holds under the label that the server names (upload amplification, up to 4096 blobs per reply). Direction: answer only IDs the Sync carried in `gained`.
- **Static-entry open.** A key actor's open takes the read secret from the Opened reply's entry box and accepts the head without verifying the server's path (`sync/open.rs::opened`). A sealed box is unauthenticated, so a server that knows the key actor's KEM key (a colluding member) can hand it a fake epoch secret; it is never established, so nothing is encrypted under it (spec/crypto.md §4), but the fake head and epoch stay recorded. Direction: verify the path before learning the secret.

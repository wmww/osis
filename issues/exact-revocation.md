# Exact revocation through snapshots
> Summary: Judging each write a snapshot carries as its claimed author's (no vouching) cannot be built on today's formats: frontiers and addenda name commits by ID, a carried session-form write names only its dot, and a node holding only the snapshot cannot map the one to the other. Doing it needs frontiers by dot range or snapshots naming each carried write's commit, plus a receipt rule for writes received only through a snapshot.
> Priority: low
> Tags: permissions, crdt, tess-call

Today a valid snapshot vouches for every write it carries (spec/permissions.md §5.2; notes/permissions.md Snapshots vouch), so a removed writer's late write stays wherever a co-writer's earlier compaction carries it, and goes where none does. spec/requirements.md Permissions states this as a Limit. The proposal: judge a carried write as its author's write at its own stamp, as if it arrived alone. Tried and stopped before changing anything, because:

- **The time is fine.** A carried write's `ts` is part of its stamp (spec/crdt.md §2.2), and copies are equal stamps only (§4.1), so a copy dated differently is a different write. It is judged on its own and covers nothing. No "earliest copy" rule is needed.
- **The commit is missing.** Once its author is demoted, a write counts only if the demotion's frontier or an addendum lists its commit ID (§5.2), whatever its time. A session-form carried write names only `(tid, nonce, counter)`. Only the commit's header maps that to a commit, and snapshots carry no commit IDs for session sources (spec/crdt.md §8). Ephemeral snapshots carry session writes that may never have been in a commit the node holds.
- **Some nodes never get the header.** Hosts lose a commit's header once its blobs are deleted under a cover, so a node that joins after compaction (a new device of the admin) holds the carried writes but not the headers. Its frontier cannot list them, it cannot match an addendum's IDs to them, and it cannot tell which listed commit a carried dot belongs to. Without vouching, such a node removing X makes all of X's compacted pre-removal writes invalid at every node: the loss is consistent, but it is everything X ever wrote that got compacted, and it depends on which device did the removal. That is worse than the Limit it replaces.
- **Patching it re-opens a known divergence.** Counting "the frontier lists a snapshot that carried it" as a receipt diverges once the listed snapshot is covered and forgotten: a node holding only a later snapshot cannot tell whether the write was in the listed one. This is the roles-model `content.rs` result behind the vouching decision (notes/permissions.md, Rejected content rules), so that reason still holds.
- **Dating by stamp instead brings back the author's timestamp.** "A carried write dated before the removal is vouched for, a later one judged as its author's" lets a removed writer backdate a write, have an unaware co-writer compact it, and keep it. That breaks Tess's rule that the author's own timestamp never decides validity.

What would make it buildable, each a format and model change (frontier wire format, osis-perm, roles-model, held-model, TLA):
1. Frontiers and addenda list dot ranges (session, counter up to n) beside commit IDs, filled only from headers the demoter verified, plus a rule for writes received only through a snapshot (counted as received by whom, and when?). This undoes "commit IDs, never counters" (notes/permissions.md).
2. Or snapshots name each carried session range's commit (a forger could map a late write to a listed commit, but that only keeps a write the forger could make itself), and a late joiner's frontier lists commits named this way.

Either way the requirements Limit stays until the receipt question in point 1 has an answer. Sim oracles `revocation_bob`, `revocation_carol` and `coverer_revoked` stay loose until then.

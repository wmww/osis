# Sync scans the log without a record bound
> Summary: a Sync in log mode reads log records until it has a page of events, so records that yield no event (superseded or expired adds) are all read in one request: up to `log_keep` (2^20) lookups, the same order as the accepted whole-space Reconcile. Low; at least the Hub stall bounds note is wrong.
> Tags: security, proto, host

- Where: `proto/src/serving.rs` `sync` (`From::Log` loop); it stops on reply bytes (`event_size`), never on records read. `event()` returns none for an `Added` record whose entry is gone or re-added later (`add_seq != seq`) or that the requester listed as gained.
- Attack: fill a label's log with records that yield no event, then Sync from an old cursor. (Push is not a vector: it scans from the subscription's position, which only moves forward, so each record is read once per subscriber.) Natural churn builds such a log too; the trigger is any opener. A depositor (deposit key) deposits blobs with a prefix expiry about now: each logs an add, the sweep expires it with no record, the budget frees again; at the default 600 deposits a minute that is 864 000 such records a day. A writer can do it faster with wrap replacements (each supersedes the previous add). Any opener of the label then costs the hub one store lookup per record per Sync, about 2^20 at `log_keep`, three such requests per input (`MAX_UNANSWERED`), repeatable since the cursor stays valid.
- Impact: hub stall of the same order as the accepted Reconcile bound (notes/flow-control.md Hub stall bounds, about 1 s at 2^20 rows), but that note says Reconcile is "the one request whose reads follow the label rather than the message"; this is a second one, and its trigger needs only a deposit key plus any reader.
- Fix sketch: bound records read per reply (e.g. a few `LOG_BATCH`es) and return `more` with the cursor at the last record read. The client abandons a Sync after `MAX_EMPTY_PAGES` (16) pages without events, so either the bound times 16 must cover `log_keep`, or the client must treat a page whose cursor advanced as progress (it already checks `asked == Some(cursor)`). Update the Hub stall bounds note either way.
- Weighed: per-input cost stays within the turns-by-source bound (3 such Syncs per input, like Reconcile), so this is fairness latency, not an unbounded stall. Reconcile alone keeps the per-input bound P near 1 s at 2^20, so bounding Sync helps only if a 2^20-record scan (one random entry lookup per record) costs well over Reconcile's 1.06 s: measure first (a `file::` release budget like `reconcile_whole_space_budget`). If fixed: a record bound of R per reply needs R × `MAX_EMPTY_PAGES` >= `log_keep` (R >= 65 536), since counting an advanced cursor as progress would let a hostile host page a client forever; per-input gain is then only 16x.

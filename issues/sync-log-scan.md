# Sync and push scan the log without a record bound
> Summary: a Sync in log mode (and a push) reads log records until it has a page of events, so records that yield no event (superseded or expired adds) are read without bound in one request: up to `log_keep` (2^20) per input, not paged. Low-medium.
> Tags: security, proto, host

- Where: `proto/src/serving.rs` `sync` (`From::Log` loop) and `push`; the loops stop on reply bytes (`event_size`), never on records read. `event()` returns none for an `Added` record whose entry is gone or re-added later (`add_seq != seq`) or that the requester listed as gained.
- Attack: fill a label's log with records that yield no event, then Sync from an old cursor (or let a subscriber's push run). A depositor (deposit key) deposits blobs with a prefix expiry about now: each logs an add, the sweep expires it with no record, the budget frees again; at the default 600 deposits a minute that is 864 000 such records a day. A writer can do it faster with wrap replacements (each supersedes the previous add). Any opener of the label then costs the hub one store lookup per record per Sync, about 2^20 at `log_keep`, three such requests per input (`MAX_UNANSWERED`), repeatable since the cursor stays valid.
- Impact: hub stall of the same order as the accepted Reconcile bound (notes/sync.md Hub stall bounds, about 1 s at 2^20 rows), but that note says Reconcile is "the one request whose reads follow the label rather than the message"; this is a second one, and its trigger needs only a deposit key plus any reader.
- Fix sketch: bound records read per reply (e.g. a few `LOG_BATCH`es) and return `more` with the cursor at the last record read. The client abandons a Sync after `MAX_EMPTY_PAGES` (16) pages without events, so either the bound times 16 must cover `log_keep`, or the client must treat a page whose cursor advanced as progress (it already checks `asked == Some(cursor)`). Update the Hub stall bounds note either way.

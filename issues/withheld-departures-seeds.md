# The withheld-departures harness failed some seeds
> Summary: Solved on branch depth0 (delete at merge once reviewed). osis-engine `withheld_departures_leak_nothing_large` failed seeds of 0..200 and 9490000..9490200. Causes: harness judging departures by the clock; a slip (a node due to finalize without a secret encrypted); a real Met gap (seed 3: a finalize held without the write it ends applies nothing, yet its name counted). Rule now: a reset names the write it ends; a role commit with a reset of an unheld entry applies none of its edge writes; a name is met only for a commit so resolved (spec/permissions.md §2, spec/crypto.md §4 Met). Modelled in core/test/tla/rotation/Finalize.tla. Seeds 9490002 and 9490147 were harness gaps (an unaware removed admin re-granting).
> Tags: security, keys, engine, tests

## The rule (Finalize.tla)
A finalize resets the live entry of each ended grant; the reset carries that entry's creation, so it already names the write it ends (spec/crdt.md §5.6). The rule:
- A role commit with a reset of an entry whose creation the node does not hold applies none of its edge writes until it does (`ix.unresolved`, `apply::validity::add_role_commit_in`). A commit's edge writes apply together or not at all.
- A name (and the departs mark) is met only when its commit is applied and resolved (`NamesHeld::resolved`).

So "holding the commit" means holding the departure it is: seed 3's X, holding the finalize without the `until` write, applies nothing and does not establish the rotation. A finalize beside a renewal ordered before it ends a superseded write and applies nothing, decided: met, so nothing locks out and the renewed holder is re-sealed. Limit: a commit resetting an entry the node never gets never applies there.

Candidates checked (Finalize.tla, README table): old (commit held) leaks seed 3; the earlier branch rule (lowering writes applied or dropped) leaks for an erase finalize (an unknown reset derives no write, so nothing is asked) and locks a group out beside a renewal, for good; the issue's candidate (old rule, rotate instead of re-sealing a holder a name removes) leaks through the new rotation's history box; resolved-names with a commit's known writes applying alone lets a name cover a holder its commit's other write had not yet removed at the rotator (and a hostile unheld reset locks out). Only the rule above passes every instance.

Tests: `finalize_without_its_until_unmet_spec_crypto_4` (fails with names not checked for resolution), `finalize_applies_whole_or_not_spec_permissions_2` (fails with known writes applying alone), `finalize_beside_renewal_settles_spec_crypto_4`, `renewed_holder_resealed_spec_crypto_4` (the earlier repros, failing under the branch rule).

## Harness gaps (no engine change)
- Clock vs keys (seeds 59, 90, 107, 147, 159): an ended grant departs by its finalize, not by the clock; the harness uses `key_holders`.
- Finalize due without a secret (59, 90, 107, 162, 171): a slip, fixed: `finalize_due` reports it stays due, `ensure_rotated` blocks every role. Test `finalize_due_without_secret_blocks_spec_permissions_2`.
- An unaware removed admin re-granting (9490002, 9490147; test `withheld_regrant_by_unaware_admin_spec_crypto_4`): admin P, past its `until` (9490002) or removed (9490147) without knowing, grants departed peer d, boxing it epochs P holds; 9490002: d reaches an older epoch through their history boxes; 9490147: X, lacking P's removal, takes the grant as valid and rotates boxing d, whose history box lists an epoch made knowing d's departure. P shares what it holds, as it could anyway. The harness's exemption for a box from a commit invalid now (seed 282407) now covers the epochs that box's history reaches, and boxes from a rotator that held d's departure yet saw it a holder by a later edge write that does not apply in the converged view; nobody may encrypt under such an epoch (checked at the owner).

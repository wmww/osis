# Own P2P: what nodes still lack
> Summary: Our P2P (`osis_transport::p2p`, spec/sync.md §10 `peer://`, notes/networking.md Implementation) is the only P2P transport, on in every build: nodes, `Multi` and osis use it, relay for their co-readers and, as dialers, exchange IPs only with them. Left: direct addresses in `reach.0`, co-readers as relays, relaying for strangers as a user setting, port mapping; open: a stranger can learn a target's IP (design below), a registration's shared flow-control window, `Config.relays` unusable until the P2P port is fixed, DHT.
> Tags: transport, node, spec, security

## Next
1. **Direct addresses in `reach.0`** (decided: a reachable node lists them, so co-readers dial it directly; spec/sync.md §10 "Published forms list relays only" and "Direct addresses are never published" change then). Rename `reach.0` field 1 (`relays`) to the URL's items when it carries both. How a node knows it is reachable is open: an observed address (`P2pListener::observed`) equal to a local one with the same port is the simple rule, but needs a relay; without one, a dial-back or listing the route addresses (`lan::route_ip`) always. Links must keep carrying relays only (filter the items in `make_link`). The listener binds `[::]:0`, so the port changes per run: a fixed port with a fallback avoids a `reach.0` commit per restart.
2. **Co-readers as relays** (decided): a node lists the relays it knows in `reach.0`: co-readers that relay (reachable ones, from their direct addresses), saved peers, configured ones (`Config::relays`). Needs registrations that follow that set without re-listening (`P2pListener` takes its relays from the URL once).
3. **Relaying for strangers** (decided: only when the user turns it on): a `Config` switch making `RelayConfig::allow` answer true (passes notes/api-design.md).
4. Port mapping (UPnP, NAT-PMP, PCP): optional, later.

## Decided (Tess)
- **Who relays**: every reachable node relays for its co-readers by default; for strangers only when the user turns it on. Relaying is a setting of an ordinary node, never a kind of node; no standalone relay program until needed.
- **Direct addresses**: a reachable node lists them in `reach.0`. IPs between nodes sharing data are fine; with a stranger they are exchanged only after consent (accepting an invite).
- **No default relay** in builds for now: a later product decision.
- **IP consent** (notes/questions-for-tess.md §17, reversible, not yet answered): punch only between nodes that share data; a stranger (a link's sharer) is dialed hidden until the invite is accepted. One predicate: osis `net.rs` gives `P2p::punching` the co-reader set; `|_| true` flips it.

## Open
- **A stranger can learn a target's IP** (security): hidden dials are the dialer's choice. Anyone holding a key and its relay (a link's holder) can send a plain dial: the relay answers the target's observed address and the target punches to the dialer. The target cannot refuse in the transport as built: dialers use ephemeral TLS keys and prove co-readership inside the session (spec/sync.md §10 Node keys), so a target-side `punching` has no key to judge, and a key claimed in the relay request is unproven. Proposed design: (a) a node dials co-readers `dial_as` its dialable key (link and other dials stay ephemeral); (b) the relay never passes either side's address to the other: its Dial answer is `0x00 ‖ addr` (the dialer's own), the forwarded stream starts with nothing, and the Hidden dial kind goes (one dial kind); (c) after the relayed TLS handshake each side sends, as the first bytes of the session, its own observed address if its `punching` accepts the peer's authenticated TLS key, else 18 zero bytes; both nonzero: the target punches and the dialer dials direct, as now. Costs: punching starts one TLS handshake later; the dialable key goes to the target (a co-reader, which knows it from `reach.0`); relayed connections all have the zero source at the target (per-source fairness: below) unless the relay passes an opaque per-dialer tag.
- **A link's relays can be the sharer's**: a redeemer reaches the sharer through relays the link names, so a sharer that runs (or colludes with) one learns the redeemer's IP. Same exposure as a link naming the sharer's host (hosts learn client IPs); a stated limit, not fixed by hidden dials.
- **One registration, one flow-control window** (security): every forwarded stream to a target shares its registration connection's 4 MiB window (the `quic` connection window; implementation, not spec). A few relayed connections whose bytes the target does not read hold all of it: ones waiting in the listener's queue (`ACCEPT_QUEUE`) or for room there, or sessions the node reads slowly. While they live (until accepted and read, ended past `MAX_FORWARDED` by newer streams, or the session's own timeouts), forwarding to that target through that relay stalls, the relay's header write for a new dial included (that dial waits instead of getting busy). `MAX_FORWARDED` bounds streams, not this; the relay's per-source rate only slows filling it. Fix: per-stream credit (the target reads each forwarded stream into its own bounded buffer and ends one past it), or a window above what can sit unread.
- **`Config.relays` cannot name an osis node yet**: a node's P2P listener binds `[::]:0` (a new port per run) and no API returns its `peer://` address; wants the fixed port of Next 1 and a way to read the address.
- Hidden dials all arrive with the zero address: the target's per-source fairness (`link::Slots`, `evict_for`) counts them as one source.
- Two nodes that both changed networks and share no live relay cannot find each other until one learns the other's new `reach.0` through a third node. A DHT is a later option.
- Switching interrupts the relayed session (one reconnect per P2P connection that punches late; on loopback the relayed path usually completes first). Moving the session without a reconnect would need in-connection migration, which the design rules out.
- Network changes are seen by route polling only (`lan::NetWatch`); a P2P listener's registrations renew once their relay connections time out (up to the 60 s idle timeout).
- A LAN listener on `[::]` relies on the OS making it dual-stack (Linux does by default); where it does not, IPv4 LAN dials to it fail.

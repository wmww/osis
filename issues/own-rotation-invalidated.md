# A node's own rotation stays established after its commit turns invalid
> Summary: `Provenance::Own` is sticky: a rotation a node made unaware of its own concurrent demotion (outside the demotion's frontier, so invalid everywhere) stays established and current at that node, an epoch no other node holds or counts, and can supersede there the epoch every other node uses.
> Tags: permissions, keys, engine

Found by `rotation::tests::forks_with_departures_settle_large` (osis-engine lib, tier 2), seed 23: peer 4, an admin of G, rotates read and admin; peer 0 concurrently demotes it to read. Peer 4's commit is outside the demotion's frontier, so invalid at every node, but at peer 4 its read epoch (n 2) is `Own`, current beside the valid newest (n 3), and only peer 4 holds it. spec/crypto.md §4 says the same ("established ... when it is the node's own rotation", unconditionally), so this is the spec's rule, not a slip.

Harmless there (a valid rotation made later is newer). Not at seed 51 of the same test: there the invalid own read rotation also supersedes, at its author alone, the epoch every other node counts current, so the author's only current read epoch is one no other node holds. A node demoted from admin to write that had rotated read so keeps wrapping its still-valid content under it. Nothing heals it: in its state the invalid commit's boxes are gone, so its epoch covers every departure, and the other nodes see it boxed at their newest, so none re-seals it. The test leaves a peer holding such an epoch out of its agreement checks. Likely fix: `Own` holds only until the node applies its own commit's validity verdict (an invalid own rotation commit unsets it, as `unset_applied` does for `Chain`), spec text to match.

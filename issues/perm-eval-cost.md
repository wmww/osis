# Evaluating the membership timeline: what is still not incremental
> Summary: A write appended to a group's membership history now costs about a quarter of a millisecond at 10^4 changes (was 20-80 ms), and a late write that applies nothing, with no drop found after it, costs no re-walk. Still costly: a late write that applies something early in a long history re-walks everything after it, a member new to a group evaluates it anew, and demotion frontiers grow with the remover's chain.
> Tags: permissions, node, performance

Repro: `cargo test --release --workspace --test it bench:: -- --ignored --nocapture` (`OSIS_BENCH_N=<n>` runs one size, for `valgrind --tool=callgrind`; `perf` has no event access on the dev box); node: `cargo test --release --workspace --test it scale::membership_change_and_open_cost -- --ignored --nocapture`. Run the bench alone: `bench_10k_edges` peaks at about 13 GB (each held set of the org at 10^4 is about 3 GB; parallel runs were OOM-killed silently).

Done: notes/permissions.md "Implementation" (`Timelines::append`, the found-order rule for D, idle late writes, shared kept states) and "Walk cost" (numbers).

Remaining, in order of expected payoff:
1. A late write that applies something re-walks everything after it (bench, 10^4, a write in the middle: 0.36 s against 0.6 s from scratch, load 18). Exact shortcuts would need the walk to detect that its state after some item equals the old walk's there; the states differ for good in the new write's own records (`applied`, `by_author_target`, `setter`), so a useful equality must be modulo those, which needs an argument per field. Untried.
2. A new node (author, or a member that may be one) or a new thing an earlier write names still evaluates the component anew (`Timeline::extend`, `Input::can_append`): a new node changes `xs` in earlier audits, so exactness needs care. Then the node re-judges every delta on it with a fresh memo (10^4 content commits: about 12 ms, mostly node-side).
3. Walk residue, from scratch (callgrind on `bench_certificates` with `--toggle-collect=osis_perm::walk::drive`, 10^4, 2.58G instructions): `Pass::roles` recomputed (`roles_expiring`, 27%: the full branch of `audit_fall` for each member of a restored team), `widest_changes` per cached node per change (9%), `reach_forward`/`reach_backward` per audit (7%). Certificates (3.0G at the end, 3.6G at the middle): `reach_backward` per (point, thing) is about half. Point queries still go through an overlay of up to 31 changes (`EdgesAt`); admins' deltas did not get faster with the shorter interval, so their cost is elsewhere.
4. Demotion frontiers grow with the remover's chain (spec/permissions.md §5.1): they list by commit ID (32 bytes each) every membership commit and roster snapshot among the remover's chain certificates, and, since membership commits use commit form, every membership commit of the demoted node it received on the things in scope; a long-serving admin's frontier can list thousands. Computing the list (`Timeline::certificates`) is about 0.7x an evaluate at 10^4. Bounding the listed chain by the newest roster snapshot of each chain thing is not exact, so it was left: (a) a membership commit before the snapshot can write edges on other things the snapshot does not replace, and carry membership-class parts judged by layer 2 (`/secrets`, `/keys`), whose coverage still decides their validity; (b) whether the snapshot is the thing's epoch start is a timeline outcome that can change after the frontier is written (a later demotion of its author drops it, or another node holds a different set), and then the earlier writes the frontier no longer lists are audited and dropped. An exact bound would need the frontier to name the snapshot and verifiers to treat the snapshot's coverage as fixed regardless of its later fate: a spec change to §5.1.
5. Compaction snapshots list every absorbed commit-form commit with its author (spec/crdt.md §8, 47 bytes each), so a `/secrets` snapshot grows with the actor's rotation count.

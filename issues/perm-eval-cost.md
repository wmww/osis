# Evaluating the membership timeline: what is still not incremental
> Summary: Appending to a group's membership history costs about a quarter of a millisecond at 10^4 changes; a late write in the middle that nothing later depends on is placed without a re-walk (3-4 ms at 10^4, was 0.36 s); a new member joins without evaluating the group anew. Still costly: late writes that audit or that later writes depend on re-walk everything after them, a new thing an earlier write names evaluates anew, and demotion frontiers grow with the remover's chain.
> Tags: permissions, node, performance

Repro: `cargo test --release --workspace --test it bench:: -- --ignored --nocapture` (`OSIS_BENCH_N=<n>` runs one size, for `valgrind --tool=callgrind`, not installed on every box; `perf` has no event access on the dev box; `bench_deltas`, `bench_late_write`, `bench_certificates` time one thing each); node: `cargo test --release --workspace --test it scale::membership_change_and_open_cost -- --ignored --nocapture`. Run the bench alone: `bench_10k_edges` peaks at about 13 GB (each held set of the org at 10^4 is about 3 GB; parallel runs were OOM-killed silently).

Done: notes/permissions.md "Implementation" (`Timelines::append`, the found-order rule for D, placed late writes and joining nodes, shared kept states) and "Walk cost" (numbers).

Remaining, in order of expected payoff:
1. Late writes still re-walk from their point when `Walked::insert` declines: one that audits (an explicit lowering), one whose author has no earlier held write on the target (falls are recorded only after one, so the old walk does not show the later falls; recording all falls would need leaf aliasing to map classes, a leaf's class differs from its owner's), one with a drop found at or after it, and one a later item depends on by the static rules (admin grants with later writes by the member's side, any edge with an invite in reach). The placement itself is still O(history) (10^4: 3.2-3.9 ms, 10^3: 0.5-1 ms; unprofiled): the later-item scan (`Walked::independent`), the undo-log and history splices and the mark shift. A dynamic check (re-judge only the dependent later items) is untried.
2. A new thing an earlier write names still evaluates the component anew (`Timeline::extend`, leaves); a saved walk restored after a new node joined is evaluated anew (`Timelines::resume` takes new things only as leaves).
3. Walk residue from scratch: 1.39G instructions at 10^4 (callgrind, `--toggle-collect=osis_perm::walk::drive`; was 2.58G) before the dense edge state (`graph::Dense`), which took 3000 writes from 386M to 178M; the last commit has no 10^4 profile. Certificates at 3000 writes 394M -> 116M; admins' deltas at 10^4 40 -> 3.5-6 ms (point overlays).
4. Demotion frontiers grow with the remover's chain (spec/permissions.md §5.1): they list by commit ID (32 bytes each) every membership commit and roster snapshot among the remover's chain certificates, and, since membership commits use commit form, every membership commit of the demoted node it received on the things in scope; a long-serving admin's frontier can list thousands. Computing the list (`Timeline::certificates`) is about 0.7x an evaluate at 10^4. Bounding the listed chain by the newest roster snapshot of each chain thing is not exact, so it was left: (a) a membership commit before the snapshot can write edges on other things the snapshot does not replace, and carry membership-class parts judged by layer 2 (`/secrets`, `/keys`), whose coverage still decides their validity; (b) whether the snapshot is the thing's epoch start is a timeline outcome that can change after the frontier is written (a later demotion of its author drops it, or another node holds a different set), and then the earlier writes the frontier no longer lists are audited and dropped. An exact bound would need the frontier to name the snapshot and verifiers to treat the snapshot's coverage as fixed regardless of its later fate: a spec change to §5.1.
5. Compaction snapshots list every absorbed commit-form commit with its author (spec/crdt.md §8, 47 bytes each), so a `/secrets` snapshot grows with the actor's rotation count.

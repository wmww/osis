# Evaluating the membership timeline: what is still not incremental
> Summary: A from-scratch evaluation of a group's membership history now takes about half a second at 10^4 membership changes (was 4-7 s); a write after the others, a late write and a restart reuse the walk (an open restores the saved walk in about 50 ms). Still costly: a late write early in a long history re-walks most of it, and each write appended to a group's history costs time proportional to that history.
> Tags: permissions, node, performance

Repro: `cargo test --release -p osis-perm --test it bench:: -- --ignored --nocapture` (`OSIS_BENCH_N=<n>` runs one size, for `valgrind --tool=callgrind`; `perf` has no event access on the dev box). Run the bench alone: `bench_10k_edges` peaks at about 16 GB (each held set of the org at 10^4 is about 3 GB; parallel runs were OOM-killed silently).

Measured (org bench: 311 nodes, 221 things, 10^4 edge writes by 10 admins; 16-core box at load 10-25, so +-50%): from scratch 0.45-0.8 s (main: 4.5-5.1 s; this branch before the round 6.4-7.5 s), one more write 30 ms, a late write at the middle 0.36-0.6 s, a role query 0.3 ms, a role at a past point 0.25-0.45 ms, `delta_valid` cold 0.2-0.4 ms (1000 deltas cold 11 ms with the per-node end-role memo), owner chain depth 64 evaluate 1.3-2 ms, a new thing (a leaf) under a team or doc with about 200 demotions 37-44 ms (its owner's demotions copied, notes/permissions.md; a re-walk from the first demotion took 0.4 s there). Done: notes/permissions.md "Walk cost", "Saved walks" (open restores each component's saved walk).

Remaining, in order of expected payoff:
1. Late arrivals early in the history: `extend` re-walks everything after the earliest new commit, and falls back to from scratch when a non-final walk reached it (any earlier restart past that point, or epoch-start changes) or a new author/member appears (`nodes`). Exactness for the latter needs care (a new node changes `xs` in earlier audits).
2. Appending costs O(component): `Timeline::extend` gathers every input again, checks leaves against every commit, copies the history to carry memo answers and kept states, and `Timelines::update` re-partitions (bench at 10^4: gather 4 ms, leaves 1, kept 1, resume 3; one more write 18-19 ms). At the node, 10^4 edge writes by one owner on one component take 81 s, 70 s in timelines (`scale.rs membership_change_and_open_cost`, `cost-stats` phases). A component evaluated anew (a member new to it) still re-judges every delta with a fresh memo; at 10^4 content commits that is about 12 ms, mostly node-side (perm's per-delta answer is a few memo lookups once `first_held` is found; notes/permissions.md Walk cost).
3. Walk residue (callgrind on `bench_certificates` with `--toggle-collect=osis_perm::walk::drive`, 10^4, 2.58G instructions): `Pass::roles` recomputed (`roles_expiring`, 27%: the full branch of `audit_fall` for each member of a restored team), `widest_changes` per cached node per change (9%), `reach_forward`/`reach_backward` per audit (7%), backward searches from the member and target when many nodes are audited (a restored team). Certificates (3.0G at the end, 3.6G at the middle): `reach_backward` per (point, thing) is about half. Point queries through the overlay (`EdgesAt`: up to 255 changes in two nested maps, rebuilt per point by `Timeline::advance`, consulted on every edge step of a search) made admins' deltas 1.6-2.8x slower than with the copied state (reviewer, interleaved: 50-71 ms against 18-37 ms per 1000); an overlay index per change (or a smaller checkpoint interval) would remove it.
4. Demotion frontiers grow with the remover's chain (spec/permissions.md §5.1): they list by commit ID (32 bytes each) every membership commit and roster snapshot among the remover's chain certificates, and, since membership commits use commit form, every membership commit of the demoted node it received on the things in scope; a long-serving admin's frontier can list thousands. Computing the list (`Timeline::certificates`) is now about 0.7x an evaluate at 10^4 (notes/permissions.md "Walk cost"). Bounding the listed chain by the newest roster snapshot of each chain thing is not exact, so it was left: (a) a membership commit before the snapshot can write edges on other things the snapshot does not replace, and carry membership-class parts judged by layer 2 (`/secrets`, `/keys`), whose coverage still decides their validity; (b) whether the snapshot is the thing's epoch start is a timeline outcome that can change after the frontier is written (a later demotion of its author drops it, or another node holds a different set), and then the earlier writes the frontier no longer lists are audited and dropped. An exact bound would need the frontier to name the snapshot and verifiers to treat the snapshot's coverage as fixed regardless of its later fate: a spec change to §5.1.
5. Compaction snapshots list every absorbed commit-form commit with its author (spec/crdt.md §8, 47 bytes each), so a `/secrets` snapshot grows with the actor's rotation count.

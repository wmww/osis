# Evaluating the membership timeline: what is still not incremental
> Summary: Appending to a group's membership history costs about a quarter of a millisecond at 10^4 changes; a late write in the middle is placed without a re-walk unless something forces one (2-5 ms when nothing later reads it; 0.1-0.3 s when over a hundred later items must be re-judged, about what a re-walk costs); new members and things named before their `/created` join by going on from where the walk meets them. Still costly: the late writes that must re-walk, re-judging many dependents, and demotion frontiers that grow with the remover's chain.
> Tags: permissions, node, performance

Repro: `cargo test --release --workspace --test it bench:: -- --ignored --nocapture` (`OSIS_BENCH_N=<n>` runs one size, for `valgrind --tool=callgrind`, not installed on every box; `perf` has no event access on the dev box; `bench_deltas`, `bench_late_write`, `bench_certificates` time one thing each); node: `cargo test --release --workspace --test it scale::membership_change_and_open_cost -- --ignored --nocapture`. Run the bench alone: `bench_10k_edges` peaks at about 13 GB (each held set of the org at 10^4 is about 3 GB; parallel runs were OOM-killed silently).

Done: notes/permissions.md "Implementation" (`Timelines::append`, the found-order rule for D, placed late writes and joining nodes, shared kept states) and "Walk cost" (numbers).

Remaining, in order of expected payoff:
1. Late writes that still re-walk (`Walked::insert`, notes/permissions.md): one with a drop of D found at or after it (found by an earlier walk of the round, whose state there is not kept); one a later item writes the same edge of (the later write's restore reads the new value; the difference runs along that edge's later writes, so exactness needs those re-judged with a changed edge record, untried); one whose thing's epoch start comes later; two ops on one edge; one whose own audit drops something new (D grows: unavoidable). A later item that does otherwise with it now only moves the re-walk to that item. Re-judging costs about 0.5 ms per dependent item at 10^4 (they are the costly items to walk: mostly explicit writes on team edges whose audits read many nodes), so it pays only for few dependents; past an eighth of a long rest the write re-walks (`SHADOW_SHARE`). `bench_late_write` at 10^4 (release, the prior binary and this one interleaved three times, box shared, load 7-32 and swinging): a read grant nothing later reads 3.1-5.5 -> 4.2-8.1 ms (noise); a read grant by the key actor at the top (no earlier write of its own on the doc) re-walked 0.14-0.45 s -> placed 8.6-20 ms; a removal (an audit, 142 dependents), an admin grant (144) and a write grant on a team (472) re-walked 0.14-0.65 s -> placed 0.09-0.35 s (one outlier 1.06 s at load 30): at the quieter pair 0.14-0.15 s -> 0.09-0.11 s. In `bench_10k_edges` the late write in the middle (an admin's read grant on a doc it had not written yet) 0.18 -> 0.05 s; the rest unchanged within the load difference. Cheaper next: a narrower static dependence (most dependents are flagged because a node that may reach a team member could be audited on what the new edge reaches; the dynamic reach check skips none of them in the bench), or re-judging only the audit pairs (x, n) the new edges touch. The plain placement is about 2.1 ms at 10^4 at low load: the later-item scan about 0.75 ms, the log splice about 0.55 ms (undo entries are 152 bytes; boxing the applied records would cut it a fifth), item and kept-state shifts about 0.35 ms.
2. A thing named by an epoch start's roster whose `/created` arrives late, a new node owning a thing walked before, or two components merging (new snapshots) still evaluate anew.
3. Walk residue from scratch: 1.39G instructions at 10^4 (callgrind, `--toggle-collect=osis_perm::walk::drive`; was 2.58G) before the dense edge state (`graph::Dense`), which took 3000 writes from 386M to 178M; the last commit has no 10^4 profile. Certificates at 3000 writes 394M -> 116M; admins' deltas at 10^4 40 -> 3.5-6 ms (point overlays).
4. Demotion frontiers grow with the remover's chain (spec/permissions.md §5.1): they list by commit ID (32 bytes each) every membership commit and roster snapshot among the remover's chain certificates, and, since membership commits use commit form, every membership commit of the demoted node it received on the things in scope; a long-serving admin's frontier can list thousands. Computing the list (`Timeline::certificates`) is about 0.7x an evaluate at 10^4. Bounding the listed chain by the newest roster snapshot of each chain thing is not exact, so it was left: (a) a membership commit before the snapshot can write edges on other things the snapshot does not replace, and carry membership-class parts judged by layer 2 (`/secrets`, `/keys`), whose coverage still decides their validity; (b) whether the snapshot is the thing's epoch start is a timeline outcome that can change after the frontier is written (a later demotion of its author drops it, or another node holds a different set), and then the earlier writes the frontier no longer lists are audited and dropped. An exact bound would need the frontier to name the snapshot and verifiers to treat the snapshot's coverage as fixed regardless of its later fate: a spec change to §5.1.
5. Compaction snapshots list every absorbed commit-form commit with its author (spec/crdt.md §8, 47 bytes each), so a `/secrets` snapshot grows with the actor's rotation count.

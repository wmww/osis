# Node-core residue: membership-heavy changes
> Summary: Granting someone new to a large tree re-checks every change in it (about 70 ms at 10^4 changes; linear); a validity flip re-reads every held change of the aspect; opening still reads every commit header and re-adapts every membership change from the index (O(commits), no bodies decoded); ingesting a first sync of 10^4 commits takes minutes.
> Tags: node, permissions, performance

Repro: `cargo test --release -p osis-node --test scale -- --ignored --nocapture membership_change_and_open_cost`.

Done (notes/node.md: Validity, Snapshots vouch for nothing, Snapshots, Import, Open, Rollback): saved membership walks restored at open, imports from compaction snapshots with the origin's schema, element-level judging of snapshot-carried writes, deaths in every held body carrying a write, the persisted index, journaled rollback, re-judging per changed timeline, `Timelines::update_touched`, `/groups` incremental, the deletion and re-snapshot queues removed, perm's reading of membership commits persisted (`node/edges`: open decodes no body).

Remaining:
- A change that perm evaluates anew (a member new to the component joins it, an out-of-order or dropping write, an epoch start change) re-judges every delta of the component: for one person's tree, every delta (perm's component granularity; issues/perm-eval-cost.md item 3 would give per-(node, thing) answers).
- A validity flip rebuilds the aspect from every held body (O(aspect history)); re-merging needs them (a register's earlier value comes back only from its body), un-merging alone would not.
- Open is still O(commits), not O(what changed): at 10^4 content plus 10^4 edge writes 0.28-0.30 s (notes/node.md Open): every commit record's head and header decoded into `Core::commits` (about 120 ms with the metas: the engine holds every header in memory), every membership commit adapted from its `node/edges` row (about 90 ms; `edge_of`'s typed read is a third of it), the saved walk's inputs re-gathered for its tag (about 57 ms). O(changed) needs `Core::commits`, the held set and the per-aspect indexes loaded lazily, and a walk tag that does not re-gather its inputs (e.g. over a persisted hash of the commit set): a redesign of the engine's in-memory indexes.
- Ingesting a large batch grows faster than linearly: a reader's first sync of a label of 10^3 content commits spends 2.5 s in `Engine::ingest` for the batch of 1024 (`sync::inbound::open_entries`); the first sync of 10^4 takes 545 s though its passes are cheap now (`scale.rs sync_pass_cost`; not profiled: no perf or ptrace on the box).

# A key with several entries: a removed element shows again, and the sweep misjudges
> Summary: Under one map key with several live entries (concurrent puts), a path op writes into the lowest live entry (spec/crdt.md §5.6 Ops), so an element's removal can sit in another entry's record than its creation; a removal of that entry by a node that saw only it brings the deleted element back in an honest history (breaks "a removal is final", spec/requirements.md Data model). The sweep, judging record by record, also resets elements the key still shows (`tests_life::sweep_laws_spec_sync_7`).
> Priority: normal
> Tags: crdt

Honest reproducer (osis-crdt ops, map of `list<int>`, checked by hand): x and y put `k` concurrently (`[1]` and `[2]`), so `k` reads `[2, 1]`. z, holding both, writes `k = [1]`: its delete of y's element goes into the lowest live entry, x's record. w, who saw only x's put, removes `k`: x's record is reset (z's delete with it), y's entry survives as a concurrent add. `k` now reads `[2]`: the element z deleted is back. Any app with two writers creating one key offline then editing and removing it can show this.

The sweep (spec/sync.md §7) assumes removal is final and judges each live record alone (with its key-erased record), so it resets an element that shows in the key's read when its creation sits in another record: another live entry of the key (seed 2990), or one not live yet because its entry's creation has not arrived (36965). Judging the join of the key's live records instead pulls in another record's list reset (fails at 35189) and still misses records not live yet. `sweep_laws` fails at about 9% of `OSIS_CRDT_SEED` values (5, 25, 2990, ...: the map-of-list types reach a key with two entries easily), always at "the view's read" or "the read of a node holding everything"; reproduce with `OSIS_CRDT_SEED=5 cargo test -p osis-crdt --lib -- sweep_laws` (the committed seed passes, and it is all the gate runs).

The outcome is fixed by the requirements; the choice is internal crdt design. Either makes per-record sweep judgment sound:
1. **Writes follow what they touch** (keeps identities; preferred): a path op into an existing list element or nested entry under `k` writes into the live record holding that target's creation (the outermost element or entry on the path); a reset with no single target (a nested collection's reset) goes into every live record of `k` holding a write it prunes, as `remove(key)` already puts its stamp on each; only new creations and value writes at the key itself go to the lowest live dot. A record's removal then takes exactly the writes made into its own content. Changes: §5.6 Ops lines, the path routing in `ops.rs`/`seq_diff.rs` (one record per write target instead of one per key), diff against the key's joined read mapping each element back to its record.
2. **One entry per key**: a write to a key with several live entries first collapses them: it resets each and writes the key's merged read as a fresh entry (the `replace` path). Uniform and small, at a cost on that rare path: fresh dots, so edits concurrent with the collapse are lost (allowed: an edit concurrent with the removal of what it is in) and inserts anchored on old elements land at the end; text under the key loses concurrent typing; one value rewrite per conflict.

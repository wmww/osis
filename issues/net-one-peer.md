# One kind of peer
> Summary: A node has two kinds of peer (saved peer, the old host; direct peer, a co-reader) behind the one hub session, local passes besides; one listening key (built, 3d) and one store (built, 3f). Make one: one key, one blind store and serving path (the hub, fed public data by node sync) that opens by key proof alone, consent by the accounts a node admits, each writing the sync IDs it wants kept into a keep list the node's account shares with it (data, no new message kind); peers chosen in each account's private list and listed on its profile, never in group data; then the API (`SyncId` out). Steps 6-8 designed with build steps 6a-8. The concept unification the rename waits for. Part of issues/net-rework.md.
> Priority: normal
> Tags: node, sync, host, proto, api, spec, tess-call

| | Saved peer (old host) | Direct peer (co-reader) |
|---|---|---|
| Found by | fixed address in `label.0`, link and card text | `reach.0`, LAN, a link's sharer |
| Who can be one | a node with `host^.0` that admits the label | a node that reads the group |
| Serving code | `ServingSession` in the hub (`osis-host`, `HostStore`) | the same hub session, node sync above it serving the stream; local passes when no host is listed (notes/peers.md) |
| Store | the node's one store (the hub's: entries, blobs, the node log) | the same (3f) |
| Key | the node's one key (the dialable key) | the same |
| Opens by | sync key, claim, static entry | those for a peer that cannot read; between readers nothing opens, the shared set's members are pulled (notes/peers.md, The stream) |
| Registration | first come, by parent's delete key | steps recorded in `label.0`, plus valid child steps peers register; new labels refused |

## Steps, in the order of what they unblock
1. **An address names a node** (built with 3d): a peer is dialed by key with hints (spec/sync.md §10, spec/wire.md §10): a `peer://` saved peer or label host is a host like any address (sim `no_server::a_peer_address_saved_peer_dialed_by_key_syncs_spec_sync_10`).
2. **One listening key per node** (built, 3d): the dialable key serves sync, data the node cannot read and the client port; dialers stay ephemeral; LAN listeners keep a fresh key per network join (issues/net-connect.md), served by the same path. A reader finds a sync ID by a peer's filter and opens it there, so the filter goes on the key that serves unread data. `Osis::listen` binds more addresses under the one key; a client is cut off by its own entry (issues/client-auth.md); key rotation is `rotate_peer_address`, by hand only, moving every listener. The client port keeps its own access rules: Auth before any request, client actors, the main-actor tier only from `Peer::Unix` (notes/client-port.md).
3. **One serving path**. Principle: one connection, one session, one store answering it; every secret above it, in node sync.
   - **Session owner**: the hub (`osis-host`), one `ServingSession` per connection, every listener and, from build 3i, every dial. The node's driver owns the transport secret and the listeners and drives the hub sans-I/O in node sync's own loop (as the simulator's `host_of` does), so node sync reads the hub's store directly (public data flows up) and the two exchange messages by function call, not by channel. Node sync is the session's upper layer on every connection, as it is for the client port.
   - **Routing** (kind: who answers):

     | kinds | answered by |
     |---|---|
     | Hello, Ping/Pong (2-3) | the session |
     | Upload (10, Status 11), Delete (14) | the hub's store, for a sync ID node sync opened on this connection by sync key (below) |
     | Register (7) | the hub's store, by admission alone (steps verify themselves; relayable, spec/sync.md §5) |
     | Fetch (19-20) with a node-range id, any answer with a node-range id | node sync (it reads the bodies from the hub's store) |
     | Stranded, Suspect (30-31), Prove/Proved, Resume/Resumed (32-35), shared set (36-40, 45-46), stream (41-44) | node sync |
     | client port (24-29) | node sync, by the port's access rules |
     | Open/Opened (4-5), Deposit/Budget (12-13), Sync/Reconcile (15-18), Fetch without a node-range id, Subscribe/Unsubscribe/Push (21-23), Path (8-9) unless build 3h uses it | gone (build 3i): an open is a Hit, a deposit an Offer item, reading the stream |
   - **The hub calls up for nothing**: it judges no open and holds no secret, filter or record. Up: every message of the table's node sync rows, a connection's start with its binding (listener key, both challenges, transport peer, source), its end, and store changes (a head moved, entries logged). Down: messages to send (node sync's requests within the session's request window, answers at once), `open(conn, L)` and `close(conn, L)` (the session's gate for the store's kinds; a new head's sync key closes it there, as `still_open` does), public data for the store (below), and closing a connection.
   - **Flow control**: one request window per connection covers both layers: a request handed up counts against the peer's `MAX_UNANSWERED` until node sync answers it (as client-port requests do now), and node sync's stream pushes wait for the session's room (`WantRoom`/`Room`, as Notify does), not sent past it.
   - **Opens**: all node sync's, one S per connection (issues/net-shared-set.md). Between readers by read secret, ByRole or static entry; at a node that cannot read L, by a Hit on the head's sync key with an open signature (over the other end's challenge and transport key, whoever dialed), a key actor's static entry (answered with `EntryGrant` from the hub's claim sets) or a Deposit item after a deposit-key hit (put through the hub store's deposit rules, spec/sync.md §5). The filter's entries for a sync ID the node cannot read (sync key, deposit key, the head's claim-set static entries) come from the hub's store and go to every connection; `changed_at` moves when such a head moves. Upload and Delete are taken only under a sync-key open, Register by admission alone: readers do not upload to readers.
   - **The store**: one (step 4), with one node-wide log the stream serves (issues/net-reconnect.md), per-label logs gone. Node sync writes its own and received entries there as a client; for a sync ID it reads it hands the hub the steps recorded in valid `label.0` (no first-come registration there; issues/net-role-sync.md, Replacement), and the hub takes Register only for sync IDs node sync does not read. Admission (`host^.0`: `open`, `labels`) decides which unread sync IDs the store keeps until step 6; `own` goes, since a node reading its own groups serves them as a reader to their holders.
   - **Readers treat a node that cannot read as a peer**: dial it by key (step 1; addresses as issues/net-connect.md, and `label.0` hosts until step 7), Hit, pull its stream, keep `known` (issues/net-reconnect.md, Peers that cannot read), and judge uploads, registration, promotions and deletes over `known`: one pass rule over `sources(L)`, a local pass being its empty case (issues/net-sync-structure.md (e)). The host client paths (Open, per-label Sync, Subscribe, fills, refusal back-offs) and replication between hubs go (replication is sync with a peer; between two nodes that cannot read, step 6).
   - Sync ID replacement (index > 0) goes last (build 3j; issues/net-role-sync.md).
4. **One store** (decided for 3f: the engine reaches the blobs in the hub's store; an engine transaction touching blob ciphertext opens one there, committed first, and the reconcile at open makes any crash point converge; app reads of large values read it directly; one set of store rules for every row, admission governing unread sync IDs only; replication to `replicate` peers only for unread sync IDs until step 6): ciphertext (entry rows with wrap and stamp, blobs, the node log, served steps and claim sets) in the hub's store, shredding on delete (notes/serving.md, Decisions); plaintext and secret-derived state (an entry's kind, certificates, `changed_at`, records, read secrets) in the engine's. `changed_at` takes its own sequence there (it fingerprints credentials, so it stays out of the hub; only `acked_pos` and `judged_pos` compare with it). A group a node reads and serves is held once. The hub's store is the truth for ciphertext and the engine's state a cache of it: an entry in the hub's store with no engine state is derived again, engine state with no ciphertext row is dropped, so a crash between the two commits converges. `host^.0` going drops the unread sync IDs (shredded), not the store. Node sync reaches it by direct calls in one loop (step 3), so no hop on hot paths; the cost to check is commits per inbound batch (two stores), counted at n and 10n. Built inside step 3's order (3e, 3f): the stream can serve unread members only from one log.

5. **Keep the boundary**: the code serving data a node cannot read cannot decrypt (`osis-host` has no engine or keys; tools/policy.py `host_blind`). With one path it serves readable data too, so the boundary is the crate: node sync stays the only reader, the hub keeps no secrets and the policy check carries over to the renamed crate.
6. **Consent**: who may store data a node cannot read on it (below, Consent). By default only the node's own account, whose nodes read what they serve, so nothing unread; anyone else's is opt-in, by the accounts the node's own `host^.0` admits, written by its operator. Which sync IDs an admitted account wants kept it writes into its keep list, a thing the node's account shares with it. Two nodes keeping L unread share it only where the account's keep lists named each to the other.
7. **Peers that cannot read** are the account's private choice (a peer list on its devices actor D) and listed with their addresses on its profile for its contacts to dial, never in group data (below, Listing). Own nodes keep both current when such a peer's key rotates. Which sync IDs a connected peer serves is found by the shared set (its filter of sync-key, deposit-key and claim-set entries, issues/net-shared-set.md Peers that cannot read), so a group's holder who is not the listing account's contact finds the peer wherever it can connect to it (a LAN, an address it knows) and never needs the listing.
8. **API** (below): `peers(g)` one list; `sync(g, peers)` adds to it; `set_serving` only limits (which accounts, how much); `SyncId` and `sync_ids` leave the public API (decided). Per-sync-ID admission is internal: what own nodes write into the keep lists of the peers their list names.

- **3h2 Readers write to it** (after 3h1). Principle: **a reader writes to a peer that cannot read L only over what that peer's stream showed it (`known`), in one pass per label that judges its own store once and then each such peer; no Open, no write acknowledgement counts as presence.**
  - **Sources**: `sources(L)` are the connected peers that cannot read L where this node opened L by a sync-key or claim Hit (3h1's `read_as_host`) and whose stream has read L to that peer's log end on this connection (`box_read`: uploads and deletes wait for the first read through its last page). Peers that read L are never sources (readers do not upload to, register at or delete at readers). The source's head is the step whose credential its Hit used, moved by the stream's head events.
  - **Credential**: a reader tests, at each arrival of every peer's filter, one credential per sync ID it reads: of the newest recorded head (`label.0`'s served path), its sync key when it holds that epoch's read secret, else its claim key while the step's claim set is held, else its static entry. Holding none of them, L is stranded for it (spec/permissions.md §4): it tests, Hits, walks and registers nothing for L (sim `member_churn` seed 4 on 3h1 is this case: it must end Failed, not loop on Opens).
  - **Stale head** (the peer holds L at an older step): found only at a peer listed for L (`label.0` hosts and saved peers until 7a; keep-list peers from 6a). Trigger: L is not open there after the peer's latest filter was tested (its filter shows no credential of L this node holds, or the Hit was refused: code 14 counts as not shown, until the next arrival), no Register of L is in flight there, and L's registration back-off at that peer (refused for now: `retry_ms` doubling to `resync_ms`, as built) has passed. Then the **walk**: the credentials of the recorded path's earlier steps, newest first, each distinct one once, against the same filter. The first shown is Hit; L opens at that step; the pass there (below) registers the rest. None shown: Register the recorded path from genesis, one step per Register in order, each with its claim set when held. A genesis answered 9 means the peer holds L at a head off this node's recorded path (ahead of it, or a fork): the Open walk (interim, below). Refusals 4, 12, 14 start the back-off; `Refused` status as built.
    - Cost: a peer on the newest head costs one test per sync ID per arrival whatever the number of steps. A walk costs one test per distinct recorded credential, once per registration attempt at a listed peer missing L (attempts backed off), never per arrival. Testing every recorded step at every arrival was rejected: steps × sync IDs × arrivals × peers, at every peer that merely shares nothing.
    - Who moves it: any reader holding the recorded path. Steps are signed by their parent's delete key, so Register needs no secret and no open (spec/sync.md §5: relayable by any node). The peer checks §5 Register as built (`prev` is its head, signature chain, claim-set hash, admission, caps, rate). Only an admin issues a new step: a child of the source's head when `step_due` against it and `label.0` records none (`reregister`, unchanged but for where the head comes from), a child of the served head when there are no sources (the local rule). Any registrant first sends, under the source's head keys, the role commits of L's actor that `known` lacks (stamped by a writer, else relayed or deposited as any body), then the recorded children of the source's head, in that order on the connection.
    - Entries under the old head stay (accepted stamps stay valid, spec/sync.md §5 Stamp). The member opened at the old head ends at the head's event. The next filter generation (its `changed_at` moved) shows the new head's credential, and the reader Hits it and rejoins from where it stopped. `known` is unchanged, so nothing is listed again.
    - The 3i routing row follows: Register is taken by admission alone, never gated on an open; 3i gates Upload and Delete only.
  - **Uploads**: per source, each must-hold body `known(s)` lacks (or shows under a wrap that counts as lacking, §5 Wraps at a node, a deposited entry for a writer holding it stamped included), once a connection while in flight (`sent`), as today's send order (stamped by a writer, else relayed under a stamp the source's head verifies, else deposited). An Upload's OK marks nothing: only the stream's Added does (a store restored from a backup has lost what it acked). The echo of an own upload is what marks presence, inverting 3h1's rule (`entry_status` no longer calls `host_holds`). Refused for now and code 9 as built. Code 6 (tombstoned) marks the entry gone at that source as `y/g` does.
  - **No bytes it holds**: an entry whose blob `known(s)` shows held at s under any sync ID goes without its bytes (the store keeps one blob per blob ID, 3f). An edit in a group nested in several groups s keeps then costs its bytes once, plus an entry under each sync ID, and a subgroup joining a group costs entries alone. Reveals nothing new: the shared blob ID already shows s which sync IDs share it (notes/whole-commits.md). Wire: `entry`'s blob becomes `Opt(blob)` beside a `blob_id` (spec/wire.md §11.2). A missing blob there is code 9-like refusal "bytes wanted", after which the uploader sends them. Test: `an_edit_in_a_group_nested_in_three_sends_its_bytes_once_spec_sync_3` (bytes sent counted at 1 and 3 enclosing groups).
  - **Promotions**: a writer stamps a deposit it would promote in its own store (today's `local_promote` rule, run with or without sources); a source whose `known` shows that entry deposited counts as lacking it, so the ordinary upload promotes it there. "No other entry holds the delta stamped" is judged over the source's `known`. One promotion rule replaces `promote` at a host and `local_promote`.
  - **Deletes**: only a holder of the needed delete key or level keys sends a Delete, of each entry `known(s)` lists that its own judgment finds must-not-hold, once `known(s)` shows the carrier (issues/net-reconnect.md, Deletes). A node without the key sends nothing, and the entry stays there until a holder connects or it expires. The stream's Deleted events are not acted on, as built. Clearing deposits (`DEPOSITS_WAITING`) counts per source over `known(s)`.
  - **Deposits**: every deposit to a peer that cannot read L goes as a Deposit item (`[2, L, blob, wrap, sig]`) of an Offer, as many as fit one Offer: an inbox delivery, an outbox role write, a non-writer's body deposit. It goes on a connection whose peer's latest filter shows L's deposit key, which opens nothing. Kind 12 is no longer sent. The peer takes it by its Deposit rules (built in 3g); 0 ends it there; refused for now (4, 5, 12) is sent again after the §5 Sending back-off; 14 is handled as built. An outbox entry ends per listed address as today. Spec: §10 Deposit items name any deposit at a node that cannot read L, not only inbox blobs with no host; §5 Sending likewise.
  - **One pass**: per label, the own part runs once: judgment over the work set, placing in its own store, certificates, stamping and promotion, local deletions, reseal, and a step when there are no sources. Then, per source: registration, uploads, deletes and clearing over `known(s)`. With no sources it is the own part alone. `pass_at_host`/`judge_label` versus `local_pass`/`judge_local`, per-connection work sets (`LConn::work`) and the label-host (`hostless`) branch go; a source opening or listing again marks the label's one work set full. `host_holds` as a presence writer goes. Its tombstone rule (an Added within this node's tombstone recorded again quietly, so the pass deletes it there) stays as part of applying an Added. Placed (spec/sync.md §5) reads `known` at a source in place of "present at a host". Expect fewer passes: one per label change whatever the number of sources, and no pass on an upload's status (`scale::a_change_costs_a_few_passes`, left by 3h1, is retested here).
  - **Ends**: "readers open a peer twice on one connection" (Open is no longer a write path); "a client's upload to a sync ID the node reads lands as a row" for honest readers (they stop uploading to readers; 3i refuses it). **Starts**: a reader whose recorded path does not reach the peer's head (a genesis answered 9) walks it by Open, kinds 4-5 kept for that alone (to 3i, which needs its replacement: Unsure); `known` of a peer that proves no known actor is kept by that peer's listening key (3h1's `BoxAt` and `y/p`; to 6a, when such peers prove their account and keep a record; otherwise per connection, issues/net-reconnect.md Limit).

    - Scaling: `filter_tests_per_arrival_do_not_grow_with_steps` (n and 10n rotations: tests per arrival equal; a walk's linear, once per attempt); `one_pass_judges_a_change_for_every_source` (1 and 3 sources: the same judgments).
- **3i The host protocol goes**: Upload and Delete taken only under node sync's open (Register by admission alone, 3h2) (above, 3g); kinds 4-5, 8-9 if unused, 12-13, 15-18, 21-23, Error 15, `osis_proto::rbsr`, per-label logs, replay and `log_keep`; `Replicator` and `replicate`; `ClientSession`, so a dialed connection is a hub session like an accepted one (issues/net-sync-structure.md (a)); spec/sync.md §5 Open, §6 First and Cursor sync, §8, spec/wire.md §11.3. Tests: a node that cannot read L and dialed a reader of L takes its uploads; remnant grep.
- **3j Replacement goes** (issues/net-role-sync.md, Replacement).

Interim states, each ended by the step named: readers open a peer that cannot read L twice on one connection, by a sync-key Hit (reading) and by Open (writing; to 3h2); a reader whose recorded path does not reach a peer's head of L walks it by Open, kinds 4-5 kept for that (3h2 to 3i); `known` of a peer that proves no known actor kept by its listening key (3h1 to 6a); a client's upload to a sync ID the node reads lands as a row node sync derives an entry from (to 3h2, when readers stop uploading to readers; 3i refuses it with the write gate); the store's totals count node sync's rows, so a heavy reader takes less for others (to step 6); stream pushes held for room only on served connections (to 3i); two logs in the hub's store (3e to 3i); `ClientSession` on dialed connections, so a node that cannot read and dialed a reader takes no uploads (to 3i); no replication between two nodes that cannot read (3i to step 6); a saved peer or label host naming a node that neither reads L nor admits it refuses its Register as any host outside its admission does (its readers sync with it only by the shared set, if they share L; to step 6, consent).

## Consent (step 6)
Principle: **a node keeps a sync ID it cannot read only while a keep list it reads names it for the node, written by an account its admission names, and drops it when no such list names it.** Admission names accounts, never sync IDs; which sync IDs is the admitted account's data, shared with the node like any group.
- **Whose node**: a node keeps L unread for account A only while a keep list A writes names L for it; the node belongs to whichever account runs it (issues/account-signing.md (c)), and the rules don't depend on whether that account also reads other groups there. A node's settings are its own account's data, which it always reads.
- **Keep list**: a thing whose first admin is the keeping node's account B, a group of its own (its own sync ID, so its only readers are B's nodes and the account A it keeps for), with `keep.0`: `map<blob, set<blob>>`, a sync ID to the keys of the nodes that keep it (one key, or several that replicate it: Two nodes keeping L unread, below). One per admitted account A, A granted write on it (per-thing roles: nothing new in spec/permissions.md). A's nodes write it; B's nodes read it.
- **Admission** (`host^.0` on the node thing, written by the node's account, its operator's choice): `admit` is `lists` (a set of keep-list tids) or `open`, plus `policy`. `labels`, `caps` and `replicate` go. An account is admitted while it holds write on a keep list `admit` names; the node's own account always is (its nodes read every group they sync, so a node with no setup keeps nothing unread and serves its own groups as a reader, 3f). Absent `host^.0` admits the own account alone.
- **What the node keeps**: L, unread, while some keep list `admit` names, on which an account other than its own holds write, maps L to a set holding the node's own key. Node sync reads its keep lists as any group it reads and hands the hub the union (`Down::Admit`, `Down::Drop`; `Admission::Only` no longer comes from `host^.0`). A kept L takes Register of its genesis or recorded path by admission, as any admitted sync ID. Under `open` a Register needs no keep list (first come, ended only by the sync ID's own deletes and expiry, as built); keep lists are still read.
- **Release**: L goes, every row shredded (`HostStore::drop_labels` for one sync ID), when no keep list names it for the node: its entry or the node's key removed from it, or its last writer's role on the list removed (an account leaving the admission takes its groups), or the list leaving `admit`. Nothing else ends it: no lease, no clock, no liveness.
- **No circularity**: the keep list is a group the keeping node reads, so it syncs between that node and A's nodes as between any co-readers (spec/sync.md §10, the shared set), needing no admission; its label is kept because the node reads it, like any group a node reads. The grant on it reaches A as any grant between accounts that know each other: its inbox blob, deposited between readers on a connection that proved A (issues/net-shared-set.md, Deposits), after which A's nodes open it by its read secret.
- **What a kept L covers**: L as a whole. Any connection that opens L by its sync key (a reader of any account) uploads, deposits and deletes there by spec/sync.md §5, within the policy. Consent is to the admitted account's group, its other holders' writes included. A delete-key holder deletes at every node L opens at, own or not (issues/net-reconnect.md, Deletes): a delete frees storage and needs no consent.
- **Who writes**: a node of A, for each peer A's peer list names whose account B is known (Listing) and whose keep list it holds (the one tid on which A holds write and whose first admin is B): it adds the live sync IDs of the groups listing that peer (every group A syncs here, home included, for an every-group peer) with the peer's key, whenever it finds one missing, and removes the peer's key (the sync ID when no key is left) for what the peer entry's `released` set names (Listing). A sync ID it can place in neither stays: nothing is inferred from absence, so a stale sibling never removes what another wants kept; one that adds a released sync ID before it holds the release removes it once it does. Several nodes of one account B share A's one list there, each keeping what names its key.
- **Known actor**: an admitted account is known at the node (spec/sync.md §10, Known actor), so the node proves its own account back and the two keep a record (issues/net-reconnect.md). The owner's nodes know the node's account by its peer entry (Listing).
- **Totals**: the hub's totals and caps count only rows of sync IDs node sync does not read (ends the interim "a heavy reader takes less for others").
- **Refused**: a Register outside the admission is code 14, as built; a keep-list write by an account without write on it is invalid and keeps nothing. Status shows `Refused` naming a listed peer of a known account where A holds no keep list from that account, or the peer refused a Register.
- **Bytes**: no new message kind. Rotation's one (spec/wire.md §11.2, node kinds; spec/sync.md §10):
  ```
  Moved    [47, 0, address]                              (unanswered; Listing, Rotation)
  ```
- **Two nodes keeping L unread** share it exactly while each keeps L by a keep-list entry naming the other's key: A listed both for L's group, so nodes of one account keeping L unread replicate it, and a node no entry names (a stranger's, another account's node keeping the same group) opens nothing. A node keeping L by an entry naming key k dials k under its listening key (the one dial that is not ephemeral, only to keys an entry names: both ends' keys are A's word, shown to each by A's choice), tests its sync-key entry of L against that peer's filter and Hits with no proof; the receiver opens L when an entry for L in its own keep lists names its key and the connection's transport key. Both pull; Added entries go into the hub's store by its Upload rules (stamps checked) and deposited ones by its Deposit rules; a Deleted does nothing (only a right holder's drop counts). Limit: two such nodes whose accounts do not know each other keep no record (first contact per connection, issues/net-reconnect.md Limit).

## Listing (step 7)
Principle: **the peers an account syncs with are its private choice; its contacts see only where to dial.**
- **Peer list**: `peers^.0` on the account's D (read by its nodes only, under D's home label): `map<blob, peer>` by the peer's key; `peer = struct { urls: list<text>, every: bool, groups: set<tid>, account: option<tid>, released: set<blob>, gone: bool }`. `every`: a peer of every group the account syncs. Written by `add_peer`, `remove_peer`, `sync(g, peers)`, and by a node of the account on a `Moved` and on learning the peer's account (the first connection where the listener at that key proved one).
  - `released`: when a group stops listing a peer (or the account stops holding a group an every-group peer serves), the writer puts that group's sync IDs there; `remove_peer` from everywhere sets `gone` (the peer's key leaves every entry of its account's keep list). Kept for the entry's life (16 B a sync ID), so a node holding neither the group nor the release never guesses. A peer of the account's own nodes (a node on D's roster) is no entry: own nodes find each other by `reach.0` under D's home label (issues/account-signing.md step 8).
- **Profile listing**: `peers.0` on the account's profile, `set<address>`: every entry not `gone`. Written in the commit that changes the peer list's set of addresses; a node that finds the two differ (concurrent writes) writes it again. For dialing only, never proof.
- **Not in group data**: `label.0`'s `hosts` and `keys.0`'s `inbox.hosts` go; `sync` writes nothing on a group; inbox blobs carry no host addresses (spec/sync.md §3 Following a payload label: no dial). Links and contact cards keep their connect hints (the sharer's text).
- **Dialing**: own nodes dial every entry (every-group always, a per-group one while one of its groups syncs here) and write its keep list there (Consent, Who writes). A node dials the listed peers of a contact account holding a role (by the rosters held) on a group it syncs, kept while its shared set holds something (issues/net-connect.md, Keeping; a priority, never a filter). What opens is the shared set's sync-key Hit.
- **Rotation**: a node that cannot read some sync ID it keeps by a keep list and rotates its key (`rotate_peer_address`) keeps the old listener, answering a dialer that proves an admitted account only with `Moved` (the new address) and serving nothing else, until each admitted account was told once or `MOVE_WAIT` passed. A node of the account receiving `Moved` rewrites the entry's key and urls and the profile listing in one commit, and the old key to the new one in every keep-list entry naming it; siblings follow by D's label, contacts by the profile's. `MOVE_WAIT` passes notes/arbitrary-values.md (0: an owner offline at the rotation adds the peer again by hand; infinity: the old key never retires). A node keeping no sync ID unread by a keep list rotates by issues/net-connect.md (The listening key).

## API (step 8)
- `peers(g) -> Vec<Address>`: the peers this account syncs g with by its choice, every-group ones then g's own. Connected co-readers are status (`sources`), not peers.
- `sync(g, &[Address])`: g synced here (admin only to make its first sync ID, as now); the peers join g's own list, so any holder adds a peer to a group it does not administer (audit row 26). No `Invalid` for a group that syncs with other peers.
- `add_peer(&Address)`: a peer of every group this account syncs. `remove_peer(&Address, PeerScope)`: `Every` removes it everywhere (its key leaves every keep-list entry); `Group(g)` from g's own list only. Adding to one group is `sync`'s, which also syncs it: no second way.
- `saved_peers` becomes `every_group_peers()` (tracked read of the every-group entries).
- `serving() -> Serving`, `set_serving(Serving)`: `Serving { admit: Admit, policy: ServingPolicy }`, `Admit::Accounts(BTreeSet<Tid>)` (default empty: the own account alone) or `Admit::Open`. No `Option`: admitting nobody else is the default, and `set_serving` makes each newly admitted account's keep list (a group of the node's account, the account granted write) and names it in `host^.0`; removing an account from `Accounts` removes its grant there, which drops what its list named. `serving()` reads the accounts from the named lists' rosters. `SyncId`, `sync_ids`, `Serving::{admitted, caps, replicate}` and `ServingCaps` go, with port methods and CLI commands (`serve --admit <account> | --open`).
- The owner side never calls `set_serving`: `sync(g, peers)`, `add_peer` and `remove_peer` write its keep lists (Consent, Who writes).
- Status: `Refused` names the listed peers whose account gave this account no keep list, or that refused a Register (`refused_by`).

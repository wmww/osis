# One kind of peer
> Summary: A node has two kinds of peer (saved peer, the old host; direct peer, a co-reader) behind the one hub session; one listening key (built, 3d) and one store (built, 3f). Make one: one key, one blind store and serving path, a peer that cannot read L pulling it like any peer (3h2). Then Tess's model: sharing is a grant (role `sync` below read gives the sync key, never the read secret), a received grant is an invitation, accepting is the account writing it under the node's synced group S, a node syncs every sync ID in S's closure (items and subgroups, sync-only groups as leaves), and two nodes sync the intersection of what each syncs and is entitled to; peers found by own `reach.0`, contacts' profile dial lists and grant hints. No admission, keep list or peer list; `SyncId` out of the API. Build steps 6a-8, each with a removal audit; What must not survive covers the whole rework. Part of issues/net-rework.md.
> Priority: normal
> Tags: node, sync, host, proto, perm, api, spec, tess-call

| | Saved peer (old host) | Direct peer (co-reader) |
|---|---|---|
| Found by | fixed address in `label.0`, link and card text | `reach.0`, LAN, a link's sharer |
| Who can be one | a node with `host^.0` that admits the label | a node that reads the group |
| Serving code | `ServingSession` in the hub (`osis-host`, `HostStore`) | the same hub session, node sync above it serving the stream; local passes when no host is listed (notes/peers.md) |
| Store | the node's one store (the hub's: entries, blobs, the node log) | the same (3f) |
| Key | the node's one key (the dialable key) | the same |
| Opens by | sync key, claim, static entry | those for a peer that cannot read; between readers nothing opens, the shared set's members are pulled (notes/peers.md, The stream) |
| Registration | first come, by parent's delete key | steps recorded in `label.0`, plus valid child steps peers register; new labels refused |

## Steps, in the order of what they unblock
1. **An address names a node** (built with 3d): a peer is dialed by key with hints (spec/sync.md §10, spec/wire.md §10): a `peer://` saved peer or label host is a host like any address (sim `no_server::a_peer_address_saved_peer_dialed_by_key_syncs_spec_sync_10`).
2. **One listening key per node** (built, 3d): the dialable key serves sync, data the node cannot read and the client port; dialers stay ephemeral; LAN listeners keep a fresh key per network join (issues/net-connect.md), served by the same path. A reader finds a sync ID by a peer's filter and opens it there, so the filter goes on the key that serves unread data. `Osis::listen` binds more addresses under the one key; a client is cut off by its own entry (issues/client-auth.md); key rotation is `rotate_peer_address`, by hand only, moving every listener. The client port keeps its own access rules: Auth before any request, client actors, the main-actor tier only from `Peer::Unix` (notes/client-port.md).
3. **One serving path**. Principle: one connection, one session, one store answering it; every secret above it, in node sync.
   - **Session owner**: the hub (`osis-host`), one `ServingSession` per connection, every listener and, from build 3i, every dial. The node's driver owns the transport secret and the listeners and drives the hub sans-I/O in node sync's own loop (as the simulator's `host_of` does), so node sync reads the hub's store directly (public data flows up) and the two exchange messages by function call, not by channel. Node sync is the session's upper layer on every connection, as it is for the client port.
   - **Routing** (kind: who answers):

     | kinds | answered by |
     |---|---|
     | Hello, Ping/Pong (2-3) | the session |
     | Delete (14) | the hub's store, for a sync ID node sync opened on this connection by sync key (below) |
     | Register (7) | the hub's store, by admission alone (steps verify themselves; relayable, spec/sync.md §5) |
     | Fetch (19-20) with a node-range id, any answer with a node-range id | node sync (it reads the bodies from the hub's store) |
     | Stranded, Suspect (30-31), Prove/Proved, Resume/Resumed (32-35), shared set (36-40, 45-46), stream (41-44) | node sync |
     | client port (24-29) | node sync, by the port's access rules |
     | Open/Opened (4-5), Deposit/Budget (12-13), Sync/Reconcile (15-18), Fetch without a node-range id, Subscribe/Unsubscribe/Push (21-23), Path (8-9) unless build 3h uses it, Upload/Status (10-11) | gone (build 3i; Upload by 3h2's pull): an open is a Hit, a deposit an Offer item, reading the stream |
   - **The hub calls up for nothing**: it judges no open and holds no secret, filter or record. Up: every message of the table's node sync rows, a connection's start with its binding (listener key, both challenges, transport peer, source), its end, and store changes (a head moved, entries logged). Down: messages to send (node sync's requests within the session's request window, answers at once), `open(conn, L)` and `close(conn, L)` (the session's gate for the store's kinds; a new head's sync key closes it there, as `still_open` does), public data for the store (below), and closing a connection.
   - **Flow control**: one request window per connection covers both layers: a request handed up counts against the peer's `MAX_UNANSWERED` until node sync answers it (as client-port requests do now), and node sync's stream pushes wait for the session's room (`WantRoom`/`Room`, as Notify does), not sent past it.
   - **Opens**: all node sync's, one S per connection (issues/net-shared-set.md). Between readers by read secret, ByRole or static entry; at a node that cannot read L, by a Hit on the head's sync key with an open signature (over the other end's challenge and transport key, whoever dialed), a key actor's static entry (answered with `EntryGrant` from the hub's claim sets) or a Deposit item after a deposit-key hit (put through the hub store's deposit rules, spec/sync.md §5). The filter's entries for a sync ID the node cannot read (sync key, deposit key, the head's claim-set static entries) come from the hub's store and go to every connection; `changed_at` moves when such a head moves. Delete is taken only under a sync-key open, Register never gated (by admission until 6b, then for the node's sync set): nobody uploads (3h2).
   - **The store**: one (step 4), with one node-wide log the stream serves (issues/net-reconnect.md), per-label logs gone. Node sync writes its own and received entries there as a client; for a sync ID it reads it hands the hub the steps recorded in valid `label.0` (no first-come registration there; issues/net-role-sync.md, Replacement), and the hub takes Register only for sync IDs node sync does not read. Admission (`host^.0`: `open`, `labels`) decides which unread sync IDs the store keeps until step 6; `own` goes, since a node reading its own groups serves them as a reader to their holders.
   - **Readers treat a node that cannot read as a peer**: dial it by key (step 1; addresses as issues/net-connect.md, and `label.0` hosts until step 8), Hit, pull its stream, keep `known` (issues/net-reconnect.md, Peers that cannot read), and judge registration and deletes over `known`: one pass rule over `sources(L)`, a local pass being its empty case (issues/net-sync-structure.md (e)). The host client paths (Open, per-label Sync, Subscribe, fills, refusal back-offs) and replication between hubs go (replication is sync with a peer; between two nodes that cannot read, 6c).
   - Sync ID replacement (index > 0) goes last (build 3j; issues/net-role-sync.md).
4. **One store** (decided for 3f: the engine reaches the blobs in the hub's store; an engine transaction touching blob ciphertext opens one there, committed first, and the reconcile at open makes any crash point converge; app reads of large values read it directly; one set of store rules for every row, admission governing unread sync IDs only; replication to `replicate` peers only for unread sync IDs until step 6): ciphertext (entry rows with wrap and stamp, blobs, the node log, served steps and claim sets) in the hub's store, shredding on delete (notes/serving.md, Decisions); plaintext and secret-derived state (an entry's kind, certificates, `changed_at`, records, read secrets) in the engine's. `changed_at` takes its own sequence there (it fingerprints credentials, so it stays out of the hub; only `acked_pos` and `judged_pos` compare with it). A group a node reads and serves is held once. The hub's store is the truth for ciphertext and the engine's state a cache of it: an entry in the hub's store with no engine state is derived again, engine state with no ciphertext row is dropped, so a crash between the two commits converges. `host^.0` going drops the unread sync IDs (shredded), not the store. Node sync reaches it by direct calls in one loop (step 3), so no hop on hot paths; the cost to check is commits per inbound batch (two stores), counted at n and 10n. Built inside step 3's order (3e, 3f): the stream can serve unread members only from one log.

5. **Keep the boundary**: the code serving data a node cannot read cannot decrypt (`osis-host` has no engine or keys; tools/policy.py `host_blind`). With one path it serves readable data too, so the boundary is the crate: node sync stays the only reader, the hub keeps no secrets and the policy check carries over to the renamed crate.
6. **Grant, accept, sync** (below, Sync model): sharing is a grant; a sync-only grant (role `sync`, below read) gives the sync credentials and never the read secret; a received grant is an invitation and syncs nothing; accepting is the account writing the thing under a node's synced group S; a node syncs every sync ID in S's closure; two nodes sync the intersection of what each syncs and grants entitle the other to.
7. **Invitations** (below): core lists the grants to the account that no node's S holds; accept and decline are app writes.
8. **Peers and API** (below, Finding peers; API): where to dial comes from own nodes' `reach.0`, contacts' profile dial lists and the grant's hint, never a peer list; `SyncId`, peer lists and admission leave the API.

- **3h2 A peer that cannot read L pulls it** (after 3h1). Principle: **every node holding L pulls it from the peers it shares L with, whether it reads L or not; a reader acts on a peer that cannot read L only over what that peer's stream showed it (`known`), registration and deletes alone, in one pass per label that judges its own store once and then each such peer; nothing is uploaded, and no write acknowledgement counts as presence.**

Peers that read L are never sources (nobody registers at or deletes at readers). The source's head is the step whose credential its Hit used, moved by the stream's head events.

Holding none of them, L is stranded for it (spec/permissions.md §4): it tests, Hits, walks and registers nothing for L (sim `member_churn` seed 4 on 3h1 is this case: it must end Failed, not loop on Opens).

Trigger (3h1's reader rule, once per filter arrival, with the walk in place of Open): L is not open there after the peer's latest filter was tested (its filter shows no credential of L this node holds, or the Hit was refused: code 14 counts as not shown, until the next arrival), no Register of L is in flight there, and L's registration back-off at that peer (refused for now: `retry_ms` doubling to `resync_ms`, as built) has passed. Then the **walk**: the credentials of the recorded path's earlier steps, newest first, each distinct one once, against the same filter. The first shown is Hit; L opens at that step; the pass there (below) registers the rest. None shown: Register the recorded path from genesis, one step per Register in order, each with its claim set when held. A genesis answered 9 means the peer holds L at a head off this node's recorded path (ahead of it, or a fork): the Open walk (interim, below). Refusals 4, 12, 14 start the back-off; `Refused` status as built until step 8.
    - Cost: a peer on the newest head costs one test per sync ID per arrival whatever the number of steps. A walk costs one test per distinct recorded credential, once per registration attempt at an entitled peer missing L (attempts backed off), never per arrival. Testing every recorded step at every arrival was rejected: steps × sync IDs × arrivals × peers, at every peer that merely shares nothing.
    - Who moves it: any reader holding the recorded path. Steps are signed by their parent's delete key, so Register needs no secret and no open (spec/sync.md §5: relayable by any node). The peer checks §5 Register as built (`prev` is its head, signature chain, claim-set hash, caps, rate; admission until 6b, then its sync set). Only an admin issues a new step: a child of the source's head when `step_due` against it and `label.0` records none (`reregister`, unchanged but for where the head comes from), a child of the served head when there are no sources (the local rule). Once L opens at the new head the peer pulls what it lacks under it.

The next filter generation (its `changed_at` moved) shows the new head's credential, and the reader Hits it and rejoins from where it stopped. `known` is unchanged, so nothing is listed again.
    - The 3i routing row follows: Register is never gated on an open; 3i gates Delete only.
  - **Pull, not upload**: a peer that cannot read L pulls L from every reader that opened L there (3h1's Hit), as readers pull each other (spec/sync.md §10, Stream; "a node that cannot read a member pulls none" goes). It applies an Added into the hub's store by the store's Upload rules (a stamp under its head's write key, one under a superseded write key refused as code 9 is today), a deposited one by its Deposit rules (budgets per source), and does nothing on a Deleted. Relay-only entries reach it as a cursorless Stream through its relay gate. So a writer's own write reaches the peer by the stream's follow push as soon as it is logged ("push it before the only other holder goes offline" is that push plus the peer's Applied); presence is the peer's reported position, then `known`; a peer restored from a backup pulls again from its stored cursor. Until 6c a reader serves L so only to a peer listed for L (above), which keeps a stranger showing L's public sync key from pulling L's ciphertext; from 6c the shared set's rule decides (Sync model).
    - **Bytes once**: the peer fetches only bodies whose blob ID its store lacks (one blob per blob ID, 3f), with `inline_limit` 0 once a member has another source (as built), so an edit in a group nested in several groups the peer holds crosses its bytes once, and a subgroup joining a group costs entries alone. ## Sync model (step 6)
Principle: **a node syncs exactly the sync IDs in its synced group's closure, and shares each with a connected peer exactly while the peer proves it may hold it; what two nodes sync together is the intersection.** Nothing else decides what a node holds: no admission, keep list or peer list.

### The synced group S
- **Shape**: per node, a plain group (`group.0`) whose first admin is the account's devices actor D, so only the account's nodes read it, and an item of D's `group.0`, so its commits travel under home (spec/sync.md §2, home closure). `synced^.0` on D: `map<tid, tid>`, node tid to its S; admin-only, written by the account (any of its nodes, as P). Every node reads every sibling's S under home: that is how siblings learn each other's. A node learns its own S with its grant on D (the pairing reply; account creation for the first node), so it never waits on `synced^.0` to begin.
- **Home stays under S**: S lists home (D) as a subgroup from its creation, since home carries `synced^.0` and S itself, and a node whose S closure lost home would never hear its S change. A write leaving home outside some node's S closure is refused locally, as a write removing the last admin edge is (spec/permissions.md §1). Limit: two concurrent writes each removing one path leave it out; that node then follows nothing new until it is paired again.
- **Organizing groups** (the account's "synced on all nodes" group, nested in every S; a "nodes with lots of storage" group, nested in some) are plain groups like S: first admin D, items of D's `group.0`, no sync ID. Which exist, and where the default accept writes, is app or node policy. Core knows no accepting, policy or node role.
- **No sync ID of S's own** (rejected): the blobs of a group with a sync ID are its whole closure (spec/sync.md §3), so a sync ID on S or on an organizing group would carry every commit of every readable group under it a second time: one more entry (wrap, stamp, log event, stream event at every puller) per commit per such level, the bytes once by blob ID, for nothing the members' own sync IDs do not carry; sync-only leaves' commits would not go under it at all (D's actor reads no part of them). Only a grant on S would make one; S is private to the account, so nothing asks for it.

### The one rule (Tess)
- **Syncing a group syncs every sync ID in its closure**: the group's own, and every thing's in it at any depth through `group.0` (spec/data-model.md §8), items and subgroups alike, a thing shared on its own (its own sync ID, from its first grant) included. A node's **sync set** is the sync IDs of the things in S's closure. "S synced but G under S not" cannot be stated.
- **Leaves**: a group the account holds sync-only has a sync ID the node syncs and a `group.0` it cannot read, so the walk stops there: what it lists is under no S through it. A thing in the closure whose sync ID the node holds no credential of (its account holds no role on it, and it travels under no sync ID the node syncs) is not synced; it is a diagnostic (`Unsyncable`, naming the thing): the node holds nothing it could sync, so this is the rule, not an exception to it.
- **Cycles and cost**: the walk is the `groups.0` index the node already keeps for tagging (spec/data-model.md §8: the groups holding a thing, transitively; a set, so a cycle adds an element, never a loop). The sync set is every thing with a sync ID whose `groups.0` holds S, S's own if any, plus S's sync-only leaves, and moves when the index does: adding a group under S costs the index rows of its own subtree, never the closure's; a removal re-derives what is still reached (a rare path, brute force allowed: O(closure) per removal). Counted at n and 10n subgroups (6b).
- **Leaving the sync set**: a sync ID that leaves it is dropped (shredded) once the node's own commits under it are placed (spec/sync.md §5, Placed), as a loss of access hears out first (spec/permissions.md §2). Removing a group from every node's S drops it from every node of the account (Tess, below).

### Sync-only grants (spec/permissions.md terms)
- **Role `sync`**, below read: sync < read < write < admin. It has a role secret like the others (spec/crypto.md §3: derived for a plain thing, its own from the first grant), sealed to every holder of sync or above. The label sync key derives from it, `kdf("label sync", sync secret, le64(i))`, in place of the read secret (spec/sync.md §2). Readers hold it as every holder of a role holds the lower roles' secrets, so they derive the same key.
- **What it gives**: the sync key, so the holder opens L at a peer (an open signature, spec/sync.md §5 Opens; a sync-key Hit, §10), pulls it, holds it and serves it. A holder that cannot read L takes, by its store's rules, entries stamped under its head's write key and deposited ones by its Deposit rules, from any connection where L opened by the sync key, and Deposit items on the deposit key, as a node that cannot read L does today (3g, 3h2); it removes an entry only on a Delete signed by the needed delete key, or at expiry. It reads nothing: no section of L opens with it, it holds no roster, J is unknown at it.
- **Who grants**: as any grant (spec/permissions.md §2): an admin, or an invite grant within the author's effective invite (`invite: sync` on a reader's grant lets that reader grant sync-only, and an app may write that by default). No carve-out in core; "any reader, by rule" is Tess's call (below).
- **Credentials travel with the grant**: the grant's inbox blob (spec/sync.md §3; every grant to an actor is delivered so, spec/permissions.md §2) carries the holder's box of the sync secret and names the thing's sync IDs. Claim sets and entry boxes stay readers' only. A sync-only holder cannot read a rotation under L, so a rotation boxing a holder whose highest role on the thing is sync is delivered to it as an inbox blob (spec/sync.md §3, What it carries about G: one more case). The path (steps, claim sets) reaches it by Register from any node holding it (3h2, Stale head; steps verify themselves).
- **Revoke and rotation**: removing a sync holder is a departure (spec/crypto.md §4) requiring a rotation of the sync role on the target; the head's sync key moves with the next step, so every open by the old key ends at the head's event (spec/sync.md §10, Lost), and the removal reaches the holder's inbox (spec/permissions.md §2), after which it drops L as any lost access. Removing a reader rotates read and, by the roles it left, sync too.
- **What the holder learns**: the target's tid and its sync IDs (from the grant), the granting account, the registration path with its claim-set size (padded to a power of two: the readers' count to a factor of two, as any peer keeping L sees today), entry count, sizes and timing, and which accounts' nodes open L there (issues/privacy.md, accepted). Never the roster, any content, or the group's members.
- **Through paths**: a grant to a group G on H boxes H's sync secret to G's sync keyset, so a sync holder of G could open H's sync key, but never learns H's sync ID (G's `group.0`, H's `label.0` and the grant are under read secrets it lacks). Only direct grants make leaves.
- **On an account's D**: a sync grant on D to another account (keeping the account's inbox) makes nobody a node of P: a node of P is a node key actor holding read or above on D, and D's node list is its node key actors (spec/permissions.md §1 reworded).

### Sharing: the intersection (spec/sync.md §10, Shared set)
- **Rule** (reworded): a node shares L with a connected peer exactly while it syncs L and, on what it holds now, the peer may hold L: a proven actor is a current holder of L at sync or above (J), or the peer showed an admissible credential with its proof. Each side judges alone, so a pair shares the intersection of what each syncs and grants entitle the other to: "willing to sync with you" is the grant, with no list. A node granted L that has not accepted it does not sync L and shares nothing of it.
- **J counts sync**: a reader of L opens L for a peer that proved an account holding sync on L (by the roster), and Hits that peer's sync-key entry with the open signature (3h1) so L opens on the peer's side too, which holds no roster. Such a peer's account is a known actor (it holds a role on L), so the two keep a record.
- **Sync-only holders test**: a node holding L sync-only tests its sync key of L against each arrival of a peer's filter and Hits with the open signature. So two such nodes open L at each other, each verifying the other's signature by its own head, and both pull with every reader offline; one dial each way is ephemeral as any. A node holding only L's public keys (an ex-reader after the rotation, a stranger holding `label.0`) opens nothing.
- A sync-only holder's filter entries of L (sync, deposit, claim-set; 3g) go to every connection, as today's (Tess, below).
- **Both pull** (3h2), every side pulling each member open on its side that it syncs; a sync-only holder applies pulled entries by its store's rules.
- **Stale head**: a node holding L's path at head h registers it (3h2's walk) at a connected peer entitled to L at h whose filter shows an older step of L: entitled by J at a reader, by a verified Hit on h's sync key at a sync-only holder. Two sync-only holders on different heads share L once either has the other's head registered by anyone holding it.

### The hub
- Keeps exactly the sync set's sync-only members (`Down::Keep(L)`, `Down::Drop(L)` from node sync's sync set; `Admission` goes), takes Register only for those (a genesis too: the sync ID is known from the grant, so nothing is first come), and its totals and caps count only them.
- `host^.0` keeps only the limits on what peers may make the node store (`policy`, `caps`), renamed with issues/net-rename.md. A Register for a sync ID outside the sync set is code 14.
- **Bytes**: no new message kind. Role `sync` is a new value of the role in `roles.0` (spec/wire.md), `synced^.0` a new core-schema aspect on D.

## Invitations (step 7)
Principle: **a received grant is data the account holds, accepting is data the account writes, and core only lists.**
- **Surfacing**: a grant reaches the account as an inbox blob under its home (spec/sync.md §3), and the node that admits it places a grant copy under home, so every node of the account holds it (§3, Grant copy). The pending list is computed, never stored: the things with a sync ID this account holds a role on (sync or above), by the grant copies and rosters held, that are in no node's S closure (siblings' S read under home; through what the node reads, plus each S's sync-only leaves).
- **Invite requests** (spec/sync.md §3: a blob whose sender is not connected) are listed too, `admitted: false`. Putting the thing under an S admits the blob (a third admit case: the blob names a thing in the node's S closure), so accepting is one write whoever sent it. Declining one stays as §3 says.
- **Accept**: the app writes the thing under S or a group under it (by default policy, the account's "synced on all nodes" group). **Decline**: the app's choice, `leave` (a self-removal the granter's admins see) or filing it in a group of the app's own outside every S (the list keeps it; the app subtracts that group). Core knows neither.
- Not Diagnostics (an invitation is state an app acts on; correctness never waits on a diagnostic) and not status (status is per sync ID synced here).

## Finding peers (step 8)
Principle: **where to dial is a hint, never authority; what opens is the shared set.**
- **Own nodes**: by `reach.0` under home; a node dials a sibling while their sync sets intersect (siblings' S closures are read under home), within `max_peers`, ordered as issues/net-connect.md (Keeping).
- **Other accounts' nodes**:
  - **Profile dial list**: `dial.0` on the account's profile, `map<blob, list<text>>`, a node's dialable key to its URLs, written by the account; each node keeps its own entry current, a rotation rewriting it in the rotating commit. Contacts (card holders) read it. Which nodes an account lists is Tess's (below); meanwhile every node that publishes `reach.0` items, the exposure `reach.0` under every group has today narrowed to contacts. A granter holds the grantee's card (it needs its `keys.0` to box it), so it can dial the grantee's listed nodes.
  - **Grant hint**: the grant's inbox blob carries the granting node's dialable key and URLs (its word, a hint only) in place of the payload's per-label host addresses, so a grantee that is no contact of the granter can dial it for that thing. Stale once the granter rotates; then the card, a LAN, or being dialed.
  - LAN, links' and cards' connect hints, and being dialed: unchanged. A link or card carries the account's dial list (with `direct`, this node too) in place of saved peers, so neither needs one.
  - **Whom to dial**: the listed nodes of accounts holding sync or above on a sync ID it syncs (by the rosters it holds, at a reader) and the granters of what it holds sync-only (by the grant copy), kept while their shared set holds something (a priority, never a filter).
- **Rotation**: a node rotating its key (`rotate_peer_address`) writes `reach.0` and its `dial.0` entry; siblings follow by home, contacts by the profile, a grant hint by neither. No `Moved`, no old listener kept, no `MOVE_WAIT`.

- `sync(group)`: makes the group's sync ID (admin; a no-op when it has one), with no peers argument; for a group of the account's own, with no grant, that is to sync on its own under some S.

## Tess
- Decided (Tess): sync-only grants follow the one grant rule, no special case (an admin, or a holder whose grant carries `invite: sync`).
Each needs her call or her nod; the design takes the reversible option meanwhile.
- **Which nodes the profile lists for dialing**: meanwhile every node publishing `reach.0` items, shown to the account's contacts. Unlisting a node (an always-on machine at home) is a flag on the entry; nothing here constrains it.
- **The grant hint**: a grant shows the grantee the granting node's address (its IP to whoever it shares with). Without it, a grantee that is no contact meets the granter only on a LAN, by a link, or by being dialed.
- **Removing a group from every node's S drops it from every node of the account**, after the node's own writes are placed, whether or not any other account still holds it: a configuration change that can lose the last copy. Option: keep it until some other holder's stream showed it whole (a wait that may never end).
- **Sync-only holders keep no subgroups**: keeping a group tree sync-only (a friend's backup node) needs a grant per sync ID in it, and a new subgroup or separately shared item is not kept until someone grants it too. Options: an app policy granting the backup on each new subgroup (a tied grant), or a core rule; the design takes the app policy.
- **A sync-only holder's filter goes to every connection**: anyone holding the group's `label.0` learns the node keeps it (issues/privacy.md). Showing it only to known actors (accounts on its grant's roster are unknown to it; only the granter is known) would hide it from strangers and from other holders alike.
- **Readability is per account**: every node of an account holds every box to it, so one account's nodes read alike; a machine of the user's that should hold the user's groups unread (a rented server) is a node of an account of its own, granted sync-only (issues/account-signing.md (c)).
- **Quotas**: per-account caps at a node keeping other accounts' groups unread are possible (grants name accounts) and not designed.
- **Requirements wording** (flag only): with a node keeping L unread knowing who asks for what (issues/privacy.md, accepted), spec/requirements.md's goal "a node can limit abuse (storage, rate) of data it cannot read without learning identities" may deserve softening; Tess's view is that guarantees about nodes not learning about the nodes they sync encrypted groups to may be more than is reasonable to provide. Hers to word.

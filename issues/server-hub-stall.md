# One hub thread: what is left of the stall bounds
> Summary: the server runs every connection's input on one hub thread. Per-input work is now bounded and close to honest work (notes/sync.md, Hub stall bounds). Left: sources a transport cannot tell apart (iroh, many addresses), no node-wide relay rate with a shared replay memory, and everything still serial on one thread. Low.
> Tags: security, server

Done (branch hub-stall): claim keys indexed as rows (an Open is a lookup); after one bogus signature a message's later ones try the head key only; Sync entries capped at 1024; one fsync per input; relays only to subscribers; full connection slots shared fairly by source (hub sessions and listener connections); a connection pipelining replies past `SEND_QUEUE` is closed mid-input; per-label maps pruned when an open ends.

Left:
- **Sources**: fairness keys on `Connection::source` (IP, IPv6 /64). iroh connections have none and count as one source together, so an iroh flood shares slots with every iroh client; an attacker holding many addresses (a botnet, many /64s: one IPv6 /48 is 65 536 sources) still gets a share per address. With slots full such an attacker squeezes every honest source down to one connection (never to none: a source is evicted from only while it holds two more than the newcomer's), e.g. a NAT'd office keeps one; before, the attacker only locked newcomers out. All iroh clients together are one source too, so with slots full IP sources squeeze them to one share. The hub's input turns go by the same sources (notes/sync.md, Hub stall bounds), so each address also gets a turn (and all iroh connections share one, by connection within it): at S sources a read waits up to (S − 1) per-input bounds, past `STALL_TIMEOUT_MS` at about 900 hostile sources at 10^5 entries or 80 at the 2^20 cap.
- **Relays**: rates are per label (`RelayLimits`), so an attacker with many labels relays without a node-wide bound (fan-out now only to subscribers, each limited by its send queue). The node-wide `MAX_RELAY_SEEN` set is shared, so such a flood evicts honest labels' replay memory (a replay is then pushed again: minor).
- **Serial work**: decode, signature checks and store access all run on the hub thread; connections take turns per 64 KiB read, by source. Moving decode and verification to per-connection tasks (store access serial) would let a slow input no longer delay others at all.

# Unvouched-entry cap is shared across servers; old-step stamps vouch for junk
> Summary: `drop_unvouched` counts a label's unopened unstamped entries over all servers, so one hostile server that fills the cap (2^16, inbox 2^12) makes the node drop later real unvouched entries announced by honest servers; and a stamp under any known step's write key vouches, so a former writer (old write key) with a hostile server can still make a node keep unbounded junk.
> Tags: security, sync, node

Code: `crates/osis-node/src/sync/inbound.rs` `log_events` (`vouched`, `unvouched`), `drop_unvouched` (`held` counts `state.entries` of the label, any server).

1. Cap shared across servers. Hostile server A announces 2^16 junk entries under label l (kept: under the cap). From then on every new unstamped entry under l that does not unwrap under a held secret is dropped whatever server announced it: deposits under an epoch the node learns later (a re-sealed member's, a rotation not yet applied), and for an inbox label grants sealed to a read KEM key of a later epoch. They come back only on a full replay or when a writer promotes them; a cursor sync never re-sends them. Withholding by A alone is always possible; this lets A suppress what honest server B serves. Fix: count per server (entries present at that server only), or drop the oldest unvouched entries of the server being over the cap.
2. Old-step stamps. A stamp verifying under any recorded step's write key makes the entry vouched: kept with its bytes, never capped. Anyone who held an old write secret (a removed writer) can stamp junk that a hostile server relays (honest servers refuse stamps not under the head). Before the wave 6 fix every unstamped entry was kept, so this is a residue, not a regression. Fix: cap entries vouched only by a superseded step like unvouched ones, or keep their entry but not their bytes until they open.

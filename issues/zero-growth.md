# Storage must not grow with writes or thing churn
> Summary: Tess's rule (spec/requirements.md Scale): neither repeated writes where history is not kept nor making and releasing things grows storage without bound; a long-lived thing may grow modestly with the role changes made on it. Replacing writes are flat and tested; set removals and some rows still grow. Lists naming commits (frontiers, addenda) are bounded per removal by what the remover held, but outlive the commits they name: fix by making each leaf evidence of every commit its verdict reads (modelled); kept for good where the lowered party writes through the edge again, unless the root bounds what a leaf can name (Leaves). Two questions for Tess (a requirement's wording; purge requests).
> Priority: normal
> Tags: engine, crdt, perm, spec, tests, tess-call

## For Tess
1. **A thing grows with role changes made on things above it, not only on it.** A removal is logged for good under every sync ID carrying a thing where the removed signer could write (stage A3, notes/write-path-design.md §2), because a stolen signer can write there at any later time and the removal must already be there to judge it. A2's evidence copies likewise grow with role churn on the edges a thing's writers go through. So each thing of an organization carries a copy of every team removal from the organization, for good. spec/requirements.md Scale says "with the number of role changes made on it". Either the property is the weaker one ("on it, or on what its writers act through"), or a design must let a removal's copy leave a thing, and none was found (the copy must be in place before the thief writes; a "settled" compaction of roles breaks Forks are permanent). Recommendation: weaken the wording.
2. **Purge requests are listed in every removal of their author while held**, and purge-carrying commits stay held, mostly for good (notes/growth.md rows 1, Purge requests, Lasting tombstones). That is growth with writes (deletes), already there without removals; each removal adds 32 B per request. Proposal 1 drops these entries only where the request commit is forgotten; decide with row Purge requests (issues/long-aspect-cost.md).
Nothing else here needs her: the list fix (Proposals 1) keeps every property as modelled.

## The rule (Tess)
- Requirements that say otherwise are wrong and get fixed; code that does not meet it is wrong and gets fixed; it is tested as far as reasonable (count stored bytes at n and 10n writes, notes/principles.md Check scaling).
- What cannot be fixed, or only with a significant trade-off, goes to Tess with the trade-off stated.
- Purging is a different matter: this is about replacing writes and released things.
- Accepted (Tess): a long-lived thing growing modestly in proportion to the role changes made on it.

## Flat today
Replacing writes once covered (osis-sync `growth::*_grow_nothing_spec_commits_5`, the S1 arms). `growth::flat` (6 vs 60 more writes) allows a store's attribution rows (`B/`, `W/`) at most one per entry, 64 B for a counter that widened, and does not count pages (their layout follows the write history within a bound: check the bound is on live data).

## Grows today
- **Set removals**: a tombstone of a few bytes per removal in the roots' `holds.0` and `tickets.0` (`TOMBSTONE_BYTES`, issues/storage-owners.md 12), so making and releasing things grows them for good; the same for any set an app adds to and removes from. Stated reason: no cover can drop one without losing a removal's finality. This is thing churn, so it breaks the rule. The tombstone is not there for late edits (an edit names its entry and has nothing to apply to once the entry is gone) but for a late-arriving older add: a node that still holds the removed element hands it on, and without the tombstone the receiver cannot tell "never seen" from "seen and removed" (spec/crdt.md §5.5 Tombstone lifetime). So with the merge rules as they are, only two of three hold: a removal is final, a node may return after any time offline, storage does not grow with churn. Look first for the design that keeps all three: a writer whose counters survive restarts lets a node hold "seen everything of this writer up to n", so an element at or below n that is absent is known removed with no tombstone, and growth follows the number of writers (Tess accepts growth with role changes); with visible signers each node is such a writer (issues/actors-one-mechanism.md, sessions). Why it is not built that way: sources are sessions and commits, random and unlinkable, with counters in memory only, which is what hiding nodes behind one account key called for; a stable writer with counters that survive a crash did not exist. Check that reading, and what durable counters cost (a crash must never reuse one). **If there is no good fix (Tess)**: loosen "a removed element never comes back". Where history is kept the removal's record is kept with it, so it stays final there (the option keeps its property and pays for it). Elsewhere a set keeps its tombstones in a buffer bounded by time and/or count, so a removed element can come back only from a node out of contact while a great deal of churn went by. The bound passes notes/arbitrary-values.md (at 0 no removal is final against a stale node; unbounded is today), and spec/requirements.md Data model then states the weaker property in place of "a removal is final".
- **Rows S1 allows**: schemas a node learned (`d/`), `cv/` at most one row per held snapshot: bounded by what, and is that bound live data?
- **Account names** at rotations (issues/rotation-names-grow.md), and whatever replaces them (issues/actors-one-mechanism.md: nothing kept per commit for good).
- **Usage rules that exist to dodge growth** (commit per editing pause, never per keystroke; presence by expiring ephemeral writes) are stated in spec/requirements.md Generality as steering toward lower cost: once growth is fixed, check they are no longer needed to keep a disk from filling.
- **Lists naming commits outlive the commits**: below.

## When an entry is dead
A verdict reads a list entry naming commit c only when it judges c itself (spec/permissions.md §5.2: c's delta is valid where a cut's list names it or a counting addendum vouches for it; an own cover S is valid where its removal's frontier names S; a purge request holds its right where a cut lists it). The roles model judges only commits a node holds (`addenda::Ctx::step`), so an entry naming a commit the node does not hold is read by no verdict there.
- **Content and purge-request entries** (frontiers, addenda) are dead at a node from the moment it forgets c (a valid held cover carries c's live writes, or c dropped as invalid, spec/commits.md §5 Forgetting) until c comes back to it. A commit can come back (a store keeping it unread, a peer that has not compacted), and then the entry must come with it: dropped for good while c can return, it loses c's live write at that node where the cover carrying it falls. Whether that changes a reading in the model: Model result below.
- **Role entries and vouches** name role commits, never forgotten while the thing is held: never dead.
- **An own cover's entry** names a snapshot; dead once later snapshots cover it, as any content entry.
- Globally dead (no node holds c, stores included) is not knowable by any node, so entries are dropped per node, as evidence.

## Proposals, ranked
1. **Recommended: an entry is evidence of the commit it names, and leaves with it** (A2's "evidence leaves with the commit that needed it", applied to lists). Rule for A3: a removal signs a root over its list tree; the role entries stay with the removal; content and purge-request entries sit in per-thing leaf blobs whose hashes the tree holds. A node holds a leaf while it holds a commit whose verdict reads the leaf: on its thing, with no edge-class part, resting on the lowered edge, named or not, stamped before or after the lowering (a list is read for any of them, and a reader cannot tell an unnamed one without the leaf), and logs it with those commits under their sync IDs (as A2 places evidence); it forgets the leaf with the last such commit. Kept only with the commits it names, a leaf leaves while an unnamed commit it judges invalid stays, which then pends for good (notes/evidence-model-findings.md 6). A commit held without the leaf its removal's root commits to pends (missing evidence, never judged invalid for it). Addenda alike: an addendum is forgotten at a node once it holds none of the commits it lists, and logged as evidence of each. Costs: one leaf blob per (removal, thing) while needed, a hash per thing in the tree, the required-set rule growing one clause. Breaks: nothing in the model (below). Bytes kept for good per removal: the root and the role entries.
2. **Accept as is (the built rule)**, stating the bound: per removal, what the remover held of the removed party then. With no history promised that is O(live state), so "never writes ever made" holds; with history kept for a time the entries outlive the history they served, a leak by notes/principles.md (Close leaks). Only acceptable with Proposal 1 for the history case, so not chosen alone.
3. **Vouches written only while no counting vouch at all names the commit** (not only the witness's own): cuts the duplication across witnesses; growth with role changes either way. Not modelled: brief, roles-model `vouches` variant (a witness writes only where no applying vouch keyed by R names c; property: `vouches` checks unchanged, writes counted). Low value.
4. Rejected: **a window** (list only commits stamped within a span before the removal): at 0 every in-flight honest write falls, at infinity it is today, and stamps are the removed party's own (backdated at will), so no span is justified (notes/arbitrary-values.md). Listing less is always safe (it never makes a write valid), so a window buys nothing Proposal 1 does not.
5. Rejected: **a later role commit compacting earlier removals' lists** ("settled" roles): two admins compacting differently give two readings, and no rule may wait for a fight to settle (notes/principles.md, Forks are permanent).

## Model result
roles-model `forget` (`Policy::Travels` against the built `HeldList`, control `Policy::Stranded`; `roles-model -- 0 forget-entries`, default test `forget::tests::entries_leaving_with_their_commit_change_no_reading`). `Travels`: every node keeps a frontier or addendum entry only while it holds the commit named, and gets it back with the commit. `Stranded`: an entry is gone for good at a node once it forgot the commit, even when the commit comes back.
Over 1,151,232 worlds (one member-family world in 8 with Bob's writes in or out of kept history, and the attack family): `Travels` reads as `HeldList` at every node in every world, with no disagreement, no fixpoint cut and no forged write shown; `Stranded` reads otherwise in 19,686 worlds (the nodes that dropped an entry with a forgotten commit lose the commit's write when it comes back after the cover it was forgotten under falls, while others keep it; minimal world `an_entry_comes_back_with_its_commit`). So within the model the only condition is the delivery one: an entry travels with its commit. Entries held at the end: 6,784,380 under the built rule, 6,221,750 under `Travels` (the model's worlds forget little; the saving is what the scenarios below count). Not modelled: entries as blobs a commit pends without (A2's pending on missing evidence, checked by held-model `evidence` P1 once A3's brief adds leaves as evidence of content bodies: brief, one clause in `Rule::fixed`'s required set and a world where a reader holds a content body and its removal under a different sync ID than the leaf).

## Leaves
Under the rule above (held-model `evidence` `LeafKeep::Judged`) a leaf leaves only once no held commit on its thing rests on the lowered edge. Where the lowered party stops writing through the edge (a removal for good, a team removed) that is when its backlog is covered or leaves history, as with the named rule: the scenarios' Proposal 1 figures stand. Where it writes through the edge again (re-granted, or a demotion leaving it write), its new writes keep every earlier lowering's leaf on that thing for good:
- 10 members, no history: 3.2 KB per such role change on the thing, for good; 30-day history: about 1 MB per such role change, for good (the named rule: gone after 30 days).
- 1,000-member organization: 32 KB per team removal or demotion followed by a re-grant (no history), 96 KB with 30-day history; 100 such: 3.2 MB or 9.6 MB for good, which is Proposal 1's whole saving in that case. History forever: unchanged (kept either way).
That is growth with role changes, by what the remover held at each, not by writes. Two narrowings, neither modelled (notes/a2-spec/README.md OPEN 12): a leaf is read only for commits needing a level its lowering cuts (a demotion to write never reads it for write content), and a root carrying per leaf the greatest `ts` it names lets a reader know a later commit unnamed without the leaf, so the leaf leaves with the last commit stamped at or before it.

## Scenarios
32 B per entry; commits about 400 B; compaction by the trigger (a snapshot once droppable bodies cost twice one).
- **A thing of 10 members, 10^6 content writes, no history promised, 10 removals** (each removed member wrote 10^5): listing every commit ever (the reading this issue first had) would be 3.2 MB per removal, 32 MB for good. The built rule lists the backlog: about 100 entries per removal on a thing of 20 small aspects, 3.2 KB, 32 KB in all, plus 32 B per purge request the member still has held (1% of writes deleting: 32 KB per removal). Under `keep` for 30 days at 1,000 writes a day: 30,000 entries, about 1 MB per removal, 10 MB kept after the history it served is gone. Proposal 1: about 1 KB per removal for good (root and role entries); the leaves leave with the window.
- **An organization of 1,000 members, 100 team removals** (teams of 10, 10 writes a day each through the organization): no history, about 1,000 uncovered commits per removal, 32 KB, 3.2 MB in all; 30-day history: 3,000 entries, 96 KB per removal, 9.6 MB kept after the window; history forever over 3 years: about 110,000 entries, 3.5 MB per removal, 350 MB, against about 4 GB of history bodies kept by choice (8%, the option's own cost). Proposal 1 removes all but the history-forever case. Independent of lists: each removal copied under every sync ID where the team could write (For Tess 1): with 10^5 things each under its own sync ID, 10^5 copies of a few hundred bytes per removal, kept at the stores holding them.

## Work, not storage
- A commit with a part no own replace covers (a part on an aspect another writer compacts, a part a setting keeps) stays whole until a snapshot covers that part too, and is judged again at each later own replace of its covered aspects (spec/commits.md §5 Own replaces): work per write grows with such commits held.
- A snapshot rewrites the whole field, so each compaction of a very large field writes and logs it whole (no snapshot links existing pages).

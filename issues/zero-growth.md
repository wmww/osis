# Storage must not grow with writes or thing churn
> Summary: Tess's rule (spec/requirements.md Scale): neither repeated writes where history is not kept nor making and releasing things grows storage without bound; a long-lived thing may grow modestly with the role changes made on it or on what its writers act through. Replacing writes are flat and tested; set removals and some rows still grow. A removal's list (frontier, addenda) is bounded by what the remover held, but stays with the removal, whole, for good (notes/write-path-design.md §2 E4), outliving the commits it names where history is kept; entries leaving with their commit is modelled and would need a per-thing form E4 rejected for now.
> Priority: normal
> Tags: engine, crdt, perm, spec, tests

## The rule (Tess)
- spec/requirements.md Scale reads "on it, or on what its writers act through" (approved, written): a thing grows with role changes on the things above it, since evidence copies follow role churn on the edges its writers go through (A2).
- Purge requests are listed in every removal of their author while held, and purge-carrying commits stay held, mostly for good (notes/growth.md rows 1, Purge requests, Lasting tombstones): 32 B per request per removal, accepted (Tess).
- Requirements that say otherwise are wrong and get fixed; code that does not meet it is wrong and gets fixed; it is tested as far as reasonable (count stored bytes at n and 10n writes, notes/principles.md Check scaling).
- What cannot be fixed, or only with a significant trade-off, goes to Tess with the trade-off stated.
- Purging is a different matter: this is about replacing writes and released things.
- Accepted (Tess): a long-lived thing growing modestly in proportion to the role changes made on it.

## Flat today
Replacing writes once covered (osis-sync `growth::*_grow_nothing_spec_commits_5`, the S1 arms). `growth::flat` (6 vs 60 more writes) allows a store's attribution rows (`B/`, `W/`) at most one per entry, 64 B for a counter that widened, and does not count pages (their layout follows the write history within a bound: check the bound is on live data).

## Grows today
- **Set removals**: a tombstone of a few bytes per removal in the roots' `holds.0` and `tickets.0` (`TOMBSTONE_BYTES`, issues/storage-owners.md 12), so making and releasing things grows them for good; the same for any set an app adds to and removes from. Stated reason: no cover can drop one without losing a removal's finality. This is thing churn, so it breaks the rule. The tombstone is not there for late edits (an edit names its entry and has nothing to apply to once the entry is gone) but for a late-arriving older add: a node that still holds the removed element hands it on, and without the tombstone the receiver cannot tell "never seen" from "seen and removed" (spec/crdt.md §5.5 Tombstone lifetime). So with the merge rules as they are, only two of three hold: a removal is final, a node may return after any time offline, storage does not grow with churn. Look first for the design that keeps all three: a writer whose counters survive restarts lets a node hold "seen everything of this writer up to n", so an element at or below n that is absent is known removed with no tombstone, and growth follows the number of writers (Tess accepts growth with role changes); in visible mode each node is such a writer (stage A4; issues/actors-one-mechanism.md, sessions). Why it is not built that way: sources are sessions and commits, random and unlinkable, with counters in memory only, which is what hiding nodes behind one account key called for; a stable writer with counters that survive a crash did not exist. Check that reading, and what durable counters cost (a crash must never reuse one). **If there is no good fix (Tess)**: loosen "a removed element never comes back". Where history is kept the removal's record is kept with it, so it stays final there (the option keeps its property and pays for it). Elsewhere a set keeps its tombstones in a buffer bounded by time and/or count, so a removed element can come back only from a node out of contact while a great deal of churn went by. The bound passes notes/arbitrary-values.md (at 0 no removal is final against a stale node; unbounded is today), and spec/requirements.md Data model then states the weaker property in place of "a removal is final".
- **Rows S1 allows**: schemas a node learned (`d/`), `cv/` at most one row per held snapshot: bounded by what, and is that bound live data?
- **Account names** at rotations (issues/rotation-names-grow.md), and whatever replaces them (issues/actors-one-mechanism.md: nothing kept per commit for good).
- **Usage rules that exist to dodge growth** (commit per editing pause, never per keystroke; presence by expiring ephemeral writes) are stated in spec/requirements.md Generality as steering toward lower cost: once growth is fixed, check they are no longer needed to keep a disk from filling.
- **Lists naming commits outlive the commits**: below.

## When an entry is dead
A verdict reads a list entry naming commit c only when it judges c itself (spec/permissions.md §5.2: c's delta is valid where a cut's list names it or a counting addendum vouches for it; an own cover S is valid where its removal's frontier names S; a purge request holds its right where a cut lists it). The roles model judges only commits a node holds (`addenda::Ctx::step`), so an entry naming a commit the node does not hold is read by no verdict there.
- **Content and purge-request entries** (frontiers, addenda) are dead at a node from the moment it forgets c (a valid held cover carries c's live writes, or c dropped as invalid, spec/commits.md §5 Forgetting) until c comes back to it. A commit can come back (a store keeping it unread, a peer that has not compacted), and then the entry must come with it: dropped for good while c can return, it loses c's live write at that node where the cover carrying it falls. Whether that changes a reading in the model: Model result below.
- **Role entries** name role commits, never forgotten while the thing is held: never dead.
- **An own cover's entry** names a snapshot; dead once later snapshots cover it, as any content entry.
- Globally dead (no node holds c, stores included) is not knowable by any node, so entries are dropped per node, as evidence.

## Proposals, ranked
The design keeps the built rule: a removal's list is inside the removal, whole in every copy (notes/write-path-design.md §2, E4), bounded per removal by what the remover held of the removed party then. With no history promised that is O(live state), so "never writes ever made" holds; with history kept for a time the entries outlive the history they served, a leak by notes/principles.md (Close leaks), which stays open.
1. **An entry is evidence of the commit it names, and leaves with it** (A2's "evidence leaves with the commit that needed it", applied to lists): content and purge-request entries in per-thing leaves a node holds while it holds a commit whose verdict reads the leaf, the role entries staying with the removal. Modelled (Model result: no reading changes). Not the design: every carriage rule tried for leaves either left a removal arriving without the leaf its listed writes need (they then pend for good: notes/evidence-model-findings.md 6, 35) or kept every leaf with its removal for good, and where the lowered party writes through the edge again its new writes keep every earlier lowering's leaf on that thing for good (3.2 KB per such role change at 10 members with no history, 1 MB with 30-day history). E4 allows a per-thing form back only under a carriage rule by which no holder of a removal can lack a part it could need.
2. Rejected: **a window** (list only commits stamped within a span before the removal): at 0 every in-flight honest write falls, at infinity it is today, and stamps are the removed party's own (backdated at will), so no span is justified (notes/arbitrary-values.md). Listing less is always safe (it never makes a write valid), so a window buys nothing.
3. Rejected: **a later role commit compacting earlier removals' lists** ("settled" roles): two admins compacting differently give two readings, and no rule may wait for a fight to settle (notes/principles.md, Forks are permanent).

## Model result
roles-model `forget` (`Policy::Travels` against the built `HeldList`, control `Policy::Stranded`; `roles-model -- 0 forget-entries`, default test `forget::tests::entries_leaving_with_their_commit_change_no_reading`). `Travels`: every node keeps a frontier or addendum entry only while it holds the commit named, and gets it back with the commit. `Stranded`: an entry is gone for good at a node once it forgot the commit, even when the commit comes back.
Over 1,151,232 worlds (one member-family world in 8 with Bob's writes in or out of kept history, and the attack family): `Travels` reads as `HeldList` at every node in every world, with no disagreement, no fixpoint cut and no forged write shown; `Stranded` reads otherwise in 19,686 worlds (the nodes that dropped an entry with a forgotten commit lose the commit's write when it comes back after the cover it was forgotten under falls, while others keep it; minimal world `an_entry_comes_back_with_its_commit`). So within the model the only condition is the delivery one: an entry travels with its commit. Entries held at the end: 6,784,380 under the built rule, 6,221,750 under `Travels` (the model's worlds forget little; the saving is what the scenarios below count). Not modelled: entries as blobs a commit pends without (the carriage question E4 leaves open).

## Scenarios
32 B per entry; commits about 400 B; compaction by the trigger (a snapshot once droppable bodies cost twice one).
- **A thing of 10 members, 10^6 content writes, no history promised, 10 removals** (each removed member wrote 10^5): listing every commit ever would be 3.2 MB per removal, 32 MB for good. The built rule lists the backlog: about 100 entries per removal on a thing of 20 small aspects, 3.2 KB, 32 KB in all, plus 32 B per purge request the member still has held (1% of writes deleting: 32 KB per removal). Under `keep` for 30 days at 1,000 writes a day: 30,000 entries, about 1 MB per removal, 10 MB kept after the history it served is gone. Proposal 1 would keep about 1 KB per removal for good (the role entries).
- **An organization of 1,000 members, 100 removals from its holders of 10** (10 writes a day each through the organization): no history, about 1,000 uncovered commits per removal, 32 KB, 3.2 MB in all; 30-day history: 3,000 entries, 96 KB per removal, 9.6 MB kept after the window; history forever over 3 years: about 110,000 entries, 3.5 MB per removal, 350 MB, against about 4 GB of history bodies kept by choice (8%, the option's own cost). Proposal 1 would remove all but the history-forever case.

## Work, not storage
- A commit with a part no own replace covers (a part on an aspect another writer compacts, a part a setting keeps) stays whole until a snapshot covers that part too, and is judged again at each later own replace of its covered aspects (spec/commits.md §5 Own replaces): work per write grows with such commits held.
- A snapshot rewrites the whole field, so each compaction of a very large field writes and logs it whole (no snapshot links existing pages).

# A destroyed thing's sync ID is never left at some nodes
> Summary: Three ways a destroyed thing's own sync ID S outlives the destruction: a node keeping S unread never learns of it and keeps S and its sync record forever; a released thing forgotten at the destroying node leaves own-store entries of its forgotten role commits, so S is never emptied there; a purge request with no `expires` keeps S (and the thing's secrets at its readers) forever, by spec.
> Priority: normal
> Tags: sync, engine, tess-call

## Unread holders never leave S
A node keeping S unread (an account given sync on t) cannot read the destroying request, so spec/sync-judgement.md §6 keeps S while its closure lists t, i.e. while its account's sync record does: forever. After emptying its store holds nothing of t's content (privacy holds), but S, its path and the sync record stay.
Plan (wire change, so not done in destroy-sync): a **closing step**. The emptying node (holder of the newest step's delete key, spec/sync-judgement.md §5) registers, once its deletes are done, a child step marked closed (fixed sentinel public keys, no claim set), signed by the parent's delete key as any step. A node keeping S unread taking that Register drops S's entries (as §6 Stops), forgets S and its path, and its account drops the sync record (a write to its own D). Readers treat a closed head as told. Only a delete-key holder of the head can close S, the same party that can already delete every entry there, so it adds no power. Needs: the step form and Register in spec/sync-ids.md, spec/sync-judgement.md §5 and §6, core/test/tla/net/NetDestroy.tla.

## Released: forgotten role commits' own entries stay
osis-sync `destruction::repro_a_released_things_sync_id_empties_and_is_forgotten_spec_sync_judgement_5` (ignored): node 0 releases t; within the window it logs fresh encryptions of t's grant commits under S; past the window the release forgets t (spec/commits.md §5 Forgetting: role commits included), so those own entries name no known commit, are never judged, never leave, and S is never forgotten (nor t's secrets). spec/sync-judgement.md §3 Dropped bodies says a commit forgotten with a released thing has its entries must-not-hold. Fix: forgetting a commit drops its own-store entries under every S (or the read judge treats an own entry naming no known commit and no record as must-not-hold).

## Purge with no `expires` keeps S forever
spec/sync-judgement.md §5 keeps the destroying requests under an emptied S until their expiry; a purge request without `expires` has none, so every node holding t's secrets keeps syncing S, keeps the secrets (for the head's delete key) and never forgets S, and stores keep the request entry. That is how a node away past the window still learns of the purge, so it may be intended; the alternative is the requests leaving at the end of their window (`wall_ms(ts) + ROLE_KEEP` or `expires`, the earlier) and accepting that a node away that long never learns (as for releases). Tess's call.

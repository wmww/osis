# A registrar holding no write secret registers a step before the store holds its write rotation
> Summary: `Engine::step_needs` at a node that is no writer of S's thing leaves out the rotation of a newer write epoch (no write secret held matches the step's write key to an epoch), so inbox's register sends the step to a store keeping S unread before that store holds the rotation; the store, on the new head, refuses the rotation's entry stamped under the parent (code 9) and takes it only as a reader's deposit.
> Priority: normal
> Tags: sync, inbox, engine, streams

spec/sync-ids.md §6 Steps: a node registers each step "only once that source's stream showed it holding the role commits of the thing's actor the step's epochs depend on (the rotations of the epochs it registers and of those they supersede)". Seen in `keep::a_head_move_restamps_own_entries_and_readers_deposit_nothing_spec_sync_judgement_3` (node 0 rotates t's write secret boxed to itself alone; node 2, a reader, registers the step at node 1): node 2's `step_needs` of the new step lists an older rotation but not the write rotation, node 1 reaches the new head, refuses the write rotation's entry (stamped under the parent, as it must be, spec/sync-judgement.md §3 Own store) and node 2 deposits a fresh encryption of it.

Cost: one deposit per write rotation per store per head move registered by a non-writer; the store holds the rotation only deposited until a writer promotes it.

Fix shape (unchecked): `step_needs` reads the rotations behind each key the step registers from the role history every reader holds rather than from the epochs it holds; or a registrar that cannot name them leaves the step to a writer. Engine side: Fathom's.

Fix tried (local branch `floor-registrar-needs-wip`): `step_needs` takes, for a role whose key no secret held tells, each current epoch of the role here, and reads "those they supersede" as `superseded_epochs` (keyset lists too: a reader opens no write history box). Then node 2 waits until node 1 holds the write rotation, and node 1 takes it stamped. But node 1 pulls node 2's whole stream in that pass, so it refuses the writes node 0 restamped under the new head (code 1: a stamp under no key of its head), and after the head moves nothing offers them again: spec/sync-streams.md §4 Refused says "a moved head shows the entry again in its stream", which is not built (`Known` records refusals with the head; nothing reads them), and how the peer shows an entry its cursor already passed is not specified. Blocked on that: the refusal re-offer is needed whatever `step_needs` does (any registrar racing a pull hits it). Simplest reading to decide: a node keeping S unread whose head moves pulls S again from the start from each source it told a refusal under the old head (as Full does when room grows, and as a raise to read does in `Store::set_holdings`).

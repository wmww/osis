# A re-deleted or snapshot-carried text creation's last death depends on arrival order
> Summary: a text element deleted, undeleted and deleted again (or whose delete and creation reach a node through a snapshot's copies as well as their own bodies) gets a last death at one node that is earlier than the order harness's oracle (a replay over every body) dates it, and a text snapshot body sometimes no death where the oracle has one. First deaths and delta bodies' deaths agree. About 1 of 20 `seq_compact_history` seeds.
> Tags: tests, crdt, engine, retention

Repros (`order::dating` skips them under `skip_seq_redelete_death_order`; remove the skip to see them): `OSIS_ORDER_SEED=4900 cargo test -p osis-node --test it order::arrival_order_seq_compact_large_spec_crdt_5_7 -- --ignored` (a snapshot's last death 11, the oracle's 13), seeds 5015-ish and 5100-ish ranges (`OSIS_ORDER_START=5000` and `5100`, 20 seeds each: a delta body's last death 16 vs 18, 06 vs 09; a snapshot body with no death vs 09).

What is known (seq-order):
- A text creation write dies once (spec/crdt.md §4.8), but the join reports a death on every delete that raises the flag (`seq::merge_elem`), also over an element deleted already or re-deleted after an undelete, and the replay over bodies in `(ts, ID)` order (`retention::deaths::replay_all`) does the same, so a body's last death is the last re-delete the replay met. A node sees fewer raises when the re-delete arrives before the undelete, or when the re-delete is a snapshot's copy (`replay_all`'s copy dedup drops a copy's second death of a stamp; the body's later arrival counts it).
- The join reports out-of-order flags and held copies as `Changes::undated`, on which the engine recomputes from the bodies; that made the node equal to its own replay for the orders tried, but the harness oracle holds more bodies (`keep_bodies`, carried commits fetched) and dates re-deaths the node cannot see, so "last death no earlier than the oracle's" still fails on these seeds.
- Two ways out, both a rule change: (a) a creation dies once in the replay too (dedup by stamp for bodies, not only copies; `remap`'s stamp-sharing caveat: an entry's creation and value share a stamp, so dedup per write kind), and the harness's oracle checks first deaths only for re-deleted elements; or (b) the harness compares the node with its own replay (`Engine::replay_deaths` on the same held set) instead of a bigger oracle for text bodies. (a) is the spec's reading.

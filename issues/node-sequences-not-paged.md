# Texts and lists: what still loads whole or writes more than it needs
> Summary: An edit against a stale read (or a list edit whose window the list does not lend) and writing a whole collection load a paged sequence whole; a cold edit writes about twice the store bytes it did before the stored placement (two more B-tree leaves). Reads by index, local inserts, deletes, moves and pastes, text and list edits, anything inside a list element at an index, undos and received joins load only their pages.
> Tags: performance, node, storage, crdt

Repro: `cargo test --release --workspace --test it scale::text_ -- --ignored --nocapture` (`text_undo_and_first_access_cost`, `text_range_and_edit_cost`; `OSIS_SCALE_ROWS=1` prints each step's store rows and cost spans).

Done (notes/node.md, Paged state): collections paged at any depth below struct fields, enum payloads and map entries; lazy loading of what a read or write touches; sequences through the crdt's placement held in part (joins, ops by index, text and list `Op::Edit` resolved around its change, ops and reads inside an element at an index, undos); a local insert's follow without its anchor's records (placement lookup, newest-stamp bound); whole fallbacks of ops counted (`paged op whole:` cost spans). Cold insert (10^5 chars, release): 2 → 1 pages loaded (only the page its record goes to), received insert 2 → 1; store rows and bytes unchanged (top +34 B).

Remaining:
- Store bytes per cold edit (10^5 chars, release): insert 30-34 KB, delete 28-30, move 42-46, edit 39-41 (12-16 / 19-23 KB before the stored placement). Per insert or delete the placement adds two B-tree leaves of the placement table: the one holding the top and its group rows (about 5.8 KB; group rows change with every count) and the block's (4-6 KB); a move rewrites every group row after the moved blocks and several blocks. The table is about 37 KB (391 blocks of about 38 B each for a typed text, 317 dot-map chunks, 13 group rows), so 5-7 leaves. Looked at and not done: keying chunks near blocks or pages (an insert's chunk is the newest dots', not near its block; chunks rarely change for deletes); moving the top and groups into the aspect unit (written every commit, but it would grow by about as much as the leaf saved); byte-packed stored blocks and chunks with compact group rows would shrink the table to about 15 KB (2-3 leaves) but need a block → pack map and pack membership across splits (in-memory blocks are `seq_lin` rows of at most 256, about √n). A placement under one leaf needs fewer, larger blocks for long chains.
- Time per cold edit is mostly decoding and joining the 1-2 pages it touches (one record per visible element: about 1 µs each).
- An edit whose base no longer matches the read near its change or has another length (a writer between a text session's read and commit: a session flushes against its old base when a remote change arrives), or whose window (change plus 32 chars each side) repeats elsewhere in base (periodic text, duplicated passages), is a miss of every record: whole, as before. Exact without a whole load would need the session's base version (the text unchanged since its read).
- An op whose layered follow (a commit's later op) or placement fails for a reason other than a miss resolves against a whole pass, which over records held in part is a miss of every record (`Partial::whole_pass`): it loads whole (counted: `paged op whole: whole pass` span). About 1 in 100-150 runs in the crdt's random partial-placement tests, none in the node's paged tests. A list edit with large items whose window the list does not lend (another length, the read differs there by content hash, a repeated stretch) also loads whole: its links come from the whole list.
- A move's follow finds each moved subtree's end by depth (`Placement::past`); after many moves depths are uneven and it can read most blocks (still below a whole load).
- A whole load reads every block and chunk of the stored placement (about a whole pass's cost; first whole read of 10^5 chars about 0.13 s idle, 0.39 s at load 22).
- Ops whose map keys or set values have struct or map parts load every page (the crdt matches them as the writer's type projects them, which the index cannot see).
- Collections inside list elements or at a `Slots` position are not paged apart from what holds them (a list element is reached through its sequence's placement now; paging inside it needs its record's anchors kept apart, osis-crdt work).
- O(aspect state) by nature (notes/node.md, Whole rewrites): a reset of a paged collection or above it, a validity rebuild, a page or skeleton outgrowing `PAGE_TARGET` (once, re-laid out).

# A commit applied by a part before its expiry stays applied where a later node holds it pending
> Summary: A node given a two-thing commit before its expiring part's T applies it by that part (the other part waits alone on an unknown thing); a node given the same commits after T drops the part and holds the commit pending whole. Same held set, same clock, one commit applied at one node only: spec/commits.md §4 says which parts apply is a function of what is held, with one stated exception (sync-set changes), and this is not it.
> Tags: engine, spec, tests

Found by the order harness's clock mode (`Clock`, `order::check_orders`), seed 731018 of `arrival_order_found_histories_spec_crdt_4_6` (already shrunk, 10 steps; `h` is the 731018 case there, `Cfg { sync: true, ..LARGE }`). The commit is `Forged { by: 2, a: 4, b: 3, how: 1, op: 12 }`: a `t:brief.0` part (schema default expiry) on a held thing and a `t:book.0` part on a thing whose `created.0` is not held. Held set `[0..=8, 10, 12, 13, 15, 16, 18, 20]`:
- delivered at the end (after T): the brief part is past its expiry on arrival, goes (`retention::pending::pending_drops`, flagged `PendingExpiry`), and the commit waits whole (`UnknownCreated`): `header()` none.
- all delivered at 1700002275181 (before T), then the clock moved to the end and `tick`: the commit applied with the brief part, the book part aside (`UnknownCreated`); at T the brief part goes value-less; the commit stays applied (its header, `by_aspect` rows and index line held) and no `PendingExpiry` flag is raised.

spec/commits.md §4: "A part past its expiry decides none of this: a commit that would wait without it waits". The part was not past its expiry when it decided. Options: state the limit in §4 beside the sync-set exception (a commit a part applied before its T stays applied; impact: its index rows and its other parts' bodies at nodes that held it early), or have an expiry of the part that applied a commit set the commit back to waiting when nothing else of it would apply (un-apply machinery; likely not worth it for a hostile or partial-sync shape).

The harness steps around it: `alike` ends a comparison with an early-clock node when a commit with a part on a `PendingExpiry`-flagged aspect is known at one node only. Remove that rule with the fix (or keep it, citing the stated limit).

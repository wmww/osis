# A body arriving after a residue went may die later
> Summary: Dropped bodies keep their writes value-less as residues (`retention/deaths.rs`) only while a held bounded body sorts at or before them, so a body arriving later, older than every held bounded body, can die later than at a node that held it before the drop (never earlier); keeping residues forever would be exact.
> Tags: retention, node, owner-call

Repro (confirmed): `OSIS_ORDER_SEED=5023 cargo test --workspace --test it order::arrival_order_alike_large -- --ignored` (shrunk: `vec![Write { by: 0, t: 7, op: 19, k: 1, v: 6 }, Write { by: 0, t: 2, op: 19, k: 1, v: 7 }, New { by: 2, parent: 5, write: true }, Edge { by: 0, t: 0, member: 1, role: Some(Read) }, Undo { by: 0, back: 2 }]`). On G's `/t/gonemap` (keep at most 0): W1 sets k1 (`ts` …05), W2 sets k1 (…06), U undoes W1 (…08, removes the entry, killing W2). In order: W2 kills W1's value at …06; W1 stays (its entry is live, grace bound); U kills W2, which drops with a residue (W1 sorts before it): W1 dies …06/…08. Order #2 (U, then W2, then W1): W2 dies on arrival and drops with no residue (no held bounded body sorts at or before it); W1 arrives, its only superseder before U is gone, so its value dies at U: …08/…08. The New and Edge steps only perturb the shuffle.

Also order seed 7562 (same on main before the deaths-windows branch; shrunk: `vec![New { by: 2, parent: 6, write: false }, Write { by: 0, t: 2, op: 19, k: 0, v: 7 }, New { by: 2, parent: 3, write: true }, Edge { by: 0, t: 0, member: 2, role: Some(Write) }, Write { by: 0, t: 0, op: 20, k: 0, v: 3 }, Undo { by: 0, back: 2 }]`): the same shape (two `/t/gonemap` writes of one key, an undo), held subset of 12 of 15 commits, one order dates a body …08 where the reference dates it …07 (later, never earlier).

Also exhaustive seed 7334 (`OSIS_ORDER_START=7300`, order #2, a `/t/gonemap` death dated …07 against …06).

Smallest form, found by the exhaustive order harness (`order::arrival_order_exhaustive_large`, seeds 2000..2200: 2018, 2022, 2098, 2120, 2157, 2197, every one this family, always later): three owner writes of one `/t/gonemap` key, W1 < W2 < W3, and nothing else (seed 2120: `vec![Write { by: 0, t: 0, op: 19, k: 1, v: 1 }, Write { by: 0, t: 1, op: 19, k: 1, v: 5 }, Write { by: 0, t: 1, op: 19, k: 1, v: 7 }]`). In order, W1 dies at W2 (…06). Delivered W3, W2, W1: W2 dies on arrival and drops with no residue, so W1 dies at W3 (…07). The other five are two writes and an undo, as above. Replay: `OSIS_ORDER_SEED=2120 cargo test --workspace --test it order::arrival_order_exhaustive_large -- --ignored`.

Fixed: deaths are a function of the applied set while the residue lives (retention.rs `deaths_alike_after_*`; the order harness compares every order with a whole replay). A residue W dates only writes with a lower stamp, so it is dropped once no held bounded body sorts at or before it. A body V arriving after that, with W its earliest superseder, dies at a later superseder (bounded by what superseded W): kept longer, under keep at most past its bound by up to that gap. A store from an earlier build has no residues for bodies it already dropped (same effect, plus their live writes come from the state as before).

Owner question: keep residues forever (exact; about 110 bytes per dropped body measured, 70 of them the record key, for a one-element set add, growth like tombstones, spec/requirements.md Scale; keeps the timing of every erased write under keep at most) or accept the window above (current)?

Growth under the current rule: residues stay while the oldest held bounded body does, so one long-held body (a live write never replaced, not yet covered by a compaction) keeps every later residue, and each whole replay reads them all. A dropped snapshot's residue keeps only copies whose own commit is neither held nor a residue (else it held the aspect's state per compaction).

Same family, in-order path (deaths-window-seed review; fixed in deaths-window-2): the replay plays a write dropped without a residue (or a residue-less dropped snapshot's copy) only with the state, so a body that arrived after that drop and died at it was dated there, while once a later in-order write killed it in the state a whole replay dates the body at a later superseder; `note_deaths` kept the earlier death, and a later window rested on records that were not the replay's (its debug check fired: strays seed 21812; end comparison: 1427). Now `note_deaths` replays the aspect whole when a death's write is stamped at or after `first_bare` and its own commit does not play it (`retention.rs late_deltas_windowed_found_histories_*`).

Same family, at the drop (open; strays seed 2423 with `OSIS_STRAYS_END=1`, on main before deaths-window-2 too): D supersedes a write W whose own commit does not play it, carried by a held bounded snapshot S after D (D sorts before S, so W died before S: no death for S). D then drops without a residue (no held bounded body sorts at or before it): a whole replay plays W from S and dates it at a later in-order superseder, after S, so S gains a death the records lack. Exact fix: keep D's residue while a held bounded snapshot or import after it may carry such a copy (`Core::carried`, residue-less drops); cost: residues kept while such snapshots are held. The end comparison stays off by default for this; no window debug check has fired from it in the strays runs (it could: a later window compares every held bounded body).

# When a node learns it syncs a thing decides whether a partial commit applies
> Summary: two nodes holding the same parts of a commit and syncing the same thing differ, for as long as the other part stays away: one started syncing first and holds the commit pending (`WaitDeltas`), the other applied it first and shows it. A node's sync set comes from what it holds (`sync_closure`), so arrival order can decide. Needs a spec decision.
> Tags: tests, spec, engine, sync

Repro (fails): `cargo test -p osis-node --test it -- --ignored repro_sync_learned_after_apply_spec_commits_4`.

spec/commits.md §4 allows it as written: atomic apply waits for deltas under a label the node syncs, pending commits are re-examined on a change, and "a delta of an already applied commit that arrives later (the node began syncing its label after applying, or the delta counted as held) is joined on arrival". But spec/requirements.md Decentralization says state is a function of held data and "nodes holding the same bodies read alike", and `SyncEngine::sync_closure` starts syncing a thing when a group's closure grows, which depends on what arrived. With every delta held in the end, the nodes agree (the order harness checks this, `Syncs::Late`); a part withheld for good is the difference, so the harness does not combine `Syncs::Late` with withheld parts (`order::Syncs::Late`).

Parts waiting alone (spec/commits.md §4) widen this: the wait need not be a missing part. A content commit on G and H, H's record or chain away: a node that syncs H first holds the whole commit, one that syncs H after it arrived shows G's write and keeps H's part waiting. All parts held, one sync set, and it lasts as long as the chain stays away, which a hostile author can make forever. A role commit is not affected (it never waits whole). The harness plays such a held set without syncs (`skip_sync_learned_wait`). The one rule with no sync timing in it is that a thing's wait never holds a commit whole, at the price of an honest commit showing partly until a synced thing's record comes: the owner's call, with this decision.

Decide: accept it (say so in spec/commits.md: atomic apply is judged at arrival, not a function of the held set) or make it exact (an applied commit under a newly synced thing with a part missing goes back to waiting: an un-merge, costly).

Recommendation: accept, as a hole in notes/convergence-study.md's table. Both nodes keep requirements' "applies all the parts it may read and syncs at once, or none" as of when each applied; exact would make a shown write vanish on learning of a group, for a part that is usually about to arrive. It lasts only while a part is withheld, and heals when it arrives. Role commits never wait, so authority is not reached. This needs the owner: it is an exception to requirements' Deterministic line (when the sync set was learned is an input, not a held body).

Studied: S's required set hanging on other paths (189, fix parked: it exposes three more), a grant on an unaccepted thing counting through certificates (138, the model is right, no fix yet), content kept with no secret (169, 180), stale status sources (113, reached once record-edge removals travel).

## S's required set hangs on what a node holds by other paths (189)
- Shrunk script (8 steps): `New(3), NewIn(3, 0), Give(3, 1, Holder::Node(1), Syncs), Strong(1, None, 1), Strong(1, None, 0), Give(3, 0, Holder::Node(1), Reads), Run, Unstrong(0, Some(0), 1)`; seed-0 form: Alice makes T0, and T1 minted with admin T0 (held from T0 alone), grants Bob sync on T1 and read on T0, Bob holds both from his root, Alice drops T0 -> T1. Fails on most worlds.
- Cause: a thing's `sync.0` and `created.0` are carried under its independent's sync ID (the nearest independent thing up its record chain) whatever that unit holds (spec/sync-ids.md §2; engine `sync_ids::published`). Bob, holding T1 by his root, logs T1's keying must-hold under T0's sync ID; Alice released T1 and forgot it. The engine is wrong by the principle (a body leaves a reader's store only for a reason every holder sees), and spec/sync-set.md §2 ("T's sync ID carries exactly T's sync unit") already says so.
- Built and parked (branch `keel-diff-rest6-withpub`, commit "A sync ID carries exactly its sync unit"): publishing removed whole, with a seed-0 holding test of the shape above. Every default test passes, but three full-size seeds start failing (61: sources status counts that are no member at quiet; 165: a paired node keeps a thing it was granted sync then read unread, shrunk `New(1), Give(1, 0, Holder::Node(0), Syncs), Run, Pair(0), Give(1, 0, Holder::Node(0), Reads), Run, Strong(3, None, 0)`; 181: entries waiting for a read secret, not parked). All three pass on main; 165 suggests a paired node finds a thing's `created.0`/`sync.0` through D's publishing. Study those before landing.

## A grant on an unaccepted thing counts through certificates (138; 183 on main since the judgement follows its own inputs)
- Seed-0 form: Alice grants Bob read on T0 and T1, mints T2 with admin T1, grants T0 read on T2; Bob accepts T0 only and holds T2 from his root (reading it through T0, he holds T1's roster among T2's certificates, his grant on T1 included); Alice lowers Bob to sync on T0: Bob still reads T2 by his never-accepted grant on T1.
- The model is right (spec/sync-inbox.md §5: a grant gives a role only accepting takes up; otherwise the role hangs on which certificates happened to arrive).
- Tried, not kept: `role_here` counting the account's grants only through things a held vertex's strong reaches (`Closure::targeted`) and `forget::read_path` judging by that role. It fixes the seed-0 test and every osis-sync test passes, but 10 engine and osis tests fail (`closure::a_node_writes_only_what_it_holds`, `sharing::role_before_delete_keys_reads_as_read`, undo tests, `thing_cost`, `strangers`): the role is asked inside a transaction before its settle sets what is targeted, and LocalPeer worlds hold things without strongs. The rule needs a place in the role computation that every caller (writes, boxes, lost access) agrees on; not a filter added to `role_here`.

## Content kept with no secret (169, 180)
- Two shapes fixed and tested: an edge write removing a mint admin's record edge did not travel under the mint admin's sync ID (`holding::a_removed_record_edge_reaches_its_mint_admins_readers_spec_permissions_4`), and a thing whose secrets derive from a thing the reader lost kept its content (`holding::a_reader_removed_as_a_sibling_keys_a_thing_below_reads_it_no_more_spec_permissions_3`).
- Still failing: the node reads a value while `why_role` shows no role and no secrets held (169: `New(0), Run, New(3), NewIn(3, 0), Give(3, 2, Holder::Node(2), Syncs), Revoke(3, 2, Holder::Thing(0))`, the record-edge removal now arriving; 180: `New(3), Give(3, 0, Holder::Node(1), Reads), Run, Strong(1, None, 0), NewIn(0, 0), Strong(1, None, 1), Run, Revoke(0, 0, Holder::Node(1)), Give(0, 0, Holder::Thing(1), Reads), Give(3, 1, Holder::Node(1), Reads)`). The secrets were dropped but the content stayed: forgetting keeps what `read_path` says a held path reads, by `may_read` (any path, accepted or not), while the drop judged by the node's role. One rule for both is the fix; it meets the class above.

## Latent, no reproducer on main
- A departed store on a live connection may never be reopened to be moved past its keys: on `keel-diff-200-wip` (store holding older epochs' secrets), the script `New(1), Give(1, 0, Holder::Node(0), Syncs), Give(1, 0, Holder::Node(2), Writes), Strong(2, None, 0), Run, Strong(0, None, 0), Run, Revoke(1, 0, Holder::Node(0))` left node 0 keeping T's entries on 80 of 80 worlds (on main 0 of 80). The readers' members at the stores (nodes 0 and 3) ended and closed when genesis, registered there, became their step; after the revocation nothing reopens S: the stores' credentials and `changed_at(S)` do not move, so they never test S again (spec/sync-opens.md §5 Testing), and a reader tests nothing toward a peer it judges departed (no walk state, §4), though its filter now shows the sync proofs the stores would hit. So `inbox::register` has no member to plan on.

## Stale status sources (113)
- Seed 113 fails "sources status counts that are no member at quiet" (node 4) since an edge write removing a mint admin's record edge travels under the mint admin's sync ID (more holder pieces, so different traffic); it passes on main before that change. No shrink yet. With publishing removed (the parked 189 branch) seed 61 fails the same way.
- `Node::closed` returns early only when it holds no session for the connection; a session goes only in `closed` itself, which then closes it in streams and opens and hands its members on, and opens learns of a connection only through its session's messages. So that early return skips nothing, and the stale path is elsewhere.

# Pairing as a rotation: osis-sync tests fail on the custody branches
> Summary: On fathom-custody-engine (pairing is a rotation of P), `siblings::a_sibling_paired_after_inbox_lifetime_keeps_an_accepted_grant_*` fails (a node paired late never gets S's head: the granter's view of P's profile dial list lacks every node paired after the card) and `growth::a_lowered_writers_invalid_writes_leave_nothing_and_return_on_regrant_*` fails (one more blob row at node 1 at 20 writes than at 10), the latter only since seed re-seals stopped boxing a node its own seed.
> Priority: critical
> Tags: engine, sync, tests

- siblings (fails before and after the re-seals): stranger_siblings, account 1's grant accepted on node 1; node 3 paired past INBOX_LIFETIME keeps S unread from the record but holds no head, so it refuses every entry node 1 streams (`Refused`, code 1). Node 1 keeps S unread too, so only a reader registers steps (`inbox::register`), and the granter (node 0) is the one reader. Node 0 dials only node 1: its copy of account 1's profile dial list (`dial^.0`) holds 1 entry where account 1's nodes hold 3 (node 2's and node 3's entries, written at their pairing epochs, never count or open at node 0). Node 2, paired before the grant, has no head of S either. Next: why node 0 does not read the dial entries written after a pairing rotation (the profile is rotated at the new nodes for the derived epoch they wrote under, `rotation::merge::due`; check that rotation boxes the card's link key, and whether a profile write signed at the pairing epoch counts at node 0).
- growth: node 1's store holds one more `B/` row at 20 lowered writes than at 10. It passed while every single-node account re-sealed its first seed to itself at each D pass end (one more commit on D per node); with that gone it fails. The extra row is not yet identified; the test reads as sensitive to an incidental commit.
- Fixed on the branch: a thing regaining its own keys restarted from every current derived epoch, so one derived from a P epoch newer than its own rotation stayed current and unboxed, and every node re-sealed it to every holder at its pass end (the storm in `flows::writers_of_two_accounts_*`, the re-seal inbox hint keeping `driver::a_removed_node_is_dialed_no_more_*` dialing); a left node kept sharing as its account (`shared_here` read `core.me()`), so `duties::a_node_removed_from_its_account_stops_syncing_*` kept syncing.
- Phase 2 (`fathom-custody-phase2-wip`, a P rotation also re-keys D) adds 16 failures, all one check (harness `must-hold bodies a caught-up reader lacks at quiet`), all fixtures built on `contacts()` plus `w.pair(..)` (ephemeral `three`, `siblings`, the driver's removed-node dial): the new device's rotation of P's profile (keys.0 + secrets.0, signed at the pairing epoch, read epoch n=2 boxed to the card's link actor and P) reaches the contact node with its `secrets.0` part `Missing(Plain)` while the contact holds read n=2, opens the entry's wrap and decodes the blob. Next: why the contact's ingest of that entry leaves the `secrets.0` part out (the roles section's epoch, or a strip/keep rule), and why D's re-key in the pairing rotation changes the profile rotation (passes on `fathom-custody-engine`; not the account-departures change).

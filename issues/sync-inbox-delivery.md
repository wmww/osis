# Inbox deposits are sent once and can be lost
> Summary: `SyncEngine::send_outbox` takes an inbox blob (a grant, a removal notice) out of the in-memory outbox as soon as the Deposit command is queued; a connection cut before the reply, a refusal (code 13 while the recipient's home label is not registered yet, a full budget), or a restart of the sender loses it, and nothing re-sends it. The grantee never learns of the grant (it holds no hint of the group's label).
> Tags: sync, node, permissions, tests

- Seen in the simulator: `osis_sim::replay("grant_lost_on_crash", 1)` (tier 1 test `grant_lost_on_crash`, ignored): the admin's device grants and crashes before the deposit is delivered; after restart the grantee's device stays outside the group (liveness check: "a member ... cannot read it at quiescence"). Under message faults the same happens on a cut (first runs of `reader_relays`), and with the recipient's home label not yet registered the deposit is refused with code 13 and dropped (diagnostic "deposit refused: code 13"). The phase B scenarios set up grants without faults to keep testing the rest.
- Fix (node-sync): keep outgoing inbox blobs in the durable sync state until a deposit reply `OK` (or a terminal refusal) from each inbox server; retry on reconnect and after code 13/12/4 with backoff. Re-sending is safe (a deposit of a held blob changes nothing). Related: notes in issues/node-sync-gaps.md (Inbox).

# A blind node links every label one connection syncs, against "unlinkable beyond their overlap"
> Summary: spec/requirements.md says different groups of one owner are unlinkable at untrusted nodes beyond their overlap, but a client opens and syncs all its labels on one connection (spec/sync.md §6), so a server learns the full label set of each device per session, plus its IP, heartbeat and deposit timing per label. notes/sync.md "What a blind node learns" admits "which labels one connection opens"; the requirement was not amended and no mitigation (one connection per label or per actor, padding of label sets, Tor) exists.
> Tags: security, sync, spec, owner-call

Consequence: one de-anonymized label (a group whose membership is public) de-anonymizes the device's whole label set at that server, with sizes and activity. Relays see the same (notes/networking.md Risks). With a stable NAT'd IP the linkage even persists across sessions.

## Recommendation (owner decision: wording)
No client policy meets the sentence literally: the server sees the IP either way, so one connection per label only hides the grouping from a server that does not log addresses, at the cost of hundreds of QUIC connections per device. The honest requirement is what the data layer guarantees, and the transport layer is left to an anonymity network for those who need it. Proposed text for spec/requirements.md Untrusted nodes:
"Nothing stored or relayed links different groups of one owner beyond their overlap. What a connection reveals (its address, and the set of labels it opens) is network metadata, hidden only by routing through a relay or an anonymity network."
Then notes/sync.md "What a blind node learns" and the requirement agree. If the owner wants the grouping hidden from the server itself, the cheap policy is one connection per group actor (a team's labels together, a person's together), which hides cross-team membership from a server that does not correlate by address; per-label connections are not worth their cost.

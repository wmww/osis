# A received role commit drops a self-removal's losses before it is placed
> Summary: node-sync's lost-access trigger (`drop_lost_due`) drops an actor this node left by its own self-removal as soon as any received role commit on it applies, whether or not the self-removal is placed (`drop_left` waits for that only on its own path). The leaver forgets the labels and the removal's outbox records, so members never learn it left (spec/permissions.md §3: drops once placed).
> Tags: node-sync, security

## Notes
- Repro (from review of self-removal-crash): B leaves g offline (`demote` + `carry_out`), the admin meanwhile adds an edge on g, the host then refuses uploads (`HostPolicy { cap_entries: 0 }`), B reconnects: B applies the admin's commit, the trigger drops g ("Removed" diagnostic), the admin's roster keeps B. Without the admin's commit B keeps g (refused uploads, waiting). With uploads accepted the race usually goes the right way (upload before apply), so a plain test passes.
- Fix direction: `drop_lost_due` skips actors with an own self-removal behind them (`departures_placing` gives a commit) and leaves them to `drop_left` (arm `left_check` when it skips any).
- Related, open: the wait has no bound. A host refusing forever, or a replacement label the leaver cannot open, keeps the secrets (the app can still call `drop_lost`). Members lose nothing by it (they keep boxing the leaver until they learn); the leaving user's data stays. Consider surfacing it (status) rather than a timeout.
- Cost while waiting: `drop_left` reruns `lost_leaving` (`lost_among` over every held actor, decoding the whole pending store in `pending_grants`) on every step that changes sync state or the engine. Fine for the usual seconds; unbounded with the wait above. Could recompute `own` only on engine generation change and recheck `placed` on state version change.
- `drop_left`'s full `drop_lost` also drops losses with no own self-removal behind them (the box-without-edge case the start check avoids, `hinted_walk_claims_for_boxed_actor_spec_sync_5`); and one unplaceable self-removal holds back the drop of every other one. A per-actor drop (only actors whose own removals are placed) fixes both.
- `drop_left` stops checking (`left_check = None`) when nothing lost has an own self-removal behind it, e.g. while a pending re-grant keeps the actor (`pending_grants`). If that grant later stops counting (a day old, never applied) the loss has no trigger until restart or the next received role commit.

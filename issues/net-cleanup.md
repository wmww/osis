# Networking crates: leftovers of the simplify pass
> Summary: Costs a hostile opener or peer can still cause in osis-proto's server engine (live-ID list per Reconcile, path reparse past the cache, whole-blob read per signed delete-key item), duplicated quinn/noq wrappers in osis-transport, driver helpers duplicated between osis-server and osis-node, InProcess streams kept per connection. None is reachable without opening a label or holding its keys, except the path reparse.
> Tags: proto, transport, server, security

- **Reconcile responder** (`ServerConnection::dispatch`, Reconcile): `store.live_ids(label)` loads every live ID of the label per Reconcile message (32 B each), so an opener of a large label pays O(label) memory and store reads per message, up to `MAX_RECONCILE_MESSAGES` per reconciliation and without limit across them. A range-scan store call (IDs in `[lower, upper)`) or a per-connection snapshot would bound it.
- **Path cache eviction** (`server.rs` `cached`, `MAX_CACHED` 4096): a peer cycling over more labels than the cache holds makes every Upload, Deposit and Delete reparse the label's whole path (`store.path`, up to `MAX_PATH` steps). Needs no open (uploads are authorized by stamp). An LRU, or a cap per message on path loads, would bound it.
- **Delete by level** (`server.rs` `delete`): after the label signature holds, the whole blob (up to `MAX_BLOB`) is read to parse its prefix, per item (1024 per message). A `LabelStore::prefix(blob_id)` read (the prefix is small) would make it cheap; `BackendStore` stores blobs whole.
- **quinn and noq wrappers** (`quic.rs`, `iroh.rs`): `conn_err`, the `Connection` impls and the send/recv stream wrappers are identical code over two crates with the same API (iroh uses n0's quinn fork); the listener accept loops (handshake under a deadline, at most `MAX_INCOMING`) differ only in where the cap is enforced. A macro could share them; left as plain code.
- **Driver helpers**: osis-server `driver.rs` and osis-node `sync/driver.rs` each have `blocking` (block_in_place on a multi-thread runtime) and a reader task forwarding a `LinkRx` into the driver's event channel; both could live in osis-transport `link`.
- **InProcess streams** (`mem.rs`): a connection keeps every stream's state until it is dropped; long-lived in-process connections that open many sessions grow (tests and the in-process runtime only).
- **Listener backlog** (`quic.rs`, `iroh.rs`): a connection whose handshake completed waits in its own task for a slot in the 64-entry accept channel; if nobody accepted, those tasks would pile up. `link::serve` accepts continuously (closing past its cap), so this is not reachable today.

# Server engine: costs a peer can still cause
> Summary: What remains after the net-cleanup pass: the listener backlog that `link::serve` keeps unreachable, and the depth of the server driver's shared input queue.
> Tags: proto, server, transport, security

- **Listener backlog** (`quic.rs` `accept_loop`, used by `iroh.rs` too): a connection whose handshake completed waits in its own task for a slot in the 64-entry accept channel; if nobody accepted, those tasks would pile up. `link::serve` accepts continuously (closing past its cap), so this is not reachable today.
- **Input queue depth** (`osis-server` `driver::run`, `link::forward`): every connection's reader sends its reads (up to 64 KiB each) into one 1024-slot channel and reads on while it has room, so one opener pacing small inputs (three whole-space Reconciles each, under `MAX_UNANSWERED`) can queue about 1024 inputs ahead of every other connection's. Each input is bounded (notes/sync.md, Hub stall bounds), but the wait is their sum: at 10^5 entries about 135 ms per input, over two minutes, past `STALL_TIMEOUT_MS`, so honest peers time out and redial behind the same queue; at the 2^20 cap about 1.5 s per input, near half an hour. A writer's Upload inputs (about 1.2 s each) do the same. A per-connection limit of one queued input (connections take turns per input) fixes the single-connection case; many hostile connections (`max_connections` 10,000) still each take a turn, which needs a per-peer work budget or turn order by peer key.

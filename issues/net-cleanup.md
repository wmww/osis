# Server engine: costs a peer can still cause
> Summary: What remains after the net-cleanup pass: a Reconcile over the whole space still sums every live ID of the label per message (needs a fingerprint index), an Open from anyone loads the label's whole path before any proof holds (plan: sync-key and child indexes), and the listener backlog that `link::serve` keeps unreachable.
> Tags: proto, server, transport, security

- **Reconcile fingerprints** (`ServerConnection::dispatch`, Reconcile): reads are now limited to the asked ranges (`LabelStore::live_ids_in`; ranges are sorted and disjoint), but a fingerprint over a large range still needs every ID in it, so an opener repeating the whole-space fingerprint pays O(label) reads per message, without limit across messages. A bound needs fingerprints the store keeps per subtree (additive sums, spec/wire.md §11.3) so a range costs O(log n). Needs an open.
- **Open loads the whole path before any proof holds** (`server.rs` `open`, `cached`; `MAX_CACHED` 4096). Anyone can send Open: `Proof::verify_sig` only checks the prover's own signature, so a stranger with a fresh key passes it, and a Sync proof under a key not on the path makes the server load and parse every step (`LabelStore::path`: one store read and one step parse per step, up to `MAX_PATH` 2^20) and then refuse. Cost per Open: L store reads (osis-server: a redb get of a ≤323-byte `S` row plus parse and hash, a few µs each), so about L × 5 µs CPU; nothing caps L except writers' rotations. It repeats per connection (fresh cache), per head change, and per Open once a connection names more than `MAX_CACHED` labels (refused Opens are not counted against `MAX_OPEN_LABELS`, which is checked after the load). Memory: a connection caches up to `MAX_CACHED` whole paths, so 4096 × L × ~400 B per connection (L = 10^4: 16 GB). Only Path needs the whole path, and only after an open.
  Plan (store format change, in place):
  1. `LabelStore`: `step_with_sync(label, pk) -> Option<StepId>` (the newest step registering that sync key: what `rposition` finds) and `child(label, step) -> Option<StepId>`. osis-server keeps them as rows written by `push_step` in its batch: `V label sync_key → step id` (overwritten, so it names the newest) and `W label prev → child id`. `MemoryLabelStore` keeps maps; `PeerStore` answers from its in-memory path.
  2. `evaluate_open` takes the head (from `head_keys`) and those lookups instead of a path slice: Static and Member read only the head (and its claim set); Sync: head's key → opened, else `step_with_sync` → `child` → one `step` read, none → refused; Claim: `claim_set(step)` and its pk check first (a stranger stops there), then `child`. Each Open is O(1) store reads whatever the proof.
  3. Path pages from `after` by `child` (≤ `MAX_PATH_STEPS` reads per page; `after = None` starts at genesis: keep a `W label 0 → genesis` row or a genesis field in the label meta). Then `Cached` and the per-connection path cache go entirely; `MAX_CACHED` remains for head keys only.
  4. Tests: an Open with a stranger's Sync proof and a stale Claim proof on a 1000-step label does no `step` read beyond O(1) (`step_reads` counter); the existing open cases (`auth.rs` tests, sync key k steps behind → child) unchanged; a BackendStore differential of the new rows against the path across reopens.
- **Listener backlog** (`quic.rs` `accept_loop`, used by `iroh.rs` too): a connection whose handshake completed waits in its own task for a slot in the 64-entry accept channel; if nobody accepted, those tasks would pile up. `link::serve` accepts continuously (closing past its cap), so this is not reachable today.

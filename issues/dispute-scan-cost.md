# The dispute listing is capped in point order
> Summary: `disputes()` walks once per contestable removal (no exact filter exists: notes/owner-removal-plan.md step 4, Scan bound), so the API examines at most 64 candidates in point order and counts the rest; a flood of early-stamped hostile writes pushes a real dispute past the cap, where it is counted, not listed, and the cap is not a parameter of the API or CLI.
> Tags: perm, api

Detection is bounded by itself (each contestable write examined once, `DETECT_MAX` per update, the rest reported as `DisputesUnexamined`), so a real dispute's default side is only missed when more than 16 contestable writes arrive or stop applying in one update. The listing's order (point order, the earliest first) lets a hostile author sign enough early-stamped unapplied removals to keep a later real dispute among the unexamined. Open: an API and CLI parameter for the bound (`disputes(max)`), or a listing that examines the recently flipped candidates first as detection does; nothing hides silently either way (the count is reported).

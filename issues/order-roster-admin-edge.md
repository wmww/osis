# A part missing again turns invalid and stays missing, keeping its thing's record
> Summary: osis-engine `order::held_set_decides_plain` seed 915130969958 (length 60, settled): a node keeps a thing's record (its roster shows the mint admin) where the keep-everything node released it. A part dropped while invalid, valid again (missing, to fetch), then invalid again before it arrives stays `Missing`, and a missing part keeps its commit's other things needed. Converting every missing invalid part to dropped-while-invalid fixes the seed but breaks never-received parts judged invalid only for now.
> Priority: normal
> Tags: engine, tests

Replay: `OSIS_ORDER_SEED=915130969958 OSIS_ORDER_LEN=60 cargo test -p osis-engine --test it -- --ignored --exact order::held_set_decides_plain` (fails in a random order, order #4, not under `NAMED`). Reproducer: `disputes::repro_a_part_missing_again_that_turns_invalid_drops_as_invalid` (ignored, fails by design until fixed).

What happens: commit C mints Y (`created.0`) with the strong on G's `holds.0`. At the failing node C's part on G is dropped while invalid, made valid again by a later arrival (`retention::valid_again`: `Missing`, to fetch), then invalid again before it arrives: it stays `Hold::Missing`. `retention::needed::needs` (`waiting`) counts a held commit's missing part on a thing in the node closure as a need of the commit's other things, so Y's record stays. A node given the same commits in another order holds C's part dropped while invalid and releases Y. `retention::drops_invalid` says an invalid part is neither held nor missing, and `reopen_to_fetch` keeps to that for a part it reopens, but `drop_invalid` only drops held parts (`goes_invalid`).

Tried: in `drop_invalid`, every missing part with `drops_invalid` becomes `Dropped(Invalid)` (no body), its commit put on `drop_due` (`Core::put_meta`, `index_validity`). The seed and the reproducer pass; four engine tests fail (`order::chainless_part_creation_missing_spec_commits_4`, `validity::a_roles_secret_opens_an_entry_only_as_its_committed_key_spec_wire_4`, `validity::an_entry_opening_under_two_keys_judges_alike_in_any_order_spec_wire_4`, `validity::hostile_split_commits_harm_only_their_forged_things_alike_everywhere_spec_wire_4`): a part never received yet whose validity is not settled (a split commit's path key not held, a record chain missing) reads invalid, so it dropped and its copy was refused. The rule needs to tell a part judged invalid from one not judgeable yet (or a part reopened by `valid_again` from one never received), or `needs` should count only a missing part the node would take; decide which against spec/commits.md §5 Invalid and What a held thing needs.

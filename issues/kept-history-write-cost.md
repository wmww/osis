# A write to an aspect with a relative history bound re-dates every body kept there
> Summary: Each write to an aspect whose setting keeps history a while after replaced (`t:kept.0`, a day) re-derives the replaced-at date (`bounds::dated_replaced_at`) and so the sync facts and fates of every body still in its history, so n writes within the window cost O(n^2). A date reads the aspect's whole state and held-writes row, which every write moves; it really depends only on its own writes' deaths.
> Priority: normal
> Tags: engine, sync, performance

Measured by the count of `listing::a_kept_write_rederives_only_what_it_replaces_spec_sync_2` pointed at `t:kept.0`: one write after 8 and after 80 earlier writes refreshes 16 and 160 read facts and held fates and dates 9 and 81 bodies (no cover joins: a kept body's coverage is not judged). For history kept for good the same test is flat (1, 1, 0, 0), since such a bound is not dated at all.

What moves: `judge_replaced_at` (memo `Core::replaced_dates`, read by `part_bounds` through `part_keeps`) reads `deaths` (the state at the body's positions: the aspect row, store catalog kind 1) and `held_writes` (the aspect's `held writes: rows` Cutoff row). Each write moves both, so every body's date runs again and, `replaced_dates` being a plain `Memo`, every reader of it (read facts, held fates) re-derives too. Putting a Cutoff between only moves the O(n) refresh from facts to dates.

The narrow input is per write: whether each of the body's writes is dead in the state, and the earliest held valid write superseding it (spec/commits.md §5 Bodies and deaths). That needs a stamped per-write (per-dot) death fact the join maintains, which `Killed::note` half computes per join but not for a late-arriving earlier superseder of an already-dead write (why leaving rows are only "never earlier" schedules, notes/engine-retention-history.md). Design question before building: such an index is a second, pushed form of the dating that `bounds` judges from the held set when asked.

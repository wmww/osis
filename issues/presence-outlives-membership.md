# A peer's presence outlives its sharing of S
> Summary: what a record source's stream showed present (`known`, spec/sync-judgement.md §3) is durable and cleared only by that stream, by this node leaving S, or by `RECORD_BUDGET` eviction, so a peer that left S (or never returns) counts as holding its last-shown entries for good: `present_anywhere` keeps covered commits' headers known and `later_held`, waits and idleness read stale presence. Recommended: a member leaving the record ends that source's word on S and its rejoin is a listing from the start.
> Priority: normal
> Tags: sync, opens

## What leaks
Presence rows (`k` per record, S, blob) go only when the peer's stream removes them, when this node stops holding S (`streams::left` with S not held: `Op::Forget`), or with the record. A peer whose member S closed (its Lost, or this node's) keeps its rows while the record keeps "where it stopped" for a rejoin. So the peer that left S, or that went away for good, keeps every commit whose entry it last showed known here (`judge::local`), keeps `later_held` true for snapshots only it showed, and holds back what reads presence. Bodies judged invalid are not affected: their headers go whatever sources show (spec/commits.md §5 Forgetting).

"Left S" is what this node knows of the peer's membership: opens' `drop_member` (member removed from the record by a Lost either way, or by this node closing it). A connection ending keeps the record's members (`release`) and is not a leave.

## Recommended (P1): a leave ends the source's word, the rejoin lists
- A member dropped from a record: streams forgets that source's presence, head and refusals of S and its place for S (as `left` does today for S not held). Needs `Moved::Left` to say whether the member left the record or only the connection (`LeftAt`).
- Every rejoin after a drop reads from the start (`Rejoin::From(None)`), so the listing rebuilds presence (spec/sync-streams.md §4 Applying: a listing from the start replaces presence). Rejoining from a cursor would leave presence missing entries the peer held before, so deletes at a store source would never reach them.
- So the receiver no longer uses a Lost's cursor; complete refactor: Lost carries sync IDs only (spec/wire.md: `[38, id, [sync_id+]]`), the answering Lost for a member being ended goes (it only carried the cursor), spec/sync-opens.md §3 (record keeps no stop position for a member that left) and §6 rewritten, NetStream.tla's `LostOlder` lag removed (its flag in every cfg, `SN_lostolder.cfg`), opens tests on Lost cursors rewritten.
- Cost: one listing per member close. The closing side already pays one (spec/sync-opens.md §6 Closed here); P1 makes the receiver pay one too. Store members close at every head move (the store ends members opened by the old step's sync key, spec/sync-opens.md §6), so yes: every head move relists S at every store, from each reader connected to it. A listing sends each entry ID and event (about 50-60 B per entry), plus bodies the reader lacks (none in steady state): at 10^5 entries about 5-6 MB per store per reader per head move, at 10^6 about 50-60 MB. Head moves come with rotations (removals), and an ANEW_HEAD pull from the start already happens at sources holding a told refusal under the old head. Acceptable as a rare path; if it is not, the fix is making a head move not close store members (re-key the open in place), not keeping stale presence.

## Rejected (P2): keep rows, count them only while a member
A durable marker per (record, S) for a closed member, presence filtered by it, cleared at rejoin; rows and the Lost cursor kept so rejoins stay cheap. Rejected: it is a marker "to know" (Design principles: close leaks by dropping and fetching again), keeps rows for a peer that never returns until eviction, and adds a stamp path (every member close or rejoin restamps each row of S at that record) as costly as forgetting them.

# Ephemeral data: differences from durable still to remove
> Summary: Places where ephemeral data still differs from durable without following from "held in memory" (notes/ephemeral.md Principle): a delete's ephemeral state stays at other holders, purge is half-built, ephemeral deltas never page, invalid parts stay held (a reader can fill a holder's cap), host presence is relearned per connection, and an extra guard on deleting bodies outside the closure. Each has a plan below.
> Priority: normal
> Tags: ephemeral, engine, sync, security, tess-call

## Delete
- Today (spec/sync.md §9 Sending, Delete; notes/ephemeral.md Deletion): `delete(T)` drops T's ephemeral state at the deleter only (`retention::memory::drop_things`); other holders keep it until they restart or it expires. Durable resets reach every holder.
- Decision: a delete leaves no ephemeral state of T at any holder, as its durable resets leave none (concurrent writes it did not see survive, as durable ones do).
- Why a reset commit alone does not do it: bodies are placed under labels whose closure holds their things now (`commit_bodies_under`), and the delete takes T out of every closure. The durable delete commit still reaches holders through its part on the group; an ephemeral reset commit has parts on T only, so it goes nowhere.
- Plan:
  1. Holders rule (memory reason: caps are per label, so state of a thing in no synced closure is under no cap; durable holders keep their copies. notes/ephemeral.md Holders already says holders keep the state "until they stop syncing the label"): a node drops a thing's ephemeral state, its own writes included, when the thing leaves every closure the node syncs. Judged only for things the node had inside a settled closure (the `State::memory_in_closure` guard: after a start the closure is what has arrived so far). Forgets locally without deleting at hosts (a new `MemoryDrop` kind; host entries go by the existing outside-closure deletes). A thing coming back into a closure is fetched again (the label reconciled). This also closes notes/ephemeral.md Open: a node that stops syncing a label or loses read access keeps that label's ephemeral state until restart.
  2. Where T stays in a closure the deleter could not take it out of, holders there still keep its ephemeral state: the delete writes its ephemeral resets as one ephemeral commit there. Tess's call (API): that makes one `Write` two commits (notes/api.md Writes: today one write is at most one commit per class only because a delete writes nothing ephemeral), and the delete's undo reverts its durable commit only.
- Tests: after a delete, every holder reads no ephemeral state of T, its own writes included; a thing removed from its only group and added back reads its ephemeral state again from the holders and hosts that kept it; a restarted node's partial closure drops nothing.

## Purge
- Today: ephemeral deltas carry retention `writer` (notes/ephemeral.md What follows from memory), so a purge request may name one, but the engine treats them apart: a request's fall restores no ephemeral delta (`purge::rejudge_purges` skips memory aspects), a waiting ephemeral part a request names is dropped as never received instead of held value-less (`pending.rs`, durable: `strip_purged`), and memory aspects are never flagged suspect (`suspect::raise`; flags are store rows, which would outlive the restart). The API offers neither purge nor purge on replace on ephemeral writes, and purge on replace reads as none on them (`engine::write::settle`): an option that loses its property.
- Plan: hold a purged memory part as its leftover (the expiry path's `make_leftover`, overlay `w/` row), which keeps its commit known, so the durable fall applies (unstrip, `Changed::undropped`, the lane fetches the entry again); the same for a waiting part (`strip_purged` in the memory class); suspect flags for memory aspects in the overlay; then offer purge and purge on replace on ephemeral writes (notes/api-design.md). Nothing writes such a request today, so this is correctness for other implementations and a future API.
- The plan must also say whether a snapshot's frontier passes a purged body: memory compacts automatically, so a snapshot written after the purge would cover the restored body without its content (the cost issues/eph-unify.md E names for durable compaction). Stopping frontiers below a purged body, as below an invalid one, avoids it.
- Tests: a purge of an ephemeral write whose right later falls reads the value again at every holder that can fetch it; a purge reaching a waiting ephemeral part reads alike in every arrival order.

## Paging
- Ephemeral deltas never page (`Unpaged`, spec/crdt.md §8, spec/commits.md §2), so a commit whose delta on one aspect does not fit a blob is refused whole (`Engine::write` maps the build error to `Misuse`, test `ephemeral::delta_past_a_blob_refused_spec_commits_2`; an undo whose inverse does not fit fails with the build error), and a memory snapshot or coalesced snapshot of a state past a blob cannot be built: `memory_compactions` reports nothing and weighs the aspect again once its held cost doubles, and writes keep going as separate entries until the node and host caps refuse them.
- At the default caps the node cap binds first (a state near a blob is charged far past 16 MiB, notes/ephemeral.md Bounds); a raised cap reaches the blob bound.
- A size check at the writer cannot replace paging: received valid commits from others can grow the state past a blob, and a receiver may not refuse them by size.
- Plan: pages on the memory path (memory page blobs in Core's overlay, placed and fetched as durable pages are), lifting both limits.

## Invalid parts
- Today (spec/permissions.md §6): a memory part judged invalid stays held until a restart, since its commit is forgotten once nothing of it is held and could not come back when valid again. Durable drops an invalid body and keeps its header.
- Security: a reader's ephemeral commit, invalid on arrival, is held at the writer it reaches (checked by a probe of `reader_cannot_write_ephemeral_spec_permissions_1`); a demoted writer's later commits likewise. So a reader can fill a holder's per-label cap with invalid commits until the holder restarts, refusing other writers' ephemeral writes there.
- Plan: drop an invalid memory part like a durable one and keep its commit known with no body (the header only, as the Purge plan keeps a purged part); a part that turns valid is fetched again (the drop deletes nothing at hosts). At least never hold a part invalid on arrival. Then remove the `!m.view.memory` exception in `retention::goes_invalid`.

## Presence at a host
- Today (spec/sync.md §9 Held at a host, `MemorySync::memory_gained`): a node relearns which memory entries a host holds on every connection, listing them as `gained` in its first Sync. Past `MAX_GAINED` entries per label it lists none and uploads every held body again, on every reconnect.
- Only a host restart loses its entries; a reconnect to the same running host does not. And past the message bound durable falls back to range reconciliation (spec/sync.md §6), not to uploading everything.
- Plan: relearn presence only when the host restarted (a cursor from another host run is invalid, as durable after a trimmed log), and past `MAX_GAINED` use durable's range reconciliation.

## Unplaced bodies
- Today (`State::memory_in_closure`, spec/sync.md §9 As durable bodies): a node deletes a memory body outside the closure only if it judged or placed it inside since it started. Durable deletes once it holds the body and its view is settled.
- The stated reason (a restarted node's closure is what has arrived so far, deleting while a placement is on its way storms) holds for durable bodies too: closures are durable data. Either the guard belongs to both classes, or `settled` suffices for both. Effect today: a body only restarted nodes had placed stays at the host until the host restarts.

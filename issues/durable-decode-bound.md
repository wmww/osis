# Durable deltas decode with no memory bound
> Summary: Tess's decision B (per-blob item cap `MAX_PAGE_ITEMS`, then verify and join page by page) is built through step 5: a 10^6-key map's commit or snapshot applies in 0.23-0.35 GB (was 9.8 GB). Left: the writer holds the delta whole (2.2 GB, the op API), its snapshot loads, clones and copy-indexes the whole state (2.3 GB, proposal in State), `covered` holds the body and the snapshot's part at it (3.5 GB), and step 6 (root tables paged, a format change).
> Priority: low
> Tags: security, crdt, engine

## State
- Done: `MAX_PAGE_ITEMS` = 2^21 (spec/crdt.md §8, notes/crdt.md Page items): a durable delta's root fragment and each page count at most that many items (CBOR items plus text bytes), from the heads before decoding; bad input otherwise. 2^21 rather than the first-proposed 2^20 because honest pages can reach about 1.4 x 2^20 (a map entry or list run holding a many-slot `Slots`); `MAX_RUN` went from 2^16 to 2^12 because a 2^16-element text run with moved and flagged chars alone passed 2^21 (measured 16 items per element, up to about 36).
- So one blob decodes to at most about 2^21 x 100-300 B (0.2-0.6 GB), but a paged delta still decodes all its pages at once: a hostile writer can still fill memory with many valid pages, and honest requirement-sized aspects (spec/requirements.md Scale) cost GBs.
- Done, steps 1-2 (osis-crdt `stream.rs`, notes/crdt.md Wire): the simpler variant, a streaming re-encode, so canonical form stays "re-encode equals input". The root decodes into a skeleton (paged collections reached through `Step`s left empty), re-encodes with the input's own tables; each such collection streams one leaf page at a time (decoded, handed over, re-encoded element by element with one open sequence run across pages, cut and compared with the input's pages in order); the tables are checked at the end (first appearances in table order as a running index; each commit's base its smallest counter). Claimed own counters are kept as runs (sized by the input). The rule-1 quirk stays (why: notes/crdt.md Wire); nothing on the wire changed. `decode_delta`/`decode_snapshot` now run on it and reassemble the whole; the old whole decoder is the test oracle (`codec::oracle`, `tests_stream`, fuzz target `delta`).
- Measured (`tests_stream::stream_memory_big_map`, dev build, one child process per step, peak RSS above its start), a 10^5-key map: whole decode (old) 361 MB delta / 442 MB snapshot; `decode_delta` on the stream 227 / 232 MB (it still builds the whole map); `stream_*` with a callback keeping nothing 38 / 60 MB, the same at 3 x 10^5 keys (46 / 60 MB: the delta's largest page grew): one page, whose 256 KiB decode to about 4-6 KB per map entry at peak (the page's value tree, the entries and their key index, their re-encoding).
- Done, step 3 (osis-engine; notes/engine-paged.md Streamed apply): measured below. What steps 4-5 can use: `atomic::each_piece` hands a part's pieces (skeleton, then pages in wire order) to a closure holding the transaction; `pages::join_reset` and `Tx::evict_pages` keep a join to about one page of state. Not streamed (decoded whole into the skeleton or into one piece): paged positions inside a `Slots` slot, inside a sequence element's content, inside a page.
- Done, step 4 (osis-engine; notes/engine-paged.md Streamed readers): the readers of held parts stream them (`apply::each_held_piece`) and read the state a piece's pages at a time (`Tx::state_at`); copy indexes are built from pieces (`CopyIndex::add`). Left whole, with reasons: role-class bodies (rosters); `covered`'s body, with the snapshot's part at the body's positions accumulated (`Fragment::part_at`; deciding coverage page by page on both sides needs the two streams walked side by side, a pull decoder osis-crdt does not have, or tracking which body positions some snapshot page reached: subtle), measured 5.1 GB at 10^6 (the whole-part form: about 7 GB, from 0.73 GB at 10^5 against 0.49 now); what is a whole state by nature (a rebuild's and a deaths replay's state, the copy indexes: O(part)); writer paths (undo's before state: step 5); a piece resetting a paged collection reads the whole state (`Tx::state_at`, as `join_reset` does not for reads).
- Done, step 5 (osis-crdt; notes/crdt.md Wire): the encoder streams. Every element array and field map goes through `codec::Pager` (held while its plain form fits the page target, then cut as elements come, each page put when it closes), and the collecting pass keeps no values, so encoding holds about one page per open position, not the delta's value tree; the bytes are unchanged. The stream check re-encodes through the same `Pager`: its per-page compare became the check's `Replay` holding the input's pages (a page cut differently is not there) plus the position's link list compared as written. The whole encoder is the test oracle (`codec::oracle::encode_*`): in osis-crdt's tests every `encode_delta`/`encode_snapshot` also runs it into content-addressed sinks and requires the same root and pages (`oracle::twin`; tier 1, `tests_stream` random histories, `stream_check_matches_whole_large_spec_8`). Encoding a 10^5-key map's delta (`tests_stream::stream_memory_big_map`, dev): 13 MB above the delta (2.4 MB of it the pages the test's sink keeps; measured with the input value kept, whose freed memory had hidden the peak: 0.4 MB), 0.3 s; the whole encoder 129 MB, 1.0 s. The local commit already applied through step 3's streamed path (examine stream-checks, apply joins a piece at a time; traced: neither raises the writer's peak).
- Left whole at the writer, with reasons and numbers (10^6 keys unless said):
  - The delta: the op API takes whole `Value`s (`Mutation::set`) and `Batch` resolves the ops into one fragment, so the writer holds the input value (about 0.4 GB with the step's clone) and the delta (`approx_bytes` 1.9 GB: about 1.9 KB per entry of an int key and int value, a representation cost of `Map`'s records and key index). That is the 2.2 GB of the write.
  - The undo footprint: the pre-state of what the delta touches, so the delta's order; stored as one record in the aspect's unit (`undo::remember`) and read whole by an undo (`undo_in`). A rewrite of every value of a 3x10^4-key map: 57 MB in memory, 556 KiB encoded. Paging it would need the undo buffer stored in pages and `osis_crdt::undo` resolving against pages; the writer holds the delta whole anyway.
  - The writer's snapshot (`snapshot_if`): loads and clones the whole state (+1.9 GB) and encodes it (now about one page). Its local apply joins it a piece at a time (a valid snapshot's copies are never compared with the state). Encoding from the paged state a page at a time (the encoder pulling each paged position's state pages, twice for the collecting pass; expiring values stripped and `own_retentions` read per page) would save the load and clone: the page-pulling encoder (the `Track` path walk the check already has, plus an engine page source over `PageIndex` in wire order).
  - Related: rewriting every value of a big paged map is superlinear in the ops (issues/big-map-rewrite-cost.md).

## Where the whole delta is held
1. Decode (core/crdt/src/codec.rs): `elem_items`/`leaf_pages` merge every page of a position into one `Value` tree; `Dec.fetched` and then `Replay` keep every page's plaintext; the canonical check re-encodes the whole fragment (two passes, each array building `items` and `encoded` for all its elements). First-appearance order of `Sources` and the `Commits` table are checked only by that re-encode.
2. Examine: fixed (step 3): only role-class and `created.0` parts are kept decoded.
3. Apply: fixed (step 3) but for paged sequences (whole-loaded) and a reset over nested paged collections.
4. Deaths: judging when a body was replaced (`retention::bounds::deaths`) joins the held part whole into the state at its positions, so O(part) for every body judged (notes/engine-paged.md Left whole).
5. Indexes: fixed (step 4): `copy_index` (cached up to 2^20 entries) reads the snapshot a piece at a time; the index itself is O(part).
6. Writer (engine/write.rs, retention `snapshot_if`): fixed (step 5) for encoding (`Pager`) and the local apply (step 3's path); left whole: the delta (op API), the undo footprint, and the snapshot's state load and clone (State, step 5).
7. Later re-decodes of whole parts via `held_parts`/`examine_stored`: fixed (step 4) but for role-class readers (keys, rotation, labeling), `covered`'s body and undo (a writer path).

## Open questions, answered
- **Store transaction memory**: bounded already. The osis pager keeps a transaction's dirty units and blobs in memory up to `StoreConfig::spill_bytes` (16 MiB), then writes them early as journal rows (each spill one backend commit); only about 48 B per unit written stays. Under the file backend each backend commit is one redb write transaction; redb 2.6 keeps its dirty pages in a write buffer capped at a tenth of its cache (default cache 1 GiB, so about 100 MiB) and writes the rest to the file before commit. Aside: osis opens redb with the default 1 GiB cache, 90% of it a read cache that a large store fills (resident memory); worth a config decision.
- **Snapshot root tables**: they do not always fit. Measured per absorbed commit with surviving stamps: session form 8 B and 4 items (`Commits` entry), so about 10^6 commits fill `MAX_BLOB`; commit form (role commits, multi-node key actors) 107 B (`Sources` 33, `Absorbed` 54, `Commits` 6) and 12 items, about 78 000 commits. An aspect past that cannot be snapshotted (the builder refuses a delta over `MAX_BLOB`). `MAX_PAGE_ITEMS` does not count these tables (bounded by `MAX_BLOB`, decoded into small records).

## Step plan (each step mergeable alone; sizes rough)
Target: memory about one decoded page (honest: 64-256 KiB encoded, a few MB decoded; hostile: at most 2^21 items) plus the state pages it touches, the store transaction's 16 MiB spill buffer, and per-delta trackers of a few bytes per element at most.

1. **Streaming canonical check** (done, as the streaming re-encode variant below). Replace the whole re-encode for paged positions: re-encode each page's elements against its bytes; check the cut rule per page (the cutter closes exactly at the page's last element, never before; link pages by the tree-node rule); sort order across page seams (last dot or field id carried over); `Sources` first appearance as a running "next new index" (each `Src` read must be at most the next unseen one); `Commits` exactness and `base` with a per-entry min-counter table and a used bitmap checked at the end; own counters in a bitmap over the header range instead of `used: BTreeSet`; links seen once (32 B per page); `MAX_DELTA_BARE` as now. The root blob, with links in place, still re-encodes whole. Simplicity: rule 1's "list runs counted as if not closed by content size" is the one ordering quirk a streaming check must model; consider dropping it (count the encoding as written) in the same step. Simpler variant to weigh first: build step 5's streaming encoder before this step and check by streaming re-encode (encode the decoded pieces in order with the root's tables, compare each page's bytes, compare the tables at the end), so canonicality stays one rule, "re-encode equals input", instead of a second rule-by-rule checker. Trackers must be sized by the input, not by header claims: a bitmap over the header's counter range lets a hostile header claim a huge range; use a sorted interval set of the counters seen. Gate: the decoder differentials (`tests_decoder`, fuzz target `delta`) accept and reject exactly as the old check on mutated inputs; keep the old check as a test oracle.
2. **Page iterator** (done: `stream_delta`, `stream_snapshot`, `Piece`): decode a delta's root into a skeleton (tables, metas, resets, unresolved links) and yield its content in dot order as fragments of consecutive elements, one leaf page at a time (a page's nested paged positions resolved inside it). Joining the pieces equals joining the whole (§8: elements independent per dot; struct fields per field).
3. **Engine apply per page** (done; notes/engine-paged.md Streamed apply): `examine` streams every part but role-class and `created.0` ones (decoded whole: their readers are perm, rotations and creation records), keeping only each part's dedup secret and a snapshot's tables; the carried-writes-after-the-commit check moved there from apply. Apply streams each part again (`each_piece`) and joins each piece, then evicts the state's pages (written already); a piece resetting or re-encoding a paged collection joins page by page (`pages::join_reset`). Deaths, vouching and an invalid delta's un-merge are per piece. The old whole join is the test oracle (`apply/oracle.rs`, `tests_paged`). Left whole, with reasons: paged sequences (placement, as planned), a reset over a collection paged inside another's elements or another encoding above a paged collection (rare; whole as before), a local commit's undo footprint (stored whole in the unit anyway: step 5).
4. **Whole-part consumers** (done; notes/engine-paged.md Streamed readers; +600/-300 lines): move the content-aspect users of `held_parts` (`covered`, `live`, `note_copies`, `kills`, `copy_index`) onto the iterator; role-class aspects (`roles.0`, `secrets.0`, `keys.0`) stay whole for now (rosters of thousands, not millions).
5. **Writer** (done for encoding; State): pages cut as elements stream, the collecting pass holding nothing; the local commit applies through step 3. Left: the writer's snapshot encoding from the paged state (proposal in State).
6. **Root tables page** (format change, about 300 lines plus spec): `Sources`, `Commits`, `Absorbed` and `Frontiers` may be `[Link+]` like element arrays, decoded first and held as compact tables (about 50 B per entry: 10^6 commits about 50 MB). Needed before snapshots of aspects written by more than about 10^6 session-form or 8 x 10^4 commit-form commits.

Expected after steps 1-5 for the 10^6-key map: under about 100 MB per step plus what the in-memory store keeps (measured after step 3: 0.24-0.35 GB per apply, about 0.23-0.26 GB of it kept), instead of 9.8 GB (`scale::big_map_apply_memory` measures it). Met for the applies; not for the writer, which holds the delta whole by the op API (2.2 GB at step 5).

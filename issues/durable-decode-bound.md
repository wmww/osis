# Durable deltas decode with no memory bound
> Summary: a writer's durable delta decodes at every reader with no bound on its in-memory size: about 100-250 times its encoded size for tiny map entries, up to about 1500 times for values of one-entry maps held as map keys; paged deltas are not limited to one blob. One commit can exhaust every reader's memory, and keeps doing so for anyone who later loads the label. Medium. Waits on the owner: a per-delta item cap conflicts with the Scale requirements; recommended instead a per-blob item cap plus page-at-a-time decode and join (Design).
> Tags: security, crdt, engine

- Measured (`osis_crdt` `decoded_bound_holds_dense_shapes` shapes, `approx_bytes` per encoded byte): tiny map entries about 110, a map of one-entry maps about 260, a map key that is a list of one-entry maps about 1500. `approx_bytes` tracks RSS within a small factor (notes/testing.md, `scale::eph_decoded_memory`). Decoding also builds the CBOR value tree first (a B-tree node per CBOR map), and re-encodes for the canonical check.
- A durable delta is paged (spec/crdt.md §8, link pages two levels deep), so its encoded size is not bounded by `MAX_BLOB`: tens of MiB of encoded delta are GBs decoded at every reader (`verify_part`, apply, opening the label).
- It persists: the commit stays valid after the writer is removed, so every node that loads the label pays it again; only a purge removes it.
- The ephemeral fix (`osis_crdt::decoded_bound` against the cap's room, notes/ephemeral.md Node cap) does not carry over: a durable commit must apply at every reader, so a local refusal diverges. Directions: a validity rule (a delta whose decoded bound passes a protocol constant is invalid, writers split such writes; the bound would have to be specified exactly), and/or a leaner in-memory layout (the CRDT's per-entry size, issues/eph-node-cost-bounds.md, and the map key index's two extra copies of each key) so the ratio itself is small.

## Design (needs the owner)
A per-delta or per-commit item cap, as first suggested, conflicts with spec/requirements.md (Scale: maps with millions of keys; a change has no size limit; no whole value needed in memory):
- A compaction snapshot of an aspect is one delta and cannot be split. At 10^6 keys it is 292 pages, about 23 MB (`scale::big_map_snapshot_rewrite`), about 10^7 items: about 2.5 GB decoded today. Honest readers of requirement-sized aspects already pay GBs.
- A cap that bounds memory usefully (2^20 items, a few hundred MB) caps an aspect at about 10^5 map entries or 10^6 text chars, or leaves bigger aspects without snapshots (no compaction, no bootstrap). A cap that admits 10^6 keys (2^24 or more) bounds nothing. Snapshots cannot be exempt: any writer of the aspect may write one.

Options:
- **B (recommended, no requirements change): bound per blob, decode and join per page.** Spec: the fragment part of a delta's root and of each page holds at most `MAX_PAGE_ITEMS` = 2^20 items (a CBOR data item, or a char of a run's text content), counted from the heads before decoding (or simply a 1 MiB byte cap on those blobs: items and chars are at most bytes). Honest blobs stay below it: a page closes at `CHUNK_MAX` plus one element, a run at `CHUNK_MAX` plus one element, keys and strings over `CHUNK_THRESHOLD` are chunked, nested positions page at `PAGE_TARGET`, so about 3 x 2^18 bytes at most. Resource bound: 0 refuses every delta, infinity is today. Implementation (the larger part, notes/crdt.md "Not yet: join over one page at a time"): verify a paged delta in a streaming pass (each page's canonical bytes, the cut rule, sort order across page seams, `Sources`/`Commits` first-appearance order, `MAX_DELTA_BARE`, links seen once), then join page by page into the paged state inside the commit's one store transaction, deaths and changes streamed, not collected. Memory is then about one page decoded plus the state pages touched.
- **A: per-delta and per-commit item caps**, writers splitting past them (as `MAX_DELTA_BARE`). Small change, but it needs spec/requirements.md changed: changes atomic only up to the cap, aspect size capped.
- A leaner in-memory layout (about 300-500 bytes per item today; issues/eph-node-cost-bounds.md) lowers every figure under either option; it is no bound by itself.

Open for B: whether redb keeps a large write transaction's dirty pages in memory; a snapshot root's `Sources` and `Commits` tables are never paged (one `Commits` entry per absorbed commit, 32 bytes per commit-form source), so a snapshot of an aspect written by very many commits may not fit a blob (unverified).


Owner decision (round 13): option B. First a per-blob item cap (2^20, checked from the encoding before decoding), then page-by-page decode and apply inside the commit's one store transaction, so memory stays about one page. B is the design the Scale requirement already asks for (a 10^6-key snapshot decodes whole today, ~2.5 GB, for honest data too); refactor cost is not a concern, ongoing complexity is, and B adds structure to one path rather than a second mechanism.

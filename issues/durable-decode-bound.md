# Durable deltas decode with no memory bound
> Summary: a writer's durable delta decodes at every reader with no bound on its in-memory size: about 100-250 times its encoded size for tiny map entries, up to about 1500 times for values of one-entry maps held as map keys; paged deltas are not limited to one blob. One commit can exhaust every reader's memory, and keeps doing so for anyone who later loads the label. Medium.
> Tags: security, crdt, engine

- Measured (`osis_crdt` `decoded_bound_holds_dense_shapes` shapes, `approx_bytes` per encoded byte): tiny map entries about 110, a map of one-entry maps about 260, a map key that is a list of one-entry maps about 1500. `approx_bytes` tracks RSS within a small factor (notes/testing.md, `scale::eph_decoded_memory`). Decoding also builds the CBOR value tree first (a B-tree node per CBOR map), and re-encodes for the canonical check.
- A durable delta is paged (spec/crdt.md §8, link pages two levels deep), so its encoded size is not bounded by `MAX_BLOB`: tens of MiB of encoded delta are GBs decoded at every reader (`verify_part`, apply, opening the label).
- It persists: the commit stays valid after the writer is removed, so every node that loads the label pays it again; only a purge removes it.
- The ephemeral fix (`osis_crdt::decoded_bound` against the cap's room, notes/ephemeral.md Node cap) does not carry over: a durable commit must apply at every reader, so a local refusal diverges. Directions: a validity rule (a delta whose decoded bound passes a protocol constant is invalid, writers split such writes; the bound would have to be specified exactly), and/or a leaner in-memory layout (the CRDT's per-entry size, issues/eph-node-cost-bounds.md, and the map key index's two extra copies of each key) so the ratio itself is small.

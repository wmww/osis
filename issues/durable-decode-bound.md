# Durable deltas decode with no memory bound
> Summary: a paged durable delta decodes whole at every reader (and twice at its writer): a 10^6-key map's commit or snapshot peaks at 2.6-2.7 GB applied and 9.7 GB written. Owner decision B: per-blob item cap (done: `MAX_PAGE_ITEMS`), then verify and join page by page inside the commit's store transaction; step plan below.
> Tags: security, crdt, engine

## State
- Done: `MAX_PAGE_ITEMS` = 2^21 (spec/crdt.md §8, notes/crdt.md Page items): a durable delta's root fragment and each page count at most that many items (CBOR items plus text bytes), from the heads before decoding; bad input otherwise. 2^21 rather than the first-proposed 2^20 because honest pages can reach about 1.4 x 2^20 (a map entry or list run holding a many-member `Slots`); `MAX_RUN` went from 2^16 to 2^12 because a 2^16-element text run with moved and flagged chars alone passed 2^21 (measured 16 items per element, up to about 36).
- So one blob decodes to at most about 2^21 x 100-300 B (0.2-0.6 GB), but a paged delta still decodes all its pages at once: a hostile writer can still fill memory with many valid pages, and honest requirement-sized aspects (spec/requirements.md Scale) cost GBs.

## Measured (`scale::big_map_apply_memory`, release, stores in memory; notes/testing.md Scale checks)
Peak RSS above each step's start (glibc reuses freed memory, so later steps are lower bounds):

| keys | commit / snapshot with pages | write the commit | member applies it | fresh node applies the snapshot |
|---|---|---|---|---|
| 10^5 | 1.8 / 1.9 MB | 0.98 GB, 5 s | 0.39 GB, 3 s | 0.23-0.48 GB, 3 s |
| 10^6 | 21 / 22 MB | 9.7 GB, 65 s | 2.6 GB, 87 s | 2.7 GB, 67 s |

The writer costs most: it encodes, then re-decodes its own commit through `examine` (`apply_local`).

## Where the whole delta is held
1. Decode (core/crdt/src/codec.rs): `elem_items`/`leaf_pages` merge every page of a position into one `Value` tree; `Dec.fetched` and then `Replay` keep every page's plaintext; the canonical check re-encodes the whole fragment (two passes, each array building `items` and `encoded` for all its elements). First-appearance order of `Sources` and the `Commits` table are checked only by that re-encode.
2. Examine (core/engine/src/apply/mod.rs `examine`): `out: Vec<(ai, di, Decoded)>` holds every part until apply ends; the validity checks read it.
3. Apply (apply/atomic.rs `apply_verified`, `join_into_state`): `d.clone()` per part, `touched_paths` collects every touched dot (and clones a sequence delta), `ensure_touch` loads every state page the delta spans, `st.join` takes the whole fragment, `write_touched` writes back every touched page; a root reset or encoding change loads and rewrites the whole state.
4. Deaths (crdt `Changes.deaths`, engine retention/deaths.rs `note_deaths`): one record per superseded write, held to the end; `note_copies` clones the whole state per snapshot fragment.
5. Indexes: `carried_of` (`Fragment::writes`) and `copy_index` (cached up to 2^20 entries) walk the whole snapshot.
6. Writer (engine/write.rs, retention `snapshot_if`): the whole state cloned; `paged()` builds all items and encodings of an array before cutting; then `apply_local` re-decodes everything (items 1-5 again).
7. Later re-decodes of whole parts via `held_parts`/`examine_stored`: retention (`covered`, `live`, `uncover`, ...), deaths, keys, undo, moves, rebuilds.

## Open questions, answered
- **Store transaction memory**: bounded already. The osis pager keeps a transaction's dirty units and blobs in memory up to `StoreConfig::spill_bytes` (16 MiB), then writes them early as journal rows (each spill one backend commit); only about 48 B per unit written stays. Under the file backend each backend commit is one redb write transaction; redb 2.6 keeps its dirty pages in a write buffer capped at a tenth of its cache (default cache 1 GiB, so about 100 MiB) and writes the rest to the file before commit. Aside: osis opens redb with the default 1 GiB cache, 90% of it a read cache that a large store fills (resident memory); worth a config decision.
- **Snapshot root tables**: they do not always fit. Measured per absorbed commit with surviving stamps: node form 8 B and 4 items (`Commits` entry), so about 10^6 commits fill `MAX_BLOB`; commit form (membership commits, multi-device key actors) 107 B (`Sources` 33, `Absorbed` 54, `Commits` 6) and 12 items, about 78 000 commits. An aspect past that cannot be snapshotted (the builder refuses a delta over `MAX_BLOB`). `MAX_PAGE_ITEMS` does not count these tables (bounded by `MAX_BLOB`, decoded into small records).

## Step plan (each step mergeable alone; sizes rough)
Target: memory about one decoded page (honest: 64-256 KiB encoded, a few MB decoded; hostile: at most 2^21 items) plus the state pages it touches, the store transaction's 16 MiB spill buffer, and per-delta trackers of a few bytes per element at most.

1. **Streaming canonical check** (osis-crdt, about 500 lines plus tests). Replace the whole re-encode for paged positions: re-encode each page's elements against its bytes; check the cut rule per page (the cutter closes exactly at the page's last element, never before; link pages by the tree-node rule); sort order across page seams (last dot or field id carried over); `Sources` first appearance as a running "next new index" (each `Src` read must be at most the next unseen one); `Commits` exactness and `base` with a per-entry min-counter table and a used bitmap checked at the end; own counters in a bitmap over the header range instead of `used: BTreeSet`; links seen once (32 B per page); `MAX_DELTA_BARE` as now. The root blob, with links in place, still re-encodes whole. Simplicity: rule 1's "list runs counted as if not closed by content size" is the one ordering quirk a streaming check must model; consider dropping it (count the encoding as written) in the same step. Simpler variant to weigh first: build step 5's streaming encoder before this step and check by streaming re-encode (encode the decoded pieces in order with the root's tables, compare each page's bytes, compare the tables at the end), so canonicality stays one rule, "re-encode equals input", instead of a second rule-by-rule checker. Trackers must be sized by the input, not by header claims: a bitmap over the header's counter range lets a hostile header claim a huge range; use a sorted interval set of the counters seen. Gate: the decoder differentials (`tests_decoder`, fuzz target `delta`) accept and reject exactly as the old check on mutated inputs; keep the old check as a test oracle.
2. **Page iterator** (osis-crdt, about 300 lines): decode a delta's root into a skeleton (tables, metas, resets, unresolved links) and yield its content in dot order as fragments of consecutive elements, one leaf page at a time (a page's nested paged positions resolved inside it). Joining the pieces equals joining the whole (§8: elements independent per dot; struct fields per field).
3. **Engine apply per page** (osis-engine, about 800 lines, the risky step): `examine` runs step 1's check streaming and keeps no fragment; `apply_verified` decodes again page by page: join each piece into the paged state (`touch_of`, `ensure_touch`, join, `write_touched`), then evict that piece's state pages from `tx.core.states` (written into the store transaction, which spills); deaths noted per page; a root reset or encoding change prunes the state page by page instead of `load` plus `write_full`. Two decode passes (verify, then apply) keep the examine/apply split and its pending/parked outcomes; CPU doubles for paged deltas only. Sequences stay whole-loaded for placement at first (notes/crdt.md: long texts load fully for linearization); a per-page sequence join needs placement updates per piece and is its own later step.
4. **Whole-part consumers** (osis-engine, about 500 lines across retention, deaths, copies, carried): move the content-aspect users of `held_parts` (`covered`, `live`, `note_copies`, `kills`, `copy_index`, `carried_of`) onto the iterator; membership-class aspects (`/members`, `/tenures`, `/secrets`, `/keys`) stay whole for now (rosters of thousands, not millions).
5. **Writer** (osis-crdt and osis-engine, about 300 lines): encode from the paged state one state page at a time (two passes: the first collects `Sources` order), cutting pages as elements stream; the local commit applies through step 3 instead of a second whole decode.
6. **Root tables page** (format change, about 300 lines plus spec): `Sources`, `Commits`, `Absorbed` and `Frontiers` may be `[Link+]` like element arrays, decoded first and held as compact tables (about 50 B per entry: 10^6 commits about 50 MB). Needed before snapshots of aspects written by more than about 10^6 node-form or 8 x 10^4 commit-form commits.

Expected after steps 1-5 for the 10^6-key map: under about 100 MB per step instead of 2.6-9.7 GB (`scale::big_map_apply_memory` measures it).

# A reader does not open S at a store source whose head moved while it was untested there
> Summary: sims::a_reader_through_a_node_keeping_it_unread fails every seed: node 2 keeps S unread, node 0 registers S's genesis there (Behind answered 13), node 1 (a writer of S) goes off and comes back with node 0 off; nodes 1 and 2 reconnect but neither tests S again, so node 1 never pulls the writes node 2 holds.
> Priority: normal
> Tags: sync, tests

- Seen (sync-integrate-4): node 2's `changed_at(S)` moved at the Register while node 1 was still on but held S by a payload hint (no recorded path: it showed no sync proof), so node 2 tested and found nothing there and its record's `acked_pos` passed S. Node 1 later recorded S's path (its `changed_at(S)` moved), tested S at node 2 by its walk credentials and opened nothing; on reconnecting each side starts from `acked_pos` past S, so neither tests S again (spec/sync-opens.md §5 Testing tests only sync IDs whose own `changed_at` is past `acked_pos`).
- spec/sync-ids.md §6 Walk says the reader tests the walk's credentials "at each arrival of the source's filter while S is not open there"; opens tests at filter arrival only the pending sync IDs (own `changed_at` past `acked_pos`). The two rules disagree for a source whose credentials moved after this side's last test: the walk's reading would re-test, opens' does not. Re-testing every S not open whose peer J judges a sync holder at each filter arrival costs O(sync IDs) per arrival; a cheaper reading is to re-mark S for the record when the source's head (its stream's head event, or its filter's additions) moves.
- Also open: why node 1's own test at its `changed_at(S)` did not open S at node 2 (node 2's filter should show its head's sync key; node 1 holds that step's sync key). Instrument opens' `test` and `accept_hit` on the scenario's seed 0 (flows.rs had a probe: node 0 writes with node 1 off, then node 0 off and node 1 on).
- Reproducer two nodes: `flows::a_sync_grant_accepted_later_is_kept_unread_with_the_writes_spec_sync_ids_6` (ignored): a sync grant the user accepts after a run (the everyday flow: an invitation accepted later) never gets S's genesis registered at the grantee, so it holds nothing; the same flow accepted at once passes. Likely the same class: the granter tested S there while the grantee did not sync S yet, and nothing tests it again once it does.
- `NodeHolds::behind` (a Behind answered with steps) has no passing test: only this scenario reaches it.
- The Walk's `verify_steps` and `step_creds` in `NodeHolds` still answer nothing (Behind answers carrying steps are never verified, so a source on a later step than this node's recorded path is never walked).

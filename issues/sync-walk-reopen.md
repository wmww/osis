# A reader does not walk a store source whose head moved after it last tested S there
> Summary: spec/sync-ids.md §6 Walk tests a store source's credentials at each arrival of its filter while S is not open there; spec/sync-opens.md §5 tests at filter arrival only the sync IDs whose own `changed_at` is past `acked_pos`. Under opens' rule a reader whose recorded path lags a source's new head never asks Behind there; and `verify_steps`/`step_creds` answer nothing, so a source's step past the recorded path is never walked.
> Priority: normal
> Tags: sync, tests

- The rule both sides rely on: each side tests on its own changes, and one Hit opens both ways, so S opens at the test of whichever side changed last, provided each side answers a Hit on what it shows. A walk breaks that: the source's head moved (its `changed_at` moved, it tested its head's sync key and proof against the reader's filter, which shows only the proof of the reader's newest recorded step); the reader's credentials did not move, so it tests nothing at the source's next filter and never asks Behind. Only a later change of its own (the new step recorded through another reader) opens S there.
- Readings: the walk's (re-test every S not open whose peer J judges a sync holder, or that was open there by a store credential, at each filter arrival: O(such S) per arrival, cheap while they are open), or re-mark S for the record when a source's head event names a step the reader does not know (no head event comes while S is not open there, so this needs the filter). Pick one and state it in both spec files.
- `NodeHolds::verify_steps` and `step_creds` still answer nothing: Behind answers carrying steps are never verified, so a source on a later step than this node's recorded path is never walked. Build with the reading above; its rule test is a reader whose recorded path lags a source that is its only route (the sim `sims::a_reader_through_a_node_keeping_it_unread` with a rotation while the reader is away).
- Reproducer two nodes: `flows::a_sync_grant_accepted_later_is_kept_unread_with_the_writes_spec_sync_ids_6` (ignored): a sync grant the user accepts after a run (the everyday flow: an invitation accepted later) never gets S's genesis registered at the grantee, so it holds nothing; the same flow accepted at once passes. Likely the same class: the granter tested S there while the grantee did not sync S yet, and nothing tests it again once it does.
- `NodeHolds::behind` (a Behind answered with steps) has no passing test: only this scenario reaches it.

# A true part kept out by a copies flood is not fetched again by node-sync
> Summary: `apply::copies` keeps differing copies of a part or signature that cannot be checked yet, up to `MAX_COPIES_BYTES` a commit. Past that a later copy is refused, even the true one. The record's arrival frees the room and the engine takes the part when it comes again, but node-sync opens an entry once, so nothing delivers it again: on a thing the node syncs the commit waits for good. Redelivery would also make `copies.rs` needless: decide that first.
> Tags: security, sync, engine

Needs 16 MiB of junk under one signed header before the true part, with the thing's record away at the node: a reader of the label, or anyone able to deposit in an inbox once the commit pends (`admits` takes a pending commit ID). Better than before `copies.rs` (one junk copy did it), not gone. Test of the engine half: `parts::copies_flood_evicts_nothing_spec_commits_4`.

Cost of the copies as built: the row is rewritten whole per copy (about 0.1 s at a full row, debug, memory store), so about 250,000 signature-only copies, some 100 MB delivered, cost hours of CPU and terabytes written (spec/requirements.md: peer input causes no unbounded work; bounded, but far from what was delivered). The per-commit cap bounds nothing on disk overall: with an author unknown any header is a fresh pending commit (notes/growth.md), so the cap only bounds one row.

Design to weigh, in place of `copies.rs`: the node already holds every copy. Each entry that unwraps keeps its blob (`Kind::Commit { commit, parts, .. }`, `State::by_commit`, `BlobRec.key`), and `SyncEngine::genuine` already reopens entries and marks a junk one `Kind::Bad`; opening once is a state of `open_one`, not a limit on reading the blob again. So the pending blob keeps the first copy of each slot; when a slot or signature proves junk (`examine` drops it, or a signature fault removes the pending commit) the engine names the commit (`take_redeliver`), and node-sync ingests again the entries of that commit that are not `Kind::Bad`, inbox blobs included. No second store, no cap, no spec MUST about copies, and a flood cannot keep a part out however large, while the entries are there. Bounded: each entry is judged bad once. Costs: order independence under relay junk then holds at the node, not at `Engine::ingest`, so `parts_differential`'s junk moves up to a harness that redelivers; a true copy deleted from every host before the record comes is gone (no worse than today's refusal).

Not storing an uncheckable part at all (fetch when the record comes) needs an index of what each entry waits for and loses the boxes `read_pending_boxes` reads; keeping the first copy needs neither.

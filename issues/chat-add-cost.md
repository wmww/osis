# A chat's add costs each node O(members + messages)
> Summary: A joiner reads its newest page in about 11 ms per member plus 0.1 ms per message (100 members, 10^4 messages: 2 s); the rest of its fill goes on behind at 1.1 ms per message. An add at a node 10-27 ms, flat in messages, an admin's own call 170 ms at 500 members. Left: per-commit constants, an admin's pass per label, store 57 KB per member. Release measurements by hand; the counted siblings are osis-sim `scale::post_reads_nothing_per_member`, `add_judges_nothing_per_message`, `joiner_reads_each_pending_commit_few_times`.
> Priority: low
> Tags: engine, node-sync, performance

Gone: the per-pass secrets decode (`Core::secrets_read`, `held_for`, `head_keys`, `Work::beats_*`, `mark_dirty_of`); an add's full pass of the label and the engine's walk of the label's commits (roles move only upstream of the changed grant's holder: `work::RoleMoves`, `Core::stale_authors`, notes/node-sync-work-sets.md, notes/engine-validity.md Validity); `secrets.0` decoded whole per add (`keys::secrets_patch`); the liveness cache walked per role write (`Core::forget_live`); finding a general update's region read a component's things once per thing of it, T^2 per add (`region_reads_each_component_once`); departures read every edge write of the component per thing below the chat, M^2 per add (`Timeline::applied_on`, `applied_on_indexes_a_timeline_once`).

Left, largest first:

1. **A joiner: linear, by constants.** To its newest page it fetches every member's role commits (order 0, 16 KB per member, about 7 commits at 1.3 ms each) and lists every message (about 100 us each, 45% the stamp's signature, the rest three rows per entry; a batch verify would halve it). 500 members: 5 s without the members' cards. The rest of the fill, 6.6M instructions per message (callgrind): `open_commit` twice 2.2M (a body is opened again by the first pass's `genuine`, its delete-key commitments again 0.9M; a blob opened once could skip them), Ed25519 verifies 1.15M (a stamp, `examine`, `parts_genuine`), four header decodes 0.95M (`ingest` decodes what `open_one` decoded), store commits 0.76M. None grows with anything.
2. **An admin: O(labels it syncs) per role commit.** A role commit passes the labels of its thing's holders (`SyncEngine::downstream`: they carry a route to it); an admin that met each member has a label per contact, a pass and a `departures` walk each. Each judges almost nothing, the passes remain.
3. **Work waiting at labels no post passes.** A changed commit goes to every label's work set (`spread_touches`) though a post passes only labels holding it (`mark_dirty_of`): the label's next pass, at the latest its resync (60 s), judges them, about 7 us per message since then per node. Memory is bounded: past `SyncConfig::work_max` (2^14, about 512 KB) commits from elsewhere since its last pass, the set goes and that pass is full, O(what the label holds), so an idle label's cost does not grow with others' messages. What the pass left and the label's own touches do not count. The price: over about 270 commits/s sustained (a bulk catch-up), every label's 60 s resync is full, about 7 us per commit it holds, more than the set it replaces wherever a label holds over 2^14. Better: keep from a label's set the commits on nothing it holds.
4. **An add at a node: 10-27 ms; an admin's call 170 ms at 500.** At a node `apply: observe` and `apply: join` load about 3 pages of `secrets.0` each (`ingest_secrets_keys`: its first page, the boxes' pages; 13 per add at 500). At the admin a general timeline update 56 ms: an add joins the member's own component to the chat's, which `Timelines::append` declines (not `lone`), so it gathers and resumes O(M) per add. Absorbing a small component's commits through `Timeline::append` would make it O(the member's commits). A per-actor walk of departures is still O(M) per add, about 3 ms a time at 500 (each role commit drops the cache whole, `Core::role_changed`); `events` walks `Timeline::dropped` per actor, so it grows with kicks.
5. **Store: 57 KB per member at every node**, 176 KB at the host. At 40 members, per member: rows 38 KB, 8.9 blobs 19 KB. In the rows: the member's own first commit (account: `created.0`, `keys.0`, `label.0`, `roles.0`, `secrets.0`) 7.1 KB, its add 4.3 KB, a `keys.0` commit 1.6 KB, node card 1.0 KB; `keys.0` states 7.6 KB (3.2 things, 2.4 KB each: post-quantum public keys), `secrets.0` state 3.6 KB (three boxes and a history box), other states 1.3 KB; the rest (11 KB) indexes and sync entries. The blobs are the same commits again, under the label's key. No small fix: a node needs only the first commit's `created.0` and `keys.0` of a member, and the record and the blob are one commit twice, but dropping either is new machinery. `Engine::held_report` prints this.

Not measured: kicks at these sizes (issues/long-aspect-cost.md has them by messages), 1000 members all online (M nodes in one process do M^2 work per add; see the table's note).

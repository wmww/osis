# A chat's add costs each node O(members + messages)
> Summary: A joiner reads its newest page in about 11 ms per member plus 0.1 ms per message (100 members, 10^4 messages: 2 s); the rest of its fill goes on behind at 1.1 ms per message. An add at a node 10-27 ms, flat in messages, an admin's own call 170 ms at 500 members. Left: per-commit constants, store 57 KB per member. Release measurements by hand, taken on the sync before the rebuild: the fetch and listing figures need measuring again on osis-sync.
> Priority: low
> Tags: engine, performance

Left, largest first:

1. **A joiner: linear, by constants.** To its newest page it fetches every member's role commits (order 0, 16 KB per member, about 7 commits at 1.3 ms each) and lists every message (about 100 us each, 45% the stamp's signature, the rest three rows per entry; a batch verify would halve it). 500 members: 5 s without the members' cards. The rest of the fill, 6.6M instructions per message (callgrind): `open_commit` twice 2.2M (a body is opened again by the first pass's `genuine`, its delete-key commitments again 0.9M; a blob opened once could skip them), Ed25519 verifies 1.15M (a stamp, `examine`, `parts_genuine`), four header decodes 0.95M (`ingest` decodes what `open_one` decoded), store commits 0.76M. None grows with anything.
2. **An add at a node: 10-27 ms; an admin's call 170 ms at 500.** At a node `apply: observe` and `apply: join` load about 3 pages of `secrets.0` each (`ingest_secrets_keys`: its first page, the boxes' pages; 13 per add at 500). At the admin a general timeline update 56 ms: an add joins the member's own component to the chat's, which `Timelines::append` declines (not `lone`), so it gathers and resumes O(M) per add. Absorbing a small component's commits through `Timeline::append` would make it O(the member's commits). A per-actor walk of departures is still O(M) per add, about 3 ms a time at 500; `events` walks `Timeline::dropped` per actor, so it grows with kicks.
3. **Store: 57 KB per member at every node**, 176 KB at a node keeping the group unread. At 40 members, per member: rows 38 KB, 8.9 blobs 19 KB. In the rows: the member's own first commit (account: `created.0`, `keys.0`, `label.0`, `roles.0`, `secrets.0`) 7.1 KB, its add 4.3 KB, a `keys.0` commit 1.6 KB, node card 1.0 KB; `keys.0` states 7.6 KB (3.2 things, 2.4 KB each: post-quantum public keys), `secrets.0` state 3.6 KB (three boxes and a history box), other states 1.3 KB; the rest (11 KB) indexes and sync entries. The blobs are the same commits again, under the sync ID's key. No small fix: a node needs only the first commit's `created.0` and `keys.0` of a member, and the record and the blob are one commit twice, but dropping either is new machinery.

Not measured: kicks at these sizes (issues/long-aspect-cost.md has them by messages), 1000 members all online (M nodes in one process do M^2 work per add; see the table's note).

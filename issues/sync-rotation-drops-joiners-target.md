# A revocation taken before its thing lists drops the outsider's access for good
> Summary: when account A removes a node, its rotation revokes A's earlier epochs (spec/permissions.md §5.5 Revoked); another account's node taking that rotation before A's thing list for a thing T it reads (a Prove, a header-only copy under another sync ID) un-counts the role commits A wrote on T at those epochs (its grant on T, T's `keys.0`/`sync.0`), so S_T leaves its sync set and the leaving pass ends at once with S_T's holder gone (`leave::judge` reads `Lost`): the list that would name them is never fetched.
> Priority: critical
> Tags: engine, sync, tests, tess-call

- Seen, `#[ignore]`d naming this issue: osis-sync `flows::writers_of_two_accounts_keep_each_others_certificates_spec_sync_judgement_2` (at "account 0 rotated" node 1 drops S_t: trace `LEAVEDBG` showed the pass done in the same step, `holder None`), osis `sync::an_outsider_reads_the_accounts_writes_across_a_node_removal_spec_permissions_3`.
- A rotation revoking no one no longer un-counts anything (the same trigger with `rotate_account`: `driver::a_sibling_rotation_proves_again_spec_sync_opens_1`, engine `an_outsider_keeps_the_accounts_word_across_a_rotation_revoking_no_one_*`). With a removal the un-count is the rule: commits at a revoked epoch count only once named.
- Why the engine cannot wait for the list instead: an outsider cannot tell a thing list not arrived from one never written (list leaves sit at random indices, the tree hides their count). Waiting until a list for T arrives would count for good a removed node's backdated write on a thing T no honest commit of A sits on at that epoch (no list for T ever comes). Positive knowledge of which things have a list (e.g. the header committing to occupied indices derived from T) is a wire change with a metadata cost.
- Why sync does not recover (spec/sync-set.md §3 promises it: "what that pass brings may give S back, as a rotation's thing lists arriving after the rotation do"): the leaving pass reads S's thing, roster and holder from the engine, all derived from the commits just un-counted, so no peer is to be waited for (A's records are revoked too), the pass ends with no source, and `holder != held` stops S as `Lost`. It concludes from what it does not hold.
- Options: (a) sync's leave keeps S through a pass with a source when S left only because a revocation un-counted its role commits, holding S's credentials from the secrets still held; (b) an engine rule letting an outsider hold a revocation only with its lists for the things it reads (needs the existence knowledge above); (c) Tess: accept a stated limit (the outsider re-reads T only once A's nodes write on T again or it is re-granted).

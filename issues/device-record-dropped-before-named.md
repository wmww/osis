# A device's record dropped before the chain names it
> Summary: A node record learned before any held rotation names it is judged unneeded and dropped whole; a rotation naming it later does not fetch it again, so a node whose line keeps it can no longer sign (`signing_due`: "the holder has no secrets of its own"). Seen by the custody property since retention roots stopped rooting every key actor.
> Priority: normal
> Tags: engine, keys, retention

`rotation::tests_custody::engine_agrees_with_custody_model_large_spec_permissions_5_4` fails 4 of the end gate's seeds (708581931285, 708581931359, 708581931364, one more), all one way: `tN: B|C signing: misuse: the holder has no secrets of its own`. Replay: `OSIS_CUSTODY_START=708581931364 OSIS_CUSTODY_SEEDS=1 cargo test -p osis-engine --lib -- --ignored --exact rotation::tests_custody::engine_agrees_with_custody_model_large_spec_permissions_5_4`. Passes on 2a63da78d; fails from 54c2fda4e (roots 8 -> 4: `Root::KeyActor` gone).

What happens (seed 708581931364, at C): device m's record arrives while no held rotation names m (`AccountView::named_device` false), so `retention::needed::settle` drops it with nothing rooted needing it. A rotation adding m is taken later: m is now named (`Need::Holder` would keep it) but its record is gone, and nothing fetches it. C's signing epoch's line keeps m (`roster_joining(&[at])`), so `custody::seed_box` asks `flows::recipient` for m's KEM key and fails; the signing pass errors on every later try.

To decide: a chain naming a device whose record is not held is a need noted at the rotation's arrival (pend the rotation on `Wake::Record(m)`, or note m lost-needed so it is fetched again, as `holding::a_released_thing_reached_again_is_fetched_again` does for strongs); or a seed box for a device whose keys are unknown is left out (and re-sealed once known, `reseal_seeds`) rather than failing the pass. Check first whether the custody harness's delivery stands for sync here (a real node may never see the record before its naming).

# A vouch on one thing keeps its commit's parts on another
> Summary: Today's "W could write c" judges a vouch over c's parts on every thing, so holders of t split by whether they hold S; along stated paths (A1 step 3, `osis_perm::paths`) that split is gone by construction (a vouch's verdict reads its own path on its own thing, an entry's counting reads the first walk and c's header facts), and the engine wiring of step 3 closes it. What survives: a counting entry names c whole, so a vouch on t keeps c's parts on S, which the voucher holds no right on.
> Priority: normal
> Tags: perm, security

**Today** (engine `apply::tests_vouches::a_vouched_commits_parts_read_alike_across_a_restart_spec_perm_5_1`, varied): X's commit c rotates keys on t and on S; H removes X from t without listing c; W vouches c on t. A node holding S counts the vouch where W holds the role c's part on S needs; a node holding t but not S does not, and S's admin can make a node release S. Closed by step 3's wiring: the paths walk reads, for a vouch V, only whether V's stated path gives admin on V's own thing at its key; for an entry keyed by R listing c, R's application in the first walk (R's path edges: evidence), V's key against R's, and c's key, signer and role-class aspects on V's thing (all in c's header, in the clear); c resting on R's edge matters only through c's parts that rest on it, which a node judging them holds. No role on, or record of, another thing c writes is read, so every holder of t reads alike whatever else it holds.

**What survives** (draft §5.1 Vouches: "each counting entry's commit read as named by its removal's list"): the entry names c whole. The entry counts (c has a role-class part on T), so c's grant on S stands too, though B holds nothing on S and S's admins never vouched. The first counting condition's "W held every right the named commit's parts on that thing needed" (notes/account-membership-design.md §4, It counts) asks only about N's parts.

# A sibling of a self-removing node never drops
> Summary: When a node removes its own account from T, its sibling (another node of the account) applies the removal but keeps T's secrets and keeps T listed for good, even after an outside co-reader holds the removal (spec/permissions.md §3 Lost access: every node of the account drops once it is held elsewhere). The engine's own trigger is right; both syncs lack the sibling half.
> Priority: normal
> Tags: sync, engine, security
> Fixed on the sync rebuild branch (capstan-sync-rebuild, b487f5346: every node of the account waits on its account's self-removal; removal_done drops per lost actor). Delete this issue when that branch lands on main, which deletes the old node-sync too.

**Engine (main), right**: the trigger (`drop_lost_due`) leaves a loss with an own self-removal behind it to sync at every node of the account alike: `rotation::departures::own_leaving` counts a commit authored by the account (every commit a node makes is), wherever it was made, so the sibling's `lost_leaving` lists T with the removal, as the writer's does.

**Old node-sync (main), sibling never placed**: `drop_left` drops once `SyncEngine::placed`, which needs an outside co-reader's report (or a host's presence) of the removal on a stream where this node's log held it. The writer gets that report from the connection the co-reader pulled the removal on (Applied before the close). The sibling never does: once the co-reader applied the removal it judges the account departed and shares nothing with any node of it, so the sibling stays `leaving` with T's secrets. Probe (sim, not committed): `own_nodes_never_both_forget_before_an_outside_source_spec_permissions_3` with everyone reachable after the leave: Alice holds the removal, the phone stops leaving, the laptop is `leaving: true`, `NotConnected`, for good. That test asserts the laptop's half only while nobody has the removal.

**Rebuilt sync (capstan-sync-rebuild)**: worse, the sibling does not even wait. `flows::edges` calls `sync::held::wait(tx, c)` for a self-removal made here only, so `held_wait` (`waiting_removals`) never holds the sibling's copy; the trigger skips the loss there (own, as above), and `removal_done` never fires for it: the sibling keeps T's secrets and keeps reading T with no wait to end.

Fix, two halves:
- Engine signal (the rebuild's facade): `held_wait` is the set of own self-removals behind a held loss, derived as `lost_leaving` derives it (by account, in the apply's transaction, rebuilt at load), not written at the writing flow. Then one rule serves both nodes: a removal in it is done when held elsewhere, and the lost actors drop once no own removal behind them waits (per actor, as `drop_left` does, not "once the set is empty": an unplaceable removal must hold back nothing else).
- Sync, "held elsewhere" for a node the source no longer serves: a proven co-reader (a known account the node's timeline holds as a holder of S's actor) refusing the node S on a connection whose shared set settled is as strong as its Applied report: it refuses because it applied the departure. This is the timed loss's `co_readers_refusing` rule; using it for self-removals makes one hearing-out rule for both. A host's refusal still counts for nothing (a hostile host gives it for free). Test: a sibling holding the removal from the writer, then meeting an outside co-reader that already applied it, drops; one meeting only a host that refuses does not.

# A link leave splits a thing labeled with no required rules
> Summary: On main: a thing made with content and no `required.0^`, then `sync`ed and shared by a write link: after one joiner leaves, the other joiner and the maker stop exchanging writes for good (both say `Synced`, complete). Convergence and delivery loss in an order the API allows.
> Tags: node-sync, engine, keys, data-loss

**Repro** (libs/chat flows, `link_joiner_leaves_spec_perm_7`): make chat `create` write no `required.0^` (`create()`, one commit of the settings aspect, `sync`), and drop the test's leaver-copy assert (no required rule, so no retained copy). Maker A makes a write link, posts; B and D join; B leaves; D posts: A never holds D's post, and after five simulated hours and a post each, A holds only its own, D only its own plus A's pre-leave post. Both report `Synced`, `refused_by` empty, history `complete`. Fails the same on main (main's `create_ownerless` swapped for `create()` in the patch).

**Order matrix** (same test): `required.0^` in the content commit before `sync` passes (chat's order; also with `retain_copies` false, so the copy is not it). `required.0^` first set after `sync` fails (record alone by `sync` then the rules commit, or the record in a settings commit, `sync`, then the rules commit). No `required.0^` ever fails. A later `overwrite` of the rules or another settings commit after `sync` passes when the first commit had them.

**Seen**: after B's leave, D's node writes `keys.0`/`secrets.0` on C twice before its post (a writer's cascade re-key after K's rotation); in the passing order A writes a further `label.0` after the leave and D does not re-key. So likely D re-keys C (or C's label) into an epoch or label A never reads, and A never reads that it missed it. Not chased: start from the commits D writes after the leave and which label/epoch they go under (notes/permissions.md One inbox rule, `rotation::own_secrets`; notes/chat.md Realms, "any writer's next pass re-keys a child").

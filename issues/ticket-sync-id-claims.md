# One sync ID claimed by several things' tickets
> Summary: Things entered on a ticket's word sync their tickets' sync IDs (spec/sync-inbox.md §5 Ticket sync IDs); where tickets for different things name one sync ID, the lowest tid keeps it for good, and a thing kept unread is not judged by which thing its path ties the sync ID to (spec/sync.md §3 Tied).
> Priority: normal
> Tags: sync, engine, security

- **Several claimants**: `Engine::sync_set_now` gives a sync ID two ticket-entered things name to the first by tid (`or_insert`). A forged ticket for a thing the node accepted (a writer of something it holds can make it accept one, spec/sync-hostile.md) naming another accepted thing's sync ID, with a lower tid, keeps that thing from fetching its own until its `sync.0` arrives some other way. The spec wanted the claimants tried in turn, each retried after `resync_ms`; that needs the open's failure fed back from sync's opens to the engine's sync set.
- **Tied** (kept unread): S's things should be those S is kept for that a step on the node's path ties it to (a step bearing a held sync secret of the thing), else all; built is first by tid, ties unread. The unread module (`osis_sync::unread`) holds the path; the engine would take the tie from it as `closed_kept` takes a close (`CipherTx::closed`).
- **Tests**: T5's other forged cases (a ticket at a stale epoch, one for a target the issuer does not hold: each opens nothing, one try per `resync_ms`) are not written; osis-sync `tickets::a_forged_ticket_sync_id_pulls_in_and_cuts_off_nothing_spec_sync_hostile` covers another thing's sync ID beside the genuine ticket.

# Cheap reconnects
> Summary: Settled design, one mechanism with issues/net-shared-set.md: a durable per-peer record found by a pair key both nodes hold (no node identity), one node-wide durable log with opaque cursors, one Pull/Push stream per peer gated by the shared set; a member joins the stream through the same Pull, from a position or from the start. Principle: a record says only what need not be sent again, so a connection first proves the two records agree (a digest of S, first in each direction), then sends what changed; nothing is inferred from absence. A reconnect between nodes that proved a known actor costs what changed, however long a node was away; a peer that cannot read and proves no known actor pays a first contact on every connection, a stated limit (Peers that cannot read). Everything recorded is a cache: losing it is a first contact. A peer may recognise the same device reconnecting (Tess; spec/requirements.md). Model first. Part of issues/net-rework.md (Tess: important).
> Priority: normal
> Tags: sync, node, proto, spec

## The rule
issues/net-shared-set.md's: what is shared is judged on what a node holds now; a record says only what need not be sent again. So a reconnect is a first contact that skips what the record proves was already sent, and losing the record is a first contact.

## The record
A node keeps, per peer node it has shared something with or whose known actor it has met, a durable record **found by the pair key r**, never by a node key:
- `r`, 32 random bytes known only to the two nodes (issues/net-shared-set.md, The pair key);
- `actors`: the proven actors last seen;
- the peer's filter and its generation;
- `sent_gen`, `acked_gen`, and `acked_pos`: the node log position below which nothing is pending: the peer has acknowledged it, this node has tested it, and no Offer from that test is unanswered, or a member closing re-marked it pending for this record alone (issues/net-shared-set.md Testing);
- `judged_pos`: the node log position up to which S was re-judged;
- the set S: each open sync ID with what each side proved, an optional `until` (a position) while it is being ended, and its `lag` (a cursor) while a join of it is in pages;
- beside S, the `lag` of each sync ID a `Lost` stopped, kept for its rejoin: not a member of S, not in the digest;
- `cursor`: its opaque position in the peer's node log.

A session finds its record by r; r is honoured only for a session whose proven actors meet the record's `actors` (a revoked node cannot prove the account, so cannot use a record; a removal not yet heard by the verifier leaves it usable until it is, the fork window of Adversaries). Each use re-checks: step 5 re-judges a bound connection when a role changes, since binding happens once. Until step 10 only key actors proved by their own key count, and a record is checked again at each use against what this node knows now.

## Resume
After the identity exchange (issues/net-connect.md), with a peer that proved a known actor:
```
Resume   [id, nonce, [tag*]]       -> Resumed [id, nonce, Opt(tag)]
```
- The dialer sends a fresh nonce and `tag = BLAKE3(key = r, "resume" || listener key || dialer challenge || listener challenge)` of every record whose `actors` include a proven actor of this session, most recent first, as many as fit one message. The tag names the listener's static key, as the proof digest does, so a node between two holders of r, proving an actor both records name, cannot pass one's tag to the other. The listener compares each against its records with a matching actor and answers `BLAKE3(key = r, "resumed" || the same)` of the one it holds, or none, an answer the dialer can check. `r` = that value, else `kdf("pair key", dialer nonce, listener nonce)` and a new record on each side.
- r itself never crosses again: a list shows other nodes of that account only tags keyed by r values they do not hold, and the peer's lookup is O(its records of that account).
- Two connections to one peer: one record, one session (Built, One connection per pair: direct before relayed, then the order hash).
- A connection that proved no known actor gets no record and no Resume; `r` for the filter a node serving sync IDs unread sends on it (issues/net-shared-set.md, Peers that cannot read) is `kdf("pair key", dialer challenge, listener challenge)` of the connection, sent nowhere and kept nowhere.

## What a reconnect sends
After Resume, in this order, none of it per sync ID that is unchanged:
0. **Digest**: the first message each way (Agreement, below), then `Members` on a difference.
1. **Beacons**: `changed_at` (below) entries after `acked_pos`, as additions at `gen = sent_gen + 1`, `base = acked_gen`, one generation in flight per direction (the next waits for its Status, so `base` is what the peer holds; the sender remembers the log position each generation reached); on code 13 or a doubling (issues/net-shared-set.md), a whole filter.
2. **Testing**: the pending set (issues/net-shared-set.md Testing), on every arrival of the peer's filter.
3. **The shared set**: each side re-judges S members whose L has `changed_at > judged_pos` (issues/net-shared-set.md rule), advancing `judged_pos` only once its Offers are answered and its `Lost` sent. If the session's proven actors differ from the record's, it re-judges every held L (admissible credentials, S, ByRole) and sends a whole filter (rare, brute force). New opens go by Offer.
4. **Data**: one `Pull`, sent only once the peer's Digest has arrived. `Lost` for a member stopped while apart goes after the Pull arrives, its cursor = the Pull's own (the position this requester holds): the member is out of the reply, and nothing before that cursor is lost. A stop with a set `until` keeps its position, and its `Lost` goes only once the requester's reported position has passed `until` (Reported position, below).

An idle reconnect, unchanged credentials, roster and stream: identity exchange; `Resume`; a digest and empty `Beacons` both ways; one empty `PullReply`. Under 1 KB and a few round trips, whatever the number of sync IDs.

## Agreement
A connection's first message each way after `Resume` is `Digest [d]`, unanswered, `d` the xor over S's open members of `BLAKE3(key = r, sync_id)`, 32 bytes, computed from the record before anything else on the connection (Rejected, per-Pull digest). Only the sync IDs count: what each side proved differs between the two records and a stopped member's `lag` is not in S. A side compares the peer's `d` with the `d` it sent, not with S as it is by then. It is the only comparison of the two records and it runs once per connection: inside a connection S changes only by that connection's messages, in order, so the two copies differ only across a connection's end (a store restored or copied, a reply or `Lost` lost with its connection). A digest that matches ends it. On a difference each side sends its member list (`Members [[sync_id*], more]`, unanswered, paged, brute force and rare) in full as it reads the peer's `Digest`, before it acts on any later message, and for every member the peer's list lacks: closes it, no `lag`, and re-marks it pending for this record (issues/net-shared-set.md Testing), on both sides. So a dropped `Lost` needs no resending, a member only one side holds is out on both and found again by the shared set's own rule (a Hit, a ByRole, or nothing if the rule no longer holds), and rejoining is a listing, which is exact where the cursor would not be. Each direction's digest precedes that direction's every other message, its list precedes every Offer or Status it answers with, no Offer (Hit or ByRole) is sent before the peer's `Digest` is read, and no open happens before the peer's digest (on a difference, its last `Members` page) is read, so an open made on this connection never crosses a digest or a list. The digest repair runs once a connection and only ever closes members or re-marks them pending: it ends.

## Changes: `changed_at`
Each held sync ID has `changed_at`, a position of the node log, advanced on: a new sync ID, a new current credential, a role change on its thing or an actor reaching it. One index (changed_at, sync ID), one entry per sync ID: bounded by what the node holds, nothing to trim. A record's S names only held sync IDs: a node that stops holding L drops it from every record's S, and any `lag` kept for it, in that same transaction (index member to records), so re-judging never meets an unheld L. A connected peer gets an immediate `Lost`; a peer not connected finds it in the next digest. A diff recomputes the current beacons of each changed sync ID for this pair; duplicates are harmless (multiset, additions only).

## One node log, one cursor
- One durable log over every sync ID the node holds: events (entry added or stamped, deleted, timed deletion, new head), each with its sync ID, one sequence, one log ID for the store's life. This is spec/sync.md §4's log made node-wide.
- A **cursor** is an opaque AEAD seal of `(log ID, incarnation, sequence)` under a durable per-log key: a peer learns neither node-wide activity nor sequence gaps. A cursor that does not open, a position past the log's end, or one on no incarnation of this store's own history is **no cursor**.
- An **incarnation**: the first durable log append after a store start draws a new one (an ephemeral append draws nothing) and records the end position of the one before; a start that appends nothing costs nothing, and a cursor it issues names the incarnation still current. A store restored from a backup, or a copy running beside the original, needs no detection: its next append ends the old incarnation at the restored position, so a cursor from the lost store is past it and one from a sibling copy names an unknown incarnation. A cursor at a position the store's own history holds names what it covers.
- **Retention** (spec/sync.md §4 made node-wide, trimmed by compaction alone): the log keeps each held entry's latest add or stamp event (an entry's earlier events drop when a later one is logged) and deletion events for `TOMBSTONE_LIFETIME`; it is compacted, never trimmed by position. So it is bounded by what the node holds plus recent deletions (notes/growth.md), and a listing from its start is the node's live set of every sync ID.
```
Pull      [id, Opt(cursor), [join*], inline_limit, max_reply, follow, ephemeral] -> PullReply [id, [[sync_id, event]*], cursor, whole, more, report]
Push      [[[sync_id, event]*], cursor, report]
Applied   [cursor]                                                      (unanswered)
  join = [sync_id, Opt(cursor)]
```
- `Pull` returns, in log order, the events after `cursor` for the members of S with no `lag`, and for each `join` (a member entering the stream: newly open, or rejoining from its `lag`) that member's events after its own cursor, from the start when it has none. With no `cursor`, or one that is no cursor (the stream's or a join's), the reply is the stream from the start for all of S, `whole` set: a join read from the start the requester did not ask for would be a listing it does not know as one. A reply from the start for a member (a `join` without a cursor, or `whole`) is a **listing**: the log's events for it from the start, so what is present plus the deletions the log still holds, and it never treats an absent entry as deleted: a node's entries are not all at any peer (a write of its own that has not reached this peer, anything this peer never received or lost in a restore). One form for a first contact, a reconnect, and a sync ID that joins or rejoins; no message per sync ID in any of them. Which to scan, the log after a position or a member's entries, is the implementor's per request (Unsure). With `follow`, the peer then pushes the same stream live (Push, carrying this cursor).
- Both sides pull. Readers do not upload to readers; own writes reach readers by the stream. Uploads stay at peers that cannot read (stamped entries they lack, spec/sync.md §5).
- **Bodies** (spec/requirements.md, "Nothing a node already holds is sent again"): `inline_limit` is the requester's. A requester with more than one source open on any sync ID of the stream sets it to 0: events carry IDs only (an announcement of about the fixed overhead per connected peer), and it fetches what it lacks, one source at a time per blob ID, the next only when that source fails. A requester with one source sets it to its inline preference, and Pulls again when that changes (a member gaining a second source). So in a mesh of m peers a body crosses once; the announcement crosses m-1 times.
- **Ephemeral**: entries are memory-only, in the log's memory part: ordered with the durable events by one in-memory counter, carrying no position a peer can hold. A reply or Push's cursor is always the last durable event at or before its end, so a cursor names only durable events and "past the log's end" reads the durable end, restart or not. Since no cursor names a memory event, the memory part's position is the connection's own: `ephemeral` true on a connection's first Pull lists the serving node's live ephemeral entries for S, every join lists its member's, and later memory events follow in counter order on that connection, paged by the reply budget like the durable part. O(live ephemeral); replaces the per-sync-ID `gained` listing and first-pass reconciliation. A server restart empties the memory part. An ephemeral log lost at the requester's restart gives live entries as spec/sync.md §5.

## Joining and rejoining
- **Joining** S (a sync ID newly open): the server adds L to the stream, and the requester's next `Pull` names it in `join` with no cursor: its listing arrives in the stream's order with everything after. Events the listing also shows are deduped by blob ID. Gap-free by order. A join in pages keeps its own position (its `lag`) until the last page; only then is it in the stream. A join of a member the server does not share is answered, never treated as an empty success. Opens from one Offer batch join in one Pull: a first contact sharing 10^4 sync IDs is one Pull with 10^4 joins and one paged reply.
- **Lost and rejoin**: `Lost [L, c]`: the cursor where L stopped for this receiver: the server's `until` position, or for an immediate `Lost` the end of what this connection's stream has delivered (the last cursor returned), `Lost` written in order after it. The receiver stores `lag = c`, or keeps an older one. When L rejoins: `join = [L, lag]` in the next Pull, L's events after that position. Cost: the events L missed, no listing. The server's `until` for a member ends the stream at the rotation event inclusive (issues/net-shared-set.md, Opens).
- **Reported position**: what the server knows of the requester's position, for ending a member: a `Pull`'s cursor, or `Applied [cursor]`. `Lost` for a member with an `until` waits for it to pass `until`; a position kept for this connection only. The server sets `until` in the transaction that logs the rotation, so no Push of the event precedes it. Every `PullReply` or `Push` carrying events has `report` set, the same reports status reads (Built, Pass ends and status: one proof that the reader applied what it was served); the requester, having applied it and stored the cursor, sends `Applied [cursor]`. A report lost with its connection needs no repair of its own: the next connection's `Pull` carries the requester's cursor, past the event if it applied it, and otherwise the event comes again with `report` set. A rotation adds no `Applied` beyond those reports.
- **Back after a long absence**: a cursor is honoured however old it is. The log holds each live entry's latest event and deletions for `TOMBSTONE_LIFETIME`, so the diff from the cursor carries everything a listing could, and a deletion older than the log is not carried by either; retention judges a stale entry the node still holds (a covering snapshot, expiry, purge; `Deletions`, below). Only a peer with a different store (restored, copied, rebuilt, another log ID) gives the whole stream from the start.

## Restart and loss
- Log, records and cursors are durable: a restart resumes. A store restored from a backup is detected by nothing and needs nothing detected (One node log, one cursor): every peer's next cursor past the restore point is no cursor, and it gets a stream from the start.
- A cursor is stored only with what it covers applied, and names only durable events (Ephemeral, above): it never runs ahead of the data it names.
- Lost record on one side: the Resume list finds nothing, new r, whole filters, S rediscovered, one listing. On the other side the orphan record is unused, evicted by LRU.
- Partial loss: atomic per record, so either whole or none.

## Deletions
A deletion reaches a node as a log event, within the log's retention of it. No event carries it after that and none is needed: a stale entry is only bytes, retention's covering snapshot, expiry or purge removes it, and a listing or diff naming a covered entry leaves it for that judgment. A listing never deletes.

A deletion event in a reader's stream is never acted on by a co-reader: only a right holder's drop counts (retention's principle). It tells the requester only that this source no longer has the entry.

## Peers that cannot read
A reader's connection to a peer that cannot read L is one-sided: the reader tests (a Hit on the sync key, issues/net-shared-set.md), the peer tests nothing and never pulls. Where either side proved no known actor the two hold no record (Resume).
- **Reading and known**: the reader pulls the peer's log like any stream, keeping in its record `known`, the entries a Pull has shown at the peer, one row per entry, counted in `RECORD_BUDGET`. A from-the-start reply replaces it. With no record (Limit, below) `known` lasts the connection.
- **Uploads**: a reader uploads each entry it must place there that `known` lacks (spec/sync.md §5), once a connection. An upload's ack adds nothing to `known`: only a Pull does, because a store restored from a backup has lost what it acked. Uploads and deletes wait for the connection's first Pull, through its last page.
- **Deletes**: retention's rule, nothing new: a reader holding a delete key sends the ordinary signed Delete (spec/sync.md §5, §7) for every entry `known` lists that it covers (a held snapshot covers it, spec/commits.md §5), once `known` shows the covering snapshot (the carrier stays at the peer). The peer judges nothing and infers nothing; it removes the entry and logs the deletion, which other readers receive by the same Pull. Because the rule reads `known`, a peer that was away, a restored peer and a reader back from a lost record are all served by the same pass, with no tombstone channel and no memory of past deletes. A reader without a delete key sends none: an entry stays until a right holder connects or it expires at the peer (spec/sync.md §5 Expiry). Whether only own boxes or also others' run this way is issues/net-one-peer.md's consent.
- **Limit: a peer with no known actor.** No record means no `r`, no cursor and no `known` across connections, so each connection to it costs a whole filter each way, one Hit with an open signature per shared sync ID, and a listing of every entry of those sync IDs. It is left: the end state is two accounts that know each other (issues/net-rework.md), and a box given an actor its owner's account knows has a record like any peer (issues/net-one-peer.md). Keying a record by the box's listening key would make a second way to find a record for a case outside that end state.

## Adversaries
- **A known actor flooding records**: each connection with no matching tag makes a record, and nothing caps records per actor: enough connections fill `RECORD_BUDGET` (evicting honest records, each then a first contact) and make its own lookups cost O(records of that actor). Accepted while only a known actor can do it; a cap per actor, the actor's own LRU going, ends it if it matters.
- **A peer flooding `Resume`, `Beacons`, `Pull`, `Members`**: the list is one message; lookup per entry. A `Members` list keeps only sync IDs in S or held here, so it is bounded by what the node holds. Filter pages linear (issues/net-shared-set.md). `Pull` bounded by `max_reply` and the flow control of spec/sync.md §6.
- **Restart losing the record**: first contact; no incorrect state, no leak beyond a first contact. A peer holding a stale copy of a whole-filter `gen` or `cursor` gets a base-unknown or no-cursor: it cannot influence opens, whose judgment is local.
- **Clock-skewed peer**: nothing in this design reads a clock. Filters, generations and cursors are sequences; judgment reads roles with `until` disregarded (spec/crypto.md §4). A skewed clock affects only the node's own writes (issues/clock-peer-offset.md).
- **Revoked node of a known actor**: Resume needs the session to prove an actor in the record's `actors`; it cannot at a closed epoch where the removal is held (issues/account-signing.md). Fork window: account signing's limit. Its r is then just a random value.

## Costs
With N held sync IDs, P peers, C changes since the last connection:
- **Per reconnect, with a record**: O(C) beacon bytes and hashes; O(events since the cursor) data, or O(live entries of S) listed for a peer with a different store; no per-sync-ID message in either; local re-judging O(C) (O(S) only when the proven actors changed).
- **Per peer stored**: about 1.2 B per peer credential (filter) plus 50-100 B per S member; for a peer that cannot read, also a row of `known` per entry it shows.
- **Idle reconnect, with a record**: under 1 KB, a few round trips, whatever N.
- **A peer that cannot read and proves no known actor**: a first contact and a listing of S per connection (Peers that cannot read, Limit).

## Hard cases
- A rotation while apart: the server's `until` stops L at the rotation (issues/net-shared-set.md, Opens); a holder rejoins by an added beacon.
- A record on one side only: base unknown, whole filters both ways.
- Subscriptions and push: `follow` is the one subscription; per-label Subscribe and Open are gone between readers.

## Replaces
`Feed` and per-start log IDs; per-(peer, label) cursors, per-label Open, Subscribe and Sync between readers (spec/sync.md §6 First sync and Cursor sync, spec/wire.md §11.2 Sync; the listing is a `join`); the per-connection caps on open labels (4096) and `MAX_SUBS` between readers (spec/wire.md §11.2); Error 15 and the trim position. Per-label logs at hosts become this log (issues/net-one-peer.md).

## Rejected
- **Reconciling per-sync-ID digests**: two readers in sync legitimately differ in entry sets (keep bounds, dropped and covered bodies): idle sync IDs would differ. The log is exact.
- **Per-sync-ID cursors reconciled over (sync ID, position) pairs**: works, but two structures.
- **A per-member first sync (`Sync(L, no cursor)`) for a join**: one round trip per sync ID, 10^4 of them for a phone back after a month or a first contact sharing 10^4, the cost this design exists to remove; the stream from the start lists the same entries in one paged reply.
- **A log trimmed by position with Error 15**: the log's retention already keeps every live entry's event, so "retained events plus trimmed below T" and "the stream from the start" are one reply; a trim position is one more value to keep and send.
- **A digest per Pull**: a digest crossing a reply in flight reads a just-opened member as a difference and the repair re-fires. At a connection's start nothing is in flight.
- **Resending `Lost` across connections**: the digest finds it, with no record state for ending members.
- **A horizon below which a cursor is refused**: a listing would teach no deletion the diff from the cursor does not; it spends a listing for nothing.
- **Keying a record by a node key or dialable key**: a connection proves accounts (issues/account-signing.md), and a LAN listener has a fresh key per join; keying by r needs neither. **Tickets minted by one side**: same lookup, but one side must trust the other's minting; a pair value is symmetric.
- **Running first contact on every connection**: one entry per sync ID each time.
- **Storing a table of the peer's beacons, or own beacons per peer**: each side tests only its additions.

## Picked values
- **`INCARNATIONS_KEPT`** 4096 (resource bound): the list of incarnations a store keeps, oldest evicted. 0 makes every cursor from before a start with an append no cursor (correct, a listing per peer), infinity is disk growing with appending restarts. Each entry is 24 bytes (ID and end position), one per start that appends: a start that does not append adds none; at 50 appending starts a day the list reaches its cap at about 82 days and 98 KB, and a peer absent longer than that is given one listing.
- **`RECORD_BUDGET`** 256 MiB total per node of durable records, resource bound: 0 is every connection a first contact (correct, more bytes), infinity is disk. Past it, evict the least recently used record not in use. A filter that would not fit is tested as it arrives and not stored: that peer is a first contact next time; no connection closes for it.

## Model
core/test/tla/net (TLC), both halves of this design with issues/net-shared-set.md; its README lists scenarios and state counts. Over restarts, record loss, deletion expiry, restored and copied stores, drops, role changes on one side and one-way dialing, each checked over all interleavings at small size:
- No node drops a write nobody deleted; a source judged caught up holds nothing this node lacks; nothing is served after the right is lost; a reconnect sends what changed; the connection settles; S is exactly the rule on what each side holds.
- Rules the design relies on, each failing the properties when removed: pending set; `acked_pos` only past what is acknowledged and tested; arrival test before later messages; the tag; ByRole; a declining tester's `Lost`; the rotation's `until`; the digest; `Lost` and digest re-marking pending; Lost's older lag; a join's own position; a join answered; the cursor applied before stored; a change announced during a Pull denying that Pull's caught-up; the server's S read per reply; both sides pull; a listing carrying retained deletions; `Applied` after a `report`, a Pull's cursor repairing a lost one; no Offer before the peer's digest; tested reset with `acked_pos` when pending again; at a peer that cannot read, `known` only from Pulls, replaced by a from-the-start reply, deletes from `known`, the carrier shown first.
- Not modelled: more than one peer, key actors and covers, deposits, account proofs, filter pages and false positives, inline bodies, ephemeral entries, record eviction, the generation base check's bug (a single credential makes additions equal the whole filter; the argument is ASSUMPTIONS.md's), a peer that cannot read with no record, two live copies each redialing.

## Built
The node log is in `core/store/src/nodelog.rs` (notes/local-store.md, Node log), written from `State::flush` of node sync: events for entries becoming servable or re-wrapped or stamped, entries removed (every path through `State::drop_entry`: delete, expiry, junk, compaction's drop) and served heads (derived from group data, logged at the next `served_labels` after a move); ephemeral entries and a label forgotten log nothing.

The stream is built (`core/node/src/sync/stream.rs`, notes/peers.md The stream; bytes spec/wire.md §11.2 Pull to Applied, kinds 41-44; spec/sync.md §10 Stream): `Pull`/`PullReply`/`Stream`/`Applied` over the node log, filtered by S, joins from a record lag or the start, `follow`, the memory part (`MemLog`) with the first Pull of a connection and every join listing the live ephemeral entries, paged with the durable part. Both sides pull, whoever dialed: between readers a connection's node state is its shared set and its stream, keyed by `ConnId` on either side (a reader source, not one connection record: peer connections carry no `LConn`, so no pass, Open, upload, delete, registration or presence runs on them; hosts keep `Conn`). It replaces the per-label in-memory log and Sync, Subscribe, Reconcile, Opens and uploads between readers.
- **Membership**: `shared_open` joins the stream, `shared_close` leaves it, both sides; the side answering an Offer sends its answer before opening, so a requester's join always reaches a server that opened L. The record holds the stream's cursor and S (each member's class, beacon and place: at the cursor, or joining from its own position), written at the open and moved as positions settle.
- **Applying** (`Src::Reader` in `log_events_from`): stamps count only under the head this node serves; a `Deleted` does nothing (only a right holder's drop counts); a Head nothing (heads come by `label.0`); bytes new here of entries unstamped there and unopened are charged to the peer budgets, past them not kept.
- **Own writes**: a node's writes reach its readers only through its own log, so every label gets a local pass placing them in its own store while a reader can pull it (`serves_readers`: `reach.0` published, or a connection sharing a sync ID), whatever hosts are connected; a host pass uploads what its host lacks. A label with no host also gets the host's part locally (notes/peers.md Local passes).
- **Bodies**: `inline_limit` 0 while a member has another source, a gained source re-pulling with 0 (a mesh body crosses once); every body announced without bytes is fetched by `Fetch` with a node-range id (any message with such an id goes to the node), one source at a time, a failure asked of the next reader sharing L.
- **Relay-only entries** go to each reader sharing L as a Stream with no cursor.
- **Opens**: an accepted static-entry Hit's answer carries the head's entry box and the label's path from genesis (`EntryGrant`), from any reader holding the head's claim set (a joiner grants as the sharer does); the redeemer verifies the path and that the box's secret derives the head's sync key, as an Open's box, before opening.
- **Pass ends and status**: a member read to its stream's end, or a push applied to a stream read to its end, is a pass end at the source's dialable key (dialed, or the proven node's by `reach.0`); a reader is a source while L is in S, caught up once this node applied its stream to the end and the reader reported (Applied) every message of L this node served it to its log's end, counted once per proven node. A session sharing a sync ID is exempt from the served idle bound (its followed stream is silent while nothing changes).
- **One connection per pair**: two connections bound to one record close down to one, whoever dialed: a direct one before a relayed one (both ends read it from the transport), then the smaller `connection_order`; a dialer whose connection lost to one its peer dialed does not dial it while that session lasts (`stand_in`).
- PullReply carries one more field than the design's line: the joins not at its cursor (in pages, with their position; not shared, with none), since a join in pages needs its own position back. A reply scans the log once from the lowest start (cost: the log after that position; a join from the start reads the whole log, `SCAN_ROWS` rows a reply).

An Error whose id is in the node's range (`NODE_IDS`, top bit) answers that node request in both sessions: a Pull answered Error is no longer in flight and goes again after `resync_ms` (`stream_refused`, `stream_retry`); a Fetch answered Error is a fetch answered with nothing. A host, and a node with no shared set on the connection, answer the shared set's and the stream's requests Error 14.

`changed_at` is built (`Transaction::changed_note/changed_at/changed_after/changed_forget`, rows in `core/store/src/nodelog.rs`, written by `SyncEngine::stamp_changes` in `credentials.rs`): a per-sync-ID fingerprint of its credentials and who reaches it through the rosters held, recomputed when a role, roster or read secret moved (`Core::role_generation`), the set of held sync IDs changed, a hint moved, or at a start; a changed fingerprint takes the next log position. Nothing reads it yet: Offers and beacons do at step 5.

Records and r are built (`core/store/src/record.rs`, `core/node/src/sync/records.rs`; bytes spec/wire.md §11.2 Resume, spec/sync.md §10 Pair key): a dialer that met a known actor lists tags, the listener answers or both make a record from the nonces, the record used durably before the answer. What proves a record: the session's own key actors known here now (`counted_actors`), so a chain-proved account finds none; step 10 changes only that set, and the account's other nodes then list tags they cannot match. `acked_pos`, S with `until` and its place, the stopped lags, the own filter (`sent_gen`, `acked_gen`, whole entries and additions) and the peer's filter (one row per generation since its last whole one), `ConnRecord` (ack, `tested_pos`) and the re-marking rule are in the store API. Not filled: `judged_pos` (a reconnect re-judges every member, O(S) local work, no messages), `until` (step 7b), `known` (step 9). The listener's answer is `"resumed"`, not the dialer's tag echoed, since an echo proves nothing.

**Reconnect** (step 7a; notes/peers.md The stream, Reconnect; spec/sync.md §10 Agreement): a connection taking a record restores S, `acked_pos`, the own filter's generations and the peer's stored filter, sends `Digest` first, re-judges every member (a `Lost` carries the last cursor served on the connection, and the receiver keeps it as the lag only with nothing of its stream unsettled and no push dropped, else none), then sends additions past `acked_pos` with `base` the last acknowledged generation (whole when none was, when the last one sent was not, or when the session proves other actors, which also makes everything pending). Offers wait for the peer's digest, Pulls for agreement; a difference lists S and closes what one side alone holds with no lag, re-marked on both. An idle reconnect is about 1.5 KB and no message per sync ID (`reconnect::` tests).

Two connections to one peer are one record and one connection (Built, One connection per pair). Two crossing dials before any record exists make two records, one per connection; the unused one goes by LRU.

The log reader must, in order: run `served_labels` and `State::flush` first (a moved head enters the log only at that compare; before it the head is stale, not lost), read in its own transaction (a read in the writing transaction could hand out a position the transaction then aborts), and filter by S (`log_read` returns every sync ID's events).

An `Added` is logged when an entry becomes servable here, row and bytes both held, in the transaction that completes the pair (`State::flush_storing`, notes/local-store.md Node log): an announcement without bytes has no event, and its bytes arriving, commit blob or chunk, log it. A blob stored outside node sync (a pairing package's, `core/osis/src/account.rs`) precedes any entry naming it, so the entry's row logs it. A cursor is set after its batch's commits are opened, so the `flush_storing` of that batch carries no cursor it covers. Bytes dropped with the row kept (`drop_blob`: the entry stays with its wrap shredded) leave the entry's `Added` in the log: the reader filters by bytes held. `Deleted` is logged for any row, one never servable included: a peer ignores it and a conditional would need state.

## Tests (default tests, over issues/net-tests.md)
An idle reconnect sends no per-sync-ID message (counted); the digest of two equal records matches at any size (counted: 32 bytes each way); a store restored so that S differs finds the difference, closes members only one side holds and reopens by the shared set, and a stopped member's `lag` does not make the digests differ; a followed member gets `Lost` after its rotation (its `Applied` is the only message that ends the wait); a rotation adds no `Applied` beyond the per-message reports (counted); a `Lost` costs other peers nothing (counted: no additions sent and no test run for any other record); a restarted node resumes; a lost record is a first contact and converges; a rotation while apart rejoins from its lag and refetches only the missed events (counted); a node back after the peer compacted deletions past its cursor converges with the messages of one stream (counted at n and 10n sync IDs: no term in n beyond pages); a first contact sharing n sync IDs joins them in O(1) Pulls (counted); a mesh body crosses once with announcements per peer (counted); a skewed clock changes nothing.

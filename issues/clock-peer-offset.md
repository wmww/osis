# A peer can pull a node's clock
> Summary: A node sets its clock correction to the median offset of its dialed connections, hosts and peers alike, unbounded, so one peer can move it any distance. A node pulled back parks every honest writer's commits, misjudges expiry, and fails its own commits signed by a key actor it holds (`redeem`, audit row 35). Against spec/requirements.md "a wrong local clock harms only that node's own writes". Proposed: no correction from other nodes, a skew diagnostic instead, and own commits never drift-judged.
> Priority: normal
> Tags: node, engine, spec, security

## Today
- Per dialed connection, osis-proto's `ClientSession` estimates the peer's offset from Ping/Pong once `MIN_PONGS` (3) of the last `MAX_SAMPLES` (9) are in (core/proto/src/client.rs; hello.rs `estimate_offset`: median, round trips over `MAX_SAMPLE_RTT_MS` dropped) and reports `ClockOffset`.
- core/node/src/sync/conn.rs (`E::ClockOffset`): the node sets `Engine::set_clock_offset` to the upper median of every open `Conn`'s last offset. No bound; one sample set per `Conn`, so a peer with two connections (a LAN probe beside a relayed one) counts twice; with one connection that peer alone sets it. Recomputed only on a new estimate: the offset stays when that connection drops. Not stored: a restart starts at 0. Served sessions give no estimate.
- The corrected clock (`Hlc::wall`, core/engine/src/engine/clock.rs) is the engine's `now` everywhere: stamps (`max(corrected, last ts)`), parking of received commits more than `MAX_DRIFT` (60 min) ahead, expiry, `until`, retention bounds, LAN windows.
- core/engine/src/apply/mod.rs (`examine`): the drift check skips commits whose author is the node (`h.author != tx.core.id.tid()`), not commits by other key actors it holds. `redeem` signs with the link key L (core/engine/src/flows/links.rs), so pulled back 120 min, the redeemer's HLC (still at real time) stamps the join 120 min ahead of its corrected clock: `Misuse("own commit not applicable: ts drift")` (p10: -120 min fails `own commit not applicable`; +120, ±30, -5 fine; the cause read from the code, not traced).
- So a wrong clock on Alice harms Bob: Bob parks Carol's honest commits, judges grants and links expired late, and cannot redeem. Bob's own stamps are unharmed (the HLC never goes back), which is also why the correction barely helps a fast node: its stamps stay at its last `ts` until real time passes it.

## Fix
- **Own commits are never drift-judged**: skip the check for every commit this node makes (`Origin::Local`), whoever signs. Needed under any option below. (implementor)
- **No correction from other nodes** (proposed). Every node uses its local wall clock for everything. Then a wrong clock harms only its holder: fast, its writes are parked elsewhere until real time catches up; slow, it parks others' writes and its writes sort early (HLC receipt pulls its stamps forward, spec/crdt.md §2.2). Nothing another node sends can move it, so no source counts more than another and no number is picked. The offset estimate stays as a diagnostic (`OFFSET_DIAGNOSTIC_MS`, 5 s, notes/sync.md) and in status, so the user fixes the device clock.
- Rejected: **a bounded or agreed correction** (cap the offset, need several sources, weigh own nodes over strangers). Each needs picked numbers and special cases (one connection, all connections from one peer, a dishonest majority, an own node with a dead clock battery), and any correction still lets other nodes move this one.
- LAN tag windows (row 34) are owned by issues/net-connect.md, LAN rules: tolerance as wide as `MAX_DRIFT`, past which the two nodes park each other's writes anyway. With no correction, a connection no longer changes the clock, so nothing there waits on one.
- Spec and notes to change: spec/sync.md §6 Handshake and clock (the SHOULD to estimate and use a corrected clock becomes: estimate for diagnostics only) and every "corrected clock" in spec/sync.md, spec/crdt.md §2.2, spec/commits.md; notes/crdt.md (Drift cap: why the corrected clock exists), notes/api.md `now()`, notes/engine.md `set_clock_offset`.
- Tests: own commit by a held key actor applies after any offset (today's p10 as `repro_`, issues/net-tests.md); a node connected to one peer 120 min off still takes a third node's writes and redeems; per-node clocks in the sim (`ClockSpec` in `NetSim`, to add in `World`).

Unsure:
- (design) Before choosing, trace why the correction exists (git log -S on `set_clock_offset`, the notes it came with) and what breaks without it; then decide between no correction (a device whose clock is far off reads and writes badly until its user fixes it) and a bounded correction (which the requirement forbids as written).
- (design) What status shows for a large skew (a field, a diagnostic only), through notes/api-design.md.

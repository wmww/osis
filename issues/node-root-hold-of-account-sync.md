# A node-root strong to a thing its account may sync holds only its stub
> Summary: A node holding T from its node root (`osis hold T`) while its account holds sync on T keeps T as a stub, not unread: it answers Head for T's sync ID with Error 13, so a shared node that accepted `chat relay` this way carries neither the chat nor its link's K, and no one joins or syncs through it. Held from the account instead, it works.
> Priority: critical
> Tags: engine, sync

Ignored on it: osis-sync `links::a_link_is_redeemed_at_a_node_keeping_t_and_k_unread_spec_permissions_7`. Node 1's account is granted sync on K (told), node 1 holds K from its node root; node 2, reaching node 1 only, cannot redeem. At node 1 `sync_set` holds K's sync ID as `Stub` and `why_role` says "role None ... held sync[3]; kept unread: sync secrets a step bears [3], held [3]; node closure: contexts {Stub(K)}". With the strong from node 1's account instead (`m.op(account, HOLDS, ..)`) the test passes.

spec/sync-set.md §2: the node's role is its own things' effective role through the holders on the way (node thing → account → sync on K), so the walk should enter K kept unread from the local part. In the engine the local part enters an independent thing by `given_by`'s `grant_carries`, whose owners from the local part are the node thing and `own_on` (own things: the node thing and link keys), with `role_on`'s Local branch gated on `local_log::counts`; the account's sync grant reaches none of them. A read grant to the account held from the node root works (seen: `osis hold` of a chat the account was added to), so the gap is the sync (kept unread) arm.

Seen in the dogfood smoke pass: host H accepted `chat relay` with `osis hold CHAT K` (tools/dogfood-member.sh `accept` does the same); it pulled both sync IDs once, then answered every joiner's Head for K's sync ID, and peers' for the chat's, with Error 13, and asked each new peer for their heads again. `chat join` through H failed ("could not confirm this link yet").

# A delete over an undelete recomputes the aspect's deaths
> Summary: since crdt-leftovers, every text delete landing on an undeleted element (redo of a delete, re-deleting restored text) marks a bounded aspect for a full deaths replay at its author and at every holder; O(held bodies) per such commit. An exact cheaper rule needs to know whether the creation already died, which the state does not show.
> Tags: engine, crdt, retention

- Why: a creation dies once, at its earliest delete (spec/crdt.md §4.8). Over an undelete the creation may have died at a delete the state no longer shows, so `merge_elem` reports the death and `Changes::undatable`; `replay_all` keeps each element death's earliest.
- Measured (dev, `tools/icount`, a kept text of 150 insert bodies, then 40 cycles of delete, undo, redo by one writer, each package delivered alone to a fresh node): author's play 2.47G instructions on main, 6.31G on the branch; the fresh node's deliveries 1.63G vs 5.40G (3.3x). Grows with the aspect's history: each redo replays every body. A node-sync step settles once per step, so a batch of redos costs one replay at a receiver; the author pays one per redo.
- Since seed-7731022 the replay also keeps every joined text delete per element (`seq::TextDeletes`, so a snapshot's late copy of a creation dies at the earliest): one map entry per deleted char per body, runs expanded (the join is per record). Measured the same way plus snapshots, 150 inserts of 100 chars, 40 cycles of a 300-char delete, undo, redo: +3.6% instructions over main (108.5G vs 104.8G) without snapshots, +4.6% (320.5G vs 306.2G) with a snapshot every 50 inserts and 10 cycles; with 1-char edits +0.3%/+0.7%. Cheaper if needed: collect only before the last held snapshot, or store per-run ranges.
- Only bounded aspects (`any_bounded`); hostile recompute forcing already exists on main (a snapshot copying held text creations is undated too).
- Cheaper exact candidate (not built): the undelete's commit `undoes` a held valid commit d0 whose body flags the element deleted with `ts` above the creation's: then the creation was dated at d0 or earlier here (or a recompute ran), so the re-delete reports nothing; else recompute. Needs the undelete's stamp in the death and one body read; a forged `undoes` must not skip (check d0's flag).
- Related inexactness: `state::cross_deaths` joins a keyed record's fragment with the dot's key-erased record and reports the element deaths of text elements only the erased record holds at its current flag each time; after a re-delete there that is later than their first death, so live `last` can exceed a replay's.

# First contact and delivery without a server
> Summary: Links, contact cards and grants assume a saved peer (audit rows 5, 6, 8, 9, 12, 21, 37). Design: once connected (issues/net-connect.md), a link's holder finds K's sync ID like any other (issues/net-shared-set.md: the link key's static entry is its credential at every node serving K, reader or not, sharer online or not), and a grant is an offer to a connected node that proved a holder of the recipient's inbox, or a deposit at one serving it unread. No `direct` links; a card is a plain link; undelivered grants show as pending. Part of issues/net-rework.md.
> Priority: normal
> Tags: sync, api, node

## Today
- Link text: L's seed, target, K, K's label ID and hosts, and with `direct` the sharer node's dialable key and relays (spec/wire.md §10). A redeemer reaches K's label only at a listed host or by dialing that key. On a LAN it cannot: a `peer://` key with no relay gives nothing to dial, and LAN tags match co-readers only (row 6). Not direct with no saved peer: `Invalid` (row 5).
- A contact card is a link that is never direct, so it is `Invalid` with no saved peer: no `import_contact`, no names, chat's `link` and `add` fail (rows 8, 12).
- A grant to an account whose inbox lists no host goes as a Deposit item to a connected node proved a holder of the inbox, and stays pending, shown, until one takes it (row 9; notes/inbox.md Deposit items). An inbox listing hosts still goes to them.
- Redeem by bundle alone times out (row 21). The format already carries claim sets with their entry boxes (spec/wire.md §8, §12), so the cause is elsewhere; not traced.
- With no host only the node that wrote the seed thing finalizes an ended link (row 37; spec/permissions.md §7 Finalized).

## Design
Connecting is issues/net-connect.md's; what two connected nodes open is issues/net-shared-set.md's. First contact adds no path of its own: it only needs those two to cover a link key and a depositor.
- **Links.** The redeemer holds L's seed: L's signing key, and K's read secret through the entry box the head claim set keeps for L's static entry (spec/wire.md §8). After the handshake it proves L, a known actor to every node holding K's roster or K's head claim set (the sharer's nodes, every other reader, a peer serving K unread), and its credential of K is L's static entry (issues/net-shared-set.md Words): each such node holds that same value, so either side's beacon on it hits and K opens, the sharer online or not. K's grant gives the target. One credential at readers and peers that cannot read alike; the redeemer's view of K's roster is unknown and blocks nothing (Admissible). A node holding K's finalize of L judges L departed and opens nothing. Recovery cards find their home the same way (issues/recovery-redesign.md).
- **Link text**: L's seed, target, K, K's sync ID, and connect hints (key and addresses of nodes serving K, the maker's to begin with). No hosts, no `direct`, no `LinkOpts.direct`. A redeemer connected some other way (LAN, a common node) finds K all the same; a node a held link names counts as one its holder may connect to (issues/net-connect.md's trust setting). `make_link` works on every node, runtime or not (row 5).
- **Contact cards**: a plain link (read on the profile), so they work when links do (rows 8, 12).
- **Grants** (row 9). The inbox is the recipient's sync ID (issues/net-role-sync.md), which its `keys.0` names with the deposit seed. The grant is an inbox blob the sender offers (issues/net-shared-set.md Deposits; built between readers, notes/inbox.md Deposit items) to any connected node that proved an actor holding the inbox's read role (the recipient's own nodes; a team's members' nodes), and deposits, signed with the deposit key, at any connected node serving the inbox unread, found by that node's deposit-key beacon. The recipient knowing the sender is the common case: it learned the sender's keys through a shared group or a card exchange. A recipient that does not know the sender is issues/net-connect.md's one-way question (Tess); until a yes, the delivery stays pending, shown, and lands through a node that knows both or a peer serving the inbox unread. Until a node takes it the delivery is pending in status and waits, never "sent". First step, before shared-set lands: report a delivery that has nowhere to go (issues/net-honest-status.md).
- **Inbox payloads** name sync IDs only, no hosts (spec/wire.md §9, spec/sync.md §3 Following a payload label).
- **Bundles**: a link redeems from a bundle alone (row 21); trace why it does not.
- **Link expiry** (row 37): any sharer node holding the seed thing and admin on K finalizes after a complete pass with its connected sources (issues/net-honest-status.md). A redemption it has not seen is dropped by the removal's frontier, as now (spec/permissions.md §7).

## Unsure
- (Tess, via issues/privacy.md) Whether links and cards carry connect hints by default: hints give an address to everyone holding the text, and a card is shared widely. Without them a holder needs another connection to a node serving K.
- (design) A grant to an account whose nodes the sender never connects to (it learned the `keys.0` through a group the recipient left): proposed, it stays pending, shown. Carrying deposits for others is relaying (issues/p2p-own.md).
- (design) Row 37 above: whether finalizing at more than one sharer node needs any order (two explicit removals of L).

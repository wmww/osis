# CLI: one process per store blocks every other command while `watch` or `serve` runs
> Summary: the store lock means a long-running `osis` invocation (`watch`, `serve`, `status --watch`, `diag --follow`) locks out every other command on that store, so an agent or script that listens must stop listening to read or write, and a host cannot be inspected or reconfigured while it serves (dogfooding, notes/dogfood.md). Proposal (owner go-ahead needed): the long-running invocation also listens on a unix socket in the store directory and later invocations proxy their whole command through it, using the existing `main_with(args, stdin, stdout, stderr)` boundary; no per-command work.
> Tags: cli, design

## Proposal
- A streaming command (`serve`, `watch`, `roster --watch`, `status --watch`, `diag --follow`) opens `<store>/sock` (unix socket, mode 0600, created with the store's owner; removed on exit, stale one replaced after a connect fails). Every invocation that finds the store locked connects to the socket instead of exiting 8; a locked store with no live socket stays exit 8 (`store in use by pid N`).
- Wire: one connection per proxied command; client sends `[args, env subset (OSIS_* and EDITOR), is_terminal, stdin bytes]` framed in CBOR, server streams `[fd, bytes]` frames for stdout/stderr and a final `[exit, code]`. The server runs `osis_cli::run(args, Some(shared handle), io)` on a thread with the same `Osis` handle (the API is `Send + Sync`; handles are cheap clones). Stdin is sent whole (no interactive commands exist: `edit` opens `$EDITOR` only on a terminal, which a proxied run reports as non-terminal and so reads stdin).
- Streaming commands proxied through a streaming command work the same (each is a thread with its own subscription); SIGINT at the client closes the connection, which cancels the server thread's wait.
- Peer check: the server accepts only connections whose peer uid is its own (`SO_PEERCRED`); the socket is inside the store directory, which `restrict_to_owner` already tightens.
- `serve` gains nothing special: hosting flags given to a proxied `hosting set` take effect live (the node reads `host.0^` per engine change; admission and caps change in place, notes/sync.md Hosting in the node), which closes the "cannot reconfigure a running host" gap of issues/cli-own-admission.md.
- Not in scope: a persistent daemon that outlives the command that started it (systemd is the answer for `serve`), Windows named pipes (the CLI is Linux-first), remote proxying.
- Cost: one module in osis-cli (socket, framing, thread per connection) and a tier-2 localhost test (two `osis` processes on one store: `watch` running while `create` and `get` go through it). Picked numbers: none (no timeouts: the client waits as long as the command; the server bounds in-flight stdin by the existing `MAX_BLOB`-sized value bound per command, since stdin is one value or one script).

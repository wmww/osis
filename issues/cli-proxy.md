## Follows from it
- **Thin clients' sharing and sync rows**: `grant`, `add_with_grant`, `leave`, `make_link`, `sync`, `unsync`, `sync_now` and `wait_synced` are the main actor's only: the engine flows they call act with the node's authority and take no actor, so a client row would be a confused deputy. Giving them an actor is the rest of `Osis::act_as` (issues/grant-rename-multi-actor.md).
- **Thin clients' schemas**: `register_schema` is the main actor's only (it stays in the engine's store, process-wide, keyed by version: a client's could retype the node's aspects). A client's typed write reaches the node untyped unless the node's main actor registered the schema. Needs per-session schemas at the replay, or a decision that the main actor registers them.
- **A removed client's actor stays**: a member of the home group with its secrets forever; one record per client ever added. Its commits' certificates may need it.
- **Stall bound for clients**: a client's `commits` costs O(the store's commits), a `write` of `MAX_WRITE_OPS` about 1.8 s, as the main actor's; a client is less trusted than the main actor and these share one worker thread. Not bounded further.
- **A move away can read behind**: `group_source(.., GroupSource::Node(..))` waits for local writes at a peer, not at the source node. With that node slow or cut from the peer, a read right after shows an older value than a write this process had acknowledged (reproduced), and stays so until it pulls. Nothing is lost. Closing it needs a "does the node hold this commit" check the port lacks.
- **Who answers rule 4**: notes/client-port.md §8 Trust in rule 4. A hostile source node can answer for any thing unknown here, and first in the list it answers for things of a routed group this engine has not heard of. Binding those to the route needs asking `groups_of` there, and still believes the answer.
- **A call has no overall deadline**: `Connection::call` waits for its reply; the session's stall timer counts any received bytes, so a hostile node that trickles never fails it. Only that caller's thread (the port worker no longer calls out). A deadline must not fail an honest large reply on a slow link.
- **Client-listener Auth guesses and session count**: nothing rate-limits Auth attempts per source on the public listener beyond the pending pool; 32-byte secrets make guessing moot, the hash compare costs a walk of `clients^.0` per attempt.
- **A daemon does not reach routed groups**: a main-actor call on a thing the node reads at another node, or does not hold while it has connected nodes, is `Unsupported` through the daemon (exit 1): the worker serves every client one at a time and must not wait on a node. So with `serve` running, the CLI on the same store reads a routed group with `--node ADDR --client-secret FILE` only; `group source` is process-wide and needs the daemon stopped. Serving these needs a worker per connection or an async row.
- **Silent link**: a call on a link that drops packets without closing waits for QUIC's idle timeout and the session's stall timeout (minutes) before `Network`; `Network` is at once only once the connection is known down. As (c). It holds the calling thread only.
- **One port worker per node**: every connection's requests run on one thread, so a slow call stalls every client; measured worst row `write` of 1024 sets about 1.8 s. Per-connection workers (bounded by `max_clients`) would not shorten that stall: the write's commit holds `eng` throughout (one engine transaction, notes/client-port.md Port stall bounds), which every other call, local or from a client, and the sync driver also wait on. They would only overlap off-lock work (reply and Notify encoding, `settle` waiting on the node's dispatcher, which a slow app callback in the node process prolongs). Revisit with (c)/(d), when several network clients share a node; the CLI daemon case has one client at a time.

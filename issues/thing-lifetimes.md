# Thing lifetimes by reference
> Summary: Design: a thing may list its retainer set (`retainers^.0`, a `set<tid>`, admin-only); it lives while a listed retainer that is itself alive references it, up to a standalone thing; anything else is released (storage reclaim, not erasure), cycles included. A node that may end the thing and judges it unreachable from what it holds writes a release request (a part on each thing's `released.0`, expiring at `ROLE_KEEP`), applied as an ending, never lasting; with it the node forgets the thing. One rule for every ending: its evidence is kept and travels while a held thing depends on, lists or references the ended thing, so what is kept is bounded by live things; elsewhere a stale copy may bring a released thing back. A node that cannot judge leaks, never deletes. `w.release(x)` releases even a retained thing. One node-local reference index serves the judgment and backlinks. Rules, costs, the model and what it must add, Tess's decisions, build steps.
> Priority: normal
> Tags: data-model, api, permissions, sync, engine

## Principle
A thing's lifetime is decided by whoever may end it. Listing retainers is their standing instruction to release the thing once none of them keeps it; a node carries the instruction out only with the right to end the thing and only on what it holds, so a node that cannot see enough leaks and never deletes. Releasing is storage reclaim, not erasure (notes/deletion.md): it leaves nothing that outlives the need to tell late nodes, and a released thing may come back from a copy still held. Nothing here is a validity rule: no write is valid or invalid because of a list or a reference.

## Words
- **Standalone**: a thing with no `retainers^.0`. Lives until ended, released explicitly or expired.
- **Referenced**: a thing with `retainers^.0`. **Retainer** of X: a thing X lists there (not the retained copy of spec/permissions.md §3, which a removed holder keeps).
- **Reference**: a tid (CBOR tag 1616) in a thing's data. One from a retainer counts for lifetime; every other reference is plain data and may dangle.
- **Released**: ended by a release request (The release). Erasure stays `end` (a purge of the creation) and expiry; "drop" stays the engine's word for bodies.
- **Dependent** of X: as spec/commits.md §5 Ending (a held thing whose authority paths X is on: its record names X first admin, an edge write names X holder, or a commit X signed).

## Rules
### The list
- `retainers^.0` (Tess's name `retainers`; `^` is the admin-only marker, spec/data-model.md §2), core schema, `set<tid>`, ordinary retention (`admin`). Absent: standalone. Present: referenced, also when empty (an empty list is unreachable).
- Concurrent writes merge as any set; a removal of the aspect against a concurrent add resolves as any reset does. A list that does not read as `set<tid>` cannot be judged: the thing is kept.
- Admin-only is needed, not a preference: nodes release a thing on what its list says, so writing the list is as strong as releasing the thing. A list any writer could write would let every writer of any thing, standalone ones included, have it released.

### What a reference is
- R **references** X when X's tid occurs in a **live value** of R (the valid held writes in R's state), in a durable aspect other than `created.0`, the role-class aspects and `retainers^.0`. So `group.0` counts (a thing may live by its group). History never counts, so a retainer's history setting never keeps anything alive (Decisions 2); a signal has no live value and keeps nothing alive (a chat's attachments live by a live value, e.g. the chat's list of them).
- Not references: a value-less write (expired, purged); an invalid write; ephemeral data (it may be lost by accident); a tid inside a chunked set element or map key (links are not followed); a tid spelled in text (`osis://...` in a string). The excluded aspects say who has authority over R and what R hangs on, not what R points to: authority is not lifetime (What is kept).
- Found without a schema: any tag-1616 value at any depth of the inline canonical value, map keys, set elements and unknown tags' content included.

### The judgment
Judged from what the node holds, per thing, as one of three:
- A thing is **known** when the node holds a live `created.0` of it and may read it. It is **ended** when the node holds what shows it ended (spec/commits.md §5: a purge, an expiry, or a release request it still holds, What is kept). Anything else is **unknown**: never held, not readable (access lost, a retained copy), or ended or released with nothing kept.
- **Kept**: the least set holding every known standalone thing, and every known thing X with a listed retainer R that is unknown, or is kept and references X.
- **Unreachable**: known and not kept. So: its last referencing retainer stopped referencing it, every listed retainer ended, or it sits on a cycle no standalone thing reaches.
- A pending thing (unreachable, right not held) is not kept: it keeps nothing.
- An unknown retainer keeps: the index holds no rows of a thing the node cannot read, and that absence is never read as "does not reference". Losing access to a retainer, a member's removal, a forgotten thing and a release request forgotten all make it unknown.
- Dependents never enter the judgment: a node cannot see every dependent of X (nothing on X names them, and anyone may mint a thing naming X first admin), so a judgment counting them would release more on a node holding less. What dependents need of X is kept by the ending rules (What is kept).
- Nodes holding the same data and trust sets judge alike. A node holding fewer things judges unreachable only what a node holding more would (model).

### The release
- A node that holds X, holds the right to end it (the purge right over every `created.0` delta of X it holds, spec/permissions.md §6: its admins by default, or what the creation's purgeable-by says; `nobody`: no one releases it), and judges X unreachable, releases it: a **release request**, authored by the node's account, one commit for every thing it releases in that run. `w.release(x)` writes the same request at once (API).
- **Form**: the request is a part on each named thing's `released.0`, a core aspect with fixed rules of its own as `purge.0` has for a purge request (spec/data-model.md §9), naming only its own thing; `created.0` keeps meaning a minting and the wire's delta rules are unchanged. It ends every minting of X, whatever its `ts`, as a purge item on `created.0` does. Its commit has `expires = ts + ROLE_KEEP` (`released.0`'s rules allow it; `purge.0`'s fixed retention would not). As ending evidence each copy carries only its own thing's part (What is kept); `ending_evidence` carries the ending request parts, `purge.0` or `released.0`.
- **When**: once every label it tracks whose closure holds X or a retainer the judgment read reads Synced (notes/api.md Sync status: a source connected, each caught up; a label with no source connected, offline or with no co-reader up, is not); a thing under no label is judged at once. A commit's parts apply together, but commits arrive in any order: without this a node that receives "R1 no longer references X" before the earlier "R2 references X" releases a live thing (model). Offline, nothing is released; it stays until the node is heard out.
- **Applying**: valid like a purge request of X's creation (the same right, judged the same way, spec/permissions.md §6 Ending); receivers do not check that X was unreachable: they cannot. A node holding a valid request ends X as spec/commits.md §5 Ending does (every part on X dropped, its states, its blobs deleted at hosts by right holders, later parts on X are parts on an unknown thing), keeping of X only what What is kept says. A right holder places the request under X's labels before it deletes X's blobs at a host, so no host holds neither. A request arriving past its expiry still ends X (the ending is the part's presence, not its value), then is forgotten.
- **Not erasure**: nothing of X counts as purged. Lasting (spec/commits.md §5) is erasure's alone: a commit's header lasts for a purge, never for a release, and no `Body::Purged` listing.
- **Forgotten**: the request expires, so hosts delete its blobs at its `expires` on their own and every node forgets it then, but for what What is kept keeps. With it the node forgets X: the headers of commits whose every part is on X, and its entry knowledge of their blobs (spec/sync.md §6 Dropped bodies); a commit with parts on live things keeps its header and forgets the drop markers of its parts on X. Those parts count as never received (spec/commits.md §5 Never received): not fetched, judged again if a copy arrives. X is unknown there.
- **Final while held**: while a node holds the request, X stays ended there: a reference or list written without knowing of it dangles and reads as gone, a stale copy or a new minting of X ends on arrival, a write to X is a write to an ended thing. Two nodes may each release X; duplicates are harmless.
- **Comes back after**: a node that forgot the request, or never received it, takes a stale copy of X as a live thing (a released thing is not self-describing). It judges X again like any thing that became known: unreachable, it is released again by a new request (one per comeback, by a node with the right); kept (a reference it holds, a retainer unknown there), it lives and its holders upload it again. A bare minting of X (no list) reads as standalone and lives. Limits, stated (notes/deletion.md).
- **Cascade**: what X kept alive is judged when X is judged unreachable, whether or not this node may end X, and released the same way by whoever may end it. A pending thing keeps nothing (its own walk fails); a walk passes through it like any known thing, so changes judged together judge the same in any order (`pending` is stale for a thing the same batch made reachable; model).
- A node without the right over an unreachable thing remembers it (`pending`) and releases it if it gains the right. A node that never holds enough leaks it.
- The judgment and the request are two transactions: a released thing stays `pending` until the request, applied, ends it, so one whose request is refused or fails to be written is judged again at the next change of the role timelines or the next open (also once its list or a reference to it changes); nothing rests on luck (node `lifetimes::a_release_that_fails_to_be_written_is_judged_again_at_the_next_open`).
- No other node deletes anything: readers, plain writers and nodes that cannot read the data act only on the request when it arrives.

### What is kept
One rule for every ending (purge, expiry, release), the dependents rule of spec/commits.md §5 Ending widened to every thing that needs X ended to judge:
- While a node holds a thing that depends on X (Words), lists X in `retainers^.0` or references X other than in `group.0` (a group contains its members, it does not need them told ended; `group.0` still keeps a member alive), it keeps the evidence that X ended, and that thing's labels carry it as ending evidence, placed by its holders (`ending_evidence`, judged at hosts by `ended_certificate`): a purge's request, an expiry's minting headers with their `expires`, a release request's part on X, each with its author's chain. A release copy has no prefix expiry, as a minting's header-only copy. A dependent also keeps X's record, value-less creation and `roles.0` parts (spec/commits.md §5). With none of these held, nothing of X outlives the request (a release) or the purge rules (a purge).
- So what is kept is bounded by live things. A node holding any such thing reads X ended and never takes it back: an expired retainer's children are judged, not leaked; a thing released on purpose stays released wherever a thing referencing it is held; a released actor's dependents judge later edge writes on it as one holding the original ending does. A node that receives such a thing receives the evidence with it and ends X again. A thing whose holders never held the evidence (it reached them only after it was forgotten) reads X unknown and keeps (leaks, never deletes).
- A released thing is an ended thing to its dependents, as for purge or expiry: authority through it stands as its frozen history says; boxing to it as a holder actor boxes its frozen holders (an ended actor holds no keys).
- Not frozen history without the evidence: a node could not tell it from a live actor's (spec/commits.md §5 Ending: the ending travels with the record), so nodes would judge later edge writes on X differently. Not "release refused while dependents exist": see The judgment.

### Disputes, validity
- Lists and references are read under the node's trust set, like every value. A release written on one side of a dispute over a retainer is an ordinary request on X and stands on both sides if X itself is not disputed. Limit, stated: a dispute over a retainer can release what only the other side reads as referenced.
- A reference whose write turns invalid (its author demoted with a frontier that omits it) stops counting; a release it caused stands while the request is held, and the thing may come back after.

## Index and backlinks
- One local, rebuildable index of references in held readable data: rows `(target, source thing, AK)` with a count, per class: live durable, live ephemeral. `retainers^.0` values are indexed like any value, which gives "who lists X" (they are not references for lifetime).
- Kept in the transaction that changes the state: apply, un-merge, expiry, purge, ending, release, forgetting. A row never outlives the data it came from (spec/commits.md §5 Dropping a body).
- **Backlinks** read the live classes: `db.backlinks(tid)`: the things, with the aspect, whose current values reference the tid, as the acting actor may read them; paged, and live through the same listener rules as `on_change` (initial delivery, then each change, local ones included, after the commit is durable). Shape per the queries pass (notes/api.md Queries); a reference is found only in data this node holds and may read, in history never, and a group listing the thing is a backlink like any other (the direct group index is this index filtered to `group.0`).

## API (notes/api-design.md)
Built as notes/api.md Lifetimes says: `core::RETAINERS` (beside `core::RETENTION`, where the other setting-like core keys are), `AspectWrite::retaining(x)` (the one motion), `Write::release(x)` (a commit of its own), the writer's `Invalid` on its own list change leaving a thing unreachable. Decided there and why: the one-motion shape (a modifier on the aspect write naming the target, checked against that aspect's reference row); a release does not carry the cascade in its commit (the node's heard-out judgment releases it); `delete` leaves `retainers^.0` (`core_types::deletable`); an ended thing reads `created`/`changed` `None`.
- Why release anyway rather than a no-op while retained: a no-op is a silent wrong default; an error or no-op decided by "has live retainers" would turn on what this node holds, so the same call would act differently per node. Released anyway, the call does what it says everywhere, and a retainer's reference to x reads as gone, as after `end` (references may dangle, spec/requirements.md Data model).
- One commit per structural change is what makes part-received data safe; the API gives no way to write a move as two commits by accident beyond writing two `Write`s.

## Interactions
- **History** (notes/engine-retention.md History): independent. A removal releases at once whatever the retainer's history keeps; undo of a removed reference restores a tid that may dangle (reads as gone). Releasing X ends X's own history with it.
- **`delete(R)`** resets R's content and memberships: R references nothing live, so what it kept is released. **`delete(X)`** removes X's memberships, so a thing living by its group is released at once.
- **Purge** of the write holding a reference releases at once ("delete for everyone" on a message releases its attachment).
- **Expiry**: an expiring write's reference counts until T. A thing referenced by an expiring thing should be created in the same expiring commit: then every node ends both at T with nobody online. Otherwise a node that may end it releases it: the expired retainer's minting headers stay with the lister and travel under its labels (What is kept), so the retainer reads ended wherever the lister is held. Limit: a lister whose holders never held them reads its retainer unknown and leaks.
- **Ending**: `end(R)` on a standalone root erases R and releases everything only it kept (the cascade is a release: erasure of R does not erase what hung on it).
- **Keys**: a released holder actor is ended for boxing (What is kept): its frozen holders are boxed in its place where the evidence is held. A node not holding it (no dependent, request forgotten) holds no dependent to box for.
- **Removal, lost access**: never a reason to release (unknown keeps). A removed member's node forgets what it lost; the others judge as before.
- **Hosts and nodes that cannot read**: do nothing; right holders delete a released thing's blobs at hosts as for any ending, after placing the request; hosts delete the request's blobs at its `expires`, and its evidence copies by `ended_certificate`.
- **Sync**: a reference syncs nothing. A node that holds R but not X sees a dangling tid; one that holds X but not R keeps X until a request arrives.

## Cost
- Index per write: O(tids that entered or left the state), read from what apply already changes; a reset of a collection costs the tids under it, once (paid for by their insertion). A rebuild (validity flip, purge) costs what the rebuild costs today plus the aspect's tids.
- Judgment: a search up the lists through referencing retainers, stopping at the first standalone or unknown thing. A single-retainer thing whose reference goes is judged in O(1). A thing with another referencing retainer costs the walk up that chain: O(depth). A failed search visits only unreachable things, each of which is then released or pending. No cache of liveness: the only kept state is the work list (things a change touched, judged when heard out) and `pending`.
  - Limit: on a thing with several referencing retainers at the bottom of a deep chain, each change of its support costs the chain's depth. If a measured budget is missed: a support forest with a dynamic-tree ancestor test, O(log n).
- A change queues: the things whose references from the written thing changed; the thing whose list changed; a thing that became known (created, or back after a forgotten request); the listers of a thing that ended, became known or unknown; the pending things of a gained right. Model: one unreference under a root of n children judges 2 things at n = 10 and n = 100.
- Releasing n things: one commit with a part on each, held by every node and at hosts until its `expires` (`ROLE_KEEP`), then nothing: with it go X's commit headers and entry knowledge. Longer only where a held thing depends on, lists or references X: one evidence copy per label carrying that thing (beside the record and edges an ending keeps for dependents anyway, notes/growth.md row 5). Nothing per released thing for good: no lasting header, no record, no purge tombstone. Short-lived things should still expire: an expiry writes nothing.
- A comeback (a stale copy after `ROLE_KEEP`) costs one judgment and, where unreachable, one new request; it needs a node that kept X unsynced for `ROLE_KEEP`.
- Growth rows to add: the index (per live reference, about 50-70 B, local, rebuildable); the work list and `pending` (per unreachable thing not yet released here); a release request (per released thing, `ROLE_KEEP`, then only while a held thing depends on, lists or references it); an expired thing's minting headers while a held thing lists or references it.

## Limits and problems, stated
1. **Creating a referenced thing under a shared actor** (Decisions 3): a writer of the shared actor creates the thing with its own account as first admin and, in the same commit, sets `retainers^.0` (and `retention^.0`), grants admin to the shared actor and removes its own record edge. One commit, so no window; no new rule. Cost: two edge writes per such thing while it lives (released with it unless it has a dependent). The API may offer this as one call.
2. **Partial views leak** (by choice): a thing readable where its retainers are not is never judged there; it goes there only by a request from a node that could judge. Requiring one sharing context would need a validity rule across things that role changes break anyway. The API path that avoids it is the usage rule already in spec/requirements.md Generality (share a set through one actor): create the thing under the retainer's actor.
3. **Offline nodes release nothing**, so an unreferenced thing is still found by a search there until the node syncs. An app that means "this goes now" calls `release`, or `end` to erase.
4. **Disputes** can release across sides (Rules, Disputes).
5. **A released thing may come back** from a copy held by a node that missed the request for `ROLE_KEEP` (offline, or a partial view that never got it); where it is unreachable a node with the right releases it again. Wherever a thing depending on, listing or referencing it is held it never comes back (the evidence travels with it).
   - `ROLE_KEEP` (notes/arbitrary-values.md, minor consequence): at 0 the request is forgotten as written, so holders that have not seen it upload X again and right holders release it again, round for good (a livelock, nothing lost); at infinity the request is a tombstone, which release may not leave. At the chosen value the round ends: a node that missed it for `ROLE_KEEP` does not sync cleanly anyway (the same reason as `LOST_HEARD_WAIT_MS`), the request is placed at a host before X's blobs are deleted there, and one arriving late still ends X before it is forgotten.
   - A bare re-minting: anyone holding X's record may mint it again (spec/commits.md §5, the re-minting limit). While the request is held the minting ends with X; after, it carries no list, so X reads as standalone and lives. Stated beside §5's limit.
6. **A released actor is an ending to its dependents**: authority through it is frozen and things keyed through it are boxed to its frozen holders; nobody writes it there again.
7. Rejected:
   - every node releasing on its own judgment with no request: a node that cannot judge (partial view) keeps the thing and its holders upload it again, so either right holders' deletes at hosts and those uploads go round for good, or hosts keep every released thing; and a released actor's dependents get no proof, so frozen history could not be told from live (spec/commits.md §5 Ending) and nodes would judge later edge writes on it differently;
   - release refused (the thing kept) while it has dependents: no node can see every dependent, so a node holding less would release more, and anyone may mint a thing naming X first admin to pin it;
   - frozen history for dependents without the request as proof (as above);
   - a release request kept for good, or a lasting header for what a release dropped: that is erasure's tombstone (notes/deletion.md);
   - fetching a forgotten release's parts again (as a fallen purge does): the release did not fall, so they count as never received;
   - the request as header items naming every thing: each evidence copy would name all of them;
   - the release part on `created.0`: a `created.0` delta means a minting everywhere (engine, wire), so a header-only copy could not tell the two apart;
   - a delete right for writers of a listed retainer (Decisions 1); the list writable by writers (above); the creating commit writing the list without admin (any writer can write a commit carrying a copy of `created.0`, so it equals a writer-writable list); the list writable by "whoever may end" judged per held creation delta (held copies of a creation can differ in purgeable-by, so validity would depend on which copies a node holds); a liveness cache per thing (state to keep right under every arrival order for a cost only deep multi-retainer chains pay); treating a not-held retainer as dead (wrong deletes at every partial holder).

## Model
`core/test/held-model/src/lifetimes.rs`, `tests/it/spec_lifetimes.rs` (15 tests, pass, 1 s):
- over every view of 3 things (unknown, ended, or known with any list and references, itself included): the walk up judges exactly as the least-fixpoint rule; with everything held, kept is what a walk down from the standalone things reaches;
- making any thing unknown never adds a release (a node missing things, or losing access, releases only what the whole view releases), over every view and over random runs;
- cycles are released unless a standalone thing reaches them, two concurrent rewrites closing one included; self-listing and an empty list release; an ended retainer releases, an unknown one keeps;
- a move written as one commit is safe in every subset of commits a node may hold; as two commits, the removal held without the earlier addition releases a live thing (why a node hears out first);
- endings: a purge (`End`, kept for good), an expiry, a release request received (`Released`, late ones too) or written (`Release`, a retained thing too), forgetting (`Forget`: unless a held thing lists or references the thing, it becomes unknown), stale copies (`Learn`) and bare mintings (`Mint`);
- 4000 random runs of 10 batches of 1-3 changes over 5 things (every event above, lost and learned things, rights gained and lost): judging only what each batch touches ends exactly what a from-scratch judgment says the node may end, and `pending` is exactly the rest; forgetting changes no judgment and keeps the evidence while a lister or referencer is held; an ending held is final against any list, reference, stale copy or minting until forgotten, a purge for good;
- an expired retainer's child is released where it is held; an explicit release takes the thing and what only it kept, stays while referenced, and after it is forgotten a stale copy comes back and is released again, a bare minting lives;
- a walk passes through a pending thing like any known thing: reading it as failed releases a live thing when a batch makes the pending thing reachable and brings a thing under it (`a_stale_pending_thing_is_walked_through`); its own walk fails anyway, so it keeps nothing;
- cost: counted at n and 10n.

Dependents are not in this model: their side is the ending model's (held-model `model.rs`, roles-model) with a release request as one more kind of ending evidence under the What is kept rule; still to check there that a node holding a dependent never revives the thing and judges later edge writes on it as one holding the original ending does.

Not modelled: what a reference reads (validity), hearing out, the request's own validity and spread (the purge right), disputes.

## Requirements wording
In spec/requirements.md Data model (Tess wrote and approved it): garbage collection by retainer set; released, purged or expired retainers keep nothing; no promise of prompt or permanent deletion; it may only function where one node syncs, reads all relevant things and may release the thing; an unretained cycle is released whole; things with no retainer set are roots.

## Decisions (Tess)
1. Who may write the drop: no new right; the nodes that may already end the thing do it.
2. Only live values count as references (history never keeps a thing alive): otherwise a retainer with history kept forever could never release anything.
3. No creation-record or creating-commit exception: a writer creates under its own account as first admin and hands admin over in the same commit (Problems 1). An initial list in the creation record (changeable later through `retainers^.0`, like the first admin through role writes) is allowed if it proves simpler or better in the build; the implementer decides and says why.
4. Partial views leak (stated), no one-sharing-context rule.

Each one worker and one reviewer, in order. Steps 1-2 are useful alone (backlinks). Steps 3-4 build on ended-keyed and ended-evidence (spec/commits.md §5 Ending, `ending_evidence`, `ended_certificate`) and wait on the model additions above.

2. **Backlinks API** (built). `db.backlinks` and its listener per notes/api-design.md and the queries shape; CLI `backlinks`. Tests: a note linking a note shows and stops showing, locally and after sync; only what the acting actor may read; ephemeral references show; paged at n and 10n.
3. **Judgment and release** (engine, node-sync). `retainers^.0` in the core schema; known/ended/unknown; the walk, the work list (comebacks and mintings queued) and `pending`; the release request (a part on each thing's `released.0`, `expires = ts + ROLE_KEEP`), applied as an ending, placed before X's blobs are deleted; forgetting with it X's headers and entry knowledge, parts never received; What is kept for every ending through `ending_evidence` / `ended_certificate`; trigger when heard out; batched; gained rights.

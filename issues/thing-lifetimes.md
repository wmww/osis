# Thing lifetimes by reference
> Summary: Design: a thing may list its retainers (`retainers^.0`, admin-only); it lives while a listed retainer that is itself alive references it, up to a standalone thing; anything else is released (storage reclaim, not erasure), cycles included. A node that may end the thing and judges it unreachable from what it holds writes a release request, applied as an ending and forgotten after `ROLE_KEEP` (kept only as ending proof for dependents and for held listers), so a stale copy may bring the thing back; a node that cannot judge leaks, never deletes. `w.release(x)` releases even a retained thing. One node-local reference index serves the judgment and backlinks. Rules, costs, the model and what it must add, Tess's decisions, build steps.
> Priority: normal
> Tags: data-model, api, permissions, sync, engine, tess-call

## Principle
A thing's lifetime is decided by whoever may end it. Listing retainers is their standing instruction to release the thing once none of them keeps it; a node carries the instruction out only with the right to end the thing and only on what it holds, so a node that cannot see enough leaks and never deletes. Releasing is storage reclaim, not erasure (notes/deletion.md): it leaves nothing that outlives the need to tell late nodes, and a released thing may come back from a copy still held. Nothing here is a validity rule: no write is valid or invalid because of a list or a reference.

## Words
- **Standalone**: a thing with no `retainers^.0`. Lives until ended, released explicitly or expired.
- **Referenced**: a thing with `retainers^.0`. **Retainer** of X: a thing X lists there (not the retained copy of spec/permissions.md §3, which a removed holder keeps).
- **Reference**: a tid (CBOR tag 1616) in a thing's data. One from a retainer counts for lifetime; every other reference is plain data and may dangle.
- **Released**: ended by a release request (The release). Erasure stays `end` (a purge of the creation) and expiry; "drop" stays the engine's word for bodies.
- **Dependent** of X: as spec/commits.md §5 Ending (a held thing whose authority paths X is on: its record names X first admin, an edge write names X holder, or a commit X signed).

## Rules
### The list
- `retainers^.0` (Tess's name `retainers`; `^` is the admin-only marker, spec/data-model.md §2), core schema, `set<tid>`, ordinary retention (`admin`). Absent: standalone. Present: referenced, also when empty (an empty list is unreachable).
- Concurrent writes merge as any set; a removal of the aspect against a concurrent add resolves as any reset does. A list that does not read as `set<tid>` cannot be judged: the thing is kept.
- Admin-only is needed, not a preference: nodes release a thing on what its list says, so writing the list is as strong as releasing the thing. A list any writer could write would let every writer of any thing, standalone ones included, have it released.

### What a reference is
- R **references** X when X's tid occurs in a **live value** of R (the valid held writes in R's state), in a durable aspect other than `created.0`, the role-class aspects and `retainers^.0`. So `group.0` counts (a thing may live by its group). History never counts, so a retainer's history setting never keeps anything alive (Decisions 2); a signal has no live value and keeps nothing alive (a chat's attachments live by a live value, e.g. the chat's list of them).
- Not references: a value-less write (expired, purged); an invalid write; ephemeral data (it may be lost by accident); a tid inside a chunked set element or map key (links are not followed); a tid spelled in text (`osis://...` in a string). The excluded aspects say who has authority over R and what R hangs on, not what R points to: authority is not lifetime (Dependents).
- Found without a schema: any tag-1616 value at any depth of the inline canonical value, map keys, set elements and unknown tags' content included.

### The judgment
Judged from what the node holds, per thing, as one of three:
- A thing is **known** when the node holds a live `created.0` of it and may read it. It is **ended** when the node holds what shows it ended (spec/commits.md §5: a purge, an expiry, or a release request it still holds). Anything else is **unknown**: never held, not readable (access lost, a retained copy), or ended or released with nothing kept.
- **Kept**: the least set holding every known standalone thing, and every known thing X with a listed retainer R that is unknown, or is kept and references X.
- **Unreachable**: known and not kept. So: its last referencing retainer stopped referencing it, every listed retainer ended, or it sits on a cycle no standalone thing reaches.
- An unknown retainer keeps: the index holds no rows of a thing the node cannot read, and that absence is never read as "does not reference". Losing access to a retainer, a member's removal, a forgotten thing and a release request forgotten all make it unknown.
- Dependents never enter the judgment: a node cannot see every dependent of X (nothing on X names them, and anyone may mint a thing naming X first admin), so a judgment counting them would release more on a node holding less. What dependents need of X is kept by the ending rules (Dependents).
- Nodes holding the same data and trust sets judge alike. A node holding fewer things judges unreachable only what a node holding more would (model).

### The release
- A node that holds X, holds the right to end it (the purge right over every `created.0` delta of X it holds, spec/permissions.md §6: its admins by default, or what the creation's purgeable-by says; `nobody`: no one releases it), and judges X unreachable, releases it: a **release request** naming X, authored by the node's account, one commit naming every thing it releases in that run. `w.release(x)` writes the same request at once (API).
- **When**: once it has heard out (spec/permissions.md §2, `SyncEngine::heard`) every label it tracks whose closure holds X or a retainer the judgment read; a thing under no label is judged at once. A commit's parts apply together, but commits arrive in any order: without this a node that receives "R1 no longer references X" before the earlier "R2 references X" releases a live thing (model). Offline, nothing is released; it stays until the node is heard out.
- **Applying**: a request is valid like a purge request of X's creation (the same right, judged the same way, spec/permissions.md §6 Ending); receivers do not check that X was unreachable: they cannot. A node holding a valid request ends X as spec/commits.md §5 Ending does (every part on X dropped, its states, its blobs deleted at hosts by right holders, later parts on X are parts on an unknown thing), keeping of X only what Dependents and Listers below keep. Nothing of X counts as purged: no lasting header, no `Body::Purged` listing.
- **Forgotten**: a release request is not a purge request and is not kept for good. Every node forgets it, and right holders delete its blobs at hosts, `ROLE_KEEP` after its `ts` (the time the protocol already gives offline nodes to sync cleanly; class: minor consequence, see Limits). Kept past that only as below. Then the node holds nothing of X: X is unknown there.
- **Final while held**: while a node holds the request, X stays ended there: a reference or list written without knowing of it dangles and reads as gone, a stale copy of X is dropped on arrival, a write to X is a write to an ended thing. Two nodes may each release X; duplicates are harmless.
- **Comes back after**: a node that forgot the request, or never received it, takes a stale copy of X as a live thing (a released thing is not self-describing). It judges X again like any thing that became known: unreachable, it is released again by a new request (one per comeback, by a node with the right); kept (a reference it holds, a retainer unknown there), it lives and its holders upload it again. Limit, stated (notes/deletion.md).
- **Cascade**: what X kept alive is judged when X is judged unreachable, whether or not this node may end X, and released the same way by whoever may end it.
- A node without the right over an unreachable thing remembers it (`pending`) and releases it if it gains the right. A node that never holds enough leaks it.
- No other node deletes anything: readers, plain writers and nodes that cannot read the data act only on the request when it arrives.

### Dependents
- A released thing is an ended thing to its dependents, exactly as for an ending by purge or expiry (spec/commits.md §5 Ending): authority through it stands as its frozen history says; boxing to it as a holder actor boxes its frozen holders (ended actors' keys, Fathom's ended-keyed: an ended actor holds no keys); a node keeps its record, value-less creation and `roles.0` parts while a dependent is held.
- The request is the ending's proof, and it travels with the frozen history (Fathom's ended-evidence, the purge request's case): under each label carrying the frozen history, while a dependent there needs it, past `ROLE_KEEP`. So every node holding a dependent reads X ended, a stale copy of X never comes back there, and an edge write on X stamped after the request (by a node holding a stale copy) is dropped wherever the dependent is judged. A node holding no dependent may take X back after forgetting the request; once it receives a dependent it receives the proof with it and ends X again. Without dependents nothing of X outlives the request.
- Not frozen history without proof: a node could not tell it from a live actor's (spec/commits.md §5 Ending: the ending travels with the record), so nodes would judge later edge writes on X differently. Not "release refused while dependents exist": see The judgment.

### Listers
- So that a released retainer is known ended: a node keeps a release request it holds, past `ROLE_KEEP`, while it holds a thing listing a thing the request names. Local; nothing travels for it. A node that receives the lister after the request was forgotten reads the retainer unknown and keeps the lister (leaks, never deletes).

### Disputes, validity
- Lists and references are read under the node's trust set, like every value. A release written on one side of a dispute over a retainer is an ordinary request on X and stands on both sides if X itself is not disputed. Limit, stated: a dispute over a retainer can release what only the other side reads as referenced.
- A reference whose write turns invalid (its author demoted with a frontier that omits it) stops counting; a release it caused stands while the request is held, and the thing may come back after.

## Index and backlinks
- One local, rebuildable index of references in held readable data: rows `(target, source thing, AK)` with a count, per class: live durable, live ephemeral. `retainers^.0` values are indexed like any value, which gives "who lists X" (they are not references for lifetime).
- Kept in the transaction that changes the state: apply, un-merge, expiry, purge, ending, release, forgetting. A row never outlives the data it came from (spec/commits.md §5 Dropping a body).
- **Backlinks** read the live classes: `db.backlinks(tid)`: the things, with the aspect, whose current values reference the tid, as the acting actor may read them; paged, and live through the same listener rules as `on_change` (initial delivery, then each change, local ones included, after the commit is durable). Shape per the queries pass (notes/api.md Queries); a reference is found only in data this node holds and may read, in history never, and a group listing the thing is a backlink like any other (the direct group index is this index filtered to `group.0`).

## API (notes/api-design.md)
One new call, `w.release(x)`; no new error or type: the list is an aspect.
- `osis::RETAINERS`, a typed key of `set<tid>`. Create referenced, in one commit: `let x = w.create()?; w.at(x, RETAINERS).set(&[r])?; w.group(r).add(x)?` (or any write putting `x` in `r`). Add: insert. Move: insert the new, remove the old, and change both references, in one `Write`. Make standalone: `w.at(x, RETAINERS).remove()`.
- `Permission { needs: Admin }` as for any admin-only aspect.
- `Invalid` at commit when a write's own change of a thing's `retainers^.0` leaves it unreachable as this node judges it (created with a list and no reference, moved under a thing that does not reference it, the list emptied): caught before it silently vanishes. Not judged when a listed retainer is unknown. So `release` is the one way to let a thing go on purpose.
- **`w.release(x)`**: writes the release request for x (and, in the same commit, for what only x kept as this node judges it) at once, whatever retains x. `Permission` without the right to end x, as `end`. A released thing reads as any ended thing: absent. No call reads "alive". Beside it `end(x)` erases: the two verbs are the two purposes of notes/deletion.md.
  - Why release anyway rather than a no-op while retained: a no-op is a silent wrong default (the caller asked for x to go and nothing says it did not); an error or no-op decided by "has live retainers" would turn on what this node holds (an unknown retainer, offline), so the same call would act differently per node. Released anyway, the call does what it says everywhere, and what it costs others is what every reference already promises: references may dangle (spec/requirements.md Data model), and a retainer's reference to x reads as gone, as after `end`. No loss the caller did not name: the cascade takes only what x alone kept, which is what releasing x means.
- **One motion** (Tess): writing a reference to X anywhere in R's data and adding R to X's `retainers^.0` should be one call, in one commit (e.g. a typed setter that takes a tid and a `retain` flag, or `w.retain(r_path, x)`); likewise creating X referenced by R. Design it in the API step per notes/api-design.md; it must refuse what it cannot do in one commit (no admin on X) rather than do half.
- One commit per structural change is what makes part-received data safe; the API gives no way to write a move as two commits by accident beyond writing two `Write`s.

## Interactions
- **History** (notes/engine-retention.md History): independent. A removal releases at once whatever the retainer's history keeps; undo of a removed reference restores a tid that may dangle (reads as gone). Releasing X ends X's own history with it.
- **`delete(R)`** resets R's content and memberships: R references nothing live, so what it kept is released. **`delete(X)`** removes X's memberships, so a thing living by its group is released at once.
- **Purge** of the write holding a reference releases at once ("delete for everyone" on a message releases its attachment).
- **Expiry**: an expiring write's reference counts until T. A thing referenced by an expiring thing should be created in the same expiring commit: then every node drops both at T with nobody online. Otherwise it waits for a node that may end it and held the retainer when it expired. Limit: a thing that reaches such a node only after its expired retainer left nothing behind is unknown-referred there and leaks.
- **Ending**: `end(R)` on a standalone root erases R and releases everything only it kept (the cascade is a release: erasure of R does not erase what hung on it).
- **Keys**: a released holder actor is ended for boxing (Dependents): its frozen holders are boxed in its place where the proof is held. A node not holding the proof (no dependent, request forgotten) holds no dependent to box for.
- **Removal, lost access**: never a reason to release (unknown keeps). A removed member's node forgets what it lost; the others judge as before.
- **Hosts and nodes that cannot read**: do nothing; right holders delete a released thing's blobs at hosts as for any ending, and the request's own blobs at `ROLE_KEEP`.
- **Sync**: a reference syncs nothing. A node that holds R but not X sees a dangling tid; one that holds X but not R keeps X until a request arrives.

## Cost
- Index per write: O(tids that entered or left the state), read from what apply already changes; a reset of a collection costs the tids under it, once (paid for by their insertion). A rebuild (validity flip, purge) costs what the rebuild costs today plus the aspect's tids.
- Judgment: a search up the lists through referencing retainers, stopping at the first standalone or unknown thing. A single-retainer thing whose reference goes is judged in O(1). A thing with another referencing retainer costs the walk up that chain: O(depth). A failed search visits only unreachable things, each of which is then released or pending. No cache of liveness: the only kept state is the work list (things a change touched, judged when heard out) and `pending`.
  - Limit: on a thing with several referencing retainers at the bottom of a deep chain, each change of its support costs the chain's depth. If a measured budget is missed: a support forest with a dynamic-tree ancestor test, O(log n).
- A change queues: the things whose references from the written thing changed; the thing whose list changed; a thing that became known (created, or back after a forgotten request); the listers of a thing that ended, became known or unknown; the pending things of a gained right. Model: one unreference under a root of n children judges 2 things at n = 10 and n = 100.
- Releasing n things: one commit naming n things, held by every node and at hosts for `ROLE_KEEP`, then nothing. Longer only where needed: with the frozen history of a dependent (one request header per label carrying it, beside the record and edges an ending keeps for dependents anyway, notes/growth.md row 5) and at a node holding a lister. Nothing per released thing for good: no lasting header, no record, no purge tombstone. Short-lived things should still expire: an expiry writes nothing.
- A comeback (a stale copy after `ROLE_KEEP`) costs one judgment and, where unreachable, one new request; it needs a node that kept X unsynced for `ROLE_KEEP`.
- Growth rows to add: the index (per live reference, about 50-70 B, local, rebuildable); the work list and `pending` (per unreachable thing not yet released here); a release request (per released thing, `ROLE_KEEP`, then only with a dependent or a held lister).

## Limits and problems, stated
1. **Creating a referenced thing under a shared actor** (Decisions 3): a writer of the shared actor creates the thing with its own account as first admin and, in the same commit, sets `retainers^.0` (and `retention^.0`), grants admin to the shared actor and removes its own record edge. One commit, so no window; no new rule. Cost: two edge writes per such thing while it lives (released with it unless it has a dependent). The API may offer this as one call.
2. **Partial views leak** (by choice): a thing readable where its retainers are not is never judged there; it goes there only by a request from a node that could judge. Requiring one sharing context would need a validity rule across things that role changes break anyway. The API path that avoids it is the usage rule already in spec/requirements.md Generality (share a set through one actor): create the thing under the retainer's actor.
3. **Offline nodes release nothing**, so an unreferenced thing is still found by a search there until the node syncs. An app that means "this goes now" calls `release`, or `end` to erase.
4. **Disputes** can release across sides (Rules, Disputes).
5. **A released thing may come back** from a copy held by a node that missed the request for `ROLE_KEEP` (offline, or a partial view that never got it), or from a new minting; where it is unreachable a node with the right releases it again. `ROLE_KEEP` (notes/arbitrary-values.md, minor consequence): at 0 every late or partial holder brings it back and costs a re-release, nothing is lost or wrong; at infinity the request is a tombstone, which release may not leave. Past it a node does not sync cleanly anyway (the same reason as `LOST_HEARD_WAIT_MS`). Where a dependent is held it never comes back (the proof travels with it).
6. **A released actor is an ending to its dependents**: authority through it is frozen and things keyed through it are boxed to its frozen holders; nobody writes it there again.
7. Rejected:
   - every node releasing on its own judgment with no request: a node that cannot judge (partial view) keeps the thing and its holders upload it again, so either right holders' deletes at hosts and those uploads go round for good, or hosts keep every released thing; and a released actor's dependents get no proof, so frozen history could not be told from live (spec/commits.md §5 Ending) and nodes would judge later edge writes on it differently;
   - release refused (the thing kept) while it has dependents: no node can see every dependent, so a node holding less would release more, and anyone may mint a thing naming X first admin to pin it;
   - frozen history for dependents without the request as proof (as above);
   - a release request kept for good: that is erasure's tombstone (notes/deletion.md);
   - a delete right for writers of a listed retainer (Decisions 1); the list writable by writers (above); the creating commit writing the list without admin (any writer can write a commit carrying a copy of `created.0`, so it equals a writer-writable list); the list writable by "whoever may end" judged per held creation delta (held copies of a creation can differ in purgeable-by, so validity would depend on which copies a node holds); a liveness cache per thing (state to keep right under every arrival order for a cost only deep multi-retainer chains pay); treating a not-held retainer as dead (wrong deletes at every partial holder).

## Model
`core/test/held-model/src/lifetimes.rs`, `tests/it/spec_lifetimes.rs` (9 tests, pass, 1 s):
- over every view of 3 things (unknown, ended, or known with any list and references, itself included): the walk up judges exactly as the least-fixpoint rule; with everything held, kept is what a walk down from the standalone things reaches;
- making any thing unknown never adds a drop (a node missing things, or losing access, drops only what the whole view drops);
- cycles drop unless a standalone thing reaches them, two concurrent rewrites closing one included; self-listing and an empty list drop; an ended retainer drops, an unknown one keeps;
- a move written as one commit is safe in every subset of commits a node may hold; as two commits, the removal held without the earlier addition drops a live thing (why a node hears out first);
- an end held is final against any later list or reference;
- 4000 random runs of 14 changes over 5 things (lists, references, ends, lost and learned things, rights gained and lost): judging only what each change touches ends exactly what a from-scratch judgment says the node may end, and `pending` is exactly the rest (two seeded mutations of the propagation fail it);
- cost: counted at n and 10n.

To add before step 3 (the model's `End` is erasure; release needs):
- `Part::Release` beside `End`, and a `Forget(x)` event (the request passes `ROLE_KEEP` with no held lister naming x: `Ended` becomes `Unknown`) and a `Stale(x)` event (a copy of x's creation and last list and references arriving at a node holding no request: `Known` again); `w.release` of a retained thing as a `Release` part on any known thing.
- Properties: forgetting a request never adds a release (the unknown-monotone property, now over random runs); a lister held keeps the request, so forgetting never turns a dependent cascade into a keep that a node holding the request would release; after `Stale`, judging only what changes touch still equals from scratch (the comeback is queued, released again iff unreachable and the right is held, else kept or pending); a release held is final against any later list, reference or stale copy until forgotten; an explicit release of a retained thing releases exactly it and what only it kept.
- Dependents are not in this model: their side is the ending model's (held-model `model.rs`, roles-model) with a release request as one more kind of ending evidence that travels with frozen history and is forgotten with no dependent; check there that a node holding a dependent never revives the thing and judges later edge writes on it as one holding the original ending does.

Not modelled: what a reference reads (validity), hearing out, the request's own validity and spread (the purge right), disputes.

## Requirements wording (Tess's sign-off)
Rewritten for release (Tess: lifetimes are storage reclaim, notes/deletion.md): Decisions 4 approved "dropped for good", which release contradicts, so this wording needs her sign-off again (`tess-call`). Data model, after "References may dangle":
> A thing may name the things whose references keep it alive. Once none of them, alive itself, references it, it is released, with whatever only it kept alive, cycles included: removed to reclaim storage, not erased, so a copy kept somewhere may bring it back. Limit: it is released only by a node that may end it and holds what shows it is unreferenced; until then, and where no such node exists, it stays. Limit: a release decided without a reference written concurrently, or not yet received, stands.

## Decisions (Tess)
1. Who may write the drop: no new right; the nodes that may already end the thing do it.
2. Only live values count as references (history never keeps a thing alive): otherwise a retainer with history kept forever could never release anything.
3. No creation-record or creating-commit exception: a writer creates under its own account as first admin and hands admin over in the same commit (Problems 1). An initial list in the creation record (changeable later through `retainers^.0`, like the first admin through role writes) is allowed if it proves simpler or better in the build; the implementer decides and says why.
4. Partial views leak (stated), no one-sharing-context rule.

## Steps
Each one worker and one reviewer, in order. Steps 1-2 are useful alone (backlinks). Steps 3-4 build on ended-keyed and ended-evidence (spec/commits.md §5 Ending; Dependents uses both) and wait on the model additions above.
1. **Reference index** (engine). Rows and counts for live durable and ephemeral values, kept on apply, un-merge, rebuild, expiry, purge, ending, release, forgetting. Tests (through `internals`, then step 2's API): rows follow the value in any arrival order; a validity flip, an expiry and a purge remove them; lost access leaves none; a path write into a map of n and 10n entries changes O(written tids) rows and reads no other entry; notes/growth.md row.
2. **Backlinks API** (built). `db.backlinks` and its listener per notes/api-design.md and the queries shape; CLI `backlinks`. Tests: a note linking a note shows and stops showing, locally and after sync; only what the acting actor may read; ephemeral references show; paged at n and 10n.
3. **List and judgment** (engine, no writes). `retainers^.0` in the core schema; known/ended/unknown (a held release request is ended); the walk; the work list (comebacks queued) and `pending`. Tests: lockstep with held-model `unreachable` and `Node` over generated worlds and changes; losing access to a retainer never yields unreachable; judged counts at n and 10n.
4. **The release** (engine, node-sync, osis). The release request (wire form: an item naming the things, not a purge request, with a delta placing it under each thing's labels), applied as an ending; forgotten at `ROLE_KEEP` (hosts and nodes), kept while a held thing lists a named thing, travelling as ending evidence with a dependent's frozen history; trigger when heard out; batched; gained rights; `w.release`, `RETAINERS`, the commit-time `Invalid`; spec (data-model §9 and a lifetimes section, commits §5 Ending), notes/api.md, notes/arbitrary-values-table.md row (`ROLE_KEEP` reused). Tests (observable, several nodes): unreferencing releases at every node; a one-commit move keeps; a subtree and a cycle release; a node without the right keeps it until an admin's node syncs; a node missing a retainer, and a removed member's node, release nothing; a two-commit move part-received releases nothing before the pass ends; a concurrent re-reference dangles; an expired retainer; `release` of a retained thing; a stale copy within `ROLE_KEEP` stays gone, past it comes back and is released again; a released actor's dependent keeps its authority frozen and its keys reach a newcomer through the actor; nothing of a released thing with no dependent is held past `ROLE_KEEP`.
5. **Notes and bookkeeping.** notes/lifetimes.md (principle, rules, limits), notes/growth.md, notes/api.md, notes/deletion.md (the release's bounded request), requirements wording as signed off; kit, app and chat adoption is app-layer work.

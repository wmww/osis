# Bodies judged must-hold that no reader of S can make
> Summary: at quiet in the osis-sync suite, 72 (node, S, commit) triples stay must-hold with no entry under S at any node: a closure body of another's commit under a sync ID the node writes but cannot encrypt it for, and a node's own certificates under a sync ID it reads with no wrap epoch. Nothing logs them; read judges them again with each change, acting on nothing.
> Priority: low
> Tags: sync, engine

- Probe (not in tree): at each `World::run` quiet, for every node, held commit and S in its `sync_bodies` with read's verdict `Must` and no entry of any blob of the commit in its store under S, list the other nodes' stores holding one. Kept only what stands at a test's last quiet.
- **Closure bodies the node cannot seal** (about 45): another account's commit (`group.0`, `u:v.0`, `created.0`, `dial^.0` parts) under a sync ID this node writes (its home, D filed in it), required there because the account reads D. The node holds the commit only as a per-sync-ID copy from D's sync ID, so `held_sections` has no genuine section to carry, and it may not seal the part itself (`wrap_under`: no epochs of the part's thing, or `passes_on_parts` false), so `seal_body` gives `None`. No other node reads that sync ID. Example: `destruction::a_remint_expiring_earlier_keeps_the_lower_copy_spec_commits_5`, node 0, its home, the filing commit of u into D.
- **Own certificates with no wrap epoch** (about 25): a node's account chain certificate under a sync ID it reads through a card or link (`ReadCredentials` holds a read secret; `epochs(S's thing)` none, or no `newest_held`), so `seal_certificate`'s `wrap_secret` is `None` and the writer of S has not logged it either.
- Question for the engine (Fathom): should such a body be judged may-hold where this node can make no encryption of it for S (spec/sync-judgement.md §3 Own store logs only what it can), or should the writer of S log a reader's certificates? Either way read should not keep a must-hold judgement it can never act on.
- Also seen, not stuck: in node-removal tests (`duties::a_node_removed_from_its_account_stops_syncing_spec_sync_set_3`, `siblings::an_outsider_with_the_card_reads_the_accounts_writes_across_a_node_removal_spec_sync_set_3`) node 0 has no source of the card's sync ID connected at the last quiet. In `siblings::a_from_now_grantee_after_a_removal_holds_the_old_readers_roster_spec_crypto_5`, node 3 (linked to node 1 alone) is caught up under t's sync ID with nothing unheld: the entries there it lacks are pre-grant bodies a from-now grantee never fetches (spec/sync-streams.md §4 Fill order); its unheld bodies (4 and 11) are under its own two sync IDs, which no other node holds: the two cases above.

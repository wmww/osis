# A member whose server deposits are refused cannot recover automatically
> Summary: A member that falls far behind (its next key step was dropped by the server) normally asks for a re-share by leaving a small "stranded" deposit at the server. When that deposit is refused (the admins refreshed the deposit seed against abuse, or the server's budget for the group is full) nobody learns the member is stuck, and it stays locked out until a co-member re-shares by hand. Within spec/requirements.md's accepted limit ("re-sealing is triggered, never guaranteed"). Owner accepted this for the MVP; the automatic fix needs one new server log event. Residue of extra, harmless re-seals: fixed (see Technical details).
> Tags: permissions, sync, post-mvp

## The decision (user terms)
- **Accept** (MVP, current): clients show "re-share with M" to any member who may rotate; the default never refreshes the deposit seed on rotation (an admin does it explicitly, against abuse). A stuck member is rare: it needs a dropped step and a refused deposit at the same time.
- **Server claim log**: the server records which reader slot claimed each step; admins map slots to members and re-share anyone whose next rotation was compacted away. Automatic and reliable, no deposits needed; the server learns nothing it does not already see. Costs one new log event kind on the wire (provisional format, so a spec edit) and a little more server state per label.
- **Servers keep every claim set forever**: the member can always walk to the head and read, but still cannot signal that it needs re-sharing. Half a fix, more server storage.

Recommended: accept now; the claim log is the right mechanism if stranded members turn out common.

## Technical details
TLC (models/tla/rotation, R2; `MC_drop_refresh.cfg`, the expected failure of `models/tla/run.sh all MC_drop_refresh`) found: a member whose next step's claim set the server dropped can neither walk to the head nor, when the deposit seed was refreshed since it last read `/keys`, place its stranded heartbeat, so nobody re-seals it. The wrongful re-seal residues of the first round (`MC_reorder.cfg`, `MC_fork_reorder.cfg`, `MC_hist.cfg`) were closed without a wire change: spec/crypto.md §4 established epochs, spec/permissions.md §3 (re-seal at chain-established epochs at the end of a complete pass), spec/sync.md §5 (the rotation chain is uploaded before the step). Rationale: notes/permissions.md (re-seal), notes/crypto.md (history boxes, opening), notes/sync.md (rotation commits before the step; Limits for the accepted post-compaction residue).

A member that reaches a refused claim places a stranded heartbeat by deposit. The deposit is refused when the admins refreshed the deposit seed since the member last read `/keys` (a MAY), or when the label's budget is full. Then no automatic trigger exists: the member is boxed at every epoch it is listed at (no "missing box") and heartbeats nothing. Conservative reading implemented: clients offer "re-share with M" by hand (`Engine::reshare`); the deposit seed is refreshed only explicitly (`Engine::refresh_deposit_seed`). notes/sync.md Limits records it.

Extra re-seals of key-actor members: the "seen without a box" trigger (`reseal_due`) used to fire once per new read or write epoch for a key-actor member boxed only by a box keyed at a higher role (`carries` found no introducing commit); harmless (one exact box per such member per rotation). Tracked with the `carries` fix in issues/flows-gaps.md.

# A removed admin keeps its own grants on things below
> Summary: With one authority class, X's grant of admin to itself on a thing below N (made while admin of N, not in the remover's frontier) is no fall when X is removed from N, so the audit keeps it; step 3's seed rule excepts "X's writes on its own edges", which as modelled includes such self-grants, so a trusted removal would not drop them either. Closes with step 3.
> Tags: security, perm, permissions

X is admin of A0; A0 is A1's first admin. X grants itself admin on A1 (unseen by n1), then n1 removes X from A0. X keeps admin on A1 by its own grant: losing the path through A0 while another keeps the class is no fall (spec/permissions.md §5.1 step 4), so the audit does not drop the grant (`scenarios::audit_drops_removal_not_self_grant_spec_permissions_5_1`, node `validity::sticky_residue_spec_perm_5_1`). n1 sees it only later, then removes it like any edge. Owner-chain class used to fall here and drop it.

Until step 3 this is inside the interim backdating hole (issues/ownerless-first-admin-backdate.md: X can backdate anything). Step 3 does not close it as written: R's seeds take X's unlisted writes before R "but X's writes on its own edges" (notes/owner-removal-plan.md step 3; roles-model `joint::seeds` excludes every write whose holder is its author), so X can backdate a self-grant on every thing below N and keep them under a node that trusts R. The stated reason for the exception covers self-removals only ("a self-removal never contests R"). Rule (coordinator, notes/owner-removal-plan.md step 3): except only X's writes lowering its own edges. Step 3 changes `joint::seeds` to it and checks it against the disputes model; this issue closes with step 3.

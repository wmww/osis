# A `/secrets` removal's role depends on what the receiver knows of the entry's key
> Summary: a removal names only the entry's dot, and its role comes from the entry's creation key as the receiver knows it (held or dropped creation, or the entry live in the state); a dropped creation's key survives open but not a rebuild or a fresh node, so an honest writer's rotation is valid at one node and invalid at another, and open differs from rebuild.
> Tags: engine, perm, security

Where: core/engine/src/apply/validity.rs `secrets_role`, `resolve_rotation` (keys from `box_keys`, or the entry live in the state; tombstones carry no key, spec/crdt.md §5.6). spec/permissions.md §3 makes the role receiver-dependent ("as the receiver knows it").

Honest repro (ignored test `secrets_removal_dropped_creation_open_equals_rebuild`): writers W1 and W2 both remove read box X (as their rotations do); the admin compacts `/secrets` after W1, drops X's creating body and W1's, then gets W2. Open: `box_keys` (persisted, never shrinks) still knows X is a read box, W2 valid. A rebuild (slow-path open) or a fresh node holding only the snapshot: X is dead in the snapshot, its key unknown, admin, W2 invalid for good. Result: state divergence across nodes and open != rebuild in an honest flow (not only under attack). Impact is convergence and availability (W2's new boxes missing where invalid), not authorization.

Also: `box_keys` keeps the first creation key it sees for a dot; an equivocating writer (two commits creating one dot with different keys, both invalid) can make a third party's removal of that dot need different roles at different nodes.

Not simple to close: treating an unknown key as write reopens the hole at snapshot-only nodes (a removal joined before the entry is seen live kills it, and the dead entry never gives its key). Directions: (1) keyed-map tombstones keep their entry's key, in snapshots and removal records, with a removal acting only on an entry of that key (a CRDT format change; then the role is read from the delta alone, as for puts); (2) a removal of an entry tombstoned in a held valid `/secrets` compaction snapshot touches nothing (converges once every node holds the snapshot; still knowledge-dependent while that snapshot is invalid or dropped).

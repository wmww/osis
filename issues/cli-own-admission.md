# Host refusals: code 12 is ambiguous, `--label` hosts cannot take links, `hosting set` needs a restart
> Summary: Left from the `--admit own` fix (a dedicated host device now admits its person's labels): a node cannot tell "not admitted" from "host full" (both code 12); a host admitting by label ID refuses a link's new K label; a person's other device calls a link's K label stranded ("deposit refused: code 1"); `hosting set` cannot run while `serve` holds the store.
> Tags: cli, node-sync, host, security

Fixed (cause, for the record): the driver's start called `host_restart`, which reset the person `set_person` had stored, so `own` admitted only groups owned by the node itself; the in-process `World` (Manual runtime) never restarts and hid it. Then a group made after the host device started was refused at its first registration (the host device learns its label by syncing the owner's labels) and the node reopened three times at once, then called it Stranded for 60 s; a path refused for now now backs off (notes/sync.md Hosting in the node).

- **Code 12 for "not admitted"**: `admit_label` answers `STORAGE_CAP`, the same as a full host. Under `own` "not admitted" is often temporary (a new label the host device has not synced yet), so the node must keep retrying either way; the client now backs off (`retry_ms` doubling to `resync_ms`) and shows Unreachable, so `init --host X` with an X that will never take the home label times out (exit 6) instead of failing loudly. Smallest change: a new code `NOT_ADMITTED` (14, spec/wire.md §11.2) for a label outside the admission set, retried on the same back-off, reported as its own status (`SyncState::Refused`), and `init --host`/`group sync` saying "host X does not admit this group (yet)" on timeout. Leaks nothing new (the host already refuses), costs one code and one status.
- **Label-ID admission and links**: `own` covers links (a link's K label is owned by the sharer's person and the host device learns it by syncing; checked by both tests). A host admitting by label ID (`--label`, a blind host that never reads the group) cannot: each `link make` makes a new K label (K's home label, spec/sync.md §2) the host was never told about, and grants deposit into recipients' inboxes (their own hosts' business, not this host's). No small rule fits: the host cannot tie K to G without reading G. Options: the CLI prints the K label ID on `link make` (as `status` lists group labels) for the owner to add, or `hosting set --label` takes an owner's public key and admits labels whose genesis registration that key signs (protocol change).
- **"deposit refused: code 1": a person's other device calls a link's K label stranded**: traced in `runtime::own_host_device_in_process_spec_data_model_9`. After `make_link` on Alice's node, the host device (a device of her person) syncs K's label too (K is owned by her person, so it is among the device's groups; K's label names the host). It opens it (`Phase::Open`) but holds no key of the head (`head_keys` all `None`: K's role secrets come from the link's seed, held only by the maker; at the device `group_actor(K)` is the person, it holding no `secrets.0` of K). `pass` then sees no read epoch (`keys.epochs[0].is_none()`) and calls `stranded()`, which deposits a stranded heartbeat signed by `deposit_key(person's deposit seed, K label)`, not the step's deposit key (from K's own seed): code 1, the heartbeat dropped. It repeats every `HEARTBEAT_MIN_INTERVAL_MS` and the device's status shows K's group Syncing forever. Not tied to hosting as far as the code reads (any second device of a link maker should do it; not checked). Fix direction: a node should not sync (or count as stranded) the label of a link actor whose seed it does not hold, or should get the seed (a device of the maker managing redemptions); a stranded heartbeat should be signed by a deposit key that matches the head's (else skipped).
- **`hosting set` while serving** (one process per store, notes/cli.md Not built): `hosting set` cannot run while `serve` holds the store, so admission cannot be tightened without a restart.

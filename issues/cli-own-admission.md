# Serving refusals: admitting by sync ID cannot take links
> Summary: Left from the `--admit own` fix (a node that only serves now admits its account's groups): a serving node admitting by sync ID (`--admitted ID`) refuses a link's new K sync ID.
> Tags: cli, node-sync, host, security

Fixed (cause, for the record): the driver's start called `host_restart`, which reset the account `set_person` had stored, so `own` admitted only groups owned by the node itself; the in-process `World` (Manual runtime) never restarts and hid it. Then a group made after the serving node started was refused at its first registration (the serving node learns its label by syncing the owner's labels) and the node reopened three times at once, then called it Stranded for 60 s; a path refused for now now backs off (notes/sync.md Hosting in the node). "Not admitted" is now code 14 with status `Refused` (was 12, as a full serving node).

- **Sync-ID admission and links**: `own` covers links (a link's K label is owned by the sharer's account and the serving node learns it by syncing; checked by both tests). A node admitting by sync ID (`serving set --admitted ID`, one that never reads the group) cannot: each `link make` makes a new K label (K's home label, spec/sync.md §2) it was never told about, and grants deposit into recipients' inboxes (their own peers' business, not this node's). No small rule fits: the serving node cannot tie K to G without reading G. Options: the CLI prints K's sync ID on `link make` (as `serving ids G` lists a group's) for the serving node's admin to add, or `serving set --admitted` takes an owner's public key and admits labels whose genesis registration that key signs (protocol change).

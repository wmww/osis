# A snapshot can carry forged writes under dots a held commit owns
> Summary: confirmed: a carried write whose dot a held commit owns (a `Commit(C)` source with a held import or commit-form C, a node dot inside a held node-form range) is never judged on its own, so a snapshot by any node that can encrypt for the thing (a reader) adds writes receivers take as the owner's: an extra `(Commit(C), k)` element shows everywhere; another value under an existing node dot and `ts` wins wherever the snapshot arrives before the commit (order-dependent state).
> Tags: security, node, validity

Repros (ignored): `cargo test -p osis-node --test it -- --ignored snapshot_forging_` in `validity.rs`:
- `snapshot_forging_import_dot_changes_nothing_spec_perm_5_2`: a reader of a copy snapshots its `/t/tags` with an extra element at `(Commit(C), hi + 10)` (C the moved tag's origin, its import held) and `Authors` naming the import; a node holding everything applies it and shows `evil`. `carried_of` skips the dot (`owns_source`), so nothing judges it.
- `snapshot_forging_held_node_dot_changes_nothing_spec_perm_5_2`: a reader's snapshot carrying `(a, lo)` at C's `ts` with another value. Where C is held first, the held body's write stays (observed: the state keeps the first-held write of a dot); where the snapshot comes first, it is judged as `a`'s write (valid) and C's real write never replaces it. Breaks Decentralization (state a function of held data) and "malicious readers can only waste storage". A different `ts` is already bad input where C is held (`note_authors`), but not where C arrives later.

Root: two writes with one dot are assumed identical (the CRDT join keeps one), and a carried owned dot is trusted by source or range, not by what the owner holds. Fix sketch: per owning commit, the set of dots (and their stamps/values, or a hash) it holds on each aspect, an index written with the commit and kept when the body drops (like `EdgeParts`); a carried write under an owned dot that the owner does not hold, or holds differently, makes the snapshot bad input where the owner is held, and where the owner arrives after the snapshot it must strip the snapshot's differing writes (a re-judge, so both orders agree). The order case needs the owner to win deterministically: same-dot writes compared by payload, or the snapshot's copy dropped once the owner is held.

# Forged text creation copies join in arrival order
> Summary: Copies of one text element with differing payloads join by the copy order of spec/crdt.md §4.1, but a char is also carried by undeletes (no creation), and the state cannot tell which record a held char came from: two valid snapshots carrying creations of one dot under different `ts` (or one beside a dropped original's residue) plus an undelete can leave holders reading different chars. The lesser such creation (a `prev` position write) is also lost by a snapshot of the state. A forged copy beside a held original no longer can (the original's writes there count for nothing, spec/permissions.md §5.2). Maps are fixed (entries keyed by (dot, key), spec/crdt.md §5.6) but for a transient expiry residue.
> Tags: security, crdt

## Problem
- Text: an undelete repeats the char (§5.7) with no creation, and joins as a copy of whatever creation is held. With two creations of one dot under different `ts` (only a forged copy), the char goes with the greater creation, so an undelete char folded into the lesser one is dropped when the greater arrives, but kept (maxed) when the greater was there first. Repro: `tests_review::repro_forged_creation_ts_undelete_char` (ignored). Taking the max char over all copies instead fails when a reset prunes the lesser creation (and its char) before the greater arrives.
- Honest copies always carry one char per dot, so only a writer forging a creation copy (snapshot), or a char in its own undelete, can cause it; readers write nothing. Since issues/forged-cover.md a valid snapshot's copy replaces a held delta's differing one in the engine (`rebuilt`), so two creations of one dot under other `ts` meet only between two valid forged snapshots, or a forged one and the state's residue of a dropped original; the crdt-level repro (two creations joined directly) is unchanged. Equal-`ts` creation copies with a differing undelete char are order-free (all chars of one creation stamp max).
- Snapshots drop the lesser creation: two creations of one dot under other `ts` (text or list) are both position writes (§5.7 Join), so the lesser can be `prev`, but a snapshot cannot carry it: `PosW` stamped with the element's own dot is read as its creation (§3.3 rule 5; `seq_wire` `push` filters by dot, the model's decoder rejects it). A node bootstrapped from that snapshot breaks a cycle through the element to END instead of to `prev` and reads another order. Repro: `tests_review::repro_forged_creation_ts_snapshot_drops_prev` (ignored). Fix if wanted: carry every `pos` write but the creation's own copy (`is_creation`) as a `PosW`, writer deltas still rejecting an own-dot `PosW` (counter claim); the many `p.0.dot != d` "is the creation" tests (copies, lifecycle, un-merge, remap) would need the same care. Or drop the lesser creation from `pos` at join (top-2 over moves and the greater creation only).
- Map residue (transient): a dot under two keys (forged; since issues/forged-cover.md only between two valid snapshots or a snapshot and a dropped original's residue), one removed. Value erasure folds both into the key-erased record, whose reset then prunes the other key's record too, so a node before the creation's `T` (or before it sees the purge) holding a post-erasure snapshot beside the valued records reads that key gone, while one without the snapshot reads it live, until it erases too. Repro: `tests_review::repro_forged_key_hidden_by_erased_reset` (ignored). Converges at `T`; honest dots carry one key.

## Direction
- No simple analogue of map keying for text chars (keying elements by (dot, char) splits the sequence's identity).
- Or engine-level: one designated carrier per dot (least snapshot ID); `copies_outside` detects the conflict between held snapshots and a rebuild resolves it (`strip_forged`).

# Forged creation copies join in arrival order
> Summary: Copies of one map entry or text element with differing payloads join by the copy order of spec/crdt.md §4.1, but a map key and a text char are also carried by records outside the creation (nested writes, undeletes), and the state cannot tell which record a held key or char came from: a forged copy plus such a record can leave holders reading different keys or chars. Needs per-record provenance, keying by (dot, payload), or an engine-level single carrier per dot.
> Tags: security, crdt

## Problem
- Map: an entry's key is repeated in every record of the entry (resurrection, spec/crdt.md §5.6), so it is carried by the creation and by nested writes of any author. §5.6 joins it as: the key of the creation with the greater stamp; between equal creation stamps the greater key.
  - Repro (osis-crdt, `forged_states` in `tests_laws.rs` with the kitchen-sink type: writers 0 and 1 share source and clock, writer 2 resets): A carries entry d with key 0 and later nested writes; B carries d's creation (same stamp) with key 1 and nothing newer; C resets above B's writes. `(A ⊔ B) ⊔ C` reads key 1 (taken while B's record lived), `A ⊔ (B ⊔ C)` key 0 (B's record pruned first). Two-way joins also differ when one side prunes the other's record before the merge. The forged-copy proptests therefore leave maps out (`sink_no_map`).
  - Also without a prune: A = creation `c1` with key kA, B = value-less (keyless) creation `c2 > c1`, C = a nested-write record (no creation) with key kC: `(A ⊔ B) ⊔ C` keeps kA, `A ⊔ (B ⊔ C)` reads kC.
- Text: an undelete repeats the char (§5.7) with no creation, and joins as a copy of whatever creation is held. With two creations of one dot under different `ts` (only a forged copy), the char goes with the greater creation, so an undelete char folded into the lesser one is dropped when the greater arrives, but kept (maxed) when the greater was there first. Repro: `tests_review::forged_creation_ts_undelete_char` (ignored). Taking the max char over all copies instead fails when a reset prunes the lesser creation (and its char) before the greater arrives.
- Honest copies always carry one key and one char per dot, so only a writer forging a creation copy (snapshot), or a key or char in its own nested write or undelete, can cause it; readers write nothing. Equal-`ts` creation copies with a differing undelete char are order-free (all chars of one creation stamp max).

## Direction
- Key entries by (dot, key): records with another key are another entry (a forged key shows as an extra map key, a pure union). Wire and state change. No simple analogue for text chars.
- Or engine-level: one designated carrier per dot (least snapshot ID); `copies_outside` detects the conflict between held snapshots and a rebuild resolves it (`strip_forged`).

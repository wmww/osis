# Keep-at-most grace under differing death dates may churn
> Summary: Unverified (found by reasoning in the 2b-regress review). Under keep at most 0 after replaced, a body with a live write is dropped at its first death + `AT_MOST_GRACE`; a node that dated a later first death (held a later superseder first) still holds it live and uncovered (a carrier-only snapshot covers none), so `must_carry` has it re-upload what the earlier node deletes, each pass, for up to the gap between the two first deaths (about `AT_MOST_GRACE`).
> Tags: sync, retention

`part_kept` caps kept-ness at keep-at-most minus `MAX_DRIFT`, but `part_live` (spec/sync.md §6 "holding a live write") has no such cap. A dead body cannot loop this way (a node's first death is a held commit's `ts`, so its bound minus `MAX_DRIFT` is already past when the other drops). Check with a Net test like `negative::local_dating_churn` on a body with one live and one superseded write; if it churns, a live part past the node's own keep-at-most minus `MAX_DRIFT` is probably no blob's alone either.

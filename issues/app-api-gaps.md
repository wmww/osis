# API gaps met by the first app
> Summary: What the kit/app prototype worked around in the `osis` API: callbacks only on the dispatcher thread, the item-versus-subgroup sync footgun, `groups_of` missing subgroup edges, deleted things still reported known, remote deletes resurrecting through a pending text session, and untyped, provenance-less revocation outcomes.
> Tags: core-ask, api, owner-call

Repro: app/ and kit/ (notes/app.md Prototype); no failing test.

- **Dispatcher on the UI thread**: callbacks run on osis's dispatcher thread, so every change crosses threads through kit's `marshal` mailbox and a winit user event before the UI can touch widgets. Ask (already in notes/app.md State in osis): a mode where the app pumps the dispatcher on its own thread (e.g. `Config.dispatch = Manual` plus `db.dispatch_pending()` and a wake callback). Not blocking.
- **Item vs subgroup**: the obvious way to make an app group sync, `create(me, Place::In(home))` plus `make_group`, syncs the group's own aspects but not its items (a group's members are its items and its subgroups' members), so notes placed in it stay local; osis reports `NotSynced` per note, which an app that does not subscribe to diagnostics never sees. The app also calls `add_subgroup(home, g)`. Ask: either document this pattern next to `Place::In` (notes/api.md, notes/tags.md "Apps keep an internal synced group") or offer it as one call; consider failing `create(.., Place::In(g))` loudly (or a typed warning on `Committed`) when the placement reaches no synced group.
- Lists: no queries (issues/api-deferred.md): the app re-reads home, its groups and every note's name on each change and holds one `/name` watch per note.
- **Subgroup edges invisible to `groups_of`**: deleting a tag removed its placements but not the `add_subgroup` edges pointing at it, because `groups_of` does not report them; the dead tag came back as an empty unnamed thing. The app (review fix f42bdd41, branch app-review) now finds and removes the edges by scanning. Ask: a way to list the groups a thing is a subgroup of, or delete dropping them.
- **Deleted things still known**: after a remote delete the app cannot tell from the API that the thing is gone (it is still reported as known), so it kept an editor open on it; the app now infers deletion. Ask: a clear deleted/absent answer.
- **Remote delete plus pending typing**: a TextSession with unsaved typing commits after another device deletes its thing, leaving an invisible orphan body (issues/text-session-app-gaps.md covers the local case).
- **Revocation outcome and provenance**: removing a tag from a thing makes the app `demote` the tag's access. It learns that the tag "still reaches it another way" only by matching core's error text (fragile; ask: a typed outcome), and it cannot tell an edge granted by tagging from one granted by hand or by another admin, so it may revoke the latter (ask: edge provenance, or a grant kind the app can tag). Also, when another person removes my thing from their tag nothing tells my side, so the tag keeps its access.

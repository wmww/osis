# A unit's carriage cannot see which sync ID brought a role entry
> Summary: nothing at ingest records which sync ID a commit came under, so a sync unit's carriage (keys open, roles, a read chain's hops) reads every role entry the node holds of a thing it carries, where the spec counts only what is logged under that unit's sync ID; evidence the node holds from another sync ID can widen a unit's read carriage. Fixing it needs per-(sync ID, thing) provenance of role parts.
> Priority: low
> Tags: engine, sync

spec/sync-set.md §2 judges a unit's carriage from its own data: "what a sync ID carries is what some node logged" there. The local part has its log (`sync::local_log`); a sync unit's log is its sync ID's store, held by the sync crate. The engine applies role parts without the sync ID they came under (`Engine::ingest` takes none; openings record an epoch for passing content on, not carriage), so `units::keys_open`/`role_on` for `Ctx::Read(T)` read X's grants whatever brought them, and a read chain's hops (`units::counted`) read every held grant on the hop things. Sync chains are gated (a hop on a thing no other unit gives is none), which closes the case the differential found (`stubs::a_chain_hop_only_evidence_shows_is_no_chain_*`). Open: a read chain through a hop whose role entries reached the node only as evidence under another sync ID, or a reference whose target's grants are evidence only, carries where no logger of T held them.

Fixing it: `Engine::ingest` (and sync's callers) name the sync ID an entry came under; the engine keeps per (sync ID, thing) the role parts it holds under it, dropped as the entry goes (`release_entry` names the commit, not the sync ID: it would need the sync ID too) and as the thing is forgotten; `units` reads X's grants for `Ctx::Read(T)` only from parts under T's sync ID, its own logging (`certs`) among them. LocalPeer and the order/judgment harnesses deliver without sync IDs and would have to name them.

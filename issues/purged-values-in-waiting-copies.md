# Waiting copies still hold purged values
> Summary: Purged values can still sit in waiting copies while something stays away, for good if it never comes: a part and its request both waiting for the thing's record (stated limit, spec/commits.md §5), a blob kept for a junk-held slot, and a waiting snapshot that carries a purged write without being named.
> Priority: normal
> Tags: security, engine, retention

- **Part and request both waiting for the thing's record** (stated limit): a request is judged only once applied (`requests_on`), and a real purge sits on the thing it names, so with the record away it waits too and the part keeps its values in the pending copy until the record comes or the last entry carrying the commit leaves (notes/node-sync.md, Unjudged input). No rule for this now: the whole-commit design (notes/whole-commits.md, in progress) is the likely way out. Tried and dropped: any held request sends the part away, unjudged. A request on another thing, the only one that fires, nearly always has no right, so it was attack surface with almost no honest use, and it added an unflagged read difference when records came before pending grants applied.
- **Blob kept for a junk-held slot** (spec/commits.md §5, "a received blob holding it ... is kept until that copy is judged"; `Engine::spent_copy`): a mixed blob holding a purged part and the possible true copy of another stays while a junk copy holds that slot and its thing's record is away. Needs a hostile junk copy. Tried: forget the blob always and reopen its entry on redelivery. It breaks `copy_kept_for_a_junk_held_slot_of_an_applied_commit_spec_commits_5` and `copy_with_a_purged_part_spent_unless_it_may_be_needed_spec_commits_5`: where no host holds the blob, that part is gone until a holder's new upload. Reverted, since those tests guard this on purpose; the call is which of the two gives way.
- **Waiting snapshot carrying a purged write** (found by reading `pending_drops`, no repro yet): a request by commit name reaches only that commit, so a waiting snapshot holding copies of its values is not named and stays until it applies. A snapshot's stamps can only be read once it decodes, which needs the record.

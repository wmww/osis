# Feature unification is not selection-invariant, so `-p` builds mint second artifact sets
> Summary: After `cargo build --workspace --all-targets`, building each package alone recompiles something for 20 of 21 packages (osis 12 crates, osis-bench 20, osis-transport 9, osis-commit 7, osis-base 6, osis-engine/osis-node/crdt-model 5, most others 1), so `cargo test -p <crate>` would build and keep a second copy of those crates; that is why `-p` is banned (notes/build.md). Making unification selection-invariant would let the dev loop and the release timing checks build one crate instead of the workspace.
> Tags: build, tests

Measured in a fresh worktree (`cargo build -p X --all-targets` after a whole-workspace build, counting `Compiling` lines); the exact list is reproducible with that loop. Cause, per the skill notes/build.md cites: features a dependent enables on a shared dependency that the package alone does not (dev-dependencies enabling features on a normal dependency; a crate's dev-dependency on itself with a test-only feature; per-crate optional features of third-party crates). cargo's `resolver.feature-unification = "workspace"` would fix it outright but is still unstable on 1.99.

Fix: for each package, `cargo tree -e features -p X` against the workspace resolution to find the differing features, then enable them unconditionally in `[dependencies]` (or drop them), until the loop above prints 0 for every package; add the loop to `tools/gate.sh` as a cheap check so it stays that way (it is a few seconds when nothing recompiles). Then notes/build.md can allow `cargo test -p X` in the dev loop and `cargo test --release -p X --test it` for timing checks (the whole-workspace release relink costs 10-38 min under load; one crate's is a fraction).

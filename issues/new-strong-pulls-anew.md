# A new strong pulls its whole unit anew
> Summary: A strong newly reaching a thing in a read unit pulls the unit's sync IDs anew from every source (`units::refetch`), re-listing the whole unit: at a second node this happens for every thing another node makes (3.8 KB of listing for one dependent at 25 entries, 15.8 KB a make averaged over 100 makes: O(n²) over n makes, plus 44 aging rows a make), and for an attach (83 KB at 4 members, 141 KB at 40). The code's exemption ("record learned in this transaction") likely misses the spec's ("record brought in a commit the node held nothing of"). First slimming job (notes/slim-design.md).
> Priority: normal
> Tags: sync, engine, performance

Measured (throwaway probe over a sync-harness world, `World::new(0)`, `add_node`, `pair(0)`; notes/thing-cost.md Survey): node 0 makes a dependent of A held by A's `holds.0`; node 1, A's second node, takes the Stream, then sends a Pull joining A's sync ID from the start (`joins: [(S, None)]`) and gets a PullReply listing every entry of A's unit. Counted `sync IDs pulled anew` 1 per make at node 1, 100 for 100 things in one commit (one Pull, 200 `verify: sync step`). Node 1's sync store keeps an aging stand row per listed entry (`w/`, 44 per make at 100 makes, gone after two tombstone lifetimes). An independent thing made by node 0 is pulled anew alike (PullReply 21 KB of the 29 KB node 1 receives for it).

Likely cause (read, not probed): spec/sync-judgement.md §3 Dropped bodies pulls anew "unless that transaction brought its record in a commit of which the node held nothing when it began". `units::refetch` exempts only a thing in `Core::learned` (its record learned in this transaction), but a reader takes the record of a thing it lacks from the commit's sealed section before the ingest (`OpenedBlob::records`, spec/sync-judgement.md §1 Sealed sections), in an earlier transaction, so the ingest finds the record held and not learned. Probe first: one line at `refetch` per call (thing, whether its minting commit was held when the transaction began).

Fix: the spec's condition: no pull anew where the transaction applied the minting commit of the thing and the node held nothing of that commit when it began (its record taken alone beforehand is no holding of the commit). Then the attach case: a pull limited to the attached thing's entries, if it meets the spec's reason for the pull anew (what was forgotten of the thing is fetched again); else state why the spec needs the whole unit. `refetch_holders` (a new strong to an independent or unknown thing nothing carries: every own and read thing's sync IDs pulled anew) takes the same exemption. Tests: bytes and pulls anew per make at n and 10n things made (none), and an attach at n and 10n members of the enclosing unit and of the attached thing, in default tests.

# A misstating snapshot leaves a key-erased remnant in the state
> Summary: In `validity::misstated_copy_keeps_no_other_record_spec_crdt_4_6`, Carol's node ingesting her own forged snapshot (Bob's dot under "evil") ends with a hidden key-erased record of that dot holding Bob's nested creation and Carol's nested write, which no held body gives. The rebuild check keeps it (it starts from the own state, spec/crdt.md §4.6), so the state depends on arrival order. Reads alike so far.
> Tags: security, engine, crdt

Found by a stronger form of the rebuild check (review of rebuild-check): when every held part of the aspect is stored whole, compare the state with the join of the bodies alone (no own state). Over osis-engine lib and osis-node `it` it flagged only this case (and `keys_tests`' forged-admin-keyset hook, which writes the cache directly on purpose). The experiment: a `NO_OWN` switch making `rebuilt` skip `current`, used when every `by_aspect` commit `holds` and `stores_part` the aspect.

At Carol (peer 2, `ingest` at validity.rs:1013) the state has `(dot :3, key None)` holding `a` (Bob's `:4` creation, no value) and Carol's `b = "2"`, beside the live "evil" record of `:3` and Bob's "late" record (no creation) holding Carol's `b`. The bodies alone give the last two, not the key-erased one. Likely `strip_forged` on the state (`rebuilt`'s `strip_state`) moving Bob's "late" record into the key-erased record instead of removing his writes as a rebuild from bodies does. spec/crdt.md §5.6 Live reads a live record joined with its dot's key-erased record, so "evil" may read Carol's `b` (see issues/vouched-key-erased.md, first bullet: same shape via expiry). Fix candidates: strip the state's misstated dots the way the bodies are stripped, or make the stronger check the rule where every part is held whole.

Still there after drop-rejoin items 1+2 (leftover-bodies): the bodies-alone rebuild at Carol lacks her nested `b` write the state holds.

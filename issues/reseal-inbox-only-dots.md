# Re-seals at the end of a complete pass break epoch establishment
> Summary: Wiring `Engine::reseal_due` at the end of every complete pass (spec/permissions.md §3) made two writers re-seal each other twice in osis-node `briefly_online_devices_spec_sync_6`; afterwards writer B never established the admin's next write epoch (held, not established), so it stamped nothing and its later write never reached the server. Not wired until fixed; the stranded-heartbeat trigger (`reshare`) is.
> Tags: flows, keys, sync

- Repro: in `crates/osis-node/src/sync/pass.rs` `reseal`, call `self.engine.reseal_due(&a, &Passed)` (a `SyncState` answering true: the pass already checked `complete_pass`) and `take_done` it; run `cargo test -p osis-node --test sync briefly`. Both nodes produce re-seal commits (listed `inbox_only`) at each online session; B's head keys then show `writer false` at the admin's rotation step, epoch 2 held but not established.
- Likely cause (not confirmed): a re-seal is a local commit on the actor's `/secrets` that only its recipient receives (by inbox). Its box entries' dots exist at the re-sealer alone; a later rotation written there removes them, and every other node holds that rotation waiting for removed keys it never saw (notes/node.md, Established epochs), or the re-seal changes the re-sealer's own establishment. Also, why `reseal_needed` fires at all here (the members were boxed by the test's `rotation` helper) is worth checking: possibly a box format the trigger does not recognize.
- Fix direction (flows/keys): re-seal commits must not leave state others cannot reproduce (write them so later removals never reference their dots, or let the re-sealer forget them after delivery), and the trigger should not fire for members boxed at the current epoch.

# Registered steps and claim sets bypass every server cap
> Summary: Register needs no open and no rate limit, and `push_step` counts nothing toward the label or node byte totals. Anyone can register a genesis step for a label of their own and then child steps without end, each with a claim set of up to about 9 MiB that the server keeps for `MEMBERSHIP_KEEP` (90 days) after it is superseded. So any stranger fills the server's disk past `max_bytes`, and replication copies it to peer servers. High.
> Tags: security, server, proto

- `ServerConnection::register` (core/proto/src/server.rs:574) checks only `admit_label` for a genesis step. `BackendStore::push_step` (core/server/src/store.rs:1297) writes the step, the `V`/`W` index rows, the `C` claim-set row and a Head log record. `Tx::before` carries the old entries and bytes, and push_step changes neither, so totals and the `cap_*`/`max_*` policy never see these bytes. Steps (`S`, `V`, `W`) are kept for good. Claim sets go only `claim_keep_ms` after their step is superseded.
- Cost to the attacker: one signature per step, with keys it generates itself. A claim set is up to `MAX_CLAIM_SET` (`MAX_MESSAGE` − 64 KiB). At line rate that is GB per minute, kept for 90 days. `max_labels` caps the label count but not the steps per label.
- `Replicator` replays each Head record with its claim set to every peer server (notes/sync.md Implementation (osis-server)), so peers fill as well.
- This is not the deferred "abuse limits" item (notes/sync.md Open): the existing caps are the accepted bound, and this path skips them.

Fix direction: count step and claim-set bytes toward the label's `cap_bytes` and the node's `max_bytes`, and refuse with 12 past them. Rate-limit Registers per label like deletes. Cap the steps (or claim-set bytes) held per label within `MEMBERSHIP_KEEP`, with the cap derived from rotation cadence (notes/arbitrary-values.md). An honest label steps once per rotation. Then say in spec/sync.md §5 that registrations count toward storage caps.

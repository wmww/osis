# Invalid commits' headers pile up
> Summary: a commit known only for parts dropped as invalid is forgettable in the engine, but a node keeps it while it knows an entry of it, and entries of invalid bodies stay in its own store and are never deleted at peers; and a commit carrying a purge request is never forgotten, invalid or not. So a member writing past its rights (a reader, a removed writer, a non-right-holder's purge requests) leaves a header (about 690 B) at every node that pulled it, for good.
> Priority: normal
> Tags: engine, sync, retention, security

- **Purge-request commits**: `Engine::forgettable` returns false whenever `view.purges` (spec/commits.md §5 Forgetting: "a commit carrying a request" is kept). A purge request judged invalid (signer lacks the right, spec/permissions.md §6) is kept too, so anyone who may log under S can grow every reader's store by one header per request. Rule to consider: a request commit every part of which dropped as invalid goes as any invalid commit (its request was never in force, so forgetting it changes no read); a request in force stays.
- **Entries kept**: osis-sync keeps an own-store entry of a body dropped as invalid (`read::judge`, `Act::Take`: the refetch source once it turns valid), and `read::judge::local` keeps a commit while an own entry is held, so the engine's forgettable never fires for a pulled invalid commit. Sources keeping S unread never delete invalid bodies either (issues/invalid-junk-kept.md). The engine test forgets by hand; no sync-level test shows an invalid commit forgotten.
- Both are bounded by what may be logged under S (the per-sync-ID caps at nodes keeping it unread), not by anything a right holder can do. Options: drop the own entry of a body invalid at every key a re-grant could reopen (then a re-grant restores only what another holder keeps, as spec/permissions.md §6 already says for bodies); or accept and state it as a limit in spec/commits.md §5.

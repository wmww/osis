# A redeemer opens K but cannot apply K's commits
> Summary: a link's first contact opens K by L's static entry and takes the head's entry box, but K's commits do not apply at the redeemer (no certificate copies of K's author chain or L's record under K's sync ID; a commit thrown out as Awaits is never fetched again), so the join never happens; the differential still exchanges contacts by hand (`history::introduce`).
> Priority: normal
> Tags: sync, engine, tests

What works (core/sync/tests/it/links.rs `a_link_opens_k_by_its_static_entry_spec_sync_inbox_6`): K and the seed thing are items of the sharer's D (`create_link`), so the sharer reads K's sync ID and shows L's static entry; the redeemer follows the link (`Engine::follow_link`: K's sync ID read in its sync set from the link text, L's signing key in `ReadCredentials::acting`), dials the sharer by the link's hints, tests L's static entry, gets the head's entry box and path (`NodeHolds::grant`), verifies the path and takes the box's secrets (`take_grant`), opens K and pulls its entries, which open under the read secret.

Missing (`a_redeemer_joins_k_spec_permissions_7`, ignored):
- **Chain certificates under K's sync ID.** K's commits are signed by the sharer's account, and K's roster names L; the redeemer holds neither's record or `keys.0`, so ingest answers `Awaits` (unknown author / created) and keeps nothing. K's sync ID must carry certificate copies of its commits' author chain and of L's `created.0`/`keys.0` (spec/permissions.md §4, spec/sync-inbox.md §5 contact card: the account's record and `keys.0` as certificate copies). The engine seals no certificate copy yet (`sync_bodies` gives `certificate: false` only; the inbox module's `log_chain` is not built). Confirmed by hand: with the sharer account's and L's creation commits handed to the redeemer first, K's commits apply.
- **Awaits fetched again.** K's `created.0` commit predates K's sync ID and is logged under it later than K's role commits, so the redeemer pulls those first; each is thrown out as `Awaits` and nothing fetches it again once K's record arrives (apply/mod.rs `Ingested::Awaits`: "node-sync fetches it again"). Even with the chain handed, L's edge did not reach K's roster at the redeemer.
- Then: the join (`Redemptions` writes it once K's roster lists L), its deposit taken at the sharer, the link unfollowed once the join is held; osis `import_contact` accepting the profile (spec/sync-set.md §4: it records the contact but files nothing); `history::introduce` replaced by contact cards (each node imports every other's card: redeem, then the profile filed as a subgroup of D); osis two-node tests and libs/chat link joins un-ignored.
- `take_grant` takes the box's secrets before the answer's signature is checked (`replier_proved` checks it after): a forged box can only add secrets that name their own epochs, which establish nothing, but the order is the spec's reversed.
- A link lists relays only (spec/wire.md §10), so a sharer with no relay is reached by a link only over a LAN.

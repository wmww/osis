# A chat's record in a content commit
> Summary: Chat creates C in its rules commit (`create()`, `required.0^`, settings, then `sync`), so C's record travels in a content commit and a joiner re-reads each pending role commit on C about twice as often as with a record-alone role commit; the record-alone order (draft, `sync`, then the rules) instead loses a link joiner's posts after another joiner leaves. Two findings, one cause to pick.
> Tags: chat, engine, sync

**Cost.** Joiners fetch role commits first (spec/commits.md §2); one per earlier member waits on C's record. Made by a record-alone role commit, a joiner at m=5 members reads pending commits 11 times (`scale::joiner_reads_each_pending_commit_few_times`, bound 2m+1); with C's record inside libs/chat's rules commit, 23. The sim test makes its chat record-alone so it keeps measuring members' records; chat itself pays the 23. The public API has no record-alone create: a draft persists by a content commit (`Write`), or by records alone only inside `sync`/`grant`/`make_link` (`Osis::persist`).

**Bug seen with the record-alone order.** libs/chat `create` as: `create()` draft, `sync(c)` (persists it by records alone, gives the label), then the `required.0^` + settings commit. `flows::link_joiner_leaves_spec_perm_7` then fails deterministically: after joiner B leaves (its edge on K), joiner D's node writes `keys.0`/`secrets.0` on C twice and posts; none of those three commits reach the maker A (A's status says synced). With the rules commit before `sync` the same test passes, and A writes a further `label.0` after the leave that it does not write in the failing order. Likely in the label/inbox handling of a thing labeled while plain (notes/permissions.md, One inbox rule, `rotation::own_secrets`); not chased.

Options: fix the bug and make chat create record-alone first; or make `apply::waits` cheap for a record arriving in a content commit (then any app's shared thing benefits).

# A rejected epoch start can outlive the write that caused its rejection
> Summary: The walk rejects an epoch start found inapplicable and keeps it rejected even after the write that made it inapplicable is dropped, so a snapshot that the spec's fixed point would take as the epoch start is ignored until a roster snapshot above repairs it. Same family as sticky drops (models/tla/membership M2).
> Tags: permissions, tests

spec/permissions.md §6: the epoch start is the newest snapshot whose author had owner-chain authority at its time "by the timelines above N". osis-perm (`walk.rs`, notes/permissions.md "Epoch starts") chooses an applicable snapshot, rebuilds D from scratch, and rejects a chosen start found inapplicable until a start changes on a thing authority may come through (this ends cycles). Example (`crates/osis-perm/tests/roster.rs` `rejected_start_residue_spec_permissions_6`): K owns P, P owns G; n1, n2 admins of P. n2 snapshots G at 6; n1 removes n2 from P at 4; K removes n1 at 18 with a frontier missing n1's removal. Walk: n1's removal drops, G's snapshot becomes the start, D is rebuilt, n1's removal applies again, the start is rejected, then n1's removal drops again and the rejection stays. Without the dropped write the snapshot is G's start; a re-snapshot of P (whose ledger has no demotion of n2) repairs it.

Found by the random neutrality runs (`snapshot_resnapshot_neutral_large`, sample stream changed when the snapshot model began generating same-key writes); the runs now tolerate it like sticky residue (`common::rejection_residue`: only undoing). About 1 in 10^4 random snapshot-model histories (3 of 30k). A fix would have to keep cycle termination: e.g. un-reject a start when the write that made it inapplicable is dropped.

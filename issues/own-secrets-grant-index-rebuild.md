# A plain thing's own-secrets grant: reopened and rebuilt secrets index differ
> Summary: after a grant flow gives a plain thing secrets of its own, a fresh node that receives the commits (as made) and reopens holds the thing's read and write epochs but not the admin epoch of the own-secrets rotation (keyset only, no secret); a rebuild of the index holds it. Owned and ownerless plain things alike; reproduces on main.
> Tags: keys, engine, tests

Found by the ownerless arrival-order harness (`order::repro_arrival_order_ownerless_large_spec_permissions_2`, about 10 of 60 seeds at offset 31517000). Smallest shape, in osis-node `tests/it/order.rs`: `check(seed, &vec![NewTop { by: 1 }, Grant { by: 1, t: 1, holder: 2, role: Role::Write, until: None, invite: None, flow: true }], Cfg { sync: true, ..LARGE })` fails at seeds 31517009, 31517014, 31517021, 31517024 (the ownerless twin `Ownerless { by: 1, under: None }` then an aimed `GrantFlow` at 31517003, 31517011, 31517017, 31517018) with "as made: the index reopened and rebuilt differ: index Table("secrets")". Main's binary fails the same way on the harness's seed 31517006 history (`OSIS_ORDER_SEED=31517006`). Needs `sync: true` (fresh nodes syncing things, `with_syncs`); the existing order harness never draws a grant through the flow, so it never reached this.

Which side is right is not settled: the rotation's keyset names all three roles, so the rebuild's view looks right and the incremental path (`apply::keys::after_join` / `revalidated` / `Core::observe_keys`, which updates only an existing `secrets` entry) misses the admin epoch.

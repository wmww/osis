# A removed admin can take a thing back by backdating
> Summary: A removed admin signs a removal of its remover stamped before that remover acted; the walk applies it and voids the remover's write at every node that has not sided against it. The walk settles the fight per node by its trust set (spec/permissions.md §5.1 Trust set, built), but no node records a side yet: until notes/owner-removal-plan.md step 4 (a default of first received at detection, choices, warnings) every node's trust set is empty and reads as the plain walk. Interim, stated.
> Tags: security, perm

n0 first admin, grants n1 at 1; n1 removes n0 at 10; n0 then signs "remove n1" stamped 5. Result: n0 admin, n1 out, also on things below (osis-perm, `scenarios::further_backdated_revoke_cancels`). n1 can answer stamped 3, n0 with 2; n1 cannot stamp before its own grant, so n0 wins the race. Frontiers do not help: n1's removal never applies, so it audits nothing.

The walk raises the dispute (n1's removal, n0) and, on a node trusting it, seeds D with n0's backdated removal: n1 stays admin above and below (`scenarios::backdated_takeback_settled_by_trust_spec_permissions_5_1`). What is missing is the node taking that side: `Timelines::set_trust` is called by nothing. Step 4 closes this: a durable trust store, the default side (first received, recorded at detection: a node that saw n1's removal first keeps n1), choices and warnings. Accounts included: a recovery key is an admin by a plain edge, so a stolen node that got there first can backdate its removal too.

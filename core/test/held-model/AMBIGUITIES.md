# held-model: spec ambiguities
> Summary: Every place the spec left a choice, contradicted itself or said too little while building held-model, the model's choice, and how each was resolved against the engine (1-39 resolved; 25-39 from undo, roles beyond one edge, waits and required retention; 40-44 from apply without atomicity and timing; 58 signals).

Each entry: the spec text, the problem, the model's choice (and where in the code), then **Resolved**: (a) spec fixed to the intended rule (the engine's), model matched; (b) engine wrong, issue filed; (c) a question for Tess (an issue tagged `tess-call`), model's choice kept. Each rule settled by reading engine code names its engine example test.

Entries 8, 14, 19, 20, 34 and the "counted held" of 37 concern spec/commits.md §4 clauses (atomic apply, counts as held, a thing's wait holding the commit) that whole-commits step 3 deleted; the model dropped them with it (held-model-3).

Entries 1, 2, 20, 23, 44 and 45, and the keep-at-most parts of 6, 9 and 38, concern keep-at-most bounds and invalid bodies counted dead, which the history modes removed (54-56: purge on replace is a writer's cover, no node drops on its own but expiry); the code and tests they cite are gone. Entries 6 and 42 concern the own state counting as a body and what a dropped snapshot gave staying in it; the state is the join of the held bodies (spec/crdt.md §4.6), so neither rule exists.

## Headline

1. **An invalid delta's hidden anchors and keep at most.** spec/commits.md §5: "A write of a delta invalid here does not die ... But under keep at most 0 after replaced ... each counts dead at its own `ts`"; spec/crdt.md §4.6: "Seq elements created by an invalid delta keep their record and creation write (anchor) as a content-less hidden anchor"; §5 live write: "including element records the state keeps only as anchors". Nothing says whether those hidden anchors make the invalid body *live*. If not, the body drops as invalid with no carrier and others' valid inserts anchored on it vanish (the model's drop property found this; test `invalid_text_body_dropped_as_invalid_keeps_its_anchors_spec_commits_5`). Choice: they are live writes, so the drop needs a carrier and the anchors stay in the state (`model.rs`, deaths loop, `crdt::holds`).
   **Resolved** (a), then superseded: an invalid delta's elements leave nothing in the state (spec/crdt.md §4.6, §6.1: what anchors at them sits at a virtual anchor), so dropping its body loses no valid insert.

2. **Keep-at-most deadline.** spec/commits.md §5: "By the bound every node MUST drop the body"; under 0 after replaced the bound is the first death, dropped as dated whatever the clock, a live write's carrier first. Choice: `MustDrop` from the bound (0 for a relative one with a death), no `MayDrop` for keep at most.
   **Resolved** (a) The engine drops at the bound (`judge_at_most`: a dead body in the killing transaction, a live one by a timer due at once after node-sync's carrier); tests deletion.rs `erasing_edit_carrier_at_once_spec_commits_5`, retention.rs `keep_at_most_zero_late_body_dropped_on_arrival_spec_commits_5`.

3. **Re-grant revives everything since the first grant.** spec/permissions.md §5.2: "An actor holding the required role in the timeline's final state ... is re-granted: each of its writes ordered at or after the first point it held that role is valid again, including those in the gap." "First point" could be the first ever grant or the start of the current grant; only the first reading revives "those in the gap". Choice: first ever. Consequence: any later re-grant undoes a demotion's omissions and a purge-right loss (§6).
   **Resolved** (a)+(c) The engine revives from the first-ever grant (perm `Timeline::first_held`; perm content.rs `frontier_decides_pre_revoke_edits`), deliberate per notes/permissions.md. Spec says "first point it ever held".

4. **A frontier validates writes made without the role.** spec/permissions.md §5.2: "Otherwise it is valid iff the frontier of a valid explicit demotion of X below write on N lists its commit, whatever their order". This does not require X to have held write when it wrote; a demoter lists every received commit of X (§5.1 Listed), unauthorized ones included. Choice: literal (valid). Likely unintended (`roles.rs`, `valid_as`).
   **Resolved** (c) The engine is literal too (perm `delta_valid_uncached`), and writes after an `until` need it (perm content.rs `until_gap_write_finalized_by_frontier`). Question 7; the model stays literal.

5. **Death dating: first held vs earliest.** spec/commits.md §5: "a superseded write's death at the `ts` of the first superseder the node held, never earlier than the death" (arrival order; and "never earlier than the death" is circular) vs spec/crdt.md §4.8: "the earliest `ts` among the valid writes the node holds that supersede it ... the order of arrival does not matter". Choice: §4.8 (`model.rs`, deaths).
   **Resolved** (a) The engine dates at the first superseder held (Tess's decision, notes/engine-retention.md; retention.rs `deaths_dated_from_first_superseder_held_spec_commits_5`), the earliest only after a recompute. spec/commits.md §5 now reads non-circularly (never earlier than the §4.8 death; a lower-`ts` superseder held later moves no date). The model has no arrival order, so it dates at the earliest, the date a recompute gives: an engine date may be later, never earlier (ASSUMPTIONS.md).

6. **Own state "counts as a snapshot" vs un-merge.** spec/crdt.md §4.6: "The node's own current state counts as a snapshot it holds, so live writes of bodies dropped under keep-at-most survive" and "A valid snapshot's copies of those writes stay". Read together, the own state would keep invalid writes forever. Choice: own-state writes are removed when their own delta is invalid, like a delta body's; only real snapshots vouch (`model.rs`, state building).
   **Resolved** (a) The engine strips the own state of invalid deltas' writes; only held valid snapshots vouch (`apply::atomic` `rebuilt`, `Unmerge::strip`). spec/crdt.md §4.6: the own state counts as a body and vouches for nothing.

7. **Which records are live writes.** spec/commits.md §5: "any write of its deltas the node's state holds by dot, including element records the state keeps only as anchors ... but not an element's or entry's tombstone (it holds the remover's reset, not the creation)". Unclear for (a) a text record whose creation a reset pruned, held for others' flag writes on it, and (b) the remover's own surviving reset or removal. Choice: both live. Consequence: a `remove_aspect` body stays live until a later reset.
   **Resolved** (a) Both live in the engine (`holds_owned_write`: a `Rec::Seq` is never a tombstone; a tombstone's reset is its remover's write; deletion.rs `dropped_snapshot_waits_for_lost_carrier_spec_sync_7`). Spec live write rewritten (resets and every sequence record count). The reset case: retention.rs `remover_reset_is_live_until_superseded_spec_commits_5`.

8. **"Author lowered" has no ordering.** spec/commits.md §4: a delta counts as held when "the node holds one of the following on the delta's thing ... with a frontier that does not list the delta's commit": no requirement that the role commit be ordered after the delta's commit. An old demotion makes every later missing delta of a since-re-granted author count as held, so its commit applies without it. Choice: literal.
   **Resolved** (a) The engine reads no ordering (`apply::gates::removed_author`, its doc accepts the cost; parts.rs `missing_delta_of_a_removed_author_any_order_spec_commits_4`). Spec says "whatever their order against the delta's commit".

9. **When a leftover may go.** spec/crdt.md §4.7: the leftover is "a held body like any other ... that uploads nowhere"; spec/commits.md §6: "every node holds them value-less, the body ... as its leftover, whatever the delta's keep-at-least bound". Nothing says when an expired or purged delta's leftover is dropped (keep at most? covered?). Choice: a leftover is terminal in the model (`Fate::Leftover` before any bound).
   **Resolved** (a) A bare leftover (no value of its own) is never dropped (`judge_at_most`, `drop_part_for` on `Meta::bare`); one stripped only of carried copies is a body like a whole one (`Meta::valued`). Spec §5 Dropping a body says so. Model: a `Copy` leftover now takes keep bounds and covering (judged stripped); test `copy_leftover_drops_at_its_bound_spec_commits_5`; engine: retention.rs `bare_leftover_stays_copy_leftover_goes_spec_commits_5`.

10. (Retired.)

## Others

11. **Covered with value-less copies.** spec/commits.md §5 Covered: covering is the canonical-bytes join test, yet the MUST beside it says "(a value-less copy matches)". Under spec/crdt.md §4.1 the valued copy wins the join, so a snapshot holding a value-less copy of a body's valued write fails the test. Choice: the join test decides (not covered).
   **Resolved** (a) The engine's join test decides (`retention::snapshot::covered`). Spec: a value-less copy is allowed under the MUST, and the join then leaves a valued body uncovered. Engine: retention.rs `valueless_copy_does_not_cover_valued_body_spec_commits_5`.

12. **"Explicit demotion below write" is not defined in §5.1's terms.** spec/permissions.md §5.1 defines demotion as a class fall (edge admin, invite); §5.2 uses "explicit demotion of X below write on N". Choice: an applied edge write by another author taking X's role from at least the need to below it (`roles.rs`, `demotions`).
   **Resolved** (a) The engine's definition is notes/permissions.md's (perm `walk.rs` `audit_fall`): an explicit write by another author that demotes X (§5.1 step 4) from write or above, the edge as restored. spec/permissions.md §5.2 now defines it. The model's single-edge version is that rule within its scope (no actors, until or invites).

13. **Applied or held purge request.** spec/commits.md §5: "Every node applying it drops"; §5 A waiting part under a purge and §4 Purged: "a held purge request". Choice: an applied request for applied targets; a held, unparked one for waiting parts and atomic apply.
   **Resolved** (a) The engine needs an applied request everywhere (`purge::apply_request` registers only on apply; shred.rs `purged_while_pending_unrecoverable_spec_commits_5`). Spec: "applied" in §4 Purged, §5 waiting part, Purge. Model: requests count only once applied.

14. **Possible admins from parked commits.** spec/commits.md §4: "by what the node holds of any validity and whatever followed". Parked commits are held but "counted as not received" (spec/crdt.md §2.2). Choice: parked commits give nothing.
   **Resolved** (a) The engine builds them from applied role commits only (`Held::ever_admins`, filled at apply). Spec §4 says so. In the model a role commit applies iff a part is held and it is not parked, so its set was already that. Engine: retention.rs `parked_grant_gives_no_purge_right_spec_commits_4`.

15. **Expiry as a death date.** spec/commits.md §5: "an expiry dates none" vs spec/crdt.md §4.8: "It dies at the earliest `ts` ... or at T". Choice: T counts once passed; no effect, since the body is then a leftover.
   **Resolved** (a) The engine never dates T (`hold_valueless` makes a leftover with no deaths). spec/crdt.md §4.8: T by expiry dates no body. Model: no death at T.

16. (Retired.)
17. **Two rights for a covered drop.** spec/commits.md §5 Between the bounds: "the covering snapshot's own commit holds the right over it, as a purge request would at that snapshot's key"; spec/sync.md §7 adds "it may purge the body" (the node itself, at no stated key). Choice: both; the node's right judged after every held key.
   **Resolved** (a) The engine needs both, the node's judged now (`bounds::drop_from`, `purge::snapshot_right`; retention.rs `snapshot_right_any_arrival_order_spec_commits_5`). spec/commits.md §5 Between the bounds adds the node's own right. Engine, the node's right alone: retention.rs `covered_drop_needs_the_nodes_own_right_spec_commits_5`.

18. **Purging a snapshot by aspect history.** spec/commits.md §5: a request names deltas "by commit, by a whole aspect history, or by author on an aspect"; "A snapshot a request names itself ... its body is dropped". Whether "a whole aspect history" includes snapshot deltas is not said. Choice: yes, judged by the snapshot's retention (`writer`) and its author.
   **Resolved** (a) The engine names them (`purge::reaches`, right by the snapshot's retention and header actor). Spec says so; naming takes nothing of a snapshot, so it shows only as a dropped snapshot's history entry reading purged (retention.rs `aspect_purge_names_its_snapshots_spec_commits_5`).

19. **A content commit with no part held.** spec/commits.md §4 Pending: "the node holds no part of it, and a thing of it waits or a delta of it is missing and not counted as held". With every part missing but counted held (expired, purged, under a snapshot), the commit is not pending, so it applies as a header alone, and counts as "another commit with a delta on the aspect" for other parts' keep at most. Choice: as written.
   **Resolved** (a) The engine applies such a commit as a header and indexes every aspect it lists (`apply::examine`, `atomic::index_commit`; shred.rs `partless_commit_pends_on_its_thing_spec_commits_4`). Spec §4 says so.

20. **Past keep at most counts any later commit as the first death.** spec/commits.md §4: "the first death taken at the earliest such commit's `ts`": a later commit on a map or text aspect need not supersede anything in the missing delta. Choice: as written (the late live part joins on arrival, §4).
   **Resolved** (a) The engine takes any later commit on the aspect (`gates::at_most_bound`; waits.rs `missing_part_waits_for_a_later_commit_spec_commits_4`). Spec: "whether or not that commit supersedes a write of the delta".

21. **Map presence after an entry expires.** spec/crdt.md §4.3 counts "its children's writes", so another delta's write inside an entry whose creation expired keeps the map present: it reads `{}`, not absent (test `expired_key_copy_in_another_body_is_stripped_spec_commits_6`). Choice: as written. (The writer MUST have given that write the same expiry, spec/crdt.md §4.7, but a receiver cannot rely on it.)
   **Resolved** (a) The engine reads `{}` (waits.rs `expired_entry_goes_with_nested_write_alike_spec_crdt_4_7`; notes/crdt.md). spec/crdt.md §4.7: a composite holding only such hidden writes stays present and reads empty.

22. **Stripped copies asked for again.** spec/permissions.md §6: "A held body stripped for carrying a purged value is asked for again with any such fall". While asked for, does the stripped copy still join? Choice: yes, value-less (it only hides).
   **Resolved** (a) The stripped body stays held as its leftover: its value-less copies only hide, and the valued copy wins wherever one joins (spec/crdt.md §4.7 Join), so a fall never takes a cover's other writes (`purge::rejudge_purges`; spec/permissions.md §6). `Part::stripped` records whose values `act` stripped.

23. **An invalid snapshot's copies' deaths.** spec/commits.md §5: "A write of a delta invalid here does not die". For an invalid snapshot carrying copies of valid writes that do die, the model treats its writes as not dying (fall under 0 after replaced).
   **Resolved** (a) The engine counts an invalid snapshot replaced at its own `ts` and nothing else (`deaths::date_falls`; retention.rs `invalid_snapshot_recomputes_no_deaths_spec_commits_5`). spec/commits.md §5 says its carried writes do not die.

24. **A purged or expired delta's own body.** spec/commits.md §5 Purge said a node "drops ... the named deltas" and "holds every body carrying their values as its leftover", leaving open whether the named delta's own body is dropped or held as its leftover. Choice: `Fate::Leftover(Purged | Expired)`.
   **Resolved** (a) spec/crdt.md §4.7 (the body goes, "the node holds the body's leftover instead") and commits §6 already said leftover for expiry; commits §5 Purge now names the delta's own body too. The engine holds it as its leftover (`Meta::stripped`); the adapter (osis-node `tests/it/held.rs`) had read every leftover as dropped (`body_not_dropped`) and accepted either.

## held-model-2 (undo, roles beyond one edge, waits, required retention)

25. **Self-removal "when either holds".** spec/permissions.md §2: "Such a write is a self-removal when either holds; otherwise it is an explicit demotion: it lowers the author's own edge ... admin on X is the author's only authority for it". Read literally, an edge admin lowering its own edge is a self-removal, which contradicts §5.1 step 2 ("a write lowering another holder's edge by an author that also has edge-admin authority ... is an explicit write"). Choice: both must hold; an author with edge-admin authority on the target writes explicitly (`roles.rs`, `decide`).
   **Resolved** (a) The engine reads "either": lowering one's own edge is always a self-removal, the only-authority condition is for another holder's edge (perm `walk.rs` `judge`; notes/permissions.md, decided at review); §5.1 step 2 speaks of another holder's edge, so no contradiction. Model changed (`decide`: self-removal first). Engine: retention.rs `edge_admin_removing_own_edge_is_self_removal_spec_perm_2` (a frontier-less removal: as an explicit write it would be a finalize, ignored on an unended edge).

26. **Finalize or self-removal through an actor.** spec/permissions.md §2 Finalize: "a removal of another holder's edge carrying no frontier"; Self-removal: "a node with admin on actor X may always remove X's edge". A frontier-less removal of X's edge by an admin of X fits both. Choice: a self-removal (it applies whatever X's `until`); finalize only when the author has no admin on the holder (`decide`).
   **Resolved** (a) The engine checks self-removal first, then finalize for any other frontier-less removal that lowers, admin on the holder or not (`walk.rs` `judge`). Spec Finalize: "that is not a self-removal". Model changed: finalize no longer excludes an admin of the holder.

27. **An undeleted element's creation stays dead.** spec/crdt.md §4.8 Revival: "Un-merge (§4.6) is the only way a dead write revives"; "its element deleted". An insert whose element a delete superseded, then an undo undeleted, stays dead at the delete's `ts` though the element shows again; under keep at most 0 its body drops (with a carrier, the creation is still live). Choice: literal (`crdt::supersedes`).
   **Open** The engine judges a text creation by its element's winning flag (crdt `winners.rs`): under a later undelete it wins again and dates no death, later than the model (kept longer; the harness tallies `keep-for-D dated later`). Re-deleted, it dates at the earliest delete held. Model unchanged.

29. **The state before an undone commit, of a held set.** spec/crdt.md §4.6 says what an undo should restore, not where the undoing node gets the state before the commit. Choice: the state from the held commits ordered before the undone one by `(ts, ID)`, judged as the node judges them now, own-state writes of those commits included, values held value-less by the undo's time or purged stripped (`undo::buffer`).
   **Resolved** (a) A writer-side choice: the engine uses its saved pre-commit state for a recent local commit, else the valid held parts ordered before by `(ts, ID)`, no own-state writes (`undo::undo_in`); a receiver judges the undo commit like any content commit. spec/crdt.md §4.6 says a receiver never derives an undo's writes again. The model's buffer only drives the generator (`undo::undo`); not compared.

30. **Whose authority judges an acting delta.** spec/commits.md §4: "Each delta is judged on its own, by its author's authority"; spec/permissions.md §5.2: "A delta by actor X on thing N is valid if X held write" and Acting: invalid "unless a delta of its author on that actor needing write ... would be valid". Choice: the header actor is X, and the author must also pass the acting rule (`Timeline::valid_delta`).
   **Resolved** (a) The engine judges every delta by its author node, the actor only through the Acting check (`apply/validity.rs` `Judge::part`, `acts_for`; notes/permissions.md: "the author's rights decide"; validity.rs `acting_valid_once_grant_arrives_spec_perm_5_2`). spec/permissions.md §5.2 says so. Model changed (`Timeline::valid_delta`).

31. **The `author` purge right under acting.** spec/permissions.md §6: "author: the actor the commit's header names while it holds write on the thing, acting through any node with write on it" and "when it acts for another actor (its header actor), so did that actor". Choice: the request's actor is the delta's header actor and both the request's author and actor hold write; `admin` and `writer` need both author and actor to hold the role; spec/commits.md §4 Purged likewise for possible holders (`Timeline::right`, `Possible::right`). `PurgeItem::Author` matches the delta's author node, not its actor.
   **Resolved** (a) The engine: each signer (author, and actor when it acts) holds the right on its own; `author` is held by the delta's header actor and any node with write on it while the actor has write on the thing (perm `purge_stands`, retention `purge::holds_right`; notes/permissions.md Purge author right); `PurgeItem::Author` names the delta's header actor (spec/wire.md §4). Spec §7 `author` reworded. Model changed (`Timeline::right`, `names`).

32. **An actor's role on itself.** spec/permissions.md §1 Effective role: "the maximum over paths from the node to the thing of the minimum role along the path". The empty path from an actor to itself: choice admin (an account actor has admin on itself; key actors own themselves anyway) (`World::reach`).
   **Resolved** (a) The engine seeds an actor with admin on itself (perm `graph.rs` `roles_expiring`). spec/permissions.md §1 Effective role says so. Model unchanged.

33. **Explicit demotion of X on N through another thing.** spec/permissions.md §5.2: "an applied explicit write ... that demotes X on N ... and takes X's role on N, with the edge as restored, from write or above to below write". With actors the write may be on another thing (X's edge on an account that is N's first admin). Choice: any applied explicit write by another author after which X's effective role on N falls below the need, judged with that write's own edge as restored (extends 12; `Timeline::demotions`).
   **Resolved** (a) The engine's audit (`walk.rs` `audit_fall`) demotes anyone reaching the holder on anything reachable from the target, the edge as restored being the join since the last explicit write (plus a self-demoter's prior values, a nuance the model does not have, ASSUMPTIONS.md). Spec §5.2 already defines it. Model unchanged.

34. **Possible admins "holding the thing".** spec/commits.md §4: "the least set holding the thing and, with each member, its first admin and any holder named with admin on that member by an edge write ... a member signed"; possible writers add "the possible admins of the thing and of each member". Choice: as written, the thing itself a member (`Possible::new`).
   **Resolved** (a) The engine starts the set with the thing (`held.rs` `ever_admins`; `possible_admins_least_and_order_free_spec_commits_4`). Model unchanged.

35. **What leads from an author to a thing.** spec/commits.md §4: "no first admin ... or holder named by an applied part's edge write ... leads from the author to it". Choice: a path from the author over first admin to its thing and holder to target, through every edge write of a joined part of an applied role commit, any validity; "on that chain" includes the thing itself (`Waits`).
   **Resolved** (a) The engine's chain includes the thing and searches first-admin links and every named holder of an applied role part, any validity (`apply/mod.rs` `thing_wait`, `validity::reaches`). Spec says so. Model unchanged.

36. **A waiting body carrying a copy of a value-less value.** spec/crdt.md §4.7 Copies: held as its leftover "from the moment the node holds that write value-less or the body arrives, whichever is later"; spec/commits.md §5 keeps a held part of a waiting commit "until its commit applies". Choice: a waiting body is held as its leftover too (`Leftover(Copy)`), found by the forced-fates property (a pending body repeating an expired entry's key).
   **Resolved** (a) The engine strips copies only from joined bodies; a waiting part keeps its body until its commit applies (`retention/pending.rs` `pending_drops`; spec/commits.md §5). Limit: a commit that never applies keeps such copies in its pending copy. spec/crdt.md §4.7 now says "or the body joins". Model changed: a waiting body is `Keep(Pending)` and its values are not forbidden.

37. **A waiting part past its expiry "goes".** spec/commits.md §5: it "goes from the node at T ... counts as never received". Choice: `MustDrop(Gone)`, the body becomes missing (counted held by the expiry clause), not a leftover.
   **Resolved** (a) Engine matches (`pending_drops`, `strip_pending`; parts.rs `parked_part_goes_at_its_expiry_spec_commits_5`). Model unchanged.

38. **Purge and expiry of an unjoinable body.** spec/versioning.md §2: for a body the node could not join "purge requests, expiry and absolute keep-at-most bounds still apply", but it cannot be stripped. Choice: purged or expired, it goes whole (`Gone`), as "With a page of it not held it cannot be stripped: it goes at once" (spec/commits.md §5).
   **Resolved** expiry (a): engine matches (same test as 38). Purge (b): the engine skips a parked part it cannot decode, so a purge leaves it whole: issue parked-part-purge-unstripped (closed). Model unchanged.

39. **Required retention entry and in force.** spec/commits.md §5: "The entry governing an AK is its own in `rules`, else `default`"; in force "the newest valid `required^.0` delta on the thing ordered before that key". Choice: an AK's own entry beats the default; "ordered" by the §5.1 key `(ts, author, commit)`; a required delta's own validity is judged as admin-only at its key, so no cycle with the deltas it judges (`model.rs`, `in_force`, `breaks`).
   **Resolved** (a) The engine: own entry else default (`core_types::required_for`), strict key order (`validity::in_force`), each setting judged admin-only at its key by the normal timeline (`Judge::settings`; required.rs `setting_falls_through_acting_spec_perm_5_2`). spec/commits.md §5 in force reworded. Model unchanged.

## held-model-3 (apply without atomicity, timing)

40. **A dropped body and "holds parts of it".** spec/commits.md §4 Pending: "the node holds parts of it and every one waits"; §5 Never received: a body dropped for its keep bounds counts as never received. A commit whose joined part was dropped, with another part held later that waits, would then pend, un-applying what applied; §5 says "a commit such a part applied before T stays applied" only for expiry. Choice: a dropped body counts as a held part that does not wait (`applies`): the commit stays applied.

41. **A waiting part past its expiry and Pending.** spec/commits.md §5: it "goes from the node at T"; §4 Pending counts the parts held. Choice: from T it is not held, so a commit whose held parts all waited and expired applies as its header alone (`applies`); before T it pends.

42. **What a dropped-valid snapshot takes back.** spec/permissions.md §5.2: a copy of a snapshot dropped while valid, held again and judged invalid, takes back "what it gave ... exactly those writes"; "A valid snapshot's body dropped leaves what it gave in the state". When another body dropped here left the same write (another dropped-valid snapshot carrying it), did this one give it? Choice: literal, the write goes from the own state (it has one copy). Writes under dots of deltas dropped here stay; a delta dropped as covered counts as dropped otherwise (ASSUMPTIONS.md).

43. **A waiting part of an applied commit under a purge.** spec/commits.md §5 Purge: "Every node applying it drops ... the named deltas" vs A waiting part under a purge: "held value-less ... it waits and applies as that". With apply no longer atomic, a part may wait alone in an applied commit. Choice: it is a waiting part (`Leftover(PendingPurged)`, its values not held, not in `purged`) until it joins.

44. **A kill stamped ahead of the clock under 0 after replaced.** spec/commits.md §5 Keep at most: "A node drops a body no earlier than its bound" (the first death, a `ts` that may be up to `MAX_DRIFT` ahead of the clock) vs Carrier: "A body with no live write needs no carrier: under 0 after replaced, the node applying the kill that leaves it none drops it in that transaction". Choice: the second, more specific rule: such a body goes at once whatever the clock (`bounds`: bound 0). The engine does the same (`judge_at_most`, "even when the killing `ts` is ahead of its clock"); found by the adapter's checks between ingests (purge seed 9430002: an invalid body's fall at its own `ts`, ahead of the node's early clock).

45. **The purge floor and keep at most 0 after replaced.** spec/commits.md §5 Purge: a commit carrying a purge request keeps its blobs "at least until `wall_ms(ts) + ROLE_KEEP`, whatever its deltas' keep bounds (at least and at most)" vs Keep at most: under 0 after replaced a body with no live write goes at the kill. Choice: the floor wins, also over that drop and over an absolute T (`bounds` raises both bounds to it). The engine does the same (`osis_commit::retention::body_keep`); the model had missed the floor (purge seed 9450000: a request-carrying `writer` body superseded, held by the node).

## held-model-4 (history modes, issues/retention-modes.md step 0)
Retention is a purgeable-by and a history mode (purge-on-replace | keep at least until T and/or D after replaced); every drop that is not expiry or purge is as covered by a valid snapshot whose commit holds the purge right over the body; the keep-at-least limits every node's covered drop alike (from the held set) and what `history()` shows. What the properties found while modeling it:

46. **"Replaced" is not "has a dead write".** spec/crdt.md §4.8 counts a register's reset dead once a later write implies one, yet canonical form keeps the aspect's root reset (it prunes), so every snapshot carrying it would count as replaced for good: a writer's cover of a purge-on-replace aspect was owed again as soon as written, covers chased each other, and two at one `ts` covered each other and both dropped (seed 360). Choice: a body is replaced when it holds a write the state joined but canonical form does not hold by identity (`Outcome::replaced`: pruned or beaten), exactly what a snapshot from the state would leave out; a write an un-merge took (a valid delta's write nested in an invalid delta's record, seed 1078) is not replaced: no cover from the state can carry it, and it comes back with the record's validity. The engine's "none = compaction on replace" (plan step 2) must judge replacement the same way, by the covering join or write membership, not by deaths.
47. **Covered-equal snapshots.** spec/sync.md §7: two snapshots covering each other at one `ts` are covered-equal and the one with the higher commit ID goes. Choice: a snapshot body is covered only by one stamped later, or at the same `ts` by a lower commit ID (`fate`); else two covers drop each other.
48. **A reader's local drop needs no right of its own.** spec/commits.md §5 Between the bounds asks the covering snapshot's commit to hold the right "and the node itself holds it now"; under the one principle (every drop is a right holder's valid covering snapshot) the snapshot is the authority and any node holding it may drop the covered body, must under purge-on-replace ("drops the body everywhere"). Choice: no `me` right for a local drop; the clause binds host deletion (not modeled).
49. **Fetching again.** A dropped body's cover turning invalid, being purged or dropped with no standing cover of its own, and a stripped body whose purge fell, are never received and fetched again (`Outcome::uncovered`, `Fate::NeverReceived`); the properties take the copy from the full history. With that repair every arrival order reads alike; without it a node that dropped reads less than one that kept (the stated Deterministic limit: a cover that turns invalid; a purge fall).
50. **A waiting part gone at its expiry diverges for good.** A part that waits (nothing leads from its author to the thing yet) past its expiry goes and is never fetched again (spec/commits.md §5), so a node that received the leading role commit before T applied the part and holds its leftover (resets, flags), one that received it after reads without it. Arrival order shows: the properties except such aspects. The surviving expiry-pending shape.
51. **A valid cover written after a kill that later turns invalid** keeps the killer's copy (a valid snapshot's copies all count, spec/permissions.md §5.2): every node holding the cover reads alike, with the kill; only one holding neither cover nor kill reads the old value, as any node missing a body. No divergence among nodes holding the same bodies.
52. **Every held body is stripped of value-less copies**, whatever its fate: a covered body (`MayDrop`) may carry a purged entry's key (seed 655). Choice: `act` strips every body it leaves held.
53. **A parked part a purge names goes whole and its commit then applies as a header alone**, its own purge request with it (a purge-carrying commit whose only part was parked): reads change at that apply (seed 302). The forced-fates property compares reads only when the applied set is unchanged.
54. **A snapshot's history mode** is purge-on-replace when any write it carries is of a purge-on-replace delta (its copy must go once replaced too), else kept for the longest D after replaced among the carried writes' own deltas (no T), else convenient (`snapshot_retention`). A snapshot's relative bound counts from the latest of its carried writes' replacements (each write's earliest valid superseder held), a delta's from the earliest: the snapshot keeps the history of every write it carries for D after that write's replacement, so compacting a keep-for-D write while live loses none of it. The engine's snapshot retention (plan step 1) follows this, from the carried writes' own headers as today. Such a snapshot covers no body that keeps history while the body has a live write (a write in the state): it could not keep that history (spec/commits.md §5 Covered).
55. **D after replaced at a node without the right.** A snapshot carries no signal of which bodies its compactor judged past D. Choice (Tess): one rule for every node: a covered D-bound body stays until D after the earliest valid replacing write the node holds (`fate`, whatever `me`'s right), so readers and writers holding the same data keep and show the same history.
56. **A body nothing held supersedes is past its relative bound**: its content left the canonical state by a reset pruning it or a copy, nothing to date from; `history()` shows it only under an absolute T.

57. **A char-less text creation.** A content delta's own value-less write was read as a body stripped for a purge that fell (never received), but a writer that inserts and deletes an element in one commit sends the creation without its char (spec/crdt.md §5.7: canonical form carries no dead content). **Resolved** (a) such a creation, deleted in its own delta, is no value-less write (`never_received`; test `charless_creation_deleted_in_its_delta_is_received_spec_crdt_5_7`).

## Signals
58. **When a signal body goes.** Decided (Tess): a signal write is replaced when written, so history from the start, kept until its keep bound, expiry or purge; never covered. Choice: past its keep bound the body goes at every node (`MustDrop(PastBound)`), whole or as an expired or purged leftover: nothing joins, so no state needs it and no history keeps it, and holding it on would show history no setting promised. A part on a signal keeping no history is bad input, never generated. spec/commits.md §5 Signals says so.

# held-model: spec ambiguities
> Summary: Every place the spec left a choice, contradicted itself or said too little while building held-model, the model's choice, and how each was resolved against the engine (3-38 resolved; 25-38 undo, roles beyond one edge, waits; 40-43 apply and timing; 46-57 covers and fetching again; 58 signals; 59-70 thing-level history). Numbers are stable: gaps are entries whose rules no longer exist.

Each entry: the spec text, the problem, the model's choice (and where in the code), then **Resolved**: (a) spec fixed to the intended rule (the engine's), model matched; (b) engine wrong, issue filed; (c) a question for Tess (an issue tagged `tess-call`), model's choice kept. Each rule settled by reading engine code names its engine example test.

## Headline

3. **Re-grant revives everything since the first grant.** spec/permissions.md §5.2: "An actor holding the required role in the timeline's final state ... is re-granted: each of its writes ordered at or after the first point it held that role is valid again, including those in the gap." "First point" could be the first ever grant or the start of the current grant; only the first reading revives "those in the gap". Choice: first ever. Consequence: any later re-grant undoes a demotion's omissions and a purge-right loss (§6).
   **Resolved** (a)+(c) The engine revives from the first-ever grant (perm `Timeline::first_held`; perm content.rs `frontier_decides_pre_revoke_edits`), deliberate per notes/permissions.md. Spec says "first point it ever held".

4. **A frontier validates writes made without the role.** spec/permissions.md §5.2: "Otherwise it is valid iff the frontier of a valid explicit demotion of X below write on N lists its commit, whatever their order". This does not require X to have held write when it wrote; a demoter lists every received commit of X (§5.1 Listed), unauthorized ones included. Choice: literal (valid). Likely unintended (`roles.rs`, `valid_as`).
   **Resolved** (c) The engine is literal too (perm `delta_valid_uncached`), and writes after an `until` need it (perm content.rs `until_gap_write_finalized_by_frontier`). Question 7; the model stays literal.

5. **Death dating: first held vs earliest.** spec/commits.md §5: "a superseded write's death at the `ts` of the first superseder the node held, never earlier than the death" (arrival order; and "never earlier than the death" is circular) vs spec/crdt.md §4.8: "the earliest `ts` among the valid writes the node holds that supersede it ... the order of arrival does not matter". Choice: §4.8 (`model.rs`, deaths).
   **Resolved** (a) The engine dates at the first superseder held (Tess's decision, notes/engine-retention-dating.md; retention.rs `deaths_dated_from_first_superseder_held_spec_commits_5`), the earliest only after a recompute. spec/commits.md §5 now reads non-circularly (never earlier than the §4.8 death; a lower-`ts` superseder held later moves no date). The model has no arrival order, so it dates at the earliest, the date a recompute gives: an engine date may be later, never earlier (ASSUMPTIONS.md).

7. **Which records are live writes.** spec/commits.md §5: "any write of its deltas the node's state holds by dot, including element records the state keeps only as anchors ... but not an element's or entry's tombstone (it holds the remover's reset, not the creation)". Unclear for (a) a text record whose creation a reset pruned, held for others' flag writes on it, and (b) the remover's own surviving reset or removal. Choice: both live. Consequence: a `remove_aspect` body stays live until a later reset. Replaced is judged by death, not by the records held: a text element's creation under a winning delete is held by its record and dead (spec/crdt.md §4.8), so its body is replaced at the delete (spec/commits.md §5 Bodies and deaths, as the engine's `replace::replaced`; `text_body_replaced_by_a_delete_spec_commits_5`).
   **Resolved** (a) Both live in the engine (`holds_owned_write`: a `Rec::Seq` is never a tombstone; a tombstone's reset is its remover's write; deletion.rs `dropped_snapshot_waits_for_its_carrier_spec_sync_7`). Spec live write rewritten (resets and every sequence record count). The reset case: retention.rs `remover_reset_is_live_until_superseded_spec_commits_5`.

9. **When a leftover may go.** spec/crdt.md §4.7: the leftover is "a held body like any other ... that uploads nowhere"; spec/commits.md §6: "every node holds them value-less, the body ... as its leftover, whatever the delta's keep-at-least bound". Nothing says when an expired or purged delta's leftover is dropped. Choice: a leftover is terminal in the model (`Fate::Leftover`).
   **Resolved** (a) A bare leftover (no value of its own) is never dropped; one stripped only of carried copies is a body like a whole one (spec/commits.md §5 Dropping a body). Model: a `Copy` leftover is judged like the body, stripped (test `copy_leftover_drops_as_covered_spec_commits_5`).

## Others

11. **Covered with value-less copies.** spec/commits.md §5 Covered: covering is the canonical-bytes join test, yet the MUST beside it says "(a value-less copy matches)". Under spec/crdt.md §4.1 the valued copy wins the join, so a snapshot holding a value-less copy of a body's valued write fails the test. Choice: the join test decides (not covered).
   **Resolved** (a) The engine's join test decides (`retention::snapshot::covered`). Spec: a value-less copy is allowed under the MUST, and the join then leaves a valued body uncovered. Engine: validity.rs `valueless_copy_loses_to_held_value_spec_crdt_4_7`.

12. **"Explicit demotion below write" is not defined in §5.1's terms.** spec/permissions.md §5.1 defines demotion as a class fall (edge admin, invite); §5.2 uses "explicit demotion of X below write on N". Choice: an applied edge write by another author taking X's role from at least the need to below it (`roles.rs`, `demotions`).
   **Resolved** (a) The engine's definition is notes/permissions.md's (perm `walk.rs` `audit_fall`): an explicit write by another author that demotes X (§5.1 step 4) from write or above, the edge as restored. spec/permissions.md §5.2 now defines it. The model's single-edge version is that rule within its scope (no actors, until or invites).

13. **Applied or held purge request.** spec/commits.md §5: "Every node applying it drops"; §5 A waiting part under a purge: "a held purge request". Choice: an applied request for applied targets; a held, unparked one for waiting parts.
   **Resolved** (a) The engine needs an applied request everywhere (`purge::apply_request` registers only on apply; shred.rs `purged_while_pending_unrecoverable_spec_commits_5`). Spec: "applied" in §5 waiting part, Purge. Model: requests count only once applied.

15. **Expiry as a death date.** spec/commits.md §5: "an expiry dates none" vs spec/crdt.md §4.8: "It dies at the earliest `ts` ... or at T". Choice: T counts once passed; no effect, since the body is then a leftover.
   **Resolved** (a) The engine never dates T (`hold_valueless` makes a leftover with no deaths). spec/crdt.md §4.8: T by expiry dates no body. Model: no death at T.

18. **Purging a snapshot by aspect history.** spec/commits.md §5: a request names deltas "by commit, by a whole aspect history, or by author on an aspect"; "A snapshot a request names itself ... its body is dropped". Whether "a whole aspect history" includes snapshot deltas is not said. Choice: yes, judged by the snapshot's retention (`writer`) and its author.
   **Resolved** No request names a snapshot (`purge::names`; spec/commits.md §5 says so): it has no values of its own, so it is never purged nor read as purged, whether held whole, as its leftover or dropped as covered (shred.rs `purge_strips_carrying_snapshots_alike_in_every_order_spec_commits_5`).

21. **Map presence after an entry expires.** spec/crdt.md §4.3 counts "its children's writes", so another delta's write inside an entry whose creation expired keeps the map present.
   **Resolved** (a) Another delta's valued write keeps the entry itself, under that write's own key (spec/crdt.md §4.7, §5.6 Live; test `other_write_outlives_an_expired_entry_spec_crdt_4_7`); a removal alone keeps only the map present.

22. **Stripped copies asked for again.** spec/permissions.md §6: "A held body stripped for carrying a purged value is asked for again with any such fall". While asked for, does the stripped copy still join? Choice: yes, value-less (it only hides).
   **Resolved** (a) The stripped body stays held as its leftover: its value-less copies only hide, and the valued copy wins wherever one joins (spec/crdt.md §4.7 Join), so a fall never takes a cover's other writes (`purge::rejudge_purges`; spec/permissions.md §6). `Part::stripped` records whose values `act` stripped.

24. **A purged or expired delta's own body.** spec/commits.md §5 Purge said a node "drops ... the named deltas" and "holds every body carrying their values as its leftover", leaving open whether the named delta's own body is dropped or held as its leftover. Choice: `Fate::Leftover(Purged | Expired)`.
   **Resolved** (a) spec/crdt.md §4.7 (the body goes, "the node holds the body's leftover instead") and commits §6 already said leftover for expiry; commits §5 Purge now names the delta's own body too. The engine holds it as its leftover (`Hold::Leftover`); the adapter (osis-node `tests/it/held.rs`) had read every leftover as dropped (`body_not_dropped`) and accepted either.

## Undo, roles beyond one edge, waits

25. **Self-removal "when either holds".** spec/permissions.md §2: "Such a write is a self-removal when either holds; otherwise it is an explicit demotion: it lowers the author's own edge ... admin on X is the author's only authority for it". Read literally, an edge admin lowering its own edge is a self-removal, which contradicts §5.1 step 2 ("a write lowering another holder's edge by an author that also has edge-admin authority ... is an explicit write"). Choice: both must hold; an author with edge-admin authority on the target writes explicitly (`roles.rs`, `decide`).
   **Resolved** (a) The engine reads "either": lowering one's own edge is always a self-removal, the only-authority condition is for another holder's edge (perm `walk.rs` `judge`; notes/permissions.md, decided at review); §5.1 step 2 speaks of another holder's edge, so no contradiction. Model changed (`decide`: self-removal first). Engine: retention.rs `edge_admin_removing_own_edge_is_self_removal_spec_perm_2` (a frontier-less removal: as an explicit write it would be a finalize, ignored on an unended edge).

26. **Finalize or self-removal through an actor.** spec/permissions.md §2 Finalize: "a removal of another holder's edge carrying no frontier"; Self-removal: "a node with admin on actor X may always remove X's edge". A frontier-less removal of X's edge by an admin of X fits both. Choice: a self-removal (it applies whatever X's `until`); finalize only when the author has no admin on the holder (`decide`).
   **Resolved** (a) The engine checks self-removal first, then finalize for any other frontier-less removal that lowers, admin on the holder or not (`walk.rs` `judge`). Spec Finalize: "that is not a self-removal". Model changed: finalize no longer excludes an admin of the holder.

27. **An undeleted element's creation stays dead.** spec/crdt.md §4.8 Revival: "Un-merge (§4.6) is the only way a dead write revives"; "its element deleted". An insert whose element a delete superseded, then an undo undeleted, stays dead at the delete's `ts` though the element shows again, so its body is replaced there. Choice: literal (`death::supersedes`).
   **Open** The engine judges a text creation by its element's winning flag (crdt `winners.rs`): under a later undelete it wins again and dates no death, later than the model (kept longer; the order harness counts bodies dated later, issues/text-creation-undelete-dating.md). Re-deleted, it dates at the earliest delete held. Model unchanged.

29. **The state before an undone commit, of a held set.** spec/crdt.md §4.6 says what an undo should restore, not where the undoing node gets the state before the commit. Choice: the held set as if the undone commit had not been written (its body gone, its writes gone from every snapshot carrying them), judged now; values held value-less by the undo's time or purged are never written back (`undo::undo`).
   **Resolved** (a) A writer-side choice: the engine uses its saved pre-commit state for a recent local commit, else the valid held parts ordered before by `(ts, ID)`, no own-state writes (`undo::undo_in`); a receiver judges the undo commit like any content commit. spec/crdt.md §4.6 says a receiver never derives an undo's writes again. The model's undo only drives the generator; not compared.

30. **Whose authority judges an acting delta.** spec/commits.md §4: "Each delta is judged on its own, by its author's authority"; spec/permissions.md §5.2: "A delta by actor X on thing N is valid if X held write" and Acting: invalid "unless a delta of its author on that actor needing write ... would be valid". Choice: the header actor is X, and the author must also pass the acting rule (`Timeline::valid_delta`).
   **Resolved** (a) The engine judges every delta by its author node, the actor only through the Acting check (`apply/validity.rs` `Judge::part`, `acts_for`; notes/permissions.md: "the author's rights decide"; validity.rs `acting_valid_once_grant_arrives_spec_perm_5_2`). spec/permissions.md §5.2 says so. Model changed (`Timeline::valid_delta`).

31. **The `author` purge right under acting.** spec/permissions.md §6: "author: the actor the commit's header names while it holds write on the thing, acting through any node with write on it" and "when it acts for another actor (its header actor), so did that actor". Choice: the request's actor is the delta's header actor and both the request's author and actor hold write; `admin` and `writer` need both author and actor to hold the role (`Timeline::right`). `PurgeItem::Author` matches the delta's author node, not its actor.
   **Resolved** (a) The engine: each signer (author, and actor when it acts) holds the right on its own; `author` is held by the delta's header actor and any node with write on it while the actor has write on the thing (perm `purge_stands`, retention `purge::holds_right`; notes/permissions.md Purge author right); `PurgeItem::Author` names the delta's header actor (spec/wire.md §4). Spec §7 `author` reworded. Model changed (`Timeline::right`, `names`).

32. **An actor's role on itself.** spec/permissions.md §1 Effective role: "the maximum over paths from the node to the thing of the minimum role along the path". The empty path from an actor to itself: choice admin (an account actor has admin on itself; key actors own themselves anyway) (`World::reach`).
   **Resolved** (a) The engine seeds an actor with admin on itself (perm `graph.rs` `roles_expiring`). spec/permissions.md §1 Effective role says so. Model unchanged.

33. **Explicit demotion of X on N through another thing.** spec/permissions.md §5.2: "an applied explicit write ... that demotes X on N ... and takes X's role on N, with the edge as restored, from write or above to below write". With actors the write may be on another thing (X's edge on an account that is N's first admin). Choice: any applied explicit write by another author after which X's effective role on N falls below the need, judged with that write's own edge as restored (extends 12; `Timeline::demotions`).
   **Resolved** (a) The engine's audit (`walk.rs` `audit_fall`) demotes anyone reaching the holder on anything reachable from the target, the edge as restored being the join since the last explicit write (plus a self-demoter's prior values, a nuance the model does not have, ASSUMPTIONS.md). Spec §5.2 already defines it. Model unchanged.

35. **What leads from an author to a thing.** spec/commits.md §4: "no first admin ... or holder named by an applied part's edge write ... leads from the author to it". Choice: a path from the author over first admin to its thing and holder to target, through every edge write of a joined part of an applied role commit, any validity; "on that chain" includes the thing itself (`model.rs` `leads`, `unreached`).
   **Resolved** (a) The engine's chain includes the thing and searches first-admin links and every named holder of an applied role part, any validity (`apply/mod.rs` `thing_wait`, `validity::reaches`). Spec says so. Model unchanged.

36. **A waiting body carrying a copy of a value-less value.** spec/crdt.md §4.7 Copies: held as its leftover "from the moment the node holds that write value-less or the body arrives, whichever is later"; spec/commits.md §5 keeps a held part of a waiting commit "until its commit applies". Choice: a waiting body is held as its leftover too (`Leftover(Copy)`), found by the forced-fates property (a pending body carrying an expired value).
   **Resolved** (a) The engine strips copies only from joined bodies; a waiting part keeps its body until its commit applies (`retention/pending.rs` `pending_drops`; spec/commits.md §5). Limit: a commit that never applies keeps such copies in its pending copy. spec/crdt.md §4.7 now says "or the body joins". Model changed: a waiting body is `Keep(Pending)` and its values are not forbidden.

37. **A waiting part past its expiry "goes".** spec/commits.md §5: it "goes from the node at T ... counts as never received". Choice: `MustDrop(Gone)`, the body becomes missing, not a leftover.
   **Resolved** (a) Engine matches (`pending_drops`, `strip_pending`; parts.rs `parked_part_goes_at_its_expiry_spec_commits_5`). Model unchanged.

38. **Purge and expiry of an unjoinable body.** spec/versioning.md §2: for a body the node could not join "purge requests, expiry and absolute keep-at-most bounds still apply", but it cannot be stripped. Choice: purged or expired, it goes whole (`Gone`), as "With a page of it not held it cannot be stripped: it goes at once" (spec/commits.md §5).
   **Resolved** expiry (a): engine matches (same test as 37). Purge (b): the engine skips a parked part it cannot decode, so a purge leaves it whole: issue parked-part-purge-unstripped (closed). Model unchanged.

## Apply and timing

43. **A waiting part of an applied commit under a purge.** spec/commits.md §5 Purge: "Every node applying it drops ... the named deltas" vs A waiting part under a purge: "held value-less ... it waits and applies as that". With apply no longer atomic, a part may wait alone in an applied commit. Choice: it is a waiting part (`Leftover(PendingPurged)`, its values not held, not in `purged`) until it joins.

## Covers and fetching again
Every drop that is not expiry, purge or invalidity is as covered by a valid snapshot (spec/commits.md §5 Covered).

46. **"Replaced" is not "has a dead write".** spec/crdt.md §4.8 counts a register's reset dead once a later write implies one, yet canonical form keeps the aspect's root reset (it prunes), so every snapshot carrying it would count as replaced for good: a writer's cover of a purge-on-replace aspect was owed again as soon as written, covers chased each other, and two at one `ts` covered each other and both dropped (seed 360). Choice: a body is replaced when it holds a write the state joined but canonical form does not hold by identity (`Outcome::replaced`: pruned or beaten), exactly what a snapshot from the state would leave out.
47. **Covered-equal snapshots.** spec/sync-compaction.md §1: two snapshots covering each other at one `ts` are covered-equal and the one with the higher commit ID goes. Choice: a snapshot body is covered only by one stamped later, or at the same `ts` by a lower commit ID (`fate`); else two covers drop each other.
48. **A reader's local drop needs no right of its own.** spec/commits.md §5 (then "Between the bounds") asked the covering snapshot's commit to hold the right "and the node itself holds it now"; under the one principle (every drop is a right holder's valid covering snapshot) the snapshot is the authority and any node holding it may drop the covered body, must under purge-on-replace ("drops the body everywhere"). Choice: no `me` right for a local drop; the clause binds host deletion (not modeled).
49. **Fetching again.** A dropped body's cover turning invalid or dropped with no standing cover of its own, and a stripped body whose purge fell, are never received and fetched again (`Outcome::uncovered`, `Fate::NeverReceived`); the properties take the copy from the full history. With that repair every arrival order reads alike; without it a node that dropped reads less than one that kept (the stated Deterministic limit: a cover that turns invalid; a purge fall).
50. **A waiting part gone at its expiry diverges for good.** A part that waits (nothing leads from its author to the thing yet) past its expiry goes and is never fetched again (spec/commits.md §5), so a node that received the leading role commit before T applied the part and holds its leftover (resets, flags), one that received it after reads without it. Arrival order shows: the properties except such aspects. The surviving expiry-pending shape.
51. **A valid cover written after a kill that later turns invalid** keeps the killer's copy (a valid snapshot's copies all count, spec/permissions.md §5.2): every node holding the cover reads alike, with the kill; only one holding neither cover nor kill reads the old value, as any node missing a body. No divergence among nodes holding the same bodies.
52. **Every held body is stripped of value-less copies**, whatever its fate: a covered body (`MayDrop`) may carry a purged entry's key (seed 655). Choice: `act` strips every body it leaves held.
53. **A parked part a purge names goes whole and its commit then applies as a header alone**, its own purge request with it (a purge-carrying commit whose only part was parked): reads change at that apply (seed 302). The forced-fates property compares reads only when the applied set is unchanged.

57. **A char-less text creation.** A content delta's own value-less write was read as a body stripped for a purge that fell (never received), but a writer that inserts and deletes an element in one commit, kept because another write of the commit anchors at it, sends the creation without its char (spec/crdt.md §4.5). **Resolved** (a) such a creation, anchored at by another write of its delta, is no value-less write (`never_received`; test `charless_creation_deleted_in_its_commit_is_received_spec_crdt_4_5`).

## Signals
58. **When a signal body goes.** Decided (Tess): a signal write is replaced when written, so history from the start, kept until its keep bound, expiry or purge; never covered. Keep history is a keep at least for signals as for values (Tess). Choice: past its keep bound the body may go (`MayDrop(PastBound)`), whole or as an expired or purged leftover: nothing joins, so no state needs it, and history lists it only before the bound, held or not. A part on a signal keeping no history is bad input, never generated. spec/commits.md §5 Signals says so.

## Thing-level history
Choices against spec/commits.md §5 The setting and Tess's decisions (notes/engine-retention-history.md).

59. **A body nothing held dates.** History counts from replaced-at; a replaced body no held body supersedes (a reset pruned its content, a copy without it; a snapshot whose every dead write a later held snapshot carries) has none. Choice: not in history (`Outcome::replaced_at` None): nothing promises it, and a later snapshot carrying the write holds its history (`a_later_snapshot_carrying_a_dead_write_holds_its_history_spec_commits_5`).
60. **Keep at least and drift.** Resolved (spec/commits.md §5 Keep at least): a node drops at `out` exactly on its clock; `MAX_DRIFT` applies to host deletes only, which the model does not cover.
61. **Which covers drop a body out of history.** History says out-of-history value bodies drop "as covered by a cover holding the right"; Purge on replace's last rule and Tess's decision 4 say any valid writer's cover. Choice: decision 4, for every replaced body not in history: `MayDrop(Covered)` under any valid snapshot covering it; a live delta (not replaced) as entry 70 says; in history, `Keep(Until)` whatever covers it; under purge on replace, `MustDrop(Covered)` only under a right holder's cover (`fate` names a right holder's cover first when there is one). **Resolved** (a): spec/commits.md §5 The setting (Out of history) says any valid writer's cover.
62. **Owed while a writer's cover is held.** A body under purge on replace covered only by a snapshot whose commit lacks the right may go (61) and is still owed a cover by a right holder: the promise is kept by right holders' covers (`out_of_history_drops_under_any_writers_cover_spec_commits_5`).
63. **A setting in an expiring commit.** "It carries no `expires`". Choice: such a delta is no setting (not in the timeline); its commit is otherwise judged as any.
64. **Fixed retention.** Governed by no setting: `roles.0`, `retention^.0`, `purge.0`, `addenda.0`, `created.0` (`Aspect::fixed`): never out of history, never covered. `PurgeBy::Nobody` stays in the input for them; a content part carrying it (bad input at the engine, spec/wire.md §4) is judged like any content part, nobody holding its purge right.
65. **Order of settings.** In force by key `(ts, author, commit)`; `thing_history` takes wall ms with each setting's rank by key, so settings at one wall ms apply in key order (`Outcome::timeline_of`; `ev_in_force_by_key_from_its_own_stamp`).
66. **One way through the default.** The one-way rule reads per AK the entry governing it, own or default: a default purge on replace followed by an AK's own keep keeps nothing there.
67. **Signal edits.** Versions and their original share their AK's window, each from its own `ts`, and a purged version is listed while a body replaced at its request's `ts` would be in history. One window per AK: a purged newest version's listing outlasts every older version's, so none shows again when it ends (`a_purged_edits_tombstone_outlasts_older_versions`); the shorter-keep limit cannot arise. `final` and the expiry bound for replacing parts are writer defaults with no validity rule (Tess's decision 5, notes/engine-retention-history.md): not modeled; the engine's `final` is the setting entry's, read only by the writer (`replace` refuses).
68. **Replaced ahead of the clock.** A body replaced by a held write stamped after `now` (within drift) has a replaced-at past `now`. **Resolved** (coordinator: purge on replace means no history at any moment): a body is in history only while a setting keeps it past its replaced-at (`out(r) > r`, `thing_history::kept`), so one replaced under no history or purge on replace is never listed, ahead of the clock or not; under a keep entry it is listed from the moment it is held until it leaves (`purge_on_replace_never_listed_ahead_of_the_clock_spec_commits_5`). Drops follow the clock where history is kept (spec/commits.md §5 Keep bounds, Dated only where history is kept): on an aspect some held setting keeps history for at some moment (one way: a keep after purge on replace reads as none, spec/commits.md §5), such a body is not dropped as covered, under purge on replace too, until `now` reaches its replaced-at; elsewhere it drops at once, whatever the thing's other aspects keep (`Outcome::kept`, `aspect_keeps`).
69. **When the walk restarts.** spec/permissions.md §5.1 step 4: "R then adds to D ... and the walk restarts", beside "the commit's applied edge writes then take effect one at a time ...; each write's demotions ... are judged". Restarting at R's own additions skips the audits of its commit's later writes, and with them drops a restart no longer reaches when R's first write cost its author the authority for the commit, so the commit's part order decided its drops. **Resolved** (a) The engine audits every applied write of the commit, then restarts (`perm/src/walk.rs` `Pass::commit`). Spec says so; the model matches (`Timeline::walk`, `commit_audits_all_its_writes_before_restart_spec_permissions_5_1`).
70. **Live deltas.** spec/commits.md §5 Kept while live keeps a held valid live delta (not a snapshot's or a signal's) to its aspect's live bound, then drops it under any cover like a replaced body out of history; spec/sync-compaction.md §1 own bodies lets its author drop it only under its own covers. Choice: a live delta is `Outcome::live_delta`; the bound is `thing_history::live_until` (the latest moment some span would keep a body replaced then, one way; property `kept_while_live_until_no_later_replacement_would_be_kept`), the fate `Keep(Live)` before it (`Outcome::live_until`, a deadline), any valid cover's `MayDrop(Covered)` after; a live delta held invalid (the author's own) keeps `Keep(Plain)`, outside that rule. Own bodies is a node-sync rule on top of what a node may drop, not modelled: it only keeps more, and `MayDrop` is optional. The adapter flags a live body dropped as covered before its bound (`order::harness_flags_a_live_drop_before_its_live_bound_spec_commits_5`). **Resolved** (a): the engine's `Timeline::live_until` reads alike; 300 plain order seeds found no held-model difference, with the property's nodes running node-sync's covered drops (`order::drop_covered`).

# What a write states, and what a reader holds to judge it
> Summary: Design (not built; §1, Owner keys and §5's last admin are in spec/permissions.md, the rest in no spec) for writes stating their path: owner keys (a key signs as the one thing listing it), what a path is and how each hop is checked, may-grant as a flag, the purge author a write names, the walk (each lowering judged once), what a remover lists and leaves out, the side a node takes in a fight (the lowering it held first, and its own); evidence in the sync unit as the closure over the paths its held commits state, a removal's list inside the removal, lazy delivery; the public thing; external signals and who may grant to a thing; core without accounts (the last admin as a writer's check); what a model must check before building; what is open.

**Principle: a write states how it has its right, and is judged by that statement alone; what a reader needs to check the statement is in the unit it reads, as a function of the writes that unit holds.** Core knows owner keys, things, roles, a write's stated path and named purge author, and each session's configured defaults for those; it has no concept of an account, a profile or a home (Tess). Each section states the one rule it follows from that; a rule that does not follow is marked **Smell**.

Marks: *decided* (Tess: Decided below, issues/actors-one-mechanism.md Answers), *modelled* (held by roles-model `paths` or held-model as they stand), *probed* (held by a throwaway run for this note, which the models are then cut to: §6), *argued* (a claim for the models, §6), *checked* (against the cited spec or code). Terms: notes/terms.md. Membership as a use of these rules: notes/account-membership-design.md.

## Decided (Tess)
Tess's words, verbatim; every rule below keeps them.
- "**Owner keys replace key actors.** An **owner key** is a key a thing lists as allowed to sign as it: a concept of its own, a value with no tid, aspects or roles."
- "It speaks for the one thing that lists it: it is no actor and holds no role. A commit it signs is that thing acting, and the actor chain is all things, from the thing the key signs as to the target. Only things hold roles."
- "A thing is minted with a mint admin or an owner key (a thing with no mint admin is where a chain starts). Owner keys are added and removed afterwards; the list is written only as the thing itself, by an owner key, and admins read it. A thing with none takes its first from an admin."
- "**May-grant becomes a flag** (Tess; to be dropped if it causes problems): a grant either lets its holder add new holders up to its own role or does not, in place of a level. A lower level is an arrangement: a thing holding the lower role with the flag, the person a writer of it."
- "**No eager delivery of removals.** [...] A removal reaches a far thing as it does today: with the thing's next key rotation by a writer holding it, and where a node holds both it and a write it judges there."
- "**A write judged invalid is dropped, as built.** [...] Nothing is kept aside for it and no drop waits for a complete pass".
- "**The last admin is a writer's check only.** A node does not remove the last admin it sees without being told to [...]; no rule every node judges, so two sole admins leaving at once leave a thing adminless, as a deliberate leave would."
- "**A write acts only as things on its chain**: writing "as" a thing that holds no role leading to what is written is refused".
- "**Nothing vouches for a role write**" (issues/role-vouch-contested.md).

## The built sync rules it rests on
The sync unit is the built one: a thing's readable closure, so a thing may be carried under several sync IDs (spec/sync-set.md §2; notes/sync-unit-scope.md). Used here:
- A commit is one blob, wrapped under the sync ID of every unit that carries a thing it writes; a certificate copy logged under several sync IDs is one blob wrapped under each (checked: spec/sync-judgement.md §1 One blob per commit, Certificate blobs). Evidence is stated per sync ID.
- A grant naming a holder travels under the holder's sync ID with the target's boxes to it and the target's `sync.0`, so the holder's readers enter what it holds roles on (checked: spec/sync-set.md §2 Node closure, read; spec/permissions.md §4 Role changes travel).
- A node opens a sync ID only while it syncs it (checked: spec/sync-opens.md §4, the shared set); nothing is logged or fetched under a sync ID outside the node's sync set without holding it.
- Deposits work per sync ID (spec/sync-inbox.md §3).
- A reader drops a body it judges invalid at once; no node deletes one at a store (checked: spec/commits.md §5 Invalid).

## Owner keys
**Rule: a key speaks for the one thing that lists it, and only things hold roles.** O1 to O7 are *modelled* (roles-model `paths`: notes/path-model-findings.md 55). A key is a value: it has no tid, no aspects, no roster, and nothing is granted to it or sealed to it. Everything a key can do is what the thing listing it can do.

### The list
- **O1. The list.** Every thing has an **owner-key list**: a set of public signing keys, read by the thing's readers (admins read it: decided), in a role-class aspect of the thing, so list writes are walked with its edge writes (§1). A thing's creation record names a mint admin or holds one owner key (decided); the record's key is on the list until a list write removes it. How a thing was minted matters to nothing afterwards (notes/principles.md, Things are all made of the same stuff).
- **O2. Signing.** A commit names the thing S it is **signed as** and the owner key that signed it, and carries one signature. S is the start of every path the commit states (§1): its actors are S, then each listed thing.
- **O3. The key hop.** The pair (k, S) is a hop like an edge with two values: **listed** (reads as admin wherever a hop's role is read) and not listed (none). It has no `until`, no may-grant flag and no levels. A commit signed by k as S holds its right at a point of a pass iff (k, S) is listed there and its path from S gives what the write needs (§1).
- **O4. Who writes the list.** A list write on S applies at a point of a pass iff
  - (a) its commit is signed as S and its path to S is empty (S acting as itself), the key hop listed there: it may add and remove any keys, its own included; or
  - (b) S lists no owner key there, the write only adds keys, and its path gives admin on S: an ordinary admin write, resting on its path's edges like any other (decided: "A thing with none takes its first from an admin").
  No other write changes the list: where a key is listed, no admin's write adds or removes one.
- **O5. A thing acting as itself is its own admin.** A path with no edges (signed as S, writing S, nothing listed) gives admin on S: the minimum over no edges. No grant gives this and none takes it; it is what "outranks admins" means (decided; issues/recovery-redesign.md). Its role writes on S apply wherever the key hop is listed, whatever the admins wrote, so it removes any admin and settles a fight among them. S's dependents are reached from it by descent like any mint ancestor's (§1).
- **O6. Removing a key is the ordinary removal, one hop earlier** (decided). A list write removing k is an explicit lowering of the hop (k, S): it carries a list naming the commits signed by k as S that its writer had received, puts in question every earlier held write resting on (k, S) (every commit k signed as S), and is judged once like any lowering (§1). A key removing itself is a self-removal: it audits nothing. Two keys removing each other are an admin dispute at the key hop: each node stands with the removal it held first, the user may switch (§1, First received).
- **O7. What rests on what.** A write signed by k as S rests on the hop (k, S) and on each edge of its path. A list write applied by (a) rests on the key hop alone, so no lowering of an edge puts it in question. A list write applied by (b) rests on its writer's admin path and falls like any role write a removal of that path leaves out (For Tess, below).
- **O8. Authority, not data** (decided): nothing is sealed to an owner key. A thing's secrets are held by its holders and by the key store that made it. A key store holding only the key signs as the thing, grants a thing of its own a role, and reads again what another reader re-seals to that holder (spec/permissions.md §4 Stranded).
- **O9. A stolen owner key has no remedy** beyond its removal by another listed key (decided: two parties holding one key cannot be told apart).

### What it gives
- **A limited key is a thing with an owner key, granted what it should have** (decided). A node root is an ordinary thing minted with its node's owner key, holding a role on its account; a node wanting two accounts unlinked uses a thing and an owner key for each; a link is a thing minted with a key derived from the link's secret, holding the role the link gives, with may-grant.
- **Recovery is an owner key on the thing to be recovered** (issues/recovery-redesign.md): written down, used from a fresh key store. None by default: a thing with no owner key is a fully valid use, and a thief with an unlocked node taking control of it is accepted (decided).
- **No kind of thing signs.** Nothing is a "key thing": no grant, sync unit or walk treats a signing thing apart from any other. A thing signed as may hold roles, be granted on, have dependents and be a path member of other things' writes.
- **Evidence**: the list writes on (k, S) are evidence wherever a commit signed by k as S is held, by the closure rule that carries edge writes (§2).
- **Until accounts move** (notes/redesign-plan.md, A4) a built key actor reads as a thing whose record holds its one key: its key hop is always listed and no list write exists, so the walk of §1 is built with the key hop from the start and gains list writes later.
- **Sessions** are keyed to S; a thing more than one key store signs as writes in commit form, since any holder of a listed key could overlap another's session dots (notes/account-membership-design.md §6).

### The flow that must hold (Tess)
"Attach an owner key, share adminship, the new admin turns hostile and backdates: no takeover and no dispute."
- **Holds by O4 and O5** where the key is on the list by the thing's record or by a list write of (a): the hostile admin's write adding a key is refused wherever a key is listed (O4), its lowering of any admin edge puts no list write in question (O7), and the owner key's removal of it applies (O5). No trust decides any of it, so no dispute is raised.
- **Holds against a backdated add** where the first key was added by an admin (b): "the admin's write adding an owner key is dated either before its grant (no right) or after the owner key exists (only an owner key writes the list)" (issues/recovery-redesign.md).
- **Does not hold against the attacher's removal** (*modelled*, asserted as built: notes/path-model-findings.md 55; For Tess 1): the first key added by admin H under (b) rests on H's admin edge. A later admin M that removes H with a list leaving that write out drops it like any unlisted role write (issues/role-vouch-contested.md), the thing lists no key, and M adds its own. No rule over the held commits can keep the key here and still drop a stolen node's backdated add of the thief's key: the two worlds hold the same commits (the attach, the removal of its writer that does not list it) and need opposite answers. Built as stated (O7: the simple rule, and the one under which a removed stolen node regains nothing); issues/owner-key-first-attach.md asks Tess.
- **Not protected, by design** (decided): a party made admin of a thing that then attaches an owner key, against an admin who held the thing earlier and backdates one ahead of it.

## 1. Paths
**Rule: a write is judged along the one path it states, hop by hop, and a removal is judged in the world its list makes.**

### What a path is
- A commit is signed as one thing S by one owner key (Owner keys). For each thing T it writes it states a **path**: a list of things [A1, ..., Ak], k ≥ 0, no thing twice and none of them S (a repeat is bad input).
- **Hops**: the key hop (k, S), then consecutive members of [S, A1, ..., Ak, T], joined by **descent** when the first is a mint ancestor of the second (the record edges down the mint chain), else by their **direct edge** (the holder's entry in the second's `roles.0`). A descent of one step is the direct edge (checked: spec/permissions.md §1 Record edge). A hop from a mint ancestor two or more record edges up is a descent unless the path marks it direct (built: notes/path-form.md). The path's role on T is the minimum over its hops; with S = T and nothing listed it is admin (O5).
- **A write acts only as things on its chain** (decided): every thing a write is made as (its purge author, below) is S or a listed thing.
- **The end**: the role a write needs is on T, except a self-removal, whose role is admin on the grant's holder X: its path ends at X. A lowering whose path ends at the holder is a self-removal, one ending at the target an explicit write.
- **What is listed**: only grant holders and the things they hold on, which are independent (checked: spec/permissions.md §3). Dependent things below the last listed thing are covered by the descent.
- **Why descent** (argued): were a path to end "at a holder on T's independent", a thing becoming independent would change which paths are valid, and a concurrent write by a node unaware of the promotion would fall (spec/requirements.md Permissions: sharing never changes how a thing behaves). Descent reads record edges, which promotion leaves standing.
- Typical paths: a node writing its own root []; writing what its account administers [A]; a member of an organization writing its things [A, Org]; a holder of a grant on a shared document D [A, D]; a link's grant [], signed as the link's thing; a recovery key acting on its account [], signed as the account.

### May-grant
A grant's value is a role, an `until` and a **may-grant flag** (decided: a flag, not a level). May-grant itself stays (decided): dropping it was weighed and rejected; it is no root cause of open bugs, and without it link joiners are either unnamed or able to evict each other.
- **G1. The path's may-grant.** A path gives may-grant on T at role r iff every hop gives at least r and its last hop either gives admin (a record edge and a descent among them) or is a direct edge carrying the flag.
- **G2. A may-grant grant.** An edge write whose path does not give admin on T applies as a may-grant grant iff it adds a grant for a thing with no current grant on T (an expired grant counts as none) and its path gives may-grant at its role r (G1). (So r is below admin: a path giving may-grant at admin gives admin.) The new grant may carry the flag ("up to its own role": the holder's own grant carries it). It carries no list, audits nothing, gets no verdict and is never trusted.
- **G3. A lower level is an arrangement** (decided): to let a person add readers and no more, a thing holds read with the flag and the person writes that thing; the person's path through it gives may-grant at read (G1).
- **G4. A holder adds people only where its own grant allows** (decided): a writer of a holder that holds admin on T grants on T by may-grant up to the chain's minimum (the path's last hop gives admin, G1), never as admin.
- **G5.** A lowering takes its edge down in role or in the flag, and a may-grant grant rests on its path's last edge for the flag and on the others for its role: clearing the flag on an edge puts the grants made by it in question (modelled: notes/path-model-findings.md 23, 54).

### The purge author
Who may purge an edit is fixed when it is written (spec/requirements.md Deletion); where the class includes its author, the write says which of its actors that is. Core picks no position on the path (decided).
- **How a write names it** (modelled, built: notes/path-form.md): each stated path carries an index i into [S, A1, ..., Ak]: 0 the thing signed as, j the thing Aj. One index per path. A write wanting two purge authors on one thing is two commits.
- The index is always present and has no default on the wire. A session's default is local configuration, written by the layer that understands what the session acts through, never by core.
- **What a purger must hold**: a request holds the `author` right over a delta iff the request's own path for that thing contains the delta's purge author (as the thing it is signed as or as a listed thing) and gives write on the thing, judged as a content write along that path at the request's key (modelled: `purges`, control `-purge-any-path`). So an edit authored as an organization is purged by any member writing through it, one authored as an account by any of its nodes, one authored as a node root by that node alone. A node removed from A and not from A2 still purges every edit authored as A2 on what A2 writes; what was authored as A it purges only by a request A's remover received and listed (modelled: story moves 38-40).
- **"Purge everything by this author"** names a thing and matches the deltas whose named purge author is exactly that thing, never every delta whose path contains it (modelled: control `-purge-contains`).
- **Delete keys**: level 2 (spec/crypto.md §7) is the write secret of the purge author; the writer holds it, since a content path gives write at every hop. Where no header is held, a snapshot's facts state the purge author (spec/commits.md §5 Purge, Without the header).

### Judging content
A delta on T with path P needing role r is valid iff every hop of P gives at least r just before the commit's key (grants' `until` at its `ts`) and no applied explicit lowering of a hop of P, taking P below r, is ordered after it; otherwise iff each such lowering's own list names its commit (a cut is answered by its own list and answers for itself alone: notes/path-model-findings.md 44), an addendum against it by a commit signed as another thing vouches for it (notes/account-membership-design.md §4), or P is **re-granted** (C1, C2; modelled: `first_by_right`, notes/path-model-findings.md 9, 56).
- **C1. Re-granted.** Every hop of P gives r in the timeline's final state (every `until` counted removed); the delta is then valid where it is ordered after P's **first point**: the latest, over P's hops, of each hop's first held write giving it r or above made by right (C2; a record edge or the record's key: from the start).
- **C2. By right.** A held edge write is made by right iff it is no self-removal or finalize and its grantor held the right at its key in this reading: every hop it rests on (its key hop first) gives admin just before its key, each `until` read at its `ts` (a list write also by O4, against the keys listed there), or, for a write that may apply as a may-grant grant, its key hop is listed and its path gives may-grant at its role there (O3, G1). Applied or dropped alike: a grant a later removal drops still counts (the collateral grantee, finding 9), and so does one the removed party backdated to before its removal (no new right, an earlier `ts`).
- It follows from the principle that a party with no right decides nothing. Rejected (finding 56): counting from each hop's first chained write (spec/permissions.md §4: by every value an earlier chained write set, never removed, `until` disregarded; control `-chain-ever`), where a grant by a party whose own grant had ended, or that a removal took, makes a re-granted holder's earlier content show; and chained writes reading `until` alone, where a party removed by a lowering, or a key that removed itself, still moves a first point back.

### Edge writes
Edge writes and list writes (O4) are the **edge-class** parts. An edge-class part applies at a point of a pass iff the key hop is listed there and:
- an explicit edge write: its path gives admin on the target;
- a may-grant grant: G2;
- a self-removal: its path gives admin on the holder (a thing leaving by itself: no edge), and it lowers;
- a finalize: write, and a role at least the grant's, along the path (spec/permissions.md §2, unchanged);
- a list write: O4.
Effective role (the maximum over paths) is no part of validity. No rule reads how many admins a thing has (§5, The last admin).

- **Resting**: an applied write is attributed to its path and **rests on** the key hop and each edge of the path; a self-removal rests also on the edge it gives up (modelled: `leave_in_question`).
- **A lowering** is an explicit write giving its hop h below what h gave, in role or in the flag, at its `ts`: an edge write giving below admin, a list write removing a key. **An end** (an explicit write leaving h giving admin at its `ts` with an `until`) is no lowering but a grant: it applies where its path gives admin in the pass, carries no list and is no dispute candidate. Taken as a lowering it fails a required property either way it is judged (modelled: notes/path-model-findings.md 38).

### Each lowering is judged once
Modelled (roles-model `paths`, `Rules::fixed`; notes/path-model-findings.md 16 to 18, 23, 27, 28, 32, 37) but for the two clauses marked *recut*. The walk is a run of **passes**. Each starts from the record edges and the records' owner keys and takes the held edge-class parts in key order (`ts`, thing signed as, commit ID), skipping D. Two things carry from pass to pass: the drop set D, and a **verdict** (applied or void) per lowering that has one.
- **The edge as restored**: the highest value h held since the last explicit write on it, in role and in flag, each value read with its `until` disregarded (a value already ended at its own `ts` restores what it names).
- **W1. A lowering with a verdict is not checked again.** Applied, it applies (whatever earlier writes now give its author, and auditing nothing) where it takes h as restored in this pass down or keeps it; where its value is above h as restored, in role or flag, it would raise h and applies only as any write does, by its path giving admin. Void, it is skipped.
- **W2. Any other part** applies iff its path gives what it needs there (Edge writes).
- **W3. A lowering with no verdict that applies there and takes h down**, as restored, in role or flag, is judged. It **puts in question** the held edge-class parts of other commits ordered before it that rest on h, are not in D and not void, and whose need at h (admin for a part applied by admin; for a may-grant grant its role on the hops before the last and role with the flag on the last; write for a finalize; listed for a part on a key hop) the hop as restored met and its new value does not. Its **drops** are those its list does not name, each with the other edge-class parts of its commit on the same thing (*modelled*: 37).
- **W4. Void.** The lowering L is void iff its drops would take its authority: `keeps(L)` fails, where `keeps(W)` holds iff every hop e of W's path keeps what W applied by: of the parts this pass applied on e before W's key, latest first, pass over each of L's drops (and of its commit's lowerings applied before it) and each grant for which `keeps` fails in turn; the first one left decides (e keeps admin iff it gives admin at W's `ts`; a key hop iff it lists the key), and with none left e keeps it iff it is a record edge or the record's key. Each step reads only parts ordered before the one it checks. Void, L does not apply and drops nothing. (*Recut*: the model's `keeps` also reads the remaining admin a lowering names; no such clause exists.)
- **W5. Applied.** Otherwise L applies; if it has drops they join D and the pass ends there. The next pass replays the parts before the earliest drop unchanged and walks on from it.
- **W6.** A lowering that applies without taking h down gets no verdict and audits nothing; one that does not apply gets none. A later pass reaching it applying and taking h down judges it then. A lowering goes at most once from no verdict to one.
- **W7. A commit of several edge-class parts** takes effect one part at a time at the commit's key, the parts on a hop of a path the commit states last (its key hop included: an owner key replacing itself applies whatever order the keys sort in), each judged with the earlier ones in effect; no part's drops reach its own commit (28, 37, 57).
- **W8. The walk ends** at a pass that adds nothing to D. Nothing is undropped. The reading is a function of the held commits and the trust set.
- **W9. Trusted writes.** A trusted lowering R's **seeds** (the held edge-class parts of other commits ordered before R, resting on its hop, that its list does not name and whose least need there R's value does not meet) start D before the first pass. A trusted write the settled walk does not apply is void and loses its seeds, all such at once, and the walk is redone from scratch without them: the one redo in the rule, bounded by the trust set's size.
- **W10. Disputes.** A dispute is a held explicit lowering of a hop whose holder (or key) is not its own, not trusted and not dropped by a trusted write, whose trust would change the node's reading (what applies, what is valid, the roles). Never a self-removal, a may-grant grant or an end. Reported; the walk acts on the trust set alone.

**What judging once gives** (modelled): a lowering applied at its key keeps its effect for good; where a later lowering drops it, its drops stay made (a **stray** drop). At a node trusting R, R's seeds act before the walk, so nothing of the removed party's that R drops is ever judged; at a node not trusting R the same writes act at their keys until R is reached. That difference is what trust is for (First received). The non-monotone fixpoint that would undo a void or dropped write's effects breaks safety (16).

### The list is its writer's
**Rule: nothing but its list decides what a removal keeps, every node reads the list as written, and its writer leaves out what the removed party aimed at the removal's own path.**
- **L1. Nothing is exempt and nothing is read as absent.** R's list alone decides which of the parts resting on h are kept, in R's audit and in a trusted R's seeds alike. The writes R's own authority rests on get no special standing: where one rests on h, R keeps it by listing it.
- **L2. What a remover names.** For R lowering h, written by a node holding the set `recv` of commits when it writes: the commits of `recv` resting on h. Content, purge requests, addenda and covers among them are all named. The edge-class ones are named by L3.
- **L3. What it leaves out.** Let `end(L)` be read in the writer's own walk over `recv` and R, with R trusted and listing L: nothing where R does not apply (a void R does not); else the earliest `ts`, at or after R's, at which a hop of R's own stated path stops giving admin (an `until` passing, or a write in that walk setting it below), or no end where none does (ordered: nothing, then any `ts`, then no end). The writer takes the edge-class commits of `recv` resting on h one at a time **in the order it received them**, starting from the list of everything else, and keeps commit c iff R applies with c added and `end` with c is no earlier than `end` without it. Where R applies with all of them named and no hop of its path has an end, all are named and the walk is run once.
  - So left out: the removed party's removal or demotion of the remover, or of whoever granted it where that drops the remover's grant (R would not apply); its end date on a hop of the remover's path, by its own write or through a made-up key it granted (the path would end: *modelled*, notes/path-model-findings.md 45); its shortening of a timed grant the remover acts by. Kept: every other lowering the removed party made, as received (decided: automatic), so a removal it made long before a theft stays made; a timed grant that is the remover's only standing (without it R does not apply).
  - **In the order received, not in key order** (modelled: control `-key-order`): the thief stamps as it likes, but cannot make the remover have received its writes before the honest history.
  - **Its own path only**: an end or lowering the removed party wrote on any other hop is kept as received, like every lowering it made while heard (notes/path-model-findings.md 19); the removal's result names them (notes/account-membership-design.md §4).
  - Cost: one walk where R applies with everything named and its path has no end; else one walk per edge-class commit of the removed party the writer received (a fight, or a remover acting by a timed grant).
- **L4. Readers check none of it.** A list that keeps what unmakes its removal leaves that removal void for every node alike; a remover that leaves out an honest earlier write has written a contest of it, which only nodes trusting that removal follow.
- It follows from the principle: a removal's statement is its path and its list; it cannot hold where that statement leaves it no authority, and nothing outside the statement is read. **Smell**, stated: L3 asks what a kept write does to the remover's own path, which no reader's rule asks; it is the writer choosing its own statement, and the writer is the only party that knows the order of receipt.

### First received
**Rule: in a fight a node stands with the lowering it held first, and with its own.** A **fight** is an explicit lowering R of a hop h and a seed of R (W9: an edge-class part of another commit ordered before R, resting on h, that R's list leaves out and R's value does not serve). Standing with R is trusting it: its seeds take that write before the walk, so the node reads in the world R's list makes; where the seed is itself an explicit lowering, the two are the sides of one fight. This is the default side of an admin dispute (decided: first received, a party with its own write, sides stick, the user may switch: notes/disputes.md), stated for the walk above. **First is a fact of the node's own readings**: R was first where a reading this node had applied R while it did not hold the write. Nothing else orders the two: not their stamps, not their IDs, not their place inside one update (the commits a node takes in between two readings). The rule is the same whoever wrote R: a node cannot tell an honest remover from a thief.
- **F1. Its own.** A node records every explicit lowering it makes (one that carries a list: no self-removal, may-grant grant or end) as trusted when it makes it; making it is a choice (F4). Its own are the commits it made, not those its key signed: a commit signed with its key that reaches it from outside (a stolen key's) is another party's.
- **F2. Held first.** When an update brings a node a commit of another party that is a seed of a held explicit lowering R, the node has no side in that fight (neither R nor a lowering that cannot stand beside it, F4, is recorded), and its reading before the update applied R (as a lowering, not a may-grant grant; whether or not it took h down there): the node records R as trusted. The seed test is W9's over what the node now holds; the reading is the one it already had; no trial walk. One side per fight is what makes a side stick: a node that recorded one lowering never records the one that lowering's seeds take, whatever its walk later applies, and is told of it (F5).
- **F3. No order, no side.** Where the node held the write before R, or first held both after one update, it records nothing: it never stood in R's world. It reads by the walk over what it has recorded, the write acting at its key, and R is an open dispute wherever its trust would change that reading (W10). A new node's first sync is this case (decided: a new node takes the walk's side); a node given its pairer's recorded sides starts from those (notes/account-membership-design.md §2). No rule reads an order inside an update, so none depends on one; counting both-at-once as R first would give a side no reading of the node ever held, and would give a thief's lowering the same claim when it arrives with an honest write it leaves out.
- **F4. A side is an answer.** A recorded side is no derived fact: it stays until the user chooses again (notes/disputes.md, Choices), and a trusted write the walk cannot apply is void there (W9). **Choosing R** records R as trusted and drops the record of every lowering that **cannot stand beside it**: one R's seeds take, one whose seeds take R, and one ordered before R that lowers a hop of R's own path (where it applies R has no right). Without the drop both sides of one fight stay recorded and the later-stamped wins whatever was chosen.
- **F5. The counter-removal is told.** Where a recorded lowering's seeds take an explicit lowering of another holder's hop, the node reports that one beside its open disputes for as long as it holds both and choosing it (F4) would change its reading: a node that recorded one admin's removal is told of the removal that admin's victim made against it (decided: warns on a counter-revocation).

**What follows** (modelled: roles-model `paths`, `Sim::sides`, `choose`, `countered`; notes/path-model-findings.md 47, 48, 50 to 53):
- **A remover reads its own removal**, whatever of the removed party's it had heard before making it (F1; L3 already leaves out what unmakes the removal and reads the writer's walk with it trusted).
- **A removal long held beats a backdated write**: a removed key's holder backdating a lowering of an honest admin to before its own removal loses at every node that held the removal first; read by the plain walk the lowering acts at its key, and what it dropped stays dropped (a stray drop) though the removal then drops it (issues/masked-backdated-lowerings.md has the world).
- **A thief heard first keeps the nodes that heard it** until their users choose (accepted: notes/disputes.md, "a thief acting first wins"), by a backdated lowering or by one stamped ahead: X demotes H stamped 7, heard at 5; H's removal of X at 6, arriving later, is to those nodes a write ordered before a held lowering that leaves it out, so they record the demotion (F2), are told of H's removal (F5) and read as H does once they choose it (F4).
- **An honest node on the other side acts for that side** until its user chooses: it answers no removal its walk does not apply (no addendum for the removed party's earlier writes), cannot answer where the thief, still an admin in its reading, took its own path, and a cover it makes carries the removed party's late writes for good, as a cover by a writer not yet holding the removal does (the accepted window: notes/path-model-findings.md 26, 50).
- **What the honest side is promised, per node**: a node that held every honest lowering it holds first (or made or chose it) reads safety, liveness, the remover's own path and one reading with every other such node; any other node is shown each honest lowering it does not apply (W10, F5), and choosing those shown reads as the first kind does.
- **Why first held and no trial walk**: a write ordered before a removal and arriving after it either was made before the removal and not received, or was backdated; the list says it was not received, and this node saw for itself that it was not here.

**What it does not give**
- A node with no order reads by the walk and is shown the removal as a dispute (W10), one candidate at a time. Two removed keys' backdated lowerings of the same admin mask each other from that test: trusting either removal alone changes nothing, so the node reads without that admin's writes and is shown nothing (*modelled*: issues/masked-backdated-lowerings.md; Open 2).
- A recorded lowering's seeds are W9's, which read no restored hop, so they can take more than its audit would, its own authority included: the lowerings a node recorded on a thief's side can be void together, the node then reading by the plain walk (*modelled*, counted: notes/path-model-findings.md 51).
- Rejected: trusting every removal from the moment it applies (the same readings at nodes that held it first, but every component with a removal then walks with a trust set, and a new node still has no order); a trusted removal's list carrying trust to the lowerings it names (it reaches no node F2 does not, and a node trusting nothing gains nothing from it); a choice that only adds its lowering (*modelled*: control `-choice-adds`); recording a lowering only where the walk judged it, not where it applied taking nothing (*modelled*: variant `-lowered`, notes/path-model-findings.md 52; a reader that holds a removal before any write of the removed party, whose grant reaches it as evidence only with the backdated write, applied the removal taking nothing, would record nothing, and the backdated write acts).

### What it gives
Each a hand world (core/test/roles-model/src/paths/tests.rs), modelled:
- a removal listing nothing, by a party its victim granted, is void, raises no dispute and drops nothing (`a_removal_whose_drops_take_its_own_standing_is_void`);
- the removed party's backdated grant to the remover, timed or not, and its grant to a made-up key that re-grants the remover, are unlisted writes resting on h and fall like any (`nothing_through_the_removed_edge_is_exempt`);
- a list naming the removed party's removal of the remover voids its removal, so its writer leaves it out; an honest earlier removal of the granter that listed the remover's grant is kept (`a_list_keeping_what_unmakes_its_removal_voids_it`);
- a removal made under a grant a later removal drops keeps its verdict at a node not trusting the later one, and is never applied where it is trusted: the later removal is shown there as a dispute (`a_removal_whose_author_falls_later_keeps_its_verdict`);
- a removal whose drops take the grant its author's granter holds is void (`a_lowering_dropping_its_granters_grant_is_void`).

**What holds where** (modelled; recut at §6): at nodes that held the honest removals first, made them or chose them (First received), safety (a thief holding a stolen key keeps or regains no role, cannot void its removal, cannot bring back a party removed earlier), liveness, honest history kept, the remover's own path kept; at every node, one reading (a function of the held commits and the trust set, any input order), no gain by a party that never legitimately held the right, and no dispute in an honest history where nobody lowers anybody concurrently.

**What an idle write changes** (modelled, counted: notes/path-model-findings.md 34 to 36): a held commit the reading does not apply mostly changes nothing users observe; it can decide a fight among admins each holding the right at their write, unshown. Decided (Tess, issues/admin-fights-not-always-shown.md): a dispute is reported where a node's trust decides the reading; nothing is built to show the rest.

**Cost** (modelled: notes/path-model-findings.md 17): a lowering that drops nothing costs its place in the walk; a void one its check (the setters along its own authority: k void lowerings by the last of a chain of k grants cost k² setters read); an applied one that drops costs its drops and one restart from the earliest of them, once.

**Rejected** (each modelled and failing: notes/path-model-findings.md 12, 15, 16, 38): exempting the writes R's path rests on from its audit; reading as absent a list entry that lowers an edge R rests on; applying a lowering whose own drops take its authority; undoing a void write's drops by redoing the walk (a fixpoint that is not monotone); an end date judged as a lowering; a rule every node judges for the last admin (§5).

### Kept unchanged
The edge as restored; lists by commit ID with own covers (a list naming a cover names what it carries); covers by copies (a cover made by a writer not yet holding a removal carries the removed party's late write for good: the accepted window, notes/path-model-findings.md 26); addenda; `until` and self-removal auditing nothing; trust sets; role cycles. **Keys do not follow paths**: who reads, whom a rotation boxes, what a departure forces to rotate all stay on effective reach over every grant (spec/permissions.md §3); only validity is path-judged.

### What changes for users
- **Removing M from A** touches every write whose path passes through (M, A), on A and on everything A reaches, and nothing M wrote by another path. Removing a key from a thing touches every commit that key signed.
- **A write whose path is valid and another would also have been** is judged by its own path: it falls with that path's removal unless named, vouched for or re-granted. Its writer's node is told (spec/permissions.md §6, own commits) and may write it again along a current path. Which path a node states is writer policy; the default is the session's configured path.
- **A writer cannot pick a path that survives a removal it should not** (argued; modelled for the story's thief): a removal audits every write through the hop it lowers, and a path naming a hop the reader holds no write for is unjudgeable, never valid (§2).

### osis-perm
Validity of a write is a point query per hop of its path instead of a maximum over paths; the walk applies an edge-class part in O(hops); a lowering finds what it puts in question by an index hop → parts. `roles_on` and effective reach stay for keys, sync units and `holders`. The built walk (osis-perm `paths`, unused) and the call on it: notes/redesign-plan.md, D1 result.

### Where the path sits
Header: `signer` is the tid of the thing signed as, with the owner key that signed (the wire form is the spec brief's: the key or its hash); `path` in one of two forms: one path with its purge-author index, or the split form with each thing's path sealed under that thing's path key (built: notes/path-form.md).

## 2. Evidence in the sync unit
**Rule: what a reader needs to judge a held commit is in the same unit, a function of what the unit holds now; nothing is placed for its own sake and nothing is kept for a write that left.**

### What a unit carries
- **E1. Evidence of a sync unit U** (decided as the direction; modelled: held-model `evidence`, notes/evidence-model-findings.md): the least set holding, for every commit with a body under U's sync ID (role commits kept included): the records of the thing it is signed as and of every thing on its paths and descents; every held list write on its key hop (Owner keys, O3); every held edge write on every edge of those paths (grants, changes, lowerings, each lowering whole with its list: E4); closed under the same for those writes' own key hops and paths. It is in U's required set beside its bodies, as copies of one role commit's parts on one thing each, logged by any node holding them and U (spec/sync-judgement.md §1-§2 Own store, unchanged).
- **E2. A function of holdings.** Each node computes E1 from what it holds now, at every change of its holdings or of U's things, never once at logging: when a thing leaves U, what U's remaining bodies still need of that thing's role commits becomes copies (modelled: notes/evidence-model-findings.md 2, 4). When a commit leaves (compacted, forgotten, dropped as invalid), the paths only it used leave the evidence and their copies go with no tombstone.
- **E3. A commit carried under several sync IDs** has its evidence under each: the same copies, one blob per (commit, thing) wrapped under each sync ID whose unit needs it, placed where that unit's bodies do not carry the parts (checked for today's certificate copies: spec/sync-judgement.md §1 Certificate blobs).
- **E4. A removal's list is in the removal** (settles notes/a3-spec/README.md, the question of a removal carried by a rotation arriving without its list; Tess's first candidate). A lowering's list is part of its commit, as built (spec/permissions.md §5.1 Frontier: commit IDs, inline or linked), and every copy of the lowering carries it whole. So whoever holds a removal holds what it keeps: no reader waits on a list part, no verdict is "not listed" for want of one, and a removal carried down by key rotations two grants below judges as it does at home. It follows from §1: a removal's statement is its path and its list, and a write is never judged apart from its statement.
  - Cost, stated: a removal's size is what it lists (32 B per commit of the removed party the remover still holds uncovered: an own cover takes the rest), carried wherever the removal is evidence; a reader of one thing learns how many commits the removed party made elsewhere through the removed edge, as today; a removal whose role commits alone pass the list bound cannot be written, as today.
  - Rejected: a list root with a leaf per thing kept under the removed-from thing's sync ID (the removal then arrives where its leaf does not, the removed party's listed writes waiting there for good: notes/evidence-model-findings.md 35; and every rule tried for where leaves live was either placed-once state or kept every leaf with its removal for good). A per-thing form may return as a size measure only under a carriage rule by which no holder of a removal can lack a part it could need.
- **Not every actor that could write**: that costs an entry under every unit a holder reaches per roster change of that holder, and a key handed down to everyone above, which every removal would force to rotate (argued). Additions travel as their writes need them.

### How a removal reaches a far thing
Decided (Tess): no eager delivery. Nothing logs a removal anywhere for its own sake.
- **D1. Where it is evidence.** A node holding a removal R and, under U, a body whose path uses R's hop has R in U's required set by E1 and logs its copy there if it can stamp U (a writer); the copy leaves with the last body it judges (E2).
- **D2. With the next key rotation.** A writer rotating a thing's keys carries the demotions it holds in the keyset (spec/crypto.md §4 Carried demotions), each as the whole removal, list included (E4).
- **D3. Role changes travel** under the removed holder's own sync ID and the sync IDs whose keys open it (spec/permissions.md §4), unchanged.
- **D4. A reader's deposit on sight, promoted form** (settled; modelled: notes/evidence-model-findings.md 41, §6): a node holding R and such a body under U that cannot stamp U deposits R's copy under U (spec/sync-inbox.md §3) where U's sources show none; a node that can stamp U, holding the deposit, logs it by D1, and readers judge only by what is logged. It is D1 with "logs" read as "deposits": no new duty, no record per removal, the copy leaving as in D1. Built, if at all, in this form only. Rejected: readers judging by unpromoted deposits, the depositor depositing again while the body stays: exactly the two troubles that need a mechanism of their own (a standing duty by another name; an unpromoted deposit treated as held evidence). Where no node that can stamp U syncs it, the gap stays.
- **The gap** (decided: an open bug in an issue, not something to build around): a thing no remaining member writes, its readers served only by stores, shows a removed key's later writes until a node holding the removal syncs it.
- **What a far reader shows meanwhile** is within spec/requirements.md as written (a node missing data reads as if it never had it; a removal binds the nodes that receive it).

### What follows
- **Pending**: a part is unjudgeable while a hop of its path has no held write putting it, or a record on it is missing; it pends under Pending storage and is examined again as role inputs move (checked for today's form: spec/commits.md §4 Unjudgeable, Pending storage). A commit judged on missing evidence is never judged invalid for it. A reader holding part of a path's evidence (an earlier lowering not yet arrived) finds a setter on every hop and judges: no rule over the held set tells partial from complete evidence, so a deposit's promotion and a delete at a store wait for a complete pass of the sync ID (spec/sync-status.md §1; modelled: notes/evidence-model-findings.md 5).
- **Invalid bodies are dropped at once** (decided, as built): a reader drops a body it judges invalid; no drop waits for a complete pass and nothing is kept aside. A write turning valid comes back from whoever still holds it (a store within its caps, the node that held the evidence making it valid) and is gone where nobody does. The loss is stated: where every holder dropped it and its writer is gone, a write is lost though a node holding everything would show it.
- **Nodes keeping U unread** store and serve evidence entries as any entries (checked: spec/sync-judgement.md §6).
- **What goes** of spec/permissions.md §4 and spec/sync-judgement.md §1-§2: chain certificates over any path; "closed under authors"; each path thing's current `keys.0` commits as evidence; account rotations as header-only copies, thing lists and list blobs; the duty to log one's account's chain on first logging under a sync ID; a removal travelling for `ROLE_KEEP` (it stays while it is evidence, E2). **What stays**: record blobs; a grant naming a holder travelling under the holder's sync ID with the target's boxes and `sync.0`; a holder's public keys under the target's sync ID for sealing (§3, The card); destroyed things' frozen role data; Stranded holder keys.
- Readers see a holder's members only as far as paths show them, so `holders` shows less to non-members than today (argued intended: those outside a holder see the holder act).
- **The three points an alternative must meet** (argued): one blob for every reader (evidence is a certificate copy under a random blob key with a wrap per sync ID; handing a holder's roles secret down fails, since every removal anywhere below would rotate it); work per roster change (a grant costs nothing until its first use in a unit; "every possible actor" owes an entry under every unit a holder reaches per node change); size (the paths of a unit's writers and their granters, independent of any organization's size).

### Readers hidden from each other
issues/readers-see-readers.md wants an option under which reader-level grants open only for holders at write or above. No conflict with validity or evidence (argued; not designed): content needs write at every hop, so every edge a content path names is a writer-level grant, which every reader still opens; an edge write is sealed for writers only when the value it sets is at or below read and the entry it ends was. To settle in that design: an act made at read through a holder shows the target's readers that member's reader-level edge as evidence, so such acts are left to writers or reveal their maker.

## 3. Public things
**Rule: a thing is public by granting read to one well-known thing that nobody can sign as.**

### The public thing
A well-known thing **public**: its record and secrets are constants of the protocol, so every node derives its KEM keys, role secrets and static entry. Its record names no mint admin and holds no owner key, so nobody signs as it and nobody adds a key (Owner keys, O4: no admin exists to add the first); nothing holds a role on it, so no path passes through it. **A thing is public by granting public read** (Tess): one edge on the thing however many read it, and nothing on it showing where its owner writes. **Every thing's keys count as opening what public reads** (Tess; a clause of spec/sync-set.md §2 T's keys open), so a strong reference brings a public thing into the referrer's sync unit like any thing the referrer can read. It is a special case and may be one (Tess); every difference from an ordinary thing is listed here and nowhere else, so the whole set can be weighed or replaced together. A new difference found in building is added to this list before it is built.

**Smells**, each a rule that does not follow from the ordinary ones, judged by every node alike from the write alone:
1. **Constants**: the one thing not minted: its record, tid and secrets are built in; no evidence copy of its record, no `keys.0`, and a box to it (the entry box of a step included) takes the symmetric form under a key derived from its role secret (every node holds the recipient's secret, so a KEM ciphertext buys nothing). It has no sync ID: a grant it takes travels under no sync ID for it, and whoever reads as public enters the target by public's static entry in the target's own steps.
2. **An edge write naming public sets at most read, without may-grant**: one setting write or admin, or the flag, is bad input. Those roles' secrets are delete keys and the unit's stamping key, which would let anyone delete or store at a node keeping the unit unread (checked: spec/crypto.md §7 Levels; spec/requirements.md, Data a node cannot read).
3. **Public takes every grant**: no write path to it, no external signal, no inbox, no delivery (§4's refusal never applies).
4. **A departure at or below read forces no rotation while public reads**, and no step of the unit's sync ID is owed for it: the departed party still opens the role as public (derived from the rule's purpose, spec/permissions.md §3 Required rotation; a rule-text exception all the same). Departures above read rotate as always; removing public rotates read, boxing the named holders, and is due a step.

What follows from the ordinary rules (no special case): nobody leaves or lowers public's grant as public, writes as it, redeems as it or fires as it, since no key signs as it; a thing's admins remove it by an ordinary removal.

Every act open to a reader, for a party whose only role is through public:

| act | may it | by what rule | what a node keeping the unit unread checks |
|---|---|---|---|
| read | yes | holds public's read secret, the box to public | nothing |
| enter the unit | yes | public's static entry is in the claim set as any static reader's (checked: spec/sync-ids.md §3 Claim set) | the claim, as any; it can test for the public entry, so it knows the unit is public, as anyone holding the sync ID does |
| leave, lower the grant | no | nobody signs as public | nothing |
| be removed, by the thing's admins | yes | an ordinary explicit removal, with its rotation of read | nothing |
| deposit | within the budget, like any reader | the deposit key derives from a seed readers hold (checked: spec/sync-inbox.md §3); what is deposited is valid only if it would be from a stranger: an enabled external fire | signature and budget, as today |
| history add | no | it is a commit; the thing the party signs as holds no role | nothing |
| external fire | as any outsider, signed as its own thing, where the signal is enabled (§4) | unchanged | deposit signature and budget |
| be granted write, admin or may-grant | no | smell 2 | nothing |
| rotation of the read epoch | boxed like any holder, symmetric form | ordinary; smell 4 removes rotations that serve nothing | nothing |
| stranded (left out by a rotator that did not hold its grant) | asks any connected writer, naming public as the holder to re-seal | the receiver checks the holder itself (checked: spec/permissions.md §4 Stranded) | nothing |
| serve the unit to others, answer offers | yes | it holds the unit like any reader | |

- **The deposit budget of a public thing is open to everyone**: no special case; it is the reader budget the requirements already call best effort (checked: spec/requirements.md, Data a node cannot read). Tess would rather public could not deposit, but only if that were a check in one place; it is not (the seed lies beside the keysets, which every reader opens), so it stays open.
- **To say in the API**: a public thing's dependents are public; a thing that grants a public thing read is read by everyone through it; a holder with may-grant at read may publish (it may already add any number of readers).

### Profiles and contact-only information (the schema's)
- A **profile** is a schema concept: a thing with a name and a picture, public, with a sync ID of its own. A writer puts a strong reference to its own profile, as ordinary data, in the thing it writes in (decided). The write placing it states its actors, which is the actor naming its profile, checkable by any reader without reading the actor.
- It is reached by the reference: every thing's keys open it, so the strong brings it into the referring thing's sync unit, and a reader served only by a node keeping the referring unit unread still fetches it. Nothing about profiles is in evidence and no rule pulls things in. Cost: each commit on the profile is an entry and stamp under every unit referencing it; one profile blob under every unit its owner writes in links those units at a node keeping them unread (issues/sync-units-linked-at-rest.md).
- Rejected: granting the referring thing read on the profile (its roster would list every thing its owner writes in); a ticket or a link's secret in the reference; proving whose profile it is from the profile's side.
- **Contact-only information** (decided): the dial list is in a thing of its own, read by those its owner shares with; where it sits and who reads it is the schema's. The dial aspect stays core's: a node dials what it reads in that aspect on any thing it holds (argued).

### The card: where a thing's inbox is named
To grant to a thing A it holds no role on, a party needs A's tid, A's current KEM public key for each role granted, and, for delivery, A's inbox: its tid and record, its read KEM key, its sync ID and its deposit seed (checked: spec/sync-inbox.md §2-§3).
- **The card** (argued; name open, here `card.0`): a core aspect holding exactly that material for one thing A, written on any thing A's members choose. **It counts as A's only where the write placing it states A as an actor** (A is the thing it is signed as or a listed thing, or the thing it is on is A itself): the same check as a profile reference.
- **Who can grant to A is who reads a card of A**: on a public thing anyone can; on a contact-only thing, the contacts can. A's members need no card.
- **An admin-only aspect of A names its inbox and its cards**: A itself by default, another thing A administers where storing and forwarding A's messages should not mean keeping A's whole unit. A node rotating A's read role, or the inbox's deposit seed, writes the cards it can; a card it cannot write is stale until a member that can does (checked: spec/crypto.md §4 Stale).
- **A holder's keys under the target** (kept from today, spec/permissions.md §4): the grant commit carries the card's key material into the target's role data, so every node that rotates the target can seal to A. That is the only place a thing that is not externally grantable publishes KEM keys (decided).

## 4. External signals and grants from outside
**Rule: a thing takes from outside only what its admins enabled, and a grant counts for its holder only once the holder took it.** Decided (Tess): grants from outside stay gated, as below.

### The routes (checked: spec/sync-inbox.md §2-§5, spec/sync-judgement.md §2)
A grant naming holder A reaches A, its granter holding nothing on A, by: (1) a box sealed to A's KEM key and a sealed `ticket@~0` fire on A's inbox; (2) a deposit of the role commit under A's own sync ID, which A's writers then log as their own copy; (3) a ticket for the target in any value one of A's members reads. Route 3 is only handing over a secret and makes A a holder nowhere. Routes 1 and 2 are closed by the rule below.

### The rule
- **The setting**: a thing's admin-only `retention^.0` entries naming external signals (spec/commits.md §5 The setting). A thing's admins **enable** an external signal by an entry of its own naming it; none is taken otherwise.
- **External fires** (built: spec/permissions.md §5.2 External fires; modelled: held-model `ExternalFires::Enabled`): a fire of external signal `s` on N valid by its author's authority is valid whatever the setting; any other is valid iff N's **current setting** enables `s`. Current, not "in force at the fire's key": a fire's `ts` is its writer's word.
- **Externally grantable**: A is externally grantable iff its inbox enables `ticket@~0`. One switch with taking tickets (decided).
- **What enabling publishes**: the cards of A (§3). Disabling writes the cards empty and rotates the deposit seed, with the deposit-only step that follows (checked: spec/permissions.md §3 Sync ID role keys).
- **What A takes**: a role commit with an edge write naming A on X is **taken** by A iff it states a path to A giving write on A (beside X's path, in the same header), or A is externally grantable at its key and one of A's writers accepted it (a reference to X in A's unit). Only a taken commit is in A's unit's required set with X's boxes to A and X's sync ID; A's members take secrets through A, and count A's role on X, only by taken grants. An untaken grant stays in X's roster: X's readers judge X by X's timeline alone.
- **A role change needs** admin on the target (or may-grant, to add a new holder: §1) and write on the holder, or the holder externally grantable and one of its writers accepting; a holder may always drop or lower its own grant (decided).
- **Without the switch: write on A gives the right to grant to it** (decided), for a new thing and an existing one alike. A reader of A may not. Cost, stated: a writer can attach outside things, adding to what members read and to the keys that change when a member is removed.
- **The granter's node, refused**: an edge write naming A is refused locally, before signing, when the node states no write path to A and holds no card of A whose inbox enables tickets. The error names the setting, never keys.
- **No grant waits on the grantee's side**: a grant that is written is valid on X at once; only delivery of the ticket is pending, shown as such.
- Ordinary signals have no switch (decided). How an app enables a signal, and the default per kind of thing, are the schema library's.

## 5. Core without accounts
**Rule: core has things, owner keys, roles and paths; an account is an arrangement of them a library makes.**

### No account root
With the account an ordinary independent thing A, it has a roster (its members), a unit, data and dependents, and rotates as any thing. So home is A, and the account's private things are A's dependents (argued).
- **To write down**: a role on A reaches everything A holds a role on anywhere (spec/requirements.md Permissions). Granting anyone a role on home grants all of the account's access, so a space to share is another realm.
- **A thing minted with A is a dependent of A like any** (issues/behaviour-depends-on-own-keys.md).

### The last admin
**Rule: a thing goes adminless only by a write that says so, and saying so is the writer's check** (decided: no rule every node judges).
- **A1.** Before signing an edge write that removes a direct admin edge of T, lowers it below admin or gives it an `until`, the writer's node reads its own walk: where no other **standing admin edge** of T would remain (a direct admin edge on T, the record edge included, with no `until`, whoever its holder), it refuses with an error unless the caller said the thing may go adminless (built: notes/permissions.md, The last admin).
- **A2.** No reader judges any of it: an edge write applies by its path alone (§1). Two sole admins leaving at once leave the thing adminless, as a deliberate leave would. Two admins removing each other leave one: the earlier-stamped removal applies and the later finds its author without authority (the admin dispute).
- **A3.** A timed admin grant is no standing admin for the check (decided): it is a removal already written.
- **A4.** An owner key changes nothing here (decided): a write removing the last admin grant says so, whether or not the thing lists a key. A thing with a key and no admin (a node root) is ordinary; its key acts as it (Owner keys, O5).
- **A5.** The check may go if it is ever in the way (Tess: not a big deal).
- **What the every-node rule did besides**, and what does it without one: it kept a remover's own path against an end date the removed party put on it (§1 L3 does); nothing else rested on it (*modelled*: notes/path-model-findings.md 45, 46).
- **An adminless thing**: admin edges and admin-only aspects change no more, so its settings, enabled external signals and cards are frozen; nobody issues a step of its sync ID; holders keep reading and writing as granted; writers still rotate the roles at or below write, self-removals and finalizes below admin still apply, and a holder with may-grant still adds holders. An owner key recovers it (Owner keys); nothing else does.

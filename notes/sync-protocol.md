# Sync protocol: wire choices, osis-proto, osis-label
> Summary: Why the sync wire is laid out as it is (fixed prefix, Padmé marker, range reconciliation, request/reply framing, what opens bind), and how osis-proto (frames, Hello, messages and their decode caps, reconciliation with measured round trips, the serving and client engines, Sync replay, Replace, relay-only gate, client port) and osis-label (blobs, chunk trees, large values, steps, proofs, bundles) are built. Not here: reply caps, windows and stall bounds (notes/flow-control.md); the host's store and policy (notes/serving.md); node sync (notes/node-sync.md). Layouts: spec/wire.md.

## Wire choices
- The blob prefix is a fixed byte layout so a host parses it without a CBOR decoder; the AEAD binds it as AD so a reader cannot re-prefix a ciphertext (new expiry or commitments) under a fresh blob ID.
- Padmé length recovery: a `0x80` marker then zeros inside the ciphertext (ISO 7816-4 style). One byte, no length field, and canonical because the padded length must equal `padme(len + 1)`.
- Header lists, the delete-key list and purge go by link above `CHUNK_THRESHOLD` (128 KiB) up to `MAX_LIST_BYTES` (64 MiB); header-list chunks carry the level-2 commitments only (notes/crypto.md).
- Range reconciliation: Negentropy-style additive fingerprints (sum of IDs mod 2^256 plus count, hashed), so a sorted ID index answers any range incrementally; 16-way splits, lists at 32 IDs, about log16(n/32) round trips. Rejected: a hash of the concatenation (not incremental); Negentropy's full encoding (bound compression and timestamps: more rules for little gain).
- Request/reply by id over length-prefixed frames; both Hellos go out at once, so negotiation costs no round trip; per-entry status, so a batch partly succeeds; a Status names a stale key (9) but never carries the head (notes/label-access.md).
- Opens bind the opened side's Hello challenge and static key (no replay elsewhere); stamps, deposits and deletes do not, so stamped entries and deletes stay relayable.

## osis-proto
- Modules: `frame` (`FrameDecoder`, `encode_frame`); `hello` (Hello, `negotiate`, `estimate_offset`: median of per-sample offsets, Hello counting as one sample, reported after three pongs; samples with a round trip over 10 s are ignored, as pings held across a suspend); `msg` (`Message`, one variant per kind over osis-label's `Step`, `ClaimSet`, `Proof`, `DeleteItem` and the `SecretBox` entry box; `decode` enforces every cap of spec/wire.md §11.2; `Rejected::code` gives the Error code); `dec` (typed reads of decoded arrays); `rbsr`; `store` (`LabelStore`, `MemoryLabelStore`); `serving` (`ServingSession`); `client` (`ClientSession`); `relay` (`RelayGate`); `api` (client-port messages); `bundle` (`BundleImport` over osis-label's reader and importer); `examples` (a fixed label and one message per kind, for tests and vectors).
- Decoder rules beyond the layouts: mode 1 lists at most 32 IDs, mode 2 lists 1024 then 32, IDs ascending and inside their range; ranges sorted, disjoint, `lower < upper`, an end bound only last; id 0 only on Error, Push and Notify (kind 24 is Auth); a step at most `MAX_STEP_BYTES` (323). Message nesting depth 6. Both sides take only a Hello-sized first frame (`MAX_HELLO_BYTES`, 256).
- **Reconciliation** (`rbsr`): the requester sends 256 ranges per message, pipelined, each batch with a token; a reply range outside what its batch asked (or a mode 2 range not answering one of our mode 1 ranges) is dropped. Reference split: subrange i holds own IDs `i*n/16..(i+1)*n/16`, bounds the full first own ID. Measured: 10 000 IDs with 100 differences each way, 2 round trips (unit test); 10^6 IDs with 10^4 differences, 3 round trips, 5.3 MB up, 5.9 MB down. Under a dense difference (most of a message's at least 16 mode 0 ranges mismatched) subranges list at most 8 IDs (`DENSE_LIST`); with 32, 35 MB up. A worst-case ReconcileReply (256 mode 2 ranges of 1056 IDs) is about 8.9 MB, under `MAX_MESSAGE` (9 MiB). The client abandons a reconciliation past `MAX_RECONCILE_MESSAGES` (4096), 2^21 differences or 2^17 queued ranges.

### Serving engine (`ServingSession`)
- `handle(now, &mut dyn LabelStore, ServingInput) -> Vec<ServingOutput>`. Cross-connection work goes through the driver: `ServingOutput::Changed(label)` goes as `ServingInput::Changed` to every connection; `ServingOutput::Relay` (a relay-only entry, accepted by stamp, not stored) as `ServingInput::Relay` to every other connection, which pushes it to a subscription of its label.
- **Nothing reads the path per request.** The store keeps indexes per step added (`LabelStore::step_with_sync`, the newest step per sync key; `child`, genesis as the child of none; osis-host's `V`/`W` rows), so an Open is at most three lookups whatever the proof (`osis_label::evaluate_open` over a `PathIndex`) and a Path page reads only the steps it sends; a claim proof loads only its step's set (`LabelStore::claim_set`, a shared `Arc`). Stamps, deposits and keyed deletes check the head's key, then the `OLDER_KEYS` (8) newest distinct earlier keys (code 9), else code 1, from `LabelStore::head_keys`, which the store keeps per head (`HeadKeys::child`; osis-host's `K` row), so these checks, which need no open, never read the path either.
- A Reconcile reads only the live IDs inside its ranges (`live_ids_in`; ranges sorted and disjoint, so at most the label once per message). A delete by delete key of an entry no longer held is refused (the prefix cannot be checked); a held one's prefix comes from `LabelStore::blob_prefix` (osis-host keeps it in the blob's `R` row), never the whole blob.
- The store applies policy: caps (the ephemeral cap included), the deposit budget, delete rate limits (`delete` return codes); ephemeral entries (prefix class) go to `Put::ephemeral`; an identical re-upload changes nothing and logs nothing.
- **Replace** (spec/sync.md §5, the wire `entry`'s 4th field): the engine checks each delete proof (`delete_auth`, shared with Delete; a name not held is skipped unchecked), the store plans and applies all or nothing (`Put::replaces`, blob IDs; HostStore `plan`/`replace`: the room freed per charge kind is credited to the cap check, removals logged after the add so a holder applies the cover before the deletion, delete-rate tokens taken before the add). In Upload and Sync entries alike; at most 1024 replace items per message (the same cost as a Delete). On co-reader peers (`PeerStore`) a replacement hides the entry from peers after the upload is applied. Node sync sends it only for a capped purge rewrite (notes/sync-convergence.md).
- **Relay-only** (`relay`, `RelayGate`, in memory per host or co-reader peer): admitted by prefix expiry and size, counted against a per-label rate (`RelayLimits`: 6000 relays and 32 MiB per minute; host policy `relays`, `relay_bytes`), pushed once per blob within its expiry window (a repeat is answered OK and pushed to nobody); at most `MAX_RELAY_SEEN` (2^16) pairs remembered, past which the earliest-expiring is forgotten and a replay of it is pushed again.
- **Sync**: with a log cursor, the log after it; without one, a replay of the live entries in blob ID order paged by a replay cursor `[BLAKE3("osis v1 replay" || log_id)[..16], first 63 bits of the last ID]` (63 bits: the first 8 bytes overflow the wire's integers above 2^63), the last page returning the log cursor taken at the start (spec/wire.md §11.2). The connection remembers the start, so a replay continues only on its connection (elsewhere: Error 10). Two IDs sharing their first 8 bytes across a page boundary would skip the second (2^-64). Add events of the requester's gained IDs and of entries in that Sync are left out. A subscription starts at the connection's last complete Sync cursor for the label (else the log head), so a client that syncs before subscribing keeps the push cursors; pushes use the last Sync's inline limit.

### Client engine (`ClientSession`)
- `handle(now, ClientInput) -> Vec<ClientOutput>`; commands are batched under the caps and paged replies followed (Sync `more`, Path `more`, Fetch prefixes). A page without progress (the same cursor, or 16 pages in a row without events) ends the exchange with `PeerError`. `Command::StopPath` stops following a label's Path pages (the node stops on a bad page or when nobody waits). A Want naming an ID the Sync did not list as gained is dropped. A Push while a Sync of its label runs gives no cursor (the Sync's later pages still bring older entries; a crash before the replay's last page would lose its remaining entries).
- Policy stays with the node: a stale-key `Step` is reported, not walked; `Want`, `NeedReconcile { trimmed }` (Error 10 or 15, whose Sync entries are re-sent as an Upload, or over 4096 gained IDs; `trimmed` for 15) and `Reconciled { need, have }` are answered by the node with Upload, Reconcile, Fetch. After a reconciliation a cursor-less Sync at inline limit 0 gets a fresh cursor (metadata only).
- **Client port** (kinds 24-29, notes/client-port.md §2, module `api`): `ServingSession::with_port` hands Auth/Call/Sub out as `ServingOutput::Request` and answers by `ServingInput::Reply` (bounded by the request's `max_reply`); Notifies go as `ServingInput::Notify` after `WantRoom` → `Room { budget }` (the push rule, `room`). The session itself answers Call/Sub before an answered Auth (1), a reused live Sub id (2), past `MAX_SUBS` (4096; code 4) and every Unsub; without `with_port` (a host) the kinds get Error 11. `ClientSession` takes `Command::{Auth, Call, Sub, Unsub}` with caller tokens and reports `ClientEvent::{Reply, Notify}`; a live Sub's id is never taken by another request. Allowances: `max_reply` for Call/Sub, `SMALL_REPLY` for Auth/Unsub (`client::allowance`). Tests: tests/it/port.rs.
- Co-reader peers use one engine per direction, not both on one stream: the dialer runs `ClientSession`, the acceptor `ServingSession`; co-readers each dial the other (notes/peers.md).

## osis-label
- Modules: `blob` (the prefix with its class, `Class`: durable, ephemeral, relay-only; frame/open; blob ID; `host_prefix`; `Prefix::for_keys`/`for_delete_keys`, the one place commitments are computed; prefix/header agreement `Prefix::agrees`; the blinded key at a level `Prefix::key_at`; `unwrap_any` newest first); `tree`; `chunks`; `step` (`Step`, `StepId`, `StepKeys`, `register` (genesis or child; claim set and entry boxes; a step without rotation passes the parent's keys), `verify_path`, `path_to`, `ClaimSet`, `open_entry_box`, `match_secret`, `genesis_label`); `auth` (`Proof`, `evaluate_open`, stamps, deposits, `DeleteItem`: `sign` by the label delete key, `sign_by` a level's delete key plus `key_for_level`'s label key, `verify`); `inbox`; `addr` (strict `address` values and their text form; base64url is osis-base's); `labels` (`label.0` records to verified steps); `link` (`ShareLink`, `RecoveryCard`); `bundle` (`BundleWriter`, `BundleReader`, `Importer` yielding `BundleEvent`s).
- `tree` re-exports osis-commit's chunk trees (streaming `TreeWriter`/`TreeReader` over `TreeSink`/`LinkSource`; errors are `osis_commit::Error`, converted by `From`). The reader is retry-safe: a `Missing` blob can be fetched and the call repeated; it checks every length it passes and `seek`s by node lengths, fetching only the path; `HashSink` gives shape and hashes without encryption. `BlobWriter`/`BlobReader` frame chunk, node, page and link-page blobs under a `Framing` (dedup secret, expiry, delete keys; `keeps(prefix)` is the re-encryption rule) and implement osis-crdt's `PageSink`/`PageSource`; `Written { id }` feeds the commit's chunk list; `Reuse::index` plus `BlobWriter::reusing` dedup by reuse; `BlobSink`/`BlobFetch`, `BlobStore`, `MemoryBlobs`.
- `chunks` (large atomic values): `LargeParams`; `ValueWriter` (a blob or string of declared length: inline at or below the threshold, else streamed into a tree; UTF-8 checked); `chunk_value` (set elements, map keys); `LargeReader` (canonical bytes, lazy, one chunk plus path in memory, rejects a chunked value at or below the threshold); `StringReader` (payload, `seek` and `io::Seek` for ranges); `read_value`.
- `label.0`, `address`, `step_record` and `box` codecs are osis-schema core types, re-exported. From osis-commit label uses only the chunk trees and their `Error`: the inbox payload carries the commit as its `CommitBlobPlaintext` value, and prefix agreement takes the header's `(level, delete key)` pairs, its blind and the expiry.
- Limits: a prefix has at most one commitment per level (3); expiry 0 means none (a `Some(0)` expiry is refused); blobs `MAX_BLOB` (8 MiB); tree nodes 1..=512 links, level 1..=48, the root always interior (an empty value is one empty chunk); claim sets a power of two up to `MAX_CLAIMS` (65 536), every entry box key among the claims, boxes strict `box` values; steps, claim sets, inbox payloads and bundle frames decode with depth 512 and `MAX_MESSAGE` bytes; links and cards 8 addresses, 4 peers, 4 relays, 256-byte URLs; bundle frames 1..=`MAX_MESSAGE`.
- Importer rules beyond the spec: an entry must follow its blob in the bundle and a stamped entry its label's path (the writer emits them in that order); deletions pass through unverified, like a peer's log events.
- The address text form `<url>#<base64url key>` is provisional and client-side only.

# Admin disputes
> Summary: Admins are equals with no authority above them, so a fight between admins (a backdated removal of the remover) is a fork each node settles for itself by a trust set: Tess's decisions, the coherence rule keeping dispute handling in three places, the walk's rule, detection, default sides and choices (engine `sides.rs`), the scan bound, coming back after erasing (designed), rotations under a fork (model-checked, built) and storage under a fork (model-checked, not built), testing oracles, why no top authority, the options weighed and what was measured.

Principle: a side is an ordinary view. A node runs the ordinary rules over held data plus its trust set (its local choices), so state is a function of both; forks are permanent and no rule waits for one to settle. Rules: spec/permissions.md §5.1 Trust set.

## Decided (Tess)
- No top authority above the admins, nothing hidden, nothing users may want to change baked into a thing. A tid and the mint admin it names stay; the mint admin is history, with no power once removed.
- Admins fight: every node has a default side (first received), warns if it can, and can be overridden. Convergence is given up only there. Switching back and forth must work and may be slow.
- Accepted: a thief with an unlocked device taking control; a wrong default sealing keys to the attacker; a current admin Q that Y left in place voiding Y's removal silently (Y should have removed Q too); a removed node erasing and re-syncing if that turns around, with data lost if no copy is left; role history growing; a kicked admin raising a warning; a new node taking the walk's side (Defaults below).
- Recovery: undesigned (issues/recovery-design.md).
- Default side: conflicts should be very rare, so whatever keeps the code simplest (first received alone).
- "Contained" means code complexity, not blast radius: a fight may do wide damage, but its handling must not spread through the code. Fix the design rather than work around oddities.
- One side per party: everyone is on a side, and their writes go to that side; no write is kept valid on both sides because its writer holds rights on both (notes/write-path-design.md F6). Storage under a fork below still assumes otherwise in places (issues/disputes-storage-under-f6.md).
- A fight decided by a write that ends up applying nowhere (notes/path-model-findings.md 34 to 36, 38) is reported as a dispute only where a node's trust decides the reading; where it does not there are no sides to choose, and nothing is built to show it. Every node holding the same writes and trusting the same side still agrees, and a node trusting the remover gives a removed party nothing.

## The coherence rule
No rule names the other side or asks whether a dispute is open, except in:
1. **Walk** (osis-perm `paths`): trust set input and dispute detection.
2. **Trust store and API**: durable local defaults and choices, a dispute listener, choose (engine `sides.rs`, `osis::{disputes, on_dispute, choose_side}`). Synced choices would be suggestions read outside the walk.
3. **Storage and sync**: the delete check, branches, members carrying clean bodies (Storage under a fork).

Everything else reads validity as with no dispute. The dispute types are private to osis-perm and the API layer plus named exceptions; tools/policy.py (`dispute_types`) fails if osis-perm's dispute queries (`set_trust`, `disputes`) are called in core outside core/perm, core/osis, engine `sides.rs` and the node test `disputes.rs`, or the engine's `sides::`, `DisputeInfo`, `DisputeDetected`, `.choose(` appear outside the store's hooks. If storage needs more than a few sites, stop and redesign. A new corner case is fixed by adjusting this list or the design, not by a check at the site that hit it.

## The walk
The rules are spec/permissions.md §5.1 Trust set; the walk is osis-perm `paths` (notes/perm-paths.md).
- **Dispute**: a held explicit lowering R of a hop whose holder is not the thing R is signed as, no self-removal and not applied as a may-grant grant, untrusted and not dropped by a trusted write, whose trust would change the node's reading (which grant-class parts apply, which deltas are valid, the roles); where two or more candidates each drop another explicit lowering of another holder's hop (reach-back), each of those is also tried beside all the others, so removals undoing two masking lowerings (two removed keys' backdated demotions of one admin) are shown though neither changes anything alone (notes/write-path-design.md §1 W10). Candidates are explicit lowerings only (notes/a1-spec/README.md Open 12): an honest holder's leave would otherwise show a dispute in an honest history. Honest histories raise none (roles-model `paths`, property `dispute`).
- **Seeds** of a trusted R: the held grant-class parts of other commits ordered before R that rest on R's hop, that R's list does not name and whose need R's value does not meet, each with its commit's other grant-class parts on the same thing. D starts at every trusted write's seeds; a trusted write the settled walk does not apply is void, and every void write loses its seeds at once, the walk redone from scratch without them.
- **Seeds stop at R**, so a choice does not reject its author for good: X's writes after a re-grant by a third admin count. Seeding every unlisted write of X whenever stamped changed the reading when trusting a lowering that applies anyway, dropped X's writes after a re-grant for good, and raised extra disputes.
- **Cost**: a candidate is read by switching its trust on and back in place, an update of its component alone (notes/perm-paths.md, Cost shapes; `counts::a_dispute_probe_reads_its_component_alone`); a trusted write costs its component a walk from scratch per update of it. Narrowing the candidates: notes/a1-spec/README.md Open 3.

## Detection and sides (engine `sides.rs`)
The rules (spec/permissions.md §5.1 Sides): held first, no order no side, a lowering that cannot stand beside a recorded one, the counter-removal told. What the engine reads short of them: notes/perm-paths.md, Read short of the spec ("cannot stand beside" and the counter-removal are not read).
- **Store**: one local record (`sides`): per dispute (R, holder) told, its side if any (whether it trusts R, whether chosen); fed to the walk as its trust set (`Timeline::set_trust`) at open, before anything is evaluated, and whenever a side is recorded. The trust set is kept by (commit, op), so a trusted write held after the set was given is trusted when it comes.
- **Detection**: after each timeline update that moved a grant write, `Timeline::disputes`; each dispute not recorded yet gets its default and is reported (`Event::DisputeDetected`).
- **Default**, per (R, holder): trust R where this node made it (its own: `Origin::Local`, decided at the first update where R is a dispute, which reads as recording it when made, without a trusted write's walk cost for every own removal), or where the update brought another party's seed of R (`Timeline::seed_commits`) and the reading before applied R, other than as a may-grant grant (held first). Otherwise nothing is recorded (no order: R came with the update, or its seed was held first): the dispute is told once (a record with no side) and a later update bringing another seed may still record R. A counter-removal written while removed is its own writer's side only by the own rule; the writer's check refuses one today (The list is not built: notes/perm-paths.md, Read short of the spec). Nodes that got the backdated removal first stay with it (accepted) and are told like the others (`on_dispute`). A new or long-offline node gets both writes with no order: the walk's side. Measured in an earlier prototype: late backdating loses at every honest node, instant backdating at 86-89%; a thief acting first wins (accepted).
- **Choices**: `Engine::choose` (API `choose_side`) records a chosen side and re-feeds the trust set; it stays until chosen again or until R is forgotten (`sides::forget_commit` from `Core::take_meta`: the record is R's, and goes with its thing like any row of it). A recorded side is an answer, not a derived fact, so switching back and forth returns the same trust set (T, T', T reads as T); a trusted write the walk cannot apply is void there.
- **Listing** (`Engine::disputes(max)`, API `disputes`, `LIST_MAX` 64): the open disputes plus every recorded side whose removal is still held (trusting a removal closes its dispute, so the fight would otherwise vanish), the rest counted. It reads a copy of the timeline per call.
- **What follows from the rules**:
  - A default recorded while a dispute was open stays if the dispute closes otherwise.
  - Arrival is when a write is taken in, so a removal and the write voiding it taken in one update record nothing (a new node's first sync, a removal waiting for an entry's creation): the walk's side. So a hostile admin X can pick a third node's side by withholding: X writes its own grant entry anew and gives it to Y alone, so Y's removal of X waits elsewhere until X releases the entry. Counting a waiting removal from its arrival instead would hand the side to whoever plants one (`disputes::planted_removal_counts_from_when_it_applies_*`).
  - A node takes its own side only through its own writes: another node of the account, or a node granted after the fight that got the backdated removal first, takes held first; `choose_side` fixes these.
  - Non-interactive nodes keep the default. Following the account's published choice (except on a dispute about that account or the choice's author) is not built. The app warning is out of scope (CLI `disputes ls`, `disputes choose`).
- **Hole: an accomplice that is a current admin raises nothing.** Y removes X listing X's grant of Q; Q removes Y stamped earlier. Y's removal is void, X is back, nobody is warned. Y can answer with a new removal of Q omitting that write, which raises one. Widening detection to it cost 10-12% false alarms on removal-rank histories against 0.07-0.16% (measured). Accepted (Tess): Y should have removed Q too.

## Scan bound
No plain filter on the settled walk is exact (measured against a model of the walk, 100k histories per shape): skipping a candidate in D hid a dispute (an R dropped by a later write's audit whose authority rests on a seed of R), and skipping one none of whose seeds the settled walk applied hid one too (drops are sticky across passes). Grouping candidates by author with the union of their seeds is a different rule. So the bound is on where the probes happen, not which: each candidate costs an update of its component, and the listing is capped and counts the rest (issues/dispute-scan-cost.md).

## Coming back after erasing (designed, not built)
A node removed under its default side erases as any removed node does, no holding period; if that turns around it re-syncs; data with no copy left is lost (accepted). No exception to forward security or remote wipe. A node that wrote its own removal first holds it first, so stays on its own side and keeps its data. The one rule: a removal whose frontier drops another's removal of G goes to G's inbox, like a grant (G stopped syncing the sync ID); G then opens the sync ID by its claim, or gets boxes by a rotation's inbox copy. A switch to a side that removed you is an ordinary loss; a switch back is this path.

## Rotations under a fork (model-checked)
Rule: spec/crypto.md §4 Foreign; model `core/test/tla/rotation/ForkRot.tla` (README there). A fork on a holder actor M of a thing A whose writers hold their rights on A directly (not through M) leaves A's epochs valid on both sides, each side boxing M at its own keysets, which the other holds invalid. Under the plain rules the sides rotate A in turn forever: each side's epoch boxes a keyset invalid on the other side (a stale box there: the knowing re-key), and its rotation lists the other's epoch, superseding it there. One side per party (F6) says such an epoch belongs to its side: an epoch whose own box names a keyset held invalid is **foreign** at the node, supersedes nothing there and makes nothing due there; blocked by that box, nobody there encrypts under it, and it stays current, so holders are re-sealed into it and the node's later rotations carry it in their history box (its content stays readable to the node's later holders; listed, it would make the other side's keysets stale to the things above). An epoch boxing a foreign keyset is foreign in turn, and above its thing a foreign keyset is never sealed to and is listed by no rotation, so the rule carries up any depth (notes/holder-actors.md, Foreign keysets; model `ForkDepth.tla`). Each side then rotates A a bounded number of times: its own news, plus one per shared epoch (one leaving M out, foreign nowhere) the other side re-seals M into.
- Both halves are needed: superseding nothing alone, each side's rotation is due at once for the other's epoch; making nothing due alone, the other side's epoch still supersedes every usable one.
- Rejected: such an epoch not established at all (F6 read as invalid): no later epoch lists it, so its content is lost to later holders, also in the honest race where a writer seals to a removed party's keyset before learning the removal.
- A fork on A itself (the fight among A's admins, or rights flowing through M) needs nothing: the other side's rotations of A are invalid there.
- Left-out records play no part: a record counts at a keyset held valid, and each side records only its own keysets or pre-fork ones.

## Storage under a fork (model-checked, not built)
A dispute is a fork of a thing; two sides may live side by side for good. A concession (one party's write listing the other's removal) is one more way a fork can end; nothing waits for one. Tess: "if that actually works great". Model: core/test/tla/sides (results table there).

**Which sync IDs a fork reaches**: the forked thing's own (keys from its secrets: each side rotates and registers its own step after the same point of the step chain), and those where a right flows through the forked thing (the walk judging D walks A's history and recognizes the same fork by (R, X), so every node knows which writes are fork-dependent).

**At sync IDs both sides use, delete only when no side needs the body.** Otherwise the sides delete and log again forever, or one deletes a body before the other fetched it. A node deletes a body at a peer (must-not-hold or compaction) only when a reason holds on its own side and, on every other side, the body is invalid or a reason holds there too: no delete on the strength of a fork-dependent write unless that write is valid wherever the body is. So every must-not-hold and cover reason names its write (a purge request, the superseder that dated a death or the demotion a fall names, the covering snapshot and the deaths its cover rests on, a membership write, the edge end behind a card going). Logging, local drops and fetches stay ordinary.
- Rejected: the plain rule (never delete on a fork-dependent write) keeps forever all of one side's churn; per field (no deletes on a field a fork-dependent write touched): a purge both sides accept never reaches peers; a neutral view, the parties' own writes only, log again once, one-side covers ungated: loops or loss.
- Cost, permanent: a delete only one side accepts never reaches peers at these sync IDs while the fork lasts.
- Several forks: k forks make 2^k sides; the rule stays a subset check if each fork-dependent write carries the set of fork picks its validity rests on. Not modelled.
- Unheld writes: a judgment resting on a write the node does not hold cannot be checked; it holds only because role commits go up and are fetched first. A peer delivering content first reopens the loss (Q0 in the model).

**The forked thing's own sync IDs: one branch per side at each peer.** With one step chain per peer, the second side's step is refused, it replaces the sync ID, and its new nodes get only what its nodes held then. Instead:
- Register gains a branch form: a step whose parent is a step on the peer's path other than the head, sent only when the registrar's view rejects the head's step (honest races re-register on the head, so never branch); also from the newest path step whose delete key the registrar holds, when the head's step registers epochs the registrar's current epochs supersede and it lacks the head's delete key (a hostile admin that rotated to itself and registered: notes/keys.md, Lockouts).
- A peer keeps every branch, each with its own head, entries, caps and opens; a new branch starts with the entries stamped while its parent was the head. A superseded step's sync key is answered with all its children; a node follows the branch its view accepts; discovery ignores validity. No thing tid changes.
- The delete rule is needed only while both sides act under the shared step: before the first one-sided step, and on the first branch until the second exists.
- Members carry clean bodies across: common members, holding both sides' keys, log and delete at the branch they read but do not follow the bodies no fork-dependent write touches. With it every scenario passes except Q0.
- Holes: (1) anyone who ever held a delete key of the sync ID can open a branch at any time; others ignore branches their view rejects; it costs the peer's storage within per-branch caps and lets the removed admin download again ciphertext stamped up to its branch point (nothing it could not read before). (2) A peer that refuses to branch: the refused side replaces the sync ID there. (3) After a concession nobody follows the conceded branch; the conceding side's admins delete its content entries.
- Stuck parts: a part sealed under an epoch a node can never open must not block the commit's other parts (spec/commits.md §4). Not modelled.
- Sites: one delete check where sync decides deletions at peers; branches (send the branch form, follow the branch the own view accepts, read every branch the keys open); common members acting on clean bodies. Not modelled: several peers, several forks, honest races under branching.
- Also from review: a part sealed under a rejected epoch counts as held; cover only under snapshots valid on both sides; no synced choice decides a dispute about its own author or account; leave both parties out of new keys, or accept the wrong-default leak (accepted).
- Open: silent rejection after a removal has been held a while, warning only the parties: needs a value that passes notes/arbitrary-values.md.

## Testing
Oracles are the design's statement of itself; change them once in the harness, not per test.
- **Alike**: same held data and same trust set read the same; the order, alike and sim oracles compare after equalizing trust sets.
- **No dispute, no effect**: with no dispute held, results equal the walk with an empty trust set; honest sim runs raise none.
- **Switching**: for a node that dropped nothing, T then T' then T reads as a fresh node with those inputs; with drops, a subset.
- **Other things**: things outside the disputed thing's reach read the same on both sides and still sync (Tess's requirement).
- **Erase and return**: after a turned-around removal a node reads alike once a holder exists.

## Why no top authority
The rejected design gave each thing an irremovable top authority fixed by its record. Its jobs and what covers each: fixing the tid (needs only a genesis: the creation record); inheritance (a role on a thing reaches the things minted with it as admin); dependent things deriving secrets (from the mint admin); settling a backdating fight between admins (the one job only an irremovable authority does, and the one per-node sides take). Every record names a mint admin, an ordinary removable admin whose edge is implicit; a thing minted with a key names none (its key holds admin on it). Details: notes/mint-admins.md.

**What no conflict rule escapes**: an ex-holder signs two conflicting writes and controls everything in them (stamps, hashes, frontiers). A rule reading only signed data has three outcomes: the ex-holder picks the winner (any tiebreak), nobody wins (burn), or someone else's signature decides (quorum, witness). Age cannot bound it without breaking "state is a function of held data".

Options weighed: A, earliest stamp wins (an ex-admin can steal back); B, a mutual removal neither side listed removes both (a stolen node can wipe out every admin of an account); C, a mutable top role above admin (two concurrent hand-offs make two top holders; an account's nodes lose power over its things); D, majority of the other admins on contested removals (falls back to B below 3 admins); E, an optional witness ordering a thing's role changes (the only real prevention, against "no trusted coordinator" unless opt-in); **F, admins only and a fight goes to each user** (Tess's idea, chosen). A user-visible cost: users choosing differently split one tid until someone switches; contacts judge an account's dispute out of band, like a safety-number warning.

## Measured
Trust sets were model-checked on the walk before stated paths, about 25M histories (one thing: `until` with finalizes, may-grant grants, links, read, write, admin, skewed receipts; several things with holders and mutual roles). These held with 0 failures: an empty trust set reads as the plain walk; nobody offline raises no dispute; equal trust sets read alike in any write order; T, T', T reads as T; a choice changes nothing outside its target's reach. The `paths` model checks the stated-path rules (notes/path-model-findings.md).
- At most 2 rounds of voiding, at most 4 rounds of a node choosing each new dispute at random. Rejected: fixed seeds (backfire); re-judging "void" each round (loops on 1.6% of random histories); removing void writes one at a time (depends on order). Switching is a pure function only with D rebuilt from scratch.
- Disputes key on (R, holder): a lone ex-admin signing more writes makes one dispute per pair; k admins all removing each other make at most k(k-1)/2. A choice can reveal or hide others (0.8-1.8% of histories with a dispute), so the list is recomputed per trust set.
- Disputes raised (histories with one, 2M per shape): one remover 0 online, 1 offline; strict rank 0; rank with free full-admin grants 5 online, 37 offline; anyone removes anyone 16 online, 0.23% offline; several things 0.50%. Without a mutual removal: 25 in 16M one-thing histories, 12 in 2M several-thing ones, all real fights (an accomplice). At most 3 disputes per one-thing history, 4 per several-thing one.

# Admin disputes
> Summary: Admins are equals with no authority above them, so a fight between admins (a backdated removal of the remover) is a fork each node settles for itself by a trust set: Tess's decisions, the coherence rule keeping dispute handling in three places, the walk's rule (osis-perm `trust.rs`), detection, default sides and choices (engine `sides.rs`), the scan bound, coming back after erasing (designed), storage under a fork (model-checked, not built), testing oracles, why no top authority, the options weighed and model results.

Principle: a side is an ordinary view. A node runs the ordinary rules over held data plus its trust set (its local choices), so state is a function of both; forks are permanent and no rule waits for one to settle. Rules: spec/permissions.md §5.1 Trust set. Account forks (nodes of one account) are not admin disputes: notes/engine-validity-epochs.md.

## Decided (Tess)
- No top authority above the admins, nothing hidden, nothing users may want to change baked into a thing. A tid and the mint admin it names stay; the mint admin is history, with no power once removed.
- Admins fight: every node has a default side (first received), warns if it can, and can be overridden. Convergence is given up only there. Switching back and forth must work and may be slow.
- Accepted: a thief with an unlocked device taking control; a wrong default sealing keys to the attacker; a current admin Q that Y left in place voiding Y's removal silently (Y should have removed Q too); a removed node erasing and re-syncing if that turns around, with data lost if no copy is left; role history growing; a kicked admin raising a warning; a new node taking the walk's side (Defaults below).
- Recovery: undesigned (issues/recovery-design.md).
- Default side: conflicts should be very rare, so whatever keeps the code simplest (first received alone).
- "Contained" means code complexity, not blast radius: a fight may do wide damage, but its handling must not spread through the code. Fix the design rather than work around oddities.

## The coherence rule
No rule names the other side or asks whether a dispute is open, except in:
1. **Walk** (osis-perm): trust set input and dispute detection.
2. **Trust store and API**: durable local defaults and choices, a dispute listener, choose (engine `sides.rs`, `osis::{disputes, on_dispute, choose_side}`). Synced choices would be suggestions read outside the walk.
3. **Storage and sync**: the delete check, branches, members carrying clean bodies (Storage under a fork).

Everything else reads validity as with no dispute. The dispute types are private to osis-perm and the API layer plus named exceptions; tools/policy.py fails if `osis_perm::{Trust, Dispute, Detected, DETECT_MAX, trust}` or `set_trust`, `disputes`, `disputes_up_to`, `evaluate_with`, `trusted_active`, `take_detected` are called in core outside core/perm, core/osis, engine `sides.rs` and the node test `disputes.rs`, or the engine's `sides::`, `DisputeInfo`, `DisputeDetected`, `DisputesUnexamined`, `.choose(` appear outside the store's hooks. If storage needs more than a few sites, stop and redesign. A new corner case is fixed by adjusting this list or the design, not by a check at the site that hit it.

## The walk (osis-perm `trust.rs`)
- **Dispute**: an admin removal R of X, and a write W by X not listed in R's frontier that would void R. Every other conflict keeps the ordinary rules, so honest histories prompt only when two admins really remove each other (or knock out the other's grantor).
- The trust set (`Trust`: a set of `WriteId`s) is an input to `Timeline::evaluate_with` and a field of `Timelines` (`set_trust`). A trusted demotion R of holder M seeds D with the unlisted writes ordered before R by M's possible admins on what R puts in question (R's target and what it ever reaches), except a write lowering its author's own edge. Void trusted ops lose their seeds, all at once ("shrink"), D rebuilt from scratch. A dispute (`Timeline::disputes`, keyed (R, M)) is a trustable op the settled walk left unapplied and no seed dropped, that applies once its seeds are in D. Trustable: a frontier whose holder is neither author nor target.
- Who and what seeds follow record edges and the edges chained writes set (the timeline's `CertIndex`), never every held write's edge, so a forged edge widens no seeds.
- **Rule choices** (each model-checked):
  1. **Seeds stop at R**, so a choice does not reject its author for good: X's later writes after a re-grant by a third admin count. Seeding every unlisted write of X whenever stamped changed the state when trusting a demotion that applies anyway, dropped X's writes after a re-grant for good, and raised extra disputes. Choosing the side that already wins (X's W ordered before R) cannot be a trust entry (W's seeds do not reach R): the store records that answer to (R, M) and hides the dispute.
  2. **Who R demotes** is static: nodes that ever reach M by admin edges, the demoter excepted (over-approximate: read members cannot contest). So trusting a demotion that applies anyway still changes the state in about 2.8% of joint and 0.03-0.2% of edge histories: harmless while trust sets hold only disputed ops.
  3. **Trust drops more than the audit**: R's seeds take every unlisted write of X before R on what R puts in question, while R's audit drops only writes of a class X fell through. Accepted unless trust sets hold more than disputed ops.
  4. **Both sides of one fight trusted** keeps the later-stamped one (the earlier's seeds are empty, so it turns void and is rejected, not disputed). A store never writes both.
  5. **Demoting** means the explicit write's value is below the edge's value just before it (not the edge as restored), in every component; an explicit write on an already-removed edge raises no dispute. So a self-removal never contests R (seeded, self-removals raised false disputes and kept X in place); a self-grant does and drops (excepting every own-edge write let a removed admin keep a backdated self-grant on every thing below).
- **Cost**: a component holding a trusted op is only evaluated from scratch (no incremental path, save or restore; continuing would need its own correctness argument), one walk per held-set change (0.3-0.5 s at 10^4 edge writes). With an empty trust set nothing changes (measured within noise).
- Kicked admin: a contest that lists its own removal is no dispute; one that omits it raises one, and only the kicked node sides with itself.

## Detection and sides (engine `sides.rs`)
The rule the stated-path walk is to be built to (a node's own lowerings, held first, one side per fight, a choice dropping the other side, the counter-removal told), modelled in roles-model `paths`: notes/write-path-design.md §1, First received. Below: what is built.
- **Store**: one local record (`sides`): per dispute (R, M), whether it trusts R and whether it was chosen; fed to `Timelines::set_trust` at open (before anything is evaluated) and whenever a side is recorded.
- **Detection** (`Timelines::detect`): after each update, the trustable ops of touched components that stopped applying (from `history_diff`) and the unapplied ones of commits new to them go through `Timeline::scan`, the stopped-applying ones first, at most `DETECT_MAX` (16) walks per update. Past the bound (`DiagnosticKind::DisputesUnexamined`): an op that stopped applying keeps its side, trusted unexamined and not told (fail safe: a flood of contestable writes cannot leave the honest removal to the walk); a newly held one gets the walk's side. A switch detects nothing; detection is off while the store loads at open. Each `Detected` carries `stood` (R applied here before the update).
- **Default**, recorded once per (R, M) at detection: first received, trust R iff it stood. A party holds its own write first, so sides with itself. Nodes that got the backdated removal first stay with it (accepted) and are told like the others (`on_dispute`). A new or long-offline node gets both writes with no memory of order: the walk's side. First received was checked in the prototype: late backdating loses at every honest node, instant backdating at 86-89%; a thief acting first wins (accepted).
- **Choices**: `Engine::choose` (API `choose_side`) records a chosen side and re-feeds the trust set; it stays until chosen again. A recorded side is an answer, not a derived fact, so switching back and forth returns the same trust set (T, T', T reads as T); a trusted write the walk cannot apply is void there, costing a shrink round and the fast path.
- **Listing** (`Engine::disputes(max)`, API `disputes`, `LIST_MAX` 64): the open disputes of every component plus every recorded side whose removal is still held (trusting a removal closes its dispute, so the fight would otherwise vanish), the rest counted as unexamined.
- **Stated limits**:
  - A default recorded while a dispute was open stays if the dispute closes otherwise; a trusted op that then applies anyway over-drops its seeds (rule choice 3).
  - A dispute whose removal arrived before the grant its author's authority rests on is examined once, at arrival: it is listed, not told, and gets the walk's side. A flood of newly held contestable writes in the update bringing a dispute's removal unapplied skips its examination: the walk's side, without a warning.
  - Arrival is when a write applies, so a removal and the write voiding it applied in one update give the walk's side (a new node's first sync, a removal waiting for an entry's creation). So a hostile admin X can pick a third node's side by withholding: X writes its own grant entry anew and gives it to Y alone, so Y's removal of X waits elsewhere until X releases the entry. Counting a waiting removal from its arrival instead would hand the side to whoever plants one (`disputes::planted_removal_counts_from_when_it_applies_*`).
  - A node takes its own side only through its own writes: another node of the account, or a node granted after the fight that got the backdated removal first, takes first received; `choose_side` fixes these.
  - Non-interactive nodes keep the default. Following the account's published choice (except on a dispute about that account or the choice's author) is not built. The app warning is out of scope (CLI `disputes ls`, `disputes choose`).
- **Hole: an accomplice that is a current admin raises nothing.** Y removes X listing X's grant of Q; Q removes Y stamped earlier. Y's removal is void, X is back, nobody is warned. Y can answer with a new removal of Q omitting that write, which raises one. Widening detection costs 10-12% false alarms on removal-rank histories against 0.07-0.16%. Accepted (Tess): Y should have removed Q too.

## Scan bound
No plain filter on the settled walk is exact (checked against the roles model, `trust` searches, 100k histories per shape): skipping a candidate in D hid a dispute (an R dropped by a later write's audit whose authority rests on a seed of R), and skipping one none of whose seeds the settled walk applied hid one too (audit drops are sticky across passes). Grouping candidates by author with the union of their seeds is a different rule. So the bound is where the walks happen, not which: each contestable write costs a walk once (at arrival or when it stops applying), capped per update, and the listing is capped and counts the rest (issues/dispute-scan-cost.md).

## Coming back after erasing (designed, not built)
A node removed under its default side erases as any removed node does, no holding period; if that turns around it re-syncs; data with no copy left is lost (accepted). No exception to forward security or remote wipe. A node that wrote its own removal first holds it first, so stays on its own side and keeps its data. The one rule: a removal whose frontier drops another's removal of G goes to G's inbox, like a grant (G stopped syncing the sync ID); G then opens the sync ID by its claim, or gets boxes by a rotation's inbox copy. A switch to a side that removed you is an ordinary loss; a switch back is this path.

## Storage under a fork (model-checked, not built)
A dispute is a fork of a thing; two sides may live side by side for good. A concession (one party's write listing the other's removal) is one more way a fork can end; nothing waits for one. Tess: "if that actually works great". Model: core/test/tla/sides (results table there).

**Which sync IDs a fork reaches**: the forked thing's own (keys from its secrets: each side rotates and registers its own step after the same point of the step chain), and those where a right flows through the forked thing (the walk judging D walks A's history and recognizes the same fork by (R, X), so every node knows which writes are fork-dependent).

**At sync IDs both sides use, delete only when no side needs the body.** Otherwise the sides delete and log again forever, or one deletes a body before the other fetched it. A node deletes a body at a peer (must-not-hold or compaction) only when a reason holds on its own side and, on every other side, the body is invalid or a reason holds there too: no delete on the strength of a fork-dependent write unless that write is valid wherever the body is. So every must-not-hold and cover reason names its write (a purge request, the superseder that dated a death or the demotion a fall names, the covering snapshot and the deaths its cover rests on, a membership write, the edge end behind a card going). Logging, local drops and fetches stay ordinary.
- Rejected: the plain rule (never delete on a fork-dependent write) keeps forever all of one side's churn; per field (no deletes on a field a fork-dependent write touched): a purge both sides accept never reaches peers; a neutral view, the parties' own writes only, log again once, one-side covers ungated: loops or loss.
- Cost, permanent: a delete only one side accepts never reaches peers at these sync IDs while the fork lasts.
- Several forks: k forks make 2^k sides; the rule stays a subset check if each fork-dependent write carries the set of fork picks its validity rests on. Not modelled.
- Unheld writes: a judgment resting on a write the node does not hold cannot be checked; it holds only because role commits go up and are fetched first. A peer delivering content first reopens the loss (Q0 in the model).

**The forked thing's own sync IDs: one branch per side at each peer.** With one step chain per peer, the second side's step is refused, it replaces the sync ID, and its new nodes get only what its nodes held then. Instead:
- Register gains a branch form: a step whose parent is a step on the peer's path other than the head, sent only when the registrar's view rejects the head's step (honest races re-register on the head, so never branch); also from the newest path step whose delete key the registrar holds, when the head's step registers epochs the registrar's current epochs supersede and it lacks the head's delete key (a hostile admin that rotated to itself and registered: notes/keys.md, Lockouts).
- A peer keeps every branch, each with its own head, entries, caps and opens; a new branch starts with the entries stamped while its parent was the head. A superseded step's sync key is answered with all its children; a node follows the branch its view accepts; discovery ignores validity. No thing tid changes.
- The delete rule is needed only while both sides act under the shared step: before the first one-sided step, and on the first branch until the second exists.
- Members carry clean bodies across: common members, holding both sides' keys, log and delete at the branch they read but do not follow the bodies no fork-dependent write touches. With it every scenario passes except Q0.
- Holes: (1) anyone who ever held a delete key of the sync ID can open a branch at any time; others ignore branches their view rejects; it costs the peer's storage within per-branch caps and lets the removed admin download again ciphertext stamped up to its branch point (nothing it could not read before). (2) A peer that refuses to branch: the refused side replaces the sync ID there. (3) After a concession nobody follows the conceded branch; the conceding side's admins delete its content entries.
- Stuck parts: a part sealed under an epoch a node can never open must not block the commit's other parts (spec/commits.md §4). Not modelled.
- Sites: one delete check where sync decides deletions at peers; branches (send the branch form, follow the branch the own view accepts, read every branch the keys open); common members acting on clean bodies. Not modelled: several peers, several forks, honest races under branching.
- Also from review: a part sealed under a rejected epoch counts as held; cover only under snapshots valid on both sides; no synced choice decides a dispute about its own author or account; leave both parties out of new keys, or accept the wrong-default leak (accepted).
- Open: silent rejection after a removal has been held a while, warning only the parties: needs a value that passes notes/arbitrary-values.md.

## Testing
Oracles are the design's statement of itself; change them once in the harness, not per test.
- **Alike**: same held data and same trust set read the same; the order, alike and sim oracles compare after equalizing trust sets.
- **No dispute, no effect**: with no dispute held, results equal the walk with an empty trust set; honest sim runs raise none.
- **Switching**: for a node that dropped nothing, T then T' then T reads as a fresh node with those inputs; with drops, a subset.
- **Other things**: things outside the disputed thing's reach read the same on both sides and still sync (Tess's requirement).
- **Erase and return**: after a turned-around removal a node reads alike once a holder exists.
- Built: osis-perm `differential::trust_model_agrees` (`_plain` and `_large`), `scenarios::*_spec_permissions_5_1`; osis-engine `disputes::*` (both orders, each party with itself, a planted waiting removal, switching, the store across a restart, other things untouched); osis `sharing::disputes_listed_told_and_chosen_*`.

## Why no top authority
The rejected design gave each thing an irremovable top authority fixed by its record. Its jobs and what covers each: fixing the tid (needs only a genesis: the creation record); inheritance (a role on a thing reaches the things minted with it as admin); dependent things deriving secrets (from the mint admin); settling a backdating fight between admins (the one job only an irremovable authority does, and the one per-node sides take). Every record names a mint admin, an ordinary removable admin whose edge is implicit; key actors have none (a node is its key). Details: notes/mint-admins.md.

**What no conflict rule escapes**: an ex-holder signs two conflicting writes and controls everything in them (stamps, hashes, frontiers). A rule reading only signed data has three outcomes: the ex-holder picks the winner (any tiebreak), nobody wins (burn), or someone else's signature decides (quorum, witness). Age cannot bound it without breaking "state is a function of held data".

Options weighed: A, earliest stamp wins (an ex-admin can steal back); B, a mutual removal neither side listed removes both (a stolen node can wipe out every admin of an account); C, a mutable top role above admin (two concurrent hand-offs make two top holders; an account's nodes lose power over its things); D, majority of the other admins on contested removals (falls back to B below 3 admins); E, an optional witness ordering a thing's role changes (the only real prevention, against "no trusted coordinator" unless opt-in); **F, admins only and a fight goes to each user** (Tess's idea, chosen). A user-visible cost: users choosing differently split one tid until someone switches; contacts judge an account's dispute out of band, like a safety-number warning.

## Model results
`core/test/roles-model` `trust`: trust sets on the `edges` walk (one thing: `until` with finalizes, invites, links, read, write, admin, skewed receipts) and the `joint` walk (several things, holder actors, mutual roles), in the built shape. About 25M histories (exhaustive edge tiers 2.0M, 2M random per shape). Hard properties, 0 failures: an empty trust set reads as the plain walk; nobody offline raises no dispute; equal trust sets read alike in any write order; T, T', T reads as T; a choice changes nothing outside its target's reach.
- At most 2 shrink rounds, at most 4 rounds of a node choosing each new dispute at random. Failed prototype variants: fixed seeds backfire; re-judging "void" each round loops on 1.6% of random histories; removing void ops one at a time depends on order.
- Switching is a pure function only with D rebuilt from scratch.
- Disputes key on (R, X): a lone ex-admin signing more writes makes one dispute per pair; k admins all removing each other make at most k(k-1)/2. A choice can reveal or hide others (0.8-1.8% of histories with a dispute), so the list is recomputed per trust set.
- Disputes raised (histories with one, 2M per shape): one remover 0 online, 1 offline; strict rank 0; rank with free full-admin grants 5 online, 37 offline; anyone removes anyone 16 online, 0.23% offline; joint 0.50%. Without a mutual removal: 25 in 16M edge histories, 12 in 2M joint, all real fights (an accomplice). At most 3 disputes per edge history, 4 per joint one.
- Not modelled: invites, `until` and finalizes across several things; holder actors in `edges`; defaults, first-received order, following published choices.

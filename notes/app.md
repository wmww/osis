# The first-party app
> Summary: Design direction for the first-party osis app over osis and schema/ (decided with Tess): data-oriented UX (things with facet views, lenses, tags as filters), the look (colour from the content, themes as parameters), state kept in osis including view state, the layer split (osis state, toolkit-free actions, Masonry driver and widgets), the libs/kit/app split (osis-kit toolkit and osis-app in their own Cargo workspace), the toolkit decision (Masonry without Xilem) with the alternatives weighed, the platform work accepted, the prototype order, how to run it, and the prototype as built (data model, screens, chat, kit modules, patches, what it showed, core changes the app has yet to adopt).

## Direction (Tess)
- Fresh and timeless, not a bundle of generic apps over osis types. Bright colours, flatish but not distinctly flat, its own look rather than the native aesthetic.
- Oriented around data, not functionality: no "tab for notes, tab for calendar". Views show whatever combination of things they can meaningfully place.
- Responsive and lightweight on every device; webview is out. Native first, web later.
- Build first in something light, simple and running everywhere; if the UX suffers, rebuild differently. Platform work (Rust embedding, possibly an iOS shell of our own) is accepted for the sake of the right foundations in text, accessibility and low-level control.
- Convergent design, not a mobile/desktop split: one layout keyed on width and input kind, phone layout designed first, desktop adds columns. Touch on desktop supported.
- Do not copy the mockup closely: it is a test bed for the look and the theme spec. The app leans simpler and less distracting and chooses its own structure and UX. UX is figured out along the way, iterating once there is something to play with.
- Motion: almost none; only unobtrusive fades or motion that adds clarity.

## Model
- **The thing is the unit.** No `kind` aspect exists (notes/tags.md); a thing is whatever its aspects make it, and may be several kinds (a meeting note is note and event).
- **Facet views.** Kind-specific views exist because aspects do not map 1:1 onto UI. Opening a thing picks the best-matching view for the aspects present (event aspects plus `body.0` → the calendar view, which includes the freeform text area; `body.0` alone → the notes view). When several views apply and none covers every aspect, the thing offers them side by side (tabs or a scroll list; undecided, unimportant).
- **Schema fallback view**, behind a context menu: shows and edits every aspect of a thing from its schema-declared types alone. Covers things whose schema the app has but no view for.
- **Create** offers a kind selector (note, event, contact, ...) plus "empty thing".
- **Lenses** are few and fixed: a filter plus an arrangement over all things, each admitting only what it can place. Time (event times; faint creation and edit ticks for the rest, from commit timestamps), People (contacts and profiles plus what links to them), Tags (the graph as navigation, with colour), Search as the primary way in, and a home lens mixing today, recently touched things and people. User structure lives in tags and links, not in lenses. Tags also narrow a lens or find things within a collection.
- **Every thing shows** its tags, what links to it (`db.backlinks`), who can see it (roster) and its history (undo). Placing into a shared tag confirms the reach (notes/tags.md guideline).
- Tagging never shares: tagging a tag nests it as a subgroup (`group.0` subgroups), which shares however core does; sharing through a tag is core's `add_with_grant` (notes/tags.md), and the app grants nothing itself (Tess). Backlinks from markdown (`body.0` has no tid reference syntax) are a library-side question (Tess).

## State in osis
- All app state lives in osis; widgets hold only what is too hot to be data (drag positions, caret blink, animation).
- Durable view state (open things, lens, filters, layout) as things in an account-private group: a view can move between devices, apps or toolkits, and be saved and restored. Not specified yet; the architecture assumes it.
- Ephemeral view state (selection, expanded panels, scroll anchor) as drafts and ephemeral aspects (notes/ephemeral.md): in memory, local unless added to a synced group; hot live state across devices is synced ephemeral data, not commits.
- An app's own per-account data (favorites, view state, themes) lives in an internal group found by scanning home's subgroups for the app's marker aspect, reading the union and writing to the smallest tid (Tess: a well-known per-app thing is incoherent, since a tid depends on its owner's key; the scan is the convention).
- Asks of the library: in-memory things support watches, queries and backlinks like stored things; the app can pump the watch dispatcher on its own UI thread (`Dispatcher::Pump`).

## Layers
- **State**: osis.
- **Actions** (in `app/`): toolkit-free Rust. Widgets emit intents (open, tag, share, edit); the actions turn them into osis writes and hold all behaviour and policy, including the share confirmation's rule (none yet).
- **Driver** (in `libs/kit/`): Masonry-specific glue. Watches fire; the driver edits the retained widget tree through Masonry's mutation API. Two pieces written once: marshalling watch callbacks onto the UI thread (`marshal`, replaceable by `Dispatcher::Pump`), and a keyed list reconciler turning a changed query result into insert/move/remove on a list widget (`list`, unused by the app while there are no queries).
- **Widgets** (in `libs/kit/`, product views in `app/`): our own look as Masonry widgets.
- A toolkit swap rewrites driver and widgets only; state and behaviour survive. There is no separate view-model crate: the view-state schema plus the actions cover it.

## Look and themes
One main colour from the content (the open thing's, else the first among what it holds or links; a soft grey on home) drives accent, selection and a subtle background; everything else is a theme's parameters (notes/theming.md). Themes are Tess-approved: Frost, Glass, Workstation, Memphis, Slate (square, flat, modern), Cel (flat, white or dark grey, anime-ish); each has light and dark, mode (Light/Dark/Auto) separate. Backgrounds: the theme picks what is drawn, the content picks the colour and the arrangement (seeded from the tid, varied slightly by kind); subtle shading of the one colour, not splotches of several. Less UI: fewer bordered elements.

**Web mockup** `app/mockup/` (plain HTML/CSS/JS, no deps, no osis; serve the directory, e.g. `python3 -m http.server`): explores look and layout. Tess's brief: things and scopes (tags, views) are fungible tiles in one list or grid; an ordered favorites list; one search over names, content and scopes; with a view open and room enough, a left bar holds search and favorites. The look should feel like what 1996, 2006, 2016 and 2026 thought 2026 would be: coloured gradient backgrounds or abstract shapes, a little Apple liquid glass (never at a perf cost), almost no Material. Layout in style.css; themes.js and engine.css are the theme reference implementation.

## kit and app
Two projects, `libs/kit/` (package `osis-kit`) and `app/` (`osis-app`).
- **osis-kit**: the first-party UI toolkit over Masonry. Holds windowing and platform shells (the iOS shell too), the osis-Masonry driver, the look, common widgets (markdown editor, text, lists), generic osis widgets needing only the osis API (schema fallback view, who-can-see display, share confirmation dialog), and the patches we carry to low-level crates. A small special-purpose app that looks like the main one depends on kit alone. kit does not abstract over the osis API, nor over Masonry: it re-exports it (`kit::masonry`, one pinned version) and apps use its types directly; design an abstraction only when actually changing base.
- **osis-app**: facet views, lenses, home, create flow, actions, the view-state schema.
- **Own Cargo workspace** for both, depending on core by path: keeps the GUI stack (wgpu, Vello, winit) out of core's builds, gate and feature unification, and puts `[patch]` entries for forked crates at the GUI workspace root (notes/build.md Layout). Costs a second `target/` per worktree. Agent limits (notes/coordination.md) count GUI agents; the gate splits by changed paths (notes/build.md, Components pay for themselves).
- Tess: the app builder updates and refactors kit as needed (Masonry upgrades allowed); core is never edited from app work: gaps become `core-ask` issues.

## Toolkit: Masonry without Xilem
Masonry is a retained widget tree designed to sit under other frontends; Xilem's job is to own app state and diff it into Masonry. With osis owning the state and delivering fine-grained changes (watches per aspect, live queries over a visible range), Xilem solves a problem we do not have. What we get: Vello (2D, GPU compute; vello_hybrid for low-end GPUs and WebGL, vello_cpu as a no-GPU fallback), Parley (the best Rust text stack: rich layout, IME), AccessKit designed in, a renderer abstraction, and a funded multi-contributor org.

Costs: pre-1.0 with breaking releases (the layout system changed in Q1 2026): pin versions, upgrade deliberately, keep the driver small so churn lands in one place. Thinner docs than Slint, so agents read source. Small stock widget set: we build our own anyway.

Alternatives weighed:
- **Slint**: the most mature on all six targets (1.15 in Feb 2026 brought Android/iOS safe areas and virtual keyboard; mobile is Rust-only), excellent tooling and docs, tiny runtime, software renderer, royalty-free license for apps (verify terms). Against: UI in a separate DSL, drawing limited to paths, plain-text editing only, less low-level control. The pick under "light and simple now" alone.
- **Makepad**: the only Rust toolkit shipping web plus all five native targets from one codebase, shader-level custom drawing by default. Against: thin docs, small team, unusual DSL, no accessibility, needs a GPU.
- **Xilem** on top of Masonry: duplicates osis's reactivity.
- **egui**: lightest and everywhere, but the look is hard to escape and mobile text input is weak. **iced**, **GPUI**: desktop only. **Dioxus native**: immature, mobile is webview. **Compose Multiplatform**: Kotlin, JVM desktop. Flutter and webviews excluded by Tess.

## Platform work accepted
- Desktop (Linux, Windows, macOS): winit. Test with the gui-testing skill.
- Android: winit plus android-activity; IME is the rough spot (notes/android.md); AccessKit has an Android backend.
- iOS: winit's backend is thinly exercised, IME weak, no AccessKit backend. Expect a UIKit shell of our own hosting the render surface and feeding touch, keyboard and VoiceOver into Masonry.
- Web: later; needs WebGPU for Vello proper, vello_hybrid/vello_cpu for a canvas fallback.

Text: Parley's plain editor exists; rich editing does not. The markdown editor is ours: an editor over Parley layouts with styled spans, first as a styled-source editor (headings larger, links coloured, markup visible), not WYSIWYG; the one place a plain-text fallback is acceptable early.

## Running it
One device with demo data (in `libs/kit/`; the first build takes a few minutes): `cargo run --bin osis-app -- ~/osis-try/solo --demo --theme glass`. The store directory is made on first run; `--demo` adds the demo things once (keeping existing favorites); `--theme frost|glass|workstation|memphis|slate|cel` and `--auto|--light|--dark` set the look, as does the picker at the foot of home. `--peer ADDR` (repeatable) adds peer addresses an existing store lacks.

Two nodes syncing through a local serving node (four terminals):
1. Repo root: `cargo run --bin osis -- -s ~/osis-try/host init`, then `cargo run --bin osis -- -s ~/osis-try/host serve --listen quic://127.0.0.1:47833 --admit open` (`open`: it also takes chats, which are ownerless). Its first line is the serving address, `quic://127.0.0.1:47833#<key>` (stable across restarts of that store); leave it running.
2. `libs/kit/`: `cargo run --bin osis-app -- ~/osis-try/a --peer 'quic://127.0.0.1:47833#<key>' --demo` (quote the address: it holds a `#`). Close the window once it shows (a store is locked while open).
3. Repo root: `cargo run --bin osis -- -s ~/osis-try/a pair offer`. It prints an `osis://pair/...` line and waits.
4. Another terminal, repo root: `cargo run --bin osis -- -s ~/osis-try/b pair join 'osis://pair/...'`. It prints an `osis://pair-request/...` line and waits. Paste that into terminal 3 and press Enter: it prints an `osis://pair-reply/...` line; paste that into terminal 4. Both exit (`b` learns the peer from the offer).
5. `libs/kit/`: `cargo run --bin osis-app -- ~/osis-try/a` and `cargo run --bin osis-app -- ~/osis-try/b`. Within a few seconds `b` shows the demo data. Typing in one window shows in the other after a short pause (a text session commits after about 2 s idle) plus sync.

Joining a chat from another device:
1. `cd libs/kit && cargo build --bin osis-app`; `cd ../.. && cargo build --bin osis`.
2. Someone in the chat runs `osis -s STORE chat link $C` and sends the `osis://link/...` line.
3. `libs/kit/target/debug/osis-app ~/osis-chat --peer 'quic://HOST:PORT#KEY'`. Type a name in "Your name in chats" and press Enter; paste the link in "Join a chat" and press Enter. The chat opens once the peer answers. Or from the command line first: `target/debug/osis -s ~/osis-chat init --peer 'ADDR'` and `target/debug/osis -s ~/osis-chat chat join 'osis://link/...'`.
4. Later runs: `libs/kit/target/debug/osis-app ~/osis-chat`; the chat is under Chats on home.

## Prototype (as built)
`osis-app DIR [--peer ADDR]... [--demo] [--theme ID] [--auto|--light|--dark]` (libs/kit/ workspace; Masonry `=0.4.0`, masonry_winit `=0.4.0`: wgpu 26, Vello 0.6, Parley 0.6, winit 0.30).

### app: data (actions, toolkit-free)
- The app group (marker `osis_app:app.0`, an item and subgroup of home, smallest tid wins, made with the four view things on first use) holds every thing the app makes, the favorites (`osis_app:favorites.0: list<tid>`, edited with `edit`) and per-node navigation (`osis_app:open.0~: map<node, tid>`, gone on restart: the app starts at home). Tags are the group's subgroups too, so their items sync.
- `Kind` by aspects (view, `tag.0`, any `event:`, any `contact:`, else note); `Tile` (name, sub line, colour); colour = `tag.0` colour, else `osis_app:color.0`, else the first tag's; `main_color` per notes/theming.md. `things()` scans the app groups and, transitively, tags; `search` scans names, bodies, places and contact fields (scopes, things, mentions with snippets, things in matching scopes). Views (calendar, people, tags, recent) are things with `osis_app:view.0`, so they are tiles and favorites like tags. `tags_of` takes direct memberships only (`groups_of` is transitive through subgroups).
- Event times (`time`, over jiff): a wall time with a zone (IANA or `+HH:MM`) shows in the system zone, a floating one as written; `span` gives (start, end, all day) in local wall ms; `week(monday)` the events touching each day; `span_in`/`occurrences_in` take the viewer's zone. A `duration` end is elapsed time (over a clock change the wall end moves). `nudge(t, by, longer)` moves an event, its end along in its own form (a moment stays one); a nonzero `longer` sets `event:end.0` to `after(duration)`: the current elapsed length plus `longer`, at least 15 min; a day event moves by whole days (test `nudge_over_dst_and_midnight`). App tests never depend on now or the system zone. Synced times, zones and rules never overflow (test `extreme_values_do_not_panic`).
- Repeating events: `time::occurrences` expands `event:repeat.0` over a window (daily; weekly on its weekdays or the start's; monthly on monthdays, the nth or last weekday, or the start's day, skipping months without it; yearly on the start's date or the nth weekday of the year, ignoring monthdays; `interval`, `count` from the start, `until` inclusive, `skip`), leaving out occurrences another event replaces through `event:overrides.0`. At most `MAX_PERIODS` (20,000) periods per expansion, starting just before the window when there is no `count` (with one, from the series start: a counted series longer than that stops showing); day choices no period can hold are dropped first, so a huge synced set costs bounded work per period. Each occurrence is the start and end shifted by whole nominal days, then converted. `events_between`/`week` give `Shown` occurrences (↻ in the week); an event's pane offers once, daily, weekly, monthly, yearly (anything finer shows as "Custom", edited in All fields).
- Two nodes racing (app/tests/it/sync): `things()` keeps one view per kind (smallest tid) and `favorites()` maps the other group's views onto those. `toggle_favorite` appends to the main group's list and removes from every group's; it never copies the other group's entries into the main one, which would bring back a favorite removed concurrently (test `unfavorite_survives_a_concurrent_first_write`). A reorder (`move_favorite`: dragging a tile in the home grid or a rail row; kit `TileGrid::reorderable` emits `Reorder`, tiles moved past 6 px do not press) is one `move_range` inside the list holding the entry, among that group's entries only, so a concurrent unfavorite wins (a sequence move never revives a deleted element; test `reorder_against_concurrent_unfavorite`). A node's open entry is found on any group and moved to the main one.
- Reads go through `Data::get`, where a value of another shape (synced data can hold anything, or a newer enum case) reads as absent; a screen that still fails to build goes home.
- `delete` also drops subgroup edges on groups I can write (`groups_of` follows membership, not subgroup edges, issues/api-subgroup-parents.md; without it a deleted tag stays as an empty note). `opened()` is `None` for a thing gone from `things()` (deleted elsewhere; `has_content` stays true after a delete).
- The look is per account on the app group (`osis_app:theme.0`: a built-in id; `osis_app:mode.0`: auto, light, dark), chosen at home's foot. Auto reads the window's system theme once and follows `on_theme_changed`.
- `create(NewKind)` makes a note, an event (next full hour, one hour), a person (an empty `contact:names.0`) or a tag (a group with the next of 8 `TAG_COLORS`, a subgroup of the app group); "New" offers the four as chips.
- `reach(t)` walks the owner and the live rosters (a grant with a later `until` counts) through shared-tag actors and their owners (implicit admins, on no roster) down to people, me and my nodes being "you", names from profiles or a contact naming the profile.
- Tagging adds a thing to a tag or nests a tag in a tag (`add_subgroup`; `tags_of` lists parents by item or subgroup, `remove_tag` removes or un-nests) and shares nothing (membership grants no rights).
- `undo(t)` is `db.undo(Scope::Thing)` (my newest commit, from any of my nodes, never another account's; on a tag that includes additions to it), except that it never reverts the creation commit, which also placed the thing (issues/undo-creation-unplaces.md; `next_undo`). `edited(t)` shows the newest content change in that scope (not roles: a grant is no edit; a membership is written on the tag) at `min(ts, received)`.
- `fields` (the schema fallback view, the bar's "All fields" toggle): `Data::new` registers the app's, event and contact schemas so `db.key` types their aspects; `field_rows(t)` flattens every aspect but the system ones (`created.0`, `group.0`, role-class aspects) down to scalar rows (structs by field with reader defaults, maps by key, enum payloads, an `option` of a scalar as one row whose empty text writes `none`); `set_field` parses a row's text by its type (string, int, float, bool, a payload-free enum by case name) and writes it at the row's path; lists, sets, texts, tids, blobs and untyped aspects are shown, not edited; a bool takes true/false/yes/no/on/off/1/0. Enter or leaving the field (kit `Panel::report_blur` emits `Blur`) saves unless the text is what was saved last; a rebuilt slot gives the focus back to the input in the same place, caret at the end. The contact form writes a field of an absent struct alone (writing the struct with defaults first would overwrite a concurrent sibling field, test `contact_fields_of_an_absent_struct_race`); an email or phone rename is remove + put by key, so two concurrent renames keep both new keys and a relabel racing a rename brings the old key back with that field (a known CRDT anomaly).
- `demo`: `--demo` adds tags, people, notes and this week's events once (`osis_app:demo.0`).
- `edit`: `splice`, typing into a `TextSession` against the text the widget showed (the widget reports its whole text); `shown_edits` and `map_byte`: a remote merge's reported splices (`on_remote`, kept per field until the UI thread shows the merge) map the widget's selection across `reset_text`, or one diffed splice when they no longer lead from the shown text to the session's (typing raced the merge).

### app: ui
- `ui` (mod: state, refresh, input; screens: building home and a thing; content: slot models and their widgets): a `Root` widget (kit) holds the screen; the width class is read from the render root's logical size on each refresh and `on_resized` refreshes when it changes; under 760 px an open thing fills the window with a back button, else a 264 px rail (home row, search, favorites or results, new) sits beside it.
- A screen is built whole when the open thing, width class or look changes; its slots (home body, rail list, rail new, pane extras, meta) are models (`Content`: lines, labels, tile runs, chip runs) rebuilt only when they differ, so editors keep their caret. `ViewState` is UI memory reset per screen (the new-kind chooser, the tag picker, the week, All fields). One `watch_thing` per shown thing, home and the app groups posts `Changed`; the UI re-reads (no queries).
- The pane: kind label ("Event · Note" with a body), favorite star, delete; the accent's title mark; text fields over text sessions (title; an event's place; body for notes, events, people); extras per kind (event time with day and hour nudges and shorter/longer, contact fields, the tags as removable chips plus "+ Tag" and its picker, a tag's subtags and items, a view's items, Recent as rows with edit times); meta chips (who can see it, when it changed, undo). Calendar is a week (earlier, this week, later; seven day panels, today's raised, events as bar rows with time and place); Tags is the tree (top tags as cards, each one's subtags as rows; a cycle under no top tag shows its first tag as top); People cards; Recent rows.
- Focus rule: a new screen focuses home's search or a new thing's title, else nothing, so Space and Enter only press a tile or chip reached by Tab, which draws a ring.
- Slots, the status line and the star are found by widget tags (freed with their widget by the masonry_core patch); a tag cannot come with properties, so the styled status label sits in a tagged `SizedBox`.

### Chat
A prototype for joining a chat from another device (Tess: no UX polish). `app/src/chat.rs` (toolkit-free, over osis-chat): `chats` (made or joined here or by the CLI on this store), `join` (a chat already here opens at once; else the redemption's own waits bound it), `send` (an optional subject goes first, `subject\n\ntext`, as the CLI's `--subject`), `recent(n)` (the newest n, oldest first, a reply naming its target's sender and first line); the sender name is the profile's `name.0`, else `OSIS_CHAT_NAME` (a hostless store has no profile). UI (`ui/chat.rs`): home lists chats as chips under the favorites, then a link field (Enter joins, on a thread) and a name field; an open chat (`Screen::Chat`, per window, not kept in osis) is back + name, the newest 200 messages (mine raised; ↩ the answered one; Reply sets reply-to), text selectable and copyable (kit `style::prose`, Masonry `Prose`; Labels are not), scrolled to the end after each rebuild (`Msg::ScrollEnd`, posted so the portal has laid out), then name, subject and message fields (Enter sends). Live by `osis_chat::on_event` (renewed on `Ended`); the list follows `watch_status`. A screen that fails to build (a chat no longer readable) goes home; a failed join shows only in the footer status line; a deleted message loses its sender's name with its body (shown as the tid's start). Not done: older pages, edit, delete, members, leave, markdown, a multi-line composer, unread marks. Android adds paste chips (notes/android.md).

### kit modules
`theme` (the parameters, the six defaults, `Mode`, `Look::new(theme, dark, main)` resolving colours: background tinted by bgTint, panel at panelOpacity, card fill composited over the background, white text past fill 0.55, accent from the main colour, shadows stronger in dark), `backdrop` (all ten backgrounds as fills, gradients and paths in shades of the background colour, placed by four seeds hashed from the open thing and its kind; no blur or layers), `fonts` (every theme font and JetBrains Mono bundled in libs/kit/assets/fonts with their OFL texts, registered in `on_start`), `icons` (line icons as SVG path data), `text` (parley layouts in the theme font family list), `widgets` (`Chip`, `Wrap` (flow), `Root` (also fades the background to a new colour over 600 ms: the one motion), `Panel` (panel, inset, field), `Tile` (card, row, new; slant, shadow, gloss, icon roundness; bar's stripe and slash's corner flag), `TileGrid` (auto-fill columns), `IconButton`, `Limit` (centred max width), `style` (labels and borderless text inputs per text role, accent weights and caps, mono section labels, title marks)), `list` (reconciler), `marshal`, `window`.

### Patches
libs/kit/patches/, `[patch.crates-io]` in libs/kit/Cargo.toml, each with a `.diff` against upstream beside it; upgrading Masonry means re-vendoring and re-applying. All are upstream candidates.
- `masonry_winit` 0.4.0 (`masonry_winit-clipboard.diff`): upstream's clipboard is copypasta's X11 context, `unwrap`ped at startup, which panics on a Wayland-only session (no `DISPLAY`); the patch uses the Wayland clipboard over the event loop's own connection (dropped in `exiting`, before the loop drops the display), else X11, else a no-op.
- `masonry_winit` (`masonry_winit-hooks.diff`): `AppDriver::on_resized(window_id, ctx, PhysicalSize<u32>)` (after the render root has the new size) and `on_theme_changed(window_id, ctx, winit::window::Theme)`, default no-ops.
- `masonry` 0.4.0 (`masonry-selection.diff`): `TextArea::selection_bytes()` (anchor, focus), the only way to read the caret, to keep it across a remote merge; its Cargo.toml allows `unfulfilled_lint_expectations`.
- `masonry_core` 0.4.0 (`masonry_core-tags.diff`): upstream's `remove_child` never frees a removed widget's tag, so re-adding a tag debug-panics and lookups find a dead id; the patch keeps the tag in `WidgetState` and frees it on removal (test `tags::`). Its Cargo.toml allows `unused_imports` and `unfulfilled_lint_expectations`.

### Tests
app/tests/it: `data` over an in-memory store (app group, favorites, open, delete, demo kinds and search, the look choice), `edit` (splice, caret mapping), `fields`, `time`, `sync` (two devices), `share` (two people by hand-delivered commits, each ingesting all the other's commit plaintexts: tagging shares nothing, reach through another's tag, undo, edited time), `chat` (two people by hand-delivered commits; edited, deleted and nameless messages; a hostless store; a link to a chat already here; joining a new chat needs a serving peer, checked by hand). The `sync` and `share` tests copy commits through `osis::internals` (`export_bundle` covers only synced groups' sync IDs, which leaves out the app group); app code itself never uses `internals`. libs/kit/tests/it: `list`, `marshal`, `tags`, `theme` (every default readable in both modes; odd synced colours made opaque and sRGB; white card text darkens a pale tag colour; extreme parameters stay finite). The window is checked by hand with the gui-testing skill.

### What the prototype showed
(Asks of core: issues tagged `core-ask`.)
- The watch-driven model works with very little driver code; the cost is in re-reading (no queries) and one subscription per visible note.
- No well-known per-app root: the app finds its group by scanning home and tolerates duplicates (issues/app-group-helper.md).
- Masonry 0.4: `TextInput`/`TextArea` do not fill a flex slot by themselves (`SizedBox::expand`); `Portal` content needs `content_must_fill`; `reset_text` drops the selection (the app maps and restores it via the patched `selection_bytes`); user events reach the driver only as `Action`s; `NewWidget` takes a tag or properties, not both.

### Core features the app has yet to adopt
Remove each line once adopted.
- Undoing a creation deletes the thing (redo restores it), and `undo_target`/`redo_target` (`commits --next`) give the one change `undo`/`redo` of a scope would revert: `Data::undo`'s creation skip and `next_undo` can go (use them to label or disable undo and redo).
- A thing watch sees a delete as aspects going absent and `has_content` is false for a deleted thing: `Data::opened` can check that instead of scanning `things()`.
- `groups_of(t)` returns `GroupsOf { item_of, subgroup_of, within }`: `tags_of` can read `item_of` and `subgroup_of` instead of scanning `all_tags()`.
- `Write::delete` removes the thing's memberships and subgroup edges in every group the node may write (skipping others): `Data::delete`'s scan for parent edges can go.
- A typed read of a stored value of another shape (or a newer version's enum case) reads as `None` with a `Mismatch` diagnostic: `Data::get`'s wrapper can go (`db.at(t, k).get()`).
- `db.changed(t) -> Option<ThingStamp>`: the last content change (not membership or sharing), else the creation, shown by `.shown()` (`min(ts, received)`, as `created`): `Data::changed` can use it instead of a commit query (which scans every aspect) per thing.
- `Config.dispatch = Dispatcher::Pump(wake)`: callbacks run on the thread calling `db.settle()`; `wake` (any thread, maybe under the osis lock, once per batch) only posts the UI wake. kit's `marshal` mailbox can go: wake the event loop, then `db.settle()` on the UI thread, and callbacks touch state directly.
- A membership change that leaves a durable thing in no synced group while the target group's own data syncs (an item of home, not a subgroup) fails `Invalid`; the app group already avoids this.

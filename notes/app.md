# The first-party app
> Summary: The first-party app over osis and schema/ (decided with Tess). Start here before any change to app/ or libs/kit/: the rule that the app is divided by view and never by feature, with its tests; the model (things, facets, pages, entries, sources, arrangements, views as data); the code shape; the look; state in osis; the kit/app split; Masonry without Xilem; platform work; text input (one model for every platform's input methods); how to run it; the app as built.

## Direction (Tess)
- Fresh and timeless, not a bundle of generic apps over osis types. Bright colours, flatish but not distinctly flat, its own look rather than the native aesthetic.
- Oriented around data, not functionality: no "tab for notes, tab for calendar". Views show whatever combination of things they can meaningfully place.
- Responsive and lightweight on every device; no webview. Native first, web later.
- Build first in something light, simple and running everywhere; if the UX suffers, rebuild differently. Platform work (Rust embedding, possibly an iOS shell of our own) is accepted for the right foundations in text, accessibility and low-level control.
- Convergent design, not a mobile/desktop split: the layout follows the space it is given, small first; more room adds columns. Platform, input kind and window size are independent: touch has nothing to do with Android, Android nothing to do with a small window. Code keys each behaviour on what it is about (the pointer's type, the space given), never on the OS (Platforms and input).
- The mockup is a test bed for the look and the theme spec, not a design to copy. The app leans simpler and less distracting; UX is found by iterating on something to play with.
- Motion: almost none; only unobtrusive fades or motion that adds clarity.

**Fast by construction (Tess).** From core through kit to app, the most ergonomic way to build something also gives it the right performance. There is no typical use to tune for: everything reacts only to what it should, nothing is done twice, nothing scales with the wrong thing. Fix slowness by design and refactoring, never by tweaking hot paths or hiding the slow thing (notes/api-design.md, notes/fast-design.md).

## The rule: the app is divided by view, never by feature
A feature is something a user notices; it is not a place in the app or a module in the code. There is no notes area, calendar area or chat area, in the UX or the source. osis data is a graph of things carrying any mix of aspects, so an app shaped around one kind of data meets, at once, the same data nested, repeated, mixed with other kinds and carrying aspects it never planned for, and answers by growing a second copy of everything.

Good interfaces are specific; things are not. A calendar entry deserves a form made for it, yet no thing is only a calendar entry. The app resolves this by making *views* specific and *things* kindless: a view says which aspects it is good for, and any thing with those aspects can be seen through it, whatever else the thing carries. Views are built from reusable parts, each knowing how to show what is there. Target property: **once two pieces of functionality each work, they work together, without anyone having thought of the pair.** Something that should compose but needs code naming both pieces is a defect in the structure.

Tests for a change (apply before writing it, and in review):
- **Could this be a thing?** Whatever a user might want to arrange, name, tag, favorite, share or find is a thing shown by the ordinary machinery. Settings, a person's own name and saved views are things and aspects, not panels.
- **No kind.** A thing has no type. A view may be as specific as it likes about the aspects it is for, but nothing classifies a thing into one category: a view's fit is computed from aspects present, and several may fit. `if chat`, `match kind`, or a list of things "of type X" is the smell.
- **No destination.** No screen, tab, section or sidebar exists for one kind of data. Any thing opens the same way (below), and many things are shown by collections.
- **Name the general concept.** Before adding a widget or block, say what it is with the data removed: "a list ordered by time", never "the message list". If the concept is not reusable, the design is not finished. Two configurations of one implementation are still two views: "a list" and "a timeline" are different concepts even if they share code.
- **Facets do not know each other.** A facet file names only its own aspect family; shared behaviour goes through the facet contract. Only the registry lists facets. A second facet needing a first's data is a missing contract method.
- **Mix must work.** Every view accepts things it did not expect: no aspects it knows, several kinds of content at once, a thing appearing twice, a cycle, things unreadable or deleted. A view shows what it can place and leaves out, without error, what it cannot.

## Terms
Used exactly, in code and notes.
- **Thing**, **aspect**: as in spec/requirements.md. A thing has no kind.
- **Facet**: the app's knowledge of one aspect family (Model). Draws nothing on its own terms: it supplies parts a view places.
- **View**: a node of the view tree: a *view type* (code), a *subject* and a *config*. Its output is `Block`s, some of which are child views.
- **View spec**: the data naming a view: type, subject, config. Plain, comparable, storable.
- **Config**: a view type's display properties (compact, read-only, what to show). The same code differently configured is the same view type. Unknown properties are ignored, so a stored config survives other versions.
- **View tree**: the window's nested views, rooted at the shell. Every piece of content on screen is a node. A node's identity is its path, which keys its state and its text sessions, so the same thing may appear twice at once.
- **Content view**: a view type presenting one thing's content for some combination of aspects (note, event, person, stream, collection). Knows nothing of how it was reached: no tabs, tags or sharing chrome. Its **fit** is computed from the aspects present; none means not offered.
- **Opener**: the generic view type a thing opened from anywhere gets: selects a content view, shows tabs if several fit, holds the thing's chrome (bar, context menu, Add, places, who can see it, change and undo), and nests the content view.
- **Raw view**: the content view showing and editing every aspect from its schema type, kind-free.
- **Collection view**: the content view of many things: a collection config resolved to entries, arranged, each element a child view.
- **Element spec**: which view type and config a collection uses for its elements; default a tile. A named content view there is an embedding, so a board's cards are note views configured to look like cards, never the opener's choice.
- **Tile**: the small view type of a thing from its summary.
- **Block**: the closed, toolkit-free presentation vocabulary a view outputs.
- **Entry**, **source**, **arrangement**: under Model. **Window**, **node state**: under State in osis.

## Model
- **Thing**: the unit. No `kind` aspect exists (notes/tags.md); a thing is whatever its aspects make it, and may be several at once.
- **Facet** (one file per aspect family, kit's `facets/` for core aspects, the app's for its own): everything the app knows about one family of aspects, behind one contract: whether it applies (the aspects are present), its part of the thing's summary (name, descriptor words, icon, colour), its section of the page, its entries, its search text, what it offers to add or create, and any live subscription it needs.
- **Opening a thing**: every open goes through the opener, which picks the content view with the best fit (accounting for the most of what the thing carries; ties by registry order), offers tabs when several fit, remembers the viewer's choice per account (`ui:viewed_as.0` on the app group, so it works on what they cannot write; a stored choice that no longer fits falls back), and gives the content the whole space. A thing no designed view fits opens in the raw view, which is otherwise reached from the context menu and is never a tab.
- A view whose fit is capability, not data held (`always_offered`: Look, on the account group) is offered although it accounts for no aspect yet. Home is the opener on the account group with `no_chrome`; collection and Look are its tabs.
- **Embedding a thing**: a parent wanting a specific presentation names a content view and config directly; that view is always shown, with no choice, tabs or chrome.
- **Entry**: one item a view shows: a key, the thing it belongs to and opens, and whichever of title, text, author, time, span and actions it has. By default a thing is one entry from its summary; a facet may instead expand it into several, not necessarily things (the occurrences of a repeating event; the messages of a chat).
- **Source**: what a view looks at: a thing's members, everything held, or the account's favorites, narrowed by aspects present and ordered.
- **Arrangement**: how entries are placed, independent of their source. Cards, rows, outline (nesting by subgroup; a cycle is cut at a repeat), days (by span, admitting only what has one), stream (by time, oldest first, following the end). Cards, rows and outline show one entry per thing; days and stream expand, so a stream or a week of a group merges everything its members contribute. All but days are windowed lists (`cx.list`): a page holds at most a window of rows and scrolls by asking for another.
- **Collection config** = source + narrowing + order + arrangement + element spec, as data: `ui:collection.0` on any thing (schema/ui.osis). A saved collection is a thing like any other, with a name, tags, a place among favorites and a page. Calendar, People, Tags and Recent are four seeded values of this aspect (app `store.rs`), nothing else. Home is the app group, whose collection's source is the favorites. A viewer's own arrangement (`ui:arranged.0`, per account on the app group) beats the stored one.
- **Everything held** is the closure from the app groups and every group this store syncs (`status().groups`, less home and the app groups) through tags' members. Nothing has to have been made by this app to appear.
- **Create** is an empty thing plus what the chosen facet offers; the default-view rule then opens it in the view that now fits. **Add** on any thing offers the same list, so a note gains a time and a chat gains a body by the path that made them.
- Every search hit, list and favorite goes through the same summary. Placing into a shared tag should confirm the reach (notes/tags.md guideline; unbuilt).
- Tagging never shares: tagging a tag nests it as a subgroup, sharing through a tag is core's `add_with_grant` (notes/tags.md); the app grants nothing itself (Tess). Backlinks from markdown (`body.0` has no tid reference syntax) are a library-side question (Tess).

## Code shape
Kit owns the view system, so a small app gets all of it; the app is a registry and its own facets.
- `libs/kit/src/view/`: toolkit-free. `Block`, `Cx` and `Act`, the dependency graph (`graph`), the tree of shown views (`tree`), keyed list steps (`keyed`), `ViewSpec`, `Config`, the `Action` and `Facet` traits, sources, arrangements (`arrange`: `OUTLINE_NODES`, `DAY_ROWS`, `STREAM_HEAD`), `paged` (`cx.list`, `Page`, `At`, the window cell), search, `Sessions`, `registry`.
- `libs/kit/src/views/`: `ViewType` (fits, parts or custom render, a `sample` subject for the cost checks), `render`, `expand` (a whole tree as a value, what tests read), `opener` (fit and default rule, tabs, bar), `chrome` (places, Add, reach, changed, undo: a node of its own so its changes do not rebuild the content), `collection`, `note`, `raw`, `tile`, `look`, `shell` (layout).
- `libs/kit/src/facets/`: core aspects: `name`, `body`, `members` (collections and the arrangement chooser), `places`, `add`, `about` (reach, changed, undo), `look`, `fields` (raw's rows).
- `libs/kit/src/store.rs`: `Data` (account state over an `Account` the app supplies, and the `Registry`): account groups, windows, favorites, look, open thing, everything held.
- `libs/kit/src/render/`: the shell driver and Masonry widgets for `Block`s; with `widgets/`, the only code touching the toolkit.
- `app/src/`: `store` (`AppAccount`: the app group among home's subgroups, the seeds, the registry), `facets/` (`event_time`, `event_place`, `contact`, `log`, `color`), `views/` (`event`, `person`, `stream`), `time` (event times and repeats), `demo`, `main`.

Reading and writing are split by type: a render gets `Cx`, an action `Act`.
- **`Cx`** derefs to `Reader`, every read: `cx.db` (`osis::ReadOnly`: a write, a listener, a session, the clock or creating the profile does not compile in a render; `cx.now()` and `cx.now_local()` are the time), `cx.things()`, `cx.tags_of(t)`, `cx.state(key, node)`, `cx.summary(t)`; also the node's `path()`, `config()` and `window`. Reads through a render's `db` subscribe.
- **`Act`** derefs to `Data` (`Reader` plus every write: `set_open`, `toggle_favorite`, `delete`, `db.write()`), holds the effects and sets node state (`set_state`). Its reads are untracked.
- **The graph** (`view/graph.rs`, notes/fast-design.md): one node type, a key, a value, a `ReadSet`, a dirty flag. A view render is a node; `cx.memo(key, f)` is a node; a local cell (`Local`: search query, the minute tick, dark, pending typing) is a node set from outside. Equal output stops propagation. `f` is a plain `fn(&Reader, &K)`: it cannot capture, so a memo depends on its key and its reads, not on where it is called. What many nodes read is a shared memo (`things`, `favorites`, `groups`, `summary`, `aspects`, `members`, `tag`, `collection`, `name`, `window_opt`), so there is one listener per address.
- **The tree** (`view/tree.rs`): the views on screen, each a graph node. A changed read marks its node; the shell's update runs marked nodes parents first; a parent that came out different reconciles its children; what is not marked does not run.
- **Sessions**: one text session per editor, following its field: another editor's committed typing, a cleared draft or an undo shows in every open editor. Actions commit pending typing where it must land first (`commit(t)`: Send, Undo, Delete); the about chip counts it as undoable (`pending(t)`, the `TYPED` cell).

Closed and open sets, deliberately:
- `Block` and the arrangements are closed: they are the vocabulary, and a new word has to be general. A feature wanting a new `Block` first states its general concept.
- Facets, `Action`s and per-section UI state are open: a facet defines its own action structs (`impl Action`, compared by value so a model stays comparable) and state type, with no central enum to extend. Actions get a typed `Input` (press, text, reorder).
- A slot per facet section is rebuilt only when its model changes, so editors keep their caret. Editors are `Block`s, each bound to its own session on a `(thing, field)`, kept while shown.
- A new aspect family is a new facet file and a registry line; it then appears on tiles, search, every arrangement and the raw view with no other change. A designed interface for it is one more content view, offered wherever it fits and embeddable by name. A change needing edits elsewhere for one family breaks the rule.

## Schemas: the architecture you can read
`schema/ui.osis` (`ui:`) is kit's data model; `schema/app.osis` (`osis_app:`) holds only what is specific to the first-party app. A reader of those two files should see the architecture without opening code: every stored concept in Terms is declared there under the same name, documented for someone who has not read the code. When a design changes, the schema changes first.
- **The line**: would a small app built on kit alone need it? Then it is kit and `ui:`: view specs and configs, collection configs, windows and node state, `viewed_as`, `arranged`, favorites, theme and mode. The app's marker, colour fallback, demo marker and the state of the app's own facets are `osis_app:`.

## State in osis
All state a user could miss lives in osis, so it syncs, survives restart and is reactive by the same path as content: a state write fires a watch and the affected nodes re-read; there is no separate UI-state path. The app is osis's first demanding client: friction here is a finding about osis (issues tagged `core-ask`), not a reason to route around it.
- **Window**: a thing per window carrying its state, listed per device on the app group (`ui:windows.0: map<node tid, tid>`), items of an internal non-tag subgroup of the app group, so they sync and are not in everything held. An ordinary thing: its raw view works, and showing another device's window needs only its tid.
- **Node state**: a view type's state is its own typed aspects on the window, each `map<node path, T>`, read and written by `cx.state(KEY, node)`. Paths use the view type and child key (a tid or entry key), never an index, so they stay stable as siblings come and go.
- **Which lifetime**, per aspect:
  - Account-wide, durable, on the app group: what a person decided about a thing (`viewed_as`, `arranged`), favorites, theme.
  - On the thing: what is meant for its other readers (`ui:collection.0`).
  - Per window, durable: where the window is and what is half-done: the open thing, a calendar's week, raw mode, a composer's draft (an editor `Block` over its window aspect) and reply target. Restored at start.
  - Per window, ephemeral (`+` aspects, notes/ephemeral.md): an open picker or menu.
  - Not in osis: what is too hot to be data: caret, focus, drag position, animation. A list's window (anchor key and rows around it) is a local cell kept across rebuilds of its slot; a later candidate for osis (as the anchor, never pixels).
- An app's own per-account data (favorites, arrangements, themes) lives in an internal group found by scanning home's subgroups for the app's marker aspect, reading the union and writing to the smallest tid (Tess: a well-known per-app thing is incoherent, since a tid depends on its first admin; issues/app-group-helper.md). Two nodes racing: `things()` keeps one collection per `(collection.0, name.0)` (smallest tid) and `favorites()` maps the other group's entries onto those; `toggle_favorite` and `move_favorite` never copy entries between groups, so a concurrent unfavorite wins.
- Asks of the library: ephemeral aspects support watches, queries and backlinks like stored ones; the app pumps the watch dispatcher on its own UI thread (`Dispatcher::Pump`).

## Layers
A toolkit swap rewrites kit's `render/` and `widgets/` only: `view/`, `views/`, `facets/` and `store` hold all behaviour and policy, toolkit-free. Kit's driver pieces are `Dispatcher::Pump` (watch callbacks on the UI thread, in `db.settle()`; `render` queues their messages and drains after it) and `list` (keyed reconciler: `reconcile` keeps the longest ordered run of unchanged rows and replaces every other row, `KeyedList` applies the steps to a `VirtualList`; a structural change ends a drag).

## Look and themes
One main colour from the content (the open thing's, else the first among what it holds or links; a soft grey on home) drives accent, selection and a subtle background; everything else is a theme's parameters (notes/theming.md). Themes (Tess-approved): Clarity, Glass, Project, Memphis, Slate (square, flat, modern), Velocity (flat, white or dark grey, anime-ish); each has light and dark, mode (Light/Dark/Auto) separate. Backgrounds: the theme picks what is drawn, the content the colour, the open thing's tid the arrangement; subtle shading of one colour, not splotches of several. Less UI: fewer bordered elements.

**Web mockup** `app/mockup/` (plain HTML/CSS/JS, no osis; serve the directory, e.g. `python3 -m http.server`): explores look and layout. Tess's brief: things and scopes (tags, views) are fungible tiles in one list or grid; an ordered favorites list; one search over names, content and scopes; with a view open and room enough, a left bar holds search and favorites. The look should feel like what 1996, 2006, 2016 and 2026 thought 2026 would be: coloured gradient backgrounds or abstract shapes, a little Apple liquid glass (never at a perf cost), almost no Material. themes.js and engine.css are the theme reference implementation.

## kit and app
Two projects, `libs/kit/` (`osis-kit`) and `app/` (`osis-app`).
- **osis-kit**: the first-party UI toolkit over Masonry: the view system (Code shape), platform shells, the osis-Masonry driver, the look, common widgets, generic osis views needing only the osis API, and the patches we carry to low-level crates. A small special-purpose app that looks like the main one depends on kit alone. kit abstracts over neither the osis API nor Masonry: it re-exports Masonry (`kit::masonry`, one pinned version) and apps use its types directly; design an abstraction only when actually changing base.
- **osis-app**: the registry and the facets and content views of its own schemas.
- Workspace members outside default-members (notes/build.md); forked crates' `[patch]` entries are in the root Cargo.toml.
- Tess: the app builder updates and refactors kit as needed (Masonry upgrades allowed); core is never edited from app work: gaps become `core-ask` issues.

## Toolkit: Masonry without Xilem
Masonry is a retained widget tree designed to sit under other frontends; Xilem's job is to own app state and diff it into Masonry. With osis holding the state and delivering fine-grained changes, Xilem solves a problem we do not have. What we get: Vello (2D, GPU compute; vello_hybrid for low-end GPUs and WebGL, vello_cpu without a GPU), Parley (rich text layout, IME), AccessKit designed in, a funded multi-contributor org. Costs: pre-1.0 with breaking releases: pin versions (`=0.4.0`), upgrade deliberately, keep the driver small so churn lands in one place; thin docs (read source); a small stock widget set (we build our own anyway).

Alternatives weighed:
- **Slint**: the most mature on all six targets, excellent tooling, software renderer. Against: UI in a separate DSL, drawing limited to paths, plain-text editing only, less low-level control. The pick under "light and simple now" alone.
- **Makepad**: web plus all five native targets, shader-level drawing. Against: thin docs, small team, unusual DSL, no accessibility, needs a GPU.
- **Xilem** on Masonry: duplicates osis's reactivity.
- **egui**: the look is hard to escape and mobile text input is weak. **iced**, **GPUI**: desktop only. **Dioxus native**: immature, mobile is webview. **Compose Multiplatform**: Kotlin, JVM desktop. Flutter and webviews excluded by Tess.

## Platforms and input
Principle: a platform shell supplies only what really differs by platform, through one interface; every decision is common code keyed on what it is about. A `cfg(target_os)` outside a shell (and masonry's own platform glue) is the smell.
- **Shell supplies**: raw input events (pointer with its type, keys, input-method edits), the platform's gesture thresholds, the clipboard, the soft keyboard (show, hide; a no-op where the platform decides), a native selection menu where there is one, the surface, insets, Back, scale and dark mode.
- **Common code decides**: gestures, when the soft keyboard is wanted, what the selection menu holds and where, the layout.
- **Layout**: from the space given, never a named device class or a picked size (The shell).

The interface is kit's `platform::Platform`, a trait object the shell gives `Ui::start` (through `Started::start`): `clipboard`, `has_clipboard_text` (whether Paste has anything, without reading the clip: Android toasts on every read), `set_clipboard`, `keyboard(wanted)`, `show_selection_menu(&SelectionMenu) -> bool` (show, or change the one shown; false: kit draws one), `hide_selection_menu`, `thresholds()` (double-tap time and slop, long-press time, touch slop; logical px). A trait object, not signals or a struct of fns: one value per shell holding what its answers need, synchronous where the answer is needed at once (paste), and a recorder in tests. Desktop (`window/desktop.rs`): masonry_winit's clipboard, no-op `keyboard`, no menu, constant thresholds. Android (osis-android `shell.rs`, notes/android.md): the clipboard over JNI, keyboard and menu as view effects queued after the shell's own, `ViewConfiguration`'s thresholds. Raw events reach `Ui` as calls (`pointer`, `text_event`, `text_focus`, `paste`, `copy`, `menu_pick`, `menu_gone`, `back`, `set_insets`, ...); every shell's pointer and text events pass through `Ui` (desktop: masonry_winit's `on_pointer_event` and `on_text_event` hooks), so the menu sees all that can change a selection.
- **Gestures** (`input::Input`, the one recognizer): a mouse goes straight through, its clicks counted (from the last release to the next press, within the slop; 1, 2, 3, then 1 again: caret, word, line). A touch or pen is held back until it is clear what it is, so widgets see only what it meant and need no touch code: a tap (lifted within the touch slop before the long-press time) arrives as press and release, counted as clicks are; a scroll (past the slop first) arrives as `PointerEvent::Scroll` pixel deltas where it went down, so whatever scrolls for a wheel scrolls for a finger, with no press begun; a long press (held still past the long-press time) arrives as the touch's secondary press (masonry_core's `is_long_press`: secondary button, not a mouse), then moves and a release. Widgets acting on a press take the primary button only (`Tile`, `Chip`, `IconButton`; masonry's own already do); those with a long-press meaning take it: `VirtualList` picks the row up (then drags it as a mouse would), `TextArea` selects the word. The long-press timer is a thread per held touch sending `Msg::LongPress(seq)` and waking the shell (`Input::long_press`; a move after that time also counts). A lift while scrolling flings: the speed over the last `VELOCITY_WINDOW` decays by e every `FLING_TAU`, stopping under half a pixel left or at an edge; `Root` reports animation frames (`widgets::Frame`) while one goes on, and render's `Attached` hands each to `Input::frame`. A touch landing on a fling stops it and is nothing else. A held touch shows as a hover, cleared by a `Leave` once lifted or scrolling. Other fingers while one is followed are left out (no pinch). A pen is touch.
- **Text by touch**: a long press selects the word under it, or on whitespace the nearest word. masonry `TextArea` (patched) then shows two selection handles (until the text changes, the selection collapses, a primary press or focus loss) in the caret's colour (`Look::caret`: the accent moved in lightness to read on a field at least as well as the text). A touch within the touch slop of a handle (`TextArea::handle_at`) drags it (`drag_handle`, never collapsing the selection) once past the slop; lifted before, it is a tap on what is under it, and held still it is no long press. A secondary mouse press in a field focuses it and puts the caret there unless on the selection.
- **Selection menu** (model in `input::Input`): cut, copy, paste, select all, for the focused field's selection as it was when it opened. Opens after a touch long press in the field, on a touch's first tap on the selection (a toggle: with the menu open it closes it; a tap following taps counts as a double or triple tap), and on a secondary click in a field (at the pointer). Holds Cut and Copy with a non-empty selection, Paste when `has_clipboard_text` said so, Select all unless all is selected; with nothing to hold it does not open. Closes at the next press (not on a handle or on kit's menu), a wheel scroll, Escape, Back, a pick, and when the field loses focus, its text changes or its selection collapses (`Input::follow`, after every `Ui` entry that can change them); any other selection change (a handle drag, Select all, the layout moving the text) moves it and changes its items. A pick sends `TextEvent::Command` (masonry_core's `TextCommand`) to the field, the path its Ctrl/Cmd shortcuts and Android's keyboard buttons take. `SelectionMenu { at: Place, items }`: `Place::Selection(rect)` (`TextArea::selection_area`, handles included) or `Place::Pointer(point)`. The shell shows the platform's own menu when it has one (Android: a floating `ActionMode`), else kit draws it: `widgets::Menu`, a layer over the window (`RenderRoot::add_layer`) whose root takes no pointer; beside a selection a row above it (below without room), at a pointer a column dropping from it (flipped to fit). Its items take no focus: `Input` takes presses on it, and a screen reader's click on a `MenuItem` reports `MenuPick` to `Ui::action`.
- **Soft keyboard**: focus is where keys go and never shows the keyboard by itself (home's search is focused at start so a hardware keyboard types into it). `Input` wants it for a tap or click over the focused text field (never a drag's end, a scroll, a long press or a secondary click), and for `TYPE_IN` (view/mod.rs): the field to type in next as (thing, aspect), which any action may set (`UseOffer` names a new thing's title, `facets::name::TITLE`); `Ui::serve_typing` focuses the first such editor after the update and clears the cell, so no later rebuild asks again (`layout::a_new_things_title_asks_for_the_keyboard_once`). Whether a keyboard then shows is the platform's. The shell reports input-method sessions (`Ui::text_focus`). Desktop: winit's `set_ime_allowed` is both "an input method may run" and Wayland's on-screen keyboard request, and input methods must type into a field focused without a click, so masonry_winit allows it while a field has focus: a Wayland on-screen keyboard follows focus (a winit limit).
- **Clipboard**: one path. The widget asks (masonry `TextArea`'s commands from Ctrl+C/X/V/A, Cmd on macOS, the menu or Android's keyboard buttons: cut and copy `ClipboardStore`, paste `ClipboardRead`); the shell hands it to `Ui::copy`/`Ui::paste`, which use the platform's clipboard (paste answers `TextEvent::ClipboardPaste`).

Platform work accepted:
- Desktop (Linux, Windows, macOS): winit. Test with the gui-testing skill.
- Android: a View of our own on the UI thread (osis-android, notes/android.md): Android's keyboard works only through a View's input connection; AccessKit has an Android backend, unwired.
- iOS: winit's backend is thinly exercised, IME weak, no AccessKit backend: expect a UIKit shell of our own hosting the render surface and feeding touch, keyboard and VoiceOver into Masonry.
- Web: later; WebGPU for Vello, vello_hybrid/vello_cpu for a canvas fallback.

## Text input
One model for every platform (masonry_core `core::text_input`, patched in): the focused text widget's `ImeText` is its whole text (composing text included, as on Android, macOS and Windows) with a selection and an optional composing region, plus `TextInputHints` (purpose, Enter's action, capitalization, suggestions, multiline); it changes only through `Ime::Edit(TextEdit)`: replace a byte range, then set the selection and composing region. `RenderRoot::focused_ime_text` reads it. A shell translates its protocol into edits against what it reads, on the UI thread, so an edit always applies to the text as shown.
- `TextArea` owns the composing region (not Parley's preedit) and a text revision; only input-method edits set the region, anything else (keys, pointer, paste, `reset_text`, `select_byte_range`) ends it keeping the text; it is underlined. Edits replace on the buffer, not through layout cursors (those snap to grapheme clusters); an edit off a char boundary is ignored.
- kit `ime`: `android` (InputConnection after `BaseInputConnection`: UTF-16 offsets, `newCursorPosition`, deletions that never split a character, `TextUtils.getCapsMode`, `EditorInfo` from hints) and `Sync` (what a keyboard keeping a picture of the text is told: selection changes always, a restart when the text changed other than by its own edits and key events). Tested on a real `TextArea` in a headless `RenderRoot` (kit `ime::`).
- Desktop (masonry_winit): winit's preedit and commit become edits (an empty preedit, a commit or the session's end removes a preedit). winit sends no surrounding text and no hints (issues/desktop-ime-context.md).
- kit fields set hints by role (`style::input`): search (search action, no capitals), editors (sentences, suggestions; Done, or Send/Next in a composer), raw form fields (no corrections). Per-field purposes (email, phone) would need a `Block` field.
- Rich editing: Parley has only a plain editor. The markdown editor is to be ours, first a styled-source editor (headings larger, links coloured, markup visible), not WYSIWYG; the one place a plain-text fallback is acceptable early.

## Running it
`osis-app DIR [--peer ADDR]... [--demo] [--theme ID] [--auto|--light|--dark]`. One device with demo data: `cargo run -p osis-app -- ~/osis-try/solo --demo --theme glass`. The store directory is made on first run; `--demo` adds the demo things once (tags, people, notes, this week's events; existing favorites kept); `--theme clarity|glass|project|memphis|slate|velocity` and the mode flags set the look, as does home's Look tab; `--peer` (repeatable) adds peer addresses an existing store lacks.

Two nodes syncing through a third local node of another account (four terminals):
1. `cargo run --bin osis -- -s ~/osis-try/relay init`, then `cargo run --bin osis -- -s ~/osis-try/relay serve --listen quic://127.0.0.1:47833 --admit open` (another account, so it reads none of the groups; `--admit` is deprecated, issues/deprecated-terms.md). Its first line is the address, `quic://127.0.0.1:47833#<key>` (stable across restarts); leave it running.
2. `cargo run -p osis-app -- ~/osis-try/a --peer 'quic://127.0.0.1:47833#<key>' --demo` (quote the `#`). Close the window once it shows (a store is locked while open).
3. `cargo run --bin osis -- -s ~/osis-try/a pair offer`: prints an `osis://pair/...` line and waits.
4. Another terminal: `cargo run --bin osis -- -s ~/osis-try/b pair join 'osis://pair/...'`: prints an `osis://pair-request/...` line. Paste it into terminal 3; paste the `osis://pair-reply/...` it prints into terminal 4. Both exit (`b` learns the peer from the offer).
5. `cargo run -p osis-app -- ~/osis-try/a` and `... ~/osis-try/b`: within seconds `b` shows the demo data; typing in one shows in the other after the text session commits (about 2 s idle) plus sync.

Joining a chat from another device: someone in it runs `osis -s STORE chat link $C`; run `osis-app ~/osis-chat --peer 'quic://HOST:PORT#KEY'`, paste the `osis://link/...` line into the search field and press Enter: the thing opens once a peer answers (at once if this account already reaches it: `Osis::redeem`). An address pasted the same way adds a peer. Name yourself by typing in the title of "You" among the favorites. Later runs find the chat in everything held.

## Prototype (as built)
Masonry `=0.4.0`, masonry_winit `=0.4.0` (wgpu 26, Vello 0.6, Parley 0.6, winit 0.30). Module layout: Code shape; platform modules: Platforms and input.
- **Startup** (`render/start.rs`), one path for every shell: a shell gives `Start` its store dir, peers, `Waker` and the app's `Data` setup (desktop's look flags and demo data go in there, so a fresh store gets them too); `Start::open` makes the dir, opens the store, makes the main group and `Ui`, and returns `Started`, which the shell hosts with `Ui`'s calls plus `error()` and `close()` (closes the store, returning once it can be opened again: dropping alone leaves it locked until the node's runtime shuts down). A failure shows a screen in the default theme with the error (desktop also prints it). Only where the store itself cannot be read (data an older build wrote) does it offer start fresh: the store moves to the first free sibling `<name>.old`, `<name>.old-2`, ... (named on the screen; never deleted or overwritten: a dir rename replaces at most an empty dir, anything else is hard-linked then unlinked; a name taken since names the next) and a new store opens in its place. No action for: nothing at the path, a store in use (`Error::InUse`: a second `osis-app` or a daemon; Android closes an older view's store before a new view opens it), a later step failing (the store is closed first, so a restart finds it free). Tests: kit `start::`.
- `window`: the `Waker` every shell gives `Ui`, and the desktop shell (`window/desktop.rs`: masonry_winit, one window). kit depends on masonry_winit only off Android. `time`, `edit` (`shown_edits`, `map_byte`: carets across merges; typing goes in by `TextSession::edit`).
- kit modules besides: `theme` (the parameters, six defaults, `Mode`, `Look::new(theme, dark, main)` resolving each colour in the main colour, `Look::card(tint)`, sizes and weights clamped for any parameter value), `backdrop` (the patterns as fills, gradients and paths; no blur), `fonts` (every theme font and JetBrains Mono in libs/kit/assets/fonts with their OFL texts), `icons` (SVG path data), `text`, `widgets` (`Chip`, `Wrap`, `Root` (fades the background to a new colour over 600 ms, the one motion; ticks frames for a fling), `Panel`, `Tile` (card, row, new), `Mark`, `TileGrid` (auto-fill columns, for what is not a list), `VirtualList`, `IconButton`, `Page`, `Menu`, `style` (labels and borderless inputs per text role)).
- App: event times: a wall time with a zone (IANA or `+HH:MM`) shows in the system zone, a floating one as written; `event_time::span` gives (start, end, all day) in local wall ms; a `duration` end is elapsed time; `nudge` moves an event, its end along in its own form; `time::occurrences` expands `event:repeat.0` over a window (bounded by `MAX_PERIODS`), leaving out occurrences another event replaces through `event:overrides.0`. App tests never depend on now or the system zone. `facets/log` is the only file naming `osis_chat` (chat's keys and edit rules, notes/chat.md).
- Search: any text; an `osis://` link is redeemed off the UI thread (`Data::redeem`, `JOIN_WAIT` 60 s; a held target opens at once, one not in everything held is placed in the account group); an address adds a peer.
- `delete` is core's: memberships and subgroup edges go in every group this node may write. `opened()` is `None` for a thing gone from `things()`. Reach walks live rosters; `undo` is `Scope::Thing` skipping the creation commit.
- Raw (`fields`): every aspect but the system's, flattened to scalar rows by schema type, edited as text and written at the row's path. The contact form writes a field of an absent struct alone; an email or phone rename is remove + put by key.

### The shell
An open thing's page has the rail (home row, search, the favorites as a collection, New) beside it exactly when both fit in the window's width clear of its insets (`render::rail_needs`: twice the rail's width plus edges; the rail is a column of rows at their least useful width `ROW_MIN`, the one picked width, also where lists put rows side by side; a page at its smallest is as wide as the rail, so the rail never takes more than half; all scaled by the theme's spacing). Without the rail the page fills the window and its bar has Back. No width or device class exists. Home is the opener of the account group, no bar, the brand and search above it, no max width (a wider window adds columns). Layout is rebuilt on the open thing, the rail coming or going, or the look; every other change goes through node models. Starting a search rebuilds nothing: the field stays the same widget (an input method keeps its session) and `IndexedStack`s beside it switch to the results. Root keeps the screen clear of the window's insets (system bars, keyboard). Cards, rows and outline draw their default tiles inline from each `Entry` (no child node per tile, so the list keeps drag-reorder); a named element spec is a child view per element shown.

**One scroller per page** (`widgets::Page`: home's column, the rail, a `Block::Filled` page; a page inside a page is plain content of the outer one). A page lays out at the height it is given and one scroll position reaches all of it; two scrollers are never nested on one axis. A page is its head (a thing's bar and tabs: `Block::Filled`'s `above`), content and foot (`has_foot`: a composer).
- Without a list the content gets the page's height when it fits (a filled child takes what is left), else its own height, and scrolls; nothing is squeezed below its own height (an editor is as tall as its text).
- With a list, the page is that list: what is above and below it are its leading and trailing parts, and the list holds the one position (`Part::Head`/`Rows`/`Foot` and an offset). The page tells the list where it sits (`LayoutCtx::descendant_origin`) and moves its content by what the list answers; every scroll input (wheel, touch and fling, keys, bar, a screen reader, scroll-into-view) moves that one position, so a fling crossing head, rows and foot carries on whole. Head and foot are pinned while the page keeps at least their height together, else they scroll. One bar: the list's when there is one, else the page's. A list following its end puts the page at its end.
- The page's list is the first laid out in it; any other list on the page (a named element spec's tile view) is laid out whole with the rows of its window (`WINDOW`), never asking for more, so its cost is bounded and rows past it are reached by opening its thing. A move into the head across unloaded rows loads windows towards the start first (`VirtualList`'s `to_head`).
- A focused text field comes into view at its caret when it takes focus, a key moving its caret brings it into view, and its caret stays in view when something other than a scroll moved it (a soft keyboard's insets, a shorter window, its text grew; `Page` compares the caret around each layout, `LayoutCtx::focused_area`).
- Rejected: a page and a list each holding a scroll with a hand-off (two states that drift: the list at its end while the head shows, a lost wheel remainder, a jump when rows start fitting); a least page height (scrolls the whole page around the list: two nested scrollers); the page as the only scroller with lists as windowed content (a list's place is known only after its parent lays it out, and Masonry cannot lay a list out again when only the page moved).

### Patches

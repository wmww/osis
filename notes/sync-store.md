# Sync: store
> Summary: osis-sync's `store` module (core/sync/src/store/): the one ciphertext store per node for every sync ID, read or kept unread; its two parts, the engine's ciphertext door, own entries, what it follows of the engine (parked entries, served heads, carriers of pending commits), caps and the policy, and the bounds on what peers make it keep.

Spec: spec/sync-ids.md §5-§6, spec/sync-streams.md §3, spec/sync-inbox.md §3 Deposits, spec/sync-judgement.md §4 (stand state). Overview: notes/sync.md. The underlying store: notes/local-store.md. Why one shredding store: notes/sync-reasons.md, Nodes.

**Principle:** one store of ciphertext per node, for every sync ID read or kept unread: it decrypts nothing and judges no open; every operation is one transaction (a crash keeps all of its rows or none) and every row change stamps, so memos and `Effects` may read it. What a peer makes it keep is charged to that peer.

## What it owns
Entries (wrap or filler, stamp, deposited flag, own, role, class, expiry; held elsewhere in a row of its own, status's), tombstones with what the entry was (also by blob, `tombstoned_under`: read's forgetting asks whether a delete of a commit's blob is recent under any sync ID), blob bytes once per node, the path per sync ID (steps and claim sets), the node log with a per-sync-ID index (osis-store `nodelog`; a join costs that sync ID's events), usage per sync ID against the caps and the deposit budget, charges against each peer's budget, and the rows a source keeps for `read` (stands, deletes seen). Row layout: `store/rows.rs`' module doc. A repair's freshly encrypted blobs are linked only by the repair, so a source deleting one refuses it.

## Two parts, one rule set
Ephemeral entries, their tombstones, bytes, the engine's memory holds and a connection's source rows live in a second osis-store kept in memory (`Inner::ram`: a `MemoryBackend` store whose transactions all run in memory mode; lost at a restart). Every entry rule (`store/entries.rs`: insert, change, remove, tombstones, usage, charges, unref) and every store-wide read runs against either part's transaction; `Inner::find` says which part holds an entry, the blob's class which part takes a new one.
- What differs by part is written once, by `t.is_memory()`: the log (node log, or the memory log's counter in `store/memory.rs`); where charge totals add up (a record's wide row or a connection's row, or `Memory::charges`: an ephemeral entry's charge goes with its source, never to an `heir`); a tombstone's lifetime (`TOMBSTONE_LIFETIME` or `MAX_DRIFT`; `t/` rows are keyed by when a tombstone ends); the caps (`make_room`: S's entries/bytes and the durable total, kept counted in `Env::total`; S's bytes and the memory total, summed); and a durable entry may wait for its bytes while an ephemeral one is taken with them only.
- Path rows, the node log, records and every other row are the durable store's alone, so a read of the head or a peer's durable charge (`source_charge`) always opens the durable store.
- Not the durable store's own memory overlay: the engine's suspended transaction (`CipherHost`) may hold no memory rows (`Transaction::suspend` refuses them), and in memory mode that store still writes its node log, records and `changed` rows durably.
- The memory part's writes (log events, feeds, charges in `Memory`) are not undone when its transaction fails: nothing assumes a module's memory survived a store failure, which closes every connection and restarts the modules (notes/sync-driver.md, Failures).

## The engine's ciphertext door
`Store` is a cheap `Clone` handle over one locked store and implements `osis_store::CipherHost` (`store/cipher.rs`): the engine holds and releases blob bytes through it, inside the engine's own transactions; sync locks it only between engine calls, so one step never holds both. A blob's bytes stay while the engine or any entry of any sync ID holds them.

## Own entries
An own entry logs a commit held here. A commit the engine forgets other than by lost access (released, needed by nothing held, covered, invalid: `sync::bodies::forget`) hands each of its blobs to the door (`CipherHost::forgot`) after the engine's store commits, noted with the releases so a crash finishes it at the next open; `forgot` drops the node's own entries of the blob under every sync ID, untombed. Lost access keeps the engine's blob rows, so its own entries stay, parked (below), and open again when access returns. Peer entries are left to read's judgement.

## Rows other modules keep
A peer's record holds other modules' rows (osis-store `record_put_row(id, tag, sync_id, key, value)`, or `record_put_wide_row` for a row about the record as a whole), one tag per owning module (`store::rows::tag`): store `b` charges, `s` stands, `d` deletes seen; opens and streams theirs (notes/sync-opens.md, notes/sync-streams.md). They go with the record, a sync ID's also with the sync ID. `with_tx` gives other modules a transaction for their own rows.

A source's stand and delete-seen rows (`Store::source_put`): a record's in the record, durably; a connection's as rows of the memory part (`C/`). Both age out after `TOMBSTONE_LIFETIME` by the one `w/` sweep; a record's also go with the record, a connection's with the connection and at a restart (connection numbers start again).

## What it follows (`store/follow.rs`, settled right after leave each round)
Each an `Effects` value: the sync IDs this node syncs (`set::SyncsFollow` over `Store::syncs_feed`; `leave` writes them, `Store::set_holdings`), the caps (`Engine::caps`, `caps^.0`), and per S read here its served path (`Store::serve_path` from `sync.0`).

### Parked entries
The store's form of the one parking rule (notes/sync.md, Arriving early). An entry waits (`follow::awaits`) for:
- **S's read secrets**, when its commit is neither held nor pending here: a peer's entry that did not open or opened to a commit thrown out; an own log of a commit forgotten with lost access (it opens again when access returns). It opens again too as one of S's things comes to be held whole: a commit thrown out as outside the node closure while S's thing was held on a ticket's word alone (its keysets not yet arrived, spec/commits.md §4) is never pulled again, since its blob is held. An own certificate blob, naming no commit, waits for nothing.
- **A thing's secrets**, for each part its blob holds in a section that did not open while that part counts missing (`Engine::blob_awaits_secrets`), whether or not any secret of that thing is held yet, or for want of holding the thing (notes/whole-commits.md Sealed sections). Examples: a sibling's account rotation, whose seed's section sits under the removal's D epoch, established only once the rotation's header and list count; an account rotation's part on the account, opening only from D's sync IDs; a commit held from a certificate copy under another sync ID, whose full blob under a link's K holds the target's `created.0` sealed under the target's secrets (the redeemer's join waits on that record).

It is parked under each awaited value (`Follow::parked`, in memory, one `Effects` key per value: `Awaits::Sync(S)` while S is read, `Awaits::Thing(t)` while an entry awaits it, valued: for a thing `Engine::section_keys`, whether its sections open whole here and its read secrets while they open at all; for S its opening secrets and whether one of S's things is held whole (`Engine::held_whole`); an entry opens again as the flag rises with secrets held or a secret is new). Parking is found by:
- the store's entry feed (which also reports removals, so a gone entry unparks);
- what `awaits` reads moving with no entry moving (`follow::Unheld`): commits held or pending no more (`Engine::unheld_feed`/`unpending_feed`: a commit forgotten with lost access leaving its entries under a sync ID still read, a role commit's certificate under its actor's), and blobs noted no more (`Engine::unnoted_feed`: a commit forgotten whole leaving its peer entries under a read S that still keeps them, such as a released holder's keying commit its readers judge must-hold; such an entry names no commit and waits for S);
- one pass over S's entries when S becomes read (a start, a grant, a raise from kept unread: S's first read-secret settle opens them, which is all a raise needs, spec/sync-judgement.md §6 Read and unread move).

Not parked: a held commit's part a blob of it opened on a thing not held whole (taken out as outside the node closure, on a ticket's word before the thing's keysets arrive) waits on no read secret. The engine names such a commit for redelivery as the thing comes to be held whole (`apply::wake_entered`, `Engine::take_redeliver`), and its entries open again; parking it here would make what an entry awaits move with the closure, which no feed of the store's follows.

When an awaited value gains an epoch, or a thing comes to open whole, only the entries parked under it open again; a pull anew of S opens every parked entry of S, each parked again under what it still awaits. One that gives something held goes off its peer budget. A thing's key opens nothing at its first settle unless it names a secret, so a part on a thing the node reads nothing of costs a set entry, never a reopen. Pending commits are the engine's to re-examine (notes/sync-facade.md Pending), so sync opens nothing again for them.

### Served heads
A stamp vouches only under S's served head; otherwise the entry is charged. At a start and each head move, `charge_unvouched` charges each peer's stamped carrier (its commit pending, or a loose record) whose stamp does not verify under the new head to the peer that brought it (`EntryRow::brought`, kept for every uncharged peer entry, passed on by `gone`); past that peer's budget, or with it gone, the entry is not kept (no tombstone; its pending copy goes as its blob goes unnamed). An honest rotation drops nothing within budget. O(entries of S) per head move.

### Carriers
Pending commits and loose records (spec/commits.md §4 Pending storage): the engine keeps a loose record only while a store entry names a blob carrying it, and a pending copy only while carried, an entry being one carrier.
- `Carriers` follows the store's `unnamed_feed` (a blob no entry names any more: removed, expired, shredded, gone with its peer) and calls `Engine::release_entry` once no blob of the commit is named (`store::release`): the engine forgets the pending copy once its fires and reports (notes/node-closure.md, Pending carriers) are gone too. A blob unnamed also drops the loose records and lists only it carried (`forget_carrier`).
- A start sweeps every pending commit, so one with no blob noted (pairing's) loses its entry then; a body not kept (past its peer's budget) is released at once (`streams::Ground::unkept`).
- A commit held here, or a certificate blob whose loose records were all learned or lists held (`loose_feed`), takes its carriers off their peers' budgets.

### Time
`settle_at` expires entries (no tombstone, no event), ends tombstones and aged stand rows after `TOMBSTONE_LIFETIME`, drops claim sets superseded for `ROLE_KEEP`, sweeps the log's deletion events, and lets the unread sync ID using most give way past the total cap.

## Caps and policy
- `Policy` (`Policy::from_caps`) reads each value from `caps^.0`'s `policy` by field name, defaults where it names nothing; per-thing caps replace `entries` and `bytes`.
- Caps apply to sync IDs kept unread only, but `memory_bytes`, which also bounds what a reader holds of S's ephemeral commits (`memory_room`; a held one's blob counts at `Engine::memory_charge`, at least its bytes, under every sync ID an entry of it is under: `set_memory_charge` keys the charge by blob, kept while an entry names it). Role entries count toward none.
- An entry or tombstone in the memory part counts what it holds there (`entries::overhead`, `tomb_overhead`: its rows at their bytes and `osis_store::MEM_ROW_COST` each, a held-elsewhere row whether written or not, its blob's place, its memory log event, `memory::EVENT`/`REMOVAL`), so the memory caps bound what the memory part holds (`Store::memory_held`; checked at n and 10n by `store::memory_caps_count_what_memory_holds_spec_sync_ids_6`). Durable ones count `ENTRY_OVERHEAD`/`TOMB_OVERHEAD`, an approximation of disk. What they leave uncounted: issues/sync-memory-uncounted.md.
- The deposit budget is the policy's raised to `osis_proto::limits::deposit_budget` for the head's claim-set size. A child step past the caps is taken at most once per `register_every_ms` per sync ID (spec/sync-ids.md §6 Storage caps; why: notes/sync-reasons.md, Nodes).

## What peers can make it keep
- **Tombstones**: a Delete of an entry not held writes nothing, so tombstones never outnumber what was held.
- **Stamp verdicts** (notes/engine.md, Signature verdicts): an entry's row keeps `vouch`, the hash of the key its stamp verified under with S, blob, wrap and stamp (`rows::Vouch`, made only by `rows::check_stamp`/`verify_stamp`), checked once where the entry enters: `log` (any stamped entry, against S's served head; a copy of a held one reuses the held verdict), `take_stamped`, `take_stamp` (a peer's new stamp for a held entry, against the head `sync.0` records: spec/sync-streams.md §4 Applying). Every later check goes through `Store::stamp_under` (read's own-entry, step-parent and deposit checks, `charge_unvouched`): the kept verdict answers when it is that key's, else the stamp is checked and nothing kept (a write would stamp the row and move its readers). So each stamp is checked once per node at its head; a head move to another write key checks each carrier once more.
- **Peer budget**: unstamped entries a peer brought count against its budget (`log` and deposits alike). `log` checks a peer's stamp against S's head write key: one that does not verify is charged as unstamped (and replaces no stamp held), so a forged stamp floods nothing. So what one peer makes pend in the engine, commits and records alike, is bounded by its own budget and never evicts another's; what a writer stamped is charged to its bringer once its key is not the head's.
- **Inheriting charges**: when a peer's connection closes, its record is dropped or evicted, or at a start (every connection that was charged or brought something: connection numbers start again), `gone` hands each durable entry charged to it (and each it brought uncharged) to the first peer record, in record ID order, whose stream showed it present (`heir`: the record's PRESENT row, osis-store `records_with_row`) and whose budget it fits; else the entry goes. A record inherits only what its stream lists, the charge fetching it from that peer would have made, so a hostile peer fills an honest one's budget no more than by giving it junk to relay. A duplicate keeps its first bringer's charge, so without inheriting, a stream that passed the entry (the survivor of a Twin, spec/sync-opens.md §1, or any other peer) would never bring it again. Not inherited: a recordless connection's presence is in memory (streams' `Known`), outside the store's transaction; ephemeral entries go with their source, relisted at the next join and living at most their drift window.
- **Deposits** per sync ID by the shared deposit budget, which any holder of the deposit key can fill until a delete-key holder clears (spec/sync-inbox.md §4).

## A reader's store of S
Its own entries plus those it pulled:
- one that opened to a commit held here (`Opening::Held`) is kept as it came: read judges it as any entry of the body, so readers pass the writer's blob on and encrypt afresh only where spec/crypto.md §5 requires. Charged to no one when it brought something new; a duplicate of what is held is charged to its bringer unless stamped, so a reader's fresh encryptions of held commits fill only its own peer budget;
- one that did not open, or opened to a commit pending in the engine (`Engine::pends`: unjudgeable, an epoch or pages away, drift): streams' `take_body` logs it as the commit's carrier, charged to the peer when unstamped;
- a pulled record or list blob is kept as it came (`Opening::Held`, judged by read's `cert_blobs`); a pulled piece is taken and not kept (`Opening::Taken`).

# Sync: rationale
> Summary: Why spec/sync.md looks the way it does: blobs and labels, stamps and deposits, sync-key gating and claim keys, delete keys and retention at hosts, convergence and compaction, why there is no recycle bin, accepted limits, what a node learns about data it cannot read, policy defaults, rejected alternatives, open items.

The requirements behind this file: spec/requirements.md, Data a node cannot read and Deletion.

## Why
- **One commit ID, one blob per commit, random key per blob**: a commit has one ID whatever groups contain it. Sharing history means adding wraps, never re-encrypting.
- **No commit size limit but `MAX_LIST_BYTES` on its header lists**: a delta pages like a snapshot and the header's lists go by link, so atomicity never depends on size and the API never splits a write. The costs (a reader stores pages it cannot apply yet, a writer that dies mid-upload leaves orphan pages for convergence to delete, apply streams pages through one staged transaction) are the ones snapshots carry anyway. The old one-blob rule bought nothing but a second commit kind of edit (split, non-atomic) that every app had to reason about.
- **Groups as sync unit**: groups are free and overlap; owner actors as the unit would force a copy for every separately syncable subset.
- **Label keys derive from the group's own role secrets**, never the owner's directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the host. The deposit key derives from the actor's deposit seed (not from group secrets, so that a plain group's readers can derive it from the owner's `keys.0`), hence it is keyed by label ID rather than by index: with the index alone every plain group of one owner registered the same deposit public key (found in the final pre-swarm review).
- **Entitlement, not group membership**, decides labeling: a thing dropped into a shared folder without a grant is silently not shared, which is the intended failure; an "add to shared folder" helper writes both. Cache the check per (thing, label), invalidated by role changes of the label actor, the thing's grants or its owner chain.
- **Convergence as the one rule**: must-hold, may-hold, must-not-hold per body. Retag on join, cleanup on leave, compaction and repair after a bad deletion are all this rule. The may-hold class keeps a compactor's drop and a lagging holder's re-upload from ping-ponging. A wrongful deletion is healed at the next holder sync by a fresh encryption.
- **Sections** (whole-commits step 2b; before it: one blob per (readable subset, retention class), "projections"): one blob per commit, one section per thing under the thing's read secret (own or derived by tid), so a thing given secrets of its own later still opens its earlier sections through its history boxes, and a reader of a label derives a section's key from the label's group before it holds the thing's record (which may be inside). A section lists its thing's owner chain in the clear so a reader derives the key before it holds the thing's record (a draft's record rides inside the section). Per-label copies (certificate copies, cross-published `label.0`/`created.0`, and parts a label reads only by role on a reader actor outside its closure, e.g. a thing placed from another actor's tree) are one section under the label group's read secret, as the wrap. A part the writer holds no secret for (a key actor's own record or card) is left out of the shared blob and travels as a certificate copy. A kept part of a blob that holds a dropped one is carried by the rewrite this node places (`body_sends` before `deletions` in a pass; `carried` asks a snapshot only for dropped parts' live writes): with mixed classes in one blob the old "no carrier: snapshot first" path would otherwise snapshot every kept aspect of every drop. Judgments compare an entry's parts the label's actor may read (`readable`), so nodes holding more secrets judge alike; `body_deleted` matches a deleted blob's part set exactly (a rewrite's superset deletion is not the body's). The prefix lists one commitment group per distinct delete-key set among the sections' aspects; a Delete needs every group signed, a Replace one (a rewrite by a right holder of one thing). Mixed retention in one commit (a "last modified, keep-at-most 0" beside a "body, forever") costs a rewrite when the register is replaced: accepted (notes/whole-commits.md §4).
- **Certificate blobs per label**: one blob across labels (a wrap each) would link every label a node syncs through its node card. Cost: a few small blobs per (node, label). They are outside the closure, so convergence names a label's required set as closure plus certificates; without that a group admin's convergence pass would delete them as "outside the closure" and the node would re-deposit forever.
- **Inbox blobs**: a non-holder cannot wrap anything under a label it does not read (a granter is not a reader of the grantee's home label), so everything that must reach an actor from outside goes boxed to its read KEM key: grants, grant changes and removals (so it erases), re-seals, each with the label IDs and hosts it needs (the old text said "the target's `label.0` commit", which a non-holder cannot wrap and which is a join of many commits anyway). They carry a delivery expiry so an unconsumed one frees the budget by itself, and the inbox is a label the recipient's admins administer so they can delete consumed ones. Direct grants to a node go by pairing only: a node is listed by DH key and cannot enter a label cold.
- **Self-certifying label IDs**: a random ID lets anyone who learned it (an ex-reader, a leaked `label.0`) squat it at a fresh host under their own keys. Two admins creating a label concurrently derive the same ID.
- **Blob prefix**: expiry and delete-key commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are the delete keys blinded by each blob's salt rather than the keys themselves, so projections and rewrites of one commit, and blobs of one author or owner across groups, are unlinkable at the host (spec/requirements.md, Data a node cannot read); a delete signature reveals nothing beyond the blinded key.
- **Stamps** (read must not give upload): the author's signature sits inside the ciphertext, so the label write key is the only writer proof a host can check. Signing (label ID, blob ID, wrap) and storing the signature beside the wrap lets anyone relay a writer-vouched entry (LAN-first flows, host to host by push, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. Stamps are checked against the current step, so a removed writer's stamps die with the rotation its removal already does. Upload needs no open: an open added nothing (a current reader could replay a stale stamped blob after its tombstone either way, and a removed one only until the next step), and requiring it blocked blind-to-blind replication. Download does need one, so hosts replicate by push, never pull (an ex-holder could otherwise run a "host" and pull). What a reader legitimately needs under a label goes by deposit: a provisional entry under a per-label budget, readable at once by co-readers, promoted by a writer's stamped re-upload, which frees the budget. Rejected: upload under the write key alone (loses relay); per-holder upload keys (linkable; Open below).
- **A stamped entry never changes at a host** (spec/sync.md §5). Every writer shares one write key and a host cannot read a wrap, so a host can tell nothing about a re-upload: last-wrap-wins let one member hide any message from every device not holding its key (reproduced before the fix). No honest node re-wraps a held stamped entry (`place` skips a blob already under the label, the pass sends only what a host lacks), so first-stamped-wins cost nothing and removed the replacement rate limits. One wrap per entry, no number to pick. A stamped upload over a deposit still replaces, or any reader could keep a writer's wrap out at a host. Residual races: only a first upload at a host can place a useless wrap, so the attacker must hold the blob from another host, or promote a deposit first. Those lose at a reader to any other host's wrap, and to a holder's fresh encryption (the existing path for a tombstoned ID; `gone` marks the entry). The copy goes to that host alone, where it is first by construction, so that race cannot repeat there. Rejected: several wraps per entry (all writers share a key, so a bound fills with the attacker's garbage and helps nothing); key-check values or commitments in the blob (a blob is shared across labels and epochs, and the host still cannot check); holders re-uploading the same blob (with replacement it never settles and leaves a window, without it it is a no-op); asking co-readers (needs reach the reader may not have). Residual gaps: a wrap opening to a wrong key, heard before the body's bytes (not inline: a blob that crossed the connection already, a replay after reconciliation), displaces a good wrap heard next from another host; the entry goes `Bad` when the bytes come, and that reader waits for a key holder's fresh encryption (a host's wrap is heard once per cursor). An honest other wrap under an epoch a node lacks (two writers placing one blob under a new label across a rotation) cannot be told from garbage when heard: a `doubts` row keeps the wrap while the host holds the entry and the mark goes once a secret arrives that opens it to the key. Rotation commits go first in a host's log and are checked with the batch, and a node lacking the head's epoch does nothing at that host, so it acts on a doubt only when the rotation has not reached that host at all (the entry goes, one fresh copy under its older epoch): every holder of the new epoch holds the older by history boxes, and the node already held that blob's key. No hold-off there: garbage and an unknown epoch look the same, and a time limit would be a guess. No OK variant saying "another wrap is held": a subscribed sender hears the add before its ack, and a bare code cannot tell a useless wrap from another epoch's.
- **Delete-key signature plus label key** for deletion: the delete key proves the purge right as of the delta, the label key current roles; the second signature is not redundant, since everyone who ever held an epoch's secret (removed holders included) can sign with its delete key. Level-3 deletes need the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the rotation the demotion already does. Levels 1 and 2 need only the sync key, because a thing's admin or author is often a mere reader of the label (anyone sharing a thing into a group they only read). The item names its level, so the host checks one commitment and knows which label signature it needs. Honest nodes enforce current write permission for every purge (spec/permissions.md §7); hosts only this approximation (spec/requirements.md, Data a node cannot read).
- **Delete keys follow retention**, one per level: the thing's admin delete key for `admin`, the write delete key of the actor above the author node (every device of the account holds it) for `author`, both for `author_or_admin`, all three with the thing's write delete key for `writer`; none for `nobody`. Without the admin level a thing admin who is not an admin of the label's group could not delete at hosts; a writer without the admin secret lists the thing's published admin key (`keys.0`), so every delta carries every level its retention calls for (Tess's decision: signatures over hashed tokens). Known gap: receivers never check the keys a header lists (only their count per level and that one level-2 key serves the whole commit); a vandal writer can list its own key at level 1 or 3 and so delete its own blob where an admin's key was due, no worse than with hashed tokens, and the label delete key still removes the blob. Blobs are projected by key set as well as reader set, so a `nobody` delta is never deletable through a commit-mate's key. Under the shared-owner pattern `author` collapses to `writer`. Chunks list their creating delta's key indices (no per-chunk bytes beyond the indices: the chunk's commitments derive from the header's keys and its own salt); a reused chunk whose thing-level commitments differ from the reusing delta's keys is re-encrypted, else a writer could delete chunks of an `author` value or an author be unable to delete its own; author-chain commitments need not match beside an admin or writer key (under `author` alone, or with no level 2, they must: else another author could delete it), so dedup across editors survives. Residue: an author's explicit purge of a value cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- **Covered means redundant under join**, not "inside the snapshot's frontiers": a snapshot that omits content covers nothing it omits, so a bad snapshot is harmless and anyone can re-snapshot. It also absorbs the versioning rule that a node never compacts what it could not join. A held body or snapshot is judged by the join alone: tables only speak for a body not held. Comparing them made cover stop at a gap: a fresh device's snapshot listed a session at 0 (it held later writes only, the older snapshot had pruned the session), so holders of a dead body found it uncovered and uploaded it, and a right holder that had dropped it deleted it each pass, forever (`snapshot_rights`, `sessions::frontier_gap_covers_what_joins_unchanged_spec_commits_5`). Inheriting frontiers does not help: the pruned session has no entry to inherit. Limit: a dead body is covered by a snapshot whose writer never saw it, so a revoke that revives it is met by `takes_late` as with a pruned session.
- **Tombstones** refuse the identical blob for `TOMBSTONE_LIFETIME`, so a stale relay cannot resurrect a purged body. Holders never need them: they sync before they upload, and a node holding the purge strips the value from any copy that arrives later. The lifetime is a storage-versus-churn dial: infinite is O(deletions) host storage; zero lets any relay or bundle from before the deletion put the ciphertext back until a holder deletes it again. A peer staler than the log horizon returning later than the lifetime can resurrect, and holders heal it. Blob IDs are hashes of ciphertext under random keys, so a tombstone is no fingerprint.
- **No timed deletes from nodes**: keep at most 0 after replaced is deleted at hosts in the killing write's sync; absolute bounds wait for a right holder (spec/requirements.md, Deletion); expiry is the only timer a host runs on its own. A relative keep at most D > 0 used to be honored by a delete the replacing writer timed at the hosts; it was dropped (Tess), with its node-side timed deletes. Hosts still accept a timed delete (spec/sync.md §5), which no node sends: issues/host-timed-delete-unused.md.
- **Purge reaches snapshots**: a compactor's snapshot carries everyone's live values, so purging a write also makes it value-less in snapshot bodies, which are held stripped (leftovers) and deleted at hosts; a writer that then holds no covering snapshot under a label re-snapshots there (deterministic trigger; duplicates are covered-equal and one gets dropped). Snapshots are `writer` so any writer can remove a stale snapshot at hosts; they are redundant by construction, so that power costs only a re-upload.
- **A purge commit is kept `ROLE_KEEP` after its `ts`** (TLC finding S1): the purge SHOULD name dead writes and resets the rest, so the next snapshot covers the purge commit at once and a compactor could drop it; a node that held the purged body and had not yet seen the purge then kept the value for ever (the body was covered, hence may-hold, and nothing ever told it). The same staleness class as revokes (90 days of role history); a node offline longer is an offline copy (spec/requirements.md, Threat model). Rejected: never covering purge commits (a blob per purge for ever); carrying purge items in snapshots (the compactor would vouch for the purger's right, which snapshots never do). `expires` on a purge commit is forbidden for the same reason (the host would drop the request unattended). The API puts a purge and its resets in a commit of their own, so an app's disappearing writes never inherit the 90 days.
- **Must-hold needs a positive "uncovered"**: a node that cannot join a body (parked) or has not fetched a snapshot's pages treats it as may-hold, never must-hold, or an old-version writer and a compactor would re-upload and delete forever. A strict-subset projection of a commit under a label (a writer whose timeline lagged uploaded less) is must-not-hold. A must-not-hold blob holds nothing (TLC S17): it neither holds a body for "the label lacks" nor makes another blob a strict subset, so a purger's rewrite goes up at once beside the purged blob still waiting for its carrier (the rewrite itself, S18), and stays; read literally, the rewrite waited on that deletion (a snapshot). A writer that has not applied the purge yet still deletes the rewrite as a strict subset of its own body until it does (S4; same window as before). node-sync: "must-not-hold" here is "holds a dropped delta (purge, expiry, keep-at-most, compaction) or one the label's actor may not read" (`holds_nothing`; unsettled views count it too, which only keeps or uploads more). Must-not-hold wins every overlap with must-hold (purged while uncovered, past keep-at-most while uncovered): the must-not reasons are the ones that remove content. A body holding no delta (every delta purged) is covered by definition; its header lives on in the nodes that applied it.
- **Rotation commits go up before the step** (TLC R9, second round): "register before any upload" (the host checks stamps against its head's write key, so content stamped under rotated keys must wait for the step) left a window in which a host's head named an epoch whose rotation commit was nowhere: every holder listed in the step reached the head, could not open it, heartbeated stranded and was re-sealed with a secret it had no commit for. Now the registrar uploads the actor's role commits the host lacks (the rotation chain) under the head's keys, then registers, then the rest; a step at a host implies the chain behind it is there (until compaction, where the `secrets.0` snapshot is), and "stranded" means not boxed. What an ex-holder gains is the removal rotation's blob under the old sync key (box map and the removal about itself, which it also gets by inbox), the same as from a dishonest host before.
- **An open ends at a head with another sync key**: before, a host kept an open (and its subscription) across steps, so a removed reader that stayed connected kept being pushed every new entry for the life of the connection. Now an open holds under the sync key of the head it was made at; reads check it lazily (one head lookup) and a push ends with the head event that ends it. Tied to the sync key, not the step: a step without a read rotation removes no reader (an epoch's readers only grow), so its opens stay, and a claim or static open at step j is held by a reader of j's epoch. The registrar's own open ends too: Register is relayable and proves only that the step is signed, so a departed node relaying the step it was pushed must not keep its open by it; the registrar reopens under the new key (one round trip, cursor kept). The remover's rotation commit still reaches a connected departed node, uploaded before the step (above). Co-reader-proof opens at co-reader peers are not step-bound.
- **Refused Register and Deposit learn the code alone** (security review): a Register not a child of the head used to get the head back, and a badly signed Deposit the budget, so anyone with a label ID (ex-holder, link holder) watched rotations and deposit activity forever. Now Error 9 and a budget only under the head's deposit key. Nothing needed them: the node reopened on any refused Register and re-signs a stale deposit from its own seed; heads reach it through its open. Upload and Delete Status lost the head the same way (it let an ex-writer or ex-admin watch rotations by re-sending an old stamped entry); the node uploads and deletes only where the label is open, so the head comes by push, or by the next resync's Sync when unsubscribed. Code 9 itself stays (vs folding it into 1): it tells a signer its key was superseded, not bad, so a stale deposit is re-signed at once with the current deposit key and an ephemeral entry or delete waits for the newer key instead of being dropped (mvp-progress item 66: a stale deposit looped, then was dropped). It tells a holder of an earlier key only that fewer than `OLDER_KEYS` rotations passed since, which it mostly knew. Open's UNKNOWN_LABEL vs REFUSED still says whether a host hosts a label (key-derived ID, accepted).
- **Local drops of live bodies snapshot first** (TLC S11): a body under an absolute keep-at-most written offline and dropped at T before any upload left its live write in one node's state with no body or snapshot anywhere; the snapshot-first rule used to fire only for deletions at a label. Now a writer writes a covering snapshot (a local commit, uploaded later as must-hold) before dropping any body with live writes it holds no snapshot for; readers drop and keep the state. An absolute bound is judged by a keep-at-most timer every held part under one gets on apply (`retention::abs_timer`, one already past included), never at apply itself or by a death or late part judging it first (`judge_at_most` drops at the header's bound only `by_timer`), so node-sync's `due_live_drops` writes the carrier before the drop; an expiry at or before a bound takes its timer key (every part of a body shares its expiry), so no keep-at-most timer is set there; a part of a waiting commit keeps its body until the commit applies. A body under keep at most 0 that still has live writes goes at the next compaction or at its first death plus `AT_MOST_GRACE`, carried then (notes/node.md).
- **Carrier tiebreaks** (TLC S12): the host cannot read the bodies, so two right holders with stale views could each delete one of two identical bodies, or one of two covered-equal snapshots, each counting the other as the carrier. Deterministic choice: an identical body carries only the one with the higher blob ID, and of covered-equal snapshots the higher commit ID goes; a must-not-hold blob (a strict subset among them) never carries.
- **A purged body waits for its rewrite** (TLC S18): node-sync judged a dropped body's liveness by its dropped deltas only, so a blob holding a purged delta and a live one went in the pass that placed the rewrite; a refused upload (a rotation racing the purge, code 9) left the label without the live write until the purger retried, and the spec and model waited for a covering snapshot instead (the rewrite, a subset, carried nothing). Now every delta's live writes count, a kept one is carried by any other blob of the commit that is not must-not-hold (the rewrite, once present at that host) or a covering snapshot, and a right holder that holds such a blob asks for no snapshot (`carried`, `snapshot_first`). Cost: the purged value's commit blob stays at the host one more round trip (its chunks go at once). Rejected: counting any held blob of the commit as a carrier (keeps the race), and waiting for a snapshot (a snapshot per purge). A full label (code 12 on the rewrite) kept the purged body for as long as it stayed full; now a rewrite the host refused for the cap (`SyncEngine::capped`, in memory) counts as the carrier when it is a strict subset of the body (`rewrite_capped`), so the rewrite is uploaded again naming the body as replaced with its delete item (`Fate::Delete`'s `via`, `replace_sends`; spec/sync.md §5 Replace): the host admits it in the body's room and removes the body in one step, so the label never lacks the kept live writes (`sync_review::purged_body_leaves_full_label_spec_sync_7` checks every hop). The first version deleted the body first and re-sent the rewrite on the delete's OK: another upload could take the freed slot in between. While a replacing upload is in flight a plain upload of the same blob waits (`Requests::replacing`): two statuses of one blob could not be told apart. The reverse is open: the pass re-sends a capped rewrite plain before `deletions` sends it replacing, so both are often in flight; the first status takes the replacement list, so a plain OK followed by a refused replacing upload (code 9 after a rotation, delete rate) marks the body absent while the host keeps it (until a reconcile). Waiting for the plain one stalled the purge for good (the pass sends it every time); a fix would skip the plain retry of a rewrite a replacing upload will carry. The purge request itself is a new entry and waits for space like any write. An `Outside` superset (holds a delta the label's actor may not read) waits likewise for its readable projection; deltas the actor may not read are skipped (their carriers are under their readers' labels; counting them kept such a blob, purged or not, for ever).
- **Header-only blobs exist only as lasting headers** (TLC S14 said may-hold, for every retention; the model still does; Tess: tombstones when history is on, purge-tombstone-forever): a purge that empties a body of any other retention leaves nothing under the label; headers persist only at the nodes that applied the commit (dedup by commit ID needs them, and a commit-form dot resolves its author through them). A purged permanent delta's commit, and its purge commit, stay must-hold as a header-only blob where no other body of the commit is wanted (`retention::lasting`, `commit_bodies_under`). Why the request too: atomic apply counts a missing delta as held only by a held request; a new device with the blob alone would wait for good, and treating a header-only blob as proof of a purge would let any writer hide another's message from new devices by uploading one. A writer keeps a witness per purge commit, so the cost stays a header per write, also for an author naming one message many times. What a host learns: one more small stamped entry with no commitments (as a `nobody` body has) close to a deletion it already sees; the header stays encrypted. For readers the header keeps what it always showed (author, actor, `ts`, retention, AK, delta hash, chunk blob IDs); the delta nonce is gone, so no guess of the value can be confirmed. A purge commit's own delta purged in turn: the first request applies as its lasting header at a new device, tombstone shown (`a_purge_purged_in_turn`). Cost: a lasting check is one view scan per commit with no body under the label, per pass, and for a purge commit one local read per named thing: `purge_one` notes a request that dropped a permanent delta (`z/`). Walking the aspect instead cost every full pass R x M for R aspect-wide requests by any writer (M the aspect's commits; measured with 10 requests at 2*10^4 messages: a full label judgment 35 ms to 400 ms, a request's walk about 1.7 us per view and decoding each permanent commit's header). A header-only blob applies as its header alone, a lasting one's other parts joining as they come (`a_lasting_header_applies_and_the_rest_joins`). A node that does not judge a header-only blob of such a commit lasting leaves it (may-hold; `delete.rs::judge`): a node may not hold what made another judge it so yet, and a delete there met the holder's re-upload every pass, its entries piling up (`a_header_only_some_judge_lasting_is_left_alone`); a purge that falls leaves its header-only blobs so; the price is a forged or stale header staying, at most what any stamped garbage costs.
- **A node offline past `ROLE_KEEP` misses purges** (TLC S15): the purge commit is compacted, the returning node's body is covered (may-hold) and it keeps the value bytes until it compacts; the value itself is dead by the snapshot's reset when the purge named dead writes (the SHOULD), so it re-spreads nothing. An offline copy (spec/requirements.md, Threat model); accepted, no mechanism (snapshots carrying purge requests was rejected above). Confirmed for the model: the purge commit's `ROLE_KEEP` overrides its keep-at-most too; any node dropping a purged body keeps the rewrite (a reader's stays local, it cannot stamp); a remover uploads its removal rotation before anything else.
- **Live writes leave a label only when another entry carries them** (TLC S2, S5, S10): a body past an absolute keep-at-most, a strict subset, or one of two duplicates is deleted at a label only while a covering snapshot, a superset blob of the commit or an identical body is under it, and a right holder that may write the aspect uploads the snapshot itself when none is there (otherwise nobody was obliged to and the host kept the body for ever). Locally a node drops the body at the bound and keeps the live writes in its state (spec/crdt.md §4.6); a snapshot it writes from that state covers every body it applied. A snapshot's keep at most is the strictest of the carried live writes' own deltas', but an absolute bound only while it is ahead of the snapshot's `ts`: one inherited after T would make the snapshot must-not-hold at birth and the carrier loop would never end; a carrier written at T drops it, so the live value keeps a servable copy. Keep bounds never change what is read; only expiry kills values. The TLA+ property "a holder can always serve current state" was too strong for readers (they cannot write snapshots): what holds is that live state is never lost from a node's state or from the label.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honor a MUST drop nor judge a purge request. A few bytes per delta.
- **Reads gated by the sync key**: without it an ex-holder, or anyone who learned a label ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Tess: nothing is served under a superseded key, not even entries the holder could have fetched before. Rejected: a grace window after re-registration; "old key serves old entries" (no gating against ex-holders); serving only rotation entries to old keys (every ex-holder watches the roster size and rotation timing forever, and the flag is unverifiable). The price: a holder that missed a rotation cannot download the commit carrying its new box, hence claim keys.
- **Claim keys** (decided with Tess): a laggard and an ex-holder hold the same shared keys, so the gate needs something only the laggard has, its own private key, and the registrar is the one party that knows the roster the step is for. So the step itself is the delivery: a fresh step key and one pseudonymous Ed25519 key per reader, derived by DH, and the laggard's recovery is a pure function of its private key and the chain the host stores anyway. Nobody delivers, drains or budgets anything. Why a signature and not a hash preimage: a dishonest host cannot replay it elsewhere. Why the step key is handed out one step at a time (a stale sync key or a claim on step j yields only step j+1): an ex-holder removed at step k+1 learns that one step exists and nothing after it, no rotation count or timing, which is what a bare `stale` reply told it before; serving the current step to anyone would leak the cadence to every ex-holder forever. The reply is the signed step, verified under the previous delete key, never a bare key: a host handing out a chosen step key could otherwise recognize a claimant by the pseudonym it signs with. The claim set is defined from the epoch's read boxes, not the registrar's roster: the registrar may hold the epoch without the removal commit and would otherwise list the holder the rotation just removed, and boxes name the owner and plain-group readers the roster does not. Nested actors chain claims: node key on the account's home label, then the account's read key on each group label. The registrar derives M's key from the newest `keys.0` it holds, so M tries old keysets as it does for boxes; a device M removed can claim until a registrar that saw M's new keyset issues a step (metadata only, M's boxes are under its new key), the same staleness class as the epoch-covers rule. Steps are not deterministic (random step key and padding), so two admins stepping concurrently produce different steps and hosts that saw different ones first hold different branches for good: steps form a tree by `prev`, a host accepts only a child of its head, and the next rotation gets one child per branch (same role keys, different parent signature). `label.0` holds the set of steps, so any admin can relay a host's branch; claim keys are bound to the step key rather than a sequence number, since a branch has no number of its own. A node that cannot match a host's head walks from the newest step it shares with it. Cost: 32 B per reader per step, about 3% on top of the rotation commit's boxes, which already leak the roster bucket through padded size; hosts keep a step's set only until the rotations it leads to are compactable (`ROLE_KEEP` after it was superseded); beyond that a walk would reach nothing readable anyway. The chain itself (role keys, step key, signature) stays, as before. The gate is classical like the Ed25519 open; a quantum ex-holder could fetch hybrid-protected ciphertext. Grants still need a way in before the grantee holds any key of the target: the inbox blob, boxed to the grantee, deposited under the inbox its `keys.0` names (an ordinary label its admins administer).
- **Rotation commits are wrapped under the epoch they supersede**: a rotation hands out the new read secret, so a wrap under it would be readable by the rotator alone (deliveries used to carry it boxed per holder). Under the old wrap a laggard reads the rotations it missed in order, each under the one before. What an ex-holder gains from the blob (an honest host serves it under the old sync key until the step is registered, since the chain goes up before the step; a dishonest host or stray bundle for ever): the box map of the rotation that removed it (tids and roles at the new epoch) and the removal about itself with its frontier, which it also receives by inbox; never a secret. Under a fork the rotator picks the newest superseded epoch; a holder granted during the fork under the other branch only cannot open it and needs a re-grant (rare).
- **Re-seal** is the one recovery path for a holder that holds the right private keys but cannot reach the current epoch: its missed rotations compacted (`ROLE_KEEP` after a roster snapshot replaced them), its grant unknown to the rotator, a fork branch it never received. Nothing a co-reader serves helps by itself (the wrap of every current commit is under the epoch it lacks, and a P2P peer serves wraps, not keys), so someone must seal the current secret to it: a role commit carrying its boxes and the epochs' history boxes (without them a re-sealed holder or a grantee could decrypt the history box but not fetch it: it sits in a rotation commit wrapped under the epoch they lack, TLC R3), by anyone who may rotate (a sibling device of the same account is usually a writer, not an admin, of the group), delivered as an inbox blob. Delivery under the label itself was dropped: a holder that needs a re-seal cannot open the label (its claim was refused or the rotator never listed it), and the wrap would have to be under an epoch it holds. Its own private keys never change, so a node stranded on its account's home label is re-sealed the same way; when the inbox is the very label it cannot open (a device offline past `ROLE_KEEP`, below), a sibling device re-seals it over the pairing channel (a direct connection, same flow as pairing, same node identity), which is cheaper than a restore from the card. Nothing unattended re-seals (a PQ box per reader per step was rejected for size); the triggers are a current holder seen without a box at a current epoch and the stranded heartbeat (spec/permissions.md §3, §4), both SHOULD, and a client may also offer it by hand. The stranded heartbeat is placed as soon as the walk fails (a refused claim), not only at the head, since a holder whose next step's set was dropped never reaches the head (TLC R2); it is a deposit wrapped under the newest secret the node holds, so it needs no open. What the triggers still miss is in issues/reseal-triggers.md.
- **Entry boxes and static entries** for recovery and link keys: a key actor entering cold holds no epoch to unwrap anything with, and the account's rotations get compacted eventually, so its box in `secrets.0` is not reliably reachable. So the current step boxes the read secret to it (one hybrid box, 1.2 KB, per step of a label listing it; nothing elsewhere; entry boxes are sealed only: the symmetric form carries no epoch to check, spec/crypto.md §4), and it claims the current step directly by a static entry, a hash of its signing key and the label ID, no walk and no old step needed. The registrar cannot do DH for it without a step private key it would have to keep, and a bare signing key in the set would tell the host a public identity; the hash tells it nothing until the key claims, which is rare. The entry is stable across steps, which only says that one slot is the owner's or the link's. A key actor granted after a label's step 0 is listed by a fresh step (an admin may step without rotating). Rejected: the read secret boxed to every reader (1.2 KB per reader per step, permanent, in `label.0` and every roster snapshot; would spare laggards past compaction the re-grant); a seed-derived rendezvous label for the recovery key (a mini mailbox: unpromotable, floodable deposits); deriving the step key from the admin secret for determinism (an ex-admin plus a dishonest host could then identify late claimants from its tenure).
- Rule of thumb: per-entry rights are delete keys whose secrets are distributed client-side (role secrets) and whose public halves the header lists; label-wide rights are role keys; revocation rides on role keys. Nothing stored at the host states a reason.

## Wire choices (spec/wire.md)
- The blob prefix is a fixed byte layout so a host parses it without a CBOR decoder; the AEAD binds it as AD so a reader cannot re-prefix a ciphertext (new expiry or commitments) under a fresh blob ID.
- Padmé length recovery: a `0x80` marker then zeros inside the ciphertext (ISO 7816-4 style). One byte, no length field, and canonical because the padded length must equal `padme(len + 1)`.
- Header lists, the delete-key list and purge go by link above `CHUNK_THRESHOLD` up to `MAX_LIST_BYTES`; header-list chunks carry the level-2 commitments only (notes/crypto.md).
- Range reconciliation: Negentropy-style additive fingerprints (sum of IDs mod 2^256 plus count, hashed) so a sorted ID index answers any range incrementally; 16-way splits, lists at 32 IDs, about log16(n/32) round trips. Rejected: hash of the concatenation (not incremental); Negentropy's full encoding (bound compression and timestamps, more rules for little gain).
- Protocol: request/reply by id over length-prefixed frames; both Hellos go out at once, so negotiation costs no round trip; per-entry status so a batch partly succeeds; a Status names a stale key (9) but never carries the head.
- Opens bind the opened side's Hello challenge and static key (no replay elsewhere); stamps, deposits and deletes do not, so stamped entries and timed deletes stay relayable.

## Protocol implementation (osis-proto)
- Modules: `frame` (`FrameDecoder`, `encode_frame`), `hello` (Hello, `negotiate`, `estimate_offset`: median of per-sample offsets, Hello counts as one sample; reported after three pongs, diagnostic above 5 s), `msg` (`Message`, one variant per kind over osis-label's `Step`, `ClaimSet`, `Proof`, `DeleteItem` and the `SecretBox` entry box; `decode` enforces every cap of spec/wire.md §11.2, `Rejected::code` gives the Error code), `rbsr`, `store` (`LabelStore`, `MemoryLabelStore`), `host` (`ServingSession`), `client` (`ClientSession`), `bundle` (`BundleImport` over osis-label's reader and importer), `examples` (a fixed label and one message per kind, for tests and vectors).
- Decoder rules beyond the layouts: mode 1 lists at most 32 IDs, mode 2 lists 1024 then 32, IDs ascending and inside their range; ranges sorted, disjoint, `lower < upper`, an end bound only last; id 0 only on Error, Push and Notify (kind 24, once the old signal, is Auth now); a step at most 323 bytes (`MAX_STEP_BYTES`). Message nesting depth 6.
- RBSR: the requester sends 256 ranges per message, pipelined, each batch with a token; a reply range outside what its batch asked (or a mode 2 range not answering one of our mode 1 ranges) is dropped. Reference split: subrange i holds own IDs `i*n/16..(i+1)*n/16`, bounds the full first own ID. 10 000 IDs with 100 differences each way: 2 round trips (unit test); 10^6 IDs with 10^4 differences: 3 round trips, 5.3 MB up, 5.9 MB down (under a dense difference, most of a message's at least 16 mode 0 ranges mismatched, subranges list at most 8 IDs: `DENSE_LIST`; with 32 it was 35 MB up). A worst-case ReconcileReply (256 mode 2 ranges of 1056 IDs) is about 8.9 MB, under `MAX_MESSAGE`.
- **Reply caps** (issue sync-rounds-per-label, deleted): each Sync and Fetch reserved `MAX_MESSAGE` of `WINDOW`, so two went per round trip. Now Sync and Fetch carry `max_reply`, Path pages hold 48 steps, every small reply's allowance is `SMALL_REPLY` 16 KiB, about 1000 such requests per round trip. A first Sync asks `FIRST_REPLY` 64 KiB (plus room for its codes and wants), 256 per round trip; later pages `REPLY_BUDGET`; a page under a small cap may hold no event when the first does not fit, and only then does the client not call it stuck. A Fetch asks `FIRST_REPLY` per ID (a batch of 144 the whole budget); an empty reply is asked again under `REPLY_BUDGET`. At `SMALL_REPLY` a role commit (about 15 KiB with its boxes) was asked twice. `demotion_receipts`' budget went from 400 to 1000 rounds for the sim's lossy links, not the wire: the phone now pipelines its Fetches, a cut (2% per message) loses all in flight, and it pays again (30 seeds: rounds mean 115 max 279 on main, 178 and 472 here; 6 cuts against 24 on seed 11). A host answers neither by reading a blob that does not fit `max_reply`: with a thousand small requests per round trip that was 8 GiB read per trip for no reply bytes. Reconcile keeps `MAX_MESSAGE`: rare per label. Test: `loopback::many_labels_sync_in_few_round_trips`.
- Host engine: `handle(now, &mut dyn LabelStore, ServingInput) -> Vec<ServingOutput>`. Cross-connection work goes through the driver: `ServingOutput::Changed(label)` goes as `ServingInput::Changed` to every connection, `ServingOutput::Relay` (a relay-only entry, accepted by stamp, not stored) as `ServingInput::Relay` to every other one, which pushes it to a subscription of its label. Open and Path never read the path: the store keeps indexes per step added (`LabelStore::step_with_sync`, the newest step per sync key; `child`, genesis as the child of none; osis-host's `V`/`W` rows), so an Open is at most three lookups whatever the proof (`osis_label::evaluate_open` over a `PathIndex`) and a Path page reads only the steps it sends; a claim proof loads only its step's set (`LabelStore::claim_set`, shared `Arc`). Stamps, deposits and keyed deletes check the head's key, then the 8 newest distinct earlier keys (code 9: Upload and Delete Status carry the head, a Deposit learns neither head nor budget unless signed under the head), else 1, from `LabelStore::head_keys`, which the store keeps per head (`HeadKeys::child`; osis-host's `K` row), so these checks (which need no open) never read the path. A Reconcile reads only the live IDs inside its ranges (`live_ids_in`; sorted and disjoint, so at most the label once per message). A delete by delete key of an entry no longer held is refused (the prefix cannot be checked); a held one's prefix comes from `LabelStore::blob_prefix` (osis-host keeps it in the blob's `R` row), never the whole blob. The store applies policy: caps (the ephemeral cap included), deposit budget, rate limits on deletes (`delete`, `schedule_delete` return codes); ephemeral entries (prefix class) go to `Put::ephemeral`; an identical re-upload changes nothing and logs nothing.
- **Replace** (spec/sync.md §5, wire `entry` 4th field): one mechanism for ephemeral snapshots (the covered entries a snapshot's upload replaces, `eph_replaces`) and a purge rewrite on a full label (`replace_sends`). The host engine checks each delete proof (`delete_auth`, shared with Delete; a name not held is skipped unchecked), the store plans and applies all or nothing (`Put::replaces`, blob IDs; HostStore `plan`/`replace`: the room freed per charge kind is credited to the cap check, removals logged after the add so a holder applies the cover before the deletion, delete-rate tokens taken before the add). Replace is in Upload and Sync entries alike; at most 1024 replace items per message (same cost as a Delete). Co-reader peers (`PeerStore`): a replacement hides the entry from peers after the upload is applied.
- Sync: with a log cursor, the log after it; without one, a replay of the live entries in blob ID order paged by a replay cursor `[BLAKE3("osis v1 replay" || log_id)[..16], first 63 bits of the last ID]` (the first 8 bytes overflowed the wire's integers above 2^63 and replayed a page twice), the last page returning the log cursor taken at the start (spec/wire.md §11.2); the connection remembers the start, so a replay continues only on its connection (elsewhere: Error 10). Two IDs sharing their first 8 bytes across a page boundary would skip the second (2^-64). Add events of the requester's gained IDs and of entries in that Sync are left out. A subscription starts at the connection's last complete Sync cursor for the label (else the log head), so a client that syncs before subscribing keeps the push cursors; pushes use the last Sync's inline limit.
- Client engine: `handle(now, ClientInput) -> Vec<ClientOutput>`; commands are batched under the caps and paged replies followed (Sync `more`, Path `more`, Fetch prefixes); a page without progress (the same cursor, or 16 pages in a row without events) ends the exchange with `PeerError`; `Command::StopPath` stops following a label's Path pages (the node stops on a bad page or when nobody waits); a Want naming an ID the Sync did not list as gained is dropped; a Push while a Sync of its label runs gives no cursor (the Sync's later pages still bring older entries); a reconciliation is abandoned past `MAX_RECONCILE_MESSAGES` (4096), 2^21 differences or 2^17 queued ranges. Both sides take only a Hello-sized first frame (`MAX_HELLO_BYTES` 256). Policy stays with the node: a stale-key `Step` is reported, not walked; `Want`, `NeedReconcile { trimmed }` (Error 10 or 15, whose Sync entries are re-sent as an Upload, or over 4096 gained IDs; `trimmed` for 15) and `Reconciled { need, have }` are answered by the node with Upload, Reconcile, Fetch; after a reconciliation a cursor-less Sync at inline limit 0 gets a fresh cursor (metadata only).
- **Client port** (kinds 24-29, notes/client-port.md §2, module `api`): `ServingSession::with_port` hands Auth/Call/Sub out as `ServingOutput::Request` and answers by `ServingInput::Reply` (bounded by the request's `max_reply`); Notifies go as `ServingInput::Notify` after `WantRoom` → `Room { budget }` (the push rule, `room`); the session answers itself Call/Sub before an answered Auth (1), a reused live Sub id (2), `MAX_SUBS` (4) and every Unsub; without `with_port` (a host) the kinds get Error 11. `ClientSession` takes `Command::{Auth, Call, Sub, Unsub}` with caller tokens and reports `ClientEvent::{Reply, Notify}`; a live Sub's id is never taken by another request. Allowances: `max_reply` for Call/Sub, `SMALL_REPLY` for Auth/Unsub (`client::allowance`). Tests: tests/it/port.rs.
- Co-reader peers use one engine per direction, not both on one stream: the dialer runs `ClientSession`, the acceptor `ServingSession`; co-readers each dial the other (notes/networking.md, Implementation (node peers)).

## Why no recycle bin
A bin at the host (writers retire entries with a soft key, restore within a grace period) is not a permission boundary: a writer can already destroy irrecoverably everywhere by compacting with an empty snapshot, while holders keep no bin; nothing ever lists the bin or restores from it, so it is a delayed delete; a retire carries no reason, so the client rule "re-upload what still changes state" undoes moderation retires. Retention per delta gives the three roles their deletion powers directly, "covered means redundant" gives the recovery a bin was for, and compaction needs no delay. Moderation is not deletion: a chat admin removes the participant, or the app hides the message with a chat-written marker (notes/chat.md).

## Limits (accepted)
- A removed writer keeps its delete keys, but they alone delete nothing; its power ends when the sync key is re-registered, which every removal does. Until an admin steps, writers stamp and open with the keys of the epoch the host's head registers (they hold it: history boxes), and wrap under the newest they hold; a writer's rotation changes no delete key, so a label whose admins are all offline keeps its old step while content under it is already unreadable to the removed holder.
- A removed admin holds the current delete key until re-registration and can win the race at a host by re-registering keys only it knows. Remedy: a replacement label (next index, keys from the rotated admin secret the removed admin lacks), O(entries). The index keeps a replacement's keys and ID apart from the old label's, and two admins replacing concurrently derive the same ID. Hostile admins are out of scope.
- An ex-writer or ex-admin keeps old-epoch delete keys and, as a reader, the sync key, so it can delete its own old `author` bodies or old `admin` bodies at hosts; healed by any holder's next sync. Level-3 deletes need the write key, so `writer` bodies are safe.
- A malicious current writer can wipe `writer`-purgeable bodies at a host; write access already lets it reset them everywhere.
- Host storage under `author` and `author_or_admin` retention grows with superseded bodies until a snapshot with the right over them is written and their right holders sync: an admin's or their author's under `author_or_admin`, their author's only under `author`, so departed authors' `author` bodies stay for good and their `author_or_admin` ones until an admin compacts (a removal is the natural moment). notes/growth.md.
- Other bounds read on a node's own clock still straddle: two nodes either side of a keep-at-most bound or a grant's `until` (`stale_card`) may delete and re-place one body for as long as their corrected clocks differ (seconds; keep-at-most cannot wait, it is a MUST).
- Relative keep bounds measure from the killing commit's `ts`, so a backdated kill shortens "at least D" by up to the drift cap.
- A holder listed in no step since its last sync (a grant a rotation raced) is locked out of the label until a later step lists it or a holder re-seals it (spec/requirements.md, Permissions); the rotation would have left it without boxes anyway, and the SHOULD re-seal rule (a holder without a box at a current epoch) repairs it at the next write. A holder whose missed rotations were compacted (`ROLE_KEEP` after they were superseded) is refused at the step whose set the host dropped and can be reached only through its inbox; its stranded heartbeat (spec/permissions.md §4) tells co-readers. **Accepted limit (Tess):** when that heartbeat's deposit is refused (the admins refreshed the deposit seed, or the label's budget is full) nobody learns the holder is stuck and it waits for a manual re-share (`Engine::reshare`, offered by clients); rare (a dropped step and a refused deposit at once), within "re-sealing is triggered, never guaranteed", and the alternative (a host claim log mapping reader slots to holders, one new log event kind) adds a third mechanism to cover the overlap of two. TLC `rotation/MC_drop_refresh` is the expected failure for it. The deposit seed is refreshed only explicitly (`Engine::refresh_deposit_seed`). A walk costs one round trip per missed step. A device offline longer than `ROLE_KEEP` on its account's home label is refused at the first dropped set and has no inbox of its own: it is re-sealed over a direct connection to a sibling device (pairing channel) or restored from the card; the official host may keep home-label sets longer by policy. A stranded holder's heartbeat is a deposit under the head's deposit key, sent only when the holder's deposit seed derives it; if an admin refreshed the deposit seed since the holder last read `keys.0`, no heartbeat goes and only a human-triggered re-seal reaches it, which is why the refresh is a MAY against observed abuse, not a routine SHOULD (issues/reseal-triggers.md). Re-seal soundness rests on established epochs (notes/permissions.md): within `ROLE_KEEP` the departures travel in the epoch chain a re-sealer must hold; after compaction they travel in the roster snapshot and the removal commit separately from the `secrets.0` snapshot, so a node whose view is incomplete (a host that never received the removal, an interrupted first sync) can box a removed holder at a snapshot-established epoch by an eager rotation or a grant (re-seals wait for a complete pass and chain-established epochs). Healed by the next rotation of a node that knows the departure; accepted. Recovery and link keys claim the current step, so compaction and set retention never strand them; a replaced label keeps its role commits and the replacement `label.0` commit at honest hosts, so only a key actor that knows no honest host is stranded (a removed admin squatting every host a card names). **Accepted limit (Tess):** a hinted-label walk (a link joiner or recovery device reaching a label it knows only by ID) claims on the host's step before it can verify it, with the keys of the hint's actor only, so a dishonest host handing out its own step can recognise that one pseudonym at join time; closing it needs `Path` to answer a claim-key holder (a wire change), declined. The pending part of the actor set comes only from the commits of inbox blobs naming the thing, decoded unverified (a sender knowing another held actor's tid can widen it; accepted). **Accepted limit (Tess):** consumed inbox blobs are not deleted early (spec/sync.md §3, a MAY): they stay until `INBOX_LIFETIME`, since later holders open a thing's label by the blob's hints until the granter's chain arrives (deleting them broke every link_redeem seed); the cost is sealed storage at the host for 90 days per grant.
- **One level up** (issues/keyset-name-later-admin-path.md, accepted residual): a grant of N on A carries its names for N under A's secrets, so a boxer of A on U that reads nothing of A never sees them. If D left N and then forges A's keyset (valid where D's removal is not held, D's path to A in the boxer's certificates), the boxer seals U's epoch to D's keyset. U-writers that know the departure find U's epoch unnamed for it and rotate first; exposed is content by U-writers that do not know it, written after it (the lost-device window). An honest admin of A produces no D-reachable keyset of A (it boxes N only holding the grant's names), so this needs a forgery, unlike the compaction residue above. Healed by the next knowing rotation of U; permissions §4's exception places the revoke under U's label so U's rotators learn it.
- A deposit-only re-registration (the head's deposit key is not the one this admin's seed derives, no newer epoch) waits until nothing under the label it can open, at a connected host that has not said it lacks it, is unopened and no `keys.0` write of the actor signed by a current admin is pending (`pass/` `keys_caught_up`, `Engine::keys_write_pending`; unsigned or unreachable ones never count: anyone can send a pending commit, and an entry only a gone host lists never opens, either would hold the step back for good; an admin-signed write that never applies holds it back while it is held): a co-admin's refresh step arrives before its `keys.0` write when blobs are not inline (or come from another host), and the laggard stepped back to the old key, re-admitting a departed party's deposits until it applied the write (`lagging_admin_keeps_refreshed_deposit_key_spec_sync_5`). Left: a head registered while its `keys.0` upload was refused (rate limit, cap: `reregister` sends Upload then Register without waiting) still gets one step back, until the refresher's next pass uploads the write and steps again.
- **Invite requests** (spec/sync.md §3; Tess, round 13: leaking an IP takes a user click). `open_one` admits an inbox blob (`admits`) when its commit is held or its author is connected, else records `Kind::Request(c)` and ingests nothing (`note_delete_hints` waits too: a stranger could evict real candidates). Connected: walk up from the author over `Held::named_on` (edge writes, rosters, ledgers held, past and invalid ones too: a cheap candidate filter, bounded by what the author is named on) to the roots (synced groups' owner chains and `contacts`), then the author's current role (`Core::role_now`) on a root met decides (an ex-holder, a removed stolen device, is a stranger again: `removed_holder_invite_is_request_spec_sync_3`); then verify the commit's signature under the author's held record (a stranger can name any author tid). `vet_inbox_hints` first re-judges requests (`release_requests`: the sender became connected, or a sibling device accepted and its grant copy under the home label made the commit held) and ingests the admitted. `accept_invite` releases by commit, `decline_invite` turns the entries into `Kind::Inbox(Some(c))` (never ingested) and records `c` in `declined` (`y/m`, one 32-byte record per click) so re-sends of the commit are held back too. A decline binds inbox blobs only (spec/sync.md §3): the commit arriving under a synced label (a sibling's acceptance copied under home) applies, so the sibling's acceptance wins (`sibling_acceptance_wins_over_decline_*`); refusing it there would leave this device holding, under its home label, a valid grant it never applies, while its siblings join. Judged per device: contacts are per node, and an accept on one device reaches the others only through the grant's copy (which waits for the joined label to apply). What an attacker can still do:
  - Fill: requests are inbox entries, so they are bounded by `INBOX_WAITING` per host (`clear_inbox`, limits below) and go with their blobs. A declined blob is stamped out of the budget (`stamp_inbox`); an unanswered one holds a slot until it expires or is cleared.
  - Spoof: a request never comes from a node known as connected (no forged signature passes); the API shows nothing about its sender or thing (the header and payload are the sender's word, a known name there would be a spoof or a device not seen yet: Attribution, notes/api.md). An app can show only "someone invites you" (left: a payload field pointing at the sender's card, verified once fetched).
  - Vouching: any holder of a role on a group this node syncs who may grant there can make any node connected by a valid grant. Accepted: they share a group already.
  - Hint hosts are unsigned: whoever holds a connected sender's genuine grant to the actor (a reader of the target's label) can re-deposit it naming its own hosts, and the device dials them. Accepted: that reader holds a role on the target.
- **Inbox clearing** (`pass/` `clear_inbox`; spec/sync.md §5): one rule for all a stranger can put in the budget (junk that opens to nothing, requests, re-seals, invalid or off-topic commits, far or no expiry): an admin device leaves at most `INBOX_WAITING` (32) and 1 MiB of them per host, deleting the rest at each pass. No "this is junk" verdict: a blob sealed to a key this device lacks yet looks like junk and stays while under the cap, and what stays under it blocks nothing, half the budget being free. Sort: requests with an honest expiry last, earliest to expire first (junk that opens to nothing never displaces one, so requests are lost only past 32 of them); before them everything else, far or no expiry first, then earliest. Requests displaced only by junk would not do: anyone with `keys.0` can seal requests that open, and 72 of them would hold the budget for `INBOX_LIFETIME` again. Keeping the oldest instead would let one fill refuse every later invite. A host rule on deposit expiry was rejected: certificate copies and other non-inbox deposits carry no expiry, and hosts cannot tell them apart. What a stranger can still do with `keys.0`:
  - Fill the budget while no admin device of the actor is online: grants wait at their senders (retried at the capped back-off) until one comes back, one pass later. An ownerless group's inbox waits for its admins alike.
  - Flood without pause: up to the host's deposit rate (default 600 a minute; deletes 20 000) slots go as they free, so an honest deposit races him, and each junk blob costs the device its bytes (up to about 320 KiB/s at the default rate with 32 KiB blobs) until he stops. Tombstones: at that rate about 26 million in `TOMBSTONE_LIFETIME`, about 2.6 GB of the label's 16 GiB; the log trims (2^20 records, about 15 hours), so offline devices reconcile.
  - Push out unanswered requests with requests of his own (they open): more than 32 displace the earliest. No flood needed: 40 real invites from unconnected people while the user is away lose the first 8 at her next sync, before she sees them, and their senders are not told; each re-sends after `INBOX_LIFETIME`. Any constant has this shape (the budget itself holds 68-72); a larger one is the owner's call. A device that does not know a connected sender yet (fresh, or behind) sees its grant as a request too, so past 32 it can cost that blob at this host, though a sibling that opened it holds the commit.
  - Past the cap, flood or not: what this device cannot open goes first and may be real: a reader's deposited linked blob (filler wrap, no expiry, spec/sync.md §3; past 32 entries or 1 MiB of them under an ownerless group's label, so only a very large chain), or a blob sealed to a key it holds only later (a team's, whose secrets come from another label). A device holding the head's read epoch holds its history, so readers' certificates, cards and heartbeats open and never count. Pending commits are exempt, so one who holds a commit pending at the actor, or a connected sender with commits that stay pending, can hold slots until they expire (at most `INBOX_LIFETIME` plus drift).
- A decline frees a slot, and a new deposit seed needs a new `keys.0` and chain step. A stamp goes only on the first blob of a commit under the label, of a valid commit about the actor with parts a copy would take or one declined, expiring within `INBOX_LIFETIME + 2 × MAX_DRIFT` (`stamp_inbox`): a stranger can seal any commit he holds in any number of blobs, so without both his re-seals of a held or once-declined commit, or of the actor's own card, would be stamped past the budget (`reseals_stay_in_the_budget_spec_sync_3`). Stated limit (spec/requirements.md, Data a node cannot read): any sender holding a role on a group the actor syncs is connected, and its fresh grants of its own things to the actor are valid, so they pass the budget, bounded only by the host's deposit rate, label caps (defaults: 600 a minute, 2^20 entries, 16 GiB) and expiry: about 14 hours to fill the home label at a host, after which that label takes no uploads there (code 12) for up to 90 days, with no node path to delete, its blobs on each device too and each grant's copy under home for good. Before the stamp: the budget, 72 entries, about 2.3 MiB. Removing the sender stops new ones only. A read-only node's heartbeats are deposits too, bounded per reader by expiry (notes/ephemeral.md).
- A reader's invite grant, self-removal or node card sits deposited until a writer promotes it; co-readers read it meanwhile. **Budget is host policy**, not a format constant: clients never compute it, they see refusals and the remaining budget in the reply. The recommended minimum (64 + 4 per padded claim slot) is sized per reader *actor*, while deposits come per *device*: a plain group owned by a team has a claim set of one, and thirty reader devices exceed the minimum on heartbeats alone. Hence the client priority (certificates, edge writes and revokes first, heartbeats skipped when tight) and the heartbeat policy below; hosts that host big read-only audiences raise the budget. Deposits are unlinkable by design, so per-reader limits are impossible. After a write-key rotation readers cannot relay old entries to a new host until a writer re-stamps them.

## What a node learns about data it cannot read
One label per synced group, overlaps between labels (shared content blobs; certificate and inbox blobs share nothing), blob counts, padded sizes, which entries are chunk blobs, the number of delete-key commitments (zero to three, which reveals the purgeable-by class), expiry times, arrival times, deletions and pending deletion times, which labels one connection opens (so: holds the current key of), the roster bucket of each step's claim set, which claim slots were used, when, and how many steps behind the claimant was (two late devices of one account use one slot), which entries were deposited and when (a grant or a reader-originated write), client addresses. Nesting only as far as overlap shows it. Not: AKs, tids, thing or aspect counts, authors, role grants, which entries are projections or rewrites of one commit, retention bounds. What it deleted (a delete, an expiry, a timed delete, a replaced entry) it forgets: the host store shreds every removal, so a later compromise of the host's device, even one that also holds the label's read secret, recovers no deleted wrap (notes/local-store.md).
- Padding with Padmé costs at most about 12% under 256 B, 6% up to 64 KB, 3% above, 1–4% on average.
- Wrap overhead: about 25% on a minimal commit, under 5% on typical edits, none on chunks.

## Policy defaults (non-normative, tune freely)
- Compaction: a right holder compacts an aspect when superseded/live bodies pass a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot. A schema that wants no automatic compaction says keep at least forever.
- Heartbeats: under the home label and under labels with more than one reader actor; not under a thousand single-note labels. `reach.0` excluded by default from labels shared with non-contacts (`publishes_reach`, notes/networking.md).
- Deposit budget: 64 + 4 per claim slot entries, 32 KiB each, as the floor; more for labels whose steps show many claim slots.
- `INBOX_LIFETIME`: 90 days (format constant), matching `ROLE_KEEP`.
- `TOMBSTONE_LIFETIME` 30 days.
- Fetching from a node that cannot read them, a client cannot prioritize permission commits before decrypting, so it downloads everything and applies role commits first.
- Clients may batch uploads to blur timing.
- Client ordering and diagnostics (moved from spec/sync.md, where they were policy): deposits go certificates, edge writes and revokes first, heartbeats last, and heartbeats are skipped when the budget is tight; a clock offset of more than a few seconds against peers is reported as a diagnostic; so is an ephemeral commit not applied for the node's cap (§9) and an ephemeral upload a host refused for its cap. Repair of a deleted chunk (§1) runs at most once per aspect per back-off interval, doubling. Handshakes: the transport handshake has no deadline beyond the idle timeout and a listener bounds the handshakes in progress (oldest dropped past the bound, notes/networking.md); a host closes a connection with no Hello after `hello_ms` (below). LAN: an announced address is a candidate route until a connection through it is up, never replacing a working route before that; a candidate whose dial fails is not dialed again for a while; a node connected off the LAN (relay) that hears the peer on the LAN dials the candidate beside that connection and closes the other once it is up (a proven LAN route is preferred).

## Rejected
- Owner actor as sync unit (above).
- State Merkle trees over aspects or the group hierarchy: expose shape and must follow a cyclic hierarchy.
- Home closure = everything the actor owns (complete backup by default): every thing would sit under its owner's home label beside any shared label. Tess chose explicit placement (spec/requirements.md, Offline and network).
- Unverifiable per-entry expiry and commitment metadata (first or latest upload wins).
- Soft retire, recycle bin, restore and a generation counter forcing concurrent uploaders to re-tag (above).
- Host-enforced keep-at-most (absolute bound in the clear prefix): the live remainder of a body may have no snapshot yet, so nodes that fetched before and after the bound would diverge for good; expiry has no such problem because the values die too.
- Compaction across clock skew: only the placer deletes its own entries on time grounds (entries of a lost or removed placer then stay for good, and keep-at-most needs others to delete); judging others' entries on the overlap of what both nodes drop (the only overlap a node can compute is "past by the largest skew", i.e. the `MAX_DRIFT` wait chosen, spec/sync.md §7).
- Leases (entries lapse unless refreshed): conflicts with immutable expiry and with a host being the only backup.
- Plain (unboxed) grants under a shared label: contradicts entitlement, since every reader of that label would read them.
- **Mailboxes** for rotation delivery (the design before claim keys): every actor named a mailbox label in `keys.0`, key actors derived theirs from the seed, and every rotation deposited one boxed-twice projection per holder (about 2.5 KB per holder per rotated actor). Dropped because the laggard's recovery became a stored, budgeted side channel someone else had to feed: a key actor's mailbox had no writer to promote deposits, so an owner offline through enough rotations found the newest deliveries refused; clients needed a mailbox-first bootstrap across nesting levels; a device's mailbox was a stable per-device label at a host, so the host counted an account's devices for life; deposits made over one connection linked the recipients' mailboxes. Variants of claim keys also rejected: the registrar's own read key as the DH key with the holder guessing among admins it knows (fails when the registrar's keyset changed since the holder last synced); an ephemeral key served to anyone or in a public chain (every ex-holder watches rotation cadence and roster bucket forever).
- A shared bootstrap label derived from the recovery seed: a stolen device could watch it forever for the account's device count and rotation timing; as a rendezvous for `label.0` only, a mini mailbox (above).
- No gating against ex-holders (reads under any sync key of the chain, writes under the current one): simplest, and download-before-upload closes most of the laggard-wrap content leak at hosts, but not via relays or bundles, and ex-holders watch label activity and harvest new ciphertext forever. Tess rejected.

## Hosting (Tess, round 13)
- One kind of node: same binary, run the same way, on a laptop or a rented machine, with any mix of data it reads and data it cannot. A node hosts a label by storing it and serving it to its role key holders. Reading is per label (it holds a read secret or not), so one node may read some groups and host others it cannot read. A machine that reads its own configuration group and hosts everything else unread is one osis instance.
- No separate program: hosting is part of the node, started by the one long-running command (`osis serve`), configured by `host.0^` on the node's own thing. Config as osis data lets any admin of the node (the account's devices) configure a node remotely; it is never in the node card; absent means not hosting.
- osis-host is its own crate below osis-node, so the compiler keeps hosting away from the engine, keys and sync state; the node hands it public data only (`HostConfig`), and policy.py's allowlist fails closed on any new decrypting call.
- Its own `Store`, not raw `Backend` rows: a node hosting a label it also reads holds the read secrets on the same device, so wraps and blobs surviving a delete in freed pages would break spec/requirements.md Deletion; Store deletes shred. Not the node's store: that would hand the host the store holding actor secrets, and engine and hosting would contend on one lock. Accepted cost: a label both read and hosted is stored twice.
- Host and co-reader serving share osis-proto's serving engine but not a store, chosen by listener: serving entries the node can read and entries it cannot from one store would make hosting depend on key state, or make co-reader serving durable and authoritative.

## Implementation (osis-host)
- `HostStore` implements osis-proto's `LabelStore` on its own osis-store `Store` (one table, blobs in the store's blob area; never the node's store, which holds actor secrets; notes/architecture.md §2). Every removal is `Shred::Yes`, overwrites `Shred::No` (a promotion wraps the same blob key, and the entry's removal later shreds every earlier version on its path), so deleted wraps are unrecoverable once committed (forensic test `hygiene::deleted_wraps_unrecoverable`). Rows: label meta (log ID, head, counters), host totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts (bytes once per host in the blob area), sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions. A mutation's writes apply together to the open store transaction (`Suspended` between calls, `Store::resume`); it commits per mutation, or once per hub batch (`defer_durability`/`durable`); a failed write aborts the open transaction and fails the batch's `durable`; a failed commit recovers the store in place (`Store::reopen`). Reads take `&self` (`LabelStore`), so the store sits in a `RefCell`. Log ID = BLAKE3(instance seed || label)[..16], seed random per storage instance, so a wiped host invalidates old cursors.
- `sweep(now, budget)`: at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record), due timed deletes in time order (tombstone, Deleted record), tombstones after `TOMBSTONE_LIFETIME`, and with them the log up to the position the entry went at (every durable removal, expiry included, puts a `Y` row holding that position: the Deleted record's, or the head's at an expiry, and whether it was a deletion (only a deletion's `Y` row drops the tombstone: an expired blob may be added and deleted again); the `Y` and `G` rows dropped count against the budget, a label's highest due `Y` row only once its trim is done, so a budget the due `Y` rows fill still progresses; a trim cut short keeps that row and raises the horizon to the last row dropped), claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`). An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s. The log is also trimmed to `log_keep` records in steps of 1/8; older cursors get Error 15 and reconcile (serving: a cursor of the label's `log_id` that `log_after` no longer reaches and not past the head is trimmed, 15; another `log_id`, past the head or a lost replay, 10).
- **Host policy** (`HostPolicy`, every knob settable by name in `host.0^`, `HostPolicy::set`): per label `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12 for new entries only); host-wide `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register Error 12 via `LabelStore::admit_label`, which answers 14 for a label outside the admission, spec/wire.md §11.2); a registered step and its claim set count toward `cap_bytes` and `max_bytes` (the set until the sweep drops it); past them `push_step` refuses a genesis step 12 but takes a child step without its set (a refused rotation would leave a removed holder's open and write keys valid at that host, and anyone may fill a host to `max_bytes`); a child step past them even without its set is taken once per `over_cap_step_ms` (1 h) per label, else Error 12 (`Meta::over_cap_until`, durable): only a label's own admin spends that room, so outsiders cannot starve an honest label's rotation, and growth past the caps is at most `max_labels` bare steps (about 300 B) per hour; the node keeps its open on a Register refused 4, 12 or 14 and registers again at a later pass (each resync), so the label stays synced (not stranded) while it waits; the rest of that pass waits with it (nothing goes under the old keys). Steps queued behind a refused one each wait an interval: `reregister` registers the recorded child of the host's head (the older rotation) before issuing one at the newest epochs, so k rotations at a full host take k intervals. A wait past one interval (clock set back) counts as over. Forgetting old steps instead was rejected: a path walk from genesis is how a node verifies a head it has not recorded; deposit budget `deposit_factor` (1) × the spec minimum; `claim_keep_ms` `ROLE_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither less); `log_keep` 2^20; fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `deposits` 600, `registers` 600 (steps pushed; a repeat of the head is free; a recorded path registered at a new host goes at that pace); connections: `max_connections` 10 000 (when full, shared by source: `Hub::accept_from` closes the newest connection of the source holding the most if it holds two more than the newcomer's, else the newcomer; `osis_transport::evict_for`, sources from `Connection::source`: IP, IPv6 /64, unknown = one source), `hello_ms` 10 s (no Hello: closed), `max_queued_bytes` 48 MiB unread per connection (then dropped), `max_buffered_bytes` 512 MiB of partial frames over all connections (the connection holding the largest is closed); the listener takes at most `max_connections` transport connections (`link::serve`, shared by source the same way). Rate limits answer code 4. Ephemeral entries: `ephemeral_bytes` 16 MiB per label and `ephemeral_total` 1 GiB in memory (code 12; notes/ephemeral.md Step 3 as built). Counters are in memory (a restart resets them). Host byte totals count an entry's bytes once per label holding it.
- `Hub` (sans-I/O, tokio-free with `--no-default-features`): one `ServingSession` per accepted connection, `Changed` to every connection and replicator, `Relay` to the label's subscribers on other connections (bytes shared, `Relayed::blob` an `Arc`); every public call is one store transaction (`HostStore::defer_durability`/`durable`: one commit per input, so at most one shredding root write; on a failed commit nothing it would send goes and those connections close); `tick` commits its sweep on its own, so a failing sweep backs off; `tick(now)` runs the bounded sweep, Hello deadlines, replication work and timers; `next_due(now)`. The simulator can drive it directly.
- Replication (`Replicator`, push only): per dialed peer, a `ClientSession` walking each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record; deposits, deletions and pending times are not relayable (signatures not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with backoff 1-60 s. A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks: a new peer, or one a removal's lifetime behind, of any label with a removal older than `TOMBSTONE_LIFETIME`). Entries stamped under keys older than the peer's head get code 9 there (diagnostic only): writers re-stamp.
- Echo suppression: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry; a replicator does not send an entry to the peer key it came from, saving the wasted upload of what the peer just sent (a held stamped entry changes nothing, so replication settles either way). It needs the dialing host to authenticate with its static key: the driver dials peers with `dial_as` and its listen secret (an ephemeral dial key would defeat it, and then every entry goes back once).
- Driver (`driver::run(hub, Endpoint { transport, listeners, secret }, peers, clock, control, log)`, tokio, feature `driver`, default; generic over `T: Transport`): sessions are osis-transport `link` sessions (notes/networking.md): `link::serve` turns every stream a dialer opens into a `Link` (peer key = the transport's), each a hub connection; hub task owns hub and store, its calls in `block_in_place` on a multi-thread runtime; reader task per link, handing over one read at a time (Hub stall bounds: turns by source); writes into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); dial task per peer (`link::dial` with `dial_as`, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`); a connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s for the finish; ticks when due or every 60 s; `Control::{Tick, Admit, Accept, Shutdown}`. Tier-1 tests run it on `InProcess` under tokio (perfect network; not `Sched`: the driver spawns tokio tasks, and the sim drives sans-I/O engines, not drivers); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). Tier 2 (tests/it/quic.rs, ignored): two drivers on QUIC replicating.
- **Hosting in the node** (osis-node `sync/host.rs`, `sync/driver.rs`): the only way a host runs. The node reads its own `host.0^` (spec/data-model.md §9; any admin of the node thing may write it) once per engine change and hands its driver `Action::Host(HostConfig)` (none: stop) when it changed: the host key, listen URLs, the admission (`open`: any label; `own`: the label IDs of groups its account owns whose hosts name the host key, plus `labels`; `SyncEngine::owns`: the owner chain reaches the node or its account (`set_person`, osis sets `me` at start; kept by `host_restart` when the driver starts: wiping it made a node that only hosts admit nothing on a real runtime, the Manual one never restarts), no role grant counting, so a stranger's grant, read or admin, to the account or the node, on the group or an actor above it, never admits a group (round 13 decision, as the inbox accept step: spending this node's storage on someone else's data takes `open` or an explicit label); ## Implementation (node sync: osis-engine `labeling/`, osis-node `sync/`)
- `labeling/`: `actors` (reader actor = the nearest thing up the owner chain with secrets of its own; `secret_actor` up the owner chain; `may_read(x, t)`: `t`'s secrets derive from `x`'s, or `x` reads that actor on the timeline; `closure(g)` from node-core's `groups.0` index; `group_labels` from `label.0`), `blobs` (`Body` = one held commit, `parts` those the label's actor may read (`readable_parts`), the blob carrying every held part; `label_bodies(g)`: commits touching the closure with a readable part, plus, on a home label, the `label.0` and `created.0` writes of labeled groups whose nearest labeled owner-chain actor it is (`to_label`: sealed per label under the label's secret); `seal` (one section per thing, `extra` sealed sections copied verbatim), `seal_to` (one section under a given secret: copies, heartbeats), `open_commit` (sections under the thing's, the label group's derived and own secrets; prefix vs header, spec/commits.md §4; `OpenedBlob::unknown` for the sealed-section retry in node-sync's `redeliver`); `wrap_secret` with the rotation exception (the commit's `keys.0` delta writes a read keyset of the label's secret actor: newest held epoch it supersedes); `head_keys` (sync key from any held secret, write/delete only established, deposit key from the actor's seed); `delete_secrets_of` (per commitment group of the blob's listed aspects)/`chunk_delete_secrets`: the header's delete keys matched over every held epoch along the owner chains (`Core::delete_chain`, `delete_secret`); an entry's `Kind::Commit` keeps its blob's prefix salt and the aspects its sections list for the signatures), `certs` (`certificates(g)`: node card commits and perm's chain certificates as (commit, aspect indexes); `partial_body`/`part_body`; labels and steps are flows' `create_label`/`issue_step`), `converge` (the pure rule: `classify(Facts) -> Hold`, `may_delete(why, live, carried)`).
- `sync/`: `SyncEngine::handle(Event) -> Vec<Action>`; `Event::{Tick, Local, Up, Bytes, Down}`, `Action::{Dial, Send, Close, Wake}`. - Open (`sync/open.rs`): tries in order the known head's sync key, the recorded steps deepest first by sync key, then by claim key (the node's own X25519 and the read-role KEM X25519 of every held read epoch of the actors it holds; filtered by a recorded claim set), then held key actors by static entry, only those the group's `roles.0` lists (a hinted label: the key actor the hint follows for, `Hint::via`, kept when a later inbox hint names the label, and those the thing's held `roles.0` lists), since the signing key in a static proof names the key to the host and links labels. A host's path is verified page by page (a bad page fails the label at once). Pushes for labels not started on the connection are dropped. `Step` replies are verified under the step tried and recorded in `label.0` by admins; a head not in `label.0` is checked against the host's path. A hinted label's walk (no recorded step to verify a `Step` reply under, `LConn.walk`) claims only with the keys of the actors the hint is for (`Engine::hint_actors`: the thing's applied holders and the holders its applied `secrets.0` boxes, plus those the pending commits of the inbox blobs naming the thing grant or box, that this node is or holds; the boxes cover reading through an actor a rotation boxed with no grant held, `hinted_walk_claims_for_boxed_actor_spec_sync_5`), not every held actor's: a host handing out a step of its choosing would otherwise recognise the claimant by every pseudonym it signs with (hostile_host `hinted_walk_claims_only_for_its_actors_spec_sync_5`). Chosen over letting `Path` answer a claim-key holder (a wire change); the hint's own grantee's pseudonym is still offered. Code 13 registers the recorded path (deepest branch). Re-registration registers a recorded child of the host's head before issuing anything (`recorded_child`), `issue_step` reuses a recorded child of the head at the current registration epochs, and a node issues a new step only once another node's rotation of the actor (a remote role commit writing its `secrets.0`, `rotation_at`) is `SETTLE_MS` old (`step_settled`; the author registers first; counting every edge write, an admin's `label.0` record of the previous step held each next rotation's step back, so two quick rotations shared one step: `stranded_reseal` failed on every seed): otherwise each admin and each connection added a sibling step per rotation (`one_step_per_rotation_without_host_spec_sync_5`). No key left after a claim: stranded heartbeat.
- Pass (`sync/pass/`; deletions in `pass/delete.rs`), after the log was read to its end (`Synced`) and on every later change: head keys recomputed; no read epoch of the head held: stranded heartbeat (only when the held deposit seed derives the head's deposit key: a sharer's other device opening a link's fresh K label before K's own `keys.0` reached the host sees K as deriving from the account and sent one signed with the account's seed, code 1), nothing else; an admin with a newer established epoch uploads the secret actor's role commits the host lacks under the head's keys and registers a child (the rest after `Registered`); then must-hold bodies (before keep-at-least, or not covered by a snapshot entry of the label), role commits first, uploaded stamped, relayed with their stamp by readers, deposited when a non-writer's own edge write; chunk/page/list blobs of uploaded commits and the held blobs their deltas link though not listed (reused chunks, a snapshot's values) with filler wraps; this node's certificates and node card per label (fresh encryption), only the deltas no genuine entry of the same commit present at every host holds (any node's copy or closure blob), never closure deltas, another node's demotion or `keys.0` only `SETTLE_MS` after receipt, a heartbeat per `HEARTBEAT_MIN_INTERVAL`; writers promote deposited entries (never `seen.0`); deletions of must-not-hold entries present there (the label delete key, else a delete-key signature with an established label key), carriers first (a later snapshot entry of the aspect at that host; else `snapshot_first` when the node may write); expired entries are forgotten, never deleted.
- Replaced labels (spec/sync.md §2): flows' `Engine::replace_label` rotates the admin secret first when the newest admin epoch is one a step of the old label registers (whoever took it may hold it; a plain group gets secrets of its own), then writes the new label and marks the old one replaced in one commit. Holders stop syncing a label once they read it is replaced; an admin keeps it (`labels`) until done: its passes there hold role-class bodies only (`bodies_under`), so content entries judge must-not-hold (outside) and go once settled, the replacement's `label.0` commit goes up, certificates (chain certificates, cards, heartbeats) stay to verify them; no certificates or heartbeats are placed there anew. A replaced label is never stepped again (`reregister` skips it), but at a host that lost it the admin registers its recorded path again (`register_path` on code 13) so the replacement's `label.0` commit is found there (spec/sync.md §2). A settled pass with nothing left to upload and no content entry present marks the label done at that host (`retire_at`, in memory; deletions there mark the label dirty for that pass); a host where no key opens it (`Phase::Failed`) counts as done; done at every host, or `ROLE_KEEP` after this admin first saw it replaced (a host never reached), it is retired for good (`y/q`: empty value retired, a time first seen). Unopened entries there that only content commits list (chunks, tree nodes, pages: `replaced_leftovers`) are deleted by delete key too, and the label is not done at a host while one is present; their deletion never queues a chunk repair (`relink_pending` skips replaced labels: the replacement holds the content).
- **An inbox chain only for a thing without a label** (`send_inbox`): a labeled thing's label carries it. Sending it always once left writers' content pending `MissingChain` in sims (`snapshot_rights`, `purge_tombstones`, `ephemeral`, `coverer_revoked`), a grantee acting under the label before its admin re-registered it. The repro has passed since at their pinned seeds, cause unpinned: re-sweep those if the chain ever goes always.
- **Inbox life** (spec/sync.md §3): an opened inbox entry records its commit (`Kind::Inbox(Some(c))`). A home-label pass walks the unexpired blobs not known copied (`InboxCopied`), a full pass all of them. Release, a full pass's `certificates`: 80/640 blobs 0.6/8.7 ms (7-13 us a blob, flat in things held since `Memo::roles_now`; was 1.2/57), about 100 us a blob more the first time after a role write dropped `holders_named` (issues/inbox-full-walk-scale.md). Once that commit applied and is valid, a device with admin on the actor (its readers would flood an ownerless group's label) places a certificate copy with the author's chain (`chain_under`: without any `keys.0` but the author's own, its card: a verifier needs creation records and edge writes only (`apply::examine`, `validity`); a keyset is often a removal's fresh deposit seed, an admin that had the commit from the inbox may not hold it, and it moves at every rotation on the way: `tied::group_admin_copies_removal_without_new_keys`, `tied::grant_lost_and_regained_with_the_admin_away`, `tied::a_copy_survives_its_granter_rotating`, oracle `tied::grant_and_removal_orders_large`), as part of `certificates`, only when the inbox is the actor's home label (spec/sync.md §3: another group's label would show its readers the actor's grants, labels and box keys), of the carried parts of a role commit on the things where it writes a grant of the actor or an actor it owns or boxes one (`Engine::holders_named`; a rotation's `keys.0` there goes along; anything else a stranger with the deposit seed sends is applied but never stamped), or of a thing's first `label.0` write (`Engine::create_label` delivers it to every actor on the roster, so a holder granted before the thing had a label finds its route; its parts on the named things the actor or an actor it owns holds a grant on, by the roster as applied here) plus the newest valid `created.0` and every valid `label.0` commit of those things that the payload names, no `label.0` of a thing the actor reads no more (a later `label.0` is a delta on the record an earlier one set, so the newest alone left the group's readers no label: `tied::grant_to_group_of_a_thing_rotated_before`; the payload's list is the sender's word), and nothing from a blob expiring less than `INBOX_COPY_MIN_LEFT` (`INBOX_LIFETIME` / 2) from now (a short sender expiry freed the deposit budget for the next copy at once) (`pass/` `inbox_certificates`; not when entries there already hold the commit's parts, counted as for chain certificates (`held_parts`), and the commit then counts as done: every device holding a role on a group actor reads its inbox, and each re-placed K's grant on C with C's `label.0` and `created.0`, 2.8 KB per chat join, and later C's new `label.0` after each rotation; the payload's hints are what a later key-actor holder, a link joiner, finds the target's label by). When a named thing has no label, the payload carries the author's chain for the carried parts and, for a grant or re-seal, the boxed things' current `keys.0` (`local.rs` `inbox_chain`, from `chain_under`; spec/wire.md §9; left out when the blob would not fit `MAX_BLOB`; without the keyset `Core::secret_actor` falls back to the owner and `may_read` denies the holder: a thin client saw nothing of its account's unrouted grant). Not for a labeled thing: the label carries the chain, and a holder that applied a grant before reading the label acted under it before its admin re-registered it (sims `snapshot_rights`, `purge_tombstones`, `ephemeral`, `coverer_revoked` left a writer's card never placed, its readers pending `MissingChain`: issues/holder-ahead-of-the-head.md), so the recipient applies the grant with no label of the thing to read the chain from: a grant on an unsynced thing is held, shown as `NoRoute`, and a group's admin copies it under the group's label before the thing is synced; the receiver ingests the chain before the commit, only for an admitted blob (`chain_commits`). Inbox hints (`inbound.rs` `vet_inbox_hints`, run from scratch after each open batch and each `run_dirty`; payloads cached in memory per entry, `inbox_opened`): per unexpired opened blob whose commit is applied or pending, the first payload thing with no known label the commit gave this node a read secret of (`Engine::boxed_by`: valid `secrets.0`, or a reading-only candidate from the pending commit), one per blob, so a stranger's hints are bounded by the deposit budget and go with the blob; a `via` hint (key actor follow) is never touched. A box that opens proves only that the sender knew the actor's KEM key, hence invite requests (Limits, Invite requests). Consumed inbox blobs are not deleted early (a MAY): a link's later joiners and an account's later devices open the named thing's label by the blob's hints while the copied `label.0` still waits for the granter's chain (deleting them failed every `link_redeem` sweep seed: a joiner never found the target's label), and an inbox at another group's label gets no copy at all; they expire after `INBOX_LIFETIME`. So a handled one leaves the deposit budget by a stamp in place (`pass/` `stamp_inbox`, after the same relay wait as a promotion; an account otherwise took 72 grants per 90 days): any writer that holds the commit applied and valid, or whose user declined it. A hostless served label has no entry budget (`serve.rs`: bytes only), so `local_promote` does not stamp them. Senders keep every flows inbox delivery (`Delivery::Inbox { resend }`, `y/v`) and, `INBOX_LIFETIME` after sending, seal it again to the holder's newest keyset and re-send unless the holder acted on it (`acted`: a held commit newer than the delivered one by the holder or a device of it writing a named thing or one it owns; any commit of the holder counted once, and a recipient that wrote anything the sender syncs lost every share its inbox had cleared for good: `cleared_share_sent_again_after_the_holder_acted_elsewhere_spec_sync_3`) or, for a grant or re-seal, is no longer a current holder of a thing the commit writes grants or secrets of; a re-sent removal notice names no label (the removed holder must not learn the target's current one), at most `MAX_INBOX_RESENDS` (3) times (`local.rs` `send_inbox`); a read-only grantee that writes nothing under the thing is so re-sent all 3 times. App-made `deliver_inbox` blobs are not re-sent. Direct commits for the app (`take_direct`) and stranded heartbeat times are sync state (`y/n`, `y/u`). Outstanding fetches stay in memory: every pass re-derives them (`refetch` of unopened present entries, `fetch_waiting` of waiting commits' blobs, `tree_wants`); only an app's lazy `fetch` is lost with a restart, and its read asks again.
- **An opened inbox blob starts the labels' passes** (`open_one`): the copy is placed at a pass of the actor's home label, and applying a commit starts one only if the commit is new here. A grant to a group its granter owns has the granter's own inbox as the group's, so the granter's deposit comes back naming a commit it already holds: with no pass, the group's members waited for the next unrelated pass (26-28 s of sim clock in one probe, at most `resync_ms`). The invite hold only made it common: the old timing hid it on a first grant, since the Register reply's pass ran after the deposit's echo.
- **Who owns a label on a connection**: `Conn.labels` is keyed by label, its `LConn.group` fixed at `start_label`, and `wanted_labels` puts `labels()` first, then hints, then receipts reads. So a hint under another thing's name would take a label whenever `labels()` leaves it out (receipts-only, no secret held). Hence: a payload names only a thing's own label (spec/wire.md §9), `vet_inbox_hints` skips a label any `label.0` here records, and `add_new_labels` restarts a Failed label wanted under another thing or another index of a hint's thing (no Open in flight then; a label still opening keeps its thing until it fails: comparing the thing alone let a sender naming one thing at two indexes alternate them forever, `hint_turns_reach_the_group`). Blobs naming one label under different things take turns: a failed open records (label, thing, index) in `hint_failed` (memory only, cleared at a Failed label's `resync_ms` retry, not at a refusal's shorter one, which a host a sender names could use to cut every round; dropped when no blob names the label any more), the next vet picks the first thing not in it, or the first if all failed (so each retry round is at most one open per named thing; no spin), and the hint carries the hosts of all of them, since one naming a dead host alone would never fail. One label can so be on different things on different connections (a host a sender names, holding the real path, can walk a hinted open to the head and take the claim: a claim cannot be checked without the step's claim set), so `group_of(l, conn)` judges per connection: what a connection delivers is fetched, kept (`drop_unvouched`), opened and wrap-judged under that connection's group, the same group `Work::unopened`/`refetch` asked under. A judge differing from the asker was a Fetch loop: bytes fetched because they unwrapped under one group were dropped as unopened under another and asked for again every pass (`hint_at_a_silent_host_does_not_hold_off_the_group`, `hint_at_a_claiming_host_does_not_hold_off_the_group`, claiming hosts in `hint_turns`). Without a connection: the group whose held `label.0` records the label (spec/sync.md §3: a hint is the sender's word until then), else an Open connection's, else any connection's, else the hint's thing. A hint's sync key opens only a head of that key. Left: a reader of the label can box its read secret as another thing's secret; that hint opens, never fails, and holds the label until the blob expires. Accepted: only a reader of the label can.
- **Revokes about authors** (spec/permissions.md §4; `Engine::revoke_certificates`, `pass/` `certificates`): the authors seen under a label are the authors of its commit entries that this node judges invalid in a part the entry holds or, for a role commit, in any grant op (aspect validity holds while any op on the aspect is valid: a single-use race loser's void grant sits beside its valid removal of L), or cannot judge yet (pending) (`Engine::judged_valid`): a revoke changes no verdict on writes its frontier covers, and placing it for them cost every link joiner the remover's whole chain (≈ 12 KB) under its home label at each joiner removal (its home holds the copy of its grant by L); a later write the revoke voids brings it then (revocation reaches a label when a holder next syncs it, spec/requirements.md); applied edge writes lowering one's grant on a thing outside the closure, and roster snapshots of such things naming one (projected to the authors), go under the label with what judges them (`Timeline::write_certificates`: their authors' chains), placed like chain certificates (another node's demotion or `keys.0` left to its author for `SETTLE_MS` when the author reads the label's actor and so places it itself (`Delivery::Removal` goes under the labels holding the holder that the author syncs); one by an author who does not, an outsider's removal from the inbox among them, is copied at once: the hold only dedupes co-readers' copies, and a blanket hold delayed a group's readers of such a removal by 30 s for nothing, `tied::grant_and_removal_orders_large` seed 15 asserting within it. A grant is never held: the hold is for frontier and `keys.0`-only commits, and no author places a grant's copy but the holder's admins). Under a read epoch that does not cover a known departure, a node that may not rotate places only the revokes of the departures inside holders of the label's actor that leave its epoch uncovered now (`rotation::uncovered_departures`, the newest write lowering the departed holder's grant on the actor it left, the last on its chain: `via[1]` there once found nothing two levels down; `Engine::inside_holder_revokes`; spec/permissions.md §4 exception), each the whole write on that actor (with its rotation's `keys.0` and `secrets.0`: a reader that syncs the holder waits for every delta of it, so an grants-only copy left the label's admin pending in `link_race`), plus the newest `keys.0` commit of each actor on the chain, projected to that `keys.0` like a chain certificate (not whole: a covered removal that rotated X stays unplaced, `only_uncovering_revokes_placed_spec_permissions_4`), with its author's chain (an intermediate rotated apart from the departure write, or M rotated after a self-removal, is otherwise unknown to a rotator holding none of its secrets: it seals to the old keyset, which the departed holds, so `rotation_due` refuses and the label strands; `revokes::nested_departure_revoke_placed_spec_permissions_4`): they tell the rotators what keeps the epoch uncovered and what to seal to; nothing else goes under it.
- **Others' certificates** (`pass/delete.rs` `stale_card`, judged once settled): another node's card entry (only its own `node.0`, `reach.0`, `keys.0`) is outside the required set when a newer valid write of that node on each of those aspects is present at the host in an entry checked genuine (`Engine::latest_by`: the newest applied commit whose delta there is valid, by the given author; `ts` is the author's word, so anyone's later commit on another's card stood for the current one before), or, for `node.0` and `reach.0`, when the node departed: it reads the label's actor no more and an applied write on its way there removed a grant or passed its `until` (its own grant, or one of an actor it reads through: its account's; a departed node is never dialed; "reads no more" alone misjudged holders whose chain the view lacked, and their cards churned in the sweep; tests `person_removed_node_card_deleted_spec_permissions_4`, `until_expired_node_card_deleted_spec_permissions_4`, `unheld_chain_card_kept_spec_permissions_4`); its `keys.0` stays, chains of its old writes may need it. Admins (the delete key) delete them. The blobs a certificate copy linked (`place_linked`) are deleted by an admin once this node knows no entry of the copied commit under the label (one placed and not confirmed yet counts) and no other present entry links them. Every "newest commit on an aspect" choice (chain certificates, inbox copies) takes the newest valid applied write. `certificates` never re-places this node's own deleted copy, except its own card while it reads the label's actor (`own_card_read`): a re-granted node whose card an admin deleted places it again (`regranted_node_card_placed_again_spec_permissions_4`). Until both converge on the role commit (an admin that has not applied the re-grant still judges the node departed) the two can ping-pong: the node places, the admin deletes, once per pass each.
- **Pass cost**: `label_bodies_meta` keeps each commit's bodies without plaintext in `Core::bodies` (dropped when the commit's record is written, when a thing it touches gets its creation record, all of them when an actor gets secrets of its own or a changing transaction rolls back; a commit whose owner chains are not all known is not kept); the pass projects a body's plaintext again only to seal it or walk its links (`body_plaintext`). A failed read-only transaction keeps every cache (`Core::rollback` returns early; a debug assertion in `Engine::run` checks that no index changed without `touch`). Test `label_bodies_cached_per_commit_spec_sync_6`.
- **Work sets** (`sync/work.rs`; spec/requirements.md Scale): a pass at a host judges only what its (connection, label) work set names (`LConn::work`): the bodies (`Engine::commit_bodies_under`) and entries of its commits, its non-commit blobs (chunks, cert-linked blobs), plus what is per pass anyway (certificates, inbox copies, heartbeat, promotion of deposits, parked relays, reseal). Triggers: one engine hook, `Engine::take_changed` (`Core::changed`, kept only while a `SyncEngine` wraps the engine): the commits whose record, parts, validity or timers changed since the last take. The engine marks them where it changes them (`engine::Changed`): an applied or joined (late parts) commit; a commit whose validity flipped, or a snapshot whose carried writes' judgments did (`rejudge_all`); a body whose death records moved (`note_deaths`: the bodies a write killed; replays mark only records that changed, so a write on an aspect re-judges O(bodies it killed)); every commit on a thing whose `created.0` record came; a dropped part (`drop_part`: compaction, keep at most, expiry, purge); a fired timer (`Engine::tick`). An aspect whose state changed other than by a valid write's join (a validity flip, an un-merge on apply or late, expiry, purge, a late delta) is marked as an aspect (`Changed::aspects`): it wakes what waits on the state and judges no commit by itself (was: every commit on it, O(aspect history) per expiry or flip). A mark from an aborted transaction stays (one extra judgment). A step settles its deaths replays before its passes; what the passes' own replays mark is drained after the step. What a step's passes mark (a refetch applied commits, an admin recorded a step, those replays) passes in the same `handle`, up to `PASS_AGAIN` rounds, not at whatever event comes next: full passes had judged it already, `work_sets_match_full_passes` showed it as a late arrival. `engine_events` drains it at each step and pass start: the commits go to every open label's set (`Touched::commits`), their aspects and the marked aspects wake the verdicts waiting on aspect states (`Touched::states`, `Left::waits`), their chunks the bodies waiting on a linked blob (`Left::links`), and they are `forget_dropped`'s candidates. Engine events stay for roles only (below: `Roster`, `created.0` and role commits, `LostAccess` judges everything). Sync's own triggers: the sync state's entry, presence, deposited, tombstone and certificate records (`State::touch`, by label), carriers (`touched_commits`), its own drops (`drop_covered`: judged in the same pass), blobs that arrived (`log_events`). Derived per pass (`prepare`): a snapshot or another node's card commit in the set expands to every commit on its aspects; things entering or leaving the closure; aspects moving in or out of the unsettled sets; due times (keep-at-least, expiry); aspect states a verdict waits on (`Left::waits`: a dropped body with live writes waiting for a carrier, woken by any write to the aspect); linked blobs not here yet (`Left::links`). The group's closure is an `Arc` from `Groups::closures`, the same one while it does not change (kept on relisting when equal): `sync_closure` walks it (`set_syncing`) only when it differs from the one last walked (`synced_closures`; `PassStats::closures` counts walks) and `prepare` diffs it with the set's only then; the bodies' `BodyCtx` shares it (taken again after `refetch` if that applied commits). The home label's published things (`published_under`) come from the `label.0` index (`Core::labeled`, kept by `index_commit`), taken for every actor at once and cached against the change counts of the held records, `own_keys` and `labeled` (`Core::published`; was a scan of every held aspect key per pass); a group's `label.0` is decoded once per write of it (`Core::labels`, dropped by `Core::wrote` and on rollback) and shared (`labels_of`: `Arc<GroupLabel>`s; `served_labels` borrows the steps). Debug builds check both against a recomputation. Local passes (labels served with no host, `local_pass`) have a work set per label (`SyncEngine::local_work`) fed by the same touches and prepared, scoped and left as a host's (`take_inputs` shared); a non-commit entry waits on its prefix's expiry (`Waits::due`); differentials `local_serve::local_work_sets_match_full_passes_spec_sync_5` (served state at every step equal to full passes) and `local_inbox_blob_expires_spec_sync_5` (an inbox blob under a host-less home label: `deliver_inbox` to an account created with no host; the only local check that fails without `Waits::due`). The deletion step's other `Left` bookkeeping (waits, due, held back) is redundant with engine triggers in every local scenario tried: leaving nothing fails only the inbox test. Marks before a `SyncEngine` wraps the engine (open, restart) are not needed: a label's first pass on a connection judges everything (`Work::default`). Roles (`note_role_moves`, `roles_moved`): a pass reads rosters only through `may_read`/roles (entitlement, a superset's foreign deltas, `stale_card`'s departure), held epochs (wraps, unopened entries, delete keys) and reader actors (`secret_actor`, `own_keys`). Perm reports the (holder, target) grants that differ now or at any point of the walk, however the walk got there (`osis_perm::Changed::edges`, `engine::Changed::edges`), and sync reads no commit's ops. A role comes from a holder up, so a changed grant moves roles only for `Held::upstream` of its holder and only on `Held::reach` of its target (`work::RoleMoves`, subjects and reached); a new `created.0` the same, and `Held::below` of it has a new owner chain (`Touched::moved`). A label is hit when its actor, its group or this node is a subject: `reached` then goes to `moved`, and a `moved` holding the label's actor judges everything, otherwise closure and published things in it expand to their commits, the label's own commits with a delta on them too, other nodes' cards, and the roster horizon is taken again. Raises and lowerings go by one rule. A plain add has as subjects the new holder and those above it, so no other label and no other node's labels judge anything for it. A card's author is a subject the rule does not look at: a card goes stale only by a departure, a departure brings a rotation, and that changes `Inputs` (full pass); deleting those branches changed no differential run. `member_churn` (scenario) is the add-heavy differential. Epochs: the group's `ActorEpochs` is a pass input; deletes lacking a key (`Note::keyless`) wait in `keyless` until any role-class write, flip or late part. Unsettled: commits judged while anything was unsettled (deletions) or an entry was being fetched (must-hold) are kept (`held_back`) and judged again once that ends; becoming unsettled only withholds actions, so it judges nothing. Full pass (`Touched::full`): a new connection's label, a role or owner chain of the label's actor moving or a change of its `own_keys`, lost access, a forget (state reloaded), `set_hosts`/`set_peers`, a changed pass input (`Inputs`: head and epochs, usable roles, replaced, group actor, published things, may rotate, the group's held epochs), the roster clock horizon (`roster_horizon`: a grant's `until`, a edge write or roster snapshot ahead of the clock, in the components of the actor and the closure's readers). A commit leaves the set once every send of it is present or tombstoned at the host and no judgment of it waits (relay wait, delete in flight or waiting, `covered` not established); entries touched mid-pass are pulled in (`pull`) with their commits' bodies. Aggregates kept with the set (rebuilt by a full pass): snapshot entries per aspect, unopened entries, unjudged authors (`certificates`), others' heartbeats (`reseal`). `covered_judged` is trimmed when consulted (a drop is a trigger). Indexes in `State`: entries by (label, commit), by kind, certificate entries, labels per blob, presence and tombstones per (label, blob). Engine changes are drained at each pass start (a carrier written by the pass before is judged by the next); late deltas mark their commit (a part that changes no read still changes the bodies other labels must hold); touches are spread at the end of each `handle` too, and dropped with no label open (a label opened later judges everything). `compact` forgets the bodies it drops (key and ciphertext, spec/commits.md §5). `forget_dropped` and `dropped_chunks` take candidates (chunk listers kept in `SyncEngine::listers`). `verdicts` judges everything. `SyncConfig::full_passes` turns the sets off: osis-sim `with_full_passes` runs a scenario both ways and the runs must end alike and reach the hosts at the same moments (`core/test/sim/tests/it/work_sets.rs`, scenario `work_sets`; it found: a carrier snapshot written by one host's pass and the next pass's set, a dropped body's blob coming back unforgotten, entries touched mid-pass judged without their bodies). - **Role moves** (`work::RoleMoves`): a pass reads roles as the label's actor, its group or this node, so only a move upstream of one of those re-judges. Stated limit: another node's card copy (its `node.0`, `reach.0`) goes at the next full pass after its departure, normally the rotation's, so a host keeps it until then. Nothing trusts the copy: dialing asks `may_read` at the dial (`peers`), rotations seal by roster. A label's waiting work is bounded (`SyncConfig::work_max`).
- **Who passes** (`engine_events`): a content change (no role commit, no role-class, creation, group or placement aspect, not on a key actor, no late drop) marks dirty only the labels whose closure holds the thing (`mark_dirty_of`); every other change marks all (`mark_dirty`, and `cfg.full_passes` always, so `work_sets_*` compare the two). A label left out takes the change into its set and passes when marked or at its `pass_at` (Idle labels). Was one pass per label per message; the admin of a chat has a label per contact. Heartbeats: a pass reads only those touched since it last looked (`Work::beats_repair`, `beats_reseal`; a full pass reads all).
- **Idle labels** (`Work::quiet`, `resync_due`, `schedule_pass`; `scale::idle_labels_pass_only_when_due`): a subscribed label passes when marked, not by the clock. A resync (`timers`) passes it only if a pass left something (`Left::commits`, `blobs`, `again`: a relay or commit deposit a writer has not promoted), its own records were touched (`State::touch`), a spread change woke a wait (`woken_by`: `waits`, `at_most`, `links`, `keyless`), something is unopened or unsettled (`unopened`, `held_back`, `unsettled`, `settled`), a set is `full`, or its `pass_at` came. A pass for a resync sent nothing to the host and caught no missed push (the subscription's order does; a new connection judges all). `pass_at` (`schedule_pass`, after each pass): the first of the set's due times, the roster's clock horizon (`until`), the next heartbeat or stranded heartbeat (not one past due: the pass that just ran could not send it, a label stranded once keeps its time for good); with none of them one `HEARTBEAT_MIN_INTERVAL` on, so there is no separate safety resync: a missed trigger waits at most as long as a heartbeat. A change from elsewhere waiting in a set (`spread_touches`) wants no pass; past `work_max` the set goes `full` and passes at its next resync, which also ends what it holds. Named so they need no resync: the wait for peers ending (`reseal` asks `settle_by`), a grant with an `until` or a role write ahead of the clock (`Touched::clock`: the horizon is taken again at the marked pass; a plain add reads no horizon). `settle_at` keeps labels: what comes due passes those labels alone, in full-pass runs too (was every label, so one deposit passed them all). The node wakes once per `resync_ms` with anything open (`last_tick`), not per label, unless a label wants its own resync: ticks stay for what relies on them (`relink_lost`, `eph_retry`, reconciling, step-level timers). `label_status`'s `last_sync` of an idle subscribed label is now, as honest as before: a resync never touched the wire, so either way a stalled connection shows until a ping finds it (`PING_INTERVAL` + `STALL_TIMEOUT`, 7 min). `pass_at` is in corrected time, as what it comes from: a host's clock sample moves it with them. A clock gone back: a `pass_at` further off than an interval passes at the next resync, a label's `last_sync` is clamped to now, so the bound holds (`scale::a_clock_gone_back_keeps_a_quiet_labels_bound`); what else counts in raw time waits for the clock (issues/clock-back-raw-timers.md). Delays of an idle label, checked against a pass at every resync in a world probe and `work_sets_match_full_passes`: expiry on reads exact (engine timer, no pass); a grant's `until` on roles exact, its pass, keep-at-least and other due times within two resyncs (the tick is per node, so a label's own resync may slip one); re-sends, deposit retries and tombstones keep their own wakes and sweeps; refused uploads, a lost reply and unsettled work are `again`: every resync, as before. `resync_ms` paces retries only, so it could grow without changing idle cost; it stays, since the ephemeral lane's retries and the opens' back-off use it. `Timeline::role` at the current grants is memoized per node until a followed `until` (`Memo::roles_now`), `closure` keeps the asker's reach (`Memo::forward`).

- **Relay wait** (`pass/promote.rs` `relay_at`, `promote`): a writer uploads or relays another node's commit at a host lacking it, and promotes a deposit, only after a wait of `RELAY_MIN_MS` (5 s) to `SETTLE_MS` (30 s) since the commit arrived (the deposit was first seen; in memory), the point fixed per (node, blob) by a hash; its own commits (origin local, a held key actor's included) and `First` placements go at once. ## First sync: newest first (spec/sync.md §6)
Why the wrap: hosts must not tell blobs apart, and a blob's header sits in its ciphertext, so for a chat message a header is the whole body. A wrap is listed for free and opened by readers only, so 8 B of order there beat a host-visible class, a separate label for role commits, or reading the log from its end (role commits sit anywhere in it, so a newest-first log read cannot stop early). No host change. A writer's lie only moves a blob in the liar's readers' queues: a flood marked 0 delays the newest page by its size (a stated limit, not defended).
Priority, not partiality: everything is fetched, so "not fetched" needs no meaning beyond "not received", and no aspect is special: a state-reading aspect reads partial during the fill, as it did during the old random-order replay, and a snapshot being recent helps it. The price is listing every entry (about 160 B each; on this box 115 us each, most of it the stamp's signature).
As built (`sync/fill.rs`): `LConn.fill` holds the queue, the batch asked (in `Requests::fetching` for its truth) and the host's position; `y/4` marks (host, label) so a restart or lost connection rebuilds the queue from the entries; the cursor is saved at the listing's end. `ready()` lets passes run past order 0, `idle()` and `bump_pass` wait for the end. `mark_dirty` leaves a filling label alone (a pass per batch costs what its work set holds, and nothing is waiting on it): passes come at `resync_ms`, on an own write, and at the end. The end asks one more Sync with the configured `inline_limit` (pushes use the last Sync's) and that Sync's end is the pass end. Entries that do not open go last and are fetched too (as a replay brought them inline; `drop_unvouched` judges them on arrival).
Order 0 covers a purge request too: a purge names only commits with a smaller `ts`, so newest first brings it before its targets anyway, except a target that is itself order 0 (a thing's first message). A thing per item (not a chat's one long aspect) makes most commits order 0: that workload fills in log-like order, as before.
Limits: a Sync with a cursor brings bytes inline, oldest first, whatever the gap, and a restart's reconciliation fetches what is new in ID order: a device back after a long time gets no newest-first (only no cursor at all fills). An order 0 entry another host's fill had in flight, on a connection then lost, waits for this fill's end (`refetch`). A host that lists an entry and never answers its fetch keeps that fill open until the stall timeout redials: the same stuck pass as a host not answering a Sync. A compaction part way is safe: a snapshot's frontiers stop at the first gap, so it covers nothing it has not got.

## Moved from the spec
Consequences and reasons, not rules. The rules stay in spec/sync.md at the section named.
- §2: the deposit key is keyed by label ID so that labels of one actor register unrelated deposit keys. After a fork (spec/crypto.md §4) hosts may hold different branches, each signed through. A `label.0` write goes under the owner's home label so that actor's devices find the group.
- §2 Replacement: a label is typically lost when a removed admin re-registers first. The old label keeps its role commits and the `label.0` commit that marks it replaced so a node that knows only the old label finds the new one.
- §3 Projection: one blob per class means a delete key never deletes a delta it does not cover, an expired class is deleted rather than rewritten, and a blob expires whole.
- §3 Inbox blob: re-send ignores a recipient acting elsewhere because the blob may have been cleared (§5). Grant copy: a chain's `keys.0` are left out because a verifier judges by creation records and edge writes and a fresh deposit seed is not for that actor's readers; the copy is what lets the actor's other and future devices and its readers find the grant. Inbox blob order: a label told unknown may be on its way.
- §5 Deposit: a client keeps sending its own deposit after losing read access because other nodes may hold parts of that commit from elsewhere and wait for the rest. A certificate copy is not deleted for an incomplete chain because a judge cannot tell a chain that will not come from one still uploading, and the chain moves after the copy. Ephemeral and relay-only deposits are refused because readers write no ephemeral data.
- §5 Host caps: an ephemeral upload refused for its cap reaches no holder through that host until room appears. Entries deleted at a host's total cap may be brought back by nodes holding them.
- §6 Convergence: a deleted body is not re-sent because a right holder's keep bounds, dated by its own deaths (spec/commits.md §5), had passed.
- §6 Flow control: within `WINDOW`, unwritten requests and unwritten replies stay below `WINDOW + MAX_MESSAGE + 4` bytes, and unwritten pushes below `MAX_MESSAGE + 4`; requests received before any is answered were all in flight at once. That is where the two close bounds come from.
- §7 Compact: the `MAX_DRIFT` margin past the keep-at-least bound means no node whose clock lags by up to `MAX_DRIFT` still judges a dropped body must-hold. Sweep: what a removal or expiry hid dies (spec/crdt.md §4.8), its bodies follow their keep bounds and no snapshot carries it.
- §9 Sending: waiting for an unanswered upload and coalescing means an aspect goes up as about one entry per round trip whatever the write rate.
- §9 Compaction: a node keeps bodies it authored until one of its own snapshots covers them because a demotion's frontier lists no ephemeral commit, so a compactor's demotion invalidates every snapshot it wrote, and what those covered is then gone at every holder but the authors.
- §9 A snapshot turning invalid: what it covered comes back to hosts and readers from each writer that held it when it fell and still holds the covered writes (its own it kept). A write no such writer holds (its author restarted, or never held that snapshot valid: it learned of the demotion first) stays gone at the hosts and readers that dropped it until its author writes the aspect again.
- §9 New sessions: a body invalid for good (an explicit demotion with no re-grant after it, spec/permissions.md §5.2, then a new grant) so has no later body of its node behind it. What the node wrote under the old session after that grant's key and before it learned of the demotion stays held uncovered, within the caps, until the node restarts.
- §9 Relay-only: within `MAX_DRIFT` of its `ts` a signal may arrive late, and a restarted node may deliver one again that a replayer uploads to a host that forgot it.

## Open
- Host abuse limits: deferred until a real problem (Tess). Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-label rate limits on deletes and deposits, per-label ephemeral caps, admin delete; anyone may register a label up to the host-wide label cap (then Error 12, so squatters can exhaust it), and any writer can fill a label's cap with junk the host cannot tell from data. Per-holder limits would need pseudonymous holder keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one host bound to (host, label), never into the relayed `label.0` chain.
- Claim sets in `label.0`: 32 B per padded reader per step plus entry boxes, droppable `ROLE_KEEP` after the step is superseded (steps are a map keyed by step ID so the drop is a field write); a host registered from a trimmed chain serves no claims at the trimmed steps. A dropped set does strand a holder whose next rotation is still readable (it cannot walk past the step); the stranded heartbeat on a refused claim is what reaches it (issues/reseal-triggers.md). `label.0` growth is about 250 B per step per group per rotation; if it ever matters, a root step carrying the current keys signed by the genesis delete key would let old steps be dropped.
- Partial restore from hosts: `label.0` writes of owned groups now go under the owner's home label (a table of contents of labels); content of a subgroup is restorable alone only when it has its own label.
- Upload batching; log retention horizon per node (beyond it peers fall back to range reconciliation).
- Flow control (spec/sync.md §6): `ClientSession` queues requests and sends while the bytes in flight (frame plus reply allowance per unanswered request) are under `WINDOW`, so a session's own requests (at the node) and replies (at the peer) never pass `WINDOW_QUEUE`; the drivers' caps (`MAX_QUEUED`, `max_queued_bytes`) are only a bound on peers that do not read. The stall timeout counts from the last byte received or `ClientInput::Sent`: drivers compare `LinkTx::taken` (the writer pump hands the transport 16 KiB pieces) before each tick and report moved connections (`Event::Sent`, `Hub::sent`). `taken` means delivery only because QUIC/iroh `write_all` waits for stream credit (`STREAM_WINDOW` 1 MiB): a peer that stops reading stops it within 1 MiB, so a dead or non-reading peer cannot keep resetting the timer (a peer reading 16 KiB per 2 min can, by design: any link speed passes). The in-process transport never blocks a write, so `taken` jumps at once there; driver tests cannot show flow control (slow_link models the queues). Serving side backpressure (stop reading while the queue is full) was weighed: it needs a pausable `ServingSession` and a drain signal, and the client still needs a request window for its own queue; the reply allowances made it unnecessary for compliant clients. `RESEND_MS` resends only an entry whose request was answered (`ClientSession::answered(tag)`: every request of the commands tagged up to `tag`, follow-ups included, got its reply; `Requests` stores the tag of `commands()` after the batch's commands went, `UNTAGGED` until then), so a held-back queue that drains sends nothing twice. Pushes (`ServingSession`): with `ServingInput::Taken(cumulative LinkTx::taken)` reported, a push goes only while the bytes written and not taken, it included, fit `REPLY_BUDGET` (or none are unwritten); otherwise the label goes to `owed` (FIFO; while any label is owed a `Changed` only queues its label) and continues from its `subs` position at a later `Taken`, labels in turn (one held again goes to the back: a busy label starved the others when `owed` was a set walked in ID order); relay-only pushes without room are dropped. Without reports (sim, test drivers: instant delivery) nothing is held. Drivers report before a connection's input bytes and at ticks; `held()` connections ask for a tick every `PUSH_POLL_MS` (hub `next_due`, node `serve_wake`). Caps: `SEND_QUEUE` = `WINDOW_QUEUE` + `PUSH_QUEUE` (one push frame); host `max_queued_bytes` 48 MiB. Test: proto `slow_link::*` (72 MiB each way at 64 KB/s, 2 MiB at 1 KB/s, both on one session with the real cap sizes, fails with the window off; 72 MiB pushed to a 640 KB/s subscriber within `SEND_QUEUE`, fails without `Taken`; held labels take turns; a random push differential (labels, sizes, rates) against the log; requests held back for hours stay unanswered).
- **Hub stall bounds** (the hub thread serves every connection, so per-input work must be bounded and comparable to honest work): an Open costs a signature and at most three lookups (claims indexed as `H` rows, never a claim-set load); a message's signatures try the head's key only after one verified under no key (spec/wire.md §11.2), so at most one older-key scan per message; Sync entries capped at 1024 like Upload; one store commit per input; a relay goes to subscribers only; a connection whose unwritten replies pass `SEND_QUEUE` within one input is closed before its further requests run (`ServingSession::unsent`); requests in one input are all unanswered when the last was sent, so their frames plus reply allowances (`client::allowance`, the one definition both sides use) stay within `MAX_UNANSWERED` (`WINDOW + 2 × MAX_MESSAGE + 4`) for a compliant peer, and one passing it is closed before that request runs: at most three MAX_MESSAGE-allowance requests (Reconcile, Fetch, Sync, Path) per input. That bounds the two requests whose reads follow the label rather than the message, Reconcile and Sync from an old cursor (Sync skips log records that yield no event, up to `log_keep`; issues/sync-log-scan.md). Reconcile: a whole-space range reads every live ID (release, redb, `file::reconcile_whole_space_budget`, pages decrypted from the host's `Store`: about 125 ms at 10^5 live entries, 1.06 s at the 2^20 per-label cap; 1024 puts in one commit at 10^5 about 0.45 s, at 2^20 about 1 s; before the bound, one 64 KiB input of about 1600 such 40-byte requests cost a minute at 10^5). An honest reconciliation also reads up to the label once per message, so per input the two are alike. Weighed: per-subtree fingerprints in the store (O(log n) per range) cut honest and hostile cost alike but need an order-statistic index persisted beside the `E` rows in three stores, and a 256-range message with splits would still cost thousands of row reads; not needed while the per-label cap (2^20) bounds a scan. These are bounds per input (one read, at most 64 KiB), not per second: an opener can send input after input and keep the hub busy, as an honest peer with a full window may, so inputs take turns (`driver::Turns`): a connection's reader hands the driver one read and the next only after the hub took it, and the driver serves waiting reads round-robin by source (`Connection::source`), then by connection within a source; reads that arrived are queued before each turn. Bound: with S sources waiting and P the per-input bound, a read waits at most (S − 1) × P once it reached the driver (k × S × P if its source has k connections waiting), plus the bookkeeping between turns (accepts, closes, ticks: a sweep is 1024 rows); a message spanning several reads waits that per read, and each read moves the sender's stream (transport progress, so stall timeouts see it). One opener with any number of connections from one source delays others by one input per turn: at 10^5 entries about 0.4 s, at the 2^20 cap about 3.2 s, against `STALL_TIMEOUT_MS` 2 min; many sources (issues/host-hub-stall.md, Sources) each get a turn. Test: `driver::flood_does_not_delay_others` (a flood's reads queued behind one reader delayed another's Sync by 190 reads, now 12, the probe's round trip), `driver::tests::turns_by_source`. Throughput: one session's 64 MiB upload then download (16 KiB blobs, QUIC loopback, release) costs the same CPU with one read handed over at a time as with the old 1024-slot queue (the link's 16-read read-ahead keeps the pipe full). Not done: decode and verification off the hub thread; a host-wide relay rate (a relay's fan-out is bounded by the subscribers' own queues and rates per label).

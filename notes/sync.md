# Sync: rationale
> Summary: Why spec/sync.md looks the way it does: blobs and labels, stamps and deposits, sync-key gating and claim keys, tokens and retention at blind nodes, convergence and compaction, why there is no recycle bin, accepted limits, what a blind node learns, policy defaults, rejected alternatives, open items.

The requirements behind this file: spec/requirements.md, Untrusted (blind) nodes and Deletion.

## Why
- **One commit ID, one blob per projection, random key per blob**: a commit has one ID whatever groups contain it. Sharing history means adding wraps, never re-encrypting.
- **No commit size limit**: a delta pages like a snapshot and the header's lists go by link, so atomicity never depends on size and the API never splits a write. The costs (a reader stores pages it cannot apply yet, a writer that dies mid-upload leaves orphan pages for convergence to delete, apply streams pages through one staged transaction) are the ones snapshots carry anyway. The old one-blob rule bought nothing but a second commit kind of edit (split, non-atomic) that every app had to reason about.
- **Groups as sync unit**: groups are free and overlap; owner actors as the unit would force a copy for every separately syncable subset.
- **Label keys derive from the group's own role secrets**, never the owner's directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the blind node. The deposit key derives from the actor's deposit seed (not from group secrets, so that a plain group's readers can derive it from the owner's `/keys`), hence it is keyed by label ID rather than by index: with the index alone every plain group of one owner registered the same deposit public key (found in the final pre-swarm review).
- **Entitlement, not group membership**, decides labeling: a thing dropped into a shared folder without an edge is silently not shared, which is the intended failure; an "add to shared folder" helper writes both. Cache the check per (thing, label), invalidated by membership changes of the label actor, the thing's edges or its owner chain.
- **Convergence as the one rule**: must-hold, may-hold, must-not-hold per body. Retag on join, cleanup on leave, compaction and repair after a bad deletion are all this rule. The may-hold class keeps a compactor's drop and a lagging member's re-upload from ping-ponging. A wrongful deletion is healed at the next member sync by a fresh encryption.
- **Projection** instead of per-delta keys wrapped per label (a wrap per delta per label plus header redaction). Every projection verifies alone since the header carries every delta hash. The projection key is (readable subset, retention class incl. expiry and token set): a commit mixing "last modified, keep-at-most 0" with "body, forever" would otherwise be rewritten on every replacement, and a per-commit expiry forced clients to split atomic writes that mix a disappearing message with a non-expiring counter.
- **Certificate blobs per label**: one blob across labels (a wrap each) would link every label a node syncs through its node card. Cost: a few small blobs per (node, label). They are outside the closure, so convergence names a label's required set as closure plus certificates; without that a group admin's convergence pass would delete them as "outside the closure" and the node would re-deposit forever.
- **Inbox blobs**: a non-member cannot wrap anything under a label it does not read (a granter is not a reader of the grantee's home label), so everything that must reach an actor from outside goes boxed to its read KEM key: grants, edge changes and removals (so it erases), re-seals, each with the label IDs and servers it needs (the old text said "the target's `/label` commit", which a non-member cannot wrap and which is a join of many commits anyway). They carry a delivery expiry so an unconsumed one frees the budget by itself, and the inbox is a label the recipient's admins administer so they can delete consumed ones. Direct grants to a node go by pairing only: a node is listed by DH key and cannot enter a label cold.
- **Self-certifying label IDs**: a random ID lets anyone who learned it (an ex-reader, a leaked `/label`) squat it at a fresh server under their own keys. Two admins creating a label concurrently derive the same ID.
- **Blob prefix**: expiry and token commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are salted per blob rather than being the header's token hashes, so projections and rewrites of one commit are unlinkable at the server.
- **Stamps** (read must not give upload): the author's signature sits inside the ciphertext, so the label write key is the only writer proof a blind node can check. Signing (label ID, blob ID, wrap) and storing the signature beside the wrap lets anyone relay a writer-vouched entry (LAN-first flows, server to server by push, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. Stamps are checked against the current step, so a removed writer's stamps die with the rotation its removal already does. Upload needs no open: an open added nothing (a current reader could replay a stale stamped blob after its tombstone either way, and a removed one only until the next step), and requiring it blocked blind-to-blind replication. Download does need one, so blind nodes replicate by push, never pull (an ex-member could otherwise run a "server" and pull). What a reader legitimately needs under a label goes by deposit: a provisional entry under a per-label budget, readable at once by co-readers, promoted by a writer's stamped re-upload, which frees the budget. Rejected: upload under the write key alone (loses relay); per-member upload keys (linkable; Open below).
- **Commit token salt in the header**: the commit's own blob ID does not exist when the header is built and changes on rewrite or projection.
- **Token plus label key** for deletion: the token proves the purge right as of the delta, the label key current membership. Thing-write-secret tokens need the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the rotation the demotion already does. Admin- and author-level tokens need only the sync key, because a thing's admin or author is often a mere reader of the label (anyone sharing a thing into a group they only read). Commitments carry a level byte so the server knows which signature a presented token needs (an imported `writer` delta has no author-chain token, so position alone would misfile its write token). Honest nodes enforce current write permission for every purge (spec/permissions.md §8); servers only this approximation (spec/requirements.md, Untrusted nodes).
- **Tokens follow retention**, one secret per level: the thing's admin secret for `admin`, plus the write secret above the author node (every device of the person holds it) for `author`, plus the thing's write secret for `writer`; none for `nobody`. Without an admin-level token a thing admin who is not an admin of the label's group could not delete at servers. Blobs are projected by token set as well as reader set, so a `nobody` delta is never deletable through a commit-mate's token. Under the shared-owner pattern `author` collapses to `writer`. Chunks carry their creating delta's tokens (16 bytes per chunk per secret in the header); a reused chunk whose thing-secret tokens differ from the reusing delta's is re-encrypted, else a writer could delete chunks of an `author` value or an author be unable to delete its own; author-chain tokens need not match, so dedup across editors survives. Residue: an author's explicit purge of a value cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- **Covered means redundant under join**, not "inside the snapshot's frontiers": a snapshot that omits content covers nothing it omits, so a bad snapshot is harmless and anyone can re-snapshot. It also absorbs the versioning rule that a node never compacts what it could not join.
- **Tombstones** refuse the identical blob for `TOMBSTONE_LIFETIME`, so a stale relay cannot resurrect a purged body. Members never need them: they sync before they upload, and a node holding the purge strips the value from any copy that arrives later. The lifetime is a storage-versus-churn dial: infinite is O(deletions) server storage; zero lets any relay or bundle from before the deletion put the ciphertext back until a member deletes it again. A peer staler than the log horizon returning later than the lifetime can resurrect, and members heal it. Blob IDs are hashes of ciphertext under random keys, so a tombstone is no fingerprint.
- **Timed delete**: a relative keep-at-most is honored with nobody online because the replacing writer schedules the server-side delete when it replaces, with its snapshot in the same sync. The server learns the deadline (owner: acceptable). Absolute bounds wait for a right holder (spec/requirements.md, Deletion); expiry is the only timer a blind node runs on its own. The earliest requested time wins, which is order-independent and matches "first death plus D".
- **Purge reaches snapshots**: a compactor's snapshot carries everyone's live values, so purging a write also makes it value-less in snapshot bodies and drops them; a writer that then holds no covering snapshot under a label re-snapshots there (deterministic trigger; duplicates are covered-equal and one gets dropped). Snapshots are `writer` so any writer can remove a stale snapshot at servers; they are redundant by construction, so that power costs only a re-upload.
- **A purge commit is kept `MEMBERSHIP_KEEP` after its `ts`** (TLC finding S1): the purge SHOULD name dead writes and resets the rest, so the next snapshot covers the purge commit at once and a compactor could drop it; a node that held the purged body and had not yet seen the purge then kept the value for ever (the body was covered, hence may-hold, and nothing ever told it). The same staleness class as revokes (90 days of membership history); a node offline longer is an offline copy (spec/requirements.md, Out of scope). Rejected: never covering purge commits (a blob per purge for ever); carrying purge items in snapshots (the compactor would vouch for the purger's right, which snapshots never do). `expires` on a purge commit is forbidden for the same reason (the server would drop the request unattended). The API puts a purge and its resets in a commit of their own, so an app's disappearing writes never inherit the 90 days.
- **Must-hold needs a positive "uncovered"**: a node that cannot join a body (parked) or has not fetched a snapshot's pages treats it as may-hold, never must-hold, or an old-version writer and a compactor would re-upload and delete forever. A strict-subset projection of a commit under a label (a writer whose timeline lagged uploaded less) is must-not-hold. Must-not-hold wins every overlap with must-hold (purged while uncovered, past keep-at-most while uncovered): the must-not reasons are the ones that remove content. A body holding no delta (every delta purged) is covered by definition; its header lives on in the nodes that applied it.
- **Rotation commits go up before the step** (TLC R9, second round): "register before any upload" (the server checks stamps against its head's write key, so content stamped under rotated keys must wait for the step) left a window in which a server's head named an epoch whose rotation commit was nowhere: every member listed in the step reached the head, could not open it, heartbeated stranded and was re-sealed with a secret it had no commit for. Now the registrar uploads the actor's membership commits the server lacks (the rotation chain) under the head's keys, then registers, then the rest; a step at a server implies the chain behind it is there (until compaction, where the `/secrets` snapshot is), and "stranded" means not boxed. What an ex-member gains is the removal rotation's blob under the old sync key (box map and the removal edge about itself, which it also gets by inbox), the same as from a dishonest server before.
- **Local drops of live bodies snapshot first** (TLC S11): a body under an absolute keep-at-most written offline and dropped at T before any upload left its live write in one node's state with no body or snapshot anywhere; the snapshot-first rule used to fire only for deletions at a label. Now a writer writes a covering snapshot (a local commit, uploaded later as must-hold) before dropping any body with live writes it holds no snapshot for; readers drop and keep the state. The same clause covers the timed delete of a relative keep-at-most (S13): the server deletes at the bound unattended, so the carrier must be up before it; the replacing node uploads the snapshot with the timed delete when the body still has live writes (same as at most 0). Cost: a snapshot per partial replacement of a multi-write body under a relative bound, inherent in body-granular retention.
- **Carrier tiebreaks** (TLC S12): the server is blind, so two right holders with stale views could each delete one of two identical bodies, or one of two covered-equal snapshots, each counting the other as the carrier. Deterministic choice: an identical body carries only the one with the higher blob ID, and of covered-equal snapshots the higher commit ID goes; a strict subset was never a carrier.
- **Header-only rewrites are may-hold** (TLC S14): a purge that empties a body leaves a header-only blob, covered by definition, so nobody uploads it and a compactor may drop it; headers persist at the nodes that applied the commit (dedup by commit ID needs them, and a commit-form dot resolves its author through them), not at the label.
- **A node offline past `MEMBERSHIP_KEEP` misses purges** (TLC S15): the purge commit is compacted, the returning node's body is covered (may-hold) and it keeps the value bytes until it compacts; the value itself is dead by the snapshot's reset when the purge named dead writes (the SHOULD), so it re-spreads nothing. An offline copy (spec/requirements.md, Out of scope); accepted, no mechanism (snapshots carrying purge requests was rejected above). Confirmed for the model: the purge commit's `MEMBERSHIP_KEEP` overrides its keep-at-most too; any node dropping a purged body keeps the rewrite (a reader's stays local, it cannot stamp); a remover uploads its removal rotation before anything else.
- **Live writes leave a label only when another entry carries them** (TLC S2, S5, S10): a body past an absolute keep-at-most, a strict subset, or one of two duplicates is deleted at a label only while a covering snapshot, a superset blob of the commit or an identical body is under it, and a right holder that may write the aspect uploads the snapshot itself when none is there (otherwise nobody was obliged to and the server kept the body for ever). Locally a node drops the body at the bound and keeps the live writes in its state (spec/crdt.md §4.6); a snapshot it writes from that state covers every body it applied. Snapshots take the schema's default bounds, never a commit's own: a snapshot inheriting a commit's absolute keep-at-most would itself be must-not-hold at T, and the live value would have no servable copy anywhere. Keep bounds never change what is read; only expiry kills values. The TLA+ property "a member can always serve current state" was too strong for readers (they cannot write snapshots): what holds is that live state is never lost from a node's state or from the label.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honor a MUST drop nor judge a purge request. A few bytes per delta.
- **Reads gated by the sync key**: without it an ex-member, or anyone who learned a label ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Owner: nothing is served under a superseded key, not even entries the holder could have fetched before. Rejected: a grace window after re-registration; "old key serves old entries" (no gating against ex-members); serving only rotation entries to old keys (every ex-member watches the roster size and rotation timing forever, and the flag is unverifiable). The price: a member that missed a rotation cannot download the commit carrying its new box, hence claim keys.
- **Claim keys** (decided with owner): a laggard and an ex-member hold the same shared keys, so the gate needs something only the laggard has, its own private key, and the registrar is the one party that knows the roster the step is for. So the step itself is the delivery: a fresh step key and one pseudonymous Ed25519 key per reader, derived by DH, and the laggard's recovery is a pure function of its private key and the chain the server stores anyway. Nobody delivers, drains or budgets anything. Why a signature and not a hash preimage: a dishonest server cannot replay it elsewhere. Why the step key is handed out one step at a time (a stale sync key or a claim on step j yields only step j+1): an ex-member removed at step k+1 learns that one step exists and nothing after it, no rotation count or timing, which is what a bare `stale` reply told it before; serving the current step to anyone would leak the cadence to every ex-member forever. The reply is the signed step, verified under the previous delete key, never a bare key: a server handing out a chosen step key could otherwise recognize a claimant by the pseudonym it signs with. The claim set is defined from the epoch's read boxes, not the registrar's roster: the registrar may hold the epoch without the removal commit and would otherwise list the member the rotation just removed, and boxes name the owner and plain-group readers the roster does not. Nested actors chain claims: node key on the person's home label, then the person's read key on each group label. The registrar derives M's key from the newest `/keys` it holds, so M tries old keysets as it does for boxes; a device M removed can claim until a registrar that saw M's new keyset issues a step (metadata only, M's boxes are under its new key), the same staleness class as the epoch-covers rule. Steps are not deterministic (random step key and padding), so two admins stepping concurrently produce different steps and servers that saw different ones first hold different branches for good: steps form a tree by `prev`, a server accepts only a child of its head, and the next rotation gets one child per branch (same role keys, different parent signature). `/label` holds the set of steps, so any admin can relay a server's branch; claim keys are bound to the step key rather than a sequence number, since a branch has no number of its own. A node that cannot match a server's head walks from the newest step it shares with it. Cost: 32 B per reader per step, about 3% on top of the rotation commit's boxes, which already leak the roster bucket through padded size; servers keep a step's set only until the rotations it leads to are compactable (`MEMBERSHIP_KEEP` after it was superseded); beyond that a walk would reach nothing readable anyway. The chain itself (role keys, step key, signature) stays, as before. The gate is classical like the Ed25519 open; a quantum ex-member could fetch hybrid-protected ciphertext. Grants still need a way in before the grantee holds any key of the target: the inbox blob, boxed to the grantee, deposited under the inbox its `/keys` names (an ordinary label its admins administer).
- **Rotation commits are wrapped under the epoch they supersede**: a rotation hands out the new read secret, so a wrap under it would be readable by the rotator alone (deliveries used to carry it boxed per member). Under the old wrap a laggard reads the rotations it missed in order, each under the one before. What an ex-member gains from the blob (an honest server serves it under the old sync key until the step is registered, since the chain goes up before the step; a dishonest server or stray bundle for ever): the box map of the rotation that removed it (tids and roles at the new epoch) and the removal edge about itself with its frontier, which it also receives by inbox; never a secret. Under a fork the rotator picks the newest superseded epoch; a member granted during the fork under the other branch only cannot open it and needs a re-grant (rare).
- **Re-seal** is the one recovery path for a member that holds the right private keys but cannot reach the current epoch: its missed rotations compacted (`MEMBERSHIP_KEEP` after a roster snapshot replaced them), its grant unknown to the rotator, a fork branch it never received. Nothing a co-member serves helps by itself (the wrap of every current commit is under the epoch it lacks, and a P2P peer serves wraps, not keys), so someone must seal the current secret to it: a membership commit carrying its boxes and the epochs' history boxes (without them a re-sealed member or a grantee could decrypt the history box but not fetch it: it sits in a rotation commit wrapped under the epoch they lack, TLC R3), by anyone who may rotate (a sibling device of the same person is usually a writer, not an admin, of the group), delivered as an inbox blob. Delivery under the label itself was dropped: a member that needs a re-seal cannot open the label (its claim was refused or the rotator never listed it), and the wrap would have to be under an epoch it holds. Its own private keys never change, so a node stranded on its person's home label is re-sealed the same way; when the inbox is the very label it cannot open (a device offline past `MEMBERSHIP_KEEP`, below), a sibling device re-seals it over the pairing channel (a direct connection, same flow as pairing, same node identity), which is cheaper than a restore from the card. Nothing unattended re-seals (a PQ box per reader per step was rejected for size); the triggers are a current member seen without a box at a current epoch and the stranded heartbeat (spec/permissions.md §3, §4), both SHOULD, and a client may also offer it by hand. The stranded heartbeat is placed as soon as the walk fails (a refused claim), not only at the head, since a member whose next step's set was dropped never reaches the head (TLC R2); it is a deposit wrapped under the newest secret the node holds, so it needs no open. What the triggers still miss is in issues/reseal-triggers.md.
- **Entry boxes and static entries** for recovery and link keys: a key actor entering cold holds no epoch to unwrap anything with, and the person actor's rotations get compacted eventually, so its box in `/secrets` is not reliably reachable. So the current step boxes the read secret to it (one hybrid box, 1.2 KB, on a home label per step; a 49-byte symmetric box on a link label; nothing elsewhere), and it claims the current step directly by a static entry, a hash of its signing key and the label ID, no walk and no old step needed. The registrar cannot do DH for it without a step private key it would have to keep, and a bare signing key in the set would tell the server a public identity; the hash tells it nothing until the key claims, which is rare. The entry is stable across steps, which only says that one slot is the owner's or the link's. A key actor granted after a label's step 0 is listed by a fresh step (an admin may step without rotating). Rejected: the read secret boxed to every reader (1.2 KB per reader per step, permanent, in `/label` and every roster snapshot; would spare laggards past compaction the re-grant); a seed-derived rendezvous label for the recovery key (a mini mailbox: unpromotable, floodable deposits); deriving the step key from the admin secret for determinism (an ex-admin plus a dishonest server could then identify late claimants from its tenure).
- Rule of thumb: per-entry rights are capabilities (tokens) whose preimage is distributed client-side; label-wide rights are role keys; revocation rides on role keys. Nothing stored at the server states a reason.

## Wire choices (spec/wire.md)
- The blob prefix is a fixed byte layout so a blind node parses it without a CBOR decoder; the AEAD binds it as AD so a reader cannot re-prefix a ciphertext (new expiry or commitments) under a fresh blob ID.
- Padmé length recovery: a `0x80` marker then zeros inside the ciphertext (ISO 7816-4 style). One byte, no length field, and canonical because the padded length must equal `padme(len + 1)`.
- Header lists, the token list, purge and origins go by link above `CHUNK_THRESHOLD` rather than being capped, since a commit has no size limit; only header-list chunk commitments needed a cap (issues/header-list-commitments.md).
- Range reconciliation: Negentropy-style additive fingerprints (sum of IDs mod 2^256 plus count, hashed) so a sorted ID index answers any range incrementally; 16-way splits, lists at 32 IDs, about log16(n/32) round trips. Rejected: hash of the concatenation (not incremental); Negentropy's full encoding (bound compression and timestamps, more rules for little gain).
- Protocol: request/reply by id over length-prefixed frames; both Hellos go out at once, so negotiation costs no round trip; per-entry status so a batch partly succeeds; a Status naming a stale key carries the head, so an uploader that never opened learns it.
- Opens bind the opened side's Hello challenge and static key (no replay elsewhere); stamps, deposits and deletes do not, so stamped entries and timed deletes stay relayable.

## Protocol implementation (osis-proto)
- Modules: `frame` (`FrameDecoder`, `encode_frame`), `hello` (Hello, `negotiate`, `estimate_offset`: median of per-sample offsets, Hello counts as one sample; reported after three pongs, diagnostic above 5 s), `msg` (`Message`, one variant per kind over osis-label's `Step`, `ClaimSet`, `Proof`, `DeleteItem`, `PublishAuth` and the `SecretBox` entry box; `decode` enforces every cap of spec/wire.md §11.2, `Rejected::code` gives the Error code), `rbsr`, `store` (`LabelStore`, `MemoryLabelStore`), `server` (`ServerConnection`), `client` (`ClientSession`), `bundle` (`BundleImport` over osis-label's reader and importer), `examples` (a fixed label and one message per kind, for tests and vectors).
- Decoder rules beyond the layouts: mode 1 lists at most 32 IDs, mode 2 lists 1024 then 32, IDs ascending and inside their range; ranges sorted, disjoint, `lower < upper`, an end bound only last; id 0 only on Error, Push and Signal; a step at most 323 bytes (`MAX_STEP_BYTES`). Message nesting depth 6.
- RBSR: the requester sends 256 ranges per message, pipelined, each batch with a token; a reply range outside what its batch asked (or a mode 2 range not answering one of our mode 1 ranges) is dropped. Reference split: subrange i holds own IDs `i*n/16..(i+1)*n/16`, bounds the full first own ID. 10 000 IDs with 100 differences each way: 2 round trips (unit test). A worst-case ReconcileReply (256 mode 2 ranges of 1056 IDs) is about 8.9 MB, under `MAX_MESSAGE`.
- Server engine: `handle(now, &mut dyn LabelStore, ServerInput) -> Vec<ServerOutput>`. Cross-connection work goes through the driver: `ServerOutput::Changed(label)` goes as `ServerInput::Changed` to every connection, `ServerOutput::Signal` to every other one. The engine caches each label's parsed path per head; a claim proof loads only its step's set (`LabelStore::claim_set`, shared `Arc`). Stamps, deposits and keyed deletes check the head's key, then the 8 newest distinct earlier keys (code 9 with the head), else 1. A token delete of an entry no longer held is refused. The store applies policy: caps, deposit budget, rate limits on deletes and signals (`delete`, `schedule_delete`, `signal` return codes); an identical re-upload changes nothing and logs nothing.
- Sync: with a log cursor, the log after it; without one, a replay of the live entries in blob ID order paged by a replay cursor `[BLAKE3("osis v1 replay" || log_id)[..16], first 8 bytes of the last ID]`, the last page returning the log cursor taken at the start (spec/wire.md §11.2); the connection remembers the start, so a replay continues only on its connection (elsewhere: Error 10). Two IDs sharing their first 8 bytes across a page boundary would skip the second (2^-64). Add events of the requester's gained IDs and of entries in that Sync are left out. A subscription starts at the connection's last complete Sync cursor for the label (else the log head), so a client that syncs before subscribing keeps the push cursors; pushes use the last Sync's inline limit.
- Client engine: `handle(now, ClientInput) -> Vec<ClientOutput>`; commands are batched under the caps and paged replies followed (Sync `more`, Path `more`, Fetch prefixes); a page without progress ends the exchange with `PeerError`. Policy stays with the node: a stale-key `Step` is reported, not walked; `Want`, `NeedReconcile` (Error 10, whose Sync entries are re-sent as an Upload, or over 4096 gained IDs) and `Reconciled { need, have }` are answered by the node with Upload, Reconcile, Fetch; after a reconciliation a cursor-less Sync at inline limit 0 gets a fresh cursor (metadata only).
- Not yet: one connection serving both sides (P2P member peers run a client and a server engine on one stream; requests and replies route by kind, ids are per direction).

## Why no recycle bin
A server-side bin (writers retire entries with a soft key, restore within a grace period) is not a permission boundary: a writer can already destroy irrecoverably everywhere by compacting with an empty snapshot, while members keep no bin; nothing ever lists the bin or restores from it, so it is a delayed delete; a retire carries no reason, so the client rule "re-upload what still changes state" undoes moderation retires. Retention per delta gives the three roles their deletion powers directly, "covered means redundant" gives the recovery a bin was for, and compaction needs no delay. Moderation is not deletion: a chat admin removes the participant, or the app hides the message with a chat-written marker (notes/chat.md).

## Limits (accepted)
- A removed writer keeps deriving tokens, but tokens alone delete nothing; its power ends when the sync key is re-registered, which every removal does. Until an admin steps, writers stamp and open with the keys of the epoch the server's head registers (they hold it: history boxes), and wrap under the newest they hold; a writer's rotation changes no delete key, so a label whose admins are all offline keeps its old step while content under it is already unreadable to the removed member.
- A removed admin holds the current delete key until re-registration and can win the race at a server by re-registering keys only it knows. Remedy: a replacement label (next index, keys from the rotated admin secret the removed admin lacks), O(entries). The index keeps a replacement's keys and ID apart from the old label's, and two admins replacing concurrently derive the same ID. Hostile admins are out of scope.
- An ex-writer or ex-admin keeps old-epoch tokens and, as a reader, the sync key, so it can delete its own old `author` bodies or old `admin` bodies at servers; healed by any member's next sync. Thing-write-secret tokens need the write key, so `writer` bodies are safe.
- A malicious current writer can wipe `writer`-purgeable bodies at a blind node; write access already lets it reset them everywhere.
- Server storage under `author` retention grows with superseded bodies of authors who have not synced since the snapshot, and departed authors' bodies stay until a thing admin cleans up (a removal is the natural moment).
- Relative keep bounds measure from the killing commit's `ts`, so a backdated kill shortens "at least D" by up to the drift cap.
- A member listed in no step since its last sync (a grant a rotation raced) is locked out of the label until a later step lists it or a member re-seals it (spec/requirements.md, Out of scope); the rotation would have left it without boxes anyway, and the SHOULD re-seal rule (a member without a box at a current epoch) repairs it at the next write. A member whose missed rotations were compacted (`MEMBERSHIP_KEEP` after they were superseded) is refused at the step whose set the server dropped and can be reached only through its inbox; its stranded heartbeat (spec/permissions.md §4) tells co-members. A walk costs one round trip per missed step. A device offline longer than `MEMBERSHIP_KEEP` on its person's home label is refused at the first dropped set and has no inbox of its own: it is re-sealed over a direct connection to a sibling device (pairing channel) or restored from the card; the official server may keep home-label sets longer by policy. A stranded member's heartbeat is a deposit under the deposit key it knows; if an admin refreshed the deposit seed since the member last read `/keys`, the heartbeat is refused and only a human-triggered re-seal reaches it, which is why the refresh is a MAY against observed abuse, not a routine SHOULD (issues/reseal-triggers.md). Re-seal soundness rests on established epochs (notes/permissions.md): within `MEMBERSHIP_KEEP` the departures travel in the epoch chain a re-sealer must hold; after compaction they travel in the roster snapshot and the removal commit separately from the `/secrets` snapshot, so a node whose view is incomplete (a server that never received the removal, an interrupted first sync) can box a removed member at a snapshot-established epoch by an eager rotation or a grant (re-seals wait for a complete pass and chain-established epochs). Healed by the next rotation of a node that knows the departure; accepted. Recovery and link keys claim the current step, so compaction and set retention never strand them; a replaced label keeps its membership commits and the replacement `/label` commit at honest servers, so only a key actor that knows no honest server is stranded (a removed admin squatting every server a card names).
- Anyone holding an actor's `/keys` can fill its inbox's deposit budget and delay grants and readers' own writes (spec/requirements.md, Untrusted nodes); an admin deletes junk, and a new deposit seed needs a new `/keys` and chain step. A read-only node's heartbeats are deposits too, bounded per reader by expiry (notes/ephemeral.md).
- A reader's invite grant, self-removal or node card sits deposited until a writer promotes it; co-readers read it meanwhile. **Budget is server policy**, not a format constant: clients never compute it, they see refusals and the remaining budget in the reply. The recommended minimum (64 + 4 per padded claim slot) is sized per reader *actor*, while deposits come per *device*: a plain group owned by a team has a claim set of one, and thirty reader devices exceed the minimum on heartbeats alone. Hence the client priority (certificates, membership writes and revokes first, heartbeats skipped when tight) and the heartbeat policy below; servers that host big read-only audiences raise the budget. Deposits are unlinkable by design, so per-reader limits are impossible. After a write-key rotation readers cannot relay old entries to a new server until a writer re-stamps them.

## What a blind node learns
One label per synced group, overlaps between labels (shared content blobs; certificate and inbox blobs share nothing), blob counts, padded sizes, which entries are chunk blobs, the number of token commitments (zero to three, which reveals the purgeable-by class), expiry times, arrival times, deletions and pending deletion times, which labels one connection opens (so: holds the current key of), the roster bucket of each step's claim set, which claim slots were used, when, and how many steps behind the claimant was (two late devices of one person use one slot), which entries were deposited and when (a grant or a reader-originated write), client addresses. Nesting only as far as overlap shows it. Not: AKs, tids, thing or aspect counts, authors, membership, which entries are projections or rewrites of one commit, retention bounds.
- Padding with Padmé costs at most about 12% under 256 B, 6% up to 64 KB, 3% above, 1–4% on average.
- Wrap overhead: about 25% on a minimal commit, under 5% on typical edits, none on chunks.

## Policy defaults (non-normative, tune freely)
- Compaction: a right holder compacts an aspect when superseded/live bodies pass a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot. A schema that wants no automatic compaction says keep at least forever.
- Heartbeats: under the home label and under labels with more than one reader actor; not under a thousand single-note labels. `/reach` excluded by default from labels shared with non-contacts.
- Deposit budget: 64 + 4 per claim slot entries, 32 KiB each, as the floor; more for labels whose steps show many claim slots.
- `INBOX_LIFETIME`: 90 days (format constant), matching `MEMBERSHIP_KEEP`.
- `TOMBSTONE_LIFETIME` 30 days.
- Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies membership commits first.
- Clients may batch uploads to blur timing.

## Rejected
- Owner actor as sync unit (above).
- State Merkle trees over aspects or the group hierarchy: expose shape and must follow a cyclic hierarchy.
- Home closure = everything the actor owns (complete backup by default): every thing would sit under its owner's home label beside any shared label. Owner chose explicit placement (spec/requirements.md, Offline and network).
- Unverifiable per-entry expiry and token metadata (first or latest upload wins).
- Soft retire, recycle bin, restore and a generation counter forcing concurrent uploaders to re-tag (above).
- Server-enforced keep-at-most (absolute bound in the clear prefix): the live remainder of a body may have no snapshot yet, so nodes that fetched before and after the bound would diverge for good; expiry has no such problem because the values die too. The timed delete gives the same effect for relative bounds without it.
- Leases (entries lapse unless refreshed): conflicts with immutable expiry and with a server being the only backup.
- Plain (unboxed) grants under a shared label: contradicts entitlement, since every reader of that label would read them.
- **Mailboxes** for rotation delivery (the design before claim keys): every actor named a mailbox label in `/keys`, key actors derived theirs from the seed, and every rotation deposited one boxed-twice projection per member (about 2.5 KB per member per rotated actor). Dropped because the laggard's recovery became a stored, budgeted side channel someone else had to feed: a key actor's mailbox had no writer to promote deposits, so an owner offline through enough rotations found the newest deliveries refused; clients needed a mailbox-first bootstrap across nesting levels; a device's mailbox was a stable per-device label at a server, so the server counted a person's devices for life; deposits made over one connection linked the recipients' mailboxes. Variants of claim keys also rejected: the registrar's own read key as the DH key with the member guessing among admins it knows (fails when the registrar's keyset changed since the member last synced); an ephemeral key served to anyone or in a public chain (every ex-member watches rotation cadence and roster bucket forever).
- A shared bootstrap label derived from the recovery seed: a stolen device could watch it forever for the person's device count and rotation timing; as a rendezvous for `/label` only, a mini mailbox (above).
- No gating against ex-members (reads under any sync key of the chain, writes under the current one): simplest, and download-before-upload closes most of the laggard-wrap content leak at servers, but not via relays or bundles, and ex-members watch label activity and harvest new ciphertext forever. Owner rejected.

## Implementation (osis-label)
- Modules: `blob` (prefix, frame/open, blob ID, `server_prefix`, prefix/header agreement `Prefix::agrees`, token match `Prefix::match_token`, `unwrap_any` newest first), `tree` (chunk trees: streaming `TreeWriter`/`TreeReader` over `TreeSink`/`LinkSource` (the reader is retry-safe: a `Missing` blob can be fetched and the call repeated), `HashSink` for shape and hashes without encryption; `BlobWriter`/`BlobReader` frame chunk, node, page and link-page blobs under a `Framing` (dedup secret, expiry, token secrets; `keeps(prefix)` is the re-encryption rule) and implement osis-crdt's `PageSink`/`PageSource` (`with_page_params` for tests); `Written { id, salt, token_hashes }` feeds the commit's chunk list; `Reuse::index` + `BlobWriter::reusing` dedup by reuse; `BlobSink`/`BlobFetch`, `BlobStore` (both), `MemoryBlobs`), `chunks` (large atomic values: `LargeParams`, `ValueWriter` (blob/string of declared length: inline at or below the threshold, else streamed into a tree; UTF-8 checked), `chunk_value` (set elements, map keys), `LargeReader` (canonical bytes, lazy, one chunk plus path in memory, rejects a chunked value at or below the threshold), `StringReader` (payload, `skip` for ranges), `read_value`), `step` (`Step`, `StepId`, `StepKeys`, `register` (genesis or child; claim set and entry boxes; a step without rotation passes the parent's keys), `verify_path`, `path_to`, `ClaimSet`, `open_entry_box`, `match_secret`, `genesis_label`), `auth` (`Proof`, `evaluate_open`, stamps, deposits, `PublishAuth`, `DeleteItem` with `key_for_level`), `inbox`, `signal`, `addr` (strict `address` values, text form, base64url), `labels` (`/label` records to verified steps), `link` (`ShareLink`, `RecoveryCard`), `bundle` (`BundleWriter`, `BundleReader`, `Importer` yielding `BundleEvent`s).
- `/label`, `address`, `step_record` and `box` codecs are osis-schema's core types; label re-exports them. osis-commit is a dependency only for the build order: the inbox payload carries the commit as its `CommitBlobPlaintext` value (module `inbox`), and prefix agreement takes header-derived `(level, token hash)` pairs and the expiry, so no commit type is used yet.
- Claim-set padding keys are public keys of random seeds (valid points), not random bytes: a server testing point validity would otherwise count the real keys. Static entries (hashes) stay distinguishable from points about half the time, which says only how many key actors read the label.
- Limits: prefix at most `MAX_COMMITMENTS`, expiry 0 means none (a `Some(0)` expiry is refused); blobs `MAX_BLOB`; tree nodes 1..=512 links, level 1..=48, root always interior (an empty value is one empty chunk); claim sets a power of two up to `MAX_CLAIMS`, every entry box key among the claims, boxes strict `box` values; steps, claim sets, inbox payloads and bundle frames decode with depth 512 and `MAX_MESSAGE` bytes; signals 64 KiB, value depth 64, kind an AK; links and cards 8 addresses, 4 peers, 4 relays, 256-byte URLs; bundle frames 1..=`MAX_MESSAGE`.
- Importer rules beyond the spec text: an entry must follow its blob in the bundle and a stamped entry its label's path (the writer emits them in that order); deletions pass through unverified like a peer's log events.
- The address text form `<url>#<base64url key>` is provisional and client-side only.

## Implementation (osis-server)
- `BackendStore<B: Backend>` implements osis-proto's `LabelStore` on osis-store's `Backend` directly (no `Store`: a blind node holds ciphertext and metadata it must see anyway; notes/architecture.md §2). Rows: label meta (log ID, head, counters), node totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts (bytes once per node in the blob area), sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions. One `WriteBatch` per mutation. Log ID = BLAKE3(instance seed || label)[..16], seed random per storage instance, so a wiped server invalidates old cursors.
- `sweep(now, budget)`: at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record), due timed deletes in time order (tombstone, Deleted record), tombstones after `TOMBSTONE_LIFETIME`, claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`). An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s. The log is trimmed to `log_keep` records in steps of 1/8; older cursors get Error 10 and reconcile.
- **Server policy** (`Policy`, all knobs in the config file): per label `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12 for new entries only); node-wide `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register Error 12 via `LabelStore::admit_label`, spec/wire.md §11.2); deposit budget `deposit_factor` (1) × the spec minimum; `claim_keep_ms` `MEMBERSHIP_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither less); `log_keep` 2^20; fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `replacements` 20 000, `deposits` 600, `signals` 1 200, plus `entry_replacements` 4 per entry (a deposited entry's promotion counts); connections: `max_connections` 10 000 (more are closed at accept), `hello_ms` 10 s (no Hello: closed), `max_queued_bytes` 32 MiB unread per connection (then dropped). Rate limits answer code 4; a limited signal is dropped. Counters are in memory (a restart resets them). Node byte totals count an entry's bytes once per label holding it.
- `Hub` (sans-I/O, tokio-free with `--no-default-features`): one `ServerConnection` per accepted connection, `Changed` to every connection and replicator, `Signal` to every other served connection; `tick(now)` runs the bounded sweep, Hello deadlines, replication work and timers; `next_due(now)`. The simulator can drive it directly.
- Replication (`Replicator`, push only): per dialed peer, a `ClientSession` walking each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record; deposits, deletions and pending times are not relayable (signatures not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with backoff 1-60 s. A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks, rare). Entries stamped under keys older than the peer's head get code 9 there (diagnostic only): writers re-stamp.
- Echo suppression: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry; a replicator does not send an entry to the peer key it came from, so mutual replication settles (one entry with two wraps ends with one replacement per side). It needs the dialing server to authenticate with its static key: the driver dials peers with `dial_as` and its listen secret (an ephemeral dial key would defeat it, and then only `entry_replacements` bounds wrap ping-pong).
- Driver (`driver::run(hub, Endpoint { transport, listener, secret }, peers, clock, control, log)`, tokio, feature `driver`, default; generic over `T: Transport`): sessions are osis-transport `link` sessions (notes/networking.md): `link::serve` turns every stream a dialer opens into a `Link` (peer key = the transport's), each a hub connection; hub task owns hub and store, its calls in `block_in_place` on a multi-thread runtime; reader task per link; writes into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); dial task per peer (`link::dial` with `dial_as`, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`); a connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s for the finish; ticks when due or every 60 s; `Control::{Tick, Shutdown}`. Tier-1 tests run it on `InProcess` under tokio (perfect network; not `Sched`: the driver spawns tokio tasks, and the sim drives sans-I/O engines, not drivers); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). Tier 2 (tests/quic.rs, ignored): two drivers on QUIC replicating, and the binary process serving a client.
- Binary `osis-server <config>` (feature `bin`, implies `quic`): required `listen` (`quic://host:port`), `key` (32-byte secret file, created 0600; a warning if others can read it); `data` (default `osis-server-data`, `server.redb` inside), repeatable `peer` (address text), policy knobs; logs to stderr, first `address <url>#<base64url key>` (the bound URL: a wildcard host must be replaced by the public one when handing it out); Ctrl-C shuts down (if signals cannot be watched it keeps running).

## Implementation (osis-node sync)
- `labeling/`: `actors` (reader actor = the thing with secrets of its own, else its owner, as node-core's body class; `secret_actor` up the owner chain; `may_read(x, t)`: `t`'s secrets derive from `x`'s, or `x` reads that actor on the timeline; `closure(g)` from node-core's `/groups` index; `group_labels` from `/label`), `blobs` (`Body` = one `osis_commit::project` class keyed by reader actor; `label_bodies(g)`: entitled projections of commits touching the closure, plus, on a home label, the `/label` and `/created` projections of labeled groups whose nearest labeled owner-chain actor it is; `seal_body`, `open_commit` (prefix vs header, spec/commits.md §4); `wrap_secret` with the rotation exception (the commit's `/keys` delta writes a read keyset of the label's secret actor: newest held epoch it supersedes); `head_keys` (sync key from any held secret, write/delete only established, deposit key from the actor's seed); `tokens_for` over every held epoch), `certs` (`certificates(g)`: node card commits and perm's chain certificates as (commit, aspect indexes); `partial_bodies`; step readers from `/secrets` box holders and the owner: nodes and actors by the X25519 half of their (read) KEM key, other key actors by static entry with a sealed entry box; `new_step`, `create_label`), `converge` (the pure rule: `classify(Facts) -> Hold`, `may_delete(why, live, carried)`).
- `sync/`: `SyncEngine::handle(Event) -> Vec<Action>`; `Event::{Tick, Local, Up, Bytes, Down}`, `Action::{Dial, Send, Close, Wake}`. One `ClientSession` per server connection (an ephemeral transport key: the driver dials without `dial_as`); the servers are the union of the synced labels' server lists, `SyncConfig.servers` and inbox hints. State in local records under `y/` (`sync/state.rs`): entries per (label, blob) with wrap, stamp, certificate flag and what the blob is (`Kind::{Unknown, Commit{commit, parts}, Inbox}`), presence per (server, label, blob) (no gained-ID lists: an upload goes to each server lacking the entry), cursors and heads per (server, label), blob keys of commit blobs (`by_commit`: an encryption is reused under other labels, a certificate never), certificates placed, heartbeat times, server tombstones (a fresh encryption next time), timed deletes sent, label hints from inbox blobs. One write batch per `handle`.
- Open (`sync/open.rs`): tries in order the known head's sync key, the recorded steps deepest first by sync key, then by claim key (the node's own X25519 and the read-role KEM X25519 of every held read epoch of the actors it holds; filtered by a recorded claim set). `Step` replies are verified under the step tried and recorded in `/label` by admins; a head not in `/label` is checked against the server's path. Code 13 registers the recorded path (deepest branch). No key left after a claim: stranded heartbeat.
- Pass (`sync/pass.rs`), after the log was read to its end (`Synced`) and on every later change: head keys recomputed; no read epoch of the head held: stranded heartbeat, nothing else; an admin with a newer established epoch uploads the secret actor's membership commits the server lacks under the head's keys and registers a child (the rest after `Registered`); then must-hold bodies (before keep-at-least, or not covered by a snapshot entry of the label), membership first, uploaded stamped, relayed with their stamp by readers, deposited when a non-writer's own membership write; chunk/page/list blobs of uploaded commits with filler wraps; this node's certificates and node card once per label (fresh encryption), a heartbeat per `HEARTBEAT_MIN_INTERVAL`; writers promote deposited entries (never `/seen`); deletions of must-not-hold entries present there (delete key, else a token under an established key), carriers first (a later snapshot entry of the aspect at that server; else `snapshot_first` when the node may write), timed deletes at a relative keep-at-most bound; expired entries are forgotten, never deleted.
- Not judged (left alone): entries not opened (chunks, newer epochs), commits not applied, membership-class commits and node-card/heartbeat commits outside the closure (others' certificates), projections that are a subset of a desired one (the superset goes up first), deltas this node does not hold.
- Inbound (`sync/inbound.rs`): blobs stored by ID; unwrap with the group's held read secrets newest first, else an inbox blob for an actor whose `/keys` inbox is the label (read KEM of each held read epoch); commit plaintexts ingested membership first; unopened entries retried while new secrets arrive; commit blobs announced without bytes fetched at once, the blobs a waiting commit's header lists fetched before apply, the rest lazily (`fetch`, `fetch_missing`). Signals: opened, the sender node's signature and write role on the thing at its `ts` checked, targeted ones for others dropped, engine `Event::Signal` fired.
- App and flows requests (`sync/local.rs`): `create_label`, `replace_label`, `signal`, `compact` (snapshot, drop covered bodies this node may purge past keep-at-least; deletions follow once the snapshot is at the server), `place_certificate(g, commit, aspects)`, `deliver_inbox(recipient, commit, aspects)` (deposited at each inbox server on the next connection), `complete_pass(actor)`, `sync_now`, `export_bundle`/`import_bundle`.
- Driver (`sync/driver.rs`, feature `driver`, default): `run(sync, transport, clock, control, log)`; per `Dial` a task `link::dial`s and forwards bytes; `Control::{Local, Tick, Call(f), Shutdown}`; engine calls under `block_in_place`. Tests: tier 1 on `InProcess` against osis-server's driver, tier 2 (ignored, feature `quic`) on localhost QUIC.
- Simulator hook: construct `SyncEngine::new(engine, raw clock, rng, cfg)`, feed `Event`s (`Up` on a `Dial`, `Bytes` from the server's `Hub`, `Tick` at `Wake`), carry `Send` bytes to `Hub::input`; `is_idle`, `describe`, `take_diagnostics`, `entries(label)` for invariants. tests/net/mod.rs is a minimal version of that driver.

## Open
- Server abuse limits: deferred until a real problem (owner). Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-label rate limits on deletes, wrap replacements, deposits and signals, admin delete; anyone may register a label up to the node-wide label cap (then Error 12, so squatters can exhaust it), and any writer can fill a label's cap with junk the server cannot tell from data. Per-member limits would need pseudonymous member keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one server bound to (server, label), never into the relayed `/label` chain.
- Claim sets in `/label`: 32 B per padded reader per step plus entry boxes, droppable `MEMBERSHIP_KEEP` after the step is superseded (steps are a map keyed by step ID so the drop is a field write); a server registered from a trimmed chain serves no claims at the trimmed steps. A dropped set does strand a member whose next rotation is still readable (it cannot walk past the step); the stranded heartbeat on a refused claim is what reaches it (issues/reseal-triggers.md). `/label` growth is about 250 B per step per group per rotation; if it ever matters, a root step carrying the current keys signed by the genesis delete key would let old steps be dropped.
- Partial restore from blind nodes: `/label` writes of owned groups now go under the owner's home label (a table of contents of labels); content of a subgroup is restorable alone only when it has its own label.
- Upload batching; log retention horizon per node (beyond it peers fall back to range reconciliation).

# Sync: blob reconciliation, blind nodes, compaction
> Summary: One protocol for all nodes: per-label cursor logs with range reconciliation as fallback, over encrypted commit/chunk blobs with per-blob keys wrapped per label; blind (keyless) nodes store and serve without seeing AKs, tids, values or structure; generations and retire lists for compaction and deletion; delete tokens for hard delete; subscriptions push entries and relay signals; `/label` holds label IDs, registration chains and servers, home labels hold nothing implicitly. Goals decided 2026-10-09, mechanism 2026-10-11, blind-node authorization 2026-10-12, subscriptions/signals/expiry 2026-10-15.

## Goals (owner 2026-10-09)
- Untrusted always-on nodes (backup servers) exist and sync efficiently.
- They learn no AKs, tids, value or thing sizes, thing/aspect counts, authorship or membership. Overlap between groups synced to the same server is an acceptable leak; it partly reveals nesting, since a nested group's blobs are a subset of its parent's.
- One protocol for every node. Trusted peers and blind nodes differ only in which keys they hold.

## Model
- **Blob**: an encrypted commit (header, signature and unpurged deltas) or an encrypted chunk of a large body. ID = BLAKE3 of the ciphertext. Indistinguishable to a keyless node. Each blob has its own random key, so a commit has one ID regardless of which groups contain it (owner 2026-10-11); a chunk's key is stored in its parent link, and dedup is by reuse from the current tree (notes/local-store.md).
- **Wrap**: the blob key encrypted under the read secret of a label, 49 bytes (suite byte, key, tag; nonce derived from the blob ID; notes/crypto.md). One per (label, blob), stored as label-entry metadata beside the ID. Anyone who can decrypt the blob and holds a label's read secret can add a wrap, so sharing history never re-encrypts. Overhead: about 25% on a minimal 200-byte commit, under 5% on typical edits, nothing on chunks; compaction drops retired wraps.
- One blob per commit (owner 2026-10-11): atomicity over partial efficiency. A node syncing some but not all things a commit touches downloads the whole commit. Purging one delta rewrites the blob without it (same commit ID, new blob ID). A commit may touch things of any owners and reader sets (owner 2026-10-16); since every reader of a label holding a blob decrypts all of it, a commit spanning reader sets is uploaded as projections (Projection, below). Membership-class writes get their own commits (notes/permissions.md).
- Every node holds a set of blobs. A node with keys decrypts commits and joins deltas into local aspect states. State is local only.
- **Sync unit = group** (notes/data-model.md). "Blobs of G" = commits touching any thing in G's transitive closure, plus the chunks they reference. Each member computes this from its own data: commits are tagged with their things' `/groups` on arrival and retagged when membership changes. Fixpoint, so cycles need nothing special; nesting depth affects only retagging cost.
- **Label**: a group that is synced has a label, a stable random ID registered at the peer with three public keys (Authorization, below). Keys derive from the group thing's role secrets: explicit ones if it has members of its own, else the ones derived from its owner's secrets by tid (notes/crypto.md); never the owner's secrets directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the blind node (review 2026-10-16). A label holds every blob of every descendant group; that is what makes a parent label a complete backup.
- **Labeling** (2026-10-11, entitlement rule 2026-10-15): an uploader puts a blob under the label of every group in its things' `/groups` for which it holds the read secret *and* whose actor may read the thing (the group thing by owner chain or an edge on the thing; for a group without own secrets, its owner). Group membership alone grants nothing; a group used as a shared label is a read member of its contents (notes/permissions.md). A wrap per label; the server creates labels it does not know. When a thing's group membership changes, its live blobs are added under the new label and retired under the old (retire is per label; the blob survives by refcount). Retag rule (2026-10-16): any member adds under the new label eagerly (upload is a reader right); only writers can retire, so stale entries under the old label leave at that label's next compaction. Harmless meanwhile: the old label's readers already held those blobs. An uploader also puts the membership commits proving its own author chain under every label it uploads to, and members add wraps for revokes, hand-over records and attestations about authors seen under a label; one wrap per blob, once per (node, label) (notes/permissions.md). The entitlement check is cached per (thing, label) and invalidated by membership changes of the label actor, the thing's edges or its owner chain. **Projection** (2026-10-16): a blob goes under a label only if the label's actor may read every delta in it. The author uploads a commit spanning reader sets as one blob per distinct readable subset, each holding the deltas that subset's readers may read, all with the same signed header and commit ID; uploaders do the same when history is shared later or edges change, by the partial-purge mechanism. Every projection verifies alone (the header carries every delta hash). **Atomic apply**: a node applies a commit only once it holds every delta of it that it may read and syncs the thing of; purged or expired deltas count as held. Until then the commit is pending, like one whose author chain has not arrived; nothing else waits on it. A node that starts syncing another thing later joins that thing's deltas then. Not taken: per-delta keys wrapped per label (a wrap per delta per label plus header redaction).
- **Protocol** (2026-10-11): every node keeps a per-label append log of entries it received, with sequence numbers. A client stores a cursor per (peer, label) and sends "since cursor" plus the IDs it has gained under that label from any source since then; the peer answers with the entries and blobs after the cursor minus those IDs, and takes the client's new blobs. One round trip each way, blobs inline with their wraps. Fallback when a cursor is missing or invalid (first contact, log truncated, peer reset): range-based set reconciliation over blob IDs within the live generation (Negentropy / Willow RBSR style), log(n) rounds. A connection may sync many labels. Blind nodes see arrival order anyway, so the log leaks nothing new.
- **Blind node**: knows a label as a flat set of (blob ID, wrap or a random 49-byte filler for chunk blobs whose key travels in a link, generation, delete token hashes, optional expiry time) entries. Same blob under two labels = one transfer, one stored copy, two entries; that is the overlap leak.
- **Partial trusted peers**: each reconciles with its current view; newly received group data may grow the closure, so repeat until a pass has no diff. Closure only grows within a session, so this terminates; extra rounds are bounded by nesting depth.
- The receiver keeps blobs a peer puts in G even if its own closure disagrees (checked after decrypt when it can); stale extras leave at compaction.
- Atomic application: a commit applies once its blob is present and its deltas are decrypted; chunks of large values may be fetched lazily (links carry the keys), by local policy.
- Partial restore from a blind node requires the subgroup to be synced to it under its own label, since blind nodes cannot filter. Possible later: an encrypted table-of-contents blob.
- Rejected sync unit: owner actor. Dedups perfectly but forces a new actor (a hand-over) for every separately syncable subset; groups are free and overlapping. Also dropped (2026-10-09): state Merkle trees over aspects or the group hierarchy (expose shape, must follow a cyclic hierarchy).

## Compaction, deletion, generations
- Per label, a generation counter; every entry carries the generation it was uploaded in. Reconciliation runs only within the live generation, and a node rejects uploads tagged below it, so retired blobs cannot resurrect from a stale peer. No tombstone set is needed.
- Compact (2026-10-11): a member uploads snapshot commits (full aspect states as deltas) tagged with generation N+1, then signs "retire [ids]" naming the blobs the snapshots supersede. Blobs not named carry over implicitly. Cost proportional to churn, not group size. Concurrent compactions are harmless: snapshots join. A snapshot delta carries, per author node, the dot frontier it covers for that aspect, so a node that never saw the retired commits closes its received-dot ranges (set tombstone GC, backfill rule) and learns the author table (review 2026-10-16; spec/crdt.md §8). Snapshots carry writes of expiring commits value-less and never retire those commits. Snapshots always carry `/created`, which anyone may carry since it is checked by hash. A chunk entry is retired only if no retained version under that label still links to it; reused chunks are shared between versions. Membership-class commits retire only through a roster snapshot of their thing by its owner chain, once it is older than the receipt horizon (notes/permissions.md, Roster snapshots); `/handover` records never; their `/secrets` and `/keys` deltas may also be dropped by the partial-purge rewrite. Attestations retire as content snapshots supersede the commits they cover.
- A returning member holding retired or generation-N commits re-tags into the live generation only those whose join still changes state; if a snapshot missed something, resurrecting it is correct.
- Blind nodes keep soft-retired blobs for the grace period (recycle bin). Members holding state can always re-upload live content as snapshots, so wipes lose history, not state, while any member remains.
- Retention class decides when bodies go (notes/crdt-sync.md): `purge` means the resetting node retires the old bodies right away, uploading a snapshot of surviving live content in the same sync; `undefined` at the next compaction; `preserve` only on explicit purge. A commit with mixed-class deltas is rewritten without the droppable ones, like a partial purge. Read-key rotation is a membership matter, not a deletion one: it happens on member removal, lazily, for new content.
- Nodes must always be able to serve current state, from bodies or a snapshot.
- Generations apply between trusted peers too; same protocol.
- Default compaction policy for `undefined` (direction 2026-10-12, tune freely): a writer compacts a label when the ratio of superseded to live bodies passes a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot at once. A node may drop a body locally by policy but keeps the blob ID in its label set so reconciliation does not re-offer it; it then cannot serve that blob. Only a retire removes an entry from the label.

## Authorization at blind nodes (2026-10-11, amended 2026-10-12)
Threat (owner): a blind node may be someone's only backup. Read access must not allow deletion or forced re-upload; write access should not casually wipe a group either.
- A label has three keys, one per role: upload (readers and up), soft-retire (writers and up), hard-delete (admins). Derived by KDF from the group thing's role secrets, so nothing extra is stored; the label is registered with its three public keys by a hard-delete-signed message, which also rotates them. Registrations form a chain (sequence number, each signed by the previous hard-delete key, step 0 by its own), stored on the group thing (`/label`, Label discovery below) and relayed by any member, so a server the admin never contacts, or one that missed a step, gets the chain from whoever uploads first (review 2026-10-16). These are shared role keys for label operations, distinct from the node signatures that authenticate commits.
- Scope: rights at a label are rights on the group thing. Example: my notes folder G is one label; I share note N by writing "friend: write" on N and making N (or a group thing holding everything I share with that friend, made a read member of each) a label with its own secrets wrapped to the friend. N's blobs sit under both labels with a wrap each. The friend can upload and soft-retire under the shared label and touch nothing under G.
- Retire and hard delete remove a blob from one label. The blob is physically deleted when no label references it (refcount).
- Upload adds a blob under the label. Readers need it to relay blobs they received from trusted peers (the briefly-online pattern). A blind node cannot tell a real commit from junk, so a reader could upload junk; members discard it at signature check and admins hard-delete it. Servers cap storage per label.
- Soft retire moves a blob into a recycle bin for a grace period set per label by admins (default 30 days, 2026-10-12; `purge`-class content never waits on it). Recoverable by any writer within the period. Used by compaction and `undefined`/`preserve` retention.
- Hard delete removes immediately, including from the bin. Admins hold the label key. In addition every entry carries a 16-byte **delete token hash**; a request carrying the token preimage *and* a signature under the label's current soft-retire key hard-deletes that one entry (two-factor, 2026-10-12). Token = `kdf("delete token", secret, chunk blob ID)` for each chunk the delta created, and `kdf("delete token", secret, salt)` for the commit blob itself, with a random 16-byte salt in the header: the commit token cannot depend on its own blob ID, since the hash sits in the header inside the ciphertext, and a purge rewrite or projection changes the blob ID but not the header (fixed 2026-10-16, was blob-ID-based). The commit carries a short list of token hashes (format cap, one hash per distinct secret), all over the same salt: one from the write secret of the actor directly above the author node in its chain (only the author's own devices derive it), plus one from the write secret (derived or explicit) of each thing a `purge`-class delta touches, so any current writer of such a thing finishes an ephemeral reset at once and a commit may span owners and reader sets regardless of class (2026-10-16; replaces splitting such commits). Any matching preimage with the signature deletes the entry. The hashes travel in the commit header (reused chunks copy theirs from the commit they came from); uploaders copy them into entry metadata, first upload wins. The server learns only the list length, almost always one: not authorship, not retention class. Refinement if a blob under several labels should be purgeable by each group's writers: random token wrapped inside the body to each writer role (about 32 bytes per wrap).
- A purge at blind nodes runs like a compaction: generation bump plus retire list, so stale peers cannot re-upload, then token-plus-signature or admin-key deletion of the retired entries from the bin. Any current writer holding the token may present it when it sees the purge, so the author's devices (or, for `purge`-class content, any writer) finish another writer's reset on their next sync.
- Limits: a removed writer keeps deriving tokens, but tokens alone delete nothing; the power ends when the label's soft-retire key rotates. Rule: re-register label keys eagerly on any member, device removal or hand-over, not lazily with content re-encryption. Re-registration is signed by the current hard-delete key, so only an admin node can issue it; the signed message is relayable by any member like a blob so it reaches servers the admin never contacts (2026-10-15). A removed admin also holds the current hard-delete key until then and can win the race by re-registering with keys only it knows, hijacking the label at that server; remedy is a new label ID under fresh keys, O(entries) since the blobs are already there. Hostile admins are out of scope; noted so nobody expects eager re-registration to cover it. A malicious reader uploading first with a wrong hash makes that entry un-purgeable by token at that server until an admin hard-deletes it or the bin expires it; no worse than withholding the relay. A malicious current writer can wipe current `purge`-class bodies at a blind node; write access already lets it reset that content everywhere under purge semantics. Preserved content keeps grace-period recovery, since non-authors can only soft-retire it.
- Scope of a writer's soft retire is the whole label, because the blind node sees no finer structure; history there is recoverable only for the grace period.
- Rule of thumb: per-entry rights are capabilities whose preimage is distributed client-side; label-wide rights are role keys; revocation rides on the role keys. Nothing stored at the server states a reason.
- Mixed-owner labels (chat pattern, notes/permissions.md): participants read the chat actor, so they upload under the chat label but cannot retire; chat admins can soft-retire everyone's messages there. Each participant's own label keeps their copies safe.
- A blind node may rate-limit soft retires per label per day as a heuristic against wipes; not a correctness mechanism.

## Label discovery and home labels (2026-10-16; home closure decided by owner)
- `/label` on the group thing: `map<label id, { chain: list<step>, servers: list<address> }>`. Membership-class (notes/permissions.md), so it is admin-written, compacted only by roster snapshots, and may sit under extra labels. A step = (label id, seq, three Ed25519 public keys, optional account token for the server (plans/protocol-spec.md item 10), signature under "osis v1 label register" by the previous step's hard-delete key; step 0 by its own). Steps are deterministic from the secret history (Ed25519 is deterministic), so any admin can regenerate the chain; stored anyway so readers can relay it. Label ID: 16 random bytes, allocated with the first step.
- Server rules: a server that does not know a label takes the first step it sees as genesis (first upload wins, like every entry); a server holding seq k rejects an upload under newer keys with "have k" and the client sends k+1 onward; equal seq with different keys is rejected. The ex-admin race at a fresh server is the hijack already accepted above; a chain neither prevents nor worsens it. One step per label per rotation: a group without own secrets gets a step whenever its owner rotates (constraints tension 13).
- **Home label**: an actor's home label is the one whose group is the actor thing itself, allocated when the thing gets explicit secrets. Nodes have none: their card already rides under every label they track. A link's K label is K's home label. **No implicit backup (owner 2026-10-16)**: the home closure is the actor thing plus what its `/group` lists, nothing an actor owns is included by owning it. A thing in no labeled group is local-only; apps put things into labeled groups explicitly, as they write edges explicitly for sharing. Rejected: home closure = everything the actor owns (a complete backup by default, at the cost of every thing sitting under its owner's home label beside any shared label).
- Discovery: the target's current `/label` commit travels with every grant, like `/keys` commits travel with certificates (notes/permissions.md), so a grantee learns the label IDs, chains and servers with the secrets. A device learns further labels by walking the `/label` aspects of the group things it holds; the grant itself reaches a new device over a direct connection (pairing) or a link redeem (K's label is in the link). Servers: written by admins, default the official server; a client also remembers servers it used.

## What a blind node learns
One label per group synced to it, overlaps between them, blob count, padded blob sizes, which entries are chunk blobs (size, filler instead of a wrap), fixed-size opaque wraps and token hashes (and how many token hashes an entry has, usually one), expiry times, arrival times (clients may batch uploads), generation numbers and retire events, client addresses. Nesting only as far as overlap shows it (a child label's blobs inside its parent's). Not: AKs, tids, thing or aspect counts, authors, membership.
- Sizes (2026-10-11, constraints tension 3): large values use content-defined chunking (notes/serialization.md). Volume may leak, so padding is coarse: every blob is padded with Padmé (keep the top ~log2 log2 L bits of the length): at most about 12% on blobs under 256 B, 6% up to 64 KB, 3% above, about 1-4% on average. Key epoch after a rotation: readers try the live keys they hold rather than a cleartext epoch byte (decided 2026-10-16, notes/crypto.md).

## Subscriptions and signals (2026-10-15, notes/ephemeral.md)
- A connection may subscribe to labels. The peer then pushes new log entries (with blobs and wraps) as they arrive, same messages as a cursor reply, unsolicited.
- A signal is an encrypted, signed envelope published under a label (upload key, like a blob). The receiving node forwards it to its other subscribers of that label and stores nothing; never in the log, never reconciled. Clients do not re-forward. Blind nodes learn the same as for a blob: label, size, arrival time.
- Expiry: an entry's expiry time is plaintext metadata; at that time the entry is deleted outright, no bin, no generation bump, and later uploads of it are refused.

## Interaction with permissions
- Receipt-time revocation rule: a blind node's receipt never counts, it is not a member. Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies membership commits and attestations first. Attestations retire only as content snapshots supersede what they cover (notes/permissions.md).
- A commit whose author chain has not arrived is held unverified until it does. A commit is valid only if its author is authorized on every thing it touches.

## Open
- Lazy chunk fetch for huge bodies a device does not want locally (local policy; reconciliation just reports the IDs it lacks).
- Encrypted table of contents for partial restore from blind nodes.
- Upload batching; log retention horizon at each node (beyond it, peers fall back to range reconciliation).
- Transport and discovery: notes/networking.md; crypto primitives and key formats: notes/crypto.md (both decided 2026-10-16).
- Download authorization at blind nodes (proposal, review 2026-10-16; owner to confirm): the upload key also authorizes downloads (both derive from the read secret, a separate download key gains nothing), re-registered eagerly like the others, so a revoked link or removed member stops fetching once keys rotate and strangers who learn a label ID cannot count blobs. Bootstrap: a new member cannot derive the key before it holds the read secret, which sits in a `/secrets` box under that very label; so a grant commit is also put under a label the grantee already reads: K's label for a link (the link carries it), the grantee actor's home or contact label otherwise (notes/crypto.md, contact label).
- Commit floor: a minimal commit is about 200 bytes of header fields, about 300 bytes once delta nonce, CBOR framing, AEAD tag and padding are counted (review 2026-10-16), plus a 49-byte wrap per label plus a 16-byte token hash. Fine for editing workloads; revisit only if huge commit volumes appear (owner 2026-10-11).

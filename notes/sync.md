# Sync: rationale
> Summary: Why spec/sync.md looks the way it does: blobs and labels, stamps and deposits, sync-key gating and claim keys, tokens and retention at blind nodes, convergence and compaction, why there is no recycle bin, accepted limits, what a blind node learns, policy defaults, rejected alternatives, open items.

The requirements behind this file: spec/requirements.md, Untrusted (blind) nodes and Deletion.

## Why
- **One commit ID, one blob per projection, random key per blob**: a commit has one ID whatever groups contain it. Sharing history means adding wraps, never re-encrypting.
- **No commit size limit**: a delta pages like a snapshot and the header's lists go by link, so atomicity never depends on size and the API never splits a write. The costs (a reader stores pages it cannot apply yet, a writer that dies mid-upload leaves orphan pages for convergence to delete, apply streams pages through one staged transaction) are the ones snapshots carry anyway. The old one-blob rule bought nothing but a second commit kind of edit (split, non-atomic) that every app had to reason about.
- **Groups as sync unit**: groups are free and overlap; owner actors as the unit would force a copy for every separately syncable subset.
- **Label keys derive from the group's own role secrets**, never the owner's directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the blind node. The deposit key derives from the actor's deposit seed (not from group secrets, so that a plain group's readers can derive it from the owner's `/keys`), hence it is keyed by label ID rather than by index: with the index alone every plain group of one owner registered the same deposit public key (found in the final pre-swarm review).
- **Entitlement, not group membership**, decides labeling: a thing dropped into a shared folder without an edge is silently not shared, which is the intended failure; an "add to shared folder" helper writes both. Cache the check per (thing, label), invalidated by membership changes of the label actor, the thing's edges or its owner chain.
- **Convergence as the one rule**: must-hold, may-hold, must-not-hold per body. Retag on join, cleanup on leave, compaction and repair after a bad deletion are all this rule. The may-hold class keeps a compactor's drop and a lagging member's re-upload from ping-ponging. A wrongful deletion is healed at the next member sync by a fresh encryption.
- **Projection** instead of per-delta keys wrapped per label (a wrap per delta per label plus header redaction). Every projection verifies alone since the header carries every delta hash. The projection key is (readable subset, retention class incl. expiry and token set): a commit mixing "last modified, keep-at-most 0" with "body, forever" would otherwise be rewritten on every replacement, and a per-commit expiry forced clients to split atomic writes that mix a disappearing message with a non-expiring counter.
- **Certificate blobs per label**: one blob across labels (a wrap each) would link every label a node syncs through its node card. Cost: a few small blobs per (node, label). They are outside the closure, so convergence names a label's required set as closure plus certificates; without that a group admin's convergence pass would delete them as "outside the closure" and the node would re-deposit forever.
- **Inbox blobs**: a non-member cannot wrap anything under a label it does not read (a granter is not a reader of the grantee's home label), so everything that must reach an actor from outside goes boxed to its read KEM key: grants, edge changes and removals (so it erases), re-seals, each with the label IDs and servers it needs (the old text said "the target's `/label` commit", which a non-member cannot wrap and which is a join of many commits anyway). They carry a delivery expiry so an unconsumed one frees the budget by itself, and the inbox is a label the recipient's admins administer so they can delete consumed ones. Direct grants to a node go by pairing only: a node is listed by DH key and cannot enter a label cold.
- **Self-certifying label IDs**: a random ID lets anyone who learned it (an ex-reader, a leaked `/label`) squat it at a fresh server under their own keys. Two admins creating a label concurrently derive the same ID.
- **Blob prefix**: expiry and token commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are salted per blob rather than being the header's token hashes, so projections and rewrites of one commit are unlinkable at the server.
- **Stamps** (read must not give upload): the author's signature sits inside the ciphertext, so the label write key is the only writer proof a blind node can check. Signing (label ID, blob ID, wrap) and storing the signature beside the wrap lets anyone relay a writer-vouched entry (LAN-first flows, server to server by push, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. Stamps are checked against the current step, so a removed writer's stamps die with the rotation its removal already does. Upload needs no open: an open added nothing (a current reader could replay a stale stamped blob after its tombstone either way, and a removed one only until the next step), and requiring it blocked blind-to-blind replication. Download does need one, so blind nodes replicate by push, never pull (an ex-member could otherwise run a "server" and pull). What a reader legitimately needs under a label goes by deposit: a provisional entry under a per-label budget, readable at once by co-readers, promoted by a writer's stamped re-upload, which frees the budget. Rejected: upload under the write key alone (loses relay); per-member upload keys (linkable; Open below).
- **Commit token salt in the header**: the commit's own blob ID does not exist when the header is built and changes on rewrite or projection.
- **Token plus label key** for deletion: the token proves the purge right as of the delta, the label key current membership. Thing-write-secret tokens need the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the rotation the demotion already does. Admin- and author-level tokens need only the sync key, because a thing's admin or author is often a mere reader of the label (anyone sharing a thing into a group they only read). Commitments carry a level byte so the server knows which signature a presented token needs (an imported `writer` delta has no author-chain token, so position alone would misfile its write token). Honest nodes enforce current write permission for every purge (spec/permissions.md §8); servers only this approximation (spec/requirements.md, Untrusted nodes).
- **Tokens follow retention**, one secret per level: the thing's admin secret for `admin`, plus the write secret above the author node (every device of the person holds it) for `author`, plus the thing's write secret for `writer`; none for `nobody`. Without an admin-level token a thing admin who is not an admin of the label's group could not delete at servers. Blobs are projected by token set as well as reader set, so a `nobody` delta is never deletable through a commit-mate's token. Under the shared-owner pattern `author` collapses to `writer`. Chunks carry their creating delta's tokens (16 bytes per chunk per secret in the header); a reused chunk whose thing-secret tokens differ from the reusing delta's is re-encrypted, else a writer could delete chunks of an `author` value or an author be unable to delete its own; author-chain tokens need not match, so dedup across editors survives. Residue: an author's explicit purge of a value cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- **Covered means redundant under join**, not "inside the snapshot's frontiers": a snapshot that omits content covers nothing it omits, so a bad snapshot is harmless and anyone can re-snapshot. It also absorbs the versioning rule that a node never compacts what it could not join.
- **Tombstones** refuse the identical blob for `TOMBSTONE_LIFETIME`, so a stale relay cannot resurrect a purged body. Members never need them: they sync before they upload, and a node holding the purge strips the value from any copy that arrives later. The lifetime is a storage-versus-churn dial: infinite is O(deletions) server storage; zero lets any relay or bundle from before the deletion put the ciphertext back until a member deletes it again. A peer staler than the log horizon returning later than the lifetime can resurrect, and members heal it. Blob IDs are hashes of ciphertext under random keys, so a tombstone is no fingerprint.
- **Timed delete**: a relative keep-at-most is honored with nobody online because the replacing writer schedules the server-side delete when it replaces, with its snapshot in the same sync. The server learns the deadline (owner: acceptable). Absolute bounds wait for a right holder (spec/requirements.md, Deletion); expiry is the only timer a blind node runs on its own. The earliest requested time wins, which is order-independent and matches "first death plus D".
- **Purge reaches snapshots**: a compactor's snapshot carries everyone's live values, so purging a write also makes it value-less in snapshot bodies and drops them; a writer that then holds no covering snapshot under a label re-snapshots there (deterministic trigger; duplicates are covered-equal and one gets dropped). Snapshots are `writer` so any writer can remove a stale snapshot at servers; they are redundant by construction, so that power costs only a re-upload.
- **Must-hold needs a positive "uncovered"**: a node that cannot join a body (parked) or has not fetched a snapshot's pages treats it as may-hold, never must-hold, or an old-version writer and a compactor would re-upload and delete forever. A strict-subset projection of a commit under a label (a writer whose timeline lagged uploaded less) is must-not-hold.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honor a MUST drop nor judge a purge request. A few bytes per delta.
- **Reads gated by the sync key**: without it an ex-member, or anyone who learned a label ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Owner: nothing is served under a superseded key, not even entries the holder could have fetched before. Rejected: a grace window after re-registration; "old key serves old entries" (no gating against ex-members); serving only rotation entries to old keys (every ex-member watches the roster size and rotation timing forever, and the flag is unverifiable). The price: a member that missed a rotation cannot download the commit carrying its new box, hence claim keys.
- **Claim keys** (decided with owner): a laggard and an ex-member hold the same shared keys, so the gate needs something only the laggard has, its own private key, and the registrar is the one party that knows the roster the step is for. So the step itself is the delivery: a fresh step key and one pseudonymous Ed25519 key per reader, derived by DH, and the laggard's recovery is a pure function of its private key and the chain the server stores anyway. Nobody delivers, drains or budgets anything. Why a signature and not a hash preimage: a dishonest server cannot replay it elsewhere. Why the step key is handed out one step at a time (a stale sync key or a claim on step j yields only step j+1): an ex-member removed at step k+1 learns that one step exists and nothing after it, no rotation count or timing, which is what a bare `stale` reply told it before; serving the current step to anyone would leak the cadence to every ex-member forever. The reply is the signed step, verified under the previous delete key, never a bare key: a server handing out a chosen step key could otherwise recognize a claimant by the pseudonym it signs with. The claim set is defined from the epoch's read boxes, not the registrar's roster: the registrar may hold the epoch without the removal commit and would otherwise list the member the rotation just removed, and boxes name the owner and plain-group readers the roster does not. Nested actors chain claims: node key on the person's home label, then the person's read key on each group label. The registrar derives M's key from the newest `/keys` it holds, so M tries old keysets as it does for boxes; a device M removed can claim until a registrar that saw M's new keyset issues a step (metadata only, M's boxes are under its new key), the same staleness class as the epoch-covers rule. Steps are not deterministic (random step key and padding), so two admins stepping concurrently produce different steps and servers that saw different ones first hold different branches for good: steps form a tree by `prev`, a server accepts only a child of its head, and the next rotation gets one child per branch (same role keys, different parent signature). `/label` holds the set of steps, so any admin can relay a server's branch; claim keys are bound to the step key rather than a sequence number, since a branch has no number of its own. A node that cannot match a server's head walks from the newest step it shares with it. Cost: 32 B per reader per step, about 3% on top of the rotation commit's boxes, which already leak the roster bucket through padded size; servers keep a step's set only until the rotations it leads to are compactable (`MEMBERSHIP_KEEP` after it was superseded); beyond that a walk would reach nothing readable anyway. The chain itself (role keys, step key, signature) stays, as before. The gate is classical like the Ed25519 open; a quantum ex-member could fetch hybrid-protected ciphertext. Grants still need a way in before the grantee holds any key of the target: the inbox blob, boxed to the grantee, deposited under the inbox its `/keys` names (an ordinary label its admins administer).
- **Rotation commits are wrapped under the epoch they supersede**: a rotation hands out the new read secret, so a wrap under it would be readable by the rotator alone (deliveries used to carry it boxed per member). Under the old wrap a laggard reads the rotations it missed in order, each under the one before. What an ex-member gains if a dishonest server or stray bundle hands it the blob: the box map of the rotation that removed it (tids and roles at the new epoch), never a secret; the removal edge and its frontier are a separate commit under the new epoch. Under a fork the rotator picks the newest superseded epoch; a member granted during the fork under the other branch only cannot open it and needs a re-grant (rare).
- **Re-seal** is the one recovery path for a member that holds the right private keys but cannot reach the current epoch: its missed rotations compacted (`MEMBERSHIP_KEEP` after a roster snapshot replaced them), its grant unknown to the rotator, a fork branch it never received. Nothing a co-member serves helps by itself (the wrap of every current commit is under the epoch it lacks, and a P2P peer serves wraps, not keys), so someone must seal the current secret to it: a membership commit carrying only its boxes, by anyone who may rotate (a sibling device of the same person is usually a writer, not an admin, of the group), delivered boxed as an inbox blob under its inbox or under the label itself, where the member opens by claim because the current step still lists it. Its own private keys never change, so a node stranded on its person's home label is re-sealed the same way; when the inbox is the very label it cannot open (a device offline past `MEMBERSHIP_KEEP`, below), a sibling device re-seals it over the pairing channel (a direct connection, same flow as pairing, same node identity), which is cheaper than a restore from the card. Nothing unattended re-seals (a PQ box per reader per step was rejected for size); the triggers are a current member seen without a box at a current epoch and the stranded heartbeat (spec/permissions.md §3, §4), both SHOULD, and a client may also offer it by hand.
- **Entry boxes and static entries** for recovery and link keys: a key actor entering cold holds no epoch to unwrap anything with, and the person actor's rotations get compacted eventually, so its box in `/secrets` is not reliably reachable. So the current step boxes the read secret to it (one hybrid box, 1.2 KB, on a home label per step; a 49-byte symmetric box on a link label; nothing elsewhere), and it claims the current step directly by a static entry, a hash of its signing key and the label ID, no walk and no old step needed. The registrar cannot do DH for it without a step private key it would have to keep, and a bare signing key in the set would tell the server a public identity; the hash tells it nothing until the key claims, which is rare. The entry is stable across steps, which only says that one slot is the owner's or the link's. A key actor granted after a label's step 0 is listed by a fresh step (an admin may step without rotating). Rejected: the read secret boxed to every reader (1.2 KB per reader per step, permanent, in `/label` and every roster snapshot; would spare laggards past compaction the re-grant); a seed-derived rendezvous label for the recovery key (a mini mailbox: unpromotable, floodable deposits); deriving the step key from the admin secret for determinism (an ex-admin plus a dishonest server could then identify late claimants from its tenure).
- Rule of thumb: per-entry rights are capabilities (tokens) whose preimage is distributed client-side; label-wide rights are role keys; revocation rides on role keys. Nothing stored at the server states a reason.

## Wire choices (spec/wire.md)
- The blob prefix is a fixed byte layout so a blind node parses it without a CBOR decoder; the AEAD binds it as AD so a reader cannot re-prefix a ciphertext (new expiry or commitments) under a fresh blob ID.
- Padmé length recovery: a `0x80` marker then zeros inside the ciphertext (ISO 7816-4 style). One byte, no length field, and canonical because the padded length must equal `padme(len + 1)`.
- Header lists, the token list, purge and origins go by link above `CHUNK_THRESHOLD` rather than being capped, since a commit has no size limit; only header-list chunk commitments needed a cap (issues/header-list-commitments.md).
- Range reconciliation: Negentropy-style additive fingerprints (sum of IDs mod 2^256 plus count, hashed) so a sorted ID index answers any range incrementally; 16-way splits, lists at 32 IDs, about log16(n/32) round trips. Rejected: hash of the concatenation (not incremental); Negentropy's full encoding (bound compression and timestamps, more rules for little gain).
- Protocol: request/reply by id over length-prefixed frames; both Hellos go out at once, so negotiation costs no round trip; per-entry status so a batch partly succeeds; a Status naming a stale key carries the head, so an uploader that never opened learns it.
- Opens bind the opened side's Hello challenge and static key (no replay elsewhere); stamps, deposits and deletes do not, so stamped entries and timed deletes stay relayable.

## Why no recycle bin
A server-side bin (writers retire entries with a soft key, restore within a grace period) is not a permission boundary: a writer can already destroy irrecoverably everywhere by compacting with an empty snapshot, while members keep no bin; nothing ever lists the bin or restores from it, so it is a delayed delete; a retire carries no reason, so the client rule "re-upload what still changes state" undoes moderation retires. Retention per delta gives the three roles their deletion powers directly, "covered means redundant" gives the recovery a bin was for, and compaction needs no delay. Moderation is not deletion: a chat admin removes the participant, or the app hides the message with a chat-written marker (notes/chat.md).

## Limits (accepted)
- A removed writer keeps deriving tokens, but tokens alone delete nothing; its power ends when the sync key is re-registered, which every removal does. Until an admin steps, writers stamp and open with the keys of the epoch the server's head registers (they hold it: history boxes), and wrap under the newest they hold; a writer's rotation changes no delete key, so a label whose admins are all offline keeps its old step while content under it is already unreadable to the removed member.
- A removed admin holds the current delete key until re-registration and can win the race at a server by re-registering keys only it knows. Remedy: a replacement label (next index, keys from the rotated admin secret the removed admin lacks), O(entries). The index keeps a replacement's keys and ID apart from the old label's, and two admins replacing concurrently derive the same ID. Hostile admins are out of scope.
- An ex-writer or ex-admin keeps old-epoch tokens and, as a reader, the sync key, so it can delete its own old `author` bodies or old `admin` bodies at servers; healed by any member's next sync. Thing-write-secret tokens need the write key, so `writer` bodies are safe.
- A malicious current writer can wipe `writer`-purgeable bodies at a blind node; write access already lets it reset them everywhere.
- Server storage under `author` retention grows with superseded bodies of authors who have not synced since the snapshot, and departed authors' bodies stay until a thing admin cleans up (a removal is the natural moment).
- Relative keep bounds measure from the killing commit's `ts`, so a backdated kill shortens "at least D" by up to the drift cap.
- A member listed in no step since its last sync (a grant a rotation raced) is locked out of the label until a later step lists it or a member re-seals it (spec/requirements.md, Out of scope); the rotation would have left it without boxes anyway, and the SHOULD re-seal rule (a member without a box at a current epoch) repairs it at the next write. A member whose missed rotations were compacted (`MEMBERSHIP_KEEP` after they were superseded) is refused at the step whose set the server dropped and can be reached only through its inbox; its stranded heartbeat (spec/permissions.md §4) tells co-members. A walk costs one round trip per missed step. A device offline longer than `MEMBERSHIP_KEEP` on its person's home label is refused at the first dropped set and has no inbox of its own: it is re-sealed over a direct connection to a sibling device (pairing channel) or restored from the card; the official server may keep home-label sets longer by policy. A stranded member's heartbeat is a deposit under the deposit key it knows; if the admin refreshed the deposit seed in the rotation that stranded it, the heartbeat is refused and only the other trigger (a current member seen without a box) reaches it. Recovery and link keys claim the current step, so compaction and set retention never strand them; a replaced label keeps its membership commits and the replacement `/label` commit at honest servers, so only a key actor that knows no honest server is stranded (a removed admin squatting every server a card names).
- Anyone holding an actor's `/keys` can fill its inbox's deposit budget and delay grants and readers' own writes (spec/requirements.md, Untrusted nodes); an admin deletes junk, and a new deposit seed needs a new `/keys` and chain step. A read-only node's heartbeats are deposits too, bounded per reader by expiry (notes/ephemeral.md).
- A reader's invite grant, self-removal or node card sits deposited until a writer promotes it; co-readers read it meanwhile. **Budget is server policy**, not a format constant: clients never compute it, they see refusals and the remaining budget in the reply. The recommended minimum (64 + 4 per padded claim slot) is sized per reader *actor*, while deposits come per *device*: a plain group owned by a team has a claim set of one, and thirty reader devices exceed the minimum on heartbeats alone. Hence the client priority (certificates, membership writes and revokes first, heartbeats skipped when tight) and the heartbeat policy below; servers that host big read-only audiences raise the budget. Deposits are unlinkable by design, so per-reader limits are impossible. After a write-key rotation readers cannot relay old entries to a new server until a writer re-stamps them.

## What a blind node learns
One label per synced group, overlaps between labels (shared content blobs; certificate and inbox blobs share nothing), blob counts, padded sizes, which entries are chunk blobs, the number of token commitments (zero to three, which reveals the purgeable-by class), expiry times, arrival times, deletions and pending deletion times, which labels one connection opens (so: holds the current key of), the roster bucket of each step's claim set, which claim slots were used, when, and how many steps behind the claimant was (two late devices of one person use one slot), which entries were deposited and when (a grant or a reader-originated write), client addresses. Nesting only as far as overlap shows it. Not: AKs, tids, thing or aspect counts, authors, membership, which entries are projections or rewrites of one commit, retention bounds.
- Padding with Padmé costs at most about 12% under 256 B, 6% up to 64 KB, 3% above, 1–4% on average.
- Wrap overhead: about 25% on a minimal commit, under 5% on typical edits, none on chunks.

## Policy defaults (non-normative, tune freely)
- Compaction: a right holder compacts an aspect when superseded/live bodies pass a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot. A schema that wants no automatic compaction says keep at least forever.
- Heartbeats: under the home label and under labels with more than one reader actor; not under a thousand single-note labels. `/reach` excluded by default from labels shared with non-contacts.
- Deposit budget: 64 + 4 per claim slot entries, 32 KiB each, as the floor; more for labels whose steps show many claim slots.
- `INBOX_LIFETIME`: 90 days (format constant), matching `MEMBERSHIP_KEEP`.
- `TOMBSTONE_LIFETIME` 30 days.
- Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies membership commits first.
- Clients may batch uploads to blur timing.

## Rejected
- Owner actor as sync unit (above).
- State Merkle trees over aspects or the group hierarchy: expose shape and must follow a cyclic hierarchy.
- Home closure = everything the actor owns (complete backup by default): every thing would sit under its owner's home label beside any shared label. Owner chose explicit placement (spec/requirements.md, Offline and network).
- Unverifiable per-entry expiry and token metadata (first or latest upload wins).
- Soft retire, recycle bin, restore and a generation counter forcing concurrent uploaders to re-tag (above).
- Server-enforced keep-at-most (absolute bound in the clear prefix): the live remainder of a body may have no snapshot yet, so nodes that fetched before and after the bound would diverge for good; expiry has no such problem because the values die too. The timed delete gives the same effect for relative bounds without it.
- Leases (entries lapse unless refreshed): conflicts with immutable expiry and with a server being the only backup.
- Plain (unboxed) grants under a shared label: contradicts entitlement, since every reader of that label would read them.
- **Mailboxes** for rotation delivery (the design before claim keys): every actor named a mailbox label in `/keys`, key actors derived theirs from the seed, and every rotation deposited one boxed-twice projection per member (about 2.5 KB per member per rotated actor). Dropped because the laggard's recovery became a stored, budgeted side channel someone else had to feed: a key actor's mailbox had no writer to promote deposits, so an owner offline through enough rotations found the newest deliveries refused; clients needed a mailbox-first bootstrap across nesting levels; a device's mailbox was a stable per-device label at a server, so the server counted a person's devices for life; deposits made over one connection linked the recipients' mailboxes. Variants of claim keys also rejected: the registrar's own read key as the DH key with the member guessing among admins it knows (fails when the registrar's keyset changed since the member last synced); an ephemeral key served to anyone or in a public chain (every ex-member watches rotation cadence and roster bucket forever).
- A shared bootstrap label derived from the recovery seed: a stolen device could watch it forever for the person's device count and rotation timing; as a rendezvous for `/label` only, a mini mailbox (above).
- No gating against ex-members (reads under any sync key of the chain, writes under the current one): simplest, and download-before-upload closes most of the laggard-wrap content leak at servers, but not via relays or bundles, and ex-members watch label activity and harvest new ciphertext forever. Owner rejected.

## Open
- Server abuse limits: deferred until a real problem (owner). Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-connection rate limits on deletes, wrap replacements and signals, admin delete; anyone may register a label, and any writer can fill a label's cap with junk the server cannot tell from data. Per-member limits would need pseudonymous member keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one server bound to (server, label), never into the relayed `/label` chain.
- Claim sets in `/label`: 32 B per padded reader per step plus entry boxes, droppable `MEMBERSHIP_KEEP` after the step is superseded (steps are a map keyed by step ID so the drop is a field write); a server registered from a trimmed chain serves no claims at the trimmed steps, which lead to nothing readable by then. `/label` growth is about 250 B per step per group per rotation; if it ever matters, a root step carrying the current keys signed by the genesis delete key would let old steps be dropped.
- Partial restore from blind nodes: `/label` writes of owned groups now go under the owner's home label (a table of contents of labels); content of a subgroup is restorable alone only when it has its own label.
- Upload batching; log retention horizon per node (beyond it peers fall back to range reconciliation).

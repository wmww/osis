# Sync: rationale
> Summary: Why spec/sync.md looks the way it does: blobs and labels, stamps and deposits, sync-key gating and mailboxes, tokens and retention at blind nodes, convergence and compaction, why there is no recycle bin, accepted limits, what a blind node learns, policy defaults, rejected alternatives, open items.

The requirements behind this file: spec/requirements.md, Untrusted (blind) nodes and Deletion.

## Why
- **One blob per commit, random key per blob**: a commit has one ID whatever groups contain it, and atomicity beats partial-fetch efficiency (tension 5). Sharing history means adding wraps, never re-encrypting.
- **Groups as sync unit**: groups are free and overlap; owner actors as the unit would force a copy for every separately syncable subset.
- **Label keys derive from the group's own role secrets**, never the owner's directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the blind node.
- **Entitlement, not group membership**, decides labeling: a thing dropped into a shared folder without an edge is silently not shared, which is the intended failure; an "add to shared folder" helper writes both. Cache the check per (thing, label), invalidated by membership changes of the label actor, the thing's edges or its owner chain.
- **Convergence as the one rule**: must-hold, may-hold, must-not-hold per body. Retag on join, cleanup on leave, compaction and repair after a bad deletion are all this rule. The may-hold class keeps a compactor's drop and a lagging member's re-upload from ping-ponging. A wrongful deletion is healed at the next member sync by a fresh encryption.
- **Projection** instead of per-delta keys wrapped per label (a wrap per delta per label plus header redaction). Every projection verifies alone since the header carries every delta hash.
- **Certificate blobs per label**: one blob across labels (a wrap each) would link every label a node syncs through its node card. Cost: a few small blobs per (node, label).
- **Self-certifying label IDs**: a random ID lets anyone who learned it (an ex-reader, a leaked `/label`) squat it at a fresh server under their own keys. Two admins creating a label concurrently derive the same ID.
- **Blob prefix**: expiry and token commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are salted per blob rather than being the header's token hashes, so projections and rewrites of one commit are unlinkable at the server.
- **Stamps** (read must not give upload): the author's signature sits inside the ciphertext, so the label write key is the only writer proof a blind node can check. Signing (label ID, blob ID, wrap) and storing the signature beside the wrap lets anyone relay a writer-vouched entry (LAN-first flows, server to server, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. Stamps are checked against the current step, so a removed writer's stamps die with the rotation its removal already does; uploads still need the label opened, or a removed reader could replay stale stamped blobs after their tombstones expire. What a reader legitimately needs under a label goes by deposit: a provisional entry under a per-label budget, readable at once by co-readers, promoted by a writer's stamped re-upload, which frees the budget. Rejected: upload under the write key alone (loses relay); per-member upload keys (linkable; Open below).
- **Commit token salt in the header**: the commit's own blob ID does not exist when the header is built and changes on rewrite or projection.
- **Token plus label key** for deletion: the token proves the purge right as of the delta, the label key current membership. Thing-write-secret tokens need the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the rotation the demotion already does. Admin- and author-level tokens need only the sync key, because a thing's admin or author is often a mere reader of the label (anyone sharing a thing into a group they only read). Honest nodes enforce current write permission for every purge (spec/permissions.md §8); servers only this approximation (tension 26).
- **Tokens follow retention**, one secret per level: the thing's admin secret for `admin`, plus the write secret above the author node (every device of the person holds it) for `author`, plus the thing's write secret for `writer`; none for `nobody`. Without an admin-level token a thing admin who is not an admin of the label's group could not delete at servers. Blobs are projected by token set as well as reader set, so a `nobody` delta is never deletable through a commit-mate's token. Under the shared-owner pattern `author` collapses to `writer`. Chunks carry their creating delta's tokens (16 bytes per chunk per secret in the header); a reused chunk whose thing-secret tokens differ from the reusing delta's is re-encrypted, else a writer could delete chunks of an `author` value or an author be unable to delete its own; author-chain tokens need not match, so dedup across editors survives. Residue: an author's explicit purge of a value cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- **Covered means redundant under join**, not "inside the snapshot's frontiers": a snapshot that omits content covers nothing it omits, so a bad snapshot is harmless and anyone can re-snapshot. It also absorbs the versioning rule that a node never compacts what it could not join.
- **Tombstones** refuse the identical blob for `TOMBSTONE_LIFETIME`, so a stale relay cannot resurrect a purged body. Members never need them: they sync before they upload, and a node holding the purge strips the value from any copy that arrives later. The lifetime is a storage-versus-churn dial: infinite is O(deletions) server storage; zero lets any relay or bundle from before the deletion put the ciphertext back until a member deletes it again. A peer staler than the log horizon returning later than the lifetime can resurrect, and members heal it. Blob IDs are hashes of ciphertext under random keys, so a tombstone is no fingerprint.
- **Timed delete**: a relative keep-at-most is honored with nobody online because the replacing writer schedules the server-side delete when it replaces, with its snapshot in the same sync. The server learns the deadline (owner: acceptable). Absolute bounds wait for a right holder (tension 25); expiry is the only timer a blind node runs on its own.
- **Purge reaches snapshots**: a compactor's snapshot carries everyone's live values, so purging a write also makes it value-less in snapshot bodies and drops them; a writer re-snapshots. Snapshots are `writer` so any writer can remove a stale snapshot at servers; they are redundant by construction, so that power costs only a re-upload.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honor a MUST drop nor judge a purge request. A few bytes per delta.
- **Reads gated by the sync key**: without it an ex-member, or anyone who learned a label ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Owner: nothing is served under a superseded key, not even entries the holder could have fetched before. Rejected: a grace window after re-registration; "old key serves old entries" (no gating against ex-members); serving only rotation entries to old keys (every ex-member watches the roster size and rotation timing forever, and the flag is unverifiable). The price: a member that missed a rotation cannot download the commit carrying its new box, hence mailboxes; the `stale` reply is its cue to read them.
- **Mailboxes**: every actor names in `/keys` a label and a deposit seed, so anyone who verified its chain, which is exactly who could need to deliver to it, can deposit there without reading it. A delivery is the rotation projected to the recipient's boxes and boxed once more to the recipient, so a mailbox shared with co-readers leaks nothing. Key actors derive their mailbox keys from their seed: a device's mailbox never rotates, is per device, and a removed device's simply stops receiving; the recovery key's mailbox is how a device holding the recovery card rejoins. Nested groups chain: device mailbox, then the person's home label, then each group's label. The deposit flag lets the recipient try to open only deposits, not every filler-wrapped chunk; the server knew which entries came by the deposit key anyway. Cost: about 2.5 KB per direct member per rotated actor, spread over the members' mailbox servers; proportional to rosters, roughly double the rotation commit itself.
- Rule of thumb: per-entry rights are capabilities (tokens) whose preimage is distributed client-side; label-wide rights are role keys; revocation rides on role keys. Nothing stored at the server states a reason.

## Why no recycle bin
A server-side bin (writers retire entries with a soft key, restore within a grace period) is not a permission boundary: a writer can already destroy irrecoverably everywhere by compacting with an empty snapshot, while members keep no bin; nothing ever lists the bin or restores from it, so it is a delayed delete; a retire carries no reason, so the client rule "re-upload what still changes state" undoes moderation retires. Retention per delta gives the three roles their deletion powers directly, "covered means redundant" gives the recovery a bin was for, and compaction needs no delay. Moderation is not deletion: a chat admin removes the participant, or the app hides the message with a chat-written marker (notes/permissions.md, Patterns).

## Limits (accepted)
- A removed writer keeps deriving tokens, but tokens alone delete nothing; its power ends when the sync key is re-registered, which every removal does.
- A removed admin holds the current delete key until re-registration and can win the race at a server by re-registering keys only it knows. Remedy: a replacement label (next index, keys from the rotated admin secret the removed admin lacks), O(entries). The index keeps a replacement's keys and ID apart from the old label's, and two admins replacing concurrently derive the same ID. Hostile admins are out of scope.
- An ex-writer or ex-admin keeps old-epoch tokens and, as a reader, the sync key, so it can delete its own old `author` bodies or old `admin` bodies at servers; healed by any member's next sync. Thing-write-secret tokens need the write key, so `writer` bodies are safe.
- A malicious current writer can wipe `writer`-purgeable bodies at a blind node; write access already lets it reset them everywhere.
- Server storage under `author` retention grows with superseded bodies of authors who have not synced since the snapshot, and departed authors' bodies stay until a thing admin cleans up (a removal is the natural moment).
- Relative keep bounds measure from the killing commit's `ts`, so a backdated kill shortens "at least D" by up to the drift cap.
- A member that missed a rotation is locked out of the label until some member delivers to its mailbox; liveness only, and P2P sync from an authenticated co-member bypasses it. A mailbox whose owner is offline long enough fills its deposit budget, after which deliveries are refused; the owner then drains it and needs a fresh delivery or a P2P sync (Open).
- Anyone holding an actor's `/keys` can fill its label's deposit budget and delay key delivery and readers' own writes (tension 17); an admin deletes junk, and a new deposit seed needs a new `/keys` and chain step. A read-only node's periodic node-card refresh is a deposit too.
- A reader's invite grant, self-removal or node card sits deposited until a writer promotes it; co-readers read it meanwhile. After a write-key rotation readers cannot relay old entries to a new server until a writer re-stamps them.
- A rotation's deposits made over one connection link the recipients' mailboxes at a server they share; clients may spread them over connections and time.

## What a blind node learns
One label per synced group, overlaps between labels (shared content blobs; certificate and delivery blobs share nothing), blob counts, padded sizes, which entries are chunk blobs, the number of token commitments (zero to three, which reveals the purgeable-by class), expiry times, arrival times, deletions and pending deletion times, which labels one connection opens (so: holds the current key of), which entries were deposited and when (a delivery, so rotation timing of some actor the mailbox owner belongs to, or a reader-originated write), client addresses. Nesting only as far as overlap shows it. Not: AKs, tids, thing or aspect counts, authors, membership, which entries are projections or rewrites of one commit, retention bounds.
- Padding with Padmé costs at most about 12% under 256 B, 6% up to 64 KB, 3% above, 1–4% on average.
- Wrap overhead: about 25% on a minimal commit, under 5% on typical edits, none on chunks.

## Policy defaults (non-normative, tune freely)
- Compaction: a right holder compacts an aspect when superseded/live bodies pass a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot. A schema that wants no automatic compaction says keep at least forever.
- `TOMBSTONE_LIFETIME` 30 days.
- Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies membership commits first.
- Clients may batch uploads to blur timing.

## Rejected
- Owner actor as sync unit (above).
- State Merkle trees over aspects or the group hierarchy: expose shape and must follow a cyclic hierarchy.
- Home closure = everything the actor owns (complete backup by default): every thing would sit under its owner's home label beside any shared label. Owner chose explicit placement (tension 16).
- Unverifiable per-entry expiry and token metadata (first or latest upload wins).
- Soft retire, recycle bin, restore and a generation counter forcing concurrent uploaders to re-tag (above).
- Server-enforced keep-at-most (absolute bound in the clear prefix): the live remainder of a body may have no snapshot yet, so nodes that fetched before and after the bound would diverge for good; expiry has no such problem because the values die too. The timed delete gives the same effect for relative bounds without it.
- Leases (entries lapse unless refreshed): conflicts with immutable expiry and with a server being the only backup.
- Plain (unboxed) deliveries under a shared label: contradicts entitlement, since every reader of that label would read them.
- A shared bootstrap label derived from the recovery seed for rotation delivery: a stolen device could watch it forever for the person's device count and rotation timing. The recovery key's own mailbox has no such watcher.

## Open
- Server abuse limits: deferred until a real problem (owner). Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-connection rate limits on deletes, wrap replacements and signals, admin delete; anyone may register a label, and any writer can fill a label's cap with junk the server cannot tell from data. Per-member limits would need pseudonymous member keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one server bound to (server, label), never into the relayed `/label` chain.
- Mailbox overflow: issues/mailbox-overflow.md.
- Encrypted table of contents for partial restore from blind nodes (today a subgroup needs its own label to be restorable alone).
- Upload batching; log retention horizon per node (beyond it peers fall back to range reconciliation).

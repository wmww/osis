# Sync: blob reconciliation, blind nodes, compaction
> Summary: One sync protocol for all nodes: per-label cursor logs with range reconciliation as fallback, over encrypted commit/chunk blobs with per-blob keys wrapped per label; blind (keyless) nodes store and serve without seeing AKs, tids, values or structure; generations and drop-list retires for compaction and deletion. Goals decided 2026-10-09, mechanism decided 2026-10-11; hard delete at blind nodes by delete token plus current writer signature or admin key, decided 2026-10-12; label subscriptions push entries and relay stored-nowhere signals, entries may carry an expiry, decided 2026-10-15.

## Goals (decided by owner 2026-10-09)
- Untrusted always-on nodes (backup servers) exist and sync efficiently.
- They learn no AKs, tids, value or thing sizes, thing/aspect counts, authorship, membership or nesting. Overlap between groups synced to the same server is an acceptable leak.
- One protocol for every node. Trusted peers and blind nodes differ only in which keys they hold. Replaces the state Merkle tree over the group hierarchy (see Dropped).
- Nothing in the earlier sync proposal is sacred; keep the plan as simple as possible while covering everything below.

## Model
- **Blob**: an encrypted commit (header, signature and its unpurged deltas inside the ciphertext) or an encrypted chunk of a large body. ID = BLAKE3 of the ciphertext. Indistinguishable to a keyless node. Encrypted under its own key, so a commit has one ID regardless of which groups contain it (decided by owner 2026-10-11). Every blob's key is random; a chunk's key is stored in its parent link, and dedup is by reuse from the current tree, so unchanged chunks keep their blob across edits and editors (notes/local-store.md).
- **Wrap**: the blob key encrypted under the read secret of a label, about 48 bytes (nonce derived from the blob ID). One per (label, blob), stored as label-entry metadata beside the ID, not inside the blob. Anyone who can decrypt the blob and holds a label's read secret can add a wrap, so sharing history never re-encrypts, and the wrap tells a holder of several keys which one opens a blob from a mixed-owner label. Overhead: about 20% on a minimal 200-byte commit, under 5% on typical edits, nothing on snapshots and chunks; compaction drops retired wraps. A commit touches things of one owner actor only.
- One blob per commit (decided by owner 2026-10-11): atomicity matters more than partial efficiency. A node syncing some but not all things a commit touches downloads the whole commit; most commits touch one thing, and multi-thing commits mostly go to nodes that want all of them. Purging one aspect rewrites the blob without that delta (same commit ID, new blob ID). Writer-chosen splitting of huge commits is a possible later optimization.
- Every node holds a set of blobs. A node with keys decrypts commits and joins deltas into local aspect states. State is local only: never synced, never hashed for sync.
- **Sync unit = group** (notes/data-model.md). "Blobs of G" = commits touching any thing in G's transitive closure, plus the chunks they reference. Each member computes this from its own data: commits are tagged with their things' `/groups` on arrival and retagged when group membership changes. Fixpoint, so cycles need nothing special; nesting depth does not affect sync cost, only retagging cost, which `/groups` already implies.
- **Protocol** (decided 2026-10-11): every node keeps a per-label append log of entries it received, with sequence numbers. A client stores a cursor per (peer, label) and sends "since cursor" plus the IDs it has gained under that label from any source since then; the peer answers with the entries and blobs after the cursor minus those IDs, and takes the client's new blobs. One round trip each way, blobs inline with their wraps. Nothing a side already holds is sent again, beyond the ID list, which is bounded by the client's own churn. Fallback when a cursor is missing or invalid (first contact, log truncated, peer reset): range-based set reconciliation over blob IDs within the live generation (Negentropy / Willow RBSR style), log(n) rounds. A connection may sync many labels. No other sync messages. Blind nodes see arrival order anyway, so the log leaks nothing new.
- **Labeling** (decided 2026-10-11): an uploader puts a blob under the label of every group in its things' `/groups` whose read secret it holds, with a wrap per label. The server creates labels it does not know. A group whose group thing the uploader cannot read gets no label from that uploader; known gap, no fix needed so far. When a thing's group membership changes, its live blobs are added under the new label and retired under the old (retire is per label; the blob survives by refcount). A label holds every blob of every descendant group; intended, that is what makes the parent label a complete backup. An uploader also puts the membership commits proving its own author chain under every label it uploads to, and members add wraps for revokes and statements about authors seen under a label; one wrap per blob, once per (node, label) (notes/permissions.md, Verifying writes).
- **Blind node**: knows a group only as an opaque label over a flat set of (blob ID, wrap, generation, delete token hash, optional expiry time) entries. At the expiry time the entry is deleted outright and later uploads of it refused (notes/ephemeral.md). Same blob under two labels = one transfer, one stored copy, two label entries; that is the overlap leak.
- **Partial trusted peers**: each reconciles with its current view; newly received group data may grow the closure, so repeat until a pass has no diff. Closure only grows within a session, so this terminates.
- The receiver keeps blobs a peer puts in G even if its own closure disagrees (checked after decrypt when it can); stale extras leave at compaction.
- **Mixed keys**: a node may hold keys for some owners in a group and not others. It is trusted for those blobs and blind for the rest, in one protocol. The chat pattern (notes/permissions.md) needs nothing extra.
- Partial restore from a blind node requires the subgroup to be synced to it under its own label, since blind nodes cannot filter. Possible later: an encrypted table-of-contents blob.
- Rejected sync unit: owner actor. Dedups perfectly but forces a new actor (a hand-over) for every separately syncable subset; groups are free and overlapping.

## Compaction, deletion, generations
- Per label, a generation counter; every entry carries the generation it was uploaded in. Reconciliation runs only within the live generation, and a node rejects uploads tagged below it, so retired blobs cannot resurrect from a stale peer. No tombstone set is needed.
- Compact (decided 2026-10-11): a member uploads snapshot commits (full aspect states as deltas) tagged with generation N+1, then signs "retire [ids]" naming the blobs the snapshots supersede. Blobs not named carry over to N+1 implicitly. Cost proportional to churn, not group size (a keep-list would cost 32 bytes per surviving blob). Concurrent compactions are harmless: snapshots join.
- A returning member holding retired or generation-N commits re-tags into the live generation only those whose join still changes state; if a snapshot missed something, resurrecting it is correct.
- Blind nodes keep soft-retired blobs for the grace period (recycle bin); see Authorization. Members holding state can always re-upload live content as snapshots, so wipes lose history, not state, while any member remains.
- Deletion follows the retention class (notes/crdt-sync.md): `purge` means the resetting node retires the old bodies at blind nodes right away (uploading a snapshot of any surviving live content in the same sync; one per edit, no batching); `undefined` means they go at the next compaction; `preserve` means only an explicit purge removes them. Read-key rotation is a membership matter, not a deletion one: it happens only on member removal, lazily, for new content; rotation does nothing for deletion against honest nodes and re-encrypting history would be O(group) (decided 2026-10-11).
- Nodes keep bodies per retention class; they must always be able to serve current state, from bodies or a snapshot.
- Generations apply between trusted peers too; same protocol.
- Default compaction policy for `undefined` retention (direction 2026-10-12, tune freely, nothing depends on it): a writer compacts a label when the ratio of superseded to live bodies passes a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot at once. Readers never drop bodies locally without a label retire; a local drop alone gets the blob re-offered on every fallback reconciliation.

## Authorization at blind nodes (proposal 2026-10-11, amended 2026-10-12, replaces single sync key)
Threat (owner): a blind node may be someone's only backup. Read access must not allow deletion or forced re-upload; write access should not casually wipe a group either.
- A label has three keys, one per role: upload (readers and up), soft-retire (writers and up), hard-delete (admins). Derived by KDF from the group thing's role secrets (notes/permissions.md: derived from its owner's by default, explicit once the group has members of its own), so nothing extra is stored; the label itself is a stable random ID registered with its three public keys by a hard-delete-signed message, which also rotates them.
- Scope: rights at a label are rights on the group thing. Example: my notes folder G (owned by me) is one label; I share note N by writing "friend: write" on N and making N (or a group thing holding everything I share with that friend) a label with its own secrets wrapped to the friend. N's blobs sit under both labels with a wrap each. The friend can upload and soft-retire under the shared label and touch nothing under G, including N's own entries there.
- Retire and hard delete remove a blob from one label. The blob is physically deleted when no label references it (refcount), so one label's deletion never affects another's data.
- Upload adds a blob under the label. Readers need it to relay blobs they received from trusted peers (the briefly-online pattern). A blind node cannot tell a real commit from junk, so a reader could upload junk that wastes server storage and one download per member; members discard it at signature check and admins hard-delete it. Servers cap storage per label.
- Soft retire removes a blob from the live set into a recycle bin for a grace period set per label by admins (default 30 days, decided 2026-10-12; ephemeral content never waits on it). Recoverable by any writer within the period. This is what compaction and `undefined`/`preserve` retention use.
- Hard delete removes immediately, including from the bin. Admins hold the label key. In addition every entry carries a 16-byte **delete token hash**; a request carrying the token preimage *and* a signature under the label's current soft-retire key hard-deletes that one entry (two-factor, decided 2026-10-12; author-or-admin purge rights, notes/permissions.md). The token proves the entry is the presenter's to purge, the signature proves current write membership; the retire message is signed anyway, so this costs nothing. Token = KDF(secret, blob ID) computed by the author of the delta that introduced the blob, for the commit itself and each chunk the delta created. Which secret depends on retention class: the author's person-actor secret normally, the owning group's writer role secret for `purge`-class deltas, so any current writer finishes an ephemeral reset at once (decided 2026-10-12, closes the lingering-window question). The hash travels in the commit header, one for the commit and one beside each chunk reference (reused chunks copy the hash from the commit they came from); readers copy it into entry metadata when uploading, first upload wins. The server sees identical hashes whatever the derivation and learns nothing: not authorship, not retention class, not why a presenter holds the token. Cost: 16 bytes per entry. Refinement if a blob under several labels should be purgeable by each group's writers: random token, hash in the header, token wrapped inside the encrypted body to each writer role (about 32 bytes per wrap).
- A purge at blind nodes runs like a compaction: generation bump plus retire list, so stale peers cannot re-upload, then token-plus-signature or admin-key deletion of the retired entries from the bin. Any current writer holding the token may present it when it sees the purge, so the author's devices (or, for ephemeral content, any writer) finish another writer's reset on their next sync.
- Limits: a revoked device or removed writer keeps deriving tokens, but tokens alone delete nothing; the power ends when the label's soft-retire key rotates, the same window in which it still holds the group read key. Rule: re-register label keys eagerly on any member or device removal, not lazily with content re-encryption. A malicious reader uploading first with a wrong hash can delete that one entry on that server, equivalent to not relaying it. A malicious current writer can wipe current `purge`-class bodies at a blind node; write access already lets it reset that content at every honest node under purge semantics, so no new power. Preserved content keeps grace-period recovery, since non-authors can only soft-retire it.
- Scope of a writer's soft retire is the whole label, because write access is granted per owner actor and the blind node sees no finer structure. Same power they have over the data itself, but history at the blind node is recoverable only for the grace period.
- Rule of thumb: per-entry rights are capabilities whose preimage is distributed client-side; label-wide rights are role keys; revocation always rides on the role keys. Nothing stored at the server states a reason.
- Mixed-owner labels (chat pattern): participants read the chat actor, so they can upload under the chat label but not retire; chat admins can soft-retire everyone's messages there. Each participant's own label keeps their copies safe. Per-uploader pseudonymous keys would separate further at the cost of leaking uploader count; not needed so far.
- A blind node may additionally rate-limit soft retires per label per day as a heuristic against wipes; not a correctness mechanism.

## What a blind node learns
One label per group synced to it, overlaps between them, blob count, padded blob sizes, fixed-size opaque wraps and token hashes, arrival times (clients may batch uploads), generation numbers and retire events, client addresses. Not: AKs, tids, thing or aspect counts, authors, membership, nesting.
- Sizes (decided 2026-10-11, constraints tension 3): large values use content-defined chunking (notes/serialization.md), since fixed-size chunks make an insert re-upload everything after it. Volume may leak, so padding is coarse: every blob is padded to the next step of one eighth of a power of two (Padmé), at most 12% and about 6% on average. Chunk size distribution leaks; accepted. Key epoch after a rotation: readers try the few live keys rather than a cleartext epoch byte (proposal).

## Interaction with other notes
- Receipt-time revocation rule: a blind node's receipt never counts, it is not a member. Statements are ordinary commits, per (aspect, author node). Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies permission commits first.
- Partial trusted peers whose closure grows mid-session repeat the exchange; extra rounds are bounded by nesting depth. Fine.
- Atomic application: a commit applies once its blob and all referenced chunks are present.
- Value hashes remain for links, dedup and undo; no state hash exists. The group hierarchy is a local index, not a sync tree.

## Dropped (2026-10-09)
Per-aspect state Merkle tree, Merkle tree over the group hierarchy, per-aspect context exchange, the state-vs-context Merkle leaf question, "one connection syncs one group". A state Merkle tree exposes shape to relays and must follow a cyclic hierarchy; blob reconciliation hides shape and makes nesting a local index problem. Note the earlier per-edit cost (a thing in many groups updated many roots) is gone: one blob, N index entries.

## Subscriptions and signals (decided 2026-10-15, notes/ephemeral.md)
- A connection may subscribe to labels. The peer then pushes new log entries (with blobs and wraps) for those labels as they arrive, instead of waiting for the next cursor request. Same messages as a cursor reply, unsolicited.
- A signal is an encrypted, signed envelope published under a label (upload key, like a blob). The receiving node forwards it to its other subscribers of that label and stores nothing; it never enters the log, has no entry metadata and is never reconciled. Clients do not re-forward. Blind nodes learn the same as for a blob: label, size, arrival time.

## Open
- Label key rotation follows the per-role actor key rotation; the label ID is stable, so no re-labeling.
- Lazy chunk fetch for huge bodies a device does not want locally (local policy; reconciliation just reports the IDs it lacks).
- Encrypted table of contents for partial restore from blind nodes.
- Upload batching; log retention horizon at each node (beyond it, peers fall back to range reconciliation).
- Peer discovery, transport, crypto primitives: not discussed yet. The transport must carry subscriptions (server push on a long-lived connection) for low-latency sync and signals. iroh (QUIC, hole punching, relays) might be a good transport option; owner unsure, evaluate when it comes up.
- Commit floor: a minimal commit is about 200 bytes plus a wrap per label plus a 16-byte token hash. Fine for editing workloads (a few MB per hour at most); revisit only if huge commit volumes appear (owner 2026-10-11).

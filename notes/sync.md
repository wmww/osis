# Sync: rationale
> Summary: Why spec/sync.md looks the way it does: blobs and labels, stamps and deposits, sync-key gating and claim keys, delete keys and retention at blind nodes, convergence and compaction, why there is no recycle bin, accepted limits, what a blind node learns, policy defaults, rejected alternatives, open items.

The requirements behind this file: spec/requirements.md, Untrusted (blind) nodes and Deletion.

## Why
- **One commit ID, one blob per projection, random key per blob**: a commit has one ID whatever groups contain it. Sharing history means adding wraps, never re-encrypting.
- **No commit size limit**: a delta pages like a snapshot and the header's lists go by link, so atomicity never depends on size and the API never splits a write. The costs (a reader stores pages it cannot apply yet, a writer that dies mid-upload leaves orphan pages for convergence to delete, apply streams pages through one staged transaction) are the ones snapshots carry anyway. The old one-blob rule bought nothing but a second commit kind of edit (split, non-atomic) that every app had to reason about.
- **Groups as sync unit**: groups are free and overlap; owner actors as the unit would force a copy for every separately syncable subset.
- **Label keys derive from the group's own role secrets**, never the owner's directly, or every label of one owner would carry the same role keys and identical wraps for a shared blob, linking them at the blind node. The deposit key derives from the actor's deposit seed (not from group secrets, so that a plain group's readers can derive it from the owner's `/keys`), hence it is keyed by label ID rather than by index: with the index alone every plain group of one owner registered the same deposit public key (found in the final pre-swarm review).
- **Entitlement, not group membership**, decides labeling: a thing dropped into a shared folder without an edge is silently not shared, which is the intended failure; an "add to shared folder" helper writes both. Cache the check per (thing, label), invalidated by membership changes of the label actor, the thing's edges or its owner chain.
- **Convergence as the one rule**: must-hold, may-hold, must-not-hold per body. Retag on join, cleanup on leave, compaction and repair after a bad deletion are all this rule. The may-hold class keeps a compactor's drop and a lagging member's re-upload from ping-ponging. A wrongful deletion is healed at the next member sync by a fresh encryption.
- **Projection** instead of per-delta keys wrapped per label (a wrap per delta per label plus header redaction). Every projection verifies alone since the header carries every delta hash. The projection key is (readable subset, retention class incl. expiry and delete-key set): a commit mixing "last modified, keep-at-most 0" with "body, forever" would otherwise be rewritten on every replacement, and a per-commit expiry forced clients to split atomic writes that mix a disappearing message with a non-expiring counter.
- **Certificate blobs per label**: one blob across labels (a wrap each) would link every label a node syncs through its node card. Cost: a few small blobs per (node, label). They are outside the closure, so convergence names a label's required set as closure plus certificates; without that a group admin's convergence pass would delete them as "outside the closure" and the node would re-deposit forever.
- **Inbox blobs**: a non-member cannot wrap anything under a label it does not read (a granter is not a reader of the grantee's home label), so everything that must reach an actor from outside goes boxed to its read KEM key: grants, edge changes and removals (so it erases), re-seals, each with the label IDs and servers it needs (the old text said "the target's `/label` commit", which a non-member cannot wrap and which is a join of many commits anyway). They carry a delivery expiry so an unconsumed one frees the budget by itself, and the inbox is a label the recipient's admins administer so they can delete consumed ones. Direct grants to a node go by pairing only: a node is listed by DH key and cannot enter a label cold.
- **Self-certifying label IDs**: a random ID lets anyone who learned it (an ex-reader, a leaked `/label`) squat it at a fresh server under their own keys. Two admins creating a label concurrently derive the same ID.
- **Blob prefix**: expiry and delete-key commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are the delete keys blinded by each blob's salt rather than the keys themselves, so projections and rewrites of one commit, and blobs of one author or owner across groups, are unlinkable at the server (spec/requirements.md, Untrusted nodes); a delete signature reveals nothing beyond the blinded key.
- **Stamps** (read must not give upload): the author's signature sits inside the ciphertext, so the label write key is the only writer proof a blind node can check. Signing (label ID, blob ID, wrap) and storing the signature beside the wrap lets anyone relay a writer-vouched entry (LAN-first flows, server to server by push, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. Stamps are checked against the current step, so a removed writer's stamps die with the rotation its removal already does. Upload needs no open: an open added nothing (a current reader could replay a stale stamped blob after its tombstone either way, and a removed one only until the next step), and requiring it blocked blind-to-blind replication. Download does need one, so blind nodes replicate by push, never pull (an ex-member could otherwise run a "server" and pull). What a reader legitimately needs under a label goes by deposit: a provisional entry under a per-label budget, readable at once by co-readers, promoted by a writer's stamped re-upload, which frees the budget. Rejected: upload under the write key alone (loses relay); per-member upload keys (linkable; Open below).
- **Delete-key signature plus label key** for deletion: the delete key proves the purge right as of the delta, the label key current membership; the second signature is not redundant, since everyone who ever held an epoch's secret (removed members included) can sign with its delete key. Level-3 deletes need the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the rotation the demotion already does. Levels 1 and 2 need only the sync key, because a thing's admin or author is often a mere reader of the label (anyone sharing a thing into a group they only read). The item names its level, so the server checks one commitment and knows which label signature it needs (an imported `writer` delta has no author-chain key, so position alone would misfile it). Honest nodes enforce current write permission for every purge (spec/permissions.md §8); servers only this approximation (spec/requirements.md, Untrusted nodes).
- **Delete keys follow retention**, one per level: the thing's admin delete key for `admin`, plus the write delete key of the actor above the author node (every device of the person holds it) for `author`, plus the thing's write delete key for `writer`; none for `nobody`. Without the admin level a thing admin who is not an admin of the label's group could not delete at servers; a writer without the admin secret lists the thing's published admin key (`/keys`), so every delta carries every level its retention calls for (owner decision: signatures over hashed tokens). Known gap: receivers never check the keys a header lists (only their count per level and that one level-2 key serves the whole commit); a vandal writer can list its own key at level 1 or 3 and so delete its own blob where an admin's key was due, no worse than with hashed tokens, and the label delete key still removes the blob. Blobs are projected by key set as well as reader set, so a `nobody` delta is never deletable through a commit-mate's key. Under the shared-owner pattern `author` collapses to `writer`. Chunks list their creating delta's key indices (no per-chunk bytes beyond the indices: the chunk's commitments derive from the header's keys and its own salt); a reused chunk whose thing-level commitments differ from the reusing delta's keys is re-encrypted, else a writer could delete chunks of an `author` value or an author be unable to delete its own; author-chain commitments need not match, so dedup across editors survives. Residue: an author's explicit purge of a value cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- **Covered means redundant under join**, not "inside the snapshot's frontiers": a snapshot that omits content covers nothing it omits, so a bad snapshot is harmless and anyone can re-snapshot. It also absorbs the versioning rule that a node never compacts what it could not join.
- **Tombstones** refuse the identical blob for `TOMBSTONE_LIFETIME`, so a stale relay cannot resurrect a purged body. Members never need them: they sync before they upload, and a node holding the purge strips the value from any copy that arrives later. The lifetime is a storage-versus-churn dial: infinite is O(deletions) server storage; zero lets any relay or bundle from before the deletion put the ciphertext back until a member deletes it again. A peer staler than the log horizon returning later than the lifetime can resurrect, and members heal it. Blob IDs are hashes of ciphertext under random keys, so a tombstone is no fingerprint.
- **Timed delete**: a relative keep-at-most is honored with nobody online because the replacing writer schedules the server-side delete when it replaces, with its snapshot in the same sync. The server learns the deadline (owner: acceptable). Absolute bounds wait for a right holder (spec/requirements.md, Deletion); expiry is the only timer a blind node runs on its own. The earliest requested time wins, which is order-independent and matches "first death plus D".
- **Purge reaches snapshots**: a compactor's snapshot carries everyone's live values, so purging a write also makes it value-less in snapshot bodies and drops them; a writer that then holds no covering snapshot under a label re-snapshots there (deterministic trigger; duplicates are covered-equal and one gets dropped). Snapshots are `writer` so any writer can remove a stale snapshot at servers; they are redundant by construction, so that power costs only a re-upload.
- **A purge commit is kept `MEMBERSHIP_KEEP` after its `ts`** (TLC finding S1): the purge SHOULD name dead writes and resets the rest, so the next snapshot covers the purge commit at once and a compactor could drop it; a node that held the purged body and had not yet seen the purge then kept the value for ever (the body was covered, hence may-hold, and nothing ever told it). The same staleness class as revokes (90 days of membership history); a node offline longer is an offline copy (spec/requirements.md, Out of scope). Rejected: never covering purge commits (a blob per purge for ever); carrying purge items in snapshots (the compactor would vouch for the purger's right, which snapshots never do). `expires` on a purge commit is forbidden for the same reason (the server would drop the request unattended). The API puts a purge and its resets in a commit of their own, so an app's disappearing writes never inherit the 90 days.
- **Must-hold needs a positive "uncovered"**: a node that cannot join a body (parked) or has not fetched a snapshot's pages treats it as may-hold, never must-hold, or an old-version writer and a compactor would re-upload and delete forever. A strict-subset projection of a commit under a label (a writer whose timeline lagged uploaded less) is must-not-hold. A must-not-hold blob holds nothing (TLC S17): it neither holds a body for "the label lacks" nor makes another blob a strict subset, so a purger's rewrite goes up at once beside the purged blob still waiting for its carrier (the rewrite itself, S18), and stays; read literally, the rewrite waited on that deletion (a snapshot). A writer that has not applied the purge yet still deletes the rewrite as a strict subset of its own body until it does (S4; same window as before). node-sync: "must-not-hold" here is "holds a dropped delta (purge, expiry, keep-at-most, compaction) or one the label's actor may not read" (`holds_nothing`; unsettled views count it too, which only keeps or uploads more). Must-not-hold wins every overlap with must-hold (purged while uncovered, past keep-at-most while uncovered): the must-not reasons are the ones that remove content. A body holding no delta (every delta purged) is covered by definition; its header lives on in the nodes that applied it.
- **Rotation commits go up before the step** (TLC R9, second round): "register before any upload" (the server checks stamps against its head's write key, so content stamped under rotated keys must wait for the step) left a window in which a server's head named an epoch whose rotation commit was nowhere: every member listed in the step reached the head, could not open it, heartbeated stranded and was re-sealed with a secret it had no commit for. Now the registrar uploads the actor's membership commits the server lacks (the rotation chain) under the head's keys, then registers, then the rest; a step at a server implies the chain behind it is there (until compaction, where the `/secrets` snapshot is), and "stranded" means not boxed. What an ex-member gains is the removal rotation's blob under the old sync key (box map and the removal edge about itself, which it also gets by inbox), the same as from a dishonest server before.
- **An open ends at a head with another sync key**: before, a server kept an open (and its subscription) across steps, so a removed reader that stayed connected kept being pushed every new entry for the life of the connection. Now an open holds under the sync key of the head it was made at; reads check it lazily (one head lookup) and a push ends with the head event that ends it. Tied to the sync key, not the step: a step without a read rotation removes no reader (an epoch's readers only grow), so its opens stay, and a claim or static open at step j is held by a reader of j's epoch. The registrar's own open ends too: Register is relayable and proves only that the step is signed, so a departed node relaying the step it was pushed must not keep its open by it; the registrar reopens under the new key (one round trip, cursor kept). The remover's rotation commit still reaches a connected departed node, uploaded before the step (above). Member-proof opens at member peers are not step-bound.
- **Refused Register and Deposit learn the code alone** (security review): a Register not a child of the head used to get the head back, and a badly signed Deposit the budget, so anyone with a label ID (ex-member, link holder) watched rotations and deposit activity forever. Now Error 9 and a budget only under the head's deposit key. Nothing needed them: the node reopened on any refused Register and re-signs a stale deposit from its own seed; heads reach it through its open. Upload and Delete Status lost the head the same way (it let an ex-writer or ex-admin watch rotations by re-sending an old stamped entry); the node uploads and deletes only where the label is open, so the head comes by push, or by the next resync's Sync when unsubscribed. Code 9 itself stays (vs folding it into 1): it tells a signer its key was superseded, not bad, so a stale deposit is re-signed at once with the current deposit key and an ephemeral entry or delete waits for the newer key instead of being dropped (mvp-progress item 66: a stale deposit looped, then was dropped). It tells a holder of an earlier key only that fewer than `OLDER_KEYS` rotations passed since, which it mostly knew. Open's UNKNOWN_LABEL vs REFUSED still says whether a server hosts a label (key-derived ID, accepted).
- **Local drops of live bodies snapshot first** (TLC S11): a body under an absolute keep-at-most written offline and dropped at T before any upload left its live write in one node's state with no body or snapshot anywhere; the snapshot-first rule used to fire only for deletions at a label. Now a writer writes a covering snapshot (a local commit, uploaded later as must-hold) before dropping any body with live writes it holds no snapshot for; readers drop and keep the state. The same clause covers the timed delete of a relative keep-at-most (S13): the server deletes at the bound unattended, so the carrier must be up before it; a body that still has live writes gets no timed delete (it goes at the next compaction or at its bound plus `AT_MOST_GRACE`, carried then; notes/node.md).
- **Carrier tiebreaks** (TLC S12): the server is blind, so two right holders with stale views could each delete one of two identical bodies, or one of two covered-equal snapshots, each counting the other as the carrier. Deterministic choice: an identical body carries only the one with the higher blob ID, and of covered-equal snapshots the higher commit ID goes; a must-not-hold blob (a strict subset among them) never carries.
- **A purged body waits for its rewrite** (TLC S18): node-sync judged a dropped body's liveness by its dropped deltas only, so a blob holding a purged delta and a live one went in the pass that placed the rewrite; a refused upload (a rotation racing the purge, code 9) left the label without the live write until the purger retried, and the spec and model waited for a covering snapshot instead (the rewrite, a subset, carried nothing). Now every delta's live writes count, a kept one is carried by any other blob of the commit that is not must-not-hold (the rewrite, once present at that server) or a covering snapshot, and a right holder that holds such a blob asks for no snapshot (`carried`, `snapshot_first`). Cost: the purged value's commit blob stays at the server one more round trip (its chunks go at once). Rejected: counting any held blob of the commit as a carrier (keeps the race), and waiting for a snapshot (a snapshot per purge). A full label (code 12 on the rewrite) kept the purged body for as long as it stayed full; now a rewrite the server refused for the cap (`SyncEngine::capped`, in memory) counts as the carrier when it is a strict subset of the body (`rewrite_capped`), so the rewrite is uploaded again naming the body as replaced with its delete item (`Fate::Delete`'s `via`, `replace_sends`; spec/sync.md §5 Replace): the server admits it in the body's room and removes the body in one step, so the label never lacks the kept live writes (`sync_review::purged_body_leaves_full_label_spec_sync_7` checks every hop). The first version deleted the body first and re-sent the rewrite on the delete's OK: another upload could take the freed slot in between. While a replacing upload is in flight a plain upload of the same blob waits (`Requests::replacing`): two statuses of one blob could not be told apart. The reverse is open: the pass re-sends a capped rewrite plain before `deletions` sends it replacing, so both are often in flight; the first status takes the replacement list, so a plain OK followed by a refused replacing upload (code 9 after a rotation, delete rate) marks the body absent while the server keeps it (until a reconcile). Waiting for the plain one stalled the purge for good (the pass sends it every time); a fix would skip the plain retry of a rewrite a replacing upload will carry. The purge request itself is a new entry and waits for space like any write. An `Outside` superset (holds a delta the label's actor may not read) waits likewise for its readable projection; deltas the actor may not read are skipped (their carriers are under their readers' labels; counting them kept such a blob, purged or not, for ever).
- **Header-only rewrites are may-hold** (TLC S14): a purge that empties a body leaves a header-only blob, covered by definition, so nobody uploads it and a compactor may drop it; headers persist at the nodes that applied the commit (dedup by commit ID needs them, and a commit-form dot resolves its author through them), not at the label.
- **A node offline past `MEMBERSHIP_KEEP` misses purges** (TLC S15): the purge commit is compacted, the returning node's body is covered (may-hold) and it keeps the value bytes until it compacts; the value itself is dead by the snapshot's reset when the purge named dead writes (the SHOULD), so it re-spreads nothing. An offline copy (spec/requirements.md, Out of scope); accepted, no mechanism (snapshots carrying purge requests was rejected above). Confirmed for the model: the purge commit's `MEMBERSHIP_KEEP` overrides its keep-at-most too; any node dropping a purged body keeps the rewrite (a reader's stays local, it cannot stamp); a remover uploads its removal rotation before anything else.
- **Live writes leave a label only when another entry carries them** (TLC S2, S5, S10): a body past an absolute keep-at-most, a strict subset, or one of two duplicates is deleted at a label only while a covering snapshot, a superset blob of the commit or an identical body is under it, and a right holder that may write the aspect uploads the snapshot itself when none is there (otherwise nobody was obliged to and the server kept the body for ever). Locally a node drops the body at the bound and keeps the live writes in its state (spec/crdt.md §4.6); a snapshot it writes from that state covers every body it applied. A snapshot's keep at most is the strictest of the carried live writes' own deltas', but an absolute bound only while it is ahead of the snapshot's `ts`: one inherited after T would make the snapshot must-not-hold at birth and the carrier loop would never end; a carrier written at T drops it, so the live value keeps a servable copy. Keep bounds never change what is read; only expiry kills values. The TLA+ property "a member can always serve current state" was too strong for readers (they cannot write snapshots): what holds is that live state is never lost from a node's state or from the label.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honor a MUST drop nor judge a purge request. A few bytes per delta.
- **Reads gated by the sync key**: without it an ex-member, or anyone who learned a label ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Owner: nothing is served under a superseded key, not even entries the holder could have fetched before. Rejected: a grace window after re-registration; "old key serves old entries" (no gating against ex-members); serving only rotation entries to old keys (every ex-member watches the roster size and rotation timing forever, and the flag is unverifiable). The price: a member that missed a rotation cannot download the commit carrying its new box, hence claim keys.
- **Claim keys** (decided with owner): a laggard and an ex-member hold the same shared keys, so the gate needs something only the laggard has, its own private key, and the registrar is the one party that knows the roster the step is for. So the step itself is the delivery: a fresh step key and one pseudonymous Ed25519 key per reader, derived by DH, and the laggard's recovery is a pure function of its private key and the chain the server stores anyway. Nobody delivers, drains or budgets anything. Why a signature and not a hash preimage: a dishonest server cannot replay it elsewhere. Why the step key is handed out one step at a time (a stale sync key or a claim on step j yields only step j+1): an ex-member removed at step k+1 learns that one step exists and nothing after it, no rotation count or timing, which is what a bare `stale` reply told it before; serving the current step to anyone would leak the cadence to every ex-member forever. The reply is the signed step, verified under the previous delete key, never a bare key: a server handing out a chosen step key could otherwise recognize a claimant by the pseudonym it signs with. The claim set is defined from the epoch's read boxes, not the registrar's roster: the registrar may hold the epoch without the removal commit and would otherwise list the member the rotation just removed, and boxes name the owner and plain-group readers the roster does not. Nested actors chain claims: node key on the person's home label, then the person's read key on each group label. The registrar derives M's key from the newest `/keys` it holds, so M tries old keysets as it does for boxes; a device M removed can claim until a registrar that saw M's new keyset issues a step (metadata only, M's boxes are under its new key), the same staleness class as the epoch-covers rule. Steps are not deterministic (random step key and padding), so two admins stepping concurrently produce different steps and servers that saw different ones first hold different branches for good: steps form a tree by `prev`, a server accepts only a child of its head, and the next rotation gets one child per branch (same role keys, different parent signature). `/label` holds the set of steps, so any admin can relay a server's branch; claim keys are bound to the step key rather than a sequence number, since a branch has no number of its own. A node that cannot match a server's head walks from the newest step it shares with it. Cost: 32 B per reader per step, about 3% on top of the rotation commit's boxes, which already leak the roster bucket through padded size; servers keep a step's set only until the rotations it leads to are compactable (`MEMBERSHIP_KEEP` after it was superseded); beyond that a walk would reach nothing readable anyway. The chain itself (role keys, step key, signature) stays, as before. The gate is classical like the Ed25519 open; a quantum ex-member could fetch hybrid-protected ciphertext. Grants still need a way in before the grantee holds any key of the target: the inbox blob, boxed to the grantee, deposited under the inbox its `/keys` names (an ordinary label its admins administer).
- **Rotation commits are wrapped under the epoch they supersede**: a rotation hands out the new read secret, so a wrap under it would be readable by the rotator alone (deliveries used to carry it boxed per member). Under the old wrap a laggard reads the rotations it missed in order, each under the one before. What an ex-member gains from the blob (an honest server serves it under the old sync key until the step is registered, since the chain goes up before the step; a dishonest server or stray bundle for ever): the box map of the rotation that removed it (tids and roles at the new epoch) and the removal edge about itself with its frontier, which it also receives by inbox; never a secret. Under a fork the rotator picks the newest superseded epoch; a member granted during the fork under the other branch only cannot open it and needs a re-grant (rare).
- **Re-seal** is the one recovery path for a member that holds the right private keys but cannot reach the current epoch: its missed rotations compacted (`MEMBERSHIP_KEEP` after a roster snapshot replaced them), its grant unknown to the rotator, a fork branch it never received. Nothing a co-member serves helps by itself (the wrap of every current commit is under the epoch it lacks, and a P2P peer serves wraps, not keys), so someone must seal the current secret to it: a membership commit carrying its boxes and the epochs' history boxes (without them a re-sealed member or a grantee could decrypt the history box but not fetch it: it sits in a rotation commit wrapped under the epoch they lack, TLC R3), by anyone who may rotate (a sibling device of the same person is usually a writer, not an admin, of the group), delivered as an inbox blob. Delivery under the label itself was dropped: a member that needs a re-seal cannot open the label (its claim was refused or the rotator never listed it), and the wrap would have to be under an epoch it holds. Its own private keys never change, so a node stranded on its person's home label is re-sealed the same way; when the inbox is the very label it cannot open (a device offline past `MEMBERSHIP_KEEP`, below), a sibling device re-seals it over the pairing channel (a direct connection, same flow as pairing, same node identity), which is cheaper than a restore from the card. Nothing unattended re-seals (a PQ box per reader per step was rejected for size); the triggers are a current member seen without a box at a current epoch and the stranded heartbeat (spec/permissions.md §3, §4), both SHOULD, and a client may also offer it by hand. The stranded heartbeat is placed as soon as the walk fails (a refused claim), not only at the head, since a member whose next step's set was dropped never reaches the head (TLC R2); it is a deposit wrapped under the newest secret the node holds, so it needs no open. What the triggers still miss is in issues/reseal-triggers.md.
- **Entry boxes and static entries** for recovery and link keys: a key actor entering cold holds no epoch to unwrap anything with, and the person actor's rotations get compacted eventually, so its box in `/secrets` is not reliably reachable. So the current step boxes the read secret to it (one hybrid box, 1.2 KB, per step of a label listing it; nothing elsewhere; entry boxes are sealed only: the symmetric form carries no epoch to check, spec/crypto.md §4), and it claims the current step directly by a static entry, a hash of its signing key and the label ID, no walk and no old step needed. The registrar cannot do DH for it without a step private key it would have to keep, and a bare signing key in the set would tell the server a public identity; the hash tells it nothing until the key claims, which is rare. The entry is stable across steps, which only says that one slot is the owner's or the link's. A key actor granted after a label's step 0 is listed by a fresh step (an admin may step without rotating). Rejected: the read secret boxed to every reader (1.2 KB per reader per step, permanent, in `/label` and every roster snapshot; would spare laggards past compaction the re-grant); a seed-derived rendezvous label for the recovery key (a mini mailbox: unpromotable, floodable deposits); deriving the step key from the admin secret for determinism (an ex-admin plus a dishonest server could then identify late claimants from its tenure).
- Rule of thumb: per-entry rights are delete keys whose secrets are distributed client-side (role secrets) and whose public halves the header lists; label-wide rights are role keys; revocation rides on role keys. Nothing stored at the server states a reason.

## Wire choices (spec/wire.md)
- The blob prefix is a fixed byte layout so a blind node parses it without a CBOR decoder; the AEAD binds it as AD so a reader cannot re-prefix a ciphertext (new expiry or commitments) under a fresh blob ID.
- Padmé length recovery: a `0x80` marker then zeros inside the ciphertext (ISO 7816-4 style). One byte, no length field, and canonical because the padded length must equal `padme(len + 1)`.
- Header lists, the delete-key list, purge and origins go by link above `CHUNK_THRESHOLD` rather than being capped, since a commit has no size limit; header-list chunks carry the level-2 commitments only (notes/crypto.md).
- Range reconciliation: Negentropy-style additive fingerprints (sum of IDs mod 2^256 plus count, hashed) so a sorted ID index answers any range incrementally; 16-way splits, lists at 32 IDs, about log16(n/32) round trips. Rejected: hash of the concatenation (not incremental); Negentropy's full encoding (bound compression and timestamps, more rules for little gain).
- Protocol: request/reply by id over length-prefixed frames; both Hellos go out at once, so negotiation costs no round trip; per-entry status so a batch partly succeeds; a Status names a stale key (9) but never carries the head.
- Opens bind the opened side's Hello challenge and static key (no replay elsewhere); stamps, deposits and deletes do not, so stamped entries and timed deletes stay relayable.

## Protocol implementation (osis-proto)
- Modules: `frame` (`FrameDecoder`, `encode_frame`), `hello` (Hello, `negotiate`, `estimate_offset`: median of per-sample offsets, Hello counts as one sample; reported after three pongs, diagnostic above 5 s), `msg` (`Message`, one variant per kind over osis-label's `Step`, `ClaimSet`, `Proof`, `DeleteItem` and the `SecretBox` entry box; `decode` enforces every cap of spec/wire.md §11.2, `Rejected::code` gives the Error code), `rbsr`, `store` (`LabelStore`, `MemoryLabelStore`), `server` (`ServerConnection`), `client` (`ClientSession`), `bundle` (`BundleImport` over osis-label's reader and importer), `examples` (a fixed label and one message per kind, for tests and vectors).
- Decoder rules beyond the layouts: mode 1 lists at most 32 IDs, mode 2 lists 1024 then 32, IDs ascending and inside their range; ranges sorted, disjoint, `lower < upper`, an end bound only last; id 0 only on Error and Push (kind 24, the old signal, retired); a step at most 323 bytes (`MAX_STEP_BYTES`). Message nesting depth 6.
- RBSR: the requester sends 256 ranges per message, pipelined, each batch with a token; a reply range outside what its batch asked (or a mode 2 range not answering one of our mode 1 ranges) is dropped. Reference split: subrange i holds own IDs `i*n/16..(i+1)*n/16`, bounds the full first own ID. 10 000 IDs with 100 differences each way: 2 round trips (unit test); 10^6 IDs with 10^4 differences: 3 round trips, 5.3 MB up, 5.9 MB down (under a dense difference, most of a message's at least 16 mode 0 ranges mismatched, subranges list at most 8 IDs: `DENSE_LIST`; with 32 it was 35 MB up). A worst-case ReconcileReply (256 mode 2 ranges of 1056 IDs) is about 8.9 MB, under `MAX_MESSAGE`.
- Server engine: `handle(now, &mut dyn LabelStore, ServerInput) -> Vec<ServerOutput>`. Cross-connection work goes through the driver: `ServerOutput::Changed(label)` goes as `ServerInput::Changed` to every connection, `ServerOutput::Relay` (a relay-only entry, accepted by stamp, not stored) as `ServerInput::Relay` to every other one, which pushes it to a subscription of its label. Open and Path never read the path: the store keeps indexes per step added (`LabelStore::step_with_sync`, the newest step per sync key; `child`, genesis as the child of none; osis-server's `V`/`W` rows), so an Open is at most three lookups whatever the proof (`osis_label::evaluate_open` over a `PathIndex`) and a Path page reads only the steps it sends; a claim proof loads only its step's set (`LabelStore::claim_set`, shared `Arc`). Stamps, deposits and keyed deletes check the head's key, then the 8 newest distinct earlier keys (code 9: Upload and Delete Status carry the head, a Deposit learns neither head nor budget unless signed under the head), else 1, from `LabelStore::head_keys`, which the store keeps per head (`HeadKeys::child`; osis-server's `K` row), so these checks (which need no open) never read the path. A Reconcile reads only the live IDs inside its ranges (`live_ids_in`; sorted and disjoint, so at most the label once per message). A delete by delete key of an entry no longer held is refused (the prefix cannot be checked); a held one's prefix comes from `LabelStore::blob_prefix` (osis-server keeps it in the blob's `R` row), never the whole blob. The store applies policy: caps (the ephemeral cap included), deposit budget, rate limits on deletes (`delete`, `schedule_delete` return codes); ephemeral entries (prefix class) go to `Put::ephemeral`; an identical re-upload changes nothing and logs nothing.
- **Replace** (spec/sync.md §5, wire `entry` 4th field): one mechanism for presence updates (the old entry by the connection's tie: no Delete, no signatures), own covers (the absorbed entries their last cover's upload completes, `eph_replaces`) and a purge rewrite on a full label (`replace_sends`). The server engine checks each delete proof (`delete_auth`, shared with Delete; a name not held is skipped unchecked), the store plans and applies all or nothing (`Put::replaces`, `Replaced`; BackendStore `plan`/`replace`: the room freed per charge kind is credited to the cap check, removals logged after the add so a holder applies the cover before the deletion, delete-rate tokens taken before the add). Ties live in the store (`Put::tie` = the hub's `ConnId`, `EphEntry::ties`, `LabelStore::untie`), so a connection's close unties instead of scanning every other connection, and an untie naming an entry not tied to this connection is skipped (refusing it let a replayer block the author: its old entry evicted or deleted at a server, re-uploaded on the replayer's connection, then every update untying it there was refused). Replace is in Upload and Sync entries alike; at most 1024 replace items per message (same cost as a Delete). Member peers (`PeerStore`): a delete-proof replacement hides the entry from peers after the upload is applied, an untie removes the session from `served_src` (only of an entry it uploaded; others skipped); the release policy for a departing session's entries at a server stays an owner call (notes/ephemeral.md Step 4).
- Sync: with a log cursor, the log after it; without one, a replay of the live entries in blob ID order paged by a replay cursor `[BLAKE3("osis v1 replay" || log_id)[..16], first 63 bits of the last ID]` (the first 8 bytes overflowed the wire's integers above 2^63 and replayed a page twice), the last page returning the log cursor taken at the start (spec/wire.md §11.2); the connection remembers the start, so a replay continues only on its connection (elsewhere: Error 10). Two IDs sharing their first 8 bytes across a page boundary would skip the second (2^-64). Add events of the requester's gained IDs and of entries in that Sync are left out. A subscription starts at the connection's last complete Sync cursor for the label (else the log head), so a client that syncs before subscribing keeps the push cursors; pushes use the last Sync's inline limit.
- Client engine: `handle(now, ClientInput) -> Vec<ClientOutput>`; commands are batched under the caps and paged replies followed (Sync `more`, Path `more`, Fetch prefixes); a page without progress (the same cursor, or 16 pages in a row without events) ends the exchange with `PeerError`; `Command::StopPath` stops following a label's Path pages (the node stops on a bad page or when nobody waits); a Want naming an ID the Sync did not list as gained is dropped; a Push while a Sync of its label runs gives no cursor (the Sync's later pages still bring older entries); a reconciliation is abandoned past `MAX_RECONCILE_MESSAGES` (4096), 2^21 differences or 2^17 queued ranges. Both sides take only a Hello-sized first frame (`MAX_HELLO_BYTES` 256). Policy stays with the node: a stale-key `Step` is reported, not walked; `Want`, `NeedReconcile` (Error 10, whose Sync entries are re-sent as an Upload, or over 4096 gained IDs) and `Reconciled { need, have }` are answered by the node with Upload, Reconcile, Fetch; after a reconciliation a cursor-less Sync at inline limit 0 gets a fresh cursor (metadata only).
- Member peers use one engine per direction, not both on one stream: the dialer runs `ClientSession`, the acceptor `ServerConnection`; co-readers each dial the other (notes/networking.md, Implementation (node peers)).

## Why no recycle bin
A server-side bin (writers retire entries with a soft key, restore within a grace period) is not a permission boundary: a writer can already destroy irrecoverably everywhere by compacting with an empty snapshot, while members keep no bin; nothing ever lists the bin or restores from it, so it is a delayed delete; a retire carries no reason, so the client rule "re-upload what still changes state" undoes moderation retires. Retention per delta gives the three roles their deletion powers directly, "covered means redundant" gives the recovery a bin was for, and compaction needs no delay. Moderation is not deletion: a chat admin removes the participant, or the app hides the message with a chat-written marker (notes/chat.md).

## Limits (accepted)
- A removed writer keeps its delete keys, but they alone delete nothing; its power ends when the sync key is re-registered, which every removal does. Until an admin steps, writers stamp and open with the keys of the epoch the server's head registers (they hold it: history boxes), and wrap under the newest they hold; a writer's rotation changes no delete key, so a label whose admins are all offline keeps its old step while content under it is already unreadable to the removed member.
- A removed admin holds the current delete key until re-registration and can win the race at a server by re-registering keys only it knows. Remedy: a replacement label (next index, keys from the rotated admin secret the removed admin lacks), O(entries). The index keeps a replacement's keys and ID apart from the old label's, and two admins replacing concurrently derive the same ID. Hostile admins are out of scope.
- An ex-writer or ex-admin keeps old-epoch delete keys and, as a reader, the sync key, so it can delete its own old `author` bodies or old `admin` bodies at servers; healed by any member's next sync. Level-3 deletes need the write key, so `writer` bodies are safe.
- A malicious current writer can wipe `writer`-purgeable bodies at a blind node; write access already lets it reset them everywhere.
- Server storage under `author` retention grows with superseded bodies of authors who have not synced since the snapshot, and departed authors' bodies stay until a thing admin cleans up (a removal is the natural moment).
- Other bounds read on a node's own clock still straddle: two nodes either side of a keep-at-most bound or an edge's `until` (`stale_card`) may delete and re-place one body for as long as their corrected clocks differ (seconds; keep-at-most cannot wait, it is a MUST).
- Relative keep bounds measure from the killing commit's `ts`, so a backdated kill shortens "at least D" by up to the drift cap.
- A member listed in no step since its last sync (a grant a rotation raced) is locked out of the label until a later step lists it or a member re-seals it (spec/requirements.md, Out of scope); the rotation would have left it without boxes anyway, and the SHOULD re-seal rule (a member without a box at a current epoch) repairs it at the next write. A member whose missed rotations were compacted (`MEMBERSHIP_KEEP` after they were superseded) is refused at the step whose set the server dropped and can be reached only through its inbox; its stranded heartbeat (spec/permissions.md §4) tells co-members. **Accepted limit (owner):** when that heartbeat's deposit is refused (the admins refreshed the deposit seed, or the label's budget is full) nobody learns the member is stuck and it waits for a manual re-share (`Engine::reshare`, offered by clients); rare (a dropped step and a refused deposit at once), within "re-sealing is triggered, never guaranteed", and the alternative (a server claim log mapping reader slots to members, one new log event kind) adds a third mechanism to cover the overlap of two. TLC `rotation/MC_drop_refresh` is the expected failure for it. The deposit seed is refreshed only explicitly (`Engine::refresh_deposit_seed`). A walk costs one round trip per missed step. A device offline longer than `MEMBERSHIP_KEEP` on its person's home label is refused at the first dropped set and has no inbox of its own: it is re-sealed over a direct connection to a sibling device (pairing channel) or restored from the card; the official server may keep home-label sets longer by policy. A stranded member's heartbeat is a deposit under the deposit key it knows; if an admin refreshed the deposit seed since the member last read `/keys`, the heartbeat is refused and only a human-triggered re-seal reaches it, which is why the refresh is a MAY against observed abuse, not a routine SHOULD (issues/reseal-triggers.md). Re-seal soundness rests on established epochs (notes/permissions.md): within `MEMBERSHIP_KEEP` the departures travel in the epoch chain a re-sealer must hold; after compaction they travel in the roster snapshot and the removal commit separately from the `/secrets` snapshot, so a node whose view is incomplete (a server that never received the removal, an interrupted first sync) can box a removed member at a snapshot-established epoch by an eager rotation or a grant (re-seals wait for a complete pass and chain-established epochs). Healed by the next rotation of a node that knows the departure; accepted. Recovery and link keys claim the current step, so compaction and set retention never strand them; a replaced label keeps its membership commits and the replacement `/label` commit at honest servers, so only a key actor that knows no honest server is stranded (a removed admin squatting every server a card names). **Accepted limit (owner):** a hinted-label walk (a link joiner or recovery device reaching a label it knows only by ID) claims on the server's step before it can verify it, with the keys of the hint's actor only, so a dishonest server handing out its own step can recognise that one pseudonym at join time; closing it needs `Path` to answer a claim-key holder (a wire change), declined. The pending part of the actor set comes only from the commits of inbox blobs naming the thing, decoded unverified (a sender knowing another held actor's tid can widen it; accepted). **Accepted limit (owner):** consumed inbox blobs are not deleted early (spec/sync.md §3, a MAY): they stay until `INBOX_LIFETIME`, since later members open a thing's label by the blob's hints until the granter's chain arrives (deleting them broke every link_redeem seed); the cost is sealed storage at the server for 90 days per grant.
- A deposit-only re-registration (the head's deposit key is not the one this admin's seed derives, no newer epoch) waits until nothing under the label it can open, at a connected server that has not said it lacks it, is unopened and no `/keys` write of the actor signed by a current admin is pending (`pass.rs` `keys_caught_up`, `Engine::keys_write_pending`; unsigned or unreachable ones never count: anyone can send a pending commit, and an entry only a gone server lists never opens, either would hold the step back for good; an admin-signed write that never applies holds it back while it is held): a co-admin's refresh step arrives before its `/keys` write when blobs are not inline (or come from another server), and the laggard stepped back to the old key, re-admitting a departed party's deposits until it applied the write (`lagging_admin_keeps_refreshed_deposit_key_spec_sync_5`). Left: a head registered while its `/keys` upload was refused (rate limit, cap: `reregister` sends Upload then Register without waiting) still gets one step back, until the refresher's next pass uploads the write and steps again.
- Anyone holding an actor's `/keys` can fill its inbox's deposit budget and delay grants and readers' own writes (spec/requirements.md, Untrusted nodes); an admin deletes junk, and a new deposit seed needs a new `/keys` and chain step. A read-only node's heartbeats are deposits too, bounded per reader by expiry (notes/ephemeral.md).
- A reader's invite grant, self-removal or node card sits deposited until a writer promotes it; co-readers read it meanwhile. **Budget is server policy**, not a format constant: clients never compute it, they see refusals and the remaining budget in the reply. The recommended minimum (64 + 4 per padded claim slot) is sized per reader *actor*, while deposits come per *device*: a plain group owned by a team has a claim set of one, and thirty reader devices exceed the minimum on heartbeats alone. Hence the client priority (certificates, membership writes and revokes first, heartbeats skipped when tight) and the heartbeat policy below; servers that host big read-only audiences raise the budget. Deposits are unlinkable by design, so per-reader limits are impossible. After a write-key rotation readers cannot relay old entries to a new server until a writer re-stamps them.

## What a blind node learns
One label per synced group, overlaps between labels (shared content blobs; certificate and inbox blobs share nothing), blob counts, padded sizes, which entries are chunk blobs, the number of delete-key commitments (zero to three, which reveals the purgeable-by class), expiry times, arrival times, deletions and pending deletion times, which labels one connection opens (so: holds the current key of), the roster bucket of each step's claim set, which claim slots were used, when, and how many steps behind the claimant was (two late devices of one person use one slot), which entries were deposited and when (a grant or a reader-originated write), client addresses. Nesting only as far as overlap shows it. Not: AKs, tids, thing or aspect counts, authors, membership, which entries are projections or rewrites of one commit, retention bounds.
- Padding with Padmé costs at most about 12% under 256 B, 6% up to 64 KB, 3% above, 1–4% on average.
- Wrap overhead: about 25% on a minimal commit, under 5% on typical edits, none on chunks.

## Policy defaults (non-normative, tune freely)
- Compaction: a right holder compacts an aspect when superseded/live bodies pass a threshold, on its next write, after a randomized delay so concurrent writers do not all snapshot. A schema that wants no automatic compaction says keep at least forever.
- Heartbeats: under the home label and under labels with more than one reader actor; not under a thousand single-note labels. `/reach` excluded by default from labels shared with non-contacts (`publishes_reach`, notes/networking.md).
- Deposit budget: 64 + 4 per claim slot entries, 32 KiB each, as the floor; more for labels whose steps show many claim slots.
- `INBOX_LIFETIME`: 90 days (format constant), matching `MEMBERSHIP_KEEP`.
- `TOMBSTONE_LIFETIME` 30 days.
- Through a blind relay a client cannot prioritize permission commits before decrypting, so it downloads everything and applies membership commits first.
- Clients may batch uploads to blur timing.

## Rejected
- Owner actor as sync unit (above).
- State Merkle trees over aspects or the group hierarchy: expose shape and must follow a cyclic hierarchy.
- Home closure = everything the actor owns (complete backup by default): every thing would sit under its owner's home label beside any shared label. Owner chose explicit placement (spec/requirements.md, Offline and network).
- Unverifiable per-entry expiry and commitment metadata (first or latest upload wins).
- Soft retire, recycle bin, restore and a generation counter forcing concurrent uploaders to re-tag (above).
- Server-enforced keep-at-most (absolute bound in the clear prefix): the live remainder of a body may have no snapshot yet, so nodes that fetched before and after the bound would diverge for good; expiry has no such problem because the values die too. The timed delete gives the same effect for relative bounds without it.
- Compaction across clock skew: only the placer deletes its own entries on time grounds (entries of a lost or removed placer then stay for good, and keep-at-most needs others to delete); judging others' entries on the overlap of what both nodes drop (the only overlap a node can compute is "past by the largest skew", i.e. the `MAX_DRIFT` wait chosen, spec/sync.md §7).
- Leases (entries lapse unless refreshed): conflicts with immutable expiry and with a server being the only backup.
- Plain (unboxed) grants under a shared label: contradicts entitlement, since every reader of that label would read them.
- **Mailboxes** for rotation delivery (the design before claim keys): every actor named a mailbox label in `/keys`, key actors derived theirs from the seed, and every rotation deposited one boxed-twice projection per member (about 2.5 KB per member per rotated actor). Dropped because the laggard's recovery became a stored, budgeted side channel someone else had to feed: a key actor's mailbox had no writer to promote deposits, so an owner offline through enough rotations found the newest deliveries refused; clients needed a mailbox-first bootstrap across nesting levels; a device's mailbox was a stable per-device label at a server, so the server counted a person's devices for life; deposits made over one connection linked the recipients' mailboxes. Variants of claim keys also rejected: the registrar's own read key as the DH key with the member guessing among admins it knows (fails when the registrar's keyset changed since the member last synced); an ephemeral key served to anyone or in a public chain (every ex-member watches rotation cadence and roster bucket forever).
- A shared bootstrap label derived from the recovery seed: a stolen device could watch it forever for the person's device count and rotation timing; as a rendezvous for `/label` only, a mini mailbox (above).
- No gating against ex-members (reads under any sync key of the chain, writes under the current one): simplest, and download-before-upload closes most of the laggard-wrap content leak at servers, but not via relays or bundles, and ex-members watch label activity and harvest new ciphertext forever. Owner rejected.

From osis-commit label uses only the chunk trees and their `Error`: the inbox payload carries the commit as its `CommitBlobPlaintext` value (module `inbox`), and prefix agreement takes the header's `(level, delete key)` pairs, its blind and the expiry.
- Claim-set padding keys are public keys of random seeds (valid points), not random bytes: a server testing point validity would otherwise count the real keys. Static entries (hashes) stay distinguishable from points about half the time, which says only how many key actors read the label.
- Limits: prefix at most one commitment per level (3), expiry 0 means none (a `Some(0)` expiry is refused); blobs `MAX_BLOB`; tree nodes 1..=512 links, level 1..=48, root always interior (an empty value is one empty chunk); claim sets a power of two up to `MAX_CLAIMS`, every entry box key among the claims, boxes strict `box` values; steps, claim sets, inbox payloads and bundle frames decode with depth 512 and `MAX_MESSAGE` bytes; links and cards 8 addresses, 4 peers, 4 relays, 256-byte URLs; bundle frames 1..=`MAX_MESSAGE`.
- Importer rules beyond the spec text: an entry must follow its blob in the bundle and a stamped entry its label's path (the writer emits them in that order); deletions pass through unverified like a peer's log events.

## Implementation (osis-server)
- `BackendStore<B: Backend>` implements osis-proto's `LabelStore` on osis-store's `Backend` directly (no `Store`: a blind node holds ciphertext and metadata it must see anyway; notes/architecture.md §2). Rows: label meta (log ID, head, counters), node totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts (bytes once per node in the blob area), sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions. One `WriteBatch` per mutation. Log ID = BLAKE3(instance seed || label)[..16], seed random per storage instance, so a wiped server invalidates old cursors.
- `sweep(now, budget)`: at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record), due timed deletes in time order (tombstone, Deleted record), tombstones after `TOMBSTONE_LIFETIME`, claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`). An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s. The log is trimmed to `log_keep` records in steps of 1/8; older cursors get Error 10 and reconcile.
- **Server policy** (`Policy`, all knobs in the config file): per label `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12 for new entries only); node-wide `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register Error 12 via `LabelStore::admit_label`, spec/wire.md §11.2); a registered step and its claim set count toward `cap_bytes` and `max_bytes` (the set until the sweep drops it); past them `push_step` refuses a genesis step 12 but takes a child step without its set (a refused rotation would leave a removed member's open and write keys valid at that server, and anyone may fill a server to `max_bytes`); a child step past them even without its set is taken once per `over_cap_step_ms` (1 h) per label, else Error 12 (`Meta::over_cap_until`, durable): only a label's own admin spends that room, so outsiders cannot starve an honest label's rotation, and growth past the caps is at most `max_labels` bare steps (about 300 B) per hour; the node keeps its open on a Register refused 4 or 12 and registers again at a later pass (each resync), so the label stays synced (not stranded) while it waits; the rest of that pass waits with it (nothing goes under the old keys). Steps queued behind a refused one each wait an interval: `reregister` registers the recorded child of the server's head (the older rotation) before issuing one at the newest epochs, so k rotations at a full server take k intervals. A wait past one interval (clock set back) counts as over. Forgetting old steps instead was rejected: a path walk from genesis is how a node verifies a head it has not recorded; deposit budget `deposit_factor` (1) × the spec minimum; `claim_keep_ms` `MEMBERSHIP_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither less); `log_keep` 2^20; fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `replacements` 20 000, `deposits` 600, `registers` 600 (steps pushed; a repeat of the head is free; a recorded path registered at a new server goes at that pace), plus `entry_replacements` 4 per entry (a deposited entry's promotion counts); connections: `max_connections` 10 000 (when full, shared by source: `Hub::accept_from` closes the newest connection of the source holding the most if it holds two more than the newcomer's, else the newcomer; `osis_transport::evict_for`, sources from `Connection::source`: IP, IPv6 /64, unknown = one source), `hello_ms` 10 s (no Hello: closed), `max_queued_bytes` 48 MiB unread per connection (then dropped), `max_buffered_bytes` 512 MiB of partial frames over all connections (the connection holding the largest is closed); the listener takes at most `max_connections` transport connections (`link::serve`, shared by source the same way). Rate limits answer code 4. Ephemeral entries: `ephemeral_bytes` 16 MiB per label, `presence_bytes` 4 MiB per label apart, and `ephemeral_total` 1 GiB in memory (code 12; notes/ephemeral.md Step 3, Step 4 as built). Counters are in memory (a restart resets them). Node byte totals count an entry's bytes once per label holding it.
- `Hub` (sans-I/O, tokio-free with `--no-default-features`): one `ServerConnection` per accepted connection, `Changed` to every connection and replicator, `Relay` to the label's subscribers on other connections (bytes shared, `Relayed::blob` an `Arc`); every public call is one durable batch (`BackendStore::defer_durability`/`durable`: lazy backend commits, one fsync per input; on a failed sync nothing it would send goes and those connections close); `tick(now)` runs the bounded sweep, Hello deadlines, replication work and timers; `next_due(now)`. The simulator can drive it directly.
- Replication (`Replicator`, push only): per dialed peer, a `ClientSession` walking each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record; deposits, deletions and pending times are not relayable (signatures not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with backoff 1-60 s. A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks, rare). Entries stamped under keys older than the peer's head get code 9 there (diagnostic only): writers re-stamp.
- Echo suppression: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry; a replicator does not send an entry to the peer key it came from, so mutual replication settles (one entry with two wraps ends with one replacement per side). It needs the dialing server to authenticate with its static key: the driver dials peers with `dial_as` and its listen secret (an ephemeral dial key would defeat it, and then only `entry_replacements` bounds wrap ping-pong).
- Driver (`driver::run(hub, Endpoint { transport, listener, secret }, peers, clock, control, log)`, tokio, feature `driver`, default; generic over `T: Transport`): sessions are osis-transport `link` sessions (notes/networking.md): `link::serve` turns every stream a dialer opens into a `Link` (peer key = the transport's), each a hub connection; hub task owns hub and store, its calls in `block_in_place` on a multi-thread runtime; reader task per link, handing over one read at a time (Hub stall bounds: turns by source); writes into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); dial task per peer (`link::dial` with `dial_as`, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`); a connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s for the finish; ticks when due or every 60 s; `Control::{Tick, Shutdown}`. Tier-1 tests run it on `InProcess` under tokio (perfect network; not `Sched`: the driver spawns tokio tasks, and the sim drives sans-I/O engines, not drivers); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). Tier 2 (tests/it/quic.rs, ignored): two drivers on QUIC replicating, and the binary process serving a client.

## Implementation (node sync: osis-engine `labeling/`, osis-node `sync/`)
- `labeling/`: `actors` (reader actor = the nearest thing up the owner chain with secrets of its own; `secret_actor` up the owner chain; `may_read(x, t)`: `t`'s secrets derive from `x`'s, or `x` reads that actor on the timeline; `closure(g)` from node-core's `/groups` index; `group_labels` from `/label`), `blobs` (`Body` = one `osis_commit::project` class keyed by reader actor; `label_bodies(g)`: entitled projections of commits touching the closure, plus, on a home label, the `/label` and `/created` projections of labeled groups whose nearest labeled owner-chain actor it is; `seal_body`, `open_commit` (prefix vs header, spec/commits.md §4); `wrap_secret` with the rotation exception (the commit's `/keys` delta writes a read keyset of the label's secret actor: newest held epoch it supersedes); `head_keys` (sync key from any held secret, write/delete only established, deposit key from the actor's seed); `delete_secrets_of`/`chunk_delete_secrets`: the header's delete keys matched over every held epoch along the owner chains (`Core::delete_chain`, `delete_secret`); an entry's `Kind::Commit` keeps its blob's prefix salt for the signature), `certs` (`certificates(g)`: node card commits and perm's chain certificates as (commit, aspect indexes); `partial_bodies`; labels and steps are flows' `create_label`/`issue_step`), `converge` (the pure rule: `classify(Facts) -> Hold`, `may_delete(why, live, carried)`).
- `sync/`: `SyncEngine::handle(Event) -> Vec<Action>`; `Event::{Tick, Local, Up, Bytes, Down}`, `Action::{Dial, Send, Close, Wake}`. One `ClientSession` per server connection (an ephemeral transport key: the driver dials without `dial_as`); the servers are the union of the synced labels' server lists, `SyncConfig.servers` and inbox hints. State in local records under `y/` (`sync/state.rs`): entries per (label, blob) with wrap, stamp, certificate flag and what the blob is (`Kind::{Unknown, Commit{commit, parts}, Inbox}`), presence per (server, label, blob) with a deposited-there flag (no gained-ID lists: an upload goes to each server lacking the entry), cursors and heads per (server, label), blob keys of commit blobs (`by_commit`: an encryption is reused under other labels, a certificate never), certificates placed, heartbeat times, server tombstones (a fresh encryption next time), timed deletes sent, label hints from inbox blobs, inbox blobs not yet answered (`y/o`). One write batch per `handle`. The synced labels (`labels()`) are cached within a step keyed on the engine generation (which a reload never takes back), the retired count and the time (an admin edge's `until` drops a replaced label); debug builds check every cache hit against a fresh list.
- Open (`sync/open.rs`): tries in order the known head's sync key, the recorded steps deepest first by sync key, then by claim key (the node's own X25519 and the read-role KEM X25519 of every held read epoch of the actors it holds; filtered by a recorded claim set), then held key actors by static entry, only those the group's `/members` lists (a hinted label: the key actor the hint follows for, `Hint::via`, kept when a later inbox hint names the label, and those the thing's held `/members` lists), since the signing key in a static proof names the key to the server and links labels. A server's path is verified page by page (a bad page fails the label at once). Pushes for labels not started on the connection are dropped. `Step` replies are verified under the step tried and recorded in `/label` by admins; a head not in `/label` is checked against the server's path. A hinted label's walk (no recorded step to verify a `Step` reply under, `LConn.walk`) claims only with the keys of the actors the hint is for (`Engine::hint_actors`: the thing's applied members and the members its applied `/secrets` boxes, plus those the pending commits of the inbox blobs naming the thing grant or box, that this node is or holds; the boxes cover reading through an actor a rotation boxed with no grant held, `hinted_walk_claims_for_boxed_actor_spec_sync_5`), not every held actor's: a server handing out a step of its choosing would otherwise recognise the claimant by every pseudonym it signs with (hostile_server `hinted_walk_claims_only_for_its_actors_spec_sync_5`). Chosen over letting `Path` answer a claim-key holder (a wire change); the hint's own grantee's pseudonym is still offered. Code 13 registers the recorded path (deepest branch). Re-registration registers a recorded child of the server's head before issuing anything (`recorded_child`), `issue_step` reuses a recorded child of the head at the current registration epochs, and a node issues a new step only once another node's rotation of the actor (a remote membership commit writing its `/secrets`, `rotation_at`) is `SETTLE_MS` old (`step_settled`; the author registers first; counting every membership write, an admin's `/label` record of the previous step held each next rotation's step back, so two quick rotations shared one step: `stranded_reseal` failed on every seed): otherwise each admin and each connection added a sibling step per rotation (`one_step_per_rotation_without_server_spec_sync_5`). No key left after a claim: stranded heartbeat.
- Pass (`sync/pass.rs`), after the log was read to its end (`Synced`) and on every later change: head keys recomputed; no read epoch of the head held: stranded heartbeat, nothing else; an admin with a newer established epoch uploads the secret actor's membership commits the server lacks under the head's keys and registers a child (the rest after `Registered`); then must-hold bodies (before keep-at-least, or not covered by a snapshot entry of the label), membership first, uploaded stamped, relayed with their stamp by readers, deposited when a non-writer's own membership write; chunk/page/list blobs of uploaded commits and the held blobs their deltas link though not listed (reused chunks, a snapshot's values) with filler wraps; this node's certificates and node card per label (fresh encryption), only the deltas no genuine entry of the same commit present at every server holds (any node's copy or closure blob), never closure deltas, another node's demotion or `/keys` only `SETTLE_MS` after receipt, a heartbeat per `HEARTBEAT_MIN_INTERVAL`; writers promote deposited entries (never `/seen`); deletions of must-not-hold entries present there (the label delete key, else a delete-key signature with an established label key), carriers first (a later snapshot entry of the aspect at that server; else `snapshot_first` when the node may write), timed deletes at a relative keep-at-most bound; expired entries are forgotten, never deleted.
- Replaced labels (spec/sync.md §2): flows' `Engine::replace_label` rotates the admin secret first when the newest admin epoch is one a step of the old label registers (whoever took it may hold it; a plain group gets secrets of its own), then writes the new label and marks the old one replaced in one commit. Members stop syncing a label once they read it is replaced; an admin keeps it (`labels`) until done: its passes there hold membership-class bodies only (`bodies_under`), so content entries judge must-not-hold (outside) and go once settled, the replacement's `/label` commit goes up, certificates (chain certificates, cards, heartbeats) stay to verify them; no certificates or heartbeats are placed there anew. A replaced label is never stepped again (`reregister` skips it), but at a server that lost it the admin registers its recorded path again (`register_path` on code 13) so the replacement's `/label` commit is found there (spec/sync.md §2). A settled pass with nothing left to upload and no content entry present marks the label done at that server (`retire_at`, in memory; deletions there mark the label dirty for that pass); a server where no key opens it (`Phase::Failed`) counts as done; done at every server, or `MEMBERSHIP_KEEP` after this admin first saw it replaced (a server never reached), it is retired for good (`y/q`: empty value retired, a time first seen). Unopened entries there that only content commits list (chunks, tree nodes, pages: `replaced_leftovers`) are deleted by delete key too, and the label is not done at a server while one is present; their deletion never queues a chunk repair (`relink_pending` skips replaced labels: the replacement holds the content).
- **Inbox life** (spec/sync.md §3): an opened inbox entry records its commit (`Kind::Inbox(Some(c))`). Once that commit applied and is valid, the receiving device places a certificate copy, only when the inbox is the actor's home label (spec/sync.md §3: another group's label would show its readers the actor's edges, labels and box keys), of the carried parts of a membership commit on the things where it writes an edge of the actor or an actor it owns or boxes one (`Engine::members_named`; a rotation's `/keys` there goes along; anything else a stranger with the deposit seed sends is applied but never stamped) plus the newest valid `/created` and `/label` commits of those things that the payload names (the payload's list is the sender's word), and nothing from a blob expiring less than `INBOX_COPY_MIN_LEFT` (`INBOX_LIFETIME` / 2) from now (a short sender expiry freed the deposit budget for the next copy at once) (`pass.rs` `inbox_copies`; not when entries there already hold the commit's parts, counted as for chain certificates (`held_parts`), and the commit then counts as done: every member device of a group actor reads its inbox, and each re-placed K's grant on C with C's `/label` and `/created`, 2.8 KB per chat join, and later C's new `/label` after each rotation; the payload's hints are what a later key-actor member, a link joiner, finds the target's label by). Inbox hints (`inbound.rs` `vet_inbox_hints`, run from scratch after each open batch and each `run_dirty`; payloads cached in memory per entry, `inbox_opened`): per unexpired opened blob whose commit is applied or pending, the first payload thing with no known label the commit gave this node a read secret of (`Engine::boxed_by`: valid `/secrets`, or a reading-only candidate from the pending commit), one per blob, so a stranger's hints are bounded by the deposit budget and go with the blob; a `via` hint (key actor follow) is never touched. A box that opens proves only that the sender knew the actor's KEM key: a stranger's invite to its own thing is still followed (issues/inbox-stranger-invite-dial.md). Consumed inbox blobs are not deleted early (a MAY): a link's later joiners and a person's later devices open the named thing's label by the blob's hints while the copied `/label` still waits for the granter's chain (deleting them failed every `link_redeem` sweep seed: a joiner never found the target's label); they expire after `INBOX_LIFETIME`. Senders keep every flows inbox delivery (`Delivery::Inbox { resend }`, `y/v`) and, `INBOX_LIFETIME` after sending, seal it again to the member's newest keyset and re-send unless the member acted or, for a grant or re-seal, is no longer a current member of a thing the commit writes edges or secrets of; a re-sent removal notice names no label (the removed member must not learn the target's current one) (a held commit newer than the delivered one by it, for it, or by a node with a role on it), at most `MAX_INBOX_RESENDS` (3) times (`local.rs` `resend_inbox`). App-made `deliver_inbox` blobs are not re-sent. Direct commits for the app (`take_direct`) and stranded heartbeat times are sync state (`y/n`, `y/u`). Outstanding fetches stay in memory: every pass re-derives them (`refetch` of unopened present entries, `fetch_waiting` of waiting commits' blobs, `tree_wants`); only an app's lazy `fetch` is lost with a restart, and its read asks again.
- **Revokes about authors** (spec/permissions.md §4; `Engine::revoke_certificates`, `pass.rs` `certificates`): the authors seen under a label are the authors of its commit entries that this node judges invalid in a part the entry holds or, for a membership commit, in any edge op (aspect validity holds while any op on the aspect is valid: a single-use race loser's void grant sits beside its valid removal of L), or cannot judge yet (pending) (`Engine::judged_valid`): a revoke changes no verdict on writes its frontier covers, and placing it for them cost every link joiner the remover's whole chain (≈ 12 KB) under its home label at each joiner removal (its home holds the copy of its grant by L); a later write the revoke voids brings it then (revocation reaches a label when a member next syncs it, spec/requirements.md); applied edge writes lowering one's edge on a thing outside the closure, and roster snapshots of such things naming one (projected to the authors), go under the label with what judges them (`Timeline::write_certificates`: their authors' chains), placed like chain certificates (another node's demotion left to its author for `SETTLE_MS`). Under a read epoch that does not cover a known departure, a node that may not rotate places only the revokes of the departures inside members of the label's actor that leave its epoch uncovered now (`rotation::uncovered_departures`, the newest write lowering the departed member's edge on the actor it left, the last on its chain: `via[1]` there once found nothing two levels down; `Engine::inside_member_revokes`; spec/permissions.md §4 exception), each the whole write on that actor (with its rotation's `/keys` and `/secrets`: a reader that syncs the member waits for every delta of it, so an edges-only copy left the label's admin pending in `link_race`), plus the newest `/keys` commit of each actor on the chain, projected to that `/keys` like a chain certificate (not whole: a covered removal that rotated X stays unplaced, `only_uncovering_revokes_placed_spec_permissions_4`), with its author's chain (an intermediate rotated apart from the departure write, or M rotated after a self-removal, is otherwise unknown to a rotator holding none of its secrets: it seals to the old keyset, which the departed holds, so `rotation_helps` refuses and the label strands; `revokes::nested_departure_revoke_placed_spec_permissions_4`): they tell the rotators what keeps the epoch uncovered and what to seal to; nothing else goes under it.
- **Others' certificates** (`pass.rs` `stale_card`, judged once settled): another node's card entry (only its own `/node`, `/reach`, `/keys`) is outside the required set when a newer valid write of that node on each of those aspects is present at the server in an entry checked genuine (`Engine::latest_by`: the newest applied commit whose delta there is valid, by the given author; `ts` is the author's word, so anyone's later commit on another's card stood for the current one before), or, for `/node` and `/reach`, when the node departed: it reads the label's actor no more and an applied write on its way there removed an edge or passed its `until` (its own edge, or one of an actor it reads through: its person's; a departed node is never dialed; "reads no more" alone misjudged members whose chain the view lacked, and their cards churned in the sweep; tests `person_removed_node_card_deleted_spec_permissions_4`, `until_expired_node_card_deleted_spec_permissions_4`, `unheld_chain_card_kept_spec_permissions_4`); its `/keys` stays, chains of its old writes may need it. Admins (the delete key) delete them. The blobs a certificate copy linked (`place_linked`) are deleted by an admin once this node knows no entry of the copied commit under the label (one placed and not confirmed yet counts) and no other present entry links them. Every "newest commit on an aspect" choice (chain certificates, inbox copies) takes the newest valid applied write. `certificates` never re-places this node's own deleted copy, except its own card while it reads the label's actor (`own_card_read`): a re-granted node whose card an admin deleted places it again (`regranted_node_card_placed_again_spec_permissions_4`). Until both converge on the membership commit (an admin that has not applied the re-grant still judges the node departed) the two can ping-pong: the node places, the admin deletes, once per pass each.
- **Pass cost**: `label_bodies_meta` keeps each commit's bodies without plaintext in `Core::bodies` (dropped when the commit's record is written, when a thing it touches gets its creation record, all of them when an actor gets secrets of its own or a changing transaction rolls back; a commit whose owner chains are not all known is not kept); the pass projects a body's plaintext again only to seal it or walk its links (`body_plaintext`). A failed read-only transaction keeps every cache (`Core::rollback` returns early; a debug assertion in `Engine::run` checks that no index changed without `touch`). Test `label_bodies_cached_per_commit_spec_sync_6`.
- **Work sets** (`sync/work.rs`; spec/requirements.md Scale): a pass at a server judges only what its (connection, label) work set names (`LConn::work`): the bodies (`Engine::commit_bodies_under`) and entries of its commits, its non-commit blobs (chunks, cert-linked blobs), plus what is per pass anyway (certificates, inbox copies, heartbeat, promotion of deposits, parked relays, reseal). Triggers: one engine hook, `Engine::take_changed` (`Core::changed`, kept only while a `SyncEngine` wraps the engine): the commits whose record, parts, validity or timers changed since the last take. The engine marks them where it changes them (`engine::Changed`): an applied or joined (late parts) commit; a commit whose validity flipped, or a snapshot whose carried writes' judgments did (`rejudge_all`); a body whose death records moved (`note_deaths`: the bodies a write killed; replays mark only records that changed, so a write on an aspect re-judges O(bodies it killed)); every commit on a thing whose `/created` record came; a dropped part (`drop_part`: compaction, keep at most, expiry, purge); a fired timer (`Engine::tick`). An aspect whose state changed other than by a valid write's join (a validity flip, an un-merge on apply or late, expiry, purge, a late delta) is marked as an aspect (`Changed::aspects`): it wakes what waits on the state and judges no commit by itself (was: every commit on it, O(aspect history) per expiry or flip). A mark from an aborted transaction stays (one extra judgment). A step settles its deaths replays before its passes; what the passes' own replays mark is drained after the step. `engine_events` drains it at each step and pass start: the commits go to every open label's set (`Touched::commits`), their aspects and the marked aspects wake the verdicts waiting on aspect states (`Touched::states`, `Left::waits`), their chunks the bodies waiting on a linked blob (`Left::links`), and they are `forget_dropped`'s candidates. Engine events stay for membership only (below: `Roster`, `/created` and membership commits, `LostAccess` judges everything). Sync's own triggers: the sync state's entry, presence, deposited, tombstone, timed-delete and certificate records (`State::touch`, by label), carriers (`touched_commits`), its own drops (`drop_covered`: judged in the same pass), blobs that arrived (`log_events`). Derived per pass (`prepare`): a snapshot or another node's card commit in the set expands to every commit on its aspects; things entering or leaving the closure; aspects moving in or out of the unsettled sets; due times (keep-at-least, expiry); aspect states a verdict waits on (`Left::waits`: a dropped body with live writes waiting for a carrier, woken by any write to the aspect; `Left::at_most`: a keep-at-most body without its timed delete and with no write dead, woken only by marked aspects (`Touched::whole`), since a valid write changes its bound or liveness only by killing its writes, which marks it; once a write died it waits in `Left::waits`: a reset pruning a removed entry's tombstone drops its last held dot and kills nothing, `pass_marks::keep_at_most_reset_after_removal`); linked blobs not here yet (`Left::links`). The group's closure is an `Arc` from `Groups::closures`, the same one while it does not change (kept on relisting when equal): `sync_closure` walks it (`set_syncing`) only when it differs from the one last walked (`synced_closures`; `PassStats::closures` counts walks) and `prepare` diffs it with the set's only then; the bodies' `BodyCtx` shares it (taken again after `refetch` if that applied commits). The home label's published things (`published_under`) come from the `/label` index (`Core::labeled`, kept by `index_commit`), taken for every actor at once and cached against the change counts of the held records, `own_keys` and `labeled` (`Core::published`; was a scan of every held aspect key per pass); a group's `/label` is decoded once per write of it (`Core::labels`, dropped by `Core::wrote` and on rollback) and shared (`labels_of`: `Arc<GroupLabel>`s; `served_labels` borrows the steps). Debug builds check both against a recomputation. Local passes (labels served with no server, `local_pass`) have a work set per label (`SyncEngine::local_work`) fed by the same touches and prepared, scoped and left as a server's (`take_inputs` shared); a non-commit entry waits on its prefix's expiry (`Work::due_blobs`); differentials `local_serve::local_work_sets_match_full_passes_spec_sync_5` (served state at every step equal to full passes) and `local_inbox_blob_expires_spec_sync_5` (an inbox blob under a server-less home label: `deliver_inbox` to a person created with no server; the only local check that fails without `due_blobs`). The deletion step's other `Left` bookkeeping (waits, due, held back) is redundant with engine triggers in every local scenario tried: leaving nothing fails only the inbox test. Marks before a `SyncEngine` wraps the engine (open, restart) are not needed: a label's first pass on a connection judges everything (`Work::default`). Membership (`membership_moved`): a pass reads rosters only through `may_read`/roles (entitlement, a superset's foreign deltas, `stale_card`'s departure, `orphan`), held epochs (wraps, unopened entries, delete keys) and reader actors (`secret_actor`, `own_keys`). Roles change only downstream of a changed roster or owner link: `Held::reach` of the `Roster` things and the things of `/created` deltas, applied or late (`Applied`, `Joined`) (owned things and things named on as a member, transitively; perm's own stale set is the whole component on a merge, i.e. every grant to a new member). A label whose actor is in that set (a roster or owner link anywhere upstream of it changed: its own roster, or e.g. an edge on the owner of its group such as a person adding a device, which full-passes every label of that owner's groups, as before), or got or lost secrets of its own, judges everything; otherwise its closure and published things in the set, or under an actor whose `own_keys` changed, expand to their commits, the label's own commits (one walk of `by_label_commit`) with a delta on such a thing too (a superset's foreign deltas read their reader actors), other nodes' card commits (aggregate `cards`) on any move, and the roster horizon is taken again when the label was hit. Epochs: the group's `ActorEpochs` is a pass input; deletes lacking a key (`Note::keyless`, timed deletes too) wait in `keyless` until any membership-class write, flip or late part. Unsettled: commits judged while anything was unsettled (deletions) or an entry was being fetched (must-hold) are kept (`held_back`) and judged again once that ends; becoming unsettled only withholds actions, so it judges nothing. Robustness idea (review, not done): the engine's own stale set (`changed.evaluated ∪ reach(changed.extended)`, `Core::update_timelines`) is more conservative and could be exposed to sync to keep it aligned with perm. Full pass (`Work::full`): a new connection's label, a roster or owner-link change upstream of the label's actor or a change of its `own_keys`, lost access, a forget (state reloaded), `set_servers`/`set_peers`, a changed pass input (`Inputs`: head and epochs, usable roles, replaced, group actor, published things, may rotate, the group's held epochs), the roster clock horizon (`roster_horizon`: an edge's `until`, a membership write or roster snapshot ahead of the clock, in the components of the actor and the closure's readers). A commit leaves the set once every send of it is present or tombstoned at the server and no judgment of it waits (relay wait, delete in flight or waiting, `covered` not established, an orphan candidate); entries touched mid-pass are pulled in (`pull`) with their commits' bodies. Aggregates kept with the set (rebuilt by a full pass): snapshot entries per aspect, unopened entries, unjudged authors (`certificates`), others' heartbeats (`reseal`). `covered_judged` is trimmed when consulted (a drop is a trigger). Indexes in `State`: entries by (label, commit), by kind, certificate entries, labels per blob, presence and tombstones per (label, blob). Engine changes are drained at each pass start (a carrier written by the pass before is judged by the next); late deltas mark their commit (a part that changes no read still changes the bodies other labels must hold); touches are spread at the end of each `handle` too, and dropped with no label open (a label opened later judges everything). `compact` forgets the bodies it drops (key and ciphertext, spec/commits.md §5). `forget_dropped` and `dropped_chunks` take candidates (chunk listers kept in `SyncEngine::listers`). `verdicts` judges everything. `SyncConfig::full_passes` turns the sets off: osis-sim `with_full_passes` runs a scenario both ways and the runs must be identical (`core/test/sim/tests/it/work_sets.rs`, scenario `work_sets`; it found: a carrier snapshot written by one server's pass and the next pass's set, a dropped body's blob coming back unforgotten, entries touched mid-pass judged without their bodies). Measured (`scale.rs sync_membership_pass_cost`, release, 10 labels of 10^3 commits, a writer and a reader): an edge write on an actor no closure reaches synced in 28 ms judging 0 bodies and 30 entries (the cards) in 10 set passes (was 0.62 s, 10 full passes, 10.3k bodies and 10.3k entries); an edge write on one label's group 0.13 s, one full pass of that label at each node, about 1.0k bodies and 1.1k entries each (was 1.3 s; writer 13 full, 13.3k / 13.4k; reader 20 full, 20.5k / 20.7k). Measured (`scale.rs sync_pass_cost`, release): one more write to a label of 10^4 commits syncs in 4.9 ms (was 12.5 s), judging 2 bodies and 1 entry at the writer and 1 and 1 at the reader (was 20.6k bodies and 20.6k entries at the writer, 10.3k and 10.3k at the reader); 10^3: 3.5 ms (was 0.23-0.34 s). Against main (review): the same server logs but for certificate copies going up one pass earlier, and departed cards deleted more often (the departures judged since). The change hook (replacing the per-event triggers) judged the same bodies and entries in both scale tests (10^3 and 10^4 one-write passes, both edge writes). Measured (`scale.rs sync_aspect_pass_cost`, dev, N = 10^3 one-key commits on one aspect, writer / reader (bodies, entries)): a keep-at-most map of N live bodies, one more key 1002/1001 and 1001/1001 → 2/1 and 1/1, a key overwrite killing one body 1003/1002 → 3/2; an expiring map, an older commit expiring among N live ones 1000/1001 → 0/1 at each node; a closure of N things, one write: same counts, no closure walk. - **Live writes** (`Engine::body_live`: a dot the body's deltas own survives in the state; unknown counts as live; writes of invalid or undone deltas are stripped from the state, so they count dead until a validity flip or redo puts them back; cached per body in `Core::live_bodies`, cleared by any changing transaction): a deletion waits for a carrier only while the body has a live write (spec/sync.md §7); such a body gets `AT_MOST_GRACE` on a relative keep-at-most bound and no timed delete (spec/commits.md §5), so neither a whole register replaced nor a partly erased text writes a snapshot.
- **Relay wait** (`pass.rs` `relay_due`, `promote`): a writer uploads or relays another node's commit at a server lacking it, and promotes a deposit, only after a wait of `RELAY_MIN_MS` (5 s) to `SETTLE_MS` (30 s) since the commit arrived (the deposit was first seen; in memory), the point fixed per (node, blob) by a hash; its own commits (origin local, a held key actor's included) and `First` placements go at once. Writers online together each uploaded a fresh encryption of the same new commits and re-sent every reader deposit; now the author or the first co-writer is done and the others find the entry. A refused promotion (a step registered meanwhile) waits again. Cost: a commit whose author is offline, a relay to a second server and a promotion wait up to 30 s; a coarse clock (the sim's `quiet`, 61 s steps) fires every waiter at once, so the sim's `concurrent_writers` moves time a second at a time. Residue: the wait is a spread, not an election; a writer whose view of a promotion lags may send it too (the sim sees a second or third upload of about one blob in 30 in a few seeds; it was every writer before).

- **Promotion completes the author's chain** (spec/sync.md §5; `pass.rs` `due_deposits`, `complete_chains`, `promote`): a writer promotes a due deposit only for a commit it applied (`Engine::author_chain`: the author's chain certificates to each thing the deposited parts touch at the commit's point, as `Timeline::certificates` plus the owner chains, minus the deposit's own parts) whose chain `not_held` finds under the label; before the sends it places the missing parts it holds as its own certificate copies (uploaded in the same batch), else leaves the deposit. Orphans (`orphan`, judged once settled): a non-closure entry of a commit this node applied, by an author that no longer reads the label's actor, whose chain is incomplete under the label, is outside the required set and admins delete it, per server and never while deposited there (seed 46: deleting deposits a promoter was about to complete tombstoned them; a stamped partial upload by a writer rotated out; nobody else completes it). - Chunks of dropped deltas (`dropped_chunks`): a chunk, tree-node or page blob whose creating deltas (the class whose delete-key indices are the chunk's own; none such: the whole commit) are all dropped and that no live commit lists nor live tree links (a lazy node fetches the missing tree nodes first) is deleted where present, by the label delete key or a delete key of its delta (a chunk never fetched is fetched for its salt); its bytes go once no entry names it. Residue: a chunk of a dropped delta that shares its class with live deltas of the same commit stays until they drop.
- Not judged (left alone): entries not opened (chunks of live deltas, newer epochs), commits not applied, membership-class commits and node-card/heartbeat commits outside the closure (others' certificates), projections that are a subset of a desired one (the superset goes up first), deltas this node does not hold.

## Open
- Server abuse limits: deferred until a real problem (owner). Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-label rate limits on deletes, wrap replacements and deposits, per-label ephemeral caps, admin delete; anyone may register a label up to the node-wide label cap (then Error 12, so squatters can exhaust it), and any writer can fill a label's cap with junk the server cannot tell from data. Per-member limits would need pseudonymous member keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one server bound to (server, label), never into the relayed `/label` chain.
- Claim sets in `/label`: 32 B per padded reader per step plus entry boxes, droppable `MEMBERSHIP_KEEP` after the step is superseded (steps are a map keyed by step ID so the drop is a field write); a server registered from a trimmed chain serves no claims at the trimmed steps. A dropped set does strand a member whose next rotation is still readable (it cannot walk past the step); the stranded heartbeat on a refused claim is what reaches it (issues/reseal-triggers.md). `/label` growth is about 250 B per step per group per rotation; if it ever matters, a root step carrying the current keys signed by the genesis delete key would let old steps be dropped.
- Partial restore from blind nodes: `/label` writes of owned groups now go under the owner's home label (a table of contents of labels); content of a subgroup is restorable alone only when it has its own label.
- Upload batching; log retention horizon per node (beyond it peers fall back to range reconciliation).
- Flow control (spec/sync.md §6): `ClientSession` queues requests and sends while the bytes in flight (frame plus reply allowance per unanswered request) are under `WINDOW`, so a session's own requests (at the node) and replies (at the peer) never pass `WINDOW_QUEUE`; the drivers' caps (`MAX_QUEUED`, `max_queued_bytes`) are only a bound on peers that do not read. The stall timeout counts from the last byte received or `ClientInput::Sent`: drivers compare `LinkTx::taken` (the writer pump hands the transport 16 KiB pieces) before each tick and report moved connections (`Event::Sent`, `Hub::sent`). `taken` means delivery only because QUIC/iroh `write_all` waits for stream credit (`STREAM_WINDOW` 1 MiB): a peer that stops reading stops it within 1 MiB, so a dead or non-reading peer cannot keep resetting the timer (a peer reading 16 KiB per 2 min can, by design: any link speed passes). The in-process transport never blocks a write, so `taken` jumps at once there; driver tests cannot show flow control (slow_link models the queues). Server-side backpressure (stop reading while the queue is full) was weighed: it needs a pausable `ServerConnection` and a drain signal, and the client still needs a request window for its own queue; the reply allowances made it unnecessary for compliant clients. `RESEND_MS` resends only an entry whose request was answered (`ClientSession::answered(tag)`: every request of the commands tagged up to `tag`, follow-ups included, got its reply; `Requests` stores the tag of `commands()` after the batch's commands went, `UNTAGGED` until then), so a held-back queue that drains sends nothing twice. Pushes (`ServerConnection`): with `ServerInput::Taken(cumulative LinkTx::taken)` reported, a push goes only while the bytes written and not taken, it included, fit `REPLY_BUDGET` (or none are unwritten); otherwise the label goes to `owed` (FIFO; while any label is owed a `Changed` only queues its label) and continues from its `subs` position at a later `Taken`, labels in turn (one held again goes to the back: a busy label starved the others when `owed` was a set walked in ID order); relay-only pushes without room are dropped. Without reports (sim, test drivers: instant delivery) nothing is held. Drivers report before a connection's input bytes and at ticks; `held()` connections ask for a tick every `PUSH_POLL_MS` (hub `next_due`, node `serve_wake`). Caps: `SEND_QUEUE` = `WINDOW_QUEUE` + `PUSH_QUEUE` (one push frame); server `max_queued_bytes` 48 MiB. Test: proto `slow_link::*` (72 MiB each way at 64 KB/s, 2 MiB at 1 KB/s, both on one session with the real cap sizes, fails with the window off; 72 MiB pushed to a 640 KB/s subscriber within `SEND_QUEUE`, fails without `Taken`; held labels take turns; a random push differential (labels, sizes, rates) against the log; requests held back for hours stay unanswered).
- **Hub stall bounds** (the hub thread serves every connection, so per-input work must be bounded and comparable to honest work): an Open costs a signature and at most three lookups (claims indexed as `H` rows, never a claim-set load); a message's signatures try the head's key only after one verified under no key (spec/wire.md §11.2), so at most one older-key scan per message; Sync entries capped at 1024 like Upload; one fsync per input; a relay goes to subscribers only; a connection whose unwritten replies pass `SEND_QUEUE` within one input is closed before its further requests run (`ServerConnection::unsent`); requests in one input are all unanswered when the last was sent, so their frames plus reply allowances (`client::allowance`, the one definition both sides use) stay within `MAX_UNANSWERED` (`WINDOW + 2 × MAX_MESSAGE + 4`) for a compliant peer, and one passing it is closed before that request runs: at most three MAX_MESSAGE-allowance requests (Reconcile, Fetch, Sync, Path) per input. That bounds Reconcile, the one request whose reads follow the label rather than the message: a whole-space range reads every live ID (release, redb, `file::reconcile_whole_space_budget`: 35-60 ms at 10^5 live entries, 0.5 s at the 2^20 per-label cap; 1024 puts with one fsync at 10^5 about 1.2 s; before the bound, one 64 KiB input of about 1600 such 40-byte requests cost a minute at 10^5). An honest reconciliation also reads up to the label once per message, so per input the two are alike. Weighed: per-subtree fingerprints in the store (O(log n) per range) cut honest and hostile cost alike but need an order-statistic index persisted beside the `E` rows in three stores, and a 256-range message with splits would still cost thousands of row reads; not needed while the per-label cap (2^20) bounds a scan. These are bounds per input (one read, at most 64 KiB), not per second: an opener can send input after input and keep the hub busy, as an honest peer with a full window may, so inputs take turns (`driver::Turns`): a connection's reader hands the driver one read and the next only after the hub took it, and the driver serves waiting reads round-robin by source (`Connection::source`), then by connection within a source; reads that arrived are queued before each turn. Bound: with S sources waiting and P the per-input bound, a read waits at most (S − 1) × P once it reached the driver (k × S × P if its source has k connections waiting), plus the bookkeeping between turns (accepts, closes, ticks: a sweep is 1024 rows); a message spanning several reads waits that per read, and each read moves the sender's stream (transport progress, so stall timeouts see it). One opener with any number of connections from one source delays others by one input per turn: at 10^5 entries about 135 ms, at the 2^20 cap about 1.5 s, against `STALL_TIMEOUT_MS` 2 min; many sources (issues/server-hub-stall.md, Sources) each get a turn. Test: `driver::flood_does_not_delay_others` (a flood's reads queued behind one reader delayed another's Sync by 190 reads, now 12, the probe's round trip), `driver::tests::turns_by_source`. Not done: decode and verification off the hub thread; a node-wide relay rate (a relay's fan-out is bounded by the subscribers' own queues and rates per label).

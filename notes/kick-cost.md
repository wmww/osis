# Kick cost on keep-forever data
> Summary: Analysis for Tess's question 3 (notes/questions-for-tess.md). A kick lists 34 B per kept commit of the kicked device, so on keep-forever data (chat messages) it costs 3.4 MB at 10^5 messages and fails past about 1.9e6 (`MAX_LIST_BYTES`); compaction cannot help there. Recommended: per-(aspect, session) counter heads for permanent aspects, `ctr` the demoter's contiguous receipt (not the highest counter: a deliberate gap is a forgery slot), everything above a gap by ID, plus a cap backstop that repudiates what was received last instead of refusing the kick. No header change, no chain walk; about 900 lines, half tests. The frontier-study links (F4) need the same per-session contiguity to be forgery-safe, so they are an optimization on top, not a different design; defer until sessions per aspect measure large. Tess chose links before (frontier-study Q3): re-ask.

## 1. Today
`Engine::frontier` (core/engine/src/apply/receipt.rs) lists by ID every received commit of the demoted node with a held part on a scope aspect, except what `droppable_here` says this node's compaction could drop now. On a permanent delta (spec/commits.md §5: keep-at-least forever, no keep-at-most, no expiry) nothing is ever droppable, so every commit is listed: 34 B each (CBOR head + 32). 10^5 messages: 3.4 MB; `MAX_LIST_BYTES` (64 MiB) refuses the kick past about 1.9e6 (`Commit(TooLarge)`, issues/long-aspect-cost.md item 1). Compacting first changes nothing (notes/core-triage.md §2.3 was wrong). Multiplier: the frontier goes under every label of the target and of the kicked actor as certificate copies, and every later roster snapshot of the target re-carries it in the ledger (issues/frontier-certificate-cost.md), so 3.4 MB is per label per snapshot, forever.

The requirement (spec/requirements.md Cost, goal): one entry per aspect it wrote, never to content or history.

## 2. What session form changes
Every content commit is session form now (item 239): dots `(Session(node, nonce), ctr)`, counters per (aspect, session) contiguous from 1, one nonce per open, `Node` source gone (item 259). The reason counters were banned from frontiers (Tess's decision (a), issues/session-sources.md rule 7) was forging into counters whose original every node had forgotten: headers are forgotten where bodies drop (compaction, expiry, keep-at-most). On a permanent aspect no body ever drops as covered, expired or at a bound; a purged one leaves a lasting header (`retention::lasting`, built), and step 6's forgetting (unbuilt) skips lasting commits by rule 8. So on permanent aspects every node that received a commit holds its header forever, a new device fetches every body (must-hold forever, spec/sync.md §6), and a re-signed commit on used counters meets its original: both void (spec/commits.md §4), the same residue an ex-writer has today by equivocating. Counter bounds are safe there, and only there.

**Gaps are the one hole, in any head design.** A session's counters are contiguous in writing, not in receipt: a backdated cutoff, a label synced partly, a commit never uploaded. A hostile X can also leave a gap on purpose (write [1,5) and [8,11), never [5,8)) and after the kick sign anything into [5,8) with any `ts`. A head "the highest counter received" covers it: a forgery that reads as a pre-kick write, forever, on data nobody can purge. So a head's `ctr` must be the **largest counter up to which the demoter received every counter of the session on that aspect**, exactly how a snapshot's `Frontiers` entry is computed (`retention::snapshot::frontiers_now` walks `ix.ranges` per (aspect, session) and stops at a hole); commits above a gap are listed by ID as today. Under that `ctr` every counter is used by a held permanent header, so a forgery meets its original wherever the original is held.

This also bears on notes/frontier-study.md F4: a link's bound is `p.hi` from X's own header, X's word; a chain walked from one head per device covers gaps in every reached session. To be safe the demoter must verify contiguity along the whole chain and, where it breaks, say so per session. So links do not remove per-session information from the design; they let the demoter skip listing sessions that chain without gaps. Frontier-study §4 ("No forgery") missed this.

## 3. F3/F4 against today's code
**C: per-session heads** (F4 without links; frontier-study §6 item 2, with the contiguity fix):
- Wire: `frontier` (spec/data-model.md §9, core/schema/src/core_types.rs) gains `1 heads: set<struct { 0 tid, 1 ak, 2 sessions: map<bytes16 nonce, uint ctr> }>`; the `tenures.0` entry carries it as it carries `commits`; `chunk_frontiers` chunks the whole value, unchanged. No header change. Vectors regenerated.
- Rule (spec/permissions.md §5.1): for an aspect in question, A lists a head for (X, aspect) only when every received delta of X there is one A holds with its header, permanent, and no receipts-only commit of X is recorded there (`r/` keeps IDs only, so retention and counters are unknown); `ctr` per session as in §2, counted over commits received by T (a backdated revoke stops at the first received later). A commit with a missing part (`part_missing`) stays listed by ID (A received it whole). A write is covered iff its commit's ID is listed, or its aspect has a head of its author and its session with `hi - 1 <= ctr`. Role-class aspects (fixed retention) and anything with an expiry never get heads; ephemeral commits never (their aspects are `~`, not durable).
- perm: `Frontier { commits, heads }`, `covers(id, write: Option<(tid, ak, nonce, hi)>)`; `Timeline::delta_valid` takes the write descriptor; its memo key gains the aspect (two permanent aspects of one commit on one thing can differ). Callers: core/engine/src/apply/validity.rs (3 sites, they hold the `AspectEntry`), `gates::removed_author` (the header is held; coverage is a pure function of header and frontier, so no monotonicity question, unlike links), `purge.rs` and `walk.rs` pass `None` (requests and role commits are by ID).
- engine: `Engine::frontier` walks `ix.ranges` per (aspect, session) of X with the permanence and receipt checks, lists heads, and lists by ID what is above a gap or on an aspect that fails the head conditions; `fit_requests` sizing unchanged.
- retention: nothing new now; when session-sources step 6 lands, its rule 8 already keeps lasting headers, and it must also keep every permanent delta's header (F3's unbuilt clause; moot until step 6).
- Spec: permissions.md §5.1 (one paragraph), data-model.md §9, growth.md frontier row, notes/permissions.md Revocation; wire.md unchanged.
- Tests: a kick at a fresh node after 10^3 uncompacted permanent commits lists one head per session; a re-signed commit on used counters voids both; a commit above `ctr` is invalid; a deliberate gap: the post-gap commit listed by ID, a later write into the gap invalid; mixed aspect and receipts-only aspect fall back to IDs; backdated cutoff stops `ctr`; new device from headers reads like a full node (`order::new_device_alike`); the ledger carries heads through a roster snapshot; `scale::long_aspect` kick at 10^5 succeeds and measures KB; roles-model `content.rs` gains sessions, heads, gaps and forgeries in its random histories (differential against a full-history node); fuzz and vectors for the schema.
- Size: schema and spec about 80 lines, perm about 60, engine about 200, tests about 500: about 900 lines, half tests. Risk: low to medium; the rules are the head conditions and the gap fallback, both local to `Engine::frontier` and `covers`.

**A: links on top of C** (F4 as designed): `Aspect.prev` on the first delta of a session per aspect (spec/wire.md §4, header/validate/builder in core/commit, vectors); the writer keeps per aspect the newest own commit of each earlier session (`ix.ranges` has it); the demoter walks chains and lists only a tip where every reached session is contiguous up to its link bound, else per-session entries from the break; receivers walk links with a cache per (aspect, device, frontier) and treat an unheld link target as uncovered for now, which `removed_author` must not read as final (frontier-study F4). About 900-1000 more lines; risk medium-high (pending semantics in the gate, restore clones linking to stale predecessors, chain verification). Gain over C: one entry per (aspect, device) instead of per (aspect, session) in the honest case, at 33 B per (aspect, session) in X's own headers forever, so the per-session bytes move from the frontier (carried per label and per roster snapshot) into the headers (carried per label).

## 4. Alternatives
- **Bounded frontier, N commits.** Refusing past N is today (N about 1.9e6): the member stays, the worst outcome. Leaving out past N is the sanctioned repudiation (spec §5.1): the omitted writes turn invalid everywhere, bodies stay must-hold, re-grant restores. As the only rule it clobbers an honest heavy chatter's history within years under IDs. As a **backstop** it belongs in every design: past `MAX_LIST_BYTES` leave out X's content commits received last, as `fit_requests` does for requests, and report it; a flood is what was received last, and no design bounds a hostile writer below O(its sessions) (it can restart per write: 300 B of permanent body per 20 B of head; 3e6 restarts, 1 GB at every holder, to reach the cap under C). Cost to users: none honest under C; implementers: about 40 lines, one spec sentence generalizing the request clause.
- **Per-session counter ranges instead of IDs** = C above. The original objection (item 193's restore gate, decision (a)) was about forgotten headers and restored clones; session nonces are random per open and permanent headers are never forgotten, so neither applies on permanent aspects; it still applies everywhere else, so IDs stay there. Honest cost: about 20 B per (permanent aspect, session that wrote on it), plus about 35 B per (aspect, device); a phone that writes in 5 launches a day, 36 KB a year per aspect; a desktop, a few KB; the cap at about 4e5 sessions, centuries. Against IDs: a 30-messages-a-day user costs 370 KB a year and hits the cap in about 20 years, a 100-a-day one in 7. Chat design E's per-year message aspects change nothing in the ratio.
- **Accept with a number.** 34 B per kept commit, kick refused past about 1.9e6, carried per label and per roster snapshot. Fails the 0/infinity test (notes/arbitrary-values.md): at infinity the member cannot be removed, and a member can make that happen on purpose by writing. Not acceptable as a stated limit, even for honest use (bots, long-lived groups).

New stated limit under C or A, hiding-host class (already accepted elsewhere, item 239): a kicked X colluding with a host that hides X's original commit can show a new device a re-signed write under those counters until the original arrives; every node holding the original voids both.

## 5. Recommendation
Build C with the cap backstop; add links (A) only if measured sessions per permanent aspect make frontiers large, since A needs C's per-session contiguity anyway. Tess chose links at frontier-study Q3 under the growth rule ("no per-session growth where there would otherwise be no growth"); on a permanent aspect every session that wrote left a body forever, so a per-session head grows only where storage already grows, and the gap finding is new: re-ask her.

**For Tess**: removing someone from a keep-forever chat would list one short entry per app launch in which they wrote, instead of one per message: a few KB a year per device even for a heavy chatter, and no more failed kicks. It changes nothing in what writes carry; the one-entry-per-device version can come later if launches ever add up, but it needs the same per-launch bookkeeping to stay forgery-proof, so it is a refinement, not a different design.

# Build internals
> Summary: Why the build is set up as it is and how the box is kept healthy: the dev profile, feature unification (what keeps `-p` and `--workspace` builds sharing artifacts), the heavy lock's log, the scheduler that must stay off, disk upkeep, rejected worktree schemes, and scripted renames. For coordinators, gate runners, and anyone changing manifests or the profile; the everyday rules are in notes/build.md.

## Profile
Dev profile for all branch work (Cargo.toml): workspace crates `opt-level = 1`, `debug = "line-tables-only"`, incremental, `lto = "off"` (Tess's call); dependencies and osis-crypto `opt-level = 2`, no debuginfo; build-time code (`[profile.dev.build-override]`) without debug assertions, which keeps build-time units apart (Feature unification). No `split-debuginfo`: its per-build `.dwo` files pile up (GBs per worktree). `.cargo/config.toml` zlib-compresses debug sections at link (test binaries about 40% of their uncompressed size, backtraces keep file:line; Rust's symbolizer cannot read zstd) and sets the test env (`PROPTEST_CASES=32`, `PROPTEST_DISABLE_FAILURE_PERSISTENCE`: Footguns).
Workspace: one `Cargo.lock`, one `deny.toml`, one `target/`, one copy of osis. `default-members` is core, so a bare `cargo build`/`test`/`clippy` never compiles the GUI. The GUI (`libs/kit/` osis-kit, `app/` osis-app, `app/android` osis-android) builds only when named with `-p`; `--workspace` means core and GUI. Its `[patch]` entries (libs/kit/patches/, vendored, not members) are in the root manifest. The GUI build reuses core's artifacts (Feature unification). Core depends on nothing in it; it depends on `osis`, `osis-schema` and `osis-chat` only.
- **Clippy says `Compiling`** for osis-engine, osis, osis-chat, osis-kit and osis-app after an edit that reaches their build scripts: clippy builds a member's build script and its build-dependencies with clippy-driver, as units apart from `cargo build`'s. Once per edit, a few CPU-s.
- A release `cargo test --release --no-run` takes about 5 min clean, 4 after an edit (thin LTO relinks every test binary); an osis-engine edit relinks the ten test executables above it.

## Worktrees
- Rejected: hardlink-seeded worktrees (a seed from a stale main rebuilt everything); one shared build checkout behind a lock (tests read fixtures through the manifest dir baked in at compile time, so it stays locked through test runs and serializes everyone).

## Feature unification
A package's features are the union of what everything in the build asks for, so `-p X` resolves differently from `--workspace` unless every crate's features are the same in both, and then rebuilds part of the tree as a second artifact set (cargo's `resolver.feature-unification = "workspace"` would fix it but is unstable). The rules that keep it selection-invariant:
- No feature a member turns on that another build of the crate leaves off: optional features only in the GUI (`accessibility`, off by default). QUIC, the LAN loop, redb and `OsRng` are unconditional.
- Third-party features go in `[workspace.dependencies]`, the same for every member (tokio's set, blake3 `zeroize`, ed25519-dalek `hazmat`); dev-dependencies add no features to a normal dependency.
- Pins: where a crate higher up enables features on a shared low dependency (quinn-proto: rand's defaults; libcrux-platform: libc's; x25519-dalek: zeroize's derive; the GUI stack: bitflags `serde`, num-traits `libm`, tracing defaults), osis-base lists that dependency at the workspace's features, unused (crdt-model, which has no osis-base, as dev-dependencies). The reverse for the GUI: osis-kit pins regex-syntax at proptest's defaults. The pins cost core builds a few small crates once.
- Build-time units never share a unit with run-time ones: `[profile.dev.build-override]` gives them a profile of their own. Otherwise cargo merges a build-time and a run-time unit of the same crate when profiles and features match, the merged unit takes the run-time `lto = "off"`, and which crates merge depends on the selection (unicode-ident is a run-time dependency of naga, so in GUI builds only): a GUI build would compile every osis crate a second time. Neither `[profile.dev.package."*"]` nor `build-override` can set `lto`, and pinning unicode-ident would hold only until the next such crate; dropping `lto = "off"` would also fix it (Tess's call). Cost: about 20 small crates built once per side.
- Checked by the gate's unification check (only when a manifest, the lock or `.cargo/` changed): after `cargo build --workspace --all-targets`, `cargo build --all-targets` and `cargo build -p <member> --all-targets` for every member compile nothing. An offender: diff `cargo tree -e normal,build,dev --prefix none -f '{p}|{f}'` with `--workspace` and with `-p X`; fix at the source by the rules above. Same features but a different fingerprint `profile` hash is a per-unit profile difference: compare the unit's rustc line in `cargo build -v` of each selection.


## Heavy lock log
Log: `~/.cache/osis/heavy.log` (JSON lines: who, command, wait, hold, CPU-s, the box's /proc/stat counters). `tools/heavy --report [--since HOURS]` lists runs (short-lane runs marked, kept out of the held/free split, totalled apart with their stops) and utilization; `tools/agent-times.py [--long N] [--since HH:MM|ISO|commit]` charges each agent its lock wait, hold, CPU-s and time by kind.

## Scheduler
`system76-scheduler` (Pop!_OS, `com.system76.Scheduler.service`) must stay off (`sudo systemctl disable --now` and `mask`; an OS upgrade can re-enable it): at its 60 s refresh it puts `cargo`, `rustc`, `ld` and all they spawn after in SCHED_IDLE, and a cargo run outliving a refresh crawls beside any other run (10-30x the wall at normal CPU-s). Unprivileged processes cannot leave SCHED_IDLE; `nice`/`chrt` don't help. Check: `ps -eo pid,cls,ni,comm | grep -E 'cargo|rustc'` shows `IDL`; the gate warns while the service runs.

## Disk
- `wt release` prunes `<wt>/target`: it runs `.claude/wt-mark`, then deletes every unit not used since the last release and all incremental sessions but the newest. The hook keeps a build key (a hash of `Cargo.lock`, the manifests, `.cargo/config.toml` and `rustc -vV`) in `target/.wt-mark-key`: unchanged, no unit can be stale, so it only marks every unit read (a release takes seconds); changed or missing, it runs every standard command (the GUI's only where the GUI was built before; add a new standard command there too), about a minute of builds a worker never ran. No cold builds result. Units a `tools/bin-at` REV with another lock built stay until the key next changes. The installed plugin (0.6.0) marks on every release with anything used: the key check lives in the hook so it holds for every plugin version.
- It needs a filesystem that records access times: on `noatime` it prints `wt: this filesystem doesn't record access times (noatime): targets not pruned` and targets only grow. `relatime` works (`findmnt -T .`).
- A warm target settles at 11-15 GB; 4-6 GB after a gate and a pruning release (the GUI 1-3.5 GB more where built). A worktree over 15 GB where no cargo runs: keep only the newest incremental session per crate dir (what rustc does next anyway, no rebuild): `python3 -c 'import glob,os,shutil,sys; [shutil.rmtree(s) for d in glob.glob(sys.argv[1]+"/target/*/incremental/*/") for s in sorted((x for x in glob.glob(d+"s-*") if os.path.isdir(x)),key=os.path.getmtime)[:-1]]' .worktrees/wtN`. Past 20 GB delete the target. `wt trim` is not the cure: the next claim builds cold.
- A `libs/kit/target` in a worktree is dead (no workspace is rooted there; wt never prunes it): delete it.
- A full disk reads as a compile error (`failed to write query cache`, `failed to parse process output`): `df` before believing a build failure. A `du` of `/home/ai/*` takes over 10 minutes: use `df` and the worktrees only.


## Scripted renames
Scripted rename sweeps over-match in ways an old-word hunt misses. Before running: list files holding both the old and the new word (shadowing, colliding names); protect third-party and other-sense names as exact tokens in every case (`x`, `X`, `X_Y`) with word boundaries (`/members(?!\w)`, not a prefix); filter paths with `git ls-files | grep -v`, not `':!path'` pathspecs (they can silently match nothing); print each rule's hit count, every rule must hit. After: hunt the new word as well as the old (`REHOLDERED`), census short forms (`sv`, `srv`); read the diff for same-token sense errors. A prose rename searches across newlines (a comment wraps `first\n// admin`). A file whose name the sweep renames moves in the same step: a kebab-form rule rewrites links to its old slug first. A token-level diff (comments dropped, identifiers and string literals compared pairwise) proves a rename pure in seconds. TLA junction lists are indentation-sensitive: realign `/\` bullets and compare `run.sh <module>` state counts.

# Client port: remote use of the API over the sync connection
> Summary: Design (owner direction, decided points listed first; revised after two wire/security reviews; steps (a) and (b) built, §8) for using the `osis` API from another process or device: per-group *sources* in the handle (local engine, or a connection to a node that holds the group's keys), API requests as new message kinds of the node-to-node protocol on the same connection as encrypted sync, served only on node listeners; three session tiers (Owner over the unix socket, a scoped client actor signing its own commits, a scoped node-authored client); scope = things owned by a scope group, actors never; stall and memory bounds per connection; the daemon case; a no-store build profile; the staged plan (tracking: issues/cli-proxy.md). Terminology: a *host* stores blind, a *node* holds keys and serves plaintext to its clients; no "server".

## Owner direction (decided)
1. Code in the node process uses the API without serialization.
2. Remote API requests and encrypted sync share one transport and one connection: a node stores plaintext it can read and hosts blind blobs; one connection may query the first while syncing the second.
3. A client may query or sync with any connected device, a peer included; peers are not treated differently from an always-on node.
4. Transport encryption must be adequate now that plaintext crosses it.
5. Browsers are one example of a thin client, not a rule: a syncing node may run in a browser, thin clients exist elsewhere.
6. A process holds any mix of locally synced groups and remotely queried ones; fully thin clients (no database, smaller binary) are worth supporting, but no process is assumed to be one kind.

Coordinator additions the owner accepted: the port is new message kinds in spec/wire.md §11, not a separate socket; the daemon is that protocol over a unix socket with a peer-uid check; a remote client is authenticated by a credential the node's owner issued, scoped to what it may read and write, enforced by the node at its API boundary; authorship of a remote write is the client's own key when it holds one (default), else the node's on its behalf (explicit); moving a group between sources is a group-level operation like `group sync`.

## 0. Session tiers
A served session is in one of three states, decided at accept or Auth and never by key equality:
- **Owner**: the transport type reported `Peer::Unix { uid }` equal to the daemon's own uid (§5). The same person at the keyboard: every API method except `read(|r| ..)`, `Internals`, `create`/`open`/`restore` and `Osis::pair` (the joining side; these make or open a store) and `set_stream` (until streaming writes exist, issues/api-deferred.md). Node-authored (`me()` as actor), no credential record.
- **Client actor** (`author: own`, the default for a remote device): the client holds a 32-byte seed deriving a signing key and a KEM key as a link key does (spec/crypto.md §3); it is its own key actor (a `KeyActor` creation record it signs for itself, §3), granted roles on its scope groups through ordinary edges by the owner. Authorship is truthful (author = actor = the client), receivers enforce its power through the permission model, and the node adds only what it decrypts for it (§3). Never a device of the person. **What the node adds for a client actor is a convenience, not a bound**: the actor holds the groups' secrets and its key, so it can read and write those groups at any host without the node; its power is exactly its edges.
- **Node-authored client** (`author: node`, explicit): the node signs as itself for `me()`; the scope record is the only barrier, hence §3's ownership rule and output filtering. For apps that cannot hold a key.

A fourth option, a thin *device* (a paired node without a store), is not designed: it is `pair` with full admin power; a scoped credential never implies it. **Owner decision**: whether a thin device mode is wanted at all.

## 1. Handle: sources
- `Osis` keeps `local: Option<Local>` (today's `Locked` + `Net`, core/osis/src/handle.rs:122-158) and `remotes: Vec<Remote>` (one per attached node: address, credential, port session state). A tid resolves to a `Source::{Local, Remote(idx)}` by `routes` (group -> source; a tid's groups by the local group index, else by the remote that reports it). Enum, no `dyn`: each API method is `match source { Local => today's body, Remote(r) => r.call(..) }`.
- **No cost on the local path**: `routes` is consulted only while `remotes` is non-empty (one atomic flag); with none, every call is today's code path. A `Write` batch touches one source (`Invalid` when its things resolve to two).
- **Per source** (by tid or group): reads (`get`, `at`, path, `stream`, `len`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`), watches (`watch`, `on_change`, `watch_thing`, `watch_roster`), `Write` batches, `commits`/`undo`/`redo`/`revert` (by scope), signals, `edit_text`, `keep_alive`, queries, sharing calls on a thing, `sync`/`unsync`/`sync_policy` of a group.
- **Process-wide, local or Owner only** (§0): `create`/`open`/`restore`/`pair*`, devices, hosts, hosting, clients, `rotate_reach`, bundles, cards, links, invites, `set_stream`, `Internals`, `read(|r| ..)`. Through a credentialed remote they fail `Unsupported` naming the call; with no local database and no Owner session, likewise. `me()`/`home()`: the local database's, else the attached node's person (one person per process; attaching a node of another person is `Invalid`). `node()`: this process's own actor tid (its node, or its client actor), else `Unsupported`. `now()` is local. `status()` merges local groups, each remote's groups in scope, and one `Remote { address, connected }` per attachment. Diagnostics: the local sink; a remote's diagnostics whose tids are all in scope arrive as pushes into it. Schemas are process-wide and mirrored to each remote session (§2).
- **Watches** over a remote are subscriptions (§2) whose pushes enter the one dispatcher queue, so remote and local callbacks run on the same thread in arrival order with the same coalescing. Initial value: the Sub's Reply (atomic with the subscription at the node, as `watch()` is locally).
- **`Write`** records API ops (create, place, group ops, set/edit/replace/remove, path ops, delete, retention and expiry made explicit from the key at the op); locally `commit` turns them into the engine `Mutation` as today; remotely the op list is the request. Existing contradiction: core/osis/src/write.rs:30-33 builds `osis_node::Mutation` while recording, so the batch has no wire form.
- **Text sessions** work remotely: buffer client-side, `commit` a batch (`edit(base, new)` on the text position), remote changes by the session's watch, idle timer in the client. **`keep_alive`**: renewed writes from the client; expiry covers a vanished client.
- **Reconnect contract**: a `Remote` whose connection dropped redials with back-off; on the new connection it Auths (learning the node's epoch, §2 Writes), registers its schemas again, Subs again for every live watch and signal listener (the new initial value closes the gap; signals in the gap are lost, within their contract), re-evaluates every `Live` query, and re-sends unanswered write Calls under their nonce when the node epoch is unchanged, else fails them `Invalid("outcome unknown")`. Between, calls fail `Network` (§6).
- **Unsupported remotely, never faked**: `read(|r| ..)` (its guarantee is the engine's read lock across the closure), `set_stream`, the process-wide calls above (except for Owner), `Internals`.
- Errors: one `Error` enum; a wire error maps back to the same variant (§2); transport failure is `Network`.

## 2. Wire
New kinds of spec/wire.md §11.2 (version 1 grows; a peer without them answers Error 11 and the client reports `Unsupported("node too old")`). Framing, ids and Hello unchanged; the id rules gain: a Sub's id stays reserved until its Unsub is answered or a Notify `lapsed` for it arrived; id 0 appears only in Push and Notify.
```
Auth    [24, id, Opt(client_pk), session_id, Opt(sig)] -> Reply [26, id, [0, seq, node_epoch]] | Error 1
                                                   sig: "osis v1 client auth" over BLAKE3(canonical [client_pk, challenge, static_key]); an Owner session sends no key and no sig
Call    [25, id, max_reply, method, args]      -> Reply [26, id, [0, seq, result]] | Reply [26, id, [1, err_code, detail*]] | Error
Sub     [27, id, max_reply, filter]            -> Reply (initial value)        the request id names the subscription
Unsub   [28, id, sub_id]                       -> Ok
Notify  [29, 0, sub_id, payload]               push, node -> client; payload: a delivery, [lapsed], or [changed_too_large, source]
Sign    [30, id, call_id, header]              -> Signed [31, id, sig] | Error   node -> client, only while write Call `call_id` is outstanding
```
- **Generic over typed keys and values**: `method` is a small integer table (`get`, `get_path`, `len`, `stream_read(tid, ak, path, offset, len)`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`, `write(nonce, batch)`, `commits(query)`, `revert(nonce, id)`, `undo(nonce, scope)`, `redo(nonce, scope)`, `send_signal`, `status`, `register_schema(bytes)`, `query`, `sync`, `unsync`, `sync_policy`, the sharing calls, and the process-wide rows Owner may call); `args` a CBOR array of plain values. Every row declares its tier(s), its scope check (§3) and its cost bound (Port stall bounds); a row without a declaration is denied. An unknown method is Reply `[1, Unsupported]`.
- Tids, AK text, groups by tid, paths as `[step*]`; values as canonical CBOR `Value` (untyped). **Typing is the client's**: a typed write is validated by the client's schema before it is sent. The node needs the schema for the structural diff of `set` (the `View`) and undo write-back, so the client registers its schemas per session (`register_schema`, in memory for the connection, at most `MAX_SCHEMA_BYTES` 1 MiB of source per connection; resource bound: 0 forbids typed sets, infinity lets one client fill memory). The node never stores a client's schema.
- **Reply allowance** (spec/sync.md §6 Flow control): a Call or Sub counts its frame plus `max_reply` against `WINDOW`; `max_reply` defaults to `SMALL_REPLY` (`MAX_MESSAGE` − `REPLY_BUDGET`, 64 KiB) and is at most `REPLY_BUDGET`; a reply that would exceed it is `[1, TooLarge { limit: max_reply }]`, and the client re-reads with a larger `max_reply` or by `stream_read` pages of `STREAM_CHUNK` 1 MiB (performance switch: 0 moves nothing, infinity is one page bounded by `REPLY_BUDGET`) or by path. Small reads keep many Calls in flight beside the connection's Sync and Fetch traffic. The remote `materialize_limit` is `min(app limit, REPLY_BUDGET)`. Auth, Unsub and Sign have the `SMALL_REPLY` allowance.
- **Subscriptions as pushes**: `filter` = the dispatcher's `Filter` (aspect, thing, roster, status, signal on thing, signal in group, diagnostics, query result), `max_reply` bounding each Notify. Notify carries the dispatcher's `Delivery` (value, `Source` with `CommitInfo`) under the existing push rule (one unwritten push frame, held pushes resume on `Taken`). A delivery above `max_reply` goes as `[changed_too_large, source]` and the client reads by `stream_read`/path. At most `MAX_SUBS` 4096 subscriptions per connection, counted apart from open labels (resource bound: 0 forbids watching remotely, infinity lets one connection grow the dirty-flag table and the per-change filter walk without bound; code 4 past it), of which at most `MAX_QUERY_SUBS` 16 query subscriptions (resource bound: each costs O(changed items) per change in its group; 0 forbids live queries, infinity multiplies that cost without bound; code 4).
- **Memory per connection is bounded in bytes**: a held subscription keeps a dirty flag and the `Source`/seq of the last change, nothing materialized; the worker materializes the next dirty subscription when push room opens (`Action::Room { conn }`), so held state is O(subscriptions). Signals are never coalesced: one per-connection byte budget `SIGNAL_BYTES` 1 MiB of fired signals waiting for room (resource bound: past it the subscription whose signal does not fit lapses, Notify `[lapsed]`, and the client re-subscribes; 0 drops every signal under backpressure, infinity lets a slow client hold unbounded memory). Schemas: `MAX_SCHEMA_BYTES`. Prepared commits: `MAX_PENDING_SIGN` 1 (§4).
- **Writes**: `write`, `revert`, `undo`, `redo` carry a client `nonce`: a sequence number from 1 per `session_id` (the client's 16 random bytes in Auth, the same across its reconnects, new per client process). The node keeps outcomes per **(tier identity, session_id)**: the credential's tid, or the Owner uid; the last `WRITE_NONCES` 64 nonces per session (resource bound: 0 makes every retry an unknown outcome, infinity is unbounded per session); at most as many sessions per identity as its connection cap (`MAX_CONNS_PER_CLIENT` for a credential, `max_clients` for Owner), the least recently used evicted. A repeat of a remembered nonce is answered with its first result, one below the remembered range fails `Invalid("outcome unknown")`, one above is new. Every map is scoped to the **node epoch**, 16 random bytes drawn at process start and returned by Auth: a client whose Auth after a reconnect returns another epoch fails its unanswered writes `Invalid("outcome unknown")` instead of retrying (a restarted node remembers nothing). A write Reply carries the node's change `seq` (the dispatcher sequence); the client's `settle` waits for Notifies up to it. Reply and Notify are not ordered against each other (pushes are held while replies go).
- **Errors**: Reply `[1, code, detail*]` maps 1:1 onto `Error` variants (`UnknownThing{tid}`, `UnknownActor`, `Permission{tid, needs}`, `Type{path, reason}`, `TooLarge{limit}`, `NotUndoable{commit, reason}`, `Unsynced{groups}`, `Invalid(m)`, `Storage(m)`, `Network(m)`, `Unsupported(m)`); protocol Error (kind 0): 1 only for a Call, Sub or Sign answer without Auth (or a wrong tier), 2 malformed, 4 the subscription or connection caps, 11 unsupported kind. Out of scope is never a protocol error (§3).
- **Decoder limits** (spec/wire.md §13): `args` within `MAX_MESSAGE` and `MAX_VALUE_DEPTH`; a `write` batch at most 1024 ops; `header` in Sign a commit header with inline lists only (§4). Domain `"osis v1 client auth"` joins spec/crypto.md §2's list.
- **Where the code goes**: osis-proto decodes and encodes the kinds (`msg`); `ServingSession` hands them out as `ServingOutput::Request { id, kind, body }` instead of Error 11 (core/proto/src/serving.rs:348) and takes `ServingInput::{Reply, Notify}` back, so one send queue and one push accounting hold; it also gains a **requester role** for Sign (its own id space and window accounting) and `ClientSession` an **answering role** (`ClientEvent::Sign`, `Command::Signed`): two new roles, not framing changes. The node's `SyncEngine` passes requests up as `Action::Request { conn, tier, .. }`, takes `Event::Reply { conn, id, frame }` and `Event::Notify { conn, frames }` (one per connection per engine change, batched), and emits `Action::Room { conn }` when held pushes drained. Semantics live in `osis` (`port/serve.rs`): the handle collects `Action::Request`s under its lock (core/osis/src/handle.rs:491 `after`) and runs them **after releasing it** on a port worker thread, one at a time per connection, as ordinary `Osis` calls through the scoped view (§3); the worker encodes replies and Notify payloads (never the lock holder) and feeds them back. The client side (`port/client.rs`, the `Remote` source) drives a proto `ClientSession` with `Command::{Call, Sub, Unsub, Signed}` through the same `Net` driver as any dial, so one connection carries its sync labels and its API traffic under one id space.
- **Port stall bounds** (notes/sync.md Hub stall bounds: the lock the sync driver needs is `eng`; each API call holds it for one engine transaction, as a local app's call does): per method row a cost bound comparable to honest sync work: reads O(one aspect) or one `stream_read` page; `write` at most 1024 ops within one frame (`MAX_MESSAGE`), the same bound a Sync's entries have; `revert` O(the reverted commit), itself bounded by having been applied; `register_schema` O(`MAX_SCHEMA_BYTES`); `query`: a page of `QUERY_PAGE` 256 hits (resource bound: 0 returns nothing, infinity materializes a group) evaluated O(items of the group) on Sub; afterwards a query subscription is marked dirty only by an engine change touching its group's closure (the dispatcher already resolves `groups_of` for signals in a group) and re-evaluated **incrementally** when push room opens: the changed items are placed against the page's bounds, O(changed items + page), never a rescan (a rescan only when a changed item carries no `ts` for the order, bounded as the Sub's evaluation). Notify evaluation batched per engine change (one lock acquisition per change for all of a connection's subscriptions, the dirty flags set off-lock by the dispatcher). Measured in (b) and (e): the worst row against one Sync pass.

## 3. Credentials and scope
- **Form**: `clients.0^` on the node's own thing (admin-only like `host.0^`, spec/data-model.md §9): `map<client id, { pk: signing key, kem: option<kem key>, groups: set<tid>, aspects: set<ak> | all, role: Read | Write | Admin, until: option<timestamp>, author: own | node }>`; `client id` is the client actor's tid (own) or BLAKE3 of `pk` (node). Issued by any admin of the node through the API: `db.add_client(keys, Scope, until, author) -> ClientId`, `db.clients()`, `db.remove_client(id)`; CLI `clients add|ls|rm`. `keys` is the client's public key text (signing, and the KEM key for `own`; the client prints it as a pairing request is printed). The node reads `clients.0^` when an engine event touches that aspect (as `host.0^`). No new signature format; revocable data the owner's devices already edit remotely.
- **A client actor comes into being at its first Auth**: a key actor owns itself, so only its own key may write its creation and `keys.0` (spec/crypto.md §3); the node holds only its public keys. So `add_client(.., own)` writes a *pending* record; on the client's first Auth (matched by `pk`) the node prepares the actor's first commit (author = actor = the client's tid, computed from its `KeyActor` record; aspects exactly `created.0` and `keys.0`, commit form) and sends it through Sign (§4; the client checks the tid is its own record's and the aspect set is exactly those two), applies it, then grants the actor `role` on each scope group (ordinary edges with `until`) and marks the record live. Node-sync places the actor's chain certificates under the groups' labels as for any holder, so third devices judge its commits. A record whose client never connects grants nothing.
- **Scope = owned by a scope group**: for both tiers a thing is in scope when its owner chain passes through a scope group (a scope group is in scope itself). This is the crypto's own rule (an edge on an actor reaches what it owns, spec/permissions.md §1; placement grants nothing), so the node never shows a client actor what it could not decrypt itself, and never accepts from it a write receivers would refuse. A thing merely *placed* in a scope group but owned elsewhere is out of scope (`UnknownThing`). Automatically out: the person (owns scope groups, is not owned by them), nodes and link seed things (owned by the person), a link's K (owned by the person). Besides, by creation record: a `KeyActor` record (any key actor) and the person actor are never in scope and never a scope group; `add_client` refuses a scope group that is an actor by record or the home group (`Invalid`); no `groups: all`. Sharing calls under `Admin` target in-scope non-actor things only.
- **What narrowing binds**: `aspects` other than `all`, the by-record exclusion and the role-class ban bind requests through the node, which is all a node-authored client has. A client actor holds its groups' secrets, so they do not bind it: `add_client(.., own)` refuses `aspects` other than `all` (`Invalid`) rather than pretend; a client actor with `Admin` on G may grant G onward and write role commits on G, as any admin may (that is what Admin means).
- **Presentation**: `Auth` once per connection, signed by the client's signing key over the node's Hello challenge and static key (the open-proof shape, replay-proof, bound to this connection); the node matches `client_pk` to a record's `pk` and remembers `(conn -> credential, tier)`; Call, Sub or Sign answer before Auth is Error 1. A session that sent no Auth, Open or Call within `serve_open_ms` is closed as today; an authenticated session is exempt from `serve_idle_ms` while its connection is up (the transport's idle timeout and keep-alive detect a dead peer; no new number).
- **Scoped read view**: one wrapper (`Scoped`) around the handle through which every credentialed request runs; it filters inputs and outputs: a tid not in scope reads as `UnknownThing`, exactly as a tid the node does not know (no existence oracle); `groups_of` lists scope groups only; `roster` of a scope group lists holder tids as names (reading them is `UnknownThing`); `commits` keeps entries with at least one `(tid, ak)` in scope and lists only those aspects; `CommitInfo` in `Source` names actor and node tids (names, not readable); `status` covers scope groups; diagnostics only with every tid in scope; values never contain links (replaced by content or `TooLarge`), and tids inside values are names. `holder_path`, `links`, `reach`, `invite_*`, `contact_*` are Owner-only rows.
- **Scope on writes**: every tid a batch names (written things, place destinations, group-op targets, deleted things, placed things) must be in scope before the batch; a thing created in the batch takes an in-scope owner (a scope group or a thing it owns): never the client actor (the person's devices could not administer it and it would go with the client) and never an out-of-scope owner (`Invalid`); placement is the app's business (the existing `require_synced` check applies); `aspects` narrows written AKs; role-class and `created.0` are writable by no node-authored request. Remote `undo`/`redo`: the newest undoable commit of the acting actor whose every `(tid, ak)` is in scope (the scoped `commits` with `Next`); `revert(id)` requires the same of its target.
- **Tiers and roles**: `Read`: reads, watches, queries, signals in. `Write`: batches, `send_signal`, undo/redo/revert, `edit_text`. `Admin`: `grant`/`change_edge`/`share_into`/`leave`/`remove_edge_of` on in-scope non-actor things and `sync`/`unsync`/`sync_policy` of scope groups. The node then reads with its own rights and writes with its own rights check (`Permission`) and, for `own`, the client actor's; the credential filters what the node could show, never widens it.
- **Checked at execution**: the worker re-reads the credential (record, `until`, and for `own` the actor's effective roles) when it runs each queued Call and when a `Signed` arrives, not only at enqueue; a revoked or narrowed credential fails the Call `Permission`/`UnknownThing` as the rule says.
- **Revocation**: for `node`, removing the record is the revocation. For `own`, removing the record revokes nothing by itself: `remove_client` demotes the client actor from every scope group (a real removal with its rotation, spec/permissions.md §3) and removes the record; the leaked or retired seed reads each group until that group's rotation has landed at its hosts, as any removed holder does. A demotion of the client actor made on another device leaves a record that grants nothing (roles are checked at execution). `until` is an engine timer (`Engine::next_timer`, the sync wake) and, for `own`, also the edges' `until`, so an expiry closes the session without another engine change. At the next `clients.0^` change the node closes sessions whose credential is gone or narrowed below what they use, and drops subscriptions now out of scope.
- **Seed custody**: `Osis::attach(NodeAddr, ClientSeed, Config)` takes the seed; it lives where the app keeps secrets (the OS keystore, else a 0600 file; the thin CLI keeps `client.seed` 0600 beside its config); the client prints its public keys once for `clients add` and never the seed; a `Remote` shreds its copy on drop.
- **Owner tier** (§0): no record, no scope filtering, Auth without a key (for the session id and epoch): the daemon's unix socket peer with the daemon's uid. Owner-only rows: the process-wide calls of §1.
- Cost: one record read per `clients.0^` change, one signature check per connection, one owner-chain walk per tid per request (`MAX_OWNER_DEPTH` steps, the in-memory records), a role check per `own` request; per client actor the owner's grant per scope group (about 2.6 KB of boxes per holder, notes/permissions.md) and an entry box in every step of each group's labels (a key actor that is not a node, spec/sync.md §2).
- Tests (tier 1, through `InProcess`): a grant targeting the person, a node thing or a key actor is `UnknownThing`; reading `link:seed.0` or a thing only placed in a scope group is `UnknownThing`; a `roles.0` write by a node-authored client is `Invalid`; a scope naming the home group, an actor, or `aspects` with `own` is refused at issue; out-of-scope reads and unknown tids are indistinguishable; a batch naming an out-of-scope tid fails; a created thing owned by the client actor or out of scope fails; undo skips a commit with an out-of-scope aspect; expiry closes with no other change; a revoke fails the next queued Call; a client actor's first Auth yields a valid `keys.0` at a third device, and its commits judged there by its edges.

## 4. Authorship
- **Client actor (default)**: per `write`, the node resolves and builds the commit from the op list against its state (deltas, pages, retention, delete keys), then sends `Sign [call_id, header]`, at most once per outstanding write Call and only while it is outstanding; the client checks every header field it can derive: content kind, no snapshot/import/roster marker, author = actor = itself, the aspect set equal to its ops' `(tid, ak)`s (or `created.0` + `keys.0` of its own tid at the first Auth, §3), no purge unless it asked, `undoes` present iff the Call was `revert` (equal to the id asked)/`undo`/`redo`, no frontier, retention and `expires` per aspect as it set them (or computed from its key's defaults), the ephemeral marker iff every op is ephemeral, `ts` within `MAX_DRIFT` of its own clock and above the `ts` of its last signed commit, and **every header list inline**: a client-signed commit never carries a list by link (a header whose aspect, chunk, purge or key list exceeds `CHUNK_THRESHOLD` is refused by the client and the node fails the Call `Invalid("batch too large for a client-signed commit")`; 1024 ops bound it anyway). It computes the commit ID from the header itself and signs under `"osis v1 commit"` (never a digest it was handed; neither Sign nor Auth can yield a signature under another domain). **Node trust, stated**: the delta contents (the hashes) and the delete keys are the node's, unverified (a thin client has no state to diff against and no `keys.0` of the bases it did not read); so a malicious node can make a client sign arbitrary content on exactly the `(tid, ak)`s it asked to write, at a time within `MAX_DRIFT`, with delete keys of the node's choosing (deletable by the node alone, or by nobody); nothing else: kind, markers, author, actor, aspects, purge, undo, frontier, retention and expiry are pinned. Client-signed attribution means "this client asked its node for a write on these aspects then". The node holds no lock while waiting, re-checks scope and roles when `Signed` arrives, then encrypts, applies and places the blob as any own commit and answers the Call. **No deadline**: `MAX_PENDING_SIGN` 1 prepared commit per connection bounds memory (resource bound: 0 forbids client-signed writes; a slow signer, a hardware key or a user approval, blocks only its own connection's worker), and a dead peer is caught by the transport's idle timeout; a `Signed` with no outstanding Sign, or after its Call ended, is ignored. Dot form: session form `Session(client, nonce)` with the nonce drawn by the node at Auth and counters per (aspect, connection) in node memory (issues/session-sources.md rule 1: a connection is a session start); until that lands, commit form (any author may use it). The client needs no state: `edit(base, new)` carries its base, `set` diffs at the node. Undo is per actor: the client actor's own changes.
- **Node-authored (explicit)**: the node is author, `me()` the actor; no Sign, no round trip. Attribution reports the node (truthfully). Two such clients of one node share the actor: their undo scopes interleave within scope (per actor by default, notes/api.md Fixed directions), narrowed by §3's in-scope rule. Also the Owner tier's mode.
- Cost: `own` pays one extra round trip per write and §3's grant and entry-box costs; `node` pays nothing and trusts the node's scope check alone.

## 5. Transport adequacy
- Already given (spec/sync.md §10): TLS 1.3 only, ALPN `osis`, raw Ed25519 keys both ways, the dialed key pinned, a fresh client transport key per connection, no 0-RTT, no tickets: confidentiality, forward secrecy, node authentication. Adequate for plaintext.
- **Node listeners only**: the port is served on the node's own listeners (co-reader serving, core/node/src/sync/serve.rs:495 `accept`): the dialable key, LAN keys, the unix socket, and `Config.client_listen` URLs (`quic://host:port`, a node reachable over the internet). Never on the host address: the host hub (core/host/src/hub.rs) is osis-host's own `ServingSession` over `HostStore`, blind, with no engine handle, and stays so; a client of a hosting node dials its node address, not its host address (a forwarding from hub to node is not designed).
- **Client listener key**: `client_listen` listens with a **client secret** of its own (a local record like the host secret, made when the first `client_listen` URL is set, shredded when the last goes), not the dialable secret: the dialable key rotates (`rotate_reach`, a link ending, spec/permissions.md §9) and would strand every client. `NodeAddr` = `url#client_key` (the `HostAddr` form; `add_client` and `clients ls` print them). The client key rotates only by hand (`db.rotate_client_key()`, after which clients need a new address, handed out of band like a new link); a client dialing a dialable or LAN address (a co-reader that also queries) follows `reach.0` as co-readers do.
- **Client authentication** changes nothing in TLS: Auth binds the client key to the connection's challenge and static key; the transport key stays ephemeral and unlinkable (notes/networking.md decision 5 holds for clients).
- **Unix socket** (`unix://<path>`, new osis-transport impl over tokio `UnixStream`; Linux-first, macOS `LOCAL_PEERCRED` later): no TLS; the kernel authenticates. The transport type reports `Peer::Unix { uid }` from `SO_PEERCRED` on both sides (the `Connection` gains `peer() -> Peer::{Key(pk), Unix{uid}}`; `peer_key` stays for keyed transports); the dialer checks the listener's uid is its own, the listener accepts only its own uid, and the Owner tier is set from `Peer::Unix` alone, never from a key value (a transport that can report any peer key, `InProcess` or a WebSocket, can never reach it). **Path sockets only, never the Linux abstract namespace** (abstract sockets ignore mount namespaces and file modes). Path: `sun_path` is 108 bytes, so the socket lives at `$XDG_RUNTIME_DIR/osis/<BLAKE3(store path)[..8]>.sock`; without `XDG_RUNTIME_DIR` (a system unit, cron, a headless box without lingering) at `/tmp/osis-<uid>/`, created 0700 and checked before use (owner = uid, mode 0700, not a symlink, else refused); `<store>/sock` is a text file naming it (removed on exit; a stale one is replaced after a connect fails). **Who gets Owner**: every process of the daemon's uid that can reach the socket: other local users are refused by uid on both sides; root is refused by uid but can read the store anyway; a rootless container or a same-uid sandbox (Flatpak, Snap, a bind-mounted runtime dir) that reaches the socket gets Owner even when it cannot read the store files. Accepted: your uid is the owner. The socket directory is osis's own (`osis/` under the runtime dir, never `$XDG_RUNTIME_DIR` itself or a path sandboxes share by default).
- **Leaks**: the node sees everything (it holds the keys). A passive observer or relay sees frame sizes and timing of plaintext queries, correlating with value sizes and activity (Padmé pads blobs at rest, not frames); a connection that both syncs and queries shows which labels a reading client is interested in by timing. Accepted now (relay-metadata class, notes/networking.md Risks); frame padding is a later option. A blind host never sees API kinds.
- Browsers: a WebSocket transport (notes/networking.md decision 1) for thin clients and syncing browser nodes; TLS by the browser, the node's key checked in-session (Hello static key, open signatures). Later.

## 6. Mixing per group
- **Resolution**: a group synced locally is `Local` whatever a remote also offers (authoritative here, works offline); a group known only through one remote is that remote; through several, the one it was attached for (`routes`), else the first; a tid in no known group and unknown locally fails `UnknownThing`.
- **Moving**: `db.group_source(g, Source::Local)` = `sync(g)` (the local node must hold the group's secrets: a device of a holder, or a client actor with the group's role, which is why a client actor can later sync what it queried) then drop the route; `db.group_source(g, Source::Remote(node))` = `unsync(g)` then record the route. Routes persist as a local app record (`sources`); without a store they live in `Config.remotes` and every group is remote. CLI `group source G local|ADDR`.
- **Offline**: a call on a remotely sourced group while its connection is down fails `Network` at once; a `Watch::current()` returns `Err(Network)`; `status` shows `connected: false`. No stale reads. Writes offline fail `Network` (an offline-capable device syncs the group locally).
- **Client cache (step g, later)**: per (tid, ak) the last delivered value with the node's `seq`, valid only while its subscription is live (pushes maintain it; a lapsed or closed subscription invalidates every entry it fed); reads from cache only for watched aspects, never a plain `get` of an unwatched aspect, never offline (invariant: a cached value is one the node reported after the last change it saw); no write-through, no offline writes. Bounded by `materialize_limit` of cache bytes (evicting re-reads).
- **No-store profile**: `osis` with `default-features = false` drops `store` (osis-node and everything under it: engine, store, keys, perm, label, host, redb, tokio), keeping base, crypto, crdt, schema, commit (header encoding for Sign), proto, transport and the `Remote` source; `Osis::attach(NodeAddr, ClientSeed, Config)` with no local database. Every workspace member keeps `store` on, so feature unification stays selection-invariant (notes/build.md); the thin check is one extra artifact set (`cargo check -p osis --no-default-features`, later for `wasm32-unknown-unknown`), a gate step only when `osis` or its deps changed. **Owner decision**: a feature outside the networking set, against notes/architecture.md §4; the alternative (an `osis-client` crate with a second API type) duplicates the surface. A browser syncing node is the other profile: full `osis` over a worker-backed store and WebSocket; out of scope here.

## 7. Consequences
- **Queries** (issues/api-deferred.md) become required: a thin client cannot read a group item by item. Minimal surface: `query(Query::in_group(g).with(key).order(Order::Time).page(after, n)) -> Live<Vec<Hit<T>>>`, `n <= QUERY_PAGE`, `Hit { tid, value, ts, received }`; `Live` = the page plus a watch (remotely one Sub with a query filter, Notify on a change in the visible range). Implementation at the node: the group index times an aspect check, O(items) on Sub; incremental page updates from the changed items of the group afterwards (§2 Port stall bounds); a per-aspect index (notes/local-store.md) later. `backlinks` second. Filters, counts, text search: the design pass.
- **Undo/redo**: per actor, unchanged; remote scoping as §3 (in-scope commits only); a per-session undo is not offered (a third model). A client actor's undo is naturally its own.
- **CLI**: "one process per store" (notes/cli.md Design) goes away when a daemon runs: `osis serve` listens on the unix socket; every invocation that finds the store locked connects there as Owner and runs its command through the `Remote` source (same code, same output; `inspect` and `init`/`restore`/`pair join` stay local: exit 8 while locked); locked with no live socket stays exit 8. `serve` stays the one long-running command (systemd keeps it alive); `hosting set` and `clients add` then take effect live (closes issues/cli-own-admission.md's last point).
- **Control plane**: an orchestrator is a client actor with `Admin` on the node's configuration group; nothing about identity, devices or hosting is reachable through a credential (§3), so it configures the node's data, never the node. Node-level control stays the owner's devices (`host.0^`, `clients.0^` are admin aspects of the node thing).
- **Dogfood** (notes/dogfood.md): the first user. The host box runs `serve` as the daemon; the agent's `watch` and `create` become Owner clients, so "stop a running watch before any other command" goes; the other box attaches as a client actor with `Write` on the channel group (the channel group owns its messages: `create --owner $G`, as the recipe already does) instead of syncing it, or keeps syncing (both must work: direction 6).
- Spec: spec/wire.md §11.1 (id rules, Notify) and §11.2 (kinds, codes, caps); spec/sync.md §10 (unix transport, client Auth, node listeners, the client listener key); spec/crypto.md §2 (domain); spec/data-model.md §9 (`clients.0^`). No sign-off needed before stability.

## Rejected
- A separate socket or program for the port: two transports, two authentications, two connection lifecycles; the owner wants one connection for both.
- One message kind per API method: a wire change per method; the method table inside `Call` grows without touching framing.
- Signed capability tokens: a second signature format and a revocation list; the `clients.0^` record is revocable data the owner already edits, synced like `host.0^`.
- A scoped client as a paired device: a device is an admin of the person with its secrets sealed to it, so the scope would bind the node, not the key. A client is its own actor with edges, or node-authored.
- The node writing the client actor's `keys.0`: invalid at every receiver (a key actor's records are written by its own key); the client signs its first commit through Sign.
- Scope by placement, or by a list of excluded kinds (`keys.0`/`secrets.0` holders): placement grants nothing in the crypto (the node became the deputy again, and a client actor's writes to placed things were refused at receivers); the kind list excluded every shared group the moment it got secrets of its own. Scope is ownership through a scope group, with key actors and the person excluded by record.
- `aspects` narrowing for a client actor: it holds the secrets; a bound the node cannot enforce is refused rather than advertised.
- A Sign deadline on `serve_open_ms`: a slow signer blocks only itself and memory is bounded by `MAX_PENDING_SIGN`; a dead peer is the transport's business.
- `NodeAddr` on the dialable key: it rotates with reach and would strand clients; a client listener key of its own.
- The Owner tier from key equality (peer key = listener key): any transport reporting an arbitrary peer key would have got it; it comes from the transport type's `Peer::Unix`.
- Abstract unix sockets: they ignore mount namespaces and file modes.
- Serving the port on the host address: the host hub is blind and has no engine handle.
- Values typed by the node: typing is a view, not data; the client decodes as locally.
- Running port requests under the handle lock: deadlock on re-entry, and a slow client would block the engine.
- Stale reads for remote groups offline: a value that may be wrong without saying so; the cache (g) is the bounded, labelled form.
- An `osis-client` crate with its own API type: duplicates the surface; one `Osis` with `Source` and a default feature instead (owner decision).
- Per-session undo: a third undo model beside per-actor and the admin view.
- Protocol Error 1 for "out of scope": an existence oracle beside `UnknownThing`; out of scope reads as unknown.
- Full query re-evaluation per engine change: `MAX_QUERY_SUBS` × `max_clients` × O(items) per change; dirty by group, incremental by changed items instead.

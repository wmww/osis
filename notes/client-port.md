# Client port: remote use of the API over the sync connection
> Summary: Design (owner direction, decided points listed first; revised after two wire/security reviews and the owner's final direction on process kinds; steps (a) to (d) built, §8) for using the `osis` API from another process or device: per-group *sources* in the handle (local engine, or a connection to a node that holds the group's keys), API requests as new message kinds of the node-to-node protocol on the same connection as encrypted sync, served only on node listeners; exactly two kinds of process (a node: keys, store, syncs what it chooses; a thin client: no keys, no store, no signing, served by a node that acts as an actor minted for that client), so authorization is the permission model's ordinary grants and no scope language exists; stall and memory bounds per connection; the daemon case; a no-store build profile; the staged plan (tracking: issues/cli-proxy.md). Terminology: a *host* stores blind, a *node* holds keys and serves plaintext to its clients; no "server".

## Owner direction (decided)
1. Code in the node process uses the API without serialization.
2. Remote API requests and encrypted sync share one transport and one connection: a node stores plaintext it can read and hosts blind blobs; one connection may query the first while syncing the second.
3. A client may query or sync with any connected device, a peer included; peers are not treated differently from an always-on node.
4. Transport encryption must be adequate now that plaintext crosses it.
5. Browsers are one example of a thin client, not a rule: a syncing node may run in a browser, thin clients exist elsewhere.
6. A process holds any mix of locally synced groups and remotely queried ones; fully thin clients (no database, smaller binary) are worth supporting, but no process is assumed to be one kind.

Coordinator additions the owner accepted: the port is new message kinds in spec/wire.md §11, not a separate socket; the daemon is that protocol over a unix socket with a peer-uid check; a thin client is authenticated by a bearer secret issued at registration, and what it may read and write is the roles of the actor the node minted for it, enforced by the node acting as that actor with the engine's own rights check; the node does all crypto and signing for it; moving a group between sources is a group-level operation like `group sync`.

## 0. Two kinds of process (owner decision, final)
- **Node**: holds keys and a store, syncs the groups it chooses; a browser docs app syncing one document is a full node (cheap by design). Code in the node process uses the API directly (direction 1). A process of the same uid talking to a node daemon over its unix socket is the node itself at the keyboard: the **Owner** session (as built in (b)): `Peer::Unix { uid }` equal to the daemon's uid, node-authored (`me()` as actor), every API method except `read(|r| ..)`, `Internals`, `create`/`open`/`restore` and `Osis::pair` (the joining side) and `set_stream`.
- **Thin client**: no keys, no store, no signing. It registers with a node (§3), holds a bearer secret, and the node does crypto and syncing for it: at `add_client` the node mints a real actor for the client (owned by the account, with secrets of its own and `keys.0`, as a sharer mints a link's K), and when serving that client it acts **as** that actor (`Osis::act_as`), so that actor's rights decide every read and write, checked by this node (§3); authorization is ordinary grants to the client's actor, nothing else. Attribution is visible: the client's actor authors its commits (header actor), the serving node is their author node, and the actor's creation record names its owner (the account), so no new core aspect is needed (a record naming the serving node would only duplicate `clients.0^` on that node's thing).
- A node acting as several actors (its person and each client actor) is the same machinery as a node managing two accounts (multi-actor `me()`; a coming issue tracks it).
- Terminology (owner direction, no renames in this note yet): "person actor" will become "account"; "edge" is to be called "grant" in prose.

## 1. Handle: sources
- `Osis` keeps `local: Option<Local>` (today's `Locked` + `Net`, core/osis/src/handle.rs:122-158) and `remotes: Vec<Remote>` (one per attached node: address, secret, port session state). A tid resolves to a `Source::{Local, Remote(idx)}` by `routes` (group -> source; a tid's groups by the local group index, else by the remote that reports it). Enum, no `dyn`: each API method is `match source { Local => today's body, Remote(r) => r.call(..) }`.
- **No cost on the local path**: `routes` is consulted only while `remotes` is non-empty (one atomic flag); with none, every call is today's code path. A `Write` batch touches one source (`Invalid` when its things resolve to two).
- **Per source** (by tid or group): reads (`get`, `at`, path, `stream`, `len`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`), watches (`watch`, `on_change`, `watch_thing`, `watch_roster`), `Write` batches, `commits`/`undo`/`redo`/`revert` (by scope), signals, `edit_text`, `keep_alive`, queries, sharing calls on a thing, `sync`/`unsync`/`sync_policy` of a group.
- **Process-wide, local or Owner only** (§0): `create`/`open`/`restore`/`pair*`, devices, hosts, hosting, clients, `rotate_reach`, bundles, cards, links, invites, `set_stream`, `Internals`, `read(|r| ..)`. Through a thin client's attachment they fail `Unsupported` naming the call; with no local database and no Owner session, likewise. `me()`: the local database's person, through an Owner attachment the node's person, in a thin client its client actor (the actor the node acts as for it); `home()` likewise, `Unsupported` for a thin client (its actor has no home group); `node()`: a node's own tid, `Unsupported` for a thin client (it has no key: the serving node is `status()`'s `Remote`). Attaching a second node as a different actor is `Invalid` (one acting actor per process). `now()` is local. `status()` merges local groups, each remote's groups the actor may read, and one `Remote { address, connected }` per attachment. Diagnostics: the local sink; a remote's diagnostics whose tids the actor may all read arrive as pushes into it. Schemas are process-wide and mirrored to each remote session (§2).
- **Watches** over a remote are subscriptions (§2) whose pushes enter the one dispatcher queue, so remote and local callbacks run on the same thread in arrival order with the same coalescing. Initial value: the Sub's Reply (atomic with the subscription at the node, as `watch()` is locally).
- **`Write`** records API ops (create, place, group ops, set/edit/replace/remove, path ops, delete, retention and expiry made explicit from the key at the op); locally `commit` turns them into the engine `Mutation` as today; remotely the op list is the request. Existing contradiction: core/osis/src/write.rs:30-33 builds `osis_node::Mutation` while recording, so the batch has no wire form.
- **Text sessions** work remotely: buffer client-side, `commit` a batch (`edit(base, new)` on the text position), remote changes by the session's watch, idle timer in the client. **`keep_alive`**: renewed writes from the client; expiry covers a vanished client.
- **Reconnect contract**: a `Remote` whose connection dropped redials with back-off; on the new connection it Auths, registers its schemas again, Subs again for every live watch and signal listener (the new initial value closes the gap; signals in the gap are lost, within their contract), re-evaluates every `Live` query, and re-sends unanswered write Calls under their nonce, marked (§2 Writes; the node answers what it remembers and `OutcomeUnknown` for what it cannot tell). Between, calls fail `Network` (§6).
- **Unsupported remotely, never faked**: `read(|r| ..)` (its guarantee is the engine's read lock across the closure), `set_stream`, the process-wide calls above (except for Owner), `Internals`. What the client's actor may not read is not Unsupported: it reads as `UnknownThing` (§3).
- Errors: one `Error` enum; a wire error maps back to the same variant (§2); transport failure is `Network`.

## 2. Wire
New kinds of spec/wire.md §11.2 (version 1 grows; a peer without them answers Error 11 and the client reports `Unsupported("node too old")`). Framing, ids and Hello unchanged; the id rules gain: a Sub's id stays reserved until its Unsub is answered or a Notify `lapsed` for it arrived; id 0 appears only in Push and Notify.
```
Auth    [24, id, Opt(secret), session_id]      -> Reply [26, id, [0, seq, []]] | Error 1
                                                   secret: the client's 32-byte bearer secret (§3), sent only over a transport pinned to the node's key; an Owner session sends none
Call    [25, id, max_reply, method, args]      -> Reply [26, id, [0, seq, result]] | Reply [26, id, [1, err_code, detail*]] | Error
Sub     [27, id, max_reply, filter]            -> Reply (initial value)        the request id names the subscription
Unsub   [28, id, sub_id]                       -> Ok
Notify  [29, 0, sub_id, payload]               push, node -> client; payload: a delivery, [lapsed], or [changed_too_large, source]
```
- **Generic over typed keys and values**: `method` is a small integer table (`get`, `get_path`, `len`, `stream_read(tid, ak, path, offset, len)`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`, `write(nonce, batch)`, `commits(query)`, `revert(nonce, id)`, `undo(nonce, scope)`, `redo(nonce, scope)`, `send_signal`, `status`, `register_schema(bytes)`, `query`, `sync`, `unsync`, `sync_policy`, the sharing calls, and the process-wide rows Owner may call); `args` a CBOR array of plain values. Every row declares its tier(s) (Owner only, or both) and its cost bound (Port stall bounds); a row without a declaration is denied. No row declares a filter: a thin client's rows run as its actor (§3). An unknown method is Reply `[1, Unsupported]`.
- Tids, AK text, groups by tid, paths as `[step*]`; values as canonical CBOR `Value` (untyped). **Typing is the client's**: a typed write is validated by the client's schema before it is sent. The node needs the schema for the structural diff of `set` (the `View`) and undo write-back, so the client registers its schemas per session (`register_schema`, in memory for the connection, at most `MAX_SCHEMA_BYTES` 1 MiB of distinct source per node (registrations are process-wide and kept); resource bound: 0 forbids typed sets, infinity lets clients fill memory). The node never stores a client's schema.
- **Reply allowance** (spec/sync.md §6 Flow control): a Call or Sub counts its frame plus `max_reply` against `WINDOW`; `max_reply` defaults to `SMALL_REPLY` (`MAX_MESSAGE` − `REPLY_BUDGET`, 64 KiB) and is at most `REPLY_BUDGET`; a reply that would exceed it is `[1, TooLarge { limit: max_reply }]`, and the client re-reads with a larger `max_reply` or by `stream_read` pages of `STREAM_CHUNK` 1 MiB (performance switch: 0 moves nothing, infinity is one page bounded by `REPLY_BUDGET`) or by path. Small reads keep many Calls in flight beside the connection's Sync and Fetch traffic. The remote `materialize_limit` is `min(app limit, REPLY_BUDGET)`. Auth and Unsub have the `SMALL_REPLY` allowance.
- **Subscriptions as pushes**: `filter` = the dispatcher's `Filter` (aspect, thing, roster, status, signal on thing, signal in group, diagnostics, query result), `max_reply` bounding each Notify. Notify carries the dispatcher's `Delivery` (value, `Source` with `CommitInfo`) under the existing push rule (one unwritten push frame, held pushes resume on `Taken`). A delivery above `max_reply` goes as `[changed_too_large, source]` and the client reads by `stream_read`/path. At most `MAX_SUBS` 4096 subscriptions per connection, counted apart from open labels (resource bound: 0 forbids watching remotely, infinity lets one connection grow the dirty-flag table and the per-change filter walk without bound; code 4 past it), of which at most `MAX_QUERY_SUBS` 16 query subscriptions (resource bound: each costs O(changed items) per change in its group; 0 forbids live queries, infinity multiplies that cost without bound; code 4).
- **Memory per connection is bounded in bytes**: a held subscription keeps a dirty flag and the `Source`/seq of the last change, nothing materialized; the worker materializes the next dirty subscription when push room opens (`Action::Room { conn }`), so held state is O(subscriptions). Signals are never coalesced: one per-connection byte budget `SIGNAL_BYTES` 1 MiB of fired signals waiting for room (resource bound: past it the subscription whose signal does not fit lapses, Notify `[lapsed]`, and the client re-subscribes; 0 drops every signal under backpressure, infinity lets a slow client hold unbounded memory). Schemas: `MAX_SCHEMA_BYTES`.
- **Writes**: `write`, `revert`, `undo`, `redo` carry a client `nonce`: a sequence number from 1 per `session_id` (the client's 16 random bytes in Auth, the same across its reconnects, new per client process). The node keeps outcomes per **(tier identity, session_id)**: the client actor's tid, or the Owner uid; the last `WRITE_NONCES` 64 nonces per session (resource bound: 0 makes every retry an unknown outcome, infinity is unbounded per session); at most as many sessions per identity as its connection cap (`MAX_CONNS_PER_CLIENT` for a client actor, `max_clients` for Owner), the least recently used evicted. A repeat of a remembered nonce is answered with its first result, one below the remembered range fails `OutcomeUnknown` (code 12), one above is new; a resend is marked (bit 62, Built (d)), so a node that remembers nothing (restarted, or the entry evicted) answers it `OutcomeUnknown` instead of running it. A write Reply carries the node's change `seq` (the dispatcher sequence); the client's `settle` waits for Notifies up to it. Reply and Notify are not ordered against each other (pushes are held while replies go).
- **Errors**: Reply `[1, code, detail*]` maps 1:1 onto `Error` variants (`UnknownThing{tid}`, `UnknownActor`, `Permission{tid, needs}`, `Type{path, reason}`, `TooLarge{limit}`, `NotUndoable{commit, reason}`, `Unsynced{groups}`, `Invalid(m)`, `Storage(m)`, `Network(m)`, `Unsupported(m)`, `OutcomeUnknown`); protocol Error (kind 0): 1 only for a Call or Sub without Auth (or an unknown secret), 2 malformed, 4 the subscription or connection caps, 11 unsupported kind. A thing the client's actor may not read is never a protocol error (§3).
- **Decoder limits** (spec/wire.md §13): `args` within `MAX_MESSAGE` and `MAX_VALUE_DEPTH`; a `write` batch at most 1024 ops; `secret` exactly 32 bytes. No new signature domain: a thin client signs nothing.
- **Where the code goes**: osis-proto decodes and encodes the kinds (`msg`); `ServingSession` hands them out as `ServingOutput::Request { id, kind, body }` instead of Error 11 (core/proto/src/serving.rs:348) and takes `ServingInput::{Reply, Notify}` back, so one send queue and one push accounting hold; no new session roles (the node never asks a client anything). The node's `SyncEngine` passes requests up as `Action::Request { conn, tier, .. }`, takes `Event::Reply { conn, id, frame }` and `Event::Notify { conn, frames }` (one per connection per engine change, batched), and emits `Action::Room { conn }` when held pushes drained. Semantics live in `osis` (`port/serve.rs`): the handle collects `Action::Request`s under its lock (core/osis/src/handle.rs:491 `after`) and runs them **after releasing it** on a port worker thread, one at a time per connection, as ordinary `Osis` calls acting as the session's actor (§3); the worker encodes replies and Notify payloads (never the lock holder) and feeds them back. The client side (`port/client.rs`, the `Remote` source) drives a proto `ClientSession` with `Command::{Auth, Call, Sub, Unsub}` through the same `Net` driver as any dial, so one connection carries its sync labels and its API traffic under one id space.
- **Port stall bounds** (notes/sync.md Hub stall bounds: the lock the sync driver needs is `eng`; each API call holds it for one engine transaction, as a local app's call does): per method row a cost bound comparable to honest sync work: reads O(one aspect) or one `stream_read` page; `write` at most 1024 ops within one frame (`MAX_MESSAGE`), the same bound a Sync's entries have; `revert` O(the reverted commit), itself bounded by having been applied; `register_schema` O(`MAX_SCHEMA_BYTES`); `query`: a page of `QUERY_PAGE` 256 hits (resource bound: 0 returns nothing, infinity materializes a group) evaluated O(items of the group) on Sub; afterwards a query subscription is marked dirty only by an engine change touching its group's closure (the dispatcher already resolves `groups_of` for signals in a group) and re-evaluated **incrementally** when push room opens: the changed items are placed against the page's bounds, O(changed items + page), never a rescan (a rescan only when a changed item carries no `ts` for the order, bounded as the Sub's evaluation). Notify evaluation batched per engine change (one lock acquisition per change for all of a connection's subscriptions, the dirty flags set off-lock by the dispatcher). Measured in (b) and (e): the worst row against one Sync pass.

## 3. Thin clients: registry, bearer Auth, acting as the client's actor
- **Registry**: `clients.0^` on the node's own thing (admin-only like `host.0^`, spec/data-model.md §9): `map<client actor tid, { secret_hash: blob (BLAKE3 of the bearer secret), until: option<timestamp> }>`. No scope fields: what a client may read and write is its actor's roles. Written by any admin of the node through the API: `db.add_client(until) -> (Tid, ClientSecret)` (mints the actor, grants this node admin on it as it is admin of its person, writes the entry, returns the 32-byte secret once; osis keeps only its hash), `db.clients()`, `db.remove_client(tid)`; CLI `clients add|ls|rm`. The node reads `clients.0^` when an engine event touches that aspect (as `host.0^`). The secret hash is readable by the account's devices (they read the node thing); they could serve the client too, if they ran the node's registry (not designed: one node serves a client).
- **The client's actor**: minted at `add_client` as a link's K is: a thing-record actor owned by the account (`Thing { owner: account }`, so its record names its owner), with secrets of its own and `keys.0` written by the node (the node administers it through the account, as it administers the person's things); never a key actor (that would need a second signing path and its record names no owner). Authorization is ordinary grants from any of the account's devices: `grant(G, client_actor, role, until)`; node-sync places its chain certificates under each group's labels as for any holder, so third devices can place its commits and name its actor (author node = the serving node, actor = the client's actor: the same shape as the node writing for its person); they judge the node's rights, not the actor's (below).
- **Bearer Auth**: `Auth [secret, session_id]` once per connection, over a transport pinned to the node's key (QUIC with the node's address key; a unix socket needs none: Owner); the sync engine hashes it and refuses an unlisted or expired hash itself (Error 1), so nothing of an unauthenticated keyed session reaches the worker; a match binds `(conn -> client actor)`. The secret is a capability: whoever holds it is the client (as a link's seed is the link); it travels only encrypted to the pinned node and is shown once at registration. A session that sent no Auth, Open or Call within `serve_open_ms` is closed as today; an authenticated session is exempt from `serve_idle_ms` while its connection is up. At most `MAX_CONNS_PER_CLIENT` 8 authenticated connections per client actor (resource bound: a further Auth is Error 4; 0 forbids clients, infinity lets one client fill the served pool); also the nonce sessions kept per client (§2).
- **Acting as the actor = the whole authorization**: every request of a client session runs on the worker as the client's actor: writes through `Mutation::confine` (the serving node checks that actor's rights before building the commit, `Permission` otherwise; the header's actor is the client's actor). **Only the serving node can enforce this**: receivers judge a commit by its author node's rights alone and the header's actor is attribution (core/engine/src/apply/validity.rs), so a third device accepts whatever the node, an admin of the account, may write, and a node that ignored the rule would be believed. That is the design's honest shape (the node holds the actor and its secrets), reads through the same acting actor: a thing the actor may not read (the permission model's `may_read`, osis-engine `labeling/actors`) reads as `UnknownThing`, exactly as a thing the node does not know (no existence oracle); `groups_of`, `roster`, `commits`, `status`, diagnostics and subscriptions (re-checked at each send, lapsing when the thing stops passing) all see what that actor sees; values never contain links, and tids inside values are names. One mechanism: no scope list, no Scoped view, no scope by kind, no "never granted" list; the person, its nodes, link seeds and K actors are unreadable to the client exactly when the crypto says so, and a grant to the client's actor on any of them is a real grant with real consequences, as for any holder. A created thing's owner must be writable by the actor; owner = the client's actor itself is refused (`Invalid`): the account's devices administer the client's things through the groups, and the actor goes away with the client.
- **Undo/redo/revert** are per actor: the client's actor's own commits, the local rule unchanged (notes/api.md Commits); several connections of one client share them, as several threads of one app do.
- **`until` and revocation**: `until` on the registry entry ends the client's sessions (an engine timer: `Event::Until`, the sync wake), so an expiry closes without another engine change; the owner also puts `until` on the grants. `remove_client` demotes the client's actor from every thing where it holds a grant (the normal removals with their rotations, spec/permissions.md §3), closes its connections and removes the entry; a demotion made on another device leaves an entry whose actor reads nothing (the rights check asks the roles). At the next `clients.0^` change the node ends sessions of removed entries. A leaked secret is revoked by `remove_client` (the actor goes) or rotated by `db.rotate_client_secret(tid)` (a new secret, the old hash gone, the actor kept).
- **Checked at execution**: the worker re-reads the entry (`until`) per request, not only at enqueue, and the engine's rights check runs per call as it does locally.
- **Secret custody** (client side): `Osis::attach(NodeAddr, ClientSecret, Config)`; the secret lives where the app keeps secrets (the OS keystore, else a 0600 file; the thin CLI keeps `client.secret` 0600 beside its config); a `Remote` shreds its copy on drop.
- **Owner tier** (§0): no entry, Auth without a secret (for the session id): the daemon's unix socket peer with the daemon's uid, node-authored as its person. Owner-only rows: the process-wide calls of §1, `add_client`/`clients`/`remove_client`/`rotate_client_secret` among them.
- Cost: one entry read per `clients.0^` change, one hash per Auth, the acting actor's rights check per call (what every local call pays), per client actor one actor's records and boxes (about 2.6 KB of boxes per grant, notes/permissions.md) and a label step entry where it is a reader as for any actor with secrets of its own.
- Tests (tier 1, through `InProcess`): a client granted Read on G reads G's things and `UnknownThing` for the person, its nodes, a link seed, another group and a thing only placed in G but owned elsewhere, indistinguishable from unknown tids; a write to a thing it has Read on is `Permission`; a thing created with the client's actor as owner is `Invalid`; its commits carry its actor and apply at a third device; undo reverts only its own commits; `until` closes with no other change; `remove_client` demotes, closes and the next Auth fails; an unknown or rotated secret never reaches the worker; a 9th connection is Error 4; the secret appears in no record (the hash does).

## 5. Transport adequacy
- Already given (spec/sync.md §10): TLS 1.3 only, ALPN `osis`, raw Ed25519 keys both ways, the dialed key pinned, a fresh client transport key per connection, no 0-RTT, no tickets: confidentiality, forward secrecy, node authentication. Adequate for plaintext.
- **Node listeners only**: the port is served on the node's own listeners (co-reader serving, core/node/src/sync/serve.rs:495 `accept`): the dialable key, LAN keys, the unix socket, and `Config.client_listen` URLs (`quic://host:port`, a node reachable over the internet). Never on the host address: the host hub (core/host/src/hub.rs) is osis-host's own `ServingSession` over `HostStore`, blind, with no engine handle, and stays so; a client of a hosting node dials its node address, not its host address (a forwarding from hub to node is not designed).
- **Client listener key**: `client_listen` listens with a **client secret** of its own (a local record like the host secret, made when the first `client_listen` URL is set, shredded when the last goes), not the dialable secret: the dialable key rotates (`rotate_reach`, a link ending, spec/permissions.md §9) and would strand every client. `NodeAddr` = `url#client_key` (the `HostAddr` form; `client_listen`, `serve --client-listen` and `clients rotate-key` print them). The client key rotates only by hand (`db.rotate_client_key()` (the old address fails `Network` for good), after which clients need a new address, handed out of band like a new link); a client dialing a dialable or LAN address (a co-reader that also queries) follows `reach.0` as co-readers do.
- **Client authentication** changes nothing in TLS: the bearer secret travels inside it; the transport key stays ephemeral and unlinkable (notes/networking.md decision 5 holds for clients).
- **Unix socket** (`unix://<path>`, new osis-transport impl over tokio `UnixStream`; Linux-first, macOS `LOCAL_PEERCRED` later): no TLS; the kernel authenticates. The transport type reports `Peer::Unix { uid }` from `SO_PEERCRED` on both sides (the `Connection` gains `peer() -> Peer::{Key(pk), Unix{uid}}`; `peer_key` stays for keyed transports); the dialer checks the listener's uid is its own, the listener accepts only its own uid, and the Owner tier is set from `Peer::Unix` alone, never from a key value (a transport that can report any peer key, `InProcess` or a WebSocket, can never reach it). **Path sockets only, never the Linux abstract namespace** (abstract sockets ignore mount namespaces and file modes). Path: `sun_path` is 108 bytes, so the socket lives at `$XDG_RUNTIME_DIR/osis/<BLAKE3(store path)[..8]>.sock`; without `XDG_RUNTIME_DIR` (a system unit, cron, a headless box without lingering) at `/tmp/osis-<uid>/`, created 0700 and checked before use (owner = uid, mode 0700, not a symlink, else refused); `<store>/sock` is a text file naming it (removed on exit; a stale one is replaced after a connect fails). **Who gets Owner**: every process of the daemon's uid that can reach the socket: other local users are refused by uid on both sides; root is refused by uid but can read the store anyway; a rootless container or a same-uid sandbox (Flatpak, Snap, a bind-mounted runtime dir) that reaches the socket gets Owner even when it cannot read the store files. Accepted: your uid is the owner. The socket directory is osis's own (`osis/` under the runtime dir, never `$XDG_RUNTIME_DIR` itself or a path sandboxes share by default).
- **Leaks**: the node sees everything (it holds the keys). A passive observer or relay sees frame sizes and timing of plaintext queries, correlating with value sizes and activity (Padmé pads blobs at rest, not frames); a connection that both syncs and queries shows which labels a reading client is interested in by timing. Accepted now (relay-metadata class, notes/networking.md Risks); frame padding is a later option. A blind host never sees API kinds.
- Browsers: a WebSocket transport (notes/networking.md decision 1) for thin clients and syncing browser nodes; TLS by the browser, the node's key checked in-session (Hello static key, open signatures). Later.

## 6. Mixing per group
- **Resolution**: a group synced locally is `Local` whatever a remote also offers (authoritative here, works offline); a group known only through one remote is that remote; through several, the one it was attached for (`routes`), else the first; a tid in no known group and unknown locally fails `UnknownThing`.
- **Moving** (as built, §8 Built (d)): `db.group_source(g, GroupSource::Local)` resumes syncing (the local node must hold the group's secrets: a device of a holder; a thin client cannot, it has no keys: a thin client that wants to sync becomes a node, a new device of the account), then waits for the node's writes at a host and this engine caught up, then drops the route; `GroupSource::Remote(addr)` waits for local writes at a host, records the route, stops syncing for this device only (`GroupPolicy::receipts_only`: `unsync` would replace the group's label for every holder, the node it moves to included). Routes persist as a local app record (`sources`); no secret is stored: `Config.remotes` carries the credentials, and without a store it is the whole routing (every group remote). CLI `group source G local|ADDR`.
- **Offline**: a call on a remotely sourced group while its connection is down fails `Network` at once; a `Watch::current()` returns `Err(Network)`; `status` shows `connected: false`. No stale reads. Writes offline fail `Network` (an offline-capable device syncs the group locally).
- **Client cache (step g, later)**: per (tid, ak) the last delivered value with the node's `seq`, valid only while its subscription is live (pushes maintain it; a lapsed or closed subscription invalidates every entry it fed); reads from cache only for watched aspects, never a plain `get` of an unwatched aspect, never offline (invariant: a cached value is one the node reported after the last change it saw); no write-through, no offline writes. Bounded by `materialize_limit` of cache bytes (evicting re-reads).
- **No-store profile**: `osis` with `default-features = false` drops `store` (osis-node and everything under it: engine, store, keys, perm, label, host, redb, tokio), keeping base, schema, proto, transport and the `Remote` source (no crypto, no commit, no crdt: a thin client signs nothing and merges nothing); `Osis::attach(NodeAddr, ClientSecret, Config)` with no local database. Every workspace member keeps `store` on, so feature unification stays selection-invariant (notes/build.md); the thin check is one extra artifact set (`cargo check -p osis --no-default-features`, later for `wasm32-unknown-unknown`), a gate step only when `osis` or its deps changed. **Owner decision**: a feature outside the networking set, against notes/architecture.md §4; the alternative (an `osis-client` crate with a second API type) duplicates the surface. A browser syncing node is the other profile: full `osis` over a worker-backed store and WebSocket; out of scope here.

## 7. Consequences
- **Queries** (issues/api-deferred.md) become required: a thin client cannot read a group item by item. Minimal surface: `query(Query::in_group(g).with(key).order(Order::Time).page(after, n)) -> Live<Vec<Hit<T>>>`, `n <= QUERY_PAGE`, `Hit { tid, value, ts, received }`; `Live` = the page plus a watch (remotely one Sub with a query filter, Notify on a change in the visible range). Implementation at the node: the group index times an aspect check, O(items) on Sub; incremental page updates from the changed items of the group afterwards (§2 Port stall bounds); a per-aspect index (notes/local-store.md) later. `backlinks` second. Filters, counts, text search: the design pass.
- **Undo/redo**: per actor, unchanged; a thin client's undo is its actor's own commits, the Owner's the node's person's (as every device of the person); a per-session undo is not offered (a third model).
- **CLI**: "one process per store" (notes/cli.md Design) goes away when a daemon runs: `osis serve` listens on the unix socket; every invocation that finds the store locked connects there as Owner and runs its command through the `Remote` source (same code, same output; `inspect` and `init`/`restore`/`pair join` stay local: exit 8 while locked); locked with no live socket stays exit 8. `serve` stays the one long-running command (systemd keeps it alive); `hosting set` and `clients add` then take effect live (closes issues/cli-own-admission.md's last point).
- **Control plane**: an orchestrator is a thin client whose actor holds Admin on the node's configuration group; it holds no role on the node thing or the person unless an admin grants one, so it configures the node's data, never the node. Node-level control stays the owner's devices (`host.0^`, `clients.0^` are admin aspects of the node thing).
- **Dogfood** (notes/dogfood.md): the first user. The host box runs `serve` as the daemon; the agent's `watch` and `create` become Owner clients, so "stop a running watch before any other command" goes; the other box attaches as a thin client whose actor is granted Write on the channel group (the channel group owns its messages: `create --owner $G`, as the recipe already does) instead of syncing it, or keeps syncing as a node (both must work: direction 6).
- Spec: spec/wire.md §11.1 (id rules, Notify) and §11.2 (kinds, codes, caps); spec/sync.md §10 (unix transport, bearer Auth over a pinned transport, node listeners, the client listener key); spec/data-model.md §9 (`clients.0^` as a registry). No sign-off needed before stability.

## Rejected
- A separate socket or program for the port: two transports, two authentications, two connection lifecycles; the owner wants one connection for both.
- One message kind per API method: a wire change per method; the method table inside `Call` grows without touching framing.
- Signed capability tokens: a second signature format and a revocation list; the `clients.0^` record is revocable data the owner already edits, synced like `host.0^`.
- **Client-signed commits** (owner decision): a client that signs a header without building the commit either needs the node's validation code (deltas, delete keys, lists) or its signature is meaningless; the node signs, as it does for its person.
- **Signing without a store**: a key without the state it signs about is a key actor that trusts its node for everything but the header; the node holding the client's actor and its secrets is honest about where the power sits.
- **Node-authored scope lists**: a scope language beside the permission model is two mechanisms for one thing, and a node-authored request carries the node's full power, so scope had to exclude by kind and filter outputs (the confused-deputy class); acting as the client's actor makes the engine's rights check the one bound.
- **Thin devices**: a device is a full admin of the person by the model (its secrets sealed to it), so a scoped one is a contradiction and an unscoped one is `pair`; a storeless process that wants full power is a thin client whose actor holds admin grants on everything the account owns, and pairing and the account's key rotation stay with real devices.
- A key actor per thin client (the owner's first form) over a thing-record actor: the node would sign as a second key, and a `KeyActor` record names no owner; the account-owned actor is the person's own machinery and its record carries the attribution.
- `NodeAddr` on the dialable key: it rotates with reach and would strand clients; a client listener key of its own.
- The Owner tier from key equality (peer key = listener key): any transport reporting an arbitrary peer key would have got it; it comes from the transport type's `Peer::Unix`.
- Abstract unix sockets: they ignore mount namespaces and file modes.
- Serving the port on the host address: the host hub is blind and has no engine handle.
- Values typed by the node: typing is a view, not data; the client decodes as locally.
- Running port requests under the handle lock: deadlock on re-entry, and a slow client would block the engine.
- Stale reads for remote groups offline: a value that may be wrong without saying so; the cache (g) is the bounded, labelled form.
- An `osis-client` crate with its own API type: duplicates the surface; one `Osis` with `Source` and a default feature instead (owner decision).
- Per-session undo: a third undo model beside per-actor and the admin view.
- Protocol Error 1 for a thing the client's actor may not read: an existence oracle beside `UnknownThing`; it reads as unknown.
- Full query re-evaluation per engine change: `MAX_QUERY_SUBS` × `max_clients` × O(items) per change; dirty by group, incremental by changed items instead.

# Client port: remote use of the API over the sync connection
> Summary: Design (owner direction, decided points listed first) for using the `osis` API from another process or device: per-group *sources* in the handle (local engine, or a connection to a node that holds the group's keys), API requests as new message kinds of the node-to-node protocol on the same connection as encrypted sync, credentials issued by the node's owner and enforced at the node's API boundary, authorship by the client's own node key by default, the daemon case (same protocol over a unix socket, peer uid), a no-store build profile, and the staged plan (tracking: issues/cli-proxy.md). Terminology: a *host* stores blind, a *node* holds keys and serves plaintext to its clients; no "server".

## Owner direction (decided)
1. Code in the node process uses the API without serialization.
2. Remote API requests and encrypted sync share one transport and one connection: a node stores plaintext it can read and hosts blind blobs; one connection may query the first while syncing the second.
3. A client may query or sync with any connected device, a peer included; peers are not treated differently from an always-on node.
4. Transport encryption must be adequate now that plaintext crosses it.
5. Browsers are one example of a thin client, not a rule: a syncing node may run in a browser, thin clients exist elsewhere.
6. A process holds any mix of locally synced groups and remotely queried ones; fully thin clients (no database, smaller binary) are worth supporting, but no process is assumed to be one kind.

Coordinator additions the owner accepted: the port is new message kinds in spec/wire.md §11, not a separate socket; the daemon is that protocol over a unix socket with a peer-uid check; a remote client is authenticated by a credential the node's owner issued, scoped to what it may read and write, enforced by the node at its API boundary; authorship of a remote write is the client's own node key when it holds one (default), else the node's on its behalf (explicit); moving a group between sources is a group-level operation like `group sync`.

## 1. Handle: sources
- `Osis` keeps `local: Option<Local>` (today's `Locked` + `Net`, core/osis/src/handle.rs:122-158) and `remotes: Vec<Remote>` (one per attached node: address, credential, port session state). A tid resolves to a `Source::{Local, Remote(idx)}` by `routes` (group -> source; a tid's groups by the local group index, else by the remote that reports it). Enum, no `dyn`: each API method is `match source { Local => today's body, Remote(r) => r.call(..) }`.
- **No cost on the local path**: `routes` is consulted only while `remotes` is non-empty (one atomic flag); with none, every call is today's code path. A `Write` batch touches one source (`Invalid` when its things resolve to two).
- **Per source** (by tid or group): reads (`get`, `at`, path, `stream`, `len`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`), watches (`watch`, `on_change`, `watch_thing`, `watch_roster`), `Write` batches, `commits`/`undo`/`redo`/`revert` (by scope), signals (`send_signal`, `on_signal`, `on_signal_in`), `edit_text`, `keep_alive`, queries, sharing calls on a thing (`grant`, `change_edge`, `share_into`, `leave`, `reach`, `holder_path`, `links`), `sync`/`unsync`/`sync_policy` of a group.
- **Process-wide, local only**: `create`/`open`/`restore`/`pair*`, `devices`/`remove_device`, `hosts`/`add_host`/`remove_host`, hosting, `rotate_reach`, bundles, `contact_card`/`import_contact`/`redeem`/`make_link`/`revoke_*`, `invite_*`, `set_stream`, `Internals`, `read(|r| ..)`. With no local database these fail `Unsupported("needs a local database")`. `me()`/`home()` come from the local database, else from the first attached node (one person per process; attaching a node of another person is `Invalid`). `node()` is this process's own node tid (it has one when it holds a node key, §4), else `Unsupported`. `now()` is local (the remote's clock offset is estimated by the session as for any peer). `status()` merges: local groups as today, each remote's groups filtered to the credential's scope, plus one `Remote { address, connected }` entry per attachment; `watch_status` likewise. Diagnostics: local sink; a remote's diagnostics about scoped things arrive as pushes into the same sink. Schemas (`register_schema*`) are process-wide and mirrored to each remote session (§2).
- **Watches** over a remote source are subscriptions (§2) whose pushes enter the one dispatcher queue as `Msg`s, so callbacks for remote and local changes run on the same thread in arrival order with the same coalescing (a watch holds the latest value). Initial value: the Sub reply carries it (atomic with the subscription at the node, as `watch()` is locally).
- **`Write`** records API ops (create, place, group ops, set/edit/replace/remove, path ops, delete, retention and expiry made explicit from the key at the op); locally `commit` turns them into the engine `Mutation` exactly as today; remotely the op list is the request. This is the one place existing code contradicts the design: core/osis/src/write.rs:30-33 builds `osis_node::Mutation` directly while recording, so the batch has no wire form.
- **Text sessions** work remotely: the buffer is client-side, `commit` is a batch (`edit(base, new)` on the text position, today's op), remote changes arrive by the session's watch; the idle timer runs in the client. **`keep_alive`** is renewed writes from the client; expiry handles a vanished client as it handles a crashed one.
- **Unsupported remotely, never faked**: `read(|r| ..)` (its guarantee is the engine's read lock across the closure; a node cannot hold it across round trips), `set_stream` (until streaming writes exist locally; issues/api-deferred.md), everything process-wide above, `Internals`. Each fails `Unsupported` naming the call.
- Errors: one `Error` enum; a remote call maps its wire error back to the same variant (§2); transport failure is `Network`.

## 2. Wire
New kinds of spec/wire.md §11.2 (version 1 grows; a peer without them answers Error 11 and the client reports `Unsupported("node too old")`). Framing, ids, Hello, WINDOW and push rules unchanged.
```
Auth    [24, id, client_pk, sig]            -> Ok | Error        sig: "osis v1 client auth" over BLAKE3([challenge, static_key])
Call    [25, id, method, args]              -> Reply [26, id, [0, result]] | Reply [26, id, [1, err_code, detail*]] | Error
Sub     [27, id, filter]                    -> Reply (initial value)        sub id = the request id
Unsub   [28, id, sub_id]                    -> Ok
Notify  [29, 0, sub_id, payload]            push, node -> client
Sign    [30, id, header]                    -> Signed [31, id, sig]          the only node-initiated request (§4)
```
- **Generic over typed keys and values**, not one kind per method: `method` is a small integer table (the API surface serialized: `get`, `get_path`, `len`, `stream_read(tid, ak, path, offset, len)`, `aspects`, `knows`, `groups_of`, `roster`, `role_on`, `owner_of`, `created`, `changed`, `same_thing`, `write(batch)`, `commits(query)`, `revert`, `undo`, `redo`, `send_signal`, `status`, `register_schema(bytes)`, `query`, `sync`, `unsync`, sharing calls); `args` a CBOR array of plain values. Adding a method is a table row, not a kind. An unknown method is Reply `[1, Unsupported]`.
- Things are named by tid, aspects by AK text, groups by tid, paths as `[step*]`; values travel as canonical CBOR `Value` (untyped). **Typing is the client's**: `AspectKey::decode` runs where the key is; a typed write is validated by the client's schema before it is sent (as locally). The node needs a schema for the structural diff of `set` (the `View`) and for undo write-back, so the client registers its schemas at the node per session (`register_schema`, held in memory for the connection; at most `MAX_SCHEMAS` 64, resource bound: 0 forbids typed sets, infinity lets one client fill memory). The node never stores a client's schema.
- **Subscriptions as pushes**: `filter` = the dispatcher's `Filter` (aspect, thing, roster, status, signal on thing, signal in group, diagnostics, query result). Notify carries the dispatcher's `Delivery` (value, `Source` with `CommitInfo`). Pushes obey the existing push rule (spec/sync.md §6 Flow control: one unwritten push frame; held pushes resume on `Taken`); per subscription the node keeps the latest delivery while held (coalescing as the local dispatcher does); signals are not coalesced: a per-subscription queue of `SIGNAL_QUEUE` 1024 fired signals (resource bound: past it the subscription lapses, Notify `[sub_id, lapsed]`, and the client re-subscribes; 0 drops every signal under backpressure, infinity lets a slow client hold unbounded memory; signals are best effort by contract). At most `MAX_SUBS` 4096 subscriptions per connection (the same bound as open labels; code 4 past it).
- **Flow control**: Call, Sub and Sign count against `WINDOW` with allowance `MAX_MESSAGE` (a read may return a large value); Auth and Unsub 64 KiB like every other small kind. A reply payload is bounded by `REPLY_BUDGET`: a value larger than that is `TooLarge { limit: REPLY_BUDGET }` remotely even when the app's `materialize_limit` is higher, and is read by `stream_read` pages of `STREAM_CHUNK` 1 MiB (performance switch: 0 moves nothing, infinity is one page bounded by `REPLY_BUDGET` anyway) or by path. The remote `materialize_limit` is `min(app limit, REPLY_BUDGET)`.
- **Errors**: Reply `[1, code, detail*]` maps 1:1 onto `Error` variants (`UnknownThing{tid}`, `UnknownActor`, `Permission{tid, needs}`, `Type{path, reason}`, `TooLarge{limit}`, `NotUndoable{commit, reason}`, `Unsynced{groups}`, `Invalid(m)`, `Storage(m)`, `Network(m)`, `Unsupported(m)`); protocol Error (kind 0) codes stay for the session: 1 refused (no credential, out of scope), 2 malformed, 4 rate limited (subscriptions), 11 unsupported kind.
- **Decoder limits** (spec/wire.md §13): `args` within `MAX_MESSAGE` and `MAX_VALUE_DEPTH`; a `write` batch at most 1024 ops (the per-message item cap); `header` in Sign is a commit header (its own limits).
- **Where the code goes**: osis-proto decodes and encodes the kinds (`msg`) and `ServingSession` hands them out as `ServingOutput::Request { id, kind, body }` instead of Error 11 (core/proto/src/serving.rs:348); replies and Notifies go back in through `ServingInput::{Reply, Notify}` so the one send queue and push accounting hold. The node's `SyncEngine` passes them up as `Action::Request { conn, client, .. }` and takes `Event::Reply`. Semantics live in `osis` (`port/serve.rs`): the handle collects `Action::Request`s under its lock (core/osis/src/handle.rs:491 `after`), runs them **after releasing the lock** on a port worker thread as ordinary `Osis` calls (re-entrancy: an API call inside `locked_in` deadlocks), one at a time per connection, and feeds `Event::Reply`. The client side (`port/client.rs`, the `Remote` source) drives a proto `ClientSession` with `Command::Call`/`Sub` through the same `Net` driver as any dial, so one connection carries its sync labels and its API traffic under one id space.
- On a connection to a node that also hosts, the two serving sides are the same `ServingSession` (host store for label kinds, the handle for API kinds); nothing new per connection.

## 3. Credentials
- **Form**: a record, not a token: `clients.0^` on the node's own thing (admin-only like `host.0^`, spec/data-model.md §9): `map<client_pk (32 B Ed25519), { scope, until: option<timestamp>, author: own | node }>`. Issued by any admin of the node (the person's devices) through the API: `db.add_client(pk, Scope, until, author)`, `db.clients()`, `db.remove_client(pk)`; CLI `clients add|ls|rm`. The owner can issue and revoke from any of its devices; the node learns it by sync like `host.0^`. No new signature format (the admin's commit is the signature); the node reads its own `clients.0^` once per engine change as it reads `host.0^`.
- **Presentation**: `Auth` once per connection, signed by the client key over the node's Hello challenge and static key (the open-proof shape, replay-proof, bound to this connection). The node answers Ok and remembers `(conn -> credential)`; Call/Sub before Auth is Error 1. A session that sent no Auth, Open or Call within `serve_open_ms` is closed as today; an authenticated session is exempt from `serve_idle_ms` while its connection is up (the transport's idle timeout and keep-alive detect a dead peer; no new number).
- **Scope** = `{ groups: set<tid> | all, aspects: set<ak> | all, role: Read | Write | Admin }`. A thing is in scope when a scope group holds it (`groups_of.within`), or it is a scope group itself. `Read`: reads, watches, queries, signals in. `Write`: batches, `send_signal`, undo/redo/revert in scope, `edit_text`. `Admin`: the sharing calls on scoped things and `sync`/`unsync`/`sync_policy` of scoped groups. `aspects` narrows reads, watches and writes to those AKs (role-class and `created.0` are readable by anyone in scope; writable by none).
- **Enforcement point**: the port server, before the API call: it resolves every tid of the request to its groups and checks scope and role; a subscription is checked at registration and each Notify is filtered again (a thing can leave scope). The node then reads with its own rights (the credential filters what the node could show, never widens it) and writes with its own rights check (`Permission` as locally) plus, for client-signed commits, the client node's.
- **Never granted**: the node's own thing and every `^` or role-class aspect of it (`host.0^`, `clients.0^`, `keys.0`...: not in any scope, so no credential changes hosting, hosts, devices or credentials), the person's secrets, pairing, restore, bundles, `rotate_reach`, link and card making, `Internals`. A credential is a view of data the node already reads, never a device of the person (unless `author: own`, §4).
- **Revocation**: remove the entry or let `until` pass; at the next engine change (`after`) the node closes the sessions whose credential is gone, expired or narrowed below what they use (as `holders_changed` closes co-reader sessions); a scope narrowed in place drops the subscriptions now out of scope.
- **Daemon's implicit credential**: the unix transport (§5) authenticates the peer by uid; a connection whose peer key is the listener's own (same uid) has scope `all, all, Admin, author: node` with no `clients.0^` entry and no Auth. Another uid is refused at accept.
- Cost: one record read per engine change, one signature check per connection, one `groups_of` per tid per request (the in-memory group index).

## 4. Authorship
- **Client-signed (default when the client holds a node key)**: the client is a device of the person with a node tid and signing secret and nothing else (`author: own` in its credential, keyed by that node's key). Per `write`: the node resolves and builds the commit from the op list against its state (deltas, pages, retention, delete keys), then sends `Sign [header]`; the client checks author = itself, actor, aspect list against what it sent, signs the commit ID and returns `Signed`; the node assembles, encrypts, applies and places the blob as any own commit, and answers the Call. Cost: one extra round trip per write; the node holds at most `MAX_PENDING_SIGN` 16 prepared commits per connection (resource bound: a client that never signs holds node memory; 0 forbids client-signed writes, infinity is unbounded); past it the Call fails `Invalid`. Dot form: session form `Session(client node, nonce)` with the nonce drawn by the node at Auth and counters per (aspect, connection) in node memory (issues/session-sources.md rule 1: a connection is a session start); until that design lands, commit form (`Form::Commit`, allowed for any author; the node cannot mint another node's node-form counters). The client needs no state: `edit(base, new)` carries its base, `set` diffs at the node.
- **Pairing without a store**: `Osis::pair` needs an engine, so a thin device joins through the node: `db.add_client(pk, scope, until, author: own)` on an admin device also writes the device grant for a new node thing with `pk` (what `pair_accept` writes), and the client's `node()` is that tid. The client holds only its secret; a thin client's identity file is 32 bytes.
- **Node-authored (explicit)**: `author: node` in the credential: the node is the header's author and the person the actor; no Sign, no counters, no round trip. Attribution reports the node (truthfully: it signed). Two such clients of one node are one actor and one node: their undo scopes interleave (per actor by default, notes/api.md Fixed directions). This is the daemon's mode (the CLI on the same uid is the owner at the keyboard).
- Which is default: own key when the credential says `own`, else node; a credential with `author: own` on a key that is not a device node's is `Invalid` at issue.

## 5. Transport adequacy
- Already given (spec/sync.md §10): TLS 1.3 only, ALPN `osis`, raw Ed25519 keys both ways, the node's key pinned by the address, a fresh client key per connection, no 0-RTT, no tickets: confidentiality, forward secrecy (ECDHE), node authentication. That is adequate for plaintext.
- **Address**: the client dials any listener of the node: its host address (if it hosts), its dialable key (`reach.0`: known to co-readers only), or the unix socket. `NodeAddr` = `HostAddr`'s form (`url#key`); `add_client` prints the addresses. No new listener: the port is served on every listener the node has, since authentication is in-session.
- **Client authentication** changes nothing in TLS: Auth binds the client key to the connection's challenge and static key, so the transport key stays ephemeral and unlinkable (notes/networking.md decision 5 holds for clients too).
- **Unix socket** (`unix://<path>`, new osis-transport impl over tokio `UnixStream`): no TLS; the kernel authenticates. The transport reports a peer key `BLAKE3("osis v1 unix peer" || le32(uid))` from `SO_PEERCRED` and the listener's key likewise from its uid, so the pinned-key check and the serving side's `accept(local, peer)` apply unchanged; a `uid` mismatch is `KeyMismatch`. Socket `<store>/sock`, mode 0600 inside `restrict_to_owner`'s directory.
- **Leaks**: the node sees everything (it holds the keys: nothing new). A passive observer or relay sees frame sizes and timing of plaintext queries, which correlate with value sizes and activity (Padmé pads blobs at rest, not frames); a connection that both syncs and queries shows which labels a reading client is interested in by timing. Accepted now (same class as relay metadata, notes/networking.md Risks); frame padding is a later option. A host that is not the node learns nothing (API kinds never reach a blind host).
- Browsers: a WebSocket transport (notes/networking.md decision 1) for thin clients and for syncing browser nodes; TLS by the browser (certificates: the node's key is then checked in-session by the Hello static key and open signatures, not by the transport). Later.

## 6. Mixing per group
- **Resolution**: a group synced locally is `Local` whatever a remote also offers (the local copy is authoritative here and works offline); a group known only through one remote is that remote; through several, the one it was attached for (`routes`), else the first; a tid in no known group and unknown locally fails `UnknownThing` (resolved against every source: one lookup each).
- **Moving**: `db.group_source(g, Source::Local)` = `sync(g)` (the local node must hold the group's secrets: it is a holder) then drop the route; `db.group_source(g, Source::Remote(node))` = `unsync(g)` (its label's local entries go as `unsync` drops them today) then record the route. Routes persist as a local app record (`sources`); without a store they live in `Config.remotes` and every group is remote. CLI `group source G local|ADDR`.
- **Offline**: a call on a remotely sourced group while its connection is down fails `Network` at once; a `Watch::current()` returns `Err(Network)`; `status` shows the remote `connected: false`. No stale reads: a value shown is what the node holds now, or an error. Writes offline fail `Network` (an offline-capable device syncs the group locally: that is what `group_source(.., Local)` is for).
- **Client cache (step g, later)**: per (tid, ak) the last delivered value with the node's commit `seq`, valid only while its subscription is live (pushes maintain it; a lapsed or closed subscription invalidates every entry it fed); reads from cache are allowed for watched aspects only, never for a plain `get` of an unwatched aspect, and never offline (invariant: a cached value is one the node reported after the last change it saw); no write-through, no offline writes. Bounded by `materialize_limit` of cache bytes (resource bound: evicting re-reads).
- **No-store profile**: `osis` with `default-features = false` drops `store` (osis-node and everything under it: engine, store, keys, perm, label, host, redb, tokio), keeping base, crypto, schema, proto, transport and the `Remote` source; `Osis::attach(NodeAddr, Secret, Config)` with no local database. Every workspace member keeps `store` on, so feature unification stays selection-invariant (notes/build.md); the thin check is one extra artifact set (`cargo check -p osis --no-default-features`, also for `wasm32-unknown-unknown` once a WebSocket transport exists), run as a gate step only when `osis` or its deps changed. **Owner decision**: this adds a feature outside the networking set, against notes/architecture.md §4; the alternative (an `osis-client` crate with a second API type) duplicates the surface. A browser syncing node (direction 5) is the other profile: full `osis` over a worker-backed store and WebSocket; out of scope here.

## 7. Consequences
- **Queries** (issues/api-deferred.md) become required: a thin client cannot read a group item by item. Minimal surface: `query(Query::in_group(g).with(key).order(Order::Time).page(after, n)) -> Live<Vec<Hit<T>>>` with `Hit { tid, value, ts, received }`; `Live` = the result plus a watch (remotely one Sub with a query filter, Notify on change in the visible range). First implementation at the node: the group index (`groups_of`, in memory) times an aspect check, O(items) per evaluation, re-evaluated per change in the group; a per-aspect index (notes/local-store.md) later. `backlinks` second. Filters, counts, text search: the design pass.
- **Undo/redo**: unchanged rule (per actor); a client-signed client's changes are the actor's like any device's. A per-session undo (only my connection's changes) is not offered: it would be a third model; a UI that wants it filters `commits()` by `node` (client-signed) and `revert`s.
- **CLI**: "one process per store" (notes/cli.md Design) goes away when a daemon runs: `osis serve` listens on `<store>/sock`; every invocation that finds the store locked connects there and runs its command through the `Remote` source (same code, same output); locked with no live socket stays exit 8. `serve` stays the one long-running command (systemd keeps it alive); `hosting set` and `clients add` then take effect live (closes issues/cli-own-admission.md's last point). `inspect` stays local-only (`Internals`).
- **Control plane**: an orchestrator is a client with an `Admin` credential on the node's configuration group; it reads status (scoped) and writes config as data. Nothing node-level is reachable through a credential (§3), so the orchestrator cannot take the node.
- **Dogfood** (notes/dogfood.md): the first user. The host box runs `serve` as the daemon; the agent's `watch` and `create` become clients, so "stop a running watch before any other command" goes; the other box attaches to it with a `Read`+`Write` credential on the channel group instead of syncing it (a thin client), or keeps syncing (both must work: direction 6).
- Spec: spec/wire.md §11.2 gains the kinds and codes; spec/sync.md §10 the unix transport and the client Auth rule; spec/data-model.md §9 `clients.0^`. No sign-off needed before stability.

Each branch merges alone (gate green), one worker and one reviewer. Owner decisions marked.

Tests: out-of-scope read refused (Error 1), narrowed scope drops a subscription, expiry closes, node thing never in scope, a hostile client cannot name `host.0^`. Spec: data-model §9, sync §10.

Tests: `cargo check -p osis --no-default-features`; one tier-1 test compiled in that profile is not possible in the workspace (unification): a `tools/gate.sh` step only.

## Picked numbers
`MAX_SCHEMAS` 64 (R), `SIGNAL_QUEUE` 1024 (R, lapse), `MAX_SUBS` 4096 (R, code 4; equals the open-label cap), `STREAM_CHUNK` 1 MiB (P), `MAX_PENDING_SIGN` 16 (R, `Invalid`); reused unchanged: `WINDOW`, `MAX_MESSAGE`, `REPLY_BUDGET`, `serve_open_ms`, `max_served`, QUIC idle and keep-alive. Each gets its row in notes/arbitrary-values-table.md when built.

## Rejected
- A separate socket or program for the port: two transports, two authentications, two connection lifecycles; the owner wants one connection for both.
- One message kind per API method: a wire change per method; the method table inside `Call` grows without touching framing.
- Signed capability tokens: a second signature format and a revocation list; the `clients.0^` record is revocable data the owner already knows how to edit, synced like `host.0^`.
- Values typed by the node (the node decodes with the client's schema and sends typed forms): typing is a view, not data; the client decodes as it does locally.
- Running port requests under the handle lock: deadlock on re-entry, and a slow client's request would block the engine.
- Stale reads for remote groups offline: a value that may be wrong without saying so; the cache (g) is the bounded, labelled form.
- An `osis-client` crate with its own API type for thin builds: duplicates the surface; one `Osis` with `Source` and a default feature instead (owner decision).
- Per-session undo: a third undo model beside per-actor and the admin view.

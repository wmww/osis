# Client port: remote use of the API over the sync connection
> Summary: Using the `osis` API from another process or machine: per-group *sources* in the handle (local engine, or a node that holds the group's keys), API requests as message kinds of the node-to-node protocol, served only on node listeners; a node acts for a client as an actor minted for it, so authorization is the permission model's grants and no scope language exists; stall and memory bounds per connection; the daemon case. Built: sources, the main actor's sessions, client actors, client listener (§8). Not built: queries, no-store profile, client cache (issues/cli-proxy.md). Terms: spec/requirements.md; no "server". What still separates nodes in code: issues/net-one-peer.md.

Words (spec/requirements.md Terms): a **client** is anything using the client protocol; a **thin client** is a client that is no node; a node may be a client too. Machine, transport and acting actor are independent. Which actors a client may act as is a node's policy; by default a unix socket offers the protocol to the node's own user as its **main actor**, and any other listener only as actors the client has authenticated for. osis-node's name for its tier is `Tier::Main`.

## Tess's direction
1. Code in the node process uses the API without serialization.
2. Remote API requests and encrypted sync share one transport and one connection: a node stores plaintext it can read and serves blobs it cannot read; one connection may query the first while syncing the second.
3. A client may query or sync with any connected node, a peer included; peers are not treated differently from an always-on node.
4. Transport encryption must be adequate now that plaintext crosses it.
5. Browsers are one example of a thin client, not a rule: a syncing node may run in a browser, thin clients exist elsewhere.
6. A process holds any mix of locally synced groups and remotely queried ones; fully thin clients (no store, smaller binary) are worth supporting, but no process is assumed to be one kind.

Coordinator additions Tess accepted: the port is new message kinds in spec/wire.md §11, not a separate socket; the daemon is that protocol over a unix socket with a peer-uid check; a client with its own actor is authenticated by a bearer secret issued at registration, and what it may read and write is the roles of the actor the node minted for it, enforced by the node acting as that actor with the engine's own rights check; the node does all crypto and signing for it; moving a group between sources is a group-level operation like `group sync`.


## 0. Who acts
- A **node** holds keys and a store and syncs the groups it chooses; a browser docs app syncing one document is a full node (cheap by design). Code in its process uses the API directly (direction 1). A process of the same uid talking to a node daemon over its unix socket is the node's own user: a session as the **main actor**: `Peer::Unix { uid }` equal to the daemon's uid, `me()` as actor, every API method except `read(|r| ..)`, `Internals`, `create`/`open`/`restore` and `Osis::pair` (the joining side) and `set_stream`. Default policy, not a rule of the model.
- A client with an actor of its own (a **client-actor session**, spec/sync.md §10: a thin client, or a node's `connect_node`) registers with a node (§3) and holds a bearer secret; a thin client holds no keys and no store and signs nothing. The node does crypto and syncing for it: at `add_client` the node mints a real actor for the client (the account its first admin, with secrets of its own and `keys.0`, as a sharer mints a link's K), and when serving that client it acts **as** that actor (`Osis::act_as`), so that actor's rights decide every read and write, checked by this node (§3). Attribution is visible: the client's actor authors its commits (header actor), the serving node is their author node, and the actor's creation record names the account.
- A node acting as several actors (its account and each client actor) is the same machinery as a node managing two accounts (issues/grant-rename-multi-actor.md).

## 1. Handle: sources
- A tid resolves to `Source::{Local, Node(connection)}` per call by the rule in `core/osis/src/sources.rs` (module comment; §8 Sources). Enum, no `dyn`: each API method is `match source`. One atomic flag (`Inner::routing`) in front: a process with no connection pays nothing. A `Write` batch touches one source (`Invalid` when its things resolve to two).
- **Per source** (by tid or group): reads, watches, `Write`s, `commits`/`undo`/`redo`/`revert` (by scope), signals, sharing calls on a thing, `sync`/`unsync` of a group.
- **Process-wide, local or the main actor's** (§0): `create`/`open`/`pair`, `pair_offer`/`pair_accept`, nodes, peers, serving, clients, `rotate_peer_address`, policies, bundles, cards, links, invites. Through a client-actor session they fail `Unsupported` (`serving` is `None` and `set_serving` refused: it is an aspect of the node's thing, read and written as such); so do they with no store here and no main-actor session. Never through a socket, for they need this process to be the node: `read(|r| ..)`, `Internals`, `listen_socket`, `client_listen`, `serving_address` (no command wants them), `connect_node`, `disconnect_node`, `group_source` (the connection and its secret are in the process, §8; the worker never waits on another node), `keep_alive`, `edit_text`. `me()`: the local account, through a main-actor connection the node's, in a client-actor session its client actor (`home()` is that actor, `node()` the serving node's tid: these return `Tid`, they cannot fail). Connecting to a second node as a different actor is `Invalid` (one acting actor per process). `status()` merges local groups, each remote's groups the actor may read, and one `NodeConnection { address, connected }` per connection.
- **Watches** over a remote are subscriptions whose pushes enter the one dispatcher queue, so remote and local callbacks run on the same thread in arrival order. Initial value: the Sub's Reply (atomic with the subscription at the node, as `watch()` locally).
- **`Write`** records API ops (`WriteOp`); locally `commit` turns them into the engine `Mutation`; remotely the op list is the request.
- **Reconnect contract**: `port/client.rs` module comment, what the caller sees case by case.
- **Unsupported remotely, never faked**: `read(|r| ..)` (its guarantee is the engine's read lock across the closure), the process-wide calls above (but for the main actor), `Internals` (panics on a handle with no store: test and `inspect` hooks). What the client's actor may not read is not Unsupported: it reads as `UnknownThing` (§3).
- **Not built, the plan**: text sessions buffer client-side and `commit` a write (`edit(base, new)` on the text position), remote changes by the session's watch, idle timer in the client; `keep_alive` is renewed writes from the client, expiry covering a vanished client. Until then both are `Unsupported`.
- Errors: one `Error` enum; a wire error maps back to the same variant (§2); transport failure is `Network`, from every call: no read answers a default when the node cannot answer. `Unsupported`: this kind of handle does not carry the call. `Refused`: the node will not take this session (secret, uid, or a serving address with no client port). A watch of a thing or its grants started while down fails `Network`; `on_status_change` and `on_diagnostic` need no answer to start and come up with the connection (`port/client.rs` module comment); `on_diagnostic` fails `Refused` once the node has ended the session. `group_sources()` alone stays infallible: it reads this process's own table, empty without a store.

## 2. Wire
Kinds 24-29 of spec/wire.md §11.2. The method table and filters: `core/osis/src/port/mod.rs`; values: `port/codec.rs`. A row is the main actor's alone unless `method::for_client` lists it (a new row is denied until listed; add it to `answers` in `port_clients.rs`). Rows without a port row yet (keep_alive, edit_text, queries) fail `Unsupported`.
- Values as canonical CBOR `Value` (untyped). **Typing is the client's**: a typed write is validated by the client's schema before it is sent. The node needs the schema for the structural diff of `set` and undo write-back: a main-actor session registers its schemas (`register_schema`, process-wide and kept, at most `MAX_SCHEMA_BYTES` of distinct source per node, so registering again on a new connection is free). The node never stores a client's schema; thin clients have no such row.
- **Reply allowance** (spec/sync.md §6 Flow control): a Call or Sub counts its frame plus `max_reply` against `WINDOW`; `max_reply` is `SMALL_REPLY` (16 KiB) by default, at most `REPLY_BUDGET`; a Call answered `TooLarge` is retried once under the materialization bound, large values read by `stream_read` pages of `STREAM_CHUNK` or by path. Small reads keep many Calls in flight beside Sync and Fetch traffic. A request handed out keeps its frame plus allowance counted across inputs until answered (`asked_bytes`): a client pipelining past `WINDOW` is closed as for sync.
- **Subscriptions as pushes**: a Notify carries a delivery under the existing push rule. Above `max_reply` it goes as `[2, source]`, and the client reads by `stream_read`/path; not even that fitting, `[1]` (lapsed). The worker makes the same checks on the encoded frame first (a Sub's initial reply above `max_reply` is answered TooLarge and its subscription dropped), so a subscription is never live at one side only and `MAX_SUBS` bounds the worker's. A fired signal's delivery has a fifth item `true`.
- **Memory per connection is bounded in bytes**: a held subscription keeps dirty state and the source of the last change, nothing materialized; the worker materializes when push room opens (`Action::Room`), so held state is O(subscriptions). Signals and diagnostics are never coalesced: one per-connection budget `SIGNAL_BYTES`; past it the subscription whose delivery does not fit lapses and the client subscribes again.
- **Writes**: `write`, `revert`, `undo`, `redo` carry a client `nonce`, a sequence number from 1 per `session_id` (16 random bytes in Auth, the same across reconnects, new per client process), taken on the client's I/O thread as each command is sent, so threads sharing a handle never send them out of order. The node keeps outcomes per (identity, session): the last `WRITE_NONCES` per session; at most as many sessions per identity as its connection cap, the least recently used going. Rule, and what an app does with `OutcomeUnknown`: §8 Reconnect.
- **History**: row `HISTORY [tid, ak, from, limit, max bytes] -> [[entry*], more, complete]` (a client row, as the actor: a hidden thing's page is an unknown tid's; `max bytes`: what one reply carries), filter `[6, tid, ak]`, a Notify per commit `[change, Opt(entry)]`, read when sent. A subscription holds the IDs waiting (`HISTORY_DIRTY_BYTES` each against `SIGNAL_BYTES`, past it a lapse), reads at most `HISTORY_SEND` per send. The client maps a Reply after the first, a closed connection and a Notify too large to `HistoryEvent::Reread`, a lapse to `Ended`.
- **Settling**: `settle` is a row, answered once the connection has nothing dirty left, so a client's `settle` sees every delivery before it. Reply and Notify are not ordered against each other.
- **Rows that wait** (`wait_synced`, `redeem`, `import_contact`; `set_role` and `revoke_link` are plain calls, `remove_node` is `set_role`, then `LINKS`) are a Sub filter `[5, method, [arg*]]`, never a Call: the worker serves everyone and must not block, and a Call has a stall timer. The worker polls the node's own async call only when its waker fires (its waiters polled after every change, as a local app's); the Reply carries `Opt(outcome)` when known at once, else the one Notify. Same rule as at the node; no row takes a timeout (the client's own runtime bounds it, dropping the future). The answer reaches the future from the connection thread, not by the dispatcher. Dropping the client's future is an Unsub, which drops the node's future: the same as dropping a local one, a redeem's key forgotten too. A connection ending before the outcome is `Network` at the client and what was done stays done (a redeem may have joined); never resent. At most `MAX_WAITS` per connection (past it `Invalid`). The main actor's only. A running one holds the node (the async calls take `&self`), so the last user handle going sends `Job::Closing`: each is told `Closed` and dropped, and a new one is refused while no user handle is left.
- **Bundles** do not fit a frame: `EXPORT_BUNDLE` builds it on the connection, `BUNDLE_READ` pages it out, `BUNDLE_WRITE` pages one in, `IMPORT_BUNDLE [length]` runs it (a reconnect loses the pages, so a wrong length is `Network` and runs nothing). The main actor's only; held per connection (an export until its last page was read), in memory as the local calls hold it. Limit: one export at a time per handle (two threads' would read each other's pages; a bundle that does not parse then says so at import).
- **Errors**: Reply `[1, code, detail*]` maps 1:1 onto `Error` variants; protocol Error (kind 0): 1 for a Call or Sub without Auth or an unknown secret, 2 malformed, 4 the subscription or connection caps, 11 unsupported kind (client: `Refused`: what answered serves no client port). A thing the client's actor may not read is never a protocol error (§3).
- **Decoder limits** (spec/wire.md §13): `args` within `MAX_MESSAGE` and `MAX_VALUE_DEPTH`; a `write` (`[nonce, actor, [ak*], [op*], expires?]`, the commit's expiry) at most `MAX_WRITE_OPS` ops; `secret` exactly 32 bytes. No new signature domain: a thin client signs nothing.
- **Layers**: `osis_proto::api` and `ServingSession::with_port` (sessions on a serving address answer these kinds Error 11) answer the protocol themselves: Call/Sub/Unsub before an answered Auth (1), a Sub reusing a live id (2), `MAX_SUBS` (4), every Unsub after Auth (Ok; the request goes up as a notice). The upper layer asks for push room (`WantRoom`) and gets `Room { budget }` when the push rule allows. The node's `SyncEngine` passes requests up as `Action::Request { conn, tier, msg }`, emits `Room`, `Authed`, `Ended`, takes `Event::{Reply, Notify, WantRoom, End}`; nothing of an unauthenticated keyed session goes up (`admit`). Semantics live in `osis` (`port/serve.rs`). The client side is `port/client.rs`, a proto `ClientSession` on a thread of its own, not the `Net` driver: the protocol allows one connection for both (direction 2), nothing uses that yet.
- **One worker thread per node** serves every connection, one request at a time, off the handle lock, each as ordinary `Osis` calls: a slow call delays other clients' calls, never the sync driver beyond its own engine transaction. Per-connection workers would not shorten the worst stall (a `write` holds `eng` for its whole commit; issues/cli-proxy.md Follows). A panic in a job ends that job's session at once, others go on, nonces kept (`top` set before the write runs, so its retry is unknown).
- **Port stall bounds** (notes/flow-control.md Hub stall bounds): per row a cost comparable to honest sync work: reads O(one aspect) or one `stream_read` page; `write` at most `MAX_WRITE_OPS` within one frame; `revert` O(the reverted commit); `register_schema` O(`MAX_SCHEMA_BYTES`); bundles O(what they copy), and each step of a row that waits as the same step locally: the main actor's only, who could run them on the node anyway. Notify evaluation batched per engine change, dirty flags set off-lock by the dispatcher. Planned for queries: a page of `QUERY_PAGE` evaluated O(items of the group) on Sub, then dirty only by a change touching its group's closure and updated incrementally, O(changed items + page).

## 3. Client actors: registry, bearer Auth, acting as the client's actor
- **Registry**: `clients.0^` on the node's own thing (admin-only like `host.0^`, spec/data-model.md §9): `map<client actor tid, { secret_hash, until }>`. No scope fields. `db.add_client(until) -> (Tid, ClientSecret)` (mints the actor and writes the entry and its home membership in one engine transaction, `Engine::mint_actor`; `until` not in the future is `Invalid`; the secret from `OsRng`, shown once), `clients()`, `remove_client(tid)`, `rotate_client_secret(tid)`; CLI `clients add|ls|rm|rotate`. The secret hash is readable by the account's nodes; they could serve the client too if they ran the registry (not designed: one node serves a client).
- **The client's actor**: minted as a link's K is: a thing-record actor whose first admin is the account, with secrets of its own and `keys.0`, administered by this node through the account; never a key actor (a second signing path). Authorization is ordinary grants from any of the account's nodes. Third nodes hold its commits and name its actor (author node = the serving node, actor = the client's actor); they judge the node's rights, not the actor's.
- **Bearer Auth**: once per connection, over a transport pinned to the node's key (never a unix socket: `connect` refuses one); the sync engine hashes it and refuses an unlisted or expired hash itself (Error 1), so nothing of an unauthenticated session reaches the worker. The secret is a capability, as a link's seed is the link. An authenticated session is exempt from `serve_idle_ms`. At most `MAX_CONNS_PER_CLIENT` connections per client (Error 4); an authenticated client leaves `max_served` for its own count against `max_clients` (apart from the unix sessions, so clients never lock the node's user out).
- **The rule**: `SyncEngine::client_of(conn)` (entry there, same `secret_hash`, before `until`) is asked by the port worker at every request and every send (`Worker::session`, invariant in the module comment of `port/serve.rs`), and every row runs on `Osis::act_as(actor)`: `Reader` answers as unknown for what `Engine::readable_by` denies, `Mutation::confine` makes `Engine::write` check the actor's rights first, reverts use `Engine::revert_as`, `commits` and `status` filter by the same. No cached scope or role. `client_of` decodes `clients.0^`, O(clients) under `eng`, per request and send. A call that passed `session` just before a revocation is ordered before it. `act_as` is `pub(crate)` (`Internals::acting_as` for tests): the sharing, sync and process-wide calls do not honour it.
- **Only the serving node can enforce this**: receivers judge a commit by its author node's rights, and its header actor only by whether the node acts for it (write on the actor, spec/permissions.md §5.2: true for a client actor whose first admin is the account, so a removed client's actor still passes), never by the actor's rights on what it writes (a purge is the exception: it drops only what its node and the actor both may, spec/permissions.md §6). A client's earlier commits stay valid after a demotion, and so does what it wrote after a demotion made on another node and before this node heard of it, on things the node administers by its own path (on a foreign group the node's only path is through the actor, so the demotion's frontier applies). What the actor does decide: purge rights of `author` retention (spec/permissions.md §6), the delete key of the commit, the dedup secret of a linked header.
- **One mechanism**: no scope list, no scoped view, no "never granted" list; the account, its nodes, link seeds and K actors are unreadable to the client exactly when the crypto says so. A thing it may not read reads as `UnknownThing`, exactly as an unknown tid (no existence oracle). `for_client` is the structural gate; the per-method `Reader::hidden` check is the second layer, kept because a gate on `Reader` alone misses read leaks review found (`groups.0`, a group scope): a new `Reader` method must add the check. Subscriptions are re-checked at each send, lapsing when the thing stops passing; one it never could read stays silent, as for an unknown tid, even through a move of its group.
- **`check_confined` judges the mutation, not the call that recorded it**: its aspects, creates, deletes, purges (write; what drops receivers judge), and every tid a `group.0` op adds (readable or created in the batch, `UnknownThing` otherwise). A created thing's first admin must be writable by the actor; the client's actor itself as first admin is `Invalid`, so `Write::create()` is `Invalid` in a client-actor session and it takes `create_with_admin(g)` (CLI `create --admin G`), needing write on `g`. A client writes no link (`replay`, code 8): one of a hidden value would send that blob under the labels of what it writes.
- **Kept copy** (spec/permissions.md §3, `Engine::copy_readable_by`): `readable_by` passes a thing of a copy for an actor that is a holder the copy hangs on (`K/`), or holds a role now both on its first admin (its creation record's) and on such a holder, through a kept holder too; so an app with a role on the account, or with its own edge on the chat removed saying retain, reads what the account kept, and a client on neither reads as for an unknown tid. A client that is only a member of a holder group, joined before the kick or after it, reads the group and no copy: a group's later members would otherwise read what the group held. Live, not recorded at the removal: the account's app registered later reads it, and one whose role on the account ended does not. Reads, watches, `commits`, `retained_copies` (filtered) follow; a write finds no role (`Permission`, not unknown: the copy is no secret from it); `drop_retained_copy` stays the main actor's row. `role_on` is `None`: how an app tells a copy. A client placing a copy in a group it writes is refused (`Permission`, `check_confined`); the node's main actor may, and that shows the group's readers the name only. A client's edge saying erase while its account's says retain reads nothing though the node holds the copy. A watch goes on with no lapse: the drop runs in the step that applied the kick. One whose role ended gets nothing more and lapses at the next change of the thing, which on a frozen copy may be when it goes: what it holds is what it had read.
- **Revert**: needs the actor's rights on all the commit touched and on each write it really makes, checked on the built deltas (`undo_in`, `revert_inner`: one source), and lists nothing the actor may not read; refused rather than partial. Undoing a creation deletes as `Write::delete` does: memberships in groups the actor may not write stay, unsaid (a refusal would tell of a hidden group). A refused undo blocks that scope's undo (nothing older instead, as for a compacted commit); a narrower scope and revert by id still reach older commits. Undo/redo are per actor; several connections of one client share them.
- **Placing a hidden thing does not send its data**: entitlement (spec/sync.md §3) judges the group's actor, and anyone reading the group also reads what that actor reads, so only the name reaches its readers. The check exists for no oracle and no listing; a readable subgroup holding hidden items may still be added. `undo`/`untie_now`: unplacing a tied item removes the tied edge with the node's rights; the rule removes it anyway.
- **`until` and revocation**: `Served.client.until` reaches `serve_wake`/`serve_timers`, so an expiry closes without another change; a `clients.0^` change is seen in `engine_events` (`clients_changed`); a session's bound `secret_hash` is compared at each check, so a rotation ends it too. `remove_client` is synchronous, its demotions `PreSync::Synced` (a client actor's commits are all this node's): entry ended (`until` 0, so a clock moved back revives nothing), demotions, entry gone; a failure or crash halfway is retried by calling again; an arbitrary actor is never demoted (no entry: `false`). A demotion made on another node leaves an entry whose actor reads nothing.
- **Secret custody** (client side): the app's keystore, else a 0600 file; the thin CLI keeps it in a 0600 file named by `--client-secret`.
- **Main-actor sessions** (§0): no entry, Auth without a secret (for the session id): the daemon's unix socket peer with the daemon's uid, as its account.
- A client call cannot block forever on a node that vanishes: unix EOF, QUIC idle 60 s, then the session's `STALL_TIMEOUT_MS` on any call in flight without bytes; that also bounds a live node whose worker stalled (4 min measured: the first timer counts the sent bytes as progress). Each dial and Auth, and how long a write in flight waits across a drop, are bounded by `CONNECTION_WAIT` (a sync call has no future to drop; `connection_wait` in `Knobs` for tests). `Connection::end` (`disconnect_node`) closes its command channel, so the thread goes though a wait still holds the `Connection`. `source_node`'s `HOLDS` runs on a thread of its own (`call_pending`): a `Call` blocks its caller, which a timeout around an async call could not then end. A caller of `connect` races its own timeout around the call.

## 5. Transport adequacy
- Already given (spec/sync.md §10): TLS 1.3 only, ALPN `osis`, raw Ed25519 keys both ways, the dialed key pinned, a fresh client transport key per connection, no 0-RTT, no tickets: confidentiality, forward secrecy, node authentication. Adequate for plaintext.
- **Node listeners only**: the port is served on the node's own listeners (`accept_peer`): the dialable key, LAN keys, the unix socket, `client_listen` URLs. Never on the serving address: that code has no engine and no keys, by design (`osis-host`); a client of a serving node dials its node address (a forwarding from hub to node is not designed).
- **Client listener**: `client_listen(&[url]) -> Vec<Address>` is a call, not a `Config` field (needs the bound port back; CLI `serve --client-listen`), not persisted: call it at each start; the key is. Listens with a **client secret** of its own (a local record, made when the first URL is set, shredded when none is left), not the dialable secret: the dialable key rotates (`rotate_peer_address`) and would strand every client. Address = `url#client_key` (`Address`). `rotate_client_address()` keeps the URLs; old addresses fail `Network` for good, new ones go out of band. Replacing listeners ends their sessions (their connections hold the UDP socket) and retries the bind for `REBIND_WAIT`. It serves the client port alone (`ServingSession::port_only`, Error 11 to Open, Deposit...): a thin client holds no labels, a co-reader syncs on the dialable key; a process wanting both on one connection dials a dialable key.
- **Slots**: `link::Slots::Pending(client_pending)` for client listeners: authenticated connections (`Action::Authed` -> driver -> `Link::authed`) leave the count, the oldest pending gives way to a newcomer from another source, a source already holding the most is refused. Same pool at the engine (`Served::public`), so a flood there costs co-readers' `max_served` nothing. Unix sessions: the `max_clients` pool.
- **Client authentication** changes nothing in TLS: the bearer secret travels inside it; the transport key stays ephemeral and unlinkable (notes/networking.md decision 5 holds for clients).
- **Unix socket** (`unix://<path>`; Linux-first): no TLS; the kernel authenticates. `Connection::peer() -> Peer::{Key, Unix { uid }}` from `SO_PEERCRED` (own uid by a socket pair, no unsafe code); the dialer checks the listener's uid is its own, the listener accepts only its own uid, and the main-actor tier is set from `Peer::Unix` alone, never from a key value (a transport that can report any peer key can never reach it). **Path sockets only, never the abstract namespace**. Path rules: `socket_path` inside `osis` (`$XDG_RUNTIME_DIR/osis/`, else `/tmp/osis-<uid>/`, created 0700 and checked, the name a hash of the store's path): `Osis::listen_socket` and `Osis::connect_socket(store_dir)` agree on it (a killed daemon's socket stays: clients fail to connect, the next `serve` replaces it). `Multi` listens on `unix://` but never dials it (a published address cannot point the sync driver at a local socket); `listen` replaces only a dead socket file; a listener's drop removes the file only while it is still its own; an accept error is retried after `ACCEPT_RETRY`. **Who acts as the main actor**: every process of the daemon's uid that can reach the socket; a rootless container or same-uid sandbox that reaches it does so even when it cannot read the store. Accepted: there is no security boundary within a uid.
- **Leaks**: the node sees everything (it holds the keys). A passive observer or relay sees frame sizes and timing of plaintext queries, correlating with value sizes and activity (Padmé pads blobs at rest, not frames); a connection that both syncs and queries shows which labels a reading client is interested in by timing. Accepted now (relay-metadata class, notes/networking.md Risks); frame padding is a later option. A node serving data it cannot read never sees API kinds.
- Browsers: a WebSocket transport (notes/networking.md decision 1) for thin clients and syncing browser nodes; TLS by the browser, the node's key checked in-session (Hello static key, open signatures). Later.

## 6. Mixing per group
- **Resolution**: §8 Sources. **Moving**: `db.group_source(g, GroupSource)`, doc comment in `sources.rs`; CLI `group source G local|ADDR`. Group sources persist as a local app record (`sources`); no secret is stored: `connect_node` brings the credentials after each open, and `connect` is the whole routing of a thin client. A thin client that wants to sync becomes a node, a new node of the account.
- **Offline**: a call on a remotely sourced group while its connection is down fails `Network` at once; an `on_change` hears `Err(Network)`; `status` shows `connected: false`. No stale reads. Writes offline fail `Network` (a node that must work offline syncs the group itself).
- **Client cache (step g, later)**: per (tid, ak) the last delivered value, valid only while its subscription is live (pushes maintain it; a lapsed or closed subscription invalidates every entry it fed); reads from cache only for watched aspects, never a plain `get` of an unwatched aspect, never offline (invariant: a cached value is one the node reported after the last change it saw); no write-through, no offline writes. Bounded by `materialize_limit` of cache bytes (evicting re-reads).
- **No-store profile**: `osis` with `default-features = false` drops `store` (osis-node and everything under it: engine, store, keys, perm, label, host, redb, tokio), keeping base, schema, proto, transport and the `Source::Node` path (no crypto, no commit, no crdt: a thin client signs nothing and merges nothing); `Osis::connect(&[NodeLogin], AppConfig)` with no local store. Every workspace member keeps `store` on, so feature unification stays selection-invariant (notes/build.md); the thin check is one extra artifact set (`cargo check -p osis --no-default-features`, later for `wasm32-unknown-unknown`), a gate step only when `osis` or its deps changed. **Tess's decision**: a feature outside the networking set, against notes/architecture.md §4; the alternative (an `osis-client` crate with a second API type) duplicates the surface. A browser syncing node is the other profile: full `osis` over a worker-backed store and WebSocket; out of scope here.

## 7. Consequences
- **Queries** (issues/api-deferred.md) become required: a thin client cannot read a group item by item. Minimal surface: `query(Query::in_group(g).with(key).order(Order::Time).page(after, n)) -> Live<Vec<Hit<T>>>`, `n <= QUERY_PAGE`, `Hit { tid, value, ts, received }`; `Live` = the page plus a watch (remotely one Sub with a query filter, Notify on a change in the visible range). Implementation at the node: the group index times an aspect check, O(items) on Sub; incremental page updates from the changed items of the group afterwards (§2 Port stall bounds); a per-aspect index (notes/local-store.md) later. `backlinks` second. Filters, counts, text search: the design pass.
- **Undo/redo**: per actor, unchanged; a thin client's undo is its actor's own commits, a main-actor session's the account's (as every node of it); a per-session undo is not offered (a third model).
- **CLI** (notes/cli.md Design): while a daemon runs, `osis serve` listens on the unix socket and every invocation that finds the store locked connects there as the main actor and runs its command through the `Source::Node` path (same code, same output; `inspect` and `init`/`restore`/`pair join` stay local: exit 8 while locked); locked with no live socket is exit 8. `serve` is the one long-running command (systemd keeps it alive); `serving set` and `clients add` take effect live.
- **Control plane**: an orchestrator is a thin client whose actor holds Admin on the node's configuration group; it holds no role on the node thing or the account unless an admin grants one, so it configures the node's data, never the node. Node-level control stays the account's nodes (`host.0^`, `clients.0^` are admin aspects of the node thing).
- **Routes for client actors**: a thing granted to a client's actor at another node reaches that node through the actor's inbox (its first admin's, the account's home); the node syncs the labels of what the actor may read, so the client reads the thing once a label carries it. `status` through a client's connection shows `NotCarried` for a thing it holds a role on that no label here carries (`Engine::unrouted`, filtered by `readable_by`), and clears once the granter's `sync` gives it one.
- **Dogfood** (notes/dogfood.md): each Claude's store runs `serve` as a daemon, so its `watch` and posts are main-actor clients side by side. A box could instead connect as a client with its own actor, granted Write on the channel group, rather than syncing it as a node: both must work (direction 6).

## 8. As built
Further steps (e) `query-min`, (f) `thin-profile`, (g) `client-cache`: issues/cli-proxy.md. Until (f), a process with no store has a scratch memory store standing in (dispatcher, clock, records for `create`).

### Sources
- **The rule** (`sources.rs` module comment states the invariant; `decide_in` is the whole of it): for a thing `t`, S = `t` and the groups holding it here. No store: the connections. A group in S sourced at another node: that node, connected or not, whatever else holds it. Known here: this engine. Else the connections in order, the first knowing it, an unreachable one stopping the search. No cache: decided per call under `eng` from the engine's own index, one atomic flag (`Inner::routing`) in front so a process with no connection pays nothing. A local write checks again under its commit's lock (`guard_local`, `guard_change`), so a move between source decision and commit fails it (`Network`) instead of stranding it. `Source::Node` holds the connection (`port::client::Connection`); a group source naming none gets `Connection::absent`, which fails `Network`, so `source` itself cannot fail and there is no path to another source.
- **Split** (a thing with a route, in a group carrying it that syncs here or routes elsewhere; `split_in`): reads stay on the route, writes are `Invalid` naming both groups, `Status.two_sources` lists it, moving either group ends it. Why a state and not refused steps (refusing at `group_source` or at adding to a group, or letting local win): another holder of H can share `t` into H at any time and this node only hears later, so a refusal could not remove the state, only add steps around it; refusing at the write covers every way in with one check. Writes refuse because a write through the route would go out only under what the source node syncs, which may not include H (no write is acknowledged and silently not sent), and asking the source node to forward is one more trust and one more round trip; a node that does sync both loses the convenience (route H too). A plain membership carries nothing, so it splits nothing, and adding `t` to H never flips a read. This engine hears of a new member in a G sourced elsewhere only through a group it syncs (G's own commits stop here), so a thing here does not go remote by surprise. Left: reads through the route miss what only H carries while split unless a node bridges the two; that is why `status` lists it. `commits` over H still list what this engine holds of `t`: history, not a current value. `undo`/`redo` over a group check its whole closure (as `status`), and `revert` of a commit not held here (a write through a route never comes here) refuses while anything is split: only the node knows what they would touch. A write already past the check when the split arrives is ordered before it; nothing can tell. The check comes after the route, so a move between them cannot slip past it (`a_split_made_after_the_route_refuses_the_write`). A check costs a closure walk only with routes: `status` per commit, under `eng`.
- Moving away uses `receipts_only`, not `unsync`: the label is shared, its replacement would have stopped every holder. Consequently a Read holder can move a group too, and "both" (routed and syncing) is a legal state that reads remote: a crash or a failed wait between the two steps leaves that, never a local copy answering while behind.
- Every other process-wide call stays gated on `!has_store()` (`Inner::client`): a node with connections keeps its own `serving`, `nodes`, `read`... `read(|r| ..)` is `Unsupported` while routes exist: a transaction over this engine would read routed groups' stale copies. `node_uploaded` polls STATUS (a client row), since a client with its own actor may not `wait_synced`.
- A write through a connection acts as this process's actor **at that node** (its client actor), `me()` staying the local account; only an explicit `Write::act_as` is sent as named (and refused). `create`'s first admin must be something the client may write there (the group).
- A move ends every watch whose source it changes: one last `Err(Network)` (`Delivery::Moved`, a remote one `PortEvent::Closed`); watch again. Rebinding a local watch onto a remote would be a second subscription machine for a rare event. A worker's subscription for a node's own client lapses. A main-actor Sub of a routed thing through a daemon is `Unsupported`.
- A node's client reads nothing the node holds only stale: `Engine::readable_by` denies a thing held only through receipts-only groups, whose read would otherwise be silently old. Acting handles never route (they would run as the node's actor at the other node).
- **Sharing flows** take the same guard as a write (`Osis::guarded`), each engine step under its lock. `set_role`, `revoke_link` and `remove_client`'s removals of a routed thing are `Unsupported` (no port row; move home first): run here they would commit to a copy that does not sync, and the revocation would silently not leave. Left out on purpose: `untie_now` (a stranded tied-edge removal is redone by the holders' obligation, and it is only a commit that goes out on the way home), `redeem` (K's label, followed). `set_hosts` (saved peers) skips groups sourced elsewhere.
- **The port worker never waits on another node** (`on_worker`): a main-actor call that routes elsewhere through a daemon is `Unsupported`, as its Sub is; `status` through it shows the connection's up/down without asking it; `settle` and schema mirroring skip the connections. The dispatcher also asks no connection for a status. Otherwise one silent connection would stall every client of the node for minutes, unbounded under a remote that trickles bytes (the stall timer counts them).
- **Catching up**: `Engine::core.routed_away` mirrors the routes: a node's own client reads a routed group as unknown until the route goes, also after syncing resumed on the way home. It holds for acting handles only (`readable_by` has no other caller), is rebuilt from the `sources` record at open, before any session; a thing also in a local group is unreadable too: its write would be refused and its copy misses the route.
- **Trust in rule 4**: a store-holding process sends every tid it does not know to its first connection (with several: asks each in order whether it holds it (row `HOLDS`: its creation is here, content or not)). So each connection learns the tids asked about, and whichever says yes first answers reads and takes writes, with nothing to check that against: a thin client verifies nothing, and a route only binds things this engine knows are in the group. Connect only to nodes you trust for everything you do not hold here (issues/cli-proxy.md Follows).
- Costs: per call on a handle with connections one `eng` lock and one `groups_of`; with several connections a thing unknown here costs one `HOLDS` round trip per connection before its call: the one place "no cache" costs real time, and a store-less process has 2+ only if they answer as one actor.

### Reconnect
- `Io` outlives connections, with subscriptions, schemas and writes in its tables. What the caller sees, case by case: `port/client.rs` module comment.
- **A resend is marked** (`NONCE_RESENT`, bit 62, a `TooLarge` retry's too): without it a session entry evicted by LRU would make an old nonce look new. A repeat of a remembered nonce gets its first result; at or below the highest seen and not remembered is `OutcomeUnknown`; above is new. A marked nonce `done` does not hold runs only under an entry not born from a resend, or after that session's next unmarked write (`Nonces::lost`): the first resend after lost state must not unlock the next. Consequence: a session's first writes, resent, are `OutcomeUnknown` even when they never ran (safe, visible, until its next new write). The marks alone decide safety, across a restart too, so there is no node epoch.
- **What an app does with `Error::OutcomeUnknown`** (code 12): the write may have applied; a repeat is a new nonce, so a blind repeat can apply twice; read, repeat if absent. Exactly-once tests need a non-idempotent op (`count_key`): a `set` of an equal value commits nothing, so a second run does not show.

Their 0/∞ lines are in that table; not built yet: `MAX_QUERY_SUBS` 0 forbids live queries, ∞ multiplies O(changed items) per change without bound; `QUERY_PAGE` 0 returns nothing, ∞ materializes a group. ## Rejected
- A separate socket or program for the port: two transports, two authentications, two connection lifecycles; Tess wants one connection for both.
- One message kind per API method: a wire change per method; the method table inside `Call` grows without touching framing.
- Signed capability tokens: a second signature format and a revocation list; the `clients.0^` record is revocable data an admin already edits, synced like `host.0^`.
- **Client-signed commits** (Tess's decision): a client that signs a header without building the commit either needs the node's validation code (deltas, delete keys, lists) or its signature is meaningless; the node signs, as it does for its account.
- **Signing without a store**: a key without the state it signs about is a key actor that trusts its node for everything but the header; the node holding the client's actor and its secrets is honest about where the power sits.
- **Node-authored scope lists**: a scope language beside the permission model is two mechanisms for one thing, and a node-authored request carries the node's full power, so scope had to exclude by kind and filter outputs (the confused-deputy class); acting as the client's actor makes the engine's rights check the one bound.
- **Thin nodes**, as a default: a node of an account is a full admin of it (its secrets sealed to it), so a scoped one needs another threat model than this default's; an unscoped one is `pair`. A process with no store that wants full power is, by default, a thin client whose actor holds admin grants on everything the account administers. Other policies are open (issues/client-auth.md).
- A key actor per thin client over a thing-record actor: the node would sign as a second key, and a `KeyActor` record names no first admin; the actor under the account is the account's own machinery and its record carries the attribution.
- `NodeAddr` on the dialable key: it rotates with reach and would strand clients; a client listener key of its own.
- The main-actor tier from key equality (peer key = listener key): any transport reporting an arbitrary peer key would have got it; it comes from the transport type's `Peer::Unix`.
- Abstract unix sockets: they ignore mount namespaces and file modes.
- Serving the port on the serving address: that code has no engine and no keys.
- Values typed by the node: typing is a view, not data; the client decodes as locally.
- Running port requests under the handle lock: deadlock on re-entry, and a slow client would block the engine.
- Stale reads for remote groups offline: a value that may be wrong without saying so; the cache (g) is the bounded, labelled form.
- An `osis-client` crate with its own API type: duplicates the surface; one `Osis` with `Route` and a default feature instead (Tess's decision).
- Per-session undo: a third undo model beside per-actor and the admin view.
- Protocol Error 1 for a thing the client's actor may not read: an existence oracle beside `UnknownThing`; it reads as unknown.
- Full query re-evaluation per engine change: `MAX_QUERY_SUBS` × `max_clients` × O(items) per change; dirty by group, incremental by changed items instead.

# Client port: remote use of the API over the sync connection
> Summary: Using the `osis` API from another process or machine: per-call *sources* (local engine, or a node this process is a client of), API requests as message kinds of the node-to-node protocol, served on every listener of a node (its one key); a node acts for a client as an actor minted for it, so authorization is the permission model's grants and no scope language exists; stall and memory bounds per connection. Built (`core/osis/src/port/`): the wire kinds, the client registry (`clients^.0`, `add_client`), the node side (Auth for main sessions over the unix transport and client actors by secret, `MAX_CONNS_PER_CLIENT` and `max_clients`, the session's end checked per request and per Notify, the rows of spec/wire.md §11.2's method table: reads, sharing reads, stamps, status, write, undo/redo/revert, value/thing/grants/status subscriptions, write nonces) and the client side (`connect`, `connect_socket` as thin clients on a scratch node; `connect_node`, `group_source`, `disconnect_node`; reconnect with marked resends). Not built: every other row of §2 (commit listings, backlinks, sharing writes, links, bundles, schemas, streams, rows that wait; their API calls are `Unsupported` through a connection), the commit, backlink and waiting filters, a Notify's dirty flag (a push without room lapses), group hand-off (issues/group-source-hand-off.md), queries, no-store profile, client cache (issues/cli-proxy.md). Terms: spec/requirements.md; no "server".

Words (spec/requirements.md Terms): a **client** is anything using the client protocol; a **thin client** is a client that is no node; a node may be a client too. Machine, transport and acting actor are independent. Which actors a client may act as is a node's policy; by default a unix socket offers the protocol to the node's own user as its **main actor**, any other listener only as actors the client authenticated for. Wire rules (Auth, session end, a client actor's rights, nonces, `max_reply`): spec/wire.md §11.2 Client port and spec/sync-opens.md §4; this note holds the method table and the design.

## Tess's direction
1. Code in the node process uses the API without serialization.
2. Remote API requests and encrypted sync share one transport and connection: a node serves plaintext it can read and blobs it cannot; one connection may do both.
3. A client may query or sync with any connected node, a peer included.
4. Transport encryption must be adequate for plaintext.
5. Browsers are one example of a thin client, not a rule: a syncing node may run in a browser.
6. A process holds any mix of locally synced and remotely queried groups; fully thin clients (no store, smaller binary) are worth supporting, but no process is assumed to be one kind.

Also accepted (designed below): the port as message kinds, the daemon over a unix socket with a peer-uid check, bearer secrets, the node acting as a minted actor and doing all crypto, moving a group between sources as a group-level operation.

## 0. Who acts
- A **node** holds keys and a store and syncs the groups it chooses (a browser docs app syncing one document is a full node). A process of the daemon's uid on its unix socket (`Peer::Unix { uid }`) is a session as the **main actor**: `me()` as actor, every API method but those §1 lists as never through a socket. Default policy, not a rule of the model.
- A **client-actor session** (spec/sync-opens.md §4: a thin client, or a node's `connect_node`) registers with a node (§3) and holds a bearer secret; a thin client holds no keys or store and signs nothing. At `add_client` the node mints a real actor for the client (the account its first admin, secrets of its own and `keys.0`, as a sharer mints a link's K) and serves it **as** that actor (`Osis::act_as`), so the actor's rights decide every read and write (§3). Attribution: the client's actor is the header actor, the node its author node, and the actor's creation record names the account.
- A node acting as several actors is the machinery of a node managing two accounts (issues/grant-rename-multi-actor.md).

## 1. Handle: sources
- A tid resolves to `Source::{Local, Node(connection)}` per call (§8 Sources). Enum, no `dyn`: each API method is `match source`. A `Write` batch touches one source (`Invalid` when its things resolve to two).
- **Per source** (by tid or group): reads, watches, `Write`s, listings (`writes`, `fired`), `undo`/`redo`/`revert` (by scope), signals, sharing calls on a thing, `sync` of a group.
- `revert` names a commit, not a thing: on a thin client it goes to its one node (`Unsupported` with several); a store-holding process reverts here, refusing a commit on a thing read elsewhere.
- **Process-wide, local or the main actor's**: `pair_offer`/`pair_accept`, nodes, peers, serving, clients, `rotate_peer_address`, policies, bundles, cards, links, invites. In a client-actor session, or with no store and no main-actor session, they fail `Unsupported` (`serving` is `None`, `set_serving` refused: it is an aspect of the node's thing). **Never through a socket**, as they need this process to be the node: `read(|r| ..)` (its guarantee is the engine's read lock across the closure), `Internals` (panics without a store), `listen_socket`, `listen`, `connect_node`, `disconnect_node`, `group_source` (the connection and its secret live in the process; the worker never waits on another node), `keep_alive`, `edit_text`, `set_stream`, `Osis::create`/`open`/`restore` and `Osis::pair` (the joining side). Nothing is faked: what the actor may not read is no `Unsupported` but `UnknownThing` (§3).
- `me()`: the local account; through a main-actor connection the node's; in a client-actor session its client actor (`home()` that actor, `node()` that node's tid; infallible). A second connection as a different actor is `Invalid` (one acting actor per process). `status()` on a thin client merges its nodes' STATUS (each as §3 Status shows it; `Network` when one cannot be reached); `on_status_change` there tells a node that cannot be reached as `connected` 0 and its things `NotConnected`, and comes up with the connection. A store-holding process's `status` is its own (not built: its connections' groups, `NodeConnection { address, connected }`).
- **Watches** over a remote are subscriptions whose pushes enter the one dispatcher queue, so remote and local callbacks run on one thread in arrival order. Initial value: the Sub's Reply, atomic with the subscription.
- **`Write`** records API ops (`WriteOp`); locally `commit` builds the engine `Mutation`, remotely the op list is the request.
- **Not built**: text sessions buffer client-side and `commit` a write (`edit(base, new)` on the text position, remote changes by the session's watch, idle timer in the client); `keep_alive` as renewed writes from the client, expiry covering a vanished client. Both `Unsupported` through a connection.
- **Errors**: one `Error` enum, a wire error mapping back to the same variant (§2); transport failure is `Network` from every call (no read answers a default). `Unsupported`: this kind of handle does not carry the call. `Refused`: the node will not take this session (secret, uid). A watch of a thing or its grants started while down fails `Network`; `on_status_change` and `on_diagnostic` need no answer and come up with the connection; `on_diagnostic` fails `Refused` once the node ended the session. `group_sources()` alone is infallible: it reads this process's table.

## 2. Wire
Kinds 24-29 (spec/wire.md §11.2, which holds the method table; `osis_proto::api`; `port::method`, `port::filter`). Every row there serves client actors too, each read as the actor; a main-only row (sharing writes, process-wide calls) is code 11 for a client. API calls with no row yet (`keep_alive`, `edit_text`, queries) fail `Unsupported`.
- Values are canonical CBOR `Value` (untyped). **Typing is the client's**: a typed write is validated by the client's schema before sending. The node needs schemas for the structural diff of `set` and undo write-back: a main-actor session registers them (`register_schema`, process-wide and kept, at most `MAX_SCHEMA_BYTES` of distinct source per node, so registering again on a new connection is free). The node never stores a client's schema; thin clients have no such row.
- **Reply allowance** (spec/sync-streams.md §1 flow control): a Call or Sub counts its frame plus `max_reply` (default `SMALL_REPLY`, at most `REPLY_BUDGET`) against `WINDOW`, so small reads keep many Calls in flight beside Sync and Fetch. A Call answered `TooLarge` is retried once under the materialization bound; large values are read by `stream_read` pages of `STREAM_CHUNK` or by path. A request handed out stays counted until answered (`asked_bytes`): a client pipelining past `WINDOW` is closed as for sync.
- **Subscriptions as pushes**: a Notify carries a delivery under the push rule; above `max_reply` it goes as `[2, source]` (the client reads by `stream_read` or path), not even that fitting `[1]` (lapsed). The worker checks the encoded frame first (a Sub's initial reply above `max_reply` is answered TooLarge and dropped), so a subscription is never live at one side only and `MAX_SUBS` bounds the worker's.
- **Memory per connection is bounded in bytes**: a value subscription is a watch on the node's dispatcher holding the digest of its last value, nothing materialized; each change is read as the session's actor and pushed under the push rule (spec/sync-streams.md §2), and one whose Notify finds no room lapses (`[1]`, pushed whatever the room) and the client subscribes again. Planned with the commit filter: fired ephemeral signals and diagnostics never coalesced, one per-connection budget `PUSH_BYTES`.
- **Writes**: `write`, `revert`, `undo`, `redo` carry a `nonce` (rules: spec/wire.md §11.2 Write nonces), numbered under the handle's lock as each is sent, so threads sharing a handle never send out of order. A write is `[nonce, actor, [ak*], [op*], Opt(expiry)]` (`Write::wire`): the recorded `WriteOp`s, aspects by index into the AK list, the node typing each AK as it types it; a text session's placement ops do not cross. A remembered nonce gets its first outcome marked or not. The session id (16 random bytes in Auth) is the same across reconnects, new per client process. The node keeps the last `WRITE_NONCES` outcomes per (identity, session), and as many sessions per identity as its connection cap, least recently used going. Resends and `OutcomeUnknown`: §8 Reconnect.
- **Commits**: `LISTING [address, query, max bytes] -> [[commit*], more, complete]`, address `[0, scope]` (a scope's writes; an aspect's is `Scope::Aspects` naming it), `[1, tid, ak]` (a signal's fires) or `[2, tid, ak, commit id]` (a fire's versions; not a filter); `LISTED_COMMIT [address, commit id] -> Opt(commit)`; a part is `[tid, ak, valid, body, Opt(edited place)]`, a fire op `[10, tid, key, value, Opt(replaces)]`. For a client: a hidden thing lists nothing (as an unknown tid), a commit carries only parts its actor may read. Filter `[6, address]`: a Notify per commit `[id, Opt(commit)]`, read when sent; a commit with no readable part takes no budget and is not told; a fired ephemeral signal's commit, held by nobody, is encoded when it fires and queued against `PUSH_BYTES`. Waiting IDs cost `COMMIT_DIRTY_BYTES` each against `PUSH_BYTES` (past it, a lapse); at most `COMMIT_SEND` read per send. The client maps a Reply after the first, a closed connection and a too-large Notify to `CommitEvent::Reread`, a lapse to `Ended`. `UNDO_TARGET`/`REDO_TARGET` answer `Opt(commit)`; `WRITE`, `UNDO`, `REDO`, `REVERT` the commit made.
- **Backlinks**: `BACKLINKS [tid, query] -> page`, query `[Opt([tid, ak]), Opt(limit)]`, page `[[[tid, ak]*], more]`; for a client only sources it may read, whoever may read the target. Filter `[7, tid, query]`: a Notify with the page when it reads otherwise (a reference row naming the thing changed, or for a client any roster or key change; dirty flag, read when sent; a page reading as last sent sends nothing, since the wake may come from what the actor may not read). The client asks with a reply bound the largest page fits (`BACKLINK_PAGE` backlinks of the longest AK), so a page never fails `TooLarge`.
- **Settling**: `settle` is a row answered once the connection has nothing dirty, so it sees every delivery before it. Reply and Notify are not ordered against each other.
- **Rows that wait** (`wait_synced`, `redeem`, `import_contact`; `set_role`, `revoke_link` are plain calls, `remove_node` is `set_role` then `LINKS`) are a Sub filter `[5, method, [arg*]]`, never a Call: the worker serves everyone and must not block, and a Call has a stall timer. The worker polls the node's async call when its waker fires; the Reply carries `Opt(outcome)` when known at once, else one Notify comes, reaching the future from the connection thread, not the dispatcher. No row takes a timeout: dropping the client's future is an Unsub, which drops the node's (a redeem's key forgotten too). A connection ending first is `Network` at the client; what was done stays done, never resent. At most `MAX_WAITS` per connection (past it `Invalid`). Main actor only. The last user handle going sends `Job::Closing`: each running one is told `Closed`, new ones refused.
- **Bundles** do not fit a frame: `EXPORT_BUNDLE` builds it on the connection, `BUNDLE_READ` pages it out, `BUNDLE_WRITE` pages one in, `IMPORT_BUNDLE [length]` runs it (a reconnect loses the pages: a wrong length is `Network` and runs nothing). Main actor only; held per connection in memory. Limit: one export at a time per handle (two threads would read each other's pages; the import then fails to parse).
- **Errors**: Reply `[1, code, detail*]` maps 1:1 onto `Error` variants; protocol Error (kind 0): 1 no Auth or unknown secret, 2 malformed, 4 caps, 11 unsupported kind (client: `Refused`). A thing the actor may not read is never a protocol error (§3).
- **Decoder limits** (spec/wire.md §13): `args` within `MAX_MESSAGE` and `MAX_VALUE_DEPTH`; a `write` (`[nonce, actor, [ak*], [op*], expires?]`) at most `MAX_WRITE_OPS` ops. No new signature domain.
- **One loop per node** serves every connection: the one feeding the node's inputs (`ReadOnly::step`) answers each request after its step, one at a time, off the handle lock, as ordinary `Osis` calls: a slow call delays other clients and that node's inputs. A Sub registers and answers under one hold of the lock, so no Notify of it goes before its Reply. Per-connection workers would not shorten the worst stall (a `write` holds `eng` for its whole commit; issues/cli-proxy.md Follows). A panic in a job ends that session alone, nonces kept (`top` set before the write runs, so its retry is unknown).
- **Port stall bounds**: each row costs about honest sync work: reads O(one aspect) or one `stream_read` page; `write` at most `MAX_WRITE_OPS` in one frame; `revert` O(the reverted commit); `register_schema` O(`MAX_SCHEMA_BYTES`); bundles O(what they copy), a row that waits as the same step locally (main actor only). Notify evaluation batched per engine change, dirty flags set off-lock by the dispatcher. Planned for queries: a page of `QUERY_PAGE` evaluated O(items of the group) on Sub, then dirty only on a change in its group's closure, updated O(changed items + page).

## 3. Client actors: registry, bearer Auth, acting as the client's actor
- **Registry**: `clients^.0` on the node's own thing (admin-only like `host^.0`, spec/data-model.md §9): `map<client actor tid, { secret_hash, until }>`, no scope fields. `db.add_client(until) -> (Tid, ClientSecret)` mints the actor and writes the entry and its home membership in one engine transaction (`Engine::mint_actor`; `until` not in the future is `Invalid`; secret from `OsRng`, shown once); also `clients()`, `remove_client(tid)`, `rotate_client_secret(tid)`; CLI `clients add|ls|rm|rotate`. The account's nodes can read the hash, but one node serves a client.
- **The client's actor** is a thing-record actor like a link's K: first admin the account, secrets of its own and `keys.0`, administered by this node through the account; never a key actor (a second signing path). It gets ordinary grants from any of the account's nodes. Third nodes judge the node's rights, not the actor's.
- **Bearer Auth** (spec/wire.md §11.2 Auth): once per connection, over a transport pinned to the node's key (`connect` refuses a unix socket); the sync engine checks it, so nothing of an unauthenticated session reaches the worker. The secret is a capability, as a link's seed is the link.
- **Status** (row 21, filter 3): a client actor sees the things with a sync ID here that it may read (`readable_by`), and as `connected` the connections that are a source of one of them; a thing it may not read changes neither, so a hidden group's sync tells it what a never-known one does (nothing). Its own client actor has a sync ID and is listed. Not the node's connection count: that counts every connection, its own client connection included.
- **The rule**: the worker checks the client entry (present, same `secret_hash`, before `until`) at every request and every send, and every row runs on `Osis::act_as(actor)`: `Reader` answers as unknown what `Engine::readable_by` denies, `Mutation::confine` makes `Engine::write` check the actor's rights first, reverts use `Engine::revert_as`, listings and `status` filter alike. No cached scope or role; `client_of` decodes `clients^.0`, O(clients) under `eng` per request and send. A call that passed `session` just before a revocation is ordered before it. `act_as` is `pub(crate)` (`Internals::acting_as` for tests): sharing, sync and process-wide calls do not honour it.
- **Only the client's node can enforce this** (spec/wire.md §11.2; a removed client's actor still passes spec/permissions.md §5.2; a purge drops only what node and actor both may, spec/permissions.md §6). So a client's earlier commits stay valid after a demotion, as does what it wrote after a demotion made elsewhere and before this node heard, on things the node administers by its own path (on a foreign group its only path is the actor, so the demotion's frontier applies). The actor does decide: purge rights of `author` retention, the commit's delete key, a linked header's dedup secret.
- **One mechanism**: no scope list or scoped view; the account, its nodes, link seeds and K actors are unreadable to the client exactly when the crypto says so. A thing it may not read reads as `UnknownThing`, as an unknown tid (no existence oracle). `for_client` is the structural gate; the per-method `Reader::hidden` check is a second layer, kept because review found read leaks a gate on `Reader` alone missed (`groups.0`, a group scope): a new `Reader` method must add it. Subscriptions are re-checked at each send and lapse when the thing stops passing; one never readable stays silent, even through a move of its group.
- **`check_confined` judges the mutation, not the call that recorded it**: its aspects, creates, deletes, purges (write; what drops receivers judge), and every tid a `group.0` op adds (readable or created in the batch, else `UnknownThing`). A created thing's first admin must be writable by the actor and not the actor itself, so `Write::create()` is `Invalid` here and the client uses `create_with_admin(g)` (CLI `create --admin G`). A client writes no link (code 8): a hidden value's link would send that blob under the labels of what it writes.
- **Kept copy** (spec/permissions.md §3, `Engine::copy_readable_by`): `readable_by` passes a thing of a copy for an actor that is a holder the copy hangs on (`K/`), or holds a role now both on its first admin and on such a holder (through a kept holder too); so an app with a role on the account, or whose own removed edge said retain, reads what the account kept; a mere member of a holder group reads no copy (later members would otherwise read what the group held). Judged live, not at the removal. Reads, watches, listings, `retained_copies` follow; a write finds no role (`Permission`: the copy is no secret from it); `drop_retained_copy` is main actor only; `role_on` is `None` for a copy. A client placing a copy in a group is refused (`Permission`); the main actor may, showing the group's readers the name only. A watch goes on through the kick with no lapse; one whose role ended lapses at the thing's next change.
- **Revert and undo**: need the actor's rights on all the commit touched and on each write really made, checked on the built deltas (`undo_in`, `revert_inner`), listing nothing the actor may not read; refused rather than partial. Undoing a creation deletes as `Write::delete`: memberships in groups the actor may not write stay, unsaid. A refused undo blocks that scope's undo (as a compacted commit does); a narrower scope or revert by id still reach older commits. Undo/redo are per actor, shared by a client's connections; a main-actor session's are the account's. No per-session undo (a third model).
- **Placing a hidden thing sends no data**: entitlement (spec/sync-judgement.md §1) judges the group's actor, and the group's readers read what it reads, so only the name reaches them. The check exists for no oracle and no listing; a readable subgroup holding hidden items may be added. `undo`/`untie_now`: unplacing a tied item removes the tied edge with the node's rights.
- **`until` and revocation**: a session's end is checked at each request and each Notify (spec/wire.md §11.2), so an ended session gets no answer and hears nothing more; its connection stays until the client drops it, and no timer closes it: an ended session holds no slot under the caps and its client's write outcomes go at the next Auth (which drops every ended session and the outcomes of every client that can no longer authenticate), so what it leaves is bounded by the clients that can; a `clients^.0` change ends what it removes; the bound `secret_hash` is compared at each check, so a rotation ends the session. `remove_client` is synchronous (a client actor's commits are all this node's): entry ended (`until` 0, so a clock moved back revives nothing), demotions, entry gone; a crash halfway is retried by calling again; an arbitrary actor is never demoted (no entry: `false`). A demotion made on another node leaves an entry whose actor reads nothing.
- **Secret custody** (client side): the app's keystore, else a 0600 file; the thin CLI's is named by `--client-secret`.
- **Main-actor sessions**: no entry; Auth without a secret (for the session id) from the unix peer of the daemon's uid.
- **No call blocks forever**: unix EOF, QUIC idle 60 s, then `STALL_TIMEOUT_MS` on the oldest call in flight without reply bytes, which also bounds a live node whose worker stalled (4 min measured: the first timer counts sent bytes as progress). Notifies ahead of a `settle` move its stall clock up to `MAX_AHEAD` bytes (spec/sync-streams.md §1), so a slow client reading a burst keeps its session; under endless churn a `settle` waits unbounded and still closes past that. Each dial and Auth, and how long a write in flight waits across a drop, are bounded by `CONNECTION_WAIT` (`connection_wait` in `Knobs` for tests). `HOLDS` runs on its own thread (`call_pending`), so a timeout can end it. A caller of `connect` races its own timeout.

## 5. Transport adequacy
- TLS as spec/sync-opens.md §4 gives it (1.3 only, raw Ed25519 keys both ways, dialed key pinned, fresh client key per connection, no 0-RTT or tickets) is adequate for plaintext. The bearer secret travels inside it; the client's transport key stays ephemeral and unlinkable (notes/networking.md decision 5).
- **Every listener** serves the port under the node's one key (spec/sync-transport.md §5, one key): the dialable key's (`Osis::listen(&[url]) -> Vec<Address>`, a call since it returns the bound port, not persisted; CLI `serve --listen`), LAN keys, the unix socket. Address = `url#key`. `rotate_peer_address` moves every listener to a new key: old addresses fail `Network` for good, new ones go out of band (Unsure in issues/sync-rewrite.md). Replacing listeners ends their sessions and retries the bind for `REBIND_WAIT`.
- **Connections**: no count limit (spec/sync-transport.md §5); a flood costs memory only. A client's connection is a client connection of its process's own sync node (`osis_sync::Node::connect`): it sends no Prove, so it proves no actor, keeps no record, opens nothing and no pair rule closes it beside a sync connection to the same node (spec/sync-transport.md §6).
- **Unix socket** (`unix://<path>`, Linux-first): no TLS, the kernel authenticates. `Connection::peer() -> Peer::{Key, Unix { uid }}` from `SO_PEERCRED`; the dialer checks the listener's uid is its own, the listener accepts only its own uid, and the main-actor tier comes from `Peer::Unix` alone, never a key value. **Path sockets only, never the abstract namespace** (it ignores mount namespaces and file modes). `socket_path`: `$XDG_RUNTIME_DIR/osis/`, else `/tmp/osis-<uid>/` (created 0700 and checked), named by a hash of the store's path, shared by `Osis::listen_socket` and `Osis::connect_socket(store_dir)`; a killed daemon's stale socket is replaced by the next `serve`. `Multi` listens on `unix://` but never dials it (a published address cannot point the sync driver at a local socket); `listen` replaces only a dead socket file; a listener's drop removes the file only while it is still its own; accept errors retry after `ACCEPT_RETRY`. Every process of the uid reaching the socket is the main actor, a same-uid sandbox unable to read the store included: there is no security boundary within a uid.
- **Leaks**: the node sees everything. A passive observer or relay sees frame sizes and timing of plaintext queries (Padmé pads blobs at rest, not frames); a connection that syncs and queries shows by timing which labels a client reads. Accepted (notes/networking.md Risks); frame padding later.
- Browsers (later): a WebSocket transport (notes/networking.md decision 1); TLS by the browser, the node's key checked in-session (Hello static key, open signatures).

## 6. Mixing per group
- **Moving**: `db.group_source(g, GroupSource)` (doc comment in `sources.rs`); CLI `group source G [local|ADDR]` (no target: shows it). Sources persist as a local app record (`sources`) holding no secret: `connect_node` brings the credentials after each open, and `connect` is a thin client's whole setup. A thin client that wants to sync becomes a new node of the account. How a move proceeds: §8 Sources.
- **Offline**: a call on a remotely sourced group while its connection is down fails `Network` at once, writes included; an `on_change` hears `Err(Network)`; `status` shows `connected: false`. No stale reads: the bounded, labelled form is the cache below.
- **Client cache (not built, step g)**: per (tid, ak) the last delivered value, valid only while its subscription is live (a lapsed or closed subscription invalidates what it fed); read only for watched aspects, never offline (a cached value is one the node reported after the last change it saw); no write-through, no offline writes; bounded in bytes (evicting re-reads).
- **A thin client** stands on a scratch node: an in-memory store no call reads (`Inner::thin` set, `has_store()` false), whose sync carries its client connections and whose dispatcher runs its watches. Every tid-addressed call goes to a node; every other call is `Unsupported` (`ReadOnly::local`, `local_at`), never the scratch engine's answer.
- **No-store profile (not built)**: `osis` with `default-features = false` drops `store` (osis-engine and below: store, keys, perm, label, redb), keeping base, schema, proto, transport and `Source::Node` (no crypto, commit or crdt); `Osis::connect(&[NodeLogin], AppConfig)`. Every workspace member keeps `store` on, so feature unification stays selection-invariant (notes/build.md); the thin check is one extra artifact set (`cargo check -p osis --no-default-features`, later for `wasm32-unknown-unknown`), a gate step only when `osis` or its deps changed. Tess's decision, against notes/architecture.md §4: an `osis-client` crate with a second API type would duplicate the surface. A browser syncing node is the other profile (full `osis` over a worker-backed store and WebSocket), out of scope.

## 7. Consequences
- **Queries** (issues/api-deferred.md) become required: a thin client cannot read a group item by item. Minimal surface: `query(Query::in_group(g).with(key).order(Order::Time).page(after, n)) -> Live<Vec<Hit<T>>>`, `n <= QUERY_PAGE`, `Hit { tid, value, ts, received }`; `Live` is the page plus a watch (one Sub with a query filter, Notify on a change in the visible range). At the node: the group index times an aspect check on Sub, then incremental (§2 Port stall bounds), not re-evaluated per change (`MAX_QUERY_SUBS` × `max_clients` × O(items)); a per-aspect index (notes/local-store.md) later. Filters, counts, text search: the design pass.
- **CLI** (notes/cli.md): while `osis serve` runs, it listens on the unix socket, and every invocation finding the store locked runs its command there as the main actor through `Source::Node` (same code and output; `inspect`, `init` and `pair join` stay local: exit 8 while locked); locked with no live socket is exit 8. `serve` is the one long-running command; `serving set` and `clients add` take effect live.
- **Control plane**: an orchestrator is a thin client whose actor holds Admin on the node's configuration group; it configures the node's data, never the node (`host^.0`, `clients^.0` are admin aspects of the node thing) unless an admin grants it a role there.
- **A client actor's grants** made at another node reach this node through the account's home; the node syncs the labels of what the actor may read.
- **Dogfood** (notes/dogfood.md): each Claude's store runs `serve`, its `watch` and posts are main-actor clients; connecting as a client actor granted Write on the channel group must work too (direction 6).

## 8. Design details (from the build the rebuild replaces)
Not built: (e) `query-min`, (f) `thin-profile`, (g) `client-cache` (issues/cli-proxy.md).

### Sources
- **The rule** (`sources.rs` module comment; `decide_in` is all of it): for a thing `t`, S = `t` and the groups holding it here. No store: the connections. A group in S sourced at another node: that node, connected or not. Known here: this engine. Else the connections in order, the first knowing it (row `HOLDS`: its creation is here), an unreachable one stopping the search. No cache: decided per call under `eng`, one atomic flag (`Inner::has_sources`) in front so a process with no connection pays nothing. A local write checks again under its commit's lock (`guard_local`), so a move in between fails it (`Network`) rather than stranding it. A group source naming no connection gets `Connection::absent`, which fails `Network`, so `source` cannot fail.
- **Split** (`split_in`: `t` sourced at a node, in a group H carrying it that syncs here or is sourced elsewhere): reads stay at the source, writes are `Invalid` naming both groups, `Status.two_sources` lists it, moving either group ends it. A state, not refused steps: another holder can share `t` into H at any time, so only a check at the write covers every way in. Writes refuse because a write through the source node goes out only under what it syncs, maybe not H (acknowledged, silently not sent). A plain membership splits nothing and never flips a read; this engine hears of a new member of a group sourced elsewhere only through a group it syncs, so a thing here never goes remote by surprise. Left: reads at the source miss what only H carries while split (why `status` lists it). `undo`/`redo` over a group check its whole closure, and `revert` of a commit not held here refuses while anything is split: only the node knows what they would touch. The check follows the source decision, so a move between them cannot slip past (`a_split_made_after_the_source_decision_refuses_the_write`). Cost: a closure walk only with sources.
- **Moving away** waits until the group is synced here (`wait_synced`), then hands it off (this node stops syncing it): the sync ID is shared with every holder, so a Read holder can move a group too. "Both" (sourced at a node and syncing) is legal and reads remote: a crash between the steps leaves that, never a local copy answering while behind.
- Process-wide calls stay gated on `!has_store()`: a node with connections keeps its own `serving`, `nodes`, `read`. `read(|r| ..)` is `Unsupported` while sources exist (it would read sourced groups' stale copies). `node_synced` polls STATUS (a client row), since a client actor may not `wait_synced`.
- A write through a connection acts as this process's client actor **at that node**, `me()` staying the local account; an explicit `Write::act_as` is sent as named (and refused). `create`'s first admin must be something the client may write there.
- A move ends every watch whose source it changes with one last `Err(Network)` (`Delivery::Moved`, remotely `PortEvent::Closed`); watch again (rebinding would be a second subscription machine for a rare event). A worker's subscription for a node's own client lapses the same way. A main-actor Sub of a sourced thing through a daemon is `Unsupported`.
- **Catching up**: `Engine::core.sourced_elsewhere` mirrors the group sources, rebuilt from the `sources` record at open: `readable_by` (acting handles only) denies a thing in a group sourced elsewhere, or still catching up on its way home, and one also in a local group (its write would be refused, its copy misses the source's), so a node's client reads nothing stale. Acting handles always read here and never look at sources, undo and revert included: a thing sourced elsewhere (split or not) is unknown to a client actor, never refused (a refusal would name the source and tell it from an unknown tid); a revert checks the actor reads the commit before anything else.
- **Sharing flows** take a write's guard (`Osis::guarded`), each engine step under its lock. `set_role`, `revoke_link` and `remove_client`'s removals of a sourced thing are `Unsupported` (no port row; move home first): run here they would commit to a copy that does not sync. Not guarded: `untie_now` (a stranded removal is redone by the holders' obligation), `redeem` (K's label).
- **The port worker never waits on another node** (`on_worker`): a main-actor call sourced elsewhere through a daemon is `Unsupported`; `status` shows the connection's up/down without asking it; `settle` and schema mirroring skip connections; the dispatcher asks no connection for status (a status listener keeps what each connection's subscription sent, notes/api.md Sync configuration and status). Otherwise one silent connection would stall every client for minutes, unbounded under a remote trickling bytes.
- **Trust in rule 4**: a store-holding process asks its connections in order about every tid it does not know, so each learns the tids asked about, and whichever says yes first answers reads and takes writes, unchecked: a thin client verifies nothing, and a group source binds only things this engine knows are in the group. Connect only to nodes you trust for everything you do not hold (issues/cli-proxy.md Follows).
- Costs: per call with connections one `eng` lock and one `enclosing`; a thing unknown here costs one `HOLDS` round trip per connection (the one place "no cache" costs real time; a store-less process has several connections only if they answer as one actor).

### Reconnect
- **What an app does with `Error::OutcomeUnknown`** (code 12): the write may have applied, and a repeat is a new nonce: read, repeat if absent. Exactly-once tests need a non-idempotent op (`count_key`): a `set` of an equal value commits nothing.
- A resend is marked (`NONCE_RESENT`, bit 62): otherwise a session entry evicted by LRU would make an old nonce look new. A remembered nonce gets its first result; one at or below the highest seen and not remembered is `OutcomeUnknown`; above is new.

## Picked numbers
Built ones with their 0/∞ lines: notes/arbitrary-values-table.md (`MAX_WAITS`, `MAX_SCHEMA_BYTES`, `PUSH_BYTES`, `COMMIT_DIRTY_BYTES`, `COMMIT_SEND`, `COMMIT_PAGE`, `MAX_SUBS`, `STREAM_CHUNK`, `WRITE_NONCES`, `max_clients`, `MAX_CONNS_PER_CLIENT`). ## Rejected
- A separate socket or program for the port: two transports, authentications and lifecycles.
- One message kind per API method: a wire change per method; the table inside `Call` grows without touching framing.
- Signed capability tokens: a second signature format and a revocation list; `clients^.0` is revocable data an admin already edits.
- **Client-signed commits** (Tess): a signature over a header the client did not build is meaningless without the node's validation code; the node signs, as for its account. A key without a store would be a key actor trusting its node for all but the header.
- **Node-authored scope lists**: two mechanisms for one thing, and a node-authored request carries the node's full power (confused deputy); acting as the client's actor makes the engine's rights check the one bound.
- **Thin nodes**, as a default: a node of an account is a full admin of it, so a scoped one needs another threat model; an unscoped one is `pair`. A store-less process wanting full power is by default a thin client whose actor holds admin grants. Other policies open (issues/client-auth.md).
- A key actor per thin client: the node would sign as a second key, and a `KeyActor` record names no first admin to carry attribution.
- The main-actor tier from key equality: any transport reporting an arbitrary peer key would get it.
- Values typed by the node: typing is a view, not data.
- Port requests under the handle lock: deadlock on re-entry; a slow client would block the engine.
- Protocol Error 1 for a thing the actor may not read: an existence oracle beside `UnknownThing`.

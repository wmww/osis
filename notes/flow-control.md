# Flow control and stall bounds
> Summary: How sync connections stay bounded and live: reply allowances (`max_reply`, `SMALL_REPLY`, `FIRST_REPLY`), the client's request window, push holding by bytes taken, stall timeouts and resends, the drivers' queue caps, and the host hub's per-input bounds with turns by source (measured costs, rejected alternatives). Rules: spec/sync.md §6 Flow control. Neighbours: notes/sync-protocol.md (the engines), notes/serving.md (the hub and driver), notes/networking.md (transport windows).

## Reply allowances
- A Sync or Fetch reserving `MAX_MESSAGE` (9 MiB) of `WINDOW` (16 MiB) would allow two per round trip, so Sync and Fetch carry `max_reply`, Path pages hold 48 steps, and every small reply's allowance is `SMALL_REPLY` (16 KiB): about 1000 such requests per round trip.
- A first Sync asks `FIRST_REPLY` (64 KiB, plus room for its codes and wants), 256 per round trip; later pages `REPLY_BUDGET` (`MAX_MESSAGE` − 64 KiB). A page under a small cap may hold no event when the first does not fit, and only then does the client not call it stuck. A Fetch asks `FIRST_REPLY` per ID (a batch of 144 fills the budget); an empty reply is asked again under `REPLY_BUDGET`. (At `SMALL_REPLY` a role commit, about 15 KiB with its boxes, would be asked twice.)
- A host answers neither by reading a blob that does not fit `max_reply`: with a thousand small requests per round trip that would be 8 GiB read per trip for no reply bytes. Reconcile keeps `MAX_MESSAGE`: rare per label.
- Pipelined Fetches over the sim's lossy links (a cut, or 2% per message, loses all in flight) cost rounds: `demotion_receipts` allows 1000 (30 seeds: mean 178, max 472). Test: `loopback::many_labels_sync_in_few_round_trips`.

## The client window
- `ClientSession` queues requests and sends while the bytes in flight (frame plus reply allowance per unanswered request, `client::allowance`, the one definition both sides use) are under `WINDOW`, so a session's own requests (at the node) and replies (at the peer) never pass `WINDOW_QUEUE` (`WINDOW + MAX_MESSAGE + 4`). The drivers' caps (`MAX_QUEUED` 64 MiB at the node, host `max_queued_bytes` 48 MiB) only bound peers that do not read.
- Reason behind the spec's two close bounds (§6): within `WINDOW`, unwritten requests and unwritten replies stay below `WINDOW + MAX_MESSAGE + 4` bytes and unwritten pushes below `MAX_MESSAGE + 4`; requests received before any is answered were all in flight at once.
- **Stall timeout**: `ClientSession` closes a session whose requests in flight saw no progress for `STALL_TIMEOUT_MS` (2 min); the node redials. Progress is the last byte received or `ClientInput::Sent`: drivers compare `LinkTx::taken` (the writer pump hands the transport 16 KiB pieces) before each tick and report moved connections (`Event::Sent`, `Hub::sent`). `taken` means delivery only because QUIC/iroh `write_all` waits for stream credit (`STREAM_WINDOW` 1 MiB): a peer that stops reading stops it within 1 MiB, so a dead or non-reading peer cannot keep resetting the timer. A peer reading 16 KiB per 2 min can, by design: any link speed passes. The in-process transport never blocks a write, so `taken` jumps at once there; driver tests cannot show flow control (`slow_link` models the queues).
- **Resends**: uploads, deposits and deletes in flight are remembered per connection (`Conn::req`: `sent`, `deleting`, beside fetches in flight and blobs the host did not deliver; dropped with the connection), so passes before the answer do not send them again; unanswered after `RESEND_MS` (30 s) they go again, but only an entry whose request was answered (`ClientSession::answered(tag)`: every request of the commands tagged up to `tag`, follow-ups included, got its reply; `Requests` stores the tag of `commands()` after the batch's commands went, `UNTAGGED` until then), so a held-back queue that drains sends nothing twice.
- Rejected: serving-side backpressure (stop reading while the queue is full): it needs a pausable `ServingSession` and a drain signal, the client still needs a request window for its own queue, and the reply allowances make it unnecessary for compliant clients.

## Pushes
- With `ServingInput::Taken` (cumulative `LinkTx::taken`) reported, a push goes only while the bytes written and not taken, it included, fit `REPLY_BUDGET` (or none are unwritten). Otherwise the label goes to `owed` (FIFO; while any label is owed a `Changed` only queues its label) and continues from its `subs` position at a later `Taken`, labels in turn: one held again goes to the back, since a set walked in ID order lets a busy label starve the others. Relay-only pushes without room are dropped. Without reports (the sim, test drivers: instant delivery) nothing is held.
- Drivers report before a connection's input bytes and at ticks; `held()` connections ask for a tick every `PUSH_POLL_MS` (1 s; hub `next_due`, node `serve_wake`). Caps: `SEND_QUEUE` = `WINDOW_QUEUE` + `PUSH_QUEUE` (one push frame).
- Tests: proto `slow_link::*`: 72 MiB each way at 64 KB/s and 2 MiB at 1 KB/s, both on one session with the real cap sizes (fails with the window off); 72 MiB pushed to a 640 KB/s subscriber within `SEND_QUEUE` (fails without `Taken`); held labels take turns; a random push differential (labels, sizes, rates) against the log; requests held back for hours stay unanswered.

## Hub stall bounds
The hub thread serves every connection of a host, so per-input work must be bounded and comparable to honest work.
- An Open costs a signature and at most three lookups (claims indexed as `H` rows, never a claim-set load). A message's signatures try older keys only after one failed under the head's key (spec/wire.md §11.2), so at most one older-key scan per message. Sync entries are capped at 1024, like Upload. One store commit per input. A relay goes to subscribers only.
- A connection whose unwritten replies pass `SEND_QUEUE` within one input is closed before its further requests run (`ServingSession::unsent`). Requests in one input are all unanswered when the last was sent, so their frames plus reply allowances stay within `MAX_UNANSWERED` (`WINDOW + 2 × MAX_MESSAGE + 4`) for a compliant peer, and one passing it is closed before that request runs: at most three `MAX_MESSAGE`-allowance requests (Reconcile, Fetch, Sync, Path) per input.
- That bounds the two requests whose reads follow the label rather than the message: Reconcile, and Sync from an old cursor (Sync skips log records that yield no event, up to `log_keep`; issues/sync-log-scan.md). Measured (release, redb, `file::reconcile_whole_space_budget`, pages decrypted from the host's `Store`): a whole-space range reads every live ID, about 125 ms at 10^5 live entries, 1.06 s at the 2^20 per-label cap; 1024 puts in one commit about 0.45 s at 10^5, about 1 s at 2^20. Without the bound one 64 KiB input of about 1600 such 40-byte requests cost a minute at 10^5. An honest reconciliation also reads up to the label once per message, so per input the two are alike.
- **Turns** (`driver::Turns`): those are bounds per input (one read, at most 64 KiB), not per second; an opener can send input after input and keep the hub busy, as an honest peer with a full window may. So a connection's reader hands the driver one read, and the next only after the hub took it; the driver serves waiting reads round-robin by source (`Connection::source`), then by connection within a source; reads that arrived are queued before each turn. With S sources waiting and P the per-input bound, a read waits at most (S − 1) × P once it reached the driver (k × S × P if its source has k connections waiting), plus the bookkeeping between turns (accepts, closes, ticks: a sweep is 1024 rows); a message spanning several reads waits that per read, and each read moves the sender's stream (transport progress, so stall timeouts see it). One opener with any number of connections from one source delays others by one input per turn: about 0.4 s at 10^5 entries, about 3.2 s at the 2^20 cap, against `STALL_TIMEOUT_MS` 2 min; many sources each get a turn (issues/host-hub-stall.md, Sources).
- Tests: `driver::flood_does_not_delay_others` (a flood's reads queued behind one reader delay another's Sync by about 12 reads, the probe's round trip), `driver::tests::turns_by_source`. Throughput: one session's 64 MiB upload then download (16 KiB blobs, QUIC loopback, release) costs the same CPU with one read handed over at a time as with a 1024-slot queue (the link's 16-read read-ahead keeps the pipe full).
- Rejected for now: per-subtree fingerprints in the store (O(log n) per range) cut honest and hostile cost alike but need an order-statistic index persisted beside the `E` rows in three stores, and a 256-range message with splits would still cost thousands of row reads; not needed while the per-label cap (2^20) bounds a scan.
- Not done: decode and verification off the hub thread; a host-wide relay rate (a relay's fan-out is bounded by the subscribers' own queues and the per-label rates).

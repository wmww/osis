# Coordination
> Summary: How a coordinator session runs osis work: one opus (or, for gnarly or already-failed problems, fable) worker per task in a worktree, a fresh opus reviewer, gate in the worktree, fast-forward main; at most three agents; the periodic checks and their cadence; the watchdog that reviews how the session went; the complaints directory agents write to.

The build and test mechanics are in notes/build.md; this note is the process around them.

## A coordinator session
- A session is one coordinator's run, of whatever length; notes/mvp-progress.md gets one section per session listing what merged, Tess's decisions, what was left in flight, and the periodic-check offsets used. (The older sections are titled "Production round N"; a round is the same thing.)
- Test budget per task (Tess: cut testing time without letting issues slip): seed breadth belongs to the periodic checks, not to branches. A worker runs tier 1, clippy, the repro that motivated the task and a quick targeted check of what it changed (not the gate: the reviewer gates after rebasing); the reviewer runs the per-branch oracles of notes/testing.md at their default sizes on a fresh offset plus any differential it writes, then the gate (test-speed measurement: the per-branch set is the largest per-agent cost, e.g. perm tier 2 ~1860 CPU-s, exhaustive order ~1300; running it once per branch instead of twice keeps the coverage). Briefs name those sizes, never periodic-sized ranges (300/200/1000/3000 seeds: those cost 30-60 min per agent and duplicated what the next periodic run covers). A branch that changes an invariant the per-branch set does not reach gets one targeted larger run, said why in the brief. To keep breadth, periodic runs go more often (whenever about six branches merged, or when idle). Effect (watchdog, 5 h after vs 10 h before, about 28 agents each): reviewers median 22 to 14 min, build/test wait per reviewer 16 to 9 min, per worker 19 to 15 (outliers excluded), model share 29% to 35%, merges per hour doubled (15 in 5 h vs 15 in 10 h); periodic run 5 found no product bug the branches had missed.
- Networking per-branch check in briefs: `cargo test-net -- --ignored driver:: runtime:: quic relay lan iroh` (unfiltered it runs all of tier 2 incl. timing benches; notes/build.md).
- Per task: `wt claim <branch>` for an opus worker (brief: the issue, the oracles for its area, the standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, commit, `wt release`, report); then a fresh opus reviewer on the same worktree (correctness review of the diff, targeted differentials for the invariant the branch changed, small fixes committed, `git rebase main` then `tools/gate.sh`; the gate is the reviewer's only full tier-1/clippy run, beyond it only targeted oracles for the changed invariant on fresh ranges); `wt release` only as the very last step after the last commit (a worktree released early is free for the next claim while its agent still works there: that happened once, and the next agent's commit landed on a detached HEAD instead of its branch; `claim` now refuses a worktree that is not on the branch after checkout); then the coordinator fast-forwards main from the local branch (`git merge --ff-only`, push main, `git branch -d`; task branches are never pushed or fetched: worktrees share the repo's branches), records the item, and briefs the next task. At most three agents at once, workers and reviewers counted together; two worktrees stay warm, more are made and trimmed as needed.
- `wt` and `claudewait` are currently missing from PATH in coordinator and subagent shells (Tess told). Briefs give the fallback: `~/.claude/plugins/cache/wmww-agent-skills/reasonable-rust-builds/<ver>/bin/wt`, and claudewait from the same cache.
- Briefs say `wt claim <branch>` prints the worktree; they do not predict which one (agents reported being misled when it differed). A reviewer who needs main's behaviour for comparison gets main's test binary with `tools/bin-at main <out>` (notes/build.md), then runs old and new side by side; under load compare CPU seconds, not wall time.
- Simplification passes (Tess, standing): alongside the periodic checks, about every six merges, run one behaviour-preserving simplification/refactor/restructure pass on the area that changed most since the last one (round 13 example: keys-cleanup, item 125), with its own reviewer; it counts as a task like any other.
- Simplicity (Tess, round 13 decisions): keep implementations simple; when a subtle aspect of a design adds a lot of complexity or bug surface, look for a way to avoid it, and in extreme cases bring it to Tess as a possible requirements compromise. Say so in design briefs.
- Brief checklist (watchdog 13e): a worker brief names no per-branch oracle the reviewer will run (from 17:44 one stretch handed both the same set, doubling it); each brief names the agent's own scratch dir (`<scratchpad>/<branch>-<random>`; 67 loose files at the scratchpad root, some with generic names); each new test is checked to fail with its fix disabled (two passed without it); the reviewer commits before starting oracles and runs them from a copied binary (5 agents edited sources under a running build); one all-core harness per agent at a time.

- Coordinator re-gates: a background `tools/gate.sh ...; echo gate=$?` always exits 0, so end the wrapper with the gate's code (`tools/gate.sh > $L 2>&1; e=$?; echo gate=$e >> $L; exit $e`) and read the log's last `== gate passed` before merging or pushing (items 131 and 253 were pushed on failed re-gates). Re-gate the rebased branch before the fast-forward, not a checkout at main's tip: there HEAD equals the merge base, so the gate runs everything, including the kit/app steps (gate-117: +110 s of app test, clippy and deny for an engine change).
- A cargo build or test stopped partway (TaskStop, a killed gate) can leave a crate's incremental cache unable to link (`rust-lld: undefined hidden symbol anon.*`); seen twice in round 13. Prefer letting a stale gate finish; if one is stopped, `cargo clean -p <crate>` for the crate that fails to link (osis-engine, osis-perm), not the whole target.

It recurred in 13i: an eph-unify-a worker sat 93 min on `rm -f $D/*.rs.bak`. Box names (ostrich: this box; devbox: Tess's other box) identify machines, not coordinators. Sub-agents get names from their coordinator: `<coordinator>-<branch>` (e.g. `lodestar-grant-keyset`), stated in the brief's first line and used in reports, complaints and channel posts.

- Two coordinators (Tess: neither is in charge): one per box (ostrich, devbox; names in the registry above), talking over the osis channel (notes/dogfood.md). Split by issue area (Tags): devbox has cli, api, schema, tests, host-store-outlives-hosting, spec-audit-protocol; ostrich has engine, crdt, permissions, keys, node-sync, host internals, ephemeral, growth, spec-audit-crdt, spec-audit-validity; anything else goes to whoever claims first. Protocol: post `claim: <issue> (<branch>)` before `wt claim`; post `merged: <sha> <branch>` after each push; `git pull --rebase` before every push; in shared notes add your own section or row, never rewrite the other's (mvp-progress: devbox numbers its own items d1, d2, ...); relay Tess's decisions verbatim with `tess:`; a pinned-binary bump is `bump? <sha>`, answered `bump ok`, before either side rebuilds. Each box runs periodic checks for its own areas.
- Re-gate after a rebase onto main that brought other branches' code: the gate decides its sim sweep by the branch's own diff, so a re-gate costs the same as the reviewer's; skip it only when the commits brought in are notes-only or in crates the branch's crates do not depend on.
- Growth (Tess): a change that adds a new kind of permanent data (a row, record, table entry or synced field that is never dropped) adds or updates a row in notes/growth.md; reviewers check.
- Reviews are where bugs are found: of 20 merges in one session, 8 reviews found 5 real bugs, all through targeted differentials or reading, none through re-running default test ranges. Keep the reviewer brief focused on the invariant the branch touched, and ask for a differential test of it.
- Budget drift measured (agent-times investigation, round 13): from about 20:00 on the second day median agent wall went 14-20 to 28-58 min, model time only 5-6 to 8-9; per-gate wall 6.4 to 14.8 min. Cause: briefs drifted back to periodic-sized ranges (oracle mentions per brief 0-0.9 to 2-3.7, worker briefs too; paged `_large` at 300 seeds = 19,450 CPU-s, 12x its 24-seed default and a third of a box-hour; rotation `_large` sets about an hour each), so agents' background oracle wall went from about 1 to 3 concurrent all-core jobs, beside periodic runs that grew to 2.3-3.4 h and ran about half the clock. Same tier-1 code ran 2-2.7x slower at that load; tier 1 itself grew only 33% in CPU (1275 to 1700 CPU-s over 104 commits). Of items 176-196's review finds, all but one came from reading or a new differential. Before briefing, add up the oracle set's CPU-s (testing.md costs; a seed count times CPU-s per seed) and keep it at default sizes.
- Per-branch tier-2 oracles finish in minutes (notes/testing.md); long runs are periodic, below.

## Adjustments (round 13 trajectory analysis, Tess-approved)
- Re-review: a reviewer change bigger than a small fix gets its own fresh reviewer before merge (round 13: an unreviewed reviewer rewrite of the deaths window produced four bugs the next periodic run found).
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- After each periodic run, append a row to the bug log in notes/mvp-progress.md: per area, bugs found and from which oracle, so convergence is read directly.
- Two agents, not three, while the box runs at load above about 20; waiting on builds is the main cost. In 13f this was not kept: three agents ran almost continuously from 02:55 to 05:12, plus coordinator re-gates and the eph-unify release builds, then the periodic run. The seven gates of 440-594 s fell in that stretch and the periodic window; quiet gates in the same session took 162-171 s.
  - Per slow gate, about a third was rebuilding after `git rebase main`: 76-222 s, when the rebase brought osis-crdt, osis-store or osis-base changes.
  - Tests ran 2-5x quiet.
  - The 5-seed sweep took 73-149 s, against 38 s quiet.
  - nice 19 does not shield a laptop: a niced 16-thread run still takes SMT siblings and the shared power and clock budget.
- Performance: the coordinator owns it (Tess: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade"). Budgets in notes/testing.md (Performance budgets); a new incremental path needs a measured miss of a budget in a realistic scenario, and simple from-scratch code that meets the budget wins.
- App work (kit/, app/): planned with Tess in a separate UX/planning session (notes/app.md); it runs alongside core work and counts toward the agent limit. When no app session is active (Tess, round 13: "nobody else is working on the app, feel free to fix any problems"), the core coordinator fixes app breakage (failing app tests, API adoption) itself.
- Core asks from app work: whatever kit/app needs from core and core lacks becomes an issue tagged `core-ask` (plus the component); app work uses a workaround meanwhile (e.g. durable data until ephemeral data lands), never edits core itself. If the fix is not obvious, also tag `tess-call`: Tess reviews it in a core coordinator session.

## Periodic checks
What: the seed-breadth runs that catch what the default ranges never will (every bug caught by a generated input in the last session came from a seed or range nobody had run): `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (45 scenarios: about 20 s per seed row at load 25-35, so 2400 s stopped at 115 of 300; 150 finished in about 50 min at that load in run 4; run 11, 46 scenarios at load 30-45, reached 78 of 150 in 3600 s), `OSIS_ORDER_START=<S> OSIS_ORDER_SEEDS=300 cargo test -p osis-node --test it -- --ignored order::arrival_order_alike_large_spec_permissions_5_2` (2 min on 16 threads) and the same with `OSIS_ORDER_SEEDS=200 ... order::arrival_order_exhaustive_large_spec_crdt_4_8` (13 min), `OSIS_PERM_SEED=<P> cargo test -p osis-perm` (only osis-perm reads it) and the osis-perm tier-2 set at that seed (`OSIS_PERM_SEED=<P> cargo test -p osis-perm --test it -- --ignored roster:: differential:: queries:: incremental::`, 2.4 min), `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_ --skip budget --skip bench:: --skip scale:: --skip hostile_moves --skip shrink_script` (the crdt random tests at other seeds; the skipped timing tests run for 30+ min in debug), `OSIS_WALKS_START=<W> OSIS_WALKS_SEEDS=1000 cargo test -p osis-node --test it -- --ignored --exact walks::open_equals_rebuild_random_histories_large` (1 min on 16 threads; every seed-ranged harness is a `_large` twin, notes/testing.md Seed runners), `core/test/tla/run.sh small`; offsets rotate and are logged in notes/mvp-progress.md so ranges never repeat. A sim sweep cut by its `--budget-secs` says so only in its per-scenario seed counts: log the seeds that ran, not the ones asked for. Harness runs with an overridden range print it even when passing (notes/build.md, harness env vars); check that line, not only `1 passed`. Run the whole periodic script under `nice -n 19`: at normal priority it held the box at load 25-35 for 2 h and every worker's and reviewer's gate in that window took 250-530 s instead of 80-150 s. The price: at nice 19 beside load 30-50 a harness can run 30x slower than its CPU-s say (run 12: 36 `random_window` seeds per variant in 13 min, then 950 in the next 13); judge a slow periodic item by its CPU-s (`/usr/bin/time`), not its wall time, before suspecting a regression.

Scope: each periodic check belongs to a component (today all to core). Run a component's checks only after significant work on that component; a session that worked on the app alone does not run core's sweeps, and core work does not run app checks. The same rule holds for the dev loop itself: working on one component must not incur the costs of components not being worked on (an app's tests do not run while iterating on core, and the gate for a core branch runs app tests only if the `osis` API surface changed); when a new component arrives, give it its own per-branch oracles and periodic checks and extend `tools/gate.sh` to select by what the branch touched (notes/build.md).

When: in the background, in a spare worktree, with at least five times the last run's wall time of coordinator work between the end of one run and the start of the next (so they take at most a sixth of the clock), measured from the last run's own duration on this box, never a fixed hour or merge count; and start one only while at most one agent is building or testing. Not at the start of every session unless they have not run for a while. If they grow, first look for a way to make them faster without losing what they check (the order harness went from 12 minutes to under 2 by running seeds on a thread per core), then run them less often. Before a release, run them at full length regardless.

## The watchdog
When the periodic checks finish, spawn one opus agent with this brief, and act on its report (fix tooling or notes yourself, file issues, or brief a worker): "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py` (the session's tasks dir; `--since` the last watchdog run) and read the gate logs the coordinator kept. For each agent: was its wall time reasonable for its task, how much was model time against waiting on builds, tests and benches, did anything hit the 180 s subagent cap repeatedly, time out, or write a wait loop; did any build or test take far longer than notes/build.md's expected costs (3x at low load is a bug: find out why rather than blame load); did agents run checks that are not on the per-branch list (notes/testing.md); did any agent, gate run or periodic check pay for a component nobody was working on (app tests during core work, core sweeps after app-only work, a whole-workspace run where a component's own would do): that shape of waste is a standing thing to look for; did reviews find bugs and what kind of test found them. Check disk: `du -sh .worktrees/*/target` and `df -h .`; a warm worktree target settles at 11-12 GB by `du` (notes/build.md); one well above that holds stacked artifact generations (after a profile, layout or toolchain change: delete it and rebuild) or a stray artifact set (`-p`, `--features`, env flags: find the command in the transcripts); more worktrees than agents means `wt trim` was skipped; also look for stray `target/` dirs outside the worktrees (`find ~ -maxdepth 4 -name CACHEDIR.TAG -path '*target*'`) and scratch dirs over a GB. Read every file in notes/complaints/ and the latest worker and reviewer reports the coordinator has in the progress note. Verify every claim about a file or a tool against the current main checkout before reporting it (two agents reported CLAUDE.md as stale when it was current). Then report: what is fine, what cost time for a fixable reason with the evidence (which agent, which command, how long, why), patterns across complaints worth fixing, and complaints not worth fixing (delete those files; fold the worth-fixing ones into your report and delete them too, so the directory holds only what the coordinator has not yet seen). Do not change code; notes and the complaints directory only. Commit and release your worktree if you used one."

## Complaints
`notes/complaints/` is where agents leave low-priority workflow mishaps, mistakes, footguns and slow spots they met, one file per task named after the branch (`notes/complaints/<branch>.md`, a few lines each, appended to during the task), committed with the branch. High-priority problems (something blocked you, a tool gave a wrong answer, a check took far longer than its documented cost) go in the report to the coordinator as well. The watchdog reads the directory, keeps the patterns, and deletes what it has consumed; the coordinator never has to read it directly.

# Coordination
> Summary: How osis is designed and how coordinators run the work: Tess's design principles (principle first, carve-outs are smells, test what users observe, options keep their property, model before building); the task loop (opus worker, fresh opus reviewer who gates, fast-forward main; up to 5 agents for the lead coordinator, 3 for the second); test budget and time limits; briefs; release checks; standing agents and their cadences; complaints; several coordinators.

Build and test mechanics: notes/build.md; the gate: notes/gate.md. Starting a session: read notes/handoff.md when it exists and delete it once its items are taken; a coordinator ending a session with work open writes it. What is in flight is the local task branches (`git branch`) and their worktrees; merges need no progress record.

## Design principles (Tess)
How osis is meant to be designed. Most fiddly bugs this project has had came from breaking one of these upstream, so apply them before writing code and check them in every review.

**Fast by construction (Tess).** From core through kit to app, the most ergonomic way to build something also gives it the right performance, so it is hard to build anything slow. There is no typical use, so there is nothing to tune for: everything reacts only to what it should, nothing is done twice, and nothing scales with the wrong thing. Fix slowness by design and by refactoring as far as needed, never by profiling and tweaking hot paths or by hiding the slow thing.

**Shape of the design**
- **Principle first.** Every area states, at the top of its note, the one rule it follows (e.g. retention: every drop that is not expiry or purge is a right holder's covering snapshot; keys: rotating needs only the right to rotate). Every other rule there must follow from it. Changing a principle is fine, done deliberately and written down.
- **A carve-out is a design smell.** A fix that gets fiddly, breeds new bugs, or needs a special case, exception or "limit" usually means the design upstream is unclear, impractical or contradictory. Before adding one, check it follows from the area's principle; if not, stop and raise the design question. Reviewers ask of every branch: what exceptions did this add, and which principle do they follow from? A chain of patches in one area (the second seed-found fix) means a class study, not a third patch.
- **Cut tentacles and cruft.** When an edge case has grown a wing of fixes, replace it with the rule that works, a stated limit, or a requirements question for Tess. Delete freely: slow or badly designed tests, notes on how things aren't, issues stating unfixable facts.
- **Rewrite, don't tack on.** Coordinators may change the design within the requirements' words or spirit. A precisely stated design problem beats a hollow finished build.
- **One mechanism, used everywhere.** Before adding a mechanism, look for the existing one it really is (e.g. a key rotation's list and a removal's list are the same witness rule at two levels). Don't drive a general mechanism from one feature's needs (expiry is not designed around ephemeral data).
- **Close leaks; don't shrink them.** Prefer dropping data and fetching again when needed over keeping markers or tombstones "to know". A smaller leak is still a leak.
- **App workarounds for engine costs are a red flag** (chat split messages by calendar year to cap an engine cost). Fix the cost in the engine for every app.
- **Complete refactors.** A rename or concept removal must read as if the code was built that way: code, API, CLI, errors, tests, spec, notes, comments; no aliases or "formerly X". Reviewers grep for remnants.
- **Rare paths may be brute force.** For rare corner cases accept more download, CPU or refetching in exchange for a simple, robust rule; from-scratch beats incremental cleverness unless a measured budget is missed.

**Users and options**
- **Requirements state properties**, not shrink-wrapped behaviour. No features built on protocol side effects. They speak in what a user or app developer observes (no snapshots, frontiers, addenda): a property with exceptions is stated as the weaker property ("generally", "up to"), not as a strong claim plus implementation-level exceptions. The precise rules go in the subsystem specs.
- **Options keep their property.** Where users choose between trade-offs (keep history, no promise, purge on replace), each option keeps its defining property and pays its own cost, stated. Never blend one toward another to dodge its cost.
- **No typical use case.** Examples are not workloads, and examples must not become definitions ("cursors and presence" is not what ephemeral data is). Aim for predictable properties across sizes and edit rates.
- **Names carry the meaning.** Convey intent through API and schema names, not a doc line: the default (no history promised) is unnamed; the costly option is named for what it does (`purge_on_replace`).
- **History is verified or absent.** Never store or use unverified, forgeable history. Expose history only where retention deliberately keeps it.
- **Forks are permanent.** Admin disputes are forks tolerated indefinitely; no rule may wait for one to be settled. Disputes get the simplest rule to build.

**Testing**
- **A failure rate is not a property.** "Loses writes in 64 of 1M worlds" describes the generator, not the system: the property is "can lose writes", so the design is broken, whatever the rate. Report and judge findings as the property they violate; a rate only says how well a test reaches the case.
- **Big random runs finding bugs is a design smell.** A sound philosophy yields a few simple properties ("invalid data cannot affect a value"); small tests check each property, and the properties compose without surprises. When a large random run finds a bug that small tests and review missed, ask which property was subtle ("invalid data affects values in certain ways") and simplify the design until it is plain, then add the small test.
- **Every check runs at every size.** A coverage floor or sanity check that runs only above some seed count hid a dead counter from every large-size run (and floors tuned for large size flip at small size): derive floors from the run's size or drop them.
- **The smallest test set that gets correctness.** When tests grow slow, rewrite and consolidate around the properties rather than optimizing what is there: add-then-optimize ends in tightly packed slop. Each test names the property it checks; one without a clear purpose goes.
- **Never pin a failing seed.** A seed test is slow and silently stops reproducing as soon as the harness, wire bytes or rng use change. What enters the default tests is a small, quick, hand-readable minimal reproducer of the property. Turn a pinned seed into a minimal reproducer or delete it. Deleting a test is fine when it checks something we don't care about, a situation that no longer exists, or has no clear purpose.
- **Test what users can observe.** Oracles compare what the API exposes (reads, promised history, errors), not internal state, unless an internal invariant is the point. When a test fails on an unobservable difference, redesign the test. An excuse in an oracle is a carve-out: compute it from the generated history, never from the node under test.
- **Check scaling, not seconds.** What matters is how cost grows with size: count the work (bodies read, commits walked, bytes stored) at n and 10n in a fast default test. Wall time of a synthetic operation on a busy box tells nothing; no release builds or long timing runs inside a task.
- **Model before building.** Model every major design change first (roles-model, held-model, TLA); greenfield models are cheap and have found real holes every time. A model of the design is an oracle, not a copy of the code.
- **A coherent design is cheap to check;** a pile of constraints with no principle needs exhaustive testing forever and still has bugs.

**Working with Tess**
- Don't block on her: take the reversible option, record the question as a `tess-call` issue, and keep going. Ask one question at a time, with the trade-off and why users care, in plain words.
- Requirements changes need her sign-off; spec, code and notes don't (CLAUDE.md).
- Don't record a recommendation as decided mid-discussion; check what she already decided before asking again.
- Liking a design's shape is not a go: on a design she is engaged in, propose, then wait for an explicit decision before briefing a build.
- Priorities: security, data loss and core correctness first; performance and optional features wait until the core is solid. If a requirement keeps generating issues, bring her the case for relaxing it rather than papering over it.

## The task loop
- `wt claim <branch> origin/main` for an opus worker; then a fresh opus reviewer in the same worktree: correctness review of the diff, a targeted differential for the invariant the branch changed, small fixes committed, rebase, gate (notes/gate.md, Running it). Then the coordinator fast-forwards main from the local branch (`git merge --ff-only`, push main, `git branch -d`) and briefs the next task. Task branches are never pushed or fetched: worktrees share the repo's branches.
- `wt release` is the last step of a branch's last agent, after its last commit: a released worktree is free for the next claim, and a second agent there commits onto the wrong HEAD. A worker whose branch gets a reviewer does not release: it reports its worktree's path and the reviewer works there, without `wt claim`. A reviewer claiming afresh gets whichever worktree is free, warm for another, older commit, and its gate rebuilds main's changes too (3 of 4 code gates in one session: 450-750 CPU-s and 1-2 min more build each).
- **Slots (Tess).** Up to 5 agents at once for the lead coordinator and up to 3 for the second, workers and reviewers counted together: sized to keep the CPU near full without heavy oversaturation. Run fewer only when all open work collides and no routine task (Standing agents) is useful. Keep two worktrees warm (`wt trim 0`/`1` after a release makes the next claim cold).
- Re-review: a reviewer change bigger than a small fix gets its own fresh reviewer before merge (an unreviewed reviewer rewrite once shipped four bugs).
- Third round: a branch whose second review changes the rule, not a line, goes back to the coordinator for a simpler rule before a third reviewer.
- One gate per branch (Tess): the reviewer's, after its fixes. If main has moved when the branch is ready, the coordinator rebases and fast-forwards on `cargo clippy --all-targets -- -D warnings` plus `cargo test -p <crate>` for each crate that both the branch and the commits it was rebased over changed (clippy catches compile breaks, the shared crates' tests most behaviour clashes). Re-gate only when the rebase had code conflicts. Never gate a checkout at main's tip: HEAD equals the merge base there, so the gate runs everything, GUI included.
- **Docs-only branches** (Markdown under spec/, notes/, issues/; TLA run by hand): the coordinator runs `tools/gate.sh`, which takes its docs path (policy and instant checks, seconds), and merges on it with no reviewer agent. Two exceptions get a reading reviewer, no further gate: a spec change a build will follow (checked against spec/requirements.md), and a prose editor's rewrite (the reviewer walks the removed facts; such reviews have restored dropped facts). A comment-only Rust change is not docs-only: it gets a reviewer, whose gate takes the comments path (notes/gate.md, Components pay for themselves).
- **Known failures.** Exit 0 (`== gate passed`) merges. Exit 3 (`== gate FAILED, KNOWN failures only`) merges too, with no rerun, when each KNOWN failure's text reads as its issue describes; say so in the report. A NEW failure (exit 1) is the branch's to fix, or, shown failing on main too (`tools/bin-at main`), gets its issue and `tools/known_failures.txt` line on main before the branch merges (notes/gate.md, The summary).
- Hung agents: one quiet far past its task's usual length is asked (SendMessage) or stopped. Agents have sat for hours on a permission prompt, and one ended its turn on a `Monitor` whose last event never woke it.
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- Main moves under long branches: on rebase, rewrite prose into main's terms rather than resolving conflicts mechanically. On a branch with earlier unmerged commits, squash only to the tip you started from.
- An agent that hits a model usage limit mid-task: commit its worktree as WIP and relaunch in the same worktree.
- Briefs and reports stay honest about what ran: a deferred or skipped check is reported as such, never as passed.
- Simplification pass (Tess, standing): about every six merges, one behaviour-preserving simplification/refactor pass on the area that changed most since the last, with its own reviewer; it counts as a task.

## Coordinator rules
- A tooling change (tools/, gate, env names) goes through a worktree and the gate like any branch, even a one-liner: an untested one-line change broke main's policy check.
- Performance is the coordinator's: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade". Budgets: notes/test-scale.md (Performance budgets). A new incremental path needs a scaling check showing the simple one grows worse than the requirements allow.
- Growth: a change that adds a new kind of permanent data adds or updates a row in notes/growth.md; reviewers check.
- Hostile-only shapes inside data the writer may write: `Priority: low`; fix only when easy, else state the limit where the area's note or spec lives.
- App work (libs/kit/, app/) is planned with Tess in a separate UX session (notes/app.md) and counts toward the slots. With no app session active, the core coordinator fixes app breakage itself. What kit/app needs from core becomes an issue tagged `core-ask`.
- Names: each coordinator picks a name and pronouns once it knows the codebase (check the registry), records both here and says them in chat. Sub-agents are `<coordinator>-<branch>` in briefs, reports and complaints.
- Registry: **Lodestar**, she/her. **Tiller**, he/him. **Wren**, they/them. **Sorrel**, they/them. **Fathom**, they/them. **Kestrel**, they/them. **Petrel**, they/them. **Halyard**, they/them. **Bowline**, they/them (app). **Capstan**, they/them.

## Test budget
Seed breadth belongs to the release checks, not to branches (Tess: cut testing time without letting issues slip): reading and targeted new tests find most bugs, rerunning ranges almost none (notes/testing.md, What finds bugs).
- Worker: the per-worker checks of notes/testing.md (When tests run), its own new tests, the task's repro and a quick targeted check of what it changed. Then commit; no gate (the reviewer gates after rebasing; worker gates cost hours of agent wall and load everyone else's).
- Reviewer: any differential it writes, then the gate, the branch's one full run (never `OSIS_FULL=1` per branch); no separate property run. Reviews find bugs through targeted differentials and reading, not by re-running default ranges: keep the reviewer brief on the invariant the branch touched, and ask for a differential test of it.
- A branch that changes a test model (held-model, roles-model, crdt-model) gets every property using it through the gate's selection; one that changes an oracle's expectations runs that oracle once before merge (a held-model rewrite once failed half the order seeds on main for several merges).
- Never large sizes in a branch, including a confirming sweep after a seed fix: a 300-seed `held_set_decides_plain` holds the heavy lock about 20 min (12-14k CPU-s) while every other agent queues. A seed fix runs its seed and a test of its mechanism; the gate samples the rest. A branch that changes an invariant the gate's selection does not reach gets one targeted larger run, saying why in the brief.
- A branch that adds or rewrites a randomized harness runs it once at `OSIS_FULL=1` before merge (small sizes have passed while large size failed 4.6% of seeds).
- **The gate's limit is 5 minutes (Tess)**, everything it runs included (it takes far longer: issues/gate-five-minutes.md) (default tests, the branch's selected properties and sim scenarios): reached by fixing perf problems (product, harness, test design), not by scaling sizes down: a size shrinks only where the extra size is shown to add no coverage; breadth goes to release checks.
- **Time limits (Tess).** Every timed run has two hard limits, CPU time and wall time, each set only a little above what it takes on this box now (the CPU limit tighter, as other work on the box barely moves it; the looser wall limit catches what CPU time cannot: waiting, idle cores, a demoted process), as a multiple of a per-box base unit so limits scale to other boxes: the gate (its one heavy-lock hold, notes/gate.md Steps, step 7, is where they hook in); the default tests; a warm rebuild in its longest common form (an osis-base edit, all targets: about 15 s, limit about 2x); a single test (over 10 s needs a reason); one heavy-lock hold, the largest of these. The gate's stage limits are shares of its own (they sum to at most it), so an over-limit gate names the stages over their share. Values and tooling: notes/build.md, Time limits; hits and investigation reports: notes/time-limits.md. Every hit and every investigation report is logged with timestamp and box. An agent that hits a limit reports why. An investigation starts when the same limit is hit 5 or more times within 3 hours, when one run exceeds its limit by more than 2x, or when the explanation implies something persistent (tests added that take longer). An investigation may raise a limit only if it finds no good solution, recording what it tried and why the raise is justified; Tess reviews these. A trigger is a chance for the bigger job: when new tests trip the limit, consider whether one is slow, there are too many (drop, consolidate), all are slow (optimize), the whole suite including old tests is slow, tests are designed slowly (a complex scenario where a minimal test proves the same), or the change that needed the new tests made old ones irrelevant (drop them).
- One all-core run at a time per box, through `tools/heavy` (notes/build.md, Heavy lock).
- Main stays green on the properties at small size: one failing on main is the next task, and until it is fixed it has a `tools/known_failures.txt` line, so reviewers merge past it without building main to tell old failures from new.

## Briefs
Standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, commit, `wt release`, report.
- Start with `export PATH=/home/ai/.claude/plugins/cache/wmww-agent-skills/reasonable-rust-builds/0.6.0/bin:/home/ai/.claude/plugins/cache/wmww-agent-skills/claudewait/0.1.0/bin:$PATH`: subagent shells lack the plugins' `bin`. Check the versions with `which wt claudewait` in your own shell (a plugin update adds a version directory).
- Say `wt claim <branch> origin/main` prints the worktree (without the base it branches from the lagging local main); never predict which one, and `cd` there first: an agent's session can start inside another agent's worktree.
- Name the agent's own scratch dir (`<scratchpad>/<branch>-<random>`), with the gate log's path inside it: every file goes there (notes/build.md, Footguns: Scratch).
- A worker brief names no property the reviewer will run, unless that oracle is the task's repro; then the worker runs that one test at its default size on one fresh offset, and the reviewer's gate still runs the selection.
- Put the reviewer's "check these cases" questions in the worker brief too (a case asked only of the reviewer costs a second round). Say "do not loosen an existing test: report it".
- Ask the simplicity question in the worker brief ("is there a rule with no points/windows/caches that meets the budget?"), not first in review.
- Security or convergence fix: the worker writes the invariant the fix relies on as a code comment, plus a randomized differential (or an extended oracle) that fails with the fix disabled; the reviewer attacks that argument. Every new test is checked to fail with its fix disabled.
- Security fix, also in the worker brief (reviewers asked alone have rewritten fixes over several rounds): prefer changing the behaviour an oracle objects to over widening the oracle; find every path that reaches the state (every caller of what mints it) and test each; for every input the rule reads, ask who can write it (a removed party forges at an epoch it held: read only what counts); a cache or visited set in a security walk gets a test where the same keyset is met two ways.
- A diagnosis that needed temporary prints keeps them as the harness's failure output or an env-gated dump (as `OSIS_ROTATION_DUMP`): failures that print only outcomes cost most seed chases a probe rebuild.
- Say "first re-run the issue's repro on current main" (issue seeds go stale), and name the commit a measurement or lead came from.
- Name sections of the big notes and issues, not whole files: the Read tool pages at about 25k tokens, and an agent writing back a file read from its first page alone drops the rest. A file only on an unmerged branch is named as `git show <commit>:<path>`, the commit that has it (a later branch tip may have deleted it); grep a branch or item name before a brief cites it. A plan for several commits splits its paste-ready spec text per commit.
- Grep the rule's words before citing a spec section or env var (a wrong env var name silently runs the default seeds).
- TLA results: name the module (`run.sh <module>`) and by-hand instances by name (README rows give their size), sized under the `heavy` hold limit, never by a minute count (notes/test-properties.md, TLA+). A one-worker TLC run of seconds needs no lock.
- Repeat the command rules agents break most (notes/build.md, Footguns): no `timeout` around cargo; `run_in_background`, then one `claudewait` per call, with the task ID the tool printed; edit and build in separate calls; `-p <crate> --test it -- <filters>`; TaskStop, never `pkill -f`; the reviewer commits before starting oracles and runs them from a copied binary; `PROPTEST_CASES=N` for deep proptest runs; `--ignored --exact` traps; and the git ones (squash to the merge base, wip-commit before a fix-disabled probe, `git fetch && git rebase origin/main` without a pipe, its result read before gating).
- A branch touching node sync, links or transport runs the networking check by hand (notes/testing.md, When tests run).
- A reviewer who needs main's behaviour builds main's test binary with `tools/bin-at main <out>` (notes/build.md, Profile and command forms) and runs old and new side by side, comparing CPU seconds, not wall time.

## Release checks
Seed-breadth runs reach what per-branch sizes never do. They detect design smells; they are not a safety net: a bug only they find names a subtle property (Design principles, Testing), fixed by a simpler rule plus a small default test.
- When (Tess): as part of the release process (not yet defined: there are no releases yet), and when Tess asks. Never on a coordinator's own initiative, a merge count, a design step or a clock.
- Alone: start one only while no agent is building or testing (between briefs, at a session's end, waiting on Tess), and brief no cargo-heavy agent until it ends. nice 19 does not shield the others: agents spend about three quarters of their wall on builds and tests (`tools/agent-times.py`), so an all-core run beside them slows them directly.
- Not a release check: TLA. TLA is run by hand when TLA is touched (`run.sh <module>`), never automatically: models read no code and TLC is exhaustive, so rerunning unchanged `.tla` files cannot find anything.
- Every offset (`--from`, `_START`, `OSIS_*_SEED`) drawn at random below 10^12 (`python3 -c 'import random; print(random.randrange(10**12))'`), so ranges never repeat without a log; the gate draws its own the same way.
- After a run: update the last-run line below and the counts in notes/testing.md (What finds bugs); an issue per new failure, saying whether the gate's selection at small size fails it too (then the selection missed it, usually a property without a size word: rename it) and naming the property behind it.
- Last full run: main e3cdd005f, every item below at `OSIS_FULL=1` on random offsets: 5.3 h wall, about 119,500 CPU-s at nice 19 beside load 25-100 (sweep 35,350, cut by two livelocked seeds; other properties 54,600; order 19,650; TLC 8,900). Six real bugs, three of which the gate's selection should have caught.

Commands (the full set; an area run takes its own items), under `nice -n 19`:
- `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (every scenario in `osis_sim::SCENARIOS`; at load 30-45 it reached 78 of 150 seeds in 3600 s). A seed past `OSIS_SEED_TIMEOUT_SECS` CPU-seconds (default 600) is named hung; one still running at the end exits the sweep (101) after naming it. A sweep cut by its budget says so only in its per-scenario seed counts: log the seeds that ran.
- Every property not named below: `OSIS_FULL=1 PROPTEST_CASES=256 cargo test -- --include-ignored --skip sweep --skip repro_ --skip _probe --skip memory:: --skip multi_gb_value_streams` (memory checks run alone, notes/test-scale.md; proptest's seed cannot be rotated).
- `OSIS_FULL=1 OSIS_ORDER_START=<S> cargo test -p osis-node --test it -- --ignored order::held_set_decides_` (plain and exhaustive, 80 seeds each).
- `OSIS_PERM_SEED=<P> cargo test -p osis-perm` (only osis-perm reads it) and `OSIS_PERM_SEED=<P> cargo test -p osis-perm --test it -- --ignored differential:: queries:: incremental::`.
- `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_ --skip hostile_moves --skip shrink_script`.
- Every seed-ranged harness has a `_large` twin (notes/test-harnesses.md Seed runners).

How:
- Harness runs with an overridden range print it even when passing (notes/test-harnesses.md); check that line, not only `1 passed`.
- Judge a slow item by its CPU-s (`/usr/bin/time`), not wall, before suspecting a regression: at nice 19 beside load 30-50 a harness ran 30x slower than its CPU-s say.
- Scope: each check belongs to a component (today all core); run a component's checks only after significant work on it, and the dev loop of one component never pays for others. A new component gets its own properties and release checks, and tools/gate.sh selects by what the branch touched. If the checks grow, first make them faster without losing coverage.

## Standing agents
Four roles run beside the task work, each an opus agent with the brief below. **Cadences are approximate floors, not targets (Tess):** these jobs tend not to get done, so the cadence keeps the habit; launch them more often, or other jobs like them, when the need shows. One may run continuously instead of starting and stopping. **Coordinators split the roles between them** as they like and record who holds which in the osis channel (notes/dogfood.md). **Each coordinator counts agents spawned since each role's last run**, and starts the role when its count comes due. **Each role keeps the normal rules:** its own worktree, a fresh reviewer, the gate, and the design principles above. Act on each report: fix tooling or notes yourself, file issues, or brief a worker.

**Watchdog**, about one per 15 agents spawned, and after a release-check run. Brief: "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py --long 3 --since <the last watchdog's commit>` and read the gate logs the coordinator kept. Per agent: wall time against its task, model time against waiting on builds, tests and benches; anything hitting the 180 s subagent cap repeatedly, timing out or writing a wait loop; a build or test far over notes/build.md's costs (3x at low load is a bug: find why, don't blame load); checks off the per-branch list (notes/testing.md, When tests run); any run paying for a component nobody worked on (app tests in core work, core sweeps after app-only work, a workspace run where one component's would do); which reviews found bugs and what kind of test found them. Disk (notes/build.md, Disk): `du -sh .worktrees/*/target`, `df -h .`; a target well above the warm size holds stacked generations (delete and rebuild) or a stray artifact set (`-p`, `--features`, env flags: find the command); more worktrees than agents means a skipped `wt trim`; stray targets (`find ~ -maxdepth 4 -name CACHEDIR.TAG -path '*target*'`) and scratch dirs over a GB. Read notes/complaints/ and notes/time-limits.md's Hits. Verify every claim about a file or tool on current main. Report what is fine, what cost time for a fixable reason (agent, command, how long, why), patterns worth fixing, and complaints not worth fixing; delete every file in notes/complaints/ you read (every coordinator's); your findings go on the osis channel for every coordinator. Notes and complaints only, no code; commit in a worktree, don't push."

**Test optimizer**, about one per 8 agents. Brief: "Make the tests faster and cleaner without losing significant coverage. Start from issues/tests-4x.md and the latest test profile (notes/testing.md, Default-test cost) and pick the area by that evidence, plus `tools/limits.py tests` (every default test under the heavy lock for minutes: not an instant check) and complaints. You may delete tests that are not useful (show what else covers them), speed up specific slow tests or functions, change the patterns or design of a test system, or make core osis faster where tests pay for its slowness. Count work in debug tests (instructions with `tools/icount`, passes, reads); no timing runs. Report the before and after counts and what coverage moved."

**Cleanup**, about one per 5 agents. Brief: "Simplify, refactor and delete code in <area, or pick one by evidence: `tools/loc.py`, profiles, complaints>. Find targets with a `#[deprecated]` probe: a wip commit marking every `pub` item of the crate `#[deprecated]`, then one `cargo clippy --all-targets --message-format=short` (under a minute warm; GUI crates need their own `-p` run) lists every use site in every crate (`use of deprecated [a-z ]+`): aggregate by item, leaving out the crate's own `src/`, and read the unused and test-only ones as candidates (a name-based grep over-reports shared names like `new`, `copy`). Also `tools/dup_windows.py <dir>` (copies; it finds little in crates already cleaned) and fns returning `Result` that never return `Err` (an infallible `Result` keeps dead error paths and state alive). Policy's `tools/dead_pub.py` misses methods that share a name with another type's and items called only by their own tests; recheck an allow-list reason naming a pending decision. A helper must save more lines than it and its doc comment cost: count before keeping it. Drop extra complexity and general code volume: duplicated rules, dead paths, vestiges of replaced concepts (removed at the root: code, tests, notes, spec), needless state. Behaviour stays; where a test counts work, count it in a debug test; no timing runs. Report what went and the line counts before and after."

**Prose editor**, about one per 8 agents. Brief: "Rewrite and simplify the text of <area, or pick one: usually notes/, also spec/, issues/ or elsewhere>. Reorganize, split and merge files so what a reader looks for is easy to find; make the text simpler, logically ordered, consistent and correct (run commands to verify claims; light code edits only where needed, e.g. a comment citing a moved section); delete outright what is no longer or never was useful (references to old designs, logs of work git already holds, descriptions of the obvious); leave less text in total, the rest maximally useful. Before committing, walk your `git diff` and for every removed rule, number, reason or rejected alternative name where it now lives or why it goes; keep Tess's own wording (lines marked Tess) as she wrote it. Keep CLAUDE.md's rules: notes state what is true now, never change narration; spec/ holds no justification or examples; every note, issue and spec keeps its `> Summary:` line, issues their Priority and Tags. Spec edits need no sign-off from Tess unless significant to, or in conflict with, spec/requirements.md."

## Complaints
`notes/complaints/<branch>.md`: low-priority workflow mishaps, footguns and slow spots an agent met, a few lines, committed with the branch; anything that blocked it, a tool that gave a wrong answer, or a check far over its documented cost goes in the report too. Whichever coordinator's watchdog runs reads every file there (every coordinator's), keeps the patterns in notes, deletes them all, and posts its findings on the osis channel (notes/dogfood.md).

## Several coordinators at once
One coordinator by default. When more run at once, each on its own machine, one is the lead (Capstan, they/them): the one Tess names, else the one the coordinators agree on (the longest-running by default). The lead assigns areas and settles disputes; the others take work from it and report to it. Slots: The task loop (Slots). They talk over the osis channel (notes/dogfood.md) and split by issue area (Tags), anything unclaimed going to whoever claims first. Protocol: post `claim: <issue> (<branch>)` before `wt claim` and `merged: <sha> <branch>` after each push; `git pull --rebase` before every push; in shared notes add your own section or row, never rewrite the other's; relay Tess's decisions verbatim with `tess:`; a pinned-binary bump is `bump? <sha>`, answered `bump ok`, before either side rebuilds. Each runs the release checks for its own areas.

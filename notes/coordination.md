# Coordination
> Summary: How a coordinator session runs osis work: one opus worker per task in a worktree, a fresh opus reviewer, gate in the worktree, fast-forward main; at most three agents; the periodic checks and their cadence; the watchdog that reviews how the session went; the complaints directory agents write to.

The build and test mechanics are in notes/build.md; this note is the process around them.

## A coordinator session
- A session is one coordinator's run, of whatever length; notes/mvp-progress.md gets one section per session listing what merged, owner decisions, what was left in flight, and the periodic-check offsets used. (The older sections are titled "Production round N"; a round is the same thing.)
- Test budget per task (owner: cut testing time without letting issues slip): seed breadth belongs to the periodic checks, not to branches. A worker runs tier 1, clippy, the repro that motivated the task and a quick targeted check of what it changed (not the gate: the reviewer gates after rebasing); the reviewer runs the per-branch oracles of notes/testing.md at their default sizes on a fresh offset plus any differential it writes, then the gate (test-speed measurement: the per-branch set is the largest per-agent cost, e.g. perm tier 2 ~1860 CPU-s, exhaustive order ~1300; running it once per branch instead of twice keeps the coverage). Briefs name those sizes, never periodic-sized ranges (300/200/1000/3000 seeds: those cost 30-60 min per agent and duplicated what the next periodic run covers). A branch that changes an invariant the per-branch set does not reach gets one targeted larger run, said why in the brief. To keep breadth, periodic runs go more often (whenever about six branches merged, or when idle). Effect (watchdog, 5 h after vs 10 h before, about 28 agents each): reviewers median 22 to 14 min, build/test wait per reviewer 16 to 9 min, per worker 19 to 15 (outliers excluded), model share 29% to 35%, merges per hour doubled (15 in 5 h vs 15 in 10 h); periodic run 5 found no product bug the branches had missed.
- Networking per-branch check in briefs: `cargo test-net -- --ignored driver:: runtime:: quic relay lan iroh` (unfiltered it runs all of tier 2 incl. timing benches; notes/build.md).
- Per task: `wt claim <branch>` for an opus worker (brief: the issue, the oracles for its area, the standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, commit, `wt release`, report); then a fresh opus reviewer on the same worktree (correctness review of the diff, targeted differentials for the invariant the branch changed, small fixes committed, `git rebase main` then `tools/gate.sh`; the gate is the reviewer's only full tier-1/clippy run, beyond it only targeted oracles for the changed invariant on fresh ranges); `wt release` only as the very last step after the last commit (a worktree released early is free for the next claim while its agent still works there: that happened once, and the next agent's commit landed on a detached HEAD instead of its branch; `claim` now refuses a worktree that is not on the branch after checkout); then the coordinator fast-forwards main from the local branch (`git merge --ff-only`, push main, `git branch -d`; task branches are never pushed or fetched: worktrees share the repo's branches), records the item, and briefs the next task. At most three agents at once, workers and reviewers counted together; two worktrees stay warm, more are made and trimmed as needed.
- Briefs say `wt claim <branch>` prints the worktree; they do not predict which one (agents reported being misled when it differed). A reviewer who needs main's behaviour for comparison builds main's test binary once in the worktree and copies it to scratch, then runs old and new side by side; under load compare CPU seconds, not wall time.
- Reviews are where bugs are found: of 20 merges in one session, 8 reviews found 5 real bugs, all through targeted differentials or reading, none through re-running default test ranges. Keep the reviewer brief focused on the invariant the branch touched, and ask for a differential test of it.
- Per-branch tier-2 oracles finish in minutes (notes/testing.md); long runs are periodic, below.

## Adjustments (round 13 trajectory analysis, owner-approved)
- Re-review: a reviewer change bigger than a small fix gets its own fresh reviewer before merge (round 13: an unreviewed reviewer rewrite of the deaths window produced four bugs the next periodic run found).
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- After each periodic run, append a row to the bug log in notes/mvp-progress.md: per area, bugs found and from which oracle, so convergence is read directly.
- Two agents, not three, while the box runs at load above about 20; waiting on builds is the main cost.
- Performance: the coordinator owns it (owner: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade"). Budgets in notes/testing.md (Performance budgets); a new incremental path needs a measured miss of a budget in a realistic scenario, and simple from-scratch code that meets the budget wins.
- App work (kit/, app/): planned with the owner in a separate UX/planning session (notes/app.md); it runs alongside core work and counts toward the agent limit.
- Core asks from app work: whatever kit/app needs from core and core lacks becomes an issue tagged `core-ask` (plus the component); app work uses a workaround meanwhile (e.g. durable data until ephemeral data lands), never edits core itself. If the fix is not obvious, also tag `owner-call`: the owner reviews it in a core coordinator session.

## Periodic checks
What: the seed-breadth runs that catch what the default ranges never will (every bug caught by a generated input in the last session came from a seed or range nobody had run): `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (45 scenarios: about 20 s per seed row at load 25-35, so 2400 s stopped at 115 of 300; 150 finishes in about 50 min at that load), `OSIS_ORDER_START=<S> OSIS_ORDER_SEEDS=300 cargo test --workspace --test it order::arrival_order_alike_large_spec_permissions_5_2 -- --ignored` (2 min on 16 threads) and the same with `OSIS_ORDER_SEEDS=200 ... order::arrival_order_exhaustive_large_spec_crdt_4_8` (13 min), `OSIS_PERM_SEED=<P> cargo test -p osis-perm` (only osis-perm reads it) and the osis-perm tier-2 set at that seed (`OSIS_PERM_SEED=<P> cargo test --workspace --test it -- --ignored roster:: differential:: queries:: incremental::`, 2.4 min), `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_` (the crdt random tests at other seeds), `OSIS_WALKS_START=<W> OSIS_WALKS_SEEDS=1000 cargo test --workspace --test it walks::open_equals_rebuild_random_histories -- --exact` (1 min on 16 threads), `core/test/tla/run.sh small`; offsets rotate and are logged in notes/mvp-progress.md so ranges never repeat. A sim sweep cut by its `--budget-secs` says so only in its per-scenario seed counts: log the seeds that ran, not the ones asked for. Harness runs with an overridden range print it even when passing (notes/build.md, harness env vars); check that line, not only `1 passed`. Run the whole periodic script under `nice -n 19`: at normal priority it held the box at load 25-35 for 2 h and every worker's and reviewer's gate in that window took 250-530 s instead of 80-150 s.

Scope: each periodic check belongs to a component (today all to core). Run a component's checks only after significant work on that component; a session that worked on the app alone does not run core's sweeps, and core work does not run app checks. The same rule holds for the dev loop itself: working on one component must not incur the costs of components not being worked on (an app's tests do not run while iterating on core, and the gate for a core branch runs app tests only if the `osis` API surface changed); when a new component arrives, give it its own per-branch oracles and periodic checks and extend `tools/gate.sh` to select by what the branch touched (notes/build.md).

When: in the background, in a spare worktree, roughly every six times as long as they take to run: at about an hour per run (2-2.4 h at load 25-35 now: eph random_window 1000 seeds 34 min one seed at a time, now on a thread per core (200 seeds of all three 89 s at load 20), the sweep 40 min, exhaustive order 16 min, strays 15 min), every six hours of coordinator work; slower on a slow box, more often if they get faster. Not at the start of every session unless they have not run for a while. If they grow, first look for a way to make them faster without losing what they check (the order harness went from 12 minutes to under 2 by running seeds on a thread per core), then run them less often. Before a release, run them at full length regardless.

## The watchdog
When the periodic checks finish, spawn one opus agent with this brief, and act on its report (fix tooling or notes yourself, file issues, or brief a worker): "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py` (the session's tasks dir; `--since` the last watchdog run) and read the gate logs the coordinator kept. For each agent: was its wall time reasonable for its task, how much was model time against waiting on builds, tests and benches, did anything hit the 180 s subagent cap repeatedly, time out, or write a wait loop; did any build or test take far longer than notes/build.md's expected costs (3x at low load is a bug: find out why rather than blame load); did agents run checks that are not on the per-branch list (notes/testing.md); did any agent, gate run or periodic check pay for a component nobody was working on (app tests during core work, core sweeps after app-only work, a whole-workspace run where a component's own would do): that shape of waste is a standing thing to look for; did reviews find bugs and what kind of test found them. Check disk: `du -sh .worktrees/*/target` and `df -h .`; a warm worktree target settles at 11-12 GB by `du` (notes/build.md); one well above that holds stacked artifact generations (after a profile, layout or toolchain change: delete it and rebuild) or a stray artifact set (`-p`, `--features`, env flags: find the command in the transcripts); more worktrees than agents means `wt trim` was skipped; also look for stray `target/` dirs outside the worktrees (`find ~ -maxdepth 4 -name CACHEDIR.TAG -path '*target*'`) and scratch dirs over a GB. Read every file in notes/complaints/ and the latest worker and reviewer reports the coordinator has in the progress note. Verify every claim about a file or a tool against the current main checkout before reporting it (two agents reported CLAUDE.md as stale when it was current). Then report: what is fine, what cost time for a fixable reason with the evidence (which agent, which command, how long, why), patterns across complaints worth fixing, and complaints not worth fixing (delete those files; fold the worth-fixing ones into your report and delete them too, so the directory holds only what the coordinator has not yet seen). Do not change code; notes and the complaints directory only. Commit and release your worktree if you used one."

## Complaints
`notes/complaints/` is where agents leave low-priority workflow mishaps, mistakes, footguns and slow spots they met, one file per task named after the branch (`notes/complaints/<branch>.md`, a few lines each, appended to during the task), committed with the branch. High-priority problems (something blocked you, a tool gave a wrong answer, a check took far longer than its documented cost) go in the report to the coordinator as well. The watchdog reads the directory, keeps the patterns, and deletes what it has consumed; the coordinator never has to read it directly.

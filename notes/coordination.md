# Coordination
> Summary: How coordinators run the work: the job mix (Tess), the task loop (opus worker, fresh opus reviewer who gates once, fast-forward main; up to 3 agents, every branch on main), known failures, test budget and time limits, briefs, rewriting an area, release checks, standing job briefs, complaints, several coordinators.

Design principles every agent follows: notes/principles.md. Build and test mechanics: notes/build.md; the gate: notes/gate.md. Starting a session: read the handoff note (notes/, named handoff) when one exists and delete it once its items are taken; a coordinator ending a session with work open writes it. What is in flight is the local task branches (`git branch`) and their worktrees.

## Job mix (Tess)
Three worker agents at once (reviewers count against them), in four kinds of job. Cleanup, code quality and workflow come before velocity on the primary workstream:
- **Cleanup**: at least one at all times: simplify notes, rewrite or delete redundant tests, dedupe and refactor code; in practice line count goes down. osis should ship with less code than it has; a cleanup may carry a bug fix or feature, always framed as making things simpler and more consistent.
- **Workflow**: about half the time: test speed first (faster tests without real coverage loss build osis faster and better; the test-time limits are soft), then watchdog, tools that speed agents up, sorting piled-up branches, hunting slowdowns.
- **Primary workstream** (the top item of notes/priorities.md, which says how to use and keep it) and **bug fixes** share the rest (about 1.5 agents): big pieces first, details after. Bug fixes are worth it when a bug threatens the design, slows or masks tests, or goes away with a complication a cleanup removes.
- **Park on a direction snag (Tess).** When a job hits something that questions the direction of what is being built, park it (wip commit, an issue or note stating the question) and run other work, rather than charging forward. Signs of a build going off the rails: a second copy of an existing mechanism, tweaked; an alternative architecture nobody expected to need. The goal is a clean, simple implementation of the model.
- Fable agents for hard jobs only, about 0.5 running on average.

How to run them (Tess):
- Complexity-bound first, CPU second, not token-bound; heavy token use is a symptom of complexity. Less code that still moves toward a working osis is better.
- osis is not in production: break main, delete tests you mean to rewrite slimmer, skip mature-codebase process. Process is quick, dirty and effective; no long incremental refactors or multi-branch rebases.
- A "critical security bug" is not urgent before release. A special-case fix can hide and ingrain a design flaw; a bug may be the first sign a design tweak is needed.
- While the primary workstream rebuilds on main (main broken, one gate at its end), cleanup and workflow jobs land on their crates' tests and clippy, no reviewer or gate; a branch changing a rule others build on still gets a fresh reviewer, and so does a cleanup deleting a product check (not a test) because no test catches its mutant: a surviving mutant shows the tests are blind, not that the check is redundant (crdt's overlapping-runs check, deleted on its crate's tests, failed the decoder differentials one run in six on main).
- A question for Tess never stalls a worktree: pick the simpler option, note whether it is easily reversed and what depends on it, record it as a `tess-call` issue, keep going.

**Working with Tess**
- Ask one question at a time, with the trade-off and why users care, in plain words.
- Requirements changes need her sign-off; spec, code and notes don't (CLAUDE.md).
- Don't record a recommendation as decided mid-discussion; check what she already decided before asking again.
- Liking a design's shape is not a go: on a design she is engaged in, propose, then wait for an explicit decision before briefing a build.
- Priorities: security, data loss and core correctness first; performance and optional features wait until the core is solid. If a requirement keeps generating issues, bring her the case for relaxing it rather than papering over it.

## The task loop
- **Worker**: an opus worker claims the branch with `W=$(tools/claim <branch>)` (notes/build.md, Worktrees), pushes it as `<coordinator>-<branch>` so briefs can name its commits, and runs `wt release` as its last step.
- **Reviewer**: a fresh opus reviewer claims the same branch the same way once the worker's `wt release` has ended (a claim during its prune fails, saying so); `tools/claim` puts it on the worker's pushed copy. It reviews the diff for correctness, writes a targeted differential for the invariant the branch changed, commits small fixes, rebases, gates (notes/gate.md, Running it), lands with `tools/land --delete <coordinator>-<branch>` (pushes HEAD to main only from a clean tree that contains origin/main as just fetched and passes `tools/policy.py --baseline`, then deletes the branch's pushed copy; unpiped).
- Every agent gets its worktree from `tools/claim`, never from a path a brief names (a named path may be someone else's claim by then).
- **Slots (Tess).** Up to 3 agents at once, workers and reviewers counted together, and only the coordinator spawns: briefs say "start no agents of your own". Keep two worktrees warm (`wt trim 0`/`1` after a release makes the next claim cold).
- **Re-review**: a reviewer change bigger than a small fix, or a rule a worker-lander (one agent finishing a parked or conflicted branch) reworks or adds, gets a fresh reviewer before the gate. A branch whose second review changes the rule, not a line, goes back to the coordinator for a simpler rule.
- **One gate per branch (Tess)**: the reviewer's, as its last step, after `git fetch && git rebase origin/main` (the gate refuses a HEAD behind origin/main). Policy, the instant checks and clippy run first and fail it in seconds; a gate refused there ran no tests, so running it again is still the one gate; a gate that reached its tests and must run again means the workflow broke: say why in the report. If main moved after the gate, the lander rebases and pushes on `cargo clippy --all-targets -- -D warnings` plus `cargo test -p <crate>` for each crate both the branch and the commits it was rebased over changed; re-gate only on code conflicts. `tools/land` refuses a HEAD lacking origin/main and lists the files both sides changed: the rebase after that refusal is followed by those crates' tests before landing again (a landing skipped them). Never gate a checkout at main's tip (it runs everything, GUI included).
- **A worker landing directly** (no reviewer or gate) runs the properties its change reaches (the sync differential at full size) on the HEAD it pushes. A rebase that brought in a commit changing a file the branch changed (`comm -12` of both sides' `git diff --name-only` under core/) runs them again (a 100-seed differential is 2 holds, about 5 min held); without that overlap the pre-rebase run stands.
- **Docs-only branches** (Markdown under spec/, notes/, issues/): the coordinator runs `tools/gate.sh` (its docs path takes seconds) and merges with no reviewer, except a spec change a build will follow (checked against spec/requirements.md) and a prose editor's rewrite (the reviewer walks the removed facts), which get a reading reviewer. A comment-only Rust change gets a reviewer, whose gate takes the comments path.
- **Known failures.** Exit 0 merges. Exit 3 (KNOWN only) merges with no rerun when each KNOWN failure's text reads as its issue describes; say so. Each `KNOWN-BUT-PASSED` line of the summary is removed from `tools/known_failures.txt` in that landing (its issue too once the reviewer sees its cause gone), or marked `rate:` when its issue shows a seeded failure: a stale line passes every check and hides the next failure of its test. A NEW failure (exit 1) never lands as gated: it is the branch's to fix (the fix is code the gate never ran: rerun each failing test by name at the gate's offset and the changed crates' tests on the fixed HEAD, and say so in the report), or, shown failing on main too (`tools/bin-at main OUT -p CRATE`), gets its issue and `tools/known_failures.txt` line on main first (notes/gate.md, The summary). Main stays green on the properties at small size: one failing on main is the next task.
  - **A `counts:` baseline** (notes/gate.md, The summary) is for a property that fails on main by design until a decision (each check failing in many worlds, not one seed). Run it on main's binary at a fixed setting (`-` for a seed-free one, else `VAR=VAL,...`), copy the counts from its panic's `{...}` map (spaces as `_`), and write `NAME SETTING ISSUE counts:CHECK=N,... PATTERN`. The gate then reports KNOWN `same failing counts`, or `NEW-COUNTS`: the branch changed what fails there, and the reviewer reads why (never by running main's binary beside it: the baseline is main's). A branch that redraws a baselined search (new generator moves) refreshes its line itself, with the reason, so the reviewer only checks it. A landing refreshes the baseline only when its reviewer explains the change in the commit message (better: fewer failing; worse: a regression to fix, not to record).
- **Hung agents**: one quiet far past its task's usual length is asked (SendMessage) or stopped; agents have sat for hours on a permission prompt or on a `Monitor` that never woke. An agent that hits a model usage limit mid-task: commit its worktree as WIP and relaunch in the same worktree.
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- **One base branch (Tess).** Every branch is claimed from `origin/main` and lands on main; no integration branch, no task started on another unmerged branch. Large work lands as ordinary branches in sequence, one builder at a time where they share files. Shared name lists (tools/code_refs_allow.txt, core/base/testenv-known.txt) are one item per line under git's union merge; tools/known_failures.txt merges as a set of records by its own driver (notes/gate.md, Policy checks).
- **Pushed branches** go to GitHub as `<coordinator>-<branch>`; that coordinator deletes them once merged or dropped; one whose coordinator is gone may be deleted.
- **Rebasing a long branch**: rewrite prose into main's terms rather than resolving conflicts mechanically; `git -c rerere.enabled=false` (the shared repo has rerere on, and a resolution recorded for one branch replays into another's conflict); after a both-sides resolution of tests appended at one spot, check the earlier block still ends in `}`; `git show --stat` each commit before the fast-forward; squash only to the merge base (notes/build.md, Footguns).
- **Stopgaps (Tess)**: nothing complex or out of the way. The smallest rule that closes the hole; every code site it touches carries `// Interim (issues/<name>.md): <what replaces it>`, the spec's weaker property and the issue name the replacement, and the replacing build's brief lists every marked site to remove.
- Briefs and reports stay honest about what ran: a deferred or skipped check is reported as such, never as passed.

## Coordinator rules
- A tooling change (tools/, gate, env names) goes through a worktree and runs the tools' own tests (`tools/*_test.*`) and policy, even a one-liner.
- Performance is the coordinator's: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade". Budgets: notes/test-scale.md (Performance budgets). A new incremental path needs a scaling check showing the simple one grows worse than the requirements allow.
- Growth: a change that adds a new kind of permanent data adds or updates a row in notes/growth.md; reviewers check.
- Hostile-only shapes inside data the writer may write: `Priority: low`; fix only when easy, else state the weaker property where the area's note or spec lives.
- App work (libs/kit/, app/) is planned with Tess in a separate UX session (notes/app.md) and counts toward the slots. With no app session active, the core coordinator fixes app breakage itself. What kit/app needs from core becomes an issue tagged `core-ask`.
- Names: each coordinator picks a name and pronouns once it knows the codebase (check the registry), records both here and says them in chat. Sub-agents are `<coordinator>-<branch>` in briefs, reports and complaints.
- Registry: **Lodestar**, she/her. **Tiller**, he/him. **Wren**, they/them. **Sorrel**, they/them. **Fathom**, they/them. **Kestrel**, they/them. **Petrel**, they/them. **Halyard**, they/them. **Bowline**, they/them (app). **Capstan**, they/them. **Sextant**, they/them (reference graph design). **Keel**, they/them. **Gimbal**, they/them (design session with Tess: studies and the terms pass). **Windlass**, they/them. **Mizzen**, they/them.

## Test budget
Seed breadth belongs to the release checks, not to branches (Tess: cut testing time without letting issues slip): reading and targeted new tests find most bugs, rerunning ranges almost none (notes/test-design.md, What finds bugs).
- Worker: the per-worker checks (notes/testing.md, When tests run), its own new tests, the task's repro and a quick targeted check of what it changed. No gate.
- Reviewer: any differential it writes, then the gate, the branch's one full run (never `OSIS_FULL=1` per branch). Whole-crate runs before the gate only for crates its own fixes changed. Reviews find bugs through targeted differentials and reading, not by re-running default ranges: keep the reviewer brief on the invariant the branch touched.
- A branch that changes a test model (held-model, roles-model, crdt-model) gets every property using it through the gate's selection; one that changes an oracle's expectations runs that oracle once before merge.
- Never large sizes in a branch, including a confirming sweep after a seed fix (a 300-seed run holds the heavy lock about 20 min while every other agent queues). A seed fix runs its seed and a test of its mechanism. A branch that changes an invariant the gate's selection does not reach gets one targeted larger run, saying why in the brief; one that adds or rewrites a randomized harness runs it once at `OSIS_FULL=1` before merge.
- **The gate's limit is 10 minutes on ostrich (Tess)**, everything it runs included (it takes far longer: issues/test-time.md) (default tests, the branch's selected properties and sim scenarios): reached by fixing perf problems (product, harness, test design), not by scaling sizes down: a size shrinks only where the extra size is shown to add no coverage; breadth goes to release checks.
- **Time limits (Tess).** Every timed run has two hard limits, CPU time and wall time, each set only a little above what it takes on this box now (the CPU limit tighter, as other work on the box barely moves it; the looser wall limit catches what CPU time cannot: waiting, idle cores, a demoted process), as a multiple of a per-box base unit so limits scale to other boxes: the gate (its one heavy-lock hold, notes/gate.md Steps, step 7, is where they hook in); the default tests; a warm rebuild in its longest common form (an osis-base edit, all targets: about 15 s, limit about 2x); a single test (over 10 s needs a reason); one heavy-lock hold, the largest of these. The gate's stage limits are shares of its own (they sum to at most it), so an over-limit gate names the stages over their share. Values and tooling: notes/time-limits.md, Limits; hits: each box's `~/.cache/osis/limits.log`; patterns and investigation reports: notes/time-limits.md. Every hit and every investigation report is logged with timestamp and box. An agent that hits a limit reports why. An investigation starts when the same limit is hit 5 or more times within 3 hours, when one run exceeds its limit by more than 2x, or when the explanation implies something persistent (tests added that take longer). An investigation may raise a limit only if it finds no good solution, recording what it tried and why the raise is justified; Tess reviews these. A trigger is a chance for the bigger job: when new tests trip the limit, consider whether one is slow, there are too many (drop, consolidate), all are slow (optimize), the whole suite including old tests is slow, tests are designed slowly (a complex scenario where a minimal test proves the same), or the change that needed the new tests made old ones irrelevant (drop them).

## Briefs
**Every brief**
- Standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, start no agents, commit, `wt release`, report.
- Start with `export PATH=/home/ai/.claude/plugins/cache/wmww-agent-skills/reasonable-rust-builds/0.6.1/bin:/home/ai/.claude/plugins/cache/wmww-agent-skills/claudewait/0.1.0/bin:$PATH`: subagent shells lack the plugins' `bin`. Check the versions with `which wt claudewait` in your own shell (a plugin update adds a version directory).
- Say `W=$(tools/claim <branch>)` (from /home/ai/osis) prints the worktree; never predict which one, and `cd` there first. Never a bare `wt claim`: `tools/claim` fetches first (`wt claim` bases on the local origin ref, which may be stale), checks `wt list`, and moves a stale local branch to its pushed copy.
- Say "ignore the working directory your environment names": a spawned agent's environment names the coordinator's shell cwd, and agents that trusted it built in unclaimed trees. So the coordinator never ends a command inside a worktree: `( cd $W && ... )` or `git -C $W`, never a bare `cd` (it persists in the main session); the last command before an Agent call ends in `/home/ai/osis`.
- Say "never touch files in /home/ai/osis itself": an agent writes only in its claimed worktree and its scratch dir (a worker deleted a committed file in the coordinator's checkout).
- Name the agent's own scratch dir (`<scratchpad>/<branch>-<random>`), with the gate log's path inside it, and say `mkdir -p` it first (notes/build.md, Footguns).
- A brief's preamble is one set of rules: a contract that supersedes a rule replaces it there.
- The first `wt release` in a worktree marks for minutes: say to run it in the background.
- Repeat the command rules agents break most (notes/build.md, Footguns): no `timeout` around cargo; `run_in_background`, then one `claudewait` per call (two chained pass the 180 s subagent cap); `wt release` from inside the worktree; a probe variable named `OSIS_PROBE_*`; edit and build in separate calls; `-p <crate> --test it -- <filters>`; TaskStop, never `pkill -f`; `tools/heavy` only around an all-core run, `tools/heavy --short` around one under about 100 CPU-s (a search, a twin, a replay; never `tools/mutate.py`, which takes the lock itself with `MUTATE_HEAVY=1`, never inside `tools/heavy`); the reviewer commits before starting oracles and runs them from a copied binary; `PROPTEST_CASES=N` for deep proptest runs; `--ignored --exact` traps; squash to the merge base, wip-commit before a fix-disabled probe, `git fetch && git rebase origin/main` without a pipe, its result read before gating; `mkdir -p` a scratch dir in an earlier call than the redirect into it (a missing dir ends a background run at once, reported exit 0); no `git stash` anywhere in a command, `list` included (the whole call is denied).

**Sizing and scope**
- **A build brief fits one session**: a list of pieces in order, each ending at a green commit (its crates' tests and clippy pass), and "stop at the first green point once the session is long, push, report what is left". Briefs naming whole phases ran sessions that ended red. Pieces sharing a file are one commit with a count or test per piece (there is no `git add -p` here to split a finished restructure). Pieces coupled through policy's pointer check or a shared trait cannot be green apart: brief them as one commit.
- Don't brief work against a commit that hasn't landed ("if the foundation has landed"): start it after, or state plainly it is absent. Every file a brief names is checked on origin/main first (a brief named an issue only on an unmerged branch).
- Don't brief two jobs into one crate's tests at once: two branches converted the same crdt loops with their own `OSIS_*` names, and the squashed rebase dropped one side's.
- A worker brief names no property the reviewer will run, unless that oracle is the task's repro; then the worker runs that one test at its default size.
- Put the reviewer's "check these cases" questions in the worker brief too, with the simplicity question ("is there a rule with no points/windows/caches that meets the budget?"). Say "do not loosen an existing test: report it".
- Name known-failing tests in the crates a brief runs, and use `--no-fail-fast` on multi-crate runs.
- While main is red by design, land with `python3 tools/policy.py --baseline`; say so in the brief.
- While a differential is being driven to 0 (e.g. the sync differential at `OSIS_FULL=1`), every landing touching engine or sync runs it (split holds under `tools/heavy`) and must not raise the count: landings that skipped it reintroduced failures. A rule added mid-session reaches running workers only by SendMessage. Cost: two holds of 50 seeds, 6-10 min of lock per landing (notes/time-limits.md, Patterns).
- A branch touching node sync, links or transport runs the networking check by hand (notes/testing.md, When tests run). A reviewer who needs main's behaviour builds main's test binary with `tools/bin-at` and compares CPU seconds, not wall time.

**Facts in a brief**
- A brief's facts are measured or marked as guesses: a failure count from both of a crate's binaries (`--lib` and `--test it`, `--no-fail-fast`), never a prediction; an "existing mechanism" grepped for first; the run that fails named, not a search that is clean on main. A cost or cause a review or issue claims is a lead to measure, not the task: issues' guessed causes pointed away from the real one in several fixes, each found in minutes by printing the deciding function's inputs on the failing run (and on the checking settle). A case filed as latent or unreachable gets a hand-written probe through the public API first (one took four writes). Before naming a mechanism for an item, read the item's own issue.
- What a branch changes is read from its `git diff --stat` and `git log`, never copied from the worker's report: a reviewer brief listed changes the branch did not contain.
- Name a commit only once it is on a pushed ref, with that ref (`<sha> on origin/<branch>`), after `git show --stat` shows it is the change meant (a bookkeeping commit's parent is not "before the rule"). A file only on an unmerged branch is named as `git show <commit>:<path>`. Name sections of big notes and issues, not whole files (the Read tool pages at about 25k tokens). Grep a rule's words, an item's name or an env var before citing it (a wrong env var name silently runs the default seeds). Name controls and findings as the code and notes name them (`Unit::Held`, a test's name), never by a numbering the note lacks.
- A rule or deletion a brief proposes is tried against the crate's default tests first (minutes). A rule changing what a node receives, holds or applies is tried against the harness too: `Engine::package` hand deliveries give a commit whole to whatever node a test names (about 270 in core/engine), so such a rule fails tests that relied on the harness, not the product: brief the harness change as its own first piece, with the failure count by class.
- A count is evidence of reach, not an argument (notes/principles.md, How often is not whether). A study or review that recommends refusing, dropping or excluding a case because it is rare (commits in the test suites that need it, callers in the tree, worlds a differential leaves out) has not argued it: the brief asks what a user loses and what the case costs to support, and the coordinator takes a removed capability to Tess before any build. Worlds a differential excludes are a finding to settle, never a rate to accept.

**Failures and seeds**
- Say "first re-run the issue's repro on current main" (issue seeds go stale), and name the commit a measurement or lead came from. A failure taken from a worker's report is replayed on current origin/main by the coordinator before the brief: landings in between fix and break things.
- A property failure is quoted as its replay line. The gate draws seeds at random offsets, so "passed at X" is no evidence of a regression: replay the seed at both ends with `tools/bin-at` before bisecting. A differential failure is briefed as its shrunk script with its rate over worlds on today's main (`differential::worlds`, notes/sync-test-harness.md, Replaying a script), never as a seed number: any byte change moves which seeds fail. A random seed's first failing commit is a trigger, not a cause (a timing change moves a seed into an older bug): write "first fails at", quote the seed's own panic line, not a story of its class, and replay its shrunk script at the good end too.
- A repro brief allows "or show the code already holds the rule" (the gap may be the model's).
- A soundness claim ("sound with no new durable state") is probed in other arrival orders than the repro's, not only the stated one. A review checks every spec trim against the code: a rule the spec drops as subsumed that the code still carries (removing it fails tests) is not subsumed.
- A diagnosis that needed temporary prints keeps them as the harness's failure output or an env-gated dump (as `OSIS_ROTATION_DUMP`).

**Models and searches**
- A new generator, move or sampled search is checked for reach before its silence counts: it fails under a rule known to be weaker, and a count shows how often a move reaches its shape. Hand worlds first, sampling second. A design brief that asks to probe a rule idea allows a throwaway model edit (a scratch patch, reverted before commit).
- A model rule's mutation check mutates each clause, not only the switch its control flips, and reports its margin (failing worlds of N). roles-model's random searches draw world `i` from its own seed (`each_world`), the same on every box, except `paths` (per thread: its worlds differ by core count); the exhaustive families' checks still draw from a per-thread generator. A family sampled by stride is checked for what it still holds (a stride aligned with a bit mask drops cases from every sampled world; a coprime stride does not): `roles_model::family_on_every_core` and the `-- N paths-exh` driver refuse a stride sharing a factor with the family's size (`stride_refusal`); a family is a mixed-radix index, so a new one runs through `family_on_every_core`. A property read as 0 failures at a search's first size is a rate until it holds at 10x that size or over the whole family ("0 in 100,000 `tiny` worlds" was 3 in 1,000,000), so the worker runs the 10x before claiming it.
- A model rule that reads who wrote something (a grantor, a listed or vouched write) gets the hostile-party pass of a security fix (below: who can write each input) in the modelling brief. The rule's text in the design note must give the model's code from its words alone, clause by clause.
- A model change runs the differentials of other crates that draw its worlds: a roles-model `paths` rule or story/tiny generator edit also runs `-p osis-perm --test it -- --ignored paths::` (new story moves broke perm's story differential at the gate; a clause no roles-model test reached decided another); a held-model evidence change runs osis-engine's `evidence::` properties (one gated twice for it).
- A control asserted to fail within a fixed small size is a rate too: a redrawn generator moves which worlds fail it, so size it with a margin when written. Run a changed rule's gate-size search before queueing its 10x run, each 10x search in a hold of its own (nine controls and two story searches at 10x in one hold ran 1.5x the `heavy` limit).
- A held-model brief changing `Aspect` or `Held` also touches osis-engine `tests/it/held.rs` (struct literals): name that crate's tests in it.
- TLA results: name the module (`run.sh <module>`) and by-hand instances by name, sized under the `heavy` hold limit (notes/test-properties.md, TLA+). A one-worker TLC run of seconds needs no lock.

**Security and new code** (in the worker brief)
- Security or convergence fix: the worker writes the invariant the fix relies on as a code comment, plus a randomized differential (or an extended oracle) that fails with the fix disabled; the reviewer attacks that argument. Every new test is checked to fail with its fix disabled. Prefer changing the behaviour an oracle objects to over widening the oracle; find every path that reaches the state (every caller of what mints it) and test each; for every input the rule reads, ask who can write it (a removed party forges at an epoch it held); a cache or visited set in a security walk gets a test where the same keyset is met two ways. A security brief offering options gets a hostile-party pass first. A new bad-input rule or forged-input class extends every hostile generator that builds that shape, in the same branch: a wire rule the generator ignored failed the crdt differential at the gate, and a generator lagging an issue's input class missed a convergence bug its hand tests never reached.
- New module or protocol code: (1) a state table: each map, set and row, who supplies its keys (a peer, the engine, this node), its bound with a test flooding past it, what removes it, and that a restart changes nothing a user sees; (2) per message received: what an unproven, removed or hostile peer controls, and what each reply tells whom; (3) per rule: break it in code and see a test fail (`tools/mutate.py`, one table row per probe, the table in the report); a test fake must not consume what an assert later counts; scripted peers speak through the real encode/decode; (4) every clock read is followed and every expiry sets a wake; (5) the actions the model lacks that the code meets (re-grant, restart, a hostile party) named, each with a test or the model extended; (6) readings of ambiguous spec go into the spec or the area's note in the worker's commit: reviewers never see the worker's report.

**Docs and spec briefs**
- A docs-only brief that deletes notes or issues first greps code for citations of them: a cited file's deletion fails tools/policy.py until the code comments follow (a code change). A new core aspect type is code too: schema/core.osis is compiled by core/osis/build.rs.
- A sweep retargeting a pointer rewrites its gloss when the gloss names the old file's role ("(draft: spec/...)" read as nonsense). A commit deleting or renaming a test or test file greps notes/ and issues/ for its name (deleted tests stayed cited: policy checks only backticked code names).
- After editing cited spec text, run `python3 tools/policy.py`: its `spec_map:` lines name test anchors quoting the old text. A spec wording rename is therefore not docs-only: test citation anchors and spec_map `RULES` substrings quote spec text, so the citation sweep touches tools/ and .rs comments: brief it with the rename and budget the full gate.
- Spec text drafted in notes/ meets policy's checks against today's spec: a pointer to a section only the draft adds fails `tools/doc_refs.py` (cite it by number, or put the name before the path), a planned name in backticks fails `tools/code_refs.py` (leave it out of backticks: an allow entry in tools/ takes the gate off its docs path), and `spec_map.py --gaps` reads spec/ only, so the draft's test anchors are checked by a scratch script matching each anchor piece against the draft's section text.
- A brief adding an item to a numbered registry (a section marked `<!-- registry -->`: the A1/A2 spec drafts' Open lists, the path and evidence model findings) tells the worker to take the next free number at rebase time and fix its own citations then; tools/policy.py (`registries`) refuses a repeat.
- A brief removing a concept has the worker grep notes, issues and the spec drafts for it and sort its senses (most hits are usually other senses), and grep citations by number after a renumber (`move [0-9]`, `§N`): notes and model comments cite story moves and sections by number.

## Rewriting an area
Spec-first delete-and-rebuild works far better than porting in place; Tess's direction is in notes/principles.md (Rewriting an area). How to run one:
- Spec, then models, then code: models find holes before any code exists.
- Foundation first: one agent writes the crate skeleton with every module declared and every shared type in one place; a fresh reviewer checks the shapes by walking two end-to-end flows on paper.
- With slots to spare, an integration agent runs beside the module agents: it drives the merged modules end to end, files what breaks between them and fixes the seams.
- One worker and one fresh reviewer per module, each module a branch on main; workers hand off the new-module checklist (Briefs). Reviews find real bugs by reading for what a hostile or removed party controls, mutating the worker's own tests (some pass vacuously), a whole product flow or a restart with state in flight, asserting what stays, not only what goes, and running `-p osis`.
- A random-history differential with shrinking finds the cross-module bugs; check the oracle before the code (an unknown-outcome write may have happened). Histories replay twice and must match: no hashed collections in that code.
- Decide fast but let implementers push back: prefer the rule whose failure is a wrong keep over a wrong drop, and state the weaker property it gives.

## Release checks
Seed-breadth runs reach what per-branch sizes never do. They detect design smells, not a safety net: a bug only they find names a subtle property (notes/principles.md, Testing), fixed by a simpler rule plus a small default test.
- When (Tess): as part of the release process (not yet defined), and when Tess asks. Never on a coordinator's own initiative.
- Alone: only while no agent is building or testing, and no cargo-heavy agent is briefed until it ends (nice 19 does not shield the others).
- TLA is not a release check: it is run by hand when TLA is touched.
- Every offset (`--from`, `_START`, `OSIS_*_SEED`) drawn at random below 10^12 (`python3 -c 'import random; print(random.randrange(10**12))'`).
- After a run: update the last-run line below and the counts in notes/test-design.md (What finds bugs); an issue per new failure, saying whether the gate's selection at small size fails it too (then the selection missed it, usually a property without a size word) and naming the property behind it. Check each harness's printed seed range, not only `1 passed`; judge a slow item by its CPU-s, not wall.
- Last full run: main e3cdd005f, every item below at `OSIS_FULL=1` on random offsets: 5.3 h wall, about 119,500 CPU-s at nice 19 beside load 25-100. Six real bugs, three of which the gate's selection should have caught.

Commands (the full set; an area run takes its own items), under `nice -n 19`:
- `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (every scenario). A sweep cut by its budget says so only in its per-scenario seed counts: log the seeds that ran.
- Every property not named below: `OSIS_FULL=1 PROPTEST_CASES=256 cargo test -- --include-ignored --skip sweep --skip repro_ --skip _probe --skip memory:: --skip multi_gb_value_streams` (memory checks run alone, notes/test-scale.md).
- `OSIS_FULL=1 OSIS_ORDER_START=<S> cargo test -p osis-engine --test it -- --ignored order::held_set_decides_`.
- `OSIS_PERM_SEED=<P> cargo test -p osis-perm` and `OSIS_PERM_SEED=<P> cargo test -p osis-perm --test it -- --ignored differential:: queries:: incremental::`.
- `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_ --skip hostile_moves --skip shrink_script`.
- Every seed-ranged harness has a `_large` twin (notes/test-harnesses.md Seed runners).

## Complaints
`notes/complaints/<branch>.md`: workflow mishaps, footguns and slow spots an agent met, committed with the branch (CLAUDE.md). The watchdog reads every file there, every coordinator's, keeps the patterns in notes and deletes them all.

## Several coordinators at once
One coordinator by default. When more run at once, each on its own machine, one is the lead (Capstan, they/them): the one Tess names, else the one the coordinators agree on. The lead assigns areas and settles disputes; the 3 slots are shared. They talk over the osis channel (notes/dogfood.md) and split by issue area (Tags). Protocol: post `claim: <issue> (<branch>)` before `tools/claim` and `merged: <sha> <branch>` after each push; read the channel and `git pull --rebase` before every push; in shared notes add your own section or row, never rewrite the other's; relay Tess's decisions verbatim with `tess:`; a pinned-binary bump is `bump? <sha>`, answered `bump ok`, before either side rebuilds. Each runs the release checks for its own areas.

# Coordination
> Summary: How osis is designed and how a coordinator runs the work: Tess's design principles (principle first, carve-outs are smells, test what users observe, options keep their property, model before building); the task loop (opus worker, fresh opus reviewer who gates, fast-forward main, at most three agents); briefs; periodic checks (before a release and after a design step, run alone); the watchdog; complaints; two coordinators.

The build and test mechanics are in notes/build.md; this note is the process around them. Starting a session: read notes/handoff.md first when it exists (what the last coordinator left in flight); delete it once its items are taken. What is in flight is the local task branches (`git branch`; never pushed) and their worktrees; a coordinator ending a session with work open writes notes/handoff.md. Merges need no progress record: git history has them.

## Design principles (Tess)
How osis is meant to be designed. Most fiddly bugs this project has had came from breaking one of these upstream, so apply them before writing code and check them in every review.

**Shape of the design**
- **Principle first.** Every area states, at the top of its note, the one rule it follows (e.g. retention: every drop that is not expiry or purge is a right holder's covering snapshot; keys: rotating needs only the right to rotate). Every other rule there must follow from it. Changing a principle is fine, done deliberately and written down.
- **A carve-out is a design smell.** A fix that gets fiddly, breeds new bugs, or needs a special case, exception or "limit" usually means the design upstream is unclear, impractical or contradictory. Before adding one, check it follows from the area's principle; if not, stop and raise the design question. Reviewers ask of every branch: what exceptions did this add, and which principle do they follow from? A chain of patches in one area (the second seed-found fix) means a class study, not a third patch.
- **Cut tentacles and cruft.** When an edge case has grown a wing of fixes, replace it with the rule that works, a stated limit, or a requirements question for Tess. Delete freely: slow or badly designed tests, notes on how things aren't, issues stating unfixable facts.
- **Rewrite, don't tack on.** Coordinators may change the design within the requirements' words or spirit. A precisely stated design problem beats a hollow finished build.
- **One mechanism, used everywhere.** Before adding a mechanism, look for the existing one it really is (e.g. a key rotation's list and a removal's list are the same witness rule at two levels). Don't drive a general mechanism from one feature's needs (expiry is not designed around ephemeral data).
- **Close leaks; don't shrink them.** Prefer dropping data and fetching again when needed over keeping markers or tombstones "to know". A smaller leak is still a leak.
- **App workarounds for engine costs are a red flag** (chat split messages by calendar year to cap an engine cost). Fix the cost in the engine for every app.
- **Complete refactors.** A rename or concept removal must read as if the code was built that way: code, API, CLI, errors, tests, spec, notes, comments; no aliases or "formerly X". Reviewers grep for remnants.
- **Rare paths may be brute force.** For rare corner cases accept more download, CPU or refetching in exchange for a simple, robust rule; from-scratch beats incremental cleverness unless a measured budget is missed.

**Users and options**
- **Requirements state properties**, not shrink-wrapped behaviour. No features built on protocol side effects. They speak in what a user or app developer observes (no snapshots, frontiers, addenda): a property with exceptions is stated as the weaker property ("generally", "up to"), not as a strong claim plus implementation-level exceptions. The precise rules go in the subsystem specs.
- **Options keep their property.** Where users choose between trade-offs (keep history, no promise, purge on replace), each option keeps its defining property and pays its own cost, stated. Never blend one toward another to dodge its cost.
- **No typical use case.** Examples are not workloads, and examples must not become definitions ("cursors and presence" is not what ephemeral data is). Aim for predictable properties across sizes and edit rates.
- **Names carry the meaning.** Convey intent through API and schema names, not a doc line: the default (no history promised) is unnamed; the costly option is named for what it does (`purge_on_replace`).
- **History is verified or absent.** Never store or use unverified, forgeable history. Expose history only where retention deliberately keeps it.
- **Forks are permanent.** Admin disputes are forks tolerated indefinitely; no rule may wait for one to be settled. Disputes get the simplest rule to build.

**Testing**
- **A failure rate is not a property.** "Loses writes in 64 of 1M worlds" describes the generator, not the system: the property is "can lose writes", so the design is broken, whatever the rate. Report and judge findings as the property they violate; a rate only says how well a test reaches the case.
- **Big random runs finding bugs is a design smell.** A sound philosophy yields a few simple properties ("invalid data cannot affect a value"); small tests check each property, and the properties compose without surprises. When a large random run finds a bug that small tests and review missed, ask which property was subtle ("invalid data affects values in certain ways") and simplify the design until it is plain, then add the small test.
- **Every check runs at every size.** A coverage floor or sanity check that runs only above some seed count hid a dead counter from every full-size run (and floors tuned for full size flip at plain size): derive floors from the run's size or drop them.
- **The smallest test set that gets correctness.** When tests grow slow, rewrite and consolidate around the properties rather than optimizing what is there: add-then-optimize ends in tightly packed slop. Each test names the property it checks; one without a clear purpose goes.
- **Never pin a failing seed.** A seed test is slow and silently stops reproducing as soon as the harness, wire bytes or rng use change. What enters tier 1 is a small, quick, hand-readable minimal reproducer of the property. Turn a pinned seed into a minimal reproducer or delete it. Deleting a test is fine when it checks something we don't care about, a situation that no longer exists, or has no clear purpose.
- **Test what users can observe.** Oracles compare what the API exposes (reads, promised history, errors), not internal state, unless an internal invariant is the point. When a test fails on an unobservable difference, redesign the test. An excuse in an oracle is a carve-out: compute it from the generated history, never from the node under test.
- **Check scaling, not seconds.** What matters is how cost grows with size: count the work (bodies read, commits walked, bytes stored) at n and 10n in a fast tier-1 test. Wall time of a synthetic operation on a busy box tells nothing; no release builds or long timing runs inside a task.
- **Model before building.** Model every major design change first (roles-model, held-model, TLA); greenfield models are cheap and have found real holes every time. A model of the design is an oracle, not a copy of the code.
- **A coherent design is cheap to check;** a pile of constraints with no principle needs exhaustive testing forever and still has bugs.

**Working with Tess**
- Don't block on her: take the reversible option, record the question as a `tess-call` issue, and keep going. Ask one question at a time, with the trade-off and why users care, in plain words.
- Requirements changes need her sign-off; spec, code and notes don't (CLAUDE.md).
- Don't record a recommendation as decided mid-discussion; check what she already decided before asking again.
- Liking a design's shape is not a go: on a design she is engaged in, propose, then wait for an explicit decision before briefing a build.
- Priorities: security, data loss and core correctness first; performance and optional features wait until the core is solid. If a requirement keeps generating issues, bring her the case for relaxing it rather than papering over it.

## The task loop
- `wt claim <branch>` for an opus worker; then a fresh opus reviewer on the same worktree: correctness review of the diff, targeted differentials for the invariant the branch changed, small fixes committed, `git rebase main` then `tools/gate.sh`. Then the coordinator fast-forwards main from the local branch (`git merge --ff-only`, push main, `git branch -d`; task branches are never pushed or fetched: worktrees share the repo's branches), then briefs the next task.
- `wt release` is the agent's very last step, after its last commit: a released worktree is free for the next claim, and a second agent there commits onto the wrong HEAD.
- At most three agents at once, workers and reviewers counted together; two while the box runs at load above about 20 (waiting on builds is the main cost: at load, gates took 440-594 s against 162-171 s quiet, a third of that rebuilding after a rebase that brought osis-crdt/-store/-base changes). Keep two worktrees warm (`wt trim 0`/`1` after a release makes the next claim cold).
- Re-review: a reviewer change bigger than a small fix gets its own fresh reviewer before merge (an unreviewed reviewer rewrite once produced four bugs the next periodic run found).
- Third round rule: a branch whose second review changes the rule, not a line, goes back to the coordinator for a simpler rule before a third reviewer (branches that kept patching a rule spent four rounds on rules later cut).
- Re-gate the rebased branch before the fast-forward, not a checkout at main's tip (there HEAD equals the merge base, so the gate runs everything, kit and app included). A re-gate after a rebase that brought other branches' code costs the same as the reviewer's (the sweep is chosen by the branch's own diff); skip it only when what came in is notes-only or in crates the branch's crates do not depend on.
- A background gate wrapper ends with the gate's code: `tools/gate.sh > $L 2>&1; e=$?; echo gate=$e >> $L; exit $e`, and the log's `== gate passed` is read before merging (`...; echo gate=$?` exits 0, and failed gates were pushed that way).
- A cargo run stopped partway (TaskStop, a killed gate) can leave a crate's incremental cache unable to link (`rust-lld: undefined hidden symbol anon.*`): prefer letting a stale gate finish; else `cargo clean -p <crate>` for the crate that fails to link, not the whole target.
- Hung agents: an agent quiet far past its task's usual length is asked (SendMessage) or stopped. Seen: agents sat for hours on a permission prompt (a foreground `rm` in the scratchpad), and one ended its turn waiting on a `Monitor` whose last event never woke it.
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- Seed chases: a second seed-found fix in one area stops patching; the next task is a study of the class (what rule is missing or wrong). Every chase so far ended with such a study after 10-30 patches (notes/testing.md (Arrival-order differential), notes/crypto.md (Frozen coverage)).
- Main moves under long branches: on rebase, rewrite prose into main's terms rather than resolving conflicts mechanically. On a branch with earlier unmerged commits, squash only to the tip you started from.
- If an agent hits a model usage limit mid-task, commit its worktree as WIP and relaunch in the same worktree.
- Keep briefs and the coordinator honest about what ran: a deferred or skipped check is reported as such, never as passed.
- Simplification pass (Tess, standing): about every six merges, one behaviour-preserving simplification/refactor pass on the area that changed most since the last, with its own reviewer; it counts as a task.

## Coordinator rules
- A tooling change (tools/, gate, env names) goes through a worktree and the gate like any branch, even a one-liner: a coordinator's untested flock line broke main's policy check.
- Models: opus for all workers and reviewers; fable only for thinking through hard problems (design and class studies, root-causing), especially where others delivered sub-par results, never for code-heavy jobs (fable usage is limited).
- Performance is the coordinator's: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade". Budgets: notes/testing.md (Performance budgets). A new incremental path needs a scaling check that shows the simple one grows worse than the requirements allow.
- Growth: a change that adds a new kind of permanent data adds or updates a row in notes/growth.md; reviewers check.
- Hostile-only shapes inside data the writer may write: `Priority: low`; fix only when easy, else state the limit where the area's note or spec lives.
- Issues carry a Priority (critical: now; normal: before release; low: if convenient) and questions for Tess are issues tagged `tess-call`.
- App work (libs/kit/, app/) is planned with Tess in a separate UX session (notes/app.md) and counts toward the agent limit. With no app session active, the core coordinator fixes app breakage itself. What kit/app needs from core becomes an issue tagged `core-ask`.
- Names: each coordinator picks a name and pronouns once it knows the codebase (check the registry), records both here and says them in chat. Sub-agents are `<coordinator>-<branch>` in briefs, reports and complaints.
- Registry: **Lodestar**, she/her. **Tiller**, he/him. **Wren**, they/them. **Sorrel**, they/them. **Fathom**, they/them. **Kestrel**, they/them.

## Test budget
Seed breadth belongs to the periodic checks, not to branches (Tess: cut testing time without letting issues slip). Of about 200 merged tasks' bugs, reading and new targeted tests found about 225, per-branch oracles about 25, periodic and wide runs about 10, rerunning already-run ranges about 2 (notes/testing.md (What finds bugs)).
- Worker: tier 1, clippy, its own tests, the task's repro, a quick targeted check of what it changed, and the instant checks (`python3 tools/policy.py && python3 tools/spec_map.py --uncited && python3 tools/spec_map.py --gaps`: uncited tests, MUSTs without a RULES anchor and unlisted `OSIS_*` variables are what failed reviewer gates). Then commit; no gate (the reviewer gates after rebasing; worker gates cost hours of agent wall and load everyone else's).
- Reviewer: the per-branch oracles of notes/testing.md for the area the branch touched, at plain sizes (a tenth of full, `osis_base::testenv::large`; never `OSIS_FULL=1` per branch) on a fresh offset, plus any differential it writes, then the gate. The gate is its only full tier-1/clippy run.
- A branch that changes a test model (held-model, roles-model, crdt-model) or an oracle's expectations runs every tier-2 oracle that uses that model once before merge: a held-model rewrite once made half the order seeds fail on main for several merges because only tier 1 ran.
- Never periodic-sized ranges in a branch (300/200/1000/3000 seeds cost 30-60 min per agent and duplicate the next periodic run; one `_large` harness at 300 seeds was 19,450 CPU-s). Before briefing, add up the oracle set's CPU-s (testing.md costs) and keep it at default sizes. A branch that changes an invariant the per-branch set does not reach gets one targeted larger run, saying why in the brief.
- A branch that adds or rewrites a randomized harness runs it once at `OSIS_FULL=1` before merge (plain sizes have passed while full size failed 4.6% of seeds).
- One all-core run (gate, oracle set, sweep, tier-2 set, TLC at several workers) at a time per box: three at once ran each at a third of the speed, and two overlapping gates each took about twice as long as one alone (sides and live-write-lost 1665 and 1562 s, addenda and retention-1 934 and 793 s, against 320-450 s alone), so neither merged sooner. A reviewer whose gate would overlap another waits for it.
- Main stays green on the per-branch oracles at plain size: one failing on main is the next task (or gets a `repro_` twin and its range skipped), since while it fails every reviewer in that area pays a `tools/bin-at main` build (3-20 min) to tell old failures from new.
- Reviews are where bugs are found, through targeted differentials and reading, not re-running default ranges. Keep the reviewer brief on the invariant the branch touched, and ask for a differential test of it.

## Briefs
Standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, commit, `wt release`, report.
- Subagent shells lack the plugins' `bin` on PATH: briefs start with `export PATH=/home/ai/.claude/plugins/cache/wmww-agent-skills/reasonable-rust-builds/0.5.1/bin:/home/ai/.claude/plugins/cache/wmww-agent-skills/claudewait/0.1.0/bin:$PATH`.
- Say `wt claim <branch>` prints the worktree; never predict which one.
- Name the agent's own scratch dir (`<scratchpad>/<branch>-<random>`) and say never `rm` in the scratchpad (a foreground `rm` there hangs on a permission prompt; use python `shutil` or leave files). Where /tmp is tmpfs (`findmnt -T /tmp`; on ostrich it is the root disk) scratch binaries are RAM: many copies overwrite one name.
- A worker brief names no per-branch oracle the reviewer will run, unless that oracle is the task's repro; then the worker runs that one test at its default size on one fresh offset, and the reviewer brief says to skip it.
- Put the reviewer's "check these cases" questions in the worker brief too (a case asked only of the reviewer cost a second round). Say "do not loosen an existing test: report it".
- Security or convergence fix: the worker writes the invariant the fix relies on as a code comment, plus a randomized differential (or an extended oracle) that fails with the fix disabled; the reviewer attacks that argument. Every new test is checked to fail with its fix disabled.
- Ask the simplicity question in the worker brief ("is there a rule with no points/windows/caches that meets the budget?"), not first in review.
- Say "first re-run the issue's repro on current main" (issue seeds go stale).
- Name sections of the big notes, not whole files (testing.md, permissions.md, ephemeral.md, sync.md are each around 100 KB or more).
- Grep the rule's words before citing a spec section or env var (a wrong env var name silently runs the default seeds).
- A brief asking for TLA results names the module (`run.sh <module>`); by-hand instances by name (README rows give their size: some take an hour).
- The three git footguns: squash with `git reset --soft $(git merge-base HEAD main)`, never `main`; wip-commit before a fix-disabled probe, so the `git checkout <file>` that undoes it loses nothing; `git fetch && git rebase origin/main` (local main lags when the other box merges), without a pipe, and read its result before gating (gates have passed on half-rebased trees; tools/gate.sh does not detect a rebase in progress).
- Command rules agents broke most (all in notes/build.md, repeated in briefs): never wrap any cargo command in `timeout` (it kills tier 1 with a green-looking log, and a killed build left osis-engine unable to link): `run_in_background`, then one `claudewait` per call. Edit and build in separate calls. Narrow node runs with `-p osis-node --test it -- <filters>`, never `--workspace --test it` (a `0 passed` line per crate hides the one that ran) and never two filters before `--`. Use the task ID the tool printed, never `ls -t` on the shared tasks dir. Never `pkill -f`/`pgrep -f` (it kills the caller's own shell): TaskStop. The reviewer commits before starting oracles and runs them from a copied binary (agents edited sources under running builds). Deep proptest runs pass `PROPTEST_CASES=N` (`.cargo/config.toml` sets 32, which overrides a test's own `cases:`). `--ignored --exact` on a tier-1 env-ranged test (walks, deaths, undoexp) runs nothing and says ok: run those without `--ignored`.
- Networking per-branch check: `cargo test-net -- --ignored driver:: runtime:: quic relay lan` (unfiltered it runs all of tier 2 incl. timing benches).
- A reviewer who needs main's behaviour for comparison gets main's test binary with `tools/bin-at main <out>` (notes/build.md) and runs old and new side by side; under load compare CPU seconds, not wall time.

## Periodic checks
Seed-breadth runs reach what per-branch sizes never do. They detect design smells; they are not a safety net: a bug only they find names a subtle property (Testing, above), fixed by a simpler rule plus a small tier-1 test.
- When: before a release, everything at full length; and after a large design step in an area merges (a retention step, a new mechanism such as addenda), that area's checks only (its sweep scenarios at 150 seeds, its `_large` twins at `OSIS_FULL=1`). Never on a merge count or a clock.
- Alone: start one only while no agent is building or testing (between briefs, at a session's end, waiting on Tess), and brief no cargo-heavy agent until it ends. nice 19 does not shield: during the e3cdd005f run gates took 316-934 s against 273-377 s just before, and a worker's first tier 1 took 36 min. Agents spend about a quarter of their wall thinking and the rest on builds and tests (`tools/agent-times.py`), so an all-core run beside them slows them directly.
- Not periodic: TLC. Models read no code and TLC is exhaustive, so rerunning unchanged `.tla` files cannot find anything (no periodic run has); the branch that edits a model runs `run.sh <module>`.
- Every offset (`--from`, `_START`, `OSIS_*_SEED`) drawn at random below 10^12 (`python3 -c 'import random; print(random.randrange(10**12))'`), so ranges never repeat without a log; reviewers' fresh offsets the same way.
- After a run: update the last-run line below and the counts in notes/testing.md (What finds bugs); an issue per new failure, saying whether a per-branch oracle at plain size fails it too (then the per-branch list has a gap: fix notes/testing.md) and naming the property behind it.
- Last full run: main e3cdd005f (the tier-2 set at `OSIS_FULL=1` with every `OSIS_*_START` and seed var drawn at random): 5.3 h wall, about 119,500 CPU-s at nice 19 beside load 25-100. Sweep 35,350 CPU-s, killed past its budget by two livelocked seeds (tally lost); tier-2 set 54,600; order alike and exhaustive 19,650 (nothing found); TLC 8,900 (nothing). Six real bugs: three per-branch-list gaps (paged-apply-dead-writes fails at seed 1, gap-snapshots-gonemap-differ at the harness's own default range, cli-own-serving-get-fails on every run) and three breadth-only (addenda-answer-loop 2 of 150 sweep seeds, eph-capped-host-keeps-dropped 3 of 150, eph-reverts-restarts-differ 1 of 200), all three in areas with redesigns queued. Test bugs: order-judged-0-stale, and the hygiene items of notes/test-design.md steps 1 and 3.
Commands (the full set; an area run takes its own items):
- `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (51 scenarios; at load 30-45 it reached 78 of 150 seeds in 3600 s; a seed past `OSIS_SEED_TIMEOUT_SECS` CPU-seconds, default 600, is named hung, and one still running at the end exits the sweep, 101, after naming it). A sweep cut by its budget says so only in its per-scenario seed counts: log the seeds that ran.
- `OSIS_FULL=1` on every tier-2 test named below that takes its plain default.
- `OSIS_FULL=1 OSIS_ORDER_START=<S> cargo test -p osis-node --test it -- --ignored order::held_set_decides_` (plain and exhaustive, 80 seeds each).
- `OSIS_PERM_SEED=<P> cargo test -p osis-perm` (only osis-perm reads it) and `OSIS_PERM_SEED=<P> cargo test -p osis-perm --test it -- --ignored differential:: queries:: incremental::` (2.4 min).
- `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_ --skip hostile_moves --skip shrink_script`.
- Every seed-ranged harness has a `_large` twin (notes/testing.md Seed runners).

How:
- Harness runs with an overridden range print it even when passing (notes/build.md); check that line, not only `1 passed`.
- Run the whole script under `nice -n 19` and judge a slow item by its CPU-s (`/usr/bin/time`), not wall time, before suspecting a regression: at nice 19 beside load 30-50 a harness ran 30x slower than its CPU-s say.
- Scope: each check belongs to a component (today all core); run a component's checks only after significant work on it; the same holds for the dev loop (working on one component must not pay for others). A new component gets its own per-branch oracles and periodic checks, and tools/gate.sh selects by what the branch touched. If the checks grow, first make them faster without losing coverage (the order harness went from 12 min to under 2 with a thread per core).

## The watchdog
After a periodic run, and otherwise about every 15 merges, spawn one opus agent with this brief, and act on its report (fix tooling or notes yourself, file issues, or brief a worker): "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py --long 3` (defaults to the session that last ran agents; `--since` the last watchdog run) and read the gate logs the coordinator kept. For each agent: was its wall time reasonable for its task, how much was model time against waiting on builds, tests and benches, did anything hit the 180 s subagent cap repeatedly, time out, or write a wait loop; did any build or test take far longer than notes/build.md's expected costs (3x at low load is a bug: find out why rather than blame load); did agents run checks that are not on the per-branch list (notes/testing.md); did any agent, gate run or periodic check pay for a component nobody was working on (app tests during core work, core sweeps after app-only work, a whole-workspace run where a component's own would do): that shape of waste is a standing thing to look for; did reviews find bugs and what kind of test found them. Check disk: `du -sh .worktrees/*/target` and `df -h .`; a warm worktree target settles at 11-12 GB by `du` (notes/build.md); one well above that holds stacked artifact generations (after a profile, layout or toolchain change: delete it and rebuild) or a stray artifact set (`-p`, `--features`, env flags: find the command in the transcripts); more worktrees than agents means `wt trim` was skipped; also look for stray `target/` dirs outside the worktrees (`find ~ -maxdepth 4 -name CACHEDIR.TAG -path '*target*'`) and scratch dirs over a GB. Read every file in notes/complaints/ and the worker and reviewer reports the coordinator appends to this brief. Verify every claim about a file or a tool against the current main checkout before reporting it. Then report: what is fine, what cost time for a fixable reason with the evidence (which agent, which command, how long, why), patterns across complaints worth fixing, and complaints not worth fixing (delete those files; fold the worth-fixing ones into your report and delete them too, so the directory holds only what the coordinator has not yet seen). Do not change code; notes and the complaints directory only. Commit and release your worktree if you used one."

## Complaints
`notes/complaints/<branch>.md`: low-priority workflow mishaps, mistakes, footguns and slow spots an agent met, a few lines, appended during the task and committed with the branch. Anything that blocked it, a tool that gave a wrong answer, or a check far over its documented cost goes in the report too. The watchdog reads the directory, keeps the patterns and deletes what it consumed; with two coordinators at once, each watchdog deletes only its own session's files (commit author and offset tell them apart).

## Several coordinators at once
One coordinator by default. When more run at once (each on its own machine), one is the lead at any time: the one Tess names, else the one the coordinators agree on (the longest-running by default). The lead assigns areas and settles disputes; the others take work from it and report to it. They talk over the osis channel (notes/dogfood.md) and split by issue area (Tags), anything unclaimed going to whoever claims first. Protocol: post `claim: <issue> (<branch>)` before `wt claim` and `merged: <sha> <branch>` after each push; `git pull --rebase` before every push; in shared notes add your own section or row, never rewrite the other's; relay Tess's decisions verbatim with `tess:`; a pinned-binary bump is `bump? <sha>`, answered `bump ok`, before either side rebuilds. Each runs the periodic checks for its own areas.

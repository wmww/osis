# Coordination
> Summary: How coordinators run the work: the job mix (Tess), the task loop (opus worker, fresh opus reviewer who gates once, fast-forward main; up to 4 agents, every branch on main), test budget and time limits, briefs, rewriting an area, release checks, standing job briefs, complaints, several coordinators.

Design principles every agent follows: notes/principles.md. Build and test mechanics: notes/build.md; the gate: notes/gate.md. Starting a session: read the handoff note (notes/, named handoff) when one exists and delete it once its items are taken; a coordinator ending a session with work open writes it. What is in flight is the local task branches (`git branch`) and their worktrees.

## Job mix (Tess)
About four agents at once, in four kinds of job:
- **Primary workstream** (the top item of notes/priorities.md, which says how to use and keep it) is the priority: always at least one agent on it, two when they won't collide.
- **Workflow**: about one running at all times, cycling through kinds and keeping what proves useful: watchdog, test optimizer, a tool that would speed agents up, sorting piled-up branches, hunting slowdowns nobody has noticed yet. If nothing big is left to gain, do other work, but never go long without one.
- **Cleanup**: about one running: simplify notes, rewrite or delete redundant tests, dedupe and refactor code. osis should ship with less code than it has; a cleanup may carry a bug fix or feature, always framed as making things simpler and more consistent.
- **Bug fixes**: few. Worth it when a bug threatens the design (pull that thread early), slows or masks tests, or goes away with a complication a cleanup removes. Otherwise wait for the primary workstream to finish.

How to run them (Tess):
- Complexity-bound first, CPU second, not token-bound; heavy token use is a symptom of complexity. Less code that still moves toward a working osis is better.
- osis is not in production: break main, delete tests you mean to rewrite slimmer, skip mature-codebase process. Process is quick, dirty and effective; no long incremental refactors or multi-branch rebases.
- A "critical security bug" is not urgent before release. A special-case fix can hide and ingrain a design flaw; a bug may be the first sign a design tweak is needed.
- While the primary workstream rebuilds on main (main broken, one gate at its end), cleanup and workflow jobs land on their crates' tests and clippy, no reviewer or gate; a branch changing a rule others build on still gets a fresh reviewer.
- A question for Tess never stalls a worktree: pick the simpler option, note whether it is easily reversed and what depends on it, record it as a `tess-call` issue, keep going.

**Working with Tess**
- Ask one question at a time, with the trade-off and why users care, in plain words.
- Requirements changes need her sign-off; spec, code and notes don't (CLAUDE.md).
- Don't record a recommendation as decided mid-discussion; check what she already decided before asking again.
- Liking a design's shape is not a go: on a design she is engaged in, propose, then wait for an explicit decision before briefing a build.
- Priorities: security, data loss and core correctness first; performance and optional features wait until the core is solid. If a requirement keeps generating issues, bring her the case for relaxing it rather than papering over it.

## The task loop
- `wt claim <branch> origin/main` for an opus worker; then a fresh opus reviewer claims the same branch by name (`wt claim <branch>`, after the worker released): correctness review of the diff, a targeted differential for the invariant the branch changed, small fixes committed, rebase, gate (notes/gate.md, Running it), then it lands: `python3 tools/policy.py --baseline && git merge-base --is-ancestor origin/main HEAD && git push origin HEAD:main`, and deletes the branch's pushed copy. The worker also pushes its branch as `<coordinator>-<branch>` so briefs can name its commits.
- Every agent gets its worktree from `wt claim`, never from a path a brief names (a named path may be someone else's claim by then), and runs `wt release` as its last step, after its last commit.
- **Slots (Tess).** Up to 4 agents at once, workers and reviewers counted together, and only the coordinator spawns: briefs say "start no agents of your own". Keep two worktrees warm (`wt trim 0`/`1` after a release makes the next claim cold).
- Re-review: a reviewer change bigger than a small fix, or a rule a worker-lander (one agent finishing a parked or conflicted branch) reworks or adds, gets a fresh reviewer before the gate. A branch whose second review changes the rule, not a line, goes back to the coordinator for a simpler rule.
- **One gate per branch (Tess)**: the reviewer's, as its last step, after `git fetch && git rebase origin/main` (the gate refuses a HEAD behind origin/main). Policy, the instant checks and clippy run first and fail it in seconds; a gate refused there ran no tests, so running it again is still the one gate; a gate that reached its tests and must run again means the workflow broke: say why in the report. If main moved after the gate, the lander rebases and pushes on `cargo clippy --all-targets -- -D warnings` plus `cargo test -p <crate>` for each crate both the branch and the commits it was rebased over changed; re-gate only on code conflicts. Never gate a checkout at main's tip (it runs everything, GUI included).
- **A worker landing directly** (no reviewer or gate) runs the properties its change reaches (the sync differential at full size, the custody property) on the HEAD it pushes. A rebase that brought in a commit changing a file the branch changed (`comm -12` of both sides' `git diff --name-only` under core/) runs them again: a 100-seed differential is 2 holds, about 5 min held; without that overlap the pre-rebase run stands. Skipped, the pair lands unswept (383f12b3a over 03b387858, both in `sync/certblobs.rs`; the end checks over the device-record fix).
- **Docs-only branches** (Markdown under spec/, notes/, issues/): the coordinator runs `tools/gate.sh` (its docs path takes seconds) and merges with no reviewer, except a spec change a build will follow (checked against spec/requirements.md) and a prose editor's rewrite (the reviewer walks the removed facts), which get a reading reviewer. A comment-only Rust change gets a reviewer, whose gate takes the comments path.
- **Known failures.** Exit 0 merges. Exit 3 (KNOWN only) merges with no rerun when each KNOWN failure's text reads as its issue describes; say so. A NEW failure (exit 1) is the branch's to fix, or, shown failing on main too (`tools/bin-at main OUT -p CRATE`), gets its issue and `tools/known_failures.txt` line on main first (notes/gate.md, The summary). Main stays green on the properties at small size: one failing on main is the next task.
- Hung agents: one quiet far past its task's usual length is asked (SendMessage) or stopped; agents have sat for hours on a permission prompt or on a `Monitor` that never woke.
- An agent that hits a model usage limit mid-task: commit its worktree as WIP and relaunch in the same worktree.
- One intricate incremental change (fast path, window, cache with a from-scratch fallback) per area in flight at a time.
- **One base branch (Tess).** Every branch is claimed from `origin/main` and lands on main; no integration branch, no task started on another unmerged branch. Large work lands as ordinary branches in sequence, one builder at a time where they share files. Shared name lists (tools/code_refs_allow.txt, core/base/testenv-known.txt) are one item per line under git's union merge; tools/known_failures.txt merges normally (notes/gate.md, Policy checks).
- **Pushed branches** go to GitHub as `<coordinator>-<branch>`; that coordinator deletes them once merged or dropped; one whose coordinator is gone may be deleted.
- **Rebasing a long branch**: rewrite prose into main's terms rather than resolving conflicts mechanically; `git -c rerere.enabled=false` (the shared repo has rerere on, and a resolution recorded for one branch replays into another's conflict); after a both-sides resolution of tests appended at one spot, check the earlier block still ends in `}`; `git show --stat` each commit before the fast-forward; squash only to the merge base (notes/build.md, Footguns).
- **Stopgaps (Tess)**: nothing complex or out of the way. The smallest rule that closes the hole; every code site it touches carries `// Interim (issues/<name>.md): <what replaces it>`, the spec limit and the issue name the replacement, and the replacing build's brief lists every marked site to remove.
- **A build brief fits one session**: a list of pieces in order, each ending at a green commit (its crates' tests and clippy pass), and "stop at the first green point once the session is long, push, report what is left". Briefs naming whole phases ran six sessions that each ended red at 300-530k tokens.
- Briefs and reports stay honest about what ran: a deferred or skipped check is reported as such, never as passed.

## Coordinator rules
- A tooling change (tools/, gate, env names) goes through a worktree and runs the tools' own tests (`tools/*_test.*`) and policy, even a one-liner.
- Performance is the coordinator's: "a little slower than optimal but much simpler, more correct or more verifiable is a good trade". Budgets: notes/test-scale.md (Performance budgets). A new incremental path needs a scaling check showing the simple one grows worse than the requirements allow.
- Growth: a change that adds a new kind of permanent data adds or updates a row in notes/growth.md; reviewers check.
- Hostile-only shapes inside data the writer may write: `Priority: low`; fix only when easy, else state the limit where the area's note or spec lives.
- App work (libs/kit/, app/) is planned with Tess in a separate UX session (notes/app.md) and counts toward the slots. With no app session active, the core coordinator fixes app breakage itself. What kit/app needs from core becomes an issue tagged `core-ask`.
- Names: each coordinator picks a name and pronouns once it knows the codebase (check the registry), records both here and says them in chat. Sub-agents are `<coordinator>-<branch>` in briefs, reports and complaints.
- Registry: **Lodestar**, she/her. **Tiller**, he/him. **Wren**, they/them. **Sorrel**, they/them. **Fathom**, they/them. **Kestrel**, they/them. **Petrel**, they/them. **Halyard**, they/them. **Bowline**, they/them (app). **Capstan**, they/them. **Sextant**, they/them (reference graph design). **Keel**, they/them.

## Test budget
Seed breadth belongs to the release checks, not to branches (Tess: cut testing time without letting issues slip): reading and targeted new tests find most bugs, rerunning ranges almost none (notes/test-design.md, What finds bugs).
- Worker: the per-worker checks (notes/testing.md, When tests run), its own new tests, the task's repro and a quick targeted check of what it changed. No gate.
- Reviewer: any differential it writes, then the gate, the branch's one full run (never `OSIS_FULL=1` per branch). Whole-crate runs before the gate only for crates its own fixes changed. Reviews find bugs through targeted differentials and reading, not by re-running default ranges: keep the reviewer brief on the invariant the branch touched.
- A branch that changes a test model (held-model, roles-model, crdt-model) gets every property using it through the gate's selection; one that changes an oracle's expectations runs that oracle once before merge.
- Never large sizes in a branch, including a confirming sweep after a seed fix (a 300-seed run holds the heavy lock about 20 min while every other agent queues). A seed fix runs its seed and a test of its mechanism. A branch that changes an invariant the gate's selection does not reach gets one targeted larger run, saying why in the brief; one that adds or rewrites a randomized harness runs it once at `OSIS_FULL=1` before merge.
- **The gate's limit is 5 minutes (Tess)**, everything it runs included (it takes far longer: issues/test-time.md) (default tests, the branch's selected properties and sim scenarios): reached by fixing perf problems (product, harness, test design), not by scaling sizes down: a size shrinks only where the extra size is shown to add no coverage; breadth goes to release checks.
- **Time limits (Tess).** Every timed run has two hard limits, CPU time and wall time, each set only a little above what it takes on this box now (the CPU limit tighter, as other work on the box barely moves it; the looser wall limit catches what CPU time cannot: waiting, idle cores, a demoted process), as a multiple of a per-box base unit so limits scale to other boxes: the gate (its one heavy-lock hold, notes/gate.md Steps, step 7, is where they hook in); the default tests; a warm rebuild in its longest common form (an osis-base edit, all targets: about 15 s, limit about 2x); a single test (over 10 s needs a reason); one heavy-lock hold, the largest of these. The gate's stage limits are shares of its own (they sum to at most it), so an over-limit gate names the stages over their share. Values and tooling: notes/time-limits.md, Limits; hits: each box's `~/.cache/osis/limits.log`; patterns and investigation reports: notes/time-limits.md. Every hit and every investigation report is logged with timestamp and box. An agent that hits a limit reports why. An investigation starts when the same limit is hit 5 or more times within 3 hours, when one run exceeds its limit by more than 2x, or when the explanation implies something persistent (tests added that take longer). An investigation may raise a limit only if it finds no good solution, recording what it tried and why the raise is justified; Tess reviews these. A trigger is a chance for the bigger job: when new tests trip the limit, consider whether one is slow, there are too many (drop, consolidate), all are slow (optimize), the whole suite including old tests is slow, tests are designed slowly (a complex scenario where a minimal test proves the same), or the change that needed the new tests made old ones irrelevant (drop them).

## Briefs
Standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, start no agents, commit, `wt release`, report.
- Start with `export PATH=/home/ai/.claude/plugins/cache/wmww-agent-skills/reasonable-rust-builds/0.6.0/bin:/home/ai/.claude/plugins/cache/wmww-agent-skills/claudewait/0.1.0/bin:$PATH`: subagent shells lack the plugins' `bin`. Check the versions with `which wt claudewait` in your own shell (a plugin update adds a version directory).
- Say `wt claim <branch> origin/main` prints the worktree; never predict which one, and `cd` there first. Say "ignore the working directory your environment names": a spawned agent's environment names the coordinator's shell cwd as its working directory, and agents that trusted it built in unclaimed trees. So the coordinator never ends a command inside a worktree: `( cd $W && ... )` or `git -C $W`, never a bare `cd` (it persists in the main session); the last command before an Agent call ends in `/home/ai/osis`.
- Name the agent's own scratch dir (`<scratchpad>/<branch>-<random>`), with the gate log's path inside it, and say `mkdir -p` it first (notes/build.md, Footguns).
- Name a commit only once it is on a pushed ref, with that ref (`<sha> on origin/<branch>`). A file only on an unmerged branch is named as `git show <commit>:<path>`. Name sections of big notes and issues, not whole files (the Read tool pages at about 25k tokens). Grep a rule's words, an item's name or an env var before citing it (a wrong env var name silently runs the default seeds).
- Say "first re-run the issue's repro on current main" (issue seeds go stale), and name the commit a measurement or lead came from. A cost or cause a review claims is a lead to measure, not the task. Before naming a mechanism for an item, read the item's own issue.
- A brief's facts are measured or marked as guesses: a failure count from both of a crate's binaries (`--lib` and `--test it`, `--no-fail-fast`), never a prediction ("far fewer should break": 700 did); an "existing mechanism" grepped for first; a property failure quoted as its replay line (the gate draws seeds at random offsets, so "passed at X" is no evidence of a regression: replay the seed at both ends with `tools/bin-at` before bisecting); the run that fails named, not a search that is clean on main. A failure taken from a worker's report is replayed on current origin/main first, by the coordinator before the brief: landings in between fix and break things (five rotation failures, a custody seed from a worker's stale base and two differential seeds main had already fixed each cost a worker 1-1.5 h). A differential failure is briefed as its shrunk script with its rate over worlds on today's main (`differential::worlds`, notes/sync-test-harness.md, Replaying a script), never as a seed number: any byte change moves which seeds fail. A random seed's first failing commit is a trigger, not a cause (a timing change moves a seed into an older bug: seeds 23 and 95, and a seed 88 "regressed with" the wrong commit): write "first fails at", quote the seed's own panic line, not a story of its class, and replay its shrunk script at the good end too. A rule or deletion a brief proposes is tried against the crate's default tests first (minutes): two such proposals broke 2 and 76 tests at once.
- Write `git fetch && wt claim <branch> origin/main`: `wt claim` bases on the local origin ref, and a stale one cost an agent an hour reproducing a bug main had fixed.
- While a differential is being driven to 0 (e.g. the sync differential at `OSIS_FULL=1`), every landing touching engine or sync runs it (split holds under `tools/heavy`) and must not raise the count: parallel landings that skipped it reintroduced failures three times. A rule added mid-session reaches running workers only by SendMessage. Cost: two holds of 50 seeds, 6-10 min of lock per landing (notes/time-limits.md, Patterns).
- While main is red by design, land with `python3 tools/policy.py --baseline`; say so in the brief.
- Don't brief work against a commit that hasn't landed ("if the foundation has landed"): start it after, or state plainly it is absent.
- A repro brief allows "or show the code already holds the rule" (the gap may be the model's).
- Name known-failing tests in the crates a brief runs, and use `--no-fail-fast` on multi-crate runs.
- The first `wt release` in a worktree marks for minutes: run it in the background.
- A brief's preamble is one set of rules: a contract that supersedes a rule replaces it there.
- A worker brief names no property the reviewer will run, unless that oracle is the task's repro; then the worker runs that one test at its default size.
- Put the reviewer's "check these cases" questions in the worker brief too, with the simplicity question ("is there a rule with no points/windows/caches that meets the budget?"). Say "do not loosen an existing test: report it".
- Security or convergence fix: the worker writes the invariant the fix relies on as a code comment, plus a randomized differential (or an extended oracle) that fails with the fix disabled; the reviewer attacks that argument. Every new test is checked to fail with its fix disabled. Also in the worker brief: prefer changing the behaviour an oracle objects to over widening the oracle; find every path that reaches the state (every caller of what mints it) and test each; for every input the rule reads, ask who can write it (a removed party forges at an epoch it held); a cache or visited set in a security walk gets a test where the same keyset is met two ways. A security brief offering options gets a hostile-party pass first.
- New module or protocol code, in the worker brief: (1) a state table: each map, set and row, who supplies its keys (a peer, the engine, this node), its bound with a test flooding past it, what removes it, and that a restart changes nothing a user sees; (2) per message received: what an unproven, removed or hostile peer controls, and what each reply tells whom; (3) per rule: break it in code and see a test fail (`tools/mutate.py`, one table row per probe, the table in the report); a test fake must not consume what an assert later counts; scripted peers speak through the real encode/decode; (4) every clock read is followed and every expiry sets a wake; (5) the actions the model lacks that the code meets (re-grant, restart, a hostile party) named, each with a test or the model extended; (6) readings of ambiguous spec go into the spec or the area's note in the worker's commit: reviewers never see the worker's report.
- A diagnosis that needed temporary prints keeps them as the harness's failure output or an env-gated dump (as `OSIS_ROTATION_DUMP`).
- TLA results: name the module (`run.sh <module>`) and by-hand instances by name, sized under the `heavy` hold limit (notes/test-properties.md, TLA+). A one-worker TLC run of seconds needs no lock.
- Repeat the command rules agents break most (notes/build.md, Footguns): no `timeout` around cargo; `run_in_background`, then one `claudewait` per call (two chained pass the 180 s subagent cap); `wt release` from inside the worktree; a probe variable named `OSIS_PROBE_*`; edit and build in separate calls; `-p <crate> --test it -- <filters>`; TaskStop, never `pkill -f`; `tools/heavy` only around an all-core run; the reviewer commits before starting oracles and runs them from a copied binary; `PROPTEST_CASES=N` for deep proptest runs; `--ignored --exact` traps; squash to the merge base, wip-commit before a fix-disabled probe, `git fetch && git rebase origin/main` without a pipe, its result read before gating; `mkdir -p` a scratch dir in an earlier call than the redirect into it (a missing dir ends a background run at once, reported exit 0); no `git stash` anywhere in a command, `list` included (the whole call is denied).
- A branch touching node sync, links or transport runs the networking check by hand (notes/testing.md, When tests run). A reviewer who needs main's behaviour builds main's test binary with `tools/bin-at` and compares CPU seconds, not wall time.

## Rewriting an area
Spec-first delete-and-rebuild worked far better than porting in place (the sync rewrite); Tess's direction is in notes/principles.md (Rewriting an area). How it ran:
- Spec, then models, then code: the models found about a dozen holes before any code existed.
- Foundation first: one agent writes the crate skeleton with every module declared and every shared type in one place; a fresh reviewer checks the shapes by walking two end-to-end flows on paper.
- With slots to spare, an integration agent runs beside the module agents: it drives the merged modules end to end, files what breaks between them and fixes the seams.
- One worker and one fresh reviewer per module, each module a branch on main; workers hand off the new-module checklist (Briefs). Nearly every module review found a real bug, by reading for what a hostile or removed party controls, mutating the worker's own tests (six passed vacuously), a whole product flow or a restart with state in flight, asserting what stays, not only what goes, and running `-p osis`.
- A random-history differential with shrinking finds the cross-module bugs; check the oracle before the code (an unknown-outcome write may have happened). Histories replay twice and must match: no hashed collections in that code.
- Decide fast but let implementers push back: prefer the rule whose failure is a wrong keep over a wrong drop, and state the limit.

## Release checks
Seed-breadth runs reach what per-branch sizes never do. They detect design smells, not a safety net: a bug only they find names a subtle property (notes/principles.md, Testing), fixed by a simpler rule plus a small default test.
- When (Tess): as part of the release process (not yet defined), and when Tess asks. Never on a coordinator's own initiative.
- Alone: only while no agent is building or testing, and no cargo-heavy agent is briefed until it ends (nice 19 does not shield the others).
- TLA is not a release check: it is run by hand when TLA is touched.
- Every offset (`--from`, `_START`, `OSIS_*_SEED`) drawn at random below 10^12 (`python3 -c 'import random; print(random.randrange(10**12))'`).
- After a run: update the last-run line below and the counts in notes/test-design.md (What finds bugs); an issue per new failure, saying whether the gate's selection at small size fails it too (then the selection missed it, usually a property without a size word) and naming the property behind it. Check each harness's printed seed range, not only `1 passed`; judge a slow item by its CPU-s, not wall.
- Last full run: main e3cdd005f, every item below at `OSIS_FULL=1` on random offsets: 5.3 h wall, about 119,500 CPU-s at nice 19 beside load 25-100. Six real bugs, three of which the gate's selection should have caught.

Commands (the full set; an area run takes its own items), under `nice -n 19`:
- `cargo run --bin sim-sweep -- --seeds 150 --from <F> --budget-secs 3600` (every scenario). A sweep cut by its budget says so only in its per-scenario seed counts: log the seeds that ran.
- Every property not named below: `OSIS_FULL=1 PROPTEST_CASES=256 cargo test -- --include-ignored --skip sweep --skip repro_ --skip _probe --skip memory:: --skip multi_gb_value_streams` (memory checks run alone, notes/test-scale.md).
- `OSIS_FULL=1 OSIS_ORDER_START=<S> cargo test -p osis-engine --test it -- --ignored order::held_set_decides_`.
- `OSIS_PERM_SEED=<P> cargo test -p osis-perm` and `OSIS_PERM_SEED=<P> cargo test -p osis-perm --test it -- --ignored differential:: queries:: incremental::`.
- `OSIS_CRDT_SEED=<C> cargo test -p osis-crdt -- --include-ignored --skip repro_ --skip hostile_moves --skip shrink_script`.
- Every seed-ranged harness has a `_large` twin (notes/test-harnesses.md Seed runners).

## Standing job briefs
Examples of workflow and cleanup jobs (Job mix). Act on each report: fix tooling or notes yourself, file issues, or brief a worker.

**Watchdog**, also after a release-check run. Brief: "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py <session transcript dir> --long 3 --since <the last watchdog's commit>` (the session's own dir, `~/.claude/projects/<project>/<session>`), `tools/heavy --report` and `python3 tools/limits.py summary`. Per agent: wall time against its task, model time against waiting on builds, tests and benches; anything hitting the 180 s subagent cap repeatedly, timing out or writing a wait loop; a build or test far over notes/build.md's costs (3x at low load is a bug: find why, don't blame load); checks off the per-branch list (notes/testing.md, When tests run); any run paying for a component nobody worked on; which reviews found bugs and what kind of test found them. Disk (notes/build-internals.md, Disk). Read notes/complaints/; fold new hit patterns into notes/time-limits.md, Patterns. Verify every claim about a file or tool on current main. Report what is fine, what cost time for a fixable reason (agent, command, how long, why), patterns worth fixing, and complaints not worth fixing; delete every file in notes/complaints/ you read (every coordinator's). Notes and complaints only, no code."

**Test optimizer**. Brief: "Make the tests faster and cleaner without losing significant coverage. Start from issues/test-time.md and the latest test profile (notes/test-harnesses.md, Default-test cost) and pick the area by that evidence, plus `tools/limits.py tests` (under the heavy lock for minutes) and complaints. You may delete tests that are not useful (show what else covers them), speed up specific slow tests or functions, change the patterns or design of a test system, or make core osis faster where tests pay for its slowness. Count work in debug tests (instructions with `tools/icount`, passes, reads); no timing runs. Report the before and after counts and what coverage moved."

**Cleanup**. Brief: "Simplify, refactor and delete code in <area, or pick one by evidence: `tools/loc.py`, profiles, complaints>. Find targets with `tools/deprecated_probe.py <crate>` (`--gui` when the GUI may use it): it marks every `pub` item `#[deprecated]`, runs one clippy, lists the items unused outside the crate's own `src/` and the test-only ones, and restores the tree; read them as candidates (a trait method or a re-exported free fn can be named another way: grep before deleting). Also `tools/dup_windows.py <dir>` and fns returning `Result` that never return `Err`. A helper must save more lines than it and its doc comment cost. Drop duplicated rules, dead paths, vestiges of replaced concepts (removed at the root: code, tests, notes, spec), needless state. Behaviour stays; no timing runs. Report what went and the line counts before and after."

**Prose editor**. Brief: "Rewrite and simplify the text of <area, or pick one: usually notes/, also spec/, issues/>. Reorganize, split and merge files so what a reader looks for is easy to find; make the text simpler, logically ordered, consistent and correct (run commands to verify claims); delete what is no longer or never was useful (references to old designs, logs of work git already holds, descriptions of the obvious). Before committing, walk your `git diff` and for every removed rule, number, reason or rejected alternative name where it now lives or why it goes; keep Tess's own wording (lines marked Tess) as she wrote it. Keep CLAUDE.md's rules on notes, spec, summaries and issue lines."

## Complaints
`notes/complaints/<branch>.md`: workflow mishaps, footguns and slow spots an agent met, committed with the branch (CLAUDE.md). The watchdog reads every file there, every coordinator's, keeps the patterns in notes and deletes them all.

## Several coordinators at once
One coordinator by default. When more run at once, each on its own machine, one is the lead (Capstan, they/them): the one Tess names, else the one the coordinators agree on. The lead assigns areas and settles disputes; the 4 slots are shared. They talk over the osis channel (notes/dogfood.md) and split by issue area (Tags). Protocol: post `claim: <issue> (<branch>)` before `wt claim` and `merged: <sha> <branch>` after each push; read the channel and `git pull --rebase` before every push; in shared notes add your own section or row, never rewrite the other's; relay Tess's decisions verbatim with `tess:`; a pinned-binary bump is `bump? <sha>`, answered `bump ok`, before either side rebuilds. Each runs the release checks for its own areas.

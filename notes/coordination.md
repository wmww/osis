# Coordination
> Summary: How a coordinator session runs osis work: one opus worker per task in a worktree, a fresh opus reviewer, gate in the worktree, fast-forward main; at most three agents; the periodic checks and their cadence; the watchdog that reviews how the session went; the complaints directory agents write to.

The build and test mechanics are in notes/build.md; this note is the process around them.

## A coordinator session
- A session is one coordinator's run, of whatever length; notes/mvp-progress.md gets one section per session listing what merged, owner decisions, what was left in flight, and the periodic-check offsets used. (The older sections are titled "Production round N"; a round is the same thing.)
- Per task: `tools/wt claim <branch>` for an opus worker (brief: the issue, the oracles for its area, the standard footer: CLAUDE.md, notes/build.md, `claudewait`, no wait loops, commit, `tools/wt release`, report); then a fresh opus reviewer on the same worktree (correctness review of the diff, targeted differentials for the invariant the branch changed, small fixes committed, `git rebase main` then `tools/gate.sh`); then the coordinator fast-forwards main (`git merge --ff-only`, push, `git branch -d`), records the item, and briefs the next task. At most three agents at once, workers and reviewers counted together; two worktrees stay warm, more are made and trimmed as needed.
- Reviews are where bugs are found: of 20 merges in one session, 8 reviews found 5 real bugs, all through targeted differentials or reading, none through re-running default test ranges. Keep the reviewer brief focused on the invariant the branch touched, and ask for a differential test of it.
- Per-branch tier-2 oracles finish in minutes (notes/testing.md); long runs are periodic, below.

## Periodic checks
What: the seed-breadth runs that catch what the default ranges never will (every bug caught by a generated input in the last session came from a seed or range nobody had run): `cargo run --bin sim-sweep -- --seeds 300 --from <F> --budget-secs 1800`, `OSIS_ORDER_START=<S> OSIS_ORDER_SEEDS=300 cargo test --workspace --test it order::arrival_order_alike_large -- --ignored`, `OSIS_PERM_SEED=<P> cargo test --workspace`, `core/test/tla/run.sh small`; offsets rotate and are logged in notes/mvp-progress.md so ranges never repeat.

When: in the background, in a spare worktree, roughly every six times as long as they take to run: at about an hour per run, every six hours of coordinator work; slower on a slow box, more often if they get faster. Not at the start of every session unless they have not run for a while. If they grow, first look for a way to make them faster without losing what they check (the order harness runs one seed per process; several processes over seed sub-ranges would cut its 15 minutes to 3), then run them less often. Before a release, run them at full length regardless.

## The watchdog
When the periodic checks finish, spawn one opus agent with this brief, and act on its report (fix tooling or notes yourself, file issues, or brief a worker): "Review how this coordinator session's agents have been working, not what they built. Run `tools/agent-times.py` (the session's tasks dir; `--since` the last watchdog run) and read the gate logs the coordinator kept. For each agent: was its wall time reasonable for its task, how much was model time against waiting on builds, tests and benches, did anything hit the 180 s subagent cap repeatedly, time out, or write a wait loop; did any build or test take far longer than notes/build.md's expected costs (3x at low load is a bug: find out why rather than blame load); did agents run checks that are not on the per-branch list (notes/testing.md); did reviews find bugs and what kind of test found them. Read every file in notes/complaints/ and the latest worker and reviewer reports the coordinator has in the progress note. Then report: what is fine, what cost time for a fixable reason with the evidence (which agent, which command, how long, why), patterns across complaints worth fixing, and complaints not worth fixing (delete those files; fold the worth-fixing ones into your report and delete them too, so the directory holds only what the coordinator has not yet seen). Do not change code; notes and the complaints directory only. Commit and release your worktree if you used one."

## Complaints
`notes/complaints/` is where agents leave low-priority workflow mishaps, mistakes, footguns and slow spots they met, one file per task named after the branch (`notes/complaints/<branch>.md`, a few lines each, appended to during the task), committed with the branch. High-priority problems (something blocked you, a tool gave a wrong answer, a check took far longer than its documented cost) go in the report to the coordinator as well. The watchdog reads the directory, keeps the patterns, and deletes what it has consumed; the coordinator never has to read it directly.

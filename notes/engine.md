# Engine
> Summary: How osis-engine (`core/engine`) is built: its layering, the facade sync reads it through, transactions and rollback, derived values (memos), the module map, and the public surface by area. Index of the engine-* notes, which hold the rules of each area. Not here: sync (notes/sync.md; the facade notes/sync-facade.md), the API over it (notes/api.md, notes/api-implementation.md), ephemeral data (notes/ephemeral.md).

## Layering
- osis-engine (layer 7) is the node's local state: identity, clock, writing and reads, receiving and applying commits, validity, retention, undo, events, labeling, role flows and rotation. Sync sits above it and reads it only through `osis_engine::sync` (notes/sync-facade.md); osis, the sim and the tests use osis-engine directly (notes/architecture.md).
- The engine calls nothing of sync's: no hook, callback or queue. What sync needs the engine keeps itself, in its own transactions (sync records, deliveries owed, passes: notes/sync-facade.md, Engine tables kept for sync), and sync follows the facade's memo values by `Effects`.

## Transactions and rollback
- Synchronous, no I/O of its own, time from a `Clock`, randomness injected. Every mutating call runs in one store transaction (`Engine::run(|tx: &mut Tx| ..)`, `Tx { txn, core, rng }`); events go out after it is durable, outside locks.
- Every in-memory index is journaled (`engine::journal`: `JMap`, `JSet`, `JSetMap`, `JNested`; `Indexes`, whose commit, mark and rollback the `indexes!` macro derives from its field list; `Groups`, the held set and `Sides` journal themselves). A failed transaction undoes its own changes newest first and evicts the states it wrote: O(changes), not a copy of every index. Perm's timelines follow the restored held set (`update_touched` around what the undo touched). A failed transaction that changed nothing keeps every derived cache (`Core::rollback_to` drops them only after a `touch` or a state write).
- **Atomic steps.** A local step (one pending commit's apply in `reexamine`, one part's judging in `examine`, one answer in `answer_removals` or `answer_rotations`, one cover in `settle_none`) applies fully or not at all; a caller catching its error goes on from exactly the state before it. `Tx::step` is the one mechanism; a whole failed transaction is the same rollback from the transaction's start mark: a store savepoint (`Transaction::savepoint`: an undo log of the dirty units and blobs, the memory overlay's journal; nothing spills while one is open, so a rollback is memory only) plus `Core::mark`/`rollback_to`.
  - What a mark covers, by class (`Core::rollback_classes` lists every `Core` field and fails to compile on an unlisted one): restored are the journals (by log length; `JMap` journals a key again after a mark; `ix`, `sides`, `schemas`; the timelines follow `ix.held`), the queued events, `commits_named`, `listed_before`, `killed`, `to_date`, `written`, `compaction`, the stale sets, `batched`, `memory_tx`, `dirty`. Every cache goes when anything changed since the mark (`dirty`, `written`, any index journal), `generation` stepping; a cache filled from restored state belongs in this class. Work lists and hints whose consumer re-checks each entry keep a failed step's entries, costing a look (`drop_due`, `none_due`, `valueless_dirty`, `changed`, `redeliver`, `missed`, the held set's `moved`/`records`, `timer_floor`, the HLC, a fresh session). The rest is set outside steps.
  - A mark is taken with every held change given to the timelines (each held-set change runs `update_timelines` before returning; debug-asserted): otherwise the rollback, re-evaluating the timelines around what it restores, would absorb an earlier change without marking what it moved.
  - A write this node makes on its own at a transaction's end is a step that never fails the transaction: an answer (`answer_removals`, `answer_rotations`) that fails is reported (`OwnWriteFailed`) and stays due, a purge-on-replace cover is reported and left; each first asks `write::may_write`, and one that may write only later (minting or delete keys not here) waits.
  - Tests: `apply::tests_steps` (a step failing after it ran equals one failing before it ran: indexes, perm view, decrypted store).
- `Core` (in memory, rebuilt by `apply::load` at open and after forgetting): the states cache with page indexes, `Core::ix` (the journaled indexes, each field documented in `engine/mod.rs`), perm's held set (`engine::held::Held`) and `Timelines`, pending reasons and kept waits, secrets, groups, commit records and parts decoded once per record write (`engine/decoded.rs`), memos and caches for sync (`bodies`, `sync_ids`, `tree_reach`, ...). The commit indexes (`by_aspect`, `by_thing`) find commits, never decide anything alone, since any signer's header can list any aspect: what a thing has reads the state, what a commit counts for reads its parts valid here (`Meta::valid_at`).

## Derived values
Rule: a value derived from mutable facts depends on exactly what it read (`osis_base::memo`, in osis-base so the store stamps its own rows; what still sits behind hand-keyed caches: issues/derived-state-recomputed.md).
- **Stamps.** Every container of mutable facts stamps its changes and reads (`memo::Stamps`), where they are written:
  - The store (`osis_store::Store`, its `Stamping`): a catalog row by its key (a local record, an aspect's unit, a counter), a scan by its prefix (`Stamps::read_prefix`: moved by any later write under it, so `Engine::aspects` and every scan of local records are stamped), a table's rows as the catalog row owning the table (an aspect's unit, an index's name); a stamp table per family (catalog kind, a local record's first key byte), since the debug comparison runs again when a table an answer read changed, and one table for the store changes at every transaction. A transaction logs the rows it writes and stamps each again when it is undone (a savepoint rolled back, an abort; a suspended transaction's log waits in the store for its resume), so a rollback moves exactly the rows it wrote. The engine's copies over the store record the rows they stand for: a decoded state at `Tx::load_lazy` (`Transaction::noted_aspect`), a decoded commit record at `Tx::get_commit` (`noted_local`; `Core::decoded` keeps each decode at its record's row stamp, `Transaction::local_stamp`, so a write, removal or undo of the record retires it with no drop by hand); a leftover, an aspect row or any local record read is stamped by the store itself.
  - The blobs the engine holds (`blobs::Cipher`, its one door to them, over `Engine::blob_stamps`): by blob, read by `held`, `read`, `len`; changed by a hold or release in a transaction (the store's release after commit changes nothing the engine sees) and again by its undo; `settle_blobs` moves them all.
  - In `Core`: the journaled collections (`get`/`contains` read one key, `Deref` the whole; an undo is a change), the held set (per key of each of its maps: `created`, the edge commits on a thing, the holders named on it, the things a holder is named on, a record's first admin's things, a commit by ID), `held::Timelines` by what each read can see (`held::Read`, moved from `osis_perm::Changed` and the things an update was given): a thing's component timeline whole (`get`: every update evaluating or continuing it), the history of the edges into a thing (`on`: its holders, roster, standings and applied writes; and a role read backward from it, `roles_on`/`role`, over each node reaching it), the edge writes held on it (`On::held`), the set of things with a timeline (also what a read of a thing without one reads), and the keyless actor grants (`keyless`: an index the update keeps per component, moved only when its value changes), the group index (`Groups`, per row: a group's definition and listing of a field, the groups listing a tid, a closure read whole, a closure holding one tid (`groups::Closure`, how `BodyCtx` reads it), `memo::Stamped` maps (`Core::key_actors`, `Core::accounts`), `memo::Tracked` values (`Core::account`), the time (`Core::time`, a `memo::Clock`: `get` reads it whole, `until(t)` only up to `t`, so an answer that holds until the next `until` or role commit in a component (`Core::horizon`) moves when the clock reaches it, and every answer when the clock goes back; set at each transaction and by node-sync before it asks).
  - Absent keys share a stamp per bucket of their hash (`ABSENT_BUCKETS`), moved by any removal in the bucket (a key present since before the stamps were, as every row at an open, reads at it too). Keys are stamped by hash: two colliding keys share a stamp (a spurious rerun, never a stale answer). A dropped container (a `Core` rebuilt) holds nothing that read it. A stamp per row written stays while the row does: the store's stamps grow with the rows written since the open.
- **`Memo<K, V>`.** `get(k, f)` runs `f` recording the stamps it read (a thread-local frame; a memo read inside passes its reads on) and keeps the answer while each stamp is the one seen. No key to pick beyond the argument, no invalidation call, nothing to do on rollback.
  - `get_in(ctx, ..)`: the same for a function that needs the engine whole and may fail (it runs a transaction); a failure is not kept. `get_checked_in` takes the debug comparison's function apart, for an `f` with effects (sync's rotation memo: `ensure_rotated` rotates when something is due; the comparison runs `Engine::rotated_already`, whose transaction always rolls back).
  - What `Engine::run` does around its function (settling, end-of-transaction follow-ups, persisting, debug checks) is read unrecorded (`memo::Unrecorded`, which opens no frame when no memo computes on the thread): a memo depends on what its function read, not on the transaction's upkeep.
  - `get_amended_in` brings a kept answer that no longer holds up to date from itself: `amend` runs recorded, and its answer is kept only if every read of the kept answer that moved is accounted (each read of that stamp, by the function or an earlier amend, was inside `memo::accounted`: an input the amend compares by value with what the kept answer saw) and read so again by this amend; any other move, or an amend giving `None`, runs the function anew. Exact, not by hash: two keys sharing a stamp leave it unaccounted unless both reads were accounted (`an_amend_is_kept_only_over_what_it_accounts_for`). An amend counts for the debug comparison as a hit after a change.
  - An answer no longer asked for is dropped when the memo has doubled since it last checked every entry (`SWEEP`). A hit costs a lock per container the answer read, not a lookup per key: an entry keeps its reads grouped by container with the container's change count at which they last held, and looks keys up only in a container that changed since (else an answer over an aspect's n bodies is O(n) per hit, O(n²) per pass asking each body).
- **`Effects<K, V>`** (`memo/effects.rs`): work in proportion to change, for an owner that acts on values (sync's verdicts, validity per part). `want(k)` follows a key, `unwant` stops; `settle(k, f)` runs `f` recorded like a memo's function, keeps the value and indexes each (container, key) it read to `k`, and gives `Some((acted, now))` when the value differs from the one last settled; `due()` gives the followed keys whose last value read a stamp written since, plus those wanted and not settled, in want order, each until settled. It finds them from each container's log of its writes (`Table::log`, kept from the oldest live mark of a reader on it, nothing when nobody follows the container), then checks each candidate's stamps: `due` costs the writes since its last call times their readers, never the keys followed (`due_costs_the_writes_not_the_keys_followed`). A removal is a candidate for every key read at its bucket's absent stamp, as with the stamps (a key read present is named by its own removal). The log holds every write since the slowest reader's last `due` or `added`: an owner calls them each pass, and dropping an `Effects` or `Feed` releases its marks. A world copy's tables carry no marks of readers left outside it (each reader cloned in the copy marks again). A followed key stays followed until unwanted, its input gone or not: the owner unwants on a settled value that says so. A write between a settle's read and its index (a container first read in that settle) leaves the key due at once. No debug comparison inside: the owner's values are effects, compared by whoever acts on them.
- **`Spread<K, V>`** (`memo/spread.rs`): early cutoff where it pays. A map cheapest derived whole but read an entry at a time, whose reads move far more often than its entries (a whole index walked), is derived through `Effects` (rerun when what it read moved) and kept per entry in a `Stamped` map: a reader of one entry moves only when that entry does, and an absent entry reads its hash bucket's stamp, so keys asked that the map lacks (a peer's sync IDs) keep nothing. On it: `Core::inboxes` (`inbox_actors` per sync ID). Where the derivation itself can go per key, follow each key with `Effects` instead and keep the rows (`labeling::published`, `sync::certified`): new keys come from a container's `Feed`, so nothing walks everything. Not an option on `Memo`: a memo copies its inner reads into its readers (below), which is exactly what a spread's readers must not hold.
  - A reader depends on the entries as last refreshed. A spread refreshes at each `get`/`get_in`, but a memo hit or an `Effects` owner's `due` does not ask it, so between a move of its reads and the next refresh a memo reading an entry hits on the old entry and a follower is not due. Sync's driver calls `Engine::follow` (all of them, in order) before each module's settle and settles again while it moves anything (notes/sync-facade.md). Not refreshed at each transaction's end instead: a refresh may be a whole walk (the sync set the read things come from), so n transactions between two sync steps would cost n walks instead of one. Not refreshed by the checker either: a memo hit or `due` holds no function to rerun (the closure is given at each `get`), the reason `Memo` has no cutoff. The debug comparison of a memo hit over a stale entry runs the function, which refreshes the spread, and fails: a refresh missed inside the engine shows there. Covered: `facade::a_chain_goes_under_a_sync_id_only_for_its_group_or_a_write_there_spec_perm_4` (a follower due after `follow` alone); the driver's calls are not reached by any test (every move in today's tests also brings a commit whose judgement refreshes the rows, and read acts on it).
- **Why a key went due**: while `costs` records (a test that `take`s), `Effects::due` counts each due key under `"<effects> <- <cause>"`: `unsettled`, or the container whose stamp moved (`Stamps::named`/`Stamps::of`, else the file and line that made the stamps; `(whole)` for a whole read). The first tool when a judgement re-runs too often.
- **`Feed<K>`** (`Stamps::feed`, `JMap::feed`): one reader's cursor over the keys a container added (`Stamps::wrote_added`) since the reader last asked, from the same log: nobody drains it, nothing writes it by hand; a key added and undone is given too (the reader finds it absent).
- **`Clock::next`**: the earliest `until` read and not passed (a reader gone since leaves a wake that moves nothing): when the driver next sets the clock.
- **What can be missed**: a function reading a mutable `Core` field outside these containers, or a copy of store rows that records no read of them. Debug builds compare a hit with a fresh run (`memo::Checks`) on two schedules: the 1st, 4th, 16th, ... hit at which a container the entry read changed since its last such hit (an amend is one), which finds a missed read whose container, or another read one, changes with it; and hits 16, 256, 4096, ... whatever changed, which finds a missed read that changes alone once the answer is asked that often (gating it on any engine change would not do: a missed read may be of a field no stamp counts). A hit inside a comparison (`memo::comparing`) counts for nothing, and no cache rechecks there (`Core::recheck_at`). A new memo's inputs get a stamped container first. A debug check reading beside a cache hit runs under `memo::unrecorded`, else its reads would cover the read the hit missed. Counted: `retention::tests::memos_follow_leftovers_through_writes_and_undo` (each stamp removed fails it).
- On memos: `Core::epochs`, `Core::account_view` (the signing chain; `refresh_epochs` re-judges this node's account by `Core::epochs_judged_from`, compared by value and read without building the chain, so an open decodes no header), `Core::account_epochs`; `Engine::head_keys`, `holders_named`, `inbox_actors`, `owned_sync_ids`, `held_links` (the link-seed things from `Indexes::aspect_things`), `Core::acting`; `Core::replaced_dates` per part and `part_bounds` per commit (`Engine::part_keeps`: the bounds but for the clock, applied after; `replaced_at`, `date_due`); `rotation::departures` and `reseal_candidates` per actor (the latter reads the time up to the actor's horizon); `Core::bodies` (`Engine::body` without plaintext, per commit: the label pass's `commit_bodies_under`) and `live_bodies` (`Engine::delta_live` per delta); `pieces_below` (`Engine::piece_below` per piece link).
  - `retention::bounds::held_writes` per aspect is amended: while the aspect holds no invalid part each body's writes are its own, so when its held commits only grew `amend_held_writes` notes the new bodies' writes; its accounted reads are the aspect's commits and invalid parts, so a drop, a late part, a validity flip or a rollback of records reads it anew; a join decodes its own body (`retention::tests::a_join_decodes_its_own_body_not_the_aspects`).
  - `flows::secrets_in` (`secrets.0` decoded) is patched by each join: the writer takes the kept answer before its write (`Memo::held`) and keeps the patched one at the stamps after it (`Memo::amend`), so a write costs its delta, not the roster. The patch reads the written keys back from the state, so the join first loads every page holding an entry of one (`apply::keys::secrets_paths`): a key's other live entries, concurrent puts, sit on pages the join's own dots do not touch.
- **The memo type's design, and why** (counts: issues/derived-state-recomputed.md, Memo design review):
  - No early cutoff inside `Memo` (`Spread` is the explicit form, above). A memo reading another copies the inner's reads, so an inner recomputed to an equal value still moves its readers. Salsa backdates by verifying an inner before its reader, which needs the inner's function at check time: here a memo's function is a closure given at each `get` over `Core`, `Tx` or `Engine` (borrowing them, so it cannot be kept), so a check cannot run it. Comparing at `get` (an inner rerun equal to its kept answer keeps the old stamps) is no cutoff: its readers hold the inner's copied reads, which moved either way, and the kept old stamps would never hold again. The sound form without the function: each memo stamps its own answers (moved only when a rerun differs), a reader records that stamp beside the copied reads, and holds when only copied reads moved, their inner's entry already rerun by another asker and its answer stamp unmoved; else it reruns. It fires only after another asker, needs a memo's entries reachable from its readers' entries, and `Effects` must still follow the copied reads (nobody reruns the inner for a follower). Not built: it saves the outers' own work, at most a few percent of osis `sources::` (cpuprof, inclusive, with their inners and debug comparisons: the epochs memo 1.7%, head keys 1.9%, sync IDs of a group 1.6%, of which the skippable reruns are 64%, 85% and 87%), and the inner reruns come from coarse stamps (below): narrow those first.
  - Push is `Effects` (above): a memo stays pulled; an owner that must act on changes (sync's modules, validity per part) follows keys there.
  - A memo keeps every answer still asked for and drops the rest at its sweeps; it has no byte bound, since its answers are small derived values proportional to what is held (an index's size). Big decodes of immutable bytes are not memos: `Core::decoded` keeps them at their record's row stamp with a byte bound.
  - Whole-container reads are exact where the container is one value (`Tracked`, `Clock::get`) and coarse elsewhere. Coarse today, by what moves memos most: a stored row read whole (an aspect's state row moves every replaced-at date and part bound on the aspect: issues/derived-state-recomputed.md step 4); a timeline read whole (`Timelines::get`: `Core::horizon`, `may_rotate`, demotions in effect, an unapplied write's verdicts) moves with any role change in the component; a range of a journaled map is read as its run where the map has runs (`JMap::by_run`, `JSetMap::by_run`: `keysets_noted`, `sealed_noted`, `on_thing`, `acting_for` per actor or thing), its key set alone where only keys are asked (`keys_held`: `acting`, `inbox_actors`), else whole.
  - Key access is global by definition (`osis_keys::key_access` orders all actor grants), but a keyless grant closes a cycle, which lies in one component: the timelines keep the union of the components' answers, judge anew at each update only the components where an actor grant or a record changed, and move `keyless` only when the set changes. A memo over every timeline instead reran at every role change and each consumer copied its reads (609 equal reruns of 609 in osis `sources::`).
  - Missed reads are found only by the sampled debug comparison. A structural guarantee would be a view type holding only the stamped containers (and immutable identity) that every memo function takes instead of `Core`/`Tx`; not built: every memo function and the helpers they call would move to it.
  - A stamped read costs a lock of its container's table; a hit costs one per container read (`Group`). Counted at about 4 M locks over 47 G instructions in a member-churn sim run and 19 M over 128 G in an osis multi-source test: under 1% at any plausible cost per uncontended lock, so kept.
- Counted: rotation `tests::epochs_are_derived_once_per_change_of_what_they_read`, `tests_account::account_view_is_built_once_per_rotation`, `memo::tests`.
- **Signature verdicts.** A signature check is a function of immutable bytes (key, signed digest, signature), so it is no memo (with nothing stamped its answer would never be swept): it runs once where the bytes enter, and its verdict is kept beside them. A commit's: `apply::signature` is the one door; its verdict (`osis_commit::Signed`, a hash of the three) is made only by a check or by the signer (`Built::signed`: the signer verifies its own signature once before anything leaves it, outside the counted costs, so a signing fault is never published: a faulty Ed25519 signature can leak the key), and read back (`Signed::from_kept`, tools/policy.py `kept_verdicts`) only from where this node kept one: the held commit's (`Meta::signed`, in its record's head, so an open checks nothing again) and a pending copy's (the store's pending row, `Pending::verdict`, read by `apply::kept_verdict`: re-examinations, one after every applied commit, and lost access's `authentic` check nothing again). Within one ingest it is handed on (`examine`'s and `memory_gate`'s `known`, in and out: from `with_pending`, the memory gate, the early check before the header lists resolve, the signer's for `apply_local`). It answers only for exactly the bytes and key it hashes, so a forged copy or another key resolved for the author is checked anew (`with_pending`: a copy whose signature bytes differ). Whether that key may sign is judged apart (validity), never by the verdict. Trust: a kept verdict is trusted as the store is, like the node's keys in it: rows are AEAD units under the key tree (notes/local-store.md), the store is this node's alone, and a restored backup holds only this node's own verdicts. Counted: `apply::tests::a_commit_signature_is_checked_once_per_node_spec_crypto_2` (the receiver one per commit, the writer none, none after a restart; a forged copy and another key refused) and `a_pending_commits_signature_is_checked_once_spec_crypto_2` (one while pending, through re-examinations, a restart and its apply; a forged copy replaces nothing). Each verification counts under its domain in `osis_base::costs` (`Domain::verify_cost`: a thread-local flag read unless a test records).

## Public surface (engine)
A map by area; rustdoc has the full list.
- Lifecycle: `Engine::create` (fresh identity: the node thing's `created.0` with `node.0`, then `keys.0`), `open` (load, re-examine pending), `reload`, `subscribe`/`subscribe_durable`, `app_record`/`set_app_record` (the `u/` records), `report(diagnostic)` (deduped like the engine's own).
- Writing: `Mutation` built up and passed to `Engine::commit(m) -> Option<CommitId>` (notes/engine-apply.md, Writer side).
- Receiving: `ingest`/`ingest_with_lists`/`ingest_memory` -> `Ingested::{Applied, Duplicate, Pending, Awaits, Parked, TooLarge}` (sync ingests through `open_entry`); `reexamine`, `tick` (expiry, purge floors, drift).
- Reads: `get`, `get_at` (a paged state loads the path's pages only), `get_range`, `read_large`/`read_large_max`, `next_chunk` (the API's `stream`), commit listings (`engine::listing`), `held_parts`.
- Retention: sync judges deletions and re-snapshots from the commit index, no queue (`snapshot`, `covered`, `drop_body`, `part_keeps` per commit by aspect index, `delta_live`, `replaced_at`, `body_not_dropped`: true for a missing part too).
- Undo: `revert` (spec/commits.md §7), `check_revertible(_as)`, `held_commits(scope)` for `osis` undo and redo, whose stacks live there.
- Schemas: one per app AK, never from the wire (`register_schema` replaces one of a lower or equal version, a local typed write only a lower one; `d/` + AK, read at open); they serve undo's typed views and large write-back after a restart. `osis::Osis::aspect_key` types only by this session's registrations, so the CLI's `schema rm` untypes.
- Labeling (notes/sync-facade.md; the module keeps its old name): `closure`, `label_bodies` (`label_bodies_meta` without plaintexts, a memo per commit in `Core::bodies`), `certificates`, `head_keys`, `tree_refs`, `body_links`, `relink`, ...
- Flows return `Done { commits }`; what a flow owes others is derived from the role commits it wrote (`deliveries`, notes/sync-facade.md), and sync logs every body from `sync_bodies`. Addenda run by `Engine::run` at every durable transaction's end.
- Rotation and lost access (notes/engine-roles.md, notes/engine-lost-access.md): `ensure_rotated(actor) -> (Done, roles still blocked)`, `pass_end`, `drop_lost_due`, `forget_lost(LostScope)`, `lost_leaving`, `kept_copies`, ...
- Events: `Applied` (with its changed `(tid, ak)` set), `Joined`, `Changed { cause }`, `Roster`, `Ephemeral`, `History` (entries that read otherwise, and fired ephemeral signals' entries), `SyncStatus`, `Diagnostic` (`DiagnosticKind`: one enum for the engine's kinds and those sync and the API report through `Engine::report`).

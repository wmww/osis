# Engine
> Summary: How osis-engine (`core/engine`) is built: its principle, layering, transactions and rollback (atomic steps, the transaction's end), derived values (memos, `Effects`, `Cutoff`, stamps), signature verdicts, the module map, the public surface by area, and the index of the engine-* notes that hold each area's rules. Not here: sync (notes/sync.md; the facade notes/sync-facade.md), the API over it (notes/api.md, notes/api-implementation.md), ephemeral data (notes/ephemeral.md).

## Principle
The engine is the node's local state, and every read and judgement in it is a function of what it holds (commits, local records, the clock), never of arrival order or of who asked first. So every mutating call is one atomic transaction that undoes cleanly, and every derived value depends on exactly what it read: nothing is invalidated, queued or kept up to date by hand.

## Layering
- osis-engine (layer 7) is the node's local state: identity, clock, writing and reads, receiving and applying commits, validity, retention, undo, events, sync_ids, role flows and rotation. Sync sits above it and reads it only through `osis_engine::sync` (notes/sync-facade.md); osis, the sim and the tests use osis-engine directly (notes/architecture.md).
- The engine calls nothing of sync's: no hook, callback or queue. What sync needs the engine keeps itself, in its own transactions (passes, falls: notes/sync-facade.md, Engine tables kept for sync), and sync follows the facade's values by `Effects`.

## Transactions and rollback
- Synchronous, no I/O of its own, time from a `Clock`, randomness injected. Every mutating call runs in one store transaction (`Engine::run(|tx: &mut Tx| ..)`, `Tx { txn, core, rng }`); events go out after it is durable, outside locks.
- `Core` (in memory, rebuilt by `apply::load` at open and after forgetting): the states cache with page indexes, `Core::ix` (the journaled indexes, each field documented in `engine/mod.rs`), perm's held set (`engine::held::Held`) and `Timelines`, pending reasons and kept waits, secrets, the node closure, commit records and parts decoded once per record write (`engine/decoded.rs`), memos and caches for sync (`bodies`, `sync_ids`, `tree_reach`, ...). The commit indexes (`by_aspect`, `by_thing`) find commits and never decide anything alone, since any signer's header can list any aspect: what a thing has reads the state, what a commit counts for reads its parts valid here (`Meta::valid_at`).
- Every in-memory index is journaled (`engine::journal`: `JMap`, `JSet`, `JSetMap`, `JNested`; `Indexes`, whose commit, mark and rollback the `indexes!` macro derives from its field list; the held set, the node closure (`sync::units::Closure`) and `Sides` journal themselves). A failed transaction undoes its own changes newest first and evicts the states it wrote: O(changes), not a copy of every index. Perm's timelines follow the restored held set (`update_touched` around what the undo touched). A failed transaction that changed nothing keeps every derived cache (`Core::rollback_to` drops them only after a `touch` or a state write).
- **Atomic steps.** A local step (one pending commit's apply in `reexamine`, one part's judging in `examine`, one removal's addenda in `addenda::write_owed`, one answer in `answer_rotations`, one cover in `settle_none`) applies fully or not at all; a caller catching its error goes on from exactly the state before it. `Tx::step` is the one mechanism; a whole failed transaction is the same rollback from the transaction's start mark: a store savepoint (`Transaction::savepoint`: an undo log of the dirty units and blobs, the memory overlay's journal; nothing spills while one is open, so a rollback is memory only) plus `Core::mark`/`rollback_to`. Tests: `apply::tests_steps` (a step failing after it ran equals one failing before it ran: indexes, perm view, decrypted store).
  - What a mark covers, by class (`Core::rollback_classes` lists every `Core` field and fails to compile on an unlisted one): restored are the journals (by log length; `JMap` journals a key again after a mark; `ix`, `sides`, `schemas`; the timelines follow `ix.held`), the queued events, `commits_named`, `listed_before`, `killed`, `to_date`, `written`, `accounts` and `left` (`accounts_undo`, logged by `Core::account_changing` at each write a step makes: a seed a failed transaction kept, a leave or a lost-access drop of `left`), the stale sets, `batched`, `fallen`, `epochs_judged_from`, `memory_tx`, `dirty`. Every cache goes when anything changed since the mark (`dirty`, `written`, any index journal), `generation` stepping; a cache filled from restored state belongs in this class. Work lists and hints whose consumer re-checks each entry keep a failed step's entries, costing a look (`drop_due`, `none_due`, `valueless_dirty`, `changed`, `redeliver`, `missed`, `signing_due`, `compaction`'s estimates, the held set's `moved`/`records`, `timer_floor`, the HLC, a fresh session); a kept entry that puts something due now (`next_timer`) belongs in the restored class. The rest is set outside transactions.
  - Two debug checks make a misfiled field fail where it is written: what `rollback_classes` returns (the class set outside transactions) is compared around every `Engine::run`, and a rolled-back transaction marks the index check due (`check_index`: an open and a rebuild of the store, which also checks each held account's seeds against custody), run at the end of history or, outcome known, before a reload replaces memory (`check_before_reload`; `check_every_tx` checks at each rollback to find the one). Not after every rollback: a whole check per transaction made sync's tests pay one per `role_duty_due` (its debug cross-check `rotated_already` always rolls back), about half of osis-sync `it`. A test poking memory must poke the store with it.
  - A mark is taken with every held change given to the timelines (each held-set change runs `update_timelines` before returning; debug-asserted): otherwise the rollback, re-evaluating the timelines around what it restores, would absorb an earlier change without marking what it moved.
- **The transaction's end** (`Engine::run`, after the caller's function, read unrecorded: `memo::Unrecorded`; steps 1–2 `end_flows`, 3–4 `end_drops`, 5 `end_settle`), in order:
  1. own secrets due (`rotation::own_secrets_due`: a thing minted with an account as admin is independent by its creating transaction's end);
  2. durable only, a loop while a member entered the node closure and stays one (`apply::entering`): closure settle (`sync::units::settle`); `apply::wake_entered` (what waits for a thing entering joins, read from `Closure::member_feed`, so no entry passes unseen) with settle again until it wakes nothing; carrier settle (`apply::carriers::settle`); then the flows: removal notices owed, `addenda::write_owed`, `signing::leave_if_removed`, `answer_rotations`, `dial::drop_departed`; settle again. The flows' writes may bring things in (an addendum makes the content it vouches for valid, a strong to a thing included), hence the loop; `entering` skips what a failed step's rollback took out, so a write failing and staying due brings no other round (`rotation::tests_signing::an_answer_undone_*`), and a flow with nothing due does nothing;
  3. invalid bodies drop (`retention::drop_invalid`, after this node's addenda vouched: notes/engine-retention.md Invalid bodies); settings changed (`leaving::date_due`, `retention::settings_changed`); a re-judge if anything is stale, with its drops and the removal notices it turns valid; setting waits; `replace::wake_covers`; `settle_none` (purge-on-replace covers, notes/engine-retention-covers.md);
  4. destructions and what nothing held needs any more (`destroy::apply_destructions`, `retention::needed::settle`), until nothing more goes;
  5. value-less lists, signal edits, freed links (`freed::settle_due`), forgotten names, handed covers, listing moves, `leaving::date_due`, a final closure settle (`check_written`), carrier settle, blob waits (`apply::reach::settle`), placements and states stored, `Core::commit_changes`; debug checks (`check_rebuilt`; nothing stale left); sides and the index persisted.
- **Own writes at the end never fail the transaction.** An addendum (`addenda::write_owed`) or an answer (`answer_rotations`) that fails is reported (`OwnWriteFailed`) and stays due; a purge-on-replace cover is reported and left. Each first asks `write::may_write`; one that may write only later (minting or delete keys not here) waits.

## Derived values
Rule: a value derived from mutable facts depends on exactly what it read (`osis_base::memo`, in osis-base so the store stamps its own rows; what still sits behind hand-keyed caches: issues/derived-state-recomputed.md). The parts: stamps on every container of mutable facts; `Memo` (lazy, pulled) for values asked; `Effects` (pushed) for an owner that acts on changes; `Cutoff` rows where a value fans in; `Feed` for new keys; `Quiet` for a follower's fixed point.

### Stamps
Every container of mutable facts stamps its changes and reads (`memo::Stamps`), where they are written:
- The store (`osis_store::Store`, its `Stamping`): a catalog row by its key (a local record, an aspect's unit, a counter), a blob's presence by its ID, a scan by its prefix (`Stamps::read_prefix`: moved by any later write under it, so `Engine::aspects` and every scan of local records are stamped), a table's rows as the catalog row owning the table (an aspect's unit, an index's name); a stamp table per family (catalog kind, a local record's first key byte), since the debug comparison runs again when a table an answer read changed, and one table for the store changes at every transaction. A transaction logs the rows it writes and stamps each again when it is undone (a savepoint rolled back, an abort; a suspended transaction's log waits in the store for its resume), so a rollback moves exactly the rows it wrote. The engine's copies over the store record the rows they stand for: a decoded state at `Tx::load_lazy` (`Transaction::noted_aspect`), a decoded commit record at `Tx::get_commit` (`noted_local`; `Core::decoded` keeps each decode at its record's row stamp, `Transaction::local_stamp`, so a write, removal or undo of the record retires it with no drop by hand); a leftover, an aspect row or any local record read is stamped by the store itself.
- The blobs the engine holds (`blobs::Cipher`, its one door to them, over `Engine::blob_stamps`): by blob, read by `held`, `read`, `len`; changed by a hold or release in a transaction (the store's release after commit changes nothing the engine sees) and again by its undo; `settle_blobs` moves them all.
- In `Core`: the journaled collections (`get`/`contains` read one key, `Deref` the whole; an undo is a change); the commits index by facet (`engine/commits.rs`): `get`/`contains_key` read the commit's key, which moves only as it comes or goes (its view, header, arrival, origin are fixed), and the `Meta` handed out records each mutable read as used (`hold(ai)` and everything built on it, `valid_at`: that part's key; `valid`, `hold_all`, the parts by state, a clone: every part's; `signed`, `repair`: their own), so a judgement of one part's body moves with that part alone; a write stamps only the facets whose value changed. A part's bytes in the commit record are read at that part's hold, not the record's row (`Tx::commit_for_parts`: the bytes are fixed by the commit ID and the record carries exactly the parts held as their bodies; read mid-write, where a hold and the record disagree, the reader reads the row too, so the write moves it in either order: `a_part_read_while_its_record_disagrees_moves_with_the_record`); the held set (per key of each of its maps: `created`, the edge commits on a thing, the holders named on it, the things a holder is named on, the things minted with each admin, a commit by ID); `held::Timelines` by what each read can see (`held::Read`, moved from `osis_perm::Changed` and the things an update was given): a thing's component timeline whole (`get`: every update evaluating or continuing it), the history of the edges into a thing (`on`: its holders, roster, standings and applied writes; and a role read backward from it, `roles_on`/`role`, over each node reaching it), the edge writes held on it (`On::held`), the set of things with a timeline (also what a read of a thing without one reads), and the keyless actor grants (`keyless`: kept per component, moved only when its value changes); `memo::Stamped` maps (`Core::key_actors`, `Core::accounts`); `memo::Tracked` values (`Core::account`); the time (`Core::time`, a `memo::Clock`, below).
- Module state a judgement reads is stamped like the engine's: sync's modules keep in-memory state (opens' members, streams' heads and presence, inbox progress) that other modules' `Effects` read, so each such container stamps its reads and writes (`Opens::member` per (connection, S), its `members` whole; `Opens::member_at` per (record, S), moved by no take or release), and a flag moving alone (a member's `departed`) re-judges what read it (`opens::a_departure_alone_moves_what_read_the_member_spec_sync_opens_6`). A field read inside a settle must be immutable for the key's life (a connection's `named`) or behind stamps.
- **Keys and removals.** A key written or removed keeps a stamp of its own, so a removal moves what read that key alone (`an_absent_key_moves_only_with_its_own_changes`). Keys never written since the stamps were (absent, or present with no stamp: every row at an open) share a stamp per bucket of their hash (`ABSENT_BUCKETS`). Removal stamps are bounded by the keys stamped otherwise (at least the bucket count): past that all are pruned (`Table::prune`), each key falling back to its bucket's stamp moved to now, so nothing that read it holds over a stale value and the stamps stay proportional to what the container holds. The bucket's move reaches a memo that read another key of it at the old stamp; an `Effects` key moves only where a key it read was written, removed or pruned since (`Effects::due`, `a_prune_moves_the_readers_of_what_it_pruned_alone`): else every prune re-judged every follower that read an absent row of the table (sync's judgements per round grew with the bodies held). A removed key never falls back to a bucket stamp a reader saw while it held a value (else an answer read before the key's first write holds again: `a_key_read_unstamped_then_written_and_removed_moves_its_first_reader`; `rotation::tests::a_held_grant_again_after_a_self_removal_serves_the_state_held_spec_perm_3`). Rejected: a removal moving its bucket (about a 64th of a table's readers of absent rows judged again per removal: n/64 judgements per delivery at n bodies held).
- `Stamped::insert` of a value equal to the one there and `Stamped::remove` of an absent key stamp nothing (`Stamped::replace` stamps always, for a value that cannot be compared: one holding secrets); `Stamped::update` edits in place. Keys are stamped by hash: two colliding keys share a stamp (a spurious rerun, never a stale answer). A dropped container (a `Core` rebuilt) holds nothing that read it. A stamp per row written stays while the row does: the store's stamps grow with the rows written since the open.

### The clock
- `Core::time` is a `memo::Clock`: `get` reads it whole, `until(t)` only up to `t`, so an answer that holds until the next `until` or role commit in a component (`Core::bound_to_horizon`) moves when the clock reaches it, and every answer when the clock goes back. Set at each transaction and by node-sync before it asks. `Clock::next`: the earliest `until` read and not passed (a reader gone since leaves a wake that moves nothing): when the driver next sets the clock.
- **The time inside a judgement** is the memo clock's, never the wall clock: `Core::now` while a memo or `Effects` settle computes (`memo::computing`) is `Clock::now`, the time as a bound over the computing frame reads it (`Clock::at(|now| (answer, deadline))`, or a `Clock::bound` guard: `bound_to_horizon` for roles at now), else a read of the time whole. So a judgement that bounds nothing reruns at every clock move (correct, and visible in `Effects` causes as the clock whole), never stays past an expiry or `until` it judged by. A memo computing inside a bound opens its own frame, bounded by nothing. Elsewhere `Core::now` is the wall clock (what a transaction stamps); `Engine::run`/`read` set the memo clock from it. Tests: `memo::effects::tests::a_time_read_unbounded_moves_with_the_clock`.
- **Roles at now** go through `Core::role_now` (and `may_read` through it): read on `Core::time` by `Clock::at` up to the first `until` the answer followed (`Timeline::roles_on_now`), so a memo or `Effects` key judging by a role now (chain placement, access) moves when an `until` passes, with a wake then. Every role-at-now read uses it (`actor_role`, `role_on` included), never `role_of(.., now_ts)`; `role_of` is for a fixed ts (a commit's).

### `Memo<K, V>`
- `get(k, f)` runs `f` recording the stamps it read (a thread-local frame; a memo read inside passes its reads on) and keeps the answer while each stamp is the one seen. No key to pick beyond the argument, no invalidation call, nothing to do on rollback. `get_in(ctx, ..)`: the same for a function that needs the engine whole and may fail (it runs a transaction); a failure is not kept.
- What `Engine::run` does around its function (settling, the transaction's end, persisting, debug checks) is read unrecorded (`memo::Unrecorded`, which opens no frame when no memo computes on the thread): a memo depends on what its function read, not on the transaction's upkeep.
- `get_amended_in` brings a kept answer that no longer holds up to date from itself: `amend` runs recorded, and its answer is kept only if every read of the kept answer that moved is accounted (each read of that stamp, by the function or an earlier amend, was inside `memo::accounted`: an input the amend compares by value with what the kept answer saw) and read so again by this amend; any other move, or an amend giving `None`, runs the function anew. Exact, not by hash: two keys sharing a stamp leave it unaccounted unless both reads were accounted (`an_amend_is_kept_only_over_what_it_accounts_for`). An amend counts for the debug comparison as a hit after a change.
- An answer no longer asked for is dropped when the memo has doubled since it last checked every entry (`SWEEP`). A memo has no byte bound: its answers are small derived values proportional to what is held. Big decodes of immutable bytes are not memos: `Core::decoded` keeps them at their record's row stamp with a byte bound.
- A hit costs a lock per container the answer read, not a lookup per key: an entry keeps its reads grouped by container with the container's change count at which they last held, and looks keys up only in a container that changed since (else an answer over an aspect's n bodies is O(n) per hit, O(n²) per pass asking each body). Counted at under 1% of instructions in a member-churn sim run and an osis multi-source test, so kept.
- No early cutoff inside `Memo`: a memo reading another copies the inner's reads, so an inner recomputed to an equal value still moves its readers, and every reader of an inner over n inputs holds n reads. A memo keeps no function (a closure given at each `get` over `Core`, `Tx` or `Engine`, borrowing them), so nothing can recompute an entry when it is checked. Where the copy costs, put a `Cutoff` row at the fan-in (Per-key rows).
- Patched memos: `retention::bounds::held_writes` per aspect is amended: while the aspect holds no invalid part each body's writes are its own, so when its held commits only grew `amend_held_writes` notes the new bodies' writes; its accounted reads are the aspect's commits and invalid parts, so a drop, a late part, a validity flip or a rollback of records reads it anew; a join decodes its own body (`retention::tests::a_join_decodes_its_own_body_not_the_aspects`). `flows::secrets_in` (`secrets.0` decoded) is patched by each join: the writer takes the kept answer before its write (`Memo::held`) and keeps the patched one at the stamps after it (`Memo::amend`), so a write costs its delta, not the roster. The patch reads the written keys back from the state, so the join first loads every page holding an entry of one (`apply::keys::secrets_paths`): a key's other live entries, concurrent puts, sit on pages the join's own dots do not touch.
- On memos: `Core::epochs`, `Core::account_view` (the signing chain; `refresh_epochs` re-judges this node's account by `Core::epochs_judged_from`, compared by value and read without building the chain, so an open decodes no header), `Core::account_epochs`; `Engine::head_keys`, `holders_named`, `owned_sync_ids`, `held_links` (the link-seed things from `Indexes::aspect_things`), `Core::acting`; `Core::part_bounds` per commit (`Engine::part_keeps`: the bounds but for the clock, applied after; each part's date read from its history row, `date_due`); `rotation::departures` and `reseal_candidates` per thing (the latter reads the time up to the thing's horizon); `live_bodies` (`Engine::delta_live` per delta); `covers` (`retention::snapshot::covered` per (cover, body, aspect): a judgement asks it per snapshot of its aspects, twice, at every rerun); `sync_body` and `sync_bodies` (`Engine::sync_body_now` per (sync ID, commit), `sync_bodies` per commit: several facade calls of one judgement ask them); `state_digests` (`Engine::state_digest` per aspect: a suspect list's entry costs a lookup unless the aspect's state or the thing's creation record moved; counted by `shred::a_state_digest_is_computed_once_per_state_spec_perm_4`); `pieces_below` (`Engine::piece_below` per piece link). Counted: rotation `tests::epochs_are_derived_once_per_change_of_what_they_read`, `memo::tests`.

### `Effects<K, V>`
- Work in proportion to change, for an owner that acts on values (sync's verdicts, validity per part; `memo/effects.rs`). `want(k)` follows a key, `unwant` stops; `settle(k, f)` runs `f` recorded like a memo's function, keeps the value and indexes each (container, key) it read to `k`, and gives `Some((acted, now))` when the value differs from the one last settled; `due` gives the followed keys whose last value read a stamp written since, plus those wanted and not settled, in want order, each until settled.
- `due` finds them from each container's log of its writes (`Table::log`, kept from the oldest live mark of a reader on it, nothing when nobody follows the container), then checks each candidate's stamps: it costs the writes since its last call times their readers, never the keys followed (`due_costs_the_writes_not_the_keys_followed`). A write or removal is a candidate for the keys that read that key; a prune (`Logged::Bucket`) also for every key read at its bucket's stamp, which is due only if a key it read was named in the log since its mark (else it reads the moved bucket stamp as its own, its value standing), or it was given before and not settled since (what moved it may be in an earlier log). The log holds every write since the slowest reader's last `due` or `added`: an owner calls them each pass, and dropping an `Effects` or `Feed` releases its marks. A world copy's tables carry no marks of readers left outside it (each reader cloned in the copy marks again).
- A followed key stays followed until unwanted, its input gone or not: the owner unwants on a settled value that says so. A write between a settle's read and its index (a container first read in that settle) leaves the key due at once.
- **Why a key went due**: while `costs` records (a test that `take`s), `Effects::due` counts each due key under `"<effects> <- <cause>"`: `unsettled`, or the container whose stamp moved (`Stamps::named`/`Stamps::of`, else the file and line that made the stamps; `(whole)` for a whole read). Containers are named where they are read: each journaled index by its field (`index: by_aspect`), the timelines by kind of read (`timelines: whole`, `into`, `held`, `ever`, `things`, `keyless`, a table each), the store's families by catalog kind and key byte (`store: catalog kind 1` is aspect state rows, `store: record rows 0x58` peer record index rows). The first tool when a judgement re-runs too often.
- A memo stays pulled; an owner that must act on changes follows keys here. Push is `Effects` only.

### Per-key rows
Early cutoff where it pays: where a derivation can go per key, follow each key with `Effects` and keep its answer as a `Stamped` row, so a reader moves only when its row does. New keys come from a container's `Feed`, so nothing walks everything. Not an option on `Memo`: a memo copies its inner reads into its readers, which is exactly what a row's readers must not hold.
- **`Cutoff<K, V>`** (`memo/cutoff.rs`) is the general form: each key followed from its first `get_in` is derived through `Effects` and kept as a row, brought up to date at each `get_in` (every due key) and by `refresh_in`, which `Engine::follow` calls. `unfollow` drops a key and its row (a reader moves; a later `get_in` derives it anew). Sync's own rows (`sync_ids::published`, `sync::certified`, `sync::own`: each (sync ID, candidate own commit) followed, candidates from the commits feed and from things entering the closure, a row per sync ID until `forget_read`) are the same shape.
- **Where it goes**: a fan-in, i.e. an aggregate over n inputs read by n readers, or a value many followers read whose inputs move to equal answers. The copy is the cost more than the rerun: a reader of an aggregate memo copies its O(n) reads, so n readers of it record and index O(n²) reads per change; a row is one read. Adding one: a field, a refresh in `follow`, a test that a follower moves after `follow` alone.
- **A reader depends on the rows as last refreshed.** Their owner refreshes them when asked (`Cutoff::get_in`), but a memo hit or an `Effects` owner's `due` does not ask it, so between a move of its reads and the next refresh a memo reading an entry hits on the old entry and a follower is not due. So a memo reading per-entry values brings them up to date before its lookup (`Engine::follow_bodies` before the bodies memos, `follow_read_things`, `dated_replaced_at`), else a hit holds over a stale entry and the debug comparison, whose fresh run refreshes, fails. Sync's driver calls `Engine::follow` (all of them, in order) once per settle round, before the modules, and settles again while it moves anything (notes/sync-driver.md). Not refreshed at each transaction's end instead: a refresh may be a whole walk (the sync set the read things come from), so n transactions between two sync steps would cost n walks instead of one. Not refreshed by the checker either: a memo hit or `due` holds no function to rerun. Without the driver's call nothing a sync test waits for happens (e.g. `holding::a_grant_beside_a_siblings_keying_reaches_the_grantee_spec_permissions_3` fails).
- On `Cutoff`:
  - `Core::read_things` (`Engine::read_things_of` per sync ID: every body judged under S reads it, through its body, `may_log` and credentials, while what it is derived from, the things naming S by `sync.0`, link or ticket, their sync IDs and holdings, moves at each ticket, link or `sync.0` of theirs) and `Core::step_write_keys` (`Engine::step_write_key` per (S, step), the write key a reader stamps under there: what `Ground::stands` reads of every entry, instead of the credentials whole, which move with every link, key and deposit seed of S's things). The memos reading `read_things` (`sync_body`, `sync_bodies`, `read_credentials`, `dial_peers`, `roster_holders`) refresh it first (`follow_read_things`). Counted: `read::a_ticket_for_a_thing_read_judges_none_of_its_bodies_at_n_and_10n` (either row read whole fails it).
  - `Core::wrap_blocks` (`wrap_blocked` per (thing, walk): read for every body a sync judgement asks may log, while what it reads, the thing's component whole through `Core::bound_to_horizon`, `may_rotate` and departures, moves at every role change).
  - `Core::held_writes_rows` (`retention::bounds::held_writes` per aspect, derived through the amended `held_writes` memo): each part's replaced-at date on the aspect reads the row, not every held body; `dated_replaced_at` refreshes it before its memo lookup.
  - `Core::read_facts` (`Engine::read_facts` per (sync ID, commit)) and `Core::held_fates` (`Engine::held_fate` per commit: `forgettable` and `covered_drops`): sync read's judgement of a body and its `local` read only these rows, so a write re-judges the bodies whose facts it changed, not every body on its aspects (the facts themselves are derived again per body whose reads moved: O(bodies on the aspect) cheap derivations per write while a part's date reads the aspect's state row and own covers read the author's newest own replace). Read unfollows a key when its judgement goes idle or the commit leaves.
  - Counted: `memo::cutoff::tests`; osis (judgements per write flat at n and 10n; quadratic without the facts rows); a missing refresh in `follow` fails `rotation::tests_stranded::whether_a_body_wraps_moves_at_a_grants_until_spec_crypto_4` (wrap blocks); the held writes rows' refresh in `follow` fails `retention::tests::a_held_writes_reader_is_due_after_follow_alone` (no date is asked where no setting keeps history).
- **`Feed<K>`** (`Stamps::feed`, `JMap::feed`): one reader's cursor over the keys a container added (`Stamps::wrote_added`) since the reader last asked, from the same log: nobody drains it, nothing writes it by hand; a key added and undone is given too (the reader finds it absent).

### `Quiet`
- A follower's fixed point (`memo/mod.rs`). `memo::writes` counts every change of any container's stamps in the process (one relaxed atomic in `Table::log`; a dropped table no reader holds counts nothing, so a follower's `mem::take` placeholder costs no follow). A follow that wrote nothing and succeeded marks its follower quiet at that count; while the count stands and the follower's `Effects` hold nothing pending (`Effects::idle`: a key wanted since, or one a failed settle left due), its next follow would find nothing and returns at once. So the queries between two writes (sync's modules ask `sync_held`, `sync_bodies`, `may_log`... many times per delivery, each refreshing the rows) cost one follow, plus one that confirms the fixed point. On it: `Cutoff::refresh_in`, the sync set's rows, `certified`, `listed`, `published`, `own`. Counted (in a child process with one test thread: the count is process-wide): `memo::cutoff::tests::a_quiet_cutoff_derives_what_came_since`.
- A follower quiet only on its own run is exact: one follower's writes are counted, so a follower reading another's rows follows again; one whose follow runs another's whatever is due (`listed` runs `certified`'s, which runs the rows') returns at once only while that one would too (`certificates_quiet`, `rows_quiet`), so a key left pending there is never skipped.
- Relaxed suffices: a write that happens-before a check (its table's lock, a channel) is seen by it, by coherence of the one atomic; a write with no such order is one that came after the check. Rejected: per-thread or per-engine counts (an engine moves between threads and its stamps are written from others, the sync store's; a per-thread count misses a write made on the thread it last ran on). So whether a follow runs depends on the process, but a follow is counted (`sync set: follows`, `certified: follows`) only where this thread's own writes owe it (`Quiet::holds_here`, the same mark over a per-thread count): a count test's follows are a function of its history whatever other tests write beside it (`memo::tests::another_threads_write_runs_a_follow_but_owes_none`).

### What can be missed, and checks
- A function reading a mutable `Core` field outside these containers, or a copy of store rows that records no read of them. A new memo's inputs get a stamped container first.
- Debug builds compare a hit with a fresh run (`memo::Checks`) on two schedules: the 1st, 4th, 16th, ... hit at which a container the entry read changed since its last such hit (an amend is one), which finds a missed read whose container, or another read one, changes with it; and hits 16, 256, 4096, ... whatever changed, which finds a missed read that changes alone once the answer is asked that often (gating it on any engine change would not do: a missed read may be of a field no stamp counts). A hit inside a comparison (`memo::comparing`) counts for nothing, and no cache rechecks there (`Core::recheck_at`). A debug check reading beside a cache hit runs under `memo::unrecorded`, else its reads would cover the read the hit missed. Counted: `retention::tests::memos_follow_leftovers_through_writes_and_undo` (each stamp removed fails it).
- `Effects` likewise, on a thread that turned it on (`memo::check_effects`): `due` adds, after the due keys, keys whose reads held, on `Memo`'s power schedules (a key whose container moved at another key, and every key now and then); their settle (costs paused) must give the kept value, else it panics naming the key (`a_read_without_its_stamp_fails_the_comparison`). An owner acts only on a changed value, so a compared key costs nothing more; `Cutoff` compares its rows.
- Not built: a view type holding only the stamped containers (and immutable identity) that every memo function takes instead of `Core`/`Tx`, which would make a missed read structural; every memo function and the helpers they call would move to it.

### Coarse reads and rejected designs
- Whole-container reads are exact where the container is one value (`Tracked`, `Clock::get`) and coarse elsewhere. Coarse today, by what moves memos most: a stored row read whole (an aspect's state row moves every replaced-at date and part bound on the aspect: issues/derived-state-recomputed.md step 4); a timeline read whole (`Timelines::get`: `Core::bound_to_horizon`, `may_rotate`, demotions in effect, an unapplied write's verdicts) moves with any role change in the component; a range of a journaled map is read as its run where the map has runs (`JMap::by_run`, `JSetMap::by_run`: `keysets_noted`, `sealed_noted`, `on_thing`, `acting_for` per actor or thing), its key set alone where only keys are asked (`keys_held`: `acting`), else whole.
- Key access is global by definition (`osis_keys::key_access` orders all actor grants), but a keyless grant closes a cycle, which lies in one component: the timelines keep the union of the components' answers, judge anew at each update only the components where an actor grant or a record changed, and move `keyless` only when the set changes. A memo over every timeline instead reran at every role change and each consumer copied its reads.
- Rejected, general early cutoff for every memo (issues/derived-state-recomputed.md, Memo design review):
  - eager (every memo a `Cutoff`): most memos' keys are many and one-off (`covers` per (snapshot, body, aspect), a new key per body at each snapshot; `bodies` per commit), which a memo drops at its sweeps and an eager refresh would rerun and keep; and inside a transaction each row reader must refresh before a hit is trusted, which a memo nested anywhere cannot know to do;
  - demand-driven red/green (salsa: an entry keeps its direct reads plus an edge to each inner entry with the inner answer's change stamp, the memo keeps its function as `fn(&mut C, &K) -> Result<V>`, a read verifies inners bottom-up): every memo's function and call sites would move to a fixed context, every entry would carry a change stamp, and `Effects` would have to verify each candidate's inner edges at `due` (an edge has no log). Measured, the cost was the copy of reads, which a fan-in row removes; what red/green would still save (recording and indexing reads, at most about 15% of the osis and osis-sync test binaries) is not worth that while a fan-in row is the cheaper fix where a count shows one.

## Signature verdicts
A signature check is a function of immutable bytes (key, signed digest, signature), so it is no memo (with nothing stamped its answer would never be swept): it runs once where the bytes enter, and its verdict is kept beside them.
- A commit's: `apply::signature` is the one door; its verdict (`osis_commit::Signed`, a hash of the three) is made only by a check or by the signer (`Built::signed`: the signer verifies its own signature once before anything leaves it, outside the counted costs, so a signing fault is never published: a faulty Ed25519 signature can leak the key), and read back (`Signed::from_kept`, tools/policy.py `kept_verdicts`) only from where this node kept one: the held commit's (`Meta::signed`, in its record's head, so an open checks nothing again) and a pending copy's (the store's pending row, `Pending::verdict`, read by `apply::kept_verdict`: re-examinations, one after every applied commit, and lost access's `authentic` check nothing again). Within one ingest it is handed on (`examine`'s and `memory_gate`'s `known`, in and out: from `with_pending`, the memory gate, the early check before the header lists resolve, the signer's for `apply_local`).
- It answers only for exactly the bytes and key it hashes, so a forged copy or another key resolved for the author is checked anew (`with_pending`: a copy whose signature bytes differ). Whether that key may sign is judged apart (validity), never by the verdict.
- Trust: a kept verdict is trusted as the store is, like the node's keys in it: rows are AEAD units under the key tree (notes/local-store.md), the store is this node's alone, and a restored backup holds only this node's own verdicts.
- Counted: `apply::tests::a_commit_signature_is_checked_once_per_node_spec_crypto_2` (the receiver one per commit, the writer none, none after a restart; a forged copy and another key refused) and `a_pending_commits_signature_is_checked_once_spec_crypto_2` (one while pending, through re-examinations, a restart and its apply; a forged copy replaces nothing). Each verification counts under its domain in `osis_base::costs` (`Domain::verify_cost`: a thread-local flag read unless a test records).

## Public surface (engine)
A map by area; rustdoc has the full list.
- Lifecycle: `Engine::create` (fresh identity: the node thing's `created.0` with `node.0`, then `keys.0`), `open` (load, re-examine pending), `reload`, `subscribe`, `app_record`/`set_app_record` (the `u/` records), `report(diagnostic)` (deduped like the engine's own).
- Writing: `Mutation` built up and passed to `Engine::commit(m) -> Option<CommitId>` (notes/engine-apply.md, Writer side). `Engine::commit` is the raw commit: the app's path is `Engine::write` (confinement, ephemeral writes).
- Receiving: `ingest`/`ingest_with_lists`/`ingest_memory` -> `Ingested::{Applied, Duplicate, Pending, Awaits, Parked, TooLarge}` (sync ingests through `open_entry`); `reexamine`, `tick` (expiry, purge floors, drift).
- Reads: `get`, `get_at` (a paged state loads the path's pages only), `get_range`, `read_large`/`read_large_max`, `next_chunk` (the API's `stream`), commit listings (`engine::listing`), `held_parts`.
- Retention: sync judges deletions and re-snapshots from the commit index, no queue (`snapshot`, `covered`, `drop_body`, `part_keeps` per commit by aspect index, `delta_live`, `replaced_at`, `body_not_dropped`: true for a missing part too).
- Undo: `revert` (spec/commits.md §7), `check_revertible(_as)`, `held_commits(scope)` for `osis` undo and redo, whose stacks live there.
- Schemas: one per app AK, never from the wire (`register_schema` replaces one of a lower or equal version, a local typed write only a lower one; `d/` + AK, read at open); they serve undo's typed views and large write-back after a restart. `osis::Osis::aspect_key` types only by this session's registrations, so the CLI's `schema rm` untypes.
- Sync IDs (`sync_ids/`, notes/sync-facade.md): `closure`, `commit_bodies_under` (a commit's bodies at a sync unit without plaintexts, each part inside read by its own hold; `body_plaintext` projects one), `certificates`, `head_keys`, `tree_refs`, `body_links`, `relink`, ...
- Flows return `Done { commits }`; what a flow owes others (tickets and removal notices, `flows/inbox.rs`) it fires in its own transaction, and sync logs every body from `sync_bodies`. Addenda are written at every durable transaction's end (The transaction's end).
- Rotation and lost access (notes/engine-roles.md, notes/engine-lost-access.md): `ensure_rotated(actor) -> (Done, roles still blocked)`, `role_duty_due(actor)`, `pass_end`, `lost_due`/`lost_passed`/`lost_timed`/`drop_lost` (sync) or `role_duties` (alone), `forget_lost(LostScope)`, `lost_leaving`, `kept_copies`, ...
- Events: `Applied` (with its changed `(tid, ak)` set), `Joined`, `Changed { cause }`, `Roster`, `Ephemeral`, `History` (entries that read otherwise, and fired ephemeral signals' entries), `SyncStatus`, `Diagnostic` (`DiagnosticKind`: one enum for the engine's kinds and those sync and the API report through `Engine::report`).

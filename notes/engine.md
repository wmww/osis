# Engine
> Summary: How osis-engine (`core/engine`) is built: its principle, layering, transactions and rollback (atomic steps, the transaction's end), derived values (memos, `Effects`, `Cutoff`, stamps), signature verdicts, the module map, the public surface, and the index of the engine-* notes that hold each area's rules. Not here: sync (notes/sync.md; the facade notes/sync-facade.md), the API over it (notes/api.md, notes/api-implementation.md), ephemeral data (notes/ephemeral.md).

## Principle
The engine is the node's local state, and every read and judgement in it is a function of what it holds (commits, local records, the clock), never of arrival order or of who asked first. So every mutating call is one atomic transaction that undoes cleanly, and every derived value depends on exactly what it read: nothing is invalidated, queued or kept up to date by hand.

## Layering
- osis-engine (layer 7) is the node's local state: identity, clock, writing and reads, receiving and applying commits, validity, retention, undo, events, sync_ids, role flows and rotation. Sync reads it only through `osis_engine::sync` (notes/sync-facade.md); osis, the sim and the tests use osis-engine directly (notes/architecture.md).
- The engine calls nothing of sync's: no hook, callback or queue. What sync needs the engine keeps in its own transactions (notes/sync-facade.md, Engine tables kept for sync), and sync follows the facade's values by `Effects`.

## Transactions and rollback
- Synchronous, no I/O of its own, time from a `Clock`, randomness injected. Every mutating call is one store transaction (`Engine::run(|tx: &mut Tx| ..)`); events go out after it is durable, outside locks.
- `Core` is in memory, rebuilt by `apply::load` at open and after forgetting (its fields are documented in `engine/mod.rs`). The commit indexes (`by_aspect`, `by_thing`) find commits and never decide anything alone, since any signer's header can list any aspect: what a thing has reads the state, what a commit counts for reads its parts valid here (`Meta::valid_at`).
- Every in-memory index is journaled (`engine::journal`; `Indexes` gets commit, mark and rollback from the `indexes!` macro; the held set, `sync::units::Closure` and `Sides` journal themselves). A failed transaction undoes its own changes newest first and evicts the states it wrote: O(changes), not a copy of every index. A failed transaction that changed nothing keeps every derived cache (`Core::rollback_to` drops them only after a `touch` or a state write).
- **Atomic steps.** A local step (the sites are `Step`'s variants) applies fully or not at all; a caller catching its error goes on from exactly the state before it. `Tx::step` is the one mechanism; a whole failed transaction is the same rollback from its start mark: a store savepoint (`Transaction::savepoint`: nothing spills while one is open, so a rollback is memory only) plus `Core::mark`/`rollback_to`. Tests: `apply::tests_steps` (a step failing after it ran equals one failing before it ran).
  - What a mark covers is classed per `Core` field in `Core::rollback_classes` (fails to compile on an unlisted field): restored (the journals, events, and the sets a step writes); dropped when anything changed since the mark (every cache, `generation` stepping; a cache filled from restored state belongs here); kept (work lists and hints whose consumer re-checks each entry, costing a look; a kept entry that puts something due now, `next_timer`, belongs in the restored class); and set outside transactions.
  - Two debug checks make a misfiled field fail where it is written: the outside-transactions class is compared around every `Engine::run`, and a rolled-back transaction marks the index check due (`check_index`: an open and a rebuild of the store), run at the end of history or before a reload replaces memory (`check_before_reload`; `check_every_tx` checks at each rollback to find the one). Not after every rollback: sync's debug cross-check `rotated_already` always rolls back, so a whole check per `role_duty_due` would cost about half of osis-sync `it`. A test poking memory must poke the store with it.
  - A mark is taken with every held change given to the timelines (each held-set change runs `update_timelines` before returning; `Core::mark` debug-asserts it): else the rollback, re-evaluating the timelines around what it restores, would absorb an earlier change without marking what it moved.
- **The transaction's end** (`Engine::run`, after the caller's function, read unrecorded: `memo::Unrecorded`), in order; each step is commented where it runs:
  2. durable only (`end_flows`), a loop while a member entered the node closure (`apply::entering`): closure settle, `apply::wake_entered` until it wakes nothing (read from `Closure::member_feed`, so no entry passes unseen), carrier settle, then the flows (`addenda::write_owed`), settle again. The flows' writes may bring things in (an addendum makes the content it vouches for valid), hence the loop; `entering` skips what a failed step's rollback took out, so a write failing and staying due brings no other round;
  3. (`end_drops`) invalid bodies drop (after this node's addenda vouched: notes/engine-retention.md Invalid bodies), settings changed, a re-judge if anything is stale, setting waits, `replace::wake_covers`, `settle_none` (notes/engine-retention-covers.md);
  4. destructions and what nothing held needs any more (`destroy::apply_destructions`, `retention::needed::settle`), until nothing more goes; then the split paths whose openers moved in any step above (`apply::paths::refresh`: a pending commit's boxes give reading secrets with no apply) and a re-judge until nothing is stale;
  5. (`end_settle`) what follows every change above: gone lists, signal edits, freed links, forgotten names, handed covers, listing moves, a final closure settle (`check_written`), carriers, blob waits, history dates, states stored, `Core::commit_changes`; then debug checks (`check_rebuilt`; nothing stale left), sides and the index persisted.
- **Own writes at the end never fail the transaction.** An addendum, an answer, a dial drop or a purge-on-replace cover that fails is reported (`OwnWriteFailed`) and stays due (a cover is left). Each first asks `write::may_write`; one that may write only later waits.

## Derived values
Rule: a value derived from mutable facts depends on exactly what it read (`osis_base::memo`, in osis-base so the store stamps its own rows; what still sits behind hand-keyed caches: issues/derived-state-recomputed.md). The parts: stamps on every container of mutable facts; `Memo` (lazy, pulled) for values asked; `Effects` (pushed) for an owner that acts on changes; `Cutoff` rows where a value fans in; `Feed` for new keys; `Quiet` for a follower's fixed point. The memo module docs and item docs state each part's contract; this section holds what they rest on.

### Stamps
Every container of mutable facts stamps its changes and reads (`memo::Stamps`), where they are written:
- The store (`osis_store::Store`, its `Stamping`): a catalog row by its key (a local record, an aspect's unit, a counter), a blob's presence by its ID, a scan by its prefix (`Stamps::read_prefix`: moved by any later write under it, so `Engine::aspects` and every scan of local records are stamped), a table's rows as the catalog row owning the table (an aspect's unit, an index's name); a stamp table per family (catalog kind, a local record's first key byte), since the debug comparison runs again when a table an answer read changed, and one table for the store changes at every transaction. A transaction logs the rows it writes and stamps each again when it is undone (a savepoint rolled back, an abort; a suspended transaction's log waits in the store for its resume), so a rollback moves exactly the rows it wrote. The engine's copies over the store record the rows they stand for: a decoded state at `Tx::load_lazy` (`Transaction::noted_aspect`), a decoded commit record at `Tx::get_commit` (`noted_local`; `Core::decoded` keeps each decode at its record's row stamp, `Transaction::local_stamp`, so a write, removal or undo of the record retires it with no drop by hand); a leftover, an aspect row or any local record read is stamped by the store itself.
- The blobs the engine holds (`blobs::Cipher`, its one door to them, over `Engine::blob_stamps`): by blob, read by `held`, `read`, `len`; changed by a hold or release in a transaction (the store's release after commit changes nothing the engine sees) and again by its undo; `settle_blobs` moves them all.
- In `Core`: the journaled collections (`get`/`contains` read one key, `Deref` the whole; an undo is a change); the commits index by facet (`engine/commits.rs`): `get`/`contains_key` read the commit's key, which moves only as it comes or goes (its view, header, arrival, origin are fixed), and the `Meta` handed out records each mutable read as used (`hold(ai)` and everything built on it, `valid_at`: that part's key; `valid`, `hold_all`, the parts by state, a clone: every part's; `signed`, `repair`: their own), so a judgement of one part's body moves with that part alone; a write stamps only the facets whose value changed. A part's bytes in the commit record are read at that part's hold, not the record's row (`Tx::commit_for_parts`: the bytes are fixed by the commit ID and the record carries exactly the parts held as their bodies; read mid-write, where a hold and the record disagree, the reader reads the row too, so the write moves it in either order: `a_part_read_while_its_record_disagrees_moves_with_the_record`); the held set (per key of each of its maps: `created`, the edge commits on a thing, the holders named on it, the things a holder is named on, the things minted with each admin, a commit by ID); `held::Timelines` by what each read can see (`held::Read`, moved from `osis_perm::Changed` and the things an update was given): a thing's component timeline whole (`get`: every update evaluating or continuing it), the history of the edges into a thing (`on`: its holders, roster, standings and applied writes; and a role read backward from it, `roles_on`/`role`, over each node reaching it), the edge writes held on it (`On::held`), the set of things with a timeline (also what a read of a thing without one reads), and the keyless actor grants (`keyless`: kept per component, moved only when its value changes); `memo::Stamped` maps (`Core::key_actors`); the time (`Core::time`, a `memo::Clock`, below).
- Module state a judgement reads is stamped like the engine's: sync's modules keep in-memory state (opens' members, streams' heads and presence, inbox progress) that other modules' `Effects` read, so each such container stamps its reads and writes (`Opens::member` per (connection, S), its `members` whole; `Opens::member_at` per (record, S), moved by no take or release), and a flag moving alone (a member's `departed`) re-judges what read it (`opens::a_departure_alone_moves_what_read_the_member_spec_sync_opens_6`). A field read inside a settle must be immutable for the key's life (a connection's `named`) or behind stamps.
- **Keys and removals.** A key written or removed keeps a stamp of its own, so a removal moves what read that key alone (`an_absent_key_moves_only_with_its_own_changes`). Keys never written since the stamps were (absent, or present with no stamp: every row at an open) share a stamp per bucket of their hash (`ABSENT_BUCKETS`). Removal stamps are bounded by the keys stamped otherwise (at least the bucket count): past that all are pruned (`Table::prune`), each key falling back to its bucket's stamp moved to now, so nothing that read it holds over a stale value and the stamps stay proportional to what the container holds. The bucket's move reaches a memo that read another key of it at the old stamp; an `Effects` key moves only where a key it read was written, removed or pruned since (`Effects::due`, `a_prune_moves_the_readers_of_what_it_pruned_alone`): else every prune would re-judge every follower that read an absent row of the table (sync's judgements per round growing with the bodies held). A removed key never falls back to a bucket stamp a reader saw while it held a value (else an answer read before the key's first write holds again: `a_key_read_unstamped_then_written_and_removed_moves_its_first_reader`; `rotation::tests::a_held_grant_again_after_a_self_removal_serves_the_state_held_spec_perm_3`). Rejected: a removal moving its bucket (about a 64th of a table's readers of absent rows judged again per removal: n/64 judgements per delivery at n bodies held).
- **A rolled-back transaction moves no frame open across it by its own writes** (`memo::Undoable`, around every `Engine::run`): the journaled collections, the commits index, the held set and the engine's own store's rows are undoable (`Stamps::undoable`, `UndoableStamps`, `Store::undoable`: a rollback undoes every write they took in it). The sync store is not: the engine's memory holds, releases and forgets commit to its memory part at once and an abort leaves them, so its rows move as usual. A transaction failing once it began committing (the ciphertext store committed first) ends the stretch kept. A frame open across it (held judging a deposit whose ingest is refused and rolled back) keeps its read of a key the transaction wrote, read before the first write or first read after it (what the transaction made of the frame's earlier reads); the undo's stamps move every other reader. So a trial costs a judgement nothing until what it read moves (`a_settle_undoing_its_own_writes_moves_only_with_what_it_read`). A container a rollback leaves as written (followers' outputs, work lists, the timelines rebuilt) is not undoable: reads of it move as usual. The read-after-write half rests on the transaction's writes following from what the frame recorded (its function runs recorded; the end work runs unrecorded but after the function's reads, and its failure is an error, never a verdict). Debug builds check each undoable claim in every stretch ended undone, frame or not: every key of an undoable container written in it must have been written again by that container's own undo since (`memo::undoing`, around each journal's `rollback_to` and the store's `Stamping::undo_to`), else `Undoable::end` panics naming the container. So an undo stamps again every key its write stamped (a `JMap` entry notes whether a change since came or went, for `Keys`; `Held::count` stamps a pair at every naming taken), and a container a rollback leaves as written (a cache, a follower's output, the timelines, the sync store) fails where it is marked; this is also what keeps undoable containers to `Core`'s restored class (`rollback_classes`): no other field is undone by `rollback_to`. The check is on stamps, not values: an undo that stamps a key but restores a wrong value is the container's own bug (`check_index` compares the restored indexes with the store). Cost: one map entry per key written in a stretch (`memo::undoable_writes_noted`, `scale::the_undo_check_costs_what_was_written`).
- `Stamped::insert` of a value equal to the one there and `Stamped::remove` of an absent key stamp nothing (`Stamped::replace` stamps always, for a value that cannot be compared: one holding secrets); `Stamped::update` edits in place. Keys are stamped by hash: two colliding keys share a stamp (a spurious rerun, never a stale answer). A dropped container (a `Core` rebuilt) holds nothing that read it. A stamp per row written stays while the row does: the store's stamps grow with the rows written since the open.

### The clock
- `Core::time` is a `memo::Clock` (its doc: `get` whole, `until(t)` only up to `t`, a move back moves every reader). An answer that holds until the next `until` or role commit in a component (`Core::bound_to_horizon`) moves when the clock reaches it. Set at each transaction and by node-sync before it asks; `Clock::next` (the earliest `until` read and not passed) is when the driver next sets it.
- **The time inside a judgement** is the memo clock's, never the wall clock: `Core::now` while a memo or `Effects` settle computes (`memo::computing`) is `Clock::now`, the time as a bound over the computing frame reads it (`Clock::at`, or a `Clock::bound` guard), else a read of the time whole. So a judgement that bounds nothing reruns at every clock move, never stays past an expiry or `until` it judged by. Elsewhere `Core::now` is the wall clock; `Engine::run`/`read` set the memo clock from it. Test: `memo::effects::tests::a_time_read_unbounded_moves_with_the_clock`.
- **Roles at now** go through `Core::role_now` (`may_read`, `actor_role`, `role_on` included): read on `Core::time` up to the first `until` the answer followed (`Timeline::roles_on_now`), so a judgement by a role now moves when an `until` passes. Never `role_of(.., now_ts)`; `role_of` is for a fixed ts (a commit's).

### `Memo<K, V>`
- `get(k, f)` keeps `f`'s answer while each stamp it read is the one seen: no invalidation call, nothing to do on rollback. `get_in` is the same for a function that needs the engine whole and may fail; a failure is not kept. `Engine::run`'s own upkeep around the function is read unrecorded (`memo::Unrecorded`): a memo depends on what its function read, not on the transaction's upkeep.
- No byte bound: answers are small derived values proportional to what is held, swept at `SWEEP`. Big decodes of immutable bytes are not memos: `Core::decoded` keeps them at their record's row stamp with a byte bound.
- A hit costs a lock per container the answer read, not a lookup per key (`moves`): else an answer over an aspect's n bodies is O(n) per hit, O(n²) per pass asking each body. Measured at under 1% of instructions in a member-churn sim run and an osis multi-source test.
- No early cutoff inside `Memo`: a memo reading another copies the inner's reads, so an inner recomputed to an equal value still moves its readers, and every reader of an inner over n inputs holds n reads. A memo keeps no function (a closure given at each `get`, borrowing `Core`, `Tx` or `Engine`), so nothing can recompute an entry when it is checked. Where the copy costs, put a `Cutoff` row at the fan-in (Per-key rows).
- Patched values: a `Cutoff` row may be amended in place (`Cutoff::refresh_amended_in`, its doc states when an amend is kept: exact, not by hash, `cutoff::tests::an_amend_is_kept_only_over_what_it_accounts_for`). A dated aspect's held writes are no memo: they are store rows followed by each join and leave (notes/engine-retention-dating.md Rows). `flows::secrets_in` is patched by each join (`Memo::held` before the write, `Memo::amend` after), so a write costs its delta, not the roster; the join first loads every page holding an entry of a written key (`apply::keys::secrets_paths`), since concurrent puts sit on pages its own dots do not touch.
- Other memos are named where declared on `Core`; counted by rotation `tests::epochs_are_derived_once_per_change_of_what_they_read`, `memo::tests`.

### `Effects<K, V>`
- Work in proportion to change, for an owner that acts on values (sync's verdicts, validity per part); its doc and `due`'s state the contract. `due` costs the writes since its last call times their readers, never the keys followed (`due_costs_the_writes_not_the_keys_followed`). The log holds every write since the slowest reader's last `due` or `added`: an owner calls them each pass, and dropping an `Effects` or `Feed` releases its marks. A world copy's tables carry no marks of readers left outside it.
- A prune (`Logged::Bucket`) is a candidate for every key read at its bucket's stamp, due only if a key it read was named in the log since its mark (else it reads the moved bucket stamp as its own), or given before and not settled since.
- A followed key stays followed until unwanted: the owner unwants on a settled value that says its input is gone. A write between a settle's read and its index leaves the key due at once.
- **Why a key went due**: while `costs` records, `Effects::due` counts each due key under `"<effects> <- <cause>"`: `unsettled`, or the container whose stamp moved (`Stamps::named`, else the file and line that made the stamps; `(whole)` for a whole read), e.g. `index: by_aspect`, `timelines: into`, `store: catalog kind 1` (aspect state rows), `store: record rows 0x58`. The first tool when a judgement re-runs too often.
- A memo stays pulled; push is `Effects` only.

### Per-key rows
Early cutoff where it pays: follow each key with `Effects` and keep its answer as a `Stamped` row, so a reader moves only when its row does; new keys come from a container's `Feed`, so nothing walks everything. Not an option on `Memo`: a memo copies its inner reads into its readers, exactly what a row's readers must not hold.
- **`Cutoff<K, V>`** (`memo/cutoff.rs`) is the general form; sync's own rows (`sync::certified`, `sync::own`) are the same shape.
- **Where it goes**: a fan-in (an aggregate over n inputs read by n readers), or a value many followers read whose inputs move to equal answers. The copy costs more than the rerun: n readers of an aggregate memo record and index O(n²) reads per change; a row is one read. Adding one: a field, a refresh in `Engine::follow`, a test that a follower moves after `follow` alone.
- **A reader depends on the rows as last refreshed.** A memo hit or an `Effects` owner's `due` does not refresh them, so a memo reading per-entry values refreshes before its lookup (`Engine::follow_bodies`, `follow_read_things`, `dated_replaced_at`), else a hit holds over a stale entry and the debug comparison fails. Sync's driver calls `Engine::follow` once per settle round, before the modules (notes/sync-driver.md); without it nothing a sync test waits for happens. Rejected: refreshing at each transaction's end (a refresh may be a whole walk of the sync set, so n transactions between two sync steps would cost n walks, not one); by the checker (a hit holds no function to rerun).
- The `Cutoff` fields on `Core` (`read_things`, `step_write_keys`, `wrap_blocks`, `read_facts`, `held_fates`) are declared with the function each keeps. What they spare: `read_things` per sync ID is read by every body judged under it, while its inputs (the things naming S, their sync IDs and holdings) move at each link or `sync.0`; `step_write_keys` is what `Ground::stands` reads instead of the credentials whole; `wrap_blocks` stands for a component's whole timeline read for one yes or no; `read_facts` and `held_fates` are all sync read's judgement of a body reads, so a write re-judges only the bodies whose facts it changed. Counted: osis (judgements per write flat at n and 10n; quadratic without the facts rows); `rotation::tests_stranded::whether_a_body_wraps_moves_at_a_grants_until_spec_crypto_4` fails without its refresh in `follow`.
- **`Feed<K>`** (`Stamps::feed`, `JMap::feed`): a key added and undone is given too (the reader finds it absent).

### `Quiet`
- A follower's fixed point (its doc). `memo::writes` is one relaxed atomic bumped in `Table::log` (a dropped table no reader holds counts nothing, so a follower's `mem::take` placeholder costs no follow). The queries between two writes (sync's modules ask `sync_held`, `sync_bodies`, `may_log`... many times per delivery) cost one follow plus one that confirms the fixed point. On it: `Cutoff::refresh_in`, the sync set's rows, `certified`, `listed`, `own`. Counted (in a child process with one test thread: the count is process-wide): `memo::cutoff::tests::a_quiet_cutoff_derives_what_came_since`.
- A follower whose follow runs another's (`listed` runs `certified`'s, which runs the rows') returns at once only while that one would too (`certificates_quiet`, `rows_quiet`), so a key left pending there is never skipped.
- Relaxed suffices: a write that happens-before a check (a lock, a channel) is seen by coherence of the one atomic; a write with no such order came after the check. Rejected: per-thread or per-engine counts (an engine moves between threads and its stamps are written from others, the sync store's). Follows are counted only where this thread's own writes owe them (`Quiet::holds_here`), so a count test is a function of its history whatever runs beside it (`memo::tests::another_threads_write_runs_a_follow_but_owes_none`).

### What can be missed, and checks
- A function reading a mutable `Core` field outside these containers, or a copy of store rows that records no read of them. A new memo's inputs get a stamped container first.
- Debug builds compare a hit with a fresh run (`memo::Checks`) on two schedules: the 1st, 4th, 16th, ... hit at which a container the entry read changed (an amend is one), finding a missed read that changes with a recorded one; and hits 16, 256, 4096, ... whatever changed, finding a missed read that changes alone (gating it on any engine change would not do: a missed read may be of a field no stamp counts). A hit inside a comparison (`memo::comparing`) counts for nothing. A debug check reading beside a cache hit runs under `memo::unrecorded`, else its reads would cover the read the hit missed. Counted: `retention::tests::memos_follow_leftovers_through_writes_and_undo` (each stamp removed fails it).
- `Effects` likewise, on a thread that turned it on (`memo::check_effects`): `due` adds keys whose reads held, on the same schedules; their settle must give the kept value, else it panics naming the key (`a_read_without_its_stamp_fails_the_comparison`). `Cutoff` compares its rows.
- Not built: a view type holding only the stamped containers that every memo function takes instead of `Core`/`Tx`, which would make a missed read structural.

### Coarse reads and rejected designs
- Whole-container reads are exact where the container is one value (`Tracked`, `Clock::until`) and coarse elsewhere. Coarsest: a stored row read whole (an aspect's state row moves every replaced-at date and part bound on it: issues/derived-state-recomputed.md step 4); a timeline read whole (`Timelines::get`) moves with any role change in the component. A journaled map with runs is read per run (`JMap::by_run`, `JSetMap::by_run`), else by key set where only keys are asked (`keys_held`), else whole.
- Key access is global (`osis_keys::key_access` orders all actor grants), but a keyless grant closes a cycle, which lies in one component: the timelines judge anew only the components where an actor grant or record changed and move `keyless` only when the union changes. Rejected: a memo over every timeline (reruns at every role change; each consumer copies its reads).
- Rejected, general early cutoff for every memo (issues/derived-state-recomputed.md, Memo design review):
  - eager (every memo a `Cutoff`): most memos' keys are many and one-off (`covers` per (snapshot, body, aspect)), which a memo sweeps and an eager refresh would rerun and keep; and inside a transaction each row reader must refresh before a hit is trusted, which a nested memo cannot know to do;
  - demand-driven red/green (salsa): every memo function would move to a fixed context, every entry carry a change stamp, and `Effects` verify each candidate's inner edges at `due` (an edge has no log). Measured, the cost is the copy of reads, which a fan-in row removes; what red/green would still save (recording and indexing reads, at most about 15% of the osis and osis-sync test binaries) is not worth it.

## Signature verdicts
A signature check is a function of immutable bytes (key, signed digest, signature), so it is no memo (with nothing stamped its answer would never be swept): it runs once where the bytes enter, and its verdict is kept beside them.
- A commit's: `apply::signature` is the one door. Its verdict (`osis_commit::Signed`, a hash of the three) is made only by a check or by the signer (`Built::signed`: the signer verifies its own signature once before anything leaves it, so a signing fault is never published: a faulty Ed25519 signature can leak the key), and read back (`Signed::from_kept`, tools/policy.py `kept_verdicts`) only from where this node kept one: the held commit's record head (`Meta::signed`, so an open checks nothing again) and a pending copy's row (`Pending::verdict`, `apply::kept_verdict`: re-examinations and lost access's `authentic` check nothing again). Within one ingest it is handed on (`examine`'s and `memory_gate`'s `known`).
- It answers only for exactly the bytes and key it hashes, so a forged copy or another key resolved for the author is checked anew. Whether that key may sign is validity's question, never the verdict's.
- Trust: a kept verdict is trusted as the store is, like the node's keys in it (AEAD units under the key tree: notes/local-store.md; a restored backup holds only this node's own verdicts).
- Counted: `apply::tests::a_commit_signature_is_checked_once_per_node_spec_crypto_2` and `a_pending_commits_signature_is_checked_once_spec_crypto_2`; each verification counts under its domain (`Domain::verify_cost`).

## Public surface (engine)
Rustdoc has the list; the rules it rests on:
- Writing: `Engine::commit(m)` is the raw commit (notes/engine-apply.md, Writer side); the app's path is `Engine::write` (confinement, ephemeral writes).
- Receiving: `ingest` and its variants answer `Ingested`; sync ingests through `open_entry`.
- Retention: sync judges deletions and re-snapshots from the commit index, no queue (`snapshot`, `covered`, `drop_body`, `part_keeps`, `delta_live`, `replaced_at`; `body_not_dropped` is true for a missing part too).
- Schemas: one per app AK, never from the wire (`register_schema` replaces one of a lower or equal version, a local typed write only a lower one; read at open); they serve undo's typed views and large write-back after a restart. `osis::Osis::aspect_key` types only by this session's registrations, so the CLI's `schema rm` untypes.
- Flows return `Done { commits }`; what a flow owes others (grant fires, stranded notices) it fires in its own transaction, and sync logs every body from `sync_bodies`.
- Rotation and lost access: notes/engine-roles.md, notes/engine-lost-access.md. Events: `Event`'s variant docs; sync and the API report diagnostics through `Engine::report` (one `DiagnosticKind` enum).

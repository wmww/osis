# Sync access: steps, claims, re-seal
> Summary: Why opening a sync ID at a node keeping it unread is gated by the head's credentials and how a holder that fell behind gets back in: steps, claim keys and the one-sync-key-at-a-time walk, rotation commits (wrapped under the superseded epoch, logged before the step), opens ending at a new sync key, refusals carrying only a code, re-seal and stranded reports, entry boxes and static entries; which thing owns a sync ID; the accepted lockout and stranding limits. Rules: spec/sync-ids.md §2-§6, spec/sync-opens.md §4-§6, spec/permissions.md §3-§4. Neighbours: notes/sync-reasons.md, notes/inbox.md (re-seals and grants travel by inbox), notes/crypto.md (epochs, history boxes), notes/sync-opens.md (the code).

## Why the gate and the claim
- **Opens at a node keeping S unread need a credential of its head** (its sync key, a claim, a static entry; spec/sync-opens.md §4): without the gate an ex-holder, or anyone who learned a sync ID, keeps fetching ciphertext old and new (counts, timing, laggards' old-epoch wraps, a wider surface against future key breaks). Tess: nothing is served under a superseded key, not even entries the holder could have fetched before. The price: a holder that missed a rotation cannot fetch the commit carrying its new box; claim keys pay it.
  - Rejected: a grace window after a new step; "old key serves old entries" (no gating against ex-holders); serving only rotation entries to old keys (every ex-holder watches roster size and rotation timing forever, and the flag is unverifiable); no gating at all (ex-holders watch activity and harvest ciphertext forever; Tess rejected).
- **Claim keys** (decided with Tess): a laggard and an ex-holder hold the same shared keys, so the gate needs what only the laggard has, its own private key, and the registrar is the one party that knows the roster a step is for. So the step itself is the delivery: a fresh step key and one pseudonymous Ed25519 claim key per reader, derived by DH (spec/wire.md §8); recovery is a pure function of the laggard's private key and the path the node stores anyway. Nobody delivers, drains or budgets anything.
  - A signature, not a hash preimage: a dishonest node cannot replay it elsewhere.
  - **One sync key at a time** (spec/sync-ids.md §6 Behind): an answer runs through the first step under another sync key and no further, so an ex-holder removed at a rotation learns that one rotation exists and nothing after it, no count or timing, however long ago it was removed (a sync key never stops being a credential; claims and static entries end with the claim set, `ROLE_KEEP`). A current reader asks on by its credential at the step given. Rejected: answering every step to the head (one item per catch-up): every holder of any old sync secret, a removed reader or a used link, would watch the rotations and learn the head's sync key, whose beacon tells it which peers keep S, forever.
  - The answer is the signed step, verified under the previous delete key, never a bare key: a node handing out a chosen step key could otherwise recognise a claimant by the pseudonym it signs with.
  - The claim set comes from the epoch's read boxes, not the registrar's roster: the registrar may hold the epoch without the removal commit and would list the holder the rotation just removed, and boxes name the first admin and plain-group readers the roster does not.
  - Nested actors chain claims: the node key on its account's D home sync ID, then the account's read key on each group's. The registrar uses M's newest `keys.0` it holds, so M tries old keysets as for boxes; a node M removed can claim until a registrar that saw M's new keyset issues a step (metadata only, M's boxes are under its new key), the same staleness class as the epoch-covers rule.
  - Steps are not deterministic (random step key and padding), so concurrent admins make sibling steps and nodes that saw different ones first keep different branches for good: steps form a tree by `prev`, a node accepts only a child of its head, and the next step due lists past them (spec/sync-ids.md §6 Steps). `sync.0` holds every branch, so any reader can register a source's branch onward; claim keys bind to the step key, not a sequence number, since a branch has no number of its own.
  - Cost: 32 B per reader per step, about 3% on top of the rotation commit's boxes (whose padded size already leaks the roster bucket). The path itself (role keys, step key, signature) stays for good; claim sets only until `ROLE_KEEP` after superseded: beyond that a walk reaches nothing readable anyway. The gate is classical like the Ed25519 open; a quantum ex-holder could fetch hybrid-protected ciphertext.
  - Claim-set padding keys are public keys of random seeds (valid points), not random bytes, or a node testing point validity would count the real keys. Static entries (hashes) stay distinguishable from points about half the time, which says only how many key actors read S.
- Grants still need a way in before the grantee holds any key of the target: the inbox blob (notes/inbox.md).
- Rejected: **mailboxes** for rotation delivery (every actor names a mailbox sync ID in `keys.0`, every rotation deposits one doubly boxed projection per holder, about 2.5 KB per holder per rotated actor): a stored, budgeted side channel someone else must feed; a key actor's mailbox has no writer to promote deposits, so a key actor offline through enough rotations finds the newest deliveries refused; clients need a mailbox-first bootstrap across nesting levels; a node's mailbox is stable per node, so the node keeping it counts an account's nodes for life; deposits over one connection link the recipients' mailboxes. Claim-key variants rejected: the registrar's own read key as the DH key with the holder guessing among admins it knows (fails once the registrar's keyset changed since the holder last synced); an ephemeral key served to anyone or in a public chain (every ex-holder watches rotation cadence and roster bucket).

## Rotations and opens
- **Rotation commits are wrapped under the epoch they supersede** (spec/crypto.md §5): a rotation hands out the new read secret, so a wrap under it would be readable by the rotator alone. Under the old wrap a laggard reads the rotations it missed in order, each under the one before. What an ex-holder gains from that blob (an honest node serves it under the old sync key until the step is registered; a dishonest node or stray bundle for ever): the box map of the rotation that removed it (tids and roles at the new epoch) and the removal about itself, which it gets by inbox anyway; never a secret. Under a fork the rotator picks the newest superseded epoch; a holder granted during the fork under the other branch only cannot open it and needs a re-seal (rare).
- **Rotation commits go before the step** (TLC R9; spec/sync-ids.md §6 Steps). The source checks stamps against its head's write key, so content stamped under rotated keys waits for the step; but a head naming an epoch whose rotation commit is nowhere strands every listed holder (it reaches the head, cannot open it, reports itself stranded and is re-sealed with a secret it has no commit for). So the registrar logs the actor's role commits the source lacks stamped under the source's head, registers once the source's stream shows them held, then logs the rest. A step at a source implies the rotation commits behind it are there (until compaction, where the `secrets.0` snapshot is), and "stranded" means not boxed.
- **An open by a store credential ends at a head with another sync key** (spec/sync-opens.md §6): an open kept across steps would push a removed reader that stays connected every new entry for the connection's life. Tied to the sync key, not the step: a step without a sync rotation removes no holder, so its opens stay. The registrar's own open ends too: Register is relayable and proves only that the step is signed, so a departed node relaying a step it was pushed must not keep its open by it; the registrar opens again under the new key (its record keeps the cursor). The remover's rotation commit still reaches a connected departed node: it is logged before the step. Opens at readers (J reader, read secret) are not step-bound.
- **Refusals carry a code alone**: a refused Register answered with the head, a refused Deposit with the budget, or a Delete's Status with the head would let anyone with a sync ID (ex-holder, link holder, an ex-admin re-sending an old delete) watch rotations and deposit activity forever. Nothing needs them: heads reach a node through its open (the stream's head events, Behind answers); a stale deposit is signed again from the node's own seed.
  - Code 9 stays apart from 1: it tells a signer its key was superseded, not bad, so a stale deposit is signed again at once with the current deposit key, and an ephemeral entry or delete waits for the newer key instead of being dropped or looping. It tells a holder of an earlier key only that it was superseded, which it mostly knew. Behind's 13 against 14 still says whether a node keeps S (spec/sync-hostile.md §2: its filter shows it anyway).

## Re-seal and stranded reports
- **Re-seal is the one recovery path** (spec/permissions.md §3 Re-seal) for a holder with the right private keys that cannot reach the current epoch: its missed rotations compacted (`ROLE_KEEP` after superseded), its grant unknown to the rotator, a fork branch it never received. Nothing a co-reader serves helps by itself (every current commit's wrap is under the epoch it lacks, and a peer serves wraps, not keys), so someone who may rotate seals the current secret to it, with the epochs' history boxes (without them a re-sealed holder could decrypt the history box but not fetch it: it sits in a rotation commit wrapped under the epoch it lacks, TLC R3). A sibling node of the same account is usually a writer, not an admin, of the group, so "who may rotate" matters.
  - It goes as an inbox blob, not under S: such a holder cannot open S, and a wrap would have to be under an epoch it holds. Its own private keys never change, so a node stranded on its account's D home sync ID is re-sealed the same way; when the inbox is the very sync ID it cannot open (a node offline past `ROLE_KEEP`), a sibling node re-seals it over a direct connection, cheaper than a restore from the card.
  - Nothing unattended re-seals (a PQ box per reader per step was rejected for size). Triggers, both SHOULD: a current holder seen without a box at a current epoch, and a stranded report; a client may also offer it by hand (`Engine::reshare`).
- **Stranded = no key it holds opens S's current epoch there** (spec/permissions.md §4 Stranded), wherever the walk stopped and whether or not a claim was tried, not only at the head: a holder whose next step's claim set was dropped never reaches the head (TLC R2), and one reaching a step where it holds no named actor (its grant not received, a key actor's static entry dropped) has nothing to claim with, yet is in the same place.
- **The report** (a Stranded message to a connected writer, else a stranded notice to each admin's inbox) needs no key of S: an inbox is the admin's own home sync ID under its own deposit seed. It names the holder the node reads through and carries that holder's current `keys.0` commits: a node that left the holder out and no longer follows it learns its next keyset and deposit seed only so (spec/crypto.md §4, Reported). A link key is never named: it reads by its static entry and has no inbox.
  - A receiver takes only the holder's authority chain from it, each commit rolled back whole unless valid with every edge write applied (`Engine::ingest_valid`), so what a report can make its receiver keep is bounded by the holder's real authority history, not by the sender (a notice has no sender to judge: anyone with an admin's deposit seed can send one).
  - Rejected: a current-role check on the author (it drops the grants a since-removed admin made that the honest chain runs through); taking a chain commit only as a carried `keys.0` commit awaits it (`Ingested::Awaits` names only records; a missing role shows as no reach, not as which edge); inferring the holder from the connection's proved actors up their record chains (it finds only account and node holders, so a member stranded through a team while connected to a writer would never be heard).
  - The cost: a few KB of `keys.0` per report, and the holder's deposit seed handed to the actor's writers. Not new in kind: the holder's rotation commits, fresh seed included, reach every reader of the actor as carried certificates once it is sealed there.
- **Entry boxes and static entries** for link keys (spec/sync-ids.md §3): a key actor entering cold holds no epoch to unwrap anything with, and the account's rotations get compacted, so its box in `secrets.0` is not reliably reachable. So each step boxes the read secret (and the superseded epoch's and the sync secret) to it (one hybrid box, about 1.2 KB, sealed form only: the symmetric form carries no epoch to check), and it claims the current step directly by its static entry (a hash of its signing key and the sync ID): no walk, no old step. The registrar cannot do DH for it without a step private key it would have to keep, and a bare signing key in the set would show the node a public identity; the hash shows nothing until the key claims. The entry is stable across steps, which says only that one slot is a link's. A key actor granted after a step is listed by a fresh step (an admin may step without rotating). Link keys claim the current step, so compaction and claim-set drops never strand them.
  - Rejected: the read secret boxed to every reader (1.2 KB per reader per step, permanent, in `sync.0`; it would spare laggards past compaction the re-seal); deriving the step key from the admin secret for determinism (an ex-admin plus a dishonest node could identify late claimants from its time as admin).
- Re-seal soundness rests on established epochs (notes/permissions.md): within `ROLE_KEEP` the departures travel in the epoch chain a re-sealer must hold; after compaction they travel in the role history and the removal commit apart from the `secrets.0` snapshot, so a node with an incomplete view (one that never received the removal, an interrupted first sync) can box a removed holder at a snapshot-established epoch by an eager rotation or a grant (re-seals themselves wait for a complete pass and chain-established epochs). Healed by the next rotation of a node that knows the departure; accepted.

## Owner of a sync ID
- **A sync ID is g's only by g's sync key** (spec/sync-ids.md §4 Owner; `labeling::actors::owns`, `Core::owns_sync_id`): any admin of g writes g's `sync.0` and can name any sync ID there, so an entry counts only when a step on a verified path from its genesis bears the sync key of a sync secret of g held here. Steps chain by signature to the genesis delete key the sync ID commits to, so only the owner's admins make a step bear g's key. Ignored, never judged invalid: the check turns on held secrets.
  - The sync key, not the genesis delete key (admin secret): every holder holds a sync secret, only admins the admin secret. Every holder holds the older secrets by history boxes, so some step always matches.
  - While this node holds no sync secret of g's own (it reads g by derived secrets no step bears), g's entries are hints (spec/sync-inbox.md §2 Sync ID hints). Bounded: such a g holds no secret deriving that sync ID's keys, so it registers and deletes nothing.
  - Limit: an admin of t that also holds sync on u can give t u's sync secret as a new epoch (nothing checks a rotation's secrets are fresh) and so list u's sync ID as t's. Hostile admins are out of scope.

## Limits (accepted)
- A removed writer keeps its delete keys, but they alone delete nothing: a Delete also needs the head's sync or write key, which the step its removal requires replaces. Until an admin steps, writers stamp and open with the keys of the epoch the source's head registers (held by history boxes) and wrap under the newest they hold; a writer's rotation changes no delete key, so a sync ID whose admins are all offline keeps its old step while content under it is already unreadable to the removed holder.
- A removed admin holds the current delete key until the next step and can register a child of its own first at a node keeping S unread. Hostile admins are out of scope; the remedy is local and manual (nothing detects it): restart S at that node (dropped and synced again, spec/sync-ids.md §6), after which a reader registers the recorded path again, or the group's readers stop syncing with it. No sync ID is ever replaced.
- A holder listed in no step since its last sync (a grant a rotation raced) is locked out until a later step lists it or a holder re-seals it (spec/requirements.md, Permissions); the rotation left it without boxes anyway, and the SHOULD re-seal (a holder without a box at a current epoch) repairs it at the next write.
- A holder whose missed rotations were compacted is refused at the step whose claim set was dropped and is reachable only through its inbox; its stranded report tells a connected writer or the admins. A walk costs one round trip per sync key it passes. A node offline past `ROLE_KEEP` on its account's D home sync ID has no inbox of its own: a sibling re-seals it over a direct connection, or it is restored from the card; a node may keep claim sets longer by policy. A dropped claim set also strands a holder whose next rotation is still readable (it cannot walk past the step).
- Re-sealing is triggered, never guaranteed: a stranded notice is lost when the admin's inbox refuses it (its budget full, or an account's deposit seed rotated since this node last read its `keys.0`) and no writer is connected; the holder then waits for a manual re-share (`Engine::reshare`).
- **Holder actors at depth 0** (spec/requirements.md, Permissions; notes/crypto.md): a party removed from a holder actor M of A reads A's content sealed to a keyset of M written without knowing the removal (an ignorant fork, or a forgery where the removal or the forgery is not held) until M's knowing rotation reaches A's writers; a grant some sealer has not seen lets a cycle form there until the writer holds the grants.
- **A deposit-only step** (a new deposit key, no other role newer) waits until the admin opened every entry it can open under S and holds no unapplied `keys.0` write of the actor signed by a current admin (spec/permissions.md §3; `Engine::keys_write_unapplied`). Why: a co-admin's refresh step can arrive before its `keys.0` write, and the laggard would step back to the old key, letting a departed party deposit again until it applied the write. Unsigned or unopenable ones never count: anyone can send a pending commit, and an entry that never opens would hold the step back for good.
- `sync.0` growth is about 320 B per step per sync ID per rotation, plus claim sets (32 B per padded reader per step, plus entry boxes) until an admin drops them `ROLE_KEEP` after superseded (steps are a map keyed by step ID, so the drop is a field write); a node registered from a trimmed path serves no claims at the trimmed steps. If growth ever matters, a root step carrying the current keys signed by the genesis delete key would let old steps be dropped.

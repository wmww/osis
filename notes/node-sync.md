# Node sync as built (osis-engine `labeling/`, osis-node `sync/`)
> Summary: How a node syncs its labels: the module map of `labeling/` and `sync/`, the sync records under `y/`, the pass in order, certificates (revokes about authors, others' cards, linked blobs), inbound entries and presence at a peer that cannot read L, pass records and complete passes, local requests, the driver, handed-off groups, junk copies, a listing from the start newest first, the simulator hook and the invariants the simulator established. Topics with their own notes: opens and re-registration (notes/label-access.md), deletion judgments (notes/sync-convergence.md), inbox, outbox and promotion (notes/inbox.md), work sets and idle labels (notes/node-sync-work-sets.md), co-reader peers and local passes (notes/peers.md), the memory lane (notes/ephemeral.md), the engine (notes/engine.md).

## Module map
- `labeling/` (osis-engine, pure judgments over engine state):
  - `actors`: reader actor = the nearest thing up the record chain with secrets of its own; `secret_actor` up the record chain; `may_read(x, t)`: `t`'s secrets derive from `x`'s, or `x` reads that actor on the timeline; `closure(g)` from the group index (members, `g` and its subgroups); `group_labels` from `label.0`.
  - `blobs`: `Body` = one held commit, `parts` those the label's actor may read (`readable_parts`), the blob carrying every held part. `label_bodies(g)`: commits touching the closure with a readable part, plus, on a home label, the `label.0` and `created.0` writes of labeled groups whose nearest labeled record-chain actor it is (through standing record edges) (`to_label`: sealed per label under the label's secret). `seal` (one section per thing, `extra` sealed sections copied verbatim), `seal_to` (one section under a given secret: copies), `open_commit` (sections under the thing's, the label group's derived and own secrets; prefix vs header, spec/commits.md §4; `OpenedBlob::unknown` for the sealed-section retry in `redeliver`). `wrap_secret` with the rotation exception (the commit's `keys.0` delta writes a read keyset of the label's secret actor: the newest held epoch it supersedes). `head_keys` (sync key from any held secret, write/delete only established, deposit key from the actor's seed). `delete_secrets_of` (per commitment group of the blob's listed aspects) and `chunk_delete_secrets`: the header's delete keys matched over every held epoch along the record chains (`Core::delete_chain`, `delete_secret`); an entry's `Kind::Commit` keeps the aspects its sections list for the signatures, and every entry (and tombstone) its blob's prefix salt (`Entry::salt`).
  - `certs`: `certificates(g)`: node card commits and perm's chain certificates as (commit, aspect indexes); `part_body`; `revoke_certificates`. Labels are made with secrets of their own (`rotation::own_secrets`), steps by flows' `issue_step`.
  - `converge`: the pure rule, `classify(Facts) -> Hold`, `may_delete(why, live, carried)`.
- `sync/` (osis-node; `SyncEngine::handle(Event) -> Vec<Action>`, sans-I/O; `Event::{Tick, Local, Up, Down, Reply, Notify, WantRoom, End, Hub}`, `Action::{Dial, Close, Wake, Reach, Host, Request, Room, Ended, Hub}`; one write batch per `handle`):
  - `conn` (connections this node dials: dialing, labels on each, its own requests in flight and their answers), `open` (opens and walks), `inbound` (entries arriving, invite requests, hints), `pass/` (the pass: `bodies` must-hold and placing, `certs`, `reseal`, `inbox` stamping/grant copies, `promote` relay wait, promotion and clearing deposits, `register` steps, `delete`), `work` and `marks` (work sets; notes/node-sync-work-sets.md), `timers` (resyncs, wakes, running marked passes), `deliver` (flows' results), `local` (app and flows requests, the outbox), `fill` (a listing from the start at a peer that cannot read L), `handoff` (groups handed off to another node), `memory` (the memory lane: notes/ephemeral.md), `peers`, `serve` and `stream` (co-readers, `reach.0`, LAN, co-reader serving, the node log stream: notes/peers.md), `host` (hosting: notes/serving.md), `bundle` (file bundles, spec/sync.md §11), `status`, `io` (config, inputs, outputs), `state` (records), `driver` (tokio).
- **Every connection is a session of the node's hub**, dialed (`Hub::dial`) or served: node sync is the upper layer of each (notes/serving.md, Hub). Each is one `Conn` (conn.rs; issues/net-sync-structure.md (a)), whoever dialed: a dialed one from `Action::Dial` (`Conn::dial`, an ephemeral transport key; the driver hands its link to the hub and feeds `Event::Up { conn, hub }`; `Event::Down` is a dial that never came up), a served one from its hub session's start. At the session's start (`Up::Start`, the binding; `conn_start`) a dialer sends three Pings and its Prove signed over the binding (`Prover::sign(false, listener challenge, listener key)`, the Proved checked by `prove::verified` against its own challenge), and a dialer to a node a label lists starts the labels that node may hold (`add_new_labels`; nowhere else); its own requests (`Conn::pending`: `Ping { sent }`, `Prove`, `Resume`, `Register(L)`, `Delete(L, ids)`) go under ids below `NODE_IDS` it picks (`request`), Deletes `MAX_ITEMS` per request with each entry's request id in `Requests::deleting`; the session hands their answers up (`conn_message`). A Ping every `PING_INTERVAL_MS`, and at a `refresh` on a connection with nothing of node sync's out and nothing sent or heard for `retry_ms` (`Conn::heard`; polling a live node sends nothing), keeps a request out, so the hub's stall clock finds a dead connection; Pongs feed the clock offset (`ClockSamples`, `ClockSkew` past `OFFSET_DIAGNOSTIC_MS`). The session's end (`Up::End`: the hub closed it, its stall at the hub's tick, or node sync's `Down::Close`) is `lost` (`close` from this side), whoever dialed; a dialed one is dialed again after its pause. The client port runs on every connection. The hosts are the union of the synced labels' host lists, `SyncConfig.hosts` and inbox hints; a label's `peer://` addresses are not hosts (`peers::host_keys`: never dialed from `label.0`), so a label listing only those is served here (notes/peers.md).

## Records (`sync/state.rs`, local records under `y/`)
Entries per (label, blob) with wrap, stamp, certificate flag, prefix salt and expiry and what the blob is (`y/e`; `Kind::{Unknown, Commit{commit, parts}, Inbox, Request, Parked, Bad}`; one with bytes held is also a row of the hub's store, the truth for its wrap and stamp: notes/serving.md, Node sync's rows); presence per (peer, label, blob) with a deposited-there flag (`y/p`, by `PeerKey`: a tag byte, then the record ID or dialed key; no gained-ID lists: what a source lacks it pulls); what was read of the stream of each peer that cannot read L with no record (`y/c`, `StreamAt` per dialed key) and heads (`y/h`) per (peer, label) (a stream position with a record is in the record, notes/peers.md The stream); blob keys of commit blobs (`y/b`; `by_commit`: an encryption is reused under other labels, a certificate's never); certificates placed (`y/k`); a peer's tombstones and useless-wrap marks (`y/g`, the wrap in `y/3`: a fresh encryption next time); label hints from inbox blobs (`y/i`); carriers (`y/s`); the outbox (`y/o`); sent inbox deliveries (`y/v`); owed deliveries (`y/y`); direct commits for the app (`y/j`); forgotten things' inbox blobs (`y/f`); filling labels (`y/4`); declined invites (`y/m`); handed-off groups (`y/w`); tombstones (`y/x`: time and what the entry was, wrap, certificate flag, salt and kind, every kind alike: a source showing it within the tombstone gets the entry recorded again quietly as present there, so the pass judges it there as any present entry; the tombstone stays, so nothing of it is fetched or stored, bytes received giving only their salt; `deleted` is rebuilt from them at load); peers' records (`y/r` dialable secret, `y/a` contacts, `y/l` link sharers); the client listener secret (`y/2`). A failed sync-state flush keeps its writes for the next flush. Growth of these: notes/growth.md.

## The pass (`sync/pass/`)
Runs after the log was read to its end (`Synced`) and on every later change marked into its work set:
1. Head keys recomputed. No read epoch of the head held: open what it can and report itself stranded (`reports`), nothing else (notes/label-access.md). A holder whose box at the head's epoch does not open (a holder actor's keyset withheld) cannot claim the head either (its claim key is at that keyset), so the open fails and `label_status` reports the label stranded (osis `SyncState::Stranded`), never synced (`sync_review::no_secret_of_the_heads_read_epoch_is_stranded_spec_sync_5`). An admin with a newer established epoch re-registers first (role commits, step, then the rest after `Registered`).
2. Must-hold bodies (before keep-at-least, or not covered by a snapshot entry of the label), role commits first: placed in the own store stamped by a writer (a source pulls them), by readers relayed under a stamp the head's write key verifies, else deposited as Deposit items (an own edge write placed for deposit goes by the outbox; others' bodies under a superseded stamp go as plain deposits, notes/inbox.md). Chunk, page and list blobs of placed commits and the held blobs their deltas link though not listed (reused chunks, a snapshot's values) go with filler wraps.
3. This node's certificates and node card per label (a fresh encryption), only the deltas no genuine entry of the same commit present at every host holds (any node's copy or closure blob), never closure deltas; another node's demotion or `keys.0` only `SETTLE_MS` after receipt; inbox grant copies.
4. Writers promote deposited entries; admins clear what waits for nothing (notes/inbox.md).
5. Deletions of must-not-hold entries present there, carriers first (notes/sync-convergence.md).
- **Expiry: one rule, before every event's work** (`SyncEngine::expire_entries`, `State::by_expiry`): an entry goes at its blob's prefix expiry (`Entry::expires`, read once the bytes are here: an own placement's at once, `held_expiry`, others' with the salt, `keep_salts`, or when a row another wrote to the hub's store brings them, derived or announced before, `take_rows`, whether or not it opens or its label is one the node can place) with its presence everywhere, no tombstone, its bytes unless another entry names them; whatever its kind or what the engine knows of its commit (a request forgotten at its expiry, an `Awaits` entry), at hosts or served, connected or not. Hosts drop it unattended then, and the hub's rows of a sync ID the node reads expire only here, so the two agree. No pass judges expiry. A commit the engine forgets whole (`MemoryDrop`) takes its bytes no entry names (`memory_step`): an entry may leave first, a host's clock ahead.
- Entries (`entry_for`) take any entry of the body (a certificate copy too) and prefer one present at the host (spec/sync.md §6); certificate copies are wrapped like the body (rotation exception), so others open them as the body.
- An entry that unwraps but does not open as a commit is `Kind::Bad` or `Kind::Parked(commit)` (handed to `ingest`, parked, relayed when stamped), never retried and never unsettling the label: one junk deposit would stop every upload under it.
- Entries present at a host, unwrapping and never opened, are opened or fetched again at each pass (`refetch`); a fetch the host cannot serve is not repeated on that connection until it announces the blob again; every fetch goes through `fetch_on`. A blob counts as asked (skipped by every other fetch, fill and stream; a pass waits on it) only while some source's fetch of it is younger than `STALL_TIMEOUT_MS` (`asked`: host fetches in `Requests::fetching` with their ask time, reader Fetches in `Fetching::at`); past it the next source of either kind is asked (each source once while its fetch is out, `may_ask`), and whatever skipped it gets a pass at that time (`asked_for`, `settle_by`). One rule for hosts and readers alike (notes/peers.md, The stream: Bodies).

## Full and refusing peers, role entries (spec/sync.md §5 Role entries, §10 Full, Refused)
- **A full peer says so**: a node that cannot read L and refuses an entry it pulled for room (code 12; pulled stamped entries meet no rate) is full for L (`Unread::full`, `unread_refused`): it sends Stream event 2 `full` true, no cursor, once per connection (again where a refused entry is shown on a new connection), and never fetches an entry it refused (`unread_wants`), else the stream owes it forever. Room of that kind (durable: the label's and the store's entries and bytes; memory: charged bytes, `HostStore::room`) below its reading at the refusal clears it (`unread_room`, each step): `full` false where told, and every stream pulling L joins it again from the start (`stream_rejoin`), so what it refused comes again. Brute force, rare.
- **A refusing peer says so**: every other refusal of a pulled entry (its stamp under no key of the head there, expired, malformed, tombstoned: whatever `serving::pulled` answers) goes back as Stream event 4 `[blob_id, code]`, no cursor (`unread_events`). One rule at the reader: code 6 is a deletion there (`set_gone`: placed anew if must-hold); any other code marks the entry refused there under (its stamp, the peer's head named on that connection when the event came: one connection carries both in order) (`State::refused`, persisted, `y/R`, dropped with the entry or once present there). While both stand, `at_source` counts it neither lacking nor holding deletes back; once either changed, the mark goes and the entry is offered again: a new stamp is its own log event, a moved head relogs it (`State::relog`, the hub store's `reader_relog`). So no position heuristic guesses what a peer read and refused, and a restart keeps the mark. A hostile peer's claim only stops the waiting (as dropping what it pulls never does: then deletes wait for good); it deletes and drops nothing here.
- **Readers**: `LabelAt::full` from the event; `LabelAt::lacking` counts the bodies this node places, stamped for the source's head (now or by the pass), that the last pass found the source lacking (a deposit is the outbox's to wait for); a source is idle only lacking nothing or full, and status names a full one, or one refusing a body it lacks (`LabelAt::refused`), in `refused_by` (the one "will not take it" concept). Waits and Placed read idle, so they wait for nothing a full peer lacks. `is_idle` (the sim's quiescence) reads `LabelAt::settled`, without lacking: a hostile peer dropping what it pulls lacks it for good, which status shows and nothing works on.
- **Role entries**: what deletes are judged by (`Out::prio <= 1`: role commits, requests, the blobs they link; `role_entry` by kind for promotions and deposits) is stamped or deposited under `"osis v1 role entry"`; a peer takes such an entry outside its caps (`Meta::role_n`/`role_bytes`, `Row::role`), a stamped one with no count of its own (a writer is inside the storage trust boundary: it can fill the label's room with content anyway, and role commits are must-hold for their fixed retention), a deposited one within the deposit budget, so a purge or a compaction's role view frees room at a full peer (`sync_review::a_purge_frees_room_at_a_full_peer_spec_sync_7`). Tests that need a peer refusing a role commit use `Net::unpulled_at` (node, host).
- **A body expiring within `MAX_DRIFT`** is not encrypted again after a delete (`delete_stands`), whatever its class or the delete's reason: clocks agree only to `MAX_DRIFT`, so a holder ahead may drop it by expiry and putting it back fights that (the sim's ephemeral storm). The cost is at most `MAX_DRIFT` of its life, which clock agreement already allows any expiring entry; durable and memory bodies alike (ephemeral is durable held in memory).
- **A connection whose peer reads L** (member opened by read credentials, `shared_reads`) is no source and its deletions are a reader's: it judges its own store (a paired node dropping a duplicate certificate copy made its owner copy it again forever).

## Certificates (`pass/certs.rs`, `pass/delete.rs`; spec/permissions.md §4)
- **Copy or body is entitlement, not closure** (`Engine::body_carried`, used by `certificates`, `place_chain`, `chain_missing`, `revoke_certificates`): a chain part goes as a copy exactly where the label's bodies do not carry it, on a thing outside the closure or one the label's actor may not read. Closure alone left a chain through an unread closure thing (a team listed in g that holds write on g) under g as neither, and g's readers never applied that team's members' writes (`labeling::a_chain_through_an_unread_closure_thing_reaches_readers_spec_sync_3`). A removal of the label's actor's edge needs no carve-out: once the actor reads the thing no more, its parts are not carried.
- `certificates` places the aspects its copies lack that the bodies do not carry (else a copy duplicating body parts is deleted as a strict subset and re-placed each pass) and counts the aspects of any present blob of the commit under the label as placed. Copies after a rotation (`place_chain`) carry only grant, `keys.0` and `created.0` deltas the bodies do not carry. A copy whose deltas another entry of the commit holds is skipped only when the entry's deltas were checked against the header, it is present at every host, and a rotation commit's exception-wrapped blob counts only under the newest epoch (notes/permissions.md, Certificates). Placing a certificate never rotates (`uncovered(g, false)`): under an uncovered epoch the copy waits in `deferred` for the next pass, which rotates first.
- **Revokes about authors** (`Engine::revoke_certificates`): the authors seen under a label are the authors of its commit entries that this node judges invalid in a part the entry holds or, for a role commit, in any grant op (aspect validity holds while any op on the aspect is valid: a single-use race loser's void grant sits beside its valid removal of L), or cannot judge yet (pending) (`Engine::judged_valid`). A revoke changes no verdict on writes its frontier covers, and placing it for them cost every link joiner the remover's whole chain (about 12 KB) under its home label at each joiner removal; a later write the revoke voids brings it then (revocation reaches a label when a holder next syncs it, spec/requirements.md).
- Applied edge writes lowering a grant on a thing the bodies do not carry go under the label with what judges them (`Timeline::write_certificates`: their authors' chains), placed like chain certificates. Another node's demotion or `keys.0` is left to its author for `SETTLE_MS` when the author reads the label's actor and so places it itself (`Delivery::Removal` goes under the labels holding the holder that the author syncs); one by an author who does not, an outsider's removal from the inbox among them, is copied at once: the hold only dedupes co-readers' copies, and a blanket hold delayed a group's readers of such a removal by 30 s for nothing (`tied::grant_and_removal_orders_large` seed 15 asserts within it). A grant is never held: the hold is for frontier and `keys.0`-only commits, and no author places a grant's copy but the holder's admins.
- **Uncovering departures**: under a read epoch that does not cover a known departure, a node that may not rotate places only the revokes of departures inside holders of the label's actor that leave its epoch uncovered now, each the whole write on that actor (with its rotation's `keys.0` and `secrets.0`: a reader that syncs the holder waits for every delta of it, so a grants-only copy left the label's admin pending in `link_race`), taking the newest write lowering the departed holder's grant on the actor it left, the last on its chain (not the second hop, which finds nothing two levels down); plus the newest `keys.0` commit of each actor on the chain, projected to that `keys.0` like a chain certificate (not whole: a covered removal that rotated X stays unplaced), with its author's chain. Without those an intermediate rotated apart from the departure write, or M rotated after a self-removal, is unknown to a rotator holding none of its secrets: it seals to the old keyset, which the departed holds, so `rotation_due` refuses and the label strands. They tell the rotators what keeps the epoch uncovered and what to seal to; nothing else goes under it (spec/permissions.md §4 exception). Tests in `core/node/tests/it/revokes.rs` (`nested_departure_*`).
- **Others' cards** (`stale_card`, judged once settled): another node's card entry (only its own `node.0`, `reach.0`, `keys.0`) is outside the required set when a newer valid write of that node on each of those aspects is present at the host in an entry checked genuine (`Engine::latest_by`: the newest applied commit whose delta there is valid, by the given author; `ts` is the author's word, so anyone's later commit on another's card stood for the current one before), or, for `node.0` and `reach.0`, when the node departed: it reads the label's actor no more and an applied write on its way there removed a grant or passed its `until` (its own grant, or one of an actor it reads through: its account's; a departed node is never dialed). "Reads no more" alone misjudged holders whose chain the view lacked, and their cards churned in the sweep (tests `account_removed_node_card_deleted_spec_permissions_4`, `until_expired_node_card_deleted_spec_permissions_4`, `unheld_chain_card_kept_spec_permissions_4`). Its `keys.0` stays: chains of its old writes may need it. Admins (the delete key) delete them.
  - `certificates` never re-places this node's own deleted copy, except its own card while it reads the label's actor (`own_card_read`): a re-granted node whose card an admin deleted places it again (`regranted_node_card_placed_again_spec_permissions_4`). Until both converge on the role commit (an admin that has not applied the re-grant still judges the node departed) the two ping-pong once per pass each.
- Every "newest commit on an aspect" choice (chain certificates, inbox copies) takes the newest valid applied write.
- **Linked blobs**: certificate copies carry the blobs their parts link (`place_linked`: header-list trees such as a demotion's linked frontier) as certificate entries, so a verifier syncing nothing else resolves them. Once this node knows no entry of the copied commit under the label (one placed and not confirmed yet counts) they go (at a host by delete key, by an admin; in this node's store, of copies no host holds, by `local_deletions`, the entry only, the bytes being the engine's), unless another commit entry there links them (`copy_links`, `linked_by`).

## Inbound (`sync/inbound.rs`)
- **Input giving nothing is bounded by the entries carrying it** (spec/requirements.md: peer input never causes unbounded storage; spec/sync.md §3 Unjudged blobs): what a node keeps of input that gives it nothing held (bytes waiting, a pending row, a header kept for a part dropped while invalid) lives only while an entry carries it, and an unvouched entry carrying it counts against the unvouched bounds. One rule, two halves:
  - A pending row (`Engine::pending`: a pending or parked commit, or an applied commit's parts that wait alone) lives only while the node holds something carrying its commit: a label entry of any kind naming it (`Commit`, `Parked`, `Awaits`), an inbox entry carrying it as its commit or in its author's chain (`State::inbox_chain`, memory; every inbox entry is retried at a start, which fills it again), or the newest stranded report (message or notice) on a label naming a current holder, for the holder keys it brought (`State::reported`, memory, one per (label, holder), stale slots dropped at the next report; a node connected to a writer reports by message only, once per step, so without it keys that pend there, e.g. for drift, would be lost: `sync_review::stranded_message_keys_pending_kept_spec_permissions_4`). Carriers are counted per commit (`State::carried`; a commit's blob record, `by_commit`, counts too). `sweep_pending` (each `redeliver`) looks at commits whose last carrier left (`State::uncarried`), commits stored pending since it last looked (`Engine::take_pended`) and, once per start, every pending one, and drops the row of each nothing carries (`Engine::forget_pending`): its parts count as never received, and the next entry carrying the commit brings it back like a first arrival. So what pends never outlives what holds it; a deposit expiring or a flood deleted takes its rows with it. What pends from no carrier goes at once: pairing packages (they come again under the home label).
  - A commit known only for a part dropped while invalid (`Engine::kept_invalid`, durable or memory: its header, so a copy is not taken while invalid and valid again it is fetched; a memory one also while such a part is valid again and not back, `Missing::ToFetch`) is forgotten once no entry of it is known and no delete of one is within its tombstone (`Engine::forgettable`, `forget_forgettable` each Tick). A reader's entry of it goes with its body (present nowhere), so a co-reader peer's flood of invalid commits leaves nothing past the next Tick (`peers_review::reader_flood_of_invalid_commits_bounded_spec_sync_5`).
  - An entry no writer vouched for counts against the unvouched bounds while it gives nothing held (`gives_nothing`: unopened, parked, awaiting, its commit pending, or its commit `kept_invalid`), not only until it opens: `unvouched_cap` per (host, label) and the peer budgets (`peer_bytes`, `peer_total_bytes`, notes/peers.md: rebuilt at open from the entries and their stored source) while at no host. A stamped one is a writer's input, bounded by the host's cap (the bounded malicious writer).
  - New entries from a host that no writer vouched for (no stamp under the head's write key; before a head is known, any step's this node knows: a superseded step's key may be a removed writer's) and that open under nothing held keep no bytes (fetched again once they unwrap, `refetch`). Past `SyncConfig::unvouched_cap` (2^16; inboxes a sixteenth, bytes kept, since an inbox blob opens by its bytes) such entries giving nothing per (host, label) keep not even the presence there, nor the entry once no host has it: one host's junk does not crowd out another's deposits. What a waiting commit's walk reaches (`Engine::blob_wants`: header-list trees, pages, value roots; an applied memory commit's value trees) is kept and fetched whether or not an entry was seen.
  - Past a bound the newest is refused, never the oldest evicted: an evicted entry still at its host would be fetched and judged again at once (a loop), while a refused real one comes back stamped once a writer promotes it, or with a holder's next upload or a replay. Refusals report `DiagnosticKind::InputCapped` (the label and the bound): `unvouched_cap` once per label until a batch there fits again (`unvouched_reported`), a reached peer budget once until pruning frees a charge (`Charges::reported`). Tests: `pending_bound::*`, `peers_review::pending_from_reader_counts_against_peer_budget_spec_sync_5`, `hostile_host::unvouched_invalid_entries_capped_spec_sync_3` (a host's unstamped invalid commits: headers known stay within the cap at n and 10n).
  - Rejected: charging a header kept for an invalid part to the label's ephemeral cap: a reader's flood then fills the cap and blocks writers. Rejected: keeping no header for an invalid commit: valid again (a grant arriving late, a demotion falling) it could not be fetched again, and a host still listing it would be fetched and judged at every pass.
  - Rejected: a new per-label pending cap with oldest-unsigned-first eviction: a number of its own, and the evicted row's entry stays held, so the bytes stay and the commit is judged again on the next look.
- Commit blobs with linked header lists get their prefix checked against the resolved header in the pass (`check_linked_prefixes`, once per blob per run); a disagreeing blob is `Kind::Bad`. Bodies and certificate copies of such commits are classed by the resolved header.
- Blobs are stored by ID; unwrapped with the group's held read secrets newest first, else as an inbox blob for an actor the label is an inbox of (`Engine::inbox_actors`) (the read KEM of each held read epoch); commit plaintexts ingested role commits first; unopened entries retried as new secrets arrive. Commit blobs announced without bytes are fetched at once; what waiting commits lack before apply, and an applied memory commit's value trees at once (`fetch_waiting`: `Engine::blob_wants`, walks the engine keeps per commit and takes on from the blobs arrived, `apply::reach`); the rest lazily (`fetch`, `fetch_missing`, or one value's tree: `fetch_tree(tid, link)` fetches what `Engine::tree_missing` lists, node blobs below held ones and the chunks held nodes list, called again as nodes arrive; osis-commit's `Missing` names no blob, the engine walks the tree instead).
- **Freed pieces** (spec/sync.md §7 Freed links; engine side notes/engine-paged.md Freed links): `freed_now` judges the freed links of some blobs, never the whole set: those the engine judged freed since (`Engine::take_freed_new`, from `forget_dropped`), and in each pass the scope's blobs whose delete is not in flight; at start or a full judgment, every row a page at a time (`freed_sweep`). It drops the bytes of links judged for the first time still held (`keep_salts` first, `delete_blobs`, memory charges released), touches their entries (so the label's next pass has them in scope), fetches the node blobs judgments wait for where present (`Engine::freed_wants`), and lets a judged link no entry names leave the set (an entry removed is touched, so its blob is judged again next pass). A pass deletes each judged link present at its host (`freed_delete`); a local pass tombstones its entries no host holds before its rule that drops unheld entries untombstoned. A judged blob's bytes arriving by any path are not stored (`Engine::is_freed`), nor fetched when announced. The salt and delete keys come from the link, so no chunk is fetched for a delete: only nodes and pages, to walk them. An add whose bytes do not hash to its blob ID is ignored as it enters (`log_events_from`, every source): no other path, and no pass woken (a hostile host answering every fetch so would otherwise ping-pong; the next pass asks again).
- Memory-class and relay-only entries (by prefix class) go to the memory lane (`sync/memory.rs`; notes/ephemeral.md, Memory commits): judged by the pass like durable bodies, with every record about them in memory, never in the sync records or the store.
- **Presence at a peer that cannot read L** (read as a store by its stream: `read_as_store`, a `LabelAt` on the connection, whoever dialed; spec/sync.md §10 At a store): what it holds is the presence rows (`known`), moved by its stream's events (an Added is present there, a Deleted goes through `absent_at`). Everything kept of such a peer (presence, gone and useless-wrap marks, refusals, its head `y/h`, a fill under way, pass ends, registration back-offs, deposits seen) is by `PeerKey`, fixed when the connection's shared set begins (`Conn::peer`): the pair's record where it has one, whichever side dialed, so one peer keeps one set of rows however it reconnects; else, for a node this node dialed that proves no known actor, its dialable key (issues/net-one-peer.md, Interim states, to 6c); else nothing (a dialer keeping no record: no record finds it, and it opens nothing by proof without being known). Rows of a record gone (evicted, `RECORD_BUDGET`) are dropped at the next start (`recorded_peers`, `forget_peer`). The stream position at such a peer is the record's; without one, by the dialed key (`StreamAt` in `state.rs`: the stored cursor, the members in the stream at it, where each that left stopped; `Conn::unrecorded`), and joins go on from there (`stream_join`). Rows keyed by a listed node's address (`passes`, `refusals` for status) are found through `dialed_peers` (the peer key of each node's last dialed connection). A join from the start (`known_join`) clears presence there and lists everything again as a fill; a listing marked `trimmed` (the peer's node log keeps a deletion horizon, the highest dropped deletion event, and answers a cursor below it from the start so marked) also takes what it held there and the listing lacks as deleted there (`LabelAt::relisted`); unmarked, absence proves nothing (a wiped or restored store looks the same) and only presence starts over. Forgetting anything (`forget_lost`) clears every `StreamAt` and restarts every such peer's stream from the start (`stream_restart_known`: no position read there covers what is held now; brute force, rare). Only events move presence: an entry announced without bytes that its fetched bytes show ephemeral (the one class change, durable to memory: `State::reclass_memory`) keeps its rows at the peers connected now as they were (presence, deposited flag, useless-wrap marks), in memory only; the rest go, from the store too (each stream shows an entry once; a row dropped there made its writer put the entry up again every pass while the others deleted it; a reconnect lists memory entries again).
- Presence at a peer comes only from its stream's Added, what it pulled from this node included; a Deposit item's answer marks nothing (a store restored from a backup lost what it acknowledged) and keeps it in flight (`sent`, `RESEND_MS`) until its stream shows it. An Added for an entry already present there with the same wrap and stamp and its bytes held changes nothing.
- A body such a peer announces without bytes (`inline_limit` is 0 while another source tracks the label) is fetched at once if it is a commit blob that opens or a deposit there (unstamped: an inbox blob), as a fill ranks them; the rest (chunks) lazily.
- **Heads at a peer that cannot read L** (`sync/open.rs`; spec/sync.md §5 Opens): a reader Hits the credential of the newest step it knows there (`newest_known`: `LabelAt::head`, the head the peer's stream named or a Behind walk's or a static grant's step, else `label.0`'s newest; `peer_creds`, `test_key`: a step's claim set not held, the claim key the filter shows), a hint's label the held sync key the filter shows (`hint_key`); a walk tests, after the recorded steps' credentials, every held sync key (`walk_candidates`: the peer's head may be a step this node never recorded, made while it was out, whose `label.0` comes only by L, and a Behind walk stops at a step of that gap it holds no credential of), and a Hit by one no recorded step bears opens with no head (`Testing { shown: (None, key) }`), the stream naming it (`new_head`); a new head in the peer's stream moves it (`new_head`: a child or a recorded step; a claim open ends on any new head, a sync-key open on a new sync key (`shared_end`: closed with a Lost, Testing at the new head); a hint's label takes the first head bearing its Hit's key on the peer's word and tests again past it). A head not in `label.0` is the peer's word alone (it may be forged): its child is recorded only under a recorded head (`new_head`), and no step is issued under it (`step_due`). One rule covers every way the peer can move past that head while nothing reads L there (no Head event comes then): once the peer's latest filter was tested and every Offer answered, each label on that connection that is not a member is walked, once per filter arrival (`shared_unopened`). It holds because every move of a head the peer keeps unread changes its filter (`changed_at`), so an arrival follows each move. Rejected: walking once per head opened (on a refused Hit, on a filter not showing the key): a walk at the same head spent it, and a later move left L unread there with nothing to say so.
- **Behind the peer's head** (spec/sync.md §5 Behind): nothing shown at an arrival, a Behind item on the newest step known, by a credential of it (its sync key, else the claim key it opened by there, else its claim keys), asks the peer for the steps after it through the first under another sync key (`behind`, `behind_from`, `behind_answered`, `Phase::Behind`; the exposure rule: notes/label-access.md, One sync key at a time); they verify as a chain from the asked step, the last is the newest step known, and its credential is tested against the same filter: shown it is Hit, else a Behind item asks on by a credential of it, else L is stranded there (`step_known`). One item per sync key crossed, flat in the history before it (`scale::a_catch_up_takes_one_behind_item_per_rotation_spec_sync_5`); a reader not listed at a rotation between (another admin's step made before it knew of a grant) is stranded there until a re-seal. Claims make a reader that missed rotations without their sync secrets catch up at a peer that cannot read L alone (the phone offline across two removals, only a storage peer online: `sync_more::two_rotations_missed_are_crossed_by_a_behind_item_each_spec_sync_5`, a claim's Behind item per rotation), while that peer keeps the steps' claim sets (an admin may drop a set `ROLE_KEEP` after its step was superseded: past that, such a reader waits for a co-reader or a re-seal). Answered 13 the peer does not keep L: the recorded path is registered from genesis; refused (14) on a recorded step, the step is off the peer's path (two admins' concurrent children: `label.0` is a tree, the peer holds one branch), so the nearest recorded step before it holding a credential asks next, each step once per walk (`Phase::Behind`'s `refused`, `asked_before`); refused on the newest step the peer gave, that is its head showing none of this node's credentials: stranded. The walk tests every recorded branch, deepest first (`deepest_first`). A hint's label asks by every held sync key at once, naming no step, and takes the first step on the peer's word (a Hit on its credential is what opens anything); a link's label holding no sync key asks by its key actor's signing key naming no step: answered with the head's entry box and path (a Static item's grant) it reads L from the head, refused it is refused there (`Phase::Failed`'s `entry_refused`, `static_entry_refused`: a used or revoked link fails clearly; the filter not showing the entry cannot say so, a peer lacking L shows nothing either). A stream head past the open head is walked to the same way, L staying open (its answer moves the head). The answers of one Offer read at most `REPLY_BUDGET / MAX_STEP_WIRE` steps, a static grant's path included (what one Shared reply carries; `unread_behind`'s `budget`, `PassStats::behind_steps`): an item reaching it is answered with the steps read, none read 4, and the asker backs off (`refused_for_now`). An Offer of 1024 genesis items reads one step each (`unread::behind_items_on_genesis_read_a_step_each_spec_sync_5`). No Register. Chosen over answering a Register of an old step with its child (it would show L's newer keys to every node that kept L unread, against Tess's rule that metadata stay hidden from nodes that cannot read) and over waiting for `label.0` from a co-reader (a reader whose only online peer cannot read L would stay behind). A Behind item names L and its key: it goes only after the walk at a peer listed for L, which a Register names anyway; naming them keeps the peer's lookup to index reads (`step_with_sync`, `child` per step crossed, the step's held claim set), where an anonymous Hit on an old key needed a table of every superseded key. Exposure is the same for every credential class: only holders of a step's credential (readers listed at it) learn the steps after it, through the next rotation. A live link key is listed at every step: `readers` takes every holder of a read box at the epoch, the link key included, so no rule answers a static entry at an older step for a link still live.
- **Deletes need the open**: the hub session takes a Delete of a sync ID kept unread only on a connection where node sync opened it (`Down::Open` when such a member opens, `Down::Shut` when it closes; the session ends it itself once the head's sync key changes, `still_open`), else Error 8 (`Session::opened`).

- **A dropped body** (`drop_blob`: bytes and key gone, its entries kept shredded with their kind, `Entry::dropped`) takes its bytes from nobody and no stream owes it (`wants`): a fetch asked before the drop may still answer. Fetching it again is `Unknown`'s (`reopen_undropped`, `reopen_awaiting`). An entry opens from what is here only with its bytes held and its wrap kept (`opens_here`): a shredded one is fetched under its own label even when another label's entry of the same blob brought the bytes back (the wrap comes only with that fetch). Every "held, so open it, else fetch" choice (`refetch`, `reask`, fills, `wants`, `fetch_missing`) and what a stream serves (`stream_added`: a shredded entry has no wrap to show) reads `opens_here`, never the bytes alone; a fetch for it goes under its own label.

## Label states at a peer's connection (`sync/conn.rs` `Phase`; spec/sync.md §5, §10)
One `Phase` per (connection, label), its data inside it (`LabelAt`: on a connection this node dialed, for each label naming the dialed node; on one the peer dialed, for each label it opened by proving its sync secret, always `Open` (`member_proved_there`), gone when it closes, nothing walked or Behind sent there: notes/peers.md Connections at the hub); `LabelAt::head` is the newest step known there in every phase. `Open` exactly while L is a member of the connection's shared set: `shared_open` opens it from any phase (`member_unread_there`), `shared_close` is the only way out (to `Testing` at the newest step known, walked from the next filter arrival: one follows the move or judgment that closed it). Each state and what always comes to move it:

| Phase (data) | Leaves by | Trigger |
|---|---|---|
| `Testing { shown }` (the key the walk found shown, and its recorded step: none for a held sync key no recorded step bears) | Hit taken: `Open`; walk: `Behind`, `Registering`, `Failed` (none shown and no credential of the newest step known: `strands`); the shown key's Hit refused: walks on at once | each filter arrival; `resync_ms` after its last walk (`timers`) |
| `Registering { path }` (steps not answered) | last taken: `Testing`; 9: next step, or `Behind` past a genesis, or `Failed`; refused for now: `Refused` | the Register answers |
| `Behind { refused }` (steps refused this walk) | steps: `Testing` at the last (`step_known`); 13: `Registering`; 14: an earlier step, or `Failed` (stranded) | the Offer's answer |
| `Open { by, doubted: None }` (the key it opened by at a peer that cannot read L) | a head past `by` (`new_head`, `registered`, a Behind answer: `open_moved`, `shared_end`), a Lost, a judgment: `Testing`; its child refused (not for now), or a stream head neither its child nor recorded: `doubted` | the peer's stream and filter, the Register's answer |
| `Open { by, doubted: Some(head) }` (the peer refused a child of the open head, or named a head off it) | Behind steps: their last is the head (`open_moved`); 14: Behind on the nearest earlier step with a credential, each once (none left: stays, registering nothing); 4: a child again after a back-off; the stream moving the head ends the doubt; else as `Open` | the Offer's answer, the stream |
| `Failed { entry_refused }` | started again | `resync_ms` (`timers`) |
| `Refused { retry_at }` | started again | `retry_at` (`timers`) |

Sibling steps of two admins share their keys, so a Hit opens at whichever sibling the peer holds while the walk assumed its own branch's step: the open head is provisional, and the peer names its step by the stream's head event or by Behind answers walked back from a doubted head. A doubted head registers nothing (`reregister` checks `doubting`), so no child is re-sent without the head moving; a Behind answer while open counts only for the doubted head (any other crossed the open or a head move). Rejected: leaving `Open` on a 9 (to `Testing` or `Behind`): `Open` is membership, and L is open at the peer whatever its head.

A child step in flight (`LabelAt::registering`) outlives the open: answered taken it is recorded and the head moves; refused in any phase it is dropped (`refused`), else a label closed with one in flight is never walked (`shared_unopened` and `timers` skip it). Rejected: the walk's step, the opening key, the shown step and the refused steps as fields beside the phase: (`Open`, not a member) and (`Testing`, a member) were reachable and neither moved (sim `member_churn`).

## Complete passes and pass records
- `SyncEngine` implements flows' `SyncState`. `complete_pass` (spec/permissions.md §3) is judged from the labels' actors and pass ends at their hosts and at the sources it received the label from that still read it, connected or not (notes/peers.md Complete passes; a push run counts as one). A live subscription only shows its end by a push, so a remote role commit asks for one: at the end of the step, each host of the actor's labels (`synced.by_actor`) whose last pass end there came before the commit gets a Sync from the cursor if the label is open, synced and not syncing (`ask_pass_ends`). A Sync sent before a role commit of the label's actor applied (`LabelAt::sync_seq`) ends no pass: its end asks again (`synced`). The host may have answered it before it held what came before the commit there (a removal's rotation, uploaded with the removal that reached this node by a co-reader), and a request sent after the commit reaches the host after all of that. Its cost: one more round trip after a Sync whose own pages brought a role commit (a first sync of a label with role commits not held). Passes go on while it runs (`LabelAt::ending`: the label was at its end before), so a slow reply holds no upload. A commit that came by that host's own push already has its pass end, so only commits from elsewhere (an inbox, a Deposit item, another host, a co-reader) cost a Sync: one round trip, O(labels of the actor). A Ping was rejected: a host answers it at once, ahead of pushes held for flow control. Peers are waited for at most `peer_pass_wait_ms` (5 min) after the actor's last remote role commit (`role_change`, memory only; from the engine's start, `started`, when none applied in this run: a restarted node hears its peers out first); a label with no host and no such peer, served here alone, passes once that wait is over, and its local pass decides re-seals. `passed_since` (untie) reads the same `label_passed`. Co-reader details: notes/peers.md.
- **Failed writes**: node sync starts again from the store as an open does whenever a store write failed (the engine's or the hub's `Store::writes` counts a new failure, checked once at the end of `handle`, whichever path met it): `restart_in_place` closes every connection and runs `start`, the one place `new` sets every field (all but the engine, its subscription, the generator, the config, the hub's store, the host config, connection IDs, untaken diagnostics and the restart bookkeeping; `start` destructures every field, so a new one must be placed). A restart waits until either store has taken a commit since the last one: a dead device only fails again, and restarting on each failure looped (every restart's redials failing anew). What a failed step had taken in memory (stream positions, entries taken, bytes not stored) is fetched again on the new connections (node `nodelog::a_failed_write_taking_bytes_needs_no_restart`). A write whose sync failed is the same: the store recovers in place on its own (notes/local-store.md, Failed writes) and the restart comes with its first commit after (`nodelog::a_failed_sync_taking_bytes_needs_no_restart`). Failed steps whose error is the store's report `DiagnosticKind::Storage`. The sims' link faults reconnect often enough that a node left stuck this way recovers anyway: a sweep with the restart off passes, so that test is the guard.
- Pass records (`SyncEngine::passes`) outlive the connection: `complete_pass` and link finalization read them as "a pass ended after X" (X = the actor's last remote role commit, or the link's `until` by wall time), which a pass from before going offline still proves; anything newer under the actor arrives as a remote role commit and restarts them. The only loss is the race any pass has (a box written right after its end: a duplicate re-seal, one box). Clearing them on disconnect would stall re-seals and finalization while any of a label's hosts is down. An expired link whose K labels list only `peer://` addresses is finalized at once by its maker, as with none.
- Pending role commits' boxes are opened read-only (`apply/keys.rs::read_pending_boxes`).

## Requests and driver
- App and flows requests (`sync/local.rs`): `compact` (a snapshot, then drop covered bodies this node may purge past keep-at-least; deletions follow once the snapshot is at the host), `place_certificate(g, commit, aspects)`, `deliver_inbox(recipient, commit, aspects)` (deposited at each inbox host on the next connection), `complete_pass(actor)`, `sync_now`, `export_bundle`/`import_bundle`.
- Driver (`sync/driver/`, feature `driver`, default): `run(sync, transport, clock, control, log)` = `run_serving` with no listeners; `run_shared` drives an engine a `Shared` owns (the osis handle). Per `Dial` a task `link::dial`s (the dialable key for a co-reader's node, `Action::Dial.dialable`, else ephemeral) and hands the link back; up, it becomes a hub session (`HubRun::dial`) and the engine gets `Event::Up`; `Action::Close` abandons a dial not up yet. Each listener's sessions (`link::serve`) go to the hub under that listener's key (`HubRun::listen`, notes/serving.md). `Control::{Local, Tick, Call, Apply, Reach, Socket, Listen, Lan, LanRejoin, PeerKeys, Shutdown}` (`Socket` and `Listen`: notes/client-port.md §5; `Reach`, `Lan`: notes/peers.md); `Action::Host` starts, changes or stops the hub it drives in the same loop (`driver/hub.rs`, notes/serving.md). Engine calls run under `block_in_place`.
- Tests: default tests on `InProcess` through one node's host (its own copy over the loopback, its self-dials cut), and peer to peer over `P2p<MemUdp>` on the NAT model; by hand (ignored) on localhost QUIC and P2P, the LAN loop (`lan`) and a relaying node.

## Handed-off groups (`sync/handoff.rs`)
- The mechanism of osis `group_source`: a group whose calls go to another node is handed off here (`SyncEngine::set_handed_off`, record `y/w`; set as the source lands, cleared before the move home catches up, so every handed-off group has a source node). It is left out of `labels()`, so nothing of it syncs, is served, or gets passes, certificates (`deliver::groups_holding` skips it) or step records; what was stored stays, stale (`Engine::readable_by` denies what is routed away to clients). `untie_unplaced` skips a pair whose target, group or removal scope meets a handed-off group (left to holders). osis status and `wait_synced` leave it out.
- Checks: `sync::removal_from_partial_node_keeps_unheld_edits_spec_permissions_5_2` (the phone places nothing under a handed-off group's label while it removes a writer), `tied::scope_handed_off_left_to_holders`, `sources::status_shows_a_group_as_its_source_does`.

## Junk copies (`SyncEngine::redeliver`; spec/commits.md §4 Copies)
- A pending commit's slot and signature keep their first copy; a junk one proved names the commit (memory only; `name_after_crash` looks at what a crash could have lost, once per start: what pends, commits neither applied nor pending, applied ones with an entry on an aspect they miss), and node sync ingests its entries that bring an empty slot, label ones and inbox ones (not a declined invite's), skipping those `genuine` judged false.
- A slot counting as never received (`Engine::settled_slots`: body dropped, part past its expiry) is not brought back: only a new copy does that, or a restart would change what a node reads. A copy with a junk part or signature is no source even for its true parts: a sender holding the true part could withhold it anyway.
- Limits: a true copy deleted from every host while junk holds the slot waits for a holder's new upload (keeping such copies while the commit pends would let one sender grow one commit's copies by flood-and-delete). The start's look costs a read of each such commit and a look at its entries, per start, not per event. A visit bound hit keeps the name for the next step (from reading: reaching it takes a chain of records inside one round; no test).

## A listing from the start: newest first (spec/sync.md §6)
- Why the wrap carries the order: hosts must not tell blobs apart, and a blob's header sits in its ciphertext, so for a chat message the header is the whole body. A wrap is listed for free and opened by readers only, so 8 B of order there beat a host-visible class, a separate label for role commits, or reading the log from its end (role commits sit anywhere in it, so a newest-first log read cannot stop early). No host change. A writer's lie only moves a blob in the liar's readers' queues: a flood marked 0 delays the newest page by its size (a stated limit, not defended).
- Priority, not partiality: everything is fetched, so "not fetched" needs no meaning beyond "not received", and no aspect is special: a state-reading aspect reads partial during the fill, and a recent snapshot helps it. The price is listing every entry (about 160 B each; on the dev box 115 us each, most of it the stamp's signature).
- Order 0 covers a purge request too: a purge names only commits with a smaller `ts`, so newest first brings it before its targets anyway, except a target that is itself order 0 (a thing's first message). A thing per item (not a chat's one long aspect) makes most commits order 0: that workload fills in log-like order.
- As built (`sync/fill.rs`): a join from the start at a peer that cannot read L lists by the stream (announcements only while the listing is under way, `stream_inline`), and `LabelAt.fill` holds the queue and the batch asked (in `Requests::fetching` for its truth); `y/4` marks (host, label) so a restart or lost connection rebuilds the queue from the entries. The listing's end is the stream reading L to the peer's end (`fill_listed`, from `stream_read`); the fill's end is the pass end there (`stream_read`) and the stream's bodies come inline from then on. No pass of the label runs while some connection's fill has not got past order 0 (`fill_first_waits`: a pass would ask what it lacks at once, out of the fill's order), and the lost-access trigger waits likewise (`fill_before_passes` in `drop_lost_due`: a role commit from the first batch must not judge before the rest of order 0, which re-ranks once its secrets arrive). A fill asks its next batch once the last is answered (the peer answers in order), and passes wait on that batch only while it counts as asked (`asked`: under `STALL_TIMEOUT_MS`; a wake then, `settle_by`, sets `first_done`), so a peer trickling its reply holds the label's passes for the stall time only, and what it lacks is asked elsewhere (`refetch`). Rejected: the fill asking its next batch past a stale one (it waits behind the trickled reply). `idle()` and `bump_pass` wait for the end. `mark_dirty` leaves a filling label alone: passes come at `resync_ms`, on an own write, and at the end. Entries that do not open are fetched too (`drop_unvouched` judges them on arrival): those the peer holds deposited (unstamped: inbox blobs, so a new device's waiting invite) right after order 0, the rest (chunks, epochs not held) last. The deposit budget bounds the first kind whatever the label holds. Rejected: what does not open first at an inbox label: a wrap cannot tell an inbox blob from a chunk, and every group's home label is its inbox (notes/permissions.md, One inbox rule), so a chat's files came before its newest messages. Limit: a handled inbox blob is stamped, so it comes last; its grant comes as its order-0 copy, except one accepted with under `INBOX_COPY_MIN_LEFT` left (no copy).
- Limits: a join from a stored position brings what came since in log order, bytes inline: a node back after a long time gets no newest-first (only a join from the start fills; issues/partial-history-fetch.md). Order 0 goes in batches of `fill_batch` in ID order, so a commit there can await a record a later order-0 batch brings: an entry woken while its label fills goes back into the fill's queue at its rank (`reopen_awaiting`). An entry a fill passes over while its fetch elsewhere counts as asked (`may_ask`) goes into `Fill::skipped` with its rank and back into the queue at the fill's next batch once that fetch counts no longer, so a peer trickling it holds it the stall time and one batch of this peer. A fill ending with entries still skipped leaves them to `refetch`. Rejected: leaving skipped entries in the queue (a fill with nothing left to ask but others' fresh fetches would wait on them). A compaction part way is safe: a snapshot's frontiers stop at the first gap, so it covers nothing it has not got.

## Simulator hook (core/test/sim/src/net; notes/test-sim.md)
- `SyncEngine::new(engine, rng, cfg)` (the engine's clock is the node's), `Event`s fed (`Up` on a `Dial` once its link is the node's hub's `Hub::dial` session, `Hub` with what each hub handed up, `Tick` at `Wake`), `Action::Hub` to the node's hub, the hubs' bytes between them; `is_idle`, `describe` (head per label), `take_diagnostics`, `entries(label)` and `verdicts(host, label)` (the pass's must-hold bodies, deletable must-not-hold entries, unsettled aspects) for invariants. tests/it/net/mod.rs is a minimal version of that driver.
- A connection it closes gets nothing more, queued or held back (`Net::forget_conn`); messages to a node carry its `life` (restart count) and one from before a restart is dropped: a restarted node numbers connections from 1 again, and a stale host Hello on the new connection broke every request there (`random_window_inflight` seeds 3300065, 173899; the sim keys by link id and cannot have it). The node ignores a second Hello (a broken frame), so it stays stuck on such a connection; a real transport never delivers an old connection's bytes on a new one.

## Invariants the simulator established
Each is a rule the code keeps; breaking one brought back churn or a stuck node. Most sit with their subject: heads (notes/label-access.md, node sync), promotion per host and durability of the outbox (notes/inbox.md), compaction agreement and carriers (notes/sync-convergence.md), requests in flight and wakes (notes/flow-control.md, notes/node-sync-work-sets.md), entries, certificates and presence (above). Also:
- Own dots are written under a zero commit ID placeholder from the start (`own_source`), so the writer's own source sorts above foreign dots (spec/crdt.md §3.3 rule 2).
- Clock: every node runs on its own wall clock; nothing a peer sends moves it, so a wrong clock harms only its holder (spec/requirements.md): fast, its writes park elsewhere until real time catches up; slow, it parks others' writes and its own sort early. A node's own commits (`Origin::Local`, a held key actor's included) are never refused for drift: its HLC may run ahead of a clock set back. `estimate_offset` (samples with a round trip over 10 s ignored) feeds only the `ClockSkew` diagnostic.
- Rejected: correcting the clock from peers' offsets (a median, a cap, a quorum, own nodes first). Any correction lets other nodes move this one, and each bound needs picked numbers and special cases (one connection, one peer on two connections, an own node with a dead clock battery).

# Frontier study: compact frontiers considered and dropped
> Summary: What a demotion's frontier lists. Decision (Tess): commit IDs only, one system for every retention: the demoted node's received commits except those the demoter's compaction could drop now (built; notes/permissions.md Revocation). On kept history that is every kept write, a stated limit (spec/requirements.md Cost). Kept here so nobody redesigns it: why no compact encoding is safe where bodies are dropped, the heads-and-links design for permanent history that was dropped, other rejected encodings, and ID batches, the fallback if kick costs ever hurt.

## Requirements the frontier meets together
No clobbering of kept history (a snapshot carries live content only, so leaving out a covered commit made its superseded writes invalid for good, and any writer could write that snapshot just before a kick); a kick's cost bounded by compaction cadence and retention, not by total history where history is not kept (Tess); validity a function of the held set; a removed writer cannot forge into counters it once used (Tess's decision: IDs, never counters); the author's own `ts` never decides; new nodes never fetch compacted headers and nodes forget them.

## Why no compact frontier exists where bodies are dropped
A compact frontier bounds each source (counters or chain heads), and a bound is safe only if every commit under it stays detectable: a forged commit re-signed on counters whose original every node has forgotten is indistinguishable from the original. Headers are forgotten exactly where bodies are dropped (compaction, expiry, keep-at-most, purge residues dropped as covered). So there the only unforgeable encoding is the commit-ID list, and the honest list is the uncompacted tail plus the keep-at-least window; the demoter can compact first to make it about empty.

Where bodies are never dropped (history kept forever, no expiry: **permanent** deltas, spec/commits.md §5), every header is held by every node forever, and a re-signed commit on used counters meets its original and both void (spec/commits.md §4), so bounds would be safe. The one leak is purge, closed by lasting headers: a purged permanent delta leaves its commit's header at the label for good (about 300 B; Tess: "if history is on, the cost of keeping history is expected"). The purge commit naming it stays too, else a new node never applies the header-only blob.

## Dropped: heads for permanent history
Designed and dropped for one system of IDs. A header field `prev` on a session's first delta per aspect named the node's newest earlier commit there (its predecessor sessions); a frontier could carry, per aspect whose received deltas were all permanent, a **head** `(tid, ak, session nonce, ctr)` per unreached session, covering every write reachable through held links at or below the bounds. Cost would have been about 60 B per permanent aspect a removed node wrote, against 32 B per kept commit by ID. Tess accepted `prev` in principle, under the growth rule: no per-session growth where there would otherwise be none (notes/growth.md). Points a rebuild must keep: a mixed aspect (some deltas not permanent, keys before a `required^.0` setting included) falls back to IDs; the removed-author check must not read "the frontier omits the commit" as final while a link is not yet held (it releases a commit for good); purge requests are judged by commit, not by aspect, so a head on `purge.0` or a request's own aspect is possible only where every request there is permanent; the request fitting keeps working on what is still by ID.

## Other encodings rejected
- One chain per session across all aspects: a verifier under label L sees only headers touching L's closure, so the chain from a head back to a commit passes commits it cannot see.
- Per-(aspect, session) counter bounds without links: sound for permanent deltas, no header change, but one entry per (aspect, app launch that wrote): for one message per launch, one per message.
- Chains or bounds on compacting aspects: forgetting and new nodes leave gaps wherever a later session's commits were dropped while an earlier one is kept; an honest write then reads as uncovered (clobbering, narrowed). Closing the gaps needs drops in chain order plus exclusions.
- `ts` against the cutoff, sessions bounding the lie: a session gives counter order, not time; a removed node appends to its last received session with any `ts` up to the cutoff. Tess rejected `ts` rules.
- Set hashes or accumulators: a verifier needs a membership proof per commit, which the kick would have to produce per surviving write.
- Per-node counters continuous across sessions: needs a per-node source kind, and a restore before sync voids both the old and the new writes instead of orphaning them until healed.

## Fallback: ID batches (Tess's idea)
For when measured kick costs hurt. A **batch** is an object listing commit IDs; a frontier may name a batch by its hash in place of the IDs in it. Anyone may write one, the author included: the frontier fixes it by hash, so a batch written later is simply not the one named (no counter, contiguity or kept-header argument). Batches can name batches. It is the ID frontier plus "a hash stands for its IDs", so coverage rules stay. Costs: about one extra ID per commit while that commit can matter to a kick (batches are kept as long as a kept frontier names them); receivers fetch named batches before judging. Open: who writes batches and when (the author per aspect at compaction or every N commits is simplest), where they live (under the aspect's labels like any commit), how a kick picks batches it received whole.

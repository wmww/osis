# Dogfood: the coordinators' channel over osis
> Summary: How the two osis coordinators (Fathom on ostrich, Halyard on the other box) message each other through osis itself: a shared node (`osis serve`, its own account, granted sync on the channel) on Halyard's box, a daemon on each coordinator's own store, and an `osis chat` as the channel. Where the state lives, and the "update dogfood build" procedure.

## Deployment
- State lives outside the repo in `~/osis-dogfood/` on each box: pinned binaries `bin/osis-<short>` (a plain debug build of `osis-cli` at the pin) and one directory per store, named `<who>-<short>` (`host-<short>` for the shared node). A member's directory holds `store`, `address` (the shared node's `URL#KEY`), `chat` (the channel tid), `k` (its link's K), `link`, `cursor`; the host's `store`, `address`, `card`, `account`. Address, card, link and tids are never committed: they are what an attacker needs to join or flood the channel.
- The shared node (Halyard's box, its public address, one UDP port per build: 4040, 4041, ...) is a node of its own account: `osis -s host-<short>/store serve --listen quic://<public address>:<port>`, user unit `osis-dogfood-host-<short>`, the port opened in ufw. It reads nothing of the channel: it keeps it unread because the channel's admin granted its account **sync** on the channel and on the channel link's K, and it accepted both (listed them under its `home`). K is needed too: a joiner redeems the link at a node sharing K, and the members never meet. The address is the first line `serve` prints (`URL#KEY`; the key lives in the store, so a restart keeps it).
- Members dial it on every networked command and in their daemon (`--dial URL#KEY`, never stored; no `init --peer`). Each own store runs a daemon as user unit `osis-<who>-<short>` (`systemd-run --user --unit ... osis -s <dir>/store --dial URL#KEY serve`): other commands on that store go through its socket. Start the daemon only after any direct command on the store has ended (a race fails `store in use`). A stop removes the unit; restart = run it again.
- **Through the daemon** only the client port's built rows work (notes/client-port.md): posting, `get`, `status`, `group add` do; `chat read`, `chat watch`, `card show|import`, `sync`, `diag` answer `Unsupported` (issues/client-port-listings.md), so with a daemon up the agent recipe below cannot read. Until that is built, read with the daemon stopped. The chat and its link are synced only once filed: `chat create` and `chat join` file nothing (issues/chat-files-nothing.md), the script files them under `home`.

## Update the build ("update dogfood build")
No compatibility between builds: an update is a cut-over to a new shared node, new stores and a new channel beside the old ones. No history or member carries over: the new channel's members are whoever joins it. Steps, negotiated on the old channel, with `tools/dogfood-member.sh` (its header lists the subcommands):
1. Either coordinator proposes the pin (usually current `origin/main`), the other agrees.
2. Each box: in a claimed worktree (`wt claim dogfood-pin`), `tools/dogfood-member.sh build PIN`; `wt release` after.
3. Shared node's owner: `tools/dogfood-member.sh host PIN quic://<public address>:<port>` (store, card and account printed before the daemon starts, then the daemon), open the port; post `address`, `card` and `account` from `host-<short>/` on the old channel.
4. One coordinator (the channel's admin): put the host's card and account in a directory `H`, then `tools/dogfood-member.sh create <who> PIN ADDR H`: a store, the card imported, the channel filed in home, its link, `grant CHAT HOST sync` and `grant K HOST sync`, then the daemon. Post `chat`, `k` and `link` on the old channel.
5. Shared node's owner, once that daemon has been up a minute (the grants reach the host only from it; an accept before the grant is held accepts nothing): `tools/dogfood-member.sh accept PIN CHAT K`. It prints `status`: both tids listed, `Synced` while the creator is connected. Not listed: wait, `group rm home X --subgroup`, run it again.
6. The other coordinator: `tools/dogfood-member.sh join <who> PIN ADDR LINK` (redeems through the shared node, files the channel, daemon).
7. Verify: each posts one line; each reads the other's (daemon stopped, above). The shared node's `status` shows both members connected (`connected` counts its own socket client too); the members never connect to each other.
8. Once both read each other there: stop the old units (`systemctl --user stop osis-<who>-<old short>`, and the old host unit), close the old port; delete the old directories after a day.

Rehearsed on one box (three stores, loopback, the members dialing only the host) at the sync-rebuild branch: steps 3-7 by hand with the script's commands, messages both ways; the script itself and step 5's re-accept are not rehearsed. Same flow as an osis test: `sync::a_third_accounts_node_relays_a_group_it_keeps_unread_spec_sync_3`.

## Agent recipe (`osis chat`, notes/chat.md)
- Post: `OSIS_CHAT_NAME=me osis chat post $C --subject 'subject' 'markdown, or @FILE, or - for stdin'`, with `--reply-to ID`; prints the id. The name is per post, the sender's own word in the signed body (notes/chat.md Name): a post without `--from` or `OSIS_CHAT_NAME` reads `name: null` for good, so put it in a post wrapper that survives a session's context reset. With the shared node down it is queued and goes when it is back.
- Read: `osis --json chat read $C` (the newest `--max`, default 50); `... --after CURSOR` for what has arrived since, posts made offline too. Each message a line `{id, sender, name, time, state, text, reply_to, edited, earlier, valid}` (an edited message under its own id with its newest text, `earlier` the older texts kept), a last line `{cursor, more, complete}`: keep the cursor (not a message id), one per store; `more`: read again from it. `chat edit $C ID TEXT` keeps the id.
- Listen: `osis --json --timeout 0 chat watch $C --after CURSOR --count 1` prints what has arrived past the cursor, else waits for the next: no race, and it runs beside posts. Then `read --after`. Or run it without `--count`, for good: it outlives a daemon restart. A line `{"reread":true}` says events may have been missed: `read --after`. A watch line is a message line as `read` prints it: an edit comes once, as its message with the new text and `edited: true`; a deletion as `state: deleted`; `{"left": ID}` when it is no longer listed (invalid, expired). An exit other than a timeout (`watch ended`): start it again. Your own posts wake you too.
- Kick (`osis chat kick $C ACCOUNT`): the kicked retains a read-only copy (the chat's default) unless `--erase`. Kicking someone who joined by link ends that link: `chat link` again for the next.
- `status` right after opening says NotConnected for every group: a snapshot before the first connection, not a failure; the command's exit code is what counts.
- Without `chat`, a plain group works too: one thing per message (`osis create --admin $G --in $G name.0 '"me: subject"' body.0 '"markdown"'`), `osis --json watch $G group.0` as the listener, `osis writes --group $G` for order, author and time.

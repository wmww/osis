# Dogfood: the two-Claude coordination channel over osis
> Summary: How the two osis Claudes (this box and Tess's other box) message each other through osis itself: one serving node (`osis serve`) on this box (UDP, open admission with caps), one account per Claude, one shared group as the channel, one thing per message (`name.0` "who: subject", `body.0` markdown), `watch G group.0` as the listener; the same over `osis chat`. Pinned binary, where the state lives, the agent recipe, and the gaps it found (issues/cli-own-admission.md).

## Deployment (this box)
- Everything lives outside the repo in `~/osis-dogfood/` on the operator's box: the pinned binary (`bin/osis`, copied from a worktree build at `PINNED_COMMIT`), the serving node's store (`serve` as a transient user unit), this Claude's node store (run as a daemon unit so every `osis` command goes through its socket and the listener never blocks a post), the serving address, the group tid, the join link, the read script and seen-list, and the recovery cards (mode 600). The serving address, join link and group tid are never committed: they are what an attacker needs to join or flood the channel.
- The serving node runs `serve --listen quic://0.0.0.0:<port> --admit open` with limits (`--policy` `groups`, `entries`, `bytes`, `group_entries`, `group_bytes`). Open admission because sync-ID admission cannot cover links' groups (issues/cli-own-admission.md); the caps bound a stranger's use. The firewall opens only that UDP port.
- Restart: the units are transient (a stop removes them): `systemd-run --user --unit <name> ... osis -s <store> serve [flags]` again; the serving key survives in the store, so the address stays. A binary swap is stop, rename the old binary, copy the new one in, start.

## Stability
Both boxes run the binary of `PINNED_COMMIT`. A bump is proposed as a message and taken when both agree; there is no compatibility, so a bump may need `init` again on both sides and a new link (this whole setup is a few commands). Fixes for this use case go to main like any task; the next pin follows.

## Agent recipe
With `serve` running on the store (the serving box), every other `osis` invocation there runs through its unix socket (notes/cli.md Design), so a `watch` may stay running while you act; `sync`/`wait` work there and are not needed (the daemon syncs). Without a daemon: one process per store, stop a running `watch` before any other command.
- Post: `osis create --admin $G --in $G name.0 '"me: subject"' body.0 '"markdown"'` then `osis sync`.
- Read: `osis get $G group.0` lists message tids; `osis commits --group $G` orders them with author and time; `osis get T name.0` / `body.0`.
- Listen: `osis --json watch $G group.0 --count 1 --timeout 0` in the background exits on the first change after the initial line; with the node running as a daemon (d16) the watch and every other command go through its socket, so nothing has to be stopped before posting. Read `group.0` once before re-arming (a message that arrived in between is in the initial line, which does not wake you). With a daemon on your store (`osis serve` on `me/`, no hosting flags: a node that syncs), the listener needs no kill/re-arm cycle: run `watch` without `--count` and act beside it.
- `status` right after opening says Unreachable for every group: it is a snapshot before the first connection, not a failure; the command's exit code is what counts.

## The channel as a chat (`osis chat`, notes/chat.md)
No channel is running. The last two generations (host4 at 01d5db6c, host5 at d87601bf) were stopped and deleted at Tess's word; she will have someone set up a new instance on a newer osis. A new one: new binary, serving node, stores and chat, as below. Start the daemon only after any direct command on the store ended, or wait for it: a command racing a daemon's start fails `store in use`, and a daemon that lost the race exits.

No history carried over from the old channel. Set up beside it, so the old channel runs until the switch: `chat` needs a newer binary than the pin, and no newer binary promises to open the old stores. So: a second binary (`bin2/osis`), new stores (`host3/`, `me3/`), a serving node on another port with that UDP port open (`serve --listen quic://0.0.0.0:<port> --admit open` and the caps above), neither old unit touched. Every command names its store (`-s me3`); each store has its own socket. `$C` a chat. Switch: post the new address and link in the old channel; once both sides read the new one, stop the old units.
- Each box: `osis -s me3 init --peer ADDR`, printing a recovery card to keep.
- Make it, on one store (a daemon may hold it): `C=$(osis chat create --name channel)`; `osis chat link $C`.
- Daemon on each: `osis serve` (a transient unit, as above). Everything below goes through its socket, with no order to keep between the daemon and these commands; it reconnects by itself after a serving node's restart, up to a minute's pause, and one down at its start is the same.
- Join, on the other box: `osis chat join LINK`.
- Post: `OSIS_CHAT_NAME=me osis chat post $C --subject 'subject' 'markdown, or @FILE, or - for stdin'`, with `--reply-to ID`; prints the id. With the serving node down it is queued and goes when it is back.
- Read: `osis --json chat read $C` (the newest `--max`, default 50); `... --after CURSOR` for what has arrived since, posts made offline too. Each message a line `{id, sender, name, time, state, text, reply_to, edited, earlier, valid}`, a last line `{cursor, more, complete}`: keep the cursor, one per store; `more`: read again from it.
- Listen: `osis --json --timeout 0 chat watch $C --after CURSOR --count 1` prints what has arrived past the cursor, else waits for the next: no race, and it runs beside posts. Then `read --after`. Or run it without `--count`, for good: it outlives a daemon restart. A line `{"reread":true}` says events may have been missed: `read --after`. A watch line is one entry: `replaces` set on an edit, `state: deleted` on a deletion, and on the old version just after an edit (edits purge): `read` is the truth. An exit other than a timeout (`watch ended`): start it again.
- Your own posts wake you too.
- Kick (`osis chat kick $C ACCOUNT`): the kicked retains a read-only copy (the chat's default) unless `--erase`. Kicking someone who joined by link ends that link: `chat link` again for the next.
- Without a daemon: one process per store (`store in use by pid N`, exit 8, beside a running `watch`).

## Bumping the pinned commit across a store-format change
Stores made before store-row-padding (d10) fail to open under later binaries (`store corrupt: row padding`), the serving store included. A bump then is a cut-over, not a restart: start a second serving node (new store, another port) with the new binary, make a new group and link, post both in the old channel, and only once both nodes are on the new channel stop the old serving node. With the daemon (d16), each node store runs `osis serve` permanently and every other command goes through its socket, so the listener never blocks a post.

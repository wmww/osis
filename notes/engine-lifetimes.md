# Engine: lifetime judgment
> Summary: How the engine judges thing lifetimes and releases (`retention/lifetimes.rs`; the writer's checks; design notes/lifetimes.md, oracle held-model `lifetimes`): known/destroyed/unknown, the walk, the work list and `pending` as local rows, what queues, the release request as a purge of the creation, the keep rule and forgetting at the request's expiry, evidence under the labels of what needs it, the engine API and sync's trigger when heard out.

## Principle
A walk reads only the current held state, so a release never rests on a queue or a cache: a missed queue only leaks. The kept state is three local row sets: `lw/` (work: things a change touched), `lh/` (held: their walk read a thing not heard out) and `lp/` (pending: judged unreachable, not destroyed here: right not held, or its release request not applied yet).

## Reading
- Status (`lifetimes::status`): destroyed (`Core::destroyed`, or released earlier in the run), known (`exists`, a minting held, a held path reads it: `forget::read_path`, which a kept copy fails), else unknown. An unread thing is never known: lost access, a kept copy, certificate and chain parts all leave its `created.0` held with no reference rows, and read as known it would release what lists it (invariant at `status`).
- List: `retainers^.0` read whole as `set<tid>`; absent or not a set of tids: standalone (kept).
- References: the reference index (notes/engine-refs.md): a durable row from R to X other than `retainers^.0` (`refs::references`); listers: X's `retainers^.0` rows (`refs::listers`).
- The walk (`walk`, as held-model `walk`): up the list through known retainers referencing what is below them; unknown or standalone: kept. A pending thing is walked through, never read as failed: `pending` is stale for a thing the same run made reachable (held-model `a_stale_pending_thing_is_walked_through`).

## Queueing
Only a known thing is queued; a thing turning destroyed or unknown loses its `lw/`, `lh/` and `lp/` rows.
- `refs::note`: a durable reference row appearing or going queues its target; any join or rebuild of `retainers^.0` queues its thing.
- `atomic::learn_record`, `destroy::apply_destructions` (destroyed or fallen), `forget::forget` (lost): the thing and its listers, read from `node/refs to` filtered by AK: O(rows naming the thing). Also paid when a thing's judgment flips (`below`).
- `update_timelines` sets `Core::lifetimes_rights` (also set at open): the next judgment re-judges every pending thing (a right may have come). Brute force: O(pending) per role timeline change.
- An index rebuild (`refs::write_all`) queues every referenced target and every list: rare, brute force.

## The release request
- A commit of `released.0` deltas alone (`timestamp`, fixed retention `author_or_admin`, no history), one per thing (so an evidence copy names only its own thing), no purge field, `expires = wall_ms(ts) + ROLE_KEEP` (`Header::validate`, `osis_commit::retention::release_expires`; `write_expires` gives it).
- **One destruction path**: `Header::requests()` reads it as a purge item on `created.0` of each such thing, and every reader of a request goes through it (`purge.rs`: `names`, `note_requests`, `apply_request`, rejudging, `requests_resting_on`; `destroy::per_minting`; `View::purges`, fetch order, addenda's plain commits). So validity is the purge right over each minting (`holds_right`, the destruction's cut included), the minting goes value-less, `destroy_thing` destroys the thing, and a late minting or stale copy is destroyed on arrival while the header is held.
- It differs from a purge only for erasure: it names every minting whatever its `expires` (`names`: a purge in an expiring commit reaches only deltas expiring no later), and `purge_one` writes no lasting-header mark for it; `purge::lasting` (and `Engine::may_last_on` for sync) reads no drop on a released thing as lasting.

## Keep and forget (`destroy::keeps`, `destroy::forget_released`)
- One rule for every destruction kind (purge, expiry, release): a destroyed thing keeps its record, value-less mintings, `roles.0` and the destroying requests' parts on it (`destroy::judges_destruction`, `osis_commit::retention::destroying_request`) while either a held thing **needs** it (`needs_evidence`: a dependent, or a durable reference-index row from another thing, `retainers^.0` included, `group.0` not: `needs_from`) or a held request destroying it is in force (`in_force`: until `wall_ms(ts) + ROLE_KEEP` or its `expires`, the earlier: a release's `expires`, a purge's floor `purge_keep_until`; not once every creation is past its expiry, which nothing can make fall). The window is how long role history is kept (spec/commits.md §5 Fixed retention), so a removal ordered before the request may still make it fall. Otherwise it keeps nothing.
- Evidence for dependents: `minting_evidence` and sync's `destroyed_certificate` carry the destroying requests' parts, purge and release alike.
- `group.0` is no need: a group contains its members, readers show nothing for an unknown member, and a release never writes on the group, so a released member still listed is forgotten at its request's expiry. It still keeps a member alive for the judgment.
- **Destroyed for good**: past a purge request's window the verdict stays without the evidence (a purge request is never dropped, so keeping for it would keep a record per purged thing for good): `keeps` marks the thing (`Indexes::destroyed_for_good`, `td/` + tid, kept for good; `Core::destroyed` reads it first), and `apply::thing_wait` takes no `created.0` part on it (a stale copy or a new minting by any record holder) and nothing else while its record is not held. Without the mark a minting arriving past the window revives the thing wherever the right came from a grant on the thing itself (dropped with its edges). A dependent arriving later still brings its record and frozen edges back (`record_back`), judged as before. Newcomers past the window that never held the destruction cannot judge it (spec/commits.md §5, Limit). Erasure's tombstone (notes/deletion.md): a release leaves none (a stale copy past its expiry is released again by rule), an expiry needs none (a copy carries its `expires`; a fresh durable minting after it is notes/expiry-creation-design.md's flagged Limit).
- **Forgotten**: a thing destroyed by release alone (`release_state`: every minting dropped by a release, none by a purge or its own expiry) whose requests are all past `expires` and that nothing keeps is forgotten whole in the same transaction:
  - commits whose every part is on it or marked forgotten (`Missing::Forgot`, meta-row bit 128: a part that joins or drops leaves `Hold::Missing`, the mark with it; it overrides `Missing::ToFetch`, a dead part is fetched nowhere) are unindexed (`unindex_commit`, role commits and requests too) and pushed to `memory.dropped` as `MemoryDrop::Gone`: sync judges their entries must-not-hold (deleted where it may) and forgets them once gone (`sweep_forgotten`);
  - commits whose other parts are marked or not held on a thing whose record is not held are unindexed too, as `MemoryDrop::Awaits { things }`. An unheld record means the thing cannot be judged, not that it is dead: it may live elsewhere with its part in these entries, so they are not deleted. sync (`memory_step`) turns them into `Kind::Awaits { things }` (`await_records`): skipped, bounded by the entry count, fetched again when any of those records arrives (`by_awaited`, `wake_awaiting`). An entry judged again (a start's `reopen_all_awaiting`) awaits every record `throw_out` names (`Engine::records_awaited_by`), so one never waits on the forgotten thing alone. Keeping the header instead would be unbounded (pending bounds cover waiting parts and entries, not a header of all-missing parts);
  - any other commit (a part on a thing held here) keeps its header, its dropped parts on the thing `reopen_in`ed (missing, not fetched) and marked forgotten, in one write. The mark lets a commit on several released things go once the last is forgotten (in one transaction or several); without it an unknown thing and one forgotten here read alike. A marked part whose thing's record is held again counts as live until its copy joins;
  - its per-aspect rows (`forget_aspect_rows`: FORGOTTEN, PURGES, PURGES_NAMED, LEFTOVER, ...) and `leaving` rows; of a commit that went, the FORGOTTEN rows unindexing writes on a held thing, every per-aspect row of a thing whose record is not held that no held part is on, and the request's notes on the purge lists (`purge::unnote_requests`).
- **Own secrets**: a destroyed thing that keeps nothing (its record goes) and had secrets of its own keeps them (`k/`, `Indexes::secrets`) only for sync's deletes: `hold_secrets` marks it (`kd/` + tid, `Indexes::destroyed_secrets`); sync (`drop_destroyed_secrets`, after `memory_step`) drops them through `Engine::drop_destroyed_secrets` once, under the labels it syncs, no entry of a commit keyed by it (held or forgotten here, with a part on it or acting for it: level 2 derives from the header actor's secrets) lists a part on it (any, acting for it) and no delete of one is within its tombstone, nor a blob of one is kept here unnamed or under such a label (one named only under labels not synced here would pin them for good), nor a freed link of it (as thing or author) is held. An entry awaiting a record (`Kind::Awaits`) has no header to tell: such entries stay at hosts once the secrets go (stated limit). Judged when marked, after each start, when such a commit is due for forgetting (`forget_due`), when a freed link of it goes (`freed_done`). A keep again or a fall clears the mark (`unhold_secrets`). The invariant is at `hold_secrets`.
- **Own labels**: such a thing's `label.0` value is kept when its destruction drops it (`kl/` + tid, `Indexes::destroyed_labels`, `keep_labels`; a fall drops it). Once it keeps nothing with secrets held (`Engine::emptying`), everything under those labels is must-not-hold: `labels_read` answers them, sync keeps them (`compute_synced`) with `empty_pass` in place of a pass (its own store's entries go; at each source whose head's delete key it holds, every entry present goes by it; nothing placed or judged), and sync's `end_emptying` (each step, before `drop_destroyed_secrets`) ends it once each label has no entry known and no tombstone left and is heard out (a hostless one: nothing to hear), or this node holds no delete key of its newest step: the labels' sync records go with the row in one transaction (`Engine::labels_emptied`), then the secrets may drop (`drop_destroyed_secrets` skips a thing still emptying). Not while it keeps: the destruction may still fall and fetch back from those hosts. The invariant is at `keep_labels`. A forgotten commit's `g/` rows go with it (`unindex_commit`).
- Sync keeps a forgotten commit's header durably while entries of it are known, so a restart before the deletes still deletes them at peers, and drops it past the deletes' tombstones. A crash-recovery look at what a crash could have lost names neither a commit forgotten whole nor a commit for its marked parts: its own held entries are no arrival, and ingested again would bring the thing back.
- Re-judged whenever a keep may have gone: a reference-index row going (`refs::note` to `Core::destroyed_due`), a record or edge write naming it leaving the held set (`Held::count` to `take_unnamed`: a thing destroyed, a role commit forgotten or re-derived), a key actor's last durable commit with a part held elsewhere going (`Indexes::signed`, kept by `Core::put_meta`/`take_meta`; checked against the walk in debug builds), a request's window ending (its part going value-less at its `expires`, or the request's floor timer `T_KEPT`). All feed `apply_destructions`' loop, which also takes what each drop there unnames, so a chain of destroyed actors kept only for each other goes in one transaction.

## Evidence under labels (`Engine::destroyed_needed`, `minting_evidence`)
`destroyed_needed(g)`: `destroyed_upstream(g)` plus each kept destroyed thing (`Core::destroyed_kept`, a superset read from every record once after an open, kept by `destroy_thing`/`learn_record`) a live thing of `g`'s closure lists or references: O(kept destroyed things + their rows). `certificates(g)` places for each its record chain, frozen edges and `minting_evidence` (which every record carries): the witness and, destroyed, its destroying requests as header-only copies (no prefix expiry: a release's copy outlives its blobs; notes/expiry-creation-design.md, A thing's mintings travel with its record). sync's `destroyed_certificate` judges header-only copies of mintings and requests of destroyed things in the closure (not one that may be lasting) and outside it, by `destroyed_needed`, waiting on the needers' rows.

## API (engine, through `internals` in osis tests)
- `Engine::judge_lifetimes(heard, held)` judges the work list (with `held` the held things too; pending when rights moved). A thing read is heard out when every group whose closure holds it (`enclosing`, itself included) is; a thing whose walk read one that is not goes to `lh/`. The unreachable things the node's account may destroy (`purge::would_hold_right` over every held minting), with their cascade, go in one release request written in a second transaction (`Engine::release`); they stay pending until the request, applied, destroys them (`queue_with_listers` clears the row), so a request refused or failing is judged again at the next role-timeline change or open. Returns `Judged { release, waiting, judged, request }`.
- `Engine::release(xs)` writes a request for any things (`Permission` without the right; `w.release` builds on it). `lifetimes_due` (work due, things held: two store seeks), `lifetimes_pending`, `lifetime_status`.
- Writer checks (`Mutation::require_kept`, `require_reference`; `write::check_lifetimes` after `check_synced`, in the commit's transaction so a refusal applies nothing): `lifetimes::unreachable_now` is the walk on the state the commit left, heard out or not; `refs::references_in` reads one durable row (target, source, AK). Opt-in per mutation: osis's `Write` asks it for its own list ops; compaction, undo and the release request never do (a snapshot changes no read, and a pending thing's snapshot must not fail).

## Sync trigger (`sync/lifetimes.rs`, `SyncEngine::judge_lifetimes`)
Run in `handle` after the passes (`PASS_AGAIN`); a request written gets one more `Local` step so it goes up at once. Nothing due or held: two store seeks. Else it reads `label_status()` (O(labels × connections), in memory): a label is heard out exactly when it reads Synced (`LabelStatus::synced`, the rule behind the API's `SyncState::Synced`: a source connected, a host by this node's pass or a co-reader by its stream and reports, each caught up, none opening); a group when each of its labels is; a group with no label, and a thing under none, is heard out. With no source connected (offline, or no host and no co-reader up) nothing under the label is released: a co-reader's commits in the bad order would otherwise release a live thing. It judges when work is due, passing `held` only when a label is heard out that was not at the last judgment (`lifetimes_heard`, `None` after start), so a step re-walks nothing while a label stays unheard.
- Cost: every held thing is walked again when any label is newly heard out, not only those waiting on it: a thing held under a label never heard out (a co-reader that never connects) is walked again each time another label comes back to Synced after a judgment ran while it was not (issues/thing-lifetimes.md).

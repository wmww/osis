## For Tess
Each a question about the model; what a user would observe.
1. **A write may show valid, then invalid.** A reader holding part of a write's evidence (a removal stamped before the write, not yet arrived) shows the write as valid until the removal arrives; nothing it holds tells it the removal is missing (finding 5). spec/requirements.md Deterministic ("A node missing some data reads as if it never had it until it arrives") covers this today and the draft keeps it. The draft makes these acts wait for a complete pass so nothing irrevocable rests on such a verdict: a deposit's promotion, dropping a body judged invalid, a delete at a store resting on a verdict, a vouch. A user then sees a non-writer's write reach readers served only by stores later: by up to `PASS_WAIT_MS` (an hour, recommended) when a peer holding the sync ID is away. Is that delay within "only propagation waits"?
2. **A thing grows with role changes on the things its writers act through.** Evidence copies are every edge write (under OPEN 10's proposal: every chained one) on an edge a held write's path uses, kept while such a write is held: a document written through an organization carries each change to the writer's grant on the organization (issues/zero-growth.md For Tess 1, here for A2). And from A3 a removal's per-thing list leaf stays while the removed party writes through the edge again (re-granted, or only demoted): one leaf of what the remover then held, per such role change, for good (issues/zero-growth.md, Leaves). spec/requirements.md Scale says "with the number of role changes made on it". Is the property the weaker one ("on it, or on what its writers act through")?
3. **What a copy shows beyond the roster fact.** A copy of a role commit is its whole signed header and its role parts on one thing. Beyond who holds roles on the thing through other things, the header shows: the tid, aspect name, counters and hash of every other part the role commit wrote, on other things too (a grant's boxes, a rotation of the target's keys, `keys.0` and `sync.0` writes it covers), so readers of D learn that those things were written with it, which the requirement promises only to those things' own readers; the session nonce (`form`), its delete keys (`keys`), `undoes`; the grant's `floor`; until A3 every commit ID the removal lists, on any thing; the root's counts (A3). Are those within "learn nothing of rosters that give no role on it", or must a writer rule keep role commits that can become evidence to one thing and nothing else (a grant's boxes travel with it, so not always possible)?
4. **A sync ID whose writers are all hostile.** Today a removal reaches such a sync ID's readers only if some honest node holding both the stolen signer's write and the removal logs it there; with only stores between, never. A2 is the same; A3 adds the remover's errand, a deposit a hostile writer of the sync ID can delete at the stores (it holds the delete key). So a reader served only by those stores keeps showing the stolen signer's writes there until it syncs with the remover or another honest node holding the removal. That is within the words ("Deletion and removal bind honest nodes that receive them"; Convergence "at the latest once a writer of that data has synced with them"); is it within "authenticated malicious writers are bounded"?
5. **A write through a path no valid grant joins** (finding 11, OPEN 10). Every write states the path it acts through. As drafted, every role change written on such a path travels as evidence, valid or not: a writer of a thing on the path who is no admin there can sign role changes that never take effect, and every thing written through it stores a copy of each, without bound (27 more for 27 more in the model); and a writer naming things that hold no role on what it writes makes honest nodes show those things' member lists to its readers. Proposed instead: only role changes that could take effect travel, and only along paths each step of which some such grant joins. A user sees no difference: a write through a path no valid grant joins is shown nowhere either way. What changes is that such a write *waits* (like a write through a path nobody ever granted, which already waits for good) instead of being *refused* (dropped after a complete pass). Kept while waiting: by whoever keeps the sync ID it is under, attributable to it, gone when it is unsynced; and only a writer of that sync ID can put one there for free (anyone else only as an unpromoted deposit, within the bounds on unvouched input), as it can already fill it with valid writes. One residue: someone allowed to end expired grants (any writer) or to invite can still sign such changes on a thing, each copied under every thing written through that edge. Accept that, or let only admins end expired grants?
6. **What a reader of one document downloads about people removed from its organisation** (OPEN 16). Today a reader of one document already downloads every removal of a writer from the organisation (each removal changes the document's keys, and the new keys name it): about 21 KB per removal, measured, most of it key material. The planned rule (OPEN 14) keeps that and adds a copy of each removal and of the grant it ends, about 1.6 KB per writer removed, kept for good and delivered whether or not anyone changes the document's keys: what it buys is that a removed member's stolen key cannot write to any document the member could ever reach without every reader of that document knowing. People who only ever read the organisation cost nothing: a document of an organisation holds 2 copies per writer ever removed, plus its writer's grant, however many readers come and go. Is a document growing with each writer ever removed from the organisations above it (about 23 KB each on a first read, about 1.6 KB of it new) within "a long-lived thing may grow modestly with the number of role changes made on it", or is the property "on it, or on what its writers act through" (For Tess 2)?

## Where the model overrode the design notes
Each as the model has it.
1. **The errand follows taken grants to the end** (finding 1, `Errand::Transitive`), each reached thing read under its own sync ID, and is a standing duty, run again when the remover's view shows a new target (finding 3, `standing`). The design note's first reading: one level of taken grants, run once. (A3's text.)
2. **The required set is computed again from current holdings at every change**, retag included, never placed once at logging (finding 2, `Placement::Function`): a thing leaving a unit turns what the remaining bodies still need into copies, logged by any holder whose view requires them.
3. **A lowering's copy carries its frontier** whole (A1's header) or, from A3, its root with every role entry; a reader seeing only its unit's leaves drops a listed grant on another thing (finding 4).
4. **Verdicts on partial evidence are provisional** (finding 5): no rule over the held set tells partial from complete; acts that no rule undoes wait for a complete pass (finding 7, Provisional).
5. **Delivery assumes an honest syncing node per sync ID** whose logging stands (Model questions (b)).
6. **A list leaf is evidence of every commit its verdict reads**, not only those it names (finding 6): on its thing, no edge-class part, resting on the lowered edge, in any order (a list is read for a commit stamped after its lowering too). The growth study's "forgotten with the last held commit it names" strands an unnamed commit, pending for good.
7. **Pending on evidence reads order**: a part pends while an edge of its path has no held edge write *ordered before it* (a removal counts), or the latest such pends. A1's Unjudgeable ("set by a held grant", any order) judges a part whose only held grant is later than it as invalid where the node holding everything judges it valid once the earlier one arrives: a provisional invalid the ordered rule turns into a wait.
8. **An addendum is evidence of the commits it lists that rest on its removal's edge** (no edge-class part, no addendum), and leaves with the last: one listing only an addendum would be kept alive by its writer's own unlogged copy (`addendum_live`).

## The model questions
**(a) Provisional verdicts.** The model: a reader's verdict on partial evidence agrees with the node holding everything but that part (P5, locality), and with the node holding everything once it holds S's whole entries (P1); between, it may differ, and no held-set rule tells (finding 5, 1,222 to 1,334 provisional readings over 300 random worlds). After a complete pass a verdict still moves when a later write arrives (a re-grant, a backdated removal), at the node holding everything too (`p8_an_act_after_a_complete_pass_is_reversed_only_by_a_later_write`). So "final" is never a state the API can show: what a complete pass gives is agreement with what the sources held when it began. `wait_synced` on a thing (heard out on every sync ID carrying it, own commits held elsewhere) is what the API exposes, at the granularity a verdict needs (a write's evidence is under the sync IDs of the thing it writes); it waits for no away peer, so it is a weaker bar than a complete pass, and History complete (spec/sync-status.md §3) is spec'd but not in the `osis` API [checked: core/osis/src/syncing.rs]. No new API: spec/requirements.md API ("no correctness that depends on surfacing it to the user") asks for none. Spec/requirements: Deterministic and Convergence ("at the latest once a writer of that data has synced") already state the weaker property; no rewording.
Acting, each with its rule and check (draft: notes/a2-spec/commits.md Provisional):
- apply, read, show, notify: at once; a later arrival moves the reading as any arrival does (P5: the reading is the node-holding-the-same's).
- log, relay, forward: at once; the required set reads no verdict (`World::req` reads stated paths only; P4).
- drop a body judged invalid: waits for a complete pass (finding 12, OPEN 11): dropped at once on a partial view (a removal held, the re-grant after it not), it is fetched again only where some node still holds it, and every reader dropping on the same view with its writer gone loses a write the node holding everything shows (`f12_*`). Checked: `Act::Drop` after a pass reversed only by a later write.
- drop its own body as covered, compact (write a snapshot carrying what shows): at once. The same window as A1's (roles-model `paths` finding 26: a writer not holding a removal carries the late write for good; a cover whose writer is removed loses what only it carried, spec/permissions.md §5.2), not a wider one: every provisional valid that turns invalid is the writer's view lacking an input that makes a lowering ordered before the write cut it (the lowering, or what gives it authority), the window's own case. Waiting would narrow it to "no source held the removal" (OPEN 8).
- show a write provisionally valid that turns invalid: the requirements promise nothing more (Deterministic, above); a removal's writes are "discarded" (spec/requirements.md Permissions) whenever the removal arrives.
- delete at a store a body covered by a cover it judges valid, or must-not-hold by a validity it reads: waits for a complete pass begun after the verdict's inputs moved (OPEN 2): `Act::Promote` stands for a cover's valid verdict; `WhenNothingPends` fails P8 on finding 5's world.
- promote a deposit: waits for its evidence under S and a complete pass (`Act::Promote`, P8).
- write a vouch against a lowering it judges applied: waits for a complete pass (`Act::Vouch`, P8; OPEN 3).

**(b) A sync ID whose only writers are hostile.** The model's delivery rule: every honest node syncing S logs what its view requires; the remover's errand logs its removal under every target's own sync ID, holding it for the errand; the thief logs only its own. The removal reaches a sync ID no honest node syncs together with the remover's only by the errand (`risk3_a_first_write_through_an_enclosing_root`: X syncs A, Y syncs R alone, the thief writes R's dependent; `Errand::Off` fails P1). In the model every writer syncs what it writes, so a sync ID with an honest admin has an honest syncing node; "only hostile writers" means hostile admins (out of scope, spec/requirements.md Threat model) or honest admins whose logging does not stand. The model has no deletes at stores: a hostile writer of S holds S's delete key and can delete the errand's deposit there, and refuse to promote it. So the promise is: a reader of S judges as the node holding everything once it holds what an honest node logged under S, by a store whose entries no hostile writer deleted, or directly from the remover's or an honest holder's own store (readers pull deposits there, spec/sync-inbox.md §3 Sending). With every writer of S hostile and only stores between, nothing. Today is no better: the removal reaches S only as a valid chain certificate some honest holder of both the write and the removal logs there (spec/sync-judgement.md §2), and no errand exists. Not modelled (For Tess 4); the check that would settle it: `evidence` with a delete-capable hostile writer and a reader served by one store.

**(c) Storage.** Evidence held is a function of the commits held (P4: what a sync ID holds is what its reader requires; forgetting a body takes what only it needed, `p4_evidence_leaves_with_the_last_commit_that_needed_it`; leaves and addenda too, `p7_*`, `P4-leaf-grow`). A node holds S's evidence only while it syncs S (`round_function`: a node keeps what a synced sync ID requires, and its own writes), so unsyncing every sync ID leaves only its own identity (Storage attributable; spec/commits.md §5 What a held thing needs, draft). Two things to keep in the briefs: the errand holds a target's sync ID only for the errand (it reads taken grants there and logs), so its storage ends once its logs stand at a source; A3's removal copies stay while the unit holds the thing (reach at any time), attributable to S.

**(d) Confidentiality.** What a reader of S learns from evidence about things outside S's unit. By induction on the closure: every body under S is on a thing T of S's unit; each edge of its stated path is (h, x) with x on that path, so h holds a role on T through x and the things after it (the path's own definition); an edge write's own path ends at its target (or holder, for a self-removal), so its edges' holders hold a role on that target, which is on a path to T, so on T through other things; the remaining admin edge (N, x) gives N admin on x, so a role on T through x; a vouch's path ends at its thing, on a path to T; (A3) a reach edge joins t to a thing of the unit at write or above. So every edge write a copy carries changes a role some holder has on T through other things: a fact of T's roster in the requirement's sense ("who holds roles on it, directly or through other things, and the actors of each change to it"). Past values included: the requirement's "each change" reads them so. Two places the induction fails: "x on that path, so h holds a role on T through x" holds only where the path's later edges carry a role at some time; a writer states its own path, so one naming things joined by no grants (or a junk grant by a non-admin) makes honest holders copy those things' rosters to T's readers (finding 11, OPEN 10); and a vouch on N whose thing the set holds nothing on (finding 10: fixed, a vouch is evidence only on a thing the set holds something on, which the induction covers). Under OPEN 10's proposal the first failure goes: a member brings its path's edges only where each is joined by a chained grant, and a chained write's own path is joined by its chain, so the induction holds (P9 over every generated world, vouches counting and not). What a copy carries beyond that (each a leak to close or accept: For Tess 3), read field by field against spec/wire.md §4's header:
- `aspects`: every other part the role commit wrote, by tid, aspect name, counter range, retention and hash: on the outside thing (`keys.0` rotated, `secrets.0` boxes sent) and on other things it covers (a rotation of dependents' keys, `keys.0` and `sync.0` writes, spec/commits.md §2), so T's readers learn those things were written with it, which spec/requirements.md promises only to their own readers; inseparable from the signature unless role commits that can become evidence carry nothing else, which a grant (its boxes travel with it) cannot;
- `form`: a session's nonce (links the commits of one session); `keys`: its delete keys; `undoes`; `blind` (random, read by A3's leaf keys); `remains` and the adminless bit (roster facts); `epoch` (until A4 the account's rotations travel anyway);
- the `roles.0` value's `floor` (granted without history at that point): not read by validity;
- until A3, the frontier: every commit ID the removal lists, on any thing (the removed party's activity count elsewhere, linkable IDs); A3's leaves close the content part (a reader holds only its own things' leaves; the root shows how many leaves); the role entries stay whole (OPEN 4);
- the root's leaf and role-entry counts (A3).
Fewer holders: `holders` (the `osis` API) shows nothing behind an actor the node does not read [checked: core/osis/src/share.rs], and a node reading an actor holds its roster under that actor's own sync ID [assumed], so evidence along stated paths, which carries no chain of a holder that wrote nothing, removes no holder the API lists; it removes only what a reader held of rosters it cannot read. Computable by exactly the nodes that must: S's evidence is computed from S's bodies' parts on S's unit's things (finding 8): their path entries open to exactly S's readers (notes/path-form.md, who opens T's entry); role commits state one clear path; nodes keeping S unread compute nothing.

**(e) What judging one part reads, against Evidence of a commit** (osis-perm `paths`: `walk.rs` `step`, `keeps`/`chase`, `remains`, `gone`, `seed`; `content.rs`; `mod.rs` `recount`). Each read, and the clause that carries it:
- the hop edges' values at the part's `ts` and their latest cut ever (`holds`), final roles and first chained keys (`regranted`): every edge write on the path's edges, any order;
- for an edge write, its own edge before it (raises or falls, invite grant onto no grant, finalize of an ended grant, a self-removal only lowering, the last-admin rule's standing old value): its edge is a path edge of what brought it in, or the remaining admin edge, or (Role changes travel) an edge naming S's actor; **(A3)** a removal brought in by its reach alone does not bring its own edge's history, which no body's verdict reads until a body rests on that edge (then the path clause brings it), so only a vouch on it could differ, and vouch writing waits for a pass;
- a lowering's own authority (`keeps` along its path, passing over what its own drops and its commit's earlier drops take; `remains` on the named or last edge): closed over the lowering's path and the remaining admin edge; an earlier part's drop of a setter on its path rests on that setter's own path edge, so it is in the setter's closure;
- a lowering's drops (`gone` over the parts resting on its edge) and trusted writes' seeds: they change a body's verdict only through a setter on its chain, which the closure holds;
- a commit's edge writes applying together (a removal waits for each reset entry's creation, spec/permissions.md §2): the other edges its commit writes on that thing (finding 9);
- vouches: counted in the first walk by the vouch's own path and its removal's lowering; an entry counts parts on the vouch's thing alone (finding 10); counting by rounds (the voucher-standing study) reads other vouchers' entries only as they move walks on things of the voucher's path, which the closure holds;
- content: lists naming the commit (frontiers, addenda, snapshots carrying it) on its own thing, addenda's and snapshots' and purge requests' own paths (bodies on the same thing), whether its commit carries a purge request or is a role commit (the header's `kind` and `purge`);
- **(until A4)** the epoch rule's rotations and thing lists, kept as they are.
No read found outside the closure but finding 9 (now modelled: `World::creations`). The closure reads more than judging needs where it takes writes that never apply (finding 11); the least closure the walk admits takes chained writes (finding 14: the re-grant rule reads a dropped grant), along joined paths, with pending read on chained grants (finding 13): OPEN 10's proposal.

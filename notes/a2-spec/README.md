## For Tess
Each a question about the model; what a user would observe.
1. **A write may show valid, then invalid.** A reader holding part of a write's evidence (a removal stamped before the write, not yet arrived) shows the write as valid until the removal arrives; nothing it holds tells it the removal is missing (finding 5). spec/requirements.md Deterministic ("reads as if it never had it until it arrives") covers this today and the draft keeps it. The draft makes four acts wait for a complete pass so nothing irrevocable rests on such a verdict: a deposit's promotion, a delete at a store of a body as covered, a vouch, a delete resting on validity. A user then sees a non-writer's write reach readers served only by stores later: by up to `PASS_WAIT_MS` (an hour, recommended) when a peer holding the sync ID is away. Is that delay within "only propagation waits"?
2. **A thing grows with role changes on the things its writers act through.** Evidence copies are every edge write on an edge a held write's path uses, kept while such a write is held: a document written through an organization carries each change to the writer's grant on the organization (the issue's For Tess 1, here for A2). spec/requirements.md Scale says "with the number of role changes made on it". Is the property the weaker one ("on it, or on what its writers act through")?
3. **What a copy shows beyond the roster fact.** A reader of D judging a write made through A holds A's edge writes on that path: every holder on them gets a role on D through A, so "who holds roles on it, through other things" covers them (argued below, Confidentiality). But a copy is a signed header: it also shows which other aspects that role commit wrote on A (that A's keys rotated with the grant, that boxes went out), the grant's history `floor`, and, until A3, how many of the removed party's commits on other things its removal lists. Are those within "learn nothing of rosters that give no role on it", or must a writer rule keep them out of role commits that become evidence?
4. **Fewer holders shown.** A reader sees a holder's members only as far as stated paths show them, where today chain certificates over any path show more: `holders` lists less to non-members. "May learn" reads as a permission; is it?
5. **A sync ID whose writers are all hostile.** A removal reaches such a sync ID's readers by the remover's errand as a deposit, which a hostile writer may delete at the stores (it holds the delete key); a reader served only by those stores then keeps showing the stolen signer's writes there as valid until it syncs with the remover or another honest node holding the removal. Is that within "authenticated malicious writers are bounded"?

## Where the model overrode the design notes
Each as the model has it.
1. **The errand follows taken grants to the end** (finding 1, `Errand::Transitive`), each reached thing read under its own sync ID, and is a standing duty, run again when the remover's view shows a new target (finding 3, `standing`). The design note's first reading: one level of taken grants, run once. (A3's text.)
2. **The required set is computed again from current holdings at every change**, retag included, never placed once at logging (finding 2, `Placement::Function`): a thing leaving a unit turns what the remaining bodies still need into copies, logged by any holder whose view requires them.
3. **A lowering's copy carries its frontier** whole (A1's header) or, from A3, its root with every role entry; a reader seeing only its unit's leaves drops a listed grant on another thing (finding 4).
4. **Verdicts on partial evidence are provisional** (finding 5): no rule over the held set tells partial from complete; acts that no rule undoes wait for a complete pass (finding 7, Provisional).
5. **Delivery assumes an honest syncing node per sync ID** whose logging stands (Model questions (b)).
6. **A list leaf is evidence of every commit its verdict reads**, not only those it names (finding 6): on its thing, no edge-class part, resting on the lowered edge, in any order (a list is read for a commit stamped after its lowering too). The growth study's "forgotten with the last held commit it names" strands an unnamed commit, pending for good.
7. **Pending on evidence reads order**: a part pends while an edge of its path has no held edge write *ordered before it* (a removal counts), or the latest such pends. A1's Unjudgeable ("set by a held grant", any order) judges a part whose only held grant is later than it as invalid where the node holding everything judges it valid once the earlier one arrives: a provisional invalid the ordered rule turns into a wait.
8. **An addendum is evidence of the commits it lists that rest on its removal's edge** (no edge-class part, no addendum), and leaves with the last: one listing only an addendum would be kept alive by its writer's own unlogged copy (`addendum_live`).

## The model questions
**(a) Provisional verdicts.** The model: a reader's verdict on partial evidence agrees with the node holding everything but that part (P5, locality), and with the node holding everything once it holds S's whole entries (P1); between, it may differ, and no held-set rule tells (finding 5, 1,222 to 1,334 provisional readings over 300 random worlds). After a complete pass a verdict still moves when a later write arrives (a re-grant, a backdated removal), at the node holding everything too (`p8_an_act_after_a_complete_pass_is_reversed_only_by_a_later_write`). So "final" is never a state the API can show: what a complete pass gives is agreement with what the sources held when it began, which `wait_synced` (heard out, own commits held elsewhere) and History complete (spec/sync-status.md §3) already expose. No new API. Spec/requirements: Deterministic and Convergence ("at the latest once a writer of that data has synced") already state the weaker property; no rewording.
Acting, each with its rule and check (draft: notes/a2-spec/commits.md Provisional):
- apply, read, show, notify: at once; a later arrival moves the reading as any arrival does (P5: the reading is the node-holding-the-same's).
- log, relay, forward: at once; the required set reads no verdict (`World::req` reads stated paths only; P4).
- drop its own entry of a body judged invalid: at once; never deleted at a peer, so valid again it is fetched where shown (spec/sync-judgement.md §3 Dropped bodies). Checked: `Act::Drop` reversed only by a later write (re-grant) after a pass; before one, also by arrival (P8 control).
- compact (write a snapshot carrying what shows): at once, the accepted window of A1 (a writer not holding the removal carries the late write for good: roles-model `paths` finding 26); waiting for a pass would narrow it to "no source held the removal" (OPEN 8).
- delete at a store a body covered by a cover it judges valid, or must-not-hold by a validity it reads: waits for a complete pass begun after the verdict's inputs moved (OPEN 2): `Act::Promote` stands for a cover's valid verdict; `WhenNothingPends` fails P8 on finding 5's world.
- promote a deposit: waits for its evidence under S and a complete pass (`Act::Promote`, P8).
- write a vouch against a lowering it judges applied: waits for a complete pass (`Act::Vouch`, P8; OPEN 3).

**(b) A sync ID whose only writers are hostile.** The model's delivery rule: every honest node syncing S logs what its view requires; the remover's errand logs its removal under every target's own sync ID, holding it for the errand; the thief logs only its own. The removal reaches a sync ID no honest node syncs together with the remover's only by the errand (`risk3_a_first_write_through_an_enclosing_root`: X syncs A, Y syncs R alone, the thief writes R's dependent; `Errand::Off` fails P1). In the model every writer syncs what it writes, so a sync ID with an honest admin has an honest syncing node; "only hostile writers" means hostile admins (out of scope, spec/requirements.md Threat model) or honest admins whose logging does not stand. The model has no deletes at stores: a hostile writer of S holds S's delete key and can delete the errand's deposit there, and refuse to promote it. So the promise is: a reader of S judges as the node holding everything once it holds what an honest node logged under S, by a store whose entries no hostile writer deleted, or directly from the remover's or an honest holder's own store (readers pull deposits there, spec/sync-inbox.md §3 Sending). With every writer of S hostile and only stores between, nothing. Not modelled (For Tess 5); the check that would settle it: `evidence` with a delete-capable hostile writer and a reader served by one store.

**(c) Storage.** Evidence held is a function of the commits held (P4: what a sync ID holds is what its reader requires; forgetting a body takes what only it needed, `p4_evidence_leaves_with_the_last_commit_that_needed_it`; leaves and addenda too, `p7_*`, `P4-leaf-grow`). A node holds S's evidence only while it syncs S (`round_function`: a node keeps what a synced sync ID requires, and its own writes), so unsyncing every sync ID leaves only its own identity (Storage attributable; spec/commits.md §5 What a held thing needs, draft). Two things to keep in the briefs: the errand holds a target's sync ID only for the errand (it reads taken grants there and logs), so its storage ends once its logs stand at a source; A3's removal copies stay while the unit holds the thing (reach at any time), attributable to S.

**(d) Confidentiality.** What a reader of S learns from evidence about things outside S's unit. By induction on the closure: every body under S is on a thing T of S's unit; each edge of its stated path is (h, x) with x on that path, so h holds a role on T through x and the things after it (the path's own definition); an edge write's own path ends at its target (or holder, for a self-removal), so its edges' holders hold a role on that target, which is on a path to T, so on T through other things; the remaining admin edge (N, x) gives N admin on x, so a role on T through x; a vouch's path ends at its thing, on a path to T; (A3) a reach edge joins t to a thing of the unit at write or above. So every edge write a copy carries changes a role some holder has on T through other things: a fact of T's roster in the requirement's sense ("who holds roles on it, directly or through other things, and the actors of each change to it"). Past values included: the requirement's "each change" reads them so. What a copy carries beyond that (each a leak to close or accept: For Tess 3):
- the header's aspect list: the other aspects the role commit wrote on the outside thing (`keys.0` rotated, `secrets.0` boxes sent), by name and hash; inseparable from the signature unless role commits that can become evidence carry nothing else, which a grant (its boxes travel with it) cannot;
- the `roles.0` value's `floor` (granted without history at that point): not read by validity;
- until A3, the frontier: every commit ID the removal lists, on any thing (the removed party's activity count elsewhere, linkable IDs); A3's leaves close the content part (a reader holds only its own things' leaves; the root shows how many leaves); the role entries stay whole (OPEN 4);
- the root's leaf and role-entry counts (A3).
Computable by exactly the nodes that must: S's evidence is computed from S's bodies' parts on S's unit's things (finding 8): their path entries open to exactly S's readers (notes/path-form.md, who opens T's entry); role commits state one clear path; nodes keeping S unread compute nothing.

## Open
*taken* marks what the draft writes; **settles** what closes it.
1. **Taken grants at A2 or A5.** The holder's grants under its sync ID and the errand follow taken grants; taken-ness is A5's (notes/write-path-design.md Needs). (a) At A2 every grant naming a holder counts as taken, as built (*taken*). (b) Build taken grants at A2 (plan brief 4). The model counts every grant (`World::seeds`, `errand_targets`). **Settles**: A5's spec, with `evidence` given an untaken grant (neither carried nor followed) and P1 at its size.
2. **Deletes at peers resting on a verdict wait for a complete pass.** (a) Wait (*taken*; P8). Cost: a covered body stays at stores up to a pass longer (`PASS_WAIT_MS` with a recorded peer away). (b) Today's: act at once; the body comes back only from a node still holding it (its writer's own body, spec/sync-compaction.md §1 Own bodies). **Settles**: covers in `evidence` (a cover by a removed writer, judged valid before the removal arrives, a store delete, the body's writer gone): property "no body is lost that the node holding everything keeps", (a) against (b).
3. **Vouch writing after a complete pass.** (a) Wait (*taken*). (b) At once: a vouch against a lowering void at the node holding everything counts nothing and is kept for good (never compacted), growth with no use. **Settles**: nothing more; the coordinator's call at brief 4.
4. **Role entries whole in the removal, or per thing** (A3): whole (the growth study, *taken*) shows every role entry's count to every reader of a copy; per-thing leaves for role entries too, required where a held edge write is on the thing (finding 4's `Leaves::Evidence` reading), close the count at a leaf per thing. **Settles**: A3's spec brief, with `evidence` `Rule::listed` taking role leaves.
5. **Leaf bytes** (A3): sorted (key, hash) pairs in the root (*taken*: a reader proves absence by not finding its key), or the §5.5 list tree at random indices (cannot show absence, so a commit could not know to wait). **Settles**: A3's spec brief.
6. **A1 step 5's certificate narrowing**: A1's plan narrows `sync/certified.rs` to the stated path before A2 deletes it. (a) Skip it: A2 brief 2 builds the derivation, brief 3 switches (*taken* in the order below). (b) Build it: one more rebuild of `certified.rs`. **Settles**: the coordinator.
7. **The header extras in a copy** (Confidentiality; For Tess 3): accept, or a writer rule. **Settles**: Tess.
8. **Compaction on a provisional verdict**: at once (*taken*, A1's accepted window), or covers only after a complete pass. **Settles**: Tess's call on the window if it widens; nothing in the model reads it (`evidence` has no covers).
9. **Hostile deletes of copies and record blobs at stores** (issues/cert-blob-hostile-delete.md, re-read): unchanged by A2 (record blobs stay one per sync ID; a certificate copy deleted at a store is logged again by holders, as today: §3 Neither excludes copies). The issue stands.

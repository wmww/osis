# Engine: receiving and writing commits
> Summary: How the engine examines, pends, applies and re-examines commits (`apply/mod.rs`, `apply/waits.rs`, `apply/carriers.rs`, `apply/atomic.rs`) and what its writer refuses: sessions and counters, the HLC and clock, how a part waits alone, chain certificates and depth, junk and bad parts, late parts, carriers and the one parking place, the writer-side rules, and apply costs. The rules themselves are spec/commits.md §2-§4; this note says how the code keeps them. Not here: validity and re-judging (notes/engine-validity.md), retention on apply (notes/engine-retention.md), role commits (notes/engine-roles.md), streamed joins (notes/engine-paged.md).

## Principle
What applies is a function of the parts held and everything else held, never of arrival order or which parts came together. A header or signature fault refuses the commit; each part is judged alone from the signed header, its bytes and held data; every wait ends only as the held set grows, so the applied parts are the least fixpoint of a monotone rule (osis-engine `order::held_set_decides`). What cannot be judged yet waits in one place and is never thrown out to be fetched again.

## Sessions, counters and the HLC
- **Counters** (spec/crdt.md §2.1): every content commit writes under this open's session (`Core::session`, a random nonce per `Engine::create`/`open`); expiring memory commits under a second one (`Core::expiring`), so an expired commit forgotten with its counters leaves no gap in `session`'s ranges that a snapshot frontier could not pass. Counters per (aspect, session) are memory overlay rows (`Transaction::counter`/`reserve_counters`, never on disk, rolled back with an aborted transaction), reserved in the transaction that applies the signed commit.
- A restored or cloned store is a new session, so nothing it writes overlaps what the lost or sibling copy wrote: no restore gate, no counter adoption, no `OverlappingCounters` on honest nodes. Two live copies still answer for one dialable key (`reach.0`) and LAN tag: a connectivity flap (LAN receivers keep the first source address they verified), not a correctness problem. Rejected: counters per (aspect, node) with a restore gate (one frontier entry per node that ever wrote an aspect in every later snapshot, two live copies void each other, and a lying frontier can push a restored copy to commit form for good).
- When an own write of the current sessions turns invalid, later writes go under fresh sessions past the hole (`Core::fresh_session`: same random first 8 bytes, next count), with an `OwnWriteInvalid` diagnostic.
- Role commits and snapshots are commit form (`write::commit_in`, `retention::write_snapshot`); `Mutation::commit_form` asks for it on a content commit.
- **HLC** (`engine/clock.rs`): a writer exhausting `logical` within one ms moves to the next ms instead of waiting. Own dots are written under a zero commit ID placeholder from the start (`write.rs` `own_source`), so the writer's own source sorts above foreign dots (spec/crdt.md §3.3 rule 2).
- **Clock**: every node runs on its own wall clock; nothing a peer sends moves it, so a wrong clock harms only its holder (spec/requirements.md): fast, its writes park elsewhere until real time catches up; slow, it parks others' writes and its own sort early. A node's own commits (`Origin::Local`, a held key actor's included) are never refused for drift: its HLC may run ahead of a clock set back. A peer's clock offset feeds only the `ClockSkew` diagnostic. Rejected: correcting the clock from peers' offsets (a median, a cap, a quorum, own nodes first): any correction lets other nodes move this one, and each bound needs picked numbers and special cases.

## Examining a commit (`apply::examine`)
- A commit pends whole only for drift, its author's epoch or an unresolved header list (the held author's signature is checked first, so a false one costs no list), never for its parts' waits. Its author's or actor's record unknown, or every held part unjudgeable: it pends whole (`Exam::Awaits`).
- **A part waits alone** (`Aside`, `Waiting`) for its pages (`WaitBlobs`), parked, or unjudgeable (`thing_wait`: record, chain, author's reach), in the applied commit's pending copy (`pend_aside`), parked under every record its parts await (`note_awaited`, `Waits::records_of`, read by `waits::wakes_of` whatever the first reason). The other parts apply (as the header alone if need be), so a commit can be applied and listed by `pending()` at once, and whether it applies does not hang on which copy came first (a header-only copy, or a destruction that drops its waiting part and then falls). Only parts the blob holds can wait: a part not held (another's private thing in a mixed commit) makes nothing wait and joins late if it comes. Nothing in apply reads what the node syncs. Accepted cost (notes/whole-commits.md): a node syncing two sync IDs fresh may show one thing's part before the other thing's record arrives.
- **Chain certificates missing** (`MissingChain`): the author's or a record chain's `created.0` is missing, or an edge of the path the commit states for the part's thing has not arrived (`validity::unreached`: the hops of that one path as the walk reads them, `osis_perm::paths::hops`, each a record edge or an edge a held edge write puts a grant on, `Held::granted_on`, of any validity and whatever followed). No other path is read (spec/permissions.md §1 Path): a signer on the thing's record chain, or reaching it by other grants, waits all the same where the path it states has an edge nobody set. A removal names its holder (`Held::holders_of`, kept for dependents and closures) and sets no edge: counting it let a thing's admin, by removing an absent grant of G, open a way for G's admins to have forged commits on the thing held. Revoked authors keep their grants' writes, so their commits apply, judged invalid; a re-grant re-merges. A `roles.0` part is read per edge write it makes: it waits while every one is unjudgeable, a self-removal's path ending at its holder (`validity::leaves`, checked once the part is decoded, `apply::edge_unreached`; a commit with a reset whose creation is not held makes no write yet and is read along the whole path). A thing too deep is not waited for (its deltas are invalid by the records alone). A node's own commit goes through the same wait: an honest writer's path is granted by what it holds, and one stating an edge nobody granted it is refused as `Error::Permission` (`apply_local`); only a hostile test writer (`skip_writer_rules`) applies its own such commit, to send it. A thing whose every held part waits keeps its entry's path key with the waiting copy alone (`Waiting::keys`): the applied record's paths are decided by what joined, whichever copy came first. Waiting commits and parts wake on `Wake::Moved`, which every edge write brings.
- **Chain depth** (spec/permissions.md §1): `validity::too_deep` makes every delta but `created.0` invalid on a thing whose chain is not known to reach its key actor within `MAX_CHAIN_DEPTH` links (deeper, or a record on it not held: forgetting a record never makes a deep delta valid); per delta, from creation records alone, so nodes holding different parts agree. `thing_wait` stops waiting for the chain there (`ChainStep::TooDeep`). A deep thing's `roles.0` writes never reach perm (`validity::add_role_commit` skips them); the writer refuses such a commit.
- **Junk and bad parts**: a part not hashing to its header entry, or on an aspect of the wrong storage class, is dropped alone (diagnostic) and the commit applies without it; a blob holding only such parts is refused. Hashes are checked before a pending copy is stored where they can be; a commit whose header lists are unresolved, or whose thing's record is away, keeps the first copy of each slot unchecked (a later copy proving itself against its header entry replaces it: `proves`, by the thing's record held or carried by the part itself, so junk sent first never holds a pending commit back). When one proves junk the commit is named (`Core::redeliver`), its name and opened blobs kept even when the junk was all its stored copy held (`retry_pending`), and sync opens every entry naming a blob of it again (`store::follow`), then calls `Engine::redelivered`. A part that hashes but is bad by itself (`judge_part`: the author signed garbage) is dropped alone, unmarked: only those bytes can ever hash there. A node that could open only a bad section holds nothing of that commit; a node opening none applies its header.
  - A slot counting as never received (body dropped, part past its expiry) is not brought back by a held copy: only a new copy does that, or a restart would change what a node reads. A copy with a junk part or signature is no source even for its true parts: a sender holding the true part could withhold it anyway. A true copy deleted everywhere while junk holds the slot waits for a holder's new copy (keeping such copies while the commit pends would let one sender grow one commit's copies by flood-and-delete).
- **Prefix vs header** (spec/commits.md §4 last rule) is checked where a blob is opened (`Engine::open_commit`), its commitment groups only once linked header lists resolve (issues/sync-unbuilt.md); `ingest` takes plaintext.
- **`created.0` minting** (spec/commits.md §2): `carried_records` refuses a durable commit whose `created.0` part is not exactly one minting (`write::is_minting`: one source, one stamp, equal to `mint_created` under the `creation` view); several commits' mintings join. Header validation and `Engine::snapshot` refuse `created.0` in a durable snapshot, so no junk enters a state kept forever. The codec already keeps slots and foreign stamps out of a writer delta; the minting rule adds refusing resets and untyped structure.
- **Role-class content rules** are writer-side only (Writer side): a received commit breaking them is applied, and perm judges each edge write at its point.
- **Faults set a commit aside** (spec/commits.md §4 No local error from peer bytes): a received commit whose taking fails with a fault (`Error::is_fault`: local, not a store failure) pends as `Reason::Fault` (`apply::set_aside`: its stored copy kept, or the bytes it came as), woken only by `Wake::Open` (an open, a reload), and a `DiagnosticKind::Fault` names it. An arrival's transaction failing so is followed by one that only sets it aside (`Engine::set_aside_arrival`; its transaction-end work counts too); in a re-examination round each commit is already a step (`retry_pending`), so a fault leaves the round's others applying. Rejected: a step around every arrival: no store spill while a savepoint is open, so a large streamed apply would grow in memory (`tests_paged::failed_streamed_apply_leaves_nothing_spec_commits_4`). One mechanism: a set-aside commit is a pending commit, so nothing held, written or claimed reads it, sync keeps its entry as carrier (`Opening::Pends`) and no peer is blamed. A store failure still fails the transaction (retried). Not covered: a fault outside any commit (a round's shared part or end work, a tick: issues/engine-invariant-wedges-sync.md). Test hook: `Core::apply_fault` (osis-sync's tests use it too).

## Late parts (`apply::late_parts`, `atomic::join_late`)
A part of an applied commit arriving later: one that waits is kept pending under the commit's ID and joined once it can be; an invalid one joins and un-merges as on apply. Late `created.0` records and `roles.0` parts reach perm as on apply (the commit's edge writes re-added from every held part: a certificate copy may bring `roles.0` after `created.0`), then held deltas are re-judged. Late `secrets.0` parts: notes/engine-roles.md (`secrets.0`, `keys.0` and established epochs). A snapshot part that comes back judged invalid gives nothing: the parts dropped under its cover alone go missing again (`retention::uncover`), as when a held snapshot turns invalid.

## Unjudgeable commits and parts (`apply/waits.rs`, `apply/carriers.rs`; notes/expiry-creation-design.md §3)
- **One parking place** (notes/sync.md Arriving early): what cannot be judged yet, a whole commit or a part of an applied one, is kept in the commit's pending copy while a carrier holds it (spec/commits.md §4 Pending storage) and examined again when what it awaits arrives. Nothing is thrown out to be fetched again: sync keeps an entry whose commit `pends` as its carrier (`Opening::Pends`), so an applied commit's part arriving before its record is never lost to an entry already taken.
- **Carriers** (`apply/carriers.rs`, rows `pc/`; its module doc has who supplies each and what bounds it): an entry in the sync store (let go by `Engine::release_entry` once no entry in sync's store names a blob of the commit: notes/sync-store.md), a fire held here that carries the commit, or the newest stranded report on a sync ID whose holder keys carry it. At the end of every durable transaction a commit pends only while it has a carrier (`carriers::settle`): the transaction where the last goes forgets its pending copy, and its parts count as never received.
- A commit that cannot be judged (`Reason::MissingChain`, `UnknownCreated`: its author's or actor's record, or every held part's) pends like any other (`Ingested::Pending`): its stored copy keeps every part, its unjudgeable ones included (`note_unjudged` notes their records), with its signature's verdict (notes/engine.md, Signature verdicts).
- `reexamine` examines what is left pending at every call, but skips a commit whose awaited record is still unknown (unless its boxes are due a re-read), so a first sync examines each once more only when its record comes.
- Reading-only secrets a commit's boxes gave are sourced from it (`Waits::reading`, rebuilt at load) and go at its last part's apply (`forget_unchecked`), when it is judged bad, or when its last carrier leaves. A commit with unchecked boxes keeps them until its last part applies. A refused box is read again when the budget frees (`Wakes::reread`).
- Tests with no sync layer keep carriers and fetch through `local_peer::Peer::receive` (a carrier delivered again when `take_redeliver` names its commit; a copy of a missing part when `Wakes` names it); `Peer::tick` and `Peer::reexamine` run them too. Test peers run what is due through those, never `<peer>.engine.tick()`/`reexamine()` (`tools/policy.py`); a test ingesting straight into `engine` (no fetch stand-in) may reexamine through an `&mut Engine` it holds. Tested straight through `Engine::ingest`, each commit given once: waits.rs `every_part_given_once_joins_in_any_order_plain_spec_commits_4` (a property).

## Synced things
What the node syncs is the facade's sync set (notes/sync-leave.md): the node closure, sync unit by sync unit (notes/node-closure.md). Apply never reads it.

## Writer side
- **Writer-side role rules**: at most one `roles.0` grant per role commit (except a redemption's grant plus self-removal, and an explicit removal of several others' grants on one target with a frontier, `revoke_joiner`); a frontier only on a commit that lowers a grant, a removal of an absent or expired grant included; a removal or demotion of another holder on a thing with a `keys.0` keyset carries its `secrets.0` and `keys.0` deltas (its rotation), a self-removal none (`validity::self_removal`: the author's own grant, or admin on the holder with no admin on the target without the holder's grant). A remove + put of one grant counts as its new grant, so a raise carries no rotation. A local commit breaking them, or with any delta invalid here, fails before it leaves.
- **Commit form encoding**: own writes of a commit-form delta are re-sourced to a commit placeholder before encoding (`build_and_apply`), so entries order as a reader decoding with the real commit source orders them (own commit first, spec/crdt.md §3.2); under the signer's own session, foreign dots sharing a map (a link redemption re-writing history boxes) would break canonical bytes.
- `Mutation::dead_resets`: map tombstones for entry dots whatever their liveness (`osis_crdt::reset_entries`: a removal of an absent grant).

## Costs
- **A commit's parts are read once** (`apply::PartsRead`): each `keys.0` part's keysets (`keys::KeysBody`: typed `KeysWrite`, each keyset with its keys parsed, `KeysetRec`) and perm's reading of its `roles.0` parts (`PermParts`) are read on first ask and shared by everything an apply, a late join (`with_held`: late and other held parts, read once for judging and joining) or a rebuild notes from them: required roles and proofs (`note_required`, may-grant grants from `PermParts`), keyset parts, keysets and rotations (`before_join`), perm's edges and the `node/perm` row.
- Counted (osis-engine `scale::`, notes/test-scale.md Scale checks): a grant does the same work with n and 10n content commits held (`grant_is_flat_in_content_commits`); an open from the persisted index rebuilds nothing (notes/engine-store.md). A first sync's ingests grow linearly, each pending commit examined again a fixed number of times (without the wait cache every pending commit would be examined again after each applied one, quadratic): `scale::a_first_sync_is_linear_spec_commits_4`.

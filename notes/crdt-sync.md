# Commits, CRDTs, retention and purge
> Summary: Commits and per-aspect delta-state CRDTs with one rule everywhere (timestamp plus author dot, later wins, removal is an LWW reset addressed by dot for collection elements, no causal contexts; decided 2026-10-14/15), the movable text/list CRDT, dots, undo, a second dot form keyed by commit ID for shared-key writers (2026-10-16), retention classes and purge mechanics. The exact spec is spec/crdt.md, checked by the reference model in crdt-model/ (2026-10-16); this note holds decisions, rationale and known anomalies, the spec the mechanism. CRDT review 2026-10-16: sequence records survive resets (newer inserts never hidden), encoding slots replace the non-associative no-edge rule, presence fixes; text state size depends on commit count, see Spec status. Sync itself in notes/sync.md.

## Spec status (2026-10-16)
spec/crdt.md is the normative description (state, wire grammar, join, read, ops, undo, un-merge, slots and embeddings, paging, structural diff); `crdt-model/` is a slow reference implementation with proptests (convergence under random delivery, lattice laws within and across encodings, single-writer text vs a sequential model, wire round trip and fuzzed decoder, embeddings, diff, un-merge, expiry with value-less writes, snapshots with frontiers, the worked examples) and the text size benchmark. Decisions taken while writing it are spec §12 (D1–D21); the user-visible ones: commit-level writes share one stamp, a write survives a reset iff not older (`>=`), composites have a presence stamp so explicitly empty collections exist, cycle breaking demotes the oldest move and never hides content, expiry strips values and keeps stamps, bag reads are order-independent, the diff takes the writer's schema view.

**CRDT review 2026-10-16 (spec D22–D27, agent's call; the owner may revisit the state-growth consequence of D22):**
- **Sequence records are never pruned.** The spec had a reset drop every old element record; a concurrent *newer* insert anchored into the removed text then had no anchor and was hidden until the next reset, which violated "a newer write never loses to an older removal" (notes/constraints.md). Now a reset drops writes and leaves bare anchors (dot only, placed at the end, never emitted), so the newer insert appears after the new content, as in Yjs. Consequence: a sequence's state never shrinks, `replace` and `remove_aspect` included (tension 14); about one byte per run in a snapshot. Emptiness is "no write and no record", or the anchors' survival would depend on arrival order (found by the model).
- **Encoding slots.** The first spec joined two unrelated encodings destructively (greater stamp wins, the loser becomes a reset). With the register embeddings that is not associative: `(register ⊔ counter) ⊔ text` ended as a counter, `register ⊔ (counter ⊔ text)` as a text (found by the model once the law was actually tested). A position now keeps one slot per encoding seen, joined pointwise, the register slot embedded into every other (embedding total: reset-only where no content edge exists), one effective reset per position, read = the slot with the greatest stamp. Writers never produce slots; the ordinary upgrade (`string` → `text`) costs one retained copy of the last register write until a reset.
- **Presence fixes:** `W` always on the wire (omitting it under a greater inner stamp broke un-merge); set/bag tombstone GC folds the dropped reset into `W` (presence otherwise depended on GC); the bag GC hints (drop non-extreme max/min elements, fold counter contributions) were not reset-safe and are gone. `Derived` (embedded character) records go with their value; an anchor naming an absent one still places.
- **Recorded, not changed:** a move displaces a concurrent insert made right after the moved range's predecessor (the re-anchored successor carries the move's stamp): `abcd`, move `b` to the end, insert `x` after `a` → `acdbx`. The diff algorithm is not normative, only "kept elements keep their dot". Two places where "newer write never loses" yields, now constraints tensions 23–24: an enum payload edit concurrent with a case change stays hidden (a half-written payload otherwise), and a field write concurrent with a container removal resurrects the container with that field alone.
- **Text size** (spec §11, automerge-paper trace, 105 KB text): snapshot is 3.2x the text at 100 edits per commit, 6.6x at 10, 44x at one commit per keystroke. Content plus run records are a 2.5x floor; the rest is about 13 bytes per commit. Hence the client rule: one commit per editing pause (seconds), never per keystroke, and a commit carries the net effect of its batch. Owner call still open: whether ~7x at a 2 s cadence is acceptable, or stability-based GC moves forward.

## Decided
- Sync unit is a group; mechanism is blob-set reconciliation (notes/sync.md).
- Movable text/list CRDT ships in v1, as good as we can make it, with whatever fuzzing and testing that takes.
- Apps see a value they can edit and listen to. No CRDT details (resets, contexts, lost writes) reach the API. A lost concurrent write is observed like any LWW loss: the listener fires with the current value.
- Authenticated malicious writers are out of scope: a writer gaming HLC to win LWW is not a concern.
- One conflict rule everywhere (owner 2026-10-14): every state element carries a timestamp and an author dot, later timestamp wins, removal is a reset. No causal contexts: nothing records what a writer had seen. No `mv` register in v1 (needs contexts).
- Collection elements (text/list elements, set elements, map entries) are identified by creation dot, never by value or key; a removal resets the observed dots (owner 2026-10-15, replaces LWW-element sets/maps). Consequence: a concurrent add the remover never saw has its own dot and survives. Tombstones carry no content, which closes constraints tension 11.
- `set_aspect` defaults to structural diff; explicit replace variant for a reset (owner 2026-10-14).
- Every composite type merges recursively down to leaf registers: struct fields, map entries, list/text element content, enum payloads (owner 2026-10-14). Enum cases never merge with each other.
- Merge encodings form an upgrade lattice (notes/versioning.md): a register write is embedded into every richer encoding present at its position (spec §7), so changing an aspect's encoding is not breaking; unrelated encodings coexist as slots and read as later-writer-wins. No terminal reset / retire marker (rejected 2026-10-14): representation changes are transitions to new IDs.
- Retention classes, purge granularity and rights, expiry: below and notes/constraints.md.
- Everything else is proposal.

## Layers (each a canonical CBOR value)
- **Aspect state**: delta-state CRDT (join-semilattice, single `join` op). Stored per aspect, local only: never synced, never hashed.
- **Delta**: a small state of the same lattice; applying = join. Idempotent, order-free, tolerates duplicates. No op log or ordered delivery.
- **Commit**: signed header plus one delta per touched aspect (a roster snapshot carries one `/members` delta per edge so certificate copies can be projected, notes/permissions.md; the aspect's delta is their join). Header: format version, author node, actor, HLC timestamp, per-aspect dot ranges, author table (spec §2.4 `sources`: node tids, commit IDs and derived dots that foreign dots in the deltas name), snapshot marker, schema table `[(schema ID, revision)]` (notes/versioning.md), list of (tid, ak, delta hash, counter range, schema index or none for an untyped write), retention class override, optional expiry time, optional purge request, delete token salt and hashes for the commit (one per secret that may finish a purge) and a token hash per chunk blob the deltas introduce (notes/sync.md), signature. A commit may touch things of any owners and reader sets (2026-10-16). Commit ID = hash(header). Header plus unpurged deltas form one encrypted blob, or one projection per reader set (notes/sync.md, Projection). A node applies all of a commit's deltas it may read and syncs, or none. Commit kinds: content, membership (own commit per membership write, notes/permissions.md), attestation (header-only receipt frontiers or commit lists for the revocation rule, no deltas, retired as content snapshots supersede what they cover).

## Guarantees
- Convergence under any delivery order.
- Atomic visibility: all deltas of a commit for tracked aspects joined in one storage txn, listeners after. Soft where a node receives a commit partially (partial tracking, snapshots replacing purged bodies).
- Not isolation: concurrent commits merge; app invariants must be merge-compatible. "Repair via listeners" only works if the repair is a deterministic function of state, otherwise two nodes ping-pong.
- Causality is intra-aspect only (tids may dangle), so no commit DAG.
- Known anomalies, all convergent: Spec status above (move displacement, enum payload, partial containers) and constraints tensions 23–24.

## Removal: LWW reset
- Every deletion-like op (delete_thing, remove_aspect, replace, set element removal, map key removal, text/list delete, compaction) is a **reset**: a write of a reset timestamp at the granularity being removed. The address is the aspect, or a collection element's creation dot; never a value or key. State carries `reset: HLC`; join takes the max and drops every element/register/dot whose write time is older. Delta = reset time plus optional new content written at or after it. Concurrent resets need no tiebreak, the later dominates.
- Dot addressing means a remove can only name dots its author has observed: "remove X" / "remove key K" resolve to the locally live dots with that value or key at write time, like index paths. A concurrent add of the same value or key elsewhere mints a new dot and survives (add-wins against unseen adds). A concurrent write *under* an observed dot still loses or wins by timestamp as for any reset. Property to keep: a newer write never loses to an older removal.
- A concurrent edit newer than the reset survives: self-contained ones (register, field, map entry) in place, a text/list insert anchored into the removed content at the end of the sequence, since the removed elements stay as bare anchors (spec §5.7, §6.4; review 2026-10-16). An older concurrent edit is dropped, like a losing register write.
- Permanent deletion of content falls out: after a reset the state is a timestamp plus, for sequences, content-free anchors (dots only). Offline copies are unavoidable.
- Undo of a reset = paste-like reinsert of the pre-reset value with fresh IDs, from the local undo buffer. Others' concurrent edits inside the removed state are gone.
- Parked deltas (encoding or format this node does not know, notes/versioning.md) are never compacted away by this node; it accepts blob-level snapshots and retires from newer nodes.
- Tombstones are content-free: a dot plus reset time, never a value or key hash. Deleted content is dropped immediately. Text/list: the record (ID, and pos while it survives) remains as an anchor forever, run-compressed, so state grows with the number of edit runs, not live size; Yjs does the same and copes. Map entries: (dot, reset time) until the aspect is reset, needed because an older nested write may still arrive and must lose. Set elements: transient. Nothing but a causally later undo can ever target a set element's dot, so once a node has applied both the add commit and the reset commit (received dot ranges are tracked per author anyway) it drops the element entirely, folding the reset into the set's presence stamp so presence does not depend on GC; the tombstone exists only while the reset arrived before the add. Parked adds count as not received; snapshots carry per-author frontiers so compacted history leaves no permanent gaps (notes/sync.md). An explicit replace (reset) gives apps a fresh value, not a smaller state.
- Tombstone compaction otherwise: none in v1 (owner 2026-10-14: worse merging after long separation is acceptable, discarding edits is not).
- Rejected: wall-clock staleness horizon (drop tombstones older than H). Two nodes separated longer than H diverge or lose a side's edits; any independent reset-style compaction has the same problem.
- Rejected 2026-10-15: LWW-element sets/maps (tombstone names the value hash or key: a fingerprint under `purge`, and one that cannot be dropped without stability information because any unseen older add must lose to it); OR-set/OR-map with causal contexts (same add-wins semantics as dot addressing, but a version vector in every state and delta). Possible later if map tombstones ever matter: stability-based GC (drop once every writer has acknowledged; needs frontiers, stalls on offline members).

## Retention, expiry, purge (owner's direction 2026-10-11, mechanics proposal)
Three retention classes for content:
- `purge`: once content is reset or superseded, every node applying that commit drops the body immediately and irrevocably; the resetting node also retires the body at blind nodes.
- `preserve`: bodies kept and synced until an explicit purge.
- `undefined` (default): nodes may drop superseded bodies by local policy. Dropping is a compaction (snapshot of live content, then retire), so current state stays servable.
Set as schema default per AK (notes/data-model.md), overridable per commit for that commit's deltas. Orthogonal: a commit may carry `expires at T` (2026-10-15, notes/ephemeral.md): at T every node holds the commit's value-carrying writes value-less (stamps kept, values gone, resets/flags/positions kept) and drops the bodies as purged; blind nodes drop the entry unattended (spec §4.7). A purge request names prior bodies or whole aspect histories ("bank details pasted into a versioned shared doc"). Not a floor at T (the review's first proposal): conditional on the expired write winning it diverges, unconditional it expires newer writes by others. Snapshots carry expiring writes value-less and never retire their commits, so the content lives only in the commit's own blob (spec §8). Membership-class commits never carry expiry (notes/permissions.md).

Mechanics:
- Purge drops bodies, never headers: fact, time, author and AK of every edit remain, including the purge itself. Headers keep hash(delta), so a purged commit stays verifiable.
- A multi-aspect commit purged for one aspect is rewritten as a blob without that delta: same commit ID, new blob ID, cost proportional to the remaining deltas. Compaction of a commit with mixed-class deltas works the same way.
- Deleting a whole thing with `purge`: retire its bodies, no snapshot. Deleting part of a value (a paragraph, a map entry): the resetting node uploads a snapshot of the aspect's live content and retires the old bodies in the same sync, per commit, no batching (owner 2026-10-12). Every edit to `purge`-class content costs O(changed chunks plus tree path) upload and a retire at every blind node.
- Undo: a node keeps its own bodies locally only while nobody has reset their content; others' `purge` resets win over undo. `purge`-class content has no undo at all: the undo buffer is just another copy.
- No fingerprints: every delta body carries a random nonce (hashed, destroyed by purge), and outward hashes (deltas, links) are keyed with the thing's dedup secret (notes/data-model.md). Blind nodes store but cannot verify bodies.
- Chunks and tree nodes of large values are encrypted under random keys stored in their parent links, so a purged version's chunks are crypto-shredded with its commit wraps (notes/local-store.md). Every local plaintext, wrap and index entry lives in the encrypted local store so dropping it is a key erasure.
- Caveat (accepted 2026-10-14): a node receiving a multi-aspect commit after one delta was purged applies the rest, so it may briefly observe an aspect combination no author produced. Final state is unaffected.

Who may purge: the delta's author or an admin (notes/permissions.md); at blind nodes by delete token plus the label's upload key (notes/sync.md). Enforcement is only against honest nodes.

## Merge per type (encoding is self-describing; schema picks the minimum)
- scalars/tid/blob: LWW (HLC + node tiebreak). Encoding wrappers (notes/data-model.md): `counter<int|float>` (PN), `max<..>`, `min<..>`; reads are order-independent by construction (spec §5.2).
- string: LWW; `text` (and `markdown`) -> text CRDT below.
- struct: per-field.
- set: the text CRDT's element store without `pos`: element = creation dot, value, reset register. Read = distinct values of live elements (canonical bytes; keyed hash for large values). Add X when X is locally live is a no-op; remove X resets every locally live dot whose value is X and drops the content. Concurrent adds of the same value become two elements, deduplicated on read, both reset by the next remove that sees them.
- map: entries are elements (creation dot, key, recursive value state, reset register). Key lookup needs a local key -> live dots index (million-key maps). Two live entries with one key (concurrent adds) read as the recursive join of their values; writes target the lowest live dot. Key removal = reset of the observed entry dots, content dropped. A nested write delta carries the entry's key so a write newer than a removal resurrects the entry with that write only, exactly as a reset-survivor does today; an older one is dropped.
- Semantics summary vs the old LWW-element design: identical for everything except a concurrent add the remover never saw, which now survives instead of being decided by clock. Worst case (accepted 2026-10-15): admin A revokes member B by removing B's `/members` entry while offline admin C, who never saw that entry, independently grants B; B stays a member until removed again. Under the old rule the later clock won, so a concurrent add could vanish silently instead. `/members` keeps the ordinary map encoding as the carrier of membership writes (owner 2026-10-16: whatever is simplest); authority and the roster apps read come from the membership timeline, not from this join (notes/permissions.md, Vocabulary). A roster snapshot may carry several deltas for one aspect (one per edge) so it can be projected per edge (notes/permissions.md, Verifying writes).
- enum: case is an LWW register; a case change is a reset of the enum value plus the new payload. Payload merges recursively while both sides are in the same case. A newer edit inside a case that lost stays hidden and is swept by the next reset (constraints tension 23).
- list<T>: the text CRDT with recursive element content, so a field of one element can be edited in place. Index paths in the API are resolved to element IDs against local state at write time; deltas never carry indices. Caveat: `set_aspect` diff on a list is a heuristic; if it reads a changed entry as delete+insert, a concurrent edit to that entry is lost. Apps that edit list entries concurrently should use the path ops.

### Text/list CRDT (text = list<char> with run compaction)
Mechanism in spec §5.7 and §6; here the semantics and why. Each element has an immutable ID (creation dot), content, and two LWW registers: `pos` (anchor element ID or HEAD, top-2 kept for cycle fallback) and `deleted`. Insert, move, delete, undelete, cut/paste are register writes. No causal context: records are grow-only, deletion is a register, nothing is ever hidden by a reset.

Read = linearization, a deterministic function of state, so cycles and races are semantics questions, not correctness ones:
- Tree: X's children are the elements anchored at X, newest `pos` write first (RGA), DFS from HEAD. Deleted elements and bare anchors are traversed but not emitted. Sibling key is the `pos` *write* time, so a moved element lands directly after its target, ahead of the target's older children.
- Cycles (only among concurrent moves): demote the oldest move edge in the cycle to its previous slot, then to the end of the sequence; content is never hidden by a cycle.
- Unknown anchor (delta arrived before its anchor's insert): hidden until it arrives; always transient, since resets keep records.

Operations:
- Move of a DFS range: write `pos` only for the range's subtree roots, never interior elements (rewriting them changes their sibling keys and reorders concurrent neighbours). Re-anchor known outside descendants (the range's successor) to the range's predecessor. Concurrent inserts inside the range follow with order preserved: FOOBAR + insert x after O / move FOO to end -> BARFOOx. Concurrent moves of the same root resolve by timestamp; never duplicate. Known anomaly: the re-anchored successor carries the move's stamp and so lands ahead of a concurrent insert after the predecessor (spec §6.4).
- Delete = `deleted` write, not a move (moving to a TRASH position would drag concurrently inserted descendants along). Content of a deleted element is dropped from state immediately: ID and `pos` stay as anchor. Undo and paste deltas carry content (undo buffer / clipboard). If a concurrent edit resurrects an element whose content this node dropped, the node requests the specific blobs that carried it (notes/sync.md), not a state comparison. Text content has no stamp of its own, so an undelete newer than a reset of the element's creation revives the flag, not the content.
- Cut = delete range; paste = move roots + undelete range (IDs preserved, so others' concurrent edits inside the cut text travel with it). Client remembers the cut ID range next to clipboard text; on paste emit move+undelete if it matches, else diff -> moves + inserts. Cross-aspect paste = insert. Optional osis clipboard MIME type with (aspect, ID ranges); the protocol has no clipboard concept.
- Undo of a delete = undelete with original IDs (keeps others' anchors valid); undo of an insert = delete flag (keeps the anchor).
- Delete vs concurrent move resolve independently (flag vs `pos`): a moved-and-deleted element is a hidden anchor at the new place.

Size: IDs on the wire are a source index plus an aspect-local counter, mostly implicit via runs, so cost scales with run and commit count, not value size (spec §11 for the measurements and the batching rule). Embedded characters from a register save get synthetic `Derived(dot)` IDs (spec §7).

## Dots and clock
- Dot = (node, aspect-local counter), not commit seq. Commit header maps each touched aspect to a counter range; a node's dots in an aspect are contiguous, gaps only from out-of-order arrival.
- Second dot form (decided 2026-10-16, for anonymous writing through a shared signing key, notes/permissions.md): dot = (commit ID, commit-local index); the header marks the form per commit. Any author may use it. Unlinkable, and collision-free even when several devices sign with one key (per-device IDs under a shared key let any key holder reuse another's dot and knock out its edit). Cost falls only on such commits: text/list runs and received-dot ranges do not continue across commits, one 32-byte `sources` entry per foreign commit, and revocation witnesses list commits instead of frontiers. Must be in the v1 format. Required for commits signed by a link key L, which every link holder signs as (notes/permissions.md).
- Every state element (register, set element, map entry, text element, counter contribution) carries its dot (decided 2026-10-14). Revocation (notes/permissions.md) drops by dot and witnesses frontiers per (aspect, author node). A bool aspect is value + timestamp + dot. Received-dot ranges per (aspect, author) are kept forever; only the receipt-time index is pruned (notes/permissions.md).
- No causal contexts: nothing records what a writer had seen. Rejected: attributing through commit headers (zero bytes in state, history lookup at revocation) for non-uniformity.
- Clock: HLC (wall ms, logical counter; the tiebreak is the write's source, node tid or commit ID, which also separates devices signing with one key; advanced on receipt; spec §2.2). Drift cap (review 2026-10-16): a commit stamped more than the cap (format constant) ahead of the receiver's clock is parked, counted as not received, until local time catches up, so a wrong clock harms only its owner's writes (spec §2.2, 1 h).

## Undo/redo
- Undo = new commit that cancels a specific earlier commit; header has `undoes: commit id`. Signed, replicated, atomic across the original's aspects. Never removes history; purged commits are not undoable.
- Cancel per dot, not "apply inverse": undo set-add / map-add = reset that dot, undo text/list insert = deleted-flag write on that dot (anchor kept); undo counter inc = cancel that dot (idempotent across devices); undo register write = write old value only if own write is still the winner; undo delete / set-remove / key-remove = undelete the original dots, delta carries the content from the undo buffer; undo aspect reset = reinsert (above).
- Stack is derived, not stored: actor's own commits in scope, minus undone, plus undo commits for redo. Replicates for free -> cross-device undo. Scope = set of aspects or a group, app-chosen.
- Per actor by default (owner 2026-10-12). Also an API to view every available change in scope regardless of author, from which an admin may remove (undo) others' changes.
- An actor's own bodies (and pre-reset snapshots) are kept locally at least for the undo horizon.

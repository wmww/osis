# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: Tess's direction, concepts, keys and rotation, sharing, certificates, revocation by demoter frontiers, retained copies, the `core/test/roles-model` findings behind the role timeline, role history and its measured cost, first admins and record chains, links, patterns, required retention, purge rights, public content, anonymous writing, and how osis-perm and the engine's role flows implement it (with measured costs), rejected alternatives throughout.

## Tess's direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: admins, editors, viewers.

## Concepts
- **Terms** (Tess; spec/permissions.md §1): rights are roles given by role grants, and an actor with a role is a holder ("Dana holds write on X"); member and membership mean only being in a group ("this note is a member of Work"), which grants no rights. One word per sense in code, API, CLI and spec; a CRDT set's value is an element, a `Slots` entry a slot.
- Any thing becomes an actor when it needs holders of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the role-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope beyond per-node sides in a fight (notes/disputes-plan.md); an account's recourse is an offline recovery key holding an admin edge beside its nodes (app policy).
- Not promised, so not in spec/requirements.md: anonymity against network, timing and style analysis; revocation reaching a group before one of the revoker's nodes next syncs it.
- What a commit spanning two things reveals to a reader of only one (Tess's wording in spec/requirements.md: no values, only metadata): the exact metadata (thing ID, `ai` list, record chain, size) is spec/wire.md §4's, and may change there without Tess's sign-off.
- Recovery of a lost recovery key is out of scope (Tess). The account keeps working (admins can remove each other); any admin can still copy its things out.
- Recovery card: not in the API until a design exists (issues/recovery-redesign.md); the engine and spec text stay. The seed alone cannot find the account (tid, labels and hosts are not derivable), hence the card format; the recovery key is an admin of the account, so every home-label step lists it with an entry box; the card names several saved peers, and the key claims the current step by its static entry and reads the read secret from the step's entry box (spec/sync.md §2).
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things, the account under its recovery key) derive secrets like any plain thing.
- Nodes are things that own themselves and grant nobody anything. The node card under every label a node tracks shows the readers of L which nodes sync L (a read-only node's card arrives by deposit), and its expiring `seen.0` heartbeat when it last did (notes/ephemeral.md), never a roster. Rejected: a grant of admin from the account to itself (covers only own nodes); a nodes group readable by contacts (leaks the node roster, misses read-only co-readers). `reach.0` carries the dialable key, relays and any global addresses (notes/networking.md Reach items); apps exclude it under open-audience labels so strangers cannot dial the node or learn its IP.

## Keys
- Writes are node-signed plus a chain of role grants. Sharing an actor's signing key erases which holder wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to sign deletes of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the admins), demotion write -> read (rotate write only), removal. A writer's rotation of read and write leaves the admin secret, its boxes and the label delete key where they were (notes/crypto.md, Epochs per role).
- **Forks**: concurrent rotations fork the epoch (spec/crypto.md §4). Boxes are keyed per epoch so both rotations' boxes survive the merge, holders keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it. At a host the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many holders forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (holder, role) (holders end up with different secrets after concurrent rotations and cannot read each other's new wraps); rotating a forked role because a box to M names a fork other than M's newest (A's and M's first admins each judged the other's box uncovered and rotated A back and forth); rotating every forked role (`used_link_with_sharer_offline_spec_permissions_7` hung). Epoch numbers others name are never trusted: the next n counts from the rotator's current epochs only, a pending commit records no epoch beyond its bounded reading-only secrets, and an epoch above 2^62 establishes only next to an established one at n-1 (a planted n = i64::MAX would overflow n+1 and block every later rotation, so removals too).
- **Write or above rotates its roles and below** (decided with Tess). With admin-only rotation, every actor an account holds a non-admin role on would keep wrapping new content to a lost node until its admins happened to rotate, and the account could do nothing. So the account's own node rotates every actor it writes to when it removes the lost node, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks holders out, worse than the storage waste a reader may cause; an actor the account only reads keeps wrapping to a lost node until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a host, which only ex-admins can (notes/label-access.md). Until an admin registers the newest epoch, a removed node keeps the old sync and write keys at hosts: ciphertext it cannot open, stale stamps and level-3 deletes that holders heal. Residue: a holder that has not heard of the removal wraps under the old epoch, and the lost node reads that one blob (as with Signal sender keys).
- **A `secrets.0` record needs the role its key names** (validity `secrets_role`): a map record acts only on the entry of its key (spec/crdt.md §5.6), removals included, so the role and the removed box are read from the delta alone (`keys::secrets_write`); a key-erased record needs admin. Rejected: looking up the removed entry's creation key (its answer depended on which bodies a node had held). `roles.0` perm adaptation (`edge_ops`) still names a removal's holder by its entry's creation (`holder_keys`, unresolved until held) but ignores a reset carrying another key, as the CRDT does.
- **No periodic rotation, no rotation policy** (Tess). A node compromise is either known, and the removal rotates before the next write, or unknown, and the node is still a holder, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy would need the node's KEM key to change from randomness the thief lacks; the seed is the node, so a thief holding it is the node. History boxes mean a compromise yields all stored history anyway; "no history for new holders" and bounded history are app or future choices.
- **Plain things derive secrets** until they have a holder other than its first admin, so nothing is stored; then explicit secrets, so that removing that holder rotates the thing alone and not its base actor. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, one-way from the base actor's), so wraps, delete keys and label steps need no special case. Content of the derived era keeps the base actor's delete keys: a later admin of the thing who is no admin of the base actor cannot delete it by key at hosts, only by the label delete key (accepted, Tess). A derived epoch has the base actor's n capped at 2^62 − 1 (notes/crypto.md, Derived epochs). Explicit secrets do not stop the cascade the other way: every rotation of a base actor is caused by a removal, and the removed holder could open every explicit secret its roles reach (things below it, grant targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `keys.0` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin acted.
- **Nesting cost** (accepted by Tess): removing a holder rotates every thing with explicit secrets whose secret it could open, so a lost node costs one lazy rotation per shared thing the account reaches; the usage rule is to share sets through one actor. A thing's admins learn what it holds roles on because every grant whose holder is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct holder per rotated role, one re-registration per label per host. A company of 50 teams with 10 labels on 3 hosts: 50 boxes and 30 signed messages per account removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `keys.0` window**: until an account's new `keys.0` reaches a co-actor's label, rotations there seal to the lost node's old keyset and its steps list its old claim key, so the lost node reads new content via an honest host. Hence the MUST to place the removal and new `keys.0` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **A removal and the rotation it requires on the target are one role commit**, so the rotation and the departure travel together (both parts on the target, one body; a sender holding the keys may still split them, spec/commits.md §4), and an omission in a held rotation can only mean the rotator did not know the holder. Without it (TLC, core/test/tla/rotation R1) a node receiving the rotation before the removal re-seals the removed holder, who reads post-removal content from an honest host (it holds the current sync key). It costs nothing: the remover had to rotate before encrypting the removal commit anyway. The inbox copy to the removed holder and the certificate copies carry the grant delta only. Rotations of other things (the cascade) stay lazy; they exclude nobody directly. A later rotation by a node that knows the removal carries no removal, and a node reading it out of order would re-seal the removed holder: establishment by names closes that (notes/crypto.md, History boxes and establishment).
- **Re-seal is a SHOULD with a trigger** (a current holder without a box at a current epoch, or a stranded heartbeat); without the trigger a grant raced by a rotation was a silent permanent lockout. A missing box marking a deliberate exclusion looks exactly like one marking an unknown grant, hence the guards: a re-seal decision comes at the end of a complete pass (every host and peer log read to its end: cheap to know, and what makes the post-compaction case sound), only at established epochs, and boxing a secret to a holder counts as encrypting under its epoch (a re-sealer that knows of a departure rotates first; one holding a grant it may finalize finalizes it first). A late joiner holding only a snapshot rotates instead (a rotation boxes everyone it thinks current). Opening a label is not encrypting under (notes/crypto.md, Wraps). The remover uploads the rotation before registering the step (notes/label-access.md), so a holder listed in the step never strands merely because the commit is not there yet. Residue (notes/label-access.md Re-seal): after compaction a node's view of the roles no longer travels with the epoch chain, so a node boxing a holder at a snapshot-established epoch from an incomplete view (a host that never got the removal, an interrupted first sync followed by an eager rotation) can box a removed holder; healed by the next rotation of a node that knows. A holder whose deposit is refused is re-shared by hand (notes/sync.md).
- **What a removal reaches** (`osis_keys::reached`, over a `Graph`: `PermGraph` adapts a perm `Timeline`, `MemoryGraph` for tests): the things the removed party's roles opened, things below them and grant targets transitively, linear in the graph: the labels a removal is placed under; `lost_access` (what a node drops) uses it too.
- **Depth 0** (Tess; notes/crypto.md, Holder actors at depth 0): a departure is from the actor itself; one inside a holder actor M reaches the actor's boxes only as M's new keyset, which makes them stale, actor by actor up. Before M rotates, a node holding M's secrets that knows the departure finds A's epoch boxing M at M's uncovered keyset blocked and rotates A leaving M out. `ensure_rotated` cascades over the holder actors this node may rotate (post-order, each once), so where it may rotate M its one rotation of A seals M's new keyset. Tests: `rotation::tests_members` (twelve deep, diamond and lattice, cycles, ignorant fork, forged keyset, hidden grant, the stated limit on grants), osis-node `flows::cascade_two_hops_spec_perm_3`, `inside_member_departure_leaves_holder_out_spec_perm_3`.
- **Role cycles**: X and Y readers of each other, D removed from X: Y's epoch boxes X's old keyset (D holds it), so X's new epoch boxed to Y leaks, and any order of lone rotations that box each other leaks. Cycles stay allowed (Tess: tags become members of each other by ordinary use; two people's shared tags have disjoint admins; nested shared tags can be one-way), but no key cycle forms (rule 4; Tess left the rule to the agents, model-checked first): the grant closing a cycle is keyless and its holder boxed nothing, so a cycle reduces to member chains. Every rule without it failed in Depth0.tla (notes/keys-requirements-study.md). Also rejected: joint rotation of the cycle in one commit; forbidding cycles. A hidden earlier grant leaks until the writer holds the grants (taint, notes/crypto.md).
- **Re-seal invariant** (`reseal_candidates`): once re-seals settle, every node counts the same current epochs (supersession is read from the rotation commits) and every holder with key access holds every current epoch any node holds (`forked_reseals_settle_*`). A re-seal is made only if it adds a box the trigger asks for (`forked_role_reseal_reaches_fixpoint_spec_permissions_3`; without that, churn seeds 140170 and 140188 looped); requiring every fork's secret of a re-sealer stranded a holder when no node held them all. A node lacking a role's current secret (a rotation left its holder actor out) rotates the other roles it may (`rotator_lacking_read_rotates_write_spec_permissions_3`) and waits for the re-seal of the one it lacks; a removal whose rotation would write that role is refused (`removal_lacking_rotated_secret_refused_spec_permissions_3`). Cycle tests: `rotation::tests_members::removal_in_cycle_spec_crypto_4` (2- and 3-cycle), `departure_below_cycle_spec_crypto_4`, `cycle_with_disjoint_admins_converges_spec_permissions_3`, `cycle_concurrent_departures_spec_crypto_4`, `second_admin_ignorant_fork_in_cycle_spec_crypto_4`, `hidden_grant_tainted_keyset_spec_crypto_4`, `cycle_removals_leak_nothing_random` (tier 2 `_large`).
- **Lockout**: removing a writer that rotated to itself recovers (notes/lockout-recovery.md); a lockout by a holder that is kept waits for a re-seal, and a hostile admin is a dispute (same note). With no admin left (a thing whose admins are all gone) nothing recovers.
- **A finalize names the write it ends** (model core/test/tla/rotation/Finalize.tla; spec/permissions.md §2, spec/crypto.md §4 Met): a role commit resetting an entry whose creation the node does not hold applies none of its edge writes until it does (`ix.unresolved`), and a name is met only for a commit so resolved (`NamesHeld::resolved`); otherwise a node holding a finalize without the `until` write it ends counted the departure as met (withheld-departures seed 3, `finalize_without_its_until_unmet_spec_crypto_4`). Rejected: known writes of such a commit applying alone (a name then covers a holder its other write had not yet removed), rotating instead of re-sealing a holder a name removes (leaks through the new history box). Limit: a commit resetting an entry the node never gets never applies there.
- **A timed end is finalized** (Tess: any writer finalizes; checks in notes/keys-requirements-study.md): a grant past its `until` is no key departure; keys read no clock (`Core::key_holders`, `rotation::key_role`: every applied write in effect, `until` disregarded, the `until` 0 keep value no grant). A node with write about to encrypt under T (`rotation::ensure_rotated` → `finalize_due`) first writes a finalize of each ended grant on T of role at most its own: a removal with no frontier carrying the rotation (`flows::edges::finalize_in`). The timeline applies a frontier-less removal of another's grant only as a finalize (perm `judge`, `Attr::Finalize`: grant past `until` at its `ts`, author with write and at least the grant's role; no class, never audited), so a renewal ordered first wins and an admin's racing finalize cannot turn into an empty-frontier revoke; test harnesses give explicit removals an empty frontier for that reason. At the guest a finalize counts as its `until` (`Timeline::role_unfinalized`, `lost_by_time`): it hears out. A renewal or removal of the grant itself is not finalized first (`ensure_rotated_but`). Removals reset every entry of the holder (`flows::edges::removal`): a void finalize resets the CRDT entry while the grant stands on the timeline. A re-grant after the `until` removes the expired entry first (`grant_in`; `regrant_after_until_reads_again_spec_permissions_2`). Fallback Tess accepts if this hits trouble: only admins finalize. Tests: core/node/tests/it/finalize.rs.

## Sharing
- Sharing never changes a tid or first admin. Moving a thing is a grant then a removal (notes/moves.md).
- One note: a grant on N, explicit secrets on N, N its own label. A set: a group thing with holders and secrets, granted read on each thing (one grant per thing, one commit). A set meant to be shared as a unit is better created under a common first admin.
- Group membership grants no rights (a grant on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Checking a write on N needs the role grants of N's record chain and of the author's own actors, which only holders can read. So signed role commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns, for every author under L, every path it ever had to the things it writes there (every held edge write between things on those paths, applied or not, each `created.0` record and hence that thing's dedup secret), never whole rosters. Author identity is inherent anyway.
- **Per label, not per node**: a certificate delta already under the label counts whoever placed it, so a joiner copies only its own chain (11.5 KB per label in a chat) and holders do not all re-copy a rotated actor's new `keys.0`. Sound because a copy counts only once this node checked every delta of it against the header's delta hash (`SyncEngine::genuine`; opening checks the prefix only, so before the check anyone able to deposit under the label could post the header with garbage deltas and stop the real copy; the same check guards `entry_for`, `carried_by` and the duplicate and strict-subset deletions), only while present at every host of the label this node syncs with, and, for a rotation commit of the label's actor, only under the newest epoch. Older epochs otherwise count: a newcomer gets the history boxes with its grant or first rotation box and opens older copies like older content (`newcomer_after_rotation_reads_older_copies_spec_crypto_4`); counting only newest-epoch copies made every holder re-copy everyone's chain after each rotation (40 KB per holder per chat removal). Residue: a holder of a link key alone (newest secret, no history box) reads none of the older entries. If another node's copy goes, the next pass places this node's own. Deletion power is the same either way (a copy commits to its commit's delete keys). Closure deltas are never copied (they are closure blobs). Another node's demotion or `keys.0` is left to its author for `SETTLE_MS` (30 s) after this node received it, with a wake then (the remover must place them, §3): otherwise every holder learning of a rotation under K's label before the remover's copy under C arrived copied it (3.3 KB per holder per removal). Measured from receipt, not the commit's `ts`, which its author sets.
- A removal of G's grant goes under G's labels (spec §2) because the target may have left G's closure, the removal ends G's reading of it, and G's inbox may reach only G's admins.
- Without `reach.0` under a label, co-readers of that label cannot dial the node off-LAN.
- The revokes placed under an uncovered epoch (spec §4) let A's rotators learn of the departure. The departed party can read them: those actors' new public keys and box keys, M's `roles.0` deltas and the writes' authors' chain certificates, not the boxes.
- **Current `keys.0`** (`Engine::current_keys`): an actor's newest `keys.0` commit may be an inbox or deposit seed write, so certificates carry that and the rotation commits of its newest keyset per role. A keyset then often reaches a node before any secret of its actor (K's rotation under its target's label, K's box under K's label alone): `Core::unboxed_epochs` gives its first admin's nodes the derived read epochs, reading only, so they still open the actor's label. Cost: one more commit per actor whose newest `keys.0` carries no keyset. Joiner's bytes down, `scale::chat_members`: M=100 members syncing with one peer, about 2.0 MB (the extra commits add 0.2%); M=30, each member having added a saved peer, 795 KB, of which the extra commits are 139 KB (4.6 KB per member, 21%).
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some holder of the revoking actor syncs L); chain depth equals nesting depth, at most `MAX_CHAIN_DEPTH` (64) record links (spec/permissions.md §1; deeper nesting would make every standing query cost more).
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor); certificates by the roles at a point (they reveal about as much, and needed more rules, below in Implementation).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Tess's decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and hosts never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too; re-grant restores it, together with Y. The revoker's view decides, as if it were a central authority (Tess: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- **One rule for both layers**: the revoke's frontier is one list of commit IDs for edge and content writes, 32 B per listed commit: the demoted node's commits the demoter received on the aspects in question, less those whose parts there its own compaction could drop now (about the tail since the last compaction plus the keep-at-least window). A long-uncompacted prolific node can make it megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), kept as long as the revoke, i.e. forever (`roles.0` is never compacted). Compact encodings were studied and dropped (notes/frontier-study.md).
- Only the revoker's own receipts matter: a held commit counts as received at its apply time (`Meta::received`; a late part does not move it), a header read for receipts only at its read time (the `r/` record, IDs only). A frontier taken as of an earlier cutoff (`Engine::frontier`, tests building late demotions by hand) lists only what was received by then (`validity::backdated_frontier_lists_by_cutoff_spec_perm_5_1`).
- **Chain writes count only through the frontier** (core/test/tla/roles M1): A's frontier lists by commit ID the role commits of its chain certificates for the target at R's point (§4: the writes on its paths, closed under their authors, so a grantor's own grant counts too; held, hence received); a forged one is not listed and drops, and A's grant reverts. An exemption for "A's own chain writes" whoever wrote them let X, after A removed it, write a backdated change to A's own grant (an `until` next week, a lower invite) that stood. Rejected narrower cuts: only the writes setting admin grants on A's own paths, read from the end state (missed a grantor's grant of A's grantor; the end state could name a later rewrite instead of the grant R rested on); exempting only chain writes that do not lower their grant (a second rule for a rare case). Residue: if A's authority at T rested only on a chain write A had not received (another verifier's view gives A a path A's own view lacked), that write drops and R with it; what R dropped in the same audit stays dropped. An honest node holds its chain, so the model generators mark each author's chain certificates as received (`roles_model::hold_chains`, TLA `Certs`); about a quarter of the writes that grant no admin are tagged written last (backdated forgeries); admin grants are never late, since an honest node does not act on authority it never received. About 1% of joint histories drop something.
- A snapshot's frontiers and `Absorbed` are no receipts (spec/crdt.md §8): a writer could list commits it signed ahead, or claim `X: 2^60`, and a demotion copying the claim would cover X's later writes for good. So a late joiner that got X's writes only through a snapshot does not list them; harmless, since hosts lose a commit's header only once every blob of it is deleted, i.e. every live write is carried by a covering snapshot, and that valid snapshot vouches for them at nodes still holding the now-invalid originals (`flows::late_joiner_after_compaction_agrees_spec_crdt_8`, `validity::late_joiner_after_compaction_keeps_writes_spec_crdt_8`).
- Clock skew: an end by `until` or self-removal is judged by the holder's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions).
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- **Re-grant validates the gap**: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it makes recovery from a stolen node's backdated mass revoke lossless. It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them. Tess: a re-grant revives all the account's writes, no special case; leaving writes out of a removal on purpose as a recovery tool depends on a side effect, so an admin who wants something gone reverts it explicitly. Don't build new uses on that side effect.
- **A removal makes its listed writes valid**, whether or not the author held the role when writing (spec/permissions.md §5.2); writes after an `until` rely on this. Side effect, a stated limit (Tess: "a strange thing for an admin to do"; no rule): a write made before its author was ever granted, which the admin happened to receive, becomes valid when that author is later granted and removed. The same holds for its purge requests (spec/requirements.md Deletion: a purge counts as an edit's validity does).
- **Frontiers list commit IDs, never counters** (Tess's decision; issues/session-sources.md rule 7). With counter frontiers a revoked actor could sign a new commit on counters its demotion covered: nodes holding the original voided both, but once compaction dropped the original and no snapshot traced the counters, new nodes counted the forgery. A fresh commit ID is listed nowhere, whatever counters it reuses and whatever its `ts` (`validity::revoked_writer_forging_into_covered_counters_spec_perm_5_1`).
- **What the demoter leaves out**: a commit only when every part in scope is one its own compaction could drop now or dropped as covered (`receipt::droppable_here`: covered by a snapshot it holds valid, purgeable by it, keep-at-least bound `MAX_DRIFT` past; the predicate `retention::drop_from` that node-sync's `drop_covered` uses, so compaction and the frontier never disagree), and it holds or dropped every part of the commit (a part on a thing it does not hold: listed). Those are invalid after the demotion and the snapshot vouches for their live writes, so a node holding the original and one holding only the snapshot read alike (`order::new_node_alike_spec_permissions_5_1`); their dead writes are what compaction erases anyway. Leaving out any covered commit instead made the superseded history of a kept aspect invalid, and any writer could write such a snapshot just before a kick (`validity::frontier_keeps_superseded_kept_write_spec_perm_5_1`; a rotation replaced inside `ROLE_KEEP`, `flows::rotation_within_role_keep_listed_spec_perm_5_1`). Kick cost: the uncompacted tail plus the keep-at-least window (Tess: accepted); measured, a node with 200 compacted writes then removed lists 1 commit on a default-retention aspect and 200 on a keep-at-least-1d one, 1 again past the window. Only coverers received by the cutoff count (for a dropped part its whole `retention::coverers` chain): a backdated revoke's demoted node may have written the coverer after the cutoff, and then it is not listed and vouches for nothing (`validity::backdated_frontier_lists_write_covered_after_cut_spec_perm_5_1`).
- Accepted residual (Tess): Y's snapshot Z covered X's commit c at the demoter of X; Y is removed later by a demoter that never received Z; Z turns invalid and c's live writes go, even where c's body is held. Listing every received commit (no droppable filter) avoids it at frontier cost; that is local policy.
- One dot still names one write: overlapping session-form ranges from one session void both commits (spec/commits.md §4). Honest nodes never overlap (every open draws a fresh session). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Role commits use commit form and a session-form one is bad input (spec/commits.md §3, §4), so a removed admin cannot void its earlier grants, revive a holder it removed or void its own rotations that way.
- Sync-then-revoke closes most of the loss from a frontier taken on an unsynced node (spec/requirements.md, Permissions); labels the node does not hold are read for receipts only (headers decrypted and verified count as received, spec/permissions.md §5.1; notes/node-sync.md Receipts-only reads), so removal needs no node holding the tree. What remains: writes at hosts the revoker does not reach, writes in transit, P2P-only edits among other holders, revokes issued offline; all recoverable by re-grant.
- Rejected: a timestamp rule (forgeable); accepting everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); a learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); roles by claimed time only (an ex-admin could mint backdated grants forever); other writers vouching for edits the revoker missed (a commit kind, a validity fixpoint over vouchers who are later revoked themselves, a per-node receipt clause and a tiebreak, for edits that reached another writer but not the revoker).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 judges edge writes one by one too.
- **Snapshots vouch** (Tess's decision; spec/permissions.md §5.2): a compaction snapshot counts iff its author could write the aspect at it, at the strictest role a carried write could need (admin for `keys.0` and `secrets.0`: a writer's snapshot could otherwise carry a forged admin keyset, inbox, deposit seed, admin box or tombstone under a dot nobody holds), judged as its delta by commit ID, so a demotion frontier covers it by listing its ID; a reader's snapshot gives nothing (malicious readers only waste storage). A valid one's carried writes count because its writer vouched for them, never re-judged per claimed author. Revocation stays exact where no valid snapshot carries the write; through another writer's earlier compaction a removed holder's unseen last writes may stay, consistently on every node, also those holding the invalid original (Tess: fixed by hand). A valid snapshot's copies count also where the original is held, and govern a held original they misstate (Snapshots and history, below), so holders converge.
  - The copy is the snapshot's write, never the delta's: un-merging an invalid delta removes its writes from its body, the state and the residues whatever a snapshot carries, and the snapshot's copy joins back with the payload it has. Keeping the delta's write whole under any dot a valid snapshot held a write of made reads depend on order (a snapshot carrying a fallen insert's creation without its char gave the char when held before the delta and not after; an equivocating writer's second commit under a carried dot stayed). Where a valid snapshot carries a write of an invalid delta the un-merge is a rebuild (`Unmerge::in_place` only otherwise).
  - A record (map entry, list element) whose creation a valid snapshot's copy keeps keeps the valid writes others nested in it, from whichever body (`Unmerge::strip`, `Fragment::remove_dots_keeping`): the entry is in the state, so a writer that put into it must see its own write, and its own later snapshot, which lists that write by frontier, must carry it (alike seed 4136).
  - Accepted: a valid writer can carry any write under any dot (it could write the value itself anyway; authorship is never exposed unverified, notes/api.md Attribution). A body dropped under a cover that later turns invalid counts as never received again and is fetched again (holders re-upload it: uncovered, so must-hold); with no copy left anywhere its writes are gone at every node alike (notes/engine-validity.md Carried writes). A commit one of whose parts a node never held and that was deleted under that cover applies there without it: a held snapshot of any validity listing the part stands in for it (Tess's decision; notes/engine-validity.md Snapshot authority).
  - Rejected content rules: any writer's snapshot carrying a revoked author's elements; "compaction snapshots vouch for nothing" (every element judged as its author's write; `core/test/roles-model` `content.rs` showed an "authorized at the snapshot's `ts`" variant diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered); snapshot authority plus per-claim judging (claims, per-write indexes, refills on late carrying deltas, and still a family of order-dependences). That divergence cannot return: a cover must carry what the snapshot it covers vouched for (spec/commits.md §5), so dropping a covered snapshot removes nothing.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual role grants are allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (record chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin grant on G could backdate a forged write to a time it held only the grant; removing the grant first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood (`core/test/roles-model`, `two_admin_paths_class_attribution`, `chain_and_edge_paths`). Path-based audits would also close it but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal falls with its grant: both are attributed to L's invite class on K (a forged redemption's self-removal kept after the finalization dropped its grant would burn the link and block the honest redemption). Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the time it held the role (the rejected claimed-time rule).
- **Acting** (spec/permissions.md §5.2): a commit naming an actor other than its author is valid only where the author's write on that actor would be (same `delta_valid`, needing write), so a valid commit's actor is its sender. Role commits must name their author (bad input otherwise): checking it inside the joint walk would make grant application depend on the actor's grants, join components on every role commit's actor, and change roles-model and TLA; nothing needs a role commit to act for another. Re-judged through `by_actor` when the actor's timeline changes (debug builds assert nothing flips outside the re-judged set). Not checked: what the actor itself may write (the author's rights decide). A demotion below write on M lists the demoted node's held commits acting for M unless each of their deltas but `created.0` is droppable here, so a node removed from its account lists its uncompacted tail and keep-at-least window, not every write it made as the account (Tess: a kick never scales with history). Receipts-only commits are not indexed by actor, so they are listed only as the aspects in question list them. `created.0` stays valid whoever acts (its record holds by its tid), else every record created as M would be listed forever.
- Writes to `secrets.0`, `keys.0`, `label.0` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering role-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Retained copy (a removed holder's copy; spec/permissions.md §3)
- The default is the `retain` field of `required.0^` (any thing, admin-only, no chat code; absent is erase): that aspect already has `^`, a kept-forever history, a valid-delta list, "in force at a key", no snapshot and no undo. The removal states the value: a plain reset is erase, reset plus a grant with `until` 0 is retain (`EdgeEnd`, `Edge::says_retain`). Why not a header bit: `until` 0 is already gone at every clock (no timer: a node behind the kicker's clock by `MAX_DRIFT` drops at once), and lies inside the signed `roles.0` delta so it cannot arrive apart from the removal. Cost: a removal saying retain leaves one dead grant on the thing until a re-grant replaces it. A tombstone value or a removal field adds a state every decoder must learn; a dead grant is the expired grant readers already skip. `retain` beside `rules`: the value is written whole, so concurrent admins changing the two lose one by key, and a toggle re-judges the thing as a rules change does; a separate aspect would need the settings machinery a second time.
- A later removal on a grant decides over an earlier one, by key; a node that erased first cannot come back (it keeps no more than the whole history, `any_order_keeps_no_more`). An `until` ending has no remover: it reads the default in force at its key (`retain_in_force`). A late setting joins (`required.0^` is not frozen content) and an `until` way reads it at the next role-commit or manual judging, so it can end such a copy, never bring one back (`any_order_until_keeps_no_more`). Without a later judging the copy stays: the holder could keep it anyway.
- Filling is the writer's: `flows::edges::written`; `retain_now` is "after every setting held". Link: K takes the target's default when made, so joiners' self-removals read it too; a later change of the target's default does not reach K (minor; the kicker's word still overrides).
- Node removal erases whatever the account's default (a removal from `Osis`'s own account writes erase unless told otherwise), and a copy kept through the account hangs on the account (`K/` record), so it goes too. Any-path: a copy stays while one way keeps. A self-removal states its own value (Tess: no protocol rule stops it; the app just does not offer it).
- Kick cost is unchanged: nothing per body. Keeping costs the removed node nothing new and is cheaper than erasing (no shredding).
- Accepted limits (Tess: keep the rules simple and consistent, state rare corners):
  - Every other removal reads the default, so under a default to retain a revoked link's L leaves a dead grant until finalizing resets it (one extra commit), and a removed thin client's dead grant is a way that keeps past its account's later erasing kick; a node's grant with an `until` reads the account's default.
  - A purge after the removal usually does not reach the copy (no label to hear it by), though one in a commit the node takes for another part applies (`keep_clients::a_commit_beside_a_copy`), and a purge pending at the drop goes with its commit unless another part holds it. Only ever less kept.
  - A hostile host can erase a copy-to-be only by hiding a second way that keeps, or a renewal of an `until`; a removal cannot apply without the value it resets, so hiding that value delays the loss instead. A denial only.
  - An `until` passing is judged at the time (the trigger's by-time list) and dropped once the node has heard out the labels whose closure holds what it would forget (`SyncEngine::heard`), so offline nothing goes: a renewal on the way and unsent writes from before the `until` come first (`keep_clients::an_until_passing_offline_loses_nothing`), and an expired share stays on a node until it next gets online. A host down, or one that never lets a pass finish, keeps it up to `ROLE_KEEP` after the loss was first judged (`LOST_HEARD_WAIT_MS`, per actor: a dead host of one thing delays only the losses whose labels it hosts). Hearing out is per label, not per write, on one `Leaving::timed` path beside the self-removal one; rejected: gating per node (one dead host delayed every timed loss) with three trigger scopes.
  - A client reads nothing past the `until` and a copy only once made, so an offline app sees an `until` share with a retain default go and come back as a copy when the node has heard out. A role commit received beside the expired grant that does not end the role changes nothing (`keep::a_commit_beside_an_expired_edge_waits`). A renewal made after the drop comes back by a re-seal through the stranded heartbeat (`keep_clients::a_late_renewal_comes_back_by_a_re_seal`).
  - A write made before the `until` and sent after the thing was rotated for the departure is refused by the host (the label closed to the old key) and lost with the drop: the window is until the next writer rotates, as for any late upload.
  - A removal of an old path that arrives after the node has kept changes nothing. A kept holder given the target after the node left it counts as a live way, so a node that also held the target directly with an erase grant keeps it (rare; telling needs when the holder held the target against when it held the grant). In a partial order a node may erase what the whole history would keep, never the reverse (`keep::any_order_keeps_no_more`). A thin client reads a copy as its account's app or through its own grant (notes/client-port.md §3, Kept copy).

## Role timeline (model findings)
Model: `core/test/roles-model` (Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test --workspace` runs the scenarios; `cargo run --bin roles-model -- [samples] [as|exempt|strat|stratw|frontier|edges|edges-prov|joint|disputes|disputes-random|digest]` searches (counterexamples printed shrunk, as traces; `digest`: notes/testing.md, Models): exhaustive up to 3 edge writes (first admin, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `edges` (`src/edges.rs`): projected rosters, links, invites (audited by level), per-op judgment, plain record-chain writes on a thing, finalizes. `joint` (`src/joint.rs`): the joint walk over several actors (record chains, holder actors, mutual role grants, ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs`: layer-2 scenarios (per-delta validity across partially synced things, snapshot authority at `ts`, the snapshot-of-snapshot divergence). `trust` (`src/trust.rs`): trust sets and disputes on `edges` and `joint` (notes/disputes.md, Model results).
- **Third-party witnesses judged by end-of-walk roles fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a holder by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the first admin's further-backdated revoke cancels a stolen node's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for edge writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin node's backdated removals stand iff the node removing it had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Demotions of a grant never audit record-chain writes.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it; node-sync writes that removal: `SyncEngine::finalize_links`, `until_link_backdated_grant_void_spec_perm_7`); plain record-chain writes on a thing (a removed node's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky. Also residue (Tess-accepted): a drop whose dropped write made its demotion a fall stays after a restart where the demotion is no fall (D only grows). Every node holding the same role commits computes the same residue, so it diverges nothing. Pinned: perm `scenarios::self_removal_dropped_without_residue_spec_permissions_5_1`, `sticky_residue_of_dropped_grant_spec_permissions_5_1`, `audit_drops_grant_and_removal_spec_permissions_5_1`, `unseen_leave_stands_spec_permissions_5_1`.
- **Self-removals are audited like any write** (Tess, simplicity): they keep only their looser authority (admin on the holder, none on the target) and carry no rotation. One through admin on holder M is attributed to the author's class on M and listed as a write on M; one lowering the author's own grant, to its class on the target. Never dropping them let a node removed from account P write backdated removals of P's grants everywhere that stood. Accepted cost: a leave the demoter had not received is dropped and gives access back until someone removes it again (re-seal covers the missing boxes). The honest demoter covers it: `Timeline::demotion_scope` adds the targets of the demoted node's applied self-removals through each thing its class falls on (their `roles.0` receipts survive forgetting). Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.

## Role history
- `roles.0` is never compaction-snapshotted: every role commit stays, and a node that starts holding a thing fetches and judges all of it (spec/requirements.md Scale states the exception). `secrets.0`, `keys.0` and `label.0` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta).
- Bytes: 364-371 B per role write, plus 34 B per commit a frontier lists. A 1000-member chat after a few thousand joins and leaves is about 10^4 role writes (3.6 MB); what hurts there is the joiner's CPU, not bytes: ingesting 10^4 role commits one by one takes 110-160 CPU-s (10^3: 1-11), mostly per-arrival timeline work and `apply: join` per `roles.0` delta, an implementation cost fixed by batching the ingest (issues/role-history-join-cost.md). Evaluating the timeline anew is 1.5-2.4 s at 10^4. The first admin's own edge write averaged 15-23 ms at 10^4 history (4.6 ms at 10^3), under the 50 ms budget but growing. 10^5 not run (the first admin's writes alone would take hours). Against the budgets (notes/testing.md): per commit they hold; a 2-3 minute join at 10^4 role writes is past "rare events under a few seconds".
- **Rejected: roster snapshots** (an record-chain roster snapshot with a ledger of ended tenures and their frontiers). Every write+ tenure and frontier had to stay forever (a write anywhere below may rest on any of them), so it saved only 1.1-2.6x for writer groups (20x only for big read rosters), a kick-heavy group at 10^4 could not write one, and it cost epoch-start rounds, linked frontiers and a second residue class. A join is O(role history) with or without snapshots (the ledger is), so the Scale exception is needed either way. Linked frontiers (extending an earlier frontier by link) save nothing in these shapes, since each kick lists the kicked member's own commits, disjoint. The frontier that does grow without bound is a single kick of a heavy writer (notes/testing.md long aspect: `TooLarge` at 3*10^5 commits).
- Measured (`scale::role_history::cost`, osis-node, release, by hand; shapes and how to run in its header; box at load 8-35, CPU-s up to 2x high at 10^3): one node writes N raw edge writes on one thing (no boxes or rotations); a joiner gets every role commit ("off") or one roster snapshot written at the end ("on", the rejected design). ## First admins
- Every thing's record names its first admin (spec/wire.md §3; a key actor's names its key): the tid commits to it, its edge is in the walk's initial state from the start and stored nowhere, and it is an ordinary admin, removable like any other. Why not "granted in the creation commit" with a creation authority: anything that lets a node write the first grant without admin could be reused to grant again later (the record is public to every reader, the creator can always write another "creation commit", backdated): a hidden admin. Fixed by hash, there is nothing to reuse. Why no authority above the admins (Tess's direction; notes/disputes.md): an un-removable authority is a hidden admin users cannot change. A removed admin can backdate a removal of its remover (n1 removes n0 at 10; n0 signs "remove n1" stamped 5, which the plain walk applies first), also on an account (a recovery key is an admin by a plain edge, so a stolen node that got there first can backdate too); the walk settles the fight per node by its trust set (Trust sets, below), and a node takes a side by default when it detects the dispute: the side it held first (notes/disputes-plan.md step 4), so a node that applied the honest removal before the backdated one arrived keeps it.
- **One authority class**: admin by any path (edge admin), or an invite level. A node admin of a thing's first admin is admin of the thing through the record edge like through any grant; losing that path while another keeps the class is no fall. So an admin that granted itself a direct edge on a thing below keeps it when its path above is removed, until an admin removes that edge too (one class, no "top" that outranks it; Tess accepts "a current admin Q that Y left in place voiding Y's removal silently").
- **Creation**: a record needs no authority (it is public); the creator names itself or an actor it holds write on (Tess, Q13: any writer of G may make a thing whose first admin is G; G's admins administer it, its writers write it). A thing is made either by its record alone (`Engine::create_with_admin`: one `created.0` delta, a role commit, spec/commits.md §2, so joiners fetching role commits first hold the record before the commits that need it; otherwise every pending role commit on the thing waits for it and is read again, `scale::joiner_reads_each_pending_commit_few_times`) or inside a content commit with its first writes (`Write::create_with_admin`, trees made in one commit, each thing's first admin possibly one the commit creates).
- **Removing the record edge**: no entry to reset, so the removal resets an entry of its own delta (`Mutation::fresh_resets`: a tombstone keyed by the holder at a fresh counter, spec/permissions.md §2). Its creation is that delta, so every reader resolves it at once, in any arrival order. A put-then-remove in one batch nets to nothing in the CRDT, so the tombstone is minted directly. An admin of the first admin removing the record edge leaves by self-removal (admin on the holder its only authority, spec §2); an admin of the thing itself removing it is an explicit demotion that audits the first admin's writes.
- **Record chain**: the chain walk (`osis_base::record_chain`) goes up first-admin links, so derivation, labels, inboxes, certificates and the `MAX_CHAIN_DEPTH` cap all count through it; it says nothing about authority, which the timeline reads from the record edges as they stand.
- **Secrets**: a plain thing derives from its first admin's epochs (spec/crypto.md §3); its first grant (or `sync`, which gives a label) gives it secrets of its own by the usual rotation from the derived epochs. Lowering the last admin edge of a plain thing is refused (`flows::edges::leaves_no_admin`, skipped under `skip_writer_rules` for tests): on a plain thing the only holder for keys is its first admin, so no other edge write on it exists and no "own secrets before any edge write" step is needed. Signed anyway, it stays plain and derives from the removed first admin for good (stated limit, spec/permissions.md §1). A derived epoch written under after the record edge went is read by the first admin's holders only (issues/derived-write-merge.md: rule 2 of the model, a stated limit).
- **Virtual record edges** (osis-perm): the walk's edge state (`Edges`) holds only edges writes set, plus the record edges writes removed (`cut`); `EdgesAt` and `View` read a record edge from the records (`Records`) where neither is the case (`RECORD_EDGE`, admin, no `until`). So a plain thing costs the edge state nothing (a kept state stays O(targets written + holders)), `Dense` materializes them for searches (its adjacency built by one push per edge and sorted once per holder, kept sorted by `set`: a holder of a million things costs no scan per edge), and a write that sets a record edge to exactly its record value is no explicit entry (canonical states compare equal). A record arriving late for a thing whose edges were walked: the undo entries of those writes were logged with the record unknown, so the resumed walk restores the record edge itself after rolling back (`Resume::fresh`); rejected: a full evaluation then (it is the common late-record case, `created_late_*`).
- Engine: `held.rs` names the first admin on the thing (`holders_of`, `reaches`) and indexes the thing under it in `first_admin_of` (one record-chain link down: `below` marks it stale when a record above it arrives), `write::role_with` gives a not-yet-held thing the first admin's role. The roster, current holders and holders for keys all include the record edge while it stands (`Timeline::roster`, `standing_since` with `None` for the record edge: an actor grant ordered before every write, never the one left keyless), so nothing reads the record as a right. A person's first admin is the node that made it; its recovery key holds a plain admin edge granted in the creation commit and recovers as an edge admin (`flows/person.rs`). A link's K has the sharer's actor as first admin. API: `Write::create_with_admin(admin)` (and `create()`: the acting actor); `Osis::create_ownerless` and `Write::create_owned_by` are doc-hidden aliases until the API work (issues/api-after-owners.md); `owner_of` reads the record's first admin (history, not a right).
- **Inbox and `label.0` reads stop at cut record edges** (`Core::inbox_chain`, `published_by_actor`): an actor's inbox is the one its `keys.0` names, else its first admin's the same way while its record edge stands at the sender, and so on up (a removed first admin would get blobs about a thing it no longer administers); a group's `label.0` and `created.0` go under the home label of the nearest labeled actor up its record chain whose record edges up to it stand at the writer. **One inbox rule**: every actor with a home label names it in `keys.0`, in the commit that makes it one (`flows::labels::takes_inbox`: an actor's first live label, a labeled plain thing getting secrets of its own (`rotation::own_secrets`: a chat made plain, labeled, then shared), or a replacement of the one named; person and link K too), because a sender may know a holder by its `keys.0` alone (certificates), not by its `label.0`: an outsider's grant to a team then lands under the team's own label, which every reader of it syncs, not with the first admin's nodes alone. The chain is for a sender holding an older `keys.0` that names none (the actor gained its label since), so a reader opens under every `keys.0` inbox up the chain (`Engine::inbox_candidates`, `inbox_actors`), and that one set is what the node treats as inboxes (smaller unvouched cap with bytes kept, clearing); a plain group's label is no inbox (a plain thing has no keyset to seal to) until it gets secrets of its own. Rejected: one label per actor at the reader (a stale sender's blob under the first admin's inbox would sit unread until its re-send, `INBOX_LIFETIME` later); a group's own label as an inbox without naming it in `keys.0` (outsiders cannot find it). Limit: blobs deposited under an inbox that is then replaced are not read; they come again with the sender's re-send, `INBOX_LIFETIME` later (issues/replaced-inbox-resend.md). Hosts: `admit own` takes labels of groups whose record chain reaches the host's node or account (records alone, static: hosting is ciphertext).
- Within one record tree nothing moves: rights are grants, so "move this doc to team B" is a grant then a removal (notes/moves.md), and the depth of record chains should match the units that travel together. Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `secrets.0` like any key-actor holder). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets; the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (and so one cascade rotation of the target); perm judges each edge write of a commit on its own, so such a commit is two removals at one point with one frontier. None of its grants may be a self-removal (refused by the writer rules). A several-grant removal under one rotation keeps the one-commit rule's guarantee, since the rotation excludes every holder it removes.
- **K's secrets are random**, not derived from the seed: with derivation every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every host) and write key, exactly the power the invite-only design takes from L; and L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K stranded L. So L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- **A link outlives K's rotations**: the rotation commit is wrapped under the epoch it supersedes (holders must read it to learn the new one) and its boxes and history box are all a late reader needs, so the entry box also carries that earlier secret (one, 32 B): the redeemer opens the rotation commit, and its history box opens all of K. Rejected: a re-seal of L in a commit under the new epoch (a commit more per rotation, and a window between a writer's rotation and an admin's step). Rejected: not rotating K on a leave (a leaver who kept the seed can come back anyway): a node removal rotates K all the same, so the path is needed regardless, and a leaver who discarded the seed (the SHOULD) stays out. What a user sees: a link works until revoked, expired, used up or a joiner kicked, however many people leave; a leaver holding the text can rejoin.
- Limits: one earlier secret, and with forks only the registrar's pick: a rotation in a fork it does not lead to stays unread until the next rotation. A commit on K pending behind it holds `redeem` to its timeout. A host holding K's head without its claim set (past its caps) refuses like a revoked link: with every other route failed too, it reads as ended.
- **`redeem` fails at once** (`Invalid`, "no longer works") on evidence only: a refusal of L's static entry (code REFUSED, not UNKNOWN_LABEL: L is in every step until it left) with every route of the label failed, so one host's word or one down decides nothing, or a held history that put L on K and ended it (`Timeline::ended`). An L not seen yet says nothing, since its grant may still be uploading; nobody answering waits until the caller drops it. `links` and `member_links` read the roster, which holds no key removed or past `until`, so what they list works.
- **A link's target is its text's word** (nothing signs it): `redeem` grants only after K's grant on the target is here, so a link pairing a target with another thing's K joins nothing, and `forget_link` has the lost-access trigger judge K, so what only L read goes. K's label carries the grant (delivery, then the sharer's certificate copy), so honest links reach it pre-grant, target unknown too. `Invalid` needs a complete pass of K's label and no commit pending on the target at the timeout: a node cut off mid-read hears `Network`, since an app reads `Invalid` as a dead link. Forgetting drops the hinted label's session too (K's commits may not be here yet, so `Forgotten.labels` lacks it): the secrets its head gave go with the key, and a retry must claim the head again. Not bound: K's first admin can put K on anything else, before or after a redemption, and K can be any actor with L on it (an existing chat holding a role on the target): a joiner then holds all of that too, and the link names only the target.
- **Finalization**: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer node writes a real removal; until then the link is honest-client-only. Node-sync (`SyncEngine::finalize_links` over `Engine::links_due`, any node holding the seed thing and admin on K, woken at the `until` by `next_link_expiry`) writes it after a complete pass of K's labels ended after `until` (passes from before going offline do not count), so the frontier covers honest grants that reached the hosts while the link worked. Without saved peers only the node that made the link finalizes, at once. A seed thing counts only when its first admin is K's first admin (a co-reader can add a `link:seed.0` thing to a shared group). A K whose label never completes a pass (host gone) is never finalized: the link stays honest-client-only. Residual window (Tess: keep, documented on `LinkOpts.until`: an expiring link closes when one of your nodes next syncs after `until`): while every sharer node is offline after `until`, or K's host is unreachable, a backdated grant uploaded then is received in that pass, covered and stands; cutting it would also cut honest late-received grants (both carry `ts` < `until`). Future option: a host receipt time as witness, one feature for removals and link expiry together (issues/revoke-needs-whole-tree.md). Idempotent: `Timeline::lowered_unaudited` (the walk's `prior`) is cleared by the first explicit write, so a second node's concurrent removal restores and audits nothing. Alternative (no `until` or single use at all) loses nothing a hostile holder respects.
- **Race flip**: the finalization's frontier can drop a competing redemption the sharer had not seen, so a redeemer that lost by its own view may win; a loser therefore keeps K's secrets and labels while L's self-removal is unfinalized (`contested` in `rotation::lost_among`; `single_use_loser_keeps_secrets_until_finalized_spec_perm_7`), and drops them once the removal arrives. Only redemption-shaped commits count on both sides (the void one and the applied one that lowered the signer's grant): a plain leave then a void grant defers nothing (`void_grant_by_leaver_keeps_no_secrets_spec_perm_3`; otherwise any self-left holder could keep any removed holder holding the thing's secrets for good). Residual: an inviter whose leave commit also granted someone can later forge a void redemption naming a removed holder, who then keeps the thing's stale secrets (no new epochs) until an explicit write on the inviter's grant. Cost: never finalized (sharer gone, a K host gone for good: `complete_pass` waits for every host), the loser follows K's and the target's labels for good. Not bounded in time as pending grants are: past a bound the race flip would leave the winner unaware again. Rejected: inbox delivery of the removal to the joiner alone (the loser had already dropped and forgotten the target's secrets, and nothing brings them back).
- **A removed node keeps the seeds** of the account's links (they sit in the home group), so it opens K's head by L's static entry past the removal's rotation until each link is revoked. Not ended by the removal (a link shared in advance dying because a phone was replaced would surprise), so `remove_node` returns the account's working links and the caller decides (`node rm` prints a revoke line per link, `--end-links` ends them). Any node of the account can list and revoke any of its links: the seed thing carries K, seed, target and single use. A link made on the removed node and not synced yet is unknown here; whoever holds that node can redeem before the revocation and stays a joiner, as with any link holder.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): a link conveys "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add grants for actors with no current grant, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier. Inviters seal only secrets they hold (their role and below). Holders read K's roster, like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- A sharer rotates its dialable key and LAN secret when a link ends (spec §9), since the link text may be in strangers' hands. A single-use link finalized by its redemption does not: its one possible user holds a role and keeps the direct path.
- Self-removal lets an actor always leave or lower its own grant; single-use links use it to drop L's own grant.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (kicking one joiner otherwise kills the link for all, spec/permissions.md §7).

## Patterns
- **Grant on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per holder, so not per note in a folder).
- **Shared actor** (spreadsheet): one actor is the first admin of everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: a minimal root actor whose admins are a few accounts; teams, chats and docs have the root or actors under it as first admin. Root admins can remove anyone below, and a departing founder is just an admin removal; a team can shed the account that made it (its first admin is an ordinary admin).
- **Shared tag** (rights live on grants, never on grouping; notes/tags.md): the tag is an actor; things keep their record and each gets a grant for the tag's actor (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same grant so rosters nest; writers may also create things with the tag as first admin. Per-holder grants on each thing do not work: entitlement puts a thing under the tag's label only when the tag's actor may read it, so no label the holders sync would carry it. Built in core/osis/tests/it/tags.rs.
- **Chat**: notes/chat.md. **Realm** (design): notes/realms.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and their grants, and `group.0` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and actors stay separate; a group may also be an actor when it serves as a shared label.

## Required retention (`required.0^`, spec/commits.md §5)
- **Prefix, longest match**: no matching language; expresses one aspect (`name.0`), a per-year family (`chat:msgs:`) and everything (empty). A name-without-version key could not express the family. The empty prefix is what stops junk on an aspect nobody named.
- **Exact match, no ordering**: purge sets are not a scale, so "at least as strict" means nothing. A duration is part of it because retention on the wire includes expiry and a required permanent retention must rule out expiring writes.
- **Key order, as an admin-only aspect**: the setting in force is a function of held deltas and the timeline, so every arrival order agrees; a fall re-judges later deltas (`in_force`, the thing re-judged when a setting commit is, acting included). Same-commit deltas are not under it: "before the key" is strict.
- **Whole value, read a delta at a time**: judging needs no CRDT replay up to a key. Writers turn `set` into a replace; a hand-made partial delta only hurts its admin. The CRDT state and the rule can differ only on two admins in one ms.
- **Fixed `nobody`, kept forever, never snapshotted**: a later node must judge an old delta as everyone did, so the setting's history cannot be compacted. Cost: one body per change, admins only.
- **Bodies**: dropping a broken body everywhere would let an admin stamp a change below existing history and erase a `nobody` or author-only body with no right. So a node drops only what it received after the setting (its own `received`; a tie keeps it), and holders of older bodies keep them; a backdated change invalidates (as an empty-frontier demotion already can) but erases nothing they hold, and removing that admin brings it back. The dropped part is a `Dropped { broke }`: reopened as missing when it turns valid, fetched again. A pass drops only with every entry of the label open, so a role commit still to come cannot be what would have saved the body.
- **A broken delta falls alone**: a commit's other deltas stand. Taking the whole commit let an admin of thing C decide a delta on thing D of a commit naming both: a member of D alone never holds C's setting, so reads differed for good (`commit_across_things_reads_alike`). A missing broken delta holds nothing back (spec/commits.md §4).
- **Hosts**: a node that dropped a body and holds the label's delete key deletes it at the host; a holder does not put it back while it is invalid, so a new node never receives it while the setting stands and reads alike; once the setting falls a holder uploads it (`setting_below_a_body_erases_nothing_held`). Under a hostile backdated setting that stands, the bodies live on their holders' nodes only: if every holder is gone by the time it falls, they are gone. A hostile admin has the delete key anyway; holders re-upload a valid body, not an invalid one, and that is the whole difference.
- **A setting by one not a possible admin goes without a right**: it binds nothing, and `nobody` with no exception would be junk a mere writer leaves forever on every node, in memory too (`ix.required`). The author alone counts: a delta is judged by its author's standing, so a header naming an admin as actor saves nothing. A possible admin's setting never goes (`Held::ever_admins`, any validity, only grows; `first_held` would count or drop the same setting by whether the signer's grant had fallen yet: `signer_whose_grant_fell_alike_in_every_order`). A late grant may find the setting gone (a grant at one host not yet relayed to another, an admin there drops the setting and deletes it at that host: `setting_before_its_grant_comes_back`): if it now stands it is fetched again (`unbreak`) and a holder puts it back. The one loss: the setter's only copy was that host's and the setter is gone before any other host has it. Bounded by `MAX_REQUIRED_ENTRIES`; an admin's count of settings is unbounded, one body each.
- **Cost** (release, one aspect, 10^4 and 2*10^4 deltas, linear; load about 25): a setting flipping every delta 110 and 250 ms, about 12 us per delta, so 12 s at 10^6 with the engine lock held (the class of the long aspect table's fall of the 30% member, 11 s), and only an admin can cause it; a setting that stands and flips nothing 6 and 12 ms; a writer's, invalid on arrival, 0.4 ms at any size. `Judge` judges a thing's settings once, so fallen ones add one walk, not one per delta. `drop_broken` over a whole thing decodes only headers of invalid commits.
- **Snapshots**: exempt, so a writer's snapshot may carry what it held of a broken delta, as for a demoted writer's write (it vouches). The rule is about bodies that cannot be removed; a snapshot is `writer`, so anyone with write removes it.
- **Accepted**: a member from before a change can backdate below it (set it at creation to rule this out); a writer that has not seen a change writes invalid deltas until it does, told by `OwnWriteInvalid`; a late copy of a dropped body is held until the next pass drops it.

## Purge rights and retention
- Retention is per delta (spec/commits.md §5), decided with Tess. Default `author_or_admin`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and keep at most 0 after replaced implies it. `nobody` is for records even admins must not drop. `admin` is what role commits use.
- Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (Tess's call; hosts approximate it, notes/sync.md). The right is exactly validity (§5.2) of a delta needing the role at the request's key, so a re-grant gives back a gap request's right as it does its writes (else a re-grant revived the reset but brought the purged value back: seed 3001).
- Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever; a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart.
- Fields are immutable: a change would need the blob re-encrypted anyway (commitments are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.
- **Lasting headers** (spec/commits.md §5): a purged permanent delta's commit keeps its header at the label for good (about 300 B), and so does the purge commit naming it (without it a new node never applies the header-only blob). Tess: "if history is on, the cost of keeping history is expected". The header-only blob goes up only when no other body of the commit is wanted at the label.
- **A purge follows the timeline, both ways** (Tess: a purge setting is a promise; deletion that is rightful really deletes; a wrong one must not destroy what honest nodes hold). `Timeline::purge_stands` reads `delta_valid` as well as the role at the key, so a request a demotion's frontier leaves out holds no right whatever its `ts`. `retention::rejudge_purges` runs at the end of `rejudge_once` per aspect with a held request on a re-judged thing (`p/`): a part a request comes to drop is purged, a part dropped for one that no longer does goes through `reopen` to `missing`, the one mechanism `Dropped { broke }` and `uncover` use. Not kept per body: own-write parts read the value-less list, others one flag bit.
  - No settling window at hosts: at 0 the demotion-first holder restores, at infinity a rightful purge never deletes, so a value could only turn "usually" into "more usually" (fails notes/arbitrary-values.md). A node syncs a label before it deletes under it, so the window is only a demotion not at that host yet, the same a hostile admin before removal has. Lost for good: only a body every holder dropped before any heard of the demotion. A holder uploads a must-hold body and a stale node deletes it only until that node syncs the demotion, which lies at the same host: judgments are functions of the held set, so the war ends.
  - A holder that saw the delete still uploads though the body's writes are carried (`Engine::named_by_a_fallen_purge`, `delete_stands`): the delete-keeps-it-out rule assumes a keep bound passed. A stand-fall-rise with no copy left must leave what a node never seeing the fall has, or an older value resurfaces: a delta's `w/` row outlives the fall and counts only while it is value-less (`make_valueless` joins it when no body gives one, covered parts too); a snapshot's stand-in is a bit (`Dropped::stands_in`), set on any drop other than as covered, so after stand-fall-rise with no copy it stands in again (seed 32032).
  - A frontier lists requests by `requests_resting_on`, not by the things where the class falls: the right by author runs signer, actor, thing, and the signer may keep its own grant on the thing (a node removed from its account). At the list bound (`receipt::fit_requests`) the requests received last go, so a heavy moderator stays demotable and a flood lands last; rightful or not they fall (a hostile flood reaches only requests of the same demoted set). A header-only blob left from a fallen purge stays at the label as may-hold (300 B each, spec/sync.md §6): deleting it needs every node's agreement that it is not lasting.
  - The gate is separate (`counts_as_purged`): a missing delta counts as held on the word of a possible right holder (`Held::ever_admins`, `ever_writers`, monotone), or a demotion's place in the order would decide whether a commit applied; `known_purged` still decides the stripping. Snapshots dropped for carrying do not say whose values: all come back with a fall; one carrying another's standing purge goes again on arrival, so that value stays gone. Where no node has its body it stays missing, and what it alone covered goes missing with its live writes until a writer's next snapshot, which every writer takes after a purge. Rejected: `reaches`-style rules using a snapshot's kept frontiers (dropped without the body they judge differently from a node that saw it: order::purge seed 890023).
  - **What reverses a purge**: only a demotion whose frontier omits the request. A demoter's frontier lists every request of the demoted node it received on a thing in question, for a fall below admin too (`Engine::frontier`), so an honest demotion reverses only a request the demoter had not seen (the backdated or raced one this rule is for). A hostile current admin can omit on purpose (§5.1) or backdate: the purges of the one it demotes fall, and the deleted values return only from a holder that kept the bytes, as a holder could show them anyway; hostile admins are out of scope and could re-post the text. A demoter that never held the request (a fresh node past `ROLE_KEEP`, non-permanent delta) makes it fall too; the body is gone at honest nodes, so that reads as never received: only a node still holding the body brings a message back (`tombstone::a_fresh_node_demotes_and_nothing_comes_back_spec_perm_6`).
  - `snapshot_right` shares the rule without the listing: after a demotion below admin an admin's old snapshot no longer lets a node drop bodies under `admin` (a growth price, no data loss). It is read by `drop_covered` and `droppable_here`, not by `covered`, so reads and must-hold are unmoved. Snapshot stale drops stay dropped: making a no-right snapshot not cover for must-hold does not converge (issues/covered-body-new-label.md), and the dropper held the right itself.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the host (host stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with Tess, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous holder: a fresh actor with its own recovery key and node keys, joined via a link or grant; the granting admin may record pseudonym -> account in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Holders write as A in commit form. Caveats: any holder can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a node the holders trust re-signs their edits under its own identity.

## Snapshots and history (spec/permissions.md §5.2)
A snapshot is trusted for current content only, never for authorship or time. Otherwise a valid writer's snapshot copying another value under the dot of a delta its holders had dropped before others got it showed the original at the holders and the copy elsewhere, for good.
- **Content**: every node follows a valid snapshot's copy, also where it holds the original: where a held delta and a held valid snapshot disagree under one of the delta's dots, the delta counts for nothing there and the valid snapshots' copies join by the copy order (the tie-break between disagreeing snapshots). Nodes holding the same valid snapshots read the same whatever deltas they hold. No worse than the writer writing the value itself; later writes win as usual. Only valid snapshots count, so a reader or a removed writer (frontier not listing the snapshot) changes nothing; a snapshot turning invalid gives the held original back. Mechanics: notes/engine-validity.md (Carried writes and vouching).
- **History**: authors and times come only from verified commits held here (notes/api.md Attribution); content known only through a snapshot has none. Nothing attributes through snapshots: the commit query and `created`/`changed` read held headers only (snapshots are no change), a watch names the commit applied (a snapshot correcting a held original is reported as the snapshot, its author and ID), undo and revert act on held commits.
- **Detection**: a node holding the original reports each misstating valid snapshot (`DiagnosticKind::Misstated`, from the rebuild that applies it, deduped; not for value-less copies alone, which an honest snapshot taken after a purge not yet seen here carries).
- **Residuals**: a copy misstating a delta this node dropped cannot be compared (the body is gone): it joins by the copy order with what the state kept of the original (a valued copy beats a value-less one), so where the original wins that order a node without the residue reads otherwise until both hold a snapshot carrying the original (a covered drop's cover does; a drop for keep bounds leaves only the residue); a snapshot turning invalid leaves its copies under dots of deltas whose cover was dropped for its bounds (the state alone holds those writes).

## Admin-only aspects (Tess, AK format decision)
The `^` marker in the AK (spec/data-model.md §2); a delta of one needs admin, judged by validity like content with admin in place of write (spec/permissions.md §5.2), from the key alone: no wire bytes, no schema. Engine: `write::required_role` (local refusal, layer 2, snapshots via `snapshot_role`, ephemeral parts). osis-perm's `delta_valid` takes the required role; a demotion's frontier covers `^` aspects with the role-class ones (`Engine::frontier`; without it an admin demoted to write lost every `^` write, covered or not). The roles-model's content model abstracts the role threshold, so it covers admin alike. A writer's `delete` of a thing holding a `^` aspect fails `Permission` (it would remove it). Tests `validity::admin_only_{aspect_needs_admin_spec_perm_5_2,snapshot_by_writer_invalid_spec_perm_5_2,write_covered_by_demotion_frontier_spec_perm_5_1}`.

## Implementation (osis-perm)
- **Record chains**: every walk up creation records (engine, osis) is `osis_base::record_chain(t, lookup)`, yielding `ChainStep::Up` per first-admin link, then a key actor, an unknown record, or `TooDeep` past `MAX_CHAIN_DEPTH` links; callers differ only in their lookup (held, ephemeral, a commit's own records) and what they do per step. perm walks no chain: effective role follows record edges one at a time with no depth cap (spec §1 defines it by paths; the engine judges writes on a too-deep thing invalid).
- **Input**: the node implements `HeldSet` (things, role commits with an edge write per thing, `created.0`; applied commits only) and adapts headers into `types` records (edge ops with their `roles.0` dots, frontiers resolved from links). perm parses no bytes, holds no state, depends on osis-base only. A `created.0` that does not hash to its tid is ignored. Value conversions of `edge` and `frontier` belong to the core aspect types (osis-schema `core_types`); perm takes decoded records.
- **Queries**: `Timeline::evaluate` is the from-scratch walk (`walk.rs`); queries take `At` (state before a point, edges alive at a ts; `At::END` = current state at the end of time, where re-grant is judged): `roster`, `role`, `invite`, `class`, `standing`, `applied`, `dropped` (with the dropping demotion's point), `demotions`, `delta_valid` (layer 2), `certificates`/`write_certificates`/`certificate_set` and `verify` (§4), `may_purge`, `may_rotate`, `demotion_scope`.
- **Incremental** (`Timelines`): components of things joined by edges, authors and records (a thing with its first admin), each evaluated from scratch and cached by its exact inputs; `changed()` lists the things whose component the last update evaluated (the node re-judges only deltas on those, plus commits whose void, required-role or overreach inputs changed; everything after a rebuild at open; a debug assertion checks the rest is unchanged).
  - **Extend**: a component that only gained role commits continues its walk (`Timeline::extend`: same things, `created.0` and nodes): the final walk rolls back to the earliest new commit p and goes on. D is kept in the order the final walks found it (`Walked::found`, saved in the walk cache): the drops found before the first one found by a write at or after p are found again, in that order, by an evaluation from scratch (every walk up to them saw only items before p, and each walk under a prefix of D finds nothing before the next drop's point), so they stay; the rest are forgotten and the walk rolls back to the first write they dropped too.
  - **Append fast path** (`Timelines::append`, `Timeline::append`): when every touched thing is in a component, its `created.0` unchanged, and it only gained commits whose author, holders and targets are in that component or are new nodes (nothing held of them but a key actor's `created.0`; they join it), the component is neither re-partitioned nor gathered again: the timeline keeps its `Input` and walk items (role commits are commit form, so no session-form range can void one). A new node can join because nothing it reaches is held yet, so no earlier audit met it (`Input::may_be_node`). New commits go in in timeline order; each is placed without walking again where exact (`Walked::insert`), else the walk resumes from it.
  - **Declined** (resume from it): a drop of D found at or after it (found by an earlier walk whose state there is not kept), a later item writing an edge it sets (that write's restore reads the new value), two of its ops on one edge, and its own audit dropping something new (D grows).
  - **Which later items may read it** (static, over `Input::ever`): with (M, T) its edges, roles change only for what reaches some M at any time (A) on what some T reaches (F), and only up to the widest role among the edges' values before and after; so classes change only through an admin value or an invite, demotion thresholds only through write or more; reaches change regardless. A later item may read it by an author in A judged on or for something in F (when classes may change); applied explicit on (m, t), by m in F, and when roles may change by t in A, a new node reaching m, or m reached from A with t reaching into F; a later fall of its author on a target it applies on; and, where its author's first held write on a target moves to its point, an explicit write after it up to the old first write whose holder the author may reach and whose target may reach the target. With none, its changes, undo entries (`by_author_target` in walk order) and mark are spliced in directly (`place_plain`).
  - **Shadow placement** (`place_shadowed`): a shadow `Pass` (`Pass::shadow`: the edge state at its place, its edges' records copied from the end state; audits also read the walk's own write records before their point, `outer`) walks it, then follows the history to each such item and walks it again: its edges' records before it come from its undo entries, the cached roles kept as `change` keeps them and restored after each item. Its effects (history, undo entries, applied records, demotions and falls) are compared with what the walk recorded there (`Walked::recorded`); equal for all, its own effects are spliced in and the falls the moved first write brings are put before the recorded ones. An item of the A-audit kind alone is first checked cheaply (no node of A reaches its holder, or its target reaches nothing of F: skipped). A re-judged item costs about 0.5 ms at 10^4, so past an eighth of a long rest (512 items or more) the write re-walks instead (`SHADOW_SHARE`, a cost choice; debug builds can force either path per thread, `force_shadow_guard`, and a test runs both on the same arrivals); figures in issues/perm-eval-cost.md. When an item does otherwise or drops something new, the walk is exact up to it: the commit's effects are spliced in and the walk goes on from that item (`Placement::From`).
  - Debug builds compare every shadow placement, every `From` continuation and every joining `extend` with a from-scratch walk on inputs up to 400 commits (`Walked::check_scratch`: history, applied, D and its found order, demotions, falls, edges, edge and write records, marks, undo entries per item). Tests: `append_adversarial_*` (random late arrivals, 3000 samples on three seeds, two nodes only some writes name), `append_shapes_*` (record chains, nested teams, `until` on every role, invites of every level, two-op commits, batched arrivals, restarts from saved walks; counts placements), `incremental_equals_from_scratch` (both modes; random and timeline-order arrivals, 2000 samples, dropped points and roles before every applied write compared).
  - A record can grow under its commit ID (a commit's edge writes arriving late): `append`, a cached component and `extend` compare held records with the walked ones by content (frontiers by size), not by ID (`Input::holds_commit`). Checkpoints and `first_held` carry by the history prefix the resumed walk reports as shared (`Outcome::common`), not by copying and comparing the whole history.
  - **Point queries** read an edge state kept every 32 history changes (`checkpoints`; `Edges` shares its per-thing maps between clones until written, so a kept state costs O(things); `Arc`-shared with the timeline `extend` makes) through an overlay of the changes since (`EdgesAt`, `View::at`: no copy). Late-write placement keeps the kept states: one later than the insert moves by the inserted changes and takes their edges (`independent`), shared maps stay shared (`Edges::set_all`), a gap past twice the interval gets a state; `Items` finds a commit by its point. `delta_valid`, `first_held` and roles at `At::END` are memoized per timeline; `extend` carries `first_held` answers found before the first changed history change.
  - **`first_held`** (where the node first held the role, re-grant's start) replays the node's roles over the history: a change of an edge out of something the node does not reach is skipped, a wider one raises in place (`roles_raised`), and only a narrowed edge that may have carried a role or an expiry searches again (debug builds compare with a search at every change, `regrant_replay_equals_search`). Rejected: a static filter (changes on edges between things on some path of the union of all edge states): in the org bench every holder reaches nearly everything through teams, so it filtered little.
- **`update_touched(held, touched)`** re-partitions only the components of the touched things and those newly linked to them (equal to `update`) and returns `Changed`: components evaluated anew, and, for those whose walk only went on or that only gained new leaves, the things touched.
  - **New leaves** (things only their `created.0` names, their first admin's component gained no commits, each above its root) skip the re-partition: `Timeline::add_leaves` does what `extend` would (record links, `alias_leaves` at the log's end, `first_held` kept) without gathering the held set (a re-gather cost 0.13 ms per thing already in the component, per commit, for a commit creating things under a big group). `creation_fast_equals_*` compares it with the general path (`Timelines::set_general_only`): `Changed`, from-scratch results, and that saved walks sit only under roots (a root moved by a leaf is retired, as is a root whose `extend` failed).
  - The walk records demotions only on the things it reached, so a new leaf takes its first admin's (`Walked::alias_leaves`, in `Timeline::extend` before any commit resume: the first admin's demotion vectors copied top-down, so chains of new leaves work; an `Undo::Demotion((x, leaf))` after each `Undo::Demotion((x, admin))`; `marks` remapped; one linear pass). A thing an earlier write names whose `created.0` arrives late, every thing below it, and a new node join the same way (`Timeline::joined`): before the first item naming any of them the walk is the same but for the demotions on those things, which take their first admin's recorded before that item; the walk then goes on from that item (its record edge put back in force after the rollback, `Resume::fresh`), D kept by the found-order rule. Declined (evaluated): a record gone, a node gone that has no record now, a new node first admin of a thing walked before, a record changed under its ID. Oracle argument: in a from-scratch walk a leaf's record edge is its only edge, so every node's role on it is its role on its first admin at every point and its demotion records equal its first admin's for every node other than the leaf itself. Without aliasing, validity was order-dependent (a holder offline through a revoke took the item as a leaf after the demotion and kept no demotion on it); a re-walk from the first demotion instead cost 0.4-1.9 s per new thing under a much-demoted team, against about 40 ms. The node re-judges below those only (notes/engine-validity.md, Validity).
  - `update_region` continues any cached component whose things, commits and `created.0` records are subsets of the new one's (the one with most commits), and reports the things whose `created.0` arrived as extended.
- **Saved walks** (`cache.rs`; the node's `node/walks` table, notes/engine-store.md Open): `Timelines::to_save(salt, min, all)` encodes a component's whole walk (`Walked` with undo log and marks, D in found order, passes, `reach`) under its root (first thing), with its `Inputs` (things, commit IDs, `created.0` tids); `update_touched_cached` restores a component with no timeline in memory from a walk saved under any of its things whose inputs are a subset of its own, continued by one `Timeline::extend`; else evaluated. Every other walk found under its things is retired (deleted by the next `to_save`). `to_save` changes nothing; `saved` applies its `SaveDone` once the writes are durable. Unit = BLAKE3 tag ‖ body; the tag covers a format string, the salt (the node's rules tag), the walk's whole input re-gathered from the held set restricted to the saved IDs and the body, so other rules, inputs or damaged bytes are evaluated from scratch, never an error. Frontiers are tagged by their sizes only and referenced by where the input holds them (`HeldSet` documents that a record's frontier is fixed by its commit ID); hashing their contents cost O(frontier) per save and restore (48M IDs: 0.9 s). Tids are indexed (things, then others in first use), commit IDs by their place in the inputs. Saved when a component evaluated or continued has at least `min` commits and grew by a quarter (and `min`) since its last save: amortized O(1) per commit (saving at every commit would about triple a commit's cost at 10^4). Tests: `restart_from_saved_walks_equals_from_scratch` (restored walks re-save byte-identical), `damaged_or_foreign_saved_walk_is_ignored`, `saved_walk_under_old_root_deleted_after_restart`.
- **Walk cost** (`walk.rs`): every state change logs its inverse with a mark per item (`Undo`, `rollback`), so a walk that grows D resumes at the first write D now skips and `extend` rolls back. Per-node `roles_from` is cached across writes (`Pass::roles`), dropped only when an edge change may narrow it (`widest_changes`) or an edge it followed expires, raised in place when an edge widens. `audit_fall` reads every candidate X's role on the holder, the target and its invite-holding holders from one backward search per thing (`roles_to`), or, for at most `FORWARD_MAX` (4) candidates, from their cached forward roles; it searches forward only for an X the restored edge raises, with what each thing's standing reads besides roles (`graph::Reads`) taken once per audit. Edge state for searches is indexed by number (`graph::Dense`; debug builds compare with `View`).
- **Chain certificates** (`cert.rs`, what a demotion frontier lists; spec §4): for (n, t), the things on any path that ever existed from n to t (`Input::ever_forward(n)` ∩ `ever_back(t)`, every edge any held write can set, and record edges), and every held edge write between two of them, applied or not; closed under authors. One index of held commits by (holder, target) per timeline (`Memo::certs`), one forward and one backward search per (node, thing) of the closure. Point-free, so it holds whatever any walk had at any point: a verifier must see every path an earlier walk had (drops are sticky, a write it audited without dropping stays), every demotion of the node on a path gained after its write, and an edge the node left itself. Rejected: closure at a point with later-demotion rounds; each of those needed a failing seed (pinned as `certificates_carry_*` and `certificates_self_demotion_regained_*` in `tests/it/queries.rs`, OSIS_PERM_SEED=90731, 115000, 116000) and cost 0.2 s at 10^4. A dropped demotion is kept because it can still have dropped a write on a projection. The projection oracles (`certificates_project_joint`, `_edges`) check applied, dropped and the author's standing per write, and each node's role on each thing at every write's point from its own certificates, against the full evaluation, sticky residue skipped.
- **Measured** (perm `tests/it/bench.rs`, release; an org of 311 nodes, 221 things; box load given): 10^4 edge writes from scratch 0.3-0.5 s (load 4-16), 10^3 5-8 ms; `drive` at 10^4 1.39G instructions (callgrind), 3000 writes 178M; certificates at 3000 116M instructions, at 10^4 7-12 ms (347 commits; with 628 drops 6-11 ms) against a 0.27 s evaluate; a late write placed without a walk (`bench_late_write`) 3.2-3.9 ms at 10^4, 0.5-1.0 ms at 10^3 (a re-walk of half through `update_touched`: 0.36 s at 10^4, 11 ms at 10^3); one more write 18-22 ms; appends 0.22-0.25 ms per write at 10^4, 0.11-0.19 ms at 10^3 (through `update`, which re-partitions and gathers: 38-84 ms, 5.6-10 ms); 1000 admins' deltas judged cold 3.5-6 ms, 1000 holders' deltas cold about 0.15 s; a role at a mid point 0.27 ms; a record chain at depth 64 1.3-2 ms; point states every 32 changes cost +60 MB peak on 12.9 GB (with full copies instead of shared maps: +1 GB); restart from the saved walk at 10^4: saved in 23-26 ms (1.5 MB), restored in 50-60 ms against 0.49-0.6 s from scratch, restored and continued over 100 later writes 76-112 ms. Node, `scale.rs role_change_and_open_cost` (release, load 3-8): the first admin's 10^4 edge writes on one component 11.4 s (timelines 0.66 s; the rest is apply, rejudge, store), 10^4 writes by 5 admins with demotions every 40 delivered to the first admin 43 s, the first admin's open from the saved walk 0.37 s.
- **Self-removal attribution** (`Attr::SelfRemoval(class, on)`): listed in `by_author_target` under (author, `on`), the holder for one through a holder, so a fall on that holder audits it; its frontier coverage reads the write's own target. `Input::first_write` (which gates recorded falls) also keys each op's holder other than the author (`written_on`), and `Walked::insert` treats those keys like targets; a commit whose self-removal goes through a holder is not placed incrementally (rare).
- **Purge author right**: the actor the delta's commit acted for (header field 2), held by any node with write on it while it has write on the thing. `PurgeBy` (osis-base) is five named sets, no scale. Consequences of `author` Tess accepts (no exceptions, spec/wire.md §4): an author who lost write leaves bodies no one may purge until re-granted; a hostile `author` write stays. A body under it still goes at an absolute keep at most (`retention::abs_timer`) or expiry; at hosts then by a label delete key. A purge acting for an actor (a client) drops what the node and the actor both may, judged at receivers, so a held or unsynced `author` delta of the node's account is safe from its client admin. A snapshot drops a covered body only if its own commit holds the right (`retention::holds_right`; `snapshot_right`): a plain writer's snapshot under `author_or_admin` drops only that writer's bodies (measured in notes/growth.md). Must-hold stays by coverage alone (issues/covered-body-new-label.md says why). `nobody` is must-hold while kept. A promise covers what honest nodes keep; hosts carrying a thing follow its labels, so taking a thing off a label deletes there whatever its retention (Tess's latitude, coordinator's call).
- **Readings of §5.1 the code fixes** (the models follow them):
  - R demotes X on N when R is an explicit write (applied, not a self-removal or invite grant) on edge (M, T), X reaches M (or is M), N is reachable from T (edges of any role and `until`, record edges included), and X's class on N is below its class with the edge restored "as if the holder still held the role": the join (componentwise max, alive) of the edge's values since the last explicit write on it, plus, for a node that lowered it by its own write, that node's values before. A value already expired when written restores nothing. So a gap left by `until` or self-removal is finalized only by the next explicit write on that edge, not by any write concerning X (a per-node "held class" cross-wired things in the joint model).
  - A's chain writes: the writer adds the commit IDs of `Timeline::certificates(A, target, R's point)` to the frontier (`flows/edges.rs`), and a frontier's commit IDs cover session-form writes too (`Frontier::covers`). The walk exempts nothing but R itself.
  - **What R puts in question** (`Timeline::demotion_scope`, `scope.rs`) is read from the settled walk with R appended to a copy of the timeline, not from standings beside it: R's audit can drop a write that held up another standing (the demoted node's grant to Y, its own self-grant), so the fall at R depends on R's frontier, and a scope from the walk without R loses honest writes. The scope: per node, things it falls below a role on at R, things its class falls on with the targets of its applied writes attributed there, the targets of the writes R drops. The writer (`remove_signed`) starts from the scope as if every held write were received (`Timeline::all_held`: no drops, so no re-walk), then builds the frontier from the scope and asks again until the answer is inside it (only grows; usually two probes). Then no received write on an aspect R puts in question is dropped. The probe's `ts` is the HLC's next (`Hlc::peek`). The commit's `ts` can still come later (wall time passes during the probes; a cascade rotation in `demote_in` commits first): an `until` expiring in between can widen R's fall past the scope (needless drops of received writes, convergent; not fixed). Cost (`bench_demotion_scope`, 10^4, load 25-30): 15-55 ms per probe, dominated by the `Walked` clone; an empty frontier dropping an admin's writes would re-walk (0.4-1.6 s), which the `all_held` start avoids. `queries::demotion_scope_covers_audits_*` checks it with random receipts.
  - A write whose holder is its target is no write; a record edge is written like any edge (set to its record value, it is in force by the record again).
  - Self-removal: lowers the grant in every component, author admin of the holder, and either the holder is the author or the author has no edge-admin authority on the target (spec §2, decided at review: removing one's group from a doc one is also admin of by its record edge is an explicit demotion that audits the group's admins); a redemption's (author is the holder, holds only an invite, commit has another op) is attributed `Invite(level)`.
  - Frontier coverage (snapshots, spec/commits.md §5): a session range is covered when its last counter is (`>= hi - 1`), or when the snapshot lists no entry for the session (it holds nothing of it).
- **Layer 2** (`content.rs`): re-grant (role at `At::END`) validates writes from where the author first held the required role on the thing ("valid again"; earlier writes stay invalid); else held at the commit's point and no later explicit demotion below the required role; else the newest such demotion's frontier decides (a gap write covered by the newest demotion's frontier is valid). Deliberate (decided at review): a write after `until` or a self-removal is invalid until the next explicit demotion, whose frontier then decides it (§5.1 "as if the holder still held the role"). Role commits are commit form; the node voids overlapping session-form ranges on other aspects (engine `apply/atomic.rs`).
- **Sticky residue** (`common::residue`, used where a projection or another drop order may differ: a drop whose cause R is not, in the settled walk, an applied class fall of the dropped write's author X on its target N through the write's class, X's class on N just before the write there, read from `Timeline::falls`; a self-removal through a holder is judged on the holder). `Walked::falls` records a class fall (point, class after, before) only where X has an earlier held write on N: a function of the held set (never on a leaf, so not aliased by `extend`), undo-logged, in the walk cache. Pinned: `scenarios::residue_classifies_sticky_and_genuine_spec_perm_5` and the residue cases of Role timeline above.
- **Trust sets and disputes** (`trust.rs`; spec §5.1 Trust set; notes/disputes-plan.md step 3): `Timeline::evaluate_with(held, &Trust)` seeds D (`Input::seeds`: `TrustIndex` over the held commits by author and by edge, `Ever::admin_holders` for who a demotion demotes, `Input::ever_forward` for what it puts in question, the "preceding value" of an edge from the last held op on it in point order else its record value) and runs the shrink loop; `Timeline::disputes` walks once more per unapplied trustable op with seeds and reads `trust::demoting` off the walk's history (the explicit change at R's point against the last change on that edge). `Timelines::set_trust` drops the components the old or new set names and evaluates them anew; such components take no `append`, `extend`, `add_leaves`, save or restore (each declines on `Trust::names`; `Timelines` checks its own set, not the kept walk's, which may have been walked under another: a trusted op arriving later or a merge), `demotion_scope` on one re-walks from scratch with its trust set. Ops that may be trusted: a frontier, holder not the author or the target (a finalize or a self-write is ignored). `trusted_active` lists the trusted ops in force. Detection (`Timelines::detect`, `take_detected`, `Detected`): after each update, the trustable ops of the touched components that stopped applying (explicit history entries gone, from the history diff `Changed::edges` already makes) and the new commits' unapplied ones go through `Timeline::scan` (the dispute walk per candidate, every component's ops that stopped applying first, at most `DETECT_MAX` walks per update; past it `Detection::kept` (stopped applying: the store trusts them) and `Detection::unexamined` (newly held: counted)), each found dispute with `stood` and the detecting node's standing on each side; `disputes_up_to(max)` is the bounded listing. The trust store and defaults: notes/disputes-plan.md step 4 (engine `sides.rs`). Only osis-perm, the API layer and the store may name these (tools/policy.py).
- Differential (`tests/it/differential.rs`): joint and edges models agree exactly on 100k histories each (tier 2; edges: projections too); `trust_model_agrees` compares the walk under trust sets, the active ops and the open disputes with the model's `trust::side` (no trust, each dispute's R alone, a node's random picks; half the histories picked with a dispute, one in 200-500 has one) and a `Timelines` switched T, T', T with a fresh evaluation under T.
- Open: the model's library exposes walks and generators but no named scenario list (its scenarios stay `#[cfg(test)]`); counterexample shrinking and quiescence checks are unbuilt.

## Implementation (role flows, osis-engine `flows/` and `rotation/`)
API and engine hooks: notes/engine.md (Public surface) and notes/engine-roles.md.
- An account is created by its node, which its record names as first admin: the fresh recovery key's card first (its creation record and `keys.0`, signed by itself), then one commit by the node with the account's creation record, its own secrets boxed to the key and the node, `keys.0` with inbox and deposit seed, the home label's genesis step listing the key by static entry, and the key's admin grant (a plain edge: a recovery acts as an edge admin); the seed leaves only in the card. Held key actors (`hold_key_actor`) sign in commit form and open their boxes; nothing persists them. The card is no part of any node's chain, so `Engine::certificates` places the cards of a group's key-actor holders without a `node.0` (nodes place their own) with every admin's certificates (the creating node may lose its disk before its first pass; the paired node then places it, sim `disk_loss`).
- Pairing is a direct grant (or, for a node already a holder, a re-seal) plus every commit touching the account, its record chain and both nodes, as one direct send.
- A plain thing with a current holder other than its first admin (its only keyset part turned invalid) gets secrets of its own again from each admin node at the end of a complete pass of its secret actor's labels (`Engine::own_secrets_due`, `pass/` `reseal`), the rotation delivered by inbox to the holders it boxes; once per admin and state, concurrent admins fork. Candidates come from `ix.holder_keys` targets (a scan per label pass, each target once; a measured cost would justify an incremental set). One that cannot be rotated (a holder's `keys.0` not held, an intermediate uncovered) is retried, with a diagnostic, each pass.
- A grant first gives the target, and a plain holder, secrets of their own, runs the cascade on the target (boxing is encrypting under) and boxes every granted role's current epochs. Authority: admin on the target, else an invite grant (no current grant, role and invite at most the effective invite), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own grant or the author's authority on the target comes only through the holder (admin on it); it carries no rotation (the next node that may rotate does) and the leaver drops what it lost. Otherwise it is an explicit demotion with the frontier from the receipt record (as of now) and the pre-sync choice, carrying the target's rotation of the roles the holder left. A removal of an absent grant (finalizing a used single-use link) resets the holder's dead entries and audits the holder's writes on the target.
- Departures are read from the timeline and from the boxes held at current epochs (a holder re-granted since drops out of the list) and cached per actor (`Core::departures`): cleared by `Core::role_changed` on any role-class state write, timeline update, held-epoch change or key-actor hold/drop, with no clock horizon (keys read no clock).
- An epoch's introducing commit (`Core::epoch_intro`: (`ts`, commit)) is the earliest valid commit writing its keyset in `keys.0` (only a rotation does; a box introduces nothing): what a box naming the keyset carries (`rotation::carry`) and a certificate of an actor's current keys. Noted from valid role-commit parts at apply; `load` notes every part, then a flip of a `keys.0` part rebuilds the actor's entries and its held keysets (`keys::rebuild_keysets`), so an invalid (backdated, forged) write never introduces or holds a keyset. A dropped `secrets.0` body takes its `boxes_to` notes along (`keys::forget_dropped`). A dropped `keys.0` body's keysets stay (`Dropped::keysets`), so a compactor keeps knowing them (`dropped_rotation_keeps_its_epoch_intro_spec_crypto_4`). A dropped part's `rotation_role` and `grant_overreach` stay too (`Dropped::role`, `overreach`), so re-judging it and a rebuild need no body; `uncover` (never received again) forgets them. `boxes_to` is noted from held `secrets.0` deltas of any validity (a lookup for `reopen_dependents`). Epochs are persisted whenever they change (`after_join` compares, `observe_state` of `keys.0`, `snapshot_keyed`'s snapshot mark).
- A demotion frontier above `CHUNK_THRESHOLD` is a chunked large value the header links (`validity::header_frontier` resolves it). `Engine::certificates` returns the parts to carry per commit; node-sync places a copy's linked blobs (header lists, linked frontiers) under the label with it (`place_linked`).
- Contact cards stay in the osis API (`contact_card`): the card composes calls flows already has (a group thing written through the API's membership, its own secrets, a label, certificate placements, a read link) plus the API's local record of the card; a flows call would only move that orchestration below the layer that owns membership and sync.
- Re-seal and registration are pull hooks for node-sync (`reseal_due` at the end of a complete pass, `issue_step` per host head); flows only return deliveries.
- Tests: `core/node/tests/it/flows.rs` (account and pairing, grant by inbox, removal rotates, invite power, demotion frontier with pre-sync choice, mutual removal, two-hop cascade, stolen-node recovery from the card, link redeem and single use, bearer and `until` with finalization, re-seal of a raced grant, key-actor holders not re-sealed, departures, stranded node re-paired, registration step after rotation, projected certificate).

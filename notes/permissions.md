# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: owner direction, why each rule, costs and leaks, revocation and move (copy) reasoning, the `models/membership` findings behind the membership timeline, sharing patterns, public content and anonymous writing, rejected alternatives.

## Owner direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: owner, admins, editors, viewers.

## Concepts
- Any thing becomes an actor when it needs members of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the membership-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope; the owner is the recourse. So a person actor's owner should be an offline recovery key, with devices as admins (app policy). Consequence: only the recovery key can roster-snapshot the person actor, so its membership history (device churn, tiny) is bounded only when the key is used.
- Recovery of a lost owning key is out of scope (owner). The actor keeps working (admins can remove each other) but can no longer be roster-snapshotted or settle an admin war; its things can still be copied out by any admin.
- Recovery card: the seed alone cannot find the person actor (tid, labels and servers are not derivable), hence the card format; the recovery key owns the person actor, so every home-label step lists it with an entry box; the card names several servers, and the key claims the current step by its static entry and reads the read secret from the step's entry box (spec/sync.md §2).
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things, the person actor under its recovery key) derive secrets like any plain thing; nothing else uses them.
- Nodes are things that own themselves and grant nobody anything; the node card under every label a node tracks shows exactly the readers of L which nodes sync L (a read-only node's card arrives by deposit), and its expiring `/seen` heartbeat when it last did (notes/ephemeral.md), never a roster. Rejected: a self-edge granting the person admin (covers only own devices); a devices group readable by contacts (leaks the device roster, misses read-only co-members). `/reach` carries no IPs (dialable key and relays only, notes/networking.md); apps exclude it under open-audience labels so strangers cannot dial the device.

## Keys
- Writes are node-signed plus a membership chain. Sharing an actor's signing key erases which member wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to derive delete tokens of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the owner), demotion write -> read (rotate write only), removal. Epochs are per role, so a writer's rotation of read and write leaves the admin secret, its boxes and the label delete key exactly where they were, and nothing "carries over". Concurrent rotations fork the epoch (spec/crypto.md §4): boxes are keyed per epoch so both rotations' boxes survive the merge, members keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it; at a server the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many members at once forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (member, role), which leaves members holding different secrets after concurrent rotations, unable to read each other's new wraps.
- **Write or above rotates its roles and below** (decided with owner). With admin-only rotation, every actor a person is a non-admin member of would keep wrapping new content to a lost device until that actor's admins happened to rotate, and the person could do nothing about it. So the person's own device rotates every actor it writes to when it removes the lost device, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks members out, worse than the storage waste a reader may cause; an actor the person only reads keeps wrapping to a lost device until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a server, which only ex-admins can (notes/sync.md). Until an admin registers the newest epoch, a removed device keeps the old sync and write keys at servers: ciphertext it cannot open, stale stamps and `writer`-token deletes that members heal. Residue: a member that has not heard of the removal wraps under the old epoch, and the lost device reads that one blob (as with Signal sender keys).
- **No periodic rotation, no rotation policy** (owner). A device compromise is either known, and the removal rotates before the next write, or unknown, and the device is still a member, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy of the secrets would need the device's KEM key to change from fresh randomness the thief lacks; the seed is the device, so a thief holding it is the device and nothing heals. History boxes mean a compromise yields all stored history anyway; "no history for new members" and bounded history are app or future choices, not core.
- A plain thing derives its secrets until it has a non-owner member, so nothing is stored; then explicit secrets, so that removing that member rotates the thing alone and not its owner. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, which are one-way from the owner's), so wraps, tokens and label steps need no special case; a derived secret's epoch is the owner's. Explicit secrets do not stop the cascade the other way: every rotation of an owner is caused by a removal, and the removed member could open every explicit secret the owner's roles reach (owned things, edge targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `/keys` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin happened to act.
- Nesting cost (accepted by owner): removing a member rotates every thing with explicit secrets whose secret it could open, so a lost device costs one lazy rotation per shared thing the person reaches; the usage rule is to share sets through one actor. A thing's admins learn what it is a member of because every edge whose member is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct member per rotated role, one re-registration per label per server. A company of 50 teams with 10 labels on 3 servers: 50 boxes and 30 signed messages per person removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `/keys` window**: until a person's new `/keys` reaches a co-actor's label, rotations there seal to the lost device's old keyset and its steps list its old claim key, so the lost device reads new content via an honest server. Hence the MUST to place the removal and new `/keys` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **Re-seal is a SHOULD with a trigger** (a current member without a box at a current epoch, or a stranded heartbeat). Objection considered: a node holding the rotation but not yet the removal would re-admit the removed member; the covers rule heals it (once the removal arrives the epoch holds a box for M, so it no longer covers and the next encryptor rotates again), at the cost of one extra rotation and a window in which an ex-member plus a dishonest server read new content. Without the trigger a grant raced by a rotation was a silent permanent lockout.
- **`until` counts as a departure** for rotation and the covers rule, else "share for a week" never ends for reading; eager rotation makes boundary disagreement between clocks harmless.

## Sharing
- Sharing never changes a tid. Moving a thing to an actor its owner owns has no double-spend harm, so it is an ordinary write (an edge). A copy with a new tid is only for moving a thing out of its owner's tree, which should be rare.
- One note: an edge on N, explicit secrets on N, N its own label. A set: a group thing with members and secrets, made a read member of each thing (one edge per thing, one commit). A set meant to be shared as a unit is better created under a common owner.
- Group membership grants no rights (an edge on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (usage rule, doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Problem: checking a write on N needs the membership of N's owner chain and of the author's own actors, which only members can read. Resolution: signed membership commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns the chain of every author under L (one edge and the roster size per level, plus each `/created` record and hence that thing's dedup secret), never rosters. Author identity is inherent anyway.
- Roster snapshots in certificates are projected per edge: a whole snapshot would hand every reader of L the full device roster of each author's person actor and the rosters, `/label` IDs and servers of every team above it.
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some member of the revoking actor syncs L); chain depth equals nesting depth.
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Owner decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and blind nodes never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too; re-grant restores it, together with Y. Centralized semantics with the revoking device as the server (owner: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- One rule for both layers: the revoke's frontier is one list for membership and content writes, about 10 bytes per (aspect, author node) entry plus 32 per commit-form commit. A prolific device over years writes 10^5–10^6 aspects, so a frontier can reach megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), and a later roster snapshot re-carrying the same ledger entry reuses the same chunks. The ledger copies it into every later roster snapshot; that is the price of a roster snapshot replacing the revoke. Rejected: per-node global counters (one counter per node plus gaps) would shrink frontiers but change dot semantics, runs and the model.
- Only the revoker's own receipts matter: a node that may revoke keeps, per (aspect, author node), when it received each counter (granularity and horizon are local policy). A backdated revoke's frontier is bounded by that record; a coarser record gives a smaller frontier and more loss.
- Clock skew: a departure by `until` or self-removal is judged by the member's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions). If ever needed: backdate revokes by a margin.
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- Re-grant validates the gap: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it makes recovery from a stolen device's backdated mass revoke lossless. It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them.
- A revoker can backdate to roll back more; not a new power, any writer can invert others' edits.
- Dot reuse by a revoked actor would let it write under covered dots forever, so overlapping node-form ranges from one node void both commits (spec/commits.md §4). Honest nodes never overlap (an unsure node uses commit form). Residue: an ex-writer can erase its own pre-revoke writes by equivocating; re-grant restores them.
- Sync-then-revoke closes most of the loss from a frontier taken on an unsynced device (spec/requirements.md, Permissions). What remains: writes at blind nodes the revoker does not reach, writes in transit, P2P-only edits among other members, revokes issued offline or backdated; all recoverable by re-grant.
- Rejected: timestamp rule (forgeable); accept everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); membership by claimed time only (an ex-admin could mint backdated grants forever); other writers vouching for edits the revoker missed (a commit kind, a validity fixpoint over vouchers who are later revoked themselves, a per-node receipt clause and a tiebreak, all for edits that reached another writer but not the revoker; not worth it).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 already judged edge writes one by one.
- **Compaction snapshots vouch for nothing** (owner decision): every element is judged as its author's write, un-merged from snapshot bodies too; re-grant is the only recovery. History: the first rule let any writer's snapshot carry a revoked author's elements, so a writer that had not yet received the revoke revalidated them everywhere by routine compaction; the sweep added "only if the author was authorized at the snapshot's `ts`", which `models/membership` (`content.rs`) showed diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered. Rejected: carrying an "earliest saved at" `ts` per commit in snapshots (converges, bytes on every entry forever, and the compactor's word lets a friendly writer launder a revoked member's backdated writes under the member's own name); newest carrying snapshot decides (converges, but the save lasts only until the next compaction). With the pre-sync before stamping a demotion (spec/permissions.md §5.3, notes/api.md) the save had no remaining job: a synced revoker's frontier covers what snapshots carried, and a revoker that fails instead of stamping loses nothing. A compacted node can still judge: current members by the roster, ended tenures by the ledger.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual membership is allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed anyway: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (owner chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin edge on G could backdate a forged write to a time it held only the edge; removing the edge first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood forever (found by `models/membership`, `two_admin_paths_class_attribution`, `chain_and_edge_paths`). Path-based audits (each removal audits what went through its path) would also close it, but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal is attributed like its grant and falls with it: "self-removals are never dropped" taken literally kept a forged redemption's self-removal after the sharer's finalization dropped its grant, burning the link and blocking the honest redemption the sharer had seen. Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the tenure (the rejected claimed-time rule).
- Writes to `/secrets`, `/keys`, `/label`, `/moved`, `/was` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering membership-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Membership timeline (membership model findings)
Model: `models/membership` (throwaway Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test -p membership-model` runs the scenarios; `cargo run --release -p membership-model -- [samples] [as|exempt|strat|stratw|frontier|snapshot|edges|edges-prov|joint]` searches (`joint`: `src/joint.rs`, the joint walk over several actors with mutual membership and commit-ID ties; `src/content.rs`: layer-2 scenarios, test-only): exhaustive up to 3 membership writes (owner, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `snapshot` (`src/snapshot.rs`) is the two-level roster-snapshot model; `edges` (`src/edges.rs`) models projected rosters, links, invites (audited by level), per-op judgment and plain owner-chain writes on a thing (its `/moved`, say); `joint` (`src/joint.rs`) is the joint walk over several actors (owner chains, actor members, mutual membership, (t, author) ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs` holds layer-2 scenarios: per-delta validity across partially synced things, snapshot authority at `ts`, and the snapshot-of-snapshot divergence that led to "snapshots vouch for nothing" (below).
- **Third-party witnesses judged by end-of-walk membership fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a member by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the owner's further-backdated revoke cancels a stolen device's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for membership writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin device's backdated removals stand iff the node removing the device had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Edge demotions never audit owner-chain writes, so an edge-admin cannot drop a roster snapshot.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it); plain owner-chain writes on a thing such as `/moved` (a removed device's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky.
- Self-removals are never dropped: otherwise a later demotion of the author could hand back what it gave up. Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.

## Roster snapshots
- Bound membership history (spec/requirements.md, Permissions and Scale). Only owner-chain snapshots can be epoch starts: their applicability depends only on the chain above N, never on N's own earlier writes, so a node holding only S and later writes computes what a full-history node does.
- **Tenure ledger**: a snapshot's roster alone cannot answer authority before S, yet things are judged against it after S: writes and epoch starts of things below N made by chain authority before S, and ex-writers' content (layer 2 needs the revoke time). Without it, a routine re-snapshot of a person actor after a device removal kills every owner-chain write the device made on things below while a legitimate admin (2.3% of valid ones in random `models/membership` runs), epoch starts included. The ledger is the compacted form of the demotions: each ended tenure with the frontier that ended it, so the member can neither gain anything (a dropped backdated record stays dropped: the frontier travels with the tenure) nor lose what the timeline had accepted. Roster edges carry `since` so a re-granted member's gap stays closed; every later tenure's frontier re-audits earlier writes, as a later demotion does in the walk. Checked (`snapshot` mode, `resnapshot_neutral`): re-snapshotting P with the roster and ledger the timeline computes changes no record's validity and no G write's application in 8M random histories; compaction, projection and order independence hold with random well-formed ledgers.
- **Ledger cost, the accepted tradeoff**: entries are never dropped, because a write or epoch start anywhere below N may depend on any of them and the snapshotter cannot know which (it does not sync everything below); a time bound was examined and rejected, since a removed member could forge a backdated write inside its tenure (an epoch start of a thing below N, say) after the bound, and only the tenure's frontier drops it. Roughly 100 bytes per ended tenure of write or above plus the frontier (by link when large, chunks reused across snapshots), carried by every later snapshot of N: a person actor grows by its device churn, a team by its member churn. Certificate copies carry only the edge and ledger deltas a chain needs (one delta per edge and per entry, so a projection drops deltas and never breaks a hash), so verifiers pay per edge in bodies but still one delta hash per edge in the signed header: direct rosters should stay in the thousands (spec/requirements.md, Scale). Rejected: writes carrying a frozen certificate of their signer's chain (cannot show the signer's later removal covered the write once that removal is compacted); listing only tenures of members whose writes the snapshotter holds (breaks writes it does not hold); a Merkle tree over per-edge hashes (saves header bytes for huge rosters, more machinery; revisit if flat rosters above ~10k matter).
- A grant in flight while a snapshot is taken is dead (finality per snapshot); snapshot after a fresh sync, re-grant a victim.
- `MEMBERSHIP_KEEP` on membership commits keeps the revoke long enough for every node offline less than that to apply it. A format constant, so nodes agree on what a label must hold.
- Un-applied epoch start (author later removed with a backdated time or a frontier not covering S): a full-history node falls back, a compacted node sees an empty roster until a fresh snapshot; this only shrinks rosters toward the owner chain. Forgeries by a removed device never become epoch starts.
- Who compacts what: a person actor's own roster only when its recovery key signs (device churn is tiny); busy actors (teams, documents) should be owned by a person actor, so its devices can snapshot them. About 25 bytes per edge. A roster snapshot carries only `/members` and `/tenures`: `/secrets`, `/keys` and `/label` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta), and a rotation's boxes page. The old design carried full `/secrets` and `/label` in the roster snapshot, which could not fit a blob for rosters above about a thousand.
- Content via compaction snapshots: with snapshots vouching for nothing, compacted and uncompacted nodes agree whatever snapshots they hold or dropped (`content.rs`, `snapshots_vouch_for_nothing`).
- Checked in `models/membership` (`snapshot`): compaction at any applied snapshot never changes the result (0 mismatches in 2.5M compactions over 4M histories), order independent, at most 4 walks; compaction points later un-applied diverge until a fresh snapshot in about 0.3% of histories, as designed.
- Rejected: edge-admin snapshots as epoch starts (a compacted node cannot judge them, a removed admin could forge one); a snapshot chain (same problem, unbounded); "a dropped epoch start empties the roster for everyone" (a permanent wipe for any removed device); key-actor-only snapshots (an offline key cannot compact a busy roster).

## Moving a thing (copy)
- Ownership is immutable: a former owner can always sign a competing transfer (double-spend; no fix without consensus), so a transfer must never let the former owner touch what the new owner holds. A copy under a new tid gives that for free: the old thing stays the former owner's, the copy is the new owner's by construction, and the former owner's whole power is to re-point or wipe the old thing, which only misleads readers that hold nothing but the old tid. Decided with the owner over the old aliasing design (below) for simplicity: no verification rule, no identity derivation, nothing kept forever.
- Imports keep history: live state with its stamps and dead bodies alike, each with its origin's retention and author, so purge rights on the copy are what they were (an origin author purges once re-granted on the copy, as it would after any removal and re-grant). What a copy cannot do: give the old authors' delete tokens at blind nodes (the importer lacks their secrets; admins' tokens delete after the author's purge request) and move rights the moved actor held elsewhere (foreign admins re-grant the new tid). Cost O(subtree + history); the owner does not mind.
- Re-sourcing to (`Commit(origin)`, k) makes an import idempotent (two of X's devices importing the same origin produce the same dots) and keeps imported dots clear of native counters, which start at 1 per (aspect, node) and would otherwise collide with an author's own old dots. Keeping the original `ts` keeps the order among imported writes; everything native on the copy is newer anyway. The origin choice depends on the importer's held set (snapshot if it holds one covering the write, else the commit), so two devices importing concurrently from different held sets would duplicate elements; hence one import per move and the client rule not to import a thing already continued by a held copy. Residual race accepted.
- Resolution is a read-time view keyed on the referencing thing's owner chain, so two readers of one thing agree: the copy's own `/was` claim wins where that owner has standing in the copy, the former owner's `/moved` pointer elsewhere. Standing can be faked only by granting the referencing thing's owner an edge on a fake, which is the same exposure any unsolicited grant has (apps place things into their sync set explicitly, spec/requirements.md, Offline and network). Values are never rewritten: an autonomous rewrite is a write with a fresh timestamp that beats a concurrent real edit, and two devices rewriting concurrently would duplicate text links.
- Within one tree nothing moves: rights are edges, the root is the un-removable admin either way, so "move this doc to team B" is an edge change, and ownership depth should match the units that travel together (a folder actor owning its things moves between teams by one edge). Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).
- Replacing a root key (the recovery key owning a person actor) is a copy of the person actor: rare, re-granted everywhere by foreign admins. Not required by anything (signatures need not be PQ, seed compromise is out of scope); devices rotate by add-and-remove.
- Rejected: **hand-over with aliasing** (the previous design): a record on the thing signed through the former owner's chain, the new identity hash(T, H) owned by the new owner by construction, everything below renamed per fork branch, a three-step read-time resolution (standing, the reader's `/follows` choice, dangle), records kept forever and hence an unbounded tenure ledger; correct and model-checked, but the whole of a spec section plus permanent per-verifier cost for a rare operation. Also rejected: sharing a tid between branches (the former owner's chain stays able to write and delete the subtree), freezing a thing on a second record (no consensus on the moment, so it is a rewind to the transfer, and a disown hands the name back), a notary or log committed at creation (closes every former-owner power but makes transfer an online operation with an outside dependency), transferring without history, a one-successor `/moved` (first-write-wins needs arrival order or a fork rule).

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `/secrets` like any key-actor member). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets (bearer read); the remaining joiners get a fresh link.
- **Why K no longer derives its secrets from the seed** (the previous design, "until K is first rotated"): every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every server) and write key, which is exactly the power the invite-only design took away from L. And L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K (allowed since d8a68b4) stranded L. Now K's secrets are random, L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip: the cold-entry path that already existed after a rotation is the only path.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- Finalization: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer device writes a real removal; until then the link is honest-client-only. Alternative (no `until` or single use at all) loses nothing a hostile holder respects.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): what a link conveys is "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add edges for actors with no current edge, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier like any membership write. Inviters seal only secrets they hold (their role and below). Holders read K's roster (they are its members), like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- Self-removal lets an actor always leave or lower its own edge; single-use links use it to drop L's own edge.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (spec/permissions.md §9: kicking one joiner otherwise kills the link for all).

- Resolution hops are capped at 8 (`RESOLUTION_HOPS`): longer move chains are pathological, and the cap keeps a read O(1).

## Patterns
- **Edge on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per member, so not per note in a folder).
- **Shared owner** (spreadsheet): one actor owns everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: an offline key owns a thin root actor whose admins are a few persons; teams, chats and docs are owned by the root or by actors under it. Root admins can roster-snapshot everything below and remove anyone, and a departing founder is just an admin removal. A team owned by a person actor cannot shed that person (owners are un-removable).
- **Folder with rights** (rights live on edges, never on grouping; owners never change): either a folder actor that owns its things (collaborators' new things created under the folder actor; moving a thing out is a copy), or things owned by the person with a client helper that mirrors the folder's edges onto each thing as it is added or removed (costly per thing, keeps ownership with the person).
- **Chat**: see notes/chat.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and ownership (each owns its messages), and `/group` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and owner actors stay separate; a group may also be an actor when it serves as a shared label.

## Purge rights and retention
Retention is per delta (spec/commits.md §5), decided with the owner. Default `author`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and a relative keep-at-most implies it. `nobody` is for records that even admins must not drop. `admin` is what membership commits use. Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (owner's call; servers approximate it, notes/sync.md). Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever, and a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart. Fields are immutable: a change would need the blob re-encrypted anyway (tokens are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a trusted node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the blind node (server stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with owner, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous member: a fresh actor with its own owning key and device keys, joined via a link or grant; the granting admin may record pseudonym -> person in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Members write as A in commit form. Caveats: any member can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a trusted node re-signs members' edits under its own identity.

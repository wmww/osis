# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: Tess's direction, why each rule, costs and leaks, revocation and ownership reasoning, the `core/test/roles-model` findings behind the role timeline, sharing patterns, public content and anonymous writing, rejected alternatives.

## Tess's direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: owner, admins, editors, viewers.

## Concepts
- **Terms** (Tess, round 13; spec/permissions.md §1): rights are roles given by role grants, and an actor with a role is a holder ("Dana holds write on X"); member and membership mean only being in a group ("this note is a member of Work"), which grants no rights. One word per sense, so code, API, CLI and spec never use member for a right; a CRDT set's value is an element, a `Slots` entry a slot.
- Any thing becomes an actor when it needs holders of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the role-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope; the owner is the recourse. So an account's owner should be an offline recovery key, with its nodes as admins (app policy).
- Not promised, so not listed in spec/requirements.md: anonymity against network, timing and style analysis; revocation reaching a group before one of the revoker's nodes next syncs it.
- Recovery of a lost owning key is out of scope (Tess). The actor keeps working (admins can remove each other) but can no longer settle an admin war; its things can still be copied out by any admin.
- Recovery card (not built in the API: removed until a design exists, issues/recovery-redesign.md; the engine and spec text stay): the seed alone cannot find the account (tid, labels and hosts are not derivable), hence the card format; the recovery key owns the account, so every home-label step lists it with an entry box; the card names several saved peers, and the key claims the current step by its static entry and reads the read secret from the step's entry box (spec/sync.md §2).
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things, the account under its recovery key) derive secrets like any plain thing; nothing else uses them.
- Nodes are things that own themselves and grant nobody anything; the node card under every label a node tracks shows exactly the readers of L which nodes sync L (a read-only node's card arrives by deposit), and its expiring `seen.0` heartbeat when it last did (notes/ephemeral.md), never a roster. Rejected: a grant of admin from the account to itself (covers only own nodes); a nodes group readable by contacts (leaks the node roster, misses read-only co-readers). `reach.0` carries no IPs (dialable key and relays only, notes/networking.md); apps exclude it under open-audience labels so strangers cannot dial the node.

## Keys
- Writes are node-signed plus a chain of role grants. Sharing an actor's signing key erases which holder wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to sign deletes of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the owner), demotion write -> read (rotate write only), removal. Epochs are per role, so a writer's rotation of read and write leaves the admin secret, its boxes and the label delete key exactly where they were, and nothing "carries over". Concurrent rotations fork the epoch (spec/crypto.md §4): boxes are keyed per epoch so both rotations' boxes survive the merge, holders keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it; a forked role of an actor M is no longer rotated because a box to M names a fork other than M's newest (`fork_named`, issue rotation-settle-livelock: A's and M's owners each judged the other's box uncovered and rotated A back and forth): the covers rule reads names, not boxes, so that livelock is gone, and the rule went with it (was issue fork-choice-keys0). Rotating every forked role looped (`used_link_with_sharer_offline_spec_permissions_7` hung). At a host the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many holders at once forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (holder, role), which leaves holders holding different secrets after concurrent rotations, unable to read each other's new wraps. Epoch numbers others name are never trusted: the next n counts from the rotator's current epochs only, a pending commit records no epoch beyond its bounded reading-only secrets, and an epoch above 2^62 establishes only next to an established one at n-1 (a planted n = i64::MAX once overflowed n+1 and blocked every later rotation, so removals too).
- **Write or above rotates its roles and below** (decided with Tess). With admin-only rotation, every actor an account holds a non-admin role on would keep wrapping new content to a lost node until that actor's admins happened to rotate, and the account could do nothing about it. So the account's own node rotates every actor it writes to when it removes the lost node, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks holders out, worse than the storage waste a reader may cause; an actor the account only reads keeps wrapping to a lost node until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a host, which only ex-admins can (notes/sync.md). Until an admin registers the newest epoch, a removed node keeps the old sync and write keys at hosts: ciphertext it cannot open, stale stamps and level-3 deletes that holders heal. Residue: a holder that has not heard of the removal wraps under the old epoch, and the lost node reads that one blob (as with Signal sender keys).
- **A `secrets.0` record needs the role its key names** (validity `secrets_role`): a map record acts only on the entry of its key (spec/crdt.md §5.6), removals included, so the role and the removed box are read from the delta alone (`keys::secrets_write`); a key-erased record needs admin. This replaced a lookup of the removed entry's creation key (`box_keys`, `rotation_unresolved`, `secrets_unresolved`), whose answer depended on which bodies a node had held. `roles.0` perm adaptation (`edge_ops`) still names a removal's holder by its entry's creation (`holder_keys`, unresolved until held) but ignores a reset carrying another key, as the CRDT does.
- **No periodic rotation, no rotation policy** (Tess). A node compromise is either known, and the removal rotates before the next write, or unknown, and the node is still a holder, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy of the secrets would need the node's KEM key to change from fresh randomness the thief lacks; the seed is the node, so a thief holding it is the node and nothing heals. History boxes mean a compromise yields all stored history anyway; "no history for new holders" and bounded history are app or future choices, not core.
- A plain thing derives its secrets until it has a non-owner holder, so nothing is stored; then explicit secrets, so that removing that holder rotates the thing alone and not its owner. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, which are one-way from the owner's), so wraps, delete keys and label steps need no special case (content of the derived era keeps the owner's delete keys: a later admin of the thing who is no admin of the owner cannot delete it by key at hosts, only the label delete key can; accepted, Tess); a derived secret's epoch has the owner's n capped at 2^62 − 1 and the nonce its secret names under the thing (spec/crypto.md §3), so a writer of the owner jumping its n past `MAX_FREE_N` cannot put the switch above the headroom line, where a holder holding no secret of the owner could establish nothing at n − 1. Explicit secrets do not stop the cascade the other way: every rotation of an owner is caused by a removal, and the removed holder could open every explicit secret the owner's roles reach (owned things, grant targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `keys.0` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin happened to act.
- Nesting cost (accepted by Tess): removing a holder rotates every thing with explicit secrets whose secret it could open, so a lost node costs one lazy rotation per shared thing the account reaches; the usage rule is to share sets through one actor. A thing's admins learn what it holds roles on because every grant whose holder is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct holder per rotated role, one re-registration per label per host. A company of 50 teams with 10 labels on 3 hosts: 50 boxes and 30 signed messages per account removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `keys.0` window**: until an account's new `keys.0` reaches a co-actor's label, rotations there seal to the lost node's old keyset and its steps list its old claim key, so the lost node reads new content via an honest host. Hence the MUST to place the removal and new `keys.0` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **Re-seal is a SHOULD with a trigger** (a current holder without a box at a current epoch, or a stranded heartbeat). Without the trigger a grant raced by a rotation was a silent permanent lockout. The missing box that marks a deliberate exclusion looks exactly like the one that marks an unknown grant, and TLC (core/test/tla/rotation, R1) showed a node that receives the rotation before the removal re-seals the removed holder, who then reads post-removal content from an *honest* host (it holds the current sync key); the earlier reasoning that the covers rule heals it was wrong about the window. Fix: **the removal or demotion and the rotation it requires on the target are one role commit**, so the rotation and the departure travel together (both parts on the target, one body; a sender holding the keys may still split them, spec/commits.md §4), and an omission in a held rotation can only mean the rotator did not know the holder. It costs nothing: the covers rule already forced the remover to rotate before encrypting the removal commit. The inbox copy to the removed holder and the certificate copies carry the grant delta only (projection). Rotations of other things (the cascade) stay lazy; they exclude nobody directly. Guards on top: a re-seal decision comes after a full sync pass (like the pre-sync before a demotion, spec/permissions.md §5.3), and boxing a secret to a holder counts as encrypting under its epoch (a re-sealer that knows of a departure rotates first; one holding a grant it may finalize finalizes it first). The second TLC round showed the one-commit rule covers only the rotation that carries the removal: a later rotation by a node that knows it omits the holder without carrying anything, and a node that reads that rotation out of order (a peer, a second host, or a re-seal's history box handing it the secret before the commit) re-seals the removed holder. Fix: **established epochs** (spec/crypto.md §4): a rotation counts only once the node has applied its commit and the commits of every epoch it supersedes, transitively (or a `secrets.0` snapshot stands in for a compacted chain), so holding an epoch means holding every departure its chain carried, whatever the arrival order; this is the order the wraps already impose on a node that never got a history box. Re-seals are made only at chain-established epochs (a late joiner holding only a snapshot rotates instead: a rotation boxes everyone it thinks current, so it is a re-seal of everyone) and at the end of a complete pass (the log of every host and peer read to its end: cheap to know, and what makes the post-compaction case sound). Opening a label is no longer "encrypting under": a re-sealed holder must open with the re-sealed sync key to fetch the rotation commit that establishes the epoch; an open proves possession to a host and produces nothing others rely on. The remover uploads the rotation before registering the step (notes/sync.md), so a holder listed in the step never strands merely because the commit is not there yet. Residue (accepted, notes/sync.md Limits): after compaction a node's view of the roles no longer travels with the epoch chain, so a node that boxes a holder at a snapshot-established epoch from an incomplete view (a host that never got the removal, an interrupted first sync followed by an eager rotation) can box a removed holder; same class as a rotation by a node that has not heard of the departure, healed by the next rotation of a node that has. The refused-deposit residue stays in issue reseal-triggers (closed: a manual re-share, notes/sync.md).
- **What a removal reaches** (`osis_keys::reached`, over a `Graph`: `PermGraph` adapts a perm `Timeline`, `MemoryGraph` for tests): the things the removed party's roles opened, owned things and grant targets transitively, linear in the graph: the labels a removal is placed under; `lost_access` (what a node drops) uses it too.
- **Depth 0** (Q2 = A; notes/crypto.md, Holder actors at depth 0): a departure is from the actor itself; one inside a holder actor M reaches the actor's boxes only as M's new keyset, which makes them stale (the chain up is staleness, actor by actor); before M rotates, a node holding M's secrets that knows the departure finds A's epoch boxing M at M's uncovered keyset blocked and rotates A leaving M out (notes/crypto.md, Blocked through holder actors). `ensure_rotated` cascades over the holder actors this node may rotate (post-order, each once), so where it may rotate M its one rotation of A seals M's new keyset. Tests: `rotation::tests_members` (twelve deep, diamond and lattice, cycles, ignorant fork, forged keyset, hidden grant, the stated limit on grants), osis-node `flows::cascade_two_hops_spec_perm_3`, `inside_member_departure_leaves_holder_out_spec_perm_3`.
- **Role cycles** (was issue rotation-cycles, issue cycle-stranding (closed)): X and Y readers of each other, D removed from X: Y's epoch boxes X's old keyset (D holds it), so X's new epoch boxed to Y leaks, and any order of lone rotations that box each other leaks. Cycles stay allowed (Tess: tags become members of each other by ordinary use; two people's shared tags have disjoint admins), but no key cycle forms (rule 4, chosen with Tess after every candidate without it failed in Depth0.tla: the study's leave-out ping-pongs, leaks below a cycle and locks out concurrent departures; Fresh leaks with a second admin, `D0_cyc_2adm_fresh`): the grant closing a cycle is keyless, its holder boxed nothing, so a cycle reduces to member chains (rules 1-3). Rejected earlier: the leave-out rule with per-departure judgement and re-seal skipping (deleted with the walk), joint rotation of the cycle in one commit, forbidding cycles. A hidden earlier grant leaks until the writer holds the grants (taint, notes/crypto.md). **Re-seal invariant** (`reseal_candidates`): once re-seals settle, every node counts the same current epochs (supersession is read from the rotation commits, notes/crypto.md) and every holder with key access holds every current epoch any node holds (`forked_reseals_settle_*`). A re-seal is made only if it adds a box the trigger asks for (`forked_role_reseal_reaches_fixpoint_spec_permissions_3`; churn seeds 140170, 140188 looped before); requiring every fork's secret of a re-sealer stranded a holder when no node held them all. A node lacking a role's current secret (a rotation left its holder actor out) rotates the other roles it may (`rotator_lacking_read_rotates_write_spec_permissions_3`) and waits for the re-seal of the one it lacks; a removal whose rotation would write that role is refused (`removal_lacking_rotated_secret_refused_spec_permissions_3`). Tests: `rotation::tests_members::removal_in_cycle_spec_crypto_4` (2- and 3-cycle; `openable` follows boxes from the departed party's old secrets), `departure_below_cycle_spec_crypto_4`, `cycle_with_disjoint_admins_converges_spec_permissions_3`, `cycle_concurrent_departures_spec_crypto_4`, `second_admin_ignorant_fork_in_cycle_spec_crypto_4`, `hidden_grant_tainted_keyset_spec_crypto_4`, `cycle_removals_leak_nothing_random` (tier 2 `_large`).
- **Lockout recovery limits** (moved from spec §3): an honest rotation by the removed node that only failed to box the recovering admin (stranded, or its holder actor left out by Seal) is left out too; content written under that epoch stays readable only where its secret is already held. A hostile admin is out of scope (it can remove the recovering admin first; only owner-chain authority over a hostile edge admin recovers), and a thing with no admin left, or an ownerless thing whose admins are all gone, has no recovery.
- **A timed end is finalized** (Tess, keys study §2.5): a grant past its `until` is no key departure; keys read no clock (`Core::key_holders`, `rotation::key_role`: every applied write in effect, `until` disregarded, the `until` 0 keep value no grant). A node with write about to encrypt under T (`rotation::ensure_rotated` → `finalize_due`) first writes a finalize of each ended grant on T of role at most its own: a removal with no frontier carrying the rotation (`flows::edges::finalize_in`). The timeline applies a frontier-less removal of another's grant only as a finalize (perm `judge`, `Attr::Finalize`: grant past `until` at its `ts`, author with write and at least the grant's role; no class, never audited), so a renewal ordered first wins and an admin's racing finalize cannot turn into an empty-frontier revoke. Test harnesses give explicit removals an empty frontier for that reason. At the guest a finalize counts as its `until` (`Timeline::role_unfinalized`, `lost_by_time`): it hears out. A renewal or removal of the grant itself is not finalized first (`ensure_rotated_but`). Removals reset every entry of the holder (`flows::edges::removal`): a void finalize resets the CRDT entry while the grant stands on the timeline. Fallback Tess accepts if this hits trouble: admins only finalize. A re-grant after the `until` removes the expired entry first (`grant_in`; `regrant_after_until_reads_again_spec_permissions_2`). Tests: core/node/tests/it/finalize.rs.

## Sharing
- Sharing never changes a tid or owner. Moving a thing to an actor its owner owns is an ordinary write (a grant).
- One note: a grant on N, explicit secrets on N, N its own label. A set: a group thing with holders and secrets, granted read on each thing (one grant per thing, one commit). A set meant to be shared as a unit is better created under a common owner.
- Group membership grants no rights (a grant on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (usage rule, doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Problem: checking a write on N needs the role grants of N's owner chain and of the author's own actors, which only holders can read. Resolution: signed role commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns, for every author under L, every path it ever had to the things it writes there (every held edge write between things on those paths, applied or not, each `created.0` record and hence that thing's dedup secret), never whole rosters. The point-based rule it replaced (item 156) already revealed about that for chains at now. Author identity is inherent anyway.
- **Per label, not per node**: a certificate delta already under the label counts whoever placed it, so a joiner copies only its own chain (11.5 KB per label in a chat) and not the sharer's again, and holders do not all re-copy a rotated actor's new `keys.0`. Sound because a copy counts only once this node checked every delta of it against the header's delta hash (`SyncEngine::genuine`; opening checks the prefix only, and a held commit's late parts are skipped unchecked, so before the check anyone able to deposit under the label could post the header with garbage deltas and stop the real copy; the same check now guards `entry_for`, `carried_by` and the duplicate and strict-subset deletions, where a forged blob could have got real copies deleted), only while present at every host of the label this node syncs with (else it skips at one host and its own copy then goes to both), and, for a rotation commit of the label's actor, only under the newest epoch. Older epochs otherwise count: a newcomer gets the history boxes with its grant or first rotation box (spec/crypto.md §4) and opens older copies like the label's older content (`newcomer_after_rotation_reads_older_copies_spec_crypto_4`); counting only newest-epoch copies made every holder re-copy everyone's chain after each rotation (40 KB per holder per chat removal). Residue: a holder of a link key alone (newest secret, no history box) reads none of the older entries, own copies included, as before. If another node's copy goes, the next pass places this node's own. Deletion power is the same either way (a copy commits to its commit's delete keys). Closure deltas are never copied (they are closure blobs; a copy was a strict subset others deleted). Another node's demotion or `keys.0` is left to its author for `SETTLE_MS` (30 s) after this node received it, with a wake then (the remover must place them, §3): holders learn of a rotation under K's label before the remover's copy under C arrives, and all of them copied it (3.3 KB per holder per removal). Measured from receipt, not the commit's `ts`, which its author sets.
- A removal of G's grant goes under G's labels (spec §2) because the target may have left G's closure, the removal ends G's reading of it, and G's inbox may reach only G's admins.
- Without `reach.0` under a label, co-readers of that label cannot dial the node off-LAN.
- The revokes placed under an uncovered epoch (spec §4, exception to spec/crypto.md §4) let A's rotators learn of the departure. The departed party can read them: those actors' new public keys and box keys, M's `roles.0` deltas and the writes' authors' chain certificates, not the boxes.
- **Current `keys.0`** (`Engine::current_keys`): an actor's newest `keys.0` commit may be an inbox or deposit seed write, so certificates carry that and the rotation commits of its newest keyset per role. A keyset then often reaches a node before any secret of its actor (K's rotation under its target's label, K's box under K's label alone): `Core::unboxed_epochs` gives its owner's nodes the derived read epochs, reading only, so they still open the actor's label. Names of an older keyset than the newest are not carried: a holder's rotation comes with a departure, so the rotation naming it follows before anyone uses the epoch. Cost: one more commit per actor whose newest `keys.0` carries no keyset. Joiner's bytes down, `scale::chat_members`: M=100, members syncing with one peer, 1,994,105 to 1,998,956; M=30, each member having added a saved peer, 655,560 to 794,811 (4.6 KB per member, 21%).
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some holder of the revoking actor syncs L); chain depth equals nesting depth, at most `MAX_OWNER_DEPTH` (64) owner links (spec/permissions.md §1; a holder nesting deeper would make every standing query cost more).
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Tess's decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and hosts never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too; re-grant restores it, together with Y. The revoker's view decides, as if it were a central authority (Tess: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- One rule for both layers: the revoke's frontier is one list of commit IDs for edge and content writes, 32 B per listed commit: the demoted node's commits the demoter received on the aspects in question, less those whose parts there its own compaction could drop now (so about the tail since the last compaction plus the keep-at-least window). A long-uncompacted prolific node can make it megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), kept as long as the revoke, i.e. forever (`roles.0` is never compacted).
- Only the revoker's own receipts matter: a held commit counts as received at its apply time (`Meta::received`; a late part does not move it), a header read for receipts only at its read time (the `r/` record, IDs only). A backdated revoke lists only what was received by its cutoff (`validity::backdated_frontier_lists_by_cutoff_spec_perm_5_1`).
- **Chain writes count only through the frontier** (core/test/tla/roles M1). The rule used to exempt "A's own chain writes" (those setting the admin grants on A's admin paths) whoever wrote them and whether A had them, so after A removed admin X, X could write a backdated change to A's own grant (an `until` next week, a lower invite) and it stood. Now A's frontier lists by commit ID the role commits of its chain certificates for the target at R's point (§4: the writes on its paths, closed under their authors, so a grantor's own grant counts too; held, hence received). A forged one is not listed and drops; A's grant reverts. First cut (reviewed out): only the writes setting admin grants on A's own paths, read from the end state: a grantor's grant of A's grantor was missed (R then failed), and the end state could name a later rewrite instead of the grant R rested on. Residue: if A's authority at T rested only on a chain write A had not received (another verifier's view gives A a path A's own view lacked), that write drops and R with it; what R dropped in the same audit stays dropped. An honest node holds its chain, so the model generators mark each author's chain certificates as received (`roles_model::hold_chains`, TLA `Certs`); random receipts that skipped them made such failures look like 1 in 500 sticky residue. About a quarter of the writes that grant no admin are tagged written last (received by nobody: backdated forgeries); admin grants are never late, since an honest node does not act on authority it never received. Rates: about 1% of joint histories drop something. A snapshot's frontiers and `Absorbed` are no receipts (spec/crdt.md §8): a writer could list commits it signed ahead, or claim `X: 2^60`, and a demotion copying the claim would cover X's later writes for good (was issue snapshot-frontier-inflation). So a late joiner that got X's writes only through a snapshot does not list them; harmless: hosts lose a commit's header only once every blob of it is deleted, i.e. every live write is carried by a covering snapshot, and that valid snapshot vouches for them at nodes still holding the now-invalid originals (`flows::late_joiner_after_compaction_agrees_spec_crdt_8`, `validity::late_joiner_after_compaction_keeps_writes_spec_crdt_8`). A backdated revoke lists only the certificates A had received by its cutoff (`Meta::received`, apply time): one cut off before A received its own grant by X would drop that grant, so it is refused as unauthorized; a later cutoff works (`flows::backdated_revoke_before_own_grant_received_spec_perm_5_1`). Rejected: exempting only chain writes that do not lower their grant (a second rule for a rare case).
- Clock skew: an end by `until` or self-removal is judged by the holder's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions). If ever needed: backdate revokes by a margin.
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- Re-grant validates the gap: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it makes recovery from a stolen node's backdated mass revoke lossless. It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them.
- A revoker can backdate to roll back more; not a new power, any writer can invert others' edits.
- **Frontiers list commit IDs, never counters** (Tess's decision (a), round 13; issues/session-sources.md rule 7). With counter frontiers a revoked actor could sign a new commit on counters its demotion covered: nodes holding the original voided both (overlap), but once compaction had dropped the original and no snapshot traced the counters any more, new nodes counted the forgery. Now its fresh commit ID is listed nowhere, whatever counters it reuses and whatever its `ts` (`validity::revoked_writer_forging_into_covered_counters_spec_perm_5_1`). The demoter leaves out a commit only when every part in scope is one its own compaction could drop now or dropped as covered (`receipt::droppable_here`: covered by a snapshot it holds valid, purgeable by it, keep-at-least bound `MAX_DRIFT` past, the predicate `retention::drop_from` node-sync's `drop_covered` uses, so compaction and the frontier never disagree), and it holds or dropped every part of the commit (a part on a thing it does not hold: listed). Those are invalid after the demotion and the snapshot vouches for their live writes, so a node holding the original and one holding only the snapshot read alike (`order::new_node_alike_spec_permissions_5_1`); their dead writes are what compaction erases anyway. Before F2 any covered commit was left out: a snapshot keeps live content only, so the superseded history of a kept aspect turned invalid, and any writer could write such a snapshot just before a kick (`validity::frontier_keeps_superseded_kept_write_spec_perm_5_1`; a rotation replaced inside `ROLE_KEEP`, `flows::rotation_within_role_keep_listed_spec_perm_5_1`). Kick cost: the uncompacted tail plus the keep-at-least window (Tess: accepted); measured, a node with 200 compacted writes then removed lists 1 commit on a default-retention aspect and 200 on a keep-at-least-1d one (1 before F2), 1 again past the window. Permanent aspects get heads instead (notes/frontier-study.md F3/F4, not built). A deliberate omission is sanctioned (spec §5.1: the demoter's repudiation, Tess's option A for the lockout recovery, F5 not built). Only coverers received by the cutoff count (for a dropped part its whole `retention::coverers` chain): a backdated revoke's demoted node may have written the coverer after the cutoff, and then it is not listed and vouches for nothing (`validity::backdated_frontier_lists_write_covered_after_cut_spec_perm_5_1`). Accepted residual (Tess): Y's snapshot Z covered X's commit c at the demoter of X; Y is removed later by a demoter that never received Z; Z turns invalid and c's live writes go, even where c's body is held (with counters D covered c). Listing every received commit (no covered filter) would avoid it at frontier cost; that is local policy. One dot still names one write: overlapping session-form ranges from one session void both commits (spec/commits.md §4). Honest nodes never overlap (every open draws a fresh session). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Role commits use commit form and a session-form one is bad input (spec/commits.md §3, §4), so a removed admin cannot void its earlier grants, revive a holder it removed or void its own rotations that way (it could make its grantee's grant never have existed, and with it a removal the grantee made of it).
- Sync-then-revoke closes most of the loss from a frontier taken on an unsynced node (spec/requirements.md, Permissions); labels the node does not hold are read for receipts only (headers decrypted and verified count as received, spec/permissions.md §5.1; notes/sync.md Receipts-only reads), so removal needs no node holding the tree. What remains: writes at hosts the revoker does not reach, writes in transit, P2P-only edits among other holders, revokes issued offline or backdated; all recoverable by re-grant.
- Rejected: timestamp rule (forgeable); accept everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); roles by claimed time only (an ex-admin could mint backdated grants forever); other writers vouching for edits the revoker missed (a commit kind, a validity fixpoint over vouchers who are later revoked themselves, a per-node receipt clause and a tiebreak, all for edits that reached another writer but not the revoker; not worth it).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 already judged edge writes one by one.
- **Snapshots vouch** (Tess's decision, round 13, option A; spec/permissions.md §5.2): a compaction snapshot counts iff its author could write the aspect at it, at the strictest role a carried write could need (admin for `keys.0` and `secrets.0`: a writer's snapshot could otherwise carry a forged admin keyset, inbox, deposit seed, admin box or tombstone under a dot nobody holds) (judged as its delta by commit ID, so a demotion frontier covers it by listing its ID; a reader's snapshot gives nothing, spec/requirements.md malicious readers only waste storage); a valid one's carried writes count because its writer vouched for them, never re-judged per claimed author. Revocation stays exact where no valid snapshot carries the write (full history); through another writer's earlier compaction a removed holder's unseen last writes may stay, consistently on every node, also those holding the invalid original (Tess: fixed by hand). A valid snapshot's copies count also where the original is held, and govern a held original they misstate (below, Snapshots and history), so holders converge. The copy is the snapshot's write, never the delta's: un-merging an invalid delta removes its writes from its body, the state and the residues whatever a snapshot carries, and the snapshot's copy joins back with the payload it has (seq-order: the un-merge used to keep the delta's write whole under any dot a valid snapshot held a write of, so a snapshot taken after the un-merge, carrying a fallen insert's creation without its char, gave the char when held before the delta and not after; and an equivocating writer's second commit under a dot a snapshot carried stayed). Where a valid snapshot carries a write of an invalid delta the un-merge is a rebuild (`Unmerge::in_place`); in place only otherwise. A record (map entry, list element) whose creation a valid snapshot's copy so keeps keeps the valid writes others nested in it, from whichever body (`Unmerge::strip`, `Fragment::remove_dots_keeping`): the entry is in the state, so a writer that put into it must see its own write, and its own later snapshot, which lists that write by frontier, must carry it (map-snapshots, alike seed 4136: the writer's un-merge dropped its nested expiring write and its snapshot carried the entry's older content, so a node repaired by that snapshot read what one that had applied the write did not). Why: per-claim judging (the previous rule) needed claims (`Authors`, held claims), per-write indexes judged per (source, author, `ts`), "removed only when no valid snapshot carries it validly", refills on late owners, and still left a family of order-dependences (a dropped valid carrier let a reader's copy void the write; forged copies under dropped deltas' dots; ephemeral session attribution). Accepted: a valid writer can carry any write under any dot (it could write the value itself anyway; authorship is never exposed unverified, notes/api.md Attribution). A body (snapshot or delta) dropped under a cover that later turns invalid counts as never received again and is fetched again (holders re-upload it: uncovered, so must-hold); with no copy left anywhere its writes are gone at every node alike (notes/node.md Carried writes). A commit one of whose parts a node never held and that was deleted under that cover applies there without it: a held snapshot of any validity listing the part stands in for it (Tess's decision (a), notes/node.md Snapshot authority).
- History of the content rule: the first rule let any writer's snapshot carry a revoked author's elements; then "compaction snapshots vouch for nothing" (every element judged as its author's write; `core/test/roles-model` `content.rs` showed an "authorized at the snapshot's `ts`" variant diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered); then snapshot authority plus per-claim judging; now vouching. The divergence `content.rs` found does not return: a cover must carry what the snapshot it covers vouched for (spec/commits.md §5), so dropping a covered snapshot removes nothing.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual role grants are allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed anyway: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (owner chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin grant on G could backdate a forged write to a time it held only the grant; removing the grant first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood forever (found by `core/test/roles-model`, `two_admin_paths_class_attribution`, `chain_and_edge_paths`). Path-based audits (each removal audits what went through its path) would also close it, but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal falls with its grant: both are attributed to L's invite class on K (a forged redemption's self-removal kept after the finalization dropped its grant would burn the link and block the honest redemption the sharer had seen). Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the time it held the role (the rejected claimed-time rule).
- **Acting** (spec/permissions.md §5.2; header-actor fix): a commit naming an actor other than its author is valid only where the author's write on that actor would be (same `delta_valid`, needing write), so a valid commit's actor is its sender. Role commits must name their author (bad input otherwise): checking it inside the joint walk would make grant application depend on the actor's grants, join components on every role commit's actor, and change roles-model and TLA; nothing needs a role commit to act for another. Re-judged through `by_actor` when the actor's timeline changes (debug builds assert nothing flips outside the re-judged set). Not checked: what the actor itself may write (the author's rights decide, as before). A demotion below write on M lists the demoted node's held commits acting for M unless each of their deltas but `created.0` is droppable here (above), so a node removed from its account lists its uncompacted tail and keep-at-least window, not every write it made as the account (Tess: a kick never scales with history). Receipts-only commits are not indexed by actor, so they are listed only as the aspects in question list them. `created.0` stays valid whoever acts (its record holds by its tid), else every record created as M would be listed forever.
- Writes to `secrets.0`, `keys.0`, `label.0` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering role-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Retained copy (a removed holder's copy; spec/permissions.md §3)
The default is the `keep` field of `required.0^` (any thing, admin-only, no chat code; absent is erase): that aspect already has `^`, a kept-forever history, a valid-delta list, "in force at a key", no snapshot and no undo, so nothing new. The removal states the value: a plain reset is erase, reset plus a grant with `until` 0 is keep (one rule in `EdgeEnd`, `Edge::says_keep`). Why this and not a header bit: `until` 0 was already gone at every clock (no timer: a node behind the kicker's clock by `MAX_DRIFT` drops at once), and lies inside the signed `roles.0` delta so it cannot arrive apart from the removal. No field or aspect added. Cost: a removal saying keep leaves one dead grant on the thing until a re-grant replaces it (role history stays whole anyway). A tombstone value or a removal field adds a state every decoder must learn; a dead grant is the expired grant readers already skip. Cost of `keep` beside `rules`: the value is written whole, so concurrent admins changing the two lose one by key, and a toggle re-judges the thing as a rules change does. A separate aspect would need the settings machinery a second time (admin validity, in force at a key, forget, undo, compaction rules): not worth it for a rare setting.
A later removal on a grant decides over an earlier one, by key; a node that erased first cannot come back (keeps no more than the whole history, `any_order_keeps_no_more`). An `until` ending has no remover: it reads the default in force at its key (`keep_in_force`). A late setting joins (`required.0^` is not frozen content) and an `until` way reads it at the next role-commit or manual judging, so it can end such a copy, never bring one back: no more than the whole history, checked with `until`s in `any_order_until_keeps_no_more`. Without a later judging the copy stays: the holder could keep it anyway.
Filling is the writer's: `flows::edges::written`; `keep_now` is "after every setting held". Link: K takes the target's default when made, so joiners' self-removals read it too; a later change of the target's default does not reach K (minor; the kicker's word still overrides).
Node removal erases whatever the account's default (a removal from `Osis`'s own account and `recover` write erase unless told otherwise), and a copy kept through the account hangs on the account (`K/` record), so it goes too. Any-path: a copy stays while one way keeps. A self-removal states its own value, Tess: no protocol rule stops it, the app just does not offer it.
Kick cost is unchanged: nothing per body. Keeping costs the removed node nothing new and is cheaper than erasing (no shredding).
Accepted limits (Tess: keep the rules simple and consistent, state rare corners): every other removal reads the default, so under a default to keep a revoked link's L leaves a dead grant until finalizing resets it (one extra commit), and a removed thin client's dead grant is a way that keeps past its account's later erasing kick (the holder could keep a copy anyway); a node's grant with an `until` reads the account's default. A purge after the removal usually does not reach the copy (no label to hear it by; a purge is no exception to "no new content"), though one in a commit the node takes for another part applies (`keep_clients::a_commit_beside_a_copy`), and a purge pending at the drop goes with its commit unless another part holds it. Only ever less kept, so harmless. A hostile host can erase a copy-to-be only by hiding: a second way that keeps, or a renewal of an `until`; a removal cannot apply without the value it resets, so hiding that value delays the loss instead. A denial only, as an admin saying erase is: nothing is read that should not be. An `until` passing is judged at the time (the trigger's by-time list) and dropped once the node has heard out the labels whose closure holds what it would forget (`SyncEngine::heard`), so offline nothing goes: a renewal on the way and unsent writes from before the `until` come first (`keep_clients::an_until_passing_offline_loses_nothing`), and an expired share stays on a node until it next gets online, as on any uncooperative client; a host down, or one that never lets a pass finish, keeps it for as long, up to `ROLE_KEEP` after the loss was first judged (`LOST_HEARD_WAIT_MS`, per actor: a dead host of one thing delays only the losses whose labels it hosts). A client reads nothing past the `until` (its role ended) and a copy only once made, so an offline app sees an `until` share with a keep default go and come back as a copy when the node has heard out. A role commit received beside the expired grant that does not end the role changes nothing (`keep::a_commit_beside_an_expired_edge_waits`). A renewal made after the drop comes back by a re-seal through the stranded heartbeat (`keep_clients::a_late_renewal_comes_back_by_a_re_seal`). A write made before the `until` and sent after the thing was rotated for the departure is refused by the host (the label closed to the old key) and lost with the drop: the window for it is until the next writer rotates, as for any late upload. Hearing out is per label, not per write: a thing whose secrets derive from a lost actor but which sits only under a label the node keeps reading is still covered (its label's closure holds it); what the previous attempt (keep-after-removal, backed out) gated per node (one dead host delayed every timed loss) and with three trigger scopes is one `Leaving::timed` path beside the self-removal one. A removal of an old path that arrives after the node has kept (an erase it cannot hear of) changes nothing. A kept holder given the target after the node left it counts as a live way, so a node that also held the target directly with an erase grant keeps it: rare, and telling needs when the holder held the target against when it held the grant. In a partial order a node may erase what the whole history would keep (it cannot come back), never the reverse (`keep::any_order_keeps_no_more`). A thin client reads a copy as its account's app or through its own grant (notes/client-port.md §3, Kept copy).

## Role timeline (model findings)
Model: `core/test/roles-model` (throwaway Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test --workspace` runs the scenarios; `cargo run --bin roles-model -- [samples] [as|exempt|strat|stratw|frontier|edges|edges-prov|joint|disputes|disputes-random|digest]` searches (counterexamples printed shrunk, as traces; `digest`: notes/testing.md, Models) (`joint`: `src/joint.rs`, the joint walk over several actors with mutual role grants and commit-ID ties; `src/content.rs`: layer-2 scenarios, test-only): exhaustive up to 3 edge writes (owner, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `edges` (`src/edges.rs`) models projected rosters, links, invites (audited by level), per-op judgment and plain owner-chain writes on a thing; `joint` (`src/joint.rs`) is the joint walk over several actors (owner chains, holder actors, mutual role grants, (t, author) ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs` holds layer-2 scenarios: per-delta validity across partially synced things, snapshot authority at `ts`, and the snapshot-of-snapshot divergence that led to "snapshots vouch for nothing" (below). `trust` (`src/trust.rs`) adds trust sets and disputes to `edges` and `joint` (notes/owners.md, Model results, committed); `edges` also models finalizes (§2).
- **Third-party witnesses judged by end-of-walk roles fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a holder by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the owner's further-backdated revoke cancels a stolen node's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for edge writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin node's backdated removals stand iff the node removing it had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Demotions of a grant never audit owner-chain writes.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it; node-sync writes that removal: `SyncEngine::finalize_links`, test `until_link_backdated_grant_void_spec_perm_7`); plain owner-chain writes on a thing (a removed node's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky. Also residue (Tess-accepted): a drop whose dropped write made its demotion a fall stays after a restart where the demotion is no fall (D only grows). Every node holding the same role commits computes the same residue (the walk is a function of the held set), so it diverges nothing. Pinned cases: perm `scenarios::self_removal_dropped_without_residue_spec_permissions_5_1`, `sticky_residue_of_dropped_grant_spec_permissions_5_1`, `audit_drops_grant_and_removal_spec_permissions_5_1`, `unseen_leave_stands_spec_permissions_5_1`.
- **Self-removals are audited like any write** (Tess, simplicity): they keep only their looser authority (admin on the holder, none on the target) and carry no rotation. One through admin on holder M is attributed to the author's class on M and listed as a write on M; one lowering the author's own grant to its class on the target. Before, they were never dropped, so a node removed from account P could write backdated removals of P's grants everywhere and they stood. Accepted cost: a leave the demoter had not received is dropped and gives access back until someone removes it again (re-seal covers the missing boxes). The honest demoter covers it: `Timeline::demotion_scope` adds the targets of the demoted node's applied self-removals through each thing its class falls on (their `roles.0` receipts survive forgetting). Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.

## Role history
- `roles.0` is never compaction-snapshotted: every role commit stays, and a node that starts holding a thing fetches and judges all of it (spec/requirements.md Scale exception). About 370 B per role write plus 34 B per commit a demotion frontier lists; a 1000-member chat after a few thousand joins and leaves is about 10^4 role writes (3.6 MB), and what hurts there is the joiner's CPU (issues/role-history-join-cost.md), not bytes. `secrets.0`, `keys.0` and `label.0` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta).
- Rejected: compacting role history into an owner-chain roster snapshot with a ledger of ended tenures and their frontiers. Every write+ tenure and frontier had to stay forever (a write anywhere below may rest on any of them), so it saved only 1.1-2.6x for writer groups (20x only for big read rosters), a kick-heavy group at 10^4 could not write one, and it cost epoch-start rounds, linked frontiers and a second residue class (notes/owner-removal-plan.md, Step 1 measurements).

## Ownerless things
- Tess's request: a general, checkable "no owner" thing, replacing the burned-key owner of the chat designs (a kept key is a hidden un-removable admin). Owned things stay the default. Cost, as a burned key's: no recovery once every admin is gone (it is stuck: members keep their roles, nothing changes its grants or keys). Lockout recovery (spec/permissions.md §3) works with any remaining admin.
- Record `{2: nonce, 4: admin}` (spec/wire.md §3): the tid commits to the first admin, whose grant is in the walk's initial state from the start. Why not "granted in the creation commit" with a creation authority: anything that lets a node write the first grant without admin could be reused to grant again later (the record is public to every reader, the creator can always write another "creation commit", backdated), a hidden admin. Fixed by hash, there is nothing to reuse. The creation commit still writes the grant as a `roles.0` entry, applied through the record edge (the author has admin on the first admin's actor), only so a removal has an entry to reset (a removal is a reset of held entries, spec/crdt.md §5.6, and grant ops are derived from resets of known entries); the timeline is holder-level, so removing that entry removes the record edge too.
- Authority falls out of the existing rules: class Chain is "admin of an actor strictly above N, or the key actor at the top"; above O there is nothing, so on O every admin is Edge class (equal, removable, audited); below O, admin of O is Chain class. `MAX_OWNER_DEPTH` counts links to the top, a key actor or an ownerless thing. Chain certificates climb to the top; the record edge is a path link, so O's `created.0` is the certificate for it.
- Secrets: random at creation (a rotation from no epoch, n counted as 0, so the first epochs are n = 1), boxed to the first admin; wrapped under its own new read epoch (nothing superseded); a creator other than the admin delivers the commit to the admin's inbox. Its deltas' delete keys are the new epochs' (`Mutation::first`, `CommitSecrets::first`).
- Implementation: `osis_base::Owner::Ownerless(admin)`, `Owners::genesis`, the edge in `walk::items`' initial edges and in `Input::gather`'s `ever`/`ever_admins`/`nodes`; `Timeline::extend` declines a new ownerless record (full evaluation); components join O with its admin. Engine: `held.rs` names the admin on O (`holders_of`, `reaches`), `apply::thing_wait` treats the admin as on the chain (the record may arrive in that commit), `write::role_with` gives a not-yet-held O the admin's role. Flow `Engine::create_ownerless`; API `Osis::create_ownerless(admin)`; CLI `ownerless ADMIN`.
- Hosts: `admit own` (labels of things the host's account owns) never admits an ownerless thing's label; a host must be told it (`admit` labels) or run `open`.

## Ownership
- A thing never changes owner (Tess; notes/moves.md says what a move could be later). Within one tree none is needed: rights are grants, the root is the un-removable admin either way, so "move this doc to team B" is a grant change, and ownership depth should match the units that travel together (a folder actor owning its things moves between teams by one grant). Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).
- A root key (the recovery key owning an account) is never replaced. Nothing requires it (signatures need not be PQ, seed compromise is out of scope); nodes rotate by add-and-remove.

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `secrets.0` like any key-actor holder). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets (bearer read); the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (and so one cascade rotation of the target): two commits paid two rotations of K and of the target for one decision. perm judges each edge write of a commit on its own (as for a redemption), so such a commit is two removals at one point with one frontier; `core/test/roles-model` needs no new operation for it. None of its grants may be a self-removal (refused by the writer rules). The one-grant rule exists so every removal carries the rotation that covers it (re-seal soundness, above); a several-grant removal under one rotation keeps that, since the rotation excludes every holder it removes.
- **Why K no longer derives its secrets from the seed** (the previous design, "until K is first rotated"): every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every host) and write key, which is exactly the power the invite-only design took away from L. And L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K (allowed since d8a68b4) stranded L. Now K's secrets are random, L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip: the cold-entry path that already existed after a rotation is the only path.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- **A link outlives K's rotations**: the rotation commit is wrapped under the epoch it supersedes (holders must read it to learn the new one) and its boxes and history box are all a late reader needs, so a seed holding only the newest secret read nothing. The entry box now also carries that earlier secret (one, 32 B): the redeemer opens the rotation commit, and its history box opens all of K; `Osis::restore` got by another route, the recovery key deriving the account's first epoch and walking every rotation's box up. Rejected: a re-seal of L in a commit under the new epoch (a commit more per rotation, and a window between a writer's rotation and an admin's step, who registers it). Rejected: not rotating K on a leave, though a leaver who kept the seed can come back anyway: a node removal rotates K all the same, so the path is needed regardless, and a leaver who discarded the seed (the SHOULD) stays out. What a user sees: a link works until revoked, expired, used up or a joiner kicked, however many people leave; a leaver holding the text can rejoin.
- Limits: one earlier secret, and with forks only the registrar's pick: a rotation in a fork it does not lead to stays unread until the next rotation. A commit on K pending behind it holds `redeem` to its timeout. A host holding K's head without its claim set (past its caps) refuses like a revoked link: with every other route failed too, it reads as ended.
- **`redeem` fails at once** (`Invalid`, "no longer works") on evidence only: a refusal of L's static entry (code REFUSED, not UNKNOWN_LABEL: L is in every step until it left) with every route of the label failed, so one host's word or one down decides nothing (a revoked link with a host down waits), or a held history that put L on K and ended it (`Timeline::ended`). An L not seen yet says nothing, since its grant may still be uploading; nobody answering waits until the caller drops it. `links` and `member_links` read the roster, which holds no key removed or past `until`, so what they list works.
- **A link's target is its text's word** (nothing signs it): `redeem` grants only after K's grant on the target is here, so a link pairing a target with another thing's K joins nothing, and `forget_link` has the lost-access trigger judge K, so what only L read goes. K's label carries the grant (delivery, then the sharer's certificate copy), so honest links reach it pre-grant, target unknown too. `Invalid` needs a complete pass of K's label and no commit pending on the target at the timeout: a node cut off mid-read hears `Network`, since an app reads `Invalid` as a dead link. Forgetting drops the hinted label's session too (K's commits may not be here yet, so `Forgotten.labels` lacks it): the secrets its head gave go with the key, and a retry must claim the head again. Not bound: K's owner can put K on anything else, before or after a redemption, and K can be any actor with L on it (an existing chat holding a role on the target): a joiner then holds all of that too, as with any actor it holds a role on, and the link names only the target.
- Finalization: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer node writes a real removal; until then the link is honest-client-only. Node-sync (`SyncEngine::finalize_links` over `Engine::links_due`, any node holding the seed thing and admin on K, woken at the `until` by `next_link_expiry`) writes it after a complete pass of K's labels ended after `until` (passes from before going offline do not count), so the frontier covers honest grants that reached the hosts while the link worked. Without saved peers only the node that made the link finalizes, at once (redeemers reached it directly; another node of the sharer may lack their grants). A seed thing counts only when its owner is K's owner (a co-reader can add a `link:seed.0` thing to a shared group). A K whose label never completes a pass (host gone) is never finalized: the link stays honest-client-only. Residual window (Tess: keep, documented on `LinkOpts.until`: an expiring link closes when one of your nodes next syncs after `until`): while every sharer node is offline after `until`, or K's host is unreachable, a backdated grant uploaded then is received in that pass and covered and stands; cutting it would also cut honest late-received grants (indistinguishable: both carry `ts` < `until`). Future option: a host receipt time as witness, one feature for removals and link expiry together (issues/revoke-needs-whole-tree.md, remaining gap), not a link-only one. Idempotent: `Timeline::lowered_unaudited` (the walk's `prior`) is cleared by the first explicit write, so a second node's concurrent removal restores and audits nothing. Alternative (no `until` or single use at all) loses nothing a hostile holder respects. Race flip: the finalization's frontier can drop a competing redemption the sharer had not seen, so a redeemer that lost by its own view may win; a loser therefore keeps K's secrets and labels while L's self-removal is unfinalized (`contested` in `rotation::lost_among`; test `single_use_loser_keeps_secrets_until_finalized_spec_perm_7`), and drops them once the removal arrives. Only redemption-shaped commits count on both sides (the void one and the applied one that lowered the signer's grant): a plain leave then a void grant (a leaver's forgery naming a removed holder) defers nothing (test `void_grant_by_leaver_keeps_no_secrets_spec_perm_3`; before, any self-left holder could keep any removed holder of the thing holding its secrets for good). Residual: an inviter whose leave commit also granted someone can later forge a void redemption naming a removed holder, who then keeps the thing's stale secrets (no new epochs) until an explicit write on the inviter's grant. Cost: never finalized (sharer gone, a K host gone for good: `complete_pass` waits for every host), the loser follows K's and the target's labels for good. Not bounded in time as pending grants are: past a bound the race flip would leave the winner unaware again. Inbox delivery of the removal to the joiner alone failed: the loser had already dropped and forgotten the target's secrets, and nothing brings them back.
- **A removed node keeps the seeds** of the account's links (they sit in the home group), so it opens K's head by L's static entry past the removal's rotation until each link is revoked. Not ended by the removal: a link shared in advance dying because a phone was replaced would surprise; so `remove_node` returns the account's working links and the caller decides (`node rm` prints a revoke line per link, `--end-links` ends them). Any node of the account can list and revoke any of its links, one made on the removed node too: the seed thing carries K, seed, target and single use. A link made on the removed node and not synced yet is unknown here. Whoever holds that node can redeem before the revocation and stays a joiner, as with any link holder: remove K, or the joiner, for that.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): what a link conveys is "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add grants for actors with no current grant, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier like any edge write. Inviters seal only secrets they hold (their role and below). Holders read K's roster (they are its holders), like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- A sharer rotates its dialable key and lan secret when a link ends (spec §9) since the link text may be in strangers' hands. A single-use link finalized by its redemption does not: its one possible user now holds a role and keeps the direct path.
- Self-removal lets an actor always leave or lower its own grant; single-use links use it to drop L's own grant.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (spec/permissions.md §7: kicking one joiner otherwise kills the link for all).

## Patterns
- **Grant on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per holder, so not per note in a folder).
- **Shared owner** (spreadsheet): one actor owns everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: an offline key owns a minimal root actor whose admins are a few accounts; teams, chats and docs are owned by the root or by actors under it. Root admins can remove anyone below, and a departing founder is just an admin removal. A team owned by an account cannot shed that account (owners are un-removable).
- **Shared tag** (rights live on grants, never on grouping; owners never change; notes/tags.md): the tag is an actor; things keep their owner and each gets a grant for the tag's actor (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same grant so rosters nest; writers may also create things owned by the tag. Per-holder grants on each thing do not work: entitlement puts a thing under the tag's label only when the tag's actor may read it, so no label the holders sync would carry it. Built in core/osis/tests/it/tags.rs.
- **Chat**: see notes/chat.md.
- **Realm** (design, notes/realms.md): a user-facing actor (`realm.0`); members are its holders, contents what it owns or holds a grant on.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and ownership (each owns its messages), and `group.0` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and owner actors stay separate; a group may also be an actor when it serves as a shared label.

## Required retention (`required.0^`, spec/commits.md §5)
Decisions, for the next reader:
- **Prefix, longest match**: no matching language; expresses one aspect (`name.0`), a per-year family (`chat:msgs:`) and everything (empty). A name-without-version key could not express the family. The empty prefix is what stops junk on an aspect nobody named.
- **Exact match, no ordering**: purge sets are not a scale, so "at least as strict" has no meaning. A duration is part of it because retention on the wire includes expiry and a required permanent retention must rule out expiring writes.
- **Key order, as an admin-only aspect**: the setting in force is a function of held deltas and the timeline, so every arrival order agrees; a fall re-judges later deltas (`in_force`, the thing re-judged when a setting commit is, acting included). Same-commit deltas are not under it: "before the key" is strict.
- **Whole value, read a delta at a time**: judging needs no CRDT replay up to a key. Writers turn `set` into a replace; a hand-made partial delta only hurts its admin. The CRDT state and the rule can differ only on two admins in one ms.
- **Fixed `nobody`, kept forever, never snapshotted**: a later node must judge an old delta as everyone did, so the history of the setting cannot be compacted. Cost: one body per change, admins only.
- **Bodies, the one departure from the issue as written**: dropping a broken body everywhere would let an admin stamp a change below existing history and erase a `nobody` or author-only body with no right. So a node drops only what it received after the setting (its own `received`, a tie keeps it), and holders of older bodies keep them; a backdated change invalidates (as an empty-frontier demotion already can) but erases nothing they hold, and removing that admin brings it back. The dropped part is a `Dropped { broke }`: reopened as missing when it turns valid, fetched again. A pass drops only with every entry of the label open, so a role commit still to come cannot be what would have saved the body.
- **A broken delta falls alone**: a commit's other deltas stand, its own thing's and others'. Taking the whole commit (an earlier version) let an admin of thing C decide a delta on thing D of a commit naming both: a member of D alone never holds C's setting, so reads differed for good (test `commit_across_things_reads_alike`). A missing broken delta holds nothing back: no commit waits for a part (spec/commits.md §4).
- **Hosts**: a node that dropped a body and holds the label's delete key deletes it at the host, a holder does not put it back while it is invalid (no live write), so a new node never receives it while the setting stands and reads alike; once the setting falls a holder uploads it (test `setting_below_a_body_erases_nothing_held`). So under a hostile backdated setting that stands, the bodies live on their holders' nodes only: if every holder is gone by the time it falls, they are gone. A hostile admin has the delete key anyway; holders re-upload a valid body after that, not an invalid one, and that is the whole difference.
- **A setting by one not a possible admin goes without a right**: it binds nothing, and `nobody` with no exception would be junk a mere writer leaves forever on every node, in memory too (`ix.required`). The author alone: a delta is judged by its author's standing, so a header naming an admin as actor saves nothing. A possible admin's setting never goes (`Held::ever_admins`, any validity, only grows; `first_held` would count or drop the same setting by whether the signer's grant had fallen yet: test `signer_whose_grant_fell_alike_in_every_order`). A late grant may find the setting gone (reachable honestly: a grant at one host not yet relayed to another, an admin there drops the setting and deletes it at that host; test `setting_before_its_grant_comes_back`): if it now stands it is fetched again (`unbreak`) and a holder puts it back. The one loss: the setter's only copy was that host's and the setter is gone before any other host has it. Bounded on the other side by `MAX_REQUIRED_ENTRIES`; what is left unbounded is an admin's count of settings, one body each.
- **Cost** (release, one aspect, 10^4 and 2*10^4 deltas, linear; load about 25): a setting flipping every delta 110 and 250 ms, about 12 us per delta, so 12 s at 10^6 with the engine lock held, the class of the long aspect table's fall of the 30% member (11 s), and only an admin can cause it; a setting that stands and flips nothing 6 and 12 ms; a writer's, invalid on arrival, 0.4 ms at any size (before: the whole walk, 0.8 us per delta, by any writer). `Judge` judges a thing's settings once, so fallen ones add one walk, not one per delta. `drop_broken` over a whole thing decodes only headers of invalid commits.
- **Snapshots**: exempt, so a writer's snapshot may carry what it held of a broken delta, as for a demoted writer's write (it vouches). The rule is about bodies that cannot be removed; a snapshot is `writer`, so anyone with write removes it.
- **Accepted**: a member from before a change can backdate below it (set it at creation to rule this out); a writer that has not seen a change writes invalid deltas until it does, told by `OwnWriteInvalid`; a late copy of a dropped body is held until the next pass drops it.

## Purge rights and retention
Retention is per delta (spec/commits.md §5), decided with Tess. Default `author_or_admin`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and keep at most 0 after replaced implies it. `nobody` is for records that even admins must not drop. `admin` is what role commits use. Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (Tess's call; hosts approximate it, notes/sync.md). The right is exactly validity (§5.2) of a delta needing the role at the request's key, so a re-grant gives back a gap request's right as it does its writes (seed 3001: else a re-grant revived the reset but brought the purged value back). Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever, and a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart. Fields are immutable: a change would need the blob re-encrypted anyway (commitments are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.

**A purge follows the timeline, both ways** (was issue purge-by-removed-admin, purge-before-demotion.md; Tess: a purge setting is a promise, deletion that is rightful really deletes, a wrong one must not destroy what honest nodes hold). `Timeline::purge_stands` reads `delta_valid` as well as the role at the key, so a request a demotion's frontier leaves out holds no right whatever its `ts`. `retention::rejudge_purges` runs at the end of `rejudge_once` per aspect with a held request on a re-judged thing (`p/`): a part a request comes to drop is purged, a part dropped for one that no longer does goes through `reopen` to `missing`, the one mechanism `Dropped { broke }` and `uncover` use. Not kept per body: own-write parts read the value-less list, others one flag bit. No settling window at hosts: at 0 the demotion-first holder restores, at infinity a rightful purge never deletes, so a value could only turn "usually" into "more usually" (fails notes/arbitrary-values.md). A node syncs a label before it deletes under it, so the window is only a demotion not at that host yet, the same a hostile admin before removal has: it had the right as far as anyone knew. Lost for good: only a body every holder dropped before any heard of the demotion. A holder uploads a must-hold body and a stale node deletes it only until that node syncs the demotion, which lies at the same host: judgments are functions of the held set, so the war ends. A holder that saw the delete still uploads though the body's writes are carried (`Engine::named_by_a_fallen_purge`, `delete_stands`): the delete-keeps-it-out rule assumes a keep bound passed. A stand-fall-rise with no copy left must leave what a node never seeing the fall has, or an older value resurfaces: a delta's `w/` row outlives the fall and counts only while it is value-less (`make_valueless` joins it when no body gives one, covered parts too); a snapshot's stand-in is a bit (`Dropped::stands_in`), set on any drop other than as covered, so after stand-fall-rise with no copy it stands in again (seed 32032; once a limit while it kept frontiers). A frontier lists requests by `requests_resting_on`, not by the things where the class falls: the right by author runs signer, actor, thing, and the signer may keep its own grant on the thing (found by review: a node removed from its account). At the list bound any listed request may go, last received first; rightful or not it falls (hostile flood: reaches only requests of the same demoted set, so an honest delete is lost only where that set also holds honest signers). A header-only blob left from a fallen purge stays at the label as may-hold (300 B each, spec/sync.md §6): deleting it needs every node's agreement that it is not lasting. The gate is separate (`counts_as_purged`): a missing delta counts as held on the word of a possible right holder (`Held::ever_admins`, `ever_writers`, monotone), or a demotion's place in the order would decide whether a commit applied; `known_purged` still decides the stripping. Snapshots dropped for carrying do not say whose values: all come back with a fall; one carrying another's standing purge goes again on arrival, so that value stays gone. Where no node has its body it stays missing, and what it alone covered goes missing with its live writes until a writer's next snapshot, which every writer takes after a purge (`reaches`-style rules using its kept frontiers were tried: dropped without the body they judge differently from a node that saw it, order::purge seed 890023). **What reverses a purge**: only a demotion whose frontier omits the request. A demoter's frontier lists every request it received of the demoted node on a thing in question, for a fall below admin too (`Engine::frontier`), so an honest demotion reverses only a request the demoter had not seen (the backdated or raced one this rule is for). A hostile current admin can omit on purpose (§5.1 repudiation) or backdate: the purges of the one it demotes fall, and the deleted values return only from a holder that kept the bytes, as a holder could show them anyway; hostile admins are out of scope in spec/requirements.md and they could re-post the text. A demoter that never held the request (a fresh node past `ROLE_KEEP`, non-permanent delta) makes it fall too; the body is gone at honest nodes, so that reads as never received. `snapshot_right` shares the rule without the listing: after a demotion below admin an admin's old snapshot no longer lets a node drop bodies under `admin` (a growth price, no data loss). Snapshot stale drops stay dropped: making a no-right snapshot not cover for must-hold does not converge (issues/covered-body-new-label.md), and the dropper held the right itself. Demotions list requests by ID (`receipt::fit_requests`: over the list bound the ones received last go, so a heavy moderator stays demotable; a flood lands last). A fresh node omits what it never held: only a node still holding the body brings a message back, `tombstone::a_fresh_node_demotes_and_nothing_comes_back_spec_perm_6`. A snapshot's right falling with its demoted author is storage only: `snapshot_right` is read by `drop_covered` and `droppable_here`, not by `covered`, so reads and must-hold are unmoved.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the host (host stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with Tess, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous holder: a fresh actor with its own owning key and node keys, joined via a link or grant; the granting admin may record pseudonym -> account in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Holders write as A in commit form. Caveats: any holder can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a node the holders trust re-signs their edits under its own identity.

## Implementation (osis-perm)
- Owner chains: every walk up creation records (perm, engine, osis) is `osis_base::owner_chain(t, lookup)`, yielding `ChainStep::Up` per link, then a key-actor or ownerless top, an unknown record, or `TooDeep` past `MAX_OWNER_DEPTH`; callers differ only in their lookup (held, ephemeral, a commit's own records) and what they do per step. `Owners::chain` gives a too-deep thing neither ancestors nor top, so no Chain class (the engine judges writes there invalid); effective role still follows owner links one at a time with no depth cap (spec §1 defines it by paths).
- Input: the node implements `HeldSet` (things, role commits with an edge write per thing, `created.0`; applied commits only, pending ones not) and adapts headers into `types` records (edge ops with their `roles.0` dots, frontiers resolved from links). perm parses no bytes, holds no state, depends on osis-base only. `created.0` that does not hash to its tid is ignored.
- `Timeline::evaluate` is the from-scratch walk (`walk.rs`); queries take `At` (state before a point, edges alive at a ts; `At::END` = current state at the end of time, where re-grant is judged): `roster`, `role`, `invite`, `class`, `standing`, `applied`, `dropped` (with the dropping demotion's point), `demotions`, `delta_valid` (layer 2), `certificates`/`write_certificates`/`certificate_set` and `verify` (§4), `may_purge`, `may_rotate`, `demotion_scope` (what a demotion's frontier must cover; the node fills counters from its receipt record).
- `Timelines` (incremental): components of things joined by edges, authors and ownership, each evaluated from scratch and cached by its exact inputs; `changed()` lists the things whose component the last update evaluated (plus `update_touched` below; the node re-judges only deltas on those, plus commits whose void, required-role or overreach inputs changed; everything after a rebuild at open; a debug assertion checks the rest is unchanged). A component that only gained role commits continues its walk (`Timeline::extend`: same things, `created.0` and nodes): the final walk rolls back to the earliest new commit p and goes on; else from scratch. D is kept in the order the final walks found it (`Walked::found`, saved in the walk cache): the drops found before the first one found by a write at or after p are found again, in that order, by an evaluation from scratch (every walk up to them saw only items before p, and each walk under a prefix of D finds nothing before the next drop's point), so they stay; the rest are forgotten and the walk rolls back to the first write they dropped too (the final walk's prefix there is the walk under the kept drops). This replaced a fallback to from scratch whenever any restart had reached p. Fast path (`Timelines::append`, `Timeline::append`): when every touched thing is in a component, its `created.0` unchanged, and it only gained commits whose author, holders and targets are in that component or are new nodes (nothing held of them but a key actor's `created.0`, in no component or alone in one, above the root: they join it), the component is neither re-partitioned nor gathered again (a commit is recorded under every thing it writes, touched or not): the timeline keeps its `Input` and its walk items (role commits are commit form, so no session-form range can void one). A new node can join because nothing it reaches is held yet (no edge of it as holder, owns nothing), so no earlier audit met it (`Input::may_be_node`). New commits go in in timeline order; each is placed without walking again where exact (`Walked::insert`), else the walk resumes from it. Declined (resume from it): a drop of D found at or after it (found by an earlier walk, whose state there is not kept, so whether it changes what that walk found cannot be judged from the final walk), a later item writing an edge it sets (that write's restore reads the new value and the difference runs along the edge's later writes), two of its ops on one edge, and its own audit dropping something new (D grows: the walk restarts at that write anyway). Otherwise the walk with it is the walk without it plus its own effects, provided every later item that may read it does the same with it as without it. Which may read it (static, over `Input::ever`): with (M, T) its edges, roles change only for what reaches some M at any time (A) on what some T reaches (F), and only up to the widest role among the edges' values before and after, since every path through them is that narrow; so classes change only through an admin value or an invite (on the edges or on an `ever` holder in F), demotion thresholds only through write or more; reaches change regardless. A later item may read it by an author in A judged on or for something in F (when classes may change); applied explicit on (m, t), by m in F (its author's kept standing reads the reach back from m), and when roles may change by t in A (reach forward), a new node reaching m, or m reached from A with t reaching into F (an audit of a node of A on a thing of F); a later fall of its author on a target it applies on (that audit reads it); and, where its author's first held write on a target moves to its point, an explicit write after it up to the old first write whose holder the author may reach and whose target may reach the target (falls are recorded only after a first write, so these were not; the top of the target's owner chain never falls there). With none, its changes, undo entries (`by_author_target` in walk order) and mark are spliced in directly (`place_plain`). Else (`place_shadowed`) a shadow `Pass` (`Pass::shadow`: the edge state at its place, its edges' records copied from the end state, which is theirs there; audits also read the walk's own write records before their point, `outer`) walks it, then follows the history to each such item and walks it again: its edges' records before it come from its undo entries (the first entry of each kind per edge holds the value before; an item reads no record it does not log), the cached roles are kept as `change` keeps them and restored after each item. Its effects (history, undo entries, applied records, demotions and falls; the last two by key from the entries at its point, and compared regardless of order within an item) are compared with what the walk recorded there (`Walked::recorded`); equal for all, its own effects are spliced in (the log rebuilt once) and the falls the moved first write brings are put before the recorded ones (none was recorded up to the old first write) with their undo entries at the end of their items. An item of the A-audit kind alone is first checked cheaply: when, with and without the new edges, no node of A reaches its holder or its target reaches nothing of F (a standing there reads roles only on what its owner chain and holders reach, all in F if any is), it cannot read it and is skipped. A re-judged item costs about 0.5 ms at 10^4 (they are the costly items: team-edge audits of many nodes), so past an eighth of a long rest (512 items or more) the write re-walks instead (`SHADOW_SHARE`, a cost choice; debug builds can force either path per thread, `force_shadow_guard`, and a test runs both on the same arrivals); figures in issues/perm-eval-cost.md. When an item does otherwise or drops something new, the walk is exact up to it: the commit's effects are spliced in and the walk goes on from that item (`Placement::From`), not from the commit. Debug builds compare every shadow placement, every `From` continuation and every joining `extend` (below) with a from-scratch walk on inputs up to 400 commits (`Walked::check_scratch`: history, applied, D and its found order, demotions, falls, edges, edge and write records, marks and undo entries per item). Then the end state holds each edge's state at its place (nothing later writes it), later kept states shifted and given the new edges (Walk cost), `first_held` kept before it. The random late-arrival test (`append_adversarial_*`, now with two nodes only some writes name) has 3000 samples on three seeds. `append_shapes_*` adds owner chains, nested teams, `until` on every role, invites of every level, two-op commits, batched arrivals and restarts from saved walks, and counts placements. A record can grow under its commit ID (a commit's edge writes arriving late): `append`, a cached component and `extend` compare held records with the walked ones by content (frontiers by size, as the saved-walk tag), not by ID alone (`Input::holds_commit`). Checkpoints and `first_held` carry by the history prefix the resumed walk reports as shared (`Outcome::common`: `rollback` moves the old changes it drops aside, `finish` compares them), not by copying and comparing the whole history. Equal to one evaluation (random and timeline-order arrivals, 2000 samples, dropped points and roles before every applied write compared). ## Snapshots and history (Tess, round 13)
A snapshot is trusted for current content only, never for authorship or time (spec/permissions.md §5.2). Was issue forged-cover (closed): a valid writer's snapshot copying another value under the dot of a delta its holders had dropped before others got it showed the original at the holders and the copy elsewhere, for good.
- **Content**: every node follows a valid snapshot's copy, also where it holds the original: where a held delta and a held valid snapshot disagree under one of the delta's dots, the delta counts for nothing there and the valid snapshots' copies join by the copy order (the tie-break between disagreeing snapshots). Nodes holding the same valid snapshots read the same whatever deltas they hold. No worse than the writer writing the value itself; later writes win as usual. Only valid snapshots count, so a reader or a removed writer (frontier not listing the snapshot) changes nothing; a snapshot turning invalid gives the held original back. Mechanics: notes/node.md (Valid snapshot copies govern).
- **History**: authors and times come only from verified commits held here (notes/api.md Attribution); content known only through a snapshot has none. The API audit found nothing attributing through snapshots: the commit query and `created`/`changed` read held headers only (snapshots are no change), a watch names the commit applied (a snapshot correcting a held original is reported as the snapshot, its author and ID), undo and revert act on held commits.
- **Detection**: a node holding the original reports each misstating valid snapshot (`DiagnosticKind::Misstated`, from the rebuild that applies it, deduped; not for value-less copies alone, which an honest snapshot taken after a purge not yet seen here carries).
- **Residuals**: a copy misstating a delta this node dropped cannot be compared (the body is gone): it joins by the copy order with what the state kept of the original (a valued copy beats a value-less one), so where the original wins that order a node without the residue reads otherwise until both hold a snapshot carrying the original (a covered drop's cover does; a drop for keep bounds leaves only the residue); a snapshot turning invalid leaves its copies under dots of deltas whose cover was dropped for its bounds (the state alone holds those writes).

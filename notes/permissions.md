# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: Tess's direction, concepts, keys and rotation, sharing, certificates, revocation by demoter frontiers, retained copies, the `core/test/roles-model` findings behind the role timeline, role history and its measured cost, first admins and record chains, links, patterns, required retention, purge rights, public content, anonymous writing, and how osis-perm and the engine's role flows implement it (with measured costs), rejected alternatives throughout.

## Tess's direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: admins, editors, viewers.

## Concepts
- **Terms** (Tess; spec/permissions.md §1): rights are roles given by role grants, and an actor with a role is a holder ("Dana holds write on X"); member and membership mean only being in a group ("this note is a member of Work"), which grants no rights. One word per sense in code, API, CLI and spec; a CRDT set's value is an element, a `Slots` entry a slot.
- Any thing becomes an actor when it needs holders of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the role-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope beyond per-node sides in a fight (notes/disputes-plan.md).
- Not promised, so not in spec/requirements.md: anonymity against network, timing and style analysis; revocation reaching a group before one of the revoker's nodes next syncs it.
- What a commit spanning two things reveals to a reader of only one (Tess's wording in spec/requirements.md: no values, only metadata): the exact metadata (thing ID, `ai` list, record chain, size) is spec/wire.md §4's, and may change there without Tess's sign-off.
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things) derive secrets like any plain thing.
- Nodes are things that own themselves and grant nobody anything. The node card under every label a node tracks shows the readers of L which nodes sync L (a read-only node's card arrives by deposit), never a roster. Rejected: a grant of admin from the account to itself (covers only own nodes); a nodes group readable by contacts (leaks the node roster, misses read-only co-readers). `reach.0` carries the dialable key, relays and any global addresses (notes/networking.md Reach items) and goes under every label the node syncs (IP consent).

## Keys
- Writes are node-signed plus a chain of role grants. Sharing an actor's signing key erases which holder wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to sign deletes of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the admins), demotion write -> read (rotate write only), removal. A writer's rotation of read and write leaves the admin secret, its boxes and the label delete key where they were (notes/crypto.md, Epochs per role).
- **Forks**: concurrent rotations fork the epoch (spec/crypto.md §4). Boxes are keyed per epoch so both rotations' boxes survive the merge, holders keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it. At a host the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many holders forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (holder, role) (holders end up with different secrets after concurrent rotations and cannot read each other's new wraps); rotating a forked role because a box to M names a fork other than M's newest (A's and M's first admins each judged the other's box uncovered and rotated A back and forth); rotating every forked role (`used_link_with_sharer_offline_spec_permissions_7` hung). Epoch numbers others name are never trusted: the next n counts from the rotator's current epochs only, a pending commit records no epoch beyond its bounded reading-only secrets, and an epoch above 2^62 establishes only next to an established one at n-1 (a planted n = i64::MAX would overflow n+1 and block every later rotation, so removals too).
- **Write or above rotates its roles and below** (decided with Tess). With admin-only rotation, every actor an account holds a non-admin role on would keep wrapping new content to a lost node until its admins happened to rotate, and the account could do nothing. So the account's own node rotates every actor it writes to when it removes the lost node, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks holders out, worse than the storage waste a reader may cause; an actor the account only reads keeps wrapping to a lost node until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a host, which only ex-admins can (notes/label-access.md). Until an admin registers the newest epoch, a removed node keeps the old sync and write keys at hosts: ciphertext it cannot open, stale stamps and level-3 deletes that holders heal. Residue: a holder that has not heard of the removal wraps under the old epoch, and the lost node reads that one blob (as with Signal sender keys).
- **A `secrets.0` record needs the role its key names** (validity `secrets_role`): a map record acts only on the entry of its key (spec/crdt.md §5.6), removals included, so the role and the removed box are read from the delta alone (`keys::secrets_write`); a key-erased record needs admin. Rejected: looking up the removed entry's creation key (its answer depended on which bodies a node had held). `roles.0` perm adaptation (`edge_ops`) still names a removal's holder by its entry's creation (`holder_keys`, unresolved until held) but ignores a reset carrying another key, as the CRDT does.
- **No periodic rotation, no rotation policy** (Tess). A node compromise is either known, and the removal rotates before the next write, or unknown, and the node is still a holder, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy would need the node's KEM key to change from randomness the thief lacks; the seed is the node, so a thief holding it is the node. History boxes mean a compromise yields all stored history anyway; "no history for new holders" and bounded history are app or future choices.
- **Plain things derive secrets** until they have a holder other than its first admin, so nothing is stored; then explicit secrets, so that removing that holder rotates the thing alone and not its base actor. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, one-way from the base actor's), so wraps, delete keys and label steps need no special case. Content of the derived era keeps the base actor's delete keys: a later admin of the thing who is no admin of the base actor cannot delete it by key at hosts, only by the label delete key (accepted, Tess). A derived epoch has the base actor's n capped at 2^62 − 1 (notes/crypto.md, Derived epochs). Explicit secrets do not stop the cascade the other way: every rotation of a base actor is caused by a removal, and the removed holder could open every explicit secret its roles reach (things below it, grant targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `keys.0` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin acted.
- **Nesting cost** (accepted by Tess): removing a holder rotates every thing with explicit secrets whose secret it could open, so a lost node costs one lazy rotation per shared thing the account reaches; the usage rule is to share sets through one actor. A thing's admins learn what it holds roles on because every grant whose holder is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct holder per rotated role, one re-registration per label per host. A company of 50 teams with 10 labels on 3 hosts: 50 boxes and 30 signed messages per account removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `keys.0` window**: until an account's new `keys.0` reaches a co-actor's label, rotations there seal to the lost node's old keyset and its steps list its old claim key, so the lost node reads new content via an honest host. Hence the MUST to place the removal and new `keys.0` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **A removal and the rotation it requires on the target are one role commit**, so the rotation and the departure travel together (both parts on the target, one body; a sender holding the keys may still split them, spec/commits.md §4), and an omission in a held rotation can only mean the rotator did not know the holder. Without it (TLC, core/test/tla/rotation R1) a node receiving the rotation before the removal re-seals the removed holder, who reads post-removal content from an honest host (it holds the current sync key). It costs nothing: the remover had to rotate before encrypting the removal commit anyway. The inbox copy to the removed holder and the certificate copies carry the grant delta only. Rotations of other things (the cascade) stay lazy; they exclude nobody directly. A later rotation by a node that knows the removal carries no removal, and a node reading it out of order would re-seal the removed holder: establishment by names closes that (notes/crypto.md, History boxes and establishment).
- **Re-seal is a SHOULD with a trigger** (a current holder without a box at a current epoch, or a stranded report: a Stranded message from a connected peer, a stranded notice in an inbox); without the trigger a grant raced by a rotation was a silent permanent lockout. A missing box marking a deliberate exclusion looks exactly like one marking an unknown grant, hence the guards: a re-seal decision comes at the end of a complete pass (every host and peer log read to its end: cheap to know, and what makes the post-compaction case sound), only at established epochs, and only to current holders: a re-sealer makes the rotations and finalizes it may first, re-seals even while a departure stays uncovered (a box carrying a secret is encrypted under its recipient's key, notes/crypto.md, The three promises), and boxes nothing to a holder whose grant it may finalize. A late joiner holding only a snapshot rotates instead (a rotation boxes everyone it thinks current). Opening a label is not encrypting under (notes/crypto.md, Wraps). The remover uploads the rotation before registering the step (notes/label-access.md), so a holder listed in the step never strands merely because the commit is not there yet. Residue (notes/label-access.md Re-seal): after compaction a node's view of the roles no longer travels with the epoch chain, so a node boxing a holder at a snapshot-established epoch from an incomplete view (a host that never got the removal, an interrupted first sync followed by an eager rotation) can box a removed holder; healed by the next rotation of a node that knows. 
- **What a removal reaches** (`osis_keys::reached`, over a `Graph`: `PermGraph` adapts a perm `Timeline`, `MemoryGraph` for tests): the things the removed party's roles opened, things below them and grant targets transitively, linear in the graph: the labels a removal is placed under; `lost_access` (what a node drops) uses it too.
- **Depth 0** (Tess; notes/crypto.md, Holder actors at depth 0): a departure is from the actor itself; one inside a holder actor M reaches the actor's boxes only as M's new keyset, which makes them stale, actor by actor up. Before M rotates, a node holding M's secrets that knows the departure finds A's epoch boxing M at M's uncovered keyset blocked and rotates A leaving M out. `ensure_rotated` cascades over the holder actors this node may rotate (post-order, each once), so where it may rotate M its one rotation of A seals M's new keyset. Tests: `rotation::tests_members` (twelve deep, diamond and lattice, cycles, ignorant fork, forged keyset, hidden grant, the stated limit on grants), osis-node `flows::cascade_two_hops_spec_perm_3`, `inside_member_departure_leaves_holder_out_spec_perm_3`.
- **Role cycles**: X and Y readers of each other, D removed from X: Y's epoch boxes X's old keyset (D holds it), so X's new epoch boxed to Y leaks, and any order of lone rotations that box each other leaks. Cycles stay allowed (Tess: tags become members of each other by ordinary use; two people's shared tags have disjoint admins; nested shared tags can be one-way), but no key cycle forms (rule 4; Tess left the rule to the agents, model-checked first): the grant closing a cycle is keyless and its holder boxed nothing, so a cycle reduces to member chains. Every rule without it failed in Depth0.tla (notes/keys-requirements-study.md). Also rejected: joint rotation of the cycle in one commit; forbidding cycles. A hidden earlier grant leaks until the writer holds the grants (taint, notes/crypto.md).
- **Re-seal invariant** (`reseal_candidates`): once re-seals settle, every node counts the same current epochs (supersession is read from the rotation commits) and every holder with key access holds every current epoch any node holds; once history adds settle too, every holder of a current epoch holds every earlier superseded established secret any of its holders holds (both checked by the rotation property, `rotation::tests_property`). A re-seal is made only if it adds a box the trigger asks for (`forked_role_reseal_reaches_fixpoint_spec_permissions_3`; without that, churn seeds 140170 and 140188 looped); requiring every fork's secret of a re-sealer stranded a holder when no node held them all. A node lacking a role's current secret (a rotation left its holder actor out) rotates it all the same when a rotation is due (rotating needs no secret, notes/crypto.md): the epoch it lacks is superseded unread and a holder adds its secret to the history (`rotator_lacking_read_rotates_read_too_spec_permissions_3`, `rotator_lacking_write_rotates_history_added_spec_permissions_3`, `removal_lacking_rotated_secret_rotates_spec_permissions_3`). Cycle tests: `rotation::tests_members::removal_in_cycle_spec_crypto_4` (2- and 3-cycle), `departure_below_cycle_spec_crypto_4`, `cycle_with_disjoint_admins_converges_spec_permissions_3`, `cycle_concurrent_departures_spec_crypto_4`, `second_admin_ignorant_fork_in_cycle_spec_crypto_4`, `hidden_grant_tainted_keyset_spec_crypto_4`, and the rotation property's holder-actor histories.
- **Lockout**: removing a writer that rotated to itself recovers, and so does the admin's next due rotation once a departure is known (notes/crypto.md, Lockouts); a hostile admin is a dispute. With no admin left (a thing whose admins are all gone) nothing recovers.
- **A finalize names the write it ends** (model core/test/tla/rotation/Finalize.tla; spec/permissions.md §2, spec/crypto.md §4 Met): a role commit resetting an entry whose creation the node does not hold applies none of its edge writes until it does (`ix.unresolved`), and a name is met only for a commit so resolved (`NamesHeld::resolved`); otherwise a node holding a finalize without the `until` write it ends counted the departure as met (withheld-departures seed 3, `finalize_without_its_until_unmet_spec_crypto_4`). Rejected: met once each lowering edge write it makes applies (an erasing finalize derives no write, so nothing is asked, and leaks; beside a renewal every rotation names the finalize and none is established); known writes of such a commit applying alone (a name then covers a holder its other write had not yet removed), rotating instead of re-sealing a holder a name removes (leaks through the new history box). Limit: a commit resetting an entry the node never gets never applies there.
- **A timed end is finalized** (Tess: any writer finalizes; checks in notes/keys-requirements-study.md): a grant past its `until` is no key departure; keys read no clock (`Core::key_holders`, `rotation::key_role`: every applied write in effect, `until` disregarded, the `until` 0 keep value no grant). A node with write about to encrypt under T (`rotation::ensure_rotated` → `finalize_due`) first writes a finalize of each ended grant on T of role at most its own: a removal with no frontier carrying the rotation (`flows::edges::finalize_in`). The timeline applies a frontier-less removal of another's grant only as a finalize (perm `judge`, `Attr::Finalize`: grant past `until` at its `ts`, author with write and at least the grant's role; no class, never audited), so a renewal ordered first wins and an admin's racing finalize cannot turn into an empty-frontier revoke; test harnesses give explicit removals an empty frontier for that reason. At the guest a finalize counts as its `until` (`Timeline::role_unfinalized`, `lost_by_time`): it hears out. A renewal or removal of the grant itself is not finalized first (`ensure_rotated_but`). Removals reset every entry of the holder (`flows::edges::removal`): a void finalize resets the CRDT entry while the grant stands on the timeline. A re-grant after the `until` removes the expired entry first (`grant_in`; `regrant_after_until_reads_again_spec_permissions_2`). Fallback Tess accepts if this hits trouble: only admins finalize. Tests: core/node/tests/it/finalize.rs.

## Sharing
- Sharing never changes a tid or first admin. Moving a thing is a grant then a removal (notes/moves.md).
- One note: a grant on N, explicit secrets on N, N its own label. A set: a group thing with holders and secrets, granted read on each thing (one grant per thing, one commit). A set meant to be shared as a unit is better created under a common first admin.
- Group membership grants no rights (a grant on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Checking a write on N needs the role grants of N's record chain and of the author's own actors, which only holders can read. So signed role commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns, for every author under L, every path it ever had to the things it writes there (every held edge write between things on those paths, applied or not, each `created.0` record and hence that thing's dedup secret), never whole rosters. Author identity is inherent anyway.
- **Per label, not per node**: a certificate delta already under the label counts whoever placed it, so a joiner copies only its own chain (11.5 KB per label in a chat) and holders do not all re-copy a rotated actor's new `keys.0`. Sound because a copy counts only once this node checked every delta of it against the header's delta hash (`SyncEngine::genuine`; opening checks the prefix only, so before the check anyone able to deposit under the label could post the header with garbage deltas and stop the real copy; the same check guards `entry_for`, `carried_by` and the duplicate and strict-subset deletions), only while present at every host of the label this node syncs with (a label served with no host: in this node's own served state, which it serves as the label's host, so which peers are connected moves no count: `counted_at`), and, for a rotation commit of the label's actor, only under the newest epoch. Older epochs otherwise count: a newcomer gets the history boxes with its grant or first rotation box and opens older copies like older content (`newcomer_after_rotation_reads_older_copies_spec_crypto_4`); counting only newest-epoch copies made every holder re-copy everyone's chain after each rotation (40 KB per holder per chat removal). Residue: a holder of a link key alone (newest secret, no history box) reads none of the older entries. If another node's copy goes, the next pass places this node's own. Deletion power is the same either way (a copy commits to its commit's delete keys). Closure deltas are never copied (they are closure blobs). Another node's demotion or `keys.0` is left to its author for `SETTLE_MS` (30 s) after this node received it, with a wake then (the remover must place them, §3): otherwise every holder learning of a rotation under K's label before the remover's copy under C arrived copied it (3.3 KB per holder per removal). Measured from receipt, not the commit's `ts`, which its author sets.
- A removal of G's grant goes under G's labels (spec §2) because the target may have left G's closure, the removal ends G's reading of it, and G's inbox may reach only G's admins.
- Without `reach.0` under a label, co-readers of that label cannot dial the node off-LAN.
- The revokes placed under an uncovered epoch (spec §4) let A's rotators learn of the departure. The departed party can read them: those actors' new public keys and box keys, M's `roles.0` deltas and the writes' authors' chain certificates, not the boxes.
- **Current `keys.0`** (`Engine::current_keys`): an actor's newest `keys.0` commit may be an inbox or deposit seed write, so certificates carry that and the rotation commits of its newest keyset per role. A keyset then often reaches a node before any secret of its actor (K's rotation under its target's label, K's box under K's label alone): `Core::unboxed_epochs` gives its first admin's nodes the derived read epochs, reading only, so they still open the actor's label. Cost: one more commit per actor whose newest `keys.0` carries no keyset. Joiner's bytes down, measured on a chat: M=100 members syncing with one peer, about 2.0 MB (the extra commits add 0.2%); M=30, each member having added a saved peer, 795 KB, of which the extra commits are 139 KB (4.6 KB per member, 21%).
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some holder of the revoking actor syncs L); chain depth equals nesting depth, at most `MAX_CHAIN_DEPTH` (64) record links (spec/permissions.md §1; deeper nesting would make every standing query cost more).
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor); certificates by the roles at a point (they reveal about as much, and needed more rules, below in Implementation).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Tess's decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and hosts never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too. A re-grant brings X and Y back only if a host received them before the writers dropped them (Tess: a re-grant restores only what some node still holds). The revoker's view decides, as if it were a central authority (Tess: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- **A frontier saves what it lists, whatever the order** (spec/permissions.md §5.2): a frontier is what its demoter had received, so every demotion's frontier validates the listed writes, also those stamped after it and after a re-removal. Applying a commit advances the demoter's clock past it, so an honest demoter's frontier lists only writes ordered before its demotion anyway: an order check would add a rule and close nothing. No new attack: an honest demoter cannot receive a write made after its demotion, and a removed writer stamping ahead to land after a demotion whose frontier lists it could as well backdate the write before that demotion, which the order-bound rule saves too (the stamp never decides validity); a demoter listing what it never received is the accepted lying-witness limit (it could re-grant). Only demotions the node's settled walk applies count, so a disputed one it does not trust saves nothing. Addenda keep their order (listed write before the removal, addendum after): that is what stops a removed writer vouching for itself or two vouching in a cycle. Models: roles-model `addenda` (receipts may precede the item's `ts`; the order-bound variant `Rerem::Later` differs in 0.6% of random worlds), held-model `valid_as`, TLA `CValid`.
- **One rule for both layers**: the revoke's frontier is one list of commit IDs for edge and content writes, 32 B per listed commit: every commit of the demoted node the demoter received on the aspects in question, held, dropped or compacted alike (roles-model `addenda`, `Cover`: leaving out what another writer's snapshot covers loses the write when that writer is removed by an admin that never received the snapshot, `another_writers_cover_falls_with_its_author`; leaving out only what the leaver's own snapshot covers, the list naming that snapshot, loses nothing, but saves little: header forgetting would still need every commit another writer compacted). A prolific node can make it megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), kept as long as the revoke, i.e. forever (`roles.0` is never compacted). Past the list bound the plain-content commits received last go to the demoter's own addenda (below), then purge requests lose their right; a role part alone over the bound is refused (stated limit). Compact encodings were studied and dropped (notes/frontier-study.md).
- Only the revoker's own receipts matter: a held commit counts as received at its apply time (`Meta::received`; a late part does not move it), nothing else counts. A frontier taken as of an earlier cutoff (`Engine::frontier`, tests building late demotions by hand) lists only what was received by then (`validity::backdated_frontier_lists_by_cutoff_spec_perm_5_1`).
- **Chain writes count only through the frontier**: A's frontier lists by commit ID the role commits of its chain certificates for the target at R's point (§4: the writes on its paths, closed under their authors, so a grantor's own grant counts too; held, hence received); a forged one is not listed and drops, and A's grant reverts. An exemption for "A's own chain writes" whoever wrote them let X, after A removed it, write a backdated change to A's own grant (an `until` next week, a lower invite) that stood. Rejected narrower cuts: only the writes setting admin grants on A's own paths, read from the end state (missed a grantor's grant of A's grantor; the end state could name a later rewrite instead of the grant R rested on); exempting only chain writes that do not lower their grant (a second rule for a rare case). Residue: if A's authority at T rested only on a chain write A had not received (another verifier's view gives A a path A's own view lacked), that write drops and R with it; what R dropped in the same audit stays dropped. An honest node holds its chain, so the model generators mark each author's chain certificates as received (`roles_model::hold_chains`, TLA `Certs`); about a quarter of the writes that grant no admin are tagged written last (backdated forgeries); admin grants are never late, since an honest node does not act on authority it never received. About 1% of joint histories drop something.
- A snapshot's frontiers and `Absorbed` are no receipts (spec/crdt.md §8): a writer could list commits it signed ahead, or claim `X: 2^60`, and a demotion copying the claim would cover X's later writes for good. So a late joiner that got X's writes only through a snapshot does not list them; harmless, since hosts lose a commit's header only once every blob of it is deleted, i.e. every live write is carried by a covering snapshot, and that valid snapshot vouches for them at nodes still holding the now-invalid originals (`flows::late_joiner_after_compaction_agrees_spec_crdt_8`, `validity::late_joiner_after_compaction_keeps_writes_spec_crdt_8`).
- Clock skew: an end by `until` or self-removal is judged by the holder's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions).
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- **Re-grant validates the gap**: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it recovers from a stolen node's backdated mass revoke all that some node still holds (writers drop invalid bodies; hosts keep what was uploaded while valid). It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them. Tess: a re-grant revives all the account's writes, no special case; leaving writes out of a removal on purpose as a recovery tool depends on a side effect, so an admin who wants something gone reverts it explicitly. Don't build new uses on that side effect.
- **A removal makes its listed writes valid**, whether or not the author held the role when writing (spec/permissions.md §5.2); writes after an `until` rely on this. Side effect, a stated limit (Tess: "a strange thing for an admin to do"; no rule): a write made before its author was ever granted, which the admin happened to receive, becomes valid when that author is later granted and removed. The same holds for its purge requests (spec/requirements.md Deletion: a purge counts as an edit's validity does).
- **Frontiers list commit IDs, never counters** (Tess's decision; issues/session-sources.md rule 7). With counter frontiers a revoked actor could sign a new commit on counters its demotion covered: nodes holding the original voided both, but once compaction dropped the original and no snapshot traced the counters, new nodes counted the forgery. A fresh commit ID is listed nowhere, whatever counters it reuses and whatever its `ts` (`validity::revoked_writer_forging_into_covered_counters_spec_perm_5_1`).
- **Addenda** (spec/permissions.md §5.2; model `core/test/roles-model/src/addenda.rs`, results below): a writer node that applies an explicit demotion answers it, per thing it writes on where the demotion takes a node below write, with one `addenda.0` entry keyed by the removal's commit ID listing that node's plain-content commits it had received by the removal's `ts` and the frontier left out (`flows/addenda.rs`, run at the end of every durable transaction). Each removal is answered once: it leaves the due set when answered, and an addendum is a content commit, never a removal to answer. A removal whose answer goes on a thing whose delete keys the node does not hold yet stays due and is answered whole by the first durable transaction that holds them (inside the transaction applying the removal the demoted thing's new keys are not usable yet); any other failure to write fails the transaction. An addendum is the entries its own delta creates, so it is written as `put_new` (a new entry whatever is live): a plain put at a key another writer already answered writes into that writer's entry and says nothing. Every writer answers on its own, duplicates accepted; the demoter's own node answers for what its frontier left out. Judgment (osis-perm `content.rs` `Timeline::vouching`, the engine's `Judge::vouching`): the least fixpoint over the held addenda on a thing (those valid as their author's plain delta count first, then those they vouch for), kept to authors with write at their key; a part is valid when the base rule says so or a counting addendum lists its commit after a demotion of its author below write ordered after it; a commit's Acting check is its part on its header actor, vouched for there by a writer of the actor (as a frontier lists it there: every osis commit acts for its account, so a rule asking the witness for write on the actor would let nobody vouch for anything). Rules and why: writers only (a reader could combine with an ex-writer), after the removal about earlier commits (a removed writer cannot backdate one, nor two vouch for each other in a cycle), plain content only (role-class, admin-only and purge writes stay with the frontier: a partly vouched role commit splits, and role-write witnesses never settle, Role timeline below), an addendum is an ordinary write audited by its author's removals (and an addendum may list a fallen addendum: Dave vouches for Carol's). Limit (receipt time is local and unprovable): a writer of N lying about receipt makes the removed side's backdated writes on N count, attributed to it; the writer could write the content itself, not as the removed side. Per part, the removed side of a team T removed from N includes T's current members: a writer of N vouches for the part on N and the member still writes T, so nothing more is needed (engine `tests_addenda::lying_writer_vouches_for_a_removed_teams_write_spec_perm_5_2`); a member removed from T needs a writer of T as well (`acting_unvouched_invalidates_every_part_spec_perm_5_2`). Whether this squares with spec/requirements.md "rights held by different parties never combine" is Tess's call. Addenda list content commits only: a removed writer's compaction snapshot the frontier left out falls, and what it covered is fetched again (sim `coverer_revoked` relies on that). Addenda are decoded whole like role parts (`whole_part`), indexed per (thing, commit) from their bodies (`Indexes::addenda`, derived at open), never compacted, dropped while invalid like any body (a body-less or purged addendum is in the fixpoint listing nothing, so a later addendum can still vouch for it and its body is fetched again). A thing with addenda is re-judged whole whenever its author-restricted or commit-restricted re-judging could change an addendum (`rejudge_once`); measured (`scale::addenda_rejudge_cost_*`, release, 10^4 commits on the thing): a member joining a team holding it 0.65 ms without an addendum, 12.3 ms with one (about 1.1 µs per commit on the thing), within budget. Earlier addenda keep counting after a re-removal (any later demotion's addenda count). Differential: osis-perm `differential::addenda_model_agrees` (the judge against the model's `ideal`, half the worlds with forged addenda).
- **Invalid bodies go** (Tess: dropping and refetching is fine; spec/permissions.md §6): at the end of the transaction that judged them, but role commits (edge writes are the timeline's input; the commit is held whole), the node's own (its user may write them again) and memory parts. A re-grant or a late addendum makes them missing, fetched from any holder: the hosts (no right deletes them there) or the author; with none, gone at every node alike. Mechanism: notes/engine-retention.md Invalid bodies.
- One dot still names one write: overlapping session-form ranges from one session void both commits (spec/commits.md §4). Honest nodes never overlap (every open draws a fresh session). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Role commits use commit form and a session-form one is bad input (spec/commits.md §3, §4), so a removed admin cannot void its earlier grants, revive a holder it removed or void its own rotations that way.
- What stays lost after addenda: an edit no writer had received by the removal's `ts` (an offline device, a reader or a blind host alone), the removed holder's purges of its own messages (no witness holds that right), a removed admin's unseen role writes. A re-grant brings them back only from a node still holding them: writers drop invalid bodies and the removed author forgets the thing, so in practice from a host that received them while valid. The API's advice (`wait_synced` first, notes/api.md Demotion and addenda) is the only protection for a group the remover never synced.
- Rejected: a timestamp rule (forgeable); accepting everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); a learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); roles by claimed time only (an ex-admin could mint backdated grants forever); a pre-sync inside `set_role` with receipts-only reads of unheld groups (slow by default, could not close the gap, and needed `_now` twins everywhere).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 judges edge writes one by one too.
- **Snapshots vouch** (Tess's decision; spec/permissions.md §5.2): a compaction snapshot counts iff its author could write the aspect at it, at the strictest role a carried write could need (admin for `keys.0` and `secrets.0`: a writer's snapshot could otherwise carry a forged admin keyset, inbox, deposit seed, admin box or tombstone under a dot nobody holds), judged as its delta by commit ID, so a demotion frontier covers it by listing its ID; a reader's snapshot gives nothing (malicious readers only waste storage). A valid one's carried writes count because its writer vouched for them, never re-judged per claimed author. Revocation stays exact where no valid snapshot carries the write; through another writer's earlier compaction a removed holder's unseen last writes may stay, consistently on every node, also those holding the invalid original (Tess: fixed by hand). A valid snapshot's copies count also where the original is held, joined with it by the copy order (Snapshots and history, below), so holders converge.
  - The copy is the snapshot's write, never the delta's: un-merging an invalid delta removes its writes from its body, the state and the residues whatever a snapshot carries, and the snapshot's copy joins back with the payload it has. Keeping the delta's write whole under any dot a valid snapshot held a write of made reads depend on order (a snapshot carrying a fallen insert's creation without its char gave the char when held before the delta and not after; an equivocating writer's second commit under a carried dot stayed). Where a valid snapshot carries a write of an invalid delta the un-merge is a rebuild (`Unmerge::in_place` only otherwise).
  - A record (map entry, list element) whose creation a valid snapshot's copy keeps keeps the valid writes others nested in it, from whichever body (`Unmerge::strip`, `Fragment::remove_dots_keeping`): the entry is in the state, so a writer that put into it must see its own write, and its own later snapshot, which lists that write by frontier, must carry it (alike seed 4136).
  - Accepted: a valid writer can carry any write under any dot (it could write the value itself anyway; authorship is never exposed unverified, notes/api.md Attribution). A body dropped under a cover that later turns invalid counts as never received again and is fetched again (holders re-upload it: uncovered, so must-hold); with no copy left anywhere its writes are gone at every node alike (notes/engine-validity.md Carried writes). A commit one of whose parts a node never held and that was deleted under that cover applies there without it: a held snapshot of any validity listing the part stands in for it (Tess's decision; notes/engine-validity.md Snapshot authority).
  - Rejected content rules: any writer's snapshot carrying a revoked author's elements; "compaction snapshots vouch for nothing" (every element judged as its author's write; `core/test/roles-model` `content.rs` showed an "authorized at the snapshot's `ts`" variant diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered); snapshot authority plus per-claim judging (claims, per-write indexes, refills on late carrying deltas, and still a family of order-dependences). That divergence cannot return: a cover must carry what the snapshot it covers vouched for (spec/commits.md §5), so dropping a covered snapshot removes nothing.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual role grants are allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (record chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin grant on G could backdate a forged write to a time it held only the grant; removing the grant first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood (`core/test/roles-model`, `two_admin_paths_class_attribution`). Path-based audits would also close it but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal falls with its grant: both are attributed to L's invite class on K (a forged redemption's self-removal kept after the finalization dropped its grant would burn the link and block the honest redemption). Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the time it held the role (the rejected claimed-time rule).
- **Acting** (spec/permissions.md §5.2): a commit naming an actor other than its author is valid only where the author's write on that actor would be (same `delta_valid`, needing write), so a valid commit's actor is its sender. Role commits must name their author (bad input otherwise): checking it inside the joint walk would make grant application depend on the actor's grants, join components on every role commit's actor, and change roles-model and TLA; nothing needs a role commit to act for another. Re-judged through `by_actor` when the actor's timeline changes (debug builds assert nothing flips outside the re-judged set). Not checked: what the actor itself may write (the author's rights decide). A demotion below write on M lists the demoted node's held commits acting for M that its author received, compacted or not, as for every aspect in question: a node removed from its account lists every write of it as the account its remover received (32 B each; past the list bound the plain ones go to the remover's addenda). `created.0` stays valid whoever acts (its record holds by its tid), else every record created as M would be listed forever.
- Writes to `secrets.0`, `keys.0`, `label.0` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering role-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Retained copy (a removed holder's copy; spec/permissions.md §3)
- The default is the `retain` field of `retention^.0` (any thing, admin-only, no chat code; absent is erase): that aspect already has `^`, a kept-forever history, a valid-delta list, "in force at a key", no snapshot and no undo. The removal states the value: a plain reset is erase, reset plus a grant with `until` 0 is retain (`EdgeEnd`, `Edge::says_retain`). Why not a header bit: `until` 0 is already gone at every clock (no timer: a node behind the kicker's clock by `MAX_DRIFT` drops at once), and lies inside the signed `roles.0` delta so it cannot arrive apart from the removal. Cost: a removal saying retain leaves one dead grant on the thing until a re-grant replaces it. A tombstone value or a removal field adds a state every decoder must learn; a dead grant is the expired grant readers already skip. `retain` beside `rules`: the value is written whole, so concurrent admins changing the two lose one by key, and a toggle re-judges the thing as a rules change does; a separate aspect would need the settings machinery a second time.
- A later removal on a grant decides over an earlier one, by key; a node that erased first cannot come back (it keeps no more than the whole history, `any_order_keeps_no_more`). An `until` ending has no remover: it reads the default in force at its key (`retain_in_force`). A late setting joins (`retention^.0` is not frozen content) and an `until` way reads it at the next role-commit or manual judging, so it can end such a copy, never bring one back (`any_order_until_keeps_no_more`). Without a later judging the copy stays: the holder could keep it anyway.
- Filling is the writer's: `flows::edges::written`; `retain_now` is "after every setting held". Link: K takes the target's default when made, so joiners' self-removals read it too; a later change of the target's default does not reach K (minor; the kicker's word still overrides).
- Node removal erases whatever the account's default (a removal from `Osis`'s own account writes erase unless told otherwise), and a copy kept through the account hangs on the account (`K/` record), so it goes too. Any-path: a copy stays while one way keeps. A self-removal states its own value (Tess: no protocol rule stops it; the app just does not offer it).
- Kick cost is unchanged: nothing per body. Keeping costs the removed node nothing new and is cheaper than erasing (no shredding).
- Accepted limits (Tess: keep the rules simple and consistent, state rare corners):
  - Every other removal reads the default, so under a default to retain a revoked link's L leaves a dead grant until finalizing resets it (one extra commit), and a removed thin client's dead grant is a way that keeps past its account's later erasing kick; a node's grant with an `until` reads the account's default.
  - A purge after the removal usually does not reach the copy (no label to hear it by), though one in a commit the node takes for another part applies (`keep_clients::a_commit_beside_a_copy`), and a purge pending at the drop goes with its commit unless another part holds it. Only ever less kept.
  - A hostile host can erase a copy-to-be only by hiding a second way that keeps, or a renewal of an `until`; a removal cannot apply without the value it resets, so hiding that value delays the loss instead. A denial only.
  - An `until` passing is judged at the time (the trigger's by-time list) and dropped once the node has heard out the labels whose closure holds what it would forget (`SyncEngine::heard`), so offline nothing goes: a renewal on the way and unsent writes from before the `until` come first (`keep_clients::an_until_passing_offline_loses_nothing`), and an expired share stays on a node until it next gets online. A host down, or one that never lets a pass finish, keeps it up to `ROLE_KEEP` after the loss was first judged (`LOST_HEARD_WAIT_MS`, per actor: a dead host of one thing delays only the losses whose labels it hosts). Hearing out is per label, not per write, on one `Leaving::timed` path beside the self-removal one; rejected: gating per node (one dead host delayed every timed loss) with three trigger scopes.
  - A client reads nothing past the `until` and a copy only once made, so an offline app sees an `until` share with a retain default go and come back as a copy when the node has heard out. A role commit received beside the expired grant that does not end the role changes nothing (`keep::a_commit_beside_an_expired_edge_waits`). A renewal made after the drop comes back by a re-seal through a stranded report (`keep_clients::a_late_renewal_comes_back_by_a_re_seal`).
  - A write made before the `until` and sent after the thing was rotated for the departure is refused by the host (the label closed to the old key) and lost with the drop: the window is until the next writer rotates, as for any late upload.
  - A removal of an old path that arrives after the node has kept changes nothing. A kept holder given the target after the node left it counts as a live way, so a node that also held the target directly with an erase grant keeps it (rare; telling needs when the holder held the target against when it held the grant). In a partial order a node may erase what the whole history would keep, never the reverse (`keep::any_order_keeps_no_more`). A thin client reads a copy as its account's app or through its own grant (notes/client-port.md §3, Kept copy).

## Role timeline (model findings)
Model: `core/test/roles-model` (Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test` runs the scenarios; `cargo run --bin roles-model -- [samples] [as|exempt|strat|stratw|frontier|edges|edges-prov|joint|disputes|disputes-random|digest|addenda|addenda-exh|addenda-cost]` searches (counterexamples printed shrunk, as traces; `digest`: notes/testing.md, Models): exhaustive up to 3 edge writes (first admin, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `edges` (`src/edges.rs`): projected rosters, links, invites (audited by level), per-op judgment, plain record-chain writes on a thing, finalizes. `joint` (`src/joint.rs`): the joint walk over several actors (record chains, holder actors, mutual role grants, ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs`: layer-2 scenarios (per-delta validity across partially synced things, snapshot authority at `ts`, the snapshot-of-snapshot divergence). `trust` (`src/trust.rs`): trust sets and disputes on `edges` and `joint` (notes/disputes.md, Model results). `addenda` (`src/addenda.rs`): layer 2 with addenda (Revocation above; results below).
- **Third-party witnesses judged by end-of-walk roles fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a holder by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the first admin's further-backdated revoke cancels a stolen node's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for edge writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin node's backdated removals stand iff the node removing it had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Demotions of a grant never audit record-chain writes.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it; node-sync writes that removal: `SyncEngine::finalize_links`, `until_link_backdated_grant_void_spec_perm_7`); plain record-chain writes on a thing (a removed node's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky. Also residue (Tess-accepted): a drop whose dropped write made its demotion a fall stays after a restart where the demotion is no fall (D only grows). Every node holding the same role commits computes the same residue, so it diverges nothing. Pinned: perm `sticky_residue_of_dropped_grant_spec_permissions_5_1`, `unseen_leave_stands_spec_permissions_5_1`.
- **Self-removals are audited like any write** (Tess, simplicity): they keep only their looser authority (admin on the holder, none on the target) and carry no rotation. One through admin on holder M is attributed to the author's class on M and listed as a write on M; one lowering the author's own grant, to its class on the target. Never dropping them let a node removed from account P write backdated removals of P's grants everywhere that stood. Accepted cost: a leave the demoter had not received is dropped and gives access back until someone removes it again (re-seal covers the missing boxes). The honest demoter covers it: `Timeline::demotion_scope` adds the targets of the demoted node's applied self-removals through each thing its class falls on (their `roles.0` receipts survive forgetting). Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.
- **Addenda model** (`src/addenda.rs`; `roles-model -- N addenda`, `-- 0 addenda-exh` (2.83M worlds, 11 min), `-- N addenda-cost`): layer 2 with several authors and things, acting commits, special (unlistable) writes, snapshots; honest witnesses publish from their own view at receipt of the removal. 1M random worlds and the exhaustive family pass: one result for every input order, monotone (removing an honest addendum never makes a write valid), the least fixpoint settles in at most 4 rounds and equals the greatest, the role layer unchanged, forged addenda by nodes of any role (any removal, thing, `ts`, list, up to three) gain nothing beyond the forger's own write power. Counting every removal's frontier and any later removal's addenda is a superset of newest-only and differs in about 1 in 40,000 random worlds (Dave vouched for the first removal; Bob re-granted and removed again while Dave is offline); bounding frontiers to earlier writes differs in 0.6% (receipts may precede an item's `ts`). Bodies dropped at once and fetched from any holder: nodes agree and read no more than the no-drop result, but lose writes: a re-grant restores nothing every holder dropped (27k of 1M worlds), and 8% of the writes valid only through addenda (the witness judged the write or its own addendum invalid before vouching and dropped it); keeping what held addenda list cut it to 208, only keeping invalid bodies to none. Cover rules (`Cover`; the cover family, `addenda-covers`: two admins, a snapshot by any node carrying the leaver's edit, its author removed or not, 38,656 worlds): leaving out what another writer's snapshot covers loses a visible write in 544 family worlds (3 in 1M random); leaving out only what the leaver's own snapshot covers, the list naming it, loses none there, in 1M random worlds or in `addenda-exh`; addenda naming a snapshot gain no attack and stay monotone. Cost: random worlds 0.06 addenda per removal; `addenda-cost` (one removal, each commit received by each node with probability 1/2): listed IDs grow as writers × commits / 4, nearly all duplicates (30 writers × 100 commits: 752 IDs in 30 addenda, about 24 KB).

## Role history
- `roles.0` is never compaction-snapshotted: every role commit stays, and a node that starts holding a thing fetches and judges all of it (spec/requirements.md Scale states it). `secrets.0`, `keys.0` and `label.0` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta).
- Bytes: 364-371 B per role write, plus 34 B per commit a frontier lists. A 1000-member chat after a few thousand joins and leaves is about 10^4 role writes (3.6 MB); what hurts there is the joiner's CPU, not bytes: ingesting 10^4 role commits one by one takes 110-160 CPU-s (10^3: 1-11), quadratic (`scale::repro_role_history_join_is_linear`, issues/role-history-join-cost.md), mostly per-arrival timeline work and `apply: join` per `roles.0` delta, an implementation cost fixed by batching the ingest (issues/role-history-join-cost.md). Evaluating the timeline anew is 1.5-2.4 s at 10^4. The first admin's own edge write averaged 15-23 ms at 10^4 history (4.6 ms at 10^3), under the 50 ms budget but growing. 10^5 not run (the first admin's writes alone would take hours). Against the budgets (notes/testing.md): per commit they hold; a 2-3 minute join at 10^4 role writes is past "rare events under a few seconds".
- **Rejected: roster snapshots** (an record-chain roster snapshot with a ledger of ended tenures and their frontiers). Every write+ tenure and frontier had to stay forever (a write anywhere below may rest on any of them), so it saved only 1.1-2.6x for writer groups (20x only for big read rosters), a kick-heavy group at 10^4 could not write one, and it cost epoch-start rounds, linked frontiers and a second residue class. A join is O(role history) with or without snapshots (the ledger is), so the Scale item on permission history is needed either way. Linked frontiers (extending an earlier frontier by link) save nothing in these shapes, since each kick lists the kicked member's own commits, disjoint. The frontier that does grow without bound is a single kick of a heavy writer (notes/testing.md long aspect: `TooLarge` at 3*10^5 commits).

## First admins
- Every thing's record names its first admin (spec/wire.md §3; a key actor's names its key): the tid commits to it, its edge is in the walk's initial state from the start and stored nowhere, and it is an ordinary admin, removable like any other. Why not "granted in the creation commit" with a creation authority: anything that lets a node write the first grant without admin could be reused to grant again later (the record is public to every reader, the creator can always write another "creation commit", backdated): a hidden admin. Fixed by hash, there is nothing to reuse. Why no authority above the admins (Tess's direction; notes/disputes.md): an un-removable authority is a hidden admin users cannot change. A removed admin can backdate a removal of its remover (n1 removes n0 at 10; n0 signs "remove n1" stamped 5, which the plain walk applies first), also on an account; the walk settles the fight per node by its trust set (Trust sets, below), and a node takes a side by default when it detects the dispute: the side it held first (notes/disputes-plan.md step 4), so a node that applied the honest removal before the backdated one arrived keeps it.
- **One authority class**: admin by any path (edge admin), or an invite level. A node admin of a thing's first admin is admin of the thing through the record edge like through any grant; losing that path while another keeps the class is no fall. So an admin that granted itself a direct edge on a thing below keeps it when its path above is removed, until an admin removes that edge too (one class, no "top" that outranks it; Tess accepts "a current admin Q that Y left in place voiding Y's removal silently").
- **Creation**: a record needs no authority (it is public); the creator names itself or an actor it holds write on (Tess, Q13: any writer of G may make a thing whose first admin is G; G's admins administer it, its writers write it). A thing is made either by its record alone (`Engine::create_with_admin`, or `Write::create` with nothing else in the write: `created.0` deltas alone, a role commit, spec/commits.md §2, so joiners fetching role commits first hold the record before the commits that need it; otherwise every pending role commit on the thing waits for it and is read again, `scale::joiner_reads_each_pending_commit_few_times`) or inside a content commit with its first writes (`Write::create_with_admin`, trees made in one commit, each thing's first admin possibly one the commit creates).
- **Removing the record edge**: no entry to reset, so the removal resets an entry of its own delta (`Mutation::fresh_resets`: a tombstone keyed by the holder at a fresh counter, spec/permissions.md §2). Its creation is that delta, so every reader resolves it at once, in any arrival order. A put-then-remove in one batch nets to nothing in the CRDT, so the tombstone is minted directly. An admin of the first admin removing the record edge leaves by self-removal (admin on the holder its only authority, spec §2); an admin of the thing itself removing it is an explicit demotion that audits the first admin's writes.
- **Record chain**: the chain walk (`osis_base::record_chain`) goes up first-admin links, so derivation, labels, inboxes, certificates and the `MAX_CHAIN_DEPTH` cap all count through it; it says nothing about authority, which the timeline reads from the record edges as they stand.
- **Secrets**: a plain thing derives from its first admin's epochs (spec/crypto.md §3); its first grant (or `sync`, which gives a label) gives it secrets of its own by the usual rotation from the derived epochs. Lowering the last admin edge of a plain thing is refused (`flows::edges::leaves_no_admin`, skipped under `skip_writer_rules` for tests): on a plain thing the only holder for keys is its first admin, so no other edge write on it exists and no "own secrets before any edge write" step is needed. Signed anyway, it stays plain and derives from the removed first admin for good (stated limit, spec/permissions.md §1). A derived epoch written under after the record edge went is read by the first admin's holders only (issues/derived-write-merge.md: rule 2 of the model, a stated limit).
- **Virtual record edges** (osis-perm): the walk's edge state (`Edges`) holds only edges writes set, plus the record edges writes removed (`cut`); `EdgesAt` and `View` read a record edge from the records (`Records`) where neither is the case (`RECORD_EDGE`, admin, no `until`). So a plain thing costs the edge state nothing (a kept state stays O(targets written + holders)), `Dense` materializes them for searches (its adjacency built by one push per edge and sorted once per holder, kept sorted by `set`: a holder of a million things costs no scan per edge), and a write that sets a record edge to exactly its record value is no explicit entry (canonical states compare equal). A record arriving late for a thing whose edges were walked: the undo entries of those writes were logged with the record unknown, so the resumed walk restores the record edge itself after rolling back (`Resume::fresh`); rejected: a full evaluation then (it is the common late-record case, `created_late_*`).
- Engine: `held.rs` names the first admin on the thing (`holders_of`, `reaches`) and indexes the thing under it in `first_admin_of` (one record-chain link down: `below` marks it stale when a record above it arrives), `write::role_with` gives a not-yet-held thing the first admin's role. The roster, current holders and holders for keys all include the record edge while it stands (`Timeline::roster`, `standing_since` with `None` for the record edge: an actor grant ordered before every write, never the one left keyless), so nothing reads the record as a right. A link's K has the sharer's actor as first admin. API: `Write::create_with_admin(admin)` (and `create()`: the acting actor); no call reads a thing's first admin (history, not a right): `grants` lists the record edge while it stands, and chat and the app tell accounts from teams and link keys by `grants` one level down (a key actor has no holders).
- **Inbox and `label.0` reads stop at cut record edges** (`Core::standing_chain`, `published_by_actor`): an actor's inbox is its home label, named in its `keys.0`; a group's `label.0` and `created.0` go under the home label of the nearest labeled actor up its record chain whose record edges up to it stand at the writer. **One inbox rule**: every actor with a home label names it in `keys.0`, in the commit that makes it one (`rotation::own_secrets`, the commit that gives it secrets and sync ID; a replacement of the one named; a person too), because a sender may know a holder by its `keys.0` alone (certificates), not by its `label.0`: an outsider's grant to a team then lands under the team's own label, which every reader of it syncs. A reader opens a blob under a label named by the `keys.0` of each actor whose secrets it holds (`Engine::inbox_actors`: more than one only when an admin wrote someone else's label there, and a blob is tried under each, so that hides nothing), and that set is what the node treats as inboxes (smaller unvouched cap with bytes kept, clearing). Rejected: a group's own label as an inbox without naming it in `keys.0` (outsiders cannot find it). Limit: blobs deposited under an inbox that is then replaced are not read; they come again with the sender's re-send, `INBOX_LIFETIME` later (issues/replaced-inbox-resend.md). **One standing-chain rule** (`Core::standing_chain`: up first-admin links while each record edge stands here, the top included): `label.0` cross-publishing, `admit own` hosting (`SyncEngine::owns`) and osis's host-list follow (`share.rs`) all read it, so a removed first admin has no standing on what is below. Derivation, entitlement and the re-send check (`acted`: evidence of receipt) read the records alone.
- **Costs and limits**: record edges are virtual, so a plain thing costs the edge state nothing; a million leaves under one actor: evaluate walks only the role commits, one more leaf walks nothing (perm `scale::record_leaves_walk_nothing_per_leaf`). Nothing resets the `MAX_CHAIN_DEPTH` cap and chats add two links: app trees must stay far under 64.
- Within one record tree nothing moves: rights are grants, so "move this doc to team B" is a grant then a removal (notes/moves.md), and the depth of record chains should match the units that travel together. Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `secrets.0` like any key-actor holder). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets; the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (and so one cascade rotation of the target); perm judges each edge write of a commit on its own, so such a commit is two removals at one point with one frontier. None of its grants may be a self-removal (refused by the writer rules). A several-grant removal under one rotation keeps the one-commit rule's guarantee, since the rotation excludes every holder it removes.
- **K's secrets are random**, not derived from the seed: with derivation every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every host) and write key, exactly the power the invite-only design takes from L; and L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K stranded L. So L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- **A link outlives K's rotations**: the rotation commit is wrapped under the epoch it supersedes (holders must read it to learn the new one) and its boxes and history box are all a late reader needs, so the entry box also carries that earlier secret (one, 32 B): the redeemer opens the rotation commit, and its history box opens all of K. Rejected: a re-seal of L in a commit under the new epoch (a commit more per rotation, and a window between a writer's rotation and an admin's step). Rejected: not rotating K on a leave (a leaver who kept the seed can come back anyway): a node removal rotates K all the same, so the path is needed regardless, and a leaver who discarded the seed (the SHOULD) stays out. What a user sees: a link works until revoked, expired, used up or a joiner kicked, however many people leave; a leaver holding the text can rejoin.
- Limits: one earlier secret, and with forks only the registrar's pick: a rotation in a fork it does not lead to stays unread until the next rotation. A commit on K pending behind it holds `redeem` to its timeout. A host holding K's head without its claim set (past its caps) refuses like a revoked link: with every other route failed too, it reads as ended.
- **`redeem` fails at once** (`Invalid`, "no longer works") on evidence only: a refusal of L's static entry (code REFUSED, not UNKNOWN_LABEL: L is in every step until it left) with every route of the label failed, so one host's word or one down decides nothing, or a held history that put L on K and ended it (`Timeline::ended`). An L not seen yet says nothing, since its grant may still be uploading; nobody answering waits until the caller drops it. `links` reads the roster, which holds no key removed or past `until`, so what they list works.
- **A link's target is its text's word** (nothing signs it): `redeem` grants only after K's grant on the target is here, so a link pairing a target with another thing's K joins nothing, and `forget_link` has the lost-access trigger judge K, so what only L read goes. K's label carries the grant (delivery, then the sharer's certificate copy), so honest links reach it pre-grant, target unknown too. `Invalid` needs a complete pass of K's label and no commit pending on the target at the timeout: a node cut off mid-read hears `Network`, since an app reads `Invalid` as a dead link. Forgetting drops the hinted label's session too (K's commits may not be here yet, so `Forgotten.labels` lacks it): the secrets its head gave go with the key, and a retry must claim the head again. Not bound: K's first admin can put K on anything else, before or after a redemption, and K can be any actor with L on it (an existing chat holding a role on the target): a joiner then holds all of that too, and the link names only the target.
- **A joiner leaves K once K is off the target** (spec/permissions.md §7, Joiner's leave): the target's admins end a link by removing K (K's only admin may be gone), which takes the target from every joiner but leaves their roles on K; without the leave each joiner syncs K's label for good and dials its sharer forever. The condition is the redeemer's "link has ended" one, K's edge on the link's target removed or past `until`, for every K the account holds by a grant (the sharer holds K by its record and keeps it to finalize and revoke; leaving would also stop its node serving the removal to no-host joiners). The target is the one K's creation record names (`link` field, so K's tid commits to it): only K's creator wrote it, and K's creator may remove any joiner anyway, so trusting it gives nobody new power; a record without it means no leave. Rejected: any thing K was put on (granting needs no grantee consent, so anyone could put K on a group of theirs and take it off, pushing every joiner off: `a_fellow_joiner_cannot_end_anothers_link_spec_permissions_7`); recording (K, target) at redemption in the home group (more state for the same answer). Node-sync writes it (`SyncEngine::leave_ended_links` over `Engine::joined_links_ended`), checking only around things whose roles or roster changed (an `until` passing is a roster event), everything at start. Concurrent leaves by two nodes of the account are two self-removals of one edge: harmless. Cost: a target admin granting K again brings no joiner back (a new link does). A no-host leaver cannot confirm its removal (issues/leaving-not-confirmed-after-rotation.md), so there it keeps syncing K like any leaver.
- **Finalization**: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer node writes a real removal; until then the link is honest-client-only. Node-sync (`SyncEngine::finalize_links` over `Engine::links_due`, any node holding the seed thing and admin on K, woken at the `until` by `next_link_expiry`) writes it after a complete pass of K's labels ended after `until` (passes from before going offline do not count), so the frontier covers honest grants that reached the hosts while the link worked. Without saved peers only the node that made the link finalizes, at once. A seed thing counts only when its first admin is K's first admin (a co-reader can add a `link:seed.0` thing to a shared group). A K whose label never completes a pass (host gone) is never finalized: the link stays honest-client-only. Residual window (Tess: keep, documented on `LinkOpts.until`: an expiring link closes when one of your nodes next syncs after `until`): while every sharer node is offline after `until`, or K's host is unreachable, a backdated grant uploaded then is received in that pass, covered and stands; cutting it would also cut honest late-received grants (both carry `ts` < `until`). Future option: a host receipt time as witness, one feature for removals and link expiry together. Idempotent: `Timeline::lowered_unaudited` (the walk's `prior`) is cleared by the first explicit write, so a second node's concurrent removal restores and audits nothing. Alternative (no `until` or single use at all) loses nothing a hostile holder respects.
- **Race flip**: the finalization's frontier can drop a competing redemption the sharer had not seen, so a redeemer that lost by its own view may win; a loser therefore keeps K's secrets and labels while L's self-removal is unfinalized (`contested` in `rotation::lost_among`; `single_use_loser_keeps_secrets_until_finalized_spec_perm_7`), and drops them once the removal arrives. Only redemption-shaped commits count on both sides (the void one and the applied one that lowered the signer's grant): a plain leave then a void grant defers nothing (`void_grant_by_leaver_keeps_no_secrets_spec_perm_3`; otherwise any self-left holder could keep any removed holder holding the thing's secrets for good). Residual: an inviter whose leave commit also granted someone can later forge a void redemption naming a removed holder, who then keeps the thing's stale secrets (no new epochs) until an explicit write on the inviter's grant. Cost: never finalized (sharer gone, a K host gone for good: `complete_pass` waits for every host), the loser follows K's and the target's labels for good. Not bounded in time as pending grants are: past a bound the race flip would leave the winner unaware again. Rejected: inbox delivery of the removal to the joiner alone (the loser had already dropped and forgotten the target's secrets, and nothing brings them back).
- **A removed node keeps the seeds** of the account's links (they sit in the home group), so it opens K's head by L's static entry past the removal's rotation until each link is revoked. Not ended by the removal (a link shared in advance dying because a phone was replaced would surprise), so `remove_node` returns the account's working links and the caller decides (`node rm` prints a revoke line per link, `--end-links` ends them). Any node of the account can list and revoke any of its links: the seed thing carries K, seed, target and single use. A link made on the removed node and not synced yet is unknown here; whoever holds that node can redeem before the revocation and stays a joiner, as with any link holder.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): a link conveys "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add grants for actors with no current grant, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier. Inviters seal only secrets they hold (their role and below). Holders read K's roster, like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- A direct link's key outlives the link: ending it rotates nothing (notes/peers.md, No automatic rotation).
- Self-removal lets an actor always leave or lower its own grant; single-use links use it to drop L's own grant.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (kicking one joiner otherwise kills the link for all, spec/permissions.md §7).

## Patterns
- **Grant on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per holder, so not per note in a folder).
- **Shared actor** (spreadsheet): one actor is the first admin of everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: a minimal root actor whose admins are a few accounts; teams, chats and docs have the root or actors under it as first admin. Root admins can remove anyone below, and a departing founder is just an admin removal; a team can shed the account that made it (its first admin is an ordinary admin).
- **Shared tag** (rights live on grants, never on grouping; notes/tags.md): the tag is an actor; things keep their record and each gets a grant for the tag's actor (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same grant so rosters nest; writers may also create things with the tag as first admin. Per-holder grants on each thing do not work: entitlement puts a thing under the tag's label only when the tag's actor may read it, so no label the holders sync would carry it. Built in core/osis/tests/it/tags.rs.
- **Chat**: notes/chat.md. **Realm** (design): notes/realms.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and their grants, and `group.0` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and actors stay separate; a group may also be an actor when it serves as a shared label.

## History setting (`retention^.0`, spec/commits.md §5 The setting)
- **By exact AK, plus `default`**: aspect names are static (notes/api-design.md), so naming each governed aspect is enough; no matching language.
- **No validity rule**: the setting decides what history keeps and what a writer fills in (expiry, `final`), never whether another delta is valid; a writer ignoring it can only give its own writes another expiry or purgeable-by (issues/thing-history.md Decisions 5).
- **Key order, as an admin-only aspect**: the timeline is the held valid settings by key, so every arrival order agrees; a setting's arrival, fall or drop re-judges its thing's history (`retention::settings_changed`), never a delta's validity.
- **Whole value, read a delta at a time**: judging needs no CRDT replay up to a key. Writers turn `set` into a replace; a hand-made partial delta only hurts its admin.
- **Fixed `nobody`, kept forever, never snapshotted**: a later node must date history as everyone did, so the setting's history cannot be compacted. Cost: one body per change, admins only.
- **A setting by one not a possible admin binds nothing**: the author alone counts (a delta is judged by its author's standing, so a header naming an admin as actor saves nothing). It goes like any invalid body but at its author and the hosts (`setting::writers_setting_keeps_nothing_spec_perm_6`), bounded by `MAX_RETENTION_ENTRIES` per body; an admin's count of settings is unbounded, one body each.

## Purge rights and retention
- Retention is per delta (spec/commits.md §5), decided with Tess. Default `author_or_admin`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and purge on replace implies it. `nobody` is for records even admins must not drop. `admin` is what role commits use.
- Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (Tess's call; hosts approximate it, notes/sync.md). The right is exactly validity (§5.2) of a delta needing the role at the request's key, so a re-grant gives back a gap request's right as it does its writes (else a re-grant revives the reset but brings the purged value back).
- Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever; a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart.
- Fields are immutable: a change would need the blob re-encrypted anyway (commitments are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.
- **Lasting headers** (spec/commits.md §5): a purged permanent delta's commit keeps its header at the label for good (about 300 B), and so does the purge commit naming it (without it a new node never applies the header-only blob). Tess: "if history is on, the cost of keeping history is expected". The header-only blob goes up only when no other body of the commit is wanted at the label.
- **A purge follows the timeline, both ways** (Tess: a purge setting is a promise; deletion that is rightful really deletes; a wrong one must not destroy what honest nodes hold). `Timeline::purge_stands` reads `delta_valid` as well as the role at the key, so a request a demotion's frontier leaves out holds no right whatever its `ts`. `retention::rejudge_purges` runs at the end of `rejudge_once` per aspect with a held request on a re-judged thing (`p/`): a part a request comes to drop is purged, a part dropped for one that no longer does goes through `reopen` to `missing`, the one mechanism `Dropped { broke }` and `uncover` use. Not kept per body: own-write parts read the value-less list, others one flag bit.
  - No settling window at hosts: at 0 the demotion-first holder restores, at infinity a rightful purge never deletes, so a value could only turn "usually" into "more usually" (fails notes/arbitrary-values.md). A node syncs a label before it deletes under it, so the window is only a demotion not at that host yet, the same a hostile admin before removal has. Lost for good: only a body every holder dropped before any heard of the demotion. A holder uploads a must-hold body and a stale node deletes it only until that node syncs the demotion, which lies at the same host: judgments are functions of the held set, so the war ends.
  - A holder that saw the delete still uploads though the body's writes are carried (`Engine::named_by_a_fallen_purge`, `delete_stands`): the delete-keeps-it-out rule assumes a keep bound passed. A stand-fall-rise with no copy left must leave what a node never seeing the fall has, or an older value resurfaces: a delta's `w/` row outlives the fall and counts only while it is value-less (`make_valueless` joins it when no body gives one, covered parts too); a snapshot is never dropped by a purge (it has no values of its own), so it needs no such row.
  - A frontier lists requests by `requests_resting_on`, not by the things where the class falls: the right by author runs signer, actor, thing, and the signer may keep its own grant on the thing (a node removed from its account). At the list bound the requests received last go, so a heavy moderator stays demotable and a flood lands last; rightful or not they fall (a hostile flood reaches only requests of the same demoted set). A header-only blob left from a fallen purge stays at the label as may-hold (300 B each, spec/sync.md §6): deleting it needs every node's agreement that it is not lasting.
  - The gate is separate (`counts_as_purged`): a missing delta counts as held on the word of a possible right holder (`Held::ever_admins`, `ever_writers`, monotone), or a demotion's place in the order would decide whether a commit applied; `known_purged` still decides the stripping. A body stripped for carrying stays held through a fall, its copies of the fallen request's values value-less: the valued copy wins wherever one joins, and a whole copy arriving replaces it (stripped again for another's standing purge). Making it missing instead lost the other writes a carrying snapshot covered, deleted at hosts on its strength. Rejected: `reaches`-style rules using a snapshot's kept frontiers (dropped without the body they judge differently from a node that saw it: order::purge seed 890023).
  - **What reverses a purge**: only a demotion whose frontier omits the request. A demoter's frontier lists every request of the demoted node it received on a thing in question, for a fall below admin too (`Engine::frontier`), so an honest demotion reverses only a request the demoter had not seen (the backdated or raced one this rule is for). A hostile current admin can omit on purpose (§5.1) or backdate: the purges of the one it demotes fall, and the deleted values return only from a holder that kept the bytes, as a holder could show them anyway; hostile admins are out of scope and could re-post the text. A demoter that never held the request (a fresh node past `ROLE_KEEP`, non-permanent delta) makes it fall too; the body is gone at honest nodes, so that reads as never received: only a node still holding the body brings a message back (`tombstone::a_fresh_node_demotes_and_nothing_comes_back_spec_perm_6`).
  - `snapshot_right` shares the rule without the listing: after a demotion below admin an admin's old snapshot no longer lets a node drop bodies under `admin` (a growth price, no data loss). It is read by `drop_covered`, not by `covered`, so reads and must-hold are unmoved. Snapshot stale drops stay dropped: making a no-right snapshot not cover for must-hold does not converge (issues/covered-body-new-label.md), and the dropper held the right itself.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the host (host stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with Tess, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous holder: a fresh actor with its own node keys, joined via a link or grant; the granting admin may record pseudonym -> account in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Holders write as A in commit form. Caveats: any holder can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a node the holders trust re-signs their edits under its own identity.

## Snapshots and history (spec/permissions.md §5.2)
A snapshot is trusted for current content only, never for authorship or time, and its copies are never compared with the deltas they copy (Tess, History is verified or absent: a copy differing from a held delta's is a writer's claim about another's history, and such claims are neither stored nor acted on).
- **Content**: a valid snapshot's writes join like any write, also where the original is held: copies of one write that differ settle by the copy order (spec/crdt.md §4.1), so nodes holding the same bodies read alike, and a node holding only the snapshot reads its copy until it holds the delta. No worse than the writer writing the value itself: a snapshot holding another copy of a live write never covers that write's body (spec/commits.md §5 Covered), so the original stays held until it dies and its keep bounds pass, and a removal of the forger gives it back; later writes win as usual. Cost: a forger can keep its victim's write held (that write's own storage). Only valid snapshots count, so a reader or a removed writer (frontier not listing the snapshot) changes nothing; a snapshot turning invalid gives the held original back. Mechanics: notes/engine-validity.md (Carried writes and vouching).
- **History**: authors and times come only from verified commits held here (notes/api.md Attribution); content known only through a snapshot has none. Nothing attributes through snapshots: listings and `created`/`changed` read held headers only (snapshots are no change), a watch names the commit applied (a snapshot correcting a held original is reported as the snapshot, its author and ID), undo and revert act on held commits.
## Admin-only aspects (Tess, AK format decision)
The `^` marker in the AK (spec/data-model.md §2); a delta of one needs admin, judged by validity like content with admin in place of write (spec/permissions.md §5.2), from the key alone: no wire bytes, no schema. Engine: `write::required_role` (local refusal, layer 2, snapshots via `snapshot_role`, ephemeral parts). osis-perm's `delta_valid` takes the required role; a demotion's frontier covers `^` aspects with the role-class ones (`Engine::frontier`; without it an admin demoted to write lost every `^` write, covered or not). The roles-model's content model abstracts the role threshold, so it covers admin alike. A writer's `delete` of a thing holding a `^` aspect fails `Permission` (it would remove it). Tests `validity::admin_only_{aspect_needs_admin_spec_perm_5_2,snapshot_by_writer_invalid_spec_perm_5_2,write_covered_by_demotion_frontier_spec_perm_5_1}`.

## Implementation (osis-perm)
Where things live, the per-step mechanics and the test names are in the code (`walk.rs`, `cache.rs`, `cert.rs`, `content.rs`, `scope.rs`, `trust.rs`, each with a module comment). This section keeps the shape, the invariants and why.
- **Boundary**: perm parses no bytes, holds no state and depends on osis-base only. The node implements `HeldSet` (things, applied role commits with an edge write per thing, `created.0`) and adapts headers into `types` records; a `created.0` that does not hash to its tid is ignored. Value conversions of `edge` and `frontier` belong to osis-schema `core_types`. Every walk up creation records (engine, osis) is `osis_base::record_chain`, capped at `MAX_CHAIN_DEPTH` (the engine judges writes on a too-deep thing invalid); perm itself follows record edges one at a time with no cap, since spec §1 defines effective role by paths.
- **Evaluation**: `Timeline::evaluate` is the from-scratch walk; queries take `At` (state before a point, edges alive at a ts; `At::END` is the end of time, where re-grant is judged). `Timelines` splits the held set into components (things joined by edges, authors and records; a thing with its first admin), each cached by its exact inputs; `changed()` lists the things whose component the last update evaluated, and the node re-judges only deltas on those plus commits whose void, required-role or overreach inputs changed (a debug assertion checks the rest is unchanged).
- **Incremental paths** avoid the from-scratch walk; each declines back to it when exactness is in doubt, and debug builds compare every one with a from-scratch walk on inputs up to 400 commits (`Walked::check_scratch`), driven by one generator test taking the shapes in turn (`incremental_equals_from_scratch`). The paths and the one argument each rests on:
  - *Extend* (a component that only gained role commits): the final walk rolls back to the earliest new commit p and goes on. D is kept in the order the final walks found it: drops found before the first one found by a write at or after p stay (every walk up to them saw only items before p, and each walk under a prefix of D finds nothing before the next drop's point); the rest are forgotten and the walk rolls back to the first write they dropped too.
  - *Append* (every touched thing in a component, `created.0` unchanged, new commits whose author, holders and targets are in it or are new nodes): the component is neither re-partitioned nor gathered again. A new node can join because nothing it reaches is held yet, so no earlier audit met it. Each new commit is placed without walking where that is exact, else the walk resumes from it. Declined: a drop of D at or after it, a later item writing an edge it sets, two ops on one edge, its own audit dropping something new.
  - *Which later items may read a placed write* is a static over-approximation over `Input::ever`: with (M, T) its edges, roles change only for what reaches some M (A) on what some T reaches (F), and only up to the widest role among the edge's values before and after; so classes change only through an admin value or an invite, demotion thresholds only through write or more; reaches change regardless. With no such item the write's changes, undo entries and mark are spliced in directly.
  - *Shadow placement*: a shadow pass walks the placed write, then each item that may read it, with the edge state as of its place; where every effect (history, undo entries, applied records, demotions, falls) equals what the walk recorded, the write's own effects are spliced in; the first item that does otherwise makes the walk exact up to it and it goes on from there. A re-judged item costs about 0.5 ms at 10^4, so past an eighth of a long rest (`SHADOW_SHARE`, 512 items or more) the write re-walks instead; debug builds can force either path and a test runs both on the same arrivals. Figures: issues/perm-eval-cost.md.
  - *New leaves* (things only their `created.0` names, above a root whose component gained no commits) skip the re-partition and the re-gather (0.13 ms per thing already in the component, per commit, for a commit creating things under a big group). A leaf's record edge is its only edge, so every node's role on it is its role on its first admin at every point and its demotion records equal the first admin's: the leaf takes the first admin's demotion vectors (`alias_leaves`), top-down so chains of leaves work. Without aliasing, validity was order-dependent (a holder offline through a revoke took the item as a leaf after the demotion and kept no demotion on it), and a re-walk from the first demotion cost 0.4-1.9 s per new thing under a much-demoted team against about 40 ms. A thing an earlier write names whose `created.0` arrives late, every thing below it, and a new node join the same way: before the first item naming them the walk is the same but for their demotions, then goes on from that item. Declined: a record gone, a node gone that has no record, a new node first admin of a thing walked before, a record changed under its ID.
  - A record can grow under its commit ID (a commit's edge writes arriving late), so held records are compared with walked ones by content (frontiers by size), not by ID.
  - Trusted components (below) take none of these paths.
- **Point queries** read an edge state kept every 32 history changes through an overlay of the changes since (no copy; `Edges` shares per-thing maps between clones until written, so a kept state costs O(things): +60 MB peak on 12.9 GB at 10^4, against +1 GB with full copies). `first_held` (where the node first held the role, re-grant's start) replays the node's roles over the history: a change of an edge out of something the node does not reach is skipped, a wider one raises in place, and only a narrowed edge that may have carried a role or an expiry searches again. Rejected: a static filter over edges on some path of the union of all edge states; in the org bench every holder reaches nearly everything through teams, so it filtered little.
- **Saved walks** (the node's `node/walks` table, notes/engine-store.md Open): a component's whole walk (undo log, marks, D in found order, passes, reach) is saved under its root with its inputs; a component with no timeline in memory is restored from a walk saved under any of its things whose inputs are a subset of its own and continued by one extend. Unit = BLAKE3 tag ‖ body; the tag covers a format string, the salt (the node's rules tag), the walk's whole input re-gathered from the held set restricted to the saved IDs, and the body, so other rules, inputs or damaged bytes mean a from-scratch evaluation, never an error. Frontiers are tagged by size only and referenced by where the input holds them (`HeldSet` documents that a record's frontier is fixed by its commit ID): hashing contents cost O(frontier) per save and restore (48M IDs: 0.9 s). Saved when a component has at least `min` commits and grew by a quarter (and `min`) since its last save: amortized O(1) per commit (saving at every commit about tripled a commit's cost at 10^4). `to_save` changes nothing; `saved` applies once the writes are durable.
- **Walk cost**: every state change logs its inverse with a mark per item, so a walk that grows D resumes at the first write D now skips and extend rolls back. Per-node `roles_from` is cached across writes, dropped only when an edge change may narrow it or an edge it followed expires, raised in place when an edge widens. `audit_fall` reads every candidate X's roles from one backward search per thing, or for at most `FORWARD_MAX` candidates from cached forward roles, and searches forward only for an X the restored edge raises. Counted (perm `scale::`, 10^2 and 10^3 writes on an org of 311 nodes, 221 things): evaluate walks each commit once; a write after the history is placed walking nothing; a late read grant mid-history is placed walking nothing, while late writes that change what later items read re-judge them; a restored walk walks nothing, a continued one only what was added; a record chain walks each commit once at any depth; evaluating with drops restarts per drop (issues/perm-eval-cost.md).
- **Chain certificates** (what a demotion frontier lists; spec §4): for (n, t), the things on any path that ever existed from n to t (every edge any held write can set, record edges included) and every held edge write between two of them, applied or not, closed under authors. Point-free, so it holds whatever any walk had at any point: a verifier must see every path an earlier walk had (drops are sticky: a write it audited without dropping stays), every demotion of the node on a path gained after its write, and an edge the node left itself. A dropped demotion is kept because it can still have dropped a write on a projection. Rejected: closure at a point with later-demotion rounds; each round needed another failing seed and cost 0.2 s at 10^4. Projection oracles check applied, dropped, the author's standing per write and each node's role on each thing at every write's point from its own certificates against the full evaluation, sticky residue skipped.
- **Self-removal attribution** (`Attr::SelfRemoval(class, on)`): listed under (author, `on`), the holder for one through a holder, so a fall on that holder audits it; its frontier coverage reads the write's own target. A commit whose self-removal goes through a holder is not placed incrementally (rare).
- **Purge author right**: the actor the delta's commit acted for (header field 2), held by any node with write on it while it has write on the thing. `PurgeBy` (osis-base) is five named sets, no scale. Consequences of `author` Tess accepts (no exceptions, spec/wire.md §4): an author who lost write leaves bodies no one may purge until re-granted; a hostile `author` write stays. A body under it still goes at an absolute keep at most (`retention::abs_timer`) or expiry; at hosts then by a label delete key. A purge acting for an actor (a client) drops what the node and the actor both may, judged at receivers, so a held or unsynced `author` delta of the node's account is safe from its client admin. A snapshot drops a covered body only if its own commit holds the right (`retention::holds_right`): a plain writer's snapshot under `author_or_admin` drops only that writer's bodies (measured in notes/growth.md). Must-hold stays by coverage alone (issues/covered-body-new-label.md says why). `nobody` is must-hold while kept. A promise covers what honest nodes keep; hosts carrying a thing follow its labels, so taking a thing off a label deletes there whatever its retention (Tess's latitude, coordinator's call).
- **Readings of §5.1 the code fixes** (the models follow them):
  - R demotes X on N when R is an explicit write (applied, not a self-removal or invite grant) on edge (M, T), X reaches M (or is M), N is reachable from T (edges of any role and `until`, record edges included), and X's class on N is below its class with the edge restored "as if the holder still held the role": the join (componentwise max, alive) of the edge's values since the last explicit write on it, plus, for a node that lowered it by its own write, that node's values before. A value already expired when written restores nothing. So a gap left by `until` or self-removal is finalized only by the next explicit write on that edge, not by any write concerning X (a per-node "held class" cross-wired things in the joint model).
  - A's chain writes: the writer adds the commit IDs of `Timeline::certificates(A, target, R's point)` to the frontier, and a frontier's commit IDs cover session-form writes too (`Frontier::covers`). The walk exempts nothing but R itself.
  - **What R puts in question** (`Timeline::demotion_scope`) is read from the settled walk with R appended to a copy of the timeline, not from standings beside it: R's audit can drop a write that held up another standing (the demoted node's grant to Y, its own self-grant), so the fall at R depends on R's frontier, and a scope from the walk without R loses honest writes. The scope: per node, things it falls below a role on at R, things its class falls on with the targets of its applied writes attributed there, the targets of the writes R drops. The writer (`Engine::demotion_frontier`) starts from the scope as if every held write were received (`Timeline::all_held`: no drops, so no re-walk; an empty frontier dropping an admin's writes would otherwise re-walk the history after it), then builds the frontier from the scope and asks again until the answer is inside it (only grows; usually two probes). Then no received write on an aspect R puts in question is dropped. The probe's `ts` is the HLC's next (`Hlc::peek`); the commit's `ts` can still come later (wall time passes during the probes; a cascade rotation in `demote_in` commits first), so an `until` expiring in between can widen R's fall past the scope: needless drops of received writes, convergent, not fixed.
  - **Every explicit write that audits carries a frontier**, whatever call writes it (spec/permissions.md §5.1 step 4): an explicit removal always (without one it is a finalize), and any other explicit write (a grant, a lowered value) when the edge as restored exceeds it (`Timeline::audits`: a lower `may_grant`, a role below one lost by leaving or a finalized `until`). One computation for `remove_signed` and `grant_signed`, gated by `Engine::needs_frontier`; the writer rule refuses a frontier where nothing audits and an explicit write that audits with none (a removal with none is a finalize, refused unless past its `until`). It also catches the race where an `until` alive at the probe's `ts` has passed by the commit's: the write fails rather than drop every write of the holder's. Principle: a write that takes something away is judged by what its author had received, and only explicit writes take; a grant is a put like a demotion to a lower role, so exempting grants from audits is no option. An `until` alive at R takes nothing there, so it does not audit (its passing audits nothing; the next explicit write does): with it the audit only ever found no fall, and every timed grant would have carried a frontier for nothing. The probe cost is paid per auditing grant only.
  - A write whose holder is its target is no write; a record edge is written like any edge (set to its record value, it is in force by the record again).
  - Self-removal: lowers the grant in every component, author admin of the holder, and either the holder is the author or the author has no edge-admin authority on the target (spec §2, decided at review: removing one's group from a doc one is also admin of by its record edge is an explicit demotion that audits the group's admins); a redemption's (author is the holder, holds only an invite, commit has another op) is attributed `Invite(level)`.
  - Frontier coverage (snapshots, spec/commits.md §5): a session range is covered when its last counter is (`>= hi - 1`), or when the snapshot lists no entry for the session (it holds nothing of it).
- **Layer 2** (`content.rs`): re-grant (role at `At::END`) validates writes from where the author first held the required role on the thing ("valid again"; earlier writes stay invalid); else held at the commit's point and no later explicit demotion below the required role; else the frontier of any later such demotion decides (a gap write listed by one of them is valid); then the addenda (`Timeline::vouching`, Revocation above). Deliberate (decided at review): a write after `until` or a self-removal is invalid until the next explicit demotion, whose frontier then decides it (§5.1 "as if the holder still held the role"). Role commits are commit form; the node voids overlapping session-form ranges on other aspects (engine `apply/atomic.rs`).
- **Sticky residue** (`common::residue`, used where a projection or another drop order may differ): a drop whose cause R is not, in the settled walk, an applied class fall of the dropped write's author X on its target N through the write's class, X's class on N just before the write there; a self-removal through a holder is judged on the holder. `Walked::falls` records a class fall only where X has an earlier held write on N: a function of the held set, never on a leaf, so not aliased by extend.
- **Trust sets and disputes** (`trust.rs`; spec §5.1 Trust set; notes/disputes-plan.md step 3): `Timeline::evaluate_with(held, &Trust)` seeds D from the trusted ops (who a demotion demotes, what it puts in question, the "preceding value" of an edge from the last held op on it in point order else its record value) and runs the shrink loop; `Timeline::disputes` walks once more per unapplied trustable op. Ops that may be trusted: a frontier, holder not the author or the target (a finalize or a self-write is ignored). `Timelines::set_trust` drops the components the old or new set names and evaluates them anew; such components take no incremental path, save or restore (`Timelines` checks its own set, not the kept walk's, which may have been walked under another), and `demotion_scope` on one re-walks from scratch. Detection after each update: the trustable ops of the touched components that stopped applying and the new commits' unapplied ones go through the dispute walk, at most `DETECT_MAX` walks per update (past it, stopped-applying ops are kept as the store trusts them, newly held ones counted as unexamined). The trust store and defaults: notes/disputes-plan.md step 4 (engine `sides.rs`). Only osis-perm, the API layer and the store may name these (tools/policy.py).
- Differential (properties): joint and edges models agree exactly on 100k histories each; `trust_model_agrees` compares the walk under trust sets, the active ops and the open disputes with the model's `trust::side` (no trust, each dispute's R alone, a node's random picks) and a `Timelines` switched T, T', T with a fresh evaluation under T.
- Open: the model's library exposes walks and generators but no named scenario list (its scenarios stay `#[cfg(test)]`); counterexample shrinking and quiescence checks are unbuilt.

## Implementation (role flows, osis-engine `flows/` and `rotation/`)
API and engine hooks: notes/engine.md (Public surface) and notes/engine-roles.md. Tests: `core/node/tests/it/flows.rs`.
- An account is created by its node (`Engine::create_account`) in one commit signed as the account: the account at its first epoch (a key actor, admin on itself, its epoch seed in `account.0` on its devices actor D), D (first admin the account, its secrets boxed to the node, the home label under D's) and the profile. Held key actors sign in commit form and open their boxes; nothing persists them. `Engine::certificates` places the account's and the node's own cards with every label; the node's goes with issues/account-signing.md step 7.
- Pairing is a direct grant (or, for a node already a holder, a re-seal) plus every commit touching the account, its record chain and both nodes, as one direct send.
- A plain thing with a current holder other than its first admin (its only keyset part turned invalid) gets secrets of its own again from an admin node at the end of a complete pass of its secret actor's labels (`Engine::own_secrets_candidates`, `give_own_secrets_again`), the rotation delivered by inbox to the holders it boxes. Each candidate is left for `SETTLE_MS` after the newest role write on it arrived to that write's author (node-sync `own_secrets_wait`, as certificates and steps are left to their authors): one admin acts, not all at once, each forking the thing's secrets and labels (a label each, which every node then syncs and prunes). Admins that act concurrently anyway fork. Candidates come from a scan of `ix.holder_keys` targets per label pass (a measured cost would justify an incremental set). One that cannot be rotated (a holder's `keys.0` not held, an intermediate uncovered) is retried, with a diagnostic, each pass.
- A grant first gives the target, and a plain holder, secrets of their own, makes the rotations it may on the holder and the target first (sealing to a holder actor's keyset is encrypting under it) and boxes every granted role's current epochs. Authority: admin on the target, else an invite grant (no current grant, role and invite at most the effective invite), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own grant or the author's authority on the target comes only through the holder (admin on it); it carries no rotation (the next node that may rotate does) and the leaver drops what it lost. Otherwise it is an explicit demotion with its frontier, carrying the target's rotation of the roles the holder left. A removal of an absent grant (finalizing a used single-use link) resets the holder's dead entries and audits the holder's writes on the target.
- Departures are read from the timeline and from the boxes held at current epochs (a holder re-granted since drops out) and cached per actor, cleared on any role-class state write, timeline update, held-epoch change or key-actor hold/drop, with no clock horizon (keys read no clock).
- An epoch's introducing commit (`Core::epoch_intro`) is the earliest valid commit writing its keyset in `keys.0` (only a rotation does; a box introduces nothing): what a box naming the keyset carries and a certificate of an actor's current keys. Noted from valid role-commit parts at apply; a flip of a `keys.0` part rebuilds the actor's entries and held keysets, so an invalid (backdated, forged) write never introduces or holds a keyset. A dropped `keys.0` body's keysets, `rotation_role` and `grant_overreach` stay, so a compactor keeps knowing them and re-judging needs no body; `uncover` (never received again) forgets them. `boxes_to` is noted from held `secrets.0` deltas of any validity (a lookup for `reopen_dependents`) and goes with a dropped body. Epochs are persisted whenever they change.
- A demotion frontier above `CHUNK_THRESHOLD` is a chunked large value the header links. `Engine::certificates` returns the parts to carry per commit; node-sync places a copy's linked blobs (header lists, linked frontiers) under the label with it.
- Contact cards stay in the osis API (`contact_card`): the card composes calls flows already has (a group thing written through the API's membership, its own secrets, a label, certificate placements, a read link) plus the API's local record of the card; a flows call would only move that orchestration below the layer that owns membership and sync.
- Re-seal and registration are pull hooks for node-sync (`reseal_due` at the end of a complete pass, `issue_step` per host head); flows only return deliveries.

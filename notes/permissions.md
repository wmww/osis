# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: owner direction, why each rule, costs and leaks, revocation and move (copy) reasoning, the `core/test/roles-model` findings behind the role timeline, sharing patterns, public content and anonymous writing, rejected alternatives.

## Owner direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: owner, admins, editors, viewers.

## Concepts
- **Terms** (owner, round 13; spec/permissions.md §1): rights are roles given by role grants, and an actor with a role is a holder ("Dana holds write on X"); member and membership mean only placement in a group ("this note is a member of Work"), which grants no rights. One word per sense, so code, API, CLI and spec never use member for a right; a CRDT set's value is an element, a `Slots` entry a slot.
- Any thing becomes an actor when it needs holders of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the role-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope; the owner is the recourse. So a person actor's owner should be an offline recovery key, with devices as admins (app policy). Consequence: only the recovery key can roster-snapshot the person actor, so its role history (device churn, tiny) is bounded only when the key is used.
- Recovery of a lost owning key is out of scope (owner). The actor keeps working (admins can remove each other) but can no longer be roster-snapshotted or settle an admin war; its things can still be copied out by any admin.
- Recovery card: the seed alone cannot find the person actor (tid, labels and hosts are not derivable), hence the card format; the recovery key owns the person actor, so every home-label step lists it with an entry box; the card names several hosts, and the key claims the current step by its static entry and reads the read secret from the step's entry box (spec/sync.md §2).
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things, the person actor under its recovery key) derive secrets like any plain thing; nothing else uses them.
- Nodes are things that own themselves and grant nobody anything; the node card under every label a node tracks shows exactly the readers of L which nodes sync L (a read-only node's card arrives by deposit), and its expiring `seen.0` heartbeat when it last did (notes/ephemeral.md), never a roster. Rejected: a self-edge granting the person admin (covers only own devices); a devices group readable by contacts (leaks the device roster, misses read-only co-readers). `reach.0` carries no IPs (dialable key and relays only, notes/networking.md); apps exclude it under open-audience labels so strangers cannot dial the device.

## Keys
- Writes are node-signed plus a chain of role grants. Sharing an actor's signing key erases which holder wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to sign deletes of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the owner), demotion write -> read (rotate write only), removal. Epochs are per role, so a writer's rotation of read and write leaves the admin secret, its boxes and the label delete key exactly where they were, and nothing "carries over". Concurrent rotations fork the epoch (spec/crypto.md §4): boxes are keyed per epoch so both rotations' boxes survive the merge, holders keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it; a forked role of an actor M with a known departure is rotated too when a current box to M names a fork other than M's newest (`fork_named`): a node holding no secret of M names M's `keys.0` keyset (the LWW winner) in a box to M, one holding the forks names the newest (lowest nonce), and each judged the other's box uncovered, so A's owner and M's owner rotated A back and forth for good (issue rotation-settle-livelock: P's cascade rotated M unsynced beside M's owner; `rotator_lacking_write_resealed_*` over seeds, tier 2 `_large`). Rotating every forked role instead looped: two redeemers of a single-use link merged K's fork concurrently forever (`used_link_with_sharer_offline_spec_permissions_9` hung). Accepting any current fork in the covers rule would break the walk's class merge, exact only for verdicts at the newest epoch; at a host the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many holders at once forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (holder, role), which leaves holders holding different secrets after concurrent rotations, unable to read each other's new wraps. Epoch numbers others name are never trusted: the next n counts from the rotator's current epochs only, a pending commit records no epoch beyond its bounded reading-only secrets, and an epoch above 2^62 establishes only next to an established one at n-1 (a planted n = i64::MAX once overflowed n+1 and blocked every later rotation, so removals too).
- **Write or above rotates its roles and below** (decided with owner). With admin-only rotation, every actor a person holds a non-admin role on would keep wrapping new content to a lost device until that actor's admins happened to rotate, and the person could do nothing about it. So the person's own device rotates every actor it writes to when it removes the lost device, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks holders out, worse than the storage waste a reader may cause; an actor the person only reads keeps wrapping to a lost device until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a host, which only ex-admins can (notes/sync.md). Until an admin registers the newest epoch, a removed device keeps the old sync and write keys at hosts: ciphertext it cannot open, stale stamps and level-3 deletes that holders heal. Residue: a holder that has not heard of the removal wraps under the old epoch, and the lost device reads that one blob (as with Signal sender keys).
- **A `secrets.0` record needs the role its key names** (validity `secrets_role`): a map record acts only on the entry of its key (spec/crdt.md §5.6), removals included, so the role and the removed box are read from the delta alone (`keys::secrets_write`); a key-erased record needs admin. This replaced a lookup of the removed entry's creation key (`box_keys`, `rotation_unresolved`, `secrets_unresolved`), whose answer depended on which bodies a node had held. `roles.0` perm adaptation (`edge_ops`) still names a removal's holder by its entry's creation (`holder_keys`, unresolved until held) but ignores a reset carrying another key, as the CRDT does.
- **No periodic rotation, no rotation policy** (owner). A device compromise is either known, and the removal rotates before the next write, or unknown, and the device is still a holder, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy of the secrets would need the device's KEM key to change from fresh randomness the thief lacks; the seed is the device, so a thief holding it is the device and nothing heals. History boxes mean a compromise yields all stored history anyway; "no history for new holders" and bounded history are app or future choices, not core.
- A plain thing derives its secrets until it has a non-owner holder, so nothing is stored; then explicit secrets, so that removing that holder rotates the thing alone and not its owner. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, which are one-way from the owner's), so wraps, delete keys and label steps need no special case (content of the derived era keeps the owner's delete keys: a later admin of the thing who is no admin of the owner cannot delete it by key at hosts, only the label delete key can; accepted, owner); a derived secret's epoch has the owner's n capped at 2^62 − 1 and the nonce its secret names under the thing (spec/crypto.md §3), so a writer of the owner jumping its n past `MAX_FREE_N` cannot put the switch above the headroom line, where a holder holding no secret of the owner could establish nothing at n − 1. Explicit secrets do not stop the cascade the other way: every rotation of an owner is caused by a removal, and the removed holder could open every explicit secret the owner's roles reach (owned things, edge targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `keys.0` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin happened to act.
- Nesting cost (accepted by owner): removing a holder rotates every thing with explicit secrets whose secret it could open, so a lost device costs one lazy rotation per shared thing the person reaches; the usage rule is to share sets through one actor. A thing's admins learn what it holds roles on because every edge whose holder is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct holder per rotated role, one re-registration per label per host. A company of 50 teams with 10 labels on 3 hosts: 50 boxes and 30 signed messages per person removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `keys.0` window**: until a person's new `keys.0` reaches a co-actor's label, rotations there seal to the lost device's old keyset and its steps list its old claim key, so the lost device reads new content via an honest host. Hence the MUST to place the removal and new `keys.0` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **Re-seal is a SHOULD with a trigger** (a current holder without a box at a current epoch, or a stranded heartbeat). Without the trigger a grant raced by a rotation was a silent permanent lockout. The missing box that marks a deliberate exclusion looks exactly like the one that marks an unknown grant, and TLC (core/test/tla/rotation, R1) showed a node that receives the rotation before the removal re-seals the removed holder, who then reads post-removal content from an *honest* host (it holds the current sync key); the earlier reasoning that the covers rule heals it was wrong about the window. Fix: **the removal or demotion and the rotation it requires on the target are one role commit**, so holding the rotation means holding the departure, and an omission in a held rotation can only mean the rotator did not know the holder. It costs nothing: the covers rule already forced the remover to rotate before encrypting the removal commit. The inbox copy to the removed holder and the certificate copies carry the edge delta only (projection). Rotations of other things (the cascade) stay lazy; they exclude nobody directly. Guards on top: a re-seal decision comes after a full sync pass (like the pre-sync before a demotion, spec/permissions.md §5.3), a holder whose `until` is within `MAX_DRIFT` is not re-sealed automatically (the rotator's and the re-sealer's clocks could disagree on whether it has left), and boxing a secret to a holder counts as encrypting under its epoch (a re-sealer that knows of a departure rotates first). The second TLC round showed the one-commit rule covers only the rotation that carries the removal: a later rotation by a node that knows it omits the holder without carrying anything, and a node that reads that rotation out of order (a peer, a second host, or a re-seal's history box handing it the secret before the commit) re-seals the removed holder. Fix: **established epochs** (spec/crypto.md §4): a rotation counts only once the node has applied its commit and the commits of every epoch it supersedes, transitively (or a `secrets.0` snapshot stands in for a compacted chain), so holding an epoch means holding every departure its chain carried, whatever the arrival order; this is the order the wraps already impose on a node that never got a history box. Re-seals are made only at chain-established epochs (a late joiner holding only a snapshot rotates instead: a rotation boxes everyone it thinks current, so it is a re-seal of everyone) and at the end of a complete pass (the log of every host and peer read to its end: cheap to know, and what makes the post-compaction case sound). Opening a label is no longer "encrypting under": a re-sealed holder must open with the re-sealed sync key to fetch the rotation commit that establishes the epoch; an open proves possession to a host and produces nothing others rely on. The remover uploads the rotation before registering the step (notes/sync.md), so a holder listed in the step never strands merely because the commit is not there yet. Residue (accepted, notes/sync.md Limits): after compaction a node's view of the roles no longer travels with the epoch chain, so a node that boxes a holder at a snapshot-established epoch from an incomplete view (a host that never got the removal, an interrupted first sync followed by an eager rotation) can box a removed holder; same class as a rotation by a node that has not heard of the departure, healed by the next rotation of a node that has. The refused-deposit residue stays in issues/reseal-triggers.md.
- **Planner** (`osis_keys::planner`): `plan_departure(graph, A, M, from, held)` walks owned things and edge targets from A over a `Graph` trait (`PermGraph` adapts a perm `Timeline`; `MemoryGraph` for tests), carrying the set of roles exposed: on T reached via role ρ, the exposed roles of the predecessor that are ≤ ρ (a role secret opens only boxes of that role). Each entry carries one `Departure { via, holder, from }` per path (`via` = the chain of actors from the entry down to the one M left), and the covers rule follows the chain recursively through `HeldActors` (each level's newest keyset and its `secrets.0`; unknown counts as uncovered). Without the recursion a two-hop chain (device left P, P in T, T in U) looked covered at U while T was unrotated. `Plan::required`/`mine` are top-down (depth from the departure); a node that may not rotate an intermediate stays stranded on what is below. Plain things are traversed but need no rotation. One departure per path is exponential in diamonds, so the planner is a test model; the engine uses `osis_keys::reached` (linear) for the labels a removal is placed under; `lost_access` (what a node drops) uses it too.
- **Departures inside holders, no depth bound** (`rotation::departures::collect`): the covers rule reaches below the first actor M of a chain only through M's newest epoch's verdict per role, so chains alike in (first actor, second actor, actor left, holder, role, M's verdicts) decide alike everywhere (covers, `rotation_due`, the revokes placed, own self-removal) and one departure per such class is kept: a fixpoint over the holder graph below A (A included when it is on a cycle), each actor keeping one departure per class of its own, a chain extended by every actor it holds a role on except its departed holder. Chains may revisit actors (cycles); classes are finite, so it ends. Polynomial (actors x classes x edges); the earlier walk enumerated every chain (exponential in diamonds, so it stopped at 8 actors: deeper removals never rotated). Exact, cycles included: the class at an actor is a function of the class one level down (verdicts at U = U's box for W plus W's verdicts), so merging commutes with extension (`walk_matches_path_walk`, and `walk_with_cycles_keeps_every_bounded_chain` against every chain up to 8 actors). The verdicts read held epochs and `secrets.0`, so the departures cache must drop whenever those change (`role_changed`, `save_epochs`). `covers` is a loop (no stack bound on depth). Chains are `osis_keys::Via`, a shared-tail list (`inside` is O(1), iterative drop): the walk holds one hop per kept departure (`walk_memory_linear_in_chain_depth`). Deep-chain cost: issues/rotation-chain-cost.md.
- **Role cycles** (was issues/rotation-cycles.md, issues/cycle-stranding.md): X and Y readers of each other, D removed from X. Y's epoch boxes X's old keyset (D holds it), so X's new epoch boxed to Y leaks; any order of lone rotations that box each other leaks. Cycles stay allowed (owner: tags place into each other by ordinary use, notes/tags.md; two people's shared tags have disjoint admins), and the **leave-out rule** handles them with each admin acting alone: a rotation never boxes a holder actor M for role r when the epoch of M the box would name does not cover a departure inside M the new epoch must cover (`holder_covers`; boxing to it is encrypting under it; the role is cut at the first such r). Grants follow it too (`grantee_left_out`, by M's own departures: before, a grant to a stale M boxed the target's current epoch to an M epoch a party that left M holds); a granter that may rotate M rotates it first (`ensure_rotated` on the holder in `grant_in`), so only a granter that may not leaves M out, and an invite grant then carries fewer boxes or none, still valid (`grant_to_stale_holder_leaves_out_spec_permissions_3`: admin, M's admin, invite holder). The grantee's nodes meanwhile hold the edge without a box (their label status reports stranded; no heartbeat, no secret to wrap it in); M's admin rotates M on its next pass of M's labels (`usable_keys`), and T's admin's re-seal trigger then boxes M. X rotates leaving Y out; Y's admin rotates Y, boxing X's new epoch; X's admin re-seals Y. The re-seal trigger (and `reshare`) skips a holder actor whose newest epoch does not cover, else it would undo the omission; re-seals supersede nothing, so no ping-pong. The trigger also skips a role unless the node holds the secret of every current epoch of it: a node may rotate an actor through a holder actor that was left out (found by `_large`, seed 1034: `reseal_holder` failed `NoSecret`), or lack one fork's secret. Re-seal fixpoint: a re-seal is made only if it changes what the trigger judges and, once made, satisfies it. A break of it looped (churn seeds 140170, 140188: a node re-sealed itself about 500 times in 20 s): a node holding one fork of write re-sealed itself with that fork alone on every pass. Every box is keyed at its own (holder, role, epoch) (notes/crypto.md), and a node re-seals a role only if it holds the secret of an epoch the holder lacks a box at, so every re-seal adds a box (`forked_role_reseal_reaches_fixpoint_spec_permissions_3`). **Re-seal invariant** (`reseal_candidates`): once re-seals settle, every node counts the same current epochs (supersession is read from the rotation commits, notes/crypto.md) and every holder holds every current epoch any node holds (`forked_reseals_settle_*`: random concurrent rotations leaving out random holders, then re-seal rounds). Requiring every fork's secret of a re-sealer instead stranded a holder when no node held them all (`forked_role_resealed_without_a_node_holding_every_fork_spec_permissions_3`). Rotating the fork away instead (as `fork_named` does) was not chosen: a re-seal is one node's local act, while rotating every forked role looped before (single-use link redeemers). A node lacking a role's current secret (it reaches the actor through a holder actor left out) rotates the other roles it may (`rotator_lacking_read_rotates_write_spec_permissions_3`) and waits for the re-seal of the one it lacks, stranded on read through its heartbeat when read is the role it lacks; when it lacks write only (read current, no heartbeat) the re-seal trigger of a node holding write re-seals the left-out holder actor once it rotates (`rotator_lacking_write_resealed_spec_permissions_3`). A removal or demotion whose rotation would write such a role is refused (`Misuse`, "waits for a re-seal": writing it would drop that secret from the history boxes; `removal_lacking_rotated_secret_refused_spec_permissions_3`). The removal commit judges with its own departures added (`collect`'s `pending`), since the chain back through X is what makes Y uncovered. The walk keeps chains that revisit actors (`a` included), else X's departures would lack [Y, X] D. Acyclic intermediates still strand (`rotation_due`: wait for a stale holder M only when `a` is not below M; a per-chain "returns to `a`" test would be unsound, since a class's kept chain need not show the cycle, and the graph test makes waits acyclic, so no deadlock): leaving them out too would be one rule, but then M's holders get `a`'s new epoch only by a re-seal inbox blob to M (wrapped under an epoch they lack, and M's inbox may be its owner's), instead of in-band from `a`'s one rotation after M's; `revokes::nested_departure_revoke_placed_spec_permissions_4` showed the nested reader cut off. Rejected: joint rotation of the cycle in one commit (about 400 lines, strands forever without a common admin); forbidding cycles (owner call against). Tests: `removal_in_cycle_leaves_out_spec_crypto_4` (2- and 3-cycle; `openable` follows boxes from the departed party's old secrets, independent of its node), `departure_below_cycle_leaves_out_spec_crypto_4`, `cycle_with_disjoint_admins_converges_spec_permissions_3`, and `cycle_removals_leak_nothing_random` (tier 2 `_large`): random 2-4 actor cycles with one or two owners; after the removal and after each admin acting alone (cascade, re-seal trigger) until nothing changes, D's old secrets open no epoch judged covered, nothing stays uncovered and every holder is boxed again.
- **`until` counts as a departure** for rotation and the covers rule, else "share for a week" never ends for reading; eager rotation makes boundary disagreement between clocks harmless, and the re-seal guard above keeps a slow clock from re-admitting a holder whose share just ended. A re-grant after the `until` removes the expired entry first (`grant_in`): a set over it kept the fields the new edge leaves out, the `until` among them, so the holder stayed out even in the granter's view (`regrant_after_until_reads_again_spec_permissions_2`).

## Sharing
- Sharing never changes a tid. Moving a thing to an actor its owner owns has no double-spend harm, so it is an ordinary write (an edge). A copy with a new tid is only for moving a thing out of its owner's tree, which should be rare.
- One note: an edge on N, explicit secrets on N, N its own label. A set: a group thing with holders and secrets, granted read on each thing (one edge per thing, one commit). A set meant to be shared as a unit is better created under a common owner.
- Group membership grants no rights (an edge on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (usage rule, doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Problem: checking a write on N needs the role grants of N's owner chain and of the author's own actors, which only holders can read. Resolution: signed role commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns, for every author under L, every path it ever had to the things it writes there (every held edge write between things on those paths, applied or not, each `created.0` record and hence that thing's dedup secret, and those things' snapshots projected to the holders on the paths), never whole rosters. The point-based rule it replaced (item 156) already revealed about that for chains at now. Author identity is inherent anyway.
- Roster snapshots in certificates are projected per edge: a whole snapshot would hand every reader of L the full device roster of each author's person actor and the rosters, `label.0` IDs and hosts of every team above it.
- **Per label, not per node**: a certificate delta already under the label counts whoever placed it, so a joiner copies only its own chain (11.5 KB per label in a chat) and not the sharer's again, and holders do not all re-copy a rotated actor's new `keys.0`. Sound because a copy counts only once this node checked every delta of it against the header's delta hash (`SyncEngine::genuine`; opening checks the prefix only, and a held commit's late parts are skipped unchecked, so before the check anyone able to deposit under the label could post the header with garbage deltas and stop the real copy; the same check now guards `entry_for`, `carried_by` and the duplicate and strict-subset deletions, where a forged blob could have got real copies deleted), only while present at every host of the label this node syncs with (else it skips at one host and its own copy then goes to both), and, for a rotation commit of the label's actor, only under the newest epoch. Older epochs otherwise count: a newcomer gets the history boxes with its grant or first rotation box (spec/crypto.md §4) and opens older copies like the label's older content (`newcomer_after_rotation_reads_older_copies_spec_crypto_4`); counting only newest-epoch copies made every holder re-copy everyone's chain after each rotation (40 KB per holder per chat removal). Residue: a holder of a link key alone (newest secret, no history box) reads none of the older entries, own copies included, as before. If another node's copy goes, the next pass places this node's own. Deletion power is the same either way (a copy commits to its commit's delete keys). Closure deltas are never copied (they are closure blobs; a copy was a strict subset others deleted). Another node's demotion or `keys.0` is left to its author for `SETTLE_MS` (30 s) after this node received it, with a wake then (the remover must place them, §3): holders learn of a rotation under K's label before the remover's copy under C arrives, and all of them copied it (3.3 KB per holder per removal). Measured from receipt, not the commit's `ts`, which its author sets.
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some holder of the revoking actor syncs L); chain depth equals nesting depth, at most `MAX_OWNER_DEPTH` (64) owner links (spec/permissions.md §1; a holder nesting deeper would make every standing query cost more).
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Owner decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and hosts never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too; re-grant restores it, together with Y. Centralized semantics with the revoking device as the host (owner: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- One rule for both layers: the revoke's frontier is one list for edge and content writes, about 10 bytes per (aspect, author node) entry plus 32 per commit-form commit. A prolific device over years writes 10^5–10^6 aspects, so a frontier can reach megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), and every later roster snapshot re-carries it (written afresh each time, so all its chunks are in the snapshot's header chunk list and receivers fetch them before judging; reuse across snapshots was dropped for that). The ledger copies it into every later roster snapshot; that is the price of a roster snapshot replacing the revoke. Rejected: per-node global counters (one counter per node plus gaps) would shrink frontiers but change dot semantics, runs and the model.
- Only the revoker's own receipts matter: a node that may revoke keeps, per (aspect, author node), when it received each counter (granularity and horizon are local policy). A backdated revoke's frontier is bounded by that record; a coarser record gives a smaller frontier and more loss.
- **Chain writes count only through the frontier** (core/test/tla/roles M1). The rule used to exempt "A's own chain writes" (those setting the admin edges on A's admin paths) whoever wrote them and whether A had them, so after A removed admin X, X could write a backdated change to A's own edge (an `until` next week, a lower invite) and it stood. Now A's frontier lists by commit ID the role commits and roster snapshots of its chain certificates for the target at R's point (§4: the writes on its paths, closed under their authors, so a grantor's own grant counts too; held, hence received; by ID because its receipts of X's counters need not be contiguous: a grantee often gets only its own grant). A forged one is not listed and drops; A's edge reverts. First cut (reviewed out): only the writes setting admin edges on A's own paths, read from the end state: a grantor's grant of A's grantor was missed (R then failed), and the end state could name a later rewrite instead of the grant R rested on. Residue: if A's authority at T rested only on a chain write A had not received (another verifier's view gives A a path A's own view lacked), that write drops and R with it; what R dropped in the same audit stays dropped. An honest node holds its chain, so the model generators mark each author's chain certificates as received (`roles_model::hold_chains`, TLA `Certs`); random receipts that skipped them made such failures look like 1 in 500 sticky residue. About a quarter of the writes that grant no admin are tagged written last (received by nobody: backdated forgeries); admin grants are never late, since an honest node does not act on authority it never received (with late grants it would; neutrality then broke through the old sticky epoch-start rejection, since removed). Rates: about 1% of joint histories drop something; sticky residue skipped in about 3 of 10^4 snapshot-model histories; no neutrality case needed the "a snapshot only undoes drops" fallback. A compaction snapshot lists the commit-form commits it absorbed (spec/crdt.md §8), but a receiver counts a listed commit (and a frontier counter) only when it holds its header: a writer could list commits it signed ahead, or claim `X: 2^60`, and the demotion copying the claim would cover X's later writes for good (was issues/snapshot-frontier-inflation.md). So a late joiner that got X's writes only through a snapshot does not cover them; harmless: hosts lose a commit's header only once every blob of it is deleted, i.e. every live write is carried by a covering snapshot, and that valid snapshot vouches for them at nodes still holding the now-invalid originals (`flows::late_joiner_after_compaction_agrees_spec_crdt_8`, `validity::late_joiner_after_compaction_keeps_writes_spec_crdt_8`). A backdated revoke lists only the certificates A had received by its cutoff (`Meta::received`, apply time): one cut off before A received its own grant by X would drop that grant, so it is refused as unauthorized; a later cutoff works (`flows::backdated_revoke_before_own_grant_received_spec_perm_5_1`). Rejected: exempting only chain writes that do not lower their edge (a second rule for a rare case).
- Clock skew: a departure by `until` or self-removal is judged by the holder's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions). If ever needed: backdate revokes by a margin.
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- Re-grant validates the gap: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it makes recovery from a stolen device's backdated mass revoke lossless. It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them.
- A revoker can backdate to roll back more; not a new power, any writer can invert others' edits.
- Dot reuse by a revoked actor would let it write under covered dots forever, so overlapping node-form ranges from one node void both commits (spec/commits.md §4). Honest nodes never overlap (an unsure node uses commit form). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Role commits use commit form and a node-form one is bad input (spec/commits.md §3, §4), so a removed admin cannot void its earlier grants, revive a holder it removed or void its own rotations that way (it could make its grantee's edge never have existed, and with it a removal the grantee made of it).
- Sync-then-revoke closes most of the loss from a frontier taken on an unsynced device (spec/requirements.md, Permissions); labels the device does not hold are read for receipts only (headers decrypted and verified count as received, spec/permissions.md §5.1; notes/sync.md Receipts-only reads), so removal needs no node holding the tree. What remains: writes at hosts the revoker does not reach, writes in transit, P2P-only edits among other holders, revokes issued offline or backdated; all recoverable by re-grant.
- Rejected: timestamp rule (forgeable); accept everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); roles by claimed time only (an ex-admin could mint backdated grants forever); other writers vouching for edits the revoker missed (a commit kind, a validity fixpoint over vouchers who are later revoked themselves, a per-node receipt clause and a tiebreak, all for edits that reached another writer but not the revoker; not worth it).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 already judged edge writes one by one.
- **Snapshots vouch** (owner decision, round 13, option A; spec/permissions.md §5.2): a compaction snapshot counts iff its author could write the aspect at it, at the strictest role a carried write could need (admin for `keys.0` and `secrets.0`: a writer's snapshot could otherwise carry a forged admin keyset, inbox, deposit seed, admin box or tombstone under a dot nobody holds) (judged as its delta by commit ID, so a demotion frontier covers it by listing its ID; a reader's snapshot gives nothing, spec/requirements.md malicious readers only waste storage); a valid one's carried writes count because its writer vouched for them, never re-judged per claimed author. Revocation stays exact where no valid snapshot carries the write (full history); through another writer's earlier compaction a removed holder's unseen last writes may stay, consistently on every device, also those holding the invalid original (owner: fixed by hand). A valid snapshot's copies count also where the original is held, and govern a held original they misstate (below, Snapshots and history), so holders converge. Why: per-claim judging (the previous rule) needed claims (`Authors`, held claims, double-import tie-breaks), per-write indexes judged per (source, author, `ts`), "removed only when no valid snapshot carries it validly", refills on late owners, and still left a family of order-dependences (a dropped valid carrier let a reader's copy void the write; forged copies under dropped deltas' dots; ephemeral session attribution). Accepted: a valid writer can carry any write under any dot (it could write the value itself anyway; authorship is never exposed unverified, notes/api.md Attribution). A body (snapshot or delta) dropped under a cover that later turns invalid counts as never received again and is fetched again (holders re-upload it: uncovered, so must-hold); with no copy left anywhere its writes are gone at every node alike (notes/node.md Carried writes). A commit one of whose parts a node never held and that was deleted under that cover applies there without it: a held snapshot of any validity listing the part stands in for it (owner decision (a), notes/node.md Snapshot authority).
- History of the content rule: the first rule let any writer's snapshot carry a revoked author's elements; then "compaction snapshots vouch for nothing" (every element judged as its author's write; `core/test/roles-model` `content.rs` showed an "authorized at the snapshot's `ts`" variant diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered); then snapshot authority plus per-claim judging; now vouching. The divergence `content.rs` found does not return: a cover must carry what the snapshot it covers vouched for (spec/commits.md §5), so dropping a covered snapshot removes nothing.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual role grants are allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed anyway: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (owner chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin edge on G could backdate a forged write to a time it held only the edge; removing the edge first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood forever (found by `core/test/roles-model`, `two_admin_paths_class_attribution`, `chain_and_edge_paths`). Path-based audits (each removal audits what went through its path) would also close it, but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal falls with its grant: both are attributed to L's invite class on K (a forged redemption's self-removal kept after the finalization dropped its grant would burn the link and block the honest redemption the sharer had seen). Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the tenure (the rejected claimed-time rule).
- Writes to `secrets.0`, `keys.0`, `label.0`, `moved.0`, `was.0` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering role-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Role timeline (model findings)
Model: `core/test/roles-model` (throwaway Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test --workspace` runs the scenarios; `cargo run --bin roles-model -- [samples] [as|exempt|strat|stratw|frontier|snapshot|edges|edges-prov|joint|digest]` searches (counterexamples printed shrunk, as traces; `digest`: notes/testing.md, Models) (`joint`: `src/joint.rs`, the joint walk over several actors with mutual role grants and commit-ID ties; `src/content.rs`: layer-2 scenarios, test-only): exhaustive up to 3 edge writes (owner, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `snapshot` (`src/snapshot.rs`) is the two-level roster-snapshot model; `edges` (`src/edges.rs`) models projected rosters, links, invites (audited by level), per-op judgment and plain owner-chain writes on a thing (its `moved.0`, say); `joint` (`src/joint.rs`) is the joint walk over several actors (owner chains, holder actors, mutual role grants, (t, author) ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs` holds layer-2 scenarios: per-delta validity across partially synced things, snapshot authority at `ts`, and the snapshot-of-snapshot divergence that led to "snapshots vouch for nothing" (below).
- **Third-party witnesses judged by end-of-walk roles fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a holder by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the owner's further-backdated revoke cancels a stolen device's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for edge writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin device's backdated removals stand iff the node removing the device had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Edge demotions never audit owner-chain writes, so an edge-admin cannot drop a roster snapshot.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it; node-sync writes that removal: `SyncEngine::finalize_links`, test `until_link_backdated_grant_void_spec_perm_9`); plain owner-chain writes on a thing such as `moved.0` (a removed device's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky. A roster snapshot also repairs it (its ledger has no demotion for the dropped cause), so §6 neutrality holds only up to sticky residue (core/test/tla/roles `MC_sticky_snap`, confirmed in osis-perm). Also residue (owner-accepted): a drop whose dropped write made its demotion a fall stays after a restart where the demotion is no fall (D only grows); a re-snapshot replays the demotion as no fall and the drop goes. The reverse too: a re-snapshot can make a sticky drop, since it erases a dropped write's transient effect (a dropped grant that kept a node's class, so an unaware demotion of its edge audited nothing; without it the demotion drops the node's write, then is dropped itself; OSIS_PERM_SEED=89000, reachable since self-removals are audited, `resnapshot_leaves_sticky_drop_spec_permissions_6`). Divergence heals: the window is one sync of the snapshot, since every holder takes it as the epoch start and converges to its answer, late joiners too (node test `resnapshot_residue_heals_on_sync_spec_perm_6`: before, the full-history device keeps the drop and the compactor does not).
- **Self-removals are audited like any write** (owner, simplicity): they keep only their looser authority (admin on the holder, none on the target) and carry no rotation. One through admin on holder M is attributed to the author's class on M and listed as a write on M; one lowering the author's own edge to its class on the target. Before, they were never dropped, so a device removed from person P could write backdated removals of P's edges everywhere and they stood. Accepted cost: a leave the demoter had not received is dropped and gives access back until someone removes it again (re-seal covers the missing boxes). The honest demoter covers it: `Timeline::demotion_scope` adds the targets of the demoted node's applied self-removals through each thing its class falls on (their `roles.0` receipts survive forgetting). Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.

## Roster snapshots
- Bound role history (spec/requirements.md, Permissions and Scale). Only owner-chain snapshots can be epoch starts: their applicability depends only on the chain above N, never on N's own earlier writes, so a node holding only S and later writes computes what a full-history node does.
- **Tenure ledger**: a snapshot's roster alone cannot answer authority before S, yet things are judged against it after S: writes and epoch starts of things below N made by chain authority before S, and ex-writers' content (layer 2 needs the revoke time). Without it, a routine re-snapshot of a person actor after a device removal kills every owner-chain write the device made on things below while a legitimate admin (2.3% of valid ones in random `core/test/roles-model` runs), epoch starts included. The ledger is the compacted form of the demotions: each ended tenure with the frontier that ended it, so the holder can neither gain anything (a dropped backdated record stays dropped: the frontier travels with the tenure) nor lose what the timeline had accepted. Roster edges carry `since` so a re-granted holder's gap stays closed; every later tenure's frontier re-audits earlier writes, as a later demotion does in the walk. Checked (`snapshot` mode, `resnapshot_neutral`): re-snapshotting P with the roster and ledger the timeline computes changes no record's validity and no G write's application in 8M random histories; compaction, projection and order independence hold with random well-formed ledgers.
- **Ledger cost, the accepted tradeoff**: entries are never dropped, because a write or epoch start anywhere below N may depend on any of them and the snapshotter cannot know which (it does not sync everything below); a time bound was examined and rejected, since a removed holder could forge a backdated write inside its tenure (an epoch start of a thing below N, say) after the bound, and only the tenure's frontier drops it. Roughly 100 bytes per ended tenure of write or above plus the frontier (by link when large, re-uploaded per snapshot), carried by every later snapshot of N: a person actor grows by its device churn, a team by its holder churn. Certificate copies carry only the edge and ledger deltas a chain needs (one delta per edge and per entry, so a projection drops deltas and never breaks a hash), so verifiers pay per edge in bodies but still one delta hash per edge in the signed header: direct rosters should stay in the thousands (spec/requirements.md, Scale). Rejected: writes carrying a frozen certificate of their signer's chain (cannot show the signer's later removal covered the write once that removal is compacted); listing only tenures of holders whose writes the snapshotter holds (breaks writes it does not hold); a Merkle tree over per-edge hashes (saves header bytes for huge rosters, more machinery; revisit if flat rosters above ~10k matter).
- A grant in flight while a snapshot is taken is dead (finality per snapshot); snapshot after a fresh sync, re-grant a victim.
- `ROLE_KEEP` on role commits keeps the revoke long enough for every node offline less than that to apply it. A format constant, so nodes agree on what a label must hold.
- Un-applied epoch start (author later removed with a backdated time or a frontier not covering S): a full-history node falls back, a compacted node sees an empty roster until a fresh snapshot; this only shrinks rosters toward the owner chain. Forgeries by a removed device never become epoch starts.
- Who compacts what: a person actor's own roster only when its recovery key signs (device churn is tiny); busy actors (teams, documents) should be owned by a person actor, so its devices can snapshot them. About 25 bytes per edge. A roster snapshot carries only `roles.0` and `tenures.0`: `secrets.0`, `keys.0` and `label.0` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta), and a rotation's boxes page. The old design carried full `secrets.0` and `label.0` in the roster snapshot, which could not fit a blob for rosters above about a thousand.
- Content via compaction snapshots: with snapshots vouching for nothing, compacted and uncompacted nodes agree whatever snapshots they hold or dropped (`content.rs`, `snapshots_vouch_for_nothing`).
- Checked in `core/test/roles-model` (`snapshot`): compaction at any applied snapshot never changes the result (0 mismatches in 2.5M compactions over 4M histories), order independent, at most 4 walks; compaction points later un-applied diverge until a fresh snapshot in about 0.3% of histories, as designed.
- Rejected: edge-admin snapshots as epoch starts (a compacted node cannot judge them, a removed admin could forge one); a snapshot chain (same problem, unbounded); "a dropped epoch start empties the roster for everyone" (a permanent wipe for any removed device); key-actor-only snapshots (an offline key cannot compact a busy roster).

## Moving a thing (copy)
- Ownership is immutable: a former owner can always sign a competing transfer (double-spend; no fix without consensus), so a transfer must never let the former owner touch what the new owner holds. A copy under a new tid gives that for free: the old thing stays the former owner's, the copy is the new owner's by construction, and the former owner's whole power is to re-point or wipe the old thing, which only misleads readers that hold nothing but the old tid. Decided with the owner over the old aliasing design (below) for simplicity: no verification rule, no identity derivation, nothing kept forever.
- Imports keep history: live state with its stamps and dead bodies alike, each with its origin's retention and author, so purge rights on the copy are what they were (an origin author purges once re-granted on the copy, as it would after any removal and re-grant). What a copy cannot do: give the old authors' delete keys at hosts (the importer lacks their secrets; admins' delete keys delete after the author's purge request) and move rights the moved actor held elsewhere (foreign admins re-grant the new tid). Cost O(subtree + history); the owner does not mind.
- Re-sourcing to (`Commit(origin)`, k) makes an import idempotent (two of X's devices importing the same origin produce the same dots) and keeps imported dots clear of native counters, which start at 1 per (aspect, node) and would otherwise collide with an author's own old dots. Keeping the original `ts` keeps the order among imported writes; everything native on the copy is newer anyway. The origin choice depends on the importer's held set (snapshot if it holds one covering the write, else the commit), so two devices importing concurrently from different held sets would duplicate elements; hence one import per move and the client rule not to import a thing already continued by a held copy. Residual race accepted. Re-sourced dots collide with a commit-form origin's own dots only when the origin is on the copy itself: such an import is void once both are held (`validity::self_origin_imports`, ix.void persisted; its body never joins, `atomic::unjoin_void` rebuilds when the origin arrives second, `invalid_of` keeps an origin owning its dots).
- Resolution is a read-time view keyed on the referencing thing's owner chain, so two readers of one thing agree: the copy's own `was.0` claim wins where that owner has standing in the copy, the former owner's `moved.0` pointer elsewhere. Standing can be faked only by granting the referencing thing's owner an edge on a fake, which is the same exposure any unsolicited grant has (apps place things into their sync set explicitly, spec/requirements.md, Offline and network). Values are never rewritten: an autonomous rewrite is a write with a fresh timestamp that beats a concurrent real edit, and two devices rewriting concurrently would duplicate text links.
- Within one tree nothing moves: rights are edges, the root is the un-removable admin either way, so "move this doc to team B" is an edge change, and ownership depth should match the units that travel together (a folder actor owning its things moves between teams by one edge). Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).
- Replacing a root key (the recovery key owning a person actor) is a copy of the person actor: rare, re-granted everywhere by foreign admins. Not required by anything (signatures need not be PQ, seed compromise is out of scope); devices rotate by add-and-remove.
- Rejected: **hand-over with aliasing** (the previous design): a record on the thing signed through the former owner's chain, the new identity hash(T, H) owned by the new owner by construction, everything below renamed per fork branch, a three-step read-time resolution (standing, the reader's `follows.0` choice, dangle), records kept forever and hence an unbounded tenure ledger; correct and model-checked, but the whole of a spec section plus permanent per-verifier cost for a rare operation. Also rejected: sharing a tid between branches (the former owner's chain stays able to write and delete the subtree), freezing a thing on a second record (no consensus on the moment, so it is a rewind to the transfer, and a disown hands the name back), a notary or log committed at creation (closes every former-owner power but makes transfer an online operation with an outside dependency), transferring without history, a one-successor `moved.0` (first-write-wins needs arrival order or a fork rule).

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `secrets.0` like any key-actor holder). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets (bearer read); the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (and so one cascade rotation of the target): two commits paid two rotations of K and of the target for one decision. perm judges each edge write of a commit on its own (as for a redemption), so such a commit is two removals at one point with one frontier; `core/test/roles-model` needs no new operation for it. None of its edges may be a self-removal (refused by the writer rules). The one-edge rule exists so every removal carries the rotation that covers it (re-seal soundness, above); a several-edge removal under one rotation keeps that, since the rotation excludes every holder it removes.
- **Why K no longer derives its secrets from the seed** (the previous design, "until K is first rotated"): every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every host) and write key, which is exactly the power the invite-only design took away from L. And L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K (allowed since d8a68b4) stranded L. Now K's secrets are random, L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip: the cold-entry path that already existed after a rotation is the only path.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- Finalization: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer device writes a real removal; until then the link is honest-client-only. Node-sync (`SyncEngine::finalize_links` over `Engine::links_due`, any device holding the seed thing and admin on K, woken at the `until` by `next_link_expiry`) writes it after a complete pass of K's labels ended after `until` (passes from before going offline do not count), so the frontier covers honest grants that reached the hosts while the link worked. Without hosts only the making device finalizes, at once (redeemers reached it directly; another device of the sharer may lack their grants). A seed thing counts only when its owner is K's owner (a co-reader can place a `link:seed.0` thing in a shared group). A K whose label never completes a pass (host gone) is never finalized: the link stays honest-client-only. Residual window (owner: keep, documented on `LinkOpts.until`: an expiring link closes when one of your devices next syncs after `until`): while every sharer device is offline after `until`, or K's host is unreachable, a backdated grant uploaded then is received in that pass and covered and stands; cutting it would also cut honest late-received grants (indistinguishable: both carry `ts` < `until`). Future option: a host receipt time as witness, one feature for removals and link expiry together (issues/revoke-needs-whole-tree.md, remaining gap), not a link-only one. Idempotent: `Timeline::lowered_unaudited` (the walk's `prior`) is cleared by the first explicit write, so a second device's concurrent removal restores and audits nothing. Alternative (no `until` or single use at all) loses nothing a hostile holder respects. Race flip: the finalization's frontier can drop a competing redemption the sharer had not seen, so a redeemer that lost by its own view may win; a loser therefore keeps K's secrets and labels while L's self-removal is unfinalized (`contested` in `rotation::lost_among`; test `single_use_loser_keeps_secrets_until_finalized_spec_perm_9`), and drops them once the removal arrives. Only redemption-shaped commits count on both sides (the void one and the applied one that lowered the signer's edge): a plain leave then a void grant (a leaver's forgery naming a removed holder) defers nothing (test `void_grant_by_leaver_keeps_no_secrets_spec_perm_3`; before, any self-left holder could keep any removed holder of the thing holding its secrets for good). Residual: an inviter whose leave commit also granted someone can later forge a void redemption naming a removed holder, who then keeps the thing's stale secrets (no new epochs) until an explicit write on the inviter's edge. Cost: never finalized (sharer gone, a K host gone for good: `complete_pass` waits for every host), the loser follows K's and the target's labels for good. Not bounded in time as pending grants are: past a bound the race flip would leave the winner unaware again. Inbox delivery of the removal to the joiner alone failed: the loser had already dropped and forgotten the target's secrets, and nothing brings them back.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): what a link conveys is "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add edges for actors with no current edge, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier like any edge write. Inviters seal only secrets they hold (their role and below). Holders read K's roster (they are its holders), like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- Self-removal lets an actor always leave or lower its own edge; single-use links use it to drop L's own edge.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (spec/permissions.md §9: kicking one joiner otherwise kills the link for all).

- Resolution hops are capped at 8 (`RESOLUTION_HOPS`): longer move chains are pathological, and the cap keeps a read O(1).

## Patterns
- **Edge on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per holder, so not per note in a folder).
- **Shared owner** (spreadsheet): one actor owns everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: an offline key owns a thin root actor whose admins are a few persons; teams, chats and docs are owned by the root or by actors under it. Root admins can roster-snapshot everything below and remove anyone, and a departing founder is just an admin removal. A team owned by a person actor cannot shed that person (owners are un-removable).
- **Shared tag** (rights live on edges, never on grouping; owners never change; notes/tags.md): the tag is an actor; things keep their owner and each gets an edge for the tag's actor (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same edge so rosters nest; writers may also create things owned by the tag. Per-holder edges on each thing do not work: entitlement puts a thing under the tag's label only when the tag's actor may read it, so no label the holders sync would carry it. Built in core/osis/tests/it/tags.rs.
- **Chat**: see notes/chat.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and ownership (each owns its messages), and `group.0` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and owner actors stay separate; a group may also be an actor when it serves as a shared label.

## Purge rights and retention
Retention is per delta (spec/commits.md §5), decided with the owner. Default `author`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and a relative keep-at-most implies it. `nobody` is for records that even admins must not drop. `admin` is what role commits use. Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (owner's call; hosts approximate it, notes/sync.md). Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever, and a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart. Fields are immutable: a change would need the blob re-encrypted anyway (commitments are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a trusted node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the host (host stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with owner, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous holder: a fresh actor with its own owning key and device keys, joined via a link or grant; the granting admin may record pseudonym -> person in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Holders write as A in commit form. Caveats: any holder can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a trusted node re-signs holders' edits under its own identity.

## Implementation (osis-perm)
- Input: the node implements `HeldSet` (things, role commits with an edge write per thing, roster snapshots, `created.0`; applied commits only, pending ones not) and adapts headers into `types` records (edge ops with their `roles.0` dots, frontiers resolved from links, rosters and ledgers). perm parses no bytes, holds no state, depends on osis-base only. `created.0` that does not hash to its tid is ignored.
- `Timeline::evaluate` is the from-scratch walk (`walk.rs`); queries take `At` (state before a point, edges alive at a ts; `At::END` = current state at the end of time, where re-grant is judged): `roster`, `role`, `invite`, `class`, `standing`, `applied`, `dropped` (with the dropping demotion's point), `epoch_start`, `demotions`, `delta_valid` (layer 2), `roster_state` (production), `certificates`/`write_certificates`/`certificate_set` and `verify` (§4), `may_purge`, `may_rotate`, `has_standing`/`resolve` over a node-supplied `MoveIndex` (§7), `demotion_scope` (what a demotion's frontier must cover; the node fills counters from its receipt record).
- `Timelines` (incremental): components of things joined by edges, authors, ownership and snapshot rosters, each evaluated from scratch and cached by its exact inputs; `changed()` lists the things whose component the last update evaluated (plus `update_touched` below; the node re-judges only deltas on those, plus commits whose void, required-role or overreach inputs changed; everything after a rebuild at open; a debug assertion checks the rest is unchanged). A component that only gained role commits continues its walk (`Timeline::extend`: same things, `created.0`, snapshots and nodes, and if epoch starts ever changed no role cycle through a snapshotted thing): the final walk rolls back to the earliest new commit p and goes on; else from scratch. D is kept in the order the final round's walks found it (`Walked::found`, saved in the walk cache): the drops found before the first one found by a write at or after p are found again, in that order, by an evaluation from scratch (every walk up to them saw only items before p, and each walk under a prefix of D finds nothing before the next drop's point), so they stay; the rest are forgotten and the walk rolls back to the first write they dropped too (the final walk's prefix there is the walk under the kept drops). This replaced a fallback to from scratch whenever any restart had reached p. Fast path (`Timelines::append`, `Timeline::append`): when every touched thing is in a component, its `created.0` and snapshots unchanged, and it only gained commits whose author, holders and targets are in that component or are new nodes (nothing held of them but a key actor's `created.0`, in no component or alone in one, above the root: they join it), the component is neither re-partitioned nor gathered again (a commit is recorded under every thing it writes, touched or not): the timeline keeps its `Input` (with a node-form range index per (node, thing) so a void, spec/commits.md §4, is caught: an overlap declines) and its walk items. A new node can join because nothing it reaches is held yet (no edge of it as holder, owns nothing), so no earlier audit met it (`Input::may_be_node`). New commits go in in timeline order; each is placed without walking again where exact (`Walked::insert`), else the walk resumes from it. Declined (resume from it): a drop of D found at or after it (found by an earlier walk of the round, whose state there is not kept, so whether it changes what that walk found cannot be judged from the final walk), a later item writing an edge it sets (that write's restore reads the new value and the difference runs along the edge's later writes), the epoch start of a thing it writes, two of its ops on one edge, and its own audit dropping something new (D grows: the walk restarts at that write anyway). Otherwise the walk with it is the walk without it plus its own effects, provided every later item that may read it does the same with it as without it. Which may read it (static, over `Input::ever`): with (M, T) its edges, roles change only for what reaches some M at any time (A) on what some T reaches (F), and only up to the widest role among the edges' values before and after, since every path through them is that narrow; so classes change only through an admin value or an invite (on the edges or on an `ever` holder in F), demotion thresholds only through write or more; reaches change regardless. A later item may read it by an author in A judged on or for something in F (when classes may change); applied explicit on (m, t), by m in F (its author's kept standing reads the reach back from m), and when roles may change by t in A (reach forward), a new node reaching m, or m reached from A with t reaching into F (an audit of a node of A on a thing of F); a later fall of its author on a target it applies on (that audit reads it); and, where its author's first held write on a target moves to its point, an explicit write after it up to the old first write whose holder the author may reach and whose target may reach the target (falls are recorded only after a first write, so these were not; the top of the target's owner chain never falls there). With none, its changes, undo entries (`by_author_target` in walk order) and mark are spliced in directly (`place_plain`). Else (`place_shadowed`) a shadow `Pass` (`Pass::shadow`: the edge state at its place, its edges' records copied from the end state, which is theirs there; audits also read the walk's own write records before their point, `outer`) walks it, then follows the history to each such item and walks it again: its edges' records before it come from its undo entries (the first entry of each kind per edge holds the value before; an item reads no record it does not log), the cached roles are kept as `change` keeps them and restored after each item. Its effects (history, undo entries, applied records, demotions and falls; the last two by key from the entries at its point, and compared regardless of order within an item) are compared with what the walk recorded there (`Walked::recorded`); equal for all, its own effects are spliced in (the log rebuilt once) and the falls the moved first write brings are put before the recorded ones (none was recorded up to the old first write) with their undo entries at the end of their items. An item of the A-audit kind alone is first checked cheaply: when, with and without the new edges, no node of A reaches its holder or its target reaches nothing of F (a standing there reads roles only on what its owner chain and holders reach, all in F if any is), it cannot read it and is skipped. A re-judged item costs about 0.5 ms at 10^4 (they are the costly items: team-edge audits of many nodes), so past an eighth of a long rest (512 items or more) the write re-walks instead (`SHADOW_SHARE`, a cost choice; debug builds can force either path per thread, `force_shadow_guard`, and a test runs both on the same arrivals); figures in issues/perm-eval-cost.md. When an item does otherwise or drops something new, the walk is exact up to it: the commit's effects are spliced in and the walk goes on from that item (`Placement::From`), not from the commit. Debug builds compare every shadow placement, every `From` continuation and every joining `extend` (below) with a from-scratch walk on inputs up to 400 commits and snapshots (`Walked::check_scratch`: history, applied, D and its found order, demotions, falls, edges, edge and write records, marks and undo entries per item). Then the end state holds each edge's state at its place (nothing later writes it), later kept states shifted and given the new edges (Walk cost), `first_held` kept before it. The random late-arrival test (`append_adversarial_*`, now with two nodes only some writes name) has 3000 samples on three seeds. `append_shapes_*` adds owner chains, nested teams, `until` on every role, invites of every level, two-op commits, batched arrivals and restarts from saved walks, and counts placements. A record can grow under its commit ID (a snapshot's `tenures.0` part, a commit's edge writes, arriving late): `append`, a cached component and `extend` compare held records with the walked ones by content (frontiers by size, as the saved-walk tag), not by ID alone (`Input::holds_commit`, voided records kept for it). Checkpoints and `first_held` carry by the history prefix the resumed walk reports as shared (`Outcome::common`: `rollback` moves the old changes it drops aside, `finish` compares them), not by copying and comparing the whole history. Equal to one evaluation (random and timeline-order arrivals incl. snapshot-model histories, 2000 samples, dropped points and roles before every applied write compared). Point queries read an edge state kept every 32 history changes (`checkpoints`; `Edges` shares its per-thing maps between clones until written, so a kept state costs O(things), not O(edges); `Arc`-shared with the timeline `extend` makes, kept up to the first history change that differs) through an overlay of the changes since (`EdgesAt`, `View::at`: no copy); `delta_valid`, `first_held` and roles at `At::END` are memoized per timeline, and `extend` carries `first_held` answers found before the first changed history change. `first_held` (re-grant's first tenure) replays the node's roles over the history: a change of an edge out of something the node does not reach is skipped, a wider one raises in place (`roles_raised`), and only a narrowed edge that may have carried a role or an expiry searches again; debug builds compare it with a search at every change (`regrant_replay_equals_search`). A static filter (changes on edges between things on some path of the union of all edge states) was tried first: in the org bench every holder reaches nearly everything through teams, so it filtered little.
- `update_touched(held, touched)` re-partitions only the components of the touched things and those newly linked to them (equal to `update`, tested by `incremental_equals_from_scratch` in both modes) and returns `Changed`: components evaluated anew, and for those whose walk only went on or that only gained new leaves (`created.0` of things nothing else names) the things touched. New leaves alone (only their `created.0` names them; their owner's component gained no commits in the update; each above its root) skip the re-partition too: `Timelines::append` hands them to `Timeline::add_leaves`, which does what `extend` would (owner links, `alias_leaves` at the log's end, `first_held` kept as `extend` keeps it, other memos dropped) without gathering the held set: a commit creating things under a big group cost the whole component's re-gather before (0.13 ms per thing already in it, per commit). `creation_fast_equals_*` compares it with the general path (`Timelines::set_general_only`) over creation-heavy arrivals: `Changed` (the general path may name more when components merge), from-scratch results, and that saved walks sit only under roots (a root moved by a leaf is retired; so is a root whose `extend` failed, which used to leak its old walk). The walk records demotions only on the things it reached, so a new leaf takes its owner's (`Walked::alias_leaves`, in `Timeline::extend` before any commit resume: the owner's demotion vectors copied top-down, so chains of new leaves work, an `Undo::Demotion((x, leaf))` after each `Undo::Demotion((x, owner))` in the undo log, `marks` remapped; one linear pass, no re-walk). A thing an earlier write names whose `created.0` arrives late (a new owner link), every thing below it, and a new node (authors and holders of new commits, a key actor's `created.0`) join the same way (`Timeline::joined`): before the first item naming any of them (author, holder, target, snapshot thing, roster or ledger holder, ledger key node) the walk is the same but for the demotions on those things, which have no edges there, so they take their owner's recorded before that item (`alias_leaves` with a log cut; those recorded on them after it are forgotten, the walk goes on before them), and a new node owns only such things, so it reaches nothing walked there; the walk then goes on from that item (or the first new commit), D kept by the found-order rule. Declined (evaluated): an owner link gone, a node gone that is not now owned, a new node owning a thing walked before, one of them in an epoch start's roster (from the start), other snapshots, a role cycle after epoch starts changed. `first_held` answers on those things are forgotten, others kept only before that point (a role through the new link can differ from there, its history changed or not). `update_region` continues any cached component whose things, commits and `created.0` records are subsets of the new one's (the one with most commits), and reports the things whose `created.0` arrived as extended. Oracle argument: in a from-scratch walk a leaf has no edges, so every node's role on it is its role on its owner at every point (`roles_from` relaxes owned things at the owner's level), it is reachable only through its owner, and so its demotion records equal its owner's for every node other than the leaf itself; its class differs (depth cap, invite) but demotion records read roles only. Was order-dependent validity (a holder offline through a revoke took the item as a leaf after the demotion and kept no demotion on it); a re-walk from the first demotion fixed that first but cost 0.4-1.9 s per new thing under a much-demoted team (now about 40 ms, as before); the node re-judges below those only (notes/node.md, Validity).
- Saved walks (`cache.rs`; the node's `node/walks` index table, notes/node.md Open): `Timelines::to_save(salt, min, all)` encodes a component's whole walk (`Walked` with undo log and marks, D in the order it was found, epoch starts, passes, `reach`; format 3) under its root (first thing), with its `Inputs` (things, commit and snapshot IDs, `created.0` tids); `update_touched_cached` restores a component with no timeline in memory from a walk saved under any of its things (root first: a thing with a smaller tid joining moves the root) whose inputs are a subset of its own (things, commits and `created.0` records), continued as at run time by one `Timeline::extend` (new leaves, things named before their `created.0`, new nodes and commits); else evaluated. Every other walk found under its things is retired (deleted by the next `to_save`): a root that moved before a restart leaves one behind. `to_save` changes nothing; `saved` applies its `SaveDone` once the writes are durable. Unit = BLAKE3 tag ‖ body; the tag covers a format string, the salt (the node's rules tag), the walk's whole input re-gathered from the held set restricted to the saved IDs (owner links, every commit and snapshot field) and the body, so other rules, inputs or damaged bytes are evaluated from scratch, never an error. Frontiers are tagged by their sizes only and referenced in the body by where the input holds them (the commit at the point, or a ledger entry ending there): `HeldSet` documents that a record's frontier is fixed by its commit ID (the node's are inline in the signed header or linked by content hash); hashing their contents cost O(frontier) per save and restore (the bench: 48M IDs, 0.9 s). Tids are indexed (things, then others in first use), commit IDs by their place in the inputs. Saved when a component evaluated or continued has at least `min` commits and grew by a quarter (and `min`) since its walk was saved: amortized O(1) per commit (saving at every commit would about triple a commit's cost at 10^4: a save encodes for about 25 ms and writes 1.5 MB, against about 30 ms for the write itself); a new leaf thing is no growth (restore takes leaves). - Certificates (spec §4): for (n, t), the things on any path that ever existed from n to t (`Input::ever_forward(n)` ∩ `ever_back(t)`: every edge any held write, roster or ledger tenure can set, `Input::ever`, and owner links), every held edge write between two of them, applied or not, and every snapshot of them projected to their holders; closed under authors (a write's author for its target and holder, a snapshot's for its thing). Point-free, so it holds whatever any walk of any round had at any point: a verifier must see every path an earlier walk of the round had (its findings stand: drops are sticky, a write it audited without dropping stays), every demotion of the node on a path gained after its write, and an edge the node left itself (a write lowering it audits from the edge as restored). A dropped demotion is kept because it can still have dropped a write on a projection. The projection oracles (`certificates_project_joint`, `_edges`) check applied, dropped and the author's standing per write, and each node's role on each thing at every write's point from its own certificates (node cards), against the full evaluation, sticky residue skipped; the joint one also compacts one actor at a snapshot of its end roster and ledger, so roster and ledger tenures are covered.

- Readings of §5.1 the code fixes (the models were aligned to them):
  - R demotes X on N when R is an explicit write (applied, not a self-removal or invite grant; or a ledger tenure end with a frontier) on edge (M, T), X reaches M (or is M), N is reachable from T (edges of any role and `until`, owner links), and X's class on N is below its class with the edge restored "as if the holder still held the role": the join (componentwise max, alive) of the edge's values since the last explicit write on it, plus, for a node that lowered it by its own write, that node's values before. A value already expired when written restores nothing. So a gap left by `until` or self-removal is finalized only by the next explicit write on that edge (not by any write concerning X; the per-node "held class" of the joint model cross-wired things and broke compaction neutrality). The models were aligned.
  - A's chain writes: the writer adds the commit IDs of `Timeline::certificates(A, target, R's point)` (role commits and snapshots) to the frontier (`flows/edges.rs`), and a frontier's commit IDs cover node-form writes too (`Frontier::covers`). The walk exempts nothing but R itself.
  - A write of an edge for the target's owner (node or actor) is no write.
  - Self-removal: lowers the edge in every component, author admin of the holder, and either the holder is the author or the author has no owner-chain or edge-admin authority on the target (spec §2, decided at review: removing one's group from a doc one also owns is an explicit demotion that audits the group's admins); a redemption's (author is the holder, holds only an invite, commit has another op) is attributed `Invite(level)`.
  - Epoch starts (`drive` argues termination; spec §6 states the rounds as an algorithm): every snapshot is judged at its position like an owner-chain edge write (`candidates`, audited and droppable like one), whether or not it is its thing's start and even when ordered before the start; only a round whose walk has settled D chooses (each thing's newest applied snapshot); D is rebuilt per round. Earlier snapshots are judged (not ignored like earlier edge writes) so a thing's choice never depends on its own current start: otherwise an older snapshot's drop would be found only once it is the start, and the rounds could oscillate even without cycles. Unless owner-chain authority on a snapshotted thing may come through the thing itself (`Input::cyclic`: owners and holders holding an admin edge at any time; an invite of admin needs an admin edge), the rounds reach the unique fixed point by round T+1 (T snapshotted things) from any starts, which lets `extend` go on from the old starts. With such a cycle a start can withdraw its own author's authority: if round T+1 since the last restart has not settled, the snapshots that are a start in exactly one of its starts and the next are excluded (never lifted, at least one) and the rounds restart from none, so at most snapshots+1 restarts of at most T+1 rounds; no pass cap. History: a chosen start found inapplicable mid-walk (D not settled) used to be rejected until a start changed above it, and the rejection stuck when the write that caused it was dropped later (a few in 10^5 snapshot-model histories broke neutrality; `start_after_dropped_write_spec_permissions_6`). The exclusion fires at a round limit rather than on a repeated assignment: no assignment history, and a polynomial bound with no pass cap (between repeats the rounds can run exponentially long in the snapshotted things on a cycle); a repeat is caught anyway, since it means the rounds have not settled. Caveat: with a role cycle, a round sequence that would have settled after round T+1 still gets an exclusion at that limit; deterministic, and reachable only through forged or stale-view snapshots, since honest snapshots do not create cycles.
  - Before its start S, N's edges are virtual writes from S's roster and ledger at their keys (placed just after the commit at that key, whose writes on N S ignores: that commit's writes on other things are judged as in the full history; a two-target self-removal plus grant showed the difference). An entry with a frontier is an explicit demotion by its key's node (exempt and keeping its standing as the author of a real one), audit-only entries included; where the roster edge takes over at that key without starting there (contradictory data), the tenure ends first, then the roster re-grants. What it restores comes from the replay itself (prior values of no-audit ends, the demoter's kept standing), as in the walk. Ledgers written before this rule (a later demotion's frontier carried on a tenure keyed at its end) now read as a demotion by the end's node, which is then exempt: no deployed data, so not migrated.
  - Production (`roster_state`): the previous start's ledger whole, then per holder every write+ tenure ended since (per role level: a promotion ends a write tenure without a frontier); an expiry inside the history ends a tenure at (first ts at `until`, zero tid and zero commit ID), so it orders before every write at that ts as the expiry does in the walk (the holder as node ordered it after same-ts writes of smaller tids); an edge never in force (expired when written) gets `since` = its write's key. Which writes audit, and from what role, comes from the walk (`Change::audited`: an explicit write whose restored edge, the demoter's kept standing included, exceeds the new value): such a write gives the tenure it ends its frontier (empty if none); with no tenure in force it is an audit-only entry (`since` = `until` = its key); auditing from above the role in force splits that tenure. Expired edges stay in the roster with their `until`. The replay equals the walk except: read edges carry no `since` and read-level tenures and audits are not in the ledger (spec keeps it to write+), so invite authority through a read edge on an actor before the snapshot, and a read-level fall's audit, are not preserved (rare). Keys are full points (`ts`, node, commit ID; perm's `Point`, the core `edge_key`): with (`ts`, node) alone, two commits of one node at one ts (one key used from two devices) that demote and re-grant a holder were one key and replayed as no demotion (core/test/tla/roles M3; `same_ts_demote_regrant_replayed_spec_permissions_6`). The commit ID over a per-key sequence: it is intrinsic to the write, so every node computes the same key whatever else it holds, while a sequence would depend on which same-key commits a node held and their order; it costs 32 bytes per key.
  - Frontier coverage: a node-form range is covered when its last counter is (`>= hi - 1`); an empty range (import) only by its commit ID.
- Layer 2 (`content.rs`): re-grant (role at `At::END`) validates writes from the start of the author's first tenure of the required role on the thing ("valid again"; earlier writes stay invalid); else held at the commit's point and no later explicit demotion below the required role; else the newest such demotion's frontier decides (literal: a gap write covered by the newest demotion's frontier is valid). ## Implementation (role flows, osis-engine `flows/` and `rotation/`)
API and engine hooks: notes/node.md (Flows, Rotation). Readings:
- A person actor is created in one commit signed by its fresh recovery key (both creation records, the key's `keys.0`, the person's own secrets boxed to the key and the node, `keys.0` with inbox and deposit seed, the home label's genesis step listing the key by static entry, the node's admin edge); the seed leaves only in the card. Held key actors (`hold_key_actor`) sign in commit form and open their boxes; nothing persists them.
- Pairing is a direct grant (or, for a device already a holder, a re-seal) plus every commit touching the person, its owner and both nodes, as one direct send.
- A plain thing with a current non-owner holder (its only keyset part turned invalid) gets secrets of its own again from each admin node at the end of a complete pass of its secret actor's labels (`Engine::own_secrets_due`, `pass/` `reseal`), the rotation delivered by inbox to the holders it boxes; once per admin and state (the thing is own-keyed after its own rotation), concurrent admins fork. Candidates come from `ix.holder_keys` targets (a scan per label pass, each target once; a measured cost would justify an incremental set). One that cannot be rotated (a holder's `keys.0` not held, an intermediate uncovered) is retried, with a diagnostic, each pass.
- A grant first gives the target, and a plain holder, secrets of their own, runs the cascade on the target (boxing is encrypting under) and boxes every granted role's current epochs. Authority: admin on the target, else an invite grant (no current edge, role and invite at most the effective invite), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own edge or the author's authority on the target comes only through the holder (admin on it); it carries no rotation (the next node that may rotate does) and the leaver drops what it lost. Otherwise it is an explicit demotion with the frontier from the receipt record (as of now, or a backdated time) and the pre-sync choice, carrying the target's rotation of the roles the holder left. A removal of an absent edge (finalizing a used single-use link) resets the holder's dead entries and audits the holder's writes on the target.
- Departures are read from the timeline and from the boxes held at current epochs (scenario tests: the two-hop cascade rotates T then U; a holder re-granted since drops out of the list) and cached per actor (`Core::departures`): cleared by `Core::role_changed` on any role-class state write, timeline update, held-epoch change or key-actor hold/drop, and valid until the next edge `until`, future write or roster snapshot `ts` of the actors walked.
- "Written by a departed party" (`rotation::departures::written_by`, judged inside `osis_keys::covers` through `HeldActors::departed_wrote`, implemented by `rotation::Judge`): at every epoch the covers rule judges, the actor's own and each holder actor's along a chain, so the box-rule verdicts (`verdicts`, `fresh_box_covers`, `holder_covers`, `uncovered`) cannot diverge from it; before, only the actor's own newest epoch was checked, so D could leave holder M after writing M's newest epoch unboxed, and a rotator of A that may not rotate M boxed A's new epoch to it (test `holder_epoch_written_by_departed_spec_crypto_4`; the random cycle test also has D rotate the roles it leaves unboxed, then leave by itself). Such an M is waited for or left out (Role cycles) until its admin rotates it. Unknown introducer at a holder: the same rule as for the actor itself, by whether this node may rotate that holder (a rotator of A that may not rotate M and lacks M's rotation commit, compacted away, judges M's epoch by its boxes: the same residual as a non-rotator at A). The party: M itself, or an author whose role on A now over paths avoiding M (`Timeline::role_avoiding`) is below r. Judged now, with no "reaches M" test: an author that left M (or a second actor it went through) and then M left A still knows the secret, and departures inside a former holder are not collected. Before, any node reaching M counted, so after an owner removed its own tag from a thing no rotation could ever cover it (every owner node reaches the tag): the thing was stuck (was issues/tag-regrant-after-revoke.md; test `regrant_after_tag_removal_spec_crypto_4`). Purpose kept: a holder reaching A only through M cannot rotate on its way out. The verdicts depend on `now` through `role_avoiding` and `may_rotate`, so the departures cache's horizon also takes the next `until` of any edge in the walked actors' timelines (`until_horizon`: an author's path may run outside the walk, an owner chain).
- An epoch's introducing commit (`Core::epoch_intro`, the covers rule's "introduced by a departed party") is the earliest valid commit writing its keyset in `keys.0` (only a rotation does; a box introduces nothing: a grant or re-seal standing in for an unheld rotation named the wrong rotator). Unknown (rotation never held: synced after a compaction, or its `keys.0` body missing again after `uncover`): a node that may rotate the role counts the epoch as written by any departed party whose chain's first actor is the owner or ever held an edge of write and at least that role (`could_rotate`, `Timeline::highest_edge`), so it rotates once (cost: a rotator that joins after `keys.0` was compacted, e.g. a device paired to a person months after a device removal still in the timeline, rotates the actor, and since boxes to it in its groups then no longer name its newest keyset, each of those groups is rotated or stranded for departures inside it: one cascade per such join; deriving the introducer from the snapshot's keyset write dot would avoid it); a non-rotator judges it covering (it could not fix it; gating it would stall its deposits for good, since rotators that know the introducer never rotate). `presumed_boxes` already takes unknown as boxed. It is noted from valid role-commit parts at apply; `load` notes every part, then `rejudge_all` rebuilds an actor's entries (`keys::rebuild_intro`) whenever a `keys.0` part of it flips, so an invalid (backdated) write never introduces an epoch. A dropped `secrets.0` body takes its `boxes_to` notes along (`keys::forget_dropped`: re-derived from the held bodies). A dropped `keys.0` body's epochs stay (`Dropped::intros`, in the record; `rebuild_intro` and `load` note them), so a compactor keeps knowing the rotator (`dropped_rotation_keeps_its_epoch_intro_spec_crypto_4`). A dropped part's `rotation_role` and `grant_overreach` stay too (`Dropped::role`, `overreach`), so re-judging it and a rebuild need no body; `uncover` (never received again) forgets all three. `boxes_to` is noted from held `secrets.0` deltas of any validity (a lookup for `reopen_dependents`). Epochs are persisted whenever they change (`after_join` compares, `observe_state` of `keys.0`, `snapshot_keyed`'s snapshot mark), not only when establishment changes.
- Roster snapshots: the writer splits the replace into a reset-only delta and one delta per edge and per ledger entry (`Fragment::split_entries`, `Resolved::split`); a tenure frontier above `CHUNK_THRESHOLD` becomes a link (`large::chunk_frontiers`; set elements are registers holding the whole tenure, spec/crdt.md §3.2); the writer refuses a ledger above `MAX_LINKED_FRONTIERS`. A receiver (`validity::linked_frontiers`): reads each distinct link once (by content hash; `Core::frontiers` in memory, `n/` records durably, so `load` never depends on the tree blobs), within `MAX_LINKED_FRONTIERS`, only through blobs in the commit's chunk list (else bad input), and waits (`WaitBlobs`) for listed blobs not held, always (a no-wait shortcut once a later epoch start applied made what counts depend on arrival order; residual: a node that fetched the body as its blobs were deleted pends for good, harmless since chunks go only once every listing commit's parts are dropped, a roster snapshot's not before `ROLE_KEEP` after replaced). An applied snapshot whose frontier is neither recorded nor held (store loss) stays out of perm for that thing (diagnostic, `Core::frontier_unknown`) and `roster_snapshot` refuses the thing: never an empty frontier. A holder named in two `roles.0` deltas is bad input. `Engine::certificates` returns parts per (aspect, delta): a snapshot is projected to the deltas naming the chain's holders plus the reset-only ones, so a snapshot naming no chain holder still arrives as an empty-roster epoch start, as perm's `certificate_set` projects it (`project(s, ∅)`); a snapshot that cannot be read here is not placed (diagnostic). node-sync places a copy's linked blobs (header lists, linked frontiers) under the label with it (`place_linked`).
- Contact cards stay in the osis API (`contact_card`): the card is a composition of calls flows already has (a group thing written through the API's placement, its own secrets, a label, certificate placements, a read link) plus the API's local record of the card; a flows call would only move that orchestration below the layer that owns placement and sync.
- Re-seal and registration are pull hooks for node-sync (`reseal_due` at the end of a complete pass, `issue_step` per host head); flows only return deliveries.

- **Import over `MAX_DELTA_BARE` (accepted, owner):** an owner change copies a thing under a new tid with the visible sequence elements and the hidden anchors they reference, without content (spec/permissions.md §7); if one origin's anchor chain needs more than `MAX_DELTA_BARE` (2^18) content-less elements the import cannot fit a delta and `move_thing` fails cleanly (the original is untouched); the remedy is compaction of the origin, which prunes dead chains. Splitting imports or exempting them from the bound was declined (new multi-commit state, or the amplification the bound prevents). ## Snapshots and history (owner, round 13)
A snapshot is trusted for current content only, never for authorship or time (spec/permissions.md §5.2). Was issues/forged-cover.md: a valid writer's snapshot copying another value under the dot of a delta its holders had dropped before others got it showed the original at the holders and the copy elsewhere, for good.
- **Content**: every node follows a valid snapshot's copy, also where it holds the original: where a held delta and a held valid snapshot disagree under one of the delta's dots, the delta counts for nothing there and the valid snapshots' copies join by the copy order (the tie-break between disagreeing snapshots). Nodes holding the same valid snapshots read the same whatever deltas they hold. No worse than the writer writing the value itself; later writes win as usual. Only valid snapshots count, so a reader or a removed writer (frontier not listing the snapshot) changes nothing; a snapshot turning invalid gives the held original back. Mechanics: notes/node.md (Valid snapshot copies govern).
- **History**: authors and times come only from verified commits held here (notes/api.md Attribution); content known only through a snapshot has none. The API audit found nothing attributing through snapshots: the commit query and `created`/`changed` read held headers only (snapshots are no change), a watch names the commit applied (a snapshot correcting a held original is reported as the snapshot, its author and ID), undo and revert act on held commits.
- **Detection**: a node holding the original reports each misstating valid snapshot (`DiagnosticKind::Misstated`, from the rebuild that applies it, deduped; not for value-less copies alone, which an honest snapshot taken after a purge not yet seen here carries).
- **Residuals**: a copy misstating a delta this node dropped cannot be compared (the body is gone): it joins by the copy order with what the state kept of the original (a valued copy beats a value-less one), so where the original wins that order a node without the residue reads otherwise until both hold a snapshot carrying the original (a covered drop's cover does; a drop for keep bounds leaves only the residue); a snapshot turning invalid leaves its copies under dots of deltas whose cover was dropped for its bounds (the state alone holds those writes); a move imports the held original, not a misstating snapshot's copy (`moves::copies_held`: such a snapshot is no import carrier), so the copy may differ from the old thing alike everywhere; text: issues/forged-creation-copies.md.

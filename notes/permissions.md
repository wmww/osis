# Permissions, sharing, hand-over, revocation
> Summary: Three concepts (actor, membership, ownership). Sharing inside the owner's tree is edges on things plus labeled membership commits as certificates (2026-10-11); hand-over (new tid, aliases) only moves a thing out of its tree (2026-09-29, spec 2026-10-15); content by a revoked member counts iff a writer received it before the revoke time (receipt-time rule, 2026-09-29; witnesses 2026-10-15); membership writes are judged by the demoter-frontier timeline (2026-10-16, replaced a looping rule; agent's call); roster snapshots by the owner chain bound membership history (owner's design 2026-10-16); share links are invites made of a link actor and a link key (2026-10-16). Review 2026-10-16b (agent's calls, see Open): roster snapshots are projected per edge so chain certificates never carry rosters (also found by the sync review); a hand-over's new identity is the new owner's by construction, the record's validity gates only the alias and inherited history; link `until` and single-use need a sharer-side finalizing removal; recovery card format; the app-visible roster is the timeline's.

## Model (2026-09-29; proposal unless marked decided)
Owner's direction: a small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors must be managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in.

Three concepts:
- **Actor**: a thing with role secrets (and a signing key for key actors). Any thing becomes one when it needs members of its own: nodes, people, agents, teams, shared documents/chats, a single shared note. Identity is the tid, so keys can rotate. A node is a leaf actor whose private key never leaves the device. Every actor except a node is synced as a group of itself, its home label, so its membership-class commits always have a label; the home closure holds nothing implicitly (notes/sync.md, Label discovery; owner 2026-10-16).
- **Membership**: edge member actor -> thing with a role (read < write < admin), written by an admin of the target (for a plain thing: an admin of its owner). Target an actor: rights on everything it owns. Target a plain thing: rights on that thing only. Actors can be members of actors; effective role is the minimum along the chain. Nesting and "node acts for person" are the same edge.
- **Ownership**: every thing has exactly one owner actor, fixed by its tid (self-certifying tids, notes/data-model.md); rights on the thing are rights in its owner plus the edges written on the thing itself. A shared doc is one actor owning all its things, so access changes in one place.

Vocabulary: read, write (editor) and admin are roles. Admin = write + change membership + purge history + hand over things the actor owns (hand-over needs admin of the *owner*; an edge-admin of a plain thing changes its membership and may purge, nothing more). Owner is not a role but which actor a thing belongs to. UX vocabulary stays the familiar one: owner, admins, editors, viewers. The roster an app reads from `/members` is the membership timeline's roster (Validity definition, layer 1), not the raw CRDT join of the stored deltas, which can disagree with it (a removal that never saw a concurrent grant's dot leaves the grant live in the join, while the timeline orders them by time); the stored encoding is only the carrier of the membership writes.

Top of an actor = its owner (decided 2026-09-29): an actor is a thing, so it has an owner actor like any other thing.
- An actor's owner is implicitly its admin, and the only one its other admins cannot remove.
- The chain ends at a key actor (node or recovery key), which owns itself; its tid commits to its public key.
- Other admins are equals: any can add or remove members, including each other. A hostile admin is out of scope like a hostile writer; the owner is the recourse. Rejected: seniority ranking of admins (unintuitive, leaks into UX).
- Mutual removal (2026-10-15, follows from the membership timeline): if two admins remove each other, the removal with the earlier timestamp applies and the other is a write by an already-removed admin, which does not apply. Earlier note said both apply; that predates the timeline.
- Conflicts between nodes acting for the same actor are ordinary merges. Only a hostile node (stolen device) matters, and that is a removal from the person actor, which its owner can always do.
- So a person actor's owner should be a recovery key kept offline, with devices as admins. App policy, not protocol: a recovery key is just another key actor. Recovery of a lost owning key is out of scope (product decision, owner 2026-10-12). Nothing precludes adding it later: the hand-over record's authorization is an enum (admin-of-owner signature today), extensible like every wire struct; social recovery of a key actor's secret is app-level. Losing the owning key leaves the actor functional (its admins keep working and can remove each other) but unable to be handed over, roster-snapshotted or to settle an admin war.
- **Recovery card** (review 2026-10-16b): the seed alone cannot find the person actor (its tid, labels and servers are not derivable), so the card is seed + person tid + home label + server, the same shape as a link. Under download gating (notes/sync.md Open) the seed also derives a bootstrap label's read secret, like a link's K label, under which the devices keep certificate copies of the person's current `/secrets`, `/label` and `/created` commits (a delivery blob would need a label the key already reads, which is this one), so a fresh device holding only the card can open its owner's box and derive the home label's keys. The recovery key has a KEM key and a `/secrets` box (member = owner, role admin) for exactly this case; its `/keys` commit rides with the chain certificates like any key actor's.
- Any key actor used from more than one device (recovery key, link key) signs with commit-ID dots (notes/crdt-sync.md), since per-device counters under one key collide. Membership writes are rare, so the cost is nil.
- A role on an actor covers both editing the actor thing's own data and acting as it (confirmed 2026-10-15): the only aspects where the two would differ are `/members`, `/secrets`, `/handover`, which are admin-gated by aspect rule regardless of role. Split only if an example ever needs writers who may act as the actor but not edit its profile.

## Keys
Mechanism splits by direction (decided):
- **Write**: node signature plus membership chain. A node always signs with its own key. Sharing an actor's signing key is rejected as the normal way to share: it erases which member wrote (the revocation rule needs the author) and makes every removal a key rotation. It is the deliberate tool for anonymous writing (below).
- **Read**: key wrapping. An actor has one secret per role (read, write, admin; proposal 2026-10-11), each wrapped to the members holding that role or higher, every epoch (a later writer needs old write epochs to derive delete tokens for old `purge`-class entries; a later reader needs old read epochs for old wraps). Each blob's own key is wrapped under the read secret of every label it sits under (notes/sync.md). Mechanism (notes/crypto.md, 2026-10-16): a role secret is sealed to a member with a hybrid post-quantum box under the member's per-role KEM public key (published in `/keys`), one box per (member, role); older epochs sit in symmetric history boxes under each epoch's secret. Label operation keys (upload, soft-retire, hard-delete) derive from the role secrets, so blind nodes distinguish roles by signature; those are shared role keys, not authorship. Demotion or removal rotates the affected secrets lazily (old content was already readable), but label keys are re-registered eagerly (notes/sync.md).
- Removed node erases (decided 2026-10-16, like `purge`): an honest node that learns it lost read access to an actor drops those role secrets and every local unit it can no longer read by another path (via membership elsewhere, or as owner of its own writes), so a later compromise of that device exposes nothing more. Not enforceable against a hostile node; that is the "could have copied" limit. If the removal is later undone (re-grant, a cancelled backdated revoke), the node re-syncs: cost only, the content lives at other members and blind nodes.
- Role secrets of a plain thing: by default derived by KDF from the owner's secrets and the tid, so nothing is stored. Once a thing has a non-owner member it gets explicit random secrets, wrapped to the owner and each member, so owner rotation does not cascade.
- Keyed hashes use a per-thing dedup secret derived from the creation nonce, so every reader hashes identically and sharing changes nothing (notes/data-model.md).
- **Nodes as things** (agent's call 2026-10-16, replaces the self-edge proposal): a node owns itself and grants nobody anything. Its `/keys`, `/node` and `/reach` commits (node card; commits of their own, touching nothing else) are published like chain certificates: a node puts them under every label it tracks, readers included (upload is a reader right), on first sync of that label and on change. So exactly the readers of L see the nodes that sync L, never a roster, and no edge, devices group or contact-visibility rule is needed. The person's own devices see it via the person's home label, which every member node tracks. `/reach` (dialable key, relays, addresses) is the exception: by default omitted under labels with link members (bearer or public readers) and narrowable by the app, since it carries IPs. Enrollment is a link redeem or a pairing flow: the new device shows its tid and `/keys`, an existing device grants and seals; the owner's key grants the first device. Rejected: a self-edge granting the person admin (covers only own devices) and a devices group readable by contacts (leaks the device roster, misses read-only co-members without the card).
- Grant/revoke are ordinary membership writes to the actor thing, judged by the membership timeline (Validity definition, layer 1).
- Check 2026-10-15 of per-role secrets against the patterns: sharing (explicit secrets on N, read and write wrapped to the grantee, admin only to the owner), demotion write -> read (rotate the write secret only, re-register soft-retire; read untouched), removal, and the mixed-owner chat (participants hold the chat's read secret, so upload only; chat admins hold write and admin) all work without extra machinery. Rotation by several admins is idempotent since keys are KDF-derived from the one new secret the revoker wrapped.
- Nesting cost (quantified 2026-10-15, accepted): removing a member rotates the secrets of every actor whose secret it could open, that is the actor it left and every actor above it in the membership graph (their secrets are wrapped under the lower actor's secret). Per rotated actor: one sealed box (about 1.2 KB, notes/crypto.md) per direct member per rotated role, one re-registration per label at each blind node, no content re-encryption. A company of 50 teams with 10 labels on 3 servers costs 50 boxes and 30 signed messages per person removal. Inherent to lazy rotation (whoever held a secret and leaves forces a new one), so no mitigation.

## Sharing within the owner's tree (decided 2026-10-11)
Sharing never changes a tid.
- Edges on plain things. Bob gets write on note N owned by Alice's actor A: an admin of A writes "Bob: write" on N. Verification chain: Bob's node -> Bob -> edge on N -> A owns N (tid).
- One note: edge on N, explicit secrets on N, N is its own label. A set: a group thing with members and secrets (the "shared with Bob" folder), made a read member of each thing by one edge per thing, written in one commit; its label then receives those things' blobs. A set meant to be shared as a unit is better created under a common owner (shared-owner pattern).
- Group membership grants no rights (2026-10-15, from the rejected "edge on a group extends to its contents"): an honest uploader wraps a thing's blobs for a label only if the label's actor may read the thing (notes/sync.md, Labeling). Groups stay an app tool; a group that should read its contents is made a member of them. Checked 2026-10-15 against the patterns: shared folder (folder actor is a read member of each thing), own folder without secrets (label actor is the owner, who may read anything shared to it), chat (chat actor is a read member of each participant) all label correctly; a thing dropped into a shared folder without an edge is silently not shared, which is the intended failure, and an "add to shared folder" helper writes both. Cost: one membership check per (thing, label) at upload, cached until the label actor's membership, the thing's edges or its owner chain change.
- Sharing history means adding wraps, never re-encrypting.
- Why no tid change: the double-spend harm of a transfer is the former owner pulling the thing back. Moving a thing to an actor the owner owns has no such harm, so it is an ordinary write on the thing; the edge is the additive form of that write. Hand-over with a new tid remains only for moving a thing out of its owner's tree, which should be rare.
- Rejected: an actor per thing at creation (usage rule, doubles the thing count); a membership edge on a group thing extending to its contents; a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set; an edge on N travels with N); per-thing derived content keys plus an encrypted hint per blob (about 24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Verifying writes without reading membership (decided 2026-10-11)
Problem: checking a write on N needs the current membership of N's owner and every actor above it up to the key actor, and of the author's own actors below; only members can read those aspects. So a grantee or a chat reader could neither verify writes nor learn of revocations.

Resolution: the signed membership commits are the certificates; they travel under the labels where they are needed. No verify role, no certificate format, no extra key.
- Membership-class aspects are `/members`, `/secrets`, `/keys`, `/handover`, `/label`; a commit touching one touches only these (a grant carries its boxes), and attestations (below) are commits of their own, so such a commit can sit under extra labels without exposing anything else. They never expire and are never purged; they retire only through a roster snapshot of their thing (Roster snapshots, below), except `/handover` commits (the record chain, kept forever) and `/secrets`/`/keys` deltas, which the partial-purge rewrite may drop (notes/sync.md). Internal rule; apps never see it.
- When a node uploads under label L it also puts the membership commits proving its own chain under L: for each thing in the chain its `/created` record, its current epoch start (the roster snapshot, projected to the entries the chain needs, Roster snapshots below) and the later writes that establish the edge, from its edge into its person actor up to the key actor, plus its own node card (Nodes as things, above). Each is a certificate blob, a fresh encryption per label (notes/sync.md), so the cost is a few small blobs once per (node, label); sharing one blob across labels would link every label a node syncs at the blind node (sync review 2026-10-16).
- Revokes, roster snapshots, hand-over records and attestations follow the same rule: any member who syncs L and holds one about an author seen under L adds the wrap, together with the certificates of that commit's own author chain and the current `/keys` commit of each actor in a relayed chain, since the verifier may hold none of them (review 2026-10-16). A grant also carries the target's current `/label` commit, so the grantee learns where to sync (notes/sync.md, Label discovery).
- Chain checks need no secrets: each link is a node signature plus a tid committing to its owner, ending at a key actor whose tid commits to its public key.
- A commit whose author chain has not arrived is held unverified until it does; same pending state as an out-of-order delta. A commit is valid only if its author is authorized on every thing it touches.

Leaks: a reader of L learns the chain of every author under L (one edge and the roster size per level, plus the `/created` record and so the dedup secret of each thing on it, which lets it check delta hashes of that thing's headers if it ever sees them) and the witness nodes that publish attestations about them, never rosters. Author identity is inherent anyway (every write is node-signed).

Accepted limits: revocation reach is eventual (if no member of the revoking actor syncs L again, L's readers keep accepting the revoked node until one does, then un-merge); chain depth equals nesting depth (node -> person -> recovery key is two blobs, each org level adds one).

Rejected: a "verify" role handed out transitively with every edge (an outside collaborator learns the team's and company's full membership; every rotation above re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 200-byte floor).

## Hand-over (accepted 2026-09-29; spec decided 2026-10-15, agent's call per owner)
Decided: ownership is immutable, since a former owner can always sign a second, competing transfer (double-spend, no fix without consensus), so a hand-over must never be able to harm what the new owner holds. Hand-over must be cheap and keep history, so not copy/re-create. Guidance (owner): hand over only to move a thing out of its owner's tree.

### Records and names
- A thing's **record chain**: creation record, then hand-over records. A hand-over record = (hash of the record it follows, new owner tid, authorization), where authorization is an enum whose only case today is a signature by an admin of the owner the followed record names. No timestamps in the record; the carrying commit has one. It is a membership write: own commit, stored on the thing (`/handover`), labeled like a revoke (above).
- **What travels with it** (review 2026-10-16b, was unstated): the new owner's members can read nothing of the thing until they hold its secrets and know where its blobs are. So the hand-over commit is also a grant: the signer gives the thing explicit secrets if it only had derived ones, seals them to the new owner (boxes per role to the new owner's role KEM keys, as for any member; old epochs follow through the history boxes), makes the thing its own label (or puts it in a group whose secrets the new owner can open) and uploads its blobs and chain certificates there, writes `/label`, and delivers the commit like a grant (notes/sync.md Open, Bootstrap): a certificate copy under the new owner's home label if the signer reads it, else a delivery blob under the new owner's contact label. For an actor, its home label and explicit secrets already exist; only the boxes to the new owner are added. The new owner then rotates every role secret and re-registers label keys, as for any removal.
- **Permanent tid** after a hand-over H: hash(previous tid, H), "the thing as handed to X". X owns it immutably; a competing hand-over hashes to a different tid and cannot touch it.
- **Fork**: a record with two or more successors. Each branch continues under its own permanent tid. The old tid is an **alias**.
- **Derived identities** (replaces "children untouched / children derived on fork"): a thing K whose owner chain passes through a handed-over thing F keeps its tid and its data; its owner resolves through F's chain. When F forks, K exists in every branch with diverging content, so K's identity in branch H_i is hash(K, H_i), applied recursively (a fork above P's branch adds another layer to everything under it). One rule for own hand-overs and ancestor forks: new identity = hash(current identity, record). Without a fork nothing below F is renamed: a key rotation renames only the rotated thing.
- **Index**: for every hand-over record it knows, a node inserts hash(t, H) -> (t, H) for every tracked thing t whose current identity resolves through the handed-over thing; the local owner table makes the enumeration cheap. Derived tids are 120-bit hashes like any tid, so without the index a receiver could not invert one. Cost O(tracked things under F) per record, local only. A derived tid whose base the node does not track dangles like any unknown tid.

### Resolution (decided 2026-10-15, replaces reference rewriting)
- Alias rule: a tid resolves one step while the record it names has exactly one known *valid* successor (an invalid record is not a successor and makes no fork; it only names a fresh, empty thing); repeat to the end of the chain. Monotone: once a node knows a second successor the alias dangles at that node for good. Nodes with the same records resolve alike.
- **Honest fork**: if every successor of a record names the same new owner (two admins, or two devices of one user, handed over concurrently), the alias resolves to the successor with the lowest record hash; there is no double-spend harm because the owner is the same. Grinding does not apply since the competing records are the same owner's.
- A dangling alias in a value held by thing R resolves, in order: (1) **standing**: if R's owner chain holds rights in exactly one branch (owns a thing in it, or is a member through an edge that exists only there, i.e. written after the fork by that branch's admins), that branch; members and edges that predate the fork exist in every branch and give no standing; (2) the reader's **follow choice**, an aspect on the person actor mapping fork record -> chosen successor, default first seen, written by the device that first meets the fork (ordinary write, so a user's devices converge; the fork diagnostic lets an app offer a choice but nothing depends on it); (3) dangle. Rule 2 is the per-node first-seen that was rejected as the primary rule, kept only as a fallback behind the deterministic one, and made convergent across a user's devices by living in synced state.
- Resolution is a **read-time view**, never a rewrite of stored data (replaces the 2026-09-29 decision to rewrite): the API returns resolved tids and resolved `osis://` links in markdown, listeners under old tids keep firing, and `set_aspect` diffs against the resolved view so a read-modify-write of another field does not touch the reference. Why no rewriting: an autonomous register rewrite is a no-op write with a fresh timestamp that beats a concurrent real edit of the same field under LWW; an autonomous text splice done by two devices concurrently duplicates the link; and aliases are permanent anyway, so rewriting bought nothing but pinning, which rules 1 and 2 provide in a few bytes instead of a commit per referencing thing. Apps that want a reference pinned write it explicitly. The backlink index (owner's idea: which things refer to which, over typed tids and markdown links) indexes resolved tids and re-resolves the affected subtree on a fork.
- Writes: a commit names things by the identity the writer's node resolved to, bare or derived. A bare tid applies in every branch where the author's chain is valid (members who predate the fork are valid in both); a derived tid applies only in that branch. A node keeps the branches it follows and never stores another unless something it tracks refers to it.

### What the record's validity gates (review 2026-10-16b)
The record H is a membership write by a device D of the former owner A, so A's timeline judges it: an ex-device's hand-over is dropped like any backdated grant unless the removal's frontier covers it, which is what stops a stolen device from handing A's things out forever. The same mechanism lets A's chain *disown* a legitimate hand-over later by removing D with a backdated time and a frontier that omits H. With no clock and no consensus nothing can tell the two apart (A's key actor is sovereign over A-side history; outside testimony cannot be ordered against a backdated claim), so instead the new owner's holdings are made independent of H's validity:
- The new identity hash(T, H) is **owned by X by construction**: its tid commits to a record naming X, exactly like a creation record, so writes by X's chain under it verify without any A-side check. Anyone can mint such a tid, as anyone can create a thing; a forged record buys an empty thing.
- H's validity (D's authority at H's time by A's timeline) gates only two things: the **alias** T -> hash(T, H), and the **inheritance** of T's pre-hand-over history into the new identity's state.
- X **snapshots on acceptance**: a content snapshot by X's writer carries the inherited elements on X's authority (Roster snapshots, Content), so from then on A can break only the alias, which is the fork power it has anyway. Nodes that never see the disowning removal and nodes that do agree on content once the snapshot is held; they differ on the alias, as in any fork.
- So the former owner's full power is: fork, or disown; both break outside links for readers without standing and nothing else. Tension 1 in notes/constraints.md says so.

### Hand-over as a revocation (gap found and closed 2026-10-15)
A hand-over removes the former owner's members from the thing, so it is a revoke under the receipt-time rule at the hand-over commit's timestamp. Without this the inherited history would be invalid: the new owner's members witnessed nothing before they owned it. So:
- The signing node publishes its frontier attestation for every aspect it holds of the thing (and, for an actor, of everything under it) alongside the hand-over commit, like any revoke. Everything that node held is valid; writes by the former owner's other members that it had not received need a witness among the new owner's members, which usually means they are invalid. Hand over from an up-to-date node; a cooperative transfer can re-grant the old members on the new side for a while instead. The acceptance snapshot above then makes the inherited elements X's own.
- An actor's own members (edges on the actor thing) are untouched by its hand-over and stay authorized; only rights that came through the former owner end.
- Inherited admins (decided; generalized 2026-10-16b from actors to every handed-over thing): a hand-over strips the explicit admin edges on the handed-over thing; readers and writers carry over. Otherwise the former owner can leave planted admins who hold every secret, re-add its members or (on an actor) hand its things back one by one, and can only be fought by the new owner racing a backdated revoke. The new owner re-adds admins it trusts. Secrets: the former owner's side keeps every epoch it held, so the new owner rotates all role secrets and re-registers label keys eagerly, as for any removal; until it syncs with a server the former owner keeps that server's label keys, so a received thing is also put under the new owner's own labels (entry cost only, the blobs are already there).

### Walk-through (2026-10-15)
- Split at birth (A hands T to X and to Y, shows each to its target): each side resolves T to its branch until it learns the other record; writes by X's members name T bare and are unauthorized in Y's branch, so the branches never mix; references from inside either branch resolve by standing; outsiders who could not read T lose a tid they could not use; readers added before the hand-over have standing in both branches, so they fall to their follow choice. No loud report, a fork is something a peer can cause; the diagnostics event is informational (notes/api.md).
- Late fork (A publishes a second record months after a clean hand-over): every reference still names T, since nothing is rewritten; standing resolves everything inside X's branch, the follow choice (first seen, which is X for everyone who used the thing) resolves the rest. The former owner breaks links only for people who never had access.
- Chains: hand-overs compose as hash layers; a fork anywhere in the chain is handled at that level; cycles are impossible because every step is a fresh hash.
- Repeated forks by one former owner: n branches, n index entries per tracked thing, diagnostics deduped per (kind, tid).
- Honest concurrent hand-over to one owner: resolved by the lowest-hash rule. To two different owners: a real fork, both branches legitimate, nothing merges them; the app may hand one branch to the other owner, who then holds two things.
- Concurrent hand-over of a child by a member valid in only one branch: valid there only; the child keeps its tid in the other branch.
- Former owner's power: break outside links that still use the old tid, for readers without standing, by forking or by disowning (above). Cannot read new content, write, take over or destroy; can drop inherited history only at nodes that lack the acceptance snapshot.
- Rotating the key at the end of a person's chain: hand over the key actor itself (its record names the new key actor as owner, one more chain link per rotation), not the person actor; handing over the person renames it in every `/members` map that lists it, which costs resolution on every chain check.
- Cost: a derived-tid index per hand-over, edge cases from a thing having several names. Unchanged guidance: hand over only to move a thing out of its owner's tree.
- Rejected: copy/re-create (loses history, O(size)); fork deletes the thing (kill switch for every former owner); picking a winner; first-seen-wins per node as the primary rule (no convergence); finality by members' receipt time (no neutral witness when a thing has no members); references always tagged with the owner (every hand-over breaks references); rewriting stored references at hand-over, on read or on write (above).

## Links (accepted by owner 2026-10-16)
A share link is an invite: it lets its holder add an actor as a member with the link's role. Built from existing concepts, no link-specific machinery:
- Per link: **K**, an ordinary actor owned by the sharer, made a member of the target with the link's role; **L**, a key actor whose 32-byte seed is in the link's URL fragment (never sent to servers; it derives L's signing key and tid and K's role secrets, so nothing is sealed to L, notes/crypto.md), made an admin member of K. The link also carries the target tid and where to fetch (server address, the target's label and K's label). The sharer keeps the seed on K under an admin-only aspect so its other devices can show the link again.
- **Redeem**: the holder's client derives K's secrets from the seed, signs as L, adds the holder's actor (or a fresh node for someone without an account) to K with the link's role, and seals K's secrets to it. No admin online, server stays blind. Effective role on the target is the minimum along the chain. L's commits use the commit-ID dot form and the commit-ID tiebreak, since every holder signs as L (notes/crdt-sync.md; review 2026-10-16).
- Falls out: several links = several (K, L) pairs; revoke the link but keep joiners = remove L from K (sync K's label first: joins the revoking device had not received are dropped by its frontier, like any grant a demoter had not seen); revoke the link and its joiners = remove K from the target; remove one joiner = remove them from K; joiners are K's `/members`; expiring link = an `until` time in L's edge value, which the timeline treats as a removal at that time (commit expiry would purge the very certificate that joiners' chains rest on, so membership-class commits never carry expiry; fixed 2026-10-16); single-use = redemption also removes L from K in the same commit.
- **Finalization** (review 2026-10-16b): `until` and single-use are weaker than a real removal, because L's claimed times are constrained by nobody's frontier (every holder signs as L, and L removing L has only L's own testimony). After `until`, a holder of the seed can still mint a join with a backdated time that honest nodes apply; after a single-use redemption, a second holder can mint a redemption with an earlier time and displace the first, and so on without bound. Rule: a demotion by `until` or by self-removal audits nothing, and the next explicit demotion of that member by a real demoter audits its writes with a frontier as if the member still held the role, even though the timeline already shows it below. A sharer's device therefore writes a plain removal of L on its first sync after `until` or after seeing a single-use redemption; until then the link is honest-client-only and the window is as for a removal nobody has published yet. Not modeled in `tools/fixpoint`.
- **Bearer use**: a client may just act as L without joining, writing nothing (a public blog's readers). Read only: all bearers would share L's node identity, so their dots would collide. Editing requires redeeming. Bearer access dies with the link.
- Caveats: every holder is an admin of K, so it sees who joined, can remove other joiners (they can rejoin while the link lives) and holds K's label hard-delete key at blind nodes (destroys only K's membership data there; members keep copies). Nothing beyond the link's role on the target. Fix if it matters: a narrow add-only admin role; not until a real need. Revoking a link is lazy rotation like any removal: old content stays readable to whoever had it, and stays fetchable from blind nodes until download is gated (notes/sync.md, Open).

## Public content (proposal 2026-10-16, not decided)
A public site (blog) running off live osis data needs plaintext serving, caching and indexing, so something holding the key must render. Options: (A) bearer link plus a static JS reader served by the blind node, key in the fragment, server stays blind, invisible to search engines; (B) a rendering gateway: a trusted node holding only the public label's read secret, subscribed to it, serving HTML (recommended for real sites); (C) publish the read secret openly so anyone can run a gateway or mirror. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots (also cheap opt-in authorship hiding, Anonymous writing below); deletion is best effort; `osis://` links to private things reveal their tids only.

## Anonymous writing (discussed with owner 2026-10-16, not a priority)
Nothing needs new machinery except the second dot form (notes/crdt-sync.md). Network, timing and style leaks apply to all; whoever first receives a commit learns which device sent it.
- Pseudonymous member (edits linked to each other, not to you): a fresh actor with its own owning key and fresh per-device keys, joined via a link or a grant. Nothing in its chain may touch your real actors. Admins-only knowledge: the granting admin records pseudonym -> person in admin-only data and grants only to pseudonyms it issued.
- Known writers, unlinkable edits: thing X readable by the group holds the signing key of key-actor-backed actor A, which has write on Y (cleaner: A owned by Y's admins, key derived from X's role secret so removal from X rotates it). Members write as A with commit-ID dots. Removing someone: remove them from X, give a fresh B write on Y, revoke A. Caveats: any member can purge or hard-delete any A edit (author = A); members' unwitnessed offline A edits die at the revoke, so clients re-sign pending ones as B; undo stacks must use locally remembered own commits, not "A's commits".
- Re-publisher: a trusted node re-signs members' edits under its own identity. No protocol involvement.

## Patterns
Three from the same concepts:
- Edge on a thing (ad-hoc share): one existing thing, or a few, shared with an actor.
- Shared owner (spreadsheet): one actor owns every thing, all writers edit everything, removal uses the receipt-time rule.
- Per-author owners with a hub (group chat, owner's design): each user has a participant actor they admin, owning their messages; the chat actor is a read member of each participant (so the chat label receives the messages); users are read members of the chat; chat admins write the chat's data, including the participant set. Members read others' messages (user -> chat -> participant, minimum = read), admins cannot edit them. The app builds the timeline from the participant set.
  - Limits, left to app design: a removed user still controls their old messages and can keep writing new ones, with no verifiable cutoff; removing a user rotates the chat's read key, after which each participant's node re-wraps lazily on next write. Keeping a removed user's past messages is the chat's choice. Reviewed 2026-10-15: acceptable, since the alternative (chat actor owns the messages) lets admins edit them and loses the author-owned guarantee; an app wanting a cutoff keeps a chat-written "accepted" marker per message (dot of the message as received), which is a timestamped acceptance by the chat and needs no protocol support. A removed user's uploads under the chat label stop at blind nodes once the upload key is re-registered; via trusted peers their new messages still arrive but the timeline excludes them.
- Sync groups and owner actors stay separate: groups overlap and may be cyclic, ownership is single. A group may also be an actor when it serves as a shared label.

## Purge rights (decided 2026-10-11)
An explicit purge of preserved history may be issued by the author of a delta or by an admin of the thing (through its owner chain or an admin edge on it; an edge-admin holds the thing's admin secret and so its label hard-delete key anyway, review 2026-10-16b aligned the local rule with that). Any writer can already destroy live state, but letting any writer purge would turn recoverable vandalism of `preserve` aspects into irrecoverable loss; purging only your own deltas gives no power you lacked by not writing them. A purge request naming an aspect's history purges the deltas the requester may purge; the purge record stays visible. Residue: a delta by another author that carries part of the content (a typo fix inside the pasted text) needs that author or an admin. At blind nodes authors act by per-entry delete token plus a signature under the label's current upload key (proof of current membership; a token already proves authorship or write on the thing), admins by the label hard-delete key; `purge`-class tokens are writer-derived so any current writer may finish the reset (notes/sync.md).

## Revocation vs concurrent offline edits
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol is offline with Bob and syncs with him there.

Decided:
- The author's own timestamp never decides validity: forgeable, and meaningless even when honest.
- "Surface it to the user" is not a solution. No adoption UI, no app-visible conflict state. The diagnostics channel reports problems; nothing depends on it being read.
- Rejected writes may exist as an *invalid write* concept: invisible to the normal API, usable by a forensic tool.

### Receipt-time rule
A write from a revoked actor is valid iff a node of a still-authorized actor *received* it (decrypted and verified, not merely stored or relayed) before the revoke's timestamp. Both times come from members' clocks, never the author's. Centralized semantics with "any member's device" as the server.
- Reference scenario: X and Y both invalid. Carol variant: X valid (Carol got it Wed), Y invalid; reads as "nothing Bob did after Thursday counts".
- A revoked actor cannot react to the revocation: by the time they know, the revoke time has passed.
- Clock skew between members leaves a window of at most the skew, only against a node that has not heard yet (constraints tension 9). If ever needed: backdate the revoke by a margin or delay sending it.
- Attestation (was "statement"): a node learning of a revocation publishes a signed "as of the revoke time I held this actor's writes up to here", one frontier per (aspect, author node). The revoker publishes its own alongside the revoke, as a separate attestation commit (2026-10-16, was embedded: the revoke retires with a roster snapshot, the attestation with content snapshots). Only published if it covers something beyond attestations already seen.
- Invalid -> valid can happen late (a witness comes online): an ordinary late merge. Valid -> invalid happens once, on a node that merged a write after the revoke time but before hearing of the revoke: it un-merges.
- An attestation is itself a write by its author, judged by the same rule if that author is revoked. Owner finds this dependency unintuitive but not blocking.

### Sync-then-revoke (decided 2026-10-16, agent's call)
Closes most of constraints tensions 6 and 15, which share one cause: a revoke, demotion or hand-over judged by a frontier taken on a device that had not synced. The receipt-time rule only asks that *some* authorized node received a write before the revoke time, and the revoker's device must be online to publish the revoke anyway, so it receives first.
- Default: before stamping a role-lowering membership write, the client syncs the labels it tracks for the affected actor and the things under it, including the actor's own label (every membership write under an edge into G is published under G's label, so the demoter's frontier over the demoted actor's grants is then complete modulo transit). The write's HLC time is taken after the last downloaded commit is decrypted and applied, so everything the reached blind nodes held counts as received before the revoke, and the embedded frontiers cover it.
- Bounded wait: if no server or peer is reachable within a short timeout the write is issued at once with the stale frontier, and diagnostics say so. A revoke must still complete with nobody else online; sync-then-revoke is a default, not a protocol condition.
- Explicit backdating (stolen device) skips the sync by intent: the user wants to cut off, not include.
- What remains (recorded as tensions 6 and 15): writes at blind nodes the revoker does not reach, writes in transit between its download and the stamp, and revokes issued offline or backdated. All recoverable by re-grant.

### Validity definition (decided 2026-10-15)
Two layers, both deterministic functions of the commits, attestations and receipt log a node holds.
1. **Membership timeline (demoter-frontier rule, 2026-10-16).** Order membership writes by (HLC, node). Start at the thing's epoch start, its newest applied roster snapshot (Roster snapshots, below; writes ordered before it are ignored, and its roster is also the thing's roster for any earlier time another timeline asks about), or at the beginning of what the node holds if there is none. Walk them, skipping a drop set D (initially empty); a write applies iff its author is admin at that point. When an applied write R by node A at time T takes actor X from admin to below, every earlier applied membership write by X that R's embedded frontier does not cover is added to D, and the walk restarts from the beginning. The first walk that adds nothing is the timeline. The frontier is A's receipt log over X's membership-write dots as of T (per node of X; A's own chain and R itself always count), embedded in R like the content frontier a revoke already carries. Nothing else is testimony: no third-party receipts or attestations for membership writes, so the timeline is a function of the membership commits alone and anyone holding the certificates can compute it. Drops are permanent (sticky) so the procedure terminates; a from-scratch re-evaluation can oscillate (a dropped removal can move its author's demotion earlier). Honest members' claimed times are trusted; a demoted actor's claimed times are constrained by its demoter's frontier, and that frontier is itself audited when the demoter is demoted. Consequences: mutual removal resolves to the earlier timestamp; a stolen admin device's backdated removals stand iff the node removing the device had received them before its revoke time, and the owner cancels the rest by backdating its revoke (frontier = its receipts before the backdated time); an admin removed by a node that had not synced recently loses the grants that node had not seen, even if other admins saw them (recoverable: re-grant, which validates the grantee's content). Membership writes in a revoked-then-re-granted actor's gap, and dropped ones, stay invalid; only content is validated by a re-grant. Requirement: a membership write made under an edge into actor G must also be published under G's label, so every admin of G holds it and a demoter's frontier is complete modulo transit. Timelines are per thing that carries edges (an actor's roster, a plain thing's edges); the effective role of a chain at time t is the minimum over them. Each membership write is attributed to the highest authority its author held at its point, owner chain before edge; a demotion audits only the writes attributed to the authority it removes: removing X from G audits X's writes made as G's admin on G and on everything G owns, which the publication requirement puts under G's label, while demoting X's edge on a thing audits only what X wrote on that thing by that edge (so an edge-admin can never drop an owner-chain write such as a roster snapshot). An edge with an `until` time counts as removed at that time, and a self-removal applies, but neither audits anything; the next explicit demotion of that member by another admin audits with its frontier as if the role were still held (Links, Finalization). "Sticky" means within one evaluation: D is rebuilt from scratch whenever the held set changes, so the result is a function of the held set, not of arrival order.
2. **Content and attestations.** Given the final membership, a content write by an authorized actor is valid; a write by a revoked actor is valid iff a valid attestation or the evaluating node's own receipt log (if that node is itself authorized and holds the revoke, whose time it needs) covers its dot before the revoke time, or a valid content snapshot carries the element (Roster snapshots, Content). Attestation validity is the least fixpoint of the same rule over attestations (monotone: attestations only add validity), seeded by attestations of authorized actors. A cycle of revoked witnesses vouching only for each other validates nothing.
- Re-grant (decided, was "never-witnessed writes stay invalid"): all writes of a currently authorized actor are valid, so a re-grant validates the writes made in between. Cheaper (no grant epochs in the log), the actor could redo them anyway, and their old timestamps lose to anything written since. It is also what makes recovery from a stolen device's backdated mass revoke lossless: restoring membership restores the state.
- Backfill: a revoked writer can mint a write claiming a dot below a witnessed frontier. Contiguous dots make it detectable. Rule (2026-10-14): a write at or below a witnessed frontier that the witness does not hold is invalid; if two witnesses hold different writes for one dot, the lower commit hash wins.
- A revoker can backdate a revoke to roll back more. Not a new power: any writer can already invert another's edits.
- Membership commits and attestations are applied before content (notes/sync.md).
- No finality: a revoked actor's writes can turn valid while a witness is still offline. Same as any long-offline node returning.

### Roster snapshots (decided 2026-10-16, owner's design; agent's call on the rule details)
Bounds membership history (constraints tension 12). A **roster snapshot** of a thing N is a membership-class commit by a node acting through N's owner chain (an admin of N's owner actor or of any actor above it, or the key actor at the top; never an edge-admin of N) carrying N's whole `/members` state as the timeline computes it (every edge with role and `until`) plus the full current state of its other membership-class aspects (`/label`, `/secrets`, `/keys`), as reset-plus-full-state deltas so it is also an ordinary CRDT snapshot of them. Published like any membership write. No frontier of its own. **Per-entry deltas** (sync review and permissions review 2026-10-16, found independently; before it a snapshot in a chain certificate handed every reader of L the full device roster of each author's person actor and the roster, `/label` IDs and servers of every team above it): the `/members` state is written as one delta per edge (each carrying the reset stamp and that edge; their join is the roster), listed separately in the header, so a snapshot relayed as a chain certificate can be projected (notes/sync.md) to the edges a verifier needs: the author's own entry, or the entries of the admins whose later grants its chain rests on. Members of N hold every delta; label readers outside N hold a projection and learn no roster (constraints: never rosters they are not part of), only its size from the header's delta count (tension 12). `/secrets` and `/label` are left out of certificate copies for the same reason. An outsider applies the deltas it holds (the atomic-apply rule binds only nodes that sync and may read the thing), so its timeline for N runs over the entries it was given, which suffices: every write it holds about those entries arrives with its own author's certificates, recursively.
- **Epoch start**: N's timeline starts at its newest *applied* roster snapshot S: the author had owner-chain authority at S's time by the chain's timelines, and no later demotion of the author dropped S. Writes ordered before S are ignored even if held, so a grant in flight while the snapshot was taken is dead (finality at each snapshot; snapshot after a fresh sync, re-grant a victim). S's roster also stands for every time before S when a child thing's timeline asks what authority someone had then. Without an applied snapshot a node walks everything it holds. Because S's applicability depends only on the chain above N, never on N's own earlier writes, a node holding only S and later writes computes exactly what a node holding all of history does.
- **Retire**: once S is older than the receipt-log horizon (weeks), any writer retires N's membership-class commits ordered before S at compaction (generation bump and retire list, notes/sync.md), except `/handover` records. Removed members' records thereby disappear (erasure). The horizon keeps the revoke itself around long enough for every node offline less than the horizon to judge its own receipts against it; a node offline longer has pruned those receipts anyway.
- **Un-applied epoch starts**: if S's author is later removed from the owner actor with a time before S (backdated) or with a frontier that does not cover S, S no longer applies. A node holding full history falls back to it; a node that compacted at S holds nothing before and sees an empty roster until a fresh snapshot after the removal exists, which both then start from. So a node removing an admin device re-snapshots, in the same sync, every thing whose epoch start that device authored (and after a snapshot of an actor, the things below whose epoch start a now-absent device authored). The failure only shrinks rosters toward the owner chain, never widens them. Forgeries by a removed device never become epoch starts: a snapshot claimed after its removal is inapplicable, one backdated into its tenure is dropped by the removal's frontier; and once a snapshot after the removal exists, neither is newest.
- **Who can compact what**: a person actor's own roster (its devices) only when its owning recovery key signs, which is fine since device churn is tiny; everything the person owns is compacted by the person's devices. Actors with real churn (companies, teams, shared documents) should be owned by a person actor or another actor rather than directly by an offline key, so their owner's devices can snapshot them. Size: about 25 bytes per edge; policy, snapshot when the writes since the epoch start outweigh the roster.
- **Content**: a compaction snapshot by writer W carries its elements on W's authority: an element it carries is valid if the snapshot commit is valid as W's content write (W authorized, or the snapshot witnessed before W's revoke time), besides the element's original path. Once a node holds a snapshot that supersedes a commit (the snapshot's per-author frontier covers the commit's dots, spec/crdt.md §8), the commit's own path is void at that node, so compacted and uncompacted nodes agree, and attestation entries covering only superseded commits are dead: the attestation is rewritten without them or dropped when empty. Cost: a backdated revoke of a compactor also invalidates the revoked-author elements its snapshot carried (a double revocation, lost like any un-merge without a valid carrier). Own receipts are judged only against a held revoke, so a node that learns of a removal through a roster snapshot alone relies on attestations and content snapshots.
- Checked in `tools/fixpoint` (two-level model `snapshot`, below): compaction at any applied snapshot never changes the result (0 mismatches in 2.5M compactions over 4M random histories), input order independent, nothing dropped when nobody is offline, at most 4 walks; compaction points later un-applied by a backdated removal diverge until a fresh snapshot in about 0.3% of random histories, as designed. Scenarios: owner snapshot then churn, late pre-snapshot grant, stolen device's snapshot undone by a backdated removal and restored by a fresh one, forged snapshots by a removed device, edge-admin snapshot ignored, owner snapshot of the person actor governing earlier time, edge demotion never auditing chain writes.
- Rejected: admin (edge-authority) snapshots as epoch starts (their applicability depends on the thing's own earlier history, so a compacted node cannot judge them and a removed admin could forge one); a snapshot chain (same problem one level up, and unbounded); "dropped epoch start empties the roster for everyone" (gives any removed device a permanent wipe by minting newer snapshots); key-actor-only snapshots (an offline key cannot compact a busy roster).

### Membership fixpoint check (2026-10-16)
Model: `tools/fixpoint` (throwaway Rust, independent of any implementation; `cargo test` runs the scenarios as test vectors, `cargo run --release [samples] [as|exempt|strat|stratw|frontier|snapshot]` the search: exhaustive up to 3 membership writes with owner, 2 admins, 1 writer, skewed receipts, offline nodes, plus millions of random histories with up to 4 admins, 2 writers, 8 writes; `snapshot` is the two-level roster-snapshot model in `src/snapshot.rs`: key actor owns a person actor whose devices act on a group it owns).
- **As written (third-party witnesses judged by end-of-walk membership) fails.** About 14% of random histories have no stable answer and the iteration loops (period 2): an admin removing itself that nobody received in time; a removal received in time only by its victim, whose author is removed later. Several stable answers are normal (1-2%, mutual removal unseen by anyone), so the answer has to be the output of a deterministic procedure. Layer 1 is inherently non-monotone in receipts (a receipt that validates a revoke invalidates its target's later writes); layer 2 was monotone in every sample.
- **Every third-party-witness variant has a self-witness hole**, including the stratified rule proposed first (witnesses judged at the removal point, admin-only, with closure and sticky attestation drops): an ex-admin's backdated grant whose only receiver is its beneficiary stands, because the beneficiary is a member by virtue of the grant; two forged grants vouching for each other likewise. Closing it needs witness eligibility independent of the audited write, a least-fixpoint admission in timestamp order (admitted removals shrink the witness set), sticky drops across repeated walks, and attestation validity for witnesses demoted later: a lot of rule for membership writes, which are rare.
- **Demoter-frontier rule (chosen):** tests pass for every expected outcome (mutual removal to the earlier timestamp, the owner's further-backdated revoke cancels a stolen device's, re-grant validates content, a cycle of removed witnesses validates nothing, self-removal, victim-only receipt, the self-witness and mutual-vouching attacks, a demoter's testimony falling with the demoter, a drop moving a demotion earlier). Search: terminates everywhere (at most 6 walks in 4M random histories), input-order independent, nothing dropped when nobody is offline, layer 2 monotone. Final roles differ from the old rule where it converged in about 6% of random histories, all of the kind "another admin or a writer received the write, the demoter had not".
- Alternatives if third-party receipts for membership writes are ever wanted back: `strat` (admin witnesses) and `stratw` (write+ witnesses) in the tool, both needing the self-witness fix above; write+ witnesses additionally let a writer colluding with an ex-admin hold admin power.

### Witnesses (decided 2026-10-15)
- **Who**: for content, nodes of actors with write or above on the thing, through the owner chain or an edge on it. A grantee with write on N is a witness for N. Readers do not witness: a reader's attestation would let a read-only member plus an ex-writer jointly write, a power neither has alone; a writer's adds nothing it did not have. Blind nodes never witness (tension 6). Membership writes have no third-party witnesses at all: only the demoting write's embedded frontier counts (Validity definition, layer 1).
- **What**: an attestation is a commit kind of its own, not an aspect write. Header only: the revoke it answers, then (tid, ak, author node, frontier counter) entries, or explicit commit lists for commit-ID dots (notes/crdt-sync.md; no gaps, so the backfill rule is moot for them), each entry authorized by the attester's write right on that tid. No deltas, no retention class, invisible to apps. This dissolves "readers cannot write to the actor thing": nothing is written to any thing.
- **Where**: labeled like membership commits, under every label of the things it covers, so label readers who are not members can evaluate validity. Retired as content snapshots supersede the commits its entries cover (Roster snapshots, Content; was never retired). Small, and only one per (witness node, revoke).
- **Cost**: one commit per witness per revoke, about 10 bytes per (aspect, author node) entry over the 200-byte floor; a witness holding ten thousand aspects by the revoked node publishes about 100 KB once. The revoke's embedded frontier usually covers most of it, and attestations that add nothing are not published.
- **Receipt log**: per commit for commit-ID dots; otherwise per (aspect, author node), checkpoints (own clock time, frontier counter) whenever the frontier advances, pruned past a horizon (policy, weeks). A revoke backdated beyond the horizon can be answered only with "nothing", so it invalidates everything by that author at that witness; bounded by the existing "a revoker can backdate" power.

Costs:
- Un-merge: drop elements by author dot; restore register values the invalid write overwrote from peers or own retained bodies. Rare loss possible if neither has it. Invalid text inserts stay as content-less anchors so others' inserts anchored to them keep their place. Every state element carries an author dot (notes/crdt-sync.md), so un-merge and frontier attestations are uniform.

Rejected: timestamp rule (forgeable); accept everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); revoker's cutoff (depends on which node revoked); learn-based witness rule (valid if a member accepted it before *learning* of the revoke: the revoked actor can race the revocation, and honest offline sync looks like a hostile push); membership evaluated by claimed time only (an ex-admin could forever mint backdated grants); attestations as aspect writes on the actor thing or on the thing written (readers and edge-grantees cannot write there, and they would need retention rules).

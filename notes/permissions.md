# Permissions: rationale
> Summary: Why spec/permissions.md looks the way it does: owner direction, why each rule, costs and leaks, revocation and move (copy) reasoning, the `models/membership` findings behind the membership timeline, sharing patterns, public content and anonymous writing, rejected alternatives.

## Owner direction
A small set of concepts that compose; hierarchical; keys for nodes, actors and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of actors managed in one place; nested actors (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: owner, admins, editors, viewers.

## Concepts
- Any thing becomes an actor when it needs members of its own: people, agents, teams, shared documents, a single shared note. Identity is the tid, so keys rotate freely.
- A role on an actor covers both editing the actor thing and acting as it: only the membership-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the actor but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope; the owner is the recourse. So a person actor's owner should be an offline recovery key, with devices as admins (app policy). Consequence: only the recovery key can roster-snapshot the person actor, so its membership history (device churn, tiny) is bounded only when the key is used.
- Recovery of a lost owning key is out of scope (owner). The actor keeps working (admins can remove each other) but can no longer be roster-snapshotted or settle an admin war; its things can still be copied out by any admin.
- Recovery card: the seed alone cannot find the person actor (tid, labels and servers are not derivable), hence the card format; the recovery key owns the person actor, so every home-label step lists it with an entry box; the card names several servers, and the key claims the current step by its static entry and reads the read secret from the step's entry box (spec/sync.md §2).
- Key actors have role secrets derived from the seed (never rotated) only so that things they own (a node's local things, the person actor under its recovery key) derive secrets like any plain thing; nothing else uses them.
- Nodes are things that own themselves and grant nobody anything; the node card under every label a node tracks shows exactly the readers of L which nodes sync L (a read-only node's card arrives by deposit), and its expiring `/seen` heartbeat when it last did (notes/ephemeral.md), never a roster. Rejected: a self-edge granting the person admin (covers only own devices); a devices group readable by contacts (leaks the device roster, misses read-only co-members). `/reach` carries no IPs (dialable key and relays only, notes/networking.md); apps exclude it under open-audience labels so strangers cannot dial the device.

## Keys
- Writes are node-signed plus a membership chain. Sharing an actor's signing key erases which member wrote (revocation needs the author) and makes every removal a key rotation; it is reserved for deliberate anonymous writing.
- Reads are key wrapping, per role and every epoch: a later writer needs old write epochs to derive delete tokens of old `writer`-purgeable entries; a later reader needs old read epochs for old wraps.
- Per-role secrets cover the patterns without extra machinery: sharing (read and write wrapped to the grantee, admin only to the owner), demotion write -> read (rotate write only), removal. Epochs are per role, so a writer's rotation of read and write leaves the admin secret, its boxes and the label delete key exactly where they were, and nothing "carries over". Concurrent rotations fork the epoch (spec/crypto.md §4): boxes are keyed per epoch so both rotations' boxes survive the merge, members keep every fork's secrets, the next rotation's history box covers them all, and a rotation that missed a concurrent removal is rotated again before anyone encrypts under it; at a server the first registration step wins and nodes use the matching branch. An epoch whose rotation commit turns out invalid (a backdated ex-admin's) is kept for reading but never encrypted under. Eager rotation by many members at once forks harmlessly but costs boxes per rotator. Rejected: boxes merged per (member, role), which leaves members holding different secrets after concurrent rotations, unable to read each other's new wraps.
- **Write or above rotates its roles and below** (decided with owner). With admin-only rotation, every actor a person is a non-admin member of would keep wrapping new content to a lost device until that actor's admins happened to rotate, and the person could do nothing about it. So the person's own device rotates every actor it writes to when it removes the lost device, and elsewhere the next writer to write does. Readers rotate nothing: a rotation sealed to an incomplete roster locks members out, worse than the storage waste a reader may cause; an actor the person only reads keeps wrapping to a lost device until a writer or admin of it next writes. A writer's bad rotation is bounded like its other vandalism (the next honest rotation forks past it). Registration stays admin-only (the delete key): if the write key signed steps, every ex-writer could race to lock a label at a server, which only ex-admins can (notes/sync.md). Until an admin registers the newest epoch, a removed device keeps the old sync and write keys at servers: ciphertext it cannot open, stale stamps and `writer`-token deletes that members heal. Residue: a member that has not heard of the removal wraps under the old epoch, and the lost device reads that one blob (as with Signal sender keys).
- **No periodic rotation, no rotation policy** (owner). A device compromise is either known, and the removal rotates before the next write, or unknown, and the device is still a member, so a scheduled epoch seals the new secrets to it as well. Healing a silent copy of the secrets would need the device's KEM key to change from fresh randomness the thief lacks; the seed is the device, so a thief holding it is the device and nothing heals. History boxes mean a compromise yields all stored history anyway; "no history for new members" and bounded history are app or future choices, not core.
- A plain thing derives its secrets until it has a non-owner member, so nothing is stored; then explicit secrets, so that removing that member rotates the thing alone and not its owner. The switch is an ordinary rotation from the derived epochs (history boxes carry the derived secrets, which are one-way from the owner's), so wraps, tokens and label steps need no special case; a derived secret's epoch is the owner's. Explicit secrets do not stop the cascade the other way: every rotation of an owner is caused by a removal, and the removed member could open every explicit secret the owner's roles reach (owned things, edge targets, transitively), so all of those rotate too, lazily, each by the next node that may and is about to encrypt under it. The `/keys` keysets of rotated roles are written by the rotator, a writer included, or labels above would keep sealing to the stale KEM key until an admin happened to act.
- Nesting cost (accepted by owner): removing a member rotates every thing with explicit secrets whose secret it could open, so a lost device costs one lazy rotation per shared thing the person reaches; the usage rule is to share sets through one actor. A thing's admins learn what it is a member of because every edge whose member is the thing is also published under its home label. Per rotated actor: one sealed box (about 1.2 KB) per direct member per rotated role, one re-registration per label per server. A company of 50 teams with 10 labels on 3 servers: 50 boxes and 30 signed messages per person removal. Inherent to lazy rotation (spec/requirements.md, Cost).
- A removed node erases what it can no longer read so a later compromise exposes nothing more; not enforceable against a hostile node. If the removal is undone, the node re-syncs. The removal reaches the removed actor's admins as an inbox blob, like a grant.
- **Stale `/keys` window**: until a person's new `/keys` reaches a co-actor's label, rotations there seal to the lost device's old keyset and its steps list its old claim key, so the lost device reads new content via an honest server. Hence the MUST to place the removal and new `/keys` under every label the removed party could read in the same sync as the removal (spec/permissions.md §3); what remains is rotations racing that sync.
- **Re-seal is a SHOULD with a trigger** (a current member without a box at a current epoch, or a stranded heartbeat). Without the trigger a grant raced by a rotation was a silent permanent lockout. The missing box that marks a deliberate exclusion looks exactly like the one that marks an unknown grant, and TLC (models/tla/rotation, R1) showed a node that receives the rotation before the removal re-seals the removed member, who then reads post-removal content from an *honest* server (it holds the current sync key); the earlier reasoning that the covers rule heals it was wrong about the window. Fix: **the removal or demotion and the rotation it requires on the target are one membership commit**, so holding the rotation means holding the departure, and an omission in a held rotation can only mean the rotator did not know the member. It costs nothing: the covers rule already forced the remover to rotate before encrypting the removal commit. The inbox copy to the removed member and the certificate copies carry the edge delta only (projection). Rotations of other things (the cascade) stay lazy; they exclude nobody directly. Guards on top: a re-seal decision comes after a full sync pass (like the pre-sync before a demotion, spec/permissions.md §5.3), a member whose `until` is within `MAX_DRIFT` is not re-sealed automatically (the rotator's and the re-sealer's clocks could disagree on whether it has left), and boxing a secret to a member counts as encrypting under its epoch (a re-sealer that knows of a departure rotates first). The second TLC round showed the one-commit rule covers only the rotation that carries the removal: a later rotation by a node that knows it omits the member without carrying anything, and a node that reads that rotation out of order (a peer, a second server, or a re-seal's history box handing it the secret before the commit) re-seals the removed member. Fix: **established epochs** (spec/crypto.md §4): a rotation counts only once the node has applied its commit and the commits of every epoch it supersedes, transitively (or a `/secrets` snapshot stands in for a compacted chain), so holding an epoch means holding every departure its chain carried, whatever the arrival order; this is the order the wraps already impose on a node that never got a history box. Re-seals are made only at chain-established epochs (a late joiner holding only a snapshot rotates instead: a rotation boxes everyone it thinks current, so it is a re-seal of everyone) and at the end of a complete pass (the log of every server and peer read to its end: cheap to know, and what makes the post-compaction case sound). Opening a label is no longer "encrypting under": a re-sealed member must open with the re-sealed sync key to fetch the rotation commit that establishes the epoch; an open proves possession to a server and produces nothing others rely on. The remover uploads the rotation before registering the step (notes/sync.md), so a member listed in the step never strands merely because the commit is not there yet. Residue (accepted, notes/sync.md Limits): after compaction a node's membership view no longer travels with the epoch chain, so a node that boxes a member at a snapshot-established epoch from an incomplete view (a server that never got the removal, an interrupted first sync followed by an eager rotation) can box a removed member; same class as a rotation by a node that has not heard of the departure, healed by the next rotation of a node that has. The refused-deposit residue stays in issues/reseal-triggers.md.
- **Planner** (`osis_keys::planner`): `plan_departure(graph, A, M, from, held)` walks owned things and edge targets from A over a `Graph` trait (`PermGraph` adapts a perm `Timeline`; `MemoryGraph` for tests), carrying the set of roles exposed: on T reached via role ρ, the exposed roles of the predecessor that are ≤ ρ (a role secret opens only boxes of that role). Each entry carries one `Departure { via, member, from }` per path (`via` = the chain of actors from the entry down to the one M left), and the covers rule follows the chain recursively through `HeldActors` (each level's newest keyset and its `/secrets`; unknown counts as uncovered). Without the recursion a two-hop chain (device left P, P in T, T in U) looked covered at U while T was unrotated. `Plan::required`/`mine` are top-down (depth from the departure); a node that may not rotate an intermediate stays stranded on what is below. Plain things are traversed but need no rotation. `lost_access` lists what a node drops.
- **`until` counts as a departure** for rotation and the covers rule, else "share for a week" never ends for reading; eager rotation makes boundary disagreement between clocks harmless, and the re-seal guard above keeps a slow clock from re-admitting a member whose share just ended.

## Sharing
- Sharing never changes a tid. Moving a thing to an actor its owner owns has no double-spend harm, so it is an ordinary write (an edge). A copy with a new tid is only for moving a thing out of its owner's tree, which should be rare.
- One note: an edge on N, explicit secrets on N, N its own label. A set: a group thing with members and secrets, made a read member of each thing (one edge per thing, one commit). A set meant to be shared as a unit is better created under a common owner.
- Group membership grants no rights (an edge on a group extending to its contents was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all label correctly.
- Rejected: an actor per thing at creation (usage rule, doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Certificates
- Problem: checking a write on N needs the membership of N's owner chain and of the author's own actors, which only members can read. Resolution: signed membership commits are the certificates and travel under the labels where needed. No verify role, no certificate format, no extra key.
- Leaks: a reader of L learns the chain of every author under L (one edge and the roster size per level, plus each `/created` record and hence that thing's dedup secret), never rosters. Author identity is inherent anyway.
- Roster snapshots in certificates are projected per edge: a whole snapshot would hand every reader of L the full device roster of each author's person actor and the rosters, `/label` IDs and servers of every team above it.
- **Per label, not per node**: a certificate delta already under the label counts whoever placed it, so a joiner copies only its own chain (11.5 KB per label in a chat) and not the sharer's again, and members do not all re-copy a rotated actor's new `/keys`. Sound because a copy counts only once this node checked every delta of it against the header's delta hash (`SyncEngine::genuine`; opening checks the prefix only, and a held commit's late parts are skipped unchecked, so before the check anyone able to deposit under the label could post the header with garbage deltas and stop the real copy; the same check now guards `entry_for`, `carried_by` and the duplicate and strict-subset deletions, where a forged blob could have got real copies deleted), only while present at every server of the label this node syncs with (else it skips at one server and its own copy then goes to both), and, for a rotation commit of the label's actor, only under the newest epoch. Older epochs otherwise count: a newcomer gets the history boxes with its grant or first rotation box (spec/crypto.md §4) and opens older copies like the label's older content (`newcomer_after_rotation_reads_older_copies_spec_crypto_4`); counting only newest-epoch copies made every member re-copy everyone's chain after each rotation (40 KB per member per chat removal). Residue: a holder of a link key alone (newest secret, no history box) reads none of the older entries, own copies included, as before. If another node's copy goes, the next pass places this node's own. Deletion power is the same either way (a copy carries its commit's tokens). Closure deltas are never copied (they are closure blobs; a copy was a strict subset others deleted). Another node's demotion or `/keys` is left to its author for `SETTLE_MS` (30 s) after this node received it, with a wake then (the remover must place them, §3): members learn of a rotation under K's label before the remover's copy under C arrives, and all of them copied it (3.3 KB per member per removal). Measured from receipt, not the commit's `ts`, which its author sets.
- Accepted: revocation reach is eventual (L's readers accept a revoked node until some member of the revoking actor syncs L); chain depth equals nesting depth, at most `MAX_OWNER_DEPTH` (64) owner links (spec/permissions.md §1; a member nesting deeper would make every standing query cost more).
- Rejected: a transitive "verify" role (outside collaborators learn full rosters; every rotation re-wraps to everyone below); per-commit certificate chains (a few hundred bytes per commit against a 300-byte floor).

## Revocation
Reference scenario: Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Owner decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and blind nodes never vouch for a revoked writer's edits.
- Frontier rule results: X and Y invalid. Carol variant: X invalid too; re-grant restores it, together with Y. Centralized semantics with the revoking device as the server (owner: fine either way). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- One rule for both layers: the revoke's frontier is one list for membership and content writes, about 10 bytes per (aspect, author node) entry plus 32 per commit-form commit. A prolific device over years writes 10^5–10^6 aspects, so a frontier can reach megabytes: it is a large value (chunked above `CHUNK_THRESHOLD`, carried by link), and every later roster snapshot re-carries it (written afresh each time, so all its chunks are in the snapshot's header chunk list and receivers fetch them before judging; reuse across snapshots was dropped for that). The ledger copies it into every later roster snapshot; that is the price of a roster snapshot replacing the revoke. Rejected: per-node global counters (one counter per node plus gaps) would shrink frontiers but change dot semantics, runs and the model.
- Only the revoker's own receipts matter: a node that may revoke keeps, per (aspect, author node), when it received each counter (granularity and horizon are local policy). A backdated revoke's frontier is bounded by that record; a coarser record gives a smaller frontier and more loss.
- **Chain writes count only through the frontier** (models/tla/membership M1). The rule used to exempt "A's own chain writes" (those setting the admin edges on A's admin paths) whoever wrote them and whether A had them, so after A removed admin X, X could write a backdated change to A's own edge (an `until` next week, a lower invite) and it stood. Now A's frontier lists by commit ID the membership commits and roster snapshots of its chain certificates for the target at R's point (§4: the writes on its paths, closed under their authors, so a grantor's own grant counts too; held, hence received; by ID because its receipts of X's counters need not be contiguous: a grantee often gets only its own grant). A forged one is not listed and drops; A's edge reverts. First cut (reviewed out): only the writes setting admin edges on A's own paths, read from the end state: a grantor's grant of A's grantor was missed (R then failed), and the end state could name a later rewrite instead of the grant R rested on. Residue: if A's authority at T rested only on a chain write A had not received (another verifier's view gives A a path A's own view lacked), that write drops and R with it; what R dropped in the same audit stays dropped. An honest node holds its chain, so the model generators mark each author's chain certificates as received (`membership_model::hold_chains`, TLA `Certs`); random receipts that skipped them made such failures look like 1 in 500 sticky residue. About a quarter of the writes that grant no admin are tagged written last (received by nobody: backdated forgeries); admin grants are never late, since an honest node does not act on authority it never received (with late grants it would; neutrality then broke through the old sticky epoch-start rejection, since removed). Rates: about 1% of joint histories drop something; sticky residue skipped in about 3 of 10^4 snapshot-model histories; no neutrality case needed the "a snapshot only undoes drops" fallback. A compaction snapshot lists the commit-form commits it absorbed (spec/crdt.md §8), so a late joiner that got X's rotations only through it still counts them received and its frontier covers them. Rejected: exempting only chain writes that do not lower their edge (a second rule for a rare case).
- Clock skew: a departure by `until` or self-removal is judged by the member's own timestamps, so its writes stamped up to `MAX_DRIFT` past the end still count (spec/requirements.md, Permissions). If ever needed: backdate revokes by a margin.
- Invalid -> valid happens only by re-grant; valid -> invalid happens once, by un-merge. No finality, like any long-offline node returning.
- Re-grant validates the gap: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it makes recovery from a stolen device's backdated mass revoke lossless. It is all or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them.
- A revoker can backdate to roll back more; not a new power, any writer can invert others' edits.
- Dot reuse by a revoked actor would let it write under covered dots forever, so overlapping node-form ranges from one node void both commits (spec/commits.md §4). Honest nodes never overlap (an unsure node uses commit form). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Membership commits use commit form and a node-form one is bad input (spec/commits.md §3, §4), so a removed admin cannot void its earlier grants, revive a member it removed or void its own rotations that way (it could make its grantee's edge never have existed, and with it a removal the grantee made of it).
- Sync-then-revoke closes most of the loss from a frontier taken on an unsynced device (spec/requirements.md, Permissions). What remains: writes at blind nodes the revoker does not reach, writes in transit, P2P-only edits among other members, revokes issued offline or backdated; all recoverable by re-grant.
- Rejected: timestamp rule (forgeable); accept everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); membership by claimed time only (an ex-admin could mint backdated grants forever); other writers vouching for edits the revoker missed (a commit kind, a validity fixpoint over vouchers who are later revoked themselves, a per-node receipt clause and a tiebreak, all for edits that reached another writer but not the revoker; not worth it).
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 already judged edge writes one by one.
- **Compaction snapshots vouch for nothing** (owner decision): every element is judged as its author's write, un-merged from snapshot bodies too; re-grant is the only recovery. History: the first rule let any writer's snapshot carry a revoked author's elements, so a writer that had not yet received the revoke revalidated them everywhere by routine compaction; the sweep added "only if the author was authorized at the snapshot's `ts`", which `models/membership` (`content.rs`) showed diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered. Rejected: carrying an "earliest saved at" `ts` per commit in snapshots (converges, bytes on every entry forever, and the compactor's word lets a friendly writer launder a revoked member's backdated writes under the member's own name); newest carrying snapshot decides (converges, but the save lasts only until the next compaction). With the pre-sync before stamping a demotion (spec/permissions.md §5.3, notes/api.md) the save had no remaining job: a synced revoker's frontier covers what snapshots carried, and a revoker that fails instead of stamping loses nothing. A compacted node can still judge: current members by the roster, ended tenures by the ledger.
- **Layer 1 is one joint walk** over all held edge writes of all things, ordered by (`ts`, author node, commit ID): authority at a point depends on other things' timelines and mutual membership is allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed anyway: a shared link key gives two holders the same (`ts`, author node). Attribution is by authority class (owner chain, edge admin, invite level). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin edge on G could backdate a forged write to a time it held only the edge; removing the edge first is no fall (the chain holds) and the later chain removal audited only chain-class writes, so the forgery stood forever (found by `models/membership`, `two_admin_paths_class_attribution`, `chain_and_edge_paths`). Path-based audits (each removal audits what went through its path) would also close it, but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal is attributed like its grant and falls with it: "self-removals are never dropped" taken literally kept a forged redemption's self-removal after the sharer's finalization dropped its grant, burning the link and blocking the honest redemption the sharer had seen. Attribution depends only on L's authority, so projections still agree.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the tenure (the rejected claimed-time rule).
- Writes to `/secrets`, `/keys`, `/label`, `/moved`, `/was` are not edge writes: they are judged like content by the role their aspect requires, with frontiers covering membership-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.

## Membership timeline (membership model findings)
Model: `models/membership` (throwaway Rust, independent of any implementation; a library whose modules follow spec sections, `src/lib.rs`, plus a search binary; osis-perm dev-depends on it as its differential oracle). `cargo test -p membership-model` runs the scenarios; `cargo run --release -p membership-model -- [samples] [as|exempt|strat|stratw|frontier|snapshot|edges|edges-prov|joint]` searches (`joint`: `src/joint.rs`, the joint walk over several actors with mutual membership and commit-ID ties; `src/content.rs`: layer-2 scenarios, test-only): exhaustive up to 3 membership writes (owner, 2 admins, 1 writer, skewed receipts, offline nodes) plus millions of random histories (up to 4 admins, 2 writers, 8 writes). `snapshot` (`src/snapshot.rs`) is the two-level roster-snapshot model; `edges` (`src/edges.rs`) models projected rosters, links, invites (audited by level), per-op judgment and plain owner-chain writes on a thing (its `/moved`, say); `joint` (`src/joint.rs`) is the joint walk over several actors (owner chains, actor members, mutual membership, (t, author) ties broken by commit ID): order independent, terminates (at most 4 walks in 4M random histories), nothing dropped with nobody offline. `src/content.rs` holds layer-2 scenarios: per-delta validity across partially synced things, snapshot authority at `ts`, and the snapshot-of-snapshot divergence that led to "snapshots vouch for nothing" (below).
- **Third-party witnesses judged by end-of-walk membership fail**: about 14% of random histories never stabilize (period-2 loops), e.g. an admin removing itself that nobody received in time. Several stable answers are normal (1–2%), so the answer must come from a deterministic procedure. Layer 1 is inherently non-monotone in receipts.
- **Every third-party-witness variant has a self-witness hole**: an ex-admin's backdated grant whose only receiver is its beneficiary stands, since the beneficiary is a member by that grant; two forged grants can vouch for each other. Closing it needs a lot of rule for rare writes.
- **Demoter-frontier rule (chosen, agent's call)**: every expected outcome holds (mutual removal resolves to the earlier timestamp; the owner's further-backdated revoke cancels a stolen device's; re-grant validates content; a cycle of removed witnesses validates nothing; self-witness and mutual-vouching attacks fail; a demoter's testimony falls with the demoter). Terminates everywhere (at most 6 walks in 4M histories), order independent, nothing dropped when nobody is offline. Drops are sticky within one evaluation; a from-scratch re-evaluation can oscillate.
- If third-party receipts for membership writes are ever wanted: `strat` (admin witnesses) and `stratw` (write+ witnesses), both needing a self-witness fix; write+ witnesses also let a writer plus an ex-admin hold admin power.
- Consequences: a stolen admin device's backdated removals stand iff the node removing the device had received them before its revoke time; an admin removed by a node that had not synced loses the grants that node had not seen, even if other admins saw them (re-grant recovers). Edge demotions never audit owner-chain writes, so an edge-admin cannot drop a roster snapshot.
- Also checked: projected rosters compute the same roles as full rosters (0 mismatches in about 320M checks, given per-write judgment inside a commit); `until` and single-use finalization (a backdated join after `until`, or a forged earlier redemption, stands until the sharer's removal of L drops it); plain owner-chain writes on a thing such as `/moved` (a removed device's late write is never valid; validity is order independent and survives compaction and projection); invite power (no joiner or link holder can remove, demote or change anyone; self-granting admin, mutual vouching, ex-admin plus invitee, and re-adding during the inviter's own revocation all fail; a removed inviter's unseen grants drop).
- **Sticky drops leave residue**: if a demotion drops a grant and that demotion is itself later dropped, the grant stays dropped (about 1 in 7,000 random histories); likewise a used single-use link can revive until the sharer finalizes. Re-grant repairs it. Drops that last only while their cause applies (`edges-prov`) remove the residue but loop forever on removal rings (about 0.04%), so drops stay sticky. A roster snapshot also repairs it (its ledger has no demotion for the dropped cause), so §6 neutrality holds only up to sticky residue (models/tla/membership `MC_sticky_snap`, confirmed in osis-perm).
- Self-removals are never dropped: otherwise a later demotion of the author could hand back what it gave up. Writes in one commit are judged one by one: all-or-nothing would make L's self-removal depend on the redeemer's roster entry, which a verifier of L does not hold.
- Concurrent invite grants for one actor: the first in timeline order wins, even with a lower role or shorter `until`.

## Roster snapshots
- Bound membership history (spec/requirements.md, Permissions and Scale). Only owner-chain snapshots can be epoch starts: their applicability depends only on the chain above N, never on N's own earlier writes, so a node holding only S and later writes computes what a full-history node does.
- **Tenure ledger**: a snapshot's roster alone cannot answer authority before S, yet things are judged against it after S: writes and epoch starts of things below N made by chain authority before S, and ex-writers' content (layer 2 needs the revoke time). Without it, a routine re-snapshot of a person actor after a device removal kills every owner-chain write the device made on things below while a legitimate admin (2.3% of valid ones in random `models/membership` runs), epoch starts included. The ledger is the compacted form of the demotions: each ended tenure with the frontier that ended it, so the member can neither gain anything (a dropped backdated record stays dropped: the frontier travels with the tenure) nor lose what the timeline had accepted. Roster edges carry `since` so a re-granted member's gap stays closed; every later tenure's frontier re-audits earlier writes, as a later demotion does in the walk. Checked (`snapshot` mode, `resnapshot_neutral`): re-snapshotting P with the roster and ledger the timeline computes changes no record's validity and no G write's application in 8M random histories; compaction, projection and order independence hold with random well-formed ledgers.
- **Ledger cost, the accepted tradeoff**: entries are never dropped, because a write or epoch start anywhere below N may depend on any of them and the snapshotter cannot know which (it does not sync everything below); a time bound was examined and rejected, since a removed member could forge a backdated write inside its tenure (an epoch start of a thing below N, say) after the bound, and only the tenure's frontier drops it. Roughly 100 bytes per ended tenure of write or above plus the frontier (by link when large, re-uploaded per snapshot), carried by every later snapshot of N: a person actor grows by its device churn, a team by its member churn. Certificate copies carry only the edge and ledger deltas a chain needs (one delta per edge and per entry, so a projection drops deltas and never breaks a hash), so verifiers pay per edge in bodies but still one delta hash per edge in the signed header: direct rosters should stay in the thousands (spec/requirements.md, Scale). Rejected: writes carrying a frozen certificate of their signer's chain (cannot show the signer's later removal covered the write once that removal is compacted); listing only tenures of members whose writes the snapshotter holds (breaks writes it does not hold); a Merkle tree over per-edge hashes (saves header bytes for huge rosters, more machinery; revisit if flat rosters above ~10k matter).
- A grant in flight while a snapshot is taken is dead (finality per snapshot); snapshot after a fresh sync, re-grant a victim.
- `MEMBERSHIP_KEEP` on membership commits keeps the revoke long enough for every node offline less than that to apply it. A format constant, so nodes agree on what a label must hold.
- Un-applied epoch start (author later removed with a backdated time or a frontier not covering S): a full-history node falls back, a compacted node sees an empty roster until a fresh snapshot; this only shrinks rosters toward the owner chain. Forgeries by a removed device never become epoch starts.
- Who compacts what: a person actor's own roster only when its recovery key signs (device churn is tiny); busy actors (teams, documents) should be owned by a person actor, so its devices can snapshot them. About 25 bytes per edge. A roster snapshot carries only `/members` and `/tenures`: `/secrets`, `/keys` and `/label` compact like any aspect (compaction snapshots page, so a big actor's boxes and steps never have to fit one delta), and a rotation's boxes page. The old design carried full `/secrets` and `/label` in the roster snapshot, which could not fit a blob for rosters above about a thousand.
- Content via compaction snapshots: with snapshots vouching for nothing, compacted and uncompacted nodes agree whatever snapshots they hold or dropped (`content.rs`, `snapshots_vouch_for_nothing`).
- Checked in `models/membership` (`snapshot`): compaction at any applied snapshot never changes the result (0 mismatches in 2.5M compactions over 4M histories), order independent, at most 4 walks; compaction points later un-applied diverge until a fresh snapshot in about 0.3% of histories, as designed.
- Rejected: edge-admin snapshots as epoch starts (a compacted node cannot judge them, a removed admin could forge one); a snapshot chain (same problem, unbounded); "a dropped epoch start empties the roster for everyone" (a permanent wipe for any removed device); key-actor-only snapshots (an offline key cannot compact a busy roster).

## Moving a thing (copy)
- Ownership is immutable: a former owner can always sign a competing transfer (double-spend; no fix without consensus), so a transfer must never let the former owner touch what the new owner holds. A copy under a new tid gives that for free: the old thing stays the former owner's, the copy is the new owner's by construction, and the former owner's whole power is to re-point or wipe the old thing, which only misleads readers that hold nothing but the old tid. Decided with the owner over the old aliasing design (below) for simplicity: no verification rule, no identity derivation, nothing kept forever.
- Imports keep history: live state with its stamps and dead bodies alike, each with its origin's retention and author, so purge rights on the copy are what they were (an origin author purges once re-granted on the copy, as it would after any removal and re-grant). What a copy cannot do: give the old authors' delete tokens at blind nodes (the importer lacks their secrets; admins' tokens delete after the author's purge request) and move rights the moved actor held elsewhere (foreign admins re-grant the new tid). Cost O(subtree + history); the owner does not mind.
- Re-sourcing to (`Commit(origin)`, k) makes an import idempotent (two of X's devices importing the same origin produce the same dots) and keeps imported dots clear of native counters, which start at 1 per (aspect, node) and would otherwise collide with an author's own old dots. Keeping the original `ts` keeps the order among imported writes; everything native on the copy is newer anyway. The origin choice depends on the importer's held set (snapshot if it holds one covering the write, else the commit), so two devices importing concurrently from different held sets would duplicate elements; hence one import per move and the client rule not to import a thing already continued by a held copy. Residual race accepted.
- Resolution is a read-time view keyed on the referencing thing's owner chain, so two readers of one thing agree: the copy's own `/was` claim wins where that owner has standing in the copy, the former owner's `/moved` pointer elsewhere. Standing can be faked only by granting the referencing thing's owner an edge on a fake, which is the same exposure any unsolicited grant has (apps place things into their sync set explicitly, spec/requirements.md, Offline and network). Values are never rewritten: an autonomous rewrite is a write with a fresh timestamp that beats a concurrent real edit, and two devices rewriting concurrently would duplicate text links.
- Within one tree nothing moves: rights are edges, the root is the un-removable admin either way, so "move this doc to team B" is an edge change, and ownership depth should match the units that travel together (a folder actor owning its things moves between teams by one edge). Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).
- Replacing a root key (the recovery key owning a person actor) is a copy of the person actor: rare, re-granted everywhere by foreign admins. Not required by anything (signatures need not be PQ, seed compromise is out of scope); devices rotate by add-and-remove.
- Rejected: **hand-over with aliasing** (the previous design): a record on the thing signed through the former owner's chain, the new identity hash(T, H) owned by the new owner by construction, everything below renamed per fork branch, a three-step read-time resolution (standing, the reader's `/follows` choice, dangle), records kept forever and hence an unbounded tenure ledger; correct and model-checked, but the whole of a spec section plus permanent per-verifier cost for a rare operation. Also rejected: sharing a tid between branches (the former owner's chain stays able to write and delete the subtree), freezing a thing on a second record (no consensus on the moment, so it is a rewind to the transfer, and a disown hands the name back), a notary or log committed at creation (closes every former-owner power but makes transfer an online operation with an outside dependency), transferring without history, a one-successor `/moved` (first-write-wins needs arrival order or a fork rule).

## Links
- Built from existing concepts: K (an ordinary actor with secrets of its own) and L (an ordinary key actor: signing and KEM keys from the seed, listed in K's steps by static entry with an entry box, boxed in K's `/secrets` like any key-actor member). Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's label first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's label, where L's boxes hand it K's rotated secrets (bearer read); the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (and so one cascade rotation of the target): two commits paid two rotations of K and of the target for one decision. perm judges each edge write of a commit on its own (as for a redemption), so such a commit is two removals at one point with one frontier; `models/membership` needs no new operation for it. None of its edges may be a self-removal (refused by the writer rules). The one-edge rule exists so every removal carries the rotation that covers it (re-seal soundness, above); a several-edge removal under one rotation keeps that, since the rotation excludes every member it removes.
- **Why K no longer derives its secrets from the seed** (the previous design, "until K is first rotated"): every holder of a read link derived K's admin secret, hence K's label delete key (wipe or squat K's label at every server) and write key, which is exactly the power the invite-only design took away from L. And L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K (allowed since d8a68b4) stranded L. Now K's secrets are random, L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip: the cold-entry path that already existed after a rotation is the only path.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- Finalization: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer device writes a real removal; until then the link is honest-client-only. Alternative (no `until` or single use at all) loses nothing a hostile holder respects.
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **Invite power** (agent's call): what a link conveys is "add yourself with a bounded role", nothing more: L holds (role r, invite r) on K and the sharer stays K's only admin. Invite grants only add edges for actors with no current edge, so no invite holder can remove or demote anyone; a revoked inviter's unseen grants drop by the demoter's frontier like any membership write. Inviters seal only secrets they hold (their role and below). Holders read K's roster (they are its members), like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's label delete key).
- Self-removal lets an actor always leave or lower its own edge; single-use links use it to drop L's own edge.
- Single-use links in teams: after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (spec/permissions.md §9: kicking one joiner otherwise kills the link for all).

- Resolution hops are capped at 8 (`RESOLUTION_HOPS`): longer move chains are pathological, and the cap keeps a read O(1).

## Patterns
- **Edge on a thing**: ad-hoc share of one or a few things (the thing gets secrets of its own: about 2.6 KB of boxes per member, so not per note in a folder).
- **Shared owner** (spreadsheet): one actor owns everything, all writers edit everything, removal by the frontier rule.
- **Root actor**: an offline key owns a thin root actor whose admins are a few persons; teams, chats and docs are owned by the root or by actors under it. Root admins can roster-snapshot everything below and remove anyone, and a departing founder is just an admin removal. A team owned by a person actor cannot shed that person (owners are un-removable).
- **Shared tag** (rights live on edges, never on grouping; owners never change; notes/tags.md): the tag is an actor; things keep their owner and each gets an edge for the tag's actor (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same edge so rosters nest; writers may also create things owned by the tag. Per-member edges on each thing do not work: entitlement puts a thing under the tag's label only when the tag's actor may read it, so no label the members sync would carry it. Built in crates/osis-std/tests/tags.rs.
- **Chat**: see notes/chat.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a label stamps with its write key, so a shared space's participants are writers of its actor; what they write is bounded by entitlement and ownership (each owns its messages), and `/group` vandalism by a writer is repaired deterministically by honest clients.
- Sync groups and owner actors stay separate; a group may also be an actor when it serves as a shared label.

## Purge rights and retention
Retention is per delta (spec/commits.md §5), decided with the owner. Default `author`: any writer can already destroy live state, but letting any writer purge by default would make vandalism of kept history irrecoverable; purging your own deltas gives no power you lacked by not writing them. `writer` is for aspects whose history is disposable, and a relative keep-at-most implies it. `nobody` is for records that even admins must not drop. `admin` is what membership commits use. Purge rights are judged at the request's time, so an author who lost write on the thing can no longer purge its old content at honest nodes (owner's call; servers approximate it, notes/sync.md). Keep-at-least binds compaction but not purge requests, so "history never compacted, authors may purge their own" is `author` with at least forever, and a deliberate purge is a signed commit while compaction is routine, which the protocol already tells apart. Fields are immutable: a change would need the blob re-encrypted anyway (tokens are fixed by blob ID), so purge and re-write; the price is that dead history cannot be made more permanent after the fact (apps export to a new permanent thing). Residue: a delta by another author that carries part of the content (a typo fix inside pasted text) needs that author or an admin. A purge also voids the write inside every snapshot carrying it, else the compactor's copy would outlive it.

## Public content (pattern; needs no core mechanism)
A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a trusted node holding only the public label's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by the blind node (server stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: author chains under the label become public and permanent, so a public label may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing (discussed with owner, not a priority)
Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous member: a fresh actor with its own owning key and device keys, joined via a link or grant; the granting admin may record pseudonym -> person in admin-only data.
- Known writers, unlinkable edits: group X holds the signing key of key actor A, which has write on Y (cleaner: A's key derived from X's role secret). Members write as A in commit form. Caveats: any member can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a trusted node re-signs members' edits under its own identity.

## Implementation (osis-perm)
- Input: the node implements `HeldSet` (things, membership commits with an edge write per thing, roster snapshots, `/created`; applied commits only, pending ones not) and adapts headers into `types` records (edge ops with their `/members` dots, frontiers resolved from links, rosters and ledgers). perm parses no bytes, holds no state, depends on osis-core only. `/created` that does not hash to its tid is ignored.
- `Timeline::evaluate` is the from-scratch walk (`walk.rs`); queries take `At` (state before a point, edges alive at a ts; `At::END` = current state at the end of time, where re-grant is judged): `roster`, `role`, `invite`, `class`, `standing`, `applied`, `dropped` (with the dropping demotion's point), `epoch_start`, `demotions`, `delta_valid` (layer 2), `roster_state` (production), `certificates`/`write_certificates`/`certificate_set` and `verify` (§4), `may_purge`, `may_rotate`, `may_write_membership`, `has_standing`/`resolve` over a node-supplied `MoveIndex` (§7), `demotion_scope` (what a demotion's frontier must cover; the node fills counters from its receipt record).
- `Timelines` (incremental): components of things joined by edges, authors, ownership and snapshot rosters, each evaluated from scratch and cached by its exact inputs; `changed()` lists the things whose component the last update evaluated (plus `update_touched` below; the node re-judges only deltas on those, plus commits whose void, required-role or overreach inputs changed; everything after a rebuild at open; a debug assertion checks the rest is unchanged). A component that only gained membership commits continues its walk (`Timeline::extend`: same things, `/created`, snapshots and nodes, and if epoch starts ever changed no membership cycle through a snapshotted thing): the final walk rolls back to the earliest new commit and goes on, provided no other walk reached that point (`reach`); else from scratch. Equal to one evaluation (random and timeline-order arrivals incl. snapshot-model histories, 2000 samples, dropped points and roles before every applied write compared). Point queries start from an edge state kept every 256 history changes (`checkpoints`); `delta_valid`, `first_held` and roles at `At::END` are memoized per timeline.
- `update_touched(held, touched)` re-partitions only the components of the touched things and those newly linked to them (equal to `update`, tested by `incremental_equals_from_scratch` in both modes) and returns `Changed`: components evaluated anew, and for those whose walk only went on or that only gained new leaves (`/created` of things nothing else names, reusing the timeline with the new owners) the things touched; the node re-judges below those only (notes/node.md, Validity).
- Walk cost (`walk.rs`): every state change logs its inverse with a mark per item (`Undo`, `rollback`), so a walk that grows D resumes at the first write D now skips (a walk with the larger D is identical up to there) and `extend` rolls back. Per-node `roles_from` is cached across writes (`Pass::roles`), dropped only when an edge change may narrow it (`widest_changes`: the old edge was as wide as the node's role on the target) or an edge it followed expires, raised in place when an edge widens (`roles_raised`). `audit_fall` reads every candidate X's role on the member, the target, its invite-holding members and its owner chain from one backward search per thing (`roles_to`, `roles_to_any`), and searches forward only for an X the restored edge raises, comparing standings only where the raise reaches. Measured (`tests/bench.rs`, org of 311 nodes, 221 things; the bench holds no roster snapshots): 10^4 edge writes from scratch 0.45-0.8 s (4.3-7.5 s before; same box, loaded 10-25 on 16 cores; main 4.5-5.1 s), 10^3 5-8 ms (63-78 ms), a late write in the middle of 10^4 0.36-0.6 s, one more write 30 ms, 1000 deltas judged cold 11 ms. Callgrind, 10^3 writes: `walk::run` 847M -> 141M instructions after the cache (main 831M); owner chain at depth 64 1.3-2 ms (0.8-4.7 ms before, noisy). Chain certificates (`cert.rs`, what a demotion frontier lists): commits looked up by (member, target) in an index built once per timeline (`Memo::certs`) instead of scanning every held commit per chain point, and the closure takes points latest first, building the edge state when the point changes (again for a point it returns to after a step queued a later one; a map of all states was slower, memory); bench `OSIS_BENCH_N=10000` (347 certificate commits, box at load 20-30, interleaved runs): before 1.0-2.9 s (1.3-2.9x a from-scratch evaluate), after 0.14-0.37 s (0.07-0.4x); at 10^3 about 4 ms either way. Left: an edge-state copy (O(edges)) per point change. Adding the node's chain at each later lowering write (§4, demotions judged with the node's other paths) costs about 10x the closure states at 10^4 (674 -> ~6500 before filtering): taken in rounds (one visit per point per round), `reach_backward` cached per point, and only for writes whose member the node can reach (itself, an actor, or a key actor with edges on it); 0.9-1.9 s against 0.14-0.33 s before, interleaved runs at load 30. Epoch-start rounds cost (depth of the snapshotted chain + 1) full walks per history plus D restarts; measured at review with 21 snapshotted things x 2 snapshots at 10^4 writes: 2 passes, from-scratch time within noise of main.
- Certificates: things on the chain are those on any path from the node to the thing at the point; "every held demotion" is taken as every held edge write between two chain things and every roster snapshot of one, at any time, applied or not (a dropped demotion can still have dropped a write: drops are sticky), each with the node's chain at its point (without it a removed edge looked like a fall where another path, granted after the write, kept the class; joint seed 4 of `certificates_project_joint_large`). Projection agreement holds on 20k joint and 20k edges histories, sticky residue skipped (`tests/queries.rs`).
- Purge `author` right: the actor the delta's commit acted for (header field 2; an import's origin), held by any node with write on it while it has write on the thing.
- Readings of §5.1 the code fixes (the models were aligned to them):
  - R demotes X on N when R is an explicit write (applied, not a self-removal or invite grant; or a ledger tenure end with a frontier) on edge (M, T), X reaches M (or is M), N is reachable from T (edges of any role and `until`, owner links), and X's class on N is below its class with the edge restored "as if the member still held the role": the join (componentwise max, alive) of the edge's values since the last explicit write on it, plus, for a node that lowered it by its own write, that node's values before. A value already expired when written restores nothing. So a gap left by `until` or self-removal is finalized only by the next explicit write on that edge (not by any write concerning X; the per-node "held class" of the joint model cross-wired things and broke compaction neutrality). The models were aligned.
  - A's chain writes: the writer adds the commit IDs of `Timeline::certificates(A, target, R's point)` (membership commits and snapshots) to the frontier (`flows/edges.rs`), and a frontier's commit IDs cover node-form writes too (`Frontier::covers`). The walk exempts nothing but R itself.
  - A write of an edge for the target's owner (node or actor) is no write.
  - Self-removal: lowers the edge in every component, author admin of the member, and either the member is the author or the author has no owner-chain or edge-admin authority on the target (spec §2, decided at review: removing one's group from a doc one also owns is an explicit demotion that audits the group's admins); a redemption's (author is the member, holds only an invite, commit has another op) is attributed `Invite(level)`.
  - Epoch starts (`drive` argues termination; spec §6 states the rounds as an algorithm): every snapshot is judged at its position like an owner-chain edge write (`candidates`, audited and droppable like one), whether or not it is its thing's start and even when ordered before the start; only a round whose walk has settled D chooses (each thing's newest applied snapshot); D is rebuilt per round. Earlier snapshots are judged (not ignored like earlier edge writes) so a thing's choice never depends on its own current start: otherwise an older snapshot's drop would be found only once it is the start, and the rounds could oscillate even without cycles. Unless owner-chain authority on a snapshotted thing may come through the thing itself (`Input::cyclic`: owners and members holding an admin edge at any time; an invite of admin needs an admin edge), the rounds reach the unique fixed point by round T+1 (T snapshotted things) from any starts, which lets `extend` go on from the old starts. With such a cycle a start can withdraw its own author's authority: if round T+1 since the last restart has not settled, the snapshots that are a start in exactly one of its starts and the next are excluded (never lifted, at least one) and the rounds restart from none, so at most snapshots+1 restarts of at most T+1 rounds; no pass cap. History: a chosen start found inapplicable mid-walk (D not settled) used to be rejected until a start changed above it, and the rejection stuck when the write that caused it was dropped later (a few in 10^5 snapshot-model histories broke neutrality; `start_after_dropped_write_spec_permissions_6`). The exclusion fires at a round limit rather than on a repeated assignment: no assignment history, and a polynomial bound with no pass cap (between repeats the rounds can run exponentially long in the snapshotted things on a cycle); a repeat is caught anyway, since it means the rounds have not settled. Caveat: with a membership cycle, a round sequence that would have settled after round T+1 still gets an exclusion at that limit; deterministic, and reachable only through forged or stale-view snapshots, since honest snapshots do not create cycles.
  - Before its start S, N's edges are virtual writes from S's roster and ledger at their keys (placed just after the commit at that key, whose writes on N S ignores: that commit's writes on other things are judged as in the full history; a two-target self-removal plus grant showed the difference). An entry with a frontier is an explicit demotion by its key's node (exempt and keeping its standing as the author of a real one), audit-only entries included; where the roster edge takes over at that key without starting there (contradictory data), the tenure ends first, then the roster re-grants. What it restores comes from the replay itself (prior values of no-audit ends, the demoter's kept standing), as in the walk. Ledgers written before this rule (a later demotion's frontier carried on a tenure keyed at its end) now read as a demotion by the end's node, which is then exempt: no deployed data, so not migrated.
  - Production (`roster_state`): the previous start's ledger whole, then per member every write+ tenure ended since (per role level: a promotion ends a write tenure without a frontier); an expiry inside the history ends a tenure at (first ts at `until`, zero tid and zero commit ID), so it orders before every write at that ts as the expiry does in the walk (the member as node ordered it after same-ts writes of smaller tids); an edge never in force (expired when written) gets `since` = its write's key. Which writes audit, and from what role, comes from the walk (`Change::audited`: an explicit write whose restored edge, the demoter's kept standing included, exceeds the new value): such a write gives the tenure it ends its frontier (empty if none); with no tenure in force it is an audit-only entry (`since` = `until` = its key); auditing from above the role in force splits that tenure. Expired edges stay in the roster with their `until`. The replay equals the walk except: read edges carry no `since` and read-level tenures and audits are not in the ledger (spec keeps it to write+), so invite authority through a read edge on an actor before the snapshot, and a read-level fall's audit, are not preserved (rare). Keys are full points (`ts`, node, commit ID; perm's `Point`, the core `edge_key`): with (`ts`, node) alone, two commits of one node at one ts (one key used from two devices) that demote and re-grant a member were one key and replayed as no demotion (models/tla/membership M3; `same_ts_demote_regrant_replayed_spec_permissions_6`). The commit ID over a per-key sequence: it is intrinsic to the write, so every node computes the same key whatever else it holds, while a sequence would depend on which same-key commits a node held and their order; it costs 32 bytes per key.
  - Frontier coverage: a node-form range is covered when its last counter is (`>= hi - 1`); an empty range (import) only by its commit ID.
- Layer 2 (`content.rs`): re-grant (role at `At::END`) validates writes from the start of the author's first tenure of the required role on the thing ("valid again"; earlier writes stay invalid); else held at the commit's point and no later explicit demotion below the required role; else the newest such demotion's frontier decides (literal: a gap write covered by the newest demotion's frontier is valid). Deliberate (decided at review): a write after `until` or a self-removal is invalid until the next explicit demotion, whose frontier then decides it, §5.1 "as if the member still held the role". Overlapping node-form `/members` ranges void both commits inside perm; the node voids those overlapping on other aspects (`overlapping`).
- Neutrality (`tests/roster.rs`): re-snapshotting any thing of random joint, edges and snapshot histories at the end, with `roster_state`, changes no roster, applied write or layer-2 answer, compacted or not (0 of 20k joint, 30k edges, 30k snapshot histories; asserted). Sticky residue (`common::sticky_residue`: a drop whose cause was dropped) may change, but only by undoing drops (asserted; a snapshot may repair it, MC_sticky_snap; none met in those runs). Same-key commits (two commits of one node at one ts) are included since keys carry the commit ID. History: the ledger used to carry a later audit's frontier on the tenure it audited and replay it at the tenure's end, nobody exempt; about 1 snapshot in 10^3 changed an answer.
- Differential (`tests/differential.rs`): joint and edges models agree exactly on 100k histories each (edges: projections too); the snapshot model (keys (t, node, write id), sometimes two writes of one (t, author)) on 50k with compactions and projections, except sticky residue (a drop whose cause was dropped; under 1 in 10^4), where the two-level model settles P before walking G and so discovers drops in another order than the joint walk; those are skipped. The harness leaves out the model's random ledger entries ended by the member's own node: that end is a self-removal (§2), never an audited one, and perm, reading it as the explicit demotion §6 says an entry with a frontier stands for, lets the member keep its standing until the next explicit write audits it (§5.1 step 4), which the model (no self-removal) does not do.
- Open: the model's library exposes walks and generators but no named scenario list (its scenarios stay `#[cfg(test)]`); counterexample shrinking and quiescence checks are unbuilt (issues/tests-unbuilt.md). Value conversions of `edge`, `tenure`, `frontier` to and from `osis_core::Value` belong to the core aspect types (osis-schema `core_types`); perm takes decoded records.

## Implementation (membership flows, osis-node `flows/` and `rotation/`)
API and engine hooks: notes/node.md (Flows, Rotation). Readings:
- A person actor is created in one commit signed by its fresh recovery key (both creation records, the key's `/keys`, the person's own secrets boxed to the key and the node, `/keys` with inbox and deposit seed, the home label's genesis step listing the key by static entry, the node's admin edge); the seed leaves only in the card. Held key actors (`hold_key_actor`) sign in commit form and open their boxes; nothing persists them.
- Pairing is a direct grant (or, for a device already a member, a re-seal) plus every commit touching the person, its owner and both nodes, as one direct send.
- A grant first gives the target, and a plain member, secrets of their own, runs the cascade on the target (boxing is encrypting under) and boxes every granted role's current epochs. Authority: admin on the target, else an invite grant (no current edge, role and invite at most the effective invite), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own edge or the author's authority on the target comes only through the member (admin on it); it carries no rotation (the next node that may rotate does) and the leaver drops what it lost. Otherwise it is an explicit demotion with the frontier from the receipt record (as of now, or a backdated time) and the pre-sync choice, carrying the target's rotation of the roles the member left. A removal of an absent edge (finalizing a used single-use link) resets the member's dead entries and audits the member's writes on the target.
- Departures are read from the timeline and from the boxes held at current epochs (scenario tests: the two-hop cascade rotates T then U; a member re-granted since drops out of the list) and cached per actor (`Core::departures`): cleared by `Core::membership_changed` on any membership-class state write, timeline update, held-epoch change or key-actor hold/drop, and valid until the next edge `until`, future write or roster snapshot `ts` of the actors walked.
- An epoch's introducing commit (`Core::epoch_intro`, the covers rule's "introduced by a departed party" and the key-actor `carries` test) is the earliest valid commit boxing it or writing its keyset in `/keys`: an epoch boxed to key actors only (a person actor's devices and recovery key) is keyed at their top role, so only the keyset names it. `Core::box_written` keeps each box's first write: a later rewrite (re-seal, grant) ordered after an epoch need not have held it (a concurrent fork). Both are noted from valid membership-kind parts at apply; `load` notes every part, then `rejudge_all` rebuilds an actor's entries (`keys::rebuild_intro`) whenever a `/secrets` or `/keys` part of it flips, so an invalid (backdated) write never introduces an epoch.
- Roster snapshots: the writer splits the replace into a reset-only delta and one delta per edge and per ledger entry (`Fragment::split_entries`, `Resolved::split`); a tenure frontier above `CHUNK_THRESHOLD` becomes a link (`large::chunk_frontiers`; set elements are registers holding the whole tenure, spec/crdt.md §3.2); the writer refuses a ledger above `MAX_LINKED_FRONTIERS`. A receiver (`validity::linked_frontiers`): reads each distinct link once (by content hash; `Core::frontiers` in memory, `n/` records durably, so `load` never depends on the tree blobs), within `MAX_LINKED_FRONTIERS`, only through blobs in the commit's chunk list (else bad input), and waits (`WaitBlobs`) for listed blobs not held unless a later epoch start of the thing is applied (then that thing's snapshot stays out of perm). An applied snapshot whose frontier is neither recorded nor held (store loss) stays out of perm for that thing (diagnostic, `Core::frontier_unknown`) and `roster_snapshot` refuses the thing: never an empty frontier. A member named in two `/members` deltas is bad input. `Engine::certificates` returns parts per (aspect, delta): a snapshot is projected to the deltas naming the chain's members plus the reset-only ones, so a snapshot naming no chain member still arrives as an empty-roster epoch start, as perm's `certificate_set` projects it (`project(s, ∅)`); a snapshot that cannot be read here is not placed (diagnostic). node-sync places a copy's linked blobs (header lists, linked frontiers) under the label with it (`place_linked`).
- Contact cards stay in the osis API (`contact_card`): the card is a composition of calls flows already has (a group thing written through the API's placement, its own secrets, a label, certificate placements, a read link) plus the API's local record of the card; a flows call would only move that orchestration below the layer that owns placement and sync.
- Re-seal and registration are pull hooks for node-sync (`reseal_due` at the end of a complete pass, `issue_step` per server head); flows only return deliveries.
- Tests: `crates/osis-node/tests/flows.rs` (person and pairing, grant by inbox, removal rotates, invite power, demotion frontier with pre-sync choice, mutual removal, two-hop cascade, stolen-device recovery from the card, link redeem and single use, bearer and `until` with finalization, re-seal of a raced grant, key-actor members not re-sealed, departures following the clock, stranded device re-paired, registration step after rotation, roster snapshot with per-edge deltas, projected certificate and linked tenure frontier, move with re-grant).

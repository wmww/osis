# Permissions: concepts and patterns
> Summary: Tess's direction for permissions, the concepts (terms, holders, roles covering edit and act-as, equal admins, nodes, the `sync` role), sharing, usage patterns (grant, shared holder, root thing, shared tag, chat), the last admin (the writer's check and the adminless mark), public content, anonymous writing, admin-only aspects. Map of the other permission notes at the top.

Principle (Tess's direction): **a small set of concepts that compose**: hierarchical; keys for nodes, holders and other scopes; private keys wrapped to a target to grant access; a set of things shared with a changing set of holders managed in one place; nested holders (tess -> tess-human, tess-agent) possible but not baked in. UX vocabulary stays familiar: admins, editors, viewers. Rights live on grants, never on references.

## Concepts
- **Terms** (Tess; spec/permissions.md §1): rights are roles given by role grants, and a thing with a role is a holder ("Dana holds write on X"); a strong says a thing belongs to a closure ("Work holds this note") and grants nothing (notes/node-closure.md Design rules). One word per sense in code, API, CLI and spec; a CRDT set's value is an element, a `Slots` entry a slot.
- Any thing may have holders: people, agents, organizations, shared documents, a single shared note; it becomes independent when it first needs holders of its own. Identity is the tid, so keys rotate freely.
- A role on a thing covers both editing the thing and acting as it: only the role-class aspects would differ, and they are admin-gated anyway. Split only if an example needs writers who may act as the thing but not edit its profile.
- Admins are equals; seniority ranking was rejected (unintuitive, leaks into UX). A hostile admin is out of scope beyond per-node sides in a fight (notes/disputes.md).
- Not promised, so not in spec/requirements.md: anonymity against network, timing and style analysis; revocation reaching a thing's holders before one of the revoker's nodes next syncs it.
- What a commit spanning two things reveals to a reader of only one (Tess's wording in spec/requirements.md: no values, only metadata): the exact metadata is spec/wire.md §4's, and may change there without Tess's sign-off.
- A node signs as its node thing, minted with its key (spec/sync-set.md §1 Node thing); readers dial nodes by their entries in `dial.0` lists (spec/sync-set.md §1, notes/networking.md decision 4). Rejected: a thing of nodes readable by contacts (leaks the node roster).
- **Role `sync`** (below read): a role with its own secret and epochs like the others; the sync ID's sync key derives from it, so a holder of only sync opens, holds and serves a thing's sync IDs and reads nothing. It takes no carve-out: the roles are a total order, so grants, may-grant (a reader with the flag grants read or sync), departures (a reader's leaves sync too), rotation (a writer rotates sync, read and write) and boxes are the same rules over one more level. Lost access per role: a node left holding only sync keeps the sync secret and drops the rest (`rotation::lost::over_held`). Cost: every rotation of read also rotates sync, one more box per holder (about 1.2 KB; with only readers the sync boxes are half a reader removal's bytes). Open: readers could derive the sync secret from the read secret's history instead of a box each (cheaper, but removing a sync holder would then need a read rotation).

## Sharing
- Sharing never changes a tid or mint admin. Moving a thing is a grant then a removal (notes/moves.md).
- One note: a grant on N, explicit secrets on N, N with its own sync ID. A set: an independent thing with holders, strongly referencing each thing and granted read on each (one grant per thing, one commit). A set meant to be shared as a unit is better minted with one common admin.
- A strong grants no rights (a grant on a thing extending to what it references was rejected). Checked against the patterns: shared folder, own folder without secrets, chat all get the right sync IDs.
- Rejected: a separate holder thing per thing at creation (doubles thing count); a grant-set thing listing shared tids (a verifier could only check N's writes after syncing the set); per-thing derived content keys plus an encrypted hint per blob (24 bytes cheaper than a wrap, loses crypto-shredding and add-a-wrap sharing).

## Patterns
- **Grant on a thing**: ad-hoc share of one or a few things (the thing becomes independent: about 2.6 KB of boxes per holder, so not per note in a folder).
- **Shared holder** (spreadsheet): one thing is the mint admin of everything, all writers edit everything, removal by the frontier rule.
- **Root thing**: a minimal root thing whose admins are a few accounts; an organization's shared spaces, chats and docs are minted with the root, or with one of its dependents, as admin. Root admins can remove anyone below, and a departing founder is just an admin removal; a shared space can shed the account that minted it (its mint admin is an ordinary admin).
- **Shared tag** (notes/tags.md): the tag is a holder; things keep their record and each gets a grant for the tag (a few KB of secrets per thing, a lazy rotation per thing per roster change), sub-tags get the same grant so rosters nest; writers may also mint things with the tag as admin. Per-holder grants on each thing do not work: entitlement puts a thing under the tag's sync ID only when the tag may read it, so no sync ID the holders sync would carry it.
- **Chat**: notes/chat.md. **Realm** (design): notes/realms.md.
- **Participation needs write** (spec/requirements.md, Permissions): anyone who posts under a sync ID stamps with its write key, so a shared space's participants are writers of the space's thing; what they write is bounded by entitlement and their grants; a writer removing a strong releases what only it held (spec/sync-set.md §3).

## Public content
A pattern; needs no core mechanism. A public site off live osis data needs something holding the key to render. Default: (B) a rendering gateway, a node holding only the public sync ID's read secret, serving HTML. Also possible: (A) bearer link plus a static JS reader served by a node keeping it unread (it stays blind, invisible to search engines); (C) publish the read secret so anyone can run a gateway. Leaks: the certificate copies under the sync ID (who wrote it, along which paths) become public and permanent, so a public sync ID may want a dedicated publisher identity that re-signs snapshots; deletion is best effort.

## Anonymous writing
Discussed with Tess, not a priority. Needs no new machinery beyond commit-form dots. Network, timing and style leaks apply to all.
- Pseudonymous holder: a fresh holder with its own node keys, joined via a link or grant; the granting admin may record pseudonym -> account in admin-only data.
- Known writers, unlinkable edits: X's holders share the key of a thing A minted with it, which has write on Y (cleaner: the key derived from X's role secret). Holders write as A in commit form. Caveats: any holder can purge any A edit; offline A edits the revoker had not received die at A's revoke, so clients re-sign pending ones; undo uses locally remembered own commits.
- Re-publisher: a node the holders trust re-signs their edits under its own identity.

## The last admin
Principle: **a thing goes adminless only by a write that says so** (Tess). A standing admin is a direct admin grant on the thing with no `until`, the record grant included (a timed admin grant is a removal already written: counted, a thing would go adminless on a date with nobody saying so). Built as the writer's check (spec/permissions.md §1): `apply::validity::leaves_no_admin`, called from the writer rules of every local role commit (`check_content_rules`), so every flow writing grants (removal, demotion, self-removal, `until` by grant, link revokes, redemptions, finalizes) goes through it; the adminless mark (header flags bit 1, spec/wire.md §4) lets it through: under `Engine::leaving_adminless` each commit that would otherwise be refused carries it, and no other (at A1 the mark will mean "this commit may leave a thing adminless", so it must not ride on side commits), `osis`'s `leave_adminless` option on `grant`, `set_role` and `leave`. It reads only the target's own grants: an audit drops nothing its writer holds (the frontier lists it), so no removal leaves another thing adminless at its writer (`flows::a_removal_by_audit_keeps_what_its_writer_holds_spec_perm_1`).
- **Readers judge nothing by the mark**: there is no last-admin rule every node judges (Tess). Two concurrent leaves (each seeing the other standing) leave a thing adminless, as a deliberate leave would (`flows::concurrent_leaves_leave_no_admin_spec_perm_1`); two admins removing each other leave one (the earlier removal applies). What such a rule did for a remover's own path, the writer's leaving out does (notes/write-path-design.md §1, L3; notes/path-model-findings.md 46).
- An adminless thing: holders read and write as granted, nobody grants (but by may-grant grants) or writes admin-only aspects, nobody destroys it by request (purge needs admin); only its record's `expires` ends it.
- A sharer leaving a thing reached through its own link would leave the link's actor K adminless (K's only admin is its record grant): `Osis::leave` refuses before writing anything unless meant.

## Admin-only aspects
Tess's AK format decision: the `^` marker in the AK (spec/data-model.md §2); a delta of one needs admin, judged by validity like content with admin in place of write (spec/permissions.md §5.2), from the key alone: no wire bytes, no schema. Engine: `write::required_role` (local refusal, layer 2, snapshots via `snapshot_role`, ephemeral parts); osis-perm's `delta_valid` takes the required role. A demotion's frontier covers `^` aspects with the role-class ones (`Engine::frontier`; without it an admin demoted to write lost every `^` write, covered or not). The roles-model's content model abstracts the role threshold, so it covers admin alike. Tests `validity::admin_only_*`.

## Role history
- `roles.0` is never compaction-snapshotted: every role commit stays, and a node that starts holding a thing fetches and judges all of it (spec/requirements.md Scale states it). `secrets.0`, `keys.0` and `sync.0` compact like any aspect (compaction snapshots page, so the boxes and steps of a thing with many holders never have to fit one delta).
- Bytes: 364-371 B per role write, plus 34 B per commit a frontier lists. A 1000-member chat after a few thousand joins and leaves is about 10^4 role writes (3.6 MB). A joiner ingesting them one by one does counted work linear in the history, and a write at the end of it and its arrival flat work: perm places each arrival without walking, and the node re-judges only the commits `Changed::reached` names. Evaluating the timeline anew was 1.5-2.4 s at 10^4 (release); the wall time of a 10^4 join on the flat per-arrival paths is unmeasured.
- The `roles.0` state keeps a tombstone per ended entry (spec/crdt.md §5.6, never compacted) and pages once its records pass 3 KB, then a write costs its pages; a tombstone keeps its holder's key (role-class, spec/crdt.md §5.6), so a write about a holder loads every record of that key (notes/crdt.md, Values as read): O(that holder's grant history on the thing), flat in the others' (`scale::role_history_join_is_linear`). The tombstones are the same order as the role commits kept forever. Nothing reads that state (the roster is the timeline's, `Engine::get`), so dropping it is the fix if it ever matters.
- **Rejected: roster snapshots** (a record-chain roster snapshot with a lgrantr of ended tenures and their frontiers). Every write+ tenure and frontier had to stay forever (a write anywhere below may rest on any of them), so it saved only 1.1-2.6x for writer rosters (20x only for big read rosters), a kick-heavy roster at 10^4 could not write one ("the commit does not fit a blob"), a chat's took 294 CPU-s to write (release), and it cost epoch-start rounds, linked frontiers and a second residue class. A join is O(role history) with or without snapshots (the lgrantr is), so the Scale item on permission history is needed either way. Linked frontiers save nothing in these shapes, since each kick lists the kicked member's own commits, disjoint. The frontier that does grow without bound is a single kick of a heavy writer (`TooLarge` at 3*10^5 commits).

# Sync: leave
> Summary: osis-sync's `leave` module (core/sync/src/leave.rs) and the engine's `forget_local`: the one owner of "the sync IDs this node syncs" (the sync set plus each leaving sync ID while it waits), the wait rule for read and kept-unread leaving, unsyncing's forget, its costs and state.

Spec: spec/sync-set.md §3. Overview: notes/sync.md.

## What this node syncs
One value: the sync set, and each sync ID that left it while it waits to stop. `leave` alone follows the engine's sync set (`set::SetFollow`, per key) and writes the value into the store (`Store::set_holdings`, stamped per S, fed by `Store::syncs_feed`). Every other module follows the store's value, never the engine's sync set: store, opens and dials by their own `set::SyncsFollow`, unread by its own, status by `Store::syncs` whole, read, streams and inbox by `Store::synced`/`holding`. So a waiting S stays open, served, logged into and judged exactly as before (spec: "stays a member of its shared sets as before"), with no per-module case. `leave` settles first in each round, so no module ever sees S drop and come back.

The engine side answers for a leaving S by its thing's held read secrets, not the sync set (`Engine::opening_thing`: the thing reading S, else S's owner while a read secret of it is held): `read_credentials`, `claim_key`, `open_entry` and `dial_peers` (as read) go by it, `sync_bodies` by `thing_sync`. So an S that left because its thing reads plain for now (an outsider's grant judged unlisted until a rotation's thing list arrives) or that a removed reader still holds the secrets of (the drop waits for the same pass, notes/engine-lost-access.md The drop) is opened, proved and dialed as before until its pass ends. A node removed from its account holds read secrets through that pass but writes nothing: `wrap_blocked` blocks every wrap and `pass_end` does nothing without a writer, so no settle fails for want of one. Certificate bodies and the pass wants (`passes_wanted`, `forget_unread` at the start) still go by the engine's sync set: a waiting S gets no new certificate copies; its own writes are what it waits on, and those are content bodies.

## The rule
- One derived value: the sync IDs out of the sync set that this node syncs or holds rows of, each an `Effects` key judged (`leave::judge`). The first settle wants every stored one (`Store::held_ids` and the synced entries: what a start, or a restart of the modules, finds), later ones each S the sync set loses (`SetFollow`); there is no separate start sweep.
- S has left when it has an entry (as synced, else as this node's keys hold it, `Engine::sync_holder`) and this node has joined an account (`Engine::sync_rooted`: before, at pairing, its sync set is empty for want of a synced group; a node removed from its account since has none either, and everything it syncs leaves). With neither (another account's inbox this node deposits to) it is left alone. Its entry and the pass place it left at (`Engine::pass_place`) are noted then (`leaving`), and it stays synced (rows found at a start are synced again).
- First, whatever made S leave, a complete pass of S begun after it left (spec/sync-set.md §3): status runs one (`Leave::passes_wanted`, by pass place) and leave reads `Status::passed_since`. Same rule for every cause.
- Lacking a list is waiting: when the keys no longer hold S after that pass and a role commit on S's thing is held uncounted (`Engine::uncounted_role_on`: its epoch revoked by a removal, no thing list naming it held yet; an outsider taking the rotation before its lists, from a Prove or a header-only copy), leave waits once more (`Left::sourced`): a pass begun at that judgement that status ends only once some source caught up (`Status` `pass_sourced`: no pass of S ends with none, nor by `PASS_WAIT_MS` alone; after that, as any pass, so a silent hostile source holds it no longer), then judges again. Only while S's thing is in the closure (`in_sync_things`): lists cannot give back an unsynced thing, so an unsync, or this node's removal, ends that wait at once. A source joins because S stays in the shared sets while it waits. Why not wait in the engine: an outsider cannot tell a list not yet arrived from one never written (a removed device's backdated write); keeping only the sync ID through one pass with a source counts nothing meanwhile. Why a source: with the account's records proved at the revoked epoch and its role on the thing uncounted, no peer is to be waited for, so a plain pass ends at once in the step the rotation arrives (before the peer's re-proved connection opens S). With no source ever, S waits, as for a peer away (it keeps only the sync ID and its rows, counting nothing meanwhile; a restart waits afresh).
- Then: this node's keys still hold S as when it left (`sync_holder` equal); else it stops at once (secrets lost, a removal, still plain: shredded, nothing forgotten). Read: each own commit with an entry under S (`Engine::own_commits`) held elsewhere by status's durable mark on one of its entries (`Store::elsewhere`). Kept unread: each own entry present at a source (streams' `Sources::present`). Either way also done when no peer is to be waited for on S (`Opens::waited`, notes/sync-opens.md Peers to wait for). A self-removal's wait is the same rule, own nodes skipped (notes/sync-status.md Self-removals). Done: every S that stops in one settle is collected; the read ones' things go in one `Engine::forget_local(things)` first (one forgetting however many left at once: unfiling a group of k separately shared things), then this node's own entries of the commits that forgot whole (the blobs `forget_local` returns) are unlogged under every sync ID naming them (`Store::naming`: no judgement reaches a commit no longer held, and the store parks an own entry whose commit is not held, so a later start would reopen and bring it back); then each S `Store::shred`, then not synced. A crash between forget and shred leaves the rows, so the start redoes all three.
- Synced again before it stops: the wait ends, nothing goes.
- State: per sync ID out of the sync set with rows or an entry, one key, and per leaving S its entry and place; bounded by the sync IDs the store holds rows of; nothing durable (the store's rows are the truth after a restart; a restart begins the wait afresh, with a new pass).
- Cost: a sync set change costs what moved (`SetFollow`); a leaving S is judged when its own commits, marks, presence, keys or peers move, O(own writes under S + records holding S).
- A restart of the modules (the engine read its store again) must not see things leave that did not: the engine keeps its followed links across a reload (`load_fresh`), as it keeps the key actors they hold, else the sync IDs of links being redeemed would leave and wait a pass at every reload.
- A start follows the sync set whole before anything is judged left: the driver starts inbox first (`Inbox::start`: links being redeemed followed again, `Engine::follow_link`, which puts things in the engine's sync set), then has the engine let go of what it kept for sync IDs not read (`Engine::forget_unread`: passes, certificate blobs), then settles leave. Judged before, a contact's profile read through a link left at every start, and its certificate blobs were sealed again (`growth::a_quiet_start_commits_nothing_at_n_and_10n`).

## forget_local (engine, core/engine/src/sync/mod.rs, retention/forget.rs `Scope::Local`)
- Forgets the things given and each thing whose secret actor is one of them, but those the node's closure holds (`Engine::node_closure`: the synced group's and each shared thing's) and those that stay local (`Core::stays_local`: the account wrote a grant on it this node never unsynced, so a share that ended keeps the copy, spec/requirements.md "shared with no one, stays local"; a revoke must not delete the user's thing) (a plain thing listed elsewhere still syncs under that group). Same machinery as lost access (`retention::forget::forget`), fate `Local`: everything an erased thing loses but `secrets.0`, so the thing stays read and syncs again when listed; commits left with no part are deleted and fetched again, others keep their other parts (late parts join). Event cause `Unsynced` (`DerivedFrom::Unsynced`). A commit that also wrote a synced thing (a creation commit adding the thing to a synced group) stays, and the forgotten thing's part of it joins again when a peer serves that commit again under the synced group's sync ID, so the forgotten thing can show that commit's values. The rule: after unsyncing, the thing shows exactly what any node syncing only this node's synced group shows (what still reaches it under a synced sync ID), never anything only its own sync ID carried (core/osis/tests/it/sync.rs `an_unsynced_write_goes_out_before_the_copy_goes_spec_sync_set_3`).
- A thing under `t`'s secrets still in the closure syncs under `t`'s S, so S stays in the sync set and `t` is never unsynced; the closure exclusion matters only to a direct call. Things known only from pending commits are not named (their parts stay pending).
- Cost: the engine's forgetting is incremental, as for lost access (notes/engine-lost-access.md, Forgetting): the commits on what left, no reload; once per settle, not per thing. Sync's unlogs cost the blobs of what forgot (`leave::leaving_several_forgets_once_and_costs_what_left_at_n_and_10n_spec_sync_set_3`: forgettings, unlogs and commits looked at flat in n, the indexes agreeing with an open, the own-commit rows of the stopped sync IDs gone).

## Reasons
- One value every module follows, written by the module that owns leaving: a per-module "also synced while waiting" would be a carve-out in each, and two writers would let modules disagree within a round.
- Any thing, admin or not, goes when unsynced: unsyncing means "not on this node" (Tess). Unsyncing everywhere the last copy loses it; stated in the spec as the behaviour, like deleting a local file.
- The wait guards only this node's own writes: a peer that never got them would lose them. Everyone else's are someone else's to keep.
- Status's durable mark, not stream presence, for a read S: a reader source shows what it holds by reported positions, which status already folds into the mark.
- The wait lasts only while a peer could take the writes (Tess: unsyncing drops the copy, own unsent writes go out first, nothing gets stuck). No peer to wait for (a lone node; no roster naming another holder; each such peer told of S and not sharing it, or its records gone): it stops at once, losing writes held nowhere else, the user's choice. A peer away (S in its record, or the rosters name it and it was never told of S's current credentials, as for a sync ID just joined): it waits for that peer; what ends the wait for a peer that never returns is another peer taking the writes (held elsewhere), the peer leaving the rosters (`may_hold` no longer names it), or its record evicted (`RECORD_BUDGET`, which a node with few peers may never fill). No timeout: a timer would drop unsent writes of a node merely offline for a while.

# Sync: leave
> Summary: osis-sync's `leave` module (core/sync/src/leave.rs) and the engine's `forget_local`: the one owner of "the sync IDs this node syncs" (the sync set plus each leaving sync ID while it waits), the wait rule for read and kept-unread leaving, unsyncing's forget, its costs and state.

Spec: spec/sync-set.md §3. Overview: notes/sync.md.

## What this node syncs
One value: the sync set, and each sync ID that left it while it waits to stop. `leave` alone follows the engine's sync set (`set::SetFollow`, per key) and writes the value into the store (`Store::set_holdings`, stamped per S, fed by `Store::syncs_feed`). Every other module follows the store's value, never the engine's sync set: store, opens and dials by their own `set::SyncsFollow`, unread by its own, status by `Store::syncs` whole, read, streams and inbox by `Store::synced`/`holding`. So a waiting S stays open, served, logged into and judged exactly as before (spec: "stays a member of its shared sets as before"), with no per-module case. `leave` settles first in each round, so no module ever sees S drop and come back.

The engine side answers for a leaving S by its thing's held read secrets, not the sync set (`Engine::opening_thing`: the thing reading S, else S's owner while a read secret of it is held): `read_credentials`, `claim_key`, `open_entry` and `dial_peers` (as read) go by it, `sync_bodies` by `thing_sync`. So an S that left because its thing reads plain for now (an outsider's grant judged unlisted until a rotation's thing list arrives) or that a removed reader still holds the secrets of (the drop waits for the same pass, notes/engine-lost-access.md The drop) is opened, proved and dialed as before until its pass ends. Certificate bodies and the pass wants (`passes_wanted`, `forget_unread` at open) still go by the engine's sync set: a waiting S gets no new certificate copies; its own writes are what it waits on, and those are content bodies.

## The rule
- One derived value: the sync IDs out of the sync set that this node syncs or holds rows of, each an `Effects` key judged (`leave::judge`). The first settle wants every stored one (`Store::held_ids` and the synced entries: what a start, or a restart of the modules, finds), later ones each S the sync set loses (`SetFollow`); there is no separate start sweep.
- S has left when it has an entry (as synced, else as this node's keys hold it, `Engine::sync_holder`) and this node knows its synced group (`Engine::sync_rooted`: before, at pairing, its sync set is empty for want of it). With neither (another account's inbox this node deposits to) it is left alone. Its entry and the pass place it left at (`Engine::pass_place`) are noted then (`leaving`), and it stays synced (rows found at a start are synced again).
- First, whatever made S leave, a complete pass of S begun after it left (spec/sync-set.md §3): status runs one (`Leave::passes_wanted`, by pass place) and leave reads `Status::passed_since`. Same rule for every cause.
- Then: this node's keys still hold S as when it left (`sync_holder` equal); else it stops at once (secrets lost, a removal, still plain: shredded, nothing forgotten). Read: each own commit with an entry under S (`Engine::own_commits`) held elsewhere by status's durable mark on one of its entries (`Store::elsewhere`). Kept unread: each own entry present at a source (streams' `Sources::present`). Either way also done when no peer shares S (`Opens::shared`). A self-removal's wait is the same rule, own nodes skipped (notes/sync-status.md Self-removals). Done: read, `Engine::forget_local(thing)` first; then `Store::shred`, then not synced. A crash between forget and shred leaves the rows, so the start redoes both.
- Synced again before it stops: the wait ends, nothing goes.
- State: per sync ID out of the sync set with rows or an entry, one key, and per leaving S its entry and place; bounded by the sync IDs the store holds rows of; nothing durable (the store's rows are the truth after a restart; a restart begins the wait afresh, with a new pass).
- Cost: a sync set change costs what moved (`SetFollow`); a leaving S is judged when its own commits, marks, presence, keys or peers move, O(own writes under S + records holding S).
- A restart of the modules (the engine read its store again) must not see things leave that did not: the engine keeps its followed links across a reload (`load_fresh`), as it keeps the key actors they hold, else the sync IDs of links being redeemed would leave and wait a pass at every reload.

## forget_local (engine, core/engine/src/sync/mod.rs, retention/forget.rs `Scope::Local`)
- Forgets `t` and each thing whose secret actor is `t`, but those the synced group's closure holds (a plain thing listed elsewhere still syncs under that group). Same machinery as lost access (`retention::forget::forget`), fate `Local`: everything an erased thing loses but `secrets.0`, so the thing stays read and syncs again when listed; commits left with no part are deleted and fetched again, others keep their other parts (late parts join). Event cause `Unsynced` (`DerivedFrom::Unsynced`). A commit that also wrote a synced thing (a creation commit adding the thing to a synced group) stays, and the forgotten thing's part of it joins again when a peer serves that commit again under the synced group's sync ID, so the forgotten thing can show that commit's values. The rule: after unsyncing, the thing shows exactly what any node syncing only this node's synced group shows (what still reaches it under a synced sync ID), never anything only its own sync ID carried (core/osis/tests/it/sync.rs `an_unsynced_write_goes_out_before_the_copy_goes_spec_sync_set_3`).
- A thing under `t`'s secrets still in the closure syncs under `t`'s S, so S stays in the sync set and `t` is never unsynced; the closure exclusion matters only to a direct call. Things known only from pending commits are not named (their parts stay pending).
- Cost: decodes every commit header and reloads the engine, like lost access. Unsyncing is rare; per thing.

## Reasons
- One value every module follows, written by the module that owns leaving: a per-module "also synced while waiting" would be a carve-out in each, and two writers would let modules disagree within a round.
- Any thing, admin or not, goes when unsynced: unsyncing means "not on this node" (Tess). Unsyncing everywhere the last copy loses it; stated in the spec as the behaviour, like deleting a local file.
- The wait guards only this node's own writes: a peer that never got them would lose them. Everyone else's are someone else's to keep.
- Status's durable mark, not stream presence, for a read S: a reader source shows what it holds by reported positions, which status already folds into the mark.
- The wait lasts only while a peer could take the writes (Tess: unsyncing drops the copy, own unsent writes go out first, nothing gets stuck). No peer sharing S (a lone node, every record of S gone): it stops at once, losing writes held nowhere else, the user's choice. A peer away (its record kept): it waits for that peer; the record budget (`RECORD_BUDGET`) bounds how long a peer that never returns is remembered. No timeout: a timer would drop unsent writes of a node merely offline for a while.

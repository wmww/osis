# Revocation
> Summary: Why validity follows the demoter's frontier (spec/permissions.md §5): Tess's decisions on the reference scenario, frontiers saving what they list in any order, one list of commit IDs for both layers and the own cover, chain writes counting only through the frontier, re-grants validating the gap, per-delta validity, snapshots vouching, the joint walk, judging at the start of a `ts`, Acting, invalid bodies going, what stays lost, why frontiers list commit IDs and no compact encoding (ID batches the fallback), snapshots and history. Addenda: notes/addenda.md; model findings: notes/role-timeline.md.

Principle: **the revoker's view decides, as if it were a central authority** (Tess: fine either way): a demotion's frontier, what its demoter had received, decides which of the demoted node's writes stay valid; the author's own timestamp never decides.

## The reference scenario
Alice shares a doc with Bob (Mon). Bob goes offline (Tue), makes edit X (Wed). Alice revokes Bob without having seen X (Thu). Bob makes edit Y (Fri), returns and syncs (Sun). Variant: Carol, offline with Bob, syncs with him.
- Tess's decisions: the author's own timestamp never decides validity; "surface it to the user" is not a solution; rejected writes may exist as an invisible "invalid write" concept for forensic tools; readers and nodes keeping S unread never vouch for a revoked writer's edits.
- Results: X and Y invalid; in the Carol variant X too. A re-grant brings X and Y back only if some node received them before the writers dropped them (Tess: a re-grant restores only what some node still holds). A revoked actor cannot react in time: by the time it knows, the revoke time has passed.
- Rejected: a timestamp rule (forgeable); accepting everything causally concurrent with the revoke (a hostile ex-writer never "sees" it); a learn-based rule (the revoked actor can race the revocation, and honest offline sync looks like a hostile push); roles by claimed time only (an ex-admin could mint backdated grants forever); a pre-sync inside `set_role` with receipts-only reads of unheld groups (slow by default, could not close the gap, and needed `_now` twins everywhere).

## Frontiers
- **A frontier saves what it lists, whatever the order** (spec/permissions.md §5.2), also writes stamped after the demotion and after a re-removal. Applying a commit advances the demoter's clock past it, so an honest frontier lists only writes ordered before its demotion anyway: an order check would add a rule and close nothing, and a removed writer stamping ahead could as well backdate. A demoter listing what it never received is the accepted lying-witness limit (it could re-grant). Only demotions the node's settled walk applies count, so a disputed one it does not trust saves nothing. Models: roles-model `addenda` (the order-bound variant `Rerem::Later` differs in 0.6% of random worlds), held-model `valid_as`.
- **One rule for both layers**: one list of commit IDs for edge and content writes, 32 B per listed commit, body held, dropped or compacted alike. What the demoter no longer holds (forgotten, spec/commits.md §5) it cannot list (Tess: "you can't list what you don't have"), so its **own cover** carries it (spec/permissions.md §5.1, Own cover; `receipt::own_cover`). No list needs a forgotten header, so forgetting stays free, and where nothing was forgotten a removal costs IDs only.
  - Why an own cover: it stands while the demotion applies, whatever later demotes its author, so it falls only with this removal; another writer's cover can fall with that writer's removal by an admin that never received it (roles-model `addenda::another_writers_cover_falls_with_its_author`). Marked in its header (spec/wire.md §4), so holders know it on arrival: only its writer drops a body under it, and addenda list what they hold whatever it carries. A removal voided later takes the own cover with it and leaves every other holder as it was, so the rule loses nothing listing every commit would keep (roles-model `forget-window`).
  - Rejected: held commits past the kept window under the own cover too (a one-write aspect cost a 534 B snapshot against a 32 B ID, and a removal saying retain had to list anyway). Cost (`own_cover_cost_counts_spec_perm_5_1`): forgotten, an own cover of a 1 MiB chunked value is a 694 B commit and no new piece, of each one-write aspect about 534 B.
  - Limits: a removal that falls takes its own cover with it, and what only that cover carried is lost where no node kept the body (notes/engine-retention-covers.md Forgetting; 2,472 of 1,147,776 model worlds, against 10,976 with held commits under the own cover too). A write the remover listed, then forgot under the leaver's own snapshot that reached it after the removal's `ts`, is lost where nothing lists that snapshot (`held_list_late_cover_limit`; 410 worlds).
  - The account level (spec/permissions.md §5.5) is the same rule, limited to writes stamped since the oldest epoch the rotation closes opened (without the bound every rotation re-snapshots every aspect holding an old forgotten write); not built (issues/account-signing.md).
- Size: a prolific node can make the frontier megabytes, kept forever (`roles.0` is never compacted), chunked above `CHUNK_THRESHOLD`. Past the list bound the plain-content commits received last go to the demoter's own addenda, then purge requests lose their right; a role part alone over the bound is refused (stated limit).
- Only the revoker's own receipts matter: a held commit counts as received at its apply time (`Meta::received`; a late part does not move it).
- **Chain writes count only through the frontier**: A's frontier lists the role commits of its chain certificates for the target at R's point (notes/certificates.md); a forged one is not listed and drops, and A's grant reverts. An exemption for "A's own chain writes" whoever wrote them let X, after A removed it, write a backdated change to A's own grant (an `until` next week, a lower invite) that stood. Rejected narrower cuts: only the admin grants on A's own paths, read from the end state (missed a grantor's grant of A's grantor; the end state could name a later rewrite instead of the grant R rested on); exempting chain writes that do not lower their grant (a second rule for a rare case). Residue: if A's authority at T rested only on a chain write A had not received, that write drops and R with it. About 1% of the models' joint histories drop something.
- A snapshot's frontiers and `Absorbed` are no receipts (spec/crdt.md §8): a writer could list commits it signed ahead, or claim `X: 2^60`, and a demotion copying the claim would cover X's later writes for good. A late joiner that got X's writes only through a snapshot does not list them: harmless, since that valid snapshot vouches for them (`flows::late_joiner_after_compaction_agrees_spec_crdt_8`).
- **Frontiers list commit IDs, never counters** (Tess's decision): with counter frontiers a revoked actor could sign a new commit on counters its demotion covered, and once compaction dropped the original new nodes counted the forgery. A fresh commit ID is listed nowhere (`validity::revoked_writer_forging_into_covered_counters_spec_perm_5_1`).

## Validity
- Clock skew: an end by `until` or self-removal is judged by the holder's own timestamps, so writes stamped up to `MAX_DRIFT` past it still count (spec/requirements.md Permissions). Invalid -> valid happens only by re-grant; valid -> invalid once, by un-merge. No finality, like any long-offline node returning.
- **Re-grant validates the gap**: cheaper than grant epochs in the log, the actor could redo the writes anyway, and it recovers from a stolen node's backdated mass revoke all that some node still holds. All or nothing: rescuing honest pre-revoke edits the revoker never saw also admits the actor's later ones until someone reverts them. Tess: a re-grant revives all the account's writes, no special case; leaving writes out of a removal on purpose as a recovery tool depends on a side effect, so an admin who wants something gone reverts it explicitly. Don't build new uses on that side effect.
- **A removal makes its listed writes valid**, whether or not the author held the role when writing; writes after an `until` rely on this. Side effect, a stated limit (Tess: "a strange thing for an admin to do"; no rule): a write made before its author was ever granted, which the admin happened to receive, becomes valid when that author is later granted and removed; likewise its purge requests.
- §5.2 says "held write at its `ts` and no later explicit demotion" rather than "authorized at its `ts`": the latter, read literally, keeps every pre-revoke edit the revoker never saw and every forgery backdated into the time it held the role.
- **Validity is per delta**, not per commit: a node that syncs only thing 2 of a commit cannot evaluate the author's authority on thing 1, while a node syncing both would un-merge the whole commit; they would diverge on thing 2 forever. Atomicity stays a rule about application. Layer 1 judges edge writes one by one too.
- **Snapshots vouch** (Tess's decision; spec/permissions.md §5.2): a compaction snapshot counts iff its author could write the aspect at it, at the strictest role a carried write could need (admin for `keys.0` and `secrets.0`: a writer's snapshot could otherwise carry a forged admin keyset, inbox, deposit seed, admin box or tombstone under a dot nobody holds), judged as its delta by commit ID, so a frontier covers it by listing its ID. Its carried writes count because its writer vouched for them, never re-judged per claimed author. Revocation stays exact where no valid snapshot carries the write; through another writer's earlier compaction a removed holder's unseen last writes may stay, consistently on every node (Tess: fixed by hand).
  - The copy is the snapshot's write, never the delta's: keeping the delta's write whole under any dot a valid snapshot held made reads depend on order (a snapshot carrying a fallen insert's creation without its char gave the char when held before the delta and not after).
  - Accepted: a valid writer can carry any write under any dot (it could write the value itself; authorship is never exposed unverified, notes/api.md Attribution). A body dropped under a cover that later turns invalid is fetched again; with no copy left its writes are gone at every node alike (notes/engine-validity.md Carried writes). A commit part a node never held, deleted under that cover, applies without it (Tess's decision; notes/engine-validity.md Authority).
  - Rejected: any writer's snapshot carrying a revoked author's elements; "compaction snapshots vouch for nothing" (roles-model `content.rs`: an "authorized at the snapshot's `ts`" variant diverges when a later snapshot re-carries an element only a pre-revoke snapshot saved and some nodes dropped that snapshot as covered); snapshot authority plus per-claim judging (claims, per-write indexes, refills, and still order-dependences). That divergence cannot return: a cover must carry what the snapshot it covers vouched for (spec/commits.md §5).
- **Layer 1 is one joint walk** over all held edge writes of all things: authority at a point depends on other things' timelines and mutual grants are allowed, so per-thing walks with restarts are the same fixpoint stated less clearly. The commit-ID tiebreak is needed: a shared link key gives two holders the same (`ts`, author node). A fall audits every class X fell through, not only the one R took away: with "the lost class" alone, X holding both the chain and an admin grant on G could backdate a forged write to a time it held only the grant (`two_admin_paths_class_attribution`). Path-based audits would also close it but need per-path attribution; class falls keep one comparison per (X, N).
- A single-use redemption's self-removal falls with its grant (both L's invite class on K): a forged redemption's self-removal kept after the finalization dropped its grant would burn the link and block the honest redemption.
- **Layer 2 judges a commit at the start of its `ts`** (spec/permissions.md §5.2, Position): the HLC stamps a commit above every one its node had received, so a content commit and an edge write at one `ts` were concurrent, and ordering them by tid made the outcome turn on whose tid was lower. So the write is always before the removal, and it survives exactly when the frontier or an addendum lists it. Nothing new for a forger: a write stamped at the removal's `ts` and sent after it needs an addendum, which a witness writes only for what it had received (`validity::a_removed_writers_write_forged_at_the_removals_ts_is_lost_everywhere_spec_perm_5_2`). It applies to every layer-2 judgment and to a destruction (the two must agree).
- **Edge writes at one `ts` order by author tid** (Tess): two admins' concurrent writes on one edge in one millisecond resolve by the walk's key order, as a register's ties go by the dot's author. A demoted admin's own edge write at its demotion's `ts` counts nowhere either way.
- **Acting** (spec/permissions.md §5.2): a valid commit's actor is its sender. Role commits must name their author: checking it inside the joint walk would make grant application depend on the actor's grants and join components on every role commit's actor, and nothing needs a role commit to act for another. The author's chain to the actor travels under every sync ID carrying a body of the commit (`Indexes::chains_on`), so a reader of the thing alone judges as one syncing the actor does. A node removed from its account lists every write of it as the account its remover received. `created.0` stays valid whoever acts, else every record created as M would be listed forever.
- Writes to `secrets.0`, `keys.0`, `sync.0` are judged like content by the role their aspect requires, with frontiers covering role-class aspects for any demotion. An un-merged rotation's secret is still kept for reading.
- One dot still names one write: overlapping session-form ranges void both commits (spec/commits.md §4). Residue: an ex-writer can erase its own pre-revoke content by equivocating; re-grant restores it. Role commits use commit form, so a removed admin cannot void its earlier grants, revive a holder it removed or void its own rotations that way.

## Bodies
- **Invalid bodies go** (Tess: dropping and refetching is fine; spec/permissions.md §6), but role commits (the timeline's input) and the node's own (its user may write them again). A re-grant or a late addendum makes them missing, fetched from any holder: nodes keeping S unread (no right deletes them there) or the author; with none, gone at every node alike. Mechanism: notes/engine-retention.md Invalid bodies.
- What stays lost after addenda: an edit no writer had received by the removal's `ts`, the removed holder's purges of its own messages (no witness holds that right), a removed admin's unseen role writes. A re-grant brings them back only from a node still holding them, in practice a node keeping S unread. The API's advice (`wait_synced` first, notes/api.md Demotion and addenda) is the only protection for a group the remover never synced.

## Frontier encoding
A frontier is commit IDs only, one system for every retention (Tess): the demoted node's received commits but those the demoter's compaction could drop now. On kept history that is every kept write, a stated limit (spec/requirements.md Cost). What it meets together: no clobbering of kept history (a snapshot carries live content only, so leaving out a covered commit made its superseded writes invalid for good, and any writer could write that snapshot just before a kick); a kick's cost bounded by compaction cadence and retention where history is not kept; validity a function of the held set; no forging into counters a removed writer once used; the author's `ts` never decides; new nodes never fetch compacted headers.
- **No compact encoding is safe where bodies are dropped**: a bound per source (counters, chain heads) is safe only while every commit under it stays detectable, and a forged commit re-signed on counters whose original every node forgot is indistinguishable from it. Headers are forgotten exactly where bodies are dropped.
- Where bodies are never dropped (permanent deltas) bounds would be safe. **Heads** for that case were designed and dropped for one system of IDs: a header field `prev` on a session's first delta per aspect naming the node's newest earlier commit there, and a frontier head `(tid, ak, session nonce, ctr)` per unreached session, about 60 B per permanent aspect against 32 B per kept commit. Tess accepted `prev` in principle under the growth rule (notes/growth.md). A rebuild must keep: a mixed aspect falls back to IDs; the removed-author check must not read "the frontier omits it" as final while a link is not yet held; a head on `purge.0` needs every request there permanent.
- Rejected encodings: one chain per session across aspects (a verifier under S sees only headers touching S's closure); per-(aspect, session) counter bounds without links (one entry per app launch that wrote); chains or bounds on compacting aspects (forgetting leaves gaps where an honest write reads uncovered); `ts` against a cutoff (Tess rejected `ts` rules); set hashes or accumulators (a membership proof per surviving write); per-node counters across sessions (a restore before sync voids old and new writes).
- **Fallback if kick costs ever hurt: ID batches** (Tess's idea). A batch is an object listing commit IDs; a frontier may name it by hash in place of its IDs, and batches can name batches. Anyone may write one: the frontier fixes it by hash. Cost about one extra ID per commit while it can matter to a kick; receivers fetch named batches before judging. Open: who writes batches and when, where they live, how a kick picks batches it received whole.

## Snapshots and history
A snapshot is trusted for current content only, never for authorship or time, and its copies are never compared with the deltas they copy (Tess, History is verified or absent: a copy differing from a held delta's is a writer's claim about another's history, and such claims are neither stored nor acted on).
- **Content**: a valid snapshot's writes join like any write, also where the original is held, copies of one write settling by the copy order (spec/crdt.md §4.1), so nodes holding the same bodies read alike. No worse than the writer writing the value itself: a snapshot holding another copy of a live write never covers that write's body (spec/commits.md §5 Covered), so the original stays held until it dies, and a removal of the forger gives it back. Cost: a forger can keep its victim's write held. Mechanics: notes/engine-validity.md (Carried writes).
- **History**: authors and times come only from verified commits held here (notes/api.md Attribution); content known only through a snapshot has none. Listings and `created`/`changed` read held headers only, a watch names the commit applied (a snapshot correcting a held original is reported as the snapshot), undo and revert act on held commits.
- **Judging carried writes as their authors' (no vouching) is not buildable**: frontiers and addenda name commits by ID, a carried session-form write names only its dot, snapshots carry no commit IDs for session sources, and a node joining after compaction never holds the headers. Without vouching such a node removing X would void everything X ever wrote that got compacted, depending on which device removed; counting "the frontier lists a snapshot that carried it" diverges once that snapshot is forgotten; dating by stamp lets a removed writer backdate. It would need frontiers by dot range or snapshots naming each carried write's commit, plus a receipt rule for writes received only through a snapshot, so the requirements Limit stays.

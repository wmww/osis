## 1. What a node syncs
Covered by: spec/sync-set.md (principle, §1-§4), spec/sync.md §3 (lines 22, 28, 29: one predicate; read/unread moves keep the store). Lines 10-36 follow from the area principle or are stated rules there; API names (35) are Phase 3's.
- One kind of node and one of peer; whether a node reads data is a property of (node, sync ID), never of the node. [R End state, Decided; P What must not survive]
- Principle: a node syncs exactly the sync IDs in its synced group's closure; nothing else decides what it holds (no admission, keep list or peer list). [P Sync model; 6B synced-group]
- The synced group: a plain group, first admin the account's devices actor D, an item of D's `group.0` (its changes travel under home), D listed as a subgroup from its making; `synced^.0` on D maps node tid to its synced group, admin-only, written by the account; siblings read each other's under home. [P; 6B spec data-model §9]
- A node learns its own synced group with its grant on D: made in the account's creation (a content commit after the role commit, one transaction) and in the pairing reply (a copy of the pairing node's synced group's items and subgroups). [P; 6B]
- Home stays under the synced group: a local commit after which some node's synced group and D no longer each hold the other in their closure is refused (`Invalid`). Limit: two concurrent writes each cutting one path leave that node following nothing new until paired again. [P; 6B spec data-model §9; 9bd89ca05 (B)]
- Before a node has read its synced group it syncs home's closure (home is under it by the refusal). [6B; 7582ec874 (B)]
- Organizing groups ("synced on all nodes", "nodes with lots of storage") are plain groups like it, no sync ID; which exist and where an accept writes is app or node policy; core knows no accepting policy. [P]
- Dropped: a sync ID of the synced group's own (or an organizing group's): it would carry every commit of every group under it a second time as entries, and sync-only leaves' commits not at all. [P]
- The sync set: the sync IDs of the things in the synced group's closure (spec/sync.md §3 closure: items and subgroups at any depth, a thing shared on its own included); "the synced group synced but G under it not" cannot be stated. [P; 6B spec §2; dd0518436]
- A thing held sync-only is a leaf: it syncs the sync IDs its grants' inbox payloads named; its `group.0` is unread, so the walk stops there. Only direct grants make leaves. [P; 6B spec §2]
- A thing in the closure the node neither reads nor holds sync of is unsyncable: diagnostic `Unsyncable`, nothing of it syncs. Limit as built: a known thing the account holds no role on reads as plain. [P; 6B; 6B-left] → COVERED: spec/sync-set.md §2 (secrets of its own is spec/crypto.md §3's count from held role commits; a thing whose keyset commit is not held counts as plain until one arrives).
- Walk cost: the group index (`enclosing`), a cycle adds an element, never a loop; adding under the synced group costs the added subtree's index rows; a removal re-derives by brute force (O(closure)). Counted at n and 10n. [P; 6B]
- A thing counts as read only while its own read secret is held (one predicate for read vs kept unread). 6B's alternative "or `label.0` held and the account holds read on it" is a judgement over projections: OPEN which predicate. [A row Read set; 560d5421c (B)] → DECIDED (Capstan): read exactly while the read secret is held (spec/sync.md §3).
- A received grant syncs nothing until the account lists the thing under some node's synced group; a link's sync ID is followed as its redeemer redeems. [P; 6B spec §2]
- Leaving the sync set: a sync ID kept unread is dropped at once; a read one once the node's own commits under it are logged (and while the account still reads the thing: a lost role ends it at once); dropping shreds its entries, what it carried stays as local data. [P; 6B spec §2; 5a3d50835 (B)]
- A sync ID followed by a hint is not dropped by leaving. [cd0728b9c (B)]
- A destroyed thing's own sync IDs stay in the sync set until emptied, wherever the synced group is (area 4, Destruction). [RL; 6B; 4049f77b8 (B)]
- A lost thing stays listed in the synced group (the group holds what the account chose; the sync set filters by what the node may hold). Dropped: unlisting at the role loss (drops before the leave's own writes are logged) and after forgetting (a removal naming a forgotten tid). [6B; 8f973ee0c supersedes 11a0dffbf (B)]
- Read to kept unread (a reader lowered to sync) keeps the ciphertext: the sync ID moves to the kept-unread set under its caps, never shredded. Bug: sync-demotion-drops-copy (old issue, at 1dcacb6b0). [A row Lost access]
- A sync ID that left the read set unforgotten sits in neither set; one predicate decides read vs kept. Bug: unsynced-label-rows-kept (old issue, at 1dcacb6b0). [A row Read set]
- Handed-off groups (`State::handed_off`) are a per-node exclusion beside the synced group, the same thing as leaving it: OPEN fold into the synced group. [6B-left] → DECIDED (Capstan): folded into the synced group; leaving it is the one way (spec/sync-set.md §3).
- Readability is per account: every node of an account holds every box to it; a machine that should hold the user's groups unread is a node of an account of its own, granted sync. [P Tess (reversible option)]
- OPEN (Tess call): removing a group from every node's synced group drops it from every node of the account after own writes are logged, even if no other account holds it (can lose the last copy); option: keep until another holder's stream showed it whole. [P Tess] → TESS CALL: kept as built (drops after own writes are held elsewhere); spec/sync-set.md §3; For Tess.
- OPEN (Tess call): a sync-only holder keeps no subgroups (a grant per sync ID; a new subgroup is kept only once granted too); the design takes an app policy granting new subgroups. [P Tess] → TESS CALL: kept as proposed; spec/sync-set.md §4; For Tess.
- No per-node data in groups: a group names accounts, never its holders' nodes. [R Decided]
- API: `synced_group(node) -> Option<Tid>`; the synced group and organizing groups are written as any group; `sync(group)` makes the group's sync ID (admin, no peers argument); `SyncId`, `sync_ids`, `peers`, `saved_peers`, `add_peer`, `remove_peer`, `unsync`, `Serving::{admit, admitted, replicate}`, `Admit`, `refused_by`, `SyncState::Refused` go. [P API; R Decided]
- Role and sync paired, strong form: holding a role is what lets a node sync a thing. [R Decided; RS]

## 2. Sync IDs
Covered by: spec/sync-ids.md §2-§6. Lines 52-66 are the steps rules of §6 (Steps, Register); the credential/walk/Behind/provisional-open-head lines are spec/sync-ids.md §6 Walk (TODO(area 2) resolved: one rule, a reader opens at a source only by a credential of the source's step, a verified step it knows that source's path holds; the stream's head event names that step, so the provisional open head needs no rule of its own). Lines 67-74 are §5 (store, caps, peer budget).
- A commit giving a thing role secrets of its own makes its one sync ID, never replaced. [RS; R]
- Dropped: sync ID replacement and the label index: their one cause (a removed admin registering keys only it knows at a peer first) needs no new sync ID, since nothing is registered first come and the remedy at a node keeping it unread is local. [P 3j; 89ad81c18]
- Key actors (nodes, link keys) have no role secrets of their own, so no sync ID: a link key starts from its link text (static entry), a node through its account's secrets or pairing. [RS Unsure]
- Role `sync` below read (sync < read < write < admin), with a role secret like the others, sealed to every holder of sync or above; the sync key is `kdf("label sync", sync secret, le64(i))` for every holder, readers deriving the same. [P Sync-only grants; 5087fcffa]
- What sync gives: the sync key, so the holder opens S at a peer, pulls, holds and serves it; it takes entries stamped under its head's write key and deposits by the Deposit rules, removes an entry only on a Delete signed by the needed delete key or at expiry, reads nothing, holds no roster; J is unknown at it. [P]
- Who grants sync: the one grant rule (an admin, or a holder whose grant carries `invite: sync`); no carve-out. [P Tess, decided]
- The grant's inbox blob carries the holder's box of the sync secret and names the thing's sync IDs; claim sets and entry boxes stay readers'; a rotation boxing a holder whose highest role is sync reaches it by inbox; the path reaches it by Register from any holder. [P]
- A sync box gives no read hint (following a payload sync ID needs a held read secret). [d0792735c]
- Removing a sync holder is a departure needing a rotation of the sync role; the head's sync key moves with the next step, ending every open by the old key at the head's event; removing a reader rotates read and sync. [P]
- What a sync holder learns: the thing's tid and sync IDs, the granting account, the path with its claim-set size padded to a power of two, entry counts, sizes and timing, which accounts' nodes open S there; never the roster, content or members. [P; issues/privacy.md accepted]
- Through paths: a grant to G on H boxes H's sync secret to G's sync keyset, but a sync holder of G never learns H's sync ID. [P]
- A sync grant on D makes nobody a node of the account: a node of P is a node key actor holding read or above on D. [P]
- Steps: a tree signed by parent delete keys; Register needs no secret and no open, relayable by any node; any reader holding the recorded path moves a peer on an older step; only an admin issues a new step (a child of the source's head when due, of the served head with no sources). [P 3h2]
- Register is never gated on an open; a Delete is taken only under an open by a credential on this connection, ended when the head's sync key changes. [P 3i2]
- Register only for sync IDs in the sync set kept unread, a genesis too (known from the grant, nothing first come); a node reading S takes no genesis by Register (its path is `label.0`'s; code 4); outside the set code 14. [6B spec §5; P The hub]
- A step is registered at a source only once that source's stream reported reading the role commits it lacks (else a removed or lagging reader never reads its removal). [c1ae629f7]
- No step is issued or registered under a head this node has not recorded (a forged head chain failed every pass). [d3ccacd54]
- A head's child is never recorded on a peer's word; a walk tests every held sync key after the recorded credentials. [49cbe0d59, c5868868a]
- A sync ID's restart clears its registered path (else a peer whose head moved past it strands it for good). [43bdfde7c]
- Behind (Halyard): a reader behind a peer's head is answered with the steps after its named step through the first under another sync key: a removed reader or used link learns at most one rotation past what it read. Dropped: answering a Register of an old step with its child (leaks to every node keeping S unread); waiting for `label.0` from another reader (a phone whose only online peer keeps S unread stays behind). [P 3i2]
- Behind bytes as built: item `[3, sync_id, Opt(step_id), sync_pk, sig]`, by any credential of the named step, answered 0 with `grant [none, [child]]`, 13 when the peer lacks S (register the path), 14 else; an Offer's answers read at most `REPLY_BUDGET / MAX_STEP_WIRE` steps counted by encoded size. [P 3i2; d8ef4d415, 9c8357568, ca03eaeb3]
- The walk tests every recorded branch deepest first; a 14 on a recorded step walks back to the nearest earlier step with a credential; a 14 on the child the peer gave strands; a genesis alone is registered first. [P 3i2]
- Provisional open head: two admins' sibling steps share keys, so a Hit may open at the peer's sibling; a child refused while open, or a stream head neither a child nor recorded, doubts the open head: nothing more registers under it, Behind asks back from it. [P 3i2; 038626483, b1372972b]
- Credential per sync ID: the newest recorded head's sync key when held, else its claim key while the claim set is held, else a static entry; none held: stranded (tests, Hits, registers nothing; Failed, never a loop). [P 3h2]
- Stranded at a peer once it took the path to its newest step and its filter since shows none of this node's credentials. [P 3h2; 6cfdfae0a, 606ad9208]
- No rotation answers a fork: forks stand until a rotation due for another reason lists them. [P 3h2 (sim member_churn)]
- A deposit-only step waits for a missing valid `keys.0` part from the group up to its secret actor (it stopped a step storm). [8923f22af]
- The node's store per sync ID: one store of ciphertext (entries with wrap and stamp, blobs once per blob ID, the node log, served steps and claim sets); plaintext and secret-derived state is the engine's; the store is the truth for ciphertext, the engine's a cache; a crash between the two commits converges (a row with no engine state is derived again, engine state with no row dropped). [P step 4]
- The code holding data a node keeps unread cannot decrypt and judges no open; every secret lives above the store (tools/policy.py `host_blind`). [P steps 3, 5]
- Blob bytes are stored once per node and deleted when no sync ID references them; a blob fetched under one sync ID is taken under every other kept sync ID naming it. [6B spec §4; P; 261f42d8a]
- Caps and rates (`host^.0`, which keeps only `policy` and `caps`) govern only kept-unread sync IDs and count only their entries, recounted when a sync ID moves between read and kept; a heavy reader takes nothing from what others may store. [6B spec §4; c7eb6ea09 (B); P The hub]
- An unstamped entry that gives nothing held costs its size against the peer that brought it; the source is stored with the entry and charges rebuilt at open. [897f2892d]
- Role entries (role commits, requests, the blobs they link) are stamped or deposited under `"osis v1 role entry"` and taken outside the caps: a current writer's stamped one has no count (a writer is inside the storage trust boundary; role commits are must-hold for fixed retention), a deposited one within the deposit budget; totals and freed room count capped entries only. [P 3h2 (Tess)]
- A reader shown one entry under two valid stamps keeps the lower. [P; 7bbf125a4]
- A dropped body's entry (shredded, kind kept) wants its bytes from nobody; an entry opens only with bytes and wrap held, else it is fetched under its own sync ID. [P 3h1; 8342da8c3, 378e8ed56]
- spec/sync.md §2 assumes every holder of a key in use holds the older secrets through history; a holder without history opens only from its cut's step on, so a walk to an older step must not strand it. [issues/history-less-grant.md]
- OPEN (Tess, keep open): per-account caps at a node keeping other accounts' groups unread are possible (grants name accounts), not designed. [P Tess] → DECIDED: kept open; nothing in spec/sync-ids.md §5 (caps per sync ID) constrains per-account caps.

## 3. Connections and opens

- At a peer full for S the author deletes its superseded ephemeral entry without waiting for the superseder there; a forgotten commit's entries are deleted at a full peer without waiting for a carrier, unless an entry of it left that peer since. [3d64f02cc superseded by 8724678b7 (capped-eph)]
- Dropping a sync ID ends each connection's stream of it; rejoining is a fresh listing. [98266d272 (B)]
- Restart: log, records and cursors are durable; a cursor is stored only with what it covers applied; a lost record is a first contact; partial loss is atomic per record. [RC Restart and loss]
- Idle reconnect: under 1 KB and a few round trips whatever the number of sync IDs; a first contact sharing n sync IDs joins them in O(1) Pulls. [RC Costs, Tests]

[RC Unsure] → DECIDED (Capstan): implementation choice; spec states only the observable rule (spec/sync-opens.md §6); notes later.

## 7. Status
Covered by: spec/sync-status.md §1-§3 (256: kept-unread S has a status row like any).

## 8. Hostile peers
Covered by: spec/sync-hostile.md §1-§2.
- Lying or flooding filters: gaps within `[lo, hi)`, pages ordered, else Error 2 and close; `f` checked against the decoded count; additions capped at the whole filter's n; one test pass in flight per peer. [SS Adversaries]
- A peer without a credential or holder J learns only the entry count and random bits; beacons are unlinkable across peers; only ByRole, Lost and Deposit carry a sync ID, each to a judged holder. [SS]
- A node holding only S's public values opens nothing; a static item reflected through a second dial opens nothing; an older step's signature opens nothing toward the peer. [C6; NO `ON_side`, `ON_answer`, `ON_old`]
- A removed sync holder gets nothing after the rotation; a removed reader or revoked link learns at most one rotation past. [C6; P 3i2]
- A revoked node of a known actor holds only the closed epoch's key; limit: a verifier not yet holding the rotation counts its proof (account signing's fork window). [SS; RC]
- A forged head and box, or a substituted box, teach nothing; a forged grant is not offered again. [P 3i2; C6 commit 3 tests]
- A known actor can flood records (accepted while only a known actor can); Resume, Beacons, Pull and Members floods are bounded by message size, `max_reply` and S. [RC Adversaries]
- Nothing reads a clock above the transport: a skewed peer affects only its own writes. [RC]
- A memory commit is room-checked whole before any decode and waits only once its signature checks; the compaction trigger skips bodies a held snapshot covers. [693dbd6cf, 58bfb6b92, 1fe169971]
- A hostile peer that drops what it pulls cannot stop a node counting idle (lacking counts only what a source pulls). [1ad048028]
- A peer lying in its own log: bounded by "logged again once" (area 4). Refusing role entries and holding requests open: the plan's stated limits (no input states them). [sync-rewrite area 8; log-liar]
- OPEN: a depositor holding a team's `keys.0` but not its roster learns from 0 against 14 whether a proved actor holds the inbox (team membership); close by taking deposits only for an inbox whose actor the receiver proved itself, or accept. [SS Adversaries] → DECIDED (Capstan): stated limit (spec/sync-hostile.md §2).
- OPEN: a known peer forces O(N) work per small message (each additions page re-sorts and tests; a Hit then Lost re-tests); no rate limit. [SS Built] → DECIDED (Capstan): stated limit (spec/sync-hostile.md §2).

## For implementers (Phase 2 boundary note)
- Sync set (spec/sync-set.md §2): tag each commit with the groups whose closures hold its things, tag again when a `group.0` changes (the group index `enclosing`); adding a subtree costs its index rows, a removal derives the set again by brute force (O(closure)), both counted at n and 10n.
- Every derived per-sync-ID value (sync set, shared set, credentials, judgements) is an `osis_base::memo` value over the engine's stamps, with a separate effect that runs when the value changes; no hand-keyed caches or generation counters (issues/derived-state-recomputed.md steps 3 and 7). The spec states this as spec/sync.md §2 "Work in proportion to change".
- `until` with no rotation entry in S (a static-entry credential, a base actor's rotation, a compacted rotation) falls back to the log's end; within a flush the log's order is not commit order. Serving a join from the start wants a per-sync-ID position index, not a scan from the lowest start.
- The sync layer depends on a connection abstraction only (spec/sync.md §2 Transport boundary): QUIC, relay, LAN, Bluetooth or a mesh hop are transports below it.

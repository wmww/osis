# Networking: transport, discovery, reachability
> Summary: Network design, decided with Tess: our own transport abstraction over any ordered byte stream; QUIC to known addresses; our own P2P on quinn (relaying by any willing node, hole punching through it, switching to direct by reconnecting) in every build; no central server, relaying is a setting of any willing node; reachability as osis data (`reach.0`), serving addresses pinning a key, transport keys apart from signing keys; first contact by link; risks, alternatives, the push wake-up proposal, Tor; and osis-transport as built (stream contract, InProcess, QUIC, P2P, LAN sockets, unix, Multi). Co-reader peers in node sync (`reach.0` publishing, dialing, LAN routes, co-reader serving): notes/peers.md.

## What osis needs from the network (spec/requirements.md)
- Long-lived connections with push from the serving side (subscriptions, relay-only signals), several labels per connection, one round trip for the common case.
- No always-on node or public IP is assumed (spec/requirements.md, Offline and network): nodes that share data sync directly, and any node may also store and serve data it cannot read for others. P2P (`p2p`) is on in every build; LAN announcements (`lan`, `Config::lan`) are on in every build (issues/net-connect.md).
- No required coordinator: any helper is replaceable and self-hostable; osis works without it (LAN, any peer, a known address).
- For data it cannot read a node must not learn authorship or role grants. It learns client IPs (accepted), not node identities.
- Authorization is application-level (node signatures, label role keys), so the transport only needs confidentiality and a stable peer key to dial.

## Decisions (Tess)
1. **Own transport abstraction.** Sync is framed messages over ordered streams; nothing depends on QUIC. Implementations: connections to a known address (QUIC or TLS/TCP, WebSocket for browsers); our P2P (decision 2); in-process for tests; file bundles for sneakernet (spec/sync.md §11).
2. **Our own P2P on quinn, not iroh.** iroh would give us only a relay client and server, hole punching and moving a live connection to a direct path, for ~190 crates, n0's quinn fork, a second dalek and Rust 1.91, from one vendor whose model is dedicated relay servers. Ours: `p2p` (relay protocol as a node setting, observed addresses, hole punching, switching, NAT model; Implementation below).
3. **No central server.** There are only nodes; some store data they cannot read for others. Fully P2P when peers are reachable; otherwise just enough bridging, which any willing node provides (relay and hole-punch meeting point, opt-in with limits). A machine with a public IP is not assumed to be a node, nor any node to have one. No standalone relay program until one is needed (Tess). Peers are found through group data (`reach.0`), LAN and links; a DHT (a shared key-to-address lookup run by its participants, as BitTorrent's) is a later option for two nodes that changed networks and share no relay.
4. **Reachability is osis data.** A node's dialable key, global addresses and relays live in `reach.0`, published under every label it tracks so co-readers can dial it; hosts see nothing of it. **IP consent (Tess)**: any positive action (sharing a group, making, sending or following a link, accepting an invite, adding a contact, choosing a relay) is consent to show this node's IP to the nodes it concerns. So `reach.0` goes under every synced label, and both sides of every relayed connection exchange addresses: whoever dials a node holds its key by the node's own act (`reach.0`, a link, a relay registration), and a node dials only nodes it chose. A node that is reachable lists its direct addresses in `reach.0`; others exchange them while hole punching. Reachable is judged by the simplest rule (Reach items in Implementation): a global address on a route out. Settings for who learns the IP (relay-only to strangers, one tunnel relay) are deferred: issues/privacy.md. LAN discovery uses our own announcement (rotating tag from the `reach.0` lan secret plus a per-network transport key, spec/sync.md §10), not mDNS-style discovery announcing a stable key on every network, which lets anyone track the device; the announced address is dialed as a `peer://` socket address (no discovery service). A co-reader removed from every label still knows the dialable key and lan secret until a rotation (`Osis::rotate_peer_address`, or a direct link ending). Mainline-DHT discovery opt-in.
5. **Transport keys are not node signing keys**, or every node serving blind data and every relay learns which node uploaded what. Dialers use an ephemeral key per connection (a co-reader proves itself inside the session). A node listens with one key (a design choice, issues/net-one-peer.md), its dialable key, rotatable at will: the key in `reach.0` and the key members know it by as a peer serving a group it cannot read are the same, so a member may learn that a co-reader's node serves a group. Code still has a separate host key and client listener key (issues/net-one-peer.md).
6. **Serving addresses pin a key**: a transport URL plus the serving node's static public key (its host secret's, `Osis::serving_address`), so serving needs no certificate authority and a middlebox cannot pose as the node.

## First contact
A link may carry the sharer node's dialable key and relays (spec/wire.md §10; a contact card carries none and needs a saved peer): a redeemer sharing no host with the sharer dials that node, which serves K's label as a co-reader peer (spec/sync.md §5). No new mechanism; redemption then needs the sharer online, as any P2P exchange does. Relay defaulting to the official serving node is client policy.
- Coordinator's decision: a link text carries the dialable key and relays only, never `reach.0` (direct addresses, lan secret); the sharer's `reach.0` goes under K's labels as under any label it syncs, nothing more for the link.
- Sharer (osis `make_link`): `LinkOpts.direct` is explicit opt-in; without saved peers a non-direct link is an error, and a direct one needs a published `reach.0`. The link text gets the key from `own_reach()`. `MadeLink { direct, ended }` (links record): `upkeep_links` (K roster change, open, a timer at `until`) rotates `reach.0` once a direct link ends (L gone from K's roster: revoked, `revoke_joiner`; or its grant expired), except a single-use link finalized by its redemption (decided: its one possible user now holds a role and keeps the direct path).
- Redeemer (`follow_link`): hosts go into K's hint, the link's peers into `follow_link_peer` (`y/l`: K, target, `peer://` addresses; inbox hints and `label.0` host lists never dial `peer://`). `link_routes` dials them as peer connections (ephemeral key, as every dial; while a redemption is under way (`SyncEngine::link_redeemed` at its end, any outcome) a failed dial is retried after `retry_ms`, a host's pause: the redemption waits on it, and one at once may beat the sharer's relisten; else `peer_retry_ms`, as a co-reader) for K's hinted label and the synced labels of K and the target only; a co-reader proof only once the sharer is a co-reader in `peers()` (its `reach.0` read under a label this node syncs, such as the target's after joining); the two exchange IPs while hole punching (IP consent: making and following the link). The follow is kept after a redemption; when it fails or the key guard drops (`KeyGuard.link`), `forget_link` drops the record and K's hint. K opens there by L's static entry like at a host.
- A sharer that syncs K and the target with nobody (no saved peer, no other node) serves them through local passes (notes/peers.md).

## Local and offline transports
Tess wants "just works" across LAN, Bluetooth and similar. LAN is our own announcement plus direct QUIC. BLE, WiFi Aware and mixnets are further transports under decision 1. Not MVP. Low-bandwidth links suit small commits and signals; large bodies wait for a fast path (chunk fetch is lazy, spec/sync.md §6).

## Future option: Tor
Hides IPs from hosts, relays and peers. Not needed now (Tess). Path: a transport over Arti (onion services were not production-ready at last check).

## Risks
- **NAT long tail.** Our hole punching is simpler than iroh's or Tailscale's; relaying covers what it misses. The in-process net can model NAT types, so behaviour is testable in tier 1.
- **Browsers** can't do UDP hole punching: relayed only, over a WebSocket transport.
- **Relays see metadata** (IPs, timing, volume, endpoint IDs). Same class as a host; ephemeral client keys limit linkability.
- Mobile background limits: sync through hosts in background, P2P in foreground.

## Alternatives considered
- **iroh**: decision 2.
- **rust-libp2p**: most decentralized (spec'd, many implementations, DHT, circuit relays by any reachable peer, hole punching over a relayed connection (DCUtR)). Large surface, mostly unneeded since peers come from group state; its relay and DCUtR are the model for ours.
- **Veilid**: private routing plus its own storage model, overlaps osis's data layer. Not a base.
- **Willow/WGPS, Syncthing BEP, Hyperswarm**: sync protocols or JS-only stacks, not transports. Syncthing's dumb volunteer relays and its untrusted (encrypted-only) devices are precedents for decision 3; its discovery servers are the semi-central part we avoid.

## Proposal: push wake-ups from hosts
Mobile notifications need the host to wake a device with no live connection (spec/sync.md §8 pushes only on subscriptions). A push token (APNs, FCM) is a stable device identifier, so registering one token for several labels would link them at the host beyond the accepted overlap leak. Not in the spec; nothing is needed before the initial implementation.
- **Wake handles**: per label the device registers a sealed box to a push proxy's public key holding the push token plus fresh randomness, so the host sees unrelated handles. On a new log event the host hands the handle to the proxy, which opens it and sends an empty push; the device syncs. The host learns handle counts per label and wake timing; the proxy learns tokens and timing, never labels; both together can link labels by timing.
- **UnifiedPush**: the host posts to per-label endpoint URLs directly, no proxy; an osis host can itself be a distributor. iOS needs APNs through the official proxy.
- Rate limits: at most one wake per handle per short interval; events batch into one wake.
- **Priority** (which writes wake): a per-upload wake bit (host learns which entries matter), a separate wake label per chat (overlap shows its pairing), or wake on everything with client-side filtering (battery). Undecided.
- Tess's calls when it comes up: who operates the push proxy (iOS needs one for APNs); priority; who pays (accounts deferred, notes/serving.md, Abuse).
- Constraints to keep while implementing: per-entry upload-time attributes stay outside the hashed blob prefix (as the deposit flag does), so a wake bit never touches blob IDs; local-store root keys must be readable after first unlock while the device is locked, or a woken app cannot present the sync key.

## Implementation (osis-transport)
- Traits: `Transport`/`Listener`/`Connection`/`SendStream`/`RecvStream` (notes/architecture.md §2). `Address { url, key }` mirrors the schema's `address`; the URL scheme picks the transport, an unknown scheme is `Error::UnknownScheme` (Parked). Error classes: key mismatch, bad URL, protocol = BadInput; unreachable, closed, I/O = Local.
- Stream contract (both impls): the peer's `accept_stream` sees a stream once data or finish is sent on it; `finish` resolves once the peer's transport has everything (quinn `stopped`); dropping a send half finishes it; `close` is abrupt (unread data lost). Graceful end: the dialer finishes, reads the peer to its end and closes (`close_gracefully`); the accepting side finishes and waits for that close, since closing first can cut the dialer's read.
- `InProcess`: endpoints on a shared `Net`; a NAT-model connection limits the streams each side has open as quinn does (one counts until its peer accepted it and dropped both halves; `open_stream` waits), plain `mem://` ones are unlimited; virtual steps; faults `latency`, seeded `jitter` (reorders deliveries across streams only, never within one), `bandwidth` per stream direction per step, `partition` (dials fail, data waits until `heal`), `disconnect`, `kill`; `Net::sleep(steps)` virtual timers. A listener's key is the Ed25519 key of its secret, as for `Quic` and `P2p` (so a dialable key verifies LAN announcements in tier-1 tests); dialers get seeded random ephemeral keys (`dial_as`: the same derivation of their secret). Closing a listener resets the connections it has not accepted. `Sched` polls ready tasks in seeded order and steps the net when all are blocked: same seed, same interleaving, no tokio. Writes never block (unbounded buffers). A stream's state goes once the peer accepted it and both sides dropped its halves (one never accepted stays until the connection goes).
- `Quic` (spec/sync.md §10 `quic://host:port`): quinn 0.11 + rustls 0.23 (ring), TLS 1.3 only, ALPN `osis`, no 0-RTT, no session tickets, no SNI, RFC 7250 raw Ed25519 keys both ways: the listener's key pair comes from its 32-byte secret (an Ed25519 seed, hand-built PKCS#8), a client's from OS randomness per dial (or the given secret for `dial_as`); custom verifiers pin the host key (mismatch -> `KeyMismatch`) and accept any Ed25519 client key. Peer protocol/TLS failures -> `Protocol` (not retried by `connect`). Each dial binds its own UDP socket, so a host cannot link a client's connections by source port. Handshakes have no deadline (any link speed connects): QUIC's idle timeout ends a silent one, both sides; listener handshakes run concurrently (`accept_loop` over `Handshakes`, also `QuicUdp`'s), at most 1024 in progress, the oldest aborted past that, so a silent client blocks nobody. A dial to an unreachable address fails after the 60 s idle timeout. Per-connection memory is bounded: 16 bidi streams, no uni streams or datagrams, stream window 1 MiB, connection window 4 MiB (the reader drains frames incrementally; `QuicUdp` shares these settings); idle timeout 60 s, keep-alive 15 s (all provisional). Why QUIC over Noise-over-TCP: native multiplexed streams, flow control, migration and keep-alive without our own mux. Cost: ring's C/asm.
- Helpers (`manage`): `Backoff` (seeded jitter in `[d/2, d]`, 500 ms doubling to 60 s, provisional), `connect` (retries only `Local` errors, sleep injected so tests use `Net::sleep`), `close_gracefully`. One connection serves many labels through proto's message ids on one session stream; no stream-per-label scheme.
- `link` (tokio): a session = one stream as a `Link` (`peer_key`, `LinkTx` with a not-yet-written byte count and cap, `LinkRx` read-ahead 16 × 64 KiB so flow control holds the peer) with two pump tasks. `link::dial(t, addr, Option<&StaticSecret>, wait)`: one stream, the dialer closes after finishing. `link::serve(listener, idle, wait, out, max)`: at most `max` connections at once; every stream a dialer opens is a session; the accepting side finishes its side, closes only after the dialer closed or `idle` without sessions. The host and node drivers use it, and its `blocking` (`block_in_place` on a multi-thread runtime) and `forward` (a `LinkRx` into a driver's event channel; the node driver's; the host driver hands reads over one at a time, notes/flow-control.md, Turns).
- `peer://` (`PEER_SCHEME`, `peer_url(hints)`, `peer_items(url)`): a node dialed by `Address::key`; the URL lists hints separated by single spaces: socket addresses (`reach.0`, LAN announcement, loopback tests) and relays (`p2p::Relay`, `<hex key>@<socket address>`). `InProcess` has no `peer://`; in process it goes through `P2p<MemUdp>` over the NAT model (a node on a host of one net, `Internals.host`).
- `P2p<U: Udp>` (`p2p.rs`, spec/sync.md §10; `Multi.p2p` over `QuicUdp` in the osis handle, `MemUdp` in a test net, which relays with `allow` answering "is a co-reader", from the driver's `Control::PeerKeys`): generic over `Udp` (bind, time, spawn, seed) and `Sock` (one UDP socket: dial with ALPN, accept, punch), implemented by `QuicUdp`/`QuicSock` (one quinn endpoint per socket; dropping a `QuicSock` leaves its connections up, `close` ends them) and `MemUdp`/`MemSock` (the NAT model), so tier 1 runs the real relay, punch and TLS code. Listener: one socket bound at the URL's one socket address, ALPN `osis` (sessions) and `osis-relay` (served when the transport was built `.relaying(RelayConfig)`), and a `Registration` per relay item from that socket (dial_as the dialable key, register, keep the stream open, accept forwarded streams; `Backoff` on loss; `observed()` per relay). Dial: a fresh socket per dial; every direct item and every relay at once (`items`, at most `MAX_ITEMS` 16); a relayed attempt, after the TLS handshake and the address exchange, starts a direct attempt to the target's address from the same socket (the target punches back); first success returns. After that, relayed attempts stop (`Gate`) and direct ones run to their handshake timeout: a direct one completing after a relayed one was returned and its stream opened is parked for `PARK_MS` (60 s) and the relayed one closed, so the caller's redial takes it (switching by reconnecting, which interrupts the relayed session); completing before that stream is opened it is closed and the connection stays relayed (a close there would read as a failed dial, which waits out `peer_retry_ms`). Punching starts only after the relayed TLS handshake and the address exchange (inside TLS, so the relay never passes an address), so the relayed connection always comes first and every connection that punches through reconnects once; the node redials a co-reader whose connection was up at once (once per `peer_retry_ms`, notes/peers.md), so the redial takes the parked direct one. Relayed connection: one stream, rustls sans-I/O over the forwarded stream (`TlsSend`/`TlsRecv` share the `rustls::Connection`; `finish` sends close_notify; an end without it reads `Closed`; dropping a `TlsSend` unfinished ends it that way); `open_stream` by the dialer once, `accept_stream` by the target once, else `Protocol`/wait for close; `source()` is the relay's tag at the target, the relay's address at the dialer. Relay (`RelayServer`): registrations by the connection's TLS key, allowed by `RelayConfig::allow` (the node's co-readers, or anyone); connections capped at `max_conns` (`RELAY_CONNS` 1024) with `evict_for` shares by source; forwarding charged to the sender's source at `rate` (`RELAY_RATE` 1 MiB/s, a one-second burst, debt waits); memory per forwarded stream two 16 KiB buffers. A Dial answer carries only the dialer's own observed address; the forwarded stream starts with a 16-byte tag of the dialer's source (keyed BLAKE3 of `ip_source` under the relay's random `tag_key`, so `relaying` is fallible), which the target uses as the connection's source: per-source fairness (`link::Slots`, `evict_for`) works on relayed connections before any address exchange. A registration grants its relay `REG_STREAMS` (2048) streams, each with its own `RELAY_STREAM_WINDOW` (64 KiB) and a connection window of `REG_STREAMS` times it (`dialer_limits`: the quinn grant of a relay connection dialed with a static key; one dialed ephemerally, a dial through the relay, grants the relay no stream; `quic://`'s 16, 1 MiB, 4 MiB otherwise), so relayed sessions the target does not read (queued, slow) hold only their own stream, never forwarding to the others (`quic_relay_unread_sessions`); worst case a relay makes a target buffer 128 MiB per registration, and a relayed session moves at most 64 KiB per round trip on the relay-target hop. The relay opens a forwarded stream only if it can at once (`ready_now`), else answers busy (3), so it never waits on a target; a target ends the oldest of its forwarded streams not yet handed to `accept` past `MAX_FORWARDED` (1024, `Forwarded`), so silent dials cannot fill the grant. `allow` is asked at registration, at each dial of the key and by `recheck_relayed`; a source without relay connections keeps no rate bucket. Cost: punching starts after the TLS handshake plus one exchange (the dialer waits for the target's address before returning the relayed connection: its session starts one round trip later), so a connection that punches through always switches (one reconnect). Limits as built: a dial's socket has the address family of the URL's first item (items of the other family fail); the target never dials back, so a dialer that is public and a target behind a symmetric NAT stay relayed; no local-address candidates (LAN discovery covers same-network peers); the dialer or the relay (through the address it reports to the dialer) can make the target send one punch packet to an address of its choosing per relayed connection, and the relay (through the target's reported address) can make the dialer dial one; the target→relay direction of a registration has the relay's `quic://` windows (1 MiB per stream, 4 MiB per connection; its server config serves both ALPNs): a few dialers that stop reading sessions the target sends a MiB on stall the target's sending through that relay (issues/p2p-own.md Open); a parked connection the peer closed is handed out once dead (the redial after it fails goes fresh).
- Reach items (`p2p::reach_items`, the driver at each dialable listen, spec/sync.md §10): `reach.0` field 1 lists the listener at each global address it is bound to (`lan::is_global`: not unspecified, multicast, broadcast, `is_local`, or 100.64/10), an unspecified IP standing for the routes' local addresses (`lan::route_ips`, IPv4 and IPv6, read when it listens; `[::]` serves both families), then its relays; co-readers dial `peer://` + those items, so a node with a global address is dialed directly beside its relays. No dial-back or observed-address check: chosen over "observed equals local" (`P2pListener::observed`), which needs a relay, while a reachable node is what lets nodes without one meet. Limits as built: a node behind any NAT, 1:1 cloud NAT included, lists nothing (port mapping, or relays); a firewall that drops inbound makes the listed address fail, costing the dialer one direct attempt beside its relays; addresses are read only when the listener starts (start, rotation), so a network change or an IPv6 temporary address rotating leaves a stale one until then (a failed direct attempt); a dial binds a socket per family its items use, so a dialer without IPv6 fails only the IPv6 items. Links carry the relay items only (`make_link` filters).
- NAT model (`nat.rs`): `Net::add_nat(public, Nat { mapping, filtering })` (`Dep::Endpoint`/`Address`/`AddressPort`, RFC 4787; `Nat::CONE`, `ADDRESS`, `SYMMETRIC`), `Net::udp(name, ip, nat)` a host (endpoint name for partitions and `kill`). A dial is a packet resent every `RESEND_MS` (100) until it reaches an accepting socket or the net's give-up passes (`DIAL_MS`, 60 s, or `Net::set_dial_ms`); the first packet through makes a normal mem connection (`MemConn::remote` = where the other end is seen). Mappings never expire; same-NAT hosts reach each other by private address only (no hairpinning). Steps are milliseconds. Tasks the transport spawns go through `Net::spawn`, which the net's `Sched` runs, or tokio after `Net::run_on_tokio`, where one model ms is one wall ms (no idle skipping; under `Sched` idle stretches are skipped).
- LAN (`lan`): `Announce { tag, key, port, sig }` datagram `"osis lan 1"` || tag || key || port (be16) || sealed signature, 124 bytes (spec/sync.md §10, provisional); `signed()` = tag || key || port; `Announce::address(sender socket address)` = `peer://ip:port` (an IPv6 link-local source keeps its `%scope`, which `SocketAddr` parses back); `is_local(ip)`; `broadcast(port)`, `multicast(port)` (`[ff02::1]:port`). `Lan`: an IPv4 UDP socket bound to the port (`lan::PORT` 47380, provisional) with broadcast on, and where the machine has IPv6 an IPv6-only socket (socket2 `set_only_v6`) at the same port in ff02::1; `announce(to)` picks the socket by `to`'s family; ff02::1 with no scope goes out each up interface with an IPv6 link-local address, as `ff02::1%<index>` (`targets`, `link_scopes`; `v6_scopes()` reads the kernel's IPv6 address list, `/proc/net/if_inet6` (`if_inet6`), at each announcement: Linux and Android only, elsewhere the default interface), nothing joined per interface (every IPv6 interface is in ff02::1, and Linux's `IPV6_MULTICAST_ALL`, on by default, delivers it to the unconnected socket; not verifiable here: the dev VM drops looped-back multicast); every scoped send failing, or no interface known: the default one, `recv()` polls both (skips other datagrams and non-local sources) and returns the source socket address. `route_ip()`: the local addresses of the IPv4 and IPv6 routes out (UDP sockets connected to documentation prefixes, no packet sent). `NetWatch`: `changed()` resolves at a network change, seen by polling the routes' local addresses every `ROUTE_POLL` (5 s; IPv6 by /64 prefix, `network_of`: temporary addresses rotate within a network). OS network events (netlink and the like) are not watched: no dependency for them; another network with the same addressing goes unseen, and a P2P listener's registrations renew on their own once their relay connections time out (its socket is bound to an unspecified address, so it survives). `recv` alternates which socket it polls first.
- `Multi` (`multi.rs`): one transport over `mem`/`quic`/`p2p`/`unix` by URL scheme (`peer://` to `P2p`; `Multi<U>` takes `P2p<QuicUdp>` or, in a test net, `P2p<MemUdp>`); a scheme without its transport is `UnknownScheme`. The osis handle's driver runs on it.
- `Unix` (`unix.rs`, `unix:///abs/path`, notes/client-port.md §5): tokio `UnixStream`, path sockets only (relative, abstract or over `MAX_PATH` 107 bytes is `BadUrl`), one stream per connection; `SO_PEERCRED` both ways, each side accepting only its own uid; `Connection::peer()` is `Peer::Unix { uid }` (every other transport `Peer::Key`), `peer_key` the uid's derived key (`uid_key`), so the dialer's pinned-key check is the usual one; `own_uid` reads `SO_PEERCRED` of a socket pair (no unsafe code). A stale socket file is replaced at `listen`, a live one is `Io("in use")`; the listener removes its file on drop. `Multi.unix` dispatches it; `Link::peer` carries the peer to the node's `accept_peer`.
- Not yet: a WebSocket transport for browsers; backpressure in `InProcess`.

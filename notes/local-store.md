# Local store: encryption at rest and forward-secure deletion
> Summary: A node keeps plaintext, wraps and indexes only inside an encrypted local store whose unit keys hang off a key tree rooted in platform erasable storage; deleting a unit erases its key, so freed pages never matter and no storage engine has to erase anything. Chunk keys are random and stored in links, so crypto-shredding covers large values too. Dedup only against content the writer holds keeps the no-fingerprint rule. Also osis-store as built (backend, root, key tree, padding, shred semantics, failed writes, savepoints, tables, the ciphertext store, stamps, memory overlay, node log). What the engine keeps in it: notes/engine-store.md.

## Requirement
spec/requirements.md, Deletion: a node that deleted honestly and is compromised later yields nothing, not even confirmation of a guess. Compromise means the attacker holds the device unlocked, so disk encryption does not help, and freed store pages, journals and indexes all count.

## Principle
No storage engine erases reliably (SSD wear levelling, copy-on-write filesystems, write-ahead logs), so never rely on erasing data. Erase keys instead. Every piece of local plaintext or key material lives in a unit encrypted under its own unit key; unit keys live in a key tree whose root sits in the one place the platform can erase; deleting a unit means dropping its key and rotating the path to a fresh root. (Reardon, Basin, Capkun, "SoK: Secure Data Deletion", 2013; DNEFS.) The storage engine, whether SQLite, redb or plain files, only ever holds ciphertext, so the backend choice is free and freed pages are harmless.

## How the wire format supports it
- Commit blobs and chunks are encrypted under random keys (spec/crypto.md §5); chunk keys travel in links (spec/data-model.md §6). A content-derived chunk key would make every retained chunk ID a fingerprint and leave nothing to shred (spec/requirements.md, Data model).
- Shredding a version: drop the wraps of its commit blob. Its deltas, hence its root links, hence every tree node and chunk only this version reached, become unreadable. Surviving chunks stay reachable through the live tree. Purge cost is independent of value size.
- Dedup of large values is by reuse: an editor recomputes content-defined boundaries over the new content, matches chunks by keyed content hash against the current tree's links and reuses their (ID, key), unless the chunk must be re-encrypted (spec/sync-ids.md §1). This covers dedup across edits, nodes and editors; two parties independently creating equal content for one thing get two blobs, and there is no cross-thing dedup.
- The dedup secret keys content hashes only, never encryption, so it may stay permanent. Chunk IDs are hashes of ciphertext under random keys, so deletion lists and node log events are not fingerprints. Delete-key commitments derive from salts and public keys, never from content.

## Units
What a node holds and the unit each lives in:
- Blob ciphertexts: outside the key tree, in the node's one store of ciphertext (Ciphertext store, below); already opaque. Physically deleted when unreferenced, for space only.
- Wraps: the unit is a page of a sync ID's entries, a few KB. Dropping a blob from a sync ID rewrites its page without the wrap under a fresh page key. Needed because a reader holds the read secret, so a lingering wrap is a key.
- Aspect state: one unit per small aspect. A large collection (any depth, notes/engine-paged.md, Paged state) lives in an aspect table (Tables, below) of size-split pages keyed by the order-preserving bytes of their first dot, so the table's B+tree is the `dot -> page` index, plus a per-collection index (`keyed hash, dot`, keyed by a node-local secret; a superset, rebuilt with the layout) finding a map key's records and a set value's elements. A session loads the skeleton, then only the pages it touches, and a write rewrites only those and their path: a million-key map write costs a page plus its path (O(change) per edit, required for scale). A paged sequence keeps its placement (the crdt's, held in part), so reads by index, local edits and received joins load only the pages and placement rows they touch (issues/node-sequences-not-paged.md).
  - Drops: a covered drop rewrites shredded only the pages holding the body (notes/engine-paged.md, Writes); a purge or an expiry rewrites the whole paged state shredded (Whole rewrites there); a whole-thing purge drops the units.
- The node's persisted index (`node/*` tables, `node/perm`: notes/engine-store.md): rebuildable, tagged with a hash of the engine's and its osis dependencies' sources (`core/engine/build.rs`), dropped (shredded) and rebuilt from the commit records when the tag differs, a forget changed the records, or a row fails to decode.
- Decrypted chunk and tree-node caches, search and query indexes: units per aspect, or dropped and rebuilt. An index spanning aspects must be rebuildable and is dropped and rebuilt on a purge of anything it covers, or sharded per aspect.
- Role and sync ID secrets: units per thing; rotation on removal drops the old unit once nothing needs it (lazy rotation keeps old read secrets until then, by design). A node removed from a thing drops that thing's units and the content units only it opened (spec/permissions.md §3).
- Cursor logs, the IDs-gained list, diagnostics: blob IDs only, harmless; stored in the store anyway for uniformity.
- Memory, swap, core dumps, OS page cache: out of scope; mlock what is practical.

## Key tree
- Wide tree (256-ary) of 32-byte keys: leaves are unit keys, an interior node lists its children's keys encrypted under its own key, the root key lives in platform storage. It has only the levels its slots need (three hold 16M units).
- Delete or rotate a unit: new unit key (or none), fresh keys along the path to the root, rewrite those nodes (about 8 KB each), write the new root to platform storage, then delete the old nodes. Batched per sync. Crash safety: the new root is written last; until it is durable the old root still opens the old tree, so the deletion counts as complete only after the root replacement is durable.
- Platform root storage, by trust: hardware-backed keystore (Secure Enclave and Keychain, Android Keystore, TPM-sealed key, Windows DPAPI or TPM); kernel keyring or secret service for the session; overwrite of a small file with fsync as last resort (`FileRoot`, the only one built: issues/root-key-erasure-tier.md). Nothing records or reports which one a node uses.
- Unlock loads the root once per session; the tree is cached in memory. The root must stay readable after first unlock while the device is locked, so background sync (and push wake-ups, notes/networking.md) can present the sync key.

## What "dropped" means for a blob under several sync IDs
- Also held under another sync ID the node reads: keep the blob and that sync ID's wrap, drop only the purged sync ID's wrap.
- Under a sync ID the node keeps unread: keep; the wrap is unopenable here.
- A node keeping S unread, or a relay, never has plaintext; it honours delete-key signatures, S's delete key and expiry, nothing else. Its copy stays openable by anyone holding the read secret until a delete-key holder deletes it (spec/requirements.md, Deletion). A node keeps entries for sync in its own `Store` (not the engine's: it holds no role secrets) and every removal there shreds: a node keeping a sync ID it also reads holds the read secret, so a wrap kept on disk after a delete would open the blob.

## Cost
- Reads: one unit decrypt per aspect load, cached. Writes: every unit version gets a fresh key, so a commit seals the units it changed, the tree nodes above them (one per level per distinct parent) and the top: work in proportion to what changed, plus a path as tall as the store needs (`a_write_seals_one_path_as_tall_as_the_slots_need`, `paged::a_small_write_seals_its_page_and_the_top`). Scale tests count bytes handed to the store, not backend bytes: the path's full nodes (about 11 KB a level) step up a level at 256 slots, so a change's backend bytes double between a store below and above it.
- Purge: a rebuild of the aspect (O(aspect history), the whole paged state rewritten), plus the wrap pages touched, a tree path and one platform write; independent of value size. A covered drop: O(pages holding the body).
- Storage: 32 bytes per unit in the tree, plus about 64 bytes more per link inside large values, under 0.01% of a 1 MB chunk.
- One edit of a 1M-key table rewrites at most 5 unit rows plus its key-tree path; a value replaced in place rewrites its leaf alone (`btree::insert`).

## Implementation
`osis-store`; each module's doc (`pager.rs`, `btree.rs`, `store.rs`, `overlay.rs`, `cipher.rs`, `nodelog.rs`, `record.rs`, `changed.rs`) gives its layout and rows; only reasons and cross-cutting rules are here.
- **Backend**: `Backend` trait (ordered KV, limited scans, atomic durable `WriteBatch` with blob puts and deletes, ranged blob reads; `&mut` commits, so reads are snapshots). Only `Store` and the tests use it.
  - `MemoryBackend`: clones share data; `record_history` keeps every value ever written, for shredding tests.
  - `RedbBackend` (redb 2.6: pure Rust, no C build; rusqlite rejected for its bundled C SQLite): redb refuses every call after an I/O error until opened again, so a failed call closes the `Database` (releasing its file lock) and the next call opens it again, redb repairing on open: the store's recovery so reads the file as an open would. A call during which a sync failed fails `BackendError::Unsynced` (noted by the storage wrapper `Watched`); every open first drops the file's cached pages (`drop_cache`, Failed writes); `with_storage` takes any redb `StorageBackend` opener, which is how tests inject faults.
  - `Faults`: one plan per simulated node over every durable write: `Fault::Fail`, `Fault::Crash` (until `revive`), `Fault::Unsynced` (`MemoryBackend::power_cut` / `MemoryRoot::power_cut` drop it; later successful writes never make it durable, as on Linux).
- **One store handle, readers and writers take turns** (decided; revisit if a read must hold the store past one page): `Store` needs `&mut` for every read, so the node holds it behind one lock and a long streaming read interleaves page by page with writers; streams resume by key between pages. Rows are versioned, so read-only snapshot handles pinned to a committed version are possible later (a reader registry, superseded-row cleanup deferred while a snapshot is open); a reader-writer lock in the node is the other option.
- **Root**: `RootStorage` (`store` destroys the previous record, `erase` crypto-shreds the whole store). `FileRoot`: two fixed 64-byte slots overwritten in place with fsync, new slot first, then the other; never renamed, so the file system keeps no stale copy by its own doing. The root file and the redb file are created 0600 and the `osis` store directory 0700; existing ones are tightened on open, best effort (`restrict_to_owner`: only when group or other bits are set, never through a symlink); a failure there is no open failure: the `osis` handle reports a `DiagnosticKind::Storage` diagnostic.
- **Key tree** (`pager`): arity fixed at creation (default 256), height the fewest levels covering `next_slot` (`height`); slots are never reused, so the tree only grows, and a shredded path rotates every node above it up to the root even when the old top ends empty (`growth_erasure_and_crashes`: random commits, shreds, crashes and growth against a model, with the forensic attack). A fixed depth is rejected: every commit of a small store would reseal its empty levels. Rows: unit `u slot ver`, node `n level index ver`, top `t ver` (under the root key), pointer `r` = (epoch, ver), pending pointer `p`, journal `j ver k`. Every row is `nonce(24) || XChaCha20-Poly1305(row key as AD, padded plaintext)` (Row padding). Transactions above `spill_bytes` write unit rows early under journal records; a unit changed after its spill has that row rewritten (same row key) at the next spill or the commit, or deleted at commit if the unit ends deleted (`spilled_rewritten_deleted_unit_leaves_no_row`). Tree nodes and units are cached decrypted, emptied wholesale at a bound.
- **Row padding**: a freed page keeps an old row version's length, and the difference across a shredded drop would confirm a guess of what was dropped. Each row's plaintext is padded inside the AEAD like a blob (`P || 0x80 || zeros`, spec/wire.md §5) to Padmé of `len + 1`, unit rows to at least `UNIT_MIN` (512 B); open checks the padded length is exactly that. Padmé, not powers of two: on the engine tests' rows (units: median 4.2 KB, p10 182 B, p90 7.4 KB; mostly table pages between `page_max/2` and `page_max`) it costs 3.7% on units with the floor (2.3% without), tree nodes 2.6%, where powers of two with a 256 B minimum cost 44% on units; `row_padding_overhead` gives 2.1% mean over 512 B..16 KiB, at most 1/16. Padding pages to exactly `page_max` would hide pages fully but doubles small tables' units (+108% measured). What still shows: a row's class (O(log log n) bits of a length); a change of d bytes crosses a class boundary with probability about d / width (width 32 B at 512 B, 256 B at 4 KiB, 512 B at 8 KiB). Tree, top and journal rows get no floor: their length counts entries, which the row names show anyway. Row names (`u slot ver`, `n level index ver`) stay plaintext: they show which slot each version belongs to, the global order of versions and how many versions of a slot linger in freed pages, i.e. the write pattern, never content or lengths beyond the class. Accepted; what would close it: name each row by a hash of its own key (every version has a fresh key, the parent holds it, so lookups stay direct while names stop linking versions).
- **Shred semantics**: `Shred::Yes` on a write or removal makes the previous bytes unrecoverable at commit (path rotation, one root write per transaction). `Shred::No` rewrites may stay recoverable from freed storage under the still-live parent key until a later shred on the same path. Every `drop_*` shreds. A value above `page_max/4` keeps its unit across rewrites of its key and goes shredded when it turns small, so a later shred of the key reaches every earlier version. Engine records holding a copy of content kept elsewhere (a pending commit once applied) are removed shredded. A table page whose entries move to another slot is always written or deleted shredded (`btree.rs`; about one extra root write per transaction that splits).
- **Versions and rollback**: transaction versions never repeat within a session; a transaction takes its version when it first puts rows on the backend (a spill or its commit), so one that stores nothing takes none and the stored bytes are a function of what was stored, never of how many transactions ran (reads a skipped or missed memo ran: `a_transaction_storing_nothing_leaves_the_bytes_as_without_it`); `begin` rolls back the spills of aborted transactions; journals list a blob as new only if it was absent, so rollback never deletes a committed blob. `Store::create` stores the root last (a crash leaves no root: create again). `RootStorage::repair` runs on open.
- **Failed writes** (principle: a commit reported landed is durable; one not known durable is `Err`). A failed write either had no effect, or reads as written with its sync failed (`Unsynced`): a failed fsync leaves the bytes in the page cache, so anything reading the file in this boot sees them, while a power cut may drop them, and Linux drops the failed pages from write-back, so a later successful sync does not save them, nor anything a CoW engine like redb builds on them. Hence:
  - On `Err` other than `Unsynced`, what the backend reads is durable. A failed commit recovers the store as `open` would and reads its outcome there, so `commit`'s result is the outcome (a shredding commit failing after its root record was stored landed: `Ok`); `Err` leaves the store at its last durable state and the next transaction works. A failed spill or rollback write fails its transaction (`Error::Broken`) and the next `begin` recovers first.
  - An `Unsynced` write (commit, spill, rollback or recovery) leaves the outcome unknown: `Err`, counted in `Writes::unknown`, and every call fails `Broken` until the store recovers in place, which it retries on its own (`Pager::begin`, `recover`, which `open` runs; between attempts it answers `Broken` without touching the backend, waits of 1 s doubling to 60 s, `RETRY_FIRST`/`RETRY_MAX`). Nothing above the store reopens anything.
  - Why the recovery reads the disk: Linux keeps pages whose fsync failed in the page cache, marked clean, so a plain reopen would read them (the commit seems landed) and later redb commits would reference pages the disk never got: a power cut then loses them or leaves the file unreadable ("All roots are corrupted"). Rewriting the landed state is no fix on redb for the same reason. So every redb open first fsyncs the file and drops its clean cached pages (`posix_fadvise(DONTNEED)` through rustix, which drops only clean unmapped pages: checked with `fincore`; redb does not mmap), then reads what the disk holds, and redb's own synced open commit makes that durable. Linux and Android only: macOS and Windows document no call that evicts a file's clean cached pages (`F_NOCACHE` and unbuffered handles only change new I/O), so there an open after a failed sync fails and the store stays `Broken` until the process restarts, and that restart in the same boot reads the cache.
  - Root: `RootStorage::repair` (run by every recovery, before `load`) writes again a record whose sync failed (`FileRoot`: slots that differ, or both after a slot's sync failed since its last repair; across a process restart only differing slots are seen, so an old key may stay until the next `store`), so recovery reads a durable root and a shredding commit whose root store failed `Unsynced` lands `Ok`. Without it the recovery's finish would move `r` to a root epoch the disk lacks: unopenable after a power cut.
  - What the owner sees: a commit answered `Err` may have landed, so an owner holding state beside the store reads it whole again (`Store::writes`): the engine at its next `run` (`Engine::reload_owed`, `Engine::load`), under a fresh session when the outcome was unknown (that commit's counters may be taken), then `Event::Reloaded` (notes/api.md Watching); sync too. The engine's journaled rollback is exact (engine `failing` and `crash::` compare against a fresh open, `check_index`). While broken, app calls fail `Error::Storage` and sync's failed steps report `DiagnosticKind::Storage`.
  - Tests: `a_commit_whose_sync_failed_is_never_reported_landed` (every durable write's sync of plain and shredding commits, memory and redb, no reopen, then a power cut: every `Ok` commit survives and the store opens), `a_failed_redb_write_anywhere_in_a_commit_reports_its_outcome` (a fresh store per fault point: redb flushes a commit's pages in no fixed order, so a fault after the header write can land, its checksums deciding), `a_spill_whose_sync_failed_recovers_in_place`, `a_lost_store_retries_after_a_wait`, osis `watch::a_commit_found_landed_after_a_failed_sync_reaches_watches`. On redb the test `FaultyRedb` fails the first file write of a planned fault (or its sync), and `Device::power_cut` puts back the bytes last synced. Power cuts come straight after the faulted commit (a later commit rewriting the same page makes the lost write durable again), on a store of a few hundred rows (with one table page every commit rewrites every page, hiding the bug); each fails with its fix disabled.
- **Savepoints** (`Transaction::savepoint`, `rollback_to`, `release`; nested): the dirty set keeps an undo log of the first change of each unit and blob under each open savepoint (memory bounded by what the step touched, not by how often it rewrote a page). Nothing spills while a savepoint is open (a spilled row is out of a rollback's reach); the outermost release spills what waited, so a transaction may overshoot `spill_bytes` by one step's writes (in the engine at most one commit's apply). Commit and suspend refuse an open savepoint. A savepoint never reaches the backend.
- **Tables** (`btree`): `page_max` default 8 KiB, fixed at creation; keys at most `page_max/4`; interior entries hold the child's first key exactly, so a shredded key leaves no separator copy. Size-split B+tree instead of content-defined (prolly) pages: local pages need no history independence, and the B+tree is simpler with the same O(log n) pages per edit. A page is decoded once per write of its unit (cached decoded, `unit_cache_bytes` counting three times its bytes; `paged::a_table_page_is_decoded_once_per_write`, `Store::pages_decoded`) and a page written in a transaction stays decoded (`DirtyUnit::Page`) until its bytes are needed, so many puts into one leaf encode it once (about two thirds of page puts in the node tests hit a page already dirty). A page is taken for change (`DirtyUnit::Taken`) only once it will change, so only an operation failed part way leaves one out, and reading it or committing then fails (`unspilled_pages_roll_back_and_absent_removals_change_nothing`).
- **Store API** (`store.rs`): `Transaction::suspend` / `Store::resume` set a transaction aside between calls (memory rows refused); `drop_aspect` shreds unit and tables but keeps counters; `reserve_counters` commits before signing; `*_local` records. Every list is paged by a limit; nothing materializes a whole table.
- **Ciphertext store** (`cipher.rs`, `Ciphertext`/`CipherTx`/`CipherStore`): the engine's blobs live in the node's store of ciphertext beside its own store (notes/sync-store.md), locked at an engine transaction's first blob use (`engine/blobs.rs` `Cipher`, `Tx::blobs`). Principle: add before, remove after. The engine `hold`s a blob in the ciphertext store's transaction, committed before the engine's store; it `release`s one only after the engine's store committed (`Cipher::after`), so engine state never names a blob gone. Crashes between the two commits: both sides note the ciphertext transaction's sequence (`CipherTx::note`, `records::BLOB_SEQ`), and `Engine::settle_blobs` (at open, after a failed commit or release) undoes or finishes it (`crash::crash_every_write_of_a_chunked_commit`, `crash_every_write_of_a_hold_and_release`). A commit the engine forgets other than by lost access (`Cipher::forgot`, `Note::forgot`) takes sync's entries of its blobs with it (`CipherStore::forgot`), so storage follows the engine's holding with no feed and no start sweep. A step rolled back (`Tx::step`) keeps none of its holds, releases or forgotten blobs (`blobs::tests`). Memory blobs live in the store's memory map, never on disk.
- **Stamps** (`Stamping`, `osis_base::memo`; notes/engine.md Derived values; the families: `Stamping`'s doc): a table's rows are stamped under their owner's stamp, apart from its catalog row's, so a row write moves no reader of the table's handle; a `table_range` by what its start and end share (an open end, `len`, `rank` and `nth` read the table whole). Module rows of peer records sit in stamp tables of their own, as a record's LRU and actor rows move at each use (`record::using_a_record_moves_no_reader_of_module_rows`). A put of a row's own bytes again, or a removal of an absent row, stamps nothing. Whether any row under a prefix passes a test (`cat_any`, `records_any_row`) is read by its witness, the first such key alone, else the prefix (`record::any_row_moves_only_as_it_can_turn`). An undone write is stamped again as removed (a dropped `Suspended` only at the next `transaction`; the stores that suspend have no memo reading them). A blob's presence is stamped by its ID (`blob_key`; `store::a_memo_over_a_blob_moves_as_it_comes_and_goes`). `noted_aspect`/`noted_local` record a read answered from a copy the caller keeps; `row_changes` counts every row change.
- **Memory overlay** (`overlay.rs`). Routing: memory mode (`set_memory`, a memory commit's application) sends every new row to memory; a row already in memory stays there; every aspect-keyed row of an ephemeral (`+`) aspect goes to memory whatever the mode; `index(name)` tables are durable and hold memory rows per row. A memory row over a durable one is a bug (debug assert); a transaction writing only memory rows commits with no backend write. Not written in memory mode: the HLC record (the next durable commit persists the clock). Durable whatever the mode: the node log, peer records and `changed` rows (`cat_put_to(.., false)`), so a memory-mode transaction that logs or writes a record commits durably; osis-sync keeps its memory part in a second store for this reason (notes/sync-store.md, Two parts). The engine routes opaque local records by class (`Tx::in_class`). `Store::memory_held` reports each row's and blob's bytes plus `MEM_ROW_COST` (160 B: a B-tree slot of two `Vec` headers at half-full nodes, two allocation headers, its key's stamp), O(rows).
- **Not here**: `PageSink`/`PageSource` adapters (wire pages are blobs under random keys with link hashes: osis-blob and the engine build them; the layer DAG keeps crdt out of store).
- **Tests**: crash tests and `failed_commit_recovers_in_place` run on memory and on redb with `FileRoot` (each slot write a fault point), and at engine level (`core/engine/tests/it/crash.rs`: every write of a purging commit). The full forensic attack (notes/test-security.md, Forensic attack) needs every row and blob ever written, so it runs on `MemoryBackend` only, over a 4-ary key tree so leaks are not rotated away by accident; on redb the test checks the file holds no plaintext. Bit flips in any row or the root: errors, never panics (`core/engine/tests/it/corrupt.rs`).

## Node log
`nodelog.rs` (the node log of spec/sync-streams.md §3; rows, incarnations and compaction: its module doc). Incarnation limit `StoreConfig::incarnations_kept` (default `INCARNATIONS_KEPT`). Whether this open has drawn an incarnation is `Meta::log_drawn`, never encoded, so a restart, a restored store and a copy all draw at their first append (a recovery in place reads the meta afresh, an aborted transaction discards the mark). Its rows hold positions and IDs only: overwrites shred nothing, removals do, so logging an entry adds no shredding commit. `changed_at` (`changed.rs`) and per-peer records (`record.rs`) are compared only within one store, so the log may live in another; the node's one log is in sync's store of entries, never the engine's. Ephemeral entries are not in it.

An `Added` is logged when an entry becomes servable, not merely known: its row and its bytes both held, in the transaction that completes the pair. An entry without bytes has no row and no event; its bytes arriving (commit or chunk) is what logs it; compaction still leaves one event per entry. A row's removal logs its deletion; an entry added and removed within one flush logs nothing (no reader saw it).

# Local store: encryption at rest and forward-secure deletion
> Summary: A node keeps plaintext, wraps and indexes only inside an encrypted local store whose unit keys hang off a key tree rooted in platform erasable storage; deleting a unit erases its key, so freed pages never matter and no storage engine has to erase anything. Chunk keys are random and stored in links, so crypto-shredding covers large values too. Design decided; part of the MVP. Dedup only against content the writer holds keeps the no-fingerprint rule.

## Requirement
spec/requirements.md, Deletion: a node that deleted honestly and is compromised later yields nothing, not even confirmation of a guess. Compromise means the attacker holds the device unlocked, so disk encryption does not help, and freed database pages, journals, undo buffers and indexes all count.

## Principle
No storage engine erases reliably (SSD wear levelling, copy-on-write filesystems, write-ahead logs), so never rely on erasing data. Erase keys instead. Every piece of local plaintext or key material lives in a unit encrypted under its own unit key; unit keys live in a key tree whose root sits in the one place the platform can erase; deleting a unit means dropping its key and rotating the path to a fresh root. (Reardon, Basin, Capkun, "SoK: Secure Data Deletion", 2013; DNEFS.) The storage engine, whether SQLite, redb or plain files, only ever holds ciphertext, so the backend choice is free and freed pages are harmless.

## How the wire format supports it
- Commit blobs and chunks are encrypted under random keys (spec/crypto.md §5); chunk keys travel in links (spec/data-model.md §6). A content-derived chunk key would make every retained chunk ID a fingerprint and leave nothing to shred (spec/requirements.md, Data model).
- Shredding a version: drop the wraps of its commit blob. Its deltas, hence its root links, hence every tree node and chunk only this version reached, become unreadable. Surviving chunks stay reachable through the live tree. Purge cost is independent of value size.
- Dedup of large values is by reuse: an editor holds the current tree, recomputes content-defined boundaries over the new content, matches chunks by keyed content hash against the tree's links and reuses their (ID, key), unless the chunk must be re-encrypted (spec/sync.md §1); only new chunks become new blobs. This covers dedup across edits, devices and editors; two parties independently creating equal content for one thing get two blobs, and there is no cross-thing dedup.
- The dedup secret keys content hashes only, never encryption, so it may stay permanent. Chunk IDs are hashes of ciphertext under random keys, so deletion lists, cursor logs and IDs-gained lists are not fingerprints. Delete-key commitments derive from salts and public keys, never from content.

## Units
What a node holds and the unit each lives in:
- Blob ciphertexts: outside the store, plain files or rows; already opaque. Physically deleted when unreferenced, for space only.
- Wraps: the unit is a page of label entries, a few KB. Dropping a blob from a label rewrites its page without the wrap under a fresh page key. Needed because a member holds the label read secret, so a lingering wrap is a key.
- Aspect state, its undo buffer and pre-reset snapshots: one unit per small aspect. A large state (above about `PAGE_TARGET`) is paged like a snapshot (spec/crdt.md §8): page units at content-defined boundaries over consecutive elements, plus index units (`key -> page`, `dot range -> page`, for text `dot -> position`) that are themselves paged as a tree once large, so a million-key map write rewrites one page plus its index path (prolly-tree style). A purge, an expiry or a keep-at-most bound rewrites the pages that held the dropped body and their index path under fresh keys, and strips its content from the undo buffer and pre-reset snapshots in the same transaction (a dropped body is not undoable, spec/commits.md §7); a whole-thing purge drops the units. Per body the store keeps its first and last death (spec/commits.md §5), updated when the killing commit applies. MVP requirement (scale: O(change) per edit). Built (notes/node.md, Paged state): every large collection at any depth below struct fields, enum payloads and map entries is paged; pages are size-split rows of an aspect table rather than content-defined, keyed by the order-preserving bytes of their first dot, so the store's B+tree is the `dot -> page` index (the page holding a dot: `table_rank` then `table_nth`); a per-collection index (`keyed hash, dot`, keyed by a node-local secret; a superset, rebuilt with the layout) finds a map key's entries and a set value's elements (links by content hash); a session loads the skeleton and then only the pages it touches. A purge, expiry or keep-at-most drop rewrites shredded the pages holding the dropped delta's dots and the skeleton, and drops the index rows of entries left keyless and set elements left value-less (a keep-at-most drop: of the dropped bodies' entries the state no longer holds). A paged sequence keeps its placement as blocks of visible dots in order with a summary of their counts (exact, rebuildable; notes/node.md Store records), so a read by index range loads only the pages holding what it reads; writes and joins still load the sequence whole (its placement is built in memory; issues/node-sequences-not-paged.md).
- The node's persisted index (what open would otherwise re-derive: per commit part its validity, rotation role and overreach, the indexes derived from membership bodies, and perm's reading of each membership commit's `/members` and `/tenures` parts (`node/edges`, written with the commit record), in store index tables `node/*`): rebuildable, tagged with a hash of every workspace crate's `src` (`build.rs`), dropped (shredded) and rebuilt from the commit records, re-judging everything, when the tag differs, a forget changed the records, or a row fails to decode.
- Saved membership walks (`node/walks`, one unit per membership component, notes/node.md Open): rebuildable, tagged by BLAKE3 over the rules tag, a format string, the walk's exact inputs and the bytes; used only on a match, else evaluated anew; written in the index's transaction and dropped with the index tables.
- Decrypted chunk and tree-node caches, search and query indexes: units per aspect, or dropped and rebuilt. An index spanning aspects must be rebuildable and is dropped and rebuilt on a purge of anything it covers, or sharded per aspect.
- Membership and label secrets: units per actor; rotation on removal drops the old unit once nothing needs it (lazy rotation keeps old read secrets until then, by design). A node removed from an actor drops that actor's units and the content units only it opened (spec/permissions.md §3).
- Cursor logs, the IDs-gained list, diagnostics: blob IDs only, harmless; stored in the store anyway for uniformity.
- Memory, swap, core dumps, OS page cache: out of scope; mlock what is practical.

## Key tree
- Wide tree (256-ary) of 32-byte keys. Leaves are unit keys; an interior node is the list of its children's keys encrypted under its own key; the root key lives in platform storage. Three levels cover 16M units; more units add a level.
- Delete or rotate a unit: new unit key (or none), fresh keys along the path to the root, rewrite those nodes (about 8 KB each), write the new root to platform storage, then delete the old nodes. Batched per sync. Crash safety: the new root is written last; until it is durable the old root still opens the old tree, so the deletion counts as complete only after the root replacement is durable.
- Platform root storage, by trust: hardware-backed keystore (Secure Enclave and Keychain, Android Keystore, TPM-sealed key, Windows DPAPI or TPM); kernel keyring or secret service for the session; overwrite of a small file with fsync as last resort. The node records its tier and diagnostics report "best effort" below hardware-backed; nothing depends on that being read.
- Unlock loads the root once per session; the tree is cached in memory. The root must stay readable after first unlock while the device is locked, so background sync (and push wake-ups, notes/networking.md) can present the sync key.

## What "dropped" means for a blob under several labels
- Also held under another label the node is a member of: keep the blob and that label's wrap, drop only the purged label's wrap. The content is legitimately still readable there.
- Under a label the node is blind for: keep; the wrap is unopenable here.
- A blind node or relay never has plaintext; it honours delete-key signatures, timed deletes, its label delete key and expiry, nothing else. Its copy stays openable by anyone holding the label read secret until a delete-key holder deletes it (spec/requirements.md, Deletion).

## Cost
- Reads: one unit decrypt per aspect load, cached. Writes: re-encrypt the unit; the tree is untouched unless a key rotates.
- Purge: O(pages holding the purged body), plus the wrap pages touched, plus three tree nodes and one platform write. Independent of history length and value size.
- Storage: 32 bytes per unit in the tree, plus about 64 bytes more per link inside large values, under 0.01% of a 1 MB chunk.

## Implementation
`osis-store` (crate doc and module docs carry the details).
- **Backend**: `Backend` trait (ordered KV, prefix/range scans with a limit, atomic durable `WriteBatch` with blob puts and deletes, blob area with ranged reads; one handle, `&mut` commits, so reads are snapshots). `MemoryBackend` (clones share data; `record_history` keeps every value ever written, for shredding tests), `FaultyBackend<B>` (wraps any backend), `RedbBackend` (feature `file-backend`; redb 2.6: pure Rust, no C build, MSRV fits; rusqlite rejected for its bundled C SQLite). `Faults`: one plan per simulated device, counting every durable write (backend commit or root store); `Fault::Fail` or `Fault::Crash` (that write and all later fail until `revive`).
- **One store handle, readers and writers take turns** (decided, revisit only if profiling shows a stall): `Store` needs `&mut` for every read, so the node holds it behind one lock and a long streaming read (a multi-gigabyte value) interleaves page by page with writers; streams resume by key between pages, so no user-visible stall is expected. Rows are versioned, so read-only snapshot handles pinned to a committed version are possible later (a reader registry, superseded-row cleanup deferred while a snapshot is open); a reader-writer lock in the node is the other option.
- **Root**: `RootStorage` (`load`, `store` destroys the previous record, `tier`). `MemoryRoot`; `FileRoot` (`file-backend`): two fixed 64-byte slots (magic, seq, epoch, key, check) overwritten in place with fsync, new slot first, then the other; never renamed, so the file system keeps no stale copy by its own doing. Tier `FileOverwrite` (best effort); hardware keystores not implemented. The root file and the redb file are created 0600 and the `osis` store directory 0700; existing ones are tightened on open, best effort (`restrict_to_owner`: only when group or other bits are set, never through a symlink, the system allowing only the owner; `RedbBackend::open` and `FileRoot` reads ignore a failure, the `osis` handle checks the dir, db and root and reports a `DiagnosticKind::Storage` diagnostic instead of failing the open).
- **Key tree** (`pager`): fixed depth (default 5) and arity (default 256), sparse nodes listing `(child, key, ver)`; capacity `arity^depth` slots, never reused. Rows: unit `u slot ver`, node `n level index ver`, top `t ver` (meta + top entries, under the root key), pointer `r` = (epoch, ver), pending pointer `p`, journal `j ver k`. Every row is `nonce(24) || XChaCha20-Poly1305(row key as AD)`; each unit version gets a fresh random key. A transaction writes new versions; commit without shredding is one batch (new rows, `r`, deletes of superseded rows); with shredding the touched nodes on shredded paths and the top get fresh keys: batch A (rows, `p`, final journal), root store (commit point), batch B (`r`, deletes). Open finishes (p.epoch = root epoch) or rolls back from journals. Transactions above `spill_bytes` write unit rows early under journal records, keys kept in memory. Tree nodes and units are cached decrypted, emptied wholesale at a bound.
- **Shred semantics**: `Shred::Yes` on a write or removal makes the previous bytes unrecoverable at commit (path rotation, one root write per transaction). `Shred::No` rewrites may stay recoverable from freed storage under the still-live parent key until a later shred on the same path. Every `drop_*` shreds. A value above `page_max/4` keeps its unit across rewrites of its key and goes shredded when it turns small, so a later shred of the key reaches every earlier version (a fresh unit per rewrite left old versions out of reach). Engine records holding a copy of content kept elsewhere (a pending commit once applied) are removed shredded. A table page whose entries move to another slot (split, merge, root move or collapse) is always written or deleted shredded, so a later shred of a moved entry reaches every old copy (about one extra root write per transaction that splits).
- **Versions and rollback**: transaction versions never repeat within a session; `begin` rolls back the spills of aborted transactions; journals list a blob as new only if it was absent, so rollback never deletes a committed blob. `Store::create` writes the catalog in its first batch and stores the root last (a crash leaves no root: create again). `RootStorage::repair` runs on open (`FileRoot`: a crash between the slot writes leaves the old key in one slot; repair overwrites it). `Transaction::commit` returning `Err` means unknown: reopen and read back.
- **Tables** (`btree`): B+trees of units, pages split and merged by encoded size (`page_max`, default 8 KiB, fixed at creation), interior entries hold the child's first key exactly (so a shredded key leaves no separator copy) and its entry count (`table_rank`, `table_nth`); values above `page_max/4` in their own unit; keys at most `page_max/4`; root slot stable. Size-split B+tree instead of content-defined (prolly) pages: local pages need no history independence, and the B+tree is simpler with the same O(log n) pages per edit.
- **Store API**: `Store::{create, open, transaction(rng)}`; `Transaction` (drop aborts, `commit`): one catalog table keyed `kind || ...` (aspect `tid || u32 len || ak`): `AspectUnit {state, undo, snapshots}`, `note_death`/`death`/`deaths` (first/last per body and aspect), `drop_body` (death records shredded, ciphertext deleted; the caller rewrites the aspect with `Shred::Yes`), `drop_aspect` (unit, tables, deaths; counters stay), aspect tables `create_table(tid, ak, idx)` with `table_*`, rebuildable `index(name)` / `drop_indexes`, wraps per (label, blob) with `drop_wrap`, actor secrets with `drop_actor_secrets`, cursors, append logs (`log_append/scan/truncate`, IDs gained), `reserve_counters` (commit before signing), pending/parked commits, `*_local` records, blob ciphertexts. Every list is paged by a limit; nothing materializes a whole table.
- **Not here**: `PageSink`/`PageSource` adapters (wire pages are blobs under random keys with link hashes: label and node build them; the layer DAG keeps crdt out of store). Concurrent readers (issues/store-concurrent-readers.md).
- Tests: crash tests run on memory and on redb with `FileRoot` (each slot write a fault point), and at node level (`osis-node/tests/it/crash.rs`: every write of a purging commit); the full forensic shredding attack needs every value ever written, so it runs on `MemoryBackend` only (store: `osis-store/tests/it/shred.rs`; node: `osis-node/tests/it/shred.rs`, purge, pending then purge, expiry, keep at most 0, chunked large value, over a 4-ary key tree so leaks are not rotated away by accident); on redb the test checks the file holds no plaintext. Bit flips in any row or the root: errors, never panics (`osis-node/tests/it/corrupt.rs`).
- Cost (release, shared 4-core box): filling a 1M-key table plus a 1M-entry index takes about 60 s (pages are decoded per access; no decoded-page cache yet); one edit of it rewrites at most 5 unit rows plus its key-tree path.

# Local store: encryption at rest and forward-secure deletion
> Summary: A node keeps plaintext, wraps and indexes only inside an encrypted local store whose unit keys hang off a key tree rooted in platform erasable storage; deleting a unit erases its key, so freed pages never matter and no storage engine has to erase anything. Chunk keys are random and stored in links, so crypto-shredding covers large values too. Dedup only against content the writer holds keeps the no-fingerprint rule. Also osis-store as built (backend, root, key tree rows, padding, shred semantics, tables, memory overlay). What the engine keeps in it: notes/engine-store.md.

## Requirement
spec/requirements.md, Deletion: a node that deleted honestly and is compromised later yields nothing, not even confirmation of a guess. Compromise means the attacker holds the device unlocked, so disk encryption does not help, and freed store pages, journals and indexes all count.

## Principle
No storage engine erases reliably (SSD wear levelling, copy-on-write filesystems, write-ahead logs), so never rely on erasing data. Erase keys instead. Every piece of local plaintext or key material lives in a unit encrypted under its own unit key; unit keys live in a key tree whose root sits in the one place the platform can erase; deleting a unit means dropping its key and rotating the path to a fresh root. (Reardon, Basin, Capkun, "SoK: Secure Data Deletion", 2013; DNEFS.) The storage engine, whether SQLite, redb or plain files, only ever holds ciphertext, so the backend choice is free and freed pages are harmless.

## How the wire format supports it
- Commit blobs and chunks are encrypted under random keys (spec/crypto.md §5); chunk keys travel in links (spec/data-model.md §6). A content-derived chunk key would make every retained chunk ID a fingerprint and leave nothing to shred (spec/requirements.md, Data model).
- Shredding a version: drop the wraps of its commit blob. Its deltas, hence its root links, hence every tree node and chunk only this version reached, become unreadable. Surviving chunks stay reachable through the live tree. Purge cost is independent of value size.
- Dedup of large values is by reuse: an editor holds the current tree, recomputes content-defined boundaries over the new content, matches chunks by keyed content hash against the tree's links and reuses their (ID, key), unless the chunk must be re-encrypted (spec/sync.md §1); only new chunks become new blobs. This covers dedup across edits, nodes and editors; two parties independently creating equal content for one thing get two blobs, and there is no cross-thing dedup.
- The dedup secret keys content hashes only, never encryption, so it may stay permanent. Chunk IDs are hashes of ciphertext under random keys, so deletion lists and node log events are not fingerprints. Delete-key commitments derive from salts and public keys, never from content.

## Units
What a node holds and the unit each lives in:
- Blob ciphertexts: outside the key tree, in the node's one store of ciphertext (Ciphertext store, below); already opaque. Physically deleted when unreferenced, for space only.
- Wraps: the unit is a page of label entries, a few KB. Dropping a blob from a label rewrites its page without the wrap under a fresh page key. Needed because a holder holds the label read secret, so a lingering wrap is a key.
- Aspect state: one unit per small aspect. A large state (above about `PAGE_TARGET`) is paged like a snapshot (spec/crdt.md §8): page units at content-defined boundaries over consecutive elements, plus index units (`key -> page`, `dot range -> page`, for text `dot -> position`) that are themselves paged as a tree once large, so a million-key map write rewrites one page plus its index path (prolly-tree style). A purge, an expiry or a covered drop rewrites the pages that held the dropped body and their index path under fresh keys; a whole-thing purge drops the units. Per body the store keeps its first and last death (spec/commits.md §5), updated when the killing commit applies. Required for scale (O(change) per edit). As built (notes/engine-paged.md): every large collection at any depth below struct fields, enum payloads and map entries is paged; pages are size-split rows of an aspect table rather than content-defined, keyed by the order-preserving bytes of their first dot, so the store's B+tree is the `dot -> page` index (the page holding a dot: `table_rank` then `table_nth`); a per-collection index (`keyed hash, dot`, keyed by a node-local secret; a superset, rebuilt with the layout) finds a map key's entries and a set value's elements (links by content hash); a session loads the skeleton and then only the pages it touches; a join rewrites only the pages it touched. A purge, expiry or covered drop rebuilds the aspect (notes/engine-validity-rebuild.md) and rewrites the whole paged state shredded, its old pages and index rows dropped: O(aspect state), not O(pages holding the body) as the design above aims. A paged sequence keeps its placement (the crdt's, held in part; notes/engine-paged.md), so reads by index, local edits (a text session's included) and received joins load only the pages and placement rows they touch (what remains: issues/node-sequences-not-paged.md).
- The node's persisted index (what open would otherwise re-derive: per commit part its validity, rotation role and overreach, the indexes derived from role-commit bodies, and perm's reading of each role commit's `roles.0` parts (`node/edges`, written with the commit record), in store index tables `node/*`): rebuildable, tagged with a hash of the engine's and its osis dependencies' sources (`core/engine/build.rs`; notes/engine-store.md), dropped (shredded) and rebuilt from the commit records, re-judging everything, when the tag differs, a forget changed the records, or a row fails to decode.
- Saved role walks (`node/walks`, one unit per role component, notes/engine-store.md Open): rebuildable, tagged by BLAKE3 over the rules tag, a format string, the walk's exact inputs and the bytes; used only on a match, else evaluated anew; written in the index's transaction and dropped with the index tables.
- Decrypted chunk and tree-node caches, search and query indexes: units per aspect, or dropped and rebuilt. An index spanning aspects must be rebuildable and is dropped and rebuilt on a purge of anything it covers, or sharded per aspect.
- Role and label secrets: units per actor; rotation on removal drops the old unit once nothing needs it (lazy rotation keeps old read secrets until then, by design). A node removed from an actor drops that actor's units and the content units only it opened (spec/permissions.md §3).
- Cursor logs, the IDs-gained list, diagnostics: blob IDs only, harmless; stored in the store anyway for uniformity.
- Memory, swap, core dumps, OS page cache: out of scope; mlock what is practical.

## Key tree
- Wide tree (256-ary) of 32-byte keys. Leaves are unit keys; an interior node is the list of its children's keys encrypted under its own key; the root key lives in platform storage. Three levels cover 16M units; more units add a level.
- Delete or rotate a unit: new unit key (or none), fresh keys along the path to the root, rewrite those nodes (about 8 KB each), write the new root to platform storage, then delete the old nodes. Batched per sync. Crash safety: the new root is written last; until it is durable the old root still opens the old tree, so the deletion counts as complete only after the root replacement is durable.
- Platform root storage, by trust: hardware-backed keystore (Secure Enclave and Keychain, Android Keystore, TPM-sealed key, Windows DPAPI or TPM); kernel keyring or secret service for the session; overwrite of a small file with fsync as last resort (`FileRoot`, the only one built: issues/root-key-erasure-tier.md). Nothing records or reports which one a node uses.
- Unlock loads the root once per session; the tree is cached in memory. The root must stay readable after first unlock while the device is locked, so background sync (and push wake-ups, notes/networking.md) can present the sync key.

## What "dropped" means for a blob under several labels
- Also held under another label the node reads: keep the blob and that label's wrap, drop only the purged label's wrap. The content is legitimately still readable there.
- Under a label the node cannot read: keep; the wrap is unopenable here.
- A host or relay never has plaintext; it honours delete-key signatures, its label delete key and expiry, nothing else. Its copy stays openable by anyone holding the label read secret until a delete-key holder deletes it (spec/requirements.md, Deletion). A node's host keeps its entries in its own `Store` (not the node's: it holds no actor secrets) and every removal there shreds: a node hosting a label it also reads holds the read secret, so a wrap kept on disk after a delete would open the blob. Blob ciphertexts there are deleted for space only; without a wrap they open nowhere.

## Cost
- Reads: one unit decrypt per aspect load, cached. Writes: re-encrypt the unit; the tree is untouched unless a key rotates.
- Purge: designed O(pages holding the purged body), plus the wrap pages touched, plus three tree nodes and one platform write, independent of history length and value size. As built a drop rebuilds the aspect (O(aspect history), the whole paged state rewritten); still independent of value size.
- Storage: 32 bytes per unit in the tree, plus about 64 bytes more per link inside large values, under 0.01% of a 1 MB chunk.

## Implementation
`osis-store` (crate doc and module docs carry the details).
- **Backend**: `Backend` trait (ordered KV, prefix/range scans with a limit, atomic durable `WriteBatch` with blob puts and deletes, blob area with ranged reads; one handle, `&mut` commits, so reads are snapshots). Only `Store` and the tests use it. `MemoryBackend` (clones share data; `record_history` keeps every value ever written, for shredding tests), `RedbBackend` (redb 2.6: pure Rust, no C build, MSRV fits; rusqlite rejected for its bundled C SQLite; redb refuses every call after an I/O error until opened again, so a failed call closes the `Database`, releasing its file lock, and the next call opens it again, redb repairing on open: one place in the backend, so the store's recovery reads the file as an open would, and fails while the open does; a call during which a sync of the file failed fails `BackendError::Unsynced` (the storage wrapper `Watched` notes it); every open first drops the file's cached pages (`drop_cache`: an fsync attempt, then `posix_fadvise(DONTNEED)` through rustix), so it reads what the disk holds (Failed writes); `with_storage` takes any redb `StorageBackend` opener, told whether a sync failed since the first open, how the tests inject faults). `Faults`: one plan per simulated node, counting every durable write (backend commit or root store); `Fault::Fail` (that write has no effect), `Fault::Crash` (that write and all later fail until `revive`) or `Fault::Unsynced` (that write reads as written but fails `Unsynced`; `MemoryBackend::power_cut` / `MemoryRoot::power_cut` drop it, and later successful writes never make it durable, as Linux drops pages whose fsync failed from write-back; a `MemoryBackend`'s next call reads what the disk holds, as redb's open after the failed call does).
- **One store handle, readers and writers take turns** (decided, revisit only if profiling shows a stall): `Store` needs `&mut` for every read, so the node holds it behind one lock and a long streaming read (a multi-gigabyte value) interleaves page by page with writers; streams resume by key between pages, so no user-visible stall is expected. Rows are versioned, so read-only snapshot handles pinned to a committed version are possible later (a reader registry, superseded-row cleanup deferred while a snapshot is open); a reader-writer lock in the node is the other option.
- **Root**: `RootStorage` (`load`, `store` destroys the previous record, `erase`: no record left, the whole store crypto-shredded; `FileRoot` overwrites both slots, then removes the file; used for the host store when hosting stops). `MemoryRoot`; `FileRoot`: two fixed 64-byte slots (magic, seq, epoch, key, check) overwritten in place with fsync, new slot first, then the other; never renamed, so the file system keeps no stale copy by its own doing. Best effort: hardware keystores are not implemented. The root file and the redb file are created 0600 and the `osis` store directory 0700; existing ones are tightened on open, best effort (`restrict_to_owner`: only when group or other bits are set, never through a symlink, the system allowing only the owner; `RedbBackend::open` and `FileRoot` reads ignore a failure, the `osis` handle checks the dir, db and root and reports a `DiagnosticKind::Storage` diagnostic instead of failing the open).
- **Key tree** (`pager`): fixed depth (default 5) and arity (default 256), sparse nodes listing `(child, key, ver)`; capacity `arity^depth` slots, never reused. Rows: unit `u slot ver`, node `n level index ver`, top `t ver` (meta + top entries, under the root key), pointer `r` = (epoch, ver), pending pointer `p`, journal `j ver k`. Every row is `nonce(24) || XChaCha20-Poly1305(row key as AD, padded plaintext)` (Row padding); each unit version gets a fresh random key. A transaction writes new versions; commit without shredding is one batch (new rows, `r`, deletes of superseded rows); with shredding the touched nodes on shredded paths and the top get fresh keys: batch A (rows, `p`, final journal), root store (commit point), batch B (`r`, deletes). Open finishes (p.epoch = root epoch) or rolls back from journals. Transactions above `spill_bytes` write unit rows early under journal records, keys kept in memory; a unit changed after its spill has that row rewritten (same row key) at the next spill or the commit, or deleted at commit if the unit ends deleted (`spilled_rewritten_deleted_unit_leaves_no_row`). Tree nodes and units are cached decrypted, emptied wholesale at a bound.
- **Row padding**: a freed page keeps an old row version's length, and the difference across a shredded drop would confirm a guess of what was dropped. Each row's plaintext is padded inside the AEAD like a blob (`P || 0x80 || zeros`, spec/wire.md §5) to Padmé of `len + 1`, unit rows to at least `UNIT_MIN` (512 B); open checks the padded length is exactly that, so decoding is unambiguous. Padmé, not powers of two: on the engine tests' rows (units: median 4.2 KB, p10 182 B, p90 7.4 KB; mostly table pages between `page_max/2` and `page_max`) it costs 3.7% on units with the floor (2.3% without), tree nodes 2.6%, where powers of two with a 256 B minimum cost 44% on units; `row_padding_overhead` gives 2.1% mean over 512 B..16 KiB, at most 1/16. Padding pages to exactly `page_max` would hide pages fully but doubles small tables' units (+108% measured). What still shows: a row's class (Padmé leaks O(log log n) bits of a length); a change of d bytes moves a version across a class boundary with probability about d / width (width 32 B at 512 B, 256 B at 4 KiB, 512 B at 8 KiB), so a drop of a small entry usually leaves equal lengths but sometimes one class step. Tree, top and journal rows get Padmé without the floor: they hold keys and row names, so their length counts entries, which the row names show anyway. Row names (`u slot ver`, `n level index ver`) stay plaintext: they show which slot each version belongs to, the global order of versions (`ver` is the transaction number) and how many versions of a slot linger in freed pages, i.e. the write pattern, never content or lengths beyond the class. Accepted; what would close it: name each row by a hash of its own key (every version has a fresh key, the parent holds it, so lookups stay direct while names stop linking versions).
- **Shred semantics**: `Shred::Yes` on a write or removal makes the previous bytes unrecoverable at commit (path rotation, one root write per transaction). `Shred::No` rewrites may stay recoverable from freed storage under the still-live parent key until a later shred on the same path. Every `drop_*` shreds. A value above `page_max/4` keeps its unit across rewrites of its key and goes shredded when it turns small, so a later shred of the key reaches every earlier version (a fresh unit per rewrite would leave old versions out of its reach). Engine records holding a copy of content kept elsewhere (a pending commit once applied) are removed shredded. A table page whose entries move to another slot (split, merge, root move or collapse) is always written or deleted shredded, so a later shred of a moved entry reaches every old copy (about one extra root write per transaction that splits).
- **Versions and rollback**: transaction versions never repeat within a session; `begin` rolls back the spills of aborted transactions; journals list a blob as new only if it was absent, so rollback never deletes a committed blob. `Store::create` writes the catalog in its first batch and stores the root last (a crash leaves no root: create again). `RootStorage::repair` runs on open (`FileRoot`: a crash between the slot writes leaves the old key in one slot; repair overwrites it).
- **Failed writes** (principle: a commit reported landed is durable; one not known durable is `Err`). A failed write either had no effect, or reads as written with its sync failed (`Unsynced`): a failed fsync leaves the bytes in the page cache, so anything reading the file in this boot (in-place recovery, a fresh open) sees them, while a power cut may drop them, and Linux drops the failed pages from write-back, so a later successful sync does not save them, nor anything a CoW engine like redb builds on them. Hence:
  - Backend: on `Err` other than `Unsynced`, what it reads is durable. A failed commit recovers the store as `open` would (finish or roll back from the journal) and reads its outcome there, so `commit`'s result is the outcome (a shredding commit failing after its root record was stored landed: `Ok`); `Err` leaves the store at its last durable state, memory overlay as before the transaction, and the next transaction works. A failed spill or rollback write fails its transaction (`Error::Broken` from then on) and the next `begin` recovers first.
  - A backend write that fails `Unsynced` (a commit, spill, rollback or recovery write) leaves the outcome unknown: `Err`, `Writes::unknown` counts it, and every call fails `Broken` until the store recovers in place; so does a recovery after a failed commit that fails (a crashed device). The store retries on its own (`Pager::begin`): the next transaction recovers in place, the same path as for any failed write (`recover`, which `open` runs), and while that fails the store answers `Broken` without touching the backend until the next attempt is due (waits of 1 s doubling to 60 s, `RETRY_FIRST`/`RETRY_MAX`). Nothing above the store reopens anything.
  - Why the recovery reads the disk: Linux keeps pages whose fsync failed in the page cache, marked clean, so a plain reopen would read them (the commit seems landed) and later redb commits would reference pages the disk never got: a power cut then loses them or leaves the file unreadable ("All roots are corrupted": the store tests' redb device shows it without the drop). Rewriting the landed state is no fix on redb for the same reason. So every redb open first fsyncs the file (dirty pages become clean, written or failed) and drops its clean cached pages (`posix_fadvise(DONTNEED)`, which drops only clean unmapped pages: checked with `fincore`, dirty pages survive it, all go after an fsync); redb does not mmap. The open then reads what the disk holds, and its own synced commit (redb's open writes one) makes that durable. Platforms: Linux and Android (same kernel call; rustix's raw syscalls). macOS and Windows: no drop is built (neither documents a call that evicts a file's clean cached pages; `F_NOCACHE` and unbuffered handles only change new I/O), so there an open after a failed sync fails and the store stays `Broken` until the process restarts, and that restart in the same boot reads the cache (the limit above). A process restart on Linux drops the cache too: one path.
  - What the owner sees: a commit answered `Err` may have landed (the disk held it after all, or a shredding commit's later batch failed after its root record was stored), so an owner holding state beside the store reads it whole again once it works: the engine compares `Writes::unknown` at each `run` and runs its open's load in place (`Engine::load`: settle blobs, reload, account, reexamine, timers) under a fresh session (that commit's counters may be taken), then sends `Event::Reloaded`, so `osis` subscriptions read everything again (notes/api.md Watching); node sync restarts from the stores once one takes a commit (notes/node-sync.md, Failed writes). While broken, app calls fail `Error::Storage` and node sync's failed steps report `DiagnosticKind::Storage`. Tests: store `a_commit_whose_sync_failed_is_never_reported_landed` (every durable write of plain and shredding commits, memory and redb, no reopen, then a power cut), `a_failed_redb_write_anywhere_in_a_commit_reports_its_outcome` (a fresh store per fault point: redb flushes a commit's pages, its header among them, in no fixed order, so a fault after the header write can land, redb's checksums deciding, and the next commit's write count differs), `a_spill_whose_sync_failed_recovers_in_place`, `a_lost_store_retries_after_a_wait`; node `crash::a_failed_sync_at_any_write_of_a_purging_commit_needs_no_restart`, osis `watch::a_commit_found_landed_after_a_failed_sync_reaches_watches`, `nodelog::a_failed_sync_taking_bytes_needs_no_restart`.
  - Root: the record is small and rewritable, so `RootStorage::repair` (run by every recovery, before `load`) writes again a record whose sync failed (`FileRoot`: slots that differ, or both after a slot's sync failed since its last repair, as a failed second slot leaves the old key on disk though both read the new; across a process restart only differing slots are seen, so that old key may stay until the next `store`; `MemoryRoot`: a record not on disk), so recovery reads a durable root and a shredding commit whose root store failed `Unsynced` lands `Ok`. Without it the recovery's finish would move `r` to a root epoch the disk lacks: unopenable after a power cut. Owners therefore treat a failed commit as an aborted transaction: the engine's journaled rollback is exact (engine `failing` and node `crash::a_failed_write_at_any_write_of_a_purging_commit_needs_no_restart` compare against a fresh open, `check_index`). `Store::writes` counts landed commits and failed writes so an owner holding state beside the store in memory knows to read it again (node sync: notes/node-sync.md, Failed writes).
  - Power-cut tests: cut straight after the faulted commit (a later commit rewriting the same page makes the lost write durable again), on a store of a few hundred rows (with one table page every commit rewrites every page, and a reopen without the cache drop still passes); check each fails with its fix disabled.
- **Savepoints** (`Transaction::savepoint`, `rollback_to`, `release`; nested, innermost first): the dirty set keeps an undo log of the first change of each unit and blob under each open savepoint (memory bounded by what the step touched, not by how often it rewrote a page), and the memory overlay rolls its journal back to the savepoint's length. Nothing spills while a savepoint is open (a spilled row is on the backend, out of a rollback's reach); the outermost release spills what waited, so a transaction may overshoot `spill_bytes` by one step's writes (in the engine at most one commit's apply). Commit and suspend refuse an open savepoint. Every backend alike: a savepoint never reaches the backend.
- **Tables** (`btree`): B+trees of units, pages split and merged by encoded size (`page_max`, default 8 KiB, fixed at creation), interior entries hold the child's first key exactly (so a shredded key leaves no separator copy) and its entry count (`table_rank`, `table_nth`); values above `page_max/4` in their own unit; keys at most `page_max/4`; root slot stable. Size-split B+tree instead of content-defined (prolly) pages: local pages need no history independence, and the B+tree is simpler with the same O(log n) pages per edit.
- **Store API**: `Store::{create, open, open_or_create, transaction(rng)}`; `Transaction::suspend` / `Store::resume` set a transaction aside between calls (the host store keeps one open across a hub batch; nothing else may begin meanwhile; memory rows refused); `Transaction` (drop aborts, `commit`): one catalog table keyed `kind || ...` (aspect `tid || u32 len || ak`): `AspectUnit {state}`, `drop_aspect` (unit and tables, shredded; counters stay), aspect tables `create_table(tid, ak, idx)` with `table_*`, rebuildable `index(name)` / `drop_indexes`, the node log (`log_*`, below), `reserve_counters` (commit before signing), pending/parked commits, `*_local` records, blob ciphertexts. Every list is paged by a limit; nothing materializes a whole table.
- **Ciphertext store** (`cipher.rs`, `Ciphertext`/`CipherTx`/`CipherHost`): the engine's blobs live in a store beside its own, a `Mutex` of a `CipherHost` (the node's: the hub's `HostStore`, notes/serving.md; `BlobArea`, blobs only, for an engine with no node), handed to `Engine::create`/`open`. An engine transaction locks it at its first blob use (`engine/blobs.rs` `Cipher`, `Tx::blobs`). Principle: add before, remove after. The engine `hold`s a blob (stored unless present) in the ciphertext store's transaction, committed before the engine's store; it `release`s one (its bytes go once nothing else keeps them) only after the engine's store committed (`Cipher::after`), so engine state never names a blob gone. `held` is the engine's hold (a release this transaction made counts), `read` any bytes present. A transaction holding or releasing a durable blob notes both under its sequence in the ciphertext store (`CipherTx::note`, local records `cipher/note/`) and records the sequence in its own commit (`records::BLOB_SEQ`); `Engine::settle_blobs` (at open, and before the next transaction after a failed commit or release) releases the holds of a noted transaction the engine's store never committed and finishes the releases of one it did, so a crash at any point leaves no blob nothing names and no name of a blob gone (`crash::crash_every_write_of_a_chunked_commit`, `crash_every_write_of_a_hold_and_release`). Removals of the ciphertext store's own rows its holder makes (`Cipher::defer`: node sync's entry rows and forgets in the hub's store) go with the releases, noted alike. A step rolled back (`Tx::step`) releases what it held and keeps none of its releases or removals, a release it took back by a hold included (`blobs::tests`); a dropped lock aborts the store's open writes; a failed write there (which drops the store's open writes, earlier holds too) fails the commit. Memory blobs live in the store's memory map, never on disk.
- **Stamps** (`Stamping`, `osis_base::memo`; notes/engine.md Derived values): the store stamps its rows for memos reading it: a catalog row by its key, a scan (`cat_scan`, `memory_local_keys`) by its prefix, a table's rows as the catalog row owning the table (`Table` carries its owner's stamp key: an aspect's unit, an index's name), a stamp table per family (catalog kind; a local record's first key byte). A transaction logs what it writes and stamps each again on undo (savepoint rollback, abort; a suspended transaction's log stays in the store until resumed, a new `transaction` treats it as aborted). Blobs are stamped by their holder (the engine's `blobs::Cipher`). `noted_aspect`/`noted_local` record a read answered from a copy the caller keeps; `row_changes` counts every row change.
- **Not here**: `PageSink`/`PageSource` adapters (wire pages are blobs under random keys with link hashes: label and node build them; the layer DAG keeps crdt out of store).
- Tests: crash tests and `failed_commit_recovers_in_place` run on memory and on redb with `FileRoot` (each slot write a fault point; on redb, test `FaultyRedb`, a planned fault fails the first write of the file inside redb, as a real I/O error does, or for `Unsynced` its sync, so positions count backend commits as on memory; the test file keeps the bytes last synced, a failed sync dropping the writes since, and `Device::power_cut` puts them back; `a_failed_redb_write_anywhere_in_a_commit_reports_its_outcome` fails each file write and sync of a commit in turn; `a_commit_whose_sync_failed_is_never_reported_landed` fails each durable write's sync on both backends, writes on with no reopen and cuts the power: every `Ok` commit survives and the store opens; the test device's open models the cache drop by putting the file back to its synced bytes), and at node level (`core/node/tests/it/crash.rs`: every write of a purging commit); the full forensic attack (notes/test-security.md, Forensic attack: rows, blobs, wraps) needs every row and blob ever written, so it runs on `MemoryBackend` only, over a 4-ary key tree so leaks are not rotated away by accident; on redb the test checks the file holds no plaintext. Bit flips in any row or the root: errors, never panics (`core/node/tests/it/corrupt.rs`).
- **Memory overlay** (`overlay.rs`): rows of the memory class (what ephemeral data derives) live in plain maps beside the encrypted store (catalog rows, table rows by table ID, blobs, the memory-class aspects), never reach the backend and are gone when the store is dropped (open starts empty). Routing inside a `Transaction`: memory mode (`set_memory`, a memory commit's application) sends every new row to memory; a row already in memory stays there; every aspect-keyed row (unit, deaths, tables, counters) of an aspect whose key is ephemeral (`+`) goes to memory, whatever the mode; `index(name)` tables are durable and hold memory rows per row. Reads merge both layers (memory first; scans, `table_range`, `len`/`rank`/`nth` over both); removals remove from both, except a blob delete, which writes nothing durable for a memory blob or in memory mode; a memory row over a durable one is a bug (debug assert). Changes apply in place with an undo journal replayed when the transaction is dropped uncommitted; a transaction writing only memory rows commits with no backend write. Not written in memory mode: the HLC record (the next durable commit persists the clock). Opaque local records a durable-mode transaction creates for memory data are routed by class in the engine (`Tx::in_class`, per commit or aspect).
- Cost: one edit of a 1M-key table rewrites at most 5 unit rows plus its key-tree path. A table page is decoded once per write of its unit: the decoded page sits beside the unit's plain bytes, in the committed unit cache (`unit_cache_bytes`, a unit with its page decoded counting three times its bytes) and in a transaction's dirty set (`Units::page`; a change takes the transaction's own copy, `take_page`, and `put_page` keeps what it wrote), so a lookup or a second edit decodes nothing it has seen (`paged::a_table_page_is_decoded_once_per_write`, `Store::pages_decoded`). A page written in a transaction stays decoded only (`DirtyUnit::Page`) and is encoded where its bytes are needed (a spill, the commit, a read of its bytes): a transaction putting many rows into one leaf encodes it once, not per put (about two thirds of page puts in the node tests rewrote a page already dirty). A page taken for change is out (`DirtyUnit::Taken`) until written back or deleted (it counts nothing toward `spill_bytes` and a spill passes over it); every table operation takes a page only once it will change it (a removal finds its key first), so only an operation failed part way leaves one, and reading it or committing then fails. Taking it under a savepoint records it in the undo log like any change (`unspilled_pages_roll_back_and_absent_removals_change_nothing`).

## Node log
`core/store/src/nodelog.rs` (`Transaction::log_added/log_deleted/log_head/log_read/log_cursor/log_position/log_sweep/log_forget`): the durable log of issues/net-reconnect.md, one per store, in catalog rows under `kind::LOG`: a meta row (cursor key, log ID, current incarnation, end), the ended incarnations (at most `INCARNATIONS_KEPT`), one row per event, a slot per entry or head with its latest event's position (an entry's also with the position it was first logged at, for an ended member's `until`), an ageing row per deletion. Whether this open of the store has drawn an incarnation is the pager's `Meta::log_drawn`, never encoded and carried in the transaction like the rest of the meta, so a restart, a restored store and a copy all draw at their first append (a recovery in place reads the meta afresh, an aborted transaction discards the mark) and a suspended transaction may append. Its rows hold positions and IDs only (harmless, as cursor logs above; a deleted blob's ciphertext stays in the blob area's freed storage under its ID anyway): an overwrite and a subject's event replaced by its later one shred nothing, so a deleted entry's earlier event may stay recoverable; a removal (sweep, `log_forget`) shreds. So logging an upload adds no shredding commit. `changed_at` is a sequence of its own (`core/store/src/changed.rs`, `changed_note` and friends: one slot and one order row per held sync ID, rows under `kind::CHANGED`), compared only with the records' `acked_pos` in the same store, so the log may live in another store. Per-peer records are `core/store/src/record.rs`, catalog rows under `kind::RECORD`, keyed by a random ID so no key holds r. The node's one log is the hub's store's (notes/serving.md, HostStore, Node sync's rows): node sync's entries are rows there, logged by the row's own writes in `State::flush` (`LogWrite`, `HostStore::reader_put`), its heads by the path it hands the store (`reader_steps`); the engine's store holds no log. Ephemeral entries are not in it.

An `Added` is logged when an entry becomes servable, not merely known: its row and its bytes both held, in the transaction that completes the pair (`State::flush_storing`, which stores inbound blobs). An entry without bytes has no row and no event; its bytes arriving (commit or chunk) is what logs it; compaction still leaves one event per entry. A row's removal logs its deletion; an entry added and removed within one flush logs nothing (no reader saw it).

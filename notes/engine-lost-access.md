# Engine: lost access and forgetting
> Summary: How a node drops what it lost read access to (spec/permissions.md §3, spec/requirements.md Deletion): when a thing counts as lost, nothing taken back (boxes and copies opened later), the derived drop and its pass gate, losses by an `until` alone, the pending-grant guard, what forgetting erases and keeps, sealed pending boxes, kept copies, self-removal drops and link races. Code: `rotation/lost.rs`, `retention/forget.rs`, the facade's `sync/held.rs`. Not here: why removal works this way (notes/revocation.md, notes/retained-copy.md), the cover check's own self-removals (notes/engine-roles.md).

## Principle
A node holds no secret of a thing it cannot read. Whether a thing is lost is a value of the held state (no list fed by arrivals), dropped only once sync has had its chance to bring the role back; the one place secrets are taken enforces the rule for whatever arrives later.

## When a thing is lost
A thing is lost when the node holds a secret of it (reading-only included; epochs observed without one are not access), neither the node thing nor a link key it keeps reading as has a role on it now (`lost::readable`: timeline, any path, `until` honoured), and no held unapplied role commit (pending, readable parked, late parts) boxes secrets to the node thing, a link key it holds or a thing the node reads now, on a thing whose role reaches it (itself, its record chain, or one with a role on it). A grant not yet applied, whose secrets may already be read (spec/crypto.md §4), is never a loss. Each thing is judged on its own, so what the node reached only through a lost one is lost with it.
- **Reading-only guard**: a thing whose secrets the node holds only from a commit not yet judged (`Waits::reading`) is kept while that commit's entries are; a checked-secret holder of a lost thing drops and re-learns when the grant applies.
- **Link race** (`contested`): where a held single-use redemption granting one of ours stands void only because an applied redemption by the same signer removed the signer's edge first, with no explicit write on that edge since, the loser keeps the secrets (and syncs the sync IDs) until the sharer's finalization arrives: it may drop the competing redemption and make ours stand (spec/permissions.md §3, §7). A plain leave followed by a void grant (a leaver's forgery) defers nothing.

## Nothing taken back (`rotation::may_take_role`)
The trigger drops what the node holds; the one place secrets are taken enforces it for what comes later, so no box's arrival needs judging again (re-judging after a join would loop: forget, refetch, rejoin).
- **Boxes**: `Core::ingest_view` (every applied `secrets.0` opening: received deltas, late or rejoined parts, `reopen_dependents` when a holder's secrets change, `reopen_all` at open) keeps a role's newly opened secrets only where `may_take_role` allows: every role's where `may_take` does (`may_hold`, reading the thing, or a `contested` link race reaching it), the sync secret alone where the node's roles give only sync (a box applied after the lowering to sync it survives gives what the lowering keeps: `rotation::tests::a_sync_holder_takes_the_sync_secret_in_any_order_spec_permissions_3`). A role kept out keeps the secrets it held, while what its epochs' history says is the state's as for any role (the read's epochs cleared, then opened from the secrets kept), as a rebuild reads it: a record started again from derived epochs (`refresh_independent`) carries their base's history until then (`rotation::tests_public::an_epochs_history_is_its_states_whatever_the_roles_spec_crypto_4`). It is listed by role wherever the state says otherwise at an epoch whose secret either view holds for use: a secret kept out, or a history the secrets kept do not open (`rotation::tests::a_role_kept_out_is_read_again_once_given_spec_permissions_3`); epochs only observed are no access and are not listed, and a secret a pending read gave for reading only counts as absent (it goes once that commit is judged, `rotation::tests::box_applied_before_its_grant_is_taken_after_a_pending_read_spec_permissions_3`) (`Waits::untaken`, in memory; the open's `reopen_all` lists it again, a rolled-back transaction restores what it took off), and `flows::retake` opens that thing's whole `secrets.0` again once `may_take_role` allows a listed role: run by `apply::rejudged` (every apply that changed held role commits); its work is one `may_take_role` per listed thing and role. Without it a box applied before the grant that makes it ours (another admin's rotation boxing the grantee; commits of different authors apply in any order) would stay unopened (over random arrival orders with the trigger run each step, a reader holding as in order and a removed node nothing: `rotation::tests::arrival_order_holds_alike_plain_spec_permissions_3`, a property). The list is only a hint: `retake` opens through `ingest_view`, which judges `may_take_role` again, so listing more costs a retry, never a secret. Pending boxes (`SecretsRead::Pending`, `read_pending_boxes`) are a grant still to be judged and stay reading-only as below.
- **Copies** (`Engine::copy_stale`, at `open_entry`): a per-sync-ID copy's section is under its blob key, so a reader of the sync ID opens it without the thing's secret. A copy left under a sync ID after its sync unit lost the thing would give the content back, so a copy carrying a content part (`core_types::is_content`) on a thing whose independent S's actor may not read now opens nothing (`Opened::NotOpen`): its parts come from a body under their own thing's sync ID. Such a copy is opened again only when S's read secrets move (issues/sync-unbuilt.md). Role-class parts never make a copy stale: each is judged as it is used (`secrets.0` boxes by `may_take`; the rest is certificate material), and refusing them would strand a slot whose copy carries it.
- **Content** (`retention::needed::whole`, read by `applies_on`, `uncarried`, `holding` and `apply::wake_entered`): content on a thing applies only where the node closure reads it (`Closure::reads`: the local part or a read sync unit, held or leaving; never kept unread) or it is a retained copy; else it waits (`Reason::Outside`) and counts never received at the pass's end. Keys still open such sections: a thing made independent after its minting keeps its earlier content under its mint admin's epochs, so after the admin's record edge goes the admin's readers (its own nodes included) and a holder keeping the thing unread can still decrypt the minting from any entry of it under the admin's sync ID (pulled, own log, a writer logging it again, a restart's pull anew). Only the closure decides, so a copy arriving before or after the loss ends alike. The closure follows roles: `Core::keys_open` lets T's read sync unit reach X only when T is X's independent or reads it now by role (a record edge is a grant); a thing above X's independent on its record chain opens nothing by that (spec/crypto.md §3: the derivation chain carries no authority). The wake follows `Closure::member_feed`, so a thing kept unread that comes to be read wakes what waits on it. Tests: `holding::a_mint_admins_readers_read_a_thing_*`, `holding::a_reader_down_a_chain_lowered_to_sync_*`, `holding::a_thing_read_through_one_unit_and_kept_unread_directly_*`, `holding::a_reader_lowered_to_sync_holds_no_content_across_a_restart_*`; a reader by standing record edges still reads: `holding::a_reader_reads_down_a_chain_of_standing_record_edges_*` (osis-sync).
- Rejected: stripping such parts at engine ingest by "no secret held and no path reads" (`LocalPeer` and the order property hand plaintext to nodes that cannot read, and arrival before the secrets made what a node holds depend on order); marking the forgotten part `Missing::Forgot` (a copy arriving joins such a part anyway).

## Owed role commits (`Engine::role_duty_due`)
What this node owes before it next encrypts under a thing (`ensure_rotated`: finalizes of grants past their `until`, required rotations, stale or keyless boxes, on the thing and the holders below it) is a value derived per held thing (`role_duty_due`: a read-only judgement, `owed_below`, of whether `rotate_below`'s walk meets a finalize or rotation due, with a memo clock read up to the next `until` on it; debug builds check it against `rotated_already`'s rolled-back run), not a list fed by arrivals: so an own commit (a removal whose rotation of holder M makes the boxes to M on what M holds stale), a received one, a keyset or record arriving, a restart and a clock wake all make it due alike. osis-sync's `Life` keeps one `Effects` key per held thing (`held_actors` at a start, `held_actors_feed` after) and runs `ensure_rotated` when it settles true, before the drop below; a start judges each held thing once (one read each, no transaction: `duties::role_duties_are_judged_once_per_held_actor_at_a_start_spec_permissions_3`). Duties are owed only on what the node closure holds, and the cascade enters only held actors (a node writes only what it holds): secrets kept of a thing not held (a loss not carried out, a holder seen only through certificates) owe nothing, and a holder actor not held never fails the cascade of the held thing above it (`NotHeld` rolled back the whole run before). Rejected: a list fed by arrivals (the targets a commit writes are not the things its rotations make due: a removal on D makes t due through M).

## The drop (`Engine::lost_due`, `lost_passed`, `drop_lost`)
A value of the state, not a list fed by events: `lost_due(a)` per held thing (a loss on record, `loss_seen`: an edge of the node thing, a link key it holds or a thing it reads ended or lowered (`Timeline::ended`, `lowered`: a lowering to sync leaves the edge alive) on a thing in `reaching(a)`, or reading-only secrets outliving their source commit, or a role its role commits show the node on `a` (`role_here`: they show what it may hold); lost by `judge`: no role by any path, no pending grant or link race keeping it; no own self-removal behind it still waiting, `held_wait`; not by an `until` alone), read without a transaction, with the memo clock read up to the next `until` on each thing whose roles reach `a` (`reaching`: `a`, its record chain, the holders of edges on them, transitively), so a role commit, a box, an account left or an `until` passing all make it due alike. Where its stamps would not move by themselves (the reading-only secrets a bad pending commit gave, `apply::keys::forget_unchecked`; an account this node left, `flows::signing::leave`), `touch_held` re-inserts the thing's secrets entry.
- **Pass gate** (spec/permissions.md §3 Lost access, When it learns it): osis-sync's `Life` drops `a` (`drop_lost`: `LostScope::Only`, judged again in its transaction) only once `lost_passed(a)` also holds: a complete pass of each sync ID of `a` read here began after the place `a`'s loss was first judged (`Cause::Lost(a)`, noted by `lost_passed` when `Life` asks with `lost_due` holding, forgotten by `lost_due` once it does not): role commits arriving after it never move the bar. Until then the node keeps the secrets, syncs the sync IDs (the sync set still holds them while `a` is reached, its secrets being held) and opens and proves by them; what the pass brings may give the role back. `passes_wanted` wants a pass of each read S after that place, so status runs it. The sync IDs counted are those this node syncs (`read_ids`: `a` in `sync_things` or left the node closure and not released yet, then `thing_sync`): a thing that left waits as its release does (its sync IDs stop by that timing, spec/sync-set.md §3 Stopping, so its own writes there are served first: `holding::an_own_write_before_a_dropped_strong_reaches_its_peer_*`); once released or sourced away no pass of it comes, so with no sync ID of `a` read it drops at once.
- `copies_due` (a stamped read of whether the kept copies' marks, judged now by `keeps`, differ from those kept) is one more `Life` key: `rejudge_copies` (`LostScope::Copies`). Every drop re-judges every mark anyway.
- An app driving the engine alone has no passes: `role_duties()` drops every held thing `lost_due` says (`LostScope::Due`, timed losses getting their `T/` record there) and re-judges the copies; `role_duties_due()` is O(held things). `drop_lost_secrets` (`LostScope::All`) drops every lost thing, guards apart from the pending grant's.
- Rejected: a work list fed by received role commits (`l/`): every source of a loss needed its own feeding (own commits, untils, bad pending commits, accounts left), and the pass gate would have needed a re-list on every pass noted.

## Lost by time alone
`lost_by_time`: walked with every edge's time ahead and every finalize undone, a role giving what the node holds is there (read for read secrets, so a lowering to sync with times ahead is no loss by time; sync for a sync-only holder) (a removal saying retain is written with `until` 0, gone at every clock, so it never counts). Such a thing gets a `T/` record when first judged and is listed in `Leaving::timed`: it drops once each sync ID of it read here is heard out (`Engine::lost_timed`: a complete pass begun after the record ended), or `LOST_HEARD_WAIT_MS` (`ROLE_KEEP_MS`) after the record's time. So a renewal on its way and unsent writes from before the `until` come first, and no node keeping S unread holds an erasure off for good. The record goes with the drop or when the thing reads again (`prune_timed`). A role commit received beside the expired grant changes nothing. osis-sync's `Life` drops it through `lost_timed` (each sync ID of it read, `read_ids`, with whether a pass after the loss ended; the wait's end): the loss's `Cause::Lost` place is kept while it is timed (`lost_due` forgets it only when neither due nor timed), so the pass `pass_wanted` asks for is after it.
- A reader that may write the sync ID's thing finalizes the ended grant once past the `until` (`ensure_rotated`); the finalize's rotation moves S's head past the node's sync key, so its open there is served only up to that step's end (spec/sync-opens.md §6), at every node that applied the finalize, and the node's unsent writes are lost there.
- Rejected as the test: a refusal from a peer the node dials for the sync ID (the dial list comes from self-declared `dial.0` entries: any reader of a shared thing could claim a reader's account and make it drop).

## Forgetting (`retention/forget.rs`)
- The drop removes the lost things' `k/` and, in the same transaction, forgets every thing whose independent is one of them and that neither the node thing nor a link key it holds may read now (`Core::may_read`: a thing up the record chain of an independent thing reads it only by its role there, so a lowered or removed record edge takes it). Of such a thing only `created.0`, `retention^.0` and the role-class aspects other than `secrets.0` stay (`forget::KEPT`: certificate material perm judges others' writes by: grants, public keysets, `sync.0`).
- Shredded: aspect units (`drop_aspect`: state, tables); its parts in `c/` records (a commit left with no part is deleted, so a re-grant fetches it again; others keep their readable parts, not marked dropped, so the forgotten ones join late if they return: their secrets and, from a copy, their content only once the node reads them again, Nothing taken back above); pending parts; `a/` `v/` `p/` `s/` `w/`; timers of forgotten parts; the rows of the forgotten things' sync IDs but those a kept thing owns; the ciphertexts nothing kept names (the store per sync ID drops its entries as their bodies leave `sync_bodies`). The thing's freed set goes (a removed party cannot delete), and the pieces the forgotten parts link go by `retention::freed::lost`: walked through held node blobs, released where no remaining source of the thing reaches them (its role-class states stay and may link pages) and the held prefix bears the link (a link copied from another thing releases nothing). Test: `freed::tests::a_link_copied_from_another_thing_frees_nothing_spec_crypto_7`.
- **Sealed pending boxes** (`rotation::boxes_kept`, `b/`): forgetting keeps the `secrets.0` parts of an unapplied commit signed by an author who may grant on the thing now, whatever its age, that box the node a read epoch newer than every checked one it held (a grant from after a rotation that left the node out), so a re-grant applied after the loss brings its boxes. Marked `b/`, they give `read_pending_boxes` no candidates until the commit applies (else they would keep the lost secrets for good). A box only at a held epoch is a grant from before the removal, which gives no role, so it goes (a re-grant after a self-removal with no rotation between boxes a held epoch too and loses its boxes: stranded until a re-seal). Costs: such a grant that never applies keeps its sealed box; a grant whose path's evidence is not held yet cannot be checked and loses its boxes, recovered by a stranded report and a re-seal.
- Incremental, no reload (`forget::forget`, shared with release, `Engine::released`): the things come from `forget::under` (down the record chains from each lost thing, `Held::mint_admin_of`), their aspects from `by_aspect` and their `ASPECTS` rows, the commits from `by_aspect` of the forgotten aspects. A commit left with no part is unindexed as never received (`apply::unindex_unreceived`: no forgotten mark, kept covers or names); another's forgotten held parts go missing in place (`forget::unreceive`: hold, rotation judgments, snapshots, leftovers, addenda; a role commit's `secrets.0` bodies drop their `boxes_to` once per aspect); each forgotten aspect is rebuilt (to nothing: what its state gave goes, strongs included) before its rows drop. The indexes stay current and persisted (`check_index` agrees: `scale::losing_access_costs_what_was_lost`, `forget: commits scanned` and its store rows read flat at n and 10n rows of each kind elsewhere). Pending rows lose their forgotten parts in place and are not examined again: a commit waits only on header-level things (records, epoch, drift, blobs), which removing parts frees none of. A drop then a re-grant brings every value back, the engine reading after the drop as an open of its store does (`flows::a_regrant_brings_back_what_a_drop_forgot_spec_perm_3`). Still whole scans: pending rows, timers (`x/` keyed by time), `z/` named-permanent rows, freed rows (`fl/` keyed by blob). Sync follows the facade values that moved. Event `Changed { cause: LostAccess }`, a `Removed` diagnostic per thing.
- A re-granted holder regains content by sync only: its own writes that reached no other node before it forgot are gone.

## Kept copies (`K/`; spec/permissions.md §3 Retain)
- `keeps` is a least fixpoint over ended grants saying retain (`Timeline::ended`, `Edge::ends_retaining`; an `until` ending by the grant's own `retain`, which its writer filled), live ways from a kept holder and the held marks, every way only by a grant with key access (a keyless one reads nothing through it, so keeps nothing: `holding::a_keyless_grant_keeps_no_copy_*`, `holding::an_ended_keyless_grant_keeps_no_copy_*`; a keyed way turns keyless only by a write ordered before it, a concurrent or backdated grant closing a key cycle first, which every node judges alike once held: `holding::an_ended_way_found_keyless_drops_its_copy_*`; a keyless way is a `Way` saying erase, so a recorded holder leaves on it). Key access is the grant's as it last stood for keys: live, or ended by an `until` alone (still standing for keys), the `Timelines::keyless` set; ended by a removal, `members::keyed_before` (the same rule over the writes before that removal: it stood then and was not keyless). Who steers it: the removal's point is its writer's, permission-checked there, and the writes before it are applied ones, so a backdated removal reads only a state an honest write there would have; a backdated removal of a competing grant changes live key access just the same: a copy hangs on holder H while the node still has H (also while H's loss waits, `not_dropped`: secrets above sync held and H not in this judging; every drop re-judges every mark, so the copy follows H's fate) and the way through H keeps; a holder already recorded goes only on the timeline's word. Holders cannot keep each other. Re-judged when a due target touches a mark.
- A kept copy goes through `forget` with `Fate::Kept`: only `secrets.0` and pending content are taken; `apply::ingest_class` strips later content parts on it (`without_frozen`, `forget::frozen`), a commit left with none being dropped unrecorded so a re-grant fetches it, and a commit's purge list still applies if another part holds the commit.
- No secret, no sync, no write; reads still read what it held. The user drops one with `LostScope::Kept` (`Engine::kept_copies`). A client's thing reads a kept copy only as a holder the copy hangs on or an app of its account (`copy_readable_by`, notes/client-port.md §3).

## Self-removal drops (the facade's `sync/held.rs`)
- One rule at every node of the account: applying a role commit (local or received, late `roles.0` parts too) that is an own self-removal (`rotation::own_self_removal`: the newest applied write that changed the holder's edge for keys, lowering it, a self-removal by its author, made here or authored by this node, its account or a link key it holds; a sibling's concurrent removal of the same edge changes nothing and leaves the first one behind the departure) puts it in `held_wait` (`hw/`, durable; `Engine::waiting_removals`) in the apply's transaction. So the node that wrote it and every sibling that applies it wait alike (spec/permissions.md §3 Lost access: whichever node of the account minted it).
- `own_commits` adds each waiting removal with a body under S, so status judges a sibling's copy held elsewhere as the writer's. Status calls `Engine::removal_done` once, under each read sync ID it has a body under, it is held elsewhere or no peer but the account's own nodes shares that sync ID (notes/sync-status.md Self-removals). The trigger skips a lost thing while an own self-removal behind it (`own_leaving`) waits.
- Only lost things drop (`removal_done` judges again): a wait set by a link key shared with another party, or any wrong `removal_done`, delays or ends a wait but never drops what the node still reads.
- `removal_done(c)` drops, per thing (`lost_leaving`, `LostScope::Only`), each lost thing with no other own self-removal behind it still waiting: one that cannot be logged holds back nothing else. The drop goes before `c` leaves the set, so a crash between finds it waiting and status tells it done again. No timeout: a peer that never takes it keeps it waiting while connected or recorded (the record budget bounds an away one).
- While it waits, leave keeps each sync ID it has a body under synced, source or none (`Engine::removal_waits_under`, notes/sync-leave.md), so the removal is still there to take.
- An own node is never the peer it waits for: it leaves by the same commit and passes nothing on, so with no outside peer they all drop at once.
- Rejected: a refusal or a rotation leaving the leaver out as the signal (any rotation the leaver is not in gives it, a hostile peer for free); a rotation naming its departures (a wire change leaking other departures' names and the fresh deposit seed); a bounded leaving period or a give-up call (a picked number, a user decision on every leave: the wait already ends once no outside peer shares where the removal goes); dropping in the removal's own transaction (it must still seal the removal under the sync IDs it leaves); setting the wait in the writing flow alone (a sibling that pulled the removal would drop before a source has it); an ungated trigger (it drops a leaver that applied any received role change on the thing before its removal went out).

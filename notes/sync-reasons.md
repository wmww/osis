# Sync: design reasons
> Summary: Why spec/sync*.md is shaped as it is at its core: one kind of node (Tess), one blob per commit, sync IDs per thing and their role keys, entitlement, sections, certificate blobs, self-certifying sync IDs, the blob prefix, stamps and first-stamped-wins, delete keys and their levels, retention on the wire; rejected designs at that level, policy defaults, open items. Not here: sync-key gating, claims and re-seal (notes/sync-access.md), deletion and convergence (notes/sync-convergence.md), inbox and deposits (notes/inbox.md), what a node keeping S unread learns (notes/unreadable-data.md), the code (notes/sync.md and the module notes it lists).

The requirements behind sync: spec/requirements.md, Data a node cannot read and Deletion. The rules: spec/sync.md and the files it maps. Byte layouts: spec/wire.md.

## Nodes (Tess)
- **One kind of node**: same binary, run the same way, on a laptop or a rented machine, with any mix of data it reads and data it keeps unread. Reading is per sync ID (a read secret held or not, spec/sync.md §3), so a machine that reads its own configuration group and keeps everything else unread is one osis instance.
- **No separate program**: keeping data for others is part of the node, started by the one long-running command (`osis serve`), configured by osis data on the node's own thing (`caps^.0`, spec/data-model.md §9) and the account's synced groups (`synced^.0`), so any node of the account configures it remotely; it is never in the node card.
- **The store of ciphertext is a shredding `Store`**: a node keeping S unread may read other sync IDs on the same machine, so wraps and blobs surviving a delete in freed pages would break spec/requirements.md Deletion (notes/local-store.md).
- **No connection count limit** (Tess; spec/sync-transport.md §5 Served connections): a count picked from memory per connection would mislead (that memory is not a fixed amount in practice) and refuse devices past it on large rosters. Later work: a node that detects low memory sheds load (closing connections, evicting caches).
- **A child step past the caps** is still taken, at most once per sync ID per interval (spec/sync-ids.md §6 Storage caps): a refused rotation would leave a removed holder's sync and write keys valid at that node, and anyone may fill a node to its total cap; only the sync ID's own admin signs a step, so outsiders cannot starve an honest rotation, and growth past the caps is at most one bare step (about 320 B) per sync ID per interval. Rejected: forgetting old steps instead (a path walk from genesis is how a node verifies a head it has not recorded).

## Blobs, sync IDs, entitlement
- **One commit ID, one blob per commit, a random key per blob.** A commit has one ID whatever sync IDs carry it, so sharing history adds wraps and never re-encrypts.
- **No commit size limit; only the header's lists are bounded** (`MAX_LIST_BYTES`). A delta pages like a snapshot and the lists go by link, so atomicity never depends on size and the API never splits a write. The costs (a reader stores pages it cannot apply yet, a writer that dies mid-write leaves orphan pages for convergence to delete, apply streams pages through one staged transaction) are those snapshots carry anyway. A one-blob size limit would only add a second, non-atomic kind of edit every app must reason about.
- **The sync unit is a thing with secrets of its own** (a group, in practice), never a record chain: groups are free and overlap; record chains as the unit would force a copy for every separately syncable subset.
- **Role keys derive from the thing's own role secrets**, never its first admin's: each thing's sync ID gets its own keys, which only its holders derive. Not for unlinkable wraps: account proofs and shared commit blobs already show a node keeping several sync IDs unread which ones overlap. The deposit key derives from the actor's deposit seed (a devices actor's from its account's), keyed by sync ID, so sync IDs sharing a seed never share a deposit key.
- **Entitlement, not membership, decides what goes under S** (spec/sync-judgement.md §1): a thing dropped into a shared folder without a grant is silently not shared, the intended failure; an "add to shared folder" helper writes both. Worth caching per (thing, sync ID), invalidated by role changes of S's actor, the thing's grants or its record chain.
- **Sections** (notes/whole-commits.md): one section per thing, under the thing's read secret (its own or derived by tid), so a thing given secrets of its own later still opens its earlier sections through its history boxes. A section lists its thing's record chain in the clear so a reader derives the key before it holds the thing's record. Copies (certificate copies and per-sync-ID copies) are one section under the blob key: whoever opens a wrap of the blob is meant to read it, so the wrap is the only gate. A part the writer holds no secret for (a key actor's own record or card) stays out of the shared blob and travels as a certificate copy.
- **Mixed retention in one commit** (a "last modified, purge on replace" beside a "body, forever") costs a rewrite when the register is replaced: accepted (notes/whole-commits.md, Decisions). The prefix carries one commitment group per distinct delete-key set among the sections' aspects; a Delete needs every group signed.
- **A certificate copy is one blob across sync IDs**: a node logging the same parts of a commit under several sync IDs seals once and wraps per sync ID, so an account in k groups seals and stores its chain once, not k times. What that shows a node keeping them unread (account X acts in both) its account proofs (spec/sync-opens.md §2) and shared commit blobs already show. Parts that differ per sync ID, per-sync-ID copies, list and record blobs stay per sync ID. Certificates lie outside the closure, so the required set is closure plus certificates (spec/sync-judgement.md §2); else a group admin's convergence pass would delete them and the node would log them again forever.
- **Self-certifying sync IDs** (derived from the genesis step's delete key): a random ID would let anyone who learned it (an ex-reader, a leaked `sync.0`) squat it at a node that keeps it unread under their own keys. Two admins creating a sync ID concurrently derive the same ID.
- **Blob prefix**: expiry and delete-key commitments are fixed by the blob ID, so no relayer can spoil them. Expiry is immutable: extending it would keep ciphertext meant to be gone for anyone who later obtains keys; content that must outlive it is re-encrypted. Commitments are the delete keys blinded by each blob's salt, not the keys, so no commitment is common to two blobs: a node keeping S unread sees no key shared by one author's or actor's blobs, and a delete signature reveals nothing beyond the blinded key.
- **Retention always on the wire**: a node without the schema (generic tools, agents) could otherwise neither honour a MUST drop nor judge a purge request. A few bytes per delta.

## Stamps and deposits
- **Stamps** (reading must not give writing): the author's signature sits inside the ciphertext, so S's write key is the only writer proof a node keeping S unread can check. Signing (sync ID, blob ID, wrap) and storing the signature beside the wrap lets any node relay a writer-vouched entry (LAN, node to node, bundles) while readers originate nothing; covering the wrap means a relaying reader can spoil nothing. A stamp is checked against the head's write key when taken, so a removed writer's new stamps are refused once the step its removal requires is registered.
- **Deposits** carry what a non-writer legitimately needs under S: an unstamped entry within a per-sync-ID budget, readable at once by co-readers, promoted when a writer stamps it, which frees the budget (notes/inbox.md). Rejected: per-holder deposit keys (linkable).
- **A stamped entry never changes while it lives** (spec/sync-ids.md §6). Every writer shares one write key and a node keeping S unread cannot read a wrap, so it can tell nothing about a second stamped copy: last-wrap-wins let one member hide any message from every node not holding its key (reproduced). No honest node re-wraps a held stamped entry, so first-stamped-wins costs nothing and needs no replacement rate limit: one wrap per entry, no number to pick. A stamped entry over a deposit still replaces it, or any reader could keep a writer's wrap out.
  - Residual race: only the first stamped copy at a node can put a useless wrap there, so the attacker must hold the blob from elsewhere or promote a deposit first. It loses at a reader to any other source's wrap, and the entry counts as lacking at that source, which gets a fresh encryption (spec/sync-ids.md §6 Wraps): a new blob ID, first there by construction, so the race cannot repeat there.
  - An honest wrap under an epoch the node lacks (two writers logging one blob across a rotation) looks like garbage when heard; every holder of the new epoch holds the older by history boxes. No hold-off: garbage and an unknown epoch look the same, and a time limit would be a guess.
  - Rejected: several wraps per entry (writers share a key, so any bound fills with the attacker's garbage); key-check values or commitments in the blob (a blob is shared across sync IDs and epochs, and the node keeping it unread still cannot check); holders logging the same blob again (with replacement it never settles and leaves a window, without it it is a no-op); asking co-readers (needs reach the reader may not have); an answer saying "another wrap is held" (a subscribed sender hears the add before its answer, and a bare code cannot tell a useless wrap from another epoch's).

## Delete keys
- **A delete-key signature plus a role key** (spec/sync-ids.md §6 Delete): the delete key proves the purge right as of the delta, the role key current roles. Not redundant: everyone who ever held an epoch's secret (removed holders included) can sign with its delete key. Level 3 needs the write key, so a writer demoted to reader loses its delete power over `writer` bodies at the step its demotion requires anyway. Levels 1 and 2 need only the sync key, because a thing's admin or author is often a mere reader of S (anyone sharing a thing into a group they only read). The item names its levels, so the node checks one commitment per group and knows which role signature it needs. Honest nodes enforce current write permission for every purge (spec/permissions.md §6); a node keeping S unread only this approximation (spec/requirements.md, Data a node cannot read).
- **Delete keys follow retention**, one per level (spec/crypto.md §7). Without the admin level a thing admin who is not an admin of S's thing could not delete at nodes keeping S unread; a writer without the admin secret lists the thing's published admin key (`keys.0`), so every delta carries every level its retention calls for (Tess: signatures over hashed tokens). A Delete needs every commitment group signed, so a `nobody` delta is never deletable through a commit-mate's key. Under the shared-actor pattern `author` collapses to `writer`.
- Known gap: receivers check only how many keys a header lists per level and that one level-2 key serves the whole commit, never which keys. A vandal writer can list its own key at level 1 or 3 and so delete its own blob where an admin's key was due: no worse than hashed tokens, and S's delete key still removes the blob.
- **Chunk commitments** derive from the creating delta's keys, the chunk's own salt and its link blind bound to its thing (notes/crypto.md Delete keys); the link carries the salt and those keys, and deleting goes by link (spec/sync-compaction.md §1 freed links). Reuse re-encrypts by spec/sync-ids.md §1 because otherwise a writer could delete chunks of an `author` value, or an author be unable to delete its own; author-chain commitments need not match beside an admin or writer key, so dedup across editors survives (under `author` alone they must, or another author could delete it). Residue: an author's explicit purge cannot delete chunks it reused from another author's version; an admin can, and honest nodes drop the keys anyway.
- Rule of thumb: per-entry rights are delete keys whose secrets travel client-side (role secrets) and whose public halves the header lists; sync-ID-wide rights are role keys; revocation rides on role keys. Nothing a node keeping S unread stores states a reason.

## Rejected
- Record chains as the sync unit (above).
- State Merkle trees over aspects or the group hierarchy: they expose shape and must follow a cyclic hierarchy.
- Home closure = everything below the actor by record chain (a complete backup by default): every thing would sit under its first admin's home sync ID beside any shared one. Tess chose explicit membership (spec/requirements.md, Offline and network; spec/sync-ids.md §2).
- Unverifiable per-entry expiry and commitment metadata (first or latest copy wins): the prefix fixes them by blob ID instead.
- Elsewhere: rejected deletion designs in notes/sync-convergence.md, rejected access designs in notes/sync-access.md, plain grants under a shared sync ID in notes/inbox.md.

## Policy defaults (non-normative, tune freely)
- Compaction: every writer runs the trigger each step (notes/engine-retention-trigger.md); a thing whose admins want its current parts kept says so in its setting (spec/commits.md §5 Kept while live).
- Deposit budget and order: notes/inbox.md. Recommended constants (`TOMBSTONE_LIFETIME`, the deposit budget, `PASS_WAIT_MS`): spec/wire.md §2.
- Diagnostics: a clock offset of more than a few seconds against a peer (`ClockSkew`, the only use of the estimate: nothing a peer sends moves a node's clock); ephemeral data not synced or not applied for a cap.

## Open
- Partial restore: a group's `sync.0` and `created.0` writes go under the home sync ID of the nearest actor with one up its record chain (spec/sync-ids.md §2), so a subgroup's content is restorable alone only when it has its own sync ID.
- **Abuse limits** (deferred until a real problem, Tess): stamps (only writers add content), a deposit budget, caps and rate limits per sync ID bound a stranger, but any writer can fill a sync ID's cap with junk a node keeping it unread cannot tell from data. Per-holder limits would need pseudonymous holder keys (linkable, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one node bound to (node, sync ID), never into the relayed `sync.0` path. Relaying: issues/p2p-own.md.

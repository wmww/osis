# Purge rules in the path model
> Summary: What the purge rules must give (from spec/requirements.md and today's spec), the rule as modelled in roles-model `paths` (classes, selectors, copies, destruction, own cover) and in purge worlds (`-- N paths-purge`), today's rule and why it is order-independent, the three readings of a purge whose right is cut later, results per rule set, the witness finding (41), delete keys (argued), the indistinguishable-pair question, and the questions for Tess. Draft text: notes/a1-spec/permissions.md §6, §5.2.

## Principle
A purge request is an edit (a content-class part on `purge.0`): it holds a right over a delta it names exactly where a delta of it needing the role of a member of that delta's retention set, along its own stated path, at its key, would be valid (§5.2). It stands and falls as an edit does: cut, listed, vouched, re-granted. Nothing is special to purges but bodies: dropping a body is an act at a node, and a reading that stops dropping it brings it back only from a node still holding one.

## Properties
Each is a gate of the purge worlds (`check`, roles-model `src/paths/purge.rs`) or of the story (`purge`), computed from the generated history.
1. **Who may erase what** (spec/requirements.md Deletion; spec/commits.md §5 Who and how long, Destruction): `admin` (every set): a request along a path giving admin; `writer`: along a path giving write, over deltas whose set is `writer`; `author`: along a path giving write whose chain (signer and listed things) holds the delta's purge author. Each named delta is judged alone. A destruction: the `admin` right alone, over every delta of the thing whatever its `ts`. Gates `purge kept` (every delta a standing request holds a right over is purged) and `purge safety` (nothing else).
2. **A removed party's requests**: a request made after its signer's removal (backdated or not), or by a key that never held the right, takes nothing at a node holding the removal, but by a path its signer keeps (`purge safety`; `a_removed_signers_backdated_request_or_destruction_takes_nothing`). Except a destruction by a key holding admin on the thing by a direct edge: its right reads no cut into the thing ordered after it, so a backdated one stands (issues/destruction-by-removed-direct-admin.md; the generator's thief holds admin only through A or A2).
3. **Honest requests kept**: one by a party still holding its right stands; one a removed party made before its removal stands where the remover listed it (`purge kept`), or where a remaining holder of the class's role received it by the removal's `ts` (`purge witnessed`: spec/requirements.md Permissions, "those of its edits the remover or another remaining writer vouches for having received by then are kept").
4. **One reading**: what is purged is a function of the held commits and the trust set (spec/commits.md §4 Order independence; spec/permissions.md §6 Judgment "in any arrival order"): `alike` (two nodes holding the same requests read every delta both hold, or show by a copy, alike), story `alike` and `one reading`.
5. **Copies**: a request reaches a named write a node shows only by a valid cover's copy (spec/commits.md §5 Purge, Without the header): `purge kept` at LJ (it holds T1 from tick 8 only) and `alike`.
6. **Gone while it counts**: purged content never returns while the purge counts; a purge whose right is cut later brings it back only where a body remains (spec/requirements.md Deletion: "a reader holding the data restores what was wrongly dropped", "It comes back only if the purge turns out invalid", "Purge is prompt ... no bin"). Counted (`bodies`): a write that shows at the end after nodes erased it on the way, restored from a node that never erased it, or lost.
7. **Stores that cannot judge** act on a request that could hold the right (spec/requirements.md Deletion; draft spec/commits.md §4 Could hold the right): `could hold` (every purged delta is named by a request whose path could give the right by the held edge writes, whatever their validity).
8. **Own cover**: a writer's own cover stands while the removal naming it applies, whatever cuts its writer's path later (draft §5.2): `own cover` (X's writes H forgot under it show at H exactly while H's removal of X applies).

## Today's rule, and order independence
spec/permissions.md §6, Judgment: "follows the role timeline the node holds, in any arrival order: A named delta a request comes to drop is dropped then. A delta held as its leftover for a request when no held request drops it any more counts as never received ...: its leftover is set aside and it is no longer held value-less, the node fetches it again where present ... A body no node holds stays gone." §5.1 Frontier, Purge requests: a removal lists "every commit whose purge request's right may rest on X's standing there". §6: "A role counts toward the right exactly when a delta of its holder needing that role at the request's key would be valid (§5.2): a demotion whose frontier does not list the request takes the right however early its `ts`". So the reading is order-independent (a function of the held set and trust set); bodies are not, and the spec says so: a node that applied a request before its right was cut erased the body and fetches it back where some node kept one.

A request is never an edge-class part: no lowering puts it in D. "Dropped" means its right is cut, as an edit's validity is: a cut of its path not listing it, judged in the timeline whatever arrived first. The draft's frontier lists commits resting on the lowered edge, a request among them, so today's separate Purge requests clause goes (notes/a1-spec/README.md, What A1 removes).

The three readings of a request whose right a later cut takes:
- **(a) Restore** (the rule, today's spec): the reading drops the purge; a body comes back from any node that never erased it. Order-independent. Lost for good where every holder erased it first: the thief's requests between theft and removal (the window), or an honest request that every holder applied before it fell. Counted in `bodies`.
- **(b) Erased stays erased where applied**: a node's reading would depend on when it judged: of two nodes holding the same commits, the one that applied the request before the cut reads the content gone and the other shows it, for good. Forbidden (order independence). Every `restored from a body` world is one where (b) diverges.
- **(c) Never cut** (`-purge-at-key`: the right read at the request's key alone, "gone means gone"): a stolen key's backdated request stamped before the removal holds for good. Fails `purge safety`. Rejected: against a stolen key, "gone means gone" and "a removed key erases nothing" cannot both hold; the requirements choose the second (Deletion: "A purge counts only if its author had the right to make it, judged as an edit's validity is").

## The rule as modelled
roles-model `paths` (`purges`, `holds`, `Names`, `Retention`; README.md, Paths, Purges): rule switches `purge_classes`, `purge_copies`, `own_cover` (the draft's readings, *taken*; `Rules::purging`), `purge_addenda` (OPEN-proposed, finding 41), `purge_at_key` (variant (c)). All off in `Rules::fixed`. The unwired walk (osis-perm `paths`, notes/perm-paths.md, Purges) builds `Rules::purging` and is compared under it (every differential, the purge worlds at every node). A destruction's right reads no cut on an edge into its own thing ordered after it (spec/commits.md §5 Destruction); the walk does not refuse edge writes on a destroyed thing (content on it reads purged). An own cover stands by an applied explicit lowering of its writer listing it whatever that lowering takes at the reading node, its path having given write just before it.

## Finding 41: a request only a witness received falls
X purges by whole aspect at 4; B, an admin, receives it; H, which did not, removes X at 6 listing nothing; B's addendum at 7 names it. The draft (and today's spec/permissions.md §6: "An addendum vouches for no purge request") drops it: the request falls everywhere and X's erased messages come back from any node that kept them. spec/requirements.md Permissions keeps "those of its edits the remover or another remaining writer vouches for having received by then". Fix modelled (`purge_addenda`): an addendum vouches for a request as for content, by a writer holding the role the class needs (admin for `admin`, write for `writer` and `author`), against a cut ordered after it. With it every gate holds, and no honest purge is lost by falling. The exclusion was a carve-out with no stated reason: a request is content-class, and the witness's word is weighed as for any edit (Indistinguishable pairs, below). `repro_a_request_only_a_witness_received_stands`, `an_addendum_by_a_holder_of_the_class_keeps_a_request`.

## Indistinguishable pairs
The role-write pair (issues/role-vouch-contested.md, Why no vouch can work: two worlds with the same held commits needing opposite answers) arises where a witness's word is weighed by a standing the thief can contest. For purges:
- Honest X purging at 4, witnessed, removed at 6; and a thief with X's key making the same request between theft and removal, witnessed: one held set. Keeping the honest one keeps the thief's window request, exactly as content made in the window is kept (accepted; requirements: "nothing shows they were made before the removal" only for what nobody received in time). Requests made after the removal are in no honest addendum (`a_request_made_after_the_removal_is_kept_by_no_witness`).
- Honest X purging before its removal by a thief-controlled admin; and a thief with X's key erasing after an honest admin's removal, backdated: one held set where the removal is trusted, so one reading. Which removal is honest is the role layer's fight (trust sets, disputes); the purge rule adds nothing.
- A witness contested by a removed key's backdated lowering: the same shape as content addenda, settled by what settles the witness's role: the side its reader holds (notes/write-path-design.md §1, First received).
So the purge property has no pair of its own: no weaker promise is needed beyond the content one.

## Delete keys (spec/crypto.md §7; argued, not modelled)
- What a store checks: a delete signature per commitment group of the blob's prefix, each under that group's committed key at its level (spec/sync-ids.md §6 Delete). The levels of a delta are one per member of its retention set: 1 the thing's admin secret, 2 its purge author's write secret (at the purge author's delete base), 3 the thing's write secret. So a deleter must hold, for every group, the secret of a level that group's deltas list: the purge right by class over everything in the blob, as of the epochs the header lists. One purge author per commit gives one level-2 key per commit: "at most one level-2 key" is the rule, not an Interim (the step-4 brief drops the mark in validate.rs).
- Who holds level 2: every party with write on the purge author P holds P's write secret by derivation (spec/permissions.md §3) at the epochs it was boxed: the author class's holders (the request's path holds P and gives write). Members of P that never wrote the thing hold it too: the key proves "could hold", which is what a store may check (spec/requirements.md Deletion: "it acts on a deletion by anyone who ever held the right").
- A removed party keeps every secret it held (spec/requirements.md Permissions: "a secret once shared cannot be un-shared"), so its delete keys match the commitments of every blob written at epochs it held, for good; a rotation after its removal only keys new blobs. Its own writes' level-2 key is its own purge author's, never revoked. The model's `could hold` gate is the soundness half (every honest right holder's request is acted on); the over-reach is the accepted cost.
- What a store takes today (osis-sync `delete_keys::`, each failing with its check planted out): a Delete by levels needs a signature for every commitment group, so a deleter must hold a right over every delta of the blob (`a_delete_by_levels_needs_the_right_over_every_delta_of_the_blob_*`); another purge author's level-2 key, or keys of another thing, cover nothing (`a_party_without_the_right_signs_no_delete_a_store_takes_*`, `a_delete_naming_another_sync_ids_or_things_blob_is_refused_*`; the first two as a peer sends them: `a_peers_delete_by_levels_is_judged_as_the_stores_*`); a purge author other than the signer keys level 2 (`a_purge_author_other_than_the_signer_keys_level_2_*`; split form: osis-commit `a_split_commit_lists_one_level_2_key`); a header list's chunks carry an empty group, which no Delete by levels covers (`nothing_deletes_a_header_lists_chunks_by_level_2_*`, Open 8). A writer lowered to read keeps S's sync key (a read epoch), so its old level-2 key deletes its own writes at a store that cannot read with no purge; holders log the body again once (spec/sync-judgement.md §4) and its second delete stands until S's head moves or a part falls, while every reader still reads the write (`a_demoted_writers_old_keys_keep_its_writes_out_of_an_unread_store_*`): For Tess 4 is this, keeping a body out of an unread store, not "until re-logged". Removed outright, the sync key rotates and its Delete answers 9 (an earlier head's key).

## For Tess (all answered)
None of these is open:
- 1: fixed as proposed, the coordinator's: a delete is content, so a witness's vouch keeps one a removed node made.
- 2, 3: confirmed by spec/requirements.md as written (a removed key erases nothing; no bin).
- 4: issues/demoted-writer-deletes-at-stores.md, Decided.
- 5: issues/destruction-by-removed-direct-admin.md, Decided: a destruction is judged as any purge request.
Each is a question about the model, with what a user would observe.
1. **Undoing an honest delete** (finding 41): today a delete a removed device made before its removal is undone unless the remover's own device had received it, even where another admin's device saw it in time; the message reappears everywhere a copy survived. The fix (a witness vouches, as for messages) keeps it. Take the fix?
2. **Gone means gone, against a stolen key**: a delete whose author is later found to have been stolen before it (its removal not listing it) is undone, and the content comes back from any node that kept it; nodes that had all applied it lose it for good. The alternative (a delete once applied is never undone) lets a stolen key erase history for good by backdating. The model keeps the first. Confirm?
3. **The theft window**: between theft and removal a stolen admin key can delete anything it reaches, and if every holder applied it before the removal arrived the data is gone for good (no bin, by requirement). Accept as the window, as for writes?
4. **Stores** (issues/demoted-writer-deletes-at-stores.md): a writer lowered to read (still a reader) can delete its own old writes at stores that cannot read, with no purge and no right to purge left, and keep them out there: other devices put the data back once, and its second delete stands until the sync ID's keys move. Nothing is erased while a device keeps the data, but a new device syncing only through that store lacks it. Removed outright, it can do nothing there. Accept (availability, not erasure), or close it by letting a level-2 delete at a store need the current write key (the lowering already changes it; a demoted author's own earlier purge then reaches stores only through other writers' and admins' devices)?
5. **A destruction by a removed direct admin** (issues/destruction-by-removed-direct-admin.md): a key holding admin on a thing by its own edge, stolen and removed, can still destroy the thing for good by backdating the request before its removal; every other delete it makes after its removal is undone (2). Make destruction follow 2, or state destruction as deliberately final?

# Rust API
> Summary: The shape of the `osis` crate as it stands: a synchronous local data API (typed aspect keys, `at`, RAII subscriptions, a `Write` that is one commit or refused, `set`/`edit`/`overwrite`/`remove` and path ops, `fire` on a signal (value and signal keys told apart at compile time), the acting actor as first admin, membership by `w.group(g)`, ephemeral aspects in memory, rights checked locally, bounded materialization), signals, commit listings and listeners with undo, redo and revert, text sessions, the sharing and sync surface (async only where another node is waited on), serving, diagnostics; why each is so; rejected shapes.

## Rules
How to judge this shape, and the standing rules: notes/api-design.md.
- Vocabulary (spec/requirements.md Terms): thing, aspect, group, member (what a group contains), holder (who has a role), actor, role, node, peer, serving, account. Below the API, "label" is a sync ID and "host" a saved peer; neither appears in anything public. Engine, `osis-host` and spec rule text keep theirs (issues/net-rework.md); every old word left is in issues/deprecated-terms.md.
- Decided words (Tess): **ephemeral** is for `+` aspects. `Tid` and `Ak` stay, and an aspect key is the whole string; a domain word plus a generic one is fine (one concept under two terms is not). "Keep" splits: a removed holder's copy is retained, `keep_alive`, `History::Keep`. History: no promise is the default and unnamed (`history: None`), the delete-on-change mode is named for what it does (`History::PurgeOnReplace`, documented as costing more per change and rarely right; public docs never say compaction). "Invite" is an incoming request from a stranger; a grant's is `may_grant`. A role says who may, `sync` where the data goes (`grant` and `share` not bundled: revisit if the app finds it awkward).
- Explicit choices: the read limit (`AppConfig::read_limit`), waiting before lowering a role (`set_role` writes at once; a caller wanting more of the holder's writes kept calls `wait_synced` first). Membership is a group op (a thing in no synced group gets `NotSynced`).
- Callbacks run on one dispatcher per node, in commit order, on its own thread (default) or the app's (`Dispatcher::Pump`; kit uses it).
- Undo: per actor by default, plus a view of all available changes in scope from which an admin may remove others' (notes/crdt.md).
- Async futures resolve by a channel from the handle's background runtime (tokio by default, or a `Handle` the app passes). A browser build later gets the same sync API over a worker-backed store.
- Internals: `osis::internals` (doc-hidden; the CLI's `inspect`, tests, sim and benches, never the app or chat); its contents are `core/osis/src/internals.rs`. Generated code has its own narrow path, `osis::generated` (`use osis::generated as osis_schema;`). A feature gate is ruled out (notes/build.md Feature unification).

## Handle and lifecycle
- `Osis: Clone + Send + Sync`; clones share one node, which closes with the last handle (drop is fine; `close() -> Result<Close>` returns `Close::Closed` once closed and its sync driver is gone, or `Close::StillOpen{handles}` at once while other user handles exist: clones, upgraded `WeakOsis`, value streams, text sessions, a `Joining`). One account per store.
- `Osis::create(Store, &[Address], Config) -> Osis`: new node, new account (this node its admin), its home group synced with the peers given. (issues/recovery-redesign.md); an account is reached again only through another of its nodes.
- `Osis::open(Store, Config)`; `Osis::pair(Store, &[Address], &PairOffer, Config) -> Joining` (Nodes, below).
- `Config` and `AppConfig` (`core/osis/src`) are all defaulted. `direct_sync` off syncs with saved peers alone (tests use that). `lan` (`Lan::On { also_announce_to }`, default on with no extra targets, or `Lan::Off`) is whether a node with direct sync is on its local network; targets are for what a broadcast cannot reach, such as a routed mesh. A relay is a node at an address, so `Address` (`peer://` only). No transport to choose: QUIC, in-process endpoints only for tests. A thin client takes `AppConfig` alone. Without a runtime everything local works; calls that wait for another node fail `Network`; peers given with no runtime are `Invalid` (a store's own saved peers stay allowed: the CLI's local commands, whose writes go out with the next networked one).
- A **client** is anything using the client protocol; a **thin client** is one that is no node; a node may be a client too (`connect_node`). `db.has_store()`. Machine, transport and actor are independent. The default policy: a unix socket offers the protocol to the node's own user, unauthenticated, as the node's main actor; a localhost or network listener lets a client act only as actors it has authenticated for. A credential naming its actor may come later: `NodeLogin` grows, and the node already says who a client is (`WHOAMI`). `async Osis::connect_socket(store_dir, AppConfig)` (notes/client-port.md): `me`/`node` are the node's, tid-addressed calls go there, process-wide calls the port does not carry are `Unsupported`; `listen_socket()` serves it (needs a runtime; a store in memory has no socket, `Invalid`; test harnesses: `Internals::listen_socket_at(path)`).
- Clients with an actor of their own (notes/client-port.md §3): `add_client`, then `Osis::connect(&[NodeLogin])`, a thin client answering as one actor: `me()` its actor, what it may not read is unknown, writes by its rights; sharing, sync and process-wide calls `Unsupported`, but for `holders` and `leave` of its own actor's grant. Grants to the actor are what the client reaches.
- Group sources (notes/client-port.md §6, §8): `connect_node`, `group_source`, `Status.two_sources`. A disconnected source is `Network`, never another's answer.
- Identity: `node() -> Tid`, `me() -> Tid` (the account: author of its writes, holder of its roles), `home() -> Tid` (the private group every node of the account syncs).
- `now() -> Result<Time>` (`Time`: milliseconds since the epoch, the one public time type): the corrected clock commits are stamped with; on a thin client its node's, `Network` when it cannot be reached.

## Keys: typed aspects and signals
- `AspectKey` is what the API takes: generated constants and `DynamicAspectKey`, not a bare name (each has `name()`, its `Ak`); `RawKey` beneath it is osis-schema's, doc-hidden, what the engine takes (`Ak` too). `DynamicAspectKey` (`Osis::aspect_key(name)`, typed by a schema registered at run time; `DynamicAspectKey::untyped(ak)`: never typed) says what an app needs without the schema: `name()`, `value_type() -> Option<NestedType>` (`get()` its shape, `name()` its declared name), `default_retention()`.
- **Two kinds, told apart at compile time.** Codegen emits `Aspect<T>` for a value aspect and `Signal<T>` for a `~` key (`Ak::check` in the constant fails the build on the other marker). Calls are bounded by a trait on the key: `ValueKey` (`Aspect`, `DynamicAspectKey`) takes `get`, `path`, `on_change`, `writes`, `on_write`, `edit_text`, `keep_alive`, and on `w.at(t, k)` the value writes (`set`, `edit`, `overwrite`, `remove`, path ops); `SignalKey` (`Signal`, `DynamicAspectKey`) takes `fired`, `on_fire` and `w.at(t, s).fire(&v)`; both take `purge`, `retention` and `commit.at` (reading a part is neither writing nor firing). So a crossing on a generated key does not compile (compile-fail doc tests in `core/osis/src/keys.rs`, one per pairing). A `DynamicAspectKey`'s kind is known only at run time: a crossing read answers by the rules, no error (a signal's `get` reads absent, its `writes` list nothing; a value aspect's `fired` lists nothing), and a crossing write (a value write on a signal, `fire` on a value aspect) fails `commit()` with `Invalid`: a write never silently does nothing. History is not in the key: whether a write is kept is a run-time fact (per-write retention, required rules).
- `ValueType` (`core/osis/src/value_type.rs`): a plain description for code handling aspects it was not generated for (the app's forms, the CLI's value text). Types may be recursive, so what is nested is a `NestedType`, one level per ask. `Schema` itself is not API.
- Untyped: `DynamicAspectKey::untyped`: `T = Value` and no schema (writes go out untyped: no validation, core default retention). Typed: constants generated from a `.osis` file (`notes::BODY: Aspect<Markdown>`, `notes::TASKS: Aspect<Vec<Task>>`) carrying AK, schema, defaults and codec. A read through a typed key cannot be mistyped; a write through one is validated against the writer's schema (every declared field required, spec/versioning.md §5). Nothing about the schema goes on the wire.
- Markers (spec/data-model.md §2): independent, read from any key's name, typed or untyped: `Ak::ephemeral()` (`+`: held in memory, never in durable commits), `Ak::admin_only()` (`^`), `Ak::signal()` (`~`: no current value, only fired); no schema flag. Doc-hidden `RawKey` has the same three for the engine's text keys. A value that lives while its author is there: `at(t, k).path(p).keep_alive(&v) -> KeepAlive` (or `at(t, k).keep_alive(&v)` for the whole aspect, typed) on an ephemeral key with a default expiry (notes/ephemeral.md Values that live while their author is there).
- `osis::core`: only what apps truly read and write by key: `NAME`, `BODY`, `TAG`/`Tag`, `REQUIRED`/`Required`/`RequiredRules`. The rest (`GROUP`, `ROLES`, `CREATED`, ...) is through calls (`members`, `grants`, `created`), and `internals::core_types` for tests.

## Reads
- `db.at(tid, key) -> AspectRef<T>` with `.get() -> Result<Option<T>>`, `.path(p).get::<U>()` (`U = Value` for untyped; a typed key's whole stored value: an untyped key; per-path reads skip one bad element of a large collection), `.path(p).byte_len()` (canonical size in bytes), `.path(p).stream() -> impl Read + Seek` (large string or blob), `.on_change(f)`, `.path(p).on_change::<U>(f)`.
- Every read returns `Result` (a node that cannot answer is `Network`, never a default); what each call means is in `core/osis/src/read.rs`. Deleted and never written are not told apart: `has_content` is false for both, and deletion is derived, never a flag. `groups_of` reads the in-memory group index rebuilt from the definitions at open, nothing scanned. No call reads a thing's first admin: it is history, and gives no power once its edge goes. `role_on` has one rule for every route to a role (`read::usable`; spec/crypto.md §7). A thing's times (`created`, `changed`) are shown and sorted by `shown() = min(written, received)`: one skew rule (an author's clock may run ahead, by at most `MAX_DRIFT` before its commit is parked; `received` is this node's clock), no app-written time field. `changed` reads the in-memory commit index: newest `ts` first per aspect, stopping once `ts` is at or below the best `shown()`; a commit known only from a snapshot is not seen (Attribution), so after compaction on a new node it may read older than the truth.
- Stored data never fails a read on typed grounds (Typed reads below): a value that does not decode through the key reads as `None` and reports a `Mismatch` diagnostic. `Error::Type { path, reason }` is for what the caller passes: a typed write's value, a path the key's schema does not have.
- **Read limit**: a value whose canonical size exceeds `AppConfig::read_limit` returns `Error::TooLarge { limit }` (the bound; a length is unknown without reading) from `get` and from any typed read; read it by `stream()` or by path (a path read into a huge map or list costs O(entry) and never loads the whole). Explicit failure beats an out-of-memory.
- Values are snapshots: plain `Value` or generated structs, nothing reactive hidden inside.
- `Path`: steps `Field(id) | Case(id) | Key(Value) | Index(usize) | Elem(Value)`; `p![..]` builds one from literals and generated field/case constants (`task::DONE`). Typed path builders from codegen are not built (optional).

## Watching
- A value listener remembers a BLAKE3 digest of the last value (`watch::digest`, as does the port's served subscription), never the value: the node does not hold every watched byte twice.
- `db.at(tid, key).on_change(|db, c: Change<T>|) -> Result<Subscription>`: taken atomically with the current value, so no change is missed between read and subscribe: the callback runs once with that value (`Origin::Initial`) through the dispatcher like every later call, then on every change. Async code forwards it to a channel of its runtime and awaits that (crate docs); no second watch type (Tess). `db.at(tid, key).path(p).on_change::<U>(f)` is the same listener at a path of any depth and type, reading what `path(p).get::<U>()` reads: called when the value there differs after a transaction from its last call (calls coalesce), whatever caused it, so a write to map entry `a` calls the listener at `p![a]` and not the one at `p![b]` (each listener on a written aspect reads its own path, O(the value there): `Reader::get_path` over `Engine::get_at`, which loads only the pages on the path). A path the schema lacks fails `Type` at registration. A thin client's goes as Sub filter `[0, tid, ak, path]`, the node sending a Notify only when the path's value differs. No changed-paths report and no map-only watch (notes/listener-design.md). `db.on_thing_change(tid)` for all aspects of a thing (`Change<Value>` names the AK); a delete, local or remote, reaches it as its aspects going absent, and `has_content(tid)` in the callback then reads `false` (no separate deletion event: a thing is deleted exactly when it holds no content). `db.on_grants_change(thing, ..)` (its callback takes `Result<Grants>`: a lost connection is told), `db.on_status_change()`; each `Result<Subscription>`, `Network` for a thing or its grants at a node that cannot be reached now.
- `Change<T> { tid, ak, value: Result<Option<T>>, origin: Origin }` with `Origin::Initial | Local(Stamp) | Remote(Stamp) | Derived(DerivedFrom)` (`DerivedFrom::{ValidityChanged, Expired, Purged, Arrived, LostAccess}`: what changed a read when no new commit did) and `Stamp { id: CommitId, actor, node, written: Time, received: Time }`. `CommitId` is opaque (`Display`/`FromStr`), ephemeral commits included. `on_change` and `Change<T>` keep the word: they are about a value changing, whatever did it (`Derived`, `Initial`), not about commits. `Stamp`, `ThingStamp`, `Commit` hold the exact hybrid time privately for ordering. `on_change`/`on_thing_change` hear nothing of a signal (Signals). Display time for feeds is `min(written, received)` (a sender's skewed clock).
- `Subscription` is RAII: dropping it unsubscribes; `detach()` keeps it for the node's life. No ids to remember.
- Who runs callbacks (`AppConfig.dispatch`): `Dispatcher::Thread` (default), a thread the node starts; `Dispatcher::Pump(wake)`, the thread that calls `db.settle()`, so a UI applies changes on its own thread with no cross-thread hop. `wake: Arc<dyn Fn() + Send + Sync>` is called once when callbacks become due after the last `settle` began, from whatever thread queued them, after it released the node lock (so calling the node there cannot deadlock): it should only schedule a `settle` (a UI loop event). `settle` is the one call for both: with a thread it waits for it (tests), with a pump it runs everything due (including what callbacks it runs cause), on the calling thread (after another thread's pump in progress). Inside a callback it returns at once. One dispatch implementation (`Pump::step` in `watch`) with two drivers.
- **Read-only handle**: `ReadOnly` has every read (`at`, `aspects`, `groups_of`, `members`, `grants`, `role_on`, `holders`, `has_content`, `created`, `changed`, `status`, `profile_of`, `saved_peers`, `writes`, `undo_target`, `redo_target`, `me`, `node`, `aspect_key`) and nothing else; `Osis` derefs to it, so `&Osis` is a `&ReadOnly` and a read path takes that one type. A write, a listener, a session, `now`, `profile`, a `WeakOsis` do not compile on it (doc test `handle::ReadOnlyChecks`). Listeners live on `Osis` (`at` there is the same `AspectRef` with them added).
- **Tracked reads**: `ReadSet::new(on_change)`, `db.tracking(&set) -> ReadOnly` (a read-only handle whose every read also keeps a listener), `set.sweep()`. Each read is one answer plus one listener at its own address, taken under the one node lock, so no write falls between them on any dispatcher; the set holds one listener per address (a repeat read reuses it, moving it past what the read showed) and `sweep` drops those not read since the last sweep. A listener calls `on_change` once when its address reads otherwise than the last read, then waits for the next read. Values and paths compare as `on_change` does; `aspects` (names), `has_content`, `groups_of`, `role_on`, `holders`, `created`, `changed`, `grants`, `profile_of` have internal listeners that re-read and compare; `writes`, `fired`, `versions`, `undo_target`/`redo_target` listen as `on_write`/`on_fire`, `commit(id)` the same filtered to `id` (a quote moves with its message alone), `status` as `on_status_change` (no comparison). Addresses: a thing's aspects (`aspects`, `has_content`), commits on the thing (`created`, `changed`), the group index (`groups_of`, `Event::Groups`), a roster or key change anywhere (`role_on`, `holders`, an `until` passing told as a roster event: their reach is the role graph, so each such event re-reads each listener, stated: O(role_on listeners) per role change). Commit listings listen first and read after (their read is not one lock with the listener's registration): a write in between fires once more, harmlessly. Reads with nothing to listen to (`peers`, `group_sources`, `nodes`, `links`, `retained_copies`, `clients`, `invite_requests`, `sync_ids`, `serving_address`, `serving_key`, `disputes`) are on `Osis` only; at a connected node `groups_of`, `role_on`, `holders`, `profile_of`, `stream`/`byte_len` fail `Unsupported` on a tracking handle (no wire filter yet; issues/tracked-read-port.md).
- Coalescing: a callback that falls behind sees every commit's effect but not necessarily one call per commit. A slow callback delays later callbacks, never writes or sync. A watch on a value above the bound delivers `Err(TooLarge)` per change and the app re-reads by stream or path.

## Writes
```
let mut w = db.write();
let note = w.create()?;                                      // first admin: the acting actor; ephemeral until a durable write
w.group(folder).add(Member::Item(note))?;
w.at(note, notes::TITLE).set(&title)?;                       // make equal: structural diff against current state
w.at(note, notes::TASKS).edit(&shown, &edited)?;             // apply only what the user changed since `shown`
w.at(note, notes::TASKS).path(p![2, task::DONE]).set(&true)?; // path op
w.at(note, notes::BODY).overwrite(&body)?;                   // always a write, of the whole value
w.at(note, notes::VIEWS).path(p![]).contribute(&1)?;
w.at(note, key).retention(r).remove()?;                      // retention per aspect
w.group(folder).remove(Member::Item(note))?;
w.group(g).add(Member::Subgroup(sub))?;
w.delete(note)?;
let done: Option<Commit> = w.commit()?;                      // one commit (two: below), or Invalid naming what clashed

let mut w = db.write();
w.expires(Expiry::In(DAY));                                  // the commit's
w.at(msg, chat::BODY).set(&text)?;
w.group(other_group).add(Member::Item(note))?;
w.commit()?;
```
- Whole-value ops: `set(&v)` makes the aspect read `v` (the spec's structural diff against the current state, spec/crdt.md §9: concurrent edits inside the value survive, but a field the app did not touch is written back if it differs from the current state); `edit(&base, &new)` writes only the difference between what the app showed and what the user produced, as path ops against the current state (struct fields, enum case, map keys, set elements, bag values exactly; sequence edits rebased onto the current sequence by matching `base` to it, notes/crdt.md Implementation), so a remote change to another field during editing is never overwritten; `overwrite(&v)` writes the whole value, always, discarding concurrent changes inside it (an equal value still counts as a write: `set` of an equal value writes nothing; a log of events is a signal, where each `fire` counts; a map overwritten on a long aspect costs O(writes so far), a scalar stays flat); `remove()`. `edit` or path ops are the rule for anything a user edits while remote changes may arrive; `set` is for "the value must be exactly this" (imports, derived data). Not named `replace`: it says nothing against `set`. Internals keep `Op::Replace`.
- Path ops at `.path(p)`, the empty path being the whole value (`at(k).set(&K::T)`, `overwrite` and `keep_alive` differ only by checking the type at compile time; `at(k).remove()` is the root's, the one shorthand, as removal is an aspect's usual end; `at` holds nothing else a path has): `set`, `overwrite`, `set_stream`, `remove` (the aspect at the empty path; a map entry, set element or list element: `p![k]`); list or text `splice(range, items)` (`SpliceItems`: a slice in a list, `&str` in text, `()` for nothing: a `&str` on a typed list is `Invalid`, an item of the wrong type `Type`, a backward range `Invalid`, nothing to do writes nothing), `move_range(range, to)`; set `add(v)`; bags `contribute(v)` (a counter's amount, a max or min's observation: one op). A map entry is `path(p![k]).set(v)`, an enum case a `set` of a `Value::Enum`. Index paths resolve against local state at commit time. A path op into a map key with no live entry creates the entry (spec/crdt.md §5.6): the first reaction to a message is `path(p![msg]).add(&emoji)`, and two nodes doing it concurrently both count; a path on through a struct field or enum case is refused (`Invalid`: it would write a partial record; `set` the whole value). An entry created by an expiring write goes at T with everything later written into it (spec/crdt.md §4.7). `group.0` field ids are `core::group::{ITEMS, SUBGROUPS}`.
- `create() -> Tid`: a new thing, the acting actor its first admin (`self.actor` at the call, so after `act_as` that actor). `create_with_admin(admin) -> Tid`: the same with `admin` as first admin (needing write on it): a thin client's way to create, whose own actor goes with it, a thing made for a group's holders, and a tree of things (write on `admin` is checked locally; a first admin the same commit creates counts through its own, so a tree of new things is one commit). A new thing is plain, deriving its secrets from its first admin's, until its first grant or `sync` gives it secrets of its own; removing the last admin of a plain thing is `Invalid` (spec/permissions.md §1). On a thin client's handle `create()` is `Invalid` at commit (its actor goes with it, notes/client-port.md §3), which leaves it `create_with_admin(g)`. The thing's record goes in the write's durable commit (a commit holding only records is a role commit acting for the node), so a `+` write on it waits for a second write (`Invalid` beside the creation; notes/ephemeral.md). Membership is `w.group(g).add(Member::Item(t))` in the same commit. **A thing becomes a group with its first member** (no `make_group`): the commit's first add to a thing with no `group.0` writes an empty `group.0` first (`Write::first_member`; a `group.0` holding one field decodes as none, so a bare `Add` would lose the member silently); once a group, always (emptying it leaves `group.0` present). A shared space with its own label (a chat, a team) is created, given data and `sync`ed, not added to the home group: its first admin's nodes find it through the home label's `label.0` cross-publish, while adding it to home copies every commit touching it (rotations with their boxes, messages) under the home label too (measured 8 KB per chat removal at 4 holders, the rotation's boxes at scale). The app's choice, not an API default. A group's items sync only through groups listing it as a subgroup (its members are its items and its subgroups' members, not its items' items), so a group meant to sync with home is both an item of home (its own aspects) and a subgroup (its items). The mistake is loud: a commit after which an added durable thing reaches no synced group while the target group's own aspects sync (an item of a synced group, no subgroup of one) fails `Invalid` naming the fix, before anything applies (`Mutation::require_synced`, checked against the state the commit leaves, so the same commit may add the subgroup). Removing a subgroup that leaves existing items in that state is not checked. A durable thing added only to groups that do not sync at all (node-local data, deliberate) is allowed and gets a `NotSynced` diagnostic after commit (spec/requirements.md, Offline and network). An add in an expiring commit makes the membership expire, item or subgroup (a disappearing message leaves its group by itself). A removal or `delete` in an expiring commit is `Invalid` at commit. (Not because it would come back at T: it would not, a reset outlives its expiry; the refusal only keeps the rule simple and could go.)
- `end(tid)`: purges the thing's creation: gone at every node, later writes ignored, not undoable; any admin, as with any purge right (`Permission`); a key actor (an account) by itself. What depends on it lives on: rights through it stand as they were. A commit that creates a thing and expires ends it at the expiry: one commit is a disappearing message.
- `delete(tid)`: removes every durable aspect that may hold content (`read::deleted_aspects`: present here, or written by a valid part not received yet that no held root reset stamped after it covers, so once synced a delete leaves the same reads at every node; not `created.0`, `required^.0`, role-class or signal ones; `remove_aspect` writes its reset even where no state is held; an aspect that cannot hold content gets none, as resetting every aspect ever written would make a required rule's refusal (Write) permanent once an aspect under another rule was ever written) and its memberships, as item and as subgroup, in every group this node may write (`groups_of`'s `item_of` and `subgroup_of`); a group it may not write keeps listing the tid, which reads deleted there. Afterwards `has_content` is `false` here and wherever the delete arrives (unless a concurrent write left content). Tids never die and a later write recreates the thing; no wire concept. Its ephemeral values are dropped at this node and not written; other holders keep them until they restart or the values end (notes/ephemeral.md Deletion).
- Rights are checked locally before signing: `Error::Permission { tid, needs: Role }` when the acting actor lacks write (admin for role-class aspects) on a touched thing, or this node does not hold a written thing's delete keys yet (a content write, whatever its retention; `role_on` says `Read` meanwhile; an admin's grant fails then too, so far with an opaque `Invalid`: issues/admin-before-keys-error.md); `Error::UnknownThing` when its `created.0` is not held. A write is never emitted to be un-merged elsewhere.
- **`commit()` makes one commit** over every touched thing, of any reader sets, of any size (deltas page, spec/crdt.md §8), or fails `Invalid` before anything applies, naming what clashed; the app writes several commits if it means to (Tess: never a quiet split). Returns `Option<Commit { id: CommitId, written: Time }>` (`pos()` its place in a history; `None`: nothing to write). What clashes:
  - **Expiry**: a commit has one. `w.expires(Expiry::{At(T), In(d)})` is the commit's (a later call replaces it; `Invalid` at commit when not in the future), else the keys' defaults, which must agree (a plain key beside a `expires(30d)` one clashes), and a thing's `required^.0` expiry stands. A write into a value expiring sooner keeps its own expiry: a reaction outlives a disappearing message (spec/crdt.md §4.7).
  - Judged on what the ops ask, not on what they turn out to write: `set` of the value already there counts.
  - **`nobody`**: a `nobody` delta shares a commit only with `nobody` deltas, a thing's record and `required^.0` aside (spec/commits.md §5). Other retention differs per aspect freely.
  - **A thing's record and `required^.0`** never expire, so an expiring commit cannot carry them. A purge request may expire: it then reaches only deltas expiring no later. The commit creating a thing therefore has no expiry: a thing with expiring content takes two commits, the first creating it (`create()` alone is enough: a commit holding the record alone) (issues/creation-record-ordinary.md would make it one commit).
  - **Durable beside ephemeral beside ephemeral signal** (`+`, `+~` keys): different commits on the wire, a peer could see one alone. A creation or a `delete` counts as durable, so a `+` write on a thing the same `Write` creates or deletes is refused.
  - A **`delete`** answers to its thing's `required^.0` like any write (each reset must carry its rule's retention and expiry), so a thing whose aspects or groups fall under different rules refuses it, saying to remove those first; every disappearing chat does (issues/delete-required-rules.md).
  - An **undo** is one commit too. It expires with the values it copies back, never at a key's default; one copying back values of different expiries (or expiring beside lasting) is `Invalid`, nothing applied, until the sooner ones have expired and there is nothing of theirs to copy back (spec/crdt.md §4.6), so a lasting value never takes another's expiry. An ephemeral undo that copies back an expiring value goes value-less at its T, as a durable one does.
  - Own watches fire after the commit is durable. Ephemeral ops take no `retention` or `purge` (`Invalid`); a signal takes one `fire`.
- `Write` is `#[must_use]`; dropped uncommitted it discards its ops (debug log). Reads inside a `Write` see committed state only; pending ops are invisible until commit.
- A write is authored by `me()`; `Write::act_as` sets the header's actor, under the node's rights; the node must hold write on that actor (else `Permission`), as receivers judge a commit invalid otherwise (spec/permissions.md §5.2), so a valid commit's actor is trustworthy. A thin client's rows run on `Osis::act_as` (crate-internal), held to the actor's own rights (notes/client-port.md §3); anonymous writing (notes/permissions.md) is later.
- Retention per aspect: `.retention(Retention { by, history: Option<History> })` on `AspectWrite`, default from the key; checked at commit. `History::Keep { until: Time, after_replaced: Duration }` (the later counts; a zero or past bound keeps nothing, and both such is written as `None`, so reading it back shows `None`: plain fields over options leave one spelling per bound), `History::FOREVER`, `History::PurgeOnReplace` (only `PurgeBy::Writer`); `PurgeBy::Nobody` only with `History::FOREVER`; a `Duration` past `u64` ms saturates, which every check refuses. The API's own types (`retention.rs`) over the engine's millisecond `osis_schema::Retention`. One enum, not fields that exclude each other: keep and purge on replace cannot be combined.
- Role-class aspects (`roles.0`, `keys.0`, `secrets.0`, `label.0`) are written only through the sharing and sync calls below; a `Write` op on them fails with `Error::Invalid`. `group.0` is written only by `Write::group` (it checks sync and cleans up tied grants), `Invalid` otherwise, also in a write from a client.

## Text editing sessions
- `db.at(t, k).path(p).edit_text() -> TextSession` (`p![]` for the whole aspect): a buffer the UI edits (`text()`, `edit(&base, &new)`: the user's change of `base`, the text the UI showed, placed in the buffer under the session's lock, so merges the UI does not show yet are kept: the change removes what it removed that they kept and inserts where its point went; as the aspect's `edit`, it says what the user did, never an index into a buffer that may have moved; cut and paste with remembered ranges not built, notes/crdt.md); the session follows its field whoever writes it (another session, a `remove`, an undo, another node): a field reading other than the text the session last committed or merged has pending typing committed first (the crdt rebases it), then the merged text replaces the buffer (a removed field reads empty), reported through `on_merge(|text, edits: &[Splice]|)` (`Splice { at, del, text }` in chars, each at the text before it, from a char diff of the buffer and the merged text; `Splice::map(pos)` moves a caret: an insert at the caret goes after it) so the UI can map cursors; its own commit's echo neither reports nor commits. So two sessions on one field share it, and clearing a draft is a plain `remove`. Commits on `commit()`, after `idle_commit` of inactivity, and on drop; at most one save of a session is in flight and none holds the buffer across a node call, so a keystroke never waits for a save. A session whose thing was deleted (locally or remotely) since it was known here (at open or a commit of its own) never recreates it: `commit()` fails `UnknownThing` with the edits kept (they commit if the thing comes back, e.g. an undo of the delete), and drop (which then loses them), the idle commit and a merge report an `Uncommitted` diagnostic. This owns the "one commit per editing pause, never per keystroke" rule (spec/requirements.md, Generality); apps never commit per keystroke by accident because the session is the only path that makes keystroke-granular changes convenient.

## Signals
A signal (key marker `~`) has no current value; it is fired, `w.at(t, s).fire(&v)` (one whole value; each fire counts, an equal value too), never written (Keys: value calls do not compile on a `Signal<T>`, and are `Invalid` through a dynamic key). Its fires are listed by `fired` and heard by `on_fire` at its key alone: no scope lists a signal, and `on_change`/`on_thing_change` hear nothing of it. The `+` marker decides the rest, independently: with it, the fire is a relay-only commit that reaches only the connected nodes that read the thing, best effort, held by none (notes/ephemeral.md): `on_fire` hears it once where it is written and once where it arrives, as it arrived (`CommitChange::fired` of `Event::Commits`, since no read finds it), and no page shows it (`w.commit()` returns it with no parts); through the port it is queued against `PUSH_BYTES` (a lapse past it ends the watch). Without it, the fire is a durable commit, each its own write, never merged, listed until its keep bound, expiry or purge (spec/commits.md §5 Signals). Such a key needs `keep_history` (the schema refuses one without; an untyped write without it is `Invalid`), an undo writes nothing back for it (it reads absent before and after; a `revert` of a commit holding only signal writes writes nothing, `NotUndoable { Superseded }`; purge removes one), and nothing compacts it. `on_fire` is told once per transaction in which the commit reads otherwise, so a fire that leaves the listing (a kick, a purge) and comes back is told again, and one purged in the transaction that applied it is told as purged (spec/commits.md §5 Signals). Needs write on the thing. Event-style signals should carry a sender sequence in their value (a node on several relays may see one twice).

**Edits** (notes/signal-edits-design.md; spec/commits.md §5 Signals): `w.at(t, s).replace(original: CommitId, &v)` is a fire naming the fire it replaces, whole (no partial edits). It is the write's one fire on that key, takes the original's expiry unless it says otherwise, and is `Invalid` at commit unless the original is this actor's fire of this durable signal, held, listed and valid, replacing none itself, and no required rule refuses it (`Required::refuse_replace`, wire `final`): the writer never emits a replacement it would not honor. An ephemeral signal is `Invalid` (nobody holds its fires). Reading is the one fold everywhere a fire is read: a page, `commit` and `on_fire` show the fire in its place under its own id, reading its newest honored replacement, `Part::edited: Option<CommitPos>` the replacement's place (`None`: as written; it stays set on a deleted message whose newest version was purged); a replacement is never listed or heard of its own once folded (`commit` of it is `None`; `w.commit()` returns it with no part there). History on demand: `db.at(t, s).versions(id, &CommitQuery) -> CommitPage`, the fire and its replacements in its place, each as written (`edited: None`), paged and filtered as `fired`; nothing for a replacement or a non-fire; no listener of its own (`on_fire` hears every change of it under `id`; the port refuses a `Versions` address as a filter). Delete: `purge(Purge::Commit(id))` of a fire names it and every replacement of it held here (`Engine::claims_on`), so one call deletes the message; drop old text by `replace` plus `Purge::Commit(original)` in one write (the new version is not held yet, so it stays). Limit: a replacement not held here when the purge is written (in flight, or written later) still shows, as a new message could. Undo writes nothing for a signal: restore by replacing again.

**One fire by id**: `db.at(t, k).commit(id) -> Result<Option<Commit>>`, any key kind: the commit as `writes`/`fired` there would list it now, `None` when it is not listed there. O(log n) and one body: what a reply quoting a message reads. Port `LISTED_COMMIT [address, commit id] -> Opt(commit)`.

## Commits (one model: listings, listeners, undo, redo, revert)
notes/listener-design.md is the design; steps 1-4 are built.
- **One `Commit`** for every commit the API shows: listed, heard, made by `w.commit()`, `revert`, `undo`, `redo`, named by `undo_target`/`redo_target`. `Commit { stamp: Stamp (id, actor, node, written, received), kind: CommitKind::{Content, Revert, Role, Snapshot}, reverts: Option<CommitId>, reverted_by: Vec<CommitId> (oldest first), in_effect, parts (private) }`; `pos()`, `at::<K>(t, k) -> Option<Part<K::T>>` (decodes then: a body not a whole value of `K::T` reads `Held(None)` with a `Mismatch` diagnostic; the untyped key shows it), `parts()` untyped. `Part<T> { valid, body: Body<T>, edited: Option<CommitPos> }` (Signals: Edits), `Body::{Held(Option<T>), TooLarge { limit }, Purged { by, actor }, NotFetched}`. A body reads as the commit wrote it (a superseded one as written). `stamp.actor` is verified exactly when a part is valid (spec/permissions.md §5.2). A `CommitKind::Snapshot` is a commit of its kind (Attribution); a chat shows `Content`s.
- **Which parts are listed**, one rule at every address: a part is listed while it is in its aspect's read (a write of it live, value-less ones included, so a purge tombstone of a live write is), or kept by history (`keep_history`, a per-write retention or a required rule, until the keep bound), or this node's own invalid write (marked `valid: false`, so its user may write it again). Replaced with no history kept, expired, dropped (compacted), another node's invalid write: not listed, whatever is still held. A commit's parts are every listed part the caller may read, on any thing, value or signal. Every node holding the same commits lists the same ones; undo writes back exactly these (Kept history only).
- **Listings**: `db.at(t, k).writes(&CommitQuery)` (a value aspect; the same as `db.writes(&Scope::Aspects([(t, k)]), q)`), `db.writes(&Scope, &CommitQuery)`, `db.at(t, s).fired(&CommitQuery)` (a signal), each `-> Result<CommitPage>`. A commit is listed at an address while it has a listed part there; a scope lists value aspects only (`Thing`/`Group`: durable ones; `Aspects`: as named, an ephemeral one too; a signal in none), a signal's fires list at its key alone. Through a dynamic key (Keys), `writes` of a signal and `fired` of a value aspect list nothing, no error. `CommitQuery { from: CommitFrom, limit: Option<usize>, actors, kinds, reverts, reverted_by, in_effect }` (plain struct, `Default`; empty filters match all). `CommitFrom::{Newest, Oldest, Before(CommitPos), After(CommitPos)}` in that direction (Newest, Before: towards older), neither bound counting itself; `CommitPos` is opaque (`Ord`, `Display`/`FromStr`, its text sorting as places do; `at()` its time, `commit()` its commit, none at a time's): a commit's `pos()`, `CommitPos::time(t)` a time (`Before` it: stamped earlier; `After` it: from there on). `CommitPage { commits, more, complete }`: a page ends early past `limit`, `COMMIT_PAGE` (256) or the read limit, and `more` says so. An unknown thing, or one the caller may not read, lists nothing.
- **A gap**: `complete: false` means a label carrying the address has not finished a pass here (or only groups sourced at another node hold the thing), so commits may yet arrive anywhere: not fetched, not absent. A new node's first sync (spec/sync.md §6) is this state: role commits, then newest first, so `CommitFrom::Newest` reads real commits at once and `Before` pages older ones as they arrive; status `Syncing` until done. A node that chooses not to fetch (not built: issues/partial-history-fetch.md) would say the same. It does not bring what compaction replaced before this node held it: that is the snapshot's commit.
- **Listeners**: `at.on_write`, `db.on_write(&scope)`, `at.on_fire`, each `(|db, CommitEvent|) -> Subscription`: `Commit { id, commit: Option<Commit> }` per commit that may read otherwise there, read when delivered (new, late, a part turned valid or invalid, a body arriving, purged, dropped, expired; `None`: not listed there, any more or at all). `Reread`: events may have been missed (a connection to a node dropped or came back, a commit did not fit a Notify): read the pages shown again. `Ended(e)`: over (the source moved, a lapse): subscribe again. No initial call: subscribe, then read pages; an event repeating what a page showed is harmless. Local writes are told as remote ones, and so is a commit leaving or entering the listing because a write replaced (or a validity change revived) its part with no history kept. So is a part leaving at its keep bound, by a timer. A purge can list a part that had left (issues/purge-relists.md).
- **As built** (`engine::listing`; the rule is `listing::listed_part`, the one function undo's `kept` uses too). Costs: a page is O(log n + places walked), and a filter matching few walks the whole address; `reverted_by` and `in_effect` scan the commits on a listed commit's value aspects stamped after it, so a page from `Oldest` of an aspect with n commits costs O(page × n), as does each listener event for an old commit (stated, not optimized). Listeners are off until an open's first listener (`Engine::watch_commits`, sticky) and cost nothing on an aspect none is on. A join on a listened aspect costs the commits it superseded (`Killed` dots, `listing::note_killed`): each is told when it reads no longer listed and has its keep-bound timer armed; only a rebuild (a validity flip, an un-merge, a drop, a paged reset, O(commits held) anyway) compares the whole listing before and after. A part listed by its keep bound alone leaves with no state change, so a `T_KEPT` timer at its bound tells it. Dispatch finds subscriptions by (tid, ak), thing, group and role slots, O(log S + matched). Purge requests are stored per aspect only when they name more than one delta; by name under `pn/` + aspect + commit.
- **Delete for everyone**: `w.at(t, key).purge(Purge::Commit(id))`; **by author**: `.purge(Purge::Author(actor))`; `.purge(Purge::All)` the whole aspect's, with its removal. Each judged per delta by the purge rights (spec/permissions.md §6), no override: under `author` or `nobody` an admin's request drops nothing, under `nobody` a flood stays (Tess; why it is not the default). Outside the chat's class a wide request's arrival-order differences are in held bodies, not reads (what the order oracle checks, notes/testing.md). `Purge::Author` names deltas stamped before the request, in any arrival order; later writes stay, so remove the member too. `actor` is one header actor: an account's nodes share theirs, each of its thin clients has its own, so a member's writes through a client take their own request. An invalid commit is named by the actor it claims. A request takes its commit's other writes' expiry (none alone, as `purge.0` has fixed retention, so the engine leaves `purge.0` out of an expiring commit), and then reaches only deltas expiring no later (spec/commits.md §5): so an edit purging its message's old text is one commit in a disappearing chat too; one naming anything else in an expiring commit, or on a thing the commit writes nothing on, is refused with `Invalid`. A request the acting actor's rights would drop none of the held deltas it names (never a snapshot: it has nothing of its own to take) is refused at commit with `Permission` on the thing (`retention::check_request`, the receivers' `holds_right` on the built header; an item naming none held is written, honored when a named delta arrives); so a request needs write on the thing (no class gives a right without it) and carries a `purge.0` write, as its commit needs a delta to go under the thing's labels (spec/commits.md §5); so the request itself is not listed at the purged aspect and resets nothing (a writer applying it may write a snapshot of the aspect, spec/commits.md §5 Purge, listed as any snapshot is): purging the live write of a register leaves it reading absent, `set` in the same commit for a value. The purged part lists as `Body::Purged { by, actor }` (the earliest request by `(ts, ID)`, its verified actor) where it would otherwise be listed; for a permanent delta that is for good and reaches new nodes (spec/commits.md §5).
- **Undo targets**: `db.undo_target(&scope)`, `db.redo_target(&scope) -> Result<Option<Commit>>`: the commit `undo`/`redo` would revert now, failing as the call would (`NotUndoable{ContentGone}` by kept history alone, `NotUndoable{Superseded}` when it would write nothing: the same computation as the revert, rolled back): what a UI labels or disables its buttons by. `undo`/`redo` take exactly that, then revert. They range over the held commits valid on the scope's value aspects; relations are judged over every held commit touching those commits' aspects (a revert touches its target's aspects; one of a creation may touch any aspect of the thing a held header names, so those count for a scope holding the creation).
- **Revert**: `db.revert(id: CommitId) -> Result<Commit>` (any held content commit, durable or ephemeral; one not held, an ephemeral commit forgotten here, `Invalid`): a commit of the target's class naming it (wire `undoes`) with the inverse writes (spec/crdt.md §4.6: parts superseded since are skipped; nothing to write is `NotUndoable{Superseded}`; role commits and snapshots are `Invalid`).
- **Kept history only** (notes/listener-design.md; spec/commits.md §7): the inverse writes back content only from kept history, the held valid parts before the target still in the read or kept by their keep bound; a body held but not kept never counts, so the answer is alike on every node, after restarts and whatever was compacted. The target's op kinds decide whether it needs replaced content (`osis_crdt::restores`): a register or value set, a removal, a move or a reset does; an insert, a set or bag add, a map entry's creation or a thing's creation does not. One that does is `NotUndoable{ContentGone}` unless every part of the aspect before it is kept or superseded by a kept part: a whole write stamped after it, or (a delta without expiry) a snapshot whose tables reach it (`undo::replaced_kept`): each by its own retention, its bound counted from the target's `ts`, so an edit older than the keep bound is `NotUndoable` by age; the target's own retention does not count. A part not fetched yet, or an ephemeral commit forgotten here, blocks too; one unkept part blocks every later restoring undo on its aspect until a kept part supersedes it (accepted limit). A first set replaced nothing and undoes to absent. A redo writes the undone value back, so it works only while the undone write is kept. A revert reverts every part of its target or fails: a part it inverts whose body was dropped (covered, expired, purged) or not fetched yet is `NotUndoable{ContentGone}` (one check, `undo::undone_parts`; never a revert of the rest). User-edited aspects declare `keep_history(1d)` (core `name.0`, `body.0`, `tag.0`, `group.0`, every `event:` and `contact:` aspect), so a `delete`, a membership removal and an undone creation's redo undo for a day. A `delete` writes each removal typed as `aspect_key` types it, so it keeps its schema's history. In effect: no revert in effect reverts it. Revert depth: 0 for a commit, +1 per revert (odd = an undo, even > 0 = a redo).
- **Undo/redo** (this actor, any node, under one lock): `undo(&scope)` reverts the newest own in-effect commit or redo (even depth); `redo(&scope)` reverts the newest own in-effect undo (odd depth) unless a newer own commit (depth 0) is in scope (a new commit clears redo). `None` when nothing qualifies; `NotUndoable` when the chosen one cannot be reverted (nothing older instead). A revert of someone else's commit counts as an undo of the reverter's: the reverter's redo reverts it, their undo skips it; the reverted commit's author can no longer undo it (out of effect) and cannot redo it (not their undo).
- Undoing a creation deletes the thing (Tess; spec/crdt.md §4.6): the commit carrying its `created.0`; its revert also does `delete`'s writes (every durable aspect that may hold content and its memberships, as item and as subgroup, in every group the node may write; `Permission` when the node may not write the thing, never a partial revert) and drops its ephemeral values here as `delete` does; redo (or `revert` of that revert) writes the removed memberships and content back, so only kept history brings anything back (Kept history only), never its ephemeral values. In a thing's scope, its creation is the oldest commit.
- Undo restores the read before the undone commit where only undos changed it since (spec/crdt.md §4.6 SHOULD): undoing the first write into a spot that did not exist resets the spot when it reads just what that write made it (concurrent writes arriving later are wiped); a register in a present struct stays (no nested register reset).

## Large values
- Typed and untyped reads materialize up to `read_limit`; above it `stream()` (`Read + Seek`, lazily fetching chunks, memory bounded to a chunk plus the tree path), `len()`, and path reads. Writes: `set_stream(impl Read)` on a `blob`/`string` position builds the chunk tree without materializing; `set`/`edit` accept in-memory values of any size the caller has. Equality is by content; links never appear in values the API returns (`Value::Link` is replaced by the materialized value, or the read fails `TooLarge`; a link that cannot be read, its blob not held or failing verification, reads as absent at its position with an `Unreadable` diagnostic, spec/data-model.md §6; a commit's part reads `NotFetched` instead). A read that missed a blob notes the aspect, a commit's read the (aspect, commit) (`Engine::missed_blob`, `Core::missed`); the next blob stored re-delivers every noted aspect to its watches (`Cause::Fetched`) and every noted commit as `Event::Commits`, and a read still missing one notes it again.

## Queries (not built: a design pass first, issues/api-deferred.md)
Per-aspect reads are not enough for any list-like UI; meanwhile apps list group items with `members(g)` plus per-thing reads. Expect most of a slow, not very feature-rich node to grow over the local store, over time; nothing of it touches the wire. The sketched shape:
- `db.query(Query::in_group(g).with(key).order(Order::Time | Order::Field(path)).page(n)) -> Live<Vec<Hit<T>>>`, things in the group (transitive) carrying the aspect, paged, with `Hit { tid, value: Result<Option<T>>, ts, received }` and a watch on the result for changes in the visible range (a chat timeline, a feed, an inbox).
- `db.backlinks(tid) -> Live<Vec<(Tid, Ak)>>`: things whose values reference the tid.
- Later: filters over values (unread, by actor, by tag) and counts, live; text search. Indexes are local, rebuildable, sharded per aspect (notes/local-store.md).

## Sharing and roles
Synchronous unless noted; each is one role commit made locally (spec/permissions.md §2), delivered by the sync layer. Nothing here assumes a role has one answer forever: admin disputes are settled per node (below).
- A thing's first grant (`grant`, `make_link`, `add_with_grant`) makes its secrets of its own and its sync ID in one commit (spec/sync.md §2): every holder of a role can then sync it, and sharing a local-only thing syncs it among the sharer's own nodes too. `grant` never waits and never lowers: lowering an admin's grant is the holder's departure, whose rotation only a demotion carries, so it takes `set_role`. What a grant does take away (a lower `may_grant`, a role below one the holder lost by leaving or a finalized `until`) it takes as `set_role` would: every admin's grant that audits (spec/permissions.md §5.1 step 4) carries this node's frontier (`Engine::grant_signed`). An invite grant audits nothing, so until the edge is out of the state it is `Permission` (over a higher ended grant it is that grant's departure, whose rotation it cannot write; spec/permissions.md §2). The holder's admins learn of it through its inbox, its home sync ID. `db.sync(group, &[Address])` makes a group's sync ID with no new holder (admin; a no-op when it syncs, unless the list names others: `Invalid`); a sync ID stays for its thing's life: a share stops by removing its holders.
- `set_role` writes at once (Demotion and addenda, below). Every way in it will remove is found before anything is written, so its refusals write nothing (`change_role`). A joiner by a link of this account is removed with the link key in one commit (`revoke_joiner`, one rotation): chat's kick and the one route to remove a joiner, whose role cannot be set (it could act as the link key; the joiner may keep the seed, spec/permissions.md §7). `retain_copy: None` fills from `RequiredRules::retain_copies`, written as any required rule, no call of its own. Removing an ended grant before a lower one says retain or erase by the thing's default, harmless: the role lost already dropped or kept the copy, and the new role ends a copy and brings the data back.
- `leave` is a self-removal with no pre-sync and so no rotation (the target's next writer or admin rotates); `me()` also an admin of the target is an explicit removal, and rotates. A link's K has kind `Link`, `through` is `[K]`, so a link to a team the holder reaches through is the team's business. A link's maker holds through K too (K's record edge), so its leave ends its admin of K: the link keeps working, and with K's only admin gone the target's admins end it by removing K from the target; sparing that way would leave the maker its role, no leave. The main actor's only: the flow runs on the node's authority, not a client's actor. A give-up call belongs with it (issues/api-leaving-give-up.md).
- Tied grants (spec/permissions.md §2, notes/tags.md Sharing a tag): `add_with_grant`. `GroupWrite::remove` removes the tied grant after the commit when that is a self-removal (`Osis::untie_now`), else node-sync's obligation does. The stored tie names the membership's element; `add_with_grant` on a tied grant whose element is gone ties it to the live one. A `with_membership` grant whose thing is no longer a member is on its way out.
- `holders`: `kind` is what the actor's creation record fixes (a share view: `Actor` with `through` empty or a single `Link`; a link that works: `Link` with a `Key` through it; both read alike on every node holding the target, spent or not). Breadth first; one entry per grant by the shortest way to it, and again by a longer way that gives more. O(grants below × distinct ways that beat each other): a crafted lattice has at most one per role per distinct `until`, nothing per path.
- Nodes: pairing is transport-agnostic: the app carries three texts (`pair_offer`, `joining.request()`, `pair_accept`'s reply), request and reply authenticated by the offer's secret. A direct-connection convenience over this is later. `remove_node` is `set_role(me, node, None, ..)`, kept for what it returns: the account's working links, whose seeds the node keeps (notes/permissions.md Links).
- Links (per call: `share.rs`). A `direct` link carries this node's dialable key and relays, never `reach.0`, so a redeemer with no common peer reaches it (notes/networking.md First contact). `redeem` returns only once the join is at a source of K (holding the link key till then: notes/networking.md First contact) and the thing is here, the latter because reads are local and absence reads `None`: a read cannot tell "not here yet" from "absent", so a read saying "not synced yet" is no alternative. A link to a thing this account already reaches for good (by grants with no `until`, as a join gives) at the link's role or above joins nothing (`share::reaches`). Anything that cannot be judged waits until dropped, as the edge may be on its way from the maker's node (a link naming the wrong target waits too: an app's timeout says "could not confirm, retrying is safe"); `import_contact` asks the same edge, the same way. Single use is in the link (`flags`, spec/wire.md §10): the redemption removes the link key and node-sync on any sharer node finalizes it, and an expired link, after a complete pass of K's labels (`SyncEngine::finalize_links`; the seed thing is an item of the home group so every node holds it). Bearer read (`Osis::open_link`) is not built (issues/api-deferred.md).
- Invite requests (spec/sync.md §3) are not watchable yet: an app polls (e.g. on status changes).
- Disputes (spec/permissions.md §5.1 Trust set, §5.4; notes/disputes-plan.md step 4): each node settles a fight for itself. `Dispute::Removal` between admins: by default the side its own role exists on, else whichever removal it held first (`Side::Author`, `Side::Holder`). `Dispute::Account`, an account's forked history, listed only in doubt: by default the version it received first, a side being a `Side::Version` (the change it ends in); the account's own devices follow their device list and are never told. Plain calls on `Osis`, per node, never a data write and nothing on `Write`. Finding one costs a walk of the role history per contestable removal, so the list examines at most 64 and counts the rest.
- Entitlement: holders read what the group (or an actor in it) holds a role on, record edges included; a thing whose first admin is `me()` added to a shared group stays unshared (notes/sync.md). Shared things take the group as first admin.

## Sync configuration and status
- `Address` = transport URL plus a node's key (`FromStr`/`Display`; a `quic://` URL without a port is kept as `:4040`, so one node has one address).
- **Saved peers**: nodes serving at a fixed address; a saved peer is what a label's hosts are underneath (two kinds of peer, issues/net-one-peer.md). A change moves only what syncs with exactly the saved list, the list written first, then the inbox; a group with holders besides the account's nodes never loses its last one.
- `peers(group)` leaves out those that dialed this node and are not known otherwise. A node is reachable as a saved peer only at a stable address (issues/net-one-peer.md).
- `reach.0` goes under every synced group (IP consent, notes/networking.md); its key changes only by `rotate_peer_address`. The home group is synced at `create`. A group's only sync choice is its source (`group_source`, read back with `group_sources`): at a node, this node holds what it had but does not sync it, and back home it syncs again.
- **Status and waits** judge one set per sync ID: its **sources**, the hosts connected now with it open and the readers whose connection shares it, whoever dialed (`SyncEngine::label_status`). Nodes known but not connected decide whom to dial, never what is true now. A host is caught up when this node's own pass with it ended with nothing outstanding and nothing changed since; a reader when this node's stream from it is read to its end with no body asked there and the reader reported applying this node's log of the sync ID to its end (notes/peers.md, Reports and status).
  - `SyncState`: `Synced` (at least one source, each caught up, and no connection still finding what it shares), `Syncing` (at least one source, some not caught up or a connection still finding; a reader is caught up once this node pulled its log to the end and the reader reported this node's log to the end, so a fresh write is `Syncing` until a source has it), `NotConnected` (none, whether or not a node is known for it), `Refused` (none, and a connected saved peer of it answered code 14: `refused_by`), `Stranded`. A group sourced at a node shows that node's status for it, and is absent while that node cannot be asked (`node_connections` shows it down): status answers for where the group's calls go, and this node's copy never does, as for reads. A group shows the worst of its live sync IDs (a replaced one with no peer does not count). `last_sync` is when the group was last `Synced`, in this run. `leaving` (`drop_left`) lasts until a source has the removal: with nobody connected it stays. `connected` counts sync connections either way (a client's session is none).
  - **Readers are counted by identity, never by connection.** Connections whose proven node (`Proven::node`) is one count as one source, caught up when any of them is; a connection naming no node counts on its own. Two connections to one peer close down to one anyway (notes/peers.md, One connection per pair). `Refused` means a saved peer: issues/net-shared-set.md's judged holder replaces it.
- `wait_synced` resolves once every live sync ID in scope is `Synced` and every delivery in scope was taken; otherwise it waits, nobody connected included; it fails only on what is known never to finish (`Stranded`, or a `Thing` held only as a log). `All` is every synced group and every delivery, so a home group with nobody connected keeps it open. `Thing(t)` waits on what `t` travels under: every sync ID of `t` itself or of a group whose closure holds it that has at least one source (`SyncScope::Thing`), plus the deliveries about `t`, what it holds or those groups; with no source on any it waits, and a sync ID with no source never holds it up while another has one (a sync ID with no source promises nothing). It also ends once something carried `t` when it began, nothing does now and this node holds no role on it: it forgot `t`, by a leave that landed or a removal. `leave` waits on `Thing(t)`, `card show` on the profile's. `Deliveries` is only this node's pending deliveries (inbox blobs), for delivery-only commands. A commit for a node over a direct connection is no delivery in any scope: only pairing carries one, so a grant to a node outside pairing is recorded with no route (spec/sync.md §2) and nothing waits on it. `wait_synced` syncs every label first (`SyncEngine::sync_now`), and a delivery whose inbox lists no node (`SentInbox::nowhere`) stays pending, resent at `INBOX_LIFETIME`.
- `Commits::complete` is false while a pass of a sync ID carrying the address is unfinished or about to run at a connected node, or before this node first finished a pass there. A sync ID this node made counts as finished, even when another node wrote under the group first: what those writes need is that node's own pass, and until then no gap is known here. Like `Synced` it says nothing of nodes not connected; unlike it, it stays true offline.
- Serving (notes/serving.md Hosting in the node): `Serving` writes the node's `host^.0`. `ServingPolicy` is the plain limits; the others are `internals::host_limit`, by name. `SyncId` is an opaque label ID kept to this one purpose: `sync_ids(group)` is the only way to ask. With `Own`, the node serves its account's own groups (record chain through the account; no grant counts, since grants need no consent) once their saved peers name its address; someone else's group, even one it reads or administers, takes `Open` or its id in `admitted`. A serving node's `serving_address` is in its `saved_peers` (`Osis::upkeep_serving_peer`, the address it added kept in the `serving_peer` record), so it learns its own groups as any node does. The CLI's `serve` is these calls.

## Diagnostics
A place to dump problems such as a colliding record from a peer, rejected writes from a revoked actor, a thing created into an unsynced group, a thing whose sync is stranded. Apps may log, surface or ignore it; correctness never depends on anyone seeing it.
- `Diagnostic` (`core/osis/src/diagnostic.rs`, translated from the engine's kinds, which the port keeps carrying) has a variant per thing an app can act on, and `Handled` for the rest (bad, parked, pending, colliding, repaired data: log material). `Parked` is never constructed yet (issues/parked-diagnostic.md).
- A peer must not be able to flood it: dedupe per (kind, tid), rate-limit per peer.
- Must include: "this node was removed from actor X by node N at time T" (a stolen node's removal otherwise looks like a silent lockout) and "stranded on group G" (also in status).

## Errors
`core/osis/src/error.rs`. Peer-caused problems never surface as errors to the app; they are diagnostics.

## Typed reads (decided; spec/versioning.md §5)
A typed read (`at().get()`, `on_change`, path reads) of a stored value with an unknown enum case (a newer version's), a type mismatch or a missing required field reads as `None` and reports `Diagnostic::Mismatch` (the thing; detail: AK, path, reason; deduped per (kind, tid) like every diagnostic). Tess's direction: synced data is other writers' input and an app cannot act on an error, so one odd thing must not fail a screen read with `?`; one read call, no lenient variant. Per-path reads let an app read the good elements of a collection with one bad element. The untyped `Value` API always shows what is stored. App types are views over the wire type, generated or hand-written; transitions and the form-choice policy are codegen conventions (notes/versioning.md). Codegen warns on `list<struct>` aspects (records edited concurrently belong in `map<K, struct>` or get path ops: the list diff pairs changed entries in order and a misaligned pair loses concurrent edits).

## Attribution (Tess's decision)
The API reports only verifiable authorship: who wrote something and when comes from the signed header of a commit held here, never from a claim another commit makes (a compaction snapshot vouches for its carried writes without naming their authors). No API type carries an "unverified" flag; what cannot be verified is not reported.
- A listing shows the commits held here, each with its own header's author and `ts` (a snapshot as itself); commits known only from a compaction snapshot have no entry. A watch's `Origin` names the commit applied: a snapshot arriving is reported as itself (its author, ID and `ts`). A valid snapshot's copy of a held original joins with it by the copy order (spec/permissions.md §5.2): where the read changes, the change has the snapshot as `Origin`, while a listing and `changed` still name the original's commit as the change it was (snapshots are no change).
- No per-write attribution call exists yet; any future one follows this rule: a value known only from a snapshot reports the snapshot or nothing.
- Required retention: `w.at(t, core::REQUIRED).set(&rules)` (an admin; `RequiredRules { rules: BTreeMap<Ak, Required { retention, expires: Option<Duration>, refuse_replace }>, default: Option<Required>, retain_copies }`, keyed by a generated key's `Aspect::name()`, wrappers over `core_types` with one wire form), `osis set T required^.0 V`, no API of its own. `default` governs every aspect not in `rules`. After it the writer's node fills that retention and expiry and an override errors. A writer that has not seen a change writes under the old rule and its delta turns invalid once it arrives: its node reports `DiagnosticKind::OwnWriteInvalid` (the app writes again: `osis chat resend`). At most `MAX_REQUIRED_ENTRIES` entries in `rules`. Set it before granting anyone: a member from before a change can backdate below it.
- Provable authorship of every write (audit trails): give the aspect `Retention { history: Some(History::FOREVER), .. }`; its bodies are then never compacted away, so each write keeps its signed original.

## Demotion and addenda (decided)
A demotion is stamped at once with the demoting node's own receipts as its frontier (notes/permissions.md, Revocation); nothing in the API waits before it (`set_role`, `revoke_link`, `remove_node` and so a chat kick are synchronous; no `_now` twins, no CLI `--now`). What the frontier leaves out survives where another writer had received it by the removal's `ts`: every writer node answers an applied removal with an addendum per thing (spec/permissions.md §5.2), the demoter's own node for what its frontier left out past the list bound. Lost: edits that reached no writer in time (an offline device, a reader or a host alone); a re-grant brings back only those some node still holds. The documented way to keep more: `wait_synced(SyncScope::Thing(target))` under the caller's timeout, then remove regardless (crate docs, Sharing); the unsynced-group case is protected by that advice alone, and `status` shows such groups `NotConnected`/`Connected`. Rejected: a timeout in the API (`Try(d)`: the caller's runtime does it), a pre-sync inside `set_role` (made removal slow by default and still could not close the gap), `Backdate`, a "cut access only" removal (`until` = now leaves a permanent backdating window), third-party receipts for role writes (they fail the fixpoint model).

## Footguns closed (keep them closed)
- Read-modify-write clobber (a form saved with `set` wipes a tag another node added meanwhile): `edit(base, new)` and path ops; docs steer every interactive edit there.
- Out of memory on an unexpectedly large value: the materialization bound fails explicitly; streaming and path reads exist.
- A thing that never syncs: membership a group op, a member of a group whose own aspects sync but whose items would not fails, `NotSynced` diagnostic for node-local memberships.
- A member lost silently: a thing becomes a group with its first member.
- `set` losing a repeated message on a log: its doc says so, and `overwrite` is named for always writing.
- A deleted thing reading as present (an editor left open on it): `has_content` is false once no content is left; deletion is derived, never a flag.
- A forgotten unsubscribe: RAII `Subscription`.
- Missed change between read and subscribe, and a callback invoked on the registering thread once and the dispatcher thread later: atomic `on_change`, initial call through the dispatcher.
- Writes a node is not allowed to make, emitted and un-merged elsewhere later: rights checked locally at commit.
- `async` reads forcing a runtime into GUI apps and hiding that nothing waits: synchronous data API.
- Per-keystroke commits (13 bytes forever each): the text session.
- A role lowered without syncing what the holder wrote: other writers' addenda keep what they received; the caller may `wait_synced` first (Demotion and addenda).
- Concurrently edited records in a `list<struct>`: codegen warning, path ops.
- Deadlock or reentrancy inside callbacks: no callback under a lock, any API usable from a callback.
- Secrets in the API: none; the link seed only in the link.

## Rejected shapes
- Everything `async`: local operations never wait, and every GUI would carry a runtime; browsers are served later by a worker-backed synchronous store.
- `ListenerId` cancellation and a callback invoked before `listen` returns.
- An entity/ORM layer typing whole things: aspects belong to different schemas and apps; per-aspect typed keys fit the model.
- Auto-subscribing reads as a thread-local or ambient context (a read registers a listener because of where it runs): hidden; tracking is a handle the caller makes (`db.tracking(&set)`), so what subscribes is visible in the code.
- `set` diffing against the app's last read implicitly (state hidden in the handle): `edit` takes the base explicitly.
- Exposing links or a `Value::Large` variant in untyped values: the bound plus `stream()` keeps values plain.
- A default membership.

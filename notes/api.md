# Rust API
> Summary: The shape of the `osis` crate as it stands: a synchronous local data API (typed aspect keys, `at`, RAII subscriptions, a `Write` that is one commit or refused, `set`/`edit`/`overwrite`/`remove` and path ops, `fire` on a signal (value and signal keys told apart at compile time), the acting actor as first admin, membership by `w.group(g)`, ephemeral aspects in memory, rights checked locally, bounded materialization), signals, commit listings and listeners with undo, redo and revert, backlinks, lifetimes (`RETAINERS`, `retaining`, `release`), text sessions, the sharing and sync surface (async only where another node is waited on), serving, diagnostics; why each is so; rejected shapes.

## Rules
How to judge this shape, and the standing rules: notes/api-design.md.
- Vocabulary (spec/requirements.md Terms): thing, aspect, group, member (what a group contains), holder (who has a role), actor, role, node, peer, serving, account. Below the API, "label" is a sync ID and "host" a saved peer; neither appears in anything public. Engine, `osis-host` and spec rule text keep theirs (issues/net-rework.md); every old word left, the API's own `saved_peers` and `SyncId` included, is in issues/deprecated-terms.md.
- Decided words (Tess): **ephemeral** is for `+` aspects. `Tid` and `Ak` stay, and an aspect key is the whole string; a domain word plus a generic one is fine (one concept under two terms is not). "Keep" splits: a removed holder's copy is retained, `keep_alive`, `History::Keep`. History: no promise is the default and unnamed (`history: None`), the delete-on-change mode is named for what it does (`History::PurgeOnReplace`, documented as costing more per change and rarely right; public docs never say compaction). "Invite" is an incoming request from a stranger; a grant's is `may_grant`. A role says who may, `sync` where the data goes (`grant` and `share` not bundled: revisit if the app finds it awkward).
- Undo: per actor by default, plus a view of every change in scope from which an admin may revert others' (notes/crdt.md).
- Async futures resolve by a channel from the handle's background runtime (tokio by default, or a `Handle` the app passes).
- Internals: `osis::internals` (doc-hidden, `core/osis/src/internals.rs`): the CLI's `inspect`, tests, sim and benches, never the app or chat. Generated code has its own narrow path, `osis::generated` (`use osis::generated as osis_schema;`). A feature gate is ruled out (notes/build.md Feature unification).

## Handle and lifecycle
- `Osis: Clone + Send + Sync`; clones share one node, which closes with the last handle (drop is fine; `close() -> Result<Close>` returns `Close::Closed` once closed and its sync driver is gone, or `Close::StillOpen{handles}` at once while other user handles exist: clones, upgraded `WeakOsis`, value streams, text sessions, a `Joining`). One account per store.
- `Osis::create(Store, &[Address], Config) -> Osis`: new node, new account (this node its admin), its home group synced with the peers given. An account is reached again only through another of its nodes (recovery: issues/recovery-redesign.md). `Osis::open(Store, Config)`; `Osis::pair(Store, &[Address], &PairOffer, Config) -> Joining` (Sharing and roles, Nodes).
- `Config` and `AppConfig` are all defaulted. `direct_sync` off syncs with saved peers alone (tests use that). `lan` (`Lan::On { also_announce_to }`, the default with no extra targets, or `Lan::Off`): whether a node with direct sync is on its local network; targets are for what a broadcast cannot reach, such as a routed mesh. A relay is a node at an address, so `Address` (`peer://` only). No transport to choose: QUIC, in-process endpoints only for tests. A thin client takes `AppConfig` alone. Without a runtime everything local works; calls that wait for another node fail `Network`; peers given with no runtime are `Invalid` (a store's own saved peers stay allowed: the CLI's local commands, whose writes go out with the next networked one).
- Clients (words and policy: notes/client-port.md): `db.has_store()` tells a node's handle; a node may be a client too (`connect_node`). `async Osis::connect_socket(store_dir, AppConfig)` is a thin client on the node's unix socket, offered unauthenticated to the node's own user as its main actor: `me`/`node` are the node's, tid-addressed calls go there, process-wide calls the port does not carry are `Unsupported`; `listen_socket()` serves it (needs a runtime; a store in memory has no socket, `Invalid`; test harnesses: `Internals::listen_socket_at(path)`). A localhost or network listener lets a client act only as actors it has authenticated for (a credential naming its actor may come later: `NodeLogin` grows; `WHOAMI` already says who a client is).
- Clients with an actor of their own (notes/client-port.md §3): `add_client`, then `Osis::connect(&[NodeLogin])`, a thin client answering as one actor: `me()` its actor, what it may not read is unknown, writes by its rights, grants to the actor are what it reaches; sharing, sync and process-wide calls are `Unsupported`, but for `holders` and `leave` of its own actor's grant.
- Group sources (notes/client-port.md §6, §8): `connect_node`, `group_source`, `Status.two_sources`. A disconnected source is `Network`, never another's answer.
- Identity: `node() -> Tid`, `me() -> Tid` (the account: author of its writes, holder of its roles), `home() -> Tid` (the private group every node of the account syncs).
- `now() -> Result<Time>` (`Time`: milliseconds since the epoch, the one public time type): the node's wall clock, which commits are stamped with (never moved by other nodes); on a thin client its node's, `Network` when it cannot be reached.

## Keys: typed aspects and signals
- `AspectKey` is what the API takes: generated constants and `DynamicAspectKey`, never a bare name (each has `name()`, its `Ak`); `RawKey` beneath it is osis-schema's, doc-hidden, what the engine takes (`Ak` too). Generated constants (`notes::BODY: Aspect<Markdown>`) carry AK, schema, defaults and codec. `DynamicAspectKey` (`Osis::aspect_key(name)`, typed by a schema registered at run time) says what an app needs without the schema: `name()`, `value_type() -> Option<NestedType>` (`get()` its shape, `name()` its declared name), `default_retention()`; `DynamicAspectKey::untyped(ak)` is `T = Value` with no schema (no validation, core default retention). A read through a typed key cannot be mistyped; a write through one is validated against the writer's schema (every declared field required, spec/versioning.md §5). Nothing about the schema goes on the wire.
- **Two kinds, told apart at compile time** (which calls each takes: notes/listener-design.md Key types). Codegen emits `Aspect<T>` for a value aspect and `Signal<T>` for a `~` key (`Ak::check` in the constant fails the build on the other marker); a trait on the key (`ValueKey`, `SignalKey`; `DynamicAspectKey` has both) bounds the calls, so a crossing on a generated key does not compile (compile-fail doc tests in `core/osis/src/keys.rs`, one per pairing). Through a `DynamicAspectKey` the kind is known only at run time: a crossing read answers by the rules, no error (a signal's `get` reads absent, its `writes` list nothing; a value aspect's `fired` lists nothing), and a crossing write fails `commit()` with `Invalid`: a write never silently does nothing. History is not in the key: whether a write is kept is its thing's `retention^.0` setting.
- `ValueType` (`core/osis/src/value_type.rs`): a plain description for code handling aspects it was not generated for (the app's forms, the CLI's value text). Types may be recursive, so what is nested is a `NestedType`, one level per ask. `Schema` itself is not API.
- Markers (spec/data-model.md §2), independent and read from any key's name: `Ak::ephemeral()` (`+`: held in memory, never in durable commits), `Ak::admin_only()` (`^`), `Ak::signal()` (`~`: no current value, only fired); no schema flag; `RawKey` has the same three. A value that lives while its author is there: `at(t, k).path(p).keep_alive(&v) -> KeepAlive` (`at(t, k).keep_alive(&v)` for the whole aspect, typed) on an ephemeral key, with a default expiry (notes/ephemeral.md Values that live while their author is there).
- `osis::core`: only what apps truly read and write by key: `NAME`, `BODY`, `TAG`/`Tag`, `RETENTION`/`RetentionSetting`/`RetentionEntry`, `RETAINERS` (Lifetimes). The rest (`GROUP`, `ROLES`, `CREATED`, ...) is through calls (`members`, `grants`, `created`), and `internals::core_types` for tests.

## Reads
- `db.at(tid, key) -> AspectRef<T>` with `.get() -> Result<Option<T>>`, `.path(p).get::<U>()` (`U = Value` for untyped; a typed key's whole stored value: an untyped key), `.path(p).stream() -> Option<ValueStream>` (a string or blob of any size: `Read + Seek`, its `len()` known without reading it), `.on_change(f)`, `.path(p).on_change::<U>(f)`. Values are snapshots: plain `Value` or generated structs, nothing reactive inside.
- Every read returns `Result` (a node that cannot answer is `Network`, never a default); what each call means is in `core/osis/src/read.rs`. Deleted and never written are not told apart: `has_content` is false for both; deletion is derived, never a flag. `groups_of` reads the in-memory group index rebuilt from the definitions at open, nothing scanned. No call reads a thing's first admin: it is history, and gives no power once its edge goes. `role_on` has one rule for every route to a role (`Engine::usable_role`; spec/crypto.md §7).
- A thing's times (`created`, `changed`) are shown and sorted by `shown() = min(written, received)`, feeds too: one skew rule (an author's clock may run ahead, by at most `MAX_DRIFT_MS` before its commit is parked; `received` is this node's clock), no app-written time field. `changed` reads the in-memory commit index, newest `ts` first per aspect, stopping once `ts` is at or below the best `shown()`; a commit known only from a snapshot is not seen (Attribution), so after compaction on a new node it may read older than the truth.
- **Read limit**: a value whose canonical size exceeds `AppConfig::read_limit` fails `Error::TooLarge { limit }` (the bound: a length is unknown without reading) from `get` and any typed read; read it by `stream()` or by path (a path read into a huge map or list costs O(entry) and never loads the whole).
- `Path`: steps `Field(id) | Case(id) | Key(Value) | Index(usize) | Elem(Value)`; `p![..]` builds one from literals and generated field/case constants (`task::DONE`).

## Watching
- `db.at(tid, key).on_change(|db, c: Change<T>|) -> Result<Subscription>`: taken atomically with the current value, so no change is missed between read and subscribe; the callback runs once with that value (`Origin::Initial`) through the dispatcher like every later call, then on every change. Async code forwards it to a channel of its runtime and awaits that (crate docs); no second watch type (Tess).
- `.path(p).on_change::<U>(f)` is the same listener at a path of any depth and type, reading what `path(p).get::<U>()` reads, called when the value there differs after a transaction from its last call (calls coalesce), whatever caused it: a write to map entry `a` calls the listener at `p![a]`, not the one at `p![b]` (each listener on a written aspect reads its own path, O(the value there): `Reader::get_path` over `Engine::get_at`, which loads only the pages on the path). A path the schema lacks fails `Type` at registration. A thin client's goes as Sub filter `[0, tid, ak, path]`, the node sending a Notify only when the path's value differs. No changed-paths report and no map-only watch (notes/listener-design.md). A value listener remembers a BLAKE3 digest of the last value (`watch::digest`, as does the port's served subscription), never the value, so the node does not hold every watched byte twice.
- `db.on_thing_change(tid)`: all aspects of a thing (`Change<Value>` names the AK); a delete, local or remote, reaches it as its aspects going absent, with `has_content` reading `false` in the callback (no deletion event: a thing is deleted exactly when it holds no content). `db.on_grants_change(thing, ..)` (its callback takes `Result<Grants>`: a lost connection is told), `db.on_status_change()` (takes `Status`: an unreachable node shows in it, so nothing fails). Each returns `Result<Subscription>`, `Network` for a thing or its grants at a node that cannot be reached now.
- `Change<T> { tid, ak, value: Result<Option<T>>, origin: Origin }` with `Origin::Initial | Local(Stamp) | Remote(Stamp) | Derived(DerivedFrom)` (`DerivedFrom::{ValidityChanged, Expired, Purged, Arrived, LostAccess, Recovered}`: what changed a read when no new commit did) and `Stamp { id: CommitId, actor, node, written: Time, received: Time }`. `CommitId` is opaque (`Display`/`FromStr`), ephemeral commits included. `on_change` and `Change<T>` keep the word: they are about a value changing, whatever did it, not about commits. `Stamp`, `ThingStamp`, `Commit` hold the exact hybrid time privately for ordering. `on_change`/`on_thing_change` hear nothing of a signal (Signals).
- `Subscription` is RAII: dropping it unsubscribes; `detach()` keeps it for the node's life.
- Who runs callbacks (`AppConfig.dispatch`), one per node, in commit order: `Dispatcher::Thread` (default), a thread the node starts, or `Dispatcher::Pump(wake)`, the thread that calls `db.settle()`, so a UI applies changes on its own thread (kit uses it). `wake: Arc<dyn Fn() + Send + Sync>` is called once when callbacks become due after the last `settle` began, from the thread that queued them, after it released the node lock (calling the node there cannot deadlock): it should only schedule a `settle`. `settle` serves both: with a thread it waits for it (tests), with a pump it runs everything due, including what those callbacks cause, on the calling thread (after another thread's pump in progress); inside a callback it returns at once. One implementation (`Pump::step` in `watch`), two drivers.
- **Read-only handle**: `ReadOnly` has every read (`at`, `aspects`, `groups_of`, `members`, `backlinks`, `grants`, `role_on`, `holders`, `has_content`, `created`, `changed`, `status`, `profile_of`, `saved_peers`, `writes`, `undo_target`, `redo_target`, `me`, `node`, `aspect_key`) and nothing else; `Osis` derefs to it, so a read path takes `&ReadOnly`. A write, a listener, a session, `now`, `profile`, a `WeakOsis` do not compile on it (doc test `handle::ReadOnlyChecks`). Listeners live on `Osis` (its `at` is the same `AspectRef` with them added).
- **Tracked reads** (notes/listener-design.md Every read can subscribe itself): `ReadSet::new(on_change)`, `db.tracking(&set) -> ReadOnly`, `set.sweep()`. Each read through the handle is one answer plus one listener at its own address, under the one node lock, so no write falls between them; a repeat read reuses its address's listener, moving it past what the read showed, and `sweep` drops those not read since the last sweep. A listener calls `on_change` once when its address reads otherwise than the last read, then waits for the next read. Values and paths compare as `on_change`; `aspects`, `has_content`, `groups_of`, `backlinks`, `role_on`, `holders`, `created`, `changed`, `grants`, `profile_of` re-read and compare internally; `writes`, `fired`, `versions`, `undo_target`/`redo_target` listen as `on_write`/`on_fire`, `commit(id)` filtered to `id` (a quote moves with its message alone), `status` as `on_status_change`. Addresses: a thing's aspects (`aspects`, `has_content`), its commits (`created`, `changed`), the group index (`groups_of`, `Event::Groups`), any roster or key change (`role_on`, `holders`; an `until` passing counts), which re-reads every such listener: O(role_on listeners) per role change. Commit listings listen first and read after: a write in between fires once more, harmlessly. Reads with nothing to listen to (`peers`, `group_sources`, `nodes`, `links`, `retained_copies`, `clients`, `invite_requests`, `sync_ids`, `disputes`) are on `Osis` only; at a connected node `groups_of`, `backlinks`, `role_on`, `holders`, `profile_of`, `saved_peers`, `stream` fail `Unsupported` on a tracking handle (issues/tracked-read-port.md).
- A commit answered `Err` that landed after all (notes/local-store.md Failed writes): the engine's in-place reload sends `Event::Reloaded`, and every subscription on this node's data reads again as its own deliveries do (`watch::targets`): values and paths compare and are told with `DerivedFrom::Recovered`, `on_thing_change` reads every aspect it showed or holds now, commit listeners hear `CommitEvent::Reread`, tracked reads re-read. A thin client's value and grants watches compare at the node like a node's own; its thing and commit subscriptions lapse, so the app hears one last `Err(Network)` (`CommitEvent::Ended`) and watches again, as after a move. Status, diagnostics and disputes are not told again (`on_dispute` tells finds, `disputes()` reads them). Brute force: the path is rare.
- Coalescing: a callback that falls behind sees every commit's effect, not necessarily one call per commit. A slow callback delays later callbacks, never writes or sync. A watch on a value above the read limit delivers `Err(TooLarge)` per change; the app re-reads by stream or path.

## Writes
```
let mut w = db.write();
let note = w.create()?;                                      // first admin: the acting actor; ephemeral until a durable write
w.group(folder).add(Member::Item(note))?;
w.at(note, notes::TITLE).set(&title)?;                       // make equal: structural diff against current state
w.at(note, notes::TASKS).edit(&shown, &edited)?;             // apply only what the user changed since `shown`
w.at(note, notes::TASKS).path(p![2, task::DONE]).set(&true)?; // path op
w.at(note, notes::BODY).overwrite(&body)?;                   // always a write, of the whole value
w.at(note, notes::VIEWS).path(p![]).contribute(&1)?;
w.at(note, key).retention(r).remove()?;                      // retention per aspect
w.group(folder).remove(Member::Item(note))?;
w.group(g).add(Member::Subgroup(sub))?;
w.delete(note)?;
let done: Option<Commit> = w.commit()?;                      // one commit (two: below), or Invalid naming what clashed

let mut w = db.write();
w.expires(Expiry::In(DAY));                                  // the commit's
w.at(msg, chat::BODY).set(&text)?;
w.group(other_group).add(Member::Item(note))?;
w.commit()?;
```
- Whole-value ops: `set(&v)` makes the aspect read `v` (structural diff against the current state, spec/crdt.md §9: concurrent edits inside the value survive, but a field the app did not touch is written back if it differs; `set` of an equal value writes nothing); `edit(&base, &new)` writes only the difference between what the app showed and what the user produced, as path ops against the current state (struct fields, enum case, map keys, set elements, bag values exactly; sequence edits rebased onto the current sequence by matching `base` to it, notes/crdt.md Implementation), so a remote change to another field during editing is never overwritten; `overwrite(&v)` always writes the whole value, discarding concurrent changes inside it (an equal value counts too; a map overwritten on a long aspect costs O(writes so far), a scalar stays flat; a log of events is a signal, where each `fire` counts); `remove()`. `edit` or path ops are the rule for anything a user edits while remote changes may arrive; `set` is for "the value must be exactly this" (imports, derived data). Not named `replace`: it says nothing against `set` (internals keep `Op::Replace`).
- Path ops at `.path(p)`, the empty path being the whole value: `set`, `overwrite`, `set_stream`, `remove` (the aspect at the empty path; a map entry, set element or list element: `p![k]`); list or text `splice(range, items)` (`SpliceItems`: a slice in a list, `&str` in text, `()` for nothing; a `&str` on a typed list is `Invalid`, an item of the wrong type `Type`, a backward range `Invalid`; nothing to do writes nothing), `move_range(range, to)`; set `add(v)`; bags `contribute(v)` (a counter's amount, a max or min's observation: one op). `at(k)` itself holds only `set`, `overwrite` and `keep_alive` (the empty path's, type-checked at compile time) and `remove()` (an aspect's usual end). A map entry is `path(p![k]).set(v)`, an enum case a `set` of a `Value::Enum`. Index paths resolve against local state at commit time. A path op into a map key with no live entry creates the entry (spec/crdt.md §5.6): the first reaction to a message is `path(p![msg]).add(&emoji)`, and two nodes doing it concurrently both count; a path on through a struct field or enum case is `Invalid` (it would write a partial record; `set` the whole value). An entry created by an expiring write goes at T with everything later written into it (spec/crdt.md §4.7). `group.0` field ids are `core::group::{ITEMS, SUBGROUPS}`.
- `create() -> Tid`: a new thing, the acting actor (after `act_as`, that actor) its first admin. `create_with_admin(admin)` names the first admin, needing write on it, checked locally (a first admin the same commit creates counts through its own, so a tree of new things is one commit): a thin client's way to create (its `create()` is `Invalid` at commit, notes/client-port.md §3) and a thing made for a group's holders. A new thing is plain, deriving its secrets from its first admin's, until its first grant or `sync` gives it its own; removing a plain thing's last admin is `Invalid` (spec/permissions.md §1). The record goes in the write's durable commit (one holding only records and no expiry is a role commit acting for the node), so a `+` write on the new thing is `Invalid` beside its creation (notes/ephemeral.md).
- **A thing becomes a group with its first member** (no `make_group`): the commit's first add to a thing with no `group.0` makes it one; once a group, always (emptying it leaves `group.0` present). Membership is `w.group(g).add(Member::Item(t))`, in the creating commit or later. A shared space with its own sync ID (a chat, a team) is created, given data and `sync`ed, not added to the home group: its first admin's nodes find it through the home sync ID's `label.0` cross-publish, while adding it to home copies every commit touching it (rotations with their boxes, messages) under the home sync ID too (measured 8 KB per chat removal at 4 holders; the rotation's boxes grow with scale). The app's choice, not an API default.
- A synced group carries its closure (spec/sync.md §3): itself, its subgroups at any depth as things, and their items, not its items' items; so a group meant to sync with home with its items is a subgroup of home (`Engine::enclosing` answers which groups carry a thing; `groups_of` stays membership). A commit after which an added durable thing is carried by no synced group while the target group is (an item of a synced group, no subgroup of one) fails `Invalid` naming the fix, before anything applies (`Mutation::require_synced`, on the state the commit leaves, so the same commit may add the subgroup). Removing a subgroup is not checked: whatever cuts one from under a synced group (a write here or elsewhere, its membership expiring), each thing its closure held (itself included) that holds content and no synced group carries afterwards is reported `NotSynced` (`Core::note_cut`/`stranded_by_cut`, against the definitions the transaction began with). A durable thing added only to groups that do not sync at all (node-local data, deliberate) is allowed, with a `NotSynced` diagnostic (spec/requirements.md, Offline and network).
- Expiring memberships: an add in an expiring commit makes the membership expire, item or subgroup (a disappearing message leaves its group by itself). A removal or `delete` in an expiring commit is `Invalid` at commit: not because it would come back at T (a reset outlives its expiry), only to keep the rule simple; it could go.
- `purge(tid)`: destroys the thing by purging its creation: gone at every node, later writes ignored, not undoable; any admin, as with any purge right (`Permission`); a key actor (an account) by itself. What depends on it lives on: rights through it stand as they were. A commit that creates a thing and expires destroys it at the expiry: one commit is a disappearing message. Named for the way, not the outcome (it is `purge` on the creation; `release` and expiry destroy too, so `destroy` would name all three).
- `delete(tid)`: resets every durable aspect that may hold content and removes its memberships, as item and as subgroup, in one durable commit; then `has_content` is `false` here and wherever the delete arrives (unless a concurrent write left content). Tids never die and a later write recreates the thing; no wire concept. Which aspects (`read::deleted_aspects`): present here, or written by a valid part not received yet that no held root reset stamped after it covers, so once synced a delete leaves the same reads everywhere (`remove_aspect` resets even where no state is held); never `created.0`, `retention^.0`, `purge.0`, role-class or signal ones, nor `retainers^.0` (`core_types::deletable`: a deleted thing stays judged by its list and goes once no retainer lists it); an aspect that cannot hold content gets no reset. Which memberships (`Engine::listing_groups`; notes/crdt.md, A removal covers the adds the remover saw): in every group this node may write that lists it here or holds a `group.0` part as a header only, so once synced the listing is alike whoever deleted and an add the node never heard of stays; a group it may not write keeps listing the tid, which reads deleted there. The same commit purges its ephemeral values written before it at every node applying it (notes/ephemeral.md Deletion); with nothing to change it commits nothing (`commit` returns `None`).
- Rights are checked locally before signing: `Error::Permission { tid, needs: Role }` when the acting actor lacks write (admin for role-class aspects) on a touched thing, or this node does not hold a written thing's delete keys yet (a content write, whatever its retention, and an admin's calls alike: `role_on` says `Read` meanwhile, one rule, `Engine::usable_role`); `Error::UnknownThing` when its `created.0` is not held. A write is never emitted to be un-merged elsewhere.
- **`commit()` makes one commit** over every touched thing, of any reader sets, of any size (deltas page, spec/crdt.md §8), or fails `Invalid` before anything applies, naming what clashed; the app writes several commits if it means to (Tess: never a quiet split). Returns `Option<Commit>` (`pos()` its place in a history; `None`: nothing to write). Own watches fire after the commit is durable. What clashes, judged on what the ops ask, not on what they turn out to write (`set` of the value already there counts):
  - **Expiry**: a commit has one: `w.expires(Expiry::{At(T), In(d)})` (a later call replaces it; `Invalid` at commit when not in the future), else the thing's setting's expiry for the key, else the keys' defaults, which must agree (a plain key beside a `expires(30d)` one clashes). A write into a value expiring sooner keeps its own expiry: a reaction outlives a disappearing message (spec/crdt.md §4.7).
  - **`nobody`**: only `created.0` may carry it, besides fixed retention (`retention^.0`); elsewhere `Invalid` (spec/commits.md §5). Admins may always purge.
  - **`retention^.0`** never expires, so an expiring commit cannot carry it. A thing's record takes its commit's expiry (spec/commits.md §6): one expiring commit creating a thing and writing its content is a thing that expires whole, destroyed at T (notes/expiry-creation-design.md). A purge request may expire: it then reaches only deltas expiring no later.
  - **Durable beside ephemeral beside ephemeral signal** (`+`, `+~` keys): different commits on the wire, a peer could see one alone. A creation or a `delete` counts as durable. Ephemeral ops take no `retention` or `purge` (`Invalid`); a signal takes one `fire`.
  - A **`delete`** answers to no rule of its thing's setting: its resets carry their own purgeable-by and the commit one expiry.
  - An **undo** is one commit too. It expires with the values it copies back, never at a key's default; one copying back values of different expiries (or expiring beside lasting) is `Invalid` until the sooner ones have expired and there is nothing of theirs to copy back (spec/crdt.md §4.6), so a lasting value never takes another's expiry. An ephemeral undo that copies back an expiring value goes value-less at its T, as a durable one does.
- `Write` is `#[must_use]`; dropped uncommitted it discards its ops (debug log). Reads inside a `Write` see committed state only.
- A write is authored by `me()`; `Write::act_as` sets the header's actor, and the node must hold write on that actor (else `Permission`), as receivers judge a commit invalid otherwise (spec/permissions.md §5.2), so a valid commit's actor is trustworthy. A thin client's rows run on `Osis::act_as` (crate-internal), held to the actor's own rights (notes/client-port.md §3); anonymous writing (notes/permissions.md) is later.
- Retention per aspect: `.retention(Retention { by })` on `AspectWrite` (who may purge: `Admin`, the default, `AuthorOrAdmin`, `Writer`; `PurgeBy::Nobody` only on a creation record), default from the key; checked at commit. What history keeps is the thing's setting (History setting), never the write. The API's own types (`retention.rs`) wrap the engine's `osis_schema::Retention`.
- Role-class aspects (`roles.0`, `keys.0`, `secrets.0`, `label.0`) are written only through the sharing and sync calls; `group.0` only by `Write::group` (it checks sync and cleans up tied grants); a `Write` op on any of them is `Invalid`, from a client too.

## Text editing sessions
- `db.at(t, k).path(p).edit_text() -> TextSession` (`p![]` for the whole aspect): a buffer the UI edits. `text()`; `edit(&base, &new)`: the user's change of `base` (the text the UI showed), placed in the buffer under the session's lock, so merges the UI does not show yet are kept: like the aspect's `edit`, it says what the user did, never an index into a buffer that may have moved. Cut and paste with remembered ranges is not built (notes/crdt.md).
- The session follows its field whoever writes it (notes/listener-design.md Text sessions): on a field reading other than its last committed or merged text, pending typing is committed first (the crdt rebases it), then the merged text replaces the buffer (a removed field reads empty), reported through `on_merge(|text, edits: &[Splice]|)` so the UI can map cursors (`Splice { at, del, text }` in chars, each at the text before it; `Splice::map(pos)` moves a caret, an insert at the caret going after it); its own commit's echo neither reports nor commits. So two sessions on one field share it, and clearing a draft is a plain `remove`.
- Commits on `commit()`, after `idle_commit` of inactivity, and on drop; at most one save is in flight and none holds the buffer across a node call, so a keystroke never waits for a save. A session whose thing was deleted (locally or remotely) since it was known here (at open or its own commit) never recreates it: `commit()` fails `UnknownThing` with the edits kept (they commit if the thing comes back, e.g. by an undo of the delete); drop (which then loses them), the idle commit and a merge report an `Uncommitted` diagnostic.
- This owns the "one commit per editing pause, never per keystroke" rule (spec/requirements.md, Generality).

## Signals
A signal (key marker `~`) has no current value; it is fired, `w.at(t, s).fire(&v)` (one whole value; each fire counts, an equal one too), never written (Keys). Its fires are listed by `fired` and heard by `on_fire` at its key alone: no scope lists a signal, and `on_change`/`on_thing_change` hear none. Needs write on the thing. Event-style signals should carry a sender sequence in their value (a node on several relays may see one twice).
- With `+` (ephemeral), a fire is a relay-only commit reaching only the connected nodes that read the thing, best effort, held by none (notes/ephemeral.md): `on_fire` hears it once where written and once where it arrives (`CommitChange::fired` of `Event::Commits`, since no read finds it); no page shows it (`w.commit()` returns it with no parts); through the port it is queued against `PUSH_BYTES` (a lapse past it ends the watch).
- Without it, a fire is a durable commit, each its own write, never merged, listed until its keep bound, expiry or purge (spec/commits.md §5 Signals). The writer refuses a fire the thing's setting keeps no history for (`Invalid`); undo writes nothing back for it (it reads absent before and after; a `revert` of a commit holding only signal writes is `NotUndoable { Superseded }`); purge removes one; nothing compacts it. `on_fire` is told once per transaction in which the commit reads otherwise, so a fire that leaves the listing (a kick, a purge) and comes back is told again, and one purged in the transaction that applied it is told as purged.

**Edits** (rules, limits and why: notes/signal-edits-design.md; spec/commits.md §5 Signals): `w.at(t, s).replace(original: CommitId, &v)` is a whole fire naming the fire it replaces, the write's one fire on that key, taking the original's expiry unless it says otherwise; `Invalid` at commit unless the writer would honor it (this actor's held, listed, valid fire of this durable signal, replacing none itself, the setting not refusing it: `RetentionEntry::refuse_replace`, wire `final`). Every read of a fire (a page, `commit`, `on_fire`) shows it under its own id reading its newest honored replacement, `Part::edited: Option<CommitPos>` the replacement's place (still set on a deleted message whose newest version was purged); a folded replacement is never listed or heard on its own (`commit` of it is `None`; `w.commit()` returns it with no part there). `db.at(t, s).versions(id, &CommitQuery) -> CommitPage`: the fire and its replacements, each as written, paged and filtered as `fired` (nothing for a replacement or a non-fire), with no listener of its own (the port refuses a `Versions` filter). `purge(Purge::Commit(id))` of a fire names every replacement held here too (`Engine::claims_on`); `replace` plus `Purge::Commit(original)` in one write drops the old text. Undo writes nothing for a signal: restore by replacing again.

**One fire by id**: `db.at(t, k).commit(id) -> Result<Option<Commit>>`, any key kind: the commit as `writes`/`fired` there would list it now, `None` when not listed there. O(log n) and one body: what a reply quoting a message reads. Port `LISTED_COMMIT [address, commit id] -> Opt(commit)`.

## Commits (one model: listings, listeners, undo, redo, revert)
The design and its properties: notes/listener-design.md.
- **One `Commit`** (notes/listener-design.md The commit) for every commit the API shows: listed, heard, made by `w.commit()`, `revert`, `undo`, `redo`, named by `undo_target`/`redo_target`. `Commit { stamp: Stamp, kind: CommitKind::{Content, Revert, Role, Snapshot}, reverts, reverted_by (oldest first), in_effect, parts (private) }`; `pos()`, `at::<K>(t, k) -> Option<Part<K::T>>` (decoded then: a body not a whole value of `K::T` reads `Held(None)` with a `Mismatch` diagnostic), `parts()` untyped. `Part<T> { valid, body: Body<T>, edited }`, `Body::{Held(Option<T>), TooLarge { limit }, Purged { by, actor }, NotFetched}`; a body reads as the commit wrote it. `stamp.actor` is verified exactly when a part is valid (spec/permissions.md §5.2). A snapshot is a commit of its own kind (Attribution); a chat shows `Content`s.
- **Which parts are listed**, one rule at every address: while in its aspect's read (value-less writes included, so a purge tombstone of a live write is), or in history by the thing's `retention^.0` setting (spec/commits.md §5 The setting), or as this node's own invalid write (`valid: false`, so its user may write it again); never by what is merely held. A commit's parts are every listed part the caller may read, on any thing. Every node holding the same commits lists the same ones; undo writes back exactly these.
- **Listings**: `db.at(t, k).writes(&CommitQuery)` (a value aspect; the same as `db.writes(&Scope::Aspects([(t, k)]), q)`), `db.writes(&Scope, &CommitQuery)`, `db.at(t, s).fired(&CommitQuery)` (a signal), each `-> Result<CommitPage>`. A commit is listed at an address while it has a listed part there; a scope lists value aspects only (`Thing`/`Group`: durable ones; `Aspects`: as named, an ephemeral one too). `CommitQuery { from: CommitFrom, limit: Option<usize>, actors, kinds, reverts, reverted_by, in_effect }` (plain struct, `Default`; empty filters match all). `CommitFrom::{Newest, Oldest, Before(CommitPos), After(CommitPos)}` in that direction (Newest, Before: towards older), neither bound counting itself; `CommitPos` is opaque (`Ord`, `Display`/`FromStr`, its text sorting as places do; `at()` its time, `commit()` its commit, none for a time's): a commit's `pos()`, or `CommitPos::time(t)` (`Before` it: stamped earlier; `After` it: from there on). `CommitPage { commits, more, complete }`: a page ends early past `limit`, `COMMIT_PAGE` (256) or the read limit, and `more` says so. An unknown thing, or one the caller may not read, lists nothing.
- **A gap**: `complete: false` means a sync ID carrying the address has not finished a pass here (or only groups sourced at another node hold the thing), so commits may yet arrive anywhere: not fetched, not absent. A new node's first sync (spec/sync.md §6) is this state: role commits, then newest first, so `CommitFrom::Newest` reads real commits at once and `Before` pages older ones as they arrive; status `Syncing` until done. A node choosing not to fetch (not built: issues/partial-history-fetch.md) would say the same. What compaction replaced before this node held it never comes: that is the snapshot's commit.
- **Listeners**: `at.on_write`, `db.on_write(&scope)`, `at.on_fire`, each `(|db, CommitEvent|) -> Subscription`: `Commit { id, commit: Option<Commit> }` per commit that may read otherwise there (new, late, a part turned valid or invalid, a body arriving, purged, dropped, expired, past its keep bound), read when delivered (`None`: not listed there). `Reread`: events may have been missed (a connection to a node dropped or came back, a commit did not fit a Notify, a commit answered `Err` was found landed): read the pages shown again. `Ended(e)`: over (the source moved, a lapse): subscribe again. No initial call: subscribe, then read pages; an event repeating what a page showed is harmless. Local writes are told as remote ones are, and so is a commit leaving or entering the listing because a write replaced (or a validity change revived) its part with no history kept. A purge can list a part that had left (issues/purge-relists.md).
- **Delete for everyone**: `w.at(t, key).purge(Purge::Commit(id))`; **by author**: `.purge(Purge::Author(actor))` (deltas stamped before the request, in any arrival order; later writes stay, so remove the member too; `actor` is one header actor: an account's nodes share theirs, each thin client has its own, an invalid commit is named by the actor it claims); `.purge(Purge::All)` the whole aspect's, with its removal (on an ephemeral aspect the request alone, its writes value-less; it reads absent alike). Judged per delta by the purge rights (spec/permissions.md §6), no override; admins may always purge. Outside the chat's class a wide request's arrival-order differences are in held bodies, not reads (notes/test-properties.md). Engine: notes/engine-retention-purge.md.
  - A purge is durable, so beside an ephemeral write it is `Invalid`. In an expiring commit it takes the commit's expiry and reaches only deltas expiring no later (spec/commits.md §5): an edit purging its message's old text is one commit in a disappearing chat too; one naming anything else there, or on a thing the commit writes nothing on, is `Invalid` (the engine leaves fixed-retention `purge.0` out of an expiring commit).
  - The writer refuses with `Permission` a request whose actor's rights would drop none of the held deltas it names (`retention::check_request`, the receivers' `holds_right` on the built header; a snapshot never counts; one naming none held is written, honored when a named delta arrives). So a request needs write on the thing (no class gives a right without it), and carries a `purge.0` write so its commit has a delta under the thing's labels. The request is not listed at the purged aspect and resets nothing (a writer applying it may write a snapshot of the aspect, spec/commits.md §5 Purge): purging a register's live write leaves it absent; `set` in the same commit for a value.
  - The purged part lists as `Body::Purged { by, actor }` (the earliest request by `(ts, ID)`, its verified actor) where it would otherwise be listed, so never past its expiry; for a permanent delta that is for good and reaches new nodes.
- **Undo targets**: `db.undo_target(&scope)`, `db.redo_target(&scope) -> Result<Option<Commit>>`: the commit `undo`/`redo` would revert now, failing as the call would (`NotUndoable{NotKept}` by kept history alone, so nothing outside it is offered; `NotUndoable{Superseded}` when it would write nothing: the revert's own computation, rolled back): what a UI labels or disables its buttons by. `undo`/`redo` take exactly that, then revert. They range over the held commits valid on the scope's value aspects; relations are judged over every held commit touching those commits' aspects (a revert touches its target's aspects; one of a creation may touch any aspect of the thing a held header names, so those count for a scope holding the creation).
- **Revert**: `db.revert(id: CommitId) -> Result<Commit>` (any held content commit, durable or ephemeral; one not held, or an ephemeral commit forgotten here, is `Invalid`): a commit of the target's class naming it (wire `undoes`) with the inverse writes (spec/crdt.md §4.6: parts superseded since are skipped; nothing to write is `NotUndoable{Superseded}`; role commits and snapshots are `Invalid`). In effect: no revert in effect reverts it. Revert depth: 0 for a commit, +1 per revert (odd = an undo, even > 0 = a redo).
- **Kept history only** (Tess; the rule, its exemptions and what an inverse needs: notes/listener-design.md Undo touches only kept history; engine: notes/engine-retention-history.md; spec/commits.md §7): undo, redo and `revert` work only while every part reverted is kept by its thing's setting, held or not, and write back content only from kept history, so the answer is alike on every node, after restarts and whatever was compacted; otherwise `NotUndoable{NotKept}`. Exempt are parts needing no stored content: signals, the creation record, `retention^.0`, parts on things the commit created, and a `group.0` part that only lists things it created (`undo::lists_only`), so a creation into a group with no setting undoes. An op whose inverse restores replaced content (`osis_crdt::restores`: a register or value set, a removal, a move, a reset) needs every earlier part of its aspect kept or superseded by a kept part (`undo::replaced_kept`), so an edit older than the keep bound is `NotUndoable` by age, and one unkept part blocks every later restoring undo on its aspect until a kept part supersedes it (accepted limit). A first set undoes to absent; a redo works only while the undone write is kept. A revert reverts every part of its target or fails (`undo::undone_parts`; a body purged, expired or not fetched yet is `NotKept` too). Kit and the app write a setting keeping a day (`osis_kit::store::keep_a_day`) on the things they create, their groups and the demo data, so a `delete` and an undone creation's redo undo for a day (undoing a delete writes the thing's memberships back).
- **Undo/redo** (this actor, any node, under one lock): `undo(&scope)` reverts the newest own in-effect commit or redo (even depth); `redo(&scope)` reverts the newest own in-effect undo (odd depth) unless a newer own commit (depth 0) is in scope (a new commit clears redo). `None` when nothing qualifies; `NotUndoable` when the chosen one cannot be reverted (nothing older instead). A revert of someone else's commit counts as the reverter's undo: their redo reverts it, their undo skips it; the reverted commit's author can no longer undo it (out of effect) nor redo it (not their undo).
- Undoing a creation deletes the thing (Tess; spec/crdt.md §4.6): the revert of the commit carrying its `created.0` also does `delete`'s writes (`Permission` when the node may not write the thing, never a partial revert) and drops its ephemeral values here as `delete` does; redo (or `revert` of that revert) writes the removed memberships and content back from kept history only, never its ephemeral values. In a thing's scope, its creation is the oldest commit.
- Undo restores the read before the undone commit where only undos changed it since (spec/crdt.md §4.6 SHOULD): undoing the first write into a spot that did not exist resets the spot when it reads just what that write made it (concurrent writes arriving later are wiped); a register in a present struct stays (no nested register reset).

## Large values
- Reads materialize up to `read_limit`; above it `stream()` (`Read + Seek`, lazily fetching chunks, memory bounded to a chunk plus the tree path), `len()`, and path reads. Writes: `set_stream(impl Read)` on a `blob`/`string` position builds the chunk tree without materializing; `set`/`edit` accept in-memory values of any size. Equality is by content. Links never appear in returned values (`Value::Link` is replaced by the materialized value, or the read fails `TooLarge`); a link that cannot be read (blob not held or failing verification) reads as absent at its position with an `Unreadable` diagnostic (spec/data-model.md §6); a commit's part reads `NotFetched` instead.
- A read that missed a blob notes the aspect, a commit's read the (aspect, commit) (`Engine::missed_blob`, `Core::missed`); the next blob stored re-delivers every noted aspect to its watches (`Cause::Fetched`) and every noted commit as `Event::Commits`, and a read still missing one notes it again.

## Backlinks
- `db.backlinks(tid, &BacklinkQuery { after: Option<Backlink>, limit: Option<usize> }) -> Result<BacklinkPage { backlinks: Vec<Backlink>, more }>`, `Backlink { tid, ak }`: the things whose current values hold the tid (at any depth: map keys, set elements, enum payloads; not in a string, not in history), each with the aspect, in `Backlink` order (thing, then aspect), after `after`. A page ends past `limit` or `BACKLINK_PAGE` (256) and `more` says so; page on with its last as `after`. Shapes follow `CommitQuery`/`CommitPage`.
- What counts is the engine's reference index (notes/engine-refs.md): only data this node holds and may read, ephemeral aspects included; `group.0` is indexed like any aspect, so a group listing the thing is a backlink (`groups_of` stays the in-memory group index, which labeling reads on every change). With an acting actor (a thin client) a source it may not read is skipped. The target itself need not be known or readable: a backlink tells only what a source the reader may read already holds (`port_clients::answers` leaves it out).
- `db.on_backlinks_change(tid, &q, |db, Result<BacklinkPage>|) -> Result<Subscription>`: the page at registration (through the dispatcher), then again whenever it reads otherwise, local changes included, after the commit is durable. Woken by `Event::References` (a row naming the tid appeared or went; on once an open's first backlinks listener or tracked read asks, `Engine::watch_references`, sticky) and, with an acting actor, by any roster or key change (`Watch::Backlinks`); each wake re-reads the page. A tracked `backlinks` read listens the same way.
- A page costs O(page + sources the actor may not read) index rows (`references_page`, counted at n and 10n in `backlinks::paged_at_n_and_10n`); nothing per backlink is materialized.
- Port: `BACKLINKS`, filter `[7, tid, query]` (notes/client-port.md §2). CLI `backlinks T [--watch [--count N]]`.

## Lifetimes
Design: notes/lifetimes.md; engine: notes/engine-lifetimes.md; spec/commits.md §5 Lifetimes.
- `core::RETAINERS` (`retainers^.0`, `set<tid>`, admin-only): absent, the thing is standalone; present, it lives while a listed thing that is itself kept references it (a tid at any depth of a live durable value) or a listed thing is unknown here. No new error or type: the list is an aspect, read as any; remove an entry by a path remove (`p![Step::Elem(Value::Tid(r))]`), make the thing standalone by `remove()`.
- **One motion** (Tess): `w.at(r, k).retaining(x)` (on a value key's `AspectWrite`, beside `retention`) adds `r` to `x`'s list, and `commit` fails `Invalid` unless after it `r`'s aspect `k` references `x` (`Mutation::require_reference`, a durable row of the reference index), `Permission` without admin on `x`; nothing applies. So the entry and the reference it stands on are one call in one commit: `let x = w.create()?; w.at(r, k).retaining(x).path(p![]).add(&x)?` creates a thing retained by `r`; a move is `retaining` the new place plus removing the old reference and entry, one `Write`. It refuses rather than halves because a `Write` is one commit. A modifier naming the target, because the reference is written by whatever op the aspect's type takes (a set add, a map entry, a field); naming the aspect makes the check exact (a row is per aspect) and the target explicit (a value may hold other tids: a flag retaining every tid an op writes would need admin on each). It stands beside a plain `RETAINERS` write, which adds an entry too, because it checks the reference the entry needs (the one-way reason: at its definition). Signal or ephemeral key: `Invalid` (no live durable value); a key no op writes (`group.0`): `Invalid` at `commit`, as `retention` on one (`Write::refused`: a chained modifier never drops silently).
- **Writer's refusal**: any commit through `Write` whose own op on `retainers^.0` (a path op, `retaining`) leaves that thing known and unreachable as this node judges it now, heard out or not, fails `Invalid` (`Mutation::require_kept`, on the state the commit leaves): a list with no referencing retainer, an emptied list, a move under a thing that does not reference it. A retainer not held here keeps, so it is not judged. A writer's rule, never a receivers', so it may turn on what the node holds: refusing is the safe side, and a node holding less refuses less. Removing the last reference is not refused: that is how a retainer lets a thing go. Undo and revert writing a list are not checked.
- **`w.release(x)`**: a release request on `x` at once (`WriteOp::Release`, a `released.0` delta; `Engine::release`'s commit form), whatever retains it. `Permission` without the right to destroy `x` (the purge right over its creation, as `purge`), `UnknownThing` when not held. A release is a commit of its own: beside any other op or an `expires`, `Invalid` (spec/commits.md §5 Destruction). `released.0` is written only by it (`not_writable`). What only `x` kept goes after it by the node's own heard-out judgment, not in the same commit (a cascade judged before hearing out would release on part-received data). Never a no-op on a retained thing (why: notes/lifetimes.md API). A released thing reads as any destroyed thing: absent (`created`, `changed` read `None`, `Engine::destroyed`), wherever a thing referencing or listing it is held. `purge(x)` erases; `release(x)` reclaims (notes/deletion.md).
- Port: write ops `[12, x]` (release) and `[13, r, key, x]` (retaining), under the actor's rights. CLI: no `release` (nor a thing `purge`); the list is written by `set T retainers^.0 V`.
- Tests: `lifetimes::`, `port_clients::retaining_and_release_are_the_actors`.

## Queries (not built: a design pass first, issues/api-deferred.md)

- `db.query(Query::in_group(g).with(key).order(Order::Time | Order::Field(path)).page(n)) -> Live<Vec<Hit<T>>>`: things in the group (transitive) carrying the aspect, paged, `Hit { tid, value: Result<Option<T>>, ts, received }`, with a watch on the visible range (a chat timeline, a feed, an inbox). Its paging and listener take the shape backlinks has (a query struct with `after`/`limit`, a page with `more`, an `on_..._change` listener), or both change together.

## Sharing and roles
Synchronous unless noted; each is one role commit made locally (spec/permissions.md §2), delivered by the sync layer. Nothing here assumes a role has one answer forever: admin disputes are settled per node (Disputes).
- A thing's first grant (`grant`, `make_link`, `add_with_grant`) makes its secrets of its own and its sync ID in one commit (spec/sync.md §2): every holder of a role can then sync it, and sharing a local-only thing syncs it among the sharer's own nodes too. `db.sync(group, &[Address])` makes a group's sync ID with no new holder (admin; a no-op when it syncs, unless the list names others: `Invalid`); a sync ID stays for its thing's life: a share stops by removing its holders.
- `grant` never waits and never lowers: lowering an admin's grant is the holder's departure, whose rotation only a demotion carries, so it takes `set_role`. What a grant does take away (a lower `may_grant`, a role below one the holder lost by leaving or a finalized `until`) it takes as `set_role` would: every admin's grant that audits (spec/permissions.md §5.1 step 4) carries this node's frontier (`Engine::grant_signed`). An invite grant audits nothing, so until the edge is out of the state it is `Permission` (over a higher lapsed grant it is that grant's departure, whose rotation it cannot write; spec/permissions.md §2). The holder's admins learn of it through its inbox, its home sync ID.
- `set_role` writes at once (Demotion and addenda). Every way in it will remove is found before anything is written, so its refusals write nothing (`change_role`). A joiner by a link of this account is removed with the link key in one commit (`revoke_joiner`, one rotation): chat's kick and the one route to remove a joiner, whose role cannot be set (it could act as the link key; the joiner may keep the seed, spec/permissions.md §7). `retain_copy: None` fills from `RetentionSetting::retain_copies`, written as the setting (no call of its own). Removing a lapsed grant (`until` passed) before a lower one says retain or erase by the thing's default, harmlessly: the role lost already dropped or kept the copy, and the new role brings the data back.
- `leave` is a self-removal with no pre-sync and so no rotation (the target's next writer or admin rotates); when `me()` is also an admin of the target it is an explicit removal, and rotates. The main actor's only: the flow runs on the node's authority, not a client's actor. A give-up call belongs with it (issues/api-leaving-give-up.md).
- Tied grants (spec/permissions.md §2, notes/tags.md Sharing a tag): `add_with_grant`. `GroupWrite::remove` removes the tied grant after the commit when that is a self-removal (`Osis::untie_now`), else node-sync's obligation does. The stored tie names the membership's element; `add_with_grant` on a tied grant whose element is gone ties it to the live one. A `with_membership` grant whose thing is no longer a member is on its way out.
- `holders`: `kind` is what the actor's creation record fixes (a share view: `Actor` with `through` empty or a single `Link`; a link that works: `Link` with a `Key` through it; both read alike on every node holding the target, spent or not). Breadth first; one entry per grant by the shortest way to it, and again by a longer way that gives more. O(grants below × distinct ways that beat each other): a crafted lattice has at most one per role per distinct `until`, nothing per path.
- Nodes: pairing is transport-agnostic: the app carries three texts (`pair_offer`, `joining.request()`, `pair_accept`'s reply), request and reply authenticated by the offer's secret. A direct-connection convenience over this is later. `remove_node` is `set_role(me, node, None, ..)`, kept for what it returns: the account's working links, whose seeds the node keeps (notes/permissions.md Links).
- Links (per call: `share.rs`). A link's K has kind `Link` and `through` `[K]`, so a link to a team the holder reaches through is the team's business. A link's maker holds through K too (K's record edge), so its leave takes its admin of K: the link keeps working, and with K's only admin gone the target's admins stop it by removing K from the target (each joiner's node then leaves K by itself: notes/permissions.md Links); sparing K on leave would leave the maker its role, no leave. A `direct` link carries this node's dialable key and relays, never `reach.0`, so a redeemer with no common peer reaches it (notes/networking.md First contact).
  - `redeem` returns only once the join is at a source of K (holding the link key till then: notes/networking.md First contact) and the thing is here: reads are local and absence reads `None`, so a read cannot tell "not here yet" from "absent" (and a read saying "not synced yet" is no alternative). A link to a thing this account already reaches for good (by grants with no `until`, as a join gives) at the link's role or above joins nothing (`share::reaches`). Anything that cannot be judged waits until dropped, as the edge may be on its way from the maker's node (a link naming the wrong target waits too: an app's timeout says "could not confirm, retrying is safe"); `import_contact` asks the same edge, the same way.
  - Single use is in the link (`flags`, spec/wire.md §10): the redemption removes the link key and node-sync on any sharer node finalizes it, as it does an expired link after a complete pass of K's sync IDs (`SyncEngine::finalize_links`; the seed thing is an item of the home group so every node holds it). Bearer read (`Osis::open_link`) is not built (issues/api-deferred.md).
- Invite requests (spec/sync.md §3) have no listener: an app polls (e.g. on status changes).
- Disputes (spec/permissions.md §5.1 Trust set, §5.4; notes/disputes-plan.md step 4): each node settles a fight for itself. `Dispute::Removal` between admins: by default the side its own role exists on, else whichever removal it held first (`Side::Author`, `Side::Holder`). `Dispute::Account`, an account's forked history, listed only in doubt: by default the version it received first, a side being a `Side::Version` (the change it ends in); the account's own devices follow their device list and are never told. Plain calls on `Osis`, per node, never a data write and nothing on `Write`. Finding one costs a walk of the role history per contestable removal, so the list examines at most 64 and counts the rest.
- Entitlement: holders read what the group (or an actor in it) holds a role on, record edges included; a thing whose first admin is `me()` added to a shared group stays unshared (notes/sync.md). Shared things take the group as first admin.

## Sync configuration and status
- `Address` = transport URL plus a node's key (`FromStr`/`Display`; a `quic://` URL without a port is kept as `:4040`, so one node has one address).
- **Saved peers** (`saved_peers`, `add_peer`, `remove_peer`; deprecated with the peer list, issues/net-one-peer.md): nodes serving at a fixed address, what a label's hosts are underneath. A change moves only what syncs with exactly the saved list, the list written first, then the inbox; a group with holders besides the account's nodes never loses its last one.
- `peers(group)` leaves out those that dialed this node and are not known otherwise. A node is reachable as a saved peer only at a stable address (issues/net-one-peer.md).
- `reach.0` goes under every synced group (IP consent, notes/networking.md); its key changes only by `rotate_peer_address`. The home group is synced at `create`. A group's only sync choice is its source (`group_source`, read back with `group_sources`): at a node, this node holds what it had but does not sync it, and back home it syncs again.
- **Status and waits** judge one set per sync ID: its **sources**, the saved peers connected now with it open and the readers whose connection shares it, whoever dialed (`SyncEngine::label_status`). Nodes known but not connected decide whom to dial, never what is true now. A saved peer is caught up when this node's own pass with it ended with nothing outstanding and nothing changed since; a reader when this node's stream from it is read to its end with no body asked there and the reader reported applying this node's log of the sync ID to its end (notes/peers.md, Reports and status).
  - `SyncState`: `Synced` (at least one source, each caught up, and no connection still finding what it shares; `LabelStatus::synced`, also what the lifetime judgment waits for), `Syncing` (at least one source, some not caught up or a connection still finding; a reader is caught up once this node pulled its log to the end and the reader reported this node's log to the end, so a fresh write is `Syncing` until a source has it), `NotConnected` (none, whether or not a node is known for it), `Refused` (none, and a connected saved peer of it answered code 14: `refused_by`), `Stranded`. A group sourced at a node shows that node's status for it, and is absent while that node cannot be asked (`node_connections` shows it down): status answers for where the group's calls go, and this node's copy never does, as for reads. A group shows the worst of its live sync IDs (a replaced one with no peer does not count). `last_sync` is when the group was last `Synced`, in this run. `leaving` (`drop_left`) lasts until a source has the removal: with nobody connected it stays. `connected` counts sync connections either way (a client's session is none). Each connection keeps what its node last said of sync (`sources::Heard`): one status subscription (`filter::STATUS`) per connection, made at the first status read that meets it and kept for the connection's life, shared by every status read and listener of the process; none before its first message or while down. `on_status_change` asks no node: it merges that again at a local change, a node's message, a connection going down or up, and a change of the connections or group sources (`Locked::remerge`), and calls only when the merged status differs. `status()` asks each connection, except inside a callback, which never waits on another node: there each node's part is as of its last message, as the listener shows it. The status a node serves its own processes over the port adds no connection's groups: their calls through it fail, and two nodes sourcing groups at each other would otherwise feed each other's `connected` forever.
  - **Readers are counted by identity, never by connection.** Connections whose proven node (`Proven::node`) is one count as one source, caught up when any of them is; a connection naming no node counts on its own. Two connections to one peer close down to one anyway (notes/peers.md, One connection per pair). `Refused` names saved peers (deprecated with them: issues/net-shared-set.md).
- `wait_synced` resolves once every live sync ID in scope is `Synced` and every delivery in scope was taken; otherwise it waits, nobody connected included; it fails only on what is known never to finish (`Stranded`, or a `Thing` held only as a log). `All` is every synced group and every delivery, so a home group with nobody connected keeps it open. `Thing(t)` waits on what `t` travels under: every sync ID of `t` itself or of a group whose closure holds it that has at least one source (`SyncScope::Thing`), plus the deliveries about `t`, what it holds or those groups; with no source on any it waits, and a sync ID with no source never holds it up while another has one (a sync ID with no source promises nothing). It also ends once something carried `t` when it began, nothing does now and this node holds no role on it: it forgot `t`, by a leave that landed or a removal. `leave` waits on `Thing(t)`, `card show` on the profile's. `Deliveries` is only this node's pending deliveries (inbox blobs), for delivery-only commands. A commit for a node over a direct connection is no delivery in any scope: only pairing carries one, so a grant to a node outside pairing is recorded with no route (spec/sync.md §2) and nothing waits on it. `wait_synced` syncs every sync ID first (`SyncEngine::sync_now`), and a delivery whose inbox lists no node stays pending, resent at `INBOX_LIFETIME`.
- `Commits::complete` is false while a pass of a sync ID carrying the address is unfinished or about to run at a connected node, or before this node first finished a pass there. A sync ID this node made counts as finished, even when another node wrote under the group first: what those writes need is that node's own pass, and until then no gap is known here. Like `Synced` it says nothing of nodes not connected; unlike it, it stays true offline.
- Serving (notes/serving.md Hosting in the node): `Serving` writes the node's `host^.0`. `ServingPolicy` is the plain limits; the others are `internals::host_limit`, by name. `SyncId` is an opaque label ID kept to this one purpose: `sync_ids(group)` is the only way to ask. The groups a node reads it stores and serves whatever `Serving` says, serving or not (issues/net-one-peer.md step 4); `admit` says which others it stores: `Listed` (those in `admitted`) or `Open`. A node is reached at its one key wherever it listens: `listen(&[Url]) -> Vec<Address>` binds URLs under it (in place of an earlier call's; not persisted), and those addresses serve sync, what it stores for others and the client port alike; `rotate_peer_address` moves them to a new key. The CLI's `serve` is these calls.

## Diagnostics
A place to dump problems such as a colliding record from a peer, rejected writes from a revoked actor, a thing created into an unsynced group, a thing whose sync is stranded. Apps may log, surface or ignore it; correctness never depends on anyone seeing it.
- `Diagnostic` (`core/osis/src/diagnostic.rs`, translated from the engine's kinds, which the port keeps carrying) has a variant per thing an app can act on, and `Handled` for the rest (bad, pending, colliding, repaired data: log material). `Parked` (a commit from a newer format: an update may read it) fires once per commit as it first waits for a newer format, alone or beside other reasons (`apply::tell_parked`).
- A peer must not be able to flood it: dedupe per (kind, tid), rate-limit per peer.
- Must include: "this node was removed from actor X by node N at time T" (a stolen node's removal otherwise looks like a silent lockout) and "stranded on group G" (also in status).

## Errors
`core/osis/src/error.rs`. Peer-caused problems are diagnostics, never errors. `InUse`: `open`/`create` of a store another process holds, or a node of this process not yet closed (redb's file lock; who holds it is not known); apart from `Storage` because nothing is wrong with the store: an app must not offer to replace it (kit's start fresh).

## Typed reads (decided; spec/versioning.md §5)
Stored data never fails a read on typed grounds: a typed read (`at().get()`, `on_change`, path reads) of a stored value with an unknown enum case (a newer version's), a type mismatch or a missing required field reads as `None` and reports `Diagnostic::Mismatch` (the thing; detail: AK, path, reason; deduped per (kind, tid)). `Error::Type { path, reason }` is only for what the caller passes: a typed write's value, a path the key's schema lacks. Tess's direction: synced data is other writers' input and an app cannot act on an error, so one odd thing must not fail a screen read with `?`; one read call, no lenient variant. Per-path reads let an app read the good elements of a collection with one bad element; the untyped `Value` API always shows what is stored. App types are views over the wire type, generated or hand-written; transitions and the form-choice policy are codegen conventions (notes/versioning.md). Codegen warns on `list<struct>` aspects (records edited concurrently belong in `map<K, struct>` or get path ops: the list diff pairs changed entries in order and a misaligned pair loses concurrent edits).

## Attribution (Tess's decision)
The API reports only verifiable authorship: who wrote something and when comes from the signed header of a commit held here, never from a claim another commit makes (a compaction snapshot vouches for its carried writes without naming their authors). No API type carries an "unverified" flag; what cannot be verified is not reported.
- A listing shows the commits held here, each with its own header's author and `ts` (a snapshot as itself); commits known only from a snapshot have no entry. A watch's `Origin` names the commit applied: a snapshot arriving is reported as itself. A valid snapshot's copy of a held original joins with it by the copy order (spec/permissions.md §5.2): where the read changes, the snapshot is the `Origin`, while a listing and `changed` still name the original's commit (snapshots are no change).
- No per-write attribution call exists; any future one follows this rule: a value known only from a snapshot reports the snapshot or nothing.
- History setting: `w.at(t, core::RETENTION).set(&setting)` (an admin; `RetentionSetting { rules: BTreeMap<Ak, RetentionEntry { history: Option<History>, expires: Option<Duration>, refuse_replace }>, default: Option<RetentionEntry>, retain_copies }`, keyed by a generated key's `Aspect::name()`, wrappers over `core_types` with one wire form; at most `MAX_RETENTION_ENTRIES` in `rules`), `osis set T retention^.0 V`, no API of its own. It decides what history keeps of replaced content per aspect (spec/commits.md §5 The setting); the writer fills an entry's expiry where a write sets none, refuses a `replace` under `refuse_replace` and a fire the setting keeps no history for. Validity of no other write depends on it: a change reaches the history nodes still hold.
- Provable authorship of every write (audit trails): an entry keeping the aspect's history forever (`History::FOREVER`); its bodies are then never compacted away while the setting stands, so each write keeps its signed original.

## Demotion and addenda (decided)
A demotion is stamped at once with the demoting node's own receipts as its frontier (notes/permissions.md, Revocation); nothing in the API waits before it (`set_role`, `revoke_link`, `remove_node` and so a chat kick are synchronous; no `_now` twins, no CLI `--now`). What the frontier leaves out survives where another writer had received it by the removal's `ts`: every writer node answers an applied removal with an addendum per thing (spec/permissions.md §5.2), the demoter's own node for what its frontier left out past the list bound. Lost: edits that reached no writer in time (an offline node, a reader or a node that cannot read the thing alone); a re-grant brings back only those some node still holds. The documented way to keep more: `wait_synced(SyncScope::Thing(target))` under the caller's timeout, then remove regardless (crate docs, Sharing); the unsynced-group case is protected by that advice alone, and `status` shows such groups `NotConnected`. Rejected: a timeout in the API (`Try(d)`: the caller's runtime does it), a pre-sync inside `set_role` (made removal slow by default and still could not close the gap), `Backdate`, a "cut access only" removal (`until` = now leaves a permanent backdating window), third-party receipts for role writes (they fail the fixpoint model).

## Footguns closed (keep them closed)
Each closed by the rule named, stated in its section:
- Read-modify-write clobber (a form saved with `set` wipes a tag another node added meanwhile): `edit(base, new)` and path ops, where docs steer every interactive edit.
- Out of memory on a large value: the read limit; streaming and path reads.
- A thing that never syncs: membership is a group op checked against the closure; `NotSynced` for node-local memberships.
- A member lost silently: a thing becomes a group with its first member.
- `set` losing a repeated message on a log: its doc says so; `overwrite` always writes.
- A deleted thing reading as present (an editor left open on it): `has_content`, deletion derived.
- A forgotten unsubscribe: RAII `Subscription`.
- A change missed between read and subscribe, or a callback run once on the registering thread and later on the dispatcher's: atomic `on_change`, initial call through the dispatcher.
- Writes a node may not make, emitted and un-merged elsewhere: rights checked at commit.
- `async` reads forcing a runtime into GUI apps and hiding that nothing waits: a synchronous data API.
- Per-keystroke commits (13 bytes forever each): the text session.
- A role lowered without syncing what the holder wrote: addenda, and `wait_synced` first.
- Concurrently edited records in a `list<struct>`: codegen warning, path ops.
- Deadlock or reentrancy in callbacks: no callback under a lock, any API usable from one.
- Secrets in the API: none; the link seed only in the link.

## Rejected shapes
- Everything `async`: local operations never wait, and every GUI would carry a runtime; browsers are served later by a worker-backed synchronous store.
- `ListenerId` cancellation and a callback invoked before `listen` returns.
- An entity/ORM layer typing whole things: aspects belong to different schemas and apps; per-aspect typed keys fit the model.
- Auto-subscribing reads as a thread-local or ambient context (a read registers a listener because of where it runs): hidden; tracking is a handle the caller makes (`db.tracking(&set)`), so what subscribes is visible in the code.
- `set` diffing against the app's last read implicitly (state hidden in the handle): `edit` takes the base explicitly.
- Exposing links or a `Value::Large` variant in untyped values: the read limit plus `stream()` keeps values plain.
- A default membership.

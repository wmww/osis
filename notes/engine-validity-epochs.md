# Engine: the epoch rule
> Summary: How the engine keeps spec/permissions.md §5.4-§5.5 (`flows/account.rs`, `lists.rs`, `signing.rs`): the filter, name rows, heads and sides, `JudgedEpochs`, what a node writes.

## The filter
- Runs first in each re-judge pass (`refresh_epochs`). A role commit that does not count stays held but no timeline reads it (`Held::set_counted`, left out of `HeldSet::edge_commits`). Every other part of a commit that does not count is invalid in `Judge::part` (`created.0` aside), but a plain part a counting addendum saves (`Vouching::saves`).
- Commits held nowhere (a relay-only signal, an inbox request) are judged whole by `Core::counts_at_epoch`.
- Addenda: one least fixpoint per thing over every author (perm `Timeline::vouching`, fed each addendum's standing). Monotone: addenda save plain content only, which neither a timeline nor an epoch reads. Tests: perm `content::addenda_fixpoint_runs_through_closed_epochs_*`, `rotation::tests_account::closed_epoch_write_falls_and_a_witness_saves_it_*`.

## Names
- Thing lists (`Engine::hold_lists`; `Engine::ingest_with_lists` holds a batch's list blobs before its rotation applies) and `listing.0` deltas (`lists::note_listing`) become name rows (`tn/` commit‖thing‖source, `tb/` source‖commit‖thing). Certs stay for good (`tl/`), as role commits do.
- A name is judged once its source is held: a rotation's lists are kept before it applies (`ingest_with_lists`, own writes) and it may wait for a head not here, so `keep_certs` marks nothing due for a rotation not held; its arrival judges what it names (`refresh_epochs`, a rotation whose count moved). A listing's names are judged as it applies.
- A list for a rotation not held is not kept: node-sync keeps the entry as `Kind::List { held: false }` until the rotation arrives.
- Inner and merge signatures are kept per rotation (`ix.rotation_sigs`, persisted); merge signatures are verified at chain build (`osis_commit::verify_merge`).

## Heads and sides
- Forks stand: every head is open (`Chain::open`), and nothing is owed a rotation for being a fork. The preferred head (`Chain::preferred`, `AccountView::preferred`) is only where this node signs and its delete key; boxes to a forked account are sealed jointly at every head (`Keysets::heads`).
- The default side (preferred by `Meta::received`) is recomputed alike after a restart, so nothing is recorded. A user's choice (`Engine::choose_line`) is kept with the admin sides (`sides::Sides::accounts`, `records::SIDES`). A node of the account sides by inner signature (`AccountView::authorized_by`). The side matters only in a dispute.
- Rejected: siding with the rotations whose seed the node holds. A node removed while rotating minted a seed its siblings hold; a sibling that got that rotation first sided with it against the rotation rejecting it for good.
- Rejected: one followed head per node with a designated merger (the node with the lowest authorized head) ending forks. Writes at a head another node did not follow counted there only once merged, so every listing, the doubt and the naming waited on one device that may be gone for good (factory reset, a lost node still on the roster); merges by every node forked each other without end.
- A closer ends an epoch for the cutoff only if it descends from it or names (authorized D-list) the removal of a node the epoch's line names no removal of (`signing::ends`, `Departures`; at a witness every closer ends it). Without that, every write at a standing head made after its sibling arrived would be nameable only by its own writer, so lost with a gone writer (`the_lowest_heads_node_gone_for_good_leaves_nothing_waiting_spec_permissions_5_4`).
- The chain is rebuilt when `account_view`'s key moves (held rotations, side, seeds, own D's roster).
- Doubt is a dispute (`Chain::dispute`), told once on its rise (`Event::AccountDisputed`) and listed (`Engine::account_disputes`); never at a node of the account.
- A rotation finds heads by `at` and accepted names, never by a supersedes list, which a removed node's fork may fill. It names only the heads D's roster authorizes: naming a removed node's fork would accept it and every later fork from its epoch (`a_removed_nodes_fork_is_rejected_by_every_node_spec_permissions_5_4`).
- Authorized (`AccountView::authorized`): minted by a current node, and no rotation on its line beside a removal of its minter (`roster_epochs`: on the removal epoch's line, or descending from a later re-grant's epoch). Only counting removals and grants are read: a removed node still holds its old epochs' keys and could forge a removal of any node there, which held but uncounted would put every later rotation of that node beside it (`a_removal_that_does_not_count_puts_nothing_beside_it_spec_permissions_5_4`). A re-added node's rotation beside its old removal stays beside it. A removed node's rotation made before its removal looks like one made after; the removal's epoch is the remover's word on where its authority ends. A sibling's line built on such a rotation is rejected too (`a_line_on_a_removed_nodes_rotation_is_merged_out_spec_permissions_5_4`): naming it would accept the rotation an earlier rotation rejected, and the new rotation's own line would void it. Standing (`AccountView::stands`) drops the current-minter half: a removed node's word from before its removal.
- Nothing honest is lost by an unnamed head: the epoch rule names commits at void epochs too, so each node's listing answering the rotation that closes them saves its own writes there (`an_honest_write_at_a_removed_nodes_rotation_counts_spec_permissions_5_5`). Only nodes signing at a head write a counting listing, so a removed node gains nothing: its own fork's lists stand only in the fork window.

## JudgedEpochs
- What the rule says per account is kept in `ix.epochs` and persisted (`node/epochs`): a standing is a lookup, and an open builds no chain and reads no list. `named` holds only held commits (`unindex_commit`), so it is bounded by the store.
- `refresh_epochs` takes the accounts due (`ix.epochs_due`, from `note_rotation`; `ix.names_due`: a commit at a closed epoch, or a word naming a held commit, arrived) and judges by `osis_perm::Epochs` only the commits whose standing may have moved (at a moved epoch, named by a rotation whose count moved via `tb/`, due, and what listings among them name). So a rotation costs the commits at the epochs it moved, a list the commits it names, a write no chain build (`rotation_judges_its_epochs_once_and_writes_stay_flat`, `a_rotation_lists_its_epoch_only`, `a_listing_named_late_names_again_spec_permissions_5_5`).

## Writing (`flows/signing.rs`)
- Removing a node from D rotates the account in the same transaction (`rotate_in`; thing lists inline only).
- Every rotation applied is due an answer, a listing or addenda (`ix.rotations_due`, `rd/`).
- What the chain owes (`rotations_due`, any node of the account, none designated) is decided at the end of a complete pass of D's labels (`Engine::signing_due`, node-sync's re-seal pass), so a removal and its rotation arriving apart do not fork: a removed node's fork no authorized rotation supersedes yet (`unanswered`, once a rotation naming its maker's removal is held: rejecting earlier would reject the removal's own parent), a blocked head, or a removal no authorized rotation names that this node may name (its own, by the cutoff, or named by a standing rotation). A removal named only by a removed node's fork is not named again (`a_removed_nodes_removal_named_only_by_its_fork_is_not_named_again_spec_permissions_5_5`).
- Several nodes owing the same rotation each make one; the fork stands (`concurrent_rotations_fork_and_every_node_supersedes_them_spec_crypto_9`). A removed node's every re-fork costs one rotation per node of the account online, never a listing (unauthorized rotations are answered by the rotation superseding them).
- Pairing carries the rotations with their lists (`Package::lists`), so D's earlier commits count at the new node.
- D is sealed to its nodes only (`Core::seals_to`). A node off D's roster drops the account's seeds and what it read as the account (`signing::leave_if_removed`; lost access and retain read `Core::member`, not `me`).

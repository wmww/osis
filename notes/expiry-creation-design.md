# Expiry and creation records: design
> Summary: Design (built) of expiry by commit and of creation records. Expiry and purge take only a commit's own values; an element shows while it is not removed and holds a live value (its creation's or anyone's inside it); records with no write go (virtual anchors place alike); the only expiry rule outside the element rule is the undo writer's; `created.0` is an ordinary write taking its commit's expiry, whose expiry or purge destroys the thing (one commit is a disappearing message); a part or commit the node cannot judge is thrown out and fetched again, and what it opened keeps the keys to fetch what judges it. Also its properties, tests and open limits.

## Principle
What deletion promises, and which side purge, expiry and destruction sit on: notes/deletion.md. Destroying a thing by purge or expiry of its creation is erasure.

A write's value lives by its own commit: at expiry or purge the commit's values go, and nothing else. Removals, positions and stamps carry no app data and stay. A node keeps no part it cannot judge, and keeps only what it needs to fetch what judges it (the reading-only secrets its boxes open), fetching the rest again once it can judge it.

## 1. The CRDT rule
**Element rule** (spec/crdt.md §4.3, §4.7). An element (map entry, list element, text char, set or bag element) shows iff:
- it is **not removed**: its creation is held (valued or value-less; for a map, in its keyed record or the dot's key-erased record), no reset at or above it reaches it, and a text char's flag is not a delete;
- its **content is present**: a set or bag element's or text char's is its creation's value; a map entry's or list element's, its fragment;
- it **holds a live value**: its creation valued, or a valued write anywhere inside it (Tess's rule). Removals are not content, so an expired entry holding only someone's removal goes. Durable data always passes.

Per container:
- **Map entry.** Each keyed record holds its valued writes, and its key lives while one does. A reaction written into another's record is that writer's own write, key included. Value-less writes of any delta sit in the dot's key-erased record, which a live record reads joined. Commit 1 (expiring) creates `k` with text, commit 2 adds text: at T commit 1's creation and text move to the key-erased record and `(dot,k)` still shows commit 2's text. Value-less writes move one at a time, never the whole dot.
  - **The records of a dot are one entry**: every reset of the dot reaches each record, and a record keeps only its writes the join of the dot's records holds, as the copy that join holds (spec/crdt.md §4.8 Which write, applied to state); a keyed record's copy carries the key, so the key-erased copy yields to it. Otherwise the strip of a state differs from the join of the leftover (X creates `k` with `a = 1`, Y later sets `a = 2`: X's value-less `a = 1` is beaten by Y's). Resets reach the whole dot because a keyed reset reaching only its record was order-dependent across a forged second key.
- **List element.** A list creation carries a value: held value-less it keeps its anchor (a bit on the creation; on the wire a `Creation` marked `false`). The element shows while its content is present and, under a value-less creation, holds a live value. No element reset at T (without a creation value, a durable element emptied by nested removals would vanish).
- **Text char.** The char is the creation's value, so nothing inside can keep it. An undelete's char is the undeleting write's own value, going by that write's expiry or purge; it shows the element by that char alone, so once it goes the element hides, whether or not the creation's char is held.
- **Nested containers.** The rule applies at every depth.
- **Registers and cases.** A value-less winner keeps its stamp: it reads absent and still beats older writes (the write's implied removal of older values).
- **`W`** writes the app value "an empty composite", held value-less like a register's (`[Stamp, false]` on the wire), so an expiring `{}` goes at T.
- **Removal is final**: a newer write inside a removed element stays hidden until a sweep resets it. The hidden-write sweep resets only records a removal ended that still hold a write: a record not live for want of a value may still show when a valued write arrives.

**Leftovers at expiry**: only the expired delta's non-value writes and its value-carrying writes value-less (resets, flags, positions, creations with their anchors, value-less register, case and `W` stamps), held as the delta's leftover body until a snapshot covers them, since holders drop the body at T. No element reset, no whole-dot key move, no hidden-dot mark.

**Late nodes.** A node that never held an expired or purged creation holds others' writes in the entry without it, so it shows nothing there until a writer compacts and the snapshot carries the creation value-less (at the latest once a writer holding the leftover has been quiet for `QUIET_MS`, notes/engine-retention-trigger.md Cover once quiet). The limit spec/commits.md §5 states for non-value writes.

**Virtual anchors.** **Every record with no write goes**, in every collection (spec/crdt.md §4.2, notes/crdt.md): a seq record left with no write is placed exactly like a virtual anchor (END, by dot, children kept). An expired creation no reset pruned keeps its anchor: others placed content on it in honest flow, and dropping it would move live neighbours to END at T, a visible reorder on a common path (a disappearing paragraph in a durable doc). Invalid writes pay that cost only because they are rare. **Positions (Tess)**: expiry and purge keep an item's bare position; if that turns messy for complexly edited text or lists, weak support there is acceptable rather than a carve-out.

## 2. Expiry outside the CRDT
The only other rule is spec/crdt.md §4.6's writer rule: an undo or undelete copying back an expiring value expires no later and refuses to mix expiries. Receivers don't check it (copying back is typing the value again). A write into an expiring entry keeps its own expiry. An honest snapshot carries an expiring value value-less (spec/crdt.md §8); a forged one carrying it valued is held as its leftover at expiry, as a carrier of a purged value is (spec/crdt.md §4.7 Copies).

**Expiry in place.** Expiry is one `strip` (`Fragment::strip`, `seq::strip_values`), changes no winner, and commutes with join, so the expiring delta's leftover is stored and the state stripped in place by its writes (`apply::strip_state`, from `make_leftover` with `in_place`): only the pages its body and leftover touch load; no other body or snapshot is read. Refs follow at the delta's reach. Its cover candidate is the delta alone; its row is dated by its meta change (`leaving::date_due`). The debug `check_rebuilt` compares every expiry with a rebuild and checks every held snapshot of the aspects it reads is indexed with a bound holding each write its body holds valued.
- **Carried bound.** In place is sound only where no held snapshot carries a valued copy of the delta's writes (it would keep showing, its refs staying). Each held snapshot keeps beside its frontiers a bound of what it carries valued (`retention::snapshot::Carried`: per source, least and greatest counter of a write `Fragment::each_valued` names; noted at join, recomputed from the leftover when held as one, read from the body at an index rebuild). An expiry whose writes a bound meets rebuilds (`snapshot::carried_meets`), holding each carrier as its leftover. Honest snapshots meet an expiring write only where one session wrote valued lasting writes on both sides of it (issues/expiry-carried-hull.md).
- Still a rebuild, each rare: a bound meeting it, a part held by the list alone at its expiry (missing, or dropped other than as covered; a leftover set aside at a purge's fall adopted again), purge (its carriers are found by reading held bodies), a late copy of an expired delta (`drop_gone`), a memory leftover a held snapshot covers (`memory::drop_covered`), a forgotten memory commit (an un-merge).
- Tests: osis-engine `scale::expiry_is_flat_spec_crdt_4_7` (n lasting then n expiring commits under a snapshot: no rebuild, one page loaded and written, each peer's bound one entry), `expiry_model::forged_copy_of_expiring_write_goes_at_expiry_spec_crdt_4_7` and `forged_copy_linking_a_thing_leaves_backlinks_at_expiry_spec_crdt_4_7`, osis-crdt `expiry_laws`.

## 3. Creation records
**Throw out and revisit.** A node holds no part whose thing record, chain record or author record it lacks, nor one whose author's reach it cannot read; no tombstone.
- **Unjudgeable.** A part is unjudgeable when `thing_wait` says so (thing record, chain record, author's reach); a commit when its author's or actor's record is unknown or every part it holds is unjudgeable, judged before an epoch or `ts` ahead could make it pending (`examine`). Such a commit pends like any other, its stored copy keeping every part, unjudgeable ones included, while an entry carries it (spec/commits.md §4 Pending storage; sync's `store::follow` Carriers releases it). `reexamine` skips one whose awaited record is still unknown. A kept first copy that proves junk once checkable names the commit for redelivery (`Engine::take_redeliver`): sync opens every entry naming a blob of it again, then `Engine::redelivered`. A part of an applied commit that cannot be judged is still thrown out (`late_parts`), fetched again by `reopen_undropped` when its record comes.
- **What stays: reading-only secrets.** A box opens with this node's own KEM key, needs no record, and proves itself by what it opens: a means to fetch, not a claim (spec/crypto.md Reading-only secrets). Before discarding, the node reads the `secrets.0` boxes of what it opened (`read_pending_boxes`) into reading-only secrets sourced from that commit, within `MAX_READING*`, never encrypting under them. So an invitee opens a sync ID whose only key is in the grant while the record judging the grant sits under that sync ID. They go when the commit's last part applies, it is judged bad, or its last entry leaves (`by_commit` empties, then `forget_unchecked`). A refused box re-reads when the budget frees (`waits::wake`).
- **A part of an applied commit that waits** keeps its slot in `m.missing`, the awaited thing derived from the held header (`waits::wake` names it in `Wakes::woken` when the record arrives, for test peers; the product fetches it again only once: issues/applied-commit-unjudgeable-part.md); `settled_slots` does not count those slots.
- **What stays pending**: `with_pending`/`redeliver` for `WaitBlobs`, `Drift`, `Epoch`, `Parked` and unjudgeable commits, a row living only while an entry carries its commit. A commit carrying its author's `created.0` keeps its aspect list inline (writer rule), so no linked header needs the record it carries.
- **Limits**: an insider can exhaust the reading budget and delay honest grants until its entries leave. A commit expiring or deleted while it awaits counts as never arrived (spec/commits.md §4). A hostile k-aspect blob can cause k examinations by publishing k records one at a time.
- **Rejected**: the grant bringing the record (removes only the first wait; the author's chain is the same problem next, and it misses the home sync ID sibling route); keeping commits with boxes for this node (bytes keyed on a claim any depositor can add).

**Destruction** (spec/commits.md §5 Destruction; notes/engine-lifetimes.md Keep and forget for what a destroyed thing keeps and when it is forgotten). `created.0` takes ordinary retention (the schema's default, `admin`) and, like every delta, its commit's expiry. Purging or expiring every minting **destroys** the thing; **a disappearing message is one commit**: an expiring commit creating a thing and writing its content (spec/commits.md §6). A creating commit with no expiry and only records is a role commit.
- **Who**: any admin at the request, as any purge right (spec/permissions.md §6). Not by standing on the first admin alone: a removed admin could then destroy a thing for everyone.
- Every node drops the thing whole in the transaction that made its last minting value-less (`retention/destroy.rs`), incremental (a disappearing message is destroyed often); headers stay, as for any purge. Each holder drops what the destruction makes must-not-hold from its own store (spec/sync-judgement.md §2), and a destroyed thing with secrets of its own tells it under its own sync IDs before emptying them (spec/sync-judgement.md §5). No wait before dropping (Tess): a destruction that later falls brings the thing back only where a copy is held.
- **A minting** needs no authority, like its record (spec/permissions.md §1). A purge item on `created.0` reaches every minting whatever its `ts` (`purge::stamped_before`).
- **Nobody writes a thing after its destruction** (Tess): a part on it stamped after (`wall_ms(ts) >= T`, or after the dropping request) is a part on an unknown thing, `roles.0` and `purge.0` included, a minting excepted (`destroy::Destruction`, `thing_wait`; `destroy_thing` drops such parts already held). Honest writers refuse the same (`Core::writable`). So "a later write recreates" holds only for things not destroyed.
- **Judged by the history before it**: a request's right over a minting is judged without the edge writes on the thing stamped after it (`purge::holds_right`, a walk over `Held::upstream` while one is held and the signers could ever hold the right; a request that destroyed nothing pays it on every role pass). Otherwise the verdict cycles: a later demotion of its author makes the destruction fall where it arrived first and is dropped as written after it where it arrived second. A demotion stamped before still undoes it.
- **Limit (flagged for Tess)**: anyone holding the record may mint the thing again at any `ts`, keeping or bringing it back, live with its frozen roster: issues/destroyed-thing-reminted.md (with why mintings escape the rule above, the option closing the purge half, and rejections). The record does not carry the expiry because `Write::create` returns the tid before the commit's expiry is resolved.
- **What remains** per destroyed thing at nodes: commit headers; for a purge also the request's `purge.0` part and the record placing it (`Core::destroyed` treats the thing as unknown), kept `ROLE_KEEP` after the request with the value-less creation and `roles.0` parts, so a removal in that window can make it fall and a stale copy is destroyed again; past it the verdict (destroyed for good). A fall reopens what the destruction dropped and judges again what waited on the thing. An expiry needs nothing: every copy carries its T. Purge is per part: other things in the commit are untouched. Disputes: a side judging the purge invalid keeps the thing, and its stores keep it while the fork lasts (notes/disputes-plan.md).

**Dependents (Tess: B, authority that passed through a destroyed actor stands as its frozen history says).** Records are identity, `created.0` is existence: a record proves itself by its hash (spec/permissions.md §1). Judging a thing x needs, of each actor t on x's authority paths (first admin or granted), t's record and `roles.0` history, which travel with x. Code: `retention/destroy.rs`, `labeling/certs.rs` (`Certs`, `Engine::destroyed_upstream`), the facade's `sync/recblobs.rs` (record blobs).
- **Raw records travel**: chain certificates carry creation records raw in record blobs (`["records", [creation+]]`, spec/wire.md §3), never copies of the minting commit (which goes with its retention); inbox payloads carry them in position 3. A node logs the records its chains need that no closure body under S carries, as one record blob (`sync/recblobs.rs`). Record blobs have no commitments, so no delete key covers one: never must-not-hold but under an emptied sync ID (spec/sync-judgement.md §2); deposited ones never count toward a chain (spec/sync-ids.md §6); a promoter logs its own. A cross-published `created.0` stays a copy: it goes when the thing is destroyed.
- **Frozen history travels with its dependents**: for each destroyed actor on an authority path into a sync ID's closure (`Engine::destroyed_upstream`, a walk of held holders), the sync ID carries its record chain and every held edge write on it with write certificates, placed by the dependents' holders: as closure bodies while the group still lists it, else as certificate copies. A node that kept nothing takes a body or copy again when it opens one (`takes_late`: a part dropped by the destruction counts as never received).
- **A thing's mintings travel with its record** (whatever lets a node judge an actor tells it whether the actor lives). One minting judges destruction: the **witness** (`retention::destroy::witness`, `Standing`, `End`; ordering in spec/commits.md §5 A thing's mintings travel with its record). Every certificate set carrying a record (`cert_parts`, `Engine::certificates`, an inbox payload's raw records) carries `minting_evidence`: the witness as a header-only copy (`Certs::headers`, `header_body`; no expiry or commitments in its prefix, `osis_commit::prefix_expiry`, so it outlives the expiry it shows) and, destroyed, every held request standing over any minting (`destroying_requests`), with their authors' chains (keysets cleared).
  - **Every destroying request, not the witness's alone**: a node holding an earlier witness W (before a purge dropped it, leaving a minting the request has no right over) would otherwise read the destroyed thing live for good. Only right holders make requests, so a reader adds none.
  - **Copies under a sync ID** (spec/commits.md §5, the sync side): the witness is logged only where no entry holds a minting of the same standing; a lower header-only copy outside the closure goes once a copy of the witness's standing expiring later is there; a destroyed thing's copy that went is logged again while the sync ID needs it. So a minting again adds no copy, and every node judges by the same witness. Sync takes a header-only copy into S's required set exactly while this node's certificates name it (`minting_evidence`, the facade's `sync/bodies.rs`); the standing check and the gates below are not built (issues/sync-unbuilt.md).
  - **Why expiry gates the drop**: standings differ between views (one lacking a request ranks a minting no lower than one holding it), so two nodes could each drop the copy the other keeps; expiry orders copies alike everywhere, so the latest-expiring copy stays and reads a live thing live. Cost: a purged minting expiring after the witness keeps its copy.
  - **Why log again once destroyed**: a node lacking a request may drop the true witness for a minting a request already dropped; logging it again only while destroyed keeps two nodes from logging and dropping each other's copy for good while the thing lives (a node keeping S unread never gets the settling request).
  - Never logged where the sync ID carries the minting already (a live closure thing's minting body, a durable commit copied with parts, as an account's minting is its card's commit). A live thing's witness goes under a sync ID only from a node whose certificate set carries its record (a role holder, a promoter completing a depositor's chain, an inbox payload).
  - Erasure stays: the header carries no content (notes/deletion.md). Rejected: reads asking for a held minting (changes every raw record's semantics); a minting needing write on the thing (a writer could still forge a destruction); the witness ordered without requests (a purge dropping it beside a live `nobody` minting would show others a destruction).
- **Keys through a destroyed actor**: boxed to its frozen holders in its place (notes/crypto.md, Destroyed holder actors).
- **A thing is known by its record**: a part on a thing whose record is held and that is not destroyed is judged, and the thing reads (`Core::exists`; an invitee reads a group's `sync.0` before its creation). A node writes a thing only while it holds a minting (`Core::writable`): a raw record learned outside certificates carries no destruction. A key actor takes writes by its record.
- **What a destruction keeps**: the record, value-less creation and `roles.0` parts while a request is in its window or a held thing needs it (`Held::named_on`, `Indexes::signed` for a key actor, a lister or referencer); else nothing, re-judged whenever a needer goes (notes/engine-lifetimes.md, Keep and forget). Per node, but unobservable: a node without a dependent judges nothing through the actor, and a dependent arriving brings what judges it.
- **A key actor is destroyed** by itself (admin on itself): what it signed still verifies, its record staying wherever something it signed or is on a path of is held.
- **History opened before the dependent** (a newcomer takes the destruction with the record first): the destruction keeps nothing, then the dependent awaits the record; the facade learns the record from a record blob kept loose once something awaits it (`take_record_blob`, `Engine::promote_loose`), reopening the frozen history for fetching (`record_back`). Untested: a certificate copy of the destroyed actor opened and dropped before the dependent arrives.
- **A destroyed thing's certificates outside the closure** (frozen edges, a destroying request, a minting's header) are in S's required set while S's things need them (spec/sync-judgement.md §2; `Engine::destroyed_needed`), judged by aspect, not by the node's own drop.
- **Limits**: a node opening a live thing's record, then an expired stale minting copy, before the witness reads it destroyed until the witness opens (the destruction then falls). A record blob placed while live and the evidence placed at destruction are separate entries: a newcomer reads the thing live until the evidence opens; a rotation of the dependent it makes meanwhile boxes the destroyed actor and is judged invalid once the evidence opens, so epochs converge (by reading, untested), losing what it wrote under that epoch. A node holding a request but not the witness's copy reads a live thing destroyed from a purged copy another node kept (untested). A key actor's dependent check walks the commits. Only a dependent's own destruction re-checks the destroyed actors named on it: one kept for a dependent that goes otherwise (access lost, `retention/forget.rs`; a key actor's signed part expiring or purged) stays. A node holding a raw record but never the creation never sees the thing destroyed. Paths through a live actor outside the closure are not carried, so neither are destroyed actors reached only through one.
- Rejected: cutting authority through a destroyed thing at its destruction: the same history must travel for past writes, and everything reached through it would lose its readers and admins at once, against "things it created live on".

**`delete`** stays the undoable removal: resets content and memberships, the creation stays live, a later write recreates. Destruction is `Write::purge`, expiry or release (notes/api-design.md).

**`retention^.0`** keeps fixed retention: every node must date history by the same settings.

## 5. Properties and tests
Models first: crdt-model states the element rule (`element_rule_spec_4_7`, `map_dot_records_one_entry_spec_5_6`) and osis-crdt runs in lockstep with it; held-model states records as writes (`tests/it/spec_records.rs`, `DropWhy::Unknown`/`Destroyed`, `Outcome::revisit`/`destroyed`) and fetching (`fetch.rs`).
- Expiry changes only the expiring commit's values; a write into an expiring entry keeps its own (osis `api` tests: a reaction outlives a disappearing message, a removal does not). `strip_carried` handles snapshots alone. Matrix: osis-engine `expiry_model::expiry_takes_only_its_commits_values_spec_crdt_4_7` (text, a map entry, a list element of text and a record, either commit expiring first, either arrival order, from a snapshot, through compaction before and after T); crdt-model `text_in_an_element_expires_by_writer_spec_4_7`.
- A thing exists while its `created.0` is held live; parts on unknown things are not held; the read is a function of the held set in every arrival order of creation, writes, purge and expiry.
- Unjudgeable parts (held-model `fetch.rs`, engine `Ingested::Awaits`, `apply/waits.rs`, sync's `store/follow.rs` Carriers): a valid grant whose sync ID is reachable reads like creation-first; forged boxes never change a read; a forged grant fills only the budget; an order-0 batch refetches nothing.
- Destruction: gone at every node at T or at the purge in any order; a later write ignored; a non-admin purge falls; holders drop the blobs. Dependents: what a destroyed actor created runs on; a destroyed first admin or holder stays a chain proof until its last dependent goes; authority through a destroyed granted admin stands. Engine tests: `rotation/tests_members.rs` (`destroyed_holder_actor_boxes_its_frozen_holders_never_one_removed_before_spec_crypto_4`); the cross-node ones (the invite routes, awaiting bytes per sync ID at n and 10n, the dependents, minting copies) await sync tests (issues/sync-rewrite.md Phase 4).

# Expiry and creation records
> Summary: How expiry by commit and creation records are built. An expired or purged commit has no effect on the read (its writes removed from every body before it joins, purging brings back what it replaced); records with no write go (virtual anchors place alike); the only expiry rule outside the element rule is the undo writer's; a thing's expiry is in its creation record (so its tid), every minting's commit expires with it and only admins purge one, so a minting never extends or restores a thing (one commit is a disappearing message); a part or commit the node cannot judge is thrown out and fetched again, and what it opened keeps the keys to fetch what judges it. Also its properties, tests and what stays open.

## Principle
What deletion promises, and which side purge, expiry and destruction sit on: notes/deletion.md. Destroying a thing by purge or expiry of its creation is erasure.

A write lives by its own commit: at expiry or purge the commit's writes go, all of them, and nothing else. A node keeps no part it cannot judge, and keeps only what it needs to fetch what judges it (the reading-only secrets its boxes open), fetching the rest again once it can judge it.

## 1. The CRDT rule
**Gone writes** (spec/crdt.md §4.7; Tess). An expired or purged delta has no effect on the read at any node, whether or not it held the body: every write attributed to it (values, resets, flags, positions, creations) is removed from each held body before it joins (`Fragment::remove_gone`, crdt-model `Frag::remove_gone`), and the state is the join of the bodies so held. What it replaced reads again wherever a body holding that is held (a register's earlier value, content its reset or delete removed); purging brings back what it replaced.
- **Elements** (§4.3, §5.6, §5.7): an element whose creation is gone is not created. Others' writes nested in its record stay held and read as at a node that never held the creation; what anchors at a removed sequence element sits at its virtual anchor unless others' position or flag writes keep the record.
- **Judged by clock and requests**, never by what the node holds of the body: a node that never held it reads as one that held and removed it. A node that dropped a body as covered under a snapshot carrying the purged write cannot bring back what it replaced from that snapshot: the purge re-snapshot duty (spec/commits.md §5 Purge, `purge::owe_resnapshot`) carries it there.
- **Dropped, not held**: a gone delta left with no write is dropped (`DropFor::Other`), an expiring snapshot at its T; no leftover row stays for either. A body keeps a leftover only for the copies it carries of others' writes.
- **Dead sequence records** (deleted elements others anchor at) are held as compact range records (`seq_span`), a `ts` and an anchor each at most.

**Virtual anchors.** **Every record with no write goes**, in every collection (spec/crdt.md §4.2, notes/crdt.md): a seq record left with no write is placed exactly like a virtual anchor (END, by dot, children kept). So a removed creation moves what others anchored at it to END: accepted for expiry and purge alike (Tess: weak support for complexly edited text or lists rather than a carve-out).

## 2. Expiry outside the CRDT
The only other rule is spec/crdt.md §4.6's writer rule: an undo or undelete copying back an expiring value expires no later and refuses to mix expiries. Receivers don't check it (copying back is typing the value again). A write into an expiring entry keeps its own expiry. An honest snapshot carries no write of an expiring delta (spec/crdt.md §8); a forged one carrying one is held as its leftover at expiry, as a carrier of a purged write is (spec/crdt.md §4.7 Gone writes).

**Expiry rebuilds.** Removing a gone delta's writes does not commute with join (what it pruned is back only from a body), so an expiry whose writes superseded no held write removes them in place (`apply::remove_in_place`, O(what expires): `scale::expiry_is_flat_spec_crdt_4_7`), and one that revives a held write rebuilds its aspect from the held bodies (`apply::rebuild`), O(bodies).
- Still a rebuild, each rare: a bound meeting it, a part held by the list alone at its expiry (missing, or dropped other than as covered; a leftover set aside at a purge's fall adopted again), purge (its carriers are found by reading held bodies), a late copy of an expired delta (`drop_gone`), a memory leftover a held snapshot covers (`memory::drop_covered`), a forgotten memory commit (an un-merge).
- Tests: osis-engine `scale::expiry_is_flat_spec_crdt_4_7` (n lasting then n expiring commits under a snapshot: no rebuild, one page loaded and written, each peer's bound one entry), `expiry_model::forged_copy_of_expiring_write_goes_at_expiry_spec_crdt_4_7` and `forged_copy_linking_a_thing_leaves_backlinks_at_expiry_spec_crdt_4_7`, osis-crdt `crdt_equals_model` (removal of gone writes equals the model's, idempotent).

## 3. Creation records
**Wait, don't judge.** A node applies no part whose thing record, chain record or author record it lacks, nor one whose author's reach it cannot read; it keeps it pending while a carrier holds it.
- **Unjudgeable.** A part is unjudgeable when `thing_wait` says so (thing record, chain record, author's reach); a commit when its author's or actor's record is unknown or every part it holds is unjudgeable, judged before an epoch or `ts` ahead could make it pending (`examine`). Such a commit pends like any other, its stored copy keeping every part, unjudgeable ones included, while an entry carries it (spec/commits.md §4 Pending storage; sync's `store::follow` Carriers releases it). `reexamine` skips one whose awaited record is still unknown. A kept first copy that proves junk once checkable names the commit for redelivery (`Engine::take_redeliver`): sync opens every entry naming a blob of it again, then `Engine::redelivered`. A part of an applied commit that cannot be judged waits alike in the commit's pending copy (`pend_aside`), joined when what it awaits arrives (notes/engine-apply.md).
- **Reading-only secrets.** A box opens with this node's own KEM key, needs no record, and proves itself by what it opens: a means to fetch, not a claim (spec/crypto.md Reading-only secrets). The node reads the `secrets.0` boxes of what pends (`read_pending_boxes`) into reading-only secrets sourced from that commit, within `MAX_READING*`, never encrypting under them. So a grantee opens a sync ID whose only key is in the grant while the record judging the grant sits under that sync ID. They go when the commit's last part applies, it is judged bad, or its last entry leaves (`by_commit` empties, then `forget_unchecked`). A refused box re-reads when the budget frees (`waits::wake`).
- **What stays pending**: `with_pending`/`redeliver` for `WaitBlobs`, `Drift`, `Epoch`, `Parked` and unjudgeable commits, a row living only while an entry carries its commit. A commit carrying its author's `created.0` keeps its aspect list inline (writer rule), so no linked header needs the record it carries.
- **Limits**: an insider can exhaust the reading budget and delay honest grants until its entries leave. A commit expiring or deleted while it awaits counts as never arrived (spec/commits.md §4). A hostile k-aspect blob can cause k examinations by publishing k records one at a time.
- **Rejected**: the grant bringing the record (removes only the first wait; the evidence of the author's path is the same problem next, and it misses the route through the nearest sync ID up the record chain); keeping commits with boxes for this node (bytes keyed on a claim any depositor can add).

**Destruction** (spec/commits.md §5 Destruction). **The rule: a minting never extends or restores a thing.** The record fixes the thing's life, and every minting carries the record:
- **Expiry in the record**: `Write::create(admin, expires)` puts the expiry in the record (`CreationRecord`'s `expires`, wire field 5), so in the tid. A commit carrying a minting expires exactly then (`apply::minted_record` refuses any other; the writer sets the `created.0` delta's expiry from the record and the osis `Write` takes it as the commit's). So every minting of a thing ends together, a thing goes by ordinary expiry at its record's T whatever was minted, and no later minting can be durable. **A disappearing message is one commit**: the creating commit expires with its record, and its content with it (spec/commits.md §6). A creating commit with no expiry and only records is a role commit.
- **Admins alone destroy**: `created.0` is `admin` (`Header::validate` refuses another purge-by). No honest writer ever wrote another (the schema default; `Write::purge` needs admin), and a per-minting class let the minting's writer choose who may destroy: a writer minting with `writer` could destroy an admin-only thing if a request reached every minting, and a reader's `admin` minting kept a non-admin's purge from destroying it if it did not. With one class a request stands over every minting or none, so no minting's purge-by or author decides anything.
- **Refused while destroyed**: while a thing is destroyed, a minting of it waits as a part on an unknown thing, whatever its `ts` (`thing_wait`), so none applies and is purged after; one held before the request falls under it as any named delta. A destruction that falls re-judges what waited.
- So every held minting of a thing stands alike (same expiry, same requests): the witness is the lowest commit ID; no copy stands lower than another (sync's `rank` logs the witness or keeps a tie, nothing more).
Purging or expiring every minting **destroys** the thing.
- **Who**: any admin at the request, as any purge right (spec/permissions.md §6). Not by standing on the mint admin alone: a removed admin could then destroy a thing for everyone.
- Every node drops the thing's states and content parts in the transaction that made its last minting gone (`retention/destroy.rs`), incremental (a disappearing message is destroyed often); headers stay, as for any purge. Each holder deletes what the destruction makes must-not-hold, in its own store and at peers keeping S unread (spec/sync-judgement.md §2); the thing's own sync IDs are synced and stopped as any held thing's (spec/sync-judgement.md §5). No wait before dropping (Tess): a destruction that later falls brings the thing back only where a copy is held.
- **A minting** needs no authority, like its record (spec/permissions.md §1). A purge item on `created.0` reaches every minting whatever its `ts` (`purge::stamped_before`).
- **Nobody writes a thing after its destruction** (Tess): a part on it stamped after (`wall_ms(ts) >= T`, or after the dropping request) is a part on an unknown thing, `purge.0` included, `roles.0` not (next item) (`destroy::Destruction`, `thing_wait`; `destroy_thing` drops such parts already held). Honest writers refuse the same (`Core::writable`). So "a later write recreates" holds only for things not destroyed.
- **Judged as any request** (Tess): a request's right over a minting reads every held edge write, those on the thing stamped after it included, so a removed key's backdated destruction falls as its other requests do. So edge writes on a destroyed thing are held and taken whatever their stamp (`destroy::kept_whole`, `thing_wait`): dropping those stamped after it would make the verdict cycle (a later removal of its author makes it fall where the removal arrived first, and is dropped as written after it where it arrived second). Rejected: reading no cut on the thing stamped after the request (a stolen direct admin key, removed, destroys the thing for good by backdating).
- **What remains** per destroyed thing at nodes (Tess: destruction follows the ordinary rules, no special case): its states and every content part go; its record, gone mintings (headers and leftovers), role-class parts and the requests' `purge.0` parts stay, held by the ordinary rules alone: while the thing is in the node closure or a held thing needs it (`retention::needed`), released whole as any thing. A request is a commit carrying a purge request, kept and logged as any (lasting for a durable minting), so a stale minting copy arriving later falls under it, and a node away for any time learns the destruction from the thing's sync IDs while some node holds it. `Core::destroyed` treats the thing as unknown. A fall reopens what the destruction dropped and judges again what waited on the thing. An expiry needs nothing: every copy carries its T.
  - Rejected: a window (`ROLE_KEEP`) keeping the thing and a tid kept for good past it (destroyed for good): a carve-out keeping data by its own clock, a tombstone growing with what was destroyed, and a node away past the window never told. Purge is per part: other things in the commit are untouched. Disputes: a side judging the purge invalid keeps the thing, and its stores keep it while the fork lasts (notes/disputes.md).

**Things relying on a destroyed thing** (the things whose authority runs through it; Tess: B, authority that passed through a destroyed thing stands as its held history says). Records are identity, `created.0` is existence: a record proves itself by its hash (spec/permissions.md §1). Judging a thing x needs, of each thing t on x's authority paths (mint admin or granted), t's record and `roles.0` history, which travel with x. Code: `retention/destroy.rs`, `sync_ids/certs.rs` (`Certs`, `Engine::destroyed_upstream`), the facade's `sync/certblobs.rs` (record blobs).
- **Raw records travel**: certificates carry creation records raw in record blobs (`["records", [creation+]]`, spec/wire.md §3), never copies of the minting commit (which goes with its retention). A node logs the records S's certificates name that no body under S delivers, as one record blob (`sync/certblobs.rs`). Record blobs have no commitments, so no delete key covers one: never must-not-hold (spec/sync-judgement.md §2); a deposited one counts toward the evidence only stamped, never promoted (spec/sync-inbox.md §4); a promoter logs its own.
- **Its history travels with what relies on it**: for each destroyed thing on an authority path into a sync ID's closure (`Engine::destroyed_upstream`, a walk of the destroyed things held, `Indexes::destroyed`: rows `dt/`, kept where a destruction lands or falls and where a thing is released, rebuilt from the mintings when the index is), the sync ID carries its record chain and every held edge write on it with write certificates, placed by the holders of the things relying on it: as sync unit bodies while a strong in the sync unit still reaches it, else as certificate copies. A node not holding the destroyed thing takes a body or copy as any released thing's certificates.
- **A thing's mintings travel with its record** (whatever lets a node judge a thing on an authority path tells it whether that thing lives). One minting judges destruction: the **witness** (`retention::destroy::witness`, `Standing`, `End`; ordering in spec/commits.md §5 A thing's mintings travel with its record). Every certificate set carrying a record (`Engine::sync_certificates`, `Engine::certificates`) carries `minting_evidence`: the witness as a header-only copy (`Certs::headers`; no expiry or commitments in its prefix, `osis_commit::prefix_expiry`, so it outlives the expiry it shows) and, destroyed, every held request standing over any minting (`destroying_requests`), each with the evidence of its parts.
  - **Every destroying request, not the witness's alone**: a node holding the witness but not a request reads the destroyed thing live. Only right holders (admins) make requests, so a reader adds none.
  - **Copies under a sync ID** (spec/commits.md §5, the sync side): the witness is logged only where no entry holds a minting of the same standing; a destroyed thing's copy that went is logged again while the sync ID needs it. So a minting again adds no copy, and every node judges by the same witness. Sync takes a header-only copy into S's required set exactly while this node's certificates name it (`minting_evidence`, the facade's `sync/bodies.rs`); the gates below are not built (issues/sync-unbuilt.md).
  - **Why log again once destroyed**: a node lacking a request may drop the true witness for a minting a request already dropped; logging it again only while destroyed keeps two nodes from logging and dropping each other's copy for good while the thing lives (a node keeping S unread never gets the settling request).
  - Never logged where the sync ID carries the minting already (a live closure thing's minting body, a durable commit copied with parts, as an account's minting is its card's commit). A live thing's witness goes under a sync ID only from a node whose certificate set carries its record (a role holder, a promoter completing a depositor's evidence).
  - Erasure stays: the header carries no content (notes/deletion.md). Rejected: reads asking for a held minting (changes every raw record's semantics); a minting needing write on the thing (it loses a removed writer's creation its removal's frontier omits, addenda vouching for content, not `created.0`).
- **Keys through a destroyed thing**: none; access through it ends at the next rotation of what it held, as at a removal (notes/holder-actors.md, Destroyed holder actors).
- **A thing is known by its record**: a part on a thing whose record is held and that is not destroyed is judged, and the thing reads (`Core::exists`; a grantee reads a thing's `sync.0` before its creation). A node writes a thing only while it holds a minting (`Core::writable`): a raw record learned outside certificates carries no destruction.
- **A thing minted with a key is destroyed** as any thing, by an admin (its key's grant among them): what it signed still verifies, its record staying wherever something it signed or is on a path of is held.
- **History opened before the thing relying on it** (a newcomer takes the destruction with the record first, needed by nothing yet): it goes at the pass end as any unneeded thing, then the relying thing awaits the record; the facade learns the record from a record blob kept loose once something awaits it (`take_record_blob`, `Engine::promote_loose`). Untested: a certificate copy of the destroyed thing opened and dropped before the relying thing arrives.
- **A destroyed thing's certificates outside the closure** (its edge writes, a destroying request, a minting's header) are in S's required set while S's things need them (spec/sync-judgement.md §2; `Engine::destroyed_upstream`), judged by aspect, not by the node's own drop.
- A record blob placed while live and the evidence placed at destruction are separate entries: a newcomer reads the thing live until the evidence opens; a rotation of the relying thing it makes meanwhile boxes the destroyed thing and is judged invalid once the evidence opens, so epochs converge (by reading, untested), losing what it wrote under that epoch. A node holding a request but not the witness's copy reads a live thing destroyed from a purged copy another node kept (untested). Only a relying thing's own destruction re-checks the destroyed things named on it: one kept for a relying thing that goes otherwise (access lost, `retention/forget.rs`) stays. A node holding a raw record but never the creation never sees the thing destroyed. Paths through a live thing outside the closure are not carried, so neither are destroyed things reached only through one.
- Rejected: cutting authority (validity) through a destroyed thing at its destruction: the same history must travel for past writes. Keys alone end access through it (notes/holder-actors.md).

**No `delete` call**: undoing a creation reverts its commit (the strong it wrote goes, the creation stays live, a later write recreates). Destruction is `Write::purge` or expiry; a thing no strong reaches is released, not destroyed (spec/sync-set.md §3).

## 4. Open
- Dead sequence records others' position or flag writes keep stay, a few bytes each (issues/seq-dead-records-grow.md); an expired element or map entry keeps no record (spec/crdt.md §4.7).
- What a held snapshot carries is runs of counters per source (`retention::snapshot::Carried`: every write its body holds), so the carriers of a gone write are found without reading bodies; its runs grow with how often a session alternates between the aspect and others.
- A destroyed thing strands, silently, what only its strongs held, as an expired one does.

## 5. Properties and tests
Models first: crdt-model states the element rule (`element_rule_spec_4_7`, `map_dot_records_one_entry_spec_5_6`) and osis-crdt runs in lockstep with it; held-model states records as writes (`tests/it/spec_records.rs`, `DropWhy::Unknown`/`Destroyed`, `Outcome::revisit`/`destroyed`) and fetching (`fetch.rs`).
- Expiry changes only the expiring commit's values; a write into an expiring entry keeps its own (osis `api` tests: a reaction outlives a disappearing message, a removal does not). `strip_carried` handles snapshots alone. Matrix: osis-engine `expiry_model::expiry_takes_its_commits_writes_spec_crdt_4_7` (text, a map entry, a list element of text and a record, either commit expiring first, either arrival order, from a snapshot, through compaction before and after T); crdt-model `text_in_an_element_expires_by_writer_spec_4_7`.
- A thing exists while its `created.0` is held live; parts on unknown things are not held; the read is a function of the held set in every arrival order of creation, writes, purge and expiry.
- Unjudgeable parts (held-model `fetch.rs`, engine `Exam::Awaits`, `apply/waits.rs`, sync's `store/follow.rs` Carriers): a valid grant whose sync ID is reachable reads like creation-first; forged boxes never change a read; a forged grant fills only the budget; an order-0 batch refetches nothing.
- Destruction: gone at every node at T or at the purge in any order; a later write ignored; a non-admin purge falls; holders drop the blobs. No minting extends or restores a thing: engine `validity::a_minting_never_extends_an_expiring_thing_spec_commits_5` (durable or later-expiring mintings refused before and after T), `validity::a_minting_never_restores_a_destroyed_thing_spec_commits_5` (stamped before or after the request, arriving before or after it), osis-commit `validate_commit_expiry` (a minting not `admin` is bad); an expired thing leaves no row: sync S1 `growth::expired_things_return_storage_to_a_fresh_nodes_spec_commits_5`. Authority through a destroyed thing: what was minted with a destroyed admin runs on; a destroyed mint admin or holder stays evidence until the last thing relying on it goes; authority through a destroyed granted admin stands. Engine tests: `rotation/tests_members.rs` (`destroying_a_holder_actor_ends_access_through_it_spec_crypto_4`: keys through it end); the cross-node ones (awaiting bytes per sync ID at n and 10n, the relying things, minting copies) await sync tests (issues/sync-tests-owed.md).

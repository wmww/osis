# Expiry and creation records: design
> Summary: Design (built) of expiry by commit and of creation records (issues/creation-record-ordinary.md). Expiry and purge take only a commit's own values; an element shows while it is not removed and holds a live value (its creation's or anyone's inside it); records with no write go (virtual anchors place alike); copy expiry leaves the CRDT (only the undo writer rule stays); `created.0` is an ordinary write whose expiry or purge destroys the thing; a part or commit the node cannot judge is thrown out and fetched again, and what it opened keeps the keys to fetch what judges it. Also its properties, tests and open limits.

## Principle
What deletion promises, and which side purge, expiry and destruction sit on: notes/deletion.md (erasure keeps a tombstone where needed; reclaim leaves no trace). Destroying a thing by purge or expiry of its creation is erasure.

A write's value lives by its own commit: at expiry or purge the commit's values go, and nothing else. Removals, positions and stamps carry no app data and stay. A node keeps no part it cannot judge, and keeps what it needs to fetch what judges it: nothing past the pass that fetched it, except the reading-only secrets its boxes open, and it fetches the rest again once it can judge them.

## 1. The CRDT rule
**Element rule.** An element (map entry, list element, text char, set or bag element) shows iff:
- it is **not removed**: its creation is held (valued or value-less; for a map, in its keyed record or the dot's key-erased record), no reset at or above it reaches it, and a text char's flag is not a delete;
- its **content is present** (§4.3): for a set or bag element or a text char, the content is its creation's value; for a map entry or list element, its fragment;
- it **holds a live value**: its creation valued, or a valued write anywhere inside it.

The third clause is Tess's rule. Removals (resets, delete flags) are not content, so an expired entry that holds only someone's removal goes. For durable data the third clause always holds.

Per container:
- **Map entry.** Each keyed record holds its valued writes, and its key lives while one of them does. A reaction written into another's record is that writer's own write, key included. Value-less writes of any delta sit in the dot's key-erased record, and a live record reads joined with it. Commit 1 (expiring) creates `k` with text and commit 2 adds text: at T, commit 1's creation and text move to the key-erased record, and record `(dot,k)` still holds commit 2's writes, so it shows `k` with commit 2's text. Value-less writes move one at a time, never the whole dot.
  - **The records of a dot are one entry**: every reset of the dot reaches each of its records, and a record keeps only its writes the join of its dot's records holds, as the copy that join holds (the map clause of spec/crdt.md §4.8 Which write, applied to state); a keyed record's copy of a write carries the key, so the key-erased record's copy yields to it. Without it the strip of a state differs from the join of the leftover: X creates `k` with `a = 1`, Y later sets `a = 2`; X's value-less `a = 1` in the key-erased record is beaten by Y's. Resets reach the whole dot because a keyed reset reaching only its record made the rule order-dependent across a forged second key.
- **List element.** A list creation carries a value, like a map key or a text char: held value-less it keeps its anchor (a bit on the creation, on the wire a `Creation` marked `false`). The element shows while its content is present and, under a value-less creation, holds a live value. No element reset at T. (With no creation value a durable element emptied by nested removals would vanish.)
- **Text char.** The char is the creation's value, so nothing inside can keep it. An undelete's char is the undeleting write's own value and goes by that write's own expiry or purge; an undelete shows the element by that char alone, so one whose char went hides it (as a value-less register winner reads absent), whether or not the node holds the creation's char.
- **Nested containers.** The rule applies at every depth. An entry's content counts the live values of its nested elements.
- **Registers and cases.** A value-less winner keeps its stamp: it reads absent and still beats older writes. This is the write's implied removal of older values, which stays.
- **`W`** carries a value: it writes the app value "an empty composite", held value-less like a register's (`[Stamp, false]` on the wire). So an expiring `{}` goes at T.
- **Removals and resets.** Removal is final: a newer write inside a removed element stays hidden until a sweep resets it.

**Late nodes.** A node that never held an expired or purged creation (hosts drop its body) holds others' writes in the entry without it, so it shows nothing there until a writer compacts and the snapshot carries the creation value-less; nodes that held it show the others' writes. The limit spec/commits.md §5 states for non-value writes, reactions included.

**Leftovers at expiry**: only the expired delta's non-value writes and its value-carrying writes value-less: resets, flags, positions, creations with their anchors, value-less register, case and `W` stamps. They are held as the delta's leftover body until a snapshot covers them, because hosts delete the body at T and it cannot be fetched again. Nothing else stays: no element reset, no whole-dot key move, no hidden-dot mark.

**Virtual anchors.**
- *Records with no write.* **Every record with no write goes**, in every collection (spec/crdt.md §4.2, notes/crdt.md "Records with no write go"): a seq record left with no write is placed exactly like a virtual anchor (END, by dot, children kept; §6.1-6.2).
- *Expired creations.* An expired creation that no reset has pruned keeps its anchor. That anchor is a non-value write, and others placed content on it in honest flow. Dropping it would move live neighbours to END at T, a visible reorder on a common path (a disappearing paragraph in a durable doc). Invalid writes accept that cost only because they are rare.

## 2. No copy expiry
Expiry is not in the CRDT beyond the element rule. What remains is spec/crdt.md §4.6's writer rule: an undo or undelete that copies back an expiring value expires no later, and refuses to mix expiries. Receivers don't check it: copying back is the same as typing the value again. A write into an expiring entry keeps its own expiry; the §4.7 Copies rule serves purge alone (snapshots carrying a purged write's value), since an expiring value is never valued in a snapshot. Expiry is one `strip` (`Fragment::strip`, `seq::strip_values`) and changes no winner (stamps stay), so it can be an in-place strip of one delta's dots instead of a rebuild.

The hidden-write sweep resets only records a removal ended that still hold a write: a record not live for want of a value may still show (a valued write arriving), so resetting it would remove others' concurrent writes.

## 3. Creation records
**No tombstone.** A node holds no part whose thing record, chain record or author record it lacks, and no part whose author's reach it cannot read.
- **Unjudgeable.** A part is unjudgeable when `thing_wait` says so (thing record, chain record, author's reach). A commit is unjudgeable when its author's or actor's record is unknown, or every part it holds is unjudgeable; that is judged before an epoch or `ts` ahead could make it pending (`examine`). A pending commit can still judge so later (its bad parts dropped once judged, its header pages resolving its aspects): its stored copy goes then and the commit is named for redelivery (`Engine::take_redeliver`), so its carriers ingest it again and each copy awaits as on arrival (node-sync's `ingest_again` marks the entry `Kind::Awaits`; `LocalPeer` keeps pending commits' copies as carriers). No such bytes are kept past the pass that fetched them: a pending commit's unjudgeable parts beside judgeable ones leave its stored copy (`throw_out_parts`) and node-sync keeps no blob holding them (`Engine::copy_awaits`).
- **What stays: reading-only secrets.** A box opens with this node's own KEM key, needs no record, and proves itself by what it opens: it is a means to fetch, not a claim (spec/crypto.md Reading-only secrets). Before discarding, the node reads the `secrets.0` boxes of what it opened (`read_pending_boxes`) into reading-only secrets sourced from that commit, within `MAX_READING*`, and never encrypts under them. This is what lets an invited person open a label whose only key is in the grant, while the record that judges the grant sits under that label. They go when the commit's last part applies, it is judged bad, or its last entry leaves (`by_commit` empties, then `forget_unchecked`). A refused box re-reads when the budget frees (`Wakes::reread`).
- **A whole commit that waits** turns its label entry into `Kind::Awaits { commit, things }`: no separate revisit set, since the entry table is bounded by what hosts list and this variant is smaller than `Kind::Commit`. An index thing → entries spans labels, under each awaited thing: any arriving wakes it (a part on another thing may then apply). `things` names what is awaited broadly enough that account signing (issues/account-signing.md) can name an epoch's minting rotation.
- **A part of an applied commit that waits** keeps its slot in `m.missing`, the awaited thing derived from the held header (`Changed::undropped`, `reopen_undropped`). `settled_slots` does not count those slots; the index is derived from the header, no stored ID.
- **Wake at pass end.** Entries whose awaited record arrived reopen, a commit thrown out whole by any one of its parts' records (the entry names only the first; a part on another thing applies when its record comes); reach waits reopen on moved edges, batched per pass (a commit thrown out whole with a reach wait among its parts' waits too, `waits::wake` rereads it by ID: the entry may name another part's record); every awaiting entry reopens when this node's secrets change, or a reading-only one becomes checked (a box opens through it; no count of secrets changes then), since a section no secret opened may open now. A refetched blob is judged afresh and may await the next record.
- **One batch per pass.** A pass judges the order-0 fetch together: `created.0` carriers, then role commits by `ts` (as `reexamine` sorts); it discards only what is still unjudgeable at pass end. Otherwise a first sync is a storm of waits.
- **Inbox.** `admits`, `vet_inbox_hints`, `boxed_by`, `hint_actors` ask "applied, or an entry held", not "applied or pending". `hint_actors` reads `inbox_opened`. The inbox blob stays local under `DEPOSITS_WAITING*`, so retrying costs no download. Stamping treats an awaiting commit as it treats a pending one.
- **Ephemeral commits** are thrown out by the same rule. An `Awaits` entry is `memory: true`, charged to the label's memory cap; past it, `refuse_memory`.
- **What stays pending.** `with_pending`/`redeliver` remain for `WaitBlobs`, `Drift`, `Epoch`, `Parked`; such a row lives only while an entry carries its commit (notes/node-sync.md, Input giving nothing). A commit carrying its author's `created.0` keeps its aspect list inline (writer rule), so no linked header needs the record it carries.
- **Stated limits.** An insider can exhaust the reading budget and delay honest grants until its entries leave. A commit that expires or whose body is deleted while it awaits is treated as if it never arrived (spec/commits.md §4): a node holds no bytes to flag it from. A hostile writer with a k-aspect blob can cause k refetches by publishing k records one at a time.
- **Rejected.** The grant bringing the record: it removes only the first wait, the author's chain is the same problem next, and it misses the home-label sibling route. Keeping commits with boxes for this node: bytes keyed on an unverified claim any depositor can add.

**Destruction.** `created.0` takes ordinary retention: a schema default per AK (proposed `admin`, no history), set per commit like any delta (no fixed `nobody` retention, no commit-sharing exemption). Purging or expiring it **destroys** the thing.
- **Who destroys** (spec/permissions.md §6): any admin at the request, as with any purge right. Reading the right from standing on the first admin alone is rejected: a removed admin could then destroy a thing for everyone.
- Every node drops the thing whole in the transaction that made its last creation value-less (`retention/destroy.rs`): incremental, cost the thing's parts, since a disappearing message is destroyed often; the commits' headers stay, as for any purge.
- Node-sync deletes at hosts what the node has delete keys for, by the dropped-body path.
- No wait before hosts delete (Tess): a destruction that later falls brings the thing back only if some node still holds a copy.
- **A minting** (a `created.0` delta) needs no authority, like its record (spec/permissions.md §1): anyone holding the record may sign one.
- **A destruction names every minting**: a purge item on `created.0` reaches every minting of the thing whatever its `ts`, so a later minting is held value-less like the first (`purge::stamped_before`).
- **Nobody writes a thing after its destruction** (Tess): a part on a destroyed thing stamped after its destruction (each minting dropped: `wall_ms(ts) >= T`, or after a request dropping it) is a part on an unknown thing, `roles.0` and `purge.0` included, a minting excepted (Limit below) (`destroy::Destruction`, `thing_wait`, `destroy_thing` drops such parts already held). Honest writers refuse the same writes (`Core::writable`), so a modified client gains nothing by destroying first.
- **A destruction is judged by the history before it**: a request's right over a minting is judged without the edge writes on the thing stamped after the request (`purge::holds_right`, a walk from scratch without them over what authority on the thing comes from, `Held::upstream`, only while one is held and the signers could ever hold the right: once the thing was destroyed they are not held, but a request that destroyed nothing pays it on every role pass over the thing; `destruction::a_fallen_destruction_walks_only_the_things_authority_spec_permissions_6`). Without it the verdict is a cycle: a later demotion of its author on the thing makes the destruction fall where it arrived first and is dropped as written after the destruction where it arrived second. So a demotion written after a destruction does not undo it; one stamped before still does.
- A later or concurrent write is a write to an unknown thing: not kept anywhere honest, so "a later write recreates" stops holding only for destroyed things.
- **Limit (flagged for Tess)**: anyone holding the record (every reader of a dependent's label, through record blobs) may mint the thing again at any `ts`. A durable minting keeps an expiring thing past its expiry or brings it back after it; one whose retention the request has no right over (`nobody`, another's `author`) keeps it from being destroyed by purge or brings it back within the request's window (past it the node keeps the verdict, destroyed for good, and takes no minting). It carries no content: content parts expire and are purged on their own, and what the destruction dropped is back only where a copy is held. But a thing brought back is live: its frozen roster stands again and its writers may write it, writes stamped after the destruction included (`destruction::a_minting_again_the_request_cannot_drop_brings_back_a_live_thing_alike_spec_commits_5`); the minter gains no role.
  - Closing the purge half (Tess): a destroying request covers every minting whatever its retention, which is the same as `created.0` taking only retentions that include `admin` (`admin`, `author_or_admin`, `writer`). Small to build (the right over a minting is the admin right on the thing), but it removes the `nobody` option for things: a message in a permanent chat (libs/chat `Nobody`) is created in a `nobody` commit, so its admins could then destroy it. It follows notes/engine-retention.md History, decision 2 (admins may always purge) once `nobody` goes for content; until then it breaks an option's property. The expiry half stays either way.
  - Why mintings are exempt from "nobody writes after its destruction": the destruction is the point every minting was dropped, so a later minting held before the destruction is computed would decide it by arrival; and any order-free cut (the first point every minting stamped before it was destroyed) lets anyone destroy a thing early with a backdated minting expiring before the real one was stamped. Data loss outweighs a revival.
  - Rejected: a minting judged as a write on its thing (needs write at its key). A removed writer's creation its removal's frontier omits then reads absent unless a witness's addendum vouches for its `created.0` (`sync::removal_from_partial_node_keeps_unheld_edits_spec_permissions_5_2`); letting addenda vouch for it made that test loop without end (never root-caused). It also only narrows the limit to writers without closing it.
- Rejected: the record carrying the expiry (every minting would agree): `Write::create` returns the tid before the commit's expiry is known.
- A disappearing message is one commit.

**What must remain.** Per destroyed thing at nodes, only what any purge leaves: commit headers; for a destruction by purge also the request's own `purge.0` part and the thing's record that places it for nodes that have not heard (`Core::destroyed` treats the thing as unknown). A destruction by expiry leaves no record unless a dependent needs it (Dependents).
- A late write is judged like any write to an unknown thing.
- A purge is proved by its own commit, held by the ordinary purge rules: blobs kept at least `ROLE_KEEP`, and a lasting header when the creation kept history forever.
- A destruction by request keeps what judges it for `ROLE_KEEP` after the request (as role history is kept): the thing's record, value-less creation and `roles.0` parts (no content), so a removal arriving in that window can make it fall and a stale copy is destroyed again. Not for good: a purge request is never dropped, so that kept a record and its edges per purged thing forever. Past the window the node keeps the verdict instead (destroyed for good, a tid per purged thing: notes/engine-lifetimes.md Keep and forget), so no minting is taken again, whatever its ID or retention. Any admin at the request may destroy, as with any purge right (issues/destruction-verdict-reads-dropped-grants.md). A fall reopens what the destruction dropped and judges again what waited on the thing.
- An expiry needs nothing: every copy of the creation carries its T in the header.
- Purge is per part: destroying one thing leaves the other things in that commit alone.
- Disputes: a side that judges the purge invalid keeps the thing, and hosts keep it while the fork lasts (notes/disputes-plan.md).

**Dependents (Tess: B, authority that passed through a destroyed actor stands as its frozen history says).** Records are identity, `created.0` is existence: a record proves itself by its hash and needs no authority (spec/permissions.md §1), so it is not data of the thing. What judging a thing x needs of an actor t on any of x's authority paths (first admin or granted: the first admin is history, spec/permissions.md §1) is t's record and t's `roles.0` history, and it travels with x. Code: `retention/destroy.rs`, `labeling/certs.rs` `Certs`, `Engine::destroyed_upstream`, node-sync `place_records`.
- **Raw records travel.** Chain certificates carry creation records raw, in record blobs (`["records", [creation+]]`, spec/wire.md §3), never copies of the commit that minted them, which go with its retention; inbox payloads carry them in position 3. A node places the records its chains need that no entry under the label holds, as one record blob; any node's opened record blob counts once present at every host. Record blobs have no commitments: only the label-wide delete key removes one; deposited ones never count toward a chain and wait for clearing (spec/sync.md §5); a promoter places its own. A cross-published `created.0` stays a copy: it is the thing's own existence, which goes when it is destroyed.
- **Frozen history travels with its dependents.** For each destroyed actor on an authority path into a label's closure (named first admin or holder on a live closure thing, or on such a destroyed actor: `Engine::destroyed_upstream`, a walk of the held holders), the label carries its record chain and every held edge write on it with their write certificates, placed by the dependents' holders: as closure bodies while the group still lists the destroyed thing (holders that keep its edges upload them again), else as certificate copies. The destruction deletes the destroyed thing's bodies where it keeps nothing; a node that kept nothing takes a body or copy again when it opens one (`takes_late`: a part dropped by the destruction counts as never received) and so deletes it no more.
- **A thing's mintings travel with its record** (principle: whatever lets a node judge an actor tells it whether the actor lives; no partial knowledge that reads as live, nor any that reads as destroyed). Destruction reads only whether every held minting is value-less, and when the last went, so one minting judges it: the **witness** (`retention::destroy::witness`), the held minting of highest `Standing` = (valued, `End`), ties by lowest commit ID. `End` is the earlier of its expiry and its earliest standing request, ordered so a part written after a later end is written after every earlier one (expiry `T` vs request: by `wall_ms(ts)`, the request later on a tie; requests by `Point`); `Destruction` is the witness's end. Every certificate set carrying a thing's record (`cert_parts`, `Engine::certificates`, an inbox payload's raw records) carries `minting_evidence`: the witness as a header-only copy (`Certs::headers`, `header_body`: no expiry or commitments in its prefix, `osis_commit::prefix_expiry`, so it outlives the expiry it shows) and, destroyed, every held request standing over any minting (`destroying_requests`), with their authors' chains (keysets cleared: no keyset judges a header). Test: osis-node `destruction::a_forged_expiring_minting_destroys_no_live_thing_known_by_its_record_spec_commits_5`.
  - **Why every destroying request, not the witness's alone**: a node holding an earlier witness (W, before a purge dropped it and left a minting the request has no right over) reads W live without the request, so once the thing is destroyed it would read it live for good. Only right holders make requests (spec/permissions.md §6: admins; an author or writer only with write), so a reader adds none; a hostile writer adds one per minting it purges, as any write it makes costs.
  - **Bound per label** (node-sync): `certificates` places the witness only where no entry holds a minting of the same standing (`witness_held_at`: a tie places nothing, so a reader's durable mintings beside a durable creation add nothing); `delete.rs::superseded_minting` deletes a header-only minting copy outside the closure that stands lower than the witness once the label holds, at that host, a minting of the witness's standing expiring later than it (durable latest) (else judged again each pass, `unsure`). A placer counts its own new entry, so it deletes the lower copy in the pass it places the witness. Copies of one commit by nodes placing it in the same round stay (duplicates are harmless; at most one per placing node). Test `a_minting_again_adds_no_copy_under_a_label_carrying_the_record_spec_commits_5`: as many copies at k = 10 re-mintings as at k = 1, all of the witness.
  - **Who deletes, and placing again** (principle: once a thing is destroyed every view agrees, since its requests travel with its witness). Any node deletes a lower copy, reader of the thing or not. One lacking a request ranks a minting no lower than one holding it, so while the thing lives what is left reads it live wherever only the copies are known; it may delete the true witness for a minting a request already dropped (a lagging reader, or a non-reader, which gets no request while the thing lives). That is repaired once the thing is destroyed: `certificates` places a header copy again despite `State::certs` when it certifies a destroyed thing the label needs (`delete.rs::header_certifies` against `destroyed_needed`), exactly what `destroyed_certificate` keeps there, so this node never re-places what it deletes; another node lacking a request deletes it at most until it opens the request copies placed in the same pass, which only a node judging the thing destroyed (so needing it the same way) may delete. While the thing lives a deleted copy is never placed again (`State::certs`, forgotten by `sweep_certs` only once its bodies are gone): a non-reader never gets the request that would settle its view, so two nodes would place and delete each other's copy for good. Tests: `a_witness_deleted_by_a_node_lacking_the_request_comes_back_once_destroyed_spec_commits_5` (b, not reading t, deletes the new witness N after a purge of W it never got; at N's expiry a places N again and every node dates the destruction at N's expiry), `a_purged_later_minting_leaves_the_destruction_at_the_creations_expiry_spec_commits_5` (a later minting Y, then purged, had C's copy deleted; C is placed again at its expiry). Both fail without placing again: a node granted the label afterwards dates the destruction at the purge.
  - **Expiry gates every delete**: standings differ between views (one holding a request ranks a purged minting low, one lacking it high), so two nodes judging in one round would each delete the copy the other keeps and leave the label with none, and an expired minting again would then read the live thing destroyed at a record-only node. Expiry orders copies alike in every view, so the latest-expiring copy is never deleted and, a live thing's witness expiring no later, it reads the thing live. Cost: a purged minting expiring after the witness keeps its copy, one per request, which only a right holder makes. Test: `a_purged_later_minting…` (Y stays beside C).
  - Limit: a node holding a request but not the witness's copy (a request commit naming several things, opened through another of them) reads a live thing destroyed from a purged copy a node lacking the request kept; nothing tests it.
  - While the thing lives, a lower copy whose witness has no copy (deleted by a lagging node) stays, and is judged every pass (`unsure`) until the witness is up again or the thing is destroyed.
  - Placed once (`header_held_at`) and never where the label carries it already (a live closure thing's minting body, a durable commit copied with parts, as an account's minting is its card's commit; a header copy placed first would mark the commit placed, `State::certs`, and keep the card copy out).
  - A live thing's witness goes under a label only from a node whose certificate set carries the thing's record: in practice one whose chains pass through the thing (a role holder, so a reader), a promoter completing such a depositor's chain, or an inbox payload's raw records. No test reaches a label where only non-readers place.
  - Erasure stays: the header carries no content (deletion.md: a tombstone is allowed). Rejected: reads asking for a held minting (a semantics change for every raw record, and the evidence closes the class); putting a thing's expiry in its record (the tid is fixed at `create`, before the write's expiry is resolved); a minting needing write on the thing (a writer could still forge a destruction a non-admin cannot make otherwise); the witness ordered without requests (a purge dropping it while a `nobody` minting lives would show others a destruction).
- **Keys through a destroyed actor**: what it held a role on is boxed to its frozen holders in its place (notes/crypto.md, Destroyed holder actors), so a dependent with secrets of its own reaches a reader joining after the destruction without a write on the destroyed thing.
- **Limit: a minting again ahead of the witness.** The record blob and the header copies are separate entries: a node that opens a live thing's record, then a minting again already expired (a stale copy not yet deleted), before the witness reads it destroyed until that copy opens; the destruction then falls (spec/commits.md §5).
- **A thing is known by its record.** A part on a thing whose record is held (from a creation or a record blob) and that is not destroyed is judged, and the thing reads (`Core::exists`; an invitee reads a group's `label.0` before its creation); a destroyed thing is unknown but for what judges its destruction. A node writes to a thing only while it holds a minting of it (`Core::writable`): a record learned raw outside certificates (an invitee's) carries no destruction, and every node that saw one would ignore the write. A key actor takes writes by its record (its creation carries nothing else, and only its own nodes see it destroyed).
- **A destruction keeps** the record, the value-less creation and the `roles.0` parts while a destroying request is in its window or something held needs it: another thing it is on an authority path of (a held record naming it first admin, a held edge write naming it holder: `Held::named_on`), or, for a key actor, a commit it signed or acted in with a part held on another thing (`Indexes::signed`), or a lister or referencer. Otherwise it keeps nothing, re-judged whenever any of those lets go (notes/engine-lifetimes.md, Keep and forget), so destroyed actors named on it, left with no dependent, go too. The keep is per node, but nothing observable depends on it: a node without a dependent judges nothing through the actor, and a dependent arriving brings what judges it.
- **A key actor is destroyed** like anything, by itself (admin on itself): an account destroying itself leaves its D, profile and chats; what it signed still verifies, since its record stays wherever something it signed or is on a path of is held.
- **History opened before the dependent** (a newcomer takes the destruction with the record, usually before the dependent's body in its first batch): its destruction keeps nothing, then the dependent awaits the record. node-sync takes the record again from a held record blob listing it once something awaits a destroyed thing's record (`Engine::destroyed_records_awaited`, `relearn_records`); the record back reopens what the destruction dropped of the frozen history for fetching (`destroy::record_back`). Untested: a node that opened a frozen-edge copy before its own destruction (issues/destroyed-history-opened-before-dependent.md).
- **A destroyed thing's certificates outside the closure** (its frozen edges, a request destroying it, a minting's header) are the label's, for its dependents, whatever a node kept: `delete.rs::destroyed_certificate` holds them (may-hold) while the node's view is unsettled or the thing is in `destroyed_upstream`, waiting on the namers' `created.0` and the group's list, and deletes them (outside) once settled with no dependent in the closure, so they leave with the last dependent (test `a_destroyed_things_certificates_leave_the_label_with_its_last_dependent_spec_commits_5`). Judged by aspect, not by the node's drop: a node that kept the thing would otherwise judge the request's `purge.0` copy outside at once (no closure body wants it) and a newcomer read a purged thing live (`a_destruction_by_purge_stays_under_a_dependents_label_for_a_newcomer_spec_commits_5`); one that kept nothing would delete the frozen edges a later dependent needs.
- **Limit: record ahead of the destruction.** A record blob placed while the thing was live and the evidence placed at its destruction are separate entries: a newcomer opening the record and the dependent first reads the thing live until the evidence opens. A rotation of the dependent it makes then boxes the destroyed actor; once the evidence opens it judges that rotation as every other node does (invalid: it shows no frozen holder actor), the destruction marking the dependent stale, so epochs converge (by reading, untested); what it wrote under that epoch meanwhile is lost to others.
- Limits: a key actor's dependent check walks the commits (a key actor's destruction is rare). Only a dependent thing's own destruction re-checks the destroyed actors named on it: one kept for a dependent that goes any other way (access lost, `retention/forget.rs`; for a key actor, its signed part expiring, purged or destroyed with its thing) stays, one record and its edges per such thing. A node that holds a raw record of a thing but never its creation never sees it destroyed: it holds no data of it and writes none to it. Paths through a live actor outside the closure are not carried for the label's own writes (as before the destruction), so neither are destroyed actors reached only through one.
- Rejected: cutting authority through a destroyed thing at its destruction (A: paths through it stop counting, past writes judged with its history): the same history must travel for the past writes, and everything reached through it (a group's items under a destroyed first admin) would lose its readers and admins at once, against "things it created live on".

**`delete`** stays the undoable removal: resets content and memberships, the creation stays live, a later write recreates. Destruction is purging or expiring the creation. Its API is `Write::purge` (notes/api-design.md).

**`retention^.0`** keeps fixed retention: every node must date history by the same settings, so purging one would change what history shows. Only its commit-sharing exemption is open, as a spec question.

## 4. Open limits
- issues/expiry-rebuild-cost.md: each expiry still rebuilds its aspect (could strip in place).
- issues/eph-expired-anchors-fill-cap.md: unpruned expired creations stay as anchors for live neighbours; the fix left is a sweep that re-anchors live children of expired runs, then resets the runs.
- issues/text-creation-undelete-dating.md: unaffected by this design.
- A destroyed group thing strands its items silently, as an expired subgroup does.

## 5. Properties and tests
Models first: crdt-model states the element rule (`element_rule_spec_4_7`, `map_dot_records_one_entry_spec_5_6`; spec/crdt.md §4.3, §4.7, §5.6, §5.7) and osis-crdt runs in lockstep with it (states and stripped snapshots' bytes); held-model states records as writes (`spec_records.rs`, `DropWhy::Unknown`/`Destroyed`, `Outcome::revisit`/`destroyed`) and fetching (`fetch.rs`).
- Copy expiry is gone: a write into an expiring entry keeps its own expiry, and expiry changes only the expiring commit's values (osis-API examples: a reaction outlives a disappearing message, a removal does not; the order oracle). `strip_carried` handles snapshots alone. The matrix test is osis-node `expiry_model::expiry_takes_only_its_commits_values_spec_crdt_4_7`: text, a map entry and a list element of text, and a record, each with commit 1 or 2 expiring first, read alike in either arrival order, from a snapshot in place of the expiring creation, and through compaction before and after T; crdt-model `text_in_an_element_expires_by_writer_spec_4_7` states the text case.
- A thing exists while its `created.0` is held live; parts on unknown things are not held; destruction forgets the thing. The read is a function of the held set in every arrival order of creation, writes, purge and expiry.
- Unjudgeable parts (held-model `fetch.rs`, engine `Ingested::Awaits` and `apply/waits.rs`, node-sync `Kind::Awaits` and `wake_awaiting`): a valid grant whose label is reachable reads like creation-first; forged boxes never change a read. Tests: invite with the record unknown and only the grant's keys open the label; the home-label sibling copy route; a forged grant fills only the budget; an order-0 batch at n and 10n counts no refetches; awaiting bytes per label at n and 10n (the bound covers record and chain waits; the other pending rows are bounded by their entries, notes/node-sync.md Input giving nothing).
- Destruction (`retention/destroy.rs`, `Write::purge`): the thing is gone at every node at T or at the purge, in any order; a write after the destruction is ignored; a non-admin purge falls; hosts drop the destroyed thing's blobs.
- Dependents (Tess: frozen history travels as chain certificates: record blobs, inbox records, the keep rule for every actor on an authority path, destroyed actors' history placed under their dependents' labels): `destruction::a_destroyed_account_leaves_what_it_created_running_spec_commits_5`, `a_destroyed_first_admin_stays_a_chain_proof_until_its_last_dependent_goes_spec_commits_5`, `a_destroyed_holder_stays_until_what_names_it_goes_spec_commits_5`, `a_destroyed_first_admins_edges_reach_a_node_that_held_no_dependent_spec_commits_5`, `authority_through_a_destroyed_granted_admin_stands_spec_commits_5`.

**Positions at expiry and purge (Tess).** Expiry and purge keep an item's bare position, so live items placed after it stay put (unlike an invalid write, which leaves nothing). If keeping positions turns messy for complexly edited text or lists, weak expiry and purge support there is acceptable: prefer the simple rule over a carve-out.

# Links
> Summary: Why a link is an ordinary independent thing K plus a key actor L (spec/permissions.md §7): random secrets for K, `until` over expiry, outliving K's rotations, when `redeem` fails, the target as the text's word, the joiner's leave, finalization and its residual window (Tess), the race flip, a removed node keeping seeds, no link at sync, may-grant power.

Principle: **a link is built from existing concepts**: K, an ordinary independent thing, and L, an ordinary key actor (signing and KEM keys from the seed) listed in K's steps by static entry and boxed in K's `secrets.0` like any key-actor holder. A link conveys "add yourself with a bounded role", nothing more.

## Shape
- Several links = several (K, L) pairs. Revoke a link but keep its joiners = remove L from K (sync K's sync ID first); revoke link and joiners = remove K. Remove one joiner = remove it from K and remove L too: a redeemer may have kept the seed, and L's claim key would keep opening K's sync ID, where L's boxes hand it K's rotated secrets; the remaining joiners get a fresh link. Both removals are one commit with one rotation of K (perm judges each edge write on its own, so two removals at one point with one frontier); none may be a self-removal. A several-grant removal under one rotation keeps the one-commit rule's guarantee, since the rotation excludes every holder it removes.
- **K's secrets are random**, not derived from the seed: with derivation every holder of a read link derived K's admin secret, hence K's sync ID delete key (wipe or squat K's sync ID at every node keeping it unread) and write key, exactly the power the may-grant design takes from L; and L's boxes used a symmetric form only the seed holder could write, so a writer's rotation of K stranded L. So L has a KEM key (1.2 KB per box, rare) and redemption is one claim round trip.
- `until` instead of commit expiry, which would purge the certificate joiners' chains rest on.
- **May-grant power** (agent's call): L holds role r with the may-grant flag on K and the sharer stays K's only admin. May-grant grants only add grants for things with no current grant, so no may-grant holder can remove or demote anyone; a revoked may-grant holder's unseen grants drop by the demoter's frontier. May-grant holders seal only secrets they hold. Holders read K's roster, like viewers of a shared doc seeing each other. Rejected: L as an admin of K (every holder could remove other joiners and held K's sync ID delete key).
- Bearer use is read only: all bearers share L's node identity, so their dots would collide.
- **No link at sync** (`create_link` refuses it): redeeming reads K's sync ID as L, which sync on K does not give. A sync link would need L at read on K beside joiners at sync, a role pair no other grant has; keeping someone's thing unread is a sync grant to their account, which also names who holds it.
- A direct link's key outlives the link: ending it rotates nothing (notes/networking.md decision 4).
- Self-removal lets a holder always leave or lower its own grant; single-use links use it to drop L's own grant. In a shared space T, after redemption an admin may re-grant the joiner directly on T and remove it from K, so K becomes disposable and the roster flattens (kicking one joiner otherwise kills the link for all).

## Redeeming
- **A link outlives K's rotations**: the rotation commit is wrapped under the epoch it supersedes and its boxes and history box are all a late reader needs, so the entry box also carries that earlier secret (one, 32 B): the redeemer opens the rotation commit, and its history box opens all of K. Rejected: a re-seal of L in a commit under the new epoch (a commit more per rotation, and a window between a writer's rotation and an admin's step); not rotating K on a leave (a node removal rotates K all the same, so the path is needed regardless, and a leaver who discarded the seed, the SHOULD, stays out). What a user sees: a link works until revoked, expired, used up or a joiner kicked, however many people leave; a leaver holding the text can rejoin.
- Limits: one earlier secret, and with forks only the registrar's pick: a rotation in a fork it does not lead to stays unread until the next rotation. A commit on K pending behind it holds `redeem` to its timeout. A node keeping K's sync ID unread, holding its head without its claim set (past its caps) refuses like a revoked link.
- **`redeem` fails at once** (`Invalid`, "no longer works") on evidence only: a refusal of L's static entry (code REFUSED, not UNKNOWN_SYNC_ID) with every route of the sync ID failed, so one peer's word or one down decides nothing, or a held history that put L on K and ended it (`Timeline::ended`). An L not seen yet says nothing, since its grant may still be on its way; nobody answering waits until the caller drops it. `links` reads the roster, which holds no key removed or past `until`, so what it lists works.
- **A link's target is its text's word** (nothing signs it): `redeem` grants only after K's grant on the target is here, so a link pairing a target with another thing's K joins nothing, and forgetting the link has the lost-access trigger judge K, so what only L read goes. K's sync ID carries the grant, so honest links reach it pre-grant. `Invalid` needs a complete pass of K's sync ID and no commit pending on the target at the timeout: a node cut off mid-read hears `Network`, since an app reads `Invalid` as a dead link. Forgetting drops the hinted sync ID's session too. Not bound: K's mint admin can put K on anything else, and K can be any thing with L on it (an existing chat holding a role on the target): a joiner then holds all of that too, and the link names only the target.
- **A joiner leaves K once K is off the target** (spec/permissions.md §7, Joiner's leave): the target's admins end a link by removing K (K's only admin may be gone), which takes the target from every joiner but leaves their roles on K; without the leave each joiner syncs K's sync ID for good and dials its sharer forever. The condition is the redeemer's "link has ended" one, for every K the account holds by a grant (the sharer holds K by its record and keeps it to finalize and revoke, and to serve the removal to joiners). The target is the one K's creation record names (`link` field): only K's creator wrote it, and K's creator may remove any joiner anyway, so trusting it gives nobody new power; a record without it means no leave. Rejected: any thing K was put on (granting needs no grantee consent, so anyone could put K on a thing of theirs and take it off, pushing every joiner off); recording (K, target) at redemption (more state for the same answer). Sync writes it (`Engine::joined_link_ended`, `Engine::leave_link`). Concurrent leaves by two nodes of the account are harmless. Cost: a target admin granting K again brings no joiner back (a new link does).

## Finalization
- **Finalization**: L's claimed times are constrained by nobody's frontier (every holder signs as L). After `until` a holder can mint a backdated join; after a single-use redemption a second holder can mint an earlier redemption. So `until` and self-removal audit nothing until a sharer node writes a real removal; until then the link is honest-client-only. Sync (`Engine::links_due`, any node holding the seed thing and admin on K, woken at the `until`) writes it after a complete pass of K's sync IDs ended after `until`, so the frontier covers honest grants that reached K's sources while the link worked. Without saved peers only the node that made the link finalizes, at once. A seed thing counts only when its mint admin is K's mint admin (a co-reader can add a `link:seed.0` thing to a shared thing's sync unit). The finalizing transaction removes the account root's strong to the seed thing, which serves only a working link, so it goes as any thing whose last reference goes; an ended link's joiner is still found through K's record (`Osis::own_link`), not the seed. A K whose sync ID never completes a pass is never finalized. Idempotent: the walk's `prior` is cleared by the first explicit write, so a second node's concurrent removal restores and audits nothing.
- Residual window (Tess: keep, documented on `LinkOpts.until`: an expiring link closes when one of your nodes next syncs after `until`): while every sharer node is offline after `until`, or K's sources are unreachable, a backdated grant logged then is received in that pass, covered and stands; cutting it would also cut honest late-received grants (both carry `ts` < `until`). Future option: a still-trusted source's receipt time as witness, one feature for removals and link expiry together. The alternative (no `until` or single use at all) loses nothing a hostile holder respects.
- **Race flip**: the finalization's frontier can drop a competing redemption the sharer had not seen, so a redeemer that lost by its own view may win; a loser therefore keeps K's secrets and sync IDs while L's self-removal is unfinalized (`rotation::lost` `contested`), and drops them once the removal arrives. Only redemption-shaped commits count on both sides: a plain leave then a void grant defers nothing (`void_grant_by_leaver_keeps_no_secrets_spec_perm_3`; otherwise any self-left holder could keep any removed holder holding the thing's secrets for good). Residual: a may-grant holder whose leave commit also granted someone can later forge a void redemption naming a removed holder, who then keeps the thing's stale secrets (no new epochs) until an explicit write on that holder's grant. Cost: never finalized, the loser follows K's and the target's sync IDs for good; not bounded in time, since past a bound the race flip would leave the winner unaware again. Rejected: inbox delivery of the removal to the joiner alone (the loser had already dropped the target's secrets, and nothing brings them back).
- **A removed node keeps the seeds** of the account's links (they sit on dependents of the account root), so it opens K's head by L's static entry past the removal's rotation until each link is revoked. Not ended by the removal (a link shared in advance dying because a phone was replaced would surprise), so `remove_node` returns the account's working links and the caller decides (`node rm` prints a revoke line per link, `--end-links` ends them). Any node of the account can list and revoke any of its links: the seed thing carries K, seed, target and single use. A link made on the removed node and not synced yet is unknown here.

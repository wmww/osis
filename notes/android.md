# Android
> Summary: The experimental Android build of the app (app/android): the same UI as desktop in a View of our own (java/: OsisActivity, OsisView, OsisInputConnection) run on the UI thread by Rust; the keyboard's input connection over the focused text (kit's ime::android); build recipe (javac, d8, aapt2, no Gradle); the selection menu as a floating `ActionMode`; what works on the emulator, and what is open (cursor anchor info, other apps' text actions).

## Shape
- `app/android` is the crate `osis-android`, a workspace member outside default-members, empty on every other target.
- Principle: Android's text input works only through a View's Java `InputConnection`, called on the UI thread, which a TextView answers from its live text. So the whole UI runs on the UI thread behind a View of ours, and the input connection reads and edits the focused text directly: no copy of the text, no second thread, no races. (NativeActivity has no input connection; GameActivity keeps a mirrored text state on another thread and needs AndroidX AppCompat, which needs Gradle.) Same shape as rust-mobile/android-view, which Masonry's IME code anticipates.
- java/ (no AndroidX, no resources): `OsisActivity` (a plain `Activity`: edge to edge, keyboard hidden at start, Back through `OnBackInvokedCallback` on 33+, which apps targeting 36 need: `onBackPressed` is not called), `OsisView` (a `SurfaceView`: every callback forwards to a native method; the methods Rust calls: `wake` (any thread, posts `nativeWake`), `requestFrame` (Choreographer), `showKeyboard`, `hideKeyboard`, `restartInput`, `updateSelection`, `setClipboard`, `showMenu`, `hideMenu`; `ViewConfiguration`'s gesture thresholds go to `nativeCreate`), `OsisInputConnection` (each `InputConnection` call to a native method; `sendKeyEvent` through the view, the hardware keyboard's path; the keyboard's own Select all, Cut, Copy and Paste buttons as the field's commands, `nativeCommand`).
- src/: `lib.rs` (the natives, `nativeCreate` starting the UI through kit's `Start`, exported by jni's `native_method!`, type-checked against java/'s declarations; `with_shell` runs one on the thread-local `Shell`, then the `Effect`s it left on the view, after releasing it, since `restartInput` re-enters at once), `shell.rs` (`RenderRoot` plus kit's `Ui`, the IME session, and kit's `Platform` for Android: clipboard read over JNI (`lib.rs`, `clipboard`; `has_clipboard_text` from the clip's description, which shows no "pasted from" toast), written through the view, keyboard show and hide and the selection menu as view effects after the shell's own; keys, input-method edits, commands and window focus go to the UI through `Ui::text_event`), `gpu.rs` (Vello over wgpu on the Surface's native window, as masonry_winit draws), `input.rs` (MotionEvent and KeyEvent as ui-events, which pass through kit's `Ui::pointer` for gestures; keycodes through ui-events' Android tables; a key's character is read without Ctrl and Meta, so Ctrl+V names V).
- The store is `<files dir>/store`, opened by kit's `Start` without a peer (an address pasted into the search field adds one); one that cannot open shows why, with start fresh (notes/app.md, Startup), and logs the error. Android may create a new view before destroying the old one: `nativeCreate` first closes any shell there is (`Started::close`), so its open never finds the store in use, and `nativeDestroy` closes the store and forgets the view only while it is still the current view.
- Lints: the workspace's with `unsafe_code = "deny"`: the one unsafe block makes a native window of the Surface (`ANativeWindow_fromSurface` has only a raw JNI form); tools/policy.py allows exactly one, under a `// SAFETY:` comment.
- Manifest: `OsisActivity`, `Theme.DeviceDefault.NoActionBar`, INTERNET, minSdk 28, targetSdk 36, `adjustResize|stateAlwaysHidden`, config changes kept in-process, `allowBackup="false"` (the store and its keys never go to cloud or device-transfer backups), not debuggable (`run-as` cannot read them; add `android:debuggable="true"` locally to inspect the store). No icon.

## Keyboard
- The input connection is kit's `ime::android` (notes/app.md, Text input), each call against the focused text as it is now. `ime::Sync` decides what the keyboard is told: `updateSelection` after every selection or composing change, `restartInput` when the text changed other than by the keyboard's own edits and key events (a merge from another device, a field cleared after Send), deferred to the end of a batch edit.
- Hints: `EditorInfo` from the field's `TextInputHints` (`ime::android::editor_info`): purpose, Enter's action (no action in a multiline field), capitalization, suggestions; never fullscreen or extract UI. `performEditorAction` is Enter.
- When the keyboard opens is kit's rule (notes/app.md, Platforms and input): a tap on a field (the focused one too, after Back put the keyboard away) or a field that appeared wanting typing (a new thing's title); never for focus alone (home's search is focused at start without a keyboard; `stateAlwaysHidden`). Losing the field hides it (the shell reports each input-method session to `Ui::text_focus`).
- Insets: system bars, cutout and the keyboard (`WindowInsets`, API 30+) pad the screen (`Ui::set_insets`, kit's `Root`); the window is not resized. Before 30 the insets are zero and `adjustResize` resizes.
- Seen on the emulator's Gboard: typing, word suggestions read from the text (a suggestion tap: a batch of `setSelection` over the word and `commitText`), emoji, backspace over a surrogate pair (one `deleteSurroundingText` of two units), newline in a multiline field, auto-capitalization, the Search key, a hardware keyboard's keys and Ctrl+A, C, V, Back hiding the keyboard and a tap bringing it back, a new note's title taking the keyboard, Gboard's clipboard chip and its Text editing panel's Paste, the layout shrinking above the emoji panel. That Gboard commits each letter (`commitText`, no composing text) in our fields and in Google Messages alike, so composing (`setComposingText`, `setComposingRegion`) is covered by kit's ime tests only, not yet by a composing keyboard on a device (a CJK layout would be one).

## Selection menu
kit decides when, what and where (notes/app.md, Platforms and input); the view shows it as a floating `ActionMode` (`startActionMode(callback, TYPE_FLOATING)`, an `ActionMode.Callback2` whose `onGetContentRect` is kit's rect in view pixels), its items the framework's (`android.R.id.cut`, `copy`, `paste`, `selectAll` with `android.R.string.*` titles). `showMenu` again with the mode up changes it in place (`invalidate`, `invalidateContentRect`): the menu follows a handle drag. A click goes to `nativeMenuItem` (`Ui::menu_pick`; then `ime::Sync`'s after-app check, since the menu is not the keyboard: a cut restarts it); `hideMenu` forgets the mode, then finishes it; a mode the system ended itself reports `nativeMenuGone`. Commands cross JNI as codes (`CUT`.. `SELECT_ALL` in `OsisView`, `command_code` in shell.rs). The system adds no items of its own to a mode on a plain View (Translate and other apps' `PROCESS_TEXT` actions come from TextView itself): issues/android-text-actions.md.

## Build recipe
- One-time, no root: Android command-line tools, `sdkmanager "platform-tools" "build-tools;36.0.0" "platforms;android-36" "ndk;27.2.12479018"` (any later build-tools and NDK work; NDK r28+ defaults to 16 KB pages), plus `emulator` and a `system-images;android-36;google_apis;x86_64` for an emulator; `rustup target add aarch64-linux-android x86_64-linux-android`; a JDK (javac, keytool, apksigner). Android Studio's default SDK dir is `~/Android/Sdk`.
- `ANDROID_HOME=<sdk> ANDROID_NDK_ROOT=<sdk>/ndk/<v> app/android/build.sh [arm64|x86_64]`: `cargo build --release -p osis-android --target <t>` with the NDK clang as linker and `CC`/`AR` for ring; javac (Java 11 classes against `android.jar`) and d8 make `classes.dex`; aapt2 links the manifest; zip adds `lib/<abi>/libosis_android.so` and `classes.dex`; `zipalign -P 16`; apksigner with `~/.android/debug.keystore` (made on first run). Prints `target/<t>/release/apk/osis-<abi>.apk`. About a minute warm, 15 cold on a loaded box.
- Release, not debug: a debug build turns on wgpu's debug labels (`InstanceFlags::from_build_config`), which crash the emulator's software Vulkan in `vkSetDebugUtilsObjectNameEXT`.
- No cargo-apk: 0.10's cargo-subcommand mishandles workspace layouts (it ignores `package.workspace` and the workspace's `exclude`). xbuild is untried; the manual packaging is about 45 lines.
- Run: `adb install -r <apk>`, `adb shell am start -n net.osis.app/.OsisActivity`; logs: `adb logcat --pid=$(adb shell pidof net.osis.app)` (tag `osis`).

## Status
- Emulator with the host GPU (AMD/Mesa through gfxstream Vulkan): renders, Back, insets, the keyboard (above), backgrounding and returning (the surface is dropped and made again). Touch is kit's (notes/app.md, Platforms and input), nothing here: taps, swipes scrolling a page and a list, a long press picking a row up to reorder, a long press selecting a word with handles that drag, the selection menu (Cut, Copy, Paste, Select all at the selection; Copy then Paste elsewhere; a tap on the selection toggling it; following a handle drag, Select all dropping out once all is selected; Back closing it; Paste alone in an empty field), a tap on a handle's disc reaching the field under it, a new thing's title asking for the keyboard (checked with `adb shell input swipe`, a swipe in place for a long press, `input motionevent DOWN/MOVE/UP` for handle drags). A fling is unit-tested only (adb's swipes are too short to show one on these short pages).
- The emulator's software GPUs (SwiftShader, lavapipe headless) lose the device on the first frame; the GLES adapter has no compute. Vello needs compute; vello_cpu would be the no-GPU fallback, unbuilt.
- Untested on a real phone. Untested anywhere: QUIC sync, joining, rotation, dark mode switching (`nativeConfig`).

# Versioning: schema evolution, mixed app versions, format changes
> Summary: Decided 2026-10-14 with owner. The wire only grows: compact field/case IDs, open structs, reader-side defaults, additive-only schema checked at compile time, one schema owns each AK. App-level type changes are views (f on read, g on write) in app code over the old representation; a breaking change is a new ID/AK with f only, the old one becomes legacy, `supersedes` resolves by timestamp. Below the schema: merge is schema-free, unknown data is parked never dropped, one format version with "write the oldest that fits". No retire, no schema-as-thing, no majors, mirroring, lenses or migration VM.

## Problem
Many apps and app versions share data like a file format; apps do not always upgrade schemas, users do not always upgrade apps, nodes with different versions must sync, and the CRDT/sync layer itself must be able to evolve (rarely). Comparable in difficulty to CRDTs and blind sync.

## Three layers of compatibility
1. **Store/relay/merge** (must be universal): merge encodings are self-describing and join needs no schema, so any node joins any aspect state. Blob reconciliation is content-agnostic. A node that cannot interpret something is a blind node for it.
2. **Typing** (per app version): whether an app's schema can type a value. Failures are ordinary errors.
3. **Semantics** (human): invariants in doc comments. Not checkable.

## Below the schema (hard constraints, in notes/constraints.md)
- **Parking rule**: a node never discards, rejects or panics on data it cannot interpret (unknown merge encoding, format version, field ID, AK). It stores, relays, and re-examines after upgrade. "Not understood" is treated exactly like "not yet received": the node lags on that aspect, its own writes are ordinary concurrent writes, convergence covers the rest. Compaction never retires bodies it could not join; parked blobs accept blob-level snapshots/retires from newer nodes like a blind node does.
- **Compatibility surface** = blob contents only: commit header, delta encodings, chunk format, value CBOR. Local store layout, indexes, reconciliation protocol and API change freely (local state is rebuildable from blobs/snapshots).
- **One format version** on that surface. Readers accept every version up to their own forever. Writers emit the oldest version that can express the delta, so one upgraded node never strands a group unless it uses a new feature, and then only on that aspect. The header format is versioned separately from delta encodings (each delta names its encoding), so a node with an unknown encoding still reads the header and knows which things and aspects it lags on.
- **Merge-encoding lattice**: the core defines an embedding for every upgrade edge (LWW register write = reset + insert-all in text CRDT; LWW int write = reset + increment in counter; ...). Join of mixed encodings converts the poorer side, so an aspect's stored encoding is the max seen. The schema's encoding is a minimum chosen by the first writer; downgrades are no-ops; value-level writes (structural diff) from an old app produce good deltas once the aspect is upgraded. Two encodings with no embedding: later write wins as a reset (lossy for concurrent edits, never broken). Note the LWW-write-as-reset case is the expected one while a text aspect is in transition: every save from an old app wipes concurrent text edits. Inherent, old code has no CRDT.
- Crypto/key changes: per-label epochs; old nodes are blind for a new epoch until upgraded (notes/sync.md, not designed).

## Wire representation
- Struct field names and enum case names never go on the wire. Each has a small integer ID, explicit in the schema, never reused. Struct = CBOR map with int keys; enum = tag around `[id]` or `[id, payload]` (notes/serialization.md). Names live in the schema and app code, so a rename never touches data. Per-field overhead was otherwise a third or more of a field's register (timestamp + dot).
- AKs stay strings in the commit header (10-20 bytes against ~200 bytes commit overhead); a schema-relative index would make deltas unjoinable until the schema arrives.
- **Open structs**: writes are validated against the writer's schema (all its fields required at write time); stored state may carry field IDs no schema knows. Readers ignore unknown IDs. An app's structural-diff writes only touch fields its schema knows, so a diff never deletes what it cannot see. The explicit replace variant resets the whole aspect, unknown fields included, by definition.
- **Reader-side defaults**: a field may declare a default (`option<T>` defaults to none). Missing field + default = default on read, never materialized. A field without default cannot be added later and cannot stop being written (see legacy).
- Unknown enum case, field type mismatch, missing required field: typed read of the aspect fails with an error carrying the path; the untyped `Value` API always works; path-based typed reads let an app skip one bad element in a large collection. No pre-declared fallback case, no `Unknown` variant (owner 2026-10-14: apps cannot do anything useful with a case they do not know; failures are the norm in osis). Consequence: a new case in an enum reachable inside a collection breaks old apps' typed reads of that whole collection unless they read per element; the checker should warn on it, and the taxonomy below does not call it free.

## Schema identity and checking
- **One schema owns each AK** (owner 2026-10-14): a schema has a single source of truth (one file, one maintainer), and only it may extend an AK's type closure and allocate field/case IDs. Apps use schemas, they do not own aspects, even when the schema file lives in an app's repo. Another party that needs more data adds aspects under its own schema. So every ID space has one allocator and the additive checker sees every change.
- A schema file is the current wire schema only: types, aspects, IDs, docs, `reserved` IDs, `legacy` items, `supersedes` links, and a **revision number** bumped on every published change. No version history in the file.
- Identity of an AK's version = BLAKE3 of its type closure (referenced named types, IDs, encodings; not docs or local flags like `indexed`, so a comment fix or two copies with different docs are the same version). Identical definitions in two places are the same version by construction.
- Compile-time checker (in `load_schema!()` and the runtime loader) compares against a snapshot of the last published schema (lock file beside the schema; the hash alone cannot check additivity) and refuses anything that is not an additive superset: ID reuse, removed item not marked legacy, default added to a formerly required field (strands old readers) unless explicitly marked, type change of an existing ID, encoding change not on an upgrade edge, revision not bumped. Edits before publishing are free. Namespace collisions (two unrelated schemas with one AK name) are detected at read time, treated as untyped plus a diagnostic.
- Commit headers carry the writer's schema hash and revision (encrypted, cheap). Revision above mine in my own schema's lineage = I am behind: the "update required" signal, with no data-level marker. Hash plus revision also let a node keep per group the oldest revision that has written recently (adaptive compatibility, below) and diagnose what a newer app wrote.
- The parsed schema is an osis value, so the maintainer may publish it as a thing in a group of their own and generic tools may load it from a file; the core does not distribute schemas. (Writing the schema into every group it is used in was rejected 2026-10-14: needs an owner per writer, a membership write on each group thing that data writers may not have rights for, one edge per cell-sized group, and two concurrent first writers mint two things. Now that each AK has one schema, old apps already know which schema wrote what they cannot type.) A value without its schema prints with numbered keys.

## Two kinds of change (owner's taxonomy, 2026-10-14)
1. **Additive**: new field with default, new aspect, encoding upgrade. New IDs, nothing else. Free. New enum case: free on the wire, but see the collection caveat above.
2. **App type change, representation additive + view**: the app's Rust type for the new version is a conversion over the wire type, f on read and g on write, in app code (codegen or hand-written; never in the schema, no VM). Old apps keep working on current data. g gets the current wire value as input (e.g. to preserve a units choice). Where the old representation cannot hold the new data, add a field (or aspect) with a new ID and declare `supersedes`: the new app writes new and g(new) in one commit; codegen reads the new field unless the old one carries a newer timestamp (an old app wrote since), in which case f(old) wins. Ties (same commit) prefer new. A deterministic function of state, so it converges; timestamps are the system's one conflict rule already, so this adds no trust assumption and no round-trip law on f and g. Prefer extension over redundancy. Cost per edit is O(edit): conversion is per element on read, path ops on write.

**Breaking change = 2 without g.** Delete g, mark the old item `legacy` in the schema: still typed and readable (f needs it), never written by code generated from the current schema, its ID reserved forever. Old apps keep working: untouched things still carry old data; on things the new app has written they see the old field as it was last written (stale), or absent/default if the new app chose to reset it when writing the new one (optional, saves bytes, turns stale into the ordinary missing-field error or default). Their later edits land in the old field and win through f by timestamp, so an old app's edit overwrites the new app's intervening edits at the granularity of the converted value: ordinary LWW loss, coarser. Nothing is irreversible: un-marking legacy and restoring g is additive.

Example (owner 2026-10-14): v1 `/measurement: struct { units: enum, value: float }`; v2 wants a float in meters. Stage 2: no wire change at all, the view converts on read and writes back (choose units: keep existing or always meters). Breaking: add `/measurement@2: float` with `supersedes /measurement`, mark `/measurement` legacy; new apps read whichever is newer (converting the old), write only the new. An aspect's wire type never changes (struct to float is not additive), so a change of an aspect's type is a new AK; `/name@2` is a naming convention with no core meaning.

What a break costs: old app versions see stale or missing data on that aspect and their edits lose coarsely. The old node still stores, relays and merges everything, every other aspect and every other app on that device keep working, an upgrade needs no refetch and no migration. Nothing can do better: old code cannot know what new data means.

## "Everyone has upgraded" needs no global agreement
Dropping g, or resetting legacy fields on write, is an app-side decision about which old versions it still serves, baked into a release; the core needs no epoch and peers need not agree. A wiped device blocks nothing; a new device with old software sees newer revisions in headers and says "update required". Optional, opt-in per field: adaptive compatibility, where codegen keeps writing g in a group while any writer there used a revision needing it within a window (from header revisions) and stops otherwise. Default is simpler: g is written until the release that deletes it.

## Rejected (2026-10-14 discussions, keep for the record)
- **Retire** (terminal reset with infinite timestamp, join drops every element under the ID forever; one marker per thing). Bought nothing the design needs: dropping old apps' later writes is worse than honoring them through f; "nothing lingers" is a few bytes; the update signal is the header revision; permanent deletion is unwanted and would be one line if wanted. Cost: irreversible, per-thing markers forever, per-instance markers for nested fields that still miss elements old apps create later, O(group) backfill or a half-migrated group, a special value in join.
- Schema as a thing in every group (above).
- Breaking change = always a new AK with dual writes and no lineage: ping-pong risk, forks by accident. (`supersedes` keeps the lineage and resolves deterministically.)
- Majors on the wire with core-managed bidirectional mirroring (f/g over aspect sets, derived-commit flag, deterministic derived IDs): duplicates every aspect under migration, O(aspect) per edit for whole-value f, needs caches, and a missing g made old nodes systematically overwrite newer edits. A path-level variant kept duplication small but needed a path language in the core and still could not express the interesting conversions.
- Declarative lens language (Cambria-style) in the schema, or any code/VM in the schema format.
- Pre-declared enum fallback case / generated `Unknown` variant.
- AK as index into the writer's schema; hashed AK names (no gain at typical lengths).
- `supersedes` resolved by comparing old with g(new): needs g∘f exact on the old representation, which float conversions break, so it would systematically prefer old.

## Open details
- DSL syntax for IDs (explicit `1 title: string` style, with a tool that assigns next IDs), defaults, `reserved`, `legacy`, `supersedes`, `revision`.
- Lock file format for the last published snapshot.
- g's codegen contract (receives current wire value); timestamp of a composite old value = max over its leaf registers and resets.
- Version-skew simulation as a standard test category: nodes on mixed schema revisions and format versions, properties: wire convergence and stable per-reader projections.

## Prior art
Protobuf (IDs, reserved numbers, additive discipline, one owner per message), Avro (reader/writer schema resolution, defaults), Cambria (Ink & Switch; lenses over ops, rejected here), SQLite's file-format promise (read everything older forever).

# Rust API: implementation
> Summary: How the `osis` crate is built over the engine and sync engine: module map, the handle's lock and `after`, writes and sources, futures, sharing helpers, status, large values, text sessions, tests. The API's shape: notes/api.md.

Module map (`core/osis/src`): `handle` (`Osis`, `Config`, `Store`, `MemStore`, the lock and `after`, schema registration), `internals` (doc-hidden: the `Internals` trait on `Osis` with `engine`, `sync_engine`, `waiting`, `take_actions`, `feed`, plus `ManualNet` and the `node` re-export, for the CLI's `inspect`, the sim and tests), `net` (`Runtime`, `Net`, the driver host, `Waiter`/`Pending`), `commit_id` (`CommitId`, `CommitPos`, `CommitFrom`, opaque over the engine's), `value_type` (`ValueType`), `account` (pairing), `share` (grants, demotions, links, cards, nodes, peers, group sync, status, bundles), `disputes`, `serving`, `clients`, `sources` (group sources), `port` (the client port), `retention`, `keep`, `read`, `write`, `large` (`ValueStream`, `len`, `set_stream`), `text` (`TextSession`), `watch`, `track` (tracked reads), `backlinks`, `commits` (`Commit`, listings, listeners, undo), `diagnostic`, `keys`, `error`, `testing` (doc-hidden test knobs).
- **Handle and sync**: one mutex over `Locked { sync: SyncEngine (owns the engine), events, seq, waiters, status, offers, connections, group_sources, remerge }`. Every call under it ends in `after`: engine events go to the dispatcher in commit order; if the call (not the driver) caused events, `SyncEngine::handle(Event::Local)` runs; then the status (a `Msg::Status` to watchers when it changed or `remerge` is set, a `Stranded` diagnostic on a new stranding) and the waiters. Network actions leave through `Net` under the lock (FIFO, so frames keep their order): `Off` drops them, `Manual(ManualNet)` queues them for a test harness (`Internals::take_actions`/`feed`), `Driver` sends `Control::Apply` to osis-node's `sync::driver::run_shared`, on the app's or osis's own tokio runtime, with the handle as its `Shared` (a weak reference; the driver stops when the node closes). Wake timers hold a weak sender and are armed only for a waiter that did not resolve at once.
- **Close**: `close()` fails `Invalid` from a callback and `StillOpen` while other user handles exist (`Life` counts them; osis's own short-lived holders, the dispatcher running a callback, a driver engine call, timers, use uncounted handles: `Osis::internal`, `WeakOsis::hold`), else waits uncapped until the store is closed; dropping `Net` sends the driver `Shutdown`. Engine calls run in `block_in_place`, which a runtime shutdown does not wait for (the task polled on after one would hit a timer of the shut-down runtime and tokio panics), so the driver task holds a drop guard:
  - osis's own runtime (`Runtime::Own`) is shut down by an `osis-sync-stop` thread once the guard dropped (`STOP_WAIT` 5 s for the driver, then `shutdown_timeout` 5 s; a thread, since the drop itself may run inside that call; the store is already closed: `Inner` drops `eng` first), and `close` waits for that thread, so every task on it, the `osis-host` store's too, is gone and `host.redb` is free for a reopen;
  - on the app's multi-thread runtime `close` waits for the guard (uncapped, in place when inside it; the driver awaits the `osis-host` task's end on `Shutdown`), so the app may shut its runtime down next; on a current-thread runtime not at all (no engine call runs in `block_in_place` there; the `osis-host` store may stay locked until the app drives that runtime again);
  - the driver polls no timer while a control message waits, so a `Shutdown` queued by a drop before the runtime's shutdown is seen first (an app dropping the runtime while the node is open can still hit the panic).
- **Driver death**: a driver task that panics (or that its runtime drops unfinished while the node is open) ends sync for the handle's life (`net::Watched` around the task, `driver_died`): under the lock it sets `Net::died` and fails every waiter with `Network("sync driver panicked: <msg>")` (else they hung: their wake timer sends to a closed channel); later waits, `listen` and `listen_socket` fail the same way at once; then a `SyncStopped` diagnostic (best effort: the engine may be what panicked); the panic goes on to the runtime. `osis serve` (and `diag --follow`) exit 6 on that diagnostic; the app shows it. A thin client's connection thread (`port::client::Io`) fails its calls and closes its subscriptions in `Drop`, so a panic there does not hang a `node_task` either.
- **Write and sources**: a `Write` records its API ops (`WriteOp`: create, group ops, path ops at a key-table index, expiry as wall time, retention, purge, delete, release), each call's checks done as it is recorded, and builds the engine `Mutation` at `commit` under the lock (`delete` expands against the state held then, and its expiry conflicts surface there); the op list is the request of a write at a node (notes/client-port.md). Writes act as `me()` unless `act_as`. Every call addressed by a tid, group or scope starts with `self.source(..)` (`sources::Source::{Local, Node(connection)}`), a match at each site.
- **Futures**: no call takes a timeout (Tess): a future cancels on drop, a caller wraps it in its own runtime's timeout. `wait_until(check)` registers a check on the sync engine and status, run after every change and on any call; without a runtime it fails `Network` at once, as does a link naming no saved peer on a node that dials nobody directly (`Inner.dials_peers`). A waiter whose future was dropped is removed; held link keys go with a guard on every outcome; a waiter dropped unanswered answers `Closed`; a driver gone answers `Network` (`driver_died`); a node closing answers port rows `Closed` (`Job::Closing`). `Pending` resolves through a slot with the stored waker, runtime-agnostic (tests poll with a no-op or park/unpark waker).
- **Connecting** is `async` too. A thin client (`connect`, `connect_socket`) needs its node for `me()` and all else, so it returns connected or fails with why its one attempt did not, leaving nothing; a node's `connect_node` keeps the connection and retries, `status` showing it, as the node works without it. `CONNECTION_WAIT` (30 s) bounds one attempt, and a sync write across a drop, which has no future to drop.
- **Account**: `create` runs flows' `create_account` (the sync engine is built first so it sees every event), writes an empty `group.0` on the home group and saves the peers given (app record `saved_peers`). `open` reads the engine's account record (`Storage` without one).
- **Sharing**: each call is a flow plus `carry_out`. `grant` maps a missing `keys.0` to `UnknownActor` and `Permission` to `needs: Admin`. A demotion syncs nothing first (notes/api.md Demotion and addenda). `sync(group)` gives the group secrets of its own and its sync ID in one commit (`Engine::give_own_secrets_on`): a label whose genesis is at its first admin's derived epochs cannot be verified by a holder reaching it through a link actor (issues/node-sync-gaps.md). Links: made by the engine flow `create_link`; single use is the link's `flags` bit (the redeemer removes L in its redemption; finalization is node-sync's). A self-removal (`leave`) is sealed and uploaded before the leaver drops what it lost (`SyncEngine::drop_lost`). `contact_card` makes profile P (first admin: me, a group of itself, with its own sync ID), holds the account's `created.0`/`keys.0` commits under P's sync ID as certificates, makes a read link to P and keeps its text (`contact` record). `import_contact` holds L, follows K's label, waits for P's first admin's `keys.0`, drops L.
- **Sharing helpers**: `holders` is a breadth-first walk over rosters. `set_role` loops over its first way for the holder: a direct grant goes through `lower` (or `grant` for a raise), a path through a link actor of a held seed thing (`held_links`, ended ones included) through `remove_joiner` (the engine's `revoke_joiner`: one commit, so no half-removal); anything else is refused. `add_peer`/`remove_peer` (deprecated with the peer list: issues/deprecated-terms.md): `follow_labels` (one commit of `label.0` host-list sets) before the list is saved, then `follow_inbox`.
- **Status**: per sync ID from `SyncEngine::label_status`, mapped by `share::label_state` (stranded, else no source: `NotConnected` or `Refused`, else `Synced` or `Syncing`); a group shows its worst sync ID. `wait_synced` judges each sync ID (`share::synced`), not the group's worst state; `Thing(t)` scopes the synced groups whose closure holds t. Deliveries: `SyncEngine::pending_about` lists what each pending one is about (an inbox delivery's `SentInbox::things`, a deposit's group; the outbox is stored, so a restart sends it again, and a queued deposit's peer is dialed until it takes it, `wanted_nodes`).
- **Diagnostics** added here: `NotSynced` (after a commit adding a thing to groups none of which is synced; the engine's for things a subgroup cut, by any cause, leaves in no synced group), `Stranded`; `Engine::report` dedups them.
- **Commit listings** (`engine::listing`; the rule is `listing::listed_part`, which undo's `kept` uses too; undo, redo and listings read `Engine::held_commits`). A page is O(log n + places walked), and a filter matching few walks the whole address; `reverted_by` and `in_effect` scan the commits on a listed commit's value aspects stamped after it, so a page from `Oldest` of an aspect with n commits costs O(page × n), as does each listener event for an old commit (stated, not optimized). Listeners are off until an open's first one (`Engine::watch_commits`, sticky) and cost nothing on an aspect none is on. A join on a listened aspect costs the commits it superseded (`Killed` dots, `listing::note_killed`), each told when it reads no longer listed; only a rebuild (a validity flip, an un-merge, a drop, a paged reset, O(commits held) anyway) compares the whole listing before and after. A part leaving at its keep bound changes no state: its aspect's one timer tells it (notes/engine-retention-history.md Leaving history). Dispatch finds subscriptions by (tid, ak), thing, group and role slots, O(log S + matched); the dispatcher coalesces per aspect. Purge requests are stored per aspect only when they name more than one delta, by name under `pn/` + aspect + commit. A register edited twice undoes twice (spec/crdt.md §4.6).
- **Ephemeral signals**: a fire of a `+~` aspect is an ephemeral write the engine signs at write time as a relay-only commit (notes/ephemeral.md Ephemeral signals); `on_fire` hears it once here, like a remote one.
- **Large values**: reads materialize against a byte budget; `stream` walks the chunk tree one chunk per call (`Engine::next_chunk` under the lock); `len` reads the CBOR head of the first chunk; a seek fetches nothing, the next read fetches the root and the nodes on the path to the target chunk (`TreeReader::seek`, lengths in tree nodes). `set_stream` reads the value whole, then sets it (issues/api-deferred.md).
- **Text sessions**: buffer plus base; `commit` writes `Op::Edit { base, new }` on a `text` position (rebased by the crdt; a paged text resolves it on the pages around the change when the text there still matches `base`, notes/engine-paged.md Paged state) or `Set` on a string register.
  - Two locks: `st` (base, buffer; taken briefly, by keystrokes too) and `save` (held across a save or a merge, never by a keystroke). A save snapshots `(base, buf)` under `st`, commits with `st` released, then sets `base` to the snapshot: typing meanwhile stays pending, and `save` keeps a second save from committing the same edit.
  - The session subscribes to its aspect undeduplicated (notes/listener-design.md Text sessions) and on every call `merge` reads the field under `save`: equal to `base`, nothing; else save, read the merged text, and if no typing came in meanwhile set base and buffer to it and call `on_merge` with `osis_crdt::changes` (the gaps of the Myers LCS over chars) as splices, else go round again.
  - `edit(base, new)` places the change in the buffer under `st`: one splice of `base -> new` carried through the changes `base -> buf`, read as one change where that is disjoint, else as the char diff, so typing between two merges stays there; an insert inside a merge's change goes to its end. So a merge landing between the UI's read and its keystroke cannot move it.
  - The first edit after a commit arms a timer on the node's runtime (`Net::after`: a tokio sleep, then a blocking task) that commits once the session has been idle `idle_commit` (re-armed for the rest otherwise; it clears `last_edit` before saving, so a keystroke during its save starts a new pause instead of saving inline); without a runtime the next edit after `idle_commit` commits inline; drop commits (a failure reported as `Uncommitted`).
  - `known` (the thing read known at open or after a commit) makes the save's write check `has_content` under the commit's lock (`Write::alive`, so a delete ingested between check and write is seen): false fails `UnknownThing` and the buffer keeps the edits (a merge then leaves the buffer alone). A commit that fails otherwise (lost write access, storage) reports `Uncommitted` and keeps the edits for the next try; a merge after a failed commit drops them. `Knobs::text_save` runs between a save's snapshot and its commit (the keystroke-during-save test).

- **Tests**: core/osis/tests/it, one module per concept (`api`, `watch`, `commits`, `undo`, `sharing`, `port*`, `lifetimes`, ...), and the standard-data scenarios (notes, tags, contact, event) end to end (notes/std.md); `sync` and `sharing` run on `World` (core/test/sim/src/world.rs: `Runtime::Manual` nodes and osis-host `Hub`s under one `ManualClock`; futures polled with a no-op waker); `runtime` drives the tokio driver over `InProcess` against another node's driver (QUIC by hand, ignored).

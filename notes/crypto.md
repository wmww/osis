# Crypto: rationale
> Summary: Why suite 1 (spec/crypto.md) is what it is: primitives, per-role epochs and boxes, history boxes and establishment, frozen coverage, holder actors at depth 0 (seal, stale, merge, key access, possession, blocked), delete keys, costs, the osis-crypto and osis-keys implementation, rejected options. The suite was the agent's call with Tess deferring; hybrid post-quantum boxes follow from long-lived secrets having to resist a future quantum attacker.

## Primitives
- **Ed25519**: 32-byte keys, 64-byte signatures, fast verification per commit. Strict verification so every node accepts exactly the same signatures; no batch verification (spec/crypto.md §1 "batch and single agree" then holds trivially; add batch only with a test that it rejects exactly what `verify_strict` rejects). PQ signatures are not required (spec/requirements.md) and ML-DSA-44 (2420-byte signatures, 1312-byte keys) is over ten times the commit floor. If ever wanted: a new enum case; nodes move by add-and-remove, a root key only to a new account; stored data stays valid. An in-place successor key in `keys.0` would be a convenience only, and its fork rule could only be keep-the-first-seen, as for colliding creation records.
- **Hybrid PQ sealed boxes**: boxes sit on hosts forever and lazy rotation keeps old secrets valid for old content, so a classical box harvested today would yield every blob under that secret, forever; a later migration cannot re-protect it. The cost lands only on role changes (about 1.2 KB per holder and role), never per blob or commit. Generic hash-everything combiner (secure if either KEM is). X-Wing was a draft at decision time; if it is an RFC by implementation, add it as a second case.
- **XChaCha20-Poly1305 over AES-GCM**: 96-bit GCM nonces plus frequent local unit rewrites invite nonce reuse; GCM is slow without hardware and in WASM. A hardware-speed suite can be added for multi-GB values.
- ML-KEM's internal SHA3/SHAKE is internal to that primitive; "one hash function" means every hash osis computes itself.
- **Wire details** (spec/wire.md): one signature domain per signed object (deposit, delete and signal publish have their own), so no signature verifies as another kind. The symmetric box's nonce is BLAKE3(AD), because its key `kdf("box", s)` repeats across every epoch boxed under one s, while the AD is unique per (actor, holder, role, epoch). Agility enums are osis enum values; case 1 matches suite 1.
- Not in the protocol: password hashing (an app exporting a recovery key uses Argon2id), transport crypto (TLS 1.3, QUIC, iroh).

## Keys, epochs and boxes
- **A KEM key per role** for non-key actors. Effective role is the minimum along the chain, so a box sealed to A's write key must open only for A's writers. Example: team A holds admin on doc T and has read-only holders; T's admin box to A must stay closed to them, else they get T's admin secret, hence its admin delete key and label keys ("readers only read", spec/requirements.md). One KEM key per actor would be held by A's readers (they need A's read boxes), and binding role and epoch only in the AD is replay-proof, not confidential; it is safe only where every holder holds every role (by convention an account), which a sealer cannot know. One box per holder actor carrying all its roles, sealed at its top role, would lock out its lower-role holders. Cheaper variants (one ML-KEM key per actor with an X25519 key per role; roles sharing a key while their holders coincide) were declined by Tess (notes/chat.md Costs).
- **Epochs per role**, not per actor: a writer may rotate read and write but not admin; per-role epochs make each role an independent chain of secrets, boxes and history boxes, and `keys.0` an independent keyset per role that its rotator writes. A per-actor epoch would have to say which roles "carry over" and where their boxes live.
- **One box per (holder, role, epoch)** for every holder, key actors included (Tess's decision): a rotation of one role removes and writes boxes of that role only, so no other role's secret moves, and the covers rule and re-seal trigger look at exact keys. Rejected: a key actor's box carrying every role, keyed at the top one. It needed a guess at what such a box carried (it could not be opened to check), a forced rotation of a carried role, a refusal to rotate when a carried secret was not held, per-fork exception boxes, and still stranded holders (a box ordered after a fork's rotation was credited with it though its writer never held it).
- **`keys.0` holds the current keyset only**: nobody seals to an old epoch on purpose, and a granter with a stale key still succeeds because holders keep old secrets. The deposit seed lives beside the keysets (one per actor; each label's deposit key derives from it by label ID, notes/sync.md). Refreshing it is a MAY against an ex-holder filling the budget, because a refresh also refuses the stranded heartbeats of holders that missed the rotation (re-share by hand, notes/sync.md).
- **Key actors have seed-derived role secrets** so a thing owned by a key actor (a node's local thing, an account under its recovery key) is a plain thing like any other; they never rotate and are never shared. Their KEM key is seed-derived and never rotates: the seed is the node, a compromise is a node removal, and a keyset epoch for key actors would put an epoch into every box and claim-set rule for a case nothing uses (nodes and link keys are replaced by add-and-remove; a suite migration is a new key actor).
- **Link keys are full key actors** (signing and KEM keys from the seed). Rejected: a sign-only link key from whose seed K's secrets derived, which handed every read-link holder K's admin secret and label delete key, and a symmetric link box only the sharer could write, which a writer's rotation of K could not refresh (notes/permissions.md, Links). Cost: 1.2 KB per box to L per rotation of K, and one hybrid entry box per step of K's label.
- **Symmetric box form** when the writer already holds the recipient's role secret (a thing's secrets to its owner): 49 bytes plus the epoch of the recipient's secret (to a holder actor, plus its 64-byte possession signature), which the covers rule needs (without it an owner's rotation after a lost node would not make the thing's epoch stale).
- **Big rosters**: a rotation's boxes page like any map, and `secrets.0` compacts by ordinary paged compaction snapshots, so no roster size makes rotation impossible.
- **Self-verifying epochs** (spec/crypto.md §4): an epoch's nonce is `kdf("epoch", s, actor || role || le64(n))`, 32 bytes, so each source of a secret (box, history entry, entry box) is checked alone, in any order, by recomputing its epoch. It removes "which copy do we trust" state, which was order-dependent: e.g. recording the first keyset seen per epoch let a writer re-publishing an epoch's keyset with junk keys make late joiners refuse the genuine box for good. Hash the secret, not the keyset: holders check either at the same strength, a non-holder gains nothing (a writer can name a fresh epoch matching junk keys), and checking the keyset costs an ML-KEM keygen. Actor, role and n are bound for domain separation. 32 bytes: one ID, one secret by plain collision resistance (16 would let a rotator equivocate at 2^64 work). Establishment still decides planted epochs (anyone writing a box, entry or entry box can make up `(n, s)`), huge n (headroom), false supersession by a history box opened with a genuine secret (bounded: such writers could rotate anyway), and junk keysets seen by non-holders (the writer DoS on sealers, healed by re-seal). Cost: one keyed BLAKE3 per secret learned.

## History boxes and establishment
- **History boxes**: holding a role's current secret opens every older one; a holder removed before epoch n opens nothing newer; a join costs one box per role, not one per epoch. A grant or re-seal re-writes the history box of each epoch it boxes (same ciphertext, a register rewrite), because the recipient could not otherwise fetch it: the rotation commit carrying it is wrapped under the epoch the recipient lacks (TLC R3). 32 bytes per earlier epoch per grant.
- **Only established epochs' secrets go in a history box** (TLC R9): a node re-sealed at e before e's commit reached it holds e's secret but not the departure e carries, and would otherwise rotate over e and hand e's secret to the holder e removed.
- **Establishment** (spec/crypto.md §4) is the one notion behind "may encrypt under", "current", what a history box carries and where a re-seal may be made. Fixed and derived epochs are established; a rotated epoch is when the node holds its valid rotation commit or a `secrets.0` snapshot keying it, and, if it holds the secret, the **names** in its history box are met. Names: each rotation's history box lists, from its rotator's own timeline, the departures from the actor it held (and itself, by `ts` and signer, when it departs someone). A node uses the epoch only once it holds them all, so it never passes on an epoch whose rotator knew of a departure the node lacks: its own roster then has the holder departed and boxes it nothing. Every link is first hand: nothing follows another rotator's list. Unestablished secrets read; nothing is written under them.
- **Rejected establishment rules**: "settled" chains, where each rotation's keyset listed the rotation commits of what it superseded and a node followed the chain down to an established epoch. Six rounds of fixes each closed one way a link was someone else's word (a writer's own list skipping a removal, a forged valid rotation listed beside a genuine unsettled one, a snapshot standing in for a removal, invalid commits passed through by name, re-grants hiding the chain, injected forged claims). Also rejected: a departed-holder set in the history box (hearsay: every boxing path must consult it, and a writer could bar any holder); re-sealing only to holders the rotator boxed (closes re-seals, not the rotation path); an age rule (clock-dependent); a roster hash from the rotator (detects a mismatch, cannot repair it); establishment from the node's own timeline without names (a node cannot know what it has not received).
- **Frozen coverage** (spec/crypto.md §4): an epoch covers exactly the departures from its actor that its rotator named; a node relies on it for nothing else, and boxes decide nothing. Any rule reading coverage from boxes ("holds no box for M") has one hole: a missing box means either "excluded" or "unknown", and the epoch gets credited with a departure its rotator never knew. The shape (C2, direct holders only; TLA `MC_c2_box`, AMBIGUITIES R19): G grants D at e0; a2 rotates to e1 before reading the grant (e1 boxes no D); a1 holds the grant, not e1, and removes D as e2 (a fork of e1 at one n); W, holding e1, e2 and the removal, takes e1 (lower nonce), which holds no box for D, so "covers", and writes under it; a2, holding e1 and the grant but not the removal, re-seals D at e1; D reads W's content. Each departure carries the name a rotation knowing it writes (`Departure::at`: its newest lowering write, a finalize for a timed end, or the demotion whose audit dropped its grant; a box holder with none of these is attributed to nothing) and the roles it concerns. Liveness: a rotator names everything it knows (`thing_names` must stay a superset of `events`, else a rotator never covers what it knows: a livelock), so its own epoch covers what it knows; two rotators alternate at most once per departure one knows and the other does not.
- **Merge** (rule 3): a node that may rotate rotates while any current epoch, not only the newest, misses a departure it knows (`osis_keys::merge_due`): a fork made without knowing the departure otherwise stays current and may win the (n, nonce) order. A current epoch whose secret the node lacks covers nothing (its history box is closed), so that rotation supersedes it too (one extra rotation, never a loop). Any other fork is merged by its merger only (`osis_keys::fork_merger`: the maker of a current epoch other than the newest, or anyone when no such maker may rotate): two knowing forks of M anchoring A's two forks left M unsealable for good (cycle seed 1838), and every admin merging ping-pongs (two nodes holding the same fork merge alike each round: the osis World sim hung).
- **Supersession is read from the rotation commit**: the epochs its keyset lists (the same at every node in any arrival order) and, at a node holding the new secret, those its history box lists. They differ only on derived epochs, which have no rotation commit. Rejected: reading supersession from the commits' box removals (a re-grant hid the chain and a departed granter steered it to a forged claim; an epoch whose rotation boxed nobody stayed current at nodes that could not open the history box), and taking it also from the `keys.0` keyset the applier held before (order-dependent: a rotation made unaware of a concurrent fork superseded that fork wherever its keyset had won `keys.0` first). A rotator removes the boxes at each of its current epochs. Tests: `rotation::supersession_independent_of_arrival_order` (osis-keys), the re-seal invariant in `forked_reseals_*` (osis-engine).

## Holder actors at depth 0
Tess's decision (notes/keys-requirements-study.md): a group never looks inside its member actors. No names of departures below the actor, no keyset names, no departure walk. A departure inside a holder actor M reaches A only as M's new keyset. Rules, all pure functions in `osis_keys::members` with the engine gathering inputs (`rotation::members`); model core/test/tla/rotation/Depth0.tla (README table).
- **Seal** (rule 1, `seal_keyset`): M is boxed at the newest held valid keyset of M that is or descends from every anchor (the keysets A's current boxes to M name), through held valid keysets only (a forged keyset lists everything). Without anchoring, A's next rotation moves onto an ignorant fork of M and its history box hands A's content since the removal to the departed node (`D0_member`). While the anchors fork (no keyset, tainted or not, descends from all) a rotation, grant or re-seal waits for M's merge (`Seal::Wait`): leaving M out instead dropped the anchors, and the next re-seal sealed M at its newest keyset, perhaps an ignorant fork (`D0_fork_out`, `D0_fork_old_safety`). A removal (a finalize too) then goes without its rotation: the role ends at once, the departure stays uncovered, so A's rotation is due and nobody that may rotate encrypts under A until it is made (`D0_fork_rm`). Holding the removal itself would let a writer of M withholding M's merge keep the removed party's role on A. One rule for every rotation that cannot be made yet: the removal applies, the rotation is due, nobody encrypts meanwhile; only a remover lacking a current secret waits (for a re-seal; a lockout: notes/lockout-recovery.md). With a tainted anchor and no keyset, M is left out and re-sealed once one exists (waiting on taint held A's removals while a grant stayed hidden: cycle harness, 1.6% of seeds).
- **Boxes judged**: every rule reads the `secrets.0` state's boxes; an invalid delta's boxes count for nothing. Such a box still opens, but carries only a secret its author held: it could hand that on anyway, and an author lowered below that role has a departure of its own that rotates the role. Counting them let a reader force one rotation per junk commit, protecting nothing (`reader_junk_boxes_force_no_rotation_spec_crypto_4`); the honest concurrent-demotion grant is the stated limit (`invalid_grant_box_judges_nothing_spec_crypto_4`).
- **Stale** (rule 2, `stale`): a box naming a keyset held invalid, tainted, or listed by a held valid keyset of M; the node rotates before encrypting. Not "any newer keyset" (that moves A onto an ignorant fork), and an unknown keyset is not stale (a co-writer may have sealed to one not received yet). Staleness carries a removal up: M's knowing rotation lists the keyset its departed party opens, every box to M at it goes stale, and so on up. `ensure_rotated` cascades over the holder actors this node may rotate first (sealing to M is encrypting under M's epoch), so one rotation of A suffices where the node may rotate M. Stale and keyless boxes block only the roles the node may rotate (spec/crypto.md §4): a reader held back by one placed no chain certificates, so M's new keyset never reached A's rotators.
- **Key access** (rule 4, `key_access`): no key cycles. Actor grants in an agreed order (an owner's implicit edge from creation first; then by the key of the write starting the grant's standing, `Timeline::standing_since`; ties by target, holder). A grant whose target's key already yields its holder's over the earlier keyed grants is keyless and boxed nothing; only grants inside a strongly connected component are judged one by one. The knowing re-key: a current epoch boxing a holder whose grant is keyless rotates. A new grant is judged with the owners of both ends added (an actor owned by its target, a thin client minted by the account, closes a cycle through the implicit edge though it holds nothing yet: keyless). Cached per roster change (`Core::key_access`). After owner removal the first admin's implicit edge must keep counting as a grant at creation (never keyless); its removal may make a later keyless grant keyed (a re-seal, as a new grant).
- **Taint** (rule 4b, the coordinator's call: churn while a host withholds a grant beats an endless leak): a keyset of M boxing a holder whose grant on M is keyless is stale and never sealed to. A box to a departed actor holder is a departure, not a taint (counting it locked a member's group out of A after the member's self-removal from M). M's `secrets.0` is read for taint only when some grant on M is keyless.
- **Possession** (`osis_keys::possession`, judged in `apply::validity::possessed`): a symmetric box to holder actor M is signed by the keyset's possession key (published in `keys.0`, like `delete_key`), per box over the AD and wrap, so not copyable; a rotation (or a removal of a box to M) counts its author's role through a holder actor only where it boxes M so. Without it a writer of A through M, removed from M where nobody syncing A knows, rotates A sealing M's new keyset without holding it (`D0_rm_*`). No rule judges a box alone: invalidating a box (an invalid box still opens for its keyset's holders) only hid a key cycle from the knowing re-key and taint (`D0_box_rule`; the cycle harness at full size, seed 1032), and demanded a signature from authors whose role on M ran through keyless grants. A box at a keyset with no held valid body is not judged (as for staleness): judging it made readers who cannot see M's keysets refuse honest rotations for good. Facts noted from the body (`Indexes::shown`, kept in `Dropped::shown`), judged again when the holder's keysets change (`apply::keys::keyset_changed`). It does not stop W forging X1's keyset itself (it writes X1): the forgery limit.
- **Blocked through holder actors** (`rotation::blocked_epoch`, model `D0_above`): sealing M at keyset k is encrypting under k, so a k blocked at the node (uncovered by a departure from M it knows; stale or keyless for M's rotators) leaves M out of A (`Sealed::Out`, re-sealed once M rotates), and an epoch of A boxing M at a blocked k is blocked too, at any height. Needed because a removal can go alone: A stays uncovered while its rotation waits, and a rotation of G above A sealing A at that keyset let the removed node read G's new content. Out, not Wait: waiting froze G's rotations with A's and still left G's existing epoch to write under. Only epochs whose secret the node holds are judged (it cannot open another's history box; counting such an epoch as uncovered would bar a reader of M from ever sealing M's write role once a writer left M), so "never looks inside" means "never past what the node itself holds" (notes/questions-for-tess.md Q12). Uncovered binds every node knowing the departure; stale, keyless and the box clause bind rotators only, so a reader still places the revokes and certificates that tell the rotators (`revokes::revoke_about_author_placed_spec_permissions_4`). Left out lasts until a rotator of M passes a label of M or of a thing above it; every sync pass rotates what is due first (`usable_keys`, `issue_step`), so no eager trigger is needed (`sharing::team_reads_again_after_a_member_left_spec_permissions_3`). Stops at actors the node may not rotate, which leaks: issues/blocked-walk-stops-at-readers.md.
- **Carried**: a rotation, grant or re-seal places under A's own labels the rotation commits of the keysets its boxes to holder actors name (`rotation::carry`), so A's writers can judge them: a forged keyset is judged invalid only by a node holding its body and the removal.
- Index: `Indexes::keysets` (per actor, each valid keyset with its list and KEM key, from valid `keys.0` bodies, kept once dropped in `Dropped::keysets`, rebuilt on validity flips); held invalid keysets are looked up on demand (`rotation::members::held_invalid`).
- **Limits** (spec/requirements.md, Permissions): a node removed from M reads A's content written under keys sealed to an ignorant or forged keyset of M (since its removal, by history boxes) until M's next knowing rotation reaches A's writers; a forged keyset whose body a host withholds from a writer that knows the removal stays unknown, so not stale, there. Hidden grants: a sealer lacking the earlier grant seals into a key cycle; with taint the leak stops once the writer holds the grants and the cycle's commits.

## Wraps
- **Opening is not encrypting under**: an open signature proves possession of the read secret to a host; the departed holder holds the same key, and nothing downstream relies on the open. Treating it as encrypting under deadlocked a re-sealed holder (it needs the sync key to fetch the commit that establishes the epoch). Stamps, steps and deletes are encrypting under: others act on them.
- **Rotation commits wrap under the superseded epoch** (the only exception to wrapping under the newest): the commit carries the new secret, so under the new wrap only its author could read it. The leak to an ex-holder via a dishonest host is the new epoch's box map (notes/label-access.md).
- **Wraps name no epoch**: a cleartext epoch byte would leak rotation timing per blob to save one tag check. A lagging relayer's older-epoch wrap extends an ex-holder's reach by that blob (spec/requirements.md, Permissions). An uploader wraps under the newest *current* epoch whose secret it holds; a node holding no current secret (the rotation it received boxed it nowhere) is stranded and places only its heartbeat, under the newest secret it has, which tells co-holders which epoch it is on.
- **Blob encryption never takes a caller key**, so a rewritten blob (purged delta) always gets a fresh key and ID.

## Delete keys
Signatures under blinded keys (Tess's decision, over hashed tokens): one mechanism for every level, and a writer that is no admin lists the thing's published admin key, so a thing admin who is no group admin deletes a writer's data at hosts (hashed tokens needed the admin secret to list level 1).
- Each blob commits to A' = h·A with h from A, the prefix salt and a 16-byte random **blind** in the encrypted header (Tor v3 style). Without the blind h would be computable from A alone, and A is widely known (level-2 keys travel in chain certificates and contact profiles, a key actor's is its signing key, a group's admin key is known to its readers), so a host colluding with any contact could link an author's blobs across groups (spec/requirements.md, Data a node cannot read). Only header readers compute A'; only the holder of a signs; a delete reveals nothing. Chunks and header-list blobs use the blind of the header that introduced them (`Reuse::index`'s `blind_of`). Blinded signing derives the nonce prefix from the seed, salt and blind, so two blinded keys never share a nonce.
- The label key signature stays: every past holder of an epoch's secret can sign with its delete key, so only the label key proves current roles.
- A thing without secrets of its own uses its delete base's keys (its owner's admins are its admins, so the right holders are the same and nothing per thing is published); a key-actor base uses its signing key (public through the creation record; key actors never rotate). The base is the first actor in the chain with secrets of its own whatever the role (all three come at once), so a thing whose `keys.0` has not arrived is not writable rather than wrongly listing its owner's key. Residue: a planted reading-only box for a plain thing creates a `secrets` entry with no keyset, so the thing is its own delete base and unwritable until its `keys.0` arrives.
- A grantee learns the target's admin and write delete keys from the inbox payload (`Core::delete_hints`, persisted, used until `keys.0` arrives), so it writes and self-removes at once; link redemption gets them from K's inbox. Hints are kept only from a commit that applied valid, touches the thing and is by an admin of it; the first stays, `keys.0` replaces it (`Core::promote_hints`).
- One level-2 key per commit (the author chain), checked at receivers: header-list chunks and tree nodes commit to it alone (Tess: one uniform rule, no cutoff); at hosts the author chain deletes them by its delete key, else the label delete key, so a thing admin who is no group admin waits for a group admin there (accepted).
- Engine: `delete_key(level, base, author)` (newest held), `delete_candidates` (every held epoch); keysets carry `delete_key`.

## Costs
- Grant or rotation: one sealed box (about 1.2 KB) per (holder, role, epoch) written, key actors included. Measured (osis-keys, one-off): an account with four key-actor admins (three nodes, recovery key) removing a node rotates all three roles: 12 sealed boxes, 14.4 KB (1196 bytes each), plus 267 bytes of history boxes; one box per key actor carrying every role would be 4 boxes, about 5.1 KB. An admin grant to a key actor: 3 boxes, 3.6 KB (one carrying all roles: about 1.3 KB). A write rotation of a key-actor admin is one box.
- History: 32 bytes per earlier epoch plus a tag, and about 75 bytes per name (one per departure from the actor ever and per audit-drop target; 27 more when the rotation departs someone itself), in every history box a rotation writes and again in each grant's or re-seal's copy. Measured (osis-engine probe, a 10-reader group removing readers one by one): the read history box grows 57, 119, 231, 343, 455, 567 bytes, about 112 per removal (36 the earlier secret, 76 its name), against about 1.2 KB of boxes per holder. Worst case: 1000 departures make about 76 KB per history box per role (issues/rotation-names-grow.md). Held epochs keep their names in the actor's local epochs unit, re-encoded whole on each save: O(epochs x names) per rotation.
- `keys.0`: about 3.6 KB for three roles. A contact card (QR-sized) is a link to a profile thing holding `keys.0`, since the keyset is too big for a QR code.
- Delete keys (measured, `budget_minimal_commit` and arithmetic, a minimal `author_or_admin` commit, two levels): header 322 bytes plaintext (two `[level, 32-byte key]`, the 16-byte blind), prefix 33-byte commitments, commit blob 444 bytes after Padmé and tag (Padmé steps at 320 bytes; with three levels, `writer`: 17 more in the header, 16 more in the prefix); a chunk's prefix carries the same 33-byte commitments; an inbox payload names a target's two delete keys (about 70 bytes per thing with secrets of its own); a delete by delete key carries a 64-byte signature per item; `keys.0` about 34 bytes per keyset for its delete key. Compute (`cargo bench --workspace --bench crypto`, release, shared box): derive a delete key ~12 µs, a blinded commitment ~27 µs per level per blob framed or prefix checked, blinded sign ~36 µs, verify ~36 µs; a host checks two signatures per delete (~66 µs).

## Implementation: osis-crypto
- Crates (versions: notes/architecture.md §5): ed25519-dalek 2, x25519-dalek 2, libcrux-ml-kem (deterministic keygen and encapsulation from explicit bytes; checked against NIST ACVP FIPS 203 answers in `core/crypto/tests/data/mlkem768_acvp.txt`), chacha20poly1305, blake3, zeroize, subtle, rand_core 0.6.
- Shape: free functions over `Secret32` (zeroizing, redacted, `subtle` constant-time eq; `kdf` returns one, public outputs copy out), `SigningSecret`/`VerifyingKey`/`Signature`, `KemSecret`/`KemPublicKey`, `X25519Secret`. Agility enums are the encoding only (`to_value`/`from_value`, unknown case = `Error::UnknownCase`, Parked); the Rust types have one case until a second suite exists.
- Surface (all at the crate root): `kdf::{kdf, kdf_xof, purpose consts}`, `aead::{seal, open}`; `Domain`, `SigningSecret::{from_seed, verifying_key, sign}`, `VerifyingKey::{from_bytes, verify, to_value, from_value}`, `Signature`; `X25519Secret::{from_secret, random, public, dh}`, `KemSecret::{derive, public, x25519}`, `KemPublicKey`, `seal`/`open_sealed`, `sealed_to_value`/`sealed_from_value`; `KeyActorKeys::from_seed`, `key_actor_role_secret`, `thing_role_secret`, `role_kem`, `creation_nonce`, `dedup_secret`, `delta_hash`, `link_hash`, `link_tree_hash`, `lan_tag`; `Epoch` (`Epoch::derive(actor, role, n, s)`, `names`, `Epoch::ZERO` for key actors), `BoxForm`, `BoxSlot` (`Secrets{actor, holder, role, epoch}` or `Entry{label, step_key, group}`, `actor()`, `ad(form)`), `seal_box`/`open_box`, `wrap_symmetric_box`/`open_symmetric_box`, `seal_history`/`open_history`; `pad`/`unpad`/`padme`, `encrypt_blob`/`decrypt_blob`, `blob_len`, `blob_id`, `wrap` (`Result`)/`unwrap`/`filler_wrap`, `seal_inbox`/`open_inbox`; `LabelRole`, `label_role_key`, `deposit_key`, `label_id`, `claim_key`, `static_entry`, `open_digest`/`sign_open`/`verify_open`; `DeleteSecret::{derive, from_seed, seed, verifying_key, sign}` (blinded signing over ed25519-dalek `hazmat`), `blind`, `commitment`, `verify_delete`; `Secret32`, `SeededRng`, `Error`, re-exported rand and zeroize types. Doc-hidden, for tests and vectors only: `seal_with` (explicit randomness), `KemSecret::from_parts`.
- Keys are validated at parse: `VerifyingKey` rejects non-canonical and small-order points (dalek's `from_bytes` alone accepts y >= p); `KemPublicKey` rejects a low-order X25519 half and ML-KEM keys failing the FIPS 203 modulus check, so sealing to a parsed key never fails.
- Box `value` encodings (`box`, `keyset`, epoch structs) belong to osis-keys and osis-schema; crypto builds every AD itself from the slot and form (`BoxSlot::ad`), so a box opens only under its own slot and form. `Epoch` n is within i64 (beyond is `TooLarge`, never clamped). Payloads carry `(n, secret)`: every opener recomputes each epoch from actor (an entry box's `group`), role, n and secret, and a box whose secret does not name its key's epoch is `Malformed`; sealers refuse such an item. History boxes reject entries out of order or with n not below the box's.
- Blob prefix layout is osis-label's; `encrypt_blob(prefix, plaintext, rng)` / `decrypt_blob(blob, prefix_len, key)`; no encrypt-under-given-key entry point (spec/crypto.md §5).
- Vectors: osis-vectors subjects `kdf/`, `keys/`, `box/` (incl. the inbox sealed box), `wrap/` (incl. blob encryption over an opaque prefix), `delete/`, `sign/`, `tid/key-actor.vec`, hand-written `padme/`; generators in `core/test/vectors/src/subjects/`. Prefixes with commitments, commit/chunk/page blobs, steps, claim sets, inbox payloads and signal envelopes are label and commit vectors.
- `SeededRng` (BLAKE3 XOF keyed by a seed) is the deterministic rng for tests, vectors and the simulator; drivers use `OsRng`.
- Bench (`cargo bench --workspace --bench crypto`, release, shared 4-core box): sealed box seal ~200 µs, open ~85 µs, KEM keygen ~40 µs, blob encrypt ~750 MB/s, decrypt ~1100 MB/s, Ed25519 sign ~19 µs, verify ~40 µs.

## Implementation: osis-keys
- `ActorEpochs`/`RoleEpochs` per actor per role; `EpochInfo`: suite, supersedes, rotations, snapshot, names, established, secret, reading, order.
- **Established** is `established: Option<Provenance>`: `Fixed` (`key_actor`) and `Derived` (`derived`) are set directly and persisted; `Rotated` is computed by `RoleEpochs::establish(held)` and never stored: base `rotations` (held valid rotation commits of it with their keyset's list, from `after_join` for valid parts only; `invalidate` drops one, `revalidated` records it again) or `snapshot` (`snapshot_keyed`), within headroom, and, its secret held, some entry of `names` (per history entry opened under its secret) met under `held` (`names::Held`: the engine's `NamesHeld` checks applied commits, the departing commit by `ts` and signer among the actor's held `roles.0` deltas). The engine's view is `Core::own_epochs` (established on read), so establishment needs no invalidation when commits or verdicts change; a view stored back goes through `ActorEpochs::into_record`. There is no own-rotation provenance: the rotator's commit applies locally before `rotation::record` stores the secrets, so its epochs fall when the commit turns invalid (`invalid_own_rotation_falls_spec_crypto_4`). `Rotation::preview` (account creation: the genesis label inside the rotation commit) marks the new epochs established in a scratch view.
- current = established and not in an established epoch's `superseded_epochs`. Supersession: what the commit's keyset lists (`Keyset::supersedes`: every current epoch but derived ones) and what its opened history box lists (`EpochInfo::superseded_epochs`), so a flipped verdict leaves nothing behind. A rotation commit is told from a grant or re-seal by its `keys.0` write: only history boxes at epochs whose keyset the commit sets count (`rotation_commit`); counting a re-seal's re-written history boxes was R9. `keys.0` vouches for no secret; nothing is inferred from the applied `secrets.0` state (`observe_secrets`, `observe_keys`, `ingest` establish nothing).
- Names are computed by `rotation::departures::names` (a superset: every applied commit lowering a grant on the actor, every audit drop of an edge write on it); `rotation_into` fixes the commit's `ts` beforehand when it departs someone. The named commits are placed with the rotation (`rotation::placed_with`). Differentials: osis-keys `names::names_establish_by_the_held_set` (random histories with withheld commits, forged entries, invalid commits, snapshots, forks, flipping verdicts, against a direct reading of the rule); osis-engine `rotation::tests::withheld_departures_leak_nothing(_large)` (end to end: no departed peer opens an epoch whose rotator held its departure). Tests for the TLC traces: `tests/it/established.rs`.
- **Reading-only secrets**: unestablished secrets read and open (`registered_epoch` matches any held secret; stamps, steps, deletes check `is_established`). `reading` holds the pending commits (`Unchecked`: author node, commit) an epoch is known from when known only from such; non-empty, the secret is reading-only (`secret`/`held` skip it; `reading_secret`, `held_newest_first`, `registered_secret` include it), and what it opens by history inherits its sources, supersedes nothing and records no names. Caps: `MAX_READING_PER_AUTHOR` (64) per author, `MAX_READING` (256) per role (each costs a trial decrypt per wrap, since wraps name no epoch); authors whose `created.0` the node lacks share one budget (`UNKNOWN_AUTHOR`), so throwaway identities gain nothing; at most `MAX_READING_ACTORS` (64) actors through reading-only secrets alone. A commit stops being a source when it applies or is dropped as bad input, and a secret it was the last source of goes (`apply::keys::forget_unchecked`; an actor left with no secret goes on the lost-access work list). Accepted limit (Tess): an insider's bogus pending commits under throwaway authors can fill the unknown-author pool, so a genuine grant whose granter's chain the node lacks reads only once the grant applies (one sync later; nothing exposed or lost). Tests `bogus_flood_bounded_by_caps_spec_crypto_4`, `genuine_grant_applies_after_flood_spec_crypto_4`.
- History keys with several live entries (an invite holder's put beside the genuine one) are opened entry by entry (`HistoryAlts`, `ingest_with`; `engine::secrets::history_alts`): a lying entry names only planted epochs, never established, or, written by a holder of the epoch, names less (accepted: it could leak the epoch anyway). A label entry box's read secret is held when it names its epoch (`Engine::learn_read_secret`); it establishes nothing.
- Persisted by `engine::secrets::encode_epochs` (rotations as `[commit, [epoch]]`, names as their wire value, reading as `[author, commit]`).
- **Derived epochs**: `ActorEpochs::derived(owner, tid)` maps each owner epoch whose secret is held to the thing's epoch at the owner's n capped at `MAX_FREE_N` − 1 (`derived_n`, `MAX_FREE_N` = 2^62), named by the derived secret, and keeps an owner epoch without a secret as a placeholder at that n whose nonce hashes the whole owner epoch (owner nonces alone could collide through made-up or capped epochs), so what it supersedes stays superseded. The cap: a writer of the owner may jump its n past `MAX_FREE_N`; uncapped, a thing's switch rotation landed above the headroom line with nothing at n − 1 that a holder holding no owner secret could establish. Not n 0 for all: derived epochs must order as the owner's, or an owner rotation leaves a plain group's label head "newer" only by nonce luck (`newer_than_head`) and a writer picks a fork other than the owner's newest. Past the cap (attack only) they keep that order through `order` (in `derived`'s result only; a rotation's wrap picks by n, spec/crypto.md §5); `RoleEpochs::is_newer`/`newest`/`newer_than_head` read it. `adopt_derived` establishes a thing's derived epochs (after its own-secrets switch) only where the owner's secret is held.
- `rotate`: n+1 over the current epochs, the epoch named by the fresh secret, history of established held secrets only (`held_established`) with the names, removes role-r boxes at the current epochs, lists in the keyset what it supersedes; the rotator's own record supersedes what every other node reads from the commit (`Rotated::supersedes`). `box_holder` (grant and re-seal: current established epochs, history boxes copied), `reseal_needed` (missing boxes at current epochs), `may_compact_secrets` (every epoch the state keys is established), `newest_secret` = newest established held (stranded wrap), `newer_than_head` also needs the head admin epoch established (the step signs under it). Key actors: `ActorEpochs::key_actor(seed)` at `Epoch::ZERO`. Writes are `SecretsWrite { boxes, removed, history }` / `KeysWrite`, turned into map deltas by the node. Recipients: `HolderKeys::{KeyActor, Actor}`; a holder actor's per role at the keyset Seal gives, symmetric when the writer holds that established epoch's secret (`rotation::members::sealed`).
- Residual: a malicious valid rotator leaks what it holds (names it omits, or a second history entry naming less, only hand on epochs it held).

## Rejected
- Per-epoch `keys.0` history; per-role boxes to nodes as extra objects: needless 1.2 KB objects.
- Node KEM keys as the only sealing target: a granter would need the grantee's node list; a new node would need re-grants from everyone.
- A tid committing to the KEM key: 1.2 KB in every chain certificate; rotation would need a new tid.
- One KEM key per actor; a cleartext epoch byte in wraps (above).
- AES-256-GCM and AEGIS (above); HPKE (SHA-256 inside, no hybrid in the RFC); X-Wing (a draft at decision time); ML-KEM-1024 (768 matches TLS and Signal practice); PQ signatures now.

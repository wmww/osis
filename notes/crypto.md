# Crypto: suite 1
> Summary: Why suite 1 (spec/crypto.md) uses its primitives (Ed25519, hybrid X25519 + ML-KEM-768 boxes, XChaCha20-Poly1305, BLAKE3), how wraps pick an epoch, the byte and compute costs, the osis-crypto crate, rejected primitives. Keys and rotation: notes/keys.md; delete keys: notes/delete-keys.md.

Principle: **secrets live in every holder's store for good, so whatever seals a secret must resist a future quantum attacker** (hybrid post-quantum boxes); everything else is the simplest safe classical primitive. The suite is the agents' call (Tess deferred it).

## Primitives
- **Ed25519**: fast verification per commit. Strict, so every node accepts exactly the same signatures; no batch verification (add it only with a test that it rejects exactly what `verify_strict` rejects). PQ signatures are not required (spec/requirements.md, Confidentiality between readers), and ML-DSA-44 (2420-byte signatures, 1312-byte keys) is over ten times the commit floor. If ever wanted: a new enum case; nodes move by add-and-remove, a root key only to a new account. An in-place successor key in `keys.0` would be a convenience only, with a keep-the-first-seen fork rule.
- **Hybrid PQ sealed boxes**: lazy rotation keeps old secrets valid for old content, so a classical box harvested today would yield every blob under that secret forever, and no later migration can re-protect it. The cost lands only on role changes (about 1.2 KB per holder and role), never per blob or commit. Generic hash-everything combiner (secure if either KEM is). X-Wing, as an RFC, would be a second case.
- **XChaCha20-Poly1305 over AES-GCM**: 96-bit GCM nonces plus frequent local unit rewrites invite nonce reuse; GCM is slow without hardware and in WASM. A hardware-speed suite can be added for multi-GB values.
- "One hash function" means every hash osis computes itself; ML-KEM's internal SHA3/SHAKE does not count.
- **Wire details** (spec/wire.md): one signature domain per signed object, so no signature verifies as another kind. The symmetric box's nonce derives from the AD because its key `kdf("box", s)` repeats across every epoch boxed under one s, while the AD is unique per (thing, holder, role, epoch).
- Not in the protocol: password hashing, transport crypto (TLS 1.3, QUIC).

## Wraps
- **Opening is not encrypting under**: an open signature proves possession of the sync secret to a node keeping S unread; the departed holder holds the same key, and nothing downstream relies on the open. Treating it as encrypting under deadlocked a re-sealed holder (it needs the sync key to fetch the commit that establishes the epoch). Stamps, steps and deletes are encrypting under: others act on them.
- **A commit giving read epochs wraps under one they supersede** (`Engine::giving_wrap_epoch`, the one exception to wrapping under the newest): a rotation, grant or re-seal boxes epochs its recipients may lack (a link left out of a rotation has no inbox and reads its re-seal only from the sync ID), so it goes under the superseded epoch with the greatest n whose roles secret the node holds (role parts need no more; a history-less holder gets every earlier roles secret from its cut), once every given epoch is established at the node (else a reader holding a grant by inbox logs a redundant fresh encryption before pulling the author's entry). A node holding none of those roles secrets wraps it under no other epoch: a holder of one logs it. First epochs (n 0) take the plain rule. Only a rotation's own wrap skips the blocked check. What it lets a removed party read, and Tess's decision: notes/keys-establishment.md, The superseded-epoch wrap. The leak to an ex-holder via a dishonest peer is the new epoch's box map (notes/sync-access.md).
- **Wraps name no epoch**: a cleartext epoch byte would leak rotation timing per blob to save one tag check. A lagging relayer's older-epoch wrap extends an ex-holder's reach by that blob (spec/requirements.md Permissions). A node holding no current secret is stranded, places nothing and reports itself (notes/sync-access.md).
- **Blob encryption never takes a caller key**, so a rewritten blob (purged delta) always gets a fresh key and ID.

## Key commitment
XChaCha20-Poly1305 commits to no key: whoever picks two keys and has a free 16-byte block solves one Poly1305 equation and gets a ciphertext opening under both (osis-engine's `validity::entry_under_two_keys` and `section_wrap_under_two_secrets` build one in about a thousand tries; tests `an_entry_opening_under_two_keys_judges_alike_in_any_order_spec_wire_4`, `a_section_wrap_opening_under_two_epochs_reads_alike_spec_wire_4`). Rule: a reading is a function of the secrets held, never of the route a key came by or the order secrets are tried in. Per AEAD use where a reader may hold two candidate keys:
- **Path entry** (key reaches readers by several routes, writer picks it, plaintext free): commits to its key, `kdf("path commit", key, "")` (spec/crypto.md §5). Binding: two keys for one entry need a BLAKE3 collision (128-bit). Hiding: a one-way function of a 256-bit key (roles-derived or random) tells a non-reader nothing it can test a guess against; the path is not an input. Commitment and AEAD keyed by one key, domain-separated by the derive_key context (`osis v1 path commit`).
- **Section wrap** (random nonce, plaintext a free section key): a reader tries every held secret until one's key opens the section (`Section::open`); a secret unwrapping to a key that opens nothing does not stop it. Only one key opens a section to its commit's parts: the plaintext is fixed by the commit (parts by delta hash, path keys by commitment) and both the wrap and the ciphertext take the commit ID as AD, so a writer keeping a free block for a second key has junk under both (a part missing its hash: the blob is bad at every reader alike). Zero bytes. `sync_ids::open_commit` notes the first epoch whose wrap unwraps as the one a section opened under: on a hostile two-secret wrap that may be the one whose key opens nothing, which lets this node pass the writer's own parts on under an epoch the writer could have sealed them under itself.
- **Blob wrap** (nonce = blob ID, plaintext suite ‖ blob key ‖ order): the first secret that unwraps is taken (`osis_blob::unwrap_any`). Bound without a commitment: the blob fixes the nonce and all but the 64 order bits of one side's plaintext, so a wrap opening under two secrets needs the Poly1305 equation (130 bits) solved within those 64 bits plus the other side's suite byte, about 2^72 blob encryptions per blob; the gain would be withholding the writer's own commit from holders of the second epoch.
- Single-key uses (sealed boxes, joint boxes, symmetric and history boxes, inner seals per epoch, rotation devices, store pages): one candidate key, nothing to bind.
- Rejected: a 32 B key commitment in every wrap (57 to 89 B a blob wrap per sync ID, 72 to 104 B a section): bytes on every commit for what trying every held secret gives free.

## Costs
- Grant or rotation: one sealed box (about 1.2 KB) per (holder, role, epoch), key actors included. An account with four key-actor admins removing a node rotates all four roles: 16 boxes plus a few hundred bytes of history boxes (one box per key actor carrying every role would be 4). An admin grant to a key actor: 4 boxes, about 4.8 KB. A write rotation of a key-actor admin is one box.
- Joint box (notes/holder-actors.md, Seal): about 1.14 KB more per keyset named past the first, and one KEM encapsulation per keyset. It names one keyset per frontier anchor, which grows only by concurrent rotations of M that no rotator of M has seen together; any rotation of M listing them, or A's next rotation once one exists, folds them back to one box.
- History: 32 bytes per earlier epoch plus a tag, and about 75 bytes per name (one per departure from the thing ever and per audit-drop target; 27 more when the rotation departs someone itself), in every history box a rotation writes and again in each grant's, re-seal's or history add's copy. Measured on a 10-reader thing removing readers one by one: the read history box grows about 112 bytes per removal (36 the earlier secret, 76 its name). 1000 departures make about 76 KB per history box per role (issues/rotation-names-grow.md). Held epochs keep their names in the thing's local epochs unit, re-encoded whole on each save: O(epochs x names) per rotation.
- `keys.0`: about 1.2 KB per role (sync, read, write, admin). A contact card (QR-sized) is a link to a profile thing holding `keys.0`, since the keyset is too big for a QR code.
- Bench (osis-bench `benches/crypto.rs`, release, shared 4-core box): sealed box seal ~200 µs, open ~85 µs, KEM keygen ~40 µs, blob encrypt ~750 MB/s, decrypt ~1100 MB/s, Ed25519 sign ~19 µs, verify ~40 µs. Delete-key costs: notes/delete-keys.md.

## Implementation (osis-crypto)
Crates and versions: notes/architecture.md §5 (libcrux-ml-kem for deterministic keygen and encapsulation from explicit bytes, checked against NIST ACVP answers). Surface: `lib.rs` (free functions over `Secret32`, typed keys, signatures and boxes; agility enums are the encoding only, one Rust case until a second suite exists).
- **Keys are validated at parse**, so sealing to a parsed key never fails: `VerifyingKey` rejects non-canonical and small-order points (dalek's `from_bytes` alone accepts y >= p: a byte comparison against p, since the only points with x = 0 are small-order); `KemPublicKey` rejects a low-order X25519 half (compared with the seven low-order u values, tested equal to the non-contributory DH check) and ML-KEM keys failing the FIPS 203 modulus check.
- **Parsed once, where decoded.** A public key is held in its parsed type, never as bytes re-parsed per use. Derived secret keys live with the seed they derive from, in the same zeroizing containers and no longer (`KeyActorKeys`, `AccountEpochKeys` hold their seed, so callers pass the bundle, not a seed to expand again). Bytes remain only below osis-crypto (`CreationRecord::KeyActor`'s key, osis-base) or where a decode deliberately skips the check (a header's `DeleteKey` under `decode_stored`).
- Crypto builds every box AD itself from the slot and form (`BoxSlot::ad`), so a box opens only under its own slot and form; every opener recomputes the epoch from thing, role, n and secret, and sealers refuse an item whose secret does not name its key's epoch. Box `value` encodings belong to osis-keys and osis-schema, the blob prefix layout to osis-blob.
- Vectors: osis-vectors generators in `core/test/vectors/src/subjects/`. `SeededRng` is the deterministic rng for tests, vectors and the simulator; drivers use `OsRng`.

## Rejected
- Per-epoch `keys.0` history; per-role boxes to nodes as extra objects: needless 1.2 KB objects.
- Node KEM keys as the only sealing target: a granter would need the grantee's node list; a new node would need re-grants from everyone.
- A tid committing to the KEM key: 1.2 KB in every certificate copy of its record; rotation would need a new tid.
- AES-256-GCM and AEGIS (slow without AES hardware and in WASM, above); HPKE (SHA-256 inside, no hybrid in the RFC); X-Wing (a draft when suite 1 was fixed); ML-KEM-1024 (768 matches TLS and Signal practice); PQ signatures now. One KEM key per independent thing: notes/keys.md.

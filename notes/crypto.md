# Crypto: rationale
> Summary: Why suite 1 (spec/crypto.md) is what it is, costs of keys and boxes, proposed crates, rejected options. The suite was the agent's call with the owner deferring; hybrid post-quantum boxes follow from the requirement that long-lived secrets resist a future quantum attacker.

## Why
- **Ed25519**: 32-byte keys, 64-byte signatures, fast verification per commit. Strict verification so every node accepts exactly the same signatures. PQ signatures not now and not required (spec/requirements.md: signatures need not resist a quantum attacker): ML-DSA-44 has 2420-byte signatures and 1312-byte keys, over ten times the commit floor. If ever wanted: a new enum case; devices move by add-and-remove, a root key by copying the person actor (spec/permissions.md §7, rare and costly); stored data stays valid. An in-place successor key in `/keys` would be a convenience only, and its fork rule could only be keep-the-first-seen, as for colliding creation records.
- **Hybrid PQ sealed boxes**: boxes sit on blind nodes forever and lazy rotation keeps old secrets valid for old content, so a classical box harvested today would yield every blob under that secret, forever; a later migration cannot re-protect it. The cost lands only on membership changes (about 1.2 KB per member and role), never per blob or commit. Generic hash-everything combiner (secure if either KEM is); X-Wing was a draft at decision time; if it is an RFC by implementation, add it as a second case.
- **XChaCha20-Poly1305 over AES-GCM**: 96-bit GCM nonces plus frequent local unit rewrites invite nonce reuse; GCM is slow without hardware and in WASM. A hardware-speed suite can be added later for multi-GB values.
- **KEM key per role** for non-key actors: effective role is the minimum along the chain, so a box sealed to A's write key must be openable only by A's writers. One KEM key per actor would hand every reader of A all of A's write and admin secrets.
- **`/keys` holds the current keyset only**: nobody seals to an old epoch on purpose, and a granter with a stale key still succeeds because members keep old secrets. The deposit seed lives beside the keysets (one per actor; each label's deposit key derives from it by label ID, notes/sync.md); refreshing it is a MAY against an ex-member filling the budget, because a refresh also refuses the stranded heartbeats of members that missed the rotation (issues/reseal-triggers.md).
- **Key actors have seed-derived role secrets** so a thing owned by a key actor (a node's local thing, a person actor under its recovery key) is a plain thing like any other; they are never rotated and never shared. The KEM key is seed-derived too and never rotates: the seed is the device, a compromise is a device removal, and a keyset epoch for key actors would have put an epoch into every box and claim-set rule for a case nothing uses (devices and link keys are replaced by add-and-remove; a suite migration is a new key actor).
- **Big rosters**: a rotation's boxes page like any map, and `/secrets` compacts by ordinary paged compaction snapshots, so no roster size makes rotation impossible; the roster snapshot's header still lists one delta hash per edge (spec/requirements.md, Scale).
- **Link keys are full key actors** (signing and KEM keys from the seed): the earlier sign-only design derived K's secrets from the seed, which handed every read-link holder K's admin secret and label delete key, and used a symmetric link box only the sharer could write, which a writer's rotation of K could not refresh (notes/permissions.md, Links). Cost: 1.2 KB per box to L per rotation of K, and one hybrid entry box per step of K's label.
- **Symmetric box form** when the writer already holds the recipient's role secret (a thing's secrets to its owner): 49 bytes plus the epoch of the recipient's secret, which the covers rule needs (without it an owner's rotation after a lost device would not make the thing's epoch stale).
- **Epochs per role**, not per actor: a writer may rotate read and write but not admin, so a per-actor epoch would have to say which roles "carry over" and where their boxes live; per-role epochs make each role an independent chain of secrets, boxes and history boxes, and `/keys` an independent keyset per role that the rotator of that role writes.
- **History boxes**: holding a role's current secret opens every older one; a member removed before epoch n opens nothing newer; a join costs one box per role, not one per epoch. A grant or re-seal re-writes the history box of each epoch it boxes (same ciphertext, a register rewrite): the recipient can decrypt it but could not otherwise fetch it, since the rotation commit that carries it is wrapped under the epoch the recipient lacks (TLC R3). Cost: 32 bytes per earlier epoch per grant.
- **Rotation commits wrap under the superseded epoch** (the only exception to wrapping under the newest): the commit carries the new secret, so under the new wrap only its author could read it; the leak to an ex-member via a dishonest server is the new epoch's box map (notes/sync.md).
- **Wraps name no epoch**: a cleartext epoch byte would leak rotation timing per blob to save one tag check. A lagging relayer's older-epoch wrap extends an ex-member's reach by that blob (spec/requirements.md, Out of scope). An uploader wraps under the newest *current* epoch whose secret it holds; a node that holds no current secret (the rotation it received boxed it nowhere) is stranded and places only its heartbeat, under the newest secret it has, which tells co-members which epoch it is on.
- **Blob encryption never takes a caller key**, so a rewritten blob (purged delta) always gets a fresh key and ID.
- ML-KEM's internal SHA3/SHAKE is internal to that primitive; "one hash function" means every hash osis computes itself.

- **Wire details** (spec/wire.md): one signature domain per signed object (deposit, delete and signal publish got their own, so no signature verifies as another kind). The symmetric box's nonce is BLAKE3(AD), because its key `kdf("box", s)` repeats across every epoch boxed under one s, while AD is unique per (actor, member, role, epoch). Agility enums are osis enum values in values and structures alike; case 1 matches suite 1.
## Costs
- Grant or rotation: one sealed box (about 1.2 KB) per (member, role at or below the granted one), one per device for key-actor members. History: 32 bytes per earlier epoch plus a tag. `/keys`: about 3.6 KB for three roles.
- A contact card (QR-sized) is a link to a profile thing holding `/keys`, since the keyset itself is too big for a QR code.

## Implementation
- `osis-crypto` (crate choices and versions: notes/architecture.md §5): ed25519-dalek 2, x25519-dalek 2, libcrux-ml-kem (deterministic keygen and encapsulation from explicit bytes; checked against NIST ACVP FIPS 203 answers in `crates/osis-crypto/tests/data/mlkem768_acvp.txt`), chacha20poly1305, blake3, zeroize, subtle, rand_core 0.6.
- Shape: free functions over `Secret32` (zeroizing, redacted, `subtle` constant-time eq; `kdf` returns one, public outputs copy out), `SigningSecret`/`VerifyingKey`/`Signature`, `KemSecret`/`KemPublicKey`, `X25519Secret`. Agility enums are the encoding only (`to_value`/`from_value`, unknown case = `Error::UnknownCase`, Parked); the Rust types have one case until a second suite exists.
- Surface (all at the crate root): `kdf::{kdf, kdf_xof, purpose consts}`, `aead::{seal, open}`; `Domain`, `SigningSecret::{from_seed, verifying_key, sign}`, `VerifyingKey::{from_bytes, verify, to_value, from_value}`, `Signature`; `X25519Secret::{from_secret, random, public, dh}`, `KemSecret::{derive, public, x25519}`, `KemPublicKey`, `seal`/`open_sealed`, `sealed_to_value`/`sealed_from_value`; `KeyActorKeys::from_seed`, `key_actor_role_secret`, `thing_role_secret`, `role_kem`, `creation_nonce`, `dedup_secret`, `delta_hash`, `link_hash`, `link_tree_hash`, `lan_tag`; `Epoch` (`Epoch::ZERO`: a key actor's fixed epoch), `BoxForm`, `BoxSlot` (`Secrets{actor, member, role, epoch}` or `Entry{label, step_key}`, `ad(form)`), `seal_box(pk, slot, keyset, items, rng)`/`open_box(kem, slot, form, sealed)`, `wrap_symmetric_box(s, slot, epoch_s, secret)`/`open_symmetric_box(s, slot, epoch_s, wrap)`, `seal_history`/`open_history`; `pad`/`unpad`/`padme`, `encrypt_blob`/`decrypt_blob`, `blob_id`, `wrap` (`Result`)/`unwrap`/`filler_wrap`, `seal_inbox`/`open_inbox`; `LabelRole`, `label_role_key`, `deposit_key`, `label_id`, `claim_key`, `static_entry`, `open_digest`/`sign_open`/`verify_open`; `delete_token`, `token_hash`, `commitment`, `verify_presented_token`; `Secret32`, `SeededRng`, `Error`, re-exported `CryptoRngCore`, `RngCore`, `CryptoRng`, `RngError`, `Zeroizing`, `OsRng` (`os-rng`). Doc-hidden, for tests and vectors only: `seal_with` (explicit randomness), `KemSecret::from_parts`.
- Keys are validated at parse: `VerifyingKey` rejects non-canonical and small-order points (dalek's `from_bytes` alone accepts y >= p), `KemPublicKey` rejects a low-order X25519 half and ML-KEM keys failing the FIPS 203 modulus check, so sealing to a parsed key never fails.
- No batch Ed25519 verification: single strict verification only, so spec/crypto.md §1 "batch and single agree" holds trivially. Add batch only with a test that it rejects exactly what `verify_strict` rejects.
- Box `value` encodings (`box`, `keyset`, epoch structs) belong to osis-keys/schema; crypto builds every AD itself from the slot and form (`BoxSlot::ad`), so a box opens only under its own slot and form, seals/opens payloads, and has `Epoch` (n within i64; an int beyond i64 is `TooLarge`, never clamped). History boxes reject two secrets at one epoch and entries whose n is not below the box's.
- Blob prefix layout is osis-label's; `encrypt_blob(prefix, plaintext, rng)` / `decrypt_blob(blob, prefix_len, key)`. There is no encrypt-under-given-key entry point (spec/crypto.md §5).
- Vectors: osis-vectors subjects `kdf/`, `keys/`, `box/` (incl. the inbox sealed box), `wrap/` (incl. blob encryption over an opaque prefix), `token/`, `sign/`, `tid/key-actor.vec`, hand-written `padme/`; generators in `vectors/src/subjects/`. Blob prefixes with commitments, commit/chunk/page blobs, steps, claim sets, full inbox payloads and signal envelopes are label/commit vectors.
- `SeededRng` (BLAKE3 XOF keyed by a seed) is the deterministic rng for tests, vectors and the simulator; drivers enable `os-rng` for `OsRng`.
- Bench: `cargo bench -p osis-bench --bench crypto` (release, shared 4-core box): sealed box seal ~200 µs, open ~85 µs, KEM keygen ~40 µs, blob encrypt ~750 MB/s, decrypt ~1100 MB/s, Ed25519 sign ~19 µs, verify ~40 µs.
- `osis-keys` (plans/keys.md): `ActorEpochs`/`RoleEpochs` per actor per role (`EpochInfo`: suite, supersedes, usable, secret); current = usable and not in a usable epoch's supersedes set; supersedes comes from a rotation's removed boxes (`SecretsWrite::rotations`) and from opened history boxes (everything a history box lists counts as superseded by its epoch), so compaction loses nothing; pending/invalid rotations are `usable = false` (read only, supersede nothing). Key actors: `ActorEpochs::key_actor(seed)` at `Epoch::ZERO`; plain things `ActorEpochs::derived(owner, tid)`. Writes are `SecretsWrite { boxes, removed, history }` / `KeysWrite` (the node turns them into map deltas). `rotate` (n+1 over every known epoch, forks and unusable included; history of every held secret; removes role-r boxes at the superseded epochs), `box_member` (grant/re-seal: every current epoch, history boxes copied), `ingest`/`open_boxes`/`open_histories`, `SecretStore` trait. Recipients: `MemberKeys::{KeyActor, Actor}`; symmetric when the writer holds the member's secret (`with_own`) unless it holds a newer keyset.
- Key-actor boxes: one per write, keyed at the top role written; a rotation's box also carries the newest current secret of the roles below the key it does not rotate, else removing the old top-keyed box (it carried them) would strand the key actor (found by the props test). A grant to a key actor carries each role's newest epoch only (forks of a lower role are not all boxed; the next rotation's history covers them). The covers rule and the re-seal trigger treat a key-actor box keyed at a higher current role as carrying the lower roles (it cannot be opened to check).
- Not in the protocol: password hashing (an app exporting a recovery key uses Argon2id), transport crypto (TLS 1.3, QUIC, iroh).

## Rejected
- Per-epoch `/keys` history, per-role boxes to devices: needless 1.2 KB objects. (A KEM key for link keys was rejected on the same ground and later reinstated, above.)
- Node KEM keys as the only sealing target: a granter would need the grantee's device list; a new device would need re-grants from everyone.
- Tid committing to the KEM key: 1.2 KB in every chain certificate; rotation would need a new tid.
- One KEM key per actor (above). Cleartext epoch byte in wraps (above).
- AES-256-GCM and AEGIS (above); HPKE (SHA-256 inside, no hybrid in the RFC); X-Wing (draft at decision time); ML-KEM-1024 (768 matches TLS and Signal practice); PQ signatures now.

# Crypto: rationale
> Summary: Why suite 1 (spec/crypto.md) is what it is, costs of keys and boxes, proposed crates, rejected options. The suite was the agent's call with Tess deferring; hybrid post-quantum boxes follow from the requirement that long-lived secrets resist a future quantum attacker.

## Why
- **Ed25519**: 32-byte keys, 64-byte signatures, fast verification per commit. Strict verification so every node accepts exactly the same signatures. PQ signatures not now and not required (spec/requirements.md: signatures need not resist a quantum attacker): ML-DSA-44 has 2420-byte signatures and 1312-byte keys, over ten times the commit floor. If ever wanted: a new enum case; devices move by add-and-remove, a root key only to a new account; stored data stays valid. An in-place successor key in `keys.0` would be a convenience only, and its fork rule could only be keep-the-first-seen, as for colliding creation records.
- **Hybrid PQ sealed boxes**: boxes sit on hosts forever and lazy rotation keeps old secrets valid for old content, so a classical box harvested today would yield every blob under that secret, forever; a later migration cannot re-protect it. The cost lands only on role changes (about 1.2 KB per holder and role), never per blob or commit. Generic hash-everything combiner (secure if either KEM is); X-Wing was a draft at decision time; if it is an RFC by implementation, add it as a second case.
- **XChaCha20-Poly1305 over AES-GCM**: 96-bit GCM nonces plus frequent local unit rewrites invite nonce reuse; GCM is slow without hardware and in WASM. A hardware-speed suite can be added later for multi-GB values.
- **KEM key per role** for non-key actors: effective role is the minimum along the chain, so a box sealed to A's write key must be openable only by A's writers. One KEM key per actor would hand every reader of A all of A's write and admin secrets. Concretely: actor A (a team) holds admin on doc T and has read-only holders; T's admin box to A must stay closed to them, else they get T's admin secret, hence T's admin delete key and label keys ("reading never allows deleting data", "readers only read", spec/requirements.md). The sealer cannot tell A's roles apart without a public key per role, and a single key must be held by A's readers (they need A's read boxes), so one KEM key per actor with role and epoch bound only in the AD (replay-proof, not confidential) breaks this for any actor whose holders hold different roles. It is safe only where every holder of A holds every role A is boxed at (by convention an account: devices and recovery key are all admins), which the sealer cannot know. For the same reason one box per holder actor carrying all its roles, sealed at its top role, would lock A's lower-role holders out. Cheaper variants (one ML-KEM key per actor with an X25519 key per role; roles sharing a key while their holders coincide) were declined by Tess: notes/chat.md Costs.
- **`keys.0` holds the current keyset only**: nobody seals to an old epoch on purpose, and a granter with a stale key still succeeds because holders keep old secrets. The deposit seed lives beside the keysets (one per actor; each label's deposit key derives from it by label ID, notes/sync.md); refreshing it is a MAY against an ex-holder filling the budget, because a refresh also refuses the stranded heartbeats of holders that missed the rotation (issues/reseal-triggers.md).
- **Key actors have seed-derived role secrets** so a thing owned by a key actor (a node's local thing, an account under its recovery key) is a plain thing like any other; they are never rotated and never shared. The KEM key is seed-derived too and never rotates: the seed is the device, a compromise is a device removal, and a keyset epoch for key actors would have put an epoch into every box and claim-set rule for a case nothing uses (devices and link keys are replaced by add-and-remove; a suite migration is a new key actor).
- **Big rosters**: a rotation's boxes page like any map, and `secrets.0` compacts by ordinary paged compaction snapshots, so no roster size makes rotation impossible; the roster snapshot's header still lists one delta hash per grant (spec/requirements.md, Scale).
- **Link keys are full key actors** (signing and KEM keys from the seed): the earlier sign-only design derived K's secrets from the seed, which handed every read-link holder K's admin secret and label delete key, and used a symmetric link box only the sharer could write, which a writer's rotation of K could not refresh (notes/permissions.md, Links). Cost: 1.2 KB per box to L per rotation of K, and one hybrid entry box per step of K's label.
- **Symmetric box form** when the writer already holds the recipient's role secret (a thing's secrets to its owner): 49 bytes plus the epoch of the recipient's secret (to a holder actor, plus its 64-byte possession signature), which the covers rule needs (without it an owner's rotation after a lost device would not make the thing's epoch stale).
- **Epochs per role**, not per actor: a writer may rotate read and write but not admin, so a per-actor epoch would have to say which roles "carry over" and where their boxes live; per-role epochs make each role an independent chain of secrets, boxes and history boxes, and `keys.0` an independent keyset per role that the rotator of that role writes.
- **History boxes**: holding a role's current secret opens every older one; a holder removed before epoch n opens nothing newer; a join costs one box per role, not one per epoch. A grant or re-seal re-writes the history box of each epoch it boxes (same ciphertext, a register rewrite): the recipient can decrypt it but could not otherwise fetch it, since the rotation commit that carries it is wrapped under the epoch the recipient lacks (TLC R3). Cost: 32 bytes per earlier epoch per grant. A history box carries only secrets of **established** epochs (TLC R9): a node re-sealed at e before e's commit reached it holds e's secret but not the departure e carries, and would otherwise rotate over e and hand e's secret, boxed in its history, to the holder e removed. Establishment (spec/crypto.md §4) is the one notion behind "may encrypt under", "current", what a history box carries and where a re-seal may be made: fixed and derived epochs, and epochs with a held valid rotation commit or a held `secrets.0` snapshot keying them whose **names** are met where the secret is held. Names: each rotation's history box lists, from its rotator's own timeline, the departures it held from the actor, each since its epoch start (and itself by `ts` and signer when it departs someone); a node uses the epoch only once it holds them all, or they lie before its epoch start. So a node never passes on an epoch whose rotator knew of a departure the node lacks: its own roster then has the holder departed and boxes it nothing. Every link is first hand: nothing follows another rotator's list. Nothing below the actor is named (Holder actors, below). Unestablished secrets read; nothing is written under them. Replaced (round 13, issues/epoch-establishment-redesign.md): "settled" chains, where each rotation's keyset listed the rotation commits of what it superseded and a node followed that chain down to an established epoch. Six fix rounds each closed one way a link was someone else's word (a writer's own list skipping a removal, a forged valid rotation listed beside an unsettled genuine one, a snapshot standing in for a removal, invalid commits passed through by name, re-grants hiding the chain, injected forged claims). Also rejected: a departed-holder set in the history box (hearsay: every boxing path has to consult it, and a writer could bar any holder); re-sealing only to holders the rotator boxed (closes re-seals, not the rotation path); an age rule (clock-dependent).
- **Frozen coverage** (spec/crypto.md §4; notes/epoch-establishment-study.md): an epoch covers exactly the departures from its actor its rotator named; a node relies on it for nothing else, and boxes decide nothing. Every earlier rule that read coverage from boxes ("holds no box for M") had one hole shape: a missing box means "excluded" or "unknown", and an epoch got credited with a departure its rotator never knew (study C2). Each departure carries the name a rotation knowing it writes (`Departure::at`: its newest lowering write, a finalize for a timed end, the demotion whose audit dropped its grant, or the epoch start for a box holder the timeline no longer shows) and the roles it concerns. Liveness: a rotator names everything it knows (`thing_names` is a superset of `events`), so its own epoch covers what it knows. Merge (rule 3): a node that may rotate rotates while any current epoch, not only the newest, misses a departure it knows (`osis_keys::merge_due`): a fork made without knowing the departure stays current otherwise and may win the (n, nonce) order; a current epoch whose secret it lacks covers nothing (its history box is closed), so that rotation supersedes it too (one extra rotation, never a loop). Also any fork, by its merger only (`osis_keys::fork_merger`: the maker of a current epoch other than the newest, or anyone when no such maker may rotate): two knowing forks of M anchoring A's two forks left M unsealable for good (cycle seed 1838); every admin merging instead ping-pongs (two devices holding the same fork merge alike each sync round: the osis World sim hung).
- **Holder actors at depth 0** (Tess, Q2 = A, notes/keys-requirements-study.md §2.1, §4; issues/keys-depth0.md; model core/test/tla/rotation/Depth0.tla): a group never looks inside its member actors. Deleted with it: names of departures below the actor, keyset names, sealers' names on boxes, bound seals and the grant `keyset`, the departure walk (`Via` chains, classes, cycles), presumed boxes, the box judgement, the stranded-until-intermediate rule and the §4 exception placing inside-holder revokes. What replaces them, all in `osis_keys::members` as pure functions with the engine gathering inputs (`rotation::members`):
  - **Seal** (rule 1, `seal_keyset`): a holder actor M is boxed at the newest held valid keyset of M that is or descends from every anchor (the keysets A's current boxes to M name), through held valid keysets only (a forged keyset lists everything). Without anchoring (newest keyset) A's next rotation moves onto an ignorant fork and its history box hands A's content since the removal to the departed device (`D0_member`). None: while the anchors fork (no keyset, tainted or not, descends from all) the rotation, grant, re-seal or removal waits for M's merge (`Seal::Wait`): leaving M out dropped the anchors and the next re-seal sealed M at its newest keyset, perhaps an ignorant fork, exposing content written knowing the merge (`D0_fork_out`, `D0_fork_old_safety`). Otherwise (a tainted anchor, no keyset) M is left out, re-sealed once one exists; waiting on taint held A's removals while a grant stayed hidden (cycle harness, 1.6% of seeds).
  - **Held boxes** (`rotation::members::held_boxes`): departures read from boxes, staleness, taint and the knowing re-key judge every box held, the state's and those of held `secrets.0` deltas judged invalid: an invalid box still opens (a grant by an admin demoted concurrently boxes X at Y's epoch, X holding no role there: a departure no epoch covers, Y rotates). Anchors and opening use the state only. Junk boxes cost one rotation per commit, as a writer's own rotations could. `Core::index_validity` drops the derived caches when a `secrets.0` part flips.
  - **Stale** (rule 2, `stale`): a box naming a keyset held invalid, tainted, or listed by a held valid keyset of M; the node rotates before encrypting. Not "any newer keyset" (that moves A onto an ignorant fork), and an unknown keyset is not stale (a co-writer may have sealed to one not received yet). Staleness is also what carries a removal up: M's knowing rotation lists the keyset its departed party opens, every box to M at it goes stale, and so on up (the old cascade's job). The cascade itself stays (`ensure_rotated`: holder actors this node may rotate first, since sealing to M is encrypting under M's epoch), so one rotation of A suffices where the node may rotate M. Stale and keyless boxes block only the roles the node may rotate (spec/crypto.md §4): a reader held back by one placed no chain certificates, so M's new keyset never reached A's rotators.
  - **Key access** (rule 4, `key_access`): actor grants in an agreed order (owners first: an implicit edge from creation; then by the key of the write starting the grant's standing, `Timeline::standing_since`; ties by target, holder); a grant whose target's key already yields its holder's over the earlier keyed grants is keyless and boxed nothing. Only grants inside a strongly connected component are judged one by one. The knowing re-key: a current epoch boxing a holder whose grant is keyless rotates. **Taint** (4b): a keyset of M boxing a holder whose grant on M is keyless is stale and never sealed to (Wren: churn while a host withholds a grant beats an endless leak); a box to a departed actor holder is a departure, not a taint (counting it brought back the inside-departure lockout: a member's self-removal from M left M out of A). Cached per roster change (`Core::key_access`); a new grant is judged with the owners of both ends added (an actor owned by its target, a thin client minted by the account, closes a cycle through the implicit edge though it holds nothing yet: such a grant is keyless). M's `secrets.0` is read for taint only when some grant on M is keyless. Owner removal step 2: the first admin's implicit edge must keep counting as a grant ordered at creation (never keyless); its removal may make a later keyless grant keyed (a re-seal, as a new grant).
  - **Possession** (`osis_keys::possession`, judged in `apply::validity::possessed`; issues/keys-depth0-removed-member-rotates.md): a symmetric box to holder actor M is signed by the keyset's possession key (published in `keys.0`, like `delete_key`); a rotation (or a removal of a box to M) counts its author's role through a holder actor only where it boxes it so (Authority). No rule judges a box alone (the Box rule, dropped): an invalid box still opens for its keyset's holders, so invalidating it only hid a key cycle from the knowing re-key and taint (model `D0_box_rule`; the cycle harness at full size, seed 1032), and demanded a signature from authors whose role on M ran through keyless grants (M left out for good). Without it a writer of A through M, removed from M where nobody syncing A knows, rotates A sealing M's new keyset without holding it and A's admin writes under an epoch it holds (`D0_rm_*`). Per box, signed over the AD and wrap: bound to the box, not copyable. Facts noted from the body (`Indexes::shown`, kept in `Dropped::shown`); judged again when the holder's keysets change (`apply::keys::keyset_changed`). A box at a keyset with no held valid body is not judged (like staleness): requiring it made readers who cannot see M's keysets (carried inside a commit they cannot open) refuse honest rotations for good. Does not stop W forging X1's keyset itself (it writes X1): the forgery limit.
  - **Carried**: a rotation, grant or re-seal places, under A's own labels, the rotation commits of the keysets its boxes to holder actors name (`rotation::carry`, the model's `Carry`), so A's writers can judge them: a forged keyset is judged invalid only by a node holding its body and the removal.
  - Index: `Indexes::keysets` (per actor, each valid keyset with its list and KEM key, from valid `keys.0` bodies, kept once dropped in `Dropped::keysets`, rebuilt on validity flips); held invalid keysets are looked up on demand (`rotation::members::held_invalid`: only a box naming a keyset not held valid asks).
  - Limits (spec/requirements.md, Permissions): a device removed from M reads A's content written under keys sealed to an ignorant or forged keyset of M (since its removal, by history boxes) until M's next knowing rotation reaches A's writers; a forged keyset whose body a host withholds from a writer that knows the removal stays unknown, so not stale, there. Hidden grants: a sealer lacking the earlier grant seals into a key cycle; with taint the leak stops once the writer holds the grants and the cycle's commits. The agreed order uses a roster snapshot's key for grants standing at it (no `since` for read grants): nodes with different epoch starts may order such grants differently, like a hidden grant, until roster snapshots go (owner-removal plan step 1).
- **Opening is not encrypting under**: an open signature proves possession of the read secret to a host; the departed holder holds the same key, and nothing downstream relies on the open. Treating it as encrypting under deadlocked a re-sealed holder (it needs the sync key to fetch the commit that establishes the epoch). Stamps, steps and deletes stay encrypting under: others act on them.
- **Rotation commits wrap under the superseded epoch** (the only exception to wrapping under the newest): the commit carries the new secret, so under the new wrap only its author could read it; the leak to an ex-holder via a dishonest host is the new epoch's box map (notes/sync.md).
- **Wraps name no epoch**: a cleartext epoch byte would leak rotation timing per blob to save one tag check. A lagging relayer's older-epoch wrap extends an ex-holder's reach by that blob (spec/requirements.md, Permissions). An uploader wraps under the newest *current* epoch whose secret it holds; a node that holds no current secret (the rotation it received boxed it nowhere) is stranded and places only its heartbeat, under the newest secret it has, which tells co-holders which epoch it is on.
- **Blob encryption never takes a caller key**, so a rewritten blob (purged delta) always gets a fresh key and ID.
- ML-KEM's internal SHA3/SHAKE is internal to that primitive; "one hash function" means every hash osis computes itself.

- **Delete keys are signatures under blinded keys** (Tess's decision, replacing hashed tokens): one mechanism for every level; a writer that is no admin lists the thing's published admin key, so a thing admin who is no group admin deletes a writer's data at hosts (the hashed scheme needed the admin secret to list level 1). Each blob commits to A' = h·A with h from A, the prefix salt and a 16-byte random **blind** in the encrypted header (Tor v3 style key blinding); without the header blind h would be computable from A alone, and A is widely known (level-2 keys travel in chain certificates and contact profiles, a key actor's is its signing key, a group's admin key is known to its readers), so a host colluding with any contact could link an author's or owner's blobs across groups (spec/requirements.md, Data a node cannot read; security review). Only header readers compute A'; only the holder of a signs; a delete reveals nothing. Chunks and header-list blobs use the blind of the header that introduced them (the reuse check looks it up: `Reuse::index`'s `blind_of`). The label key signature stays: every past holder of an epoch's secret can sign with its delete key, so only it proves current roles. A thing without secrets of its own uses its delete base's keys (its owner's admins are its admins, so the right holders are the same and nothing per thing is published); a key-actor base uses its signing key (public through the creation record; key actors never rotate). The base is the first actor in the chain with secrets of its own whatever the role (all three come at once), so a thing whose `keys.0` has not arrived is not writable rather than wrongly listing its owner's key. Blinded signing derives the nonce prefix from the seed, salt and blind, so two blinded keys never share a nonce. A grantee learns the target's admin and write delete keys from the inbox payload (`Core::delete_hints`, persisted, used until `keys.0` arrives), so it writes and self-removes at once; link redemption gets them from K's inbox. One level-2 key per commit (the author chain), checked at receivers: header-list blobs commit to it alone. Inbox hints are kept only from a commit that applied valid, touches the thing and is by an admin of it; the first stays, `keys.0` replaces it (`Core::promote_hints`). Residue (not new): a planted reading-only box for a plain thing creates a `secrets` entry with no keyset, so the thing is its own delete base and unwritable until its `keys.0` arrives.
- **Wire details** (spec/wire.md): one signature domain per signed object (deposit, delete and signal publish got their own, so no signature verifies as another kind). The symmetric box's nonce is BLAKE3(AD), because its key `kdf("box", s)` repeats across every epoch boxed under one s, while AD is unique per (actor, holder, role, epoch). Agility enums are osis enum values in values and structures alike; case 1 matches suite 1.
## Costs
- Grant or rotation: one sealed box (about 1.2 KB) per (holder, role, epoch) written, for key actors (devices, link and recovery keys) as for actors. Measured (osis-keys, one-off): an account with four key-actor admins (three devices, recovery key) removing a device rotates all three roles: 12 sealed boxes, 14.4 KB (1196 bytes each), plus 267 bytes of history boxes; with one box per key actor carrying every role it was 4 boxes, about 5.1 KB (computed: 37 bytes per extra item). An admin grant to a key actor: 3 boxes, 3.6 KB (was one, about 1.3 KB). A read-only rotation costs the same as before; a write rotation of a key-actor admin is one box either way (it no longer re-carries read). History: 32 bytes per earlier epoch plus a tag, and 76 bytes per name (spec/crypto.md §4: one per departure from the actor since its epoch start; 27 more when the rotation departs someone itself). Measured (osis-engine probe, a 10-reader group removing readers one by one, no roster snapshot): the read history box grows 57, 119, 231, 343, 455, 567 bytes, about 112 per removal (36 the earlier secret, 76 its name), against about 1.2 KB of boxes per holder. Every grant and re-seal copies it. Worst case: names are bounded only by the departures since the actor's last roster snapshot (1000 departures: about 76 KB per history box per role); the owner chain's roster snapshots reset the list (policy, not spec). `keys.0`: about 3.6 KB for three roles.
- Names (spec/crypto.md §4, arithmetic): about 75 B each, in every history box a rotation writes and again in each grant's or re-seal's copy of it: one per departure from the actor since its epoch start and per audit-drop target. Held epochs keep their names in the actor's local epochs unit, which is re-encoded whole on each save: O(epochs x names) per rotation.
- A contact card (QR-sized) is a link to a profile thing holding `keys.0`, since the keyset itself is too big for a QR code.
- Delete keys (measured, `budget_minimal_commit` and arithmetic on a minimal `author_or_admin` commit, two levels): header +34 bytes (two `[level, 32-byte key]` instead of `[level, 16-byte hash]`, the 16-byte salt now the 16-byte blind; plaintext 288 to 322), prefix +32 (33-byte commitments instead of 17), commit blob 380 to 444 bytes after Padmé and tag (+64, +17%: the padding step at 320 bytes; with three levels, `writer`: header +51, prefix +48); a chunk adds nothing beyond its key indices (its 16-byte token hashes are gone) but 16 bytes per commitment in its prefix; an inbox payload names a target's two delete keys (+70 bytes per thing with secrets of its own); a delete by delete key +34 bytes per item (a 64-byte signature instead of a 32-byte token); `keys.0` +34 bytes per keyset. Compute (`cargo bench --workspace --bench crypto`, release, shared box): derive a delete key ~12 µs, a blinded commitment ~27 µs per level per blob framed or prefix checked, blinded sign ~36 µs, verify ~36 µs; a host checks two signatures per such delete (~66 µs) where it hashed twice and verified one.

## Implementation
- `osis-crypto` (crate choices and versions: notes/architecture.md §5): ed25519-dalek 2, x25519-dalek 2, libcrux-ml-kem (deterministic keygen and encapsulation from explicit bytes; checked against NIST ACVP FIPS 203 answers in `core/crypto/tests/data/mlkem768_acvp.txt`), chacha20poly1305, blake3, zeroize, subtle, rand_core 0.6.
- Shape: free functions over `Secret32` (zeroizing, redacted, `subtle` constant-time eq; `kdf` returns one, public outputs copy out), `SigningSecret`/`VerifyingKey`/`Signature`, `KemSecret`/`KemPublicKey`, `X25519Secret`. Agility enums are the encoding only (`to_value`/`from_value`, unknown case = `Error::UnknownCase`, Parked); the Rust types have one case until a second suite exists.
- Surface (all at the crate root): `kdf::{kdf, kdf_xof, purpose consts}`, `aead::{seal, open}`; `Domain`, `SigningSecret::{from_seed, verifying_key, sign}`, `VerifyingKey::{from_bytes, verify, to_value, from_value}`, `Signature`; `X25519Secret::{from_secret, random, public, dh}`, `KemSecret::{derive, public, x25519}`, `KemPublicKey`, `seal`/`open_sealed`, `sealed_to_value`/`sealed_from_value`; `KeyActorKeys::from_seed`, `key_actor_role_secret`, `thing_role_secret`, `role_kem`, `creation_nonce`, `dedup_secret`, `delta_hash`, `link_hash`, `link_tree_hash`, `lan_tag`; `Epoch` (`Epoch::derive(actor, role, n, s)`: the nonce rule; `names`; `Epoch::ZERO`: a key actor's fixed epoch), `BoxForm`, `BoxSlot` (`Secrets{actor, holder, role, epoch}` or `Entry{label, step_key, group}`, `actor()`, `ad(form)`), `seal_box(pk, slot, keyset, item, rng)`/`open_box(kem, slot, form, sealed)`, `wrap_symmetric_box(s, slot, epoch_s, secret)`/`open_symmetric_box(s, slot, epoch_s, wrap)`, `seal_history`/`open_history`; `pad`/`unpad`/`padme`, `encrypt_blob`/`decrypt_blob`, `blob_len`, `blob_id`, `wrap` (`Result`)/`unwrap`/`filler_wrap`, `seal_inbox`/`open_inbox`; `LabelRole`, `label_role_key`, `deposit_key`, `label_id`, `claim_key`, `static_entry`, `open_digest`/`sign_open`/`verify_open`; `DeleteSecret::{derive, from_seed, seed, verifying_key, sign}` (blinded signing over ed25519-dalek `hazmat`), `blind`, `commitment`, `verify_delete`; `Secret32`, `SeededRng`, `Error`, re-exported `CryptoRngCore`, `RngCore`, `CryptoRng`, `RngError`, `Zeroizing`, `OsRng`. Doc-hidden, for tests and vectors only: `seal_with` (explicit randomness), `KemSecret::from_parts`.
- Keys are validated at parse: `VerifyingKey` rejects non-canonical and small-order points (dalek's `from_bytes` alone accepts y >= p), `KemPublicKey` rejects a low-order X25519 half and ML-KEM keys failing the FIPS 203 modulus check, so sealing to a parsed key never fails.
- No batch Ed25519 verification: single strict verification only, so spec/crypto.md §1 "batch and single agree" holds trivially. Add batch only with a test that it rejects exactly what `verify_strict` rejects.
- Box `value` encodings (`box`, `keyset`, epoch structs) belong to osis-keys/schema; crypto builds every AD itself from the slot and form (`BoxSlot::ad`), so a box opens only under its own slot and form, seals/opens payloads, and has `Epoch` (n within i64; an int beyond i64 is `TooLarge`, never clamped). Payloads carry `(n, secret)` (a sealed box's `[role, n, secret]`): every opener (`open_box`, `open_symmetric_box` at a `secrets.0` slot, `open_history`) recomputes each epoch from the actor (an entry box's `group`), role, n and secret, and a box whose secret for its key's role does not name the key's epoch is `Malformed`; sealers refuse an item whose epoch its secret does not name. History boxes reject entries out of order or whose n is not below the box's.
- Blob prefix layout is osis-label's; `encrypt_blob(prefix, plaintext, rng)` / `decrypt_blob(blob, prefix_len, key)`. There is no encrypt-under-given-key entry point (spec/crypto.md §5).
- Vectors: osis-vectors subjects `kdf/`, `keys/`, `box/` (incl. the inbox sealed box), `wrap/` (incl. blob encryption over an opaque prefix), `delete/`, `sign/`, `tid/key-actor.vec`, hand-written `padme/`; generators in `core/test/vectors/src/subjects/`. Blob prefixes with commitments, commit/chunk/page blobs, steps, claim sets, full inbox payloads and signal envelopes are label/commit vectors.
- `SeededRng` (BLAKE3 XOF keyed by a seed) is the deterministic rng for tests, vectors and the simulator; drivers use `OsRng`.
- Bench: `cargo bench --workspace --bench crypto` (release, shared 4-core box): sealed box seal ~200 µs, open ~85 µs, KEM keygen ~40 µs, blob encrypt ~750 MB/s, decrypt ~1100 MB/s, Ed25519 sign ~19 µs, verify ~40 µs.
- **Self-verifying epochs** (spec/crypto.md §4): an epoch's nonce is `kdf("epoch", s, actor || role || le64(n))`, 32 bytes, so each source of a secret (box, history entry, entry box) is checked alone, in any order, by recomputing its epoch. This replaced order-dependent "which copy do we trust" state: the first keyset recorded per epoch (a writer re-publishing an epoch's keyset with junk keys made late joiners refuse the genuine box for good), the hash of the first rotation's history box, unverified and per-author candidate lists, and reopening `secrets.0` when a keyset refuted a held secret. Hashing the secret, not the keyset: holders check either at the same strength, a non-holder gains nothing (a writer can name a fresh epoch matching junk keys), and the keyset costs an ML-KEM keygen per check. Actor, role and n are bound for domain separation (one secret never names two epochs). 32 bytes: one ID, one secret by plain collision resistance at the suite's level (16 would let a rotator equivocate at 2^64 work). What it does not decide stays with establishment: planted epochs (anyone writing a box, entry or entry box can make up `(n, s)`), huge n (headroom), false supersession by a history box opened with a genuine secret (bounded: such writers could rotate anyway), junk keysets seen by non-holders (the existing writer DoS on sealers, healed by re-seal). Cost: one keyed BLAKE3 per secret learned; boxes +16 bytes per epoch named, payload items -17 bytes.
- `osis-keys`: `ActorEpochs`/`RoleEpochs` per actor per role (`EpochInfo`: suite, supersedes, rotations, snapshot, names, established, secret, reading, order: a derived epoch past the cap keeps the owner epoch's n as its order n, so `RoleEpochs::is_newer`/`newest` and `newer_than_head` order it as the owner's; supersession alone would not pick among concurrent owner forks). **Established** (spec/crypto.md §4) is `established: Option<Provenance>`: `Fixed` (`key_actor`) and `Derived` (`derived`, where the owner's is) are set directly and persisted; `Rotated` is computed by `RoleEpochs::establish(held)` and never stored: base `rotations` (held valid rotation commits of it, each with its keyset's list, `SecretsWrite::rotated` from `after_join` for valid parts only; `invalidate` drops one, `revalidated` records it again) or `snapshot` (`snapshot_keyed`), within headroom, and, its secret held for use, some entry of `names` (the names of each of its history entries opened under its secret, `open_histories`) met under `held` (`names::Held`: the engine's `NamesHeld` checks applied commits, epoch starts, the departing commit by `ts` and signer among the actor's held `roles.0` deltas). The engine's view is `Core::own_epochs` (the record `own_record` established on read), so establishment needs no invalidation when commits, verdicts or epoch starts change; a view stored back into the record goes through `ActorEpochs::into_record`. Differentials: osis-keys `names::names_establish_by_the_held_set` (random histories with withheld commits, forged entries, invalid commits, snapshots, forks, flipping verdicts in any order, against a direct reading of the rule, plus the invariant), osis-engine `rotation::tests::withheld_departures_leak_nothing(_large)` (end to end: an admin withheld departing commits re-seals and rotates; no departed peer opens an epoch whose rotator held its departure). Names are computed by `rotation::departures::names` (a superset over the actor: every applied commit after its epoch start lowering a grant on it, every audit drop of an edge write on it); `rotation_into` fixes the commit's `ts` beforehand when it departs someone (`departs`: its own `ts` and signer). The named commits are placed with the rotation (`rotation::placed_with`). Supersession is read from the commit: what its keyset lists (`Keyset::supersedes`, a set: every current epoch but derived ones, which have no rotation commit and are superseded through the history box) and what its opened history box lists (`EpochInfo::superseded_epochs`), so a flipped verdict leaves nothing behind. There is no own-rotation provenance: the rotator's commit applies locally before `rotation::record` stores the secrets, so its epochs fall when the commit turns invalid (osis-engine `invalid_own_rotation_falls_spec_crypto_4`). `Rotation::preview` (account creation: the genesis label inside the rotation commit) marks the new epochs established in a scratch view. A rotation commit is told from a grant or re-seal by its `keys.0` write: only history boxes at the epochs whose keyset the commit sets count (`rotation_commit`); a re-seal re-writes history boxes too, and counting those was R9. `keys.0` vouches for no secret. Nothing is inferred from the applied `secrets.0` state (`observe_secrets`, `observe_keys`, `ingest` establish nothing). current = established and not in an established epoch's `superseded_epochs`. Unestablished secrets are for reading and opening (`registered_epoch` matches any held secret; stamps, steps, deletes check `is_established`). One secret per epoch (`secret`); `reading` holds the pending commits (`Unchecked`: author node, commit) it is known from when known only from such: non-empty, it is reading-only (`secret`/`held` skip it; `reading_secret`, `held_newest_first`, `registered_secret` include it), and what a reading-only secret opens by history inherits its sources, supersedes nothing and records no names. Epochs known only from pending commits are capped at `MAX_READING_PER_AUTHOR` (64) per author and `MAX_READING` (256) per role (each costs a trial decrypt per wrap, since wraps name no epoch); authors whose `created.0` the node lacks share one budget (`UNKNOWN_AUTHOR`), so throwaway identities gain nothing; the node holds at most `MAX_READING_ACTORS` (64) actors through reading-only secrets alone; the node drops a commit as a source when it applies or is dropped as bad input, and a secret it was the last source of goes (`apply::keys::forget_unchecked`; an actor left with no secret goes on the lost-access work list, which forgets what they read). Accepted limit (Tess): an insider's bogus pending commits under throwaway authors can fill the unknown-author pool, so a genuine grant whose granter's chain the node lacks adds nothing and the holder reads only once the grant applies (one sync later; nothing exposed or lost). Tests `bogus_flood_bounded_by_caps_spec_crypto_4`, `genuine_grant_applies_after_flood_spec_crypto_4`. History keys with several live entries (an invite holder's put beside the genuine one) are opened entry by entry (`HistoryAlts`, `ingest_with`; the node passes `engine::secrets::history_alts` of the state): a lying entry only names planted epochs, never established, or, written by a holder of the epoch, names less (accepted: it could leak the epoch anyway). A label entry box's read secret is held when it names its epoch (`Engine::learn_read_secret`); it establishes nothing. Persisted by `engine::secrets::encode_epochs` (rotations as `[commit, [epoch]]`, names as their wire value, reading as `[author, commit]`). Derived epochs: `ActorEpochs::derived(owner, tid)` maps each owner epoch whose secret is held to the thing's epoch at the owner's n capped at `MAX_FREE_N` − 1 (`derived_n`) named by the derived secret, and keeps an owner epoch without a secret as a placeholder at that n whose nonce hashes the whole owner epoch (no secret names it; owner nonces alone could collide through made-up or capped epochs) so that what it supersedes stays superseded. The cap: a writer of the owner may jump its n past `MAX_FREE_N`; uncapped, a thing's switch rotation then landed above the headroom line with nothing at n − 1 a holder holding no owner secret could establish. Not n 0 for all: derived epochs must order as the owner's, or an owner rotation leaves a plain group's label head "newer" only by nonce luck (`newer_than_head`, re-registration skipped half the time) and a writer picks a fork other than the owner's newest. Past the cap (attack only) they keep that order through `order` (only in `derived`'s result; a thing with own secrets holds its derived epochs without it, and a rotation's wrap picks by n, spec/crypto.md §5); `adopt_derived` establishes a thing's derived epochs (after its own-secrets switch) only where the owner's secret is held. `rotate`: n+1 over the current epochs, the epoch named by the fresh secret, history of established held secrets only (`held_established`) with the names, removes role-r boxes at the current epochs, lists in the keyset what it supersedes; its own record supersedes what every other node reads from the commit (`Rotated::supersedes`). `box_holder` (grant and re-seal: current established epochs, history boxes copied), `reseal_needed` (missing boxes at current epochs), `may_compact_secrets` (every epoch the state keys is established), `newest_secret` = newest established held (stranded wrap), `newer_than_head` also needs the head admin epoch established (the step signs under it). Writes are `SecretsWrite { boxes, removed, history }` / `KeysWrite` (the node turns them into map deltas). `ingest`/`open_boxes`/`open_histories`. Recipients: `HolderKeys::{KeyActor, Actor}`; a holder actor's per role at the keyset Seal gives, symmetric when the writer holds that established epoch's secret (`rotation::members::sealed`). Tests for the TLC traces: `tests/it/established.rs`. Residual: a malicious valid rotator leaks what it holds (names it omits, or a second history entry naming less, only hand on epochs it held).
- **One box per (holder, role, epoch)** for every holder, key actors included (Tess's decision, reseal-forks; `box_items`): a rotation of one role removes and writes boxes of that role only, so no other role's secret moves, and the covers rule and re-seal trigger look at exact keys. A key actor's box once carried every role written, keyed at the top one, plus the lower roles' newest when a rotation replaced it; that needed a ts-ordered guess at what such a box carried (it could not be opened to check), a forced rotation of a carried role that did not cover, a refusal to rotate when a carried secret was not held, and per-fork exception boxes, and still stranded holders: a box ordered after a fork's rotation was credited with it though written by a node that never held it (was issues/reseal-stranded-forks.md: `forked_reseals_settle_*` seed 3). Cost below (Costs).
- **Supersession is read from the rotation commit** (spec/crypto.md §4): the epochs its keyset lists, the same at every node in any arrival order, and, at a node holding the new secret, those its history box lists. The two differ only on derived epochs (unlisted: they have no rotation commit, and a node holding no owner secret never establishes one). Reading it from the commits' box removals instead (dots naming the removed records' writers) let a re-grant hide the chain and a departed granter steer it to a forged claim, and left an epoch whose rotation boxed nobody current at nodes that could not open the history box. Taking it also from the `keys.0` keyset the applier held before (needed only while key actors' boxes were keyed at their top role) made the set depend on order: a rotation made unaware of a concurrent fork superseded that fork wherever its keyset had won `keys.0` first, and the fork's holders lost it (seed 75 there). A rotator removes the boxes at each of its current epochs. Test `rotation::supersession_independent_of_arrival_order` (osis-keys), the re-seal invariant in `forked_reseals_*` (osis-engine).

## Rejected
- Per-epoch `keys.0` history, per-role boxes to devices: needless 1.2 KB objects. (A KEM key for link keys was rejected on the same ground and later reinstated, above.)
- Node KEM keys as the only sealing target: a granter would need the grantee's device list; a new device would need re-grants from everyone.
- Tid committing to the KEM key: 1.2 KB in every chain certificate; rotation would need a new tid.
- One KEM key per actor (above). Cleartext epoch byte in wraps (above).
- AES-256-GCM and AEGIS (above); HPKE (SHA-256 inside, no hybrid in the RFC); X-Wing (draft at decision time); ML-KEM-1024 (768 matches TLS and Signal practice); PQ signatures now.

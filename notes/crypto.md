# Crypto: rationale
> Summary: Why suite 1 (spec/crypto.md) is what it is, costs of keys and boxes, proposed crates, rejected options. The suite was the agent's call with the owner deferring; hybrid post-quantum boxes follow from the requirement that long-lived secrets resist a future quantum attacker.

## Why
- **Ed25519**: 32-byte keys, 64-byte signatures, fast verification per commit. Strict verification so every node accepts exactly the same signatures. PQ signatures not now and not required (spec/requirements.md: signatures need not resist a quantum attacker): ML-DSA-44 has 2420-byte signatures and 1312-byte keys, over ten times the commit floor. If ever wanted: a new enum case; devices move by add-and-remove, a root key by copying the person actor (spec/permissions.md §7, rare and costly); stored data stays valid. An in-place successor key in `/keys` would be a convenience only, and its fork rule could only be keep-the-first-seen, as for colliding creation records.
- **Hybrid PQ sealed boxes**: boxes sit on blind nodes forever and lazy rotation keeps old secrets valid for old content, so a classical box harvested today would yield every blob under that secret, forever; a later migration cannot re-protect it. The cost lands only on membership changes (about 1.2 KB per member and role), never per blob or commit. Generic hash-everything combiner (secure if either KEM is); X-Wing was a draft at decision time; if it is an RFC by implementation, add it as a second case.
- **XChaCha20-Poly1305 over AES-GCM**: 96-bit GCM nonces plus frequent local unit rewrites invite nonce reuse; GCM is slow without hardware and in WASM. A hardware-speed suite can be added later for multi-GB values.
- **KEM key per role** for non-key actors: effective role is the minimum along the chain, so a box sealed to A's write key must be openable only by A's writers. One KEM key per actor would hand every reader of A all of A's write and admin secrets. Concretely: actor A (a team) holds admin on doc T and has read-only members; T's admin box to A must stay closed to them, else they get T's admin secret, hence T's admin delete key and label keys ("reading never allows deleting data", "readers only read", spec/requirements.md). The sealer cannot tell A's roles apart without a public key per role, and a single key must be held by A's readers (they need A's read boxes), so one KEM key per actor with role and epoch bound only in the AD (replay-proof, not confidential) breaks this for any actor whose members hold different roles. It is safe only where every member of A holds every role A is boxed at (by convention a person actor: devices and recovery key are all admins), which the sealer cannot know. For the same reason one box per actor member carrying all its roles, sealed at its top role, would lock A's lower-role members out. Cheaper variants (one ML-KEM key per actor with an X25519 key per role; roles sharing a key while their holders coincide) were declined by the owner: notes/chat.md Costs.
- **`/keys` holds the current keyset only**: nobody seals to an old epoch on purpose, and a granter with a stale key still succeeds because members keep old secrets. The deposit seed lives beside the keysets (one per actor; each label's deposit key derives from it by label ID, notes/sync.md); refreshing it is a MAY against an ex-member filling the budget, because a refresh also refuses the stranded heartbeats of members that missed the rotation (issues/reseal-triggers.md).
- **Key actors have seed-derived role secrets** so a thing owned by a key actor (a node's local thing, a person actor under its recovery key) is a plain thing like any other; they are never rotated and never shared. The KEM key is seed-derived too and never rotates: the seed is the device, a compromise is a device removal, and a keyset epoch for key actors would have put an epoch into every box and claim-set rule for a case nothing uses (devices and link keys are replaced by add-and-remove; a suite migration is a new key actor).
- **Big rosters**: a rotation's boxes page like any map, and `/secrets` compacts by ordinary paged compaction snapshots, so no roster size makes rotation impossible; the roster snapshot's header still lists one delta hash per edge (spec/requirements.md, Scale).
- **Link keys are full key actors** (signing and KEM keys from the seed): the earlier sign-only design derived K's secrets from the seed, which handed every read-link holder K's admin secret and label delete key, and used a symmetric link box only the sharer could write, which a writer's rotation of K could not refresh (notes/permissions.md, Links). Cost: 1.2 KB per box to L per rotation of K, and one hybrid entry box per step of K's label.
- **Symmetric box form** when the writer already holds the recipient's role secret (a thing's secrets to its owner): 49 bytes plus the epoch of the recipient's secret, which the covers rule needs (without it an owner's rotation after a lost device would not make the thing's epoch stale).
- **Epochs per role**, not per actor: a writer may rotate read and write but not admin, so a per-actor epoch would have to say which roles "carry over" and where their boxes live; per-role epochs make each role an independent chain of secrets, boxes and history boxes, and `/keys` an independent keyset per role that the rotator of that role writes.
- **History boxes**: holding a role's current secret opens every older one; a member removed before epoch n opens nothing newer; a join costs one box per role, not one per epoch. A grant or re-seal re-writes the history box of each epoch it boxes (same ciphertext, a register rewrite): the recipient can decrypt it but could not otherwise fetch it, since the rotation commit that carries it is wrapped under the epoch the recipient lacks (TLC R3). Cost: 32 bytes per earlier epoch per grant. A history box carries only secrets of **established** epochs (TLC R9): a node re-sealed at e before e's commit reached it holds e's secret but not the departure e carries, and would otherwise rotate over e and hand e's secret, boxed in its history, to the member e removed. Establishment (spec/crypto.md §4) is the one notion behind "may encrypt under", "current", what a history box carries and where a re-seal may be made: own rotations, fixed and derived epochs, applied rotation commits with their whole superseded chain applied, and epochs a held `/secrets` snapshot keys (the chain is compacted; a node snapshots `/secrets` only from a fully established state so its snapshot vouches for nothing it did not verify). Unestablished secrets read; nothing is written under them. Alternatives rejected: an age rule (a rotation commit older than `MEMBERSHIP_KEEP` needs no chain) depends on the clock and needs rotation commits kept while current; a re-seal carrying the rotation commits it boxes is a new inbox payload (wire) and does not help a grant raced by a rotation.
- **Opening is not encrypting under**: an open signature proves possession of the read secret to a server; the departed member holds the same key, and nothing downstream relies on the open. Treating it as encrypting under deadlocked a re-sealed member (it needs the sync key to fetch the commit that establishes the epoch). Stamps, steps and deletes stay encrypting under: others act on them.
- **Rotation commits wrap under the superseded epoch** (the only exception to wrapping under the newest): the commit carries the new secret, so under the new wrap only its author could read it; the leak to an ex-member via a dishonest server is the new epoch's box map (notes/sync.md).
- **Wraps name no epoch**: a cleartext epoch byte would leak rotation timing per blob to save one tag check. A lagging relayer's older-epoch wrap extends an ex-member's reach by that blob (spec/requirements.md, Out of scope). An uploader wraps under the newest *current* epoch whose secret it holds; a node that holds no current secret (the rotation it received boxed it nowhere) is stranded and places only its heartbeat, under the newest secret it has, which tells co-members which epoch it is on.
- **Blob encryption never takes a caller key**, so a rewritten blob (purged delta) always gets a fresh key and ID.
- ML-KEM's internal SHA3/SHAKE is internal to that primitive; "one hash function" means every hash osis computes itself.

- **Delete keys are signatures under blinded keys** (owner decision, replacing hashed tokens): one mechanism for every level; a writer that is no admin lists the thing's published admin key, so a thing admin who is no group admin deletes a writer's data at servers (the hashed scheme needed the admin secret to list level 1). Each blob commits to A' = h·A with h from A, the prefix salt and a 16-byte random **blind** in the encrypted header (Tor v3 style key blinding); without the header blind h would be computable from A alone, and A is widely known (level-2 keys travel in chain certificates and contact profiles, a key actor's is its signing key, a group's admin key is known to its readers), so a server colluding with any contact could link an author's or owner's blobs across groups (spec/requirements.md, Untrusted nodes; security review). Only header readers compute A'; only the holder of a signs; a delete reveals nothing. Chunks and header-list blobs use the blind of the header that introduced them (the reuse check looks it up: `Reuse::index`'s `blind_of`). The label key signature stays: every past holder of an epoch's secret can sign with its delete key, so only it proves current membership. A thing without secrets of its own uses its delete base's keys (its owner's admins are its admins, so the right holders are the same and nothing per thing is published); a key-actor base uses its signing key (public through the creation record; key actors never rotate). The base is the first actor in the chain with secrets of its own whatever the role (all three come at once), so a thing whose `/keys` has not arrived is not writable rather than wrongly listing its owner's key. Blinded signing derives the nonce prefix from the seed, salt and blind, so two blinded keys never share a nonce. A grantee learns the target's admin and write delete keys from the inbox payload (`Core::delete_hints`, persisted, used until `/keys` arrives), so it writes and self-removes at once; link redemption gets them from K's inbox. One level-2 key per commit (the author chain), checked at receivers: header-list blobs commit to it alone. Inbox hints are kept only from a commit that applied valid, touches the thing and is by an admin of it; the first stays, `/keys` replaces it (`Core::promote_hints`). Residue (not new): a planted reading-only box for a plain thing creates a `secrets` entry with no keyset, so the thing is its own delete base and unwritable until its `/keys` arrives.
- **Wire details** (spec/wire.md): one signature domain per signed object (deposit, delete and signal publish got their own, so no signature verifies as another kind). The symmetric box's nonce is BLAKE3(AD), because its key `kdf("box", s)` repeats across every epoch boxed under one s, while AD is unique per (actor, member, role, epoch). Agility enums are osis enum values in values and structures alike; case 1 matches suite 1.
## Costs
- Grant or rotation: one sealed box (about 1.2 KB) per (member, role at or below the granted one), one per device for key-actor members. History: 32 bytes per earlier epoch plus a tag. `/keys`: about 3.6 KB for three roles.
- A contact card (QR-sized) is a link to a profile thing holding `/keys`, since the keyset itself is too big for a QR code.
- Delete keys (measured, `budget_minimal_commit` and arithmetic on a minimal `author` commit, two levels): header +34 bytes (two `[level, 32-byte key]` instead of `[level, 16-byte hash]`, the 16-byte salt now the 16-byte blind; plaintext 288 to 322), prefix +32 (33-byte commitments instead of 17), commit blob 380 to 444 bytes after Padmé and tag (+64, +17%: the padding step at 320 bytes; with three levels, `writer`: header +51, prefix +48); a chunk adds nothing beyond its key indices (its 16-byte token hashes are gone) but 16 bytes per commitment in its prefix; an inbox payload names a target's two delete keys (+70 bytes per thing with secrets of its own); a delete by delete key +34 bytes per item (a 64-byte signature instead of a 32-byte token); `/keys` +34 bytes per keyset. Compute (`cargo bench --workspace --bench crypto`, release, shared box): derive a delete key ~12 µs, a blinded commitment ~27 µs per level per blob framed or prefix checked, blinded sign ~36 µs, verify ~36 µs; a server checks two signatures per such delete (~66 µs) where it hashed twice and verified one.

## Implementation
- `osis-crypto` (crate choices and versions: notes/architecture.md §5): ed25519-dalek 2, x25519-dalek 2, libcrux-ml-kem (deterministic keygen and encapsulation from explicit bytes; checked against NIST ACVP FIPS 203 answers in `core/crypto/tests/data/mlkem768_acvp.txt`), chacha20poly1305, blake3, zeroize, subtle, rand_core 0.6.
- Shape: free functions over `Secret32` (zeroizing, redacted, `subtle` constant-time eq; `kdf` returns one, public outputs copy out), `SigningSecret`/`VerifyingKey`/`Signature`, `KemSecret`/`KemPublicKey`, `X25519Secret`. Agility enums are the encoding only (`to_value`/`from_value`, unknown case = `Error::UnknownCase`, Parked); the Rust types have one case until a second suite exists.
- Surface (all at the crate root): `kdf::{kdf, kdf_xof, purpose consts}`, `aead::{seal, open}`; `Domain`, `SigningSecret::{from_seed, verifying_key, sign}`, `VerifyingKey::{from_bytes, verify, to_value, from_value}`, `Signature`; `X25519Secret::{from_secret, random, public, dh}`, `KemSecret::{derive, public, x25519}`, `KemPublicKey`, `seal`/`open_sealed`, `sealed_to_value`/`sealed_from_value`; `KeyActorKeys::from_seed`, `key_actor_role_secret`, `thing_role_secret`, `role_kem`, `creation_nonce`, `dedup_secret`, `delta_hash`, `link_hash`, `link_tree_hash`, `lan_tag`; `Epoch` (`Epoch::ZERO`: a key actor's fixed epoch), `BoxForm`, `BoxSlot` (`Secrets{actor, member, role, epoch}` or `Entry{label, step_key}`, `ad(form)`), `seal_box(pk, slot, keyset, items, rng)`/`open_box(kem, slot, form, sealed)`, `wrap_symmetric_box(s, slot, epoch_s, secret)`/`open_symmetric_box(s, slot, epoch_s, wrap)`, `seal_history`/`open_history`; `pad`/`unpad`/`padme`, `encrypt_blob`/`decrypt_blob`, `blob_id`, `wrap` (`Result`)/`unwrap`/`filler_wrap`, `seal_inbox`/`open_inbox`; `LabelRole`, `label_role_key`, `deposit_key`, `label_id`, `claim_key`, `static_entry`, `open_digest`/`sign_open`/`verify_open`; `DeleteSecret::{derive, from_seed, seed, verifying_key, sign}` (blinded signing over ed25519-dalek `hazmat`), `blind`, `commitment`, `verify_delete`; `Secret32`, `SeededRng`, `Error`, re-exported `CryptoRngCore`, `RngCore`, `CryptoRng`, `RngError`, `Zeroizing`, `OsRng` (`os-rng`). Doc-hidden, for tests and vectors only: `seal_with` (explicit randomness), `KemSecret::from_parts`.
- Keys are validated at parse: `VerifyingKey` rejects non-canonical and small-order points (dalek's `from_bytes` alone accepts y >= p), `KemPublicKey` rejects a low-order X25519 half and ML-KEM keys failing the FIPS 203 modulus check, so sealing to a parsed key never fails.
- No batch Ed25519 verification: single strict verification only, so spec/crypto.md §1 "batch and single agree" holds trivially. Add batch only with a test that it rejects exactly what `verify_strict` rejects.
- Box `value` encodings (`box`, `keyset`, epoch structs) belong to osis-keys/schema; crypto builds every AD itself from the slot and form (`BoxSlot::ad`), so a box opens only under its own slot and form, seals/opens payloads, and has `Epoch` (n within i64; an int beyond i64 is `TooLarge`, never clamped). History boxes reject two secrets at one epoch and entries whose n is not below the box's.
- Blob prefix layout is osis-label's; `encrypt_blob(prefix, plaintext, rng)` / `decrypt_blob(blob, prefix_len, key)`. There is no encrypt-under-given-key entry point (spec/crypto.md §5).
- Vectors: osis-vectors subjects `kdf/`, `keys/`, `box/` (incl. the inbox sealed box), `wrap/` (incl. blob encryption over an opaque prefix), `delete/`, `sign/`, `tid/key-actor.vec`, hand-written `padme/`; generators in `core/test/vectors/src/subjects/`. Blob prefixes with commitments, commit/chunk/page blobs, steps, claim sets, full inbox payloads and signal envelopes are label/commit vectors.
- `SeededRng` (BLAKE3 XOF keyed by a seed) is the deterministic rng for tests, vectors and the simulator; drivers enable `os-rng` for `OsRng`.
- Bench: `cargo bench --workspace --bench crypto` (release, shared 4-core box): sealed box seal ~200 µs, open ~85 µs, KEM keygen ~40 µs, blob encrypt ~750 MB/s, decrypt ~1100 MB/s, Ed25519 sign ~19 µs, verify ~40 µs.
- `osis-keys`: `ActorEpochs`/`RoleEpochs` per actor per role (`EpochInfo`: suite, supersedes, applied, snapshot, established, secret). **Established** (spec/crypto.md §4) is `established: Option<Provenance>`: `Own` (`Rotation::record`), `Fixed` (`key_actor`), `Derived` (`derived`, where the owner's is) are set directly; `Chain` and `Snapshot` are recomputed by the `establish` fixpoint from the persisted inputs `applied` (the superseded set of the epoch's applied valid rotation commit, `SecretsWrite::applied`) and `snapshot` (a held `/secrets` compaction snapshot keys it, `snapshot_keyed`); Chain beats Snapshot (re-seal allowed). A rotation commit is told from a grant or re-seal by its `/keys` write: only history boxes at the epochs whose keyset the commit sets count (`rotation_commit`); a re-seal re-writes history boxes too, and counting those was R9. Nothing is ever inferred from the applied `/secrets` state (`observe_secrets`, `observe_keys`, `ingest` establish nothing). current = established and not in an established epoch's `supersedes` (from removed boxes, the replaced keyset, and opened history boxes, so a snapshot-established state still orders itself; the chain condition uses only the commit's set, else a derived base epoch the node never held would block it). Unestablished secrets are for reading and opening (`registered_epoch` matches any held secret; stamps, steps, deletes check `is_established`). Reading-only secrets (from unchecked boxes) are `EpochInfo::reading`, candidates with their source (`Unchecked`: author node, pending commit): one per author and epoch (a wrong one planted first by an insider does not hide the genuine one from another author), at most `MAX_READING_PER_AUTHOR` (64) per author and `MAX_READING` (256) per role; authors whose `/created` the node lacks share one budget (`UNKNOWN_AUTHOR`, several per epoch), so throwaway identities gain nothing; a candidate for an epoch the actor's held `/keys` publishes must derive its KEM key (`prune_reading`, at ingest and when `/keys` arrives: planted secrets for known actors go entirely); the node holds at most `MAX_READING_ACTORS` (64) actors through reading-only secrets alone; the node drops a commit's candidates when it applies or is dropped as bad input (`apply::keys::forget_unchecked`; an actor they were the only secrets of goes on the lost-access work list, which forgets what they read). Accepted limit (owner): an insider's bogus pending commits under throwaway authors can fill the unknown-author pool, so a genuine grant whose granter's chain the node lacks adds no candidate and the member reads only once the grant applies (one sync later; nothing exposed or lost). A per-grantee budget was removed: a claimed grant is as unverified as the boxes. Tests `bogus_flood_bounded_by_caps_spec_crypto_4`, `genuine_grant_applies_after_flood_spec_crypto_4`. History keys with several live entries (an invite holder's put beside the genuine one) are opened entry by entry (`HistoryAlts`, `ingest_with`; the node passes `engine::secrets::history_alts` of the state). `reading_secrets`, `held_newest_first` and `registered_secret` try each, history boxes open with whichever opens them (what it opens inherits its source); a checked secret (`set_secret`) drops them. `secret`/`held` give checked secrets only. Persisted as an 8th field of `[secret, author, commit]` (the older `Bool` layout decodes with an unknown source). `rotate`: n+1 over every known epoch, history of established held secrets only (`held_established`), removes role-r boxes at the superseded epochs. `box_member` (grant: current established epochs, history boxes copied), `reseal_member` (Chain/Own current epochs only), `reseal_needed` (missing boxes at Chain/Own current epochs), `newest_is_snapshot` (re-sealer may rotate instead), `may_compact_secrets` (every epoch the state keys is established), `newest_secret` = newest established held (stranded wrap), `newer_than_head` also needs the head admin epoch established (the step signs under it). Key actors: `ActorEpochs::key_actor(seed)` at `Epoch::ZERO`; plain things `ActorEpochs::derived(owner, tid)`. Writes are `SecretsWrite { boxes, removed, history }` / `KeysWrite` (the node turns them into map deltas). `ingest`/`open_boxes`/`open_histories`, `SecretStore` trait (persists establishment). Recipients: `MemberKeys::{KeyActor, Actor}`; symmetric when the writer holds the member's secret (`with_own`) unless it holds a newer keyset. Tests for the TLC traces: `tests/it/established.rs`.
- Key-actor boxes: one per write, keyed at the top role written; a rotation's box also carries the newest current secret of the roles below the key it does not rotate, and a rotation that removes a key actor's box but writes it no role (its demotion) writes it one box with every role it holds, else the key actor is stranded (found by the props test, which no longer re-seals). Carried secrets go through `rotate`'s `may_carry` (the covers rule): an uncovered carried role is rotated too. A grant to a key actor carries each role's newest epoch only (forks of a lower role are not all boxed; the next rotation's history covers them). The covers rule treats a key-actor box keyed at a higher current role as carrying the lower roles (it cannot be opened; leniency only costs rotations); the re-seal trigger counts it for (r, e) only where the caller's `carries` says its writing commit knew e (a key actor's grant raced by a read-only rotation otherwise looked boxed). Delete keys: `delete_key(level, base, author)` (newest held), `delete_candidates` (every held epoch); keysets carry `delete_key` (`keyset`), and `prune_reading` checks it with the KEM key.
- Header-list chunks and tree nodes carry only the commit's level-2 (author-chain) commitment (owner: one uniform rule, no cutoff): at blind nodes the author chain deletes them by its delete key, else the label delete key; a thing admin who is no group admin waits for a group admin there (accepted). An import's lists carry none.
- Not in the protocol: password hashing (an app exporting a recovery key uses Argon2id), transport crypto (TLS 1.3, QUIC, iroh).

## Rejected
- Per-epoch `/keys` history, per-role boxes to devices: needless 1.2 KB objects. (A KEM key for link keys was rejected on the same ground and later reinstated, above.)
- Node KEM keys as the only sealing target: a granter would need the grantee's device list; a new device would need re-grants from everyone.
- Tid committing to the KEM key: 1.2 KB in every chain certificate; rotation would need a new tid.
- One KEM key per actor (above). Cleartext epoch byte in wraps (above).
- AES-256-GCM and AEGIS (above); HPKE (SHA-256 inside, no hybrid in the RFC); X-Wing (draft at decision time); ML-KEM-1024 (768 matches TLS and Signal practice); PQ signatures now.

# Chat
> Summary: Chat as built on design E (notes/chat-designs/e.md): crate `osis-chat` (libs/chat) over the `osis` API, and `osis chat`: one ownerless actor per chat, participants hold write, a message is one kept write on `chat:msgs:y<year>.0`, the sender the verified actor. What is built, what the app layer decided, what is left out, costs. Kept from the old pattern: rotation costs and Tess's decision on them.

## As built
- **Create** (`create`, one flow): `create_ownerless(me)` (plain `create()` once owners go), `required.0^` (`chat:msgs:` the message rule; the empty prefix the plain default, so `nobody` junk on another aspect is invalid; `keep` true), `chat:settings.0^` (name, edit mode), `make_group`, `sync`. A host must take it by label or `--admit open`: `admit own` does not.
- **Participants**: `add` is `grant` (a chat is synced from `create`); a link is `make_link`, `join` is `redeem`, except that a chat already in `chats` is returned without redeeming, and a redemption that fails is a success if the chat is in `chats` afterwards (before, the maker's own link hung until the timeout, a second redemption failed `Permission`, a used single-use link `Invalid`). So a link never raises a participant's role, and a link whose target names a held chat opens it unredeemed, whatever its key (`redeem` itself refuses a link whose K has no edge on the target); a kept copy is not held, so its link rejoins. A link joiner holds through K, and `participants` reads through K to them, at the lesser role, and drops L; `links` lists the Ks with their key. An actor is read through when owned by an owner with an owner (a link's K, a team): an account's owner is a key, its holders are devices. A direct participant learns a joiner at its first post (the joiner's chain comes with it) and lists K till it knows someone of it; a joiner and the link's maker know all. Only the device that made a link can kick one joiner (`MadeLink` is local); any admin can kick K, ending everyone behind it. Moderator: `Role::Admin`; all admins equal. `kick` is `set_role(.., None, ..)`, keep filled from the default, `Some(false)` erases; `purge_participant` is `purge_author` per year. `leave` removes every grant the account holds the chat through (a link joiner's is on K); the admin's following removal that audits backdated posts is not automated. Kicking a link joiner ends the link for those who have not redeemed it (`set_role`): make a new one. A leave ends nothing: the link goes on working however many leave, and a leaver who kept the text can rejoin by it (notes/permissions.md Links).
- **Message**: `replace`, never `set` (an equal `set` writes nothing), of one scalar: CBOR bytes of a map, `0` text, `1` original, `2` prior, `3` name, `4` reply-to (a `replace` of a map leaves state per entry, so writes on a long aspect grow: 0.5 to 1.2 ms over 4000 writes, flat with a scalar). An id is `YEAR/TS/COMMIT`: the aspect and the place, so a reference needs no scan. Retention and expiry come from the rule, filled by the node.
- **Name**: in the signed body, per message: the sender's own word, nobody can name another's messages; no registry. Tid beside it is what is verified. CLI: `--from` or `OSIS_CHAT_NAME`.
- **Read**: `entries` merges the years (creation's to next year's) by `(ts, ID)` both ways, no tie of year to stamp. `Timeline::older` goes from the newest: it has then seen every edit of what it reaches, so a page back costs the distance from the newest, not a lookup per message. `since(after)` goes by arrival at this node (`received`, then `(ts, ID)`), not by stamp: a post made offline is stamped before what the reader has seen and still comes after the cursor. It reads the whole history each call (no arrival index; about 0.2 s at 10^4 messages), so it is for a reader that comes and goes: an app showing a timeline uses `watch`. An edit of an older message comes as that message again under its id; a deletion of an older message moves no cursor (use `watch`). Limits: an entry arriving in the cursor's millisecond with a lesser ID, or after the node's clock jumped back past the cursor, is missed. `cursor` is this node's: not to be carried to another. `find` reads back to the original. Others' invalid writes are hidden; one's own show `valid: false` with the text.
- **Edit**: a new message naming the original and every earlier version; honored only if the original is here, is no edit itself and has the same verified sender, else it is a message of its own. Newest by `(ts, ID)` wins. Under `EditMode::Purge` a second commit purges the old (a commit with a request carries no expiry, so never the same commit). Named versions' tombstones are the message's, so an edited message shows once.
- **Delete**: `purge_commit` of every version known, one commit. `Body::Deleted { who }` is the request's verified actor (`HistoryBody::Purged`). Refused locally without the right (a request without it drops nothing). Tombstones of permanent deltas reach new devices and newcomers. Purge sets from `Options::purge`.
- **Disappearing**: per chat, the rule's expiry; `set_disappearing` writes `required.0^` whole. Leaves kept copies too.
- **Told, re-sent**: `on_rejected` is `OwnWriteInvalid` per commit (a write before the writer saw a `required.0^` change with a key after it, or its own kick). `resend` writes its text, name and reply as a new message; the old one stays, shown to its sender alone. An undelivered edit goes as a plain message. A window of one sync gap, or for good if a participant-held chat's setting changes later.
- **Thin client**: reads and watches over the port; with its own write edge it is its own sender, so it cannot edit what its account's device sent.

## Left out
- Unbuilt core: adding without history (issues/history-less-grant.md), stopping a fetch short of old messages (issues/partial-history-fetch.md; a label does fill newest first, so old messages reach a new device late, each past a cursor), a kick past about 1.9×10^6 messages of one participant (frontier heads), realms (notes/realms.md: servers and channels; a channel is a chat a realm holds write on).
- Not done here: reactions, read marker, typing, hidden set, `chat:next.0^` segments, attachments, the leave audit.
- Known and small: an edited message deleted leaves a tombstone per version (the link was in the purged bodies). A watch hears an edit under `Purge` as an edit and then a deletion of the old version: a read tells them apart. A concurrent edit landing after a delete brings the text back on the versions it did not purge. Re-adding a participant revives posts it made while kicked (a design E forced answer; `kicked_while_offline` asserts it). A kicked account's new device gets nothing, its own messages included.

## Costs
On the sim (`--release`, every node in one process, `scale_long`, `scale_small`, `scale_post_read`):
- 10^4 messages, 1 participant: 624 B up per message; a local post at the end 8.8 ms, its pass included; newest 50 read 1.5 ms; all 10^4 by pages 0.2 s; `find` 5000 back 0.36 s; a new participant's fetch 23 s, 6 MB down; a kick 3 s.
- Many participants: `scale::chat_members`, notes/testing.md; what is left: issues/chat-add-cost.md.

## Rotation costs (kept from the old pattern)
- A read+write rotation costs 2.7 KB per remaining holder (`scale.rs` `roster_removal_cost`: 272 KB at 100 writers, 2.70 MB at 1000; 1.05 s to commit at 1000). Downloads multiply by the holder count, only on removals.
- **Tess's decision: accepted; keep the simple format.** Cheaper only by wire-format changes, both declined: the header once per commit (a second fetch per message); one KEM key per actor and one box per holder for all roles (done plainly gives read-only holders write and admin secrets; the safe variants make role separation classical-only, or delay reads after a lower-role grant). Removals are rare, groups of hundreds are rare, simplicity and the post-quantum promise win.

## Links: why joiners stay on K
A joiner's own edge on C would need L to grant on C: K with invite on C, a spec change. It would not end shared fate: the joiner may keep the seed, so a kick that leaves the link lets it rejoin. So `kick` ends the link either way. Kept; `participants` reads through K.

# Merge gate
> Summary: What `tools/gate.sh` runs and in what order, which steps the changed paths select (GUI, docs-only, comments-only), how `tools/test_select.py` picks the properties and sim scenarios, how failures are marked KNOWN or NEW (`tools/known_failures.txt`) and each default-test binary held to its instruction budget (`tools/test_cost.txt`), and the instant checks (policy.py with the spec map's, the tools' own tests).

The gate runs once per reviewed change (notes/coordination.md, The task loop). Each tool's docstring has its exact rules; this note says what they do. Stage limits: notes/time-limits.md, Limits.

## Running it
`tools/merge-branch gate <name> [GATE ARGS]` (its header) runs `tools/gate.sh [--all] [--base REV] [--plan]` in the worktree holding `<name>`; `tools/merge-branch land <name>` then lands it. Never call the gate by hand. A big change already on main is gated from a fresh claim at origin/main with `--base` naming the commit before it (or `--all`); what it finds is fixed on main like any job.
- **Before**, done by it: fetch, rebase on origin/main (a conflict in notes/handoff.md alone takes main's side; any other stops it), policy. It prints `git diff origin/main` of the merge-driven lists: check it shows only the change's own lines, since a union merge can bring back a line the change removed.
- **Never** piped and never under `tools/heavy` (it takes the lock itself). Run it with `run_in_background` and `claudewait`. Each run's log `gate-N.log` and record go under gate-logs/<name>/ in the common git dir, for `merge-branch land`, which removes the directory once landed.
- **Base**: the merge base with a fresh origin/main, never local main. It refuses a tree mid-rebase or with conflicts, and a HEAD lacking origin/main. `--all` selects every crate (as does a HEAD equal to origin/main without `--base`); `--plan` prints `core= gui= unify= select=all|diff|none` (plus `doc=` and `tooling=1` when they apply) and exits.
- **Exit**: 0 `== gate passed`; 3 `== gate FAILED, KNOWN failures only`; 1 `== gate FAILED: N NEW, M KNOWN`; 2 bad use or refused. Lines may end `; N KNOWN-BUT-PASSED to remove`, `; N STALE-RATE to remove` or `; N STALE-COST to lower`: `merge-branch land` applies those in a commit of its own (a `rate:` known line not replayed passing, and a cost line main changed since the gate, kept). After exit 1, land rereads the summary against the known list it carries (HEAD's merged with origin/main's): a NEW failure since listed on main lands without `--fixed`.

## Steps
Each prints its wall and CPU-s and checks its time limit. Steps before the tests fail fast; every test stage runs to its end.
1. The lockfile is current (`cargo metadata --locked`); `tools/policy.py`, the spec map's checks among it.
2. Instant checks, when the change touched tools/, .gitattributes or notes/time-limits.md (`tooling`): every `tools/*_test.*` at once (`policy_test.py` plants one violation per policy check in a tree copy, each must be reported) and `tools/limits.py split`.
3. The selection, printed with its commands (The selection).
4. Lints: core clippy, then the GUI's on the same artifacts. Then the fuzz targets (core/test/fuzz: their own workspace, lock and target): `cargo metadata --locked` on their lock and `cargo +nightly fuzz check`. Nothing else compiles them.
5. Builds, unlocked: `cargo test --no-run`, every binary the selection runs, with the runs' own arguments, and the GUI's test binaries when the GUI tests run, so the hold builds nothing but doctests. Every selected property must be listed by the built binaries (`tools/test_select.py --listed`): a name no target compiles would pass silently.
6. The unification check when a `Cargo.toml`, `Cargo.lock` or `.cargo/` changed (notes/build-internals.md, Feature unification); `osis schema check` on every `schema/*.osis`; `cargo deny check`, then core's bans alone (deny.toml skip-trees the GUI stack, which would hide a core duplicate).
7. One `tools/heavy` hold: the default tests (`cargo test --locked --no-fail-fast`, each binary counted: The summary), the selected properties, the selected sim scenarios at 15 seeds, each rate replay (The selection).
8. The GUI tests (`cargo test -p osis-kit -p osis-app -p osis-android`): on every full gate, and on the reduced gates when libs/kit/ or app/ changed.
9. The whole gate against `gate` (without its lock wait and build stage), then the summary.

## Components pay for themselves
The paths changed since the merge base (committed or not, untracked included) pick the steps; `tools/gate_paths.py BASE` decides (`-v` says why a docs or comments diff took the full gate). A .toml file whose every changed line is blank or a whole-line `#` comment (no multi-line string in it) is left out first, here and in the selection:
- Only libs/kit/ or app/: the GUI lint and tests, unification if a manifest changed, deny.
- Everything else is Markdown under spec/, notes/ or issues/ (`core=docs`): steps 1-2, plus the GUI steps if the GUI changed. A Rust line reading or including a file there sends the full gate.
- That Markdown plus .rs files whose every changed line is a whole-line `//` comment (`core=comments`): steps 1-2, core clippy, the doctests of each crate with a changed doc comment whose library has doctests (`gate.doctests`), plus the GUI steps if the GUI changed. Anything a comment could change falls through to the full gate (the docstring lists the cases).
- Anything else: every step; the GUI lint and tests always (a core change must not silently break the app).

## The selection
`tools/test_select.py [--base REV | --all] [--offset N]` prints what a gate would select; `--paths P...` asks about paths without a diff; `--all` lists every property and the `OSIS_*` variable each reads.
- **What it selects**: every property of the crates the paths touch and of their dependents in the Cargo graph, and every sim scenario if osis-sim is among them. A normal or build edge carries on to dependents; a dev or `cfg(fuzzing)` edge selects that one crate and stops, and of a crate reached only that way only the properties in files that can call the dependency. A test name selected in one crate runs in every selected crate defining it. A change low in the graph selects nearly everything: that is the graph's answer, don't trim it by hand.
- **Test-only edits** (`test_only`): a .rs file under a crate's `tests/`, or a src/ module declared only under exactly `#[cfg(test)]`, selects only that crate's properties in the same place. When unsure (`#[path]`, `include!`, a file read as text, a deleted src/ file, `cfg(any(test, ..))`) it falls back to the crate and its dependents.
- **A property test** is an `#[ignore]` test whose name ends in a size word (`_large`, `_plain`, `_exhaustive`) before any `_spec_*` suffix, never a `repro_`. The name is all: there is no list. An `#[ignore]` the scan cannot name (a macro's `fn $name`) prints as `not read`. Anything else ignored is by hand (named `_by_hand` when it is a property).
- **Paths outside a crate**: `Cargo.toml`, `Cargo.lock`, `.cargo/`, `rust-toolchain` select every crate; a `schema/*.osis` the crates whose Rust names it, and their dependents; notes/, spec/, issues/, docs/, tools/, core/test/tla/ and core/test/fuzz/ nothing; anything else nothing, printed as not classified.
- **Files an instant check pins** (`PINNED`) select nothing: a run-time-read file a check fixes from the sources (core/base/testenv-known.txt). A data file a test reads is not pinned: it selects its crate like code.
- **How they run**: one `cargo test` over the selected crates with tools/prop_run.py as cargo's runner, each test in its own process, so the gate measures each one's CPU.
- **Rate replays**: each `rate:` line of tools/known_failures.txt whose crate is selected (a `sim-sweep:` one's when the sim is) runs once at its REPRO, a `gate.replay` stage of its own.
- **Offsets**: one random offset per gate starts every `OSIS_*_START` and is xor'ed into `OSIS_CRDT_SEED` and `OSIS_PERM_SEED`; `--offset N` repeats one.
- Never at the gate: large sizes and by-hand tests. A change to an invariant the selection does not reach gets one targeted larger run, named in its brief.

## Hung tests
The default-test stages run under `tools/test_watch.py`: a target where no test finishes for 10 times the `test` wall limit, at least 120 s (`GATE_HANG_S` overrides), is stopped and cargo goes on. Each test libtest said had run over 60 seconds fails as `hung: no test finished for N s`; a hang naming no test is NEW. Properties and sim scenarios are not watched: their seeds have the seed runner's bound (`OSIS_SEED_TIMEOUT_SECS`, sim-sweep's hung-seed exit).

## The summary
`tools/gate_failures.py` (its docstring has the parse rules): one line per failure, `KNOWN` (with its issue) or `NEW`, each failing seed under it with its replay line. Whatever it cannot account for is NEW: a stage that did not run, a crashed or killed target, a hung-seed exit, a cargo `error` outside a target, a missing sim tally. A failing gate keeps its logs and prints the command that rereads the summary (after a known line is added).
- First, the property and sim runs by CPU-s, costliest first.
- **Test cost**: each default-test binary runs under tools/test_count.sh and tools/icount and is held to its line in tools/test_cost.txt (`CRATE/NAME G`, 10^9 user-space instructions; NAME without cargo's hash: `osis-engine/it`, `osis-engine/osis_engine` for the lib). Over G, or no line: `NEW-COST`, counted NEW: slim it, or write the line the summary prints (1.5x the count) with the reason in the commit message. Under G / 2, or a line for a binary the run lacked: `STALE-COST`, which `merge-branch land` lowers or drops. Instructions, not wall: a count repeats within about 2% at any load. Per binary, not per test (shared fixtures are paid once). A binary without a count is NEW (`INSTR unavailable`: `kernel.perf_event_paranoid` above 2).
- `KNOWN-BUT-PASSED`: a listed test (not `rate:`) that ran and passed everywhere it ran. Its line would hide the next failure as the known one; `merge-branch land` removes it. A test whose lines are all `rate:` prints `KNOWN, passed` instead.
- `STALE-RATE`: a `rate:` line whose REPRO passed when replayed: it no longer shows the failure, so `merge-branch land` removes it. A replay failing as its NAME's patterns say prints `replayed:` and counts as no failure; failing otherwise, `NEW-TEXT`.
- `NEW-TEXT`: a listed test failing with a unit no pattern of its NAME matches; counted NEW.
- `NEW-COUNTS`: a test with a `counts:` baseline failing with other counts; counted NEW.
- **tools/known_failures.txt**: one failure on main per line, `NAME REPRO ISSUE PATTERN`. NAME is `CRATE/LIBTEST_PATH` or `sim-sweep:SCENARIO`; REPRO the setting that fails on main, prefixed `rate:` when it fails on some seeds only (`rate:VAR=VAL,...` for a test, `rate:SEED` for a sim scenario: the gate replays it); PATTERN a regex. A failure is KNOWN when every failing unit of NAME (each seed's line, or the whole panic) matches a pattern of NAME; REPRO's seed never needs to match. Keep a pattern as narrow as the issue's own words, so a new bug in a known test stays NEW; the reviewer still reads a KNOWN failure's text.
- **A `counts:` line**, `NAME SETTING ISSUE counts:CHECK=N,... PATTERN`, is for a property failing on main by design in many worlds (a model search waiting on a decision): SETTING is `-` or `VAR=VAL,...`, at which prop_run.py runs that test so its counts compare; the counts are the `"CHECK": N` pairs of the `{...}` its panic prints after PATTERN's match (a space in CHECK written `_`). Such a test has no other line.
- A property failing on main gets its issue and line at once; the fix deletes both. A REPRO passing on a later main is no fix of the bug: its `rate:` line goes (STALE-RATE), and while the failure is still seen at other seeds it comes back with a REPRO that fails. `tools/policy.py` refuses a line whose issue or test is gone or whose pattern does not compile.

## Policy checks
`python3 tools/policy.py` (its docstring lists every check; each failure names its rule). While main is red, `--baseline [REF]` fails only on violations REF lacks. The ones that catch everyday edits:
- **Pointers** (`tools/doc_refs.py`): every `notes/`, `issues/` or `spec/` file named exists, and capitalised words after a file name (`<file>, Section`, `<file> (Section)`, `<file> §N Section`) must start a heading, bold lead, list item or `Lead:` paragraph there. Grep an issue's name everywhere before deleting it. An aside straight after a file name starts lowercase; capitalised words naming no section follow `;`.
- **Code names** cited in backticks by notes, issues and Rust doc comments must exist (`tools/code_refs.py`): a rename or deletion fixes its citations in the same commit; a name absent on purpose goes in tools/code_refs_allow.txt with its reason, and a line nothing cites any more is dropped.
- **Union-merged lists** (.gitattributes `merge=union`: tools/code_refs_allow.txt, core/base/testenv-known.txt): one name per line; duplicates and stale lines (`UNION_STALE`) are refused, since union brings back a line one side removed.
- **tools/known_failures.txt** merges three ways as a set (`merge=known-failures`, set up by tools/claim): a removed line stays removed, both sides' additions stay. Without the driver, `python3 tools/known_failures_merge.py` resolves git's conflict.
- Every external dependency has its line in notes/architecture.md §5; `cargo deny check` (deny.toml) denies duplicate versions (a forced one gets a `skip` with a reason); the core crates below the engine pull no tokio, quinn, redb or ML-KEM.

## Spec-to-test map
`python3 tools/spec_map.py` writes notes/testing-map.md (gitignored): per numbered spec section, the tests and vector cases citing it, the rule checklist, gaps and uncited tests. `--uncited` fails on a test in core/, libs/chat/ or cli/ that cites nothing (models exempt); `--gaps` fails on a rule with neither a test nor an issue, or a MUST sentence no rule anchors. `tools/policy.py` runs both (lines prefixed `spec_map:`).
- **Rules**: every MUST / MUST NOT sentence of spec/*.md plus the refusal rules, each a `RULES` entry in the script (file, §, anchor, a substring of the sentence). A test or issue covers one by citing `spec/<file>.md §N (anchor)`, several anchors `;`-separated (a comma is part of one anchor). A new MUST fails `--gaps` until it has an entry. `VACUOUS` lists rules nothing can test yet. Citation form: notes/testing.md, Conventions.
- Not in the map: SHOULDs, policy numbers (cited as `spec: none` or by section), normative text without a MUST (section level only), spec/requirements.md (covered by reviews).

# Merge gate
> Summary: What `tools/gate.sh` runs and in what order, which steps the changed paths select (GUI, docs-only, comments-only), how `tools/test_select.py` picks the properties and sim scenarios, how failures are marked KNOWN or NEW (`tools/known_failures.txt`) and each default-test binary held to its instruction budget (`tools/test_cost.txt`), and the instant checks (policy.py with the spec map's, the tools' own tests).

The gate runs once per reviewed change: a rule others build on, a security fix, or a big change at its end (notes/coordination.md, The task loop). Other jobs land on their crates' tests and clippy without it. Each tool's docstring has its exact rules; this note says what they do. Stage costs and limits: notes/time-limits.md, Limits.

## Running it
`tools/merge-branch gate <name> [GATE ARGS]` (its header) runs `tools/gate.sh [--all] [--base REV] [--plan]` in the worktree holding `<name>`, then `tools/merge-branch land <name>` lands it; never call the gate by hand. A big change already on main is gated from a fresh claim at origin/main with `--base` naming the commit before it (or `--all`); what it finds is fixed on main like any job.
- **Before**, done by it: fetch, rebase on origin/main (a conflict in notes/handoff.md alone takes main's side; any other stops it, the rebase left in progress), policy. It prints `git diff origin/main` of the merge-driven lists (.gitattributes: union lists, tools/known_failures.txt): check it shows only the change's own lines, since a union merge can bring back a line it removed.
- **Never** piped and never under `tools/heavy` (the gate takes the lock itself; a nested one refuses). Run it with `run_in_background` and `claudewait`: its exit is the gate's (2 when refused before the gate ran). It prints the summary, the log path and `gate=EXIT` (also the log's last line); each run's log `gate-N.log` and its record (exit, HEAD, origin/main) go under gate-logs/<name>/ in the common git dir, for `merge-branch land`, which removes the directory once landed.
- **Base**: the gate fetches origin/main and diffs against the merge base with it, never local main. It refuses a tree mid-rebase or with conflicts, and a HEAD that lacks origin/main. `--base REV` diffs against REV instead; `--all` selects every crate (as for a HEAD equal to origin/main with no `--base`); `--plan` prints `core= gui= unify= select=all|diff|none` (and `doc=` with the comments path's doctest crates, `tooling=1` when the tools' tests run) and exits.
- **Exit**: 0 `== gate passed`; 3 `== gate FAILED, KNOWN failures only`; 1 `== gate FAILED: N NEW, M KNOWN` (NEW-TEXT counted as NEW); 2 bad use or refused. The 0, 3 and 1 lines end `; N KNOWN-BUT-PASSED to remove` and `; N STALE-COST to lower` when the summary lists any; the exit is unchanged and the landing removes them. After exit 1, land reads the kept summary again against the known list the landing carries (HEAD's merged with origin/main's): a NEW failure shown on main and listed there since lands without `--fixed`.

## Steps
Each prints its wall and CPU-s and checks its time limit. The steps before the tests fail fast; every test stage runs to its end.
1. The lockfile is current (`cargo metadata --locked`; not `--offline`, where an uncached crate fails like a stale lock; the failure prints the refresh command); `tools/policy.py`, the spec map's `--uncited --gaps` among its checks.
2. Instant checks, when the change touched tools/, .gitattributes or notes/time-limits.md (`tooling`): every `tools/*_test.*` at once (each in its own scratch dirs; output and exit printed per test in order, the stage failing after all ran if any failed; `policy_test.py` plants one violation per policy check in a copy of the tree, each must be reported) and `tools/limits.py split`.
3. The selection, printed with its commands (The selection).
4. Lints: core clippy, then the GUI's on the same artifacts (re-lints only kit and app, a few seconds; cold, about 1.5 min once per worktree). Then the fuzz targets (core/test/fuzz: their own workspace, lock and target dir): `cargo metadata --locked` on their lock, then `cargo +nightly fuzz check` (needs nightly and cargo-fuzz). Nothing else compiles them.
5. Builds, unlocked: `cargo test --no-run` and every binary the selection runs, with the runs' own cargo arguments, so the hold builds nothing (doctests still compile inside it). Then every selected property must be listed by the built binaries (`tools/test_select.py --listed`): a name no target compiles would match no libtest filter and pass silently.
6. The unification check, when a `Cargo.toml`, `Cargo.lock` or `.cargo/` changed (notes/build-internals.md, Feature unification); `osis schema check` on every `schema/*.osis`; `cargo deny check`, then core's bans alone (deny.toml skip-trees the GUI stack, which would hide a core duplicate with a copy there).
7. One `tools/heavy` hold: the default tests (`cargo test --locked --no-fail-fast`, each test binary counted: The summary, Test cost), the selected properties, the selected sim scenarios at 15 seeds.
8. The GUI tests (`cargo test -p osis-kit -p osis-app -p osis-android`), when libs/kit/ or app/ changed.
9. The whole gate against its cap (`gate`), leaving out its lock wait and its build stage (a rebuild after a rebase is not test cost; the gate prints its CPU-s and wall beside the check). Then the summary (The summary).

## Components pay for themselves
Iterating on one project must not run the others' checks. The paths changed since the merge base (committed or not, untracked included) pick the steps; `tools/gate_paths.py BASE` decides (`-v` says why a diff of comments and docs took the full gate):
- Only libs/kit/ or app/: the GUI lint and tests, unification if a manifest changed, deny.
- Everything outside libs/kit/ and app/ is Markdown under spec/, notes/ or issues/ (`core=docs`): steps 1-2, plus the GUI steps if the GUI changed. A Rust line that reads or includes a file there (one-line calls `git grep` finds) sends the full gate and is named, here and on the comments path.
- That Markdown plus .rs files whose every changed line is a whole-line `//` comment (`core=comments`, e.g. a spec pointer sweep): steps 1-2, core clippy, the doctests of each crate with a changed doc comment whose library has doctests (`gate.doctests`: osis and osis-base), plus the GUI steps if the GUI changed. Anything a comment could change falls through to the full gate (code after a comment on its line, a `/* */` block, a string, an added or deleted file, `include_str!`, macros, proc macros outside `DOCS_BLIND`): tools/gate_paths.py's docstring lists the cases.
- Anything else: every step; the GUI lint always (an osis API change must not silently break the app), the GUI tests only if the GUI changed.

A new project extends the same pattern, with its own properties and release checks.

## The selection
`tools/test_select.py [--base REV | --all] [--offset N]` prints what a gate would select and run; `--paths P...` asks about paths without a diff; `--all` lists every property and the `OSIS_*` variable each reads.
- **What it selects**: every property of the crates the paths touch and of their dependents in the Cargo graph, and every sim scenario if osis-sim is among them. A normal or build edge carries on to that crate's dependents; a dev edge (or a `cfg(fuzzing)` one: fuzz targets are by hand) selects that one crate and stops, and of a crate reached only that way only the properties in files that can call the dependency (`reaching`: the docstring has the rule). A test name selected in one crate runs in every selected crate defining it. So a roles-model change selects perm's differentials and its own searches, not every engine property. A change low in the graph (osis-base, -crypto, -store, -crdt, -perm, -engine) selects nearly everything: that is the graph's answer, don't trim it by hand.
- **Test-only edits** (`test_only`, whose comment has the exact rule): a .rs file under a crate's `tests/`, or a src/ module declared only under exactly `#[cfg(test)]`, compiles only into that crate's own test binaries, so it selects only that crate's properties in the same place (tests/ or src/): no dependent and no sim. When unsure (`#[path]` or `include!`, a file read as text, a deleted src/ file, `cfg(any(test, ..))`) it falls back to the crate and its dependents. So roles-model's `paths/tests.rs` selects only roles-model's own searches, while a roles-model library module (`paths/purge.rs`) still selects held-model and its users.
- **A property test** is an `#[ignore]` test whose name ends in a size word (`_large`, `_plain`, `_exhaustive`) before any `_spec_*` suffix; never a `repro_`. The name is all: there is no list. An `#[ignore]` the scan cannot name (a macro's `fn $name`) prints as `not read`. Anything else ignored is by hand; a by-hand property is named `_by_hand` (notes/testing.md, When tests run).
- **Paths outside a crate**: `Cargo.toml`, `Cargo.lock`, `.cargo/`, `rust-toolchain` select every crate; a `schema/*.osis` the crates whose Rust names it, and their dependents; notes/, spec/, issues/, docs/, tools/, core/test/tla/ and core/test/fuzz/ nothing (TLA and fuzzing are by hand: notes/test-properties.md); anything else nothing, printed as not classified.
- **Files an instant check pins** (`PINNED`) select nothing: a file compiled into nothing (read at run time) whose content, as its readers read it, a check fixes from the sources, so any edit that could change what a test sees fails that check first. core/base/testenv-known.txt is one (policy.py keeps it equal to the `OSIS_*` names the sources use; the Cargo graph would select everything, as osis-base library code reads it). A data file a test reads is not pinned: it selects its crate like code.
- **How they run**: one `cargo test` over the selected crates with tools/prop_run.py as cargo's runner, each selected test in its own process (as many at once as libtest would run threads), so the gate measures each one's CPU from its rusage.
- **Offsets**: one random offset per gate starts every `OSIS_*_START` and is xor'ed into `OSIS_CRDT_SEED` and `OSIS_PERM_SEED`, so no two gates sample the same seeds; `--offset N` repeats one.
- Never at the gate: large sizes and by-hand tests. A change to an invariant the selection does not reach gets one targeted larger run, named in its brief.

## Hung tests
The default-test stages (default tests, GUI tests) run under `tools/test_watch.py`: a target where no test finishes for 10 times the `test` wall limit (notes/time-limits.md, Limits), at least 120 s (`GATE_HANG_S` overrides), is stopped by PID and cargo goes on with the next target. Each test libtest said had run over 60 seconds and has not finished since fails as `hung: no test finished for N s`, KNOWN or NEW like any other; a hang naming no test is NEW. Properties and sim scenarios are not watched: their seeds have the seed runner's bound (`OSIS_SEED_TIMEOUT_SECS`, sim-sweep's hung-seed exit), and a property may rightly run minutes with nothing finishing.

## The summary
`tools/gate_failures.py` (its docstring has the parse rules): one line per failure, `KNOWN` (with its issue) or `NEW`, each failing seed under it with its replay line. Whatever it cannot account for is NEW: a stage that did not run, a crashed or killed target, a hung-seed exit, a hung target naming no test, a cargo `error` outside a target, a missing sim tally. A failing gate keeps its selection, results and logs and prints the command that reads the summary again (after a known line is added); remove the directory once done.
- First, the per-property cost table: the property and sim stages' runs by CPU-s, costliest first (tools/prop_run.py's `gate: cost NAME: W s, C CPU-s`, the sim sweep's summary line; `(no CPU line)` for a test with neither).
- **Test cost**: each default-test binary runs under tools/test_count.sh (prints `gate: binary CRATE/NAME`, NAME without cargo's hash: `osis-engine/it`, `osis-engine/osis_engine` for the lib's tests) and tools/icount, and is held to its line in tools/test_cost.txt, `CRATE/NAME G` (10^9 user-space instructions). Over G, or with no line, it is `NEW-COST`, counted NEW: slim it, or write the line the summary prints (1.5x the count) with the reason in the commit message. Under G / 2 (or a line naming a binary the run lacked) it is `STALE-COST`: the landing lowers or drops it. So a binary that doubles fails. Instructions, not wall: a count repeats within about 2% at any load, where wall swings 3-6x. Per binary, not per test (a process per test pays shared fixtures again, about 1.6x). `== test cost: N binaries, T G instructions` says the check ran; a binary without a count is NEW (`INSTR unavailable`: `kernel.perf_event_paranoid` above 2). Doctests and properties are not counted here.
- `KNOWN-BUT-PASSED: NAME (STAGES; ISSUE)`, under `== KNOWN-BUT-PASSED (N)`: a listed test, not `rate:`, that ran and passed in every stage running it (a sim scenario tallied with 0 failed). Its line is stale and would hide the next failure of its test as the known one; the landing removes it (notes/coordination.md, Known failures). When every line of NAME is `rate:` it prints `KNOWN, passed: NAME ...: fails at a rate (ISSUE): passing this run is expected` instead.
- `NEW-TEXT`: a listed test failing with a unit no pattern of its NAME matches (a second failure behind the known one); counted as NEW.
- `NEW-COUNTS`: a test with a `counts:` baseline whose failure's counts differ from it (the change moved what fails there, better or worse); counted as NEW. Equal counts print `KNOWN ... same failing counts`.
- **tools/known_failures.txt**: one failure on main per line, `NAME REPRO ISSUE PATTERN`. NAME is `CRATE/LIBTEST_PATH` or `sim-sweep:SCENARIO`; REPRO the setting that fails on main, prefixed `rate:` when it fails on some seeds only (its issue says so); PATTERN a regex. A failure is KNOWN when every failing unit of NAME (each seed's line, or the whole panic when it names no seed) matches a pattern of NAME; the gate's seeds are random, so REPRO's seed never needs to match. Keep a pattern as narrow as the issue's own words, so a new bug in a known test stays NEW; the reviewer still reads a KNOWN failure's text.
- **A `counts:` line**, `NAME SETTING ISSUE counts:CHECK=N,... PATTERN`, is for a property failing on main by design in many worlds (a model search waiting on a decision): SETTING is `-` (seed-free) or `VAR=VAL,...`, which prop_run.py runs that test at instead of the gate's offset, so its counts compare; the counts are the `"CHECK": N` pairs of the `{...}` its panic prints after PATTERN's match (a space in CHECK written `_`). Such a test has no other line.
- A property failing on main gets its issue and line at once (REPRO checked on main against the pattern); the fix deletes both. REPRO passing on a later main is no fix: the gate draws fresh seeds and the pattern catches them, so the line stays until a change explains the failure away. `tools/policy.py` refuses a line whose issue or test is gone or whose pattern does not compile.

## Policy checks
`python3 tools/policy.py` (its docstring lists every check; each failure names its rule). While main is red, `--baseline [REF]` (default origin/main) fails only on violations REF lacks, matched by message without line numbers. Among them:
- Workspace lints on every member, so the compiler forbids unsafe (app/android denies it and may keep one `unsafe` block, under a `// SAFETY:` comment); every external dependency has its line in notes/architecture.md §5; core/base/testenv-known.txt lists exactly the `OSIS_*` variables the sources name (an `OSIS_PROBE_*` one fails: a probe left in; tools/ counts as source, so a tools test fixture uses a listed name).
- **Pointers** (`tools/doc_refs.py`, whose docstring lists the accepted forms): every `notes/`, `issues/` or `spec/` file named exists, and a pointer into a notes or spec file names a part that exists, so a deleted issue or renamed section fails the change that did it: grep an issue's name everywhere before deleting it. Capitalised words after a file name (`<file>, Section`, `<file> (Section)`, `<file> §N Section`) must start a heading, bold lead, list item or `Lead:` paragraph there; a lowercase or code first word is not checked, so an aside straight after a file name starts lowercase; capitalised words that name no section follow `;` (`<file> §N; Interim (issues/<name>.md)`).
- **Code names** notes, issues and Rust doc comments (`///`, `//!`) cite in backticks must exist (`tools/code_refs.py`): a rename or deletion fixes its citations in the same commit; a name absent on purpose (third-party, placeholder, planned, rejected, removed) goes in tools/code_refs_allow.txt with its reason. Checked: path segments, calls, names with `_` or an inner capital, a span of one capitalised word, and a family `name_*` (some code word starts with `name_`), each against code with its comments left out; `<Type>::<item>` where our Rust defines the type must be one of its variants, fields or associated items (regex over rustfmt'd source). A name only under `tests/` or `#[cfg(test)]` cited as product passes, as does a name that exists but is the wrong kind (a builder cited as a test).
- **Union-merged lists** (.gitattributes `merge=union`: tools/code_refs_allow.txt, core/base/testenv-known.txt): one name per line, so concurrent additions never conflict. Union keeps both sides of a hunk, so policy.py refuses a duplicate line (`union_lists`), and each list must have a check refusing a stale line (`UNION_STALE`: a line one side removed beside the other's change comes back); a new list joins only with such a check.
- **tools/known_failures.txt** is not union-merged (a revived stale line for a still-failing test passes every check): it merges three ways as a set (`merge=known-failures`, tools/known_failures_merge.py, set up by tools/claim): a line either side removed stays removed, both sides' additions stay, a test whose lines both sides changed conflicts. With no driver, `python3 tools/known_failures_merge.py` resolves git's conflict (and drops lines whose issue is gone); a conflict marker left fails policy.
- **`cargo deny check`** (deny.toml): licence allowlist, duplicate versions denied (a forced one gets a `skip` with a reason), advisories, crates.io only. Members are `publish = false`.
- The core crates below the engine (osis-base, -crdt, -perm, -schema) pull no tokio, quinn, redb or ML-KEM; tokio enters only in osis-transport and osis (notes/architecture.md §5).

## Spec-to-test map
`python3 tools/spec_map.py` writes notes/testing-map.md (gitignored): per numbered spec section, the tests and vector cases citing it, the rule checklist, gaps and uncited tests. `--uncited` fails on a test in core/, libs/chat/ or cli/ that cites nothing (models exempt); `--gaps` fails on a rule with neither a test nor an issue, or a MUST sentence no rule anchors. `tools/policy.py` runs both (`spec_anchors`, each line prefixed `spec_map:`).
- **Rules**: every MUST / MUST NOT sentence of spec/*.md plus the refusal rules (spec/permissions.md and the sync spec files), each a `RULES` entry in the script (file, §, anchor, a substring of the sentence). A test or issue covers one by citing `spec/<file>.md §N (anchor)`, several anchors `;`-separated (`(Covered; Purge on replace)`: a comma is part of one anchor). A new MUST fails `--gaps` until it has an entry. `VACUOUS` lists rules nothing can test yet. How to write a citation: notes/testing.md, Conventions.
- Not in the map: SHOULDs (listed, not gated), policy numbers (cited as `spec: none` or by section), normative text without a MUST (section level only), spec/requirements.md (no numbered sections; covered by reviews).

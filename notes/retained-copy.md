# Retained copy
> Summary: Why a removed holder's copy is kept or erased by the `retain` field of `retention^.0` and the removal's stated value (spec/permissions.md §3): why an `until` 0 grant over a header bit, which removal decides, filling, node removals and any-path keeping, costs, and the accepted limits (Tess).

Principle (Tess: keep the rules simple and consistent, state rare corners): **the removal states the value**; a plain reset is erase, reset plus a grant with `until` 0 is retain, and everything else reads the thing's current default.

## Design
- The default is the `retain` field of `retention^.0` (any thing, admin-only, no chat code; absent is erase): that aspect already has `^`, a current setting every node reads, and no undo. The removal's value (`EdgeEnd`, `Edge::says_retain`): `until` 0 is already gone at every clock (no timer: a node behind the kicker's clock by `MAX_DRIFT` drops at once), and lies inside the signed `roles.0` delta so it cannot arrive apart from the removal. Cost: a removal saying retain leaves one dead grant until a re-grant replaces it. Rejected: a header bit; a tombstone value or a removal field (a state every decoder must learn; a dead grant is the expired grant readers already skip). `retain` beside `rules`: the value is written whole, so concurrent admins changing the two lose one by key, and a toggle re-judges the thing as a rules change does; a separate aspect would need the settings machinery a second time.
- A later removal on a grant decides over an earlier one, by key; a node that erased first cannot come back (it keeps no more than the whole history). An `until` ending has no remover: it reads the thing's current default (`retain_default`; no node keeps an earlier setting). A changed default reaches an `until` way at the next role-commit or manual judging, so it can end such a copy, never bring one back; without a later judging the copy stays (the holder could keep it anyway).
- Filling is the writer's: `flows::edges::written`; `retain_default` reads the current setting. Link: K takes the target's default when made, so joiners' self-removals read it too; a later change of the target's default does not reach K (minor; the kicker's word still overrides).
- Node removal erases whatever the account's default (a removal from `Osis`'s own account writes erase unless told otherwise), and a copy kept through the account hangs on the account, so it goes too. Any-path: a copy stays while one way keeps. A holder whose loss is not carried out yet (an `until` left to sync, a pending grant) still counts as had (`keeps`, `not_dropped`), and the copy is judged again when it drops; otherwise a copy judged while its holder's drop waits erases where judging both together keeps. A self-removal states its own value (Tess: no protocol rule stops it; the app just does not offer it).
- Kick cost is unchanged: nothing per body. Keeping costs the removed node nothing new and is cheaper than erasing (no shredding).

## Accepted limits
- Every other removal reads the default, so under a default to retain a revoked link's L leaves a dead grant until finalizing resets it (one extra commit), and a removed thin client's dead grant is a way that keeps past its account's later erasing kick; a node's grant with an `until` reads the account's default.
- A purge after the removal usually does not reach the copy (no sync ID to hear it by), though one in a commit the node takes for another part applies, and a purge pending at the drop goes with its commit unless another part holds it. Only ever less kept.
- A hostile source can erase a copy-to-be only by hiding a second way that keeps, or a renewal of an `until`; a removal cannot apply without the value it resets, so hiding that value delays the loss instead. A denial only.
- An `until` passing is judged at the time and dropped once the node has heard out the sync IDs whose closure holds what it would forget, so offline nothing goes: a renewal on the way and unsent writes from before the `until` come first, and an expired share stays on a node until it next gets online. A source down, or one that never lets a pass finish, keeps it up to `ROLE_KEEP` after the loss was first judged (`LOST_HEARD_WAIT_MS`, per actor). Hearing out is per sync ID, not per write, on one `Leaving::timed` path beside the self-removal one; rejected: gating per node (one dead source delayed every timed loss). A refusal (code 14 says nothing of why) ends the wait on its peer alone, never on S: an own write held nowhere else waits for every other peer still to be waited for. Rejected: counting any refusal held now as hearing S out (a stale one, or one by a reader not syncing S, dropped own writes the owner would still take); a complete pass after the loss for the refusal path (no pass ends with no source while the refusing owner is still waited for); a fresh ByRole after the loss (nothing sends one on a connection whose credentials did not move).
- A client reads nothing past the `until` and a copy only once made, so an offline app sees an `until` share with a retain default go and come back as a copy when the node has heard out. A role commit received beside the expired grant that does not end the role changes nothing. A renewal made after the drop comes back by a re-seal through a stranded report (not built in sync: issues/sync-unbuilt.md).
- A write made before the `until` and sent after the thing was rotated for the departure is refused by a node keeping S unread and lost with the drop: the window is until the next writer rotates, as for any late write.
- A removal of an old path that arrives after the node has kept changes nothing. A kept holder given the target after the node left it counts as a live way, so a node that also held the target directly with an erase grant keeps it (rare; telling needs when the holder held the target against when it held the grant). In a partial order a node may erase what the whole history would keep, never the reverse. A thin client reads a copy as its account's app or through its own grant (notes/client-port.md §3, Kept copy).

# First admins and record chains
> Summary: Why every thing's record names a first admin that is an ordinary, removable admin (spec/wire.md §3, spec/permissions.md §1-§2): no authority above the admins, one authority class, creation, removing the record edge, the record chain, a plain thing's secrets, virtual record edges in osis-perm, the engine's reading, the standing-chain rule, costs and limits.

Principle: **the first admin is fixed by the record's hash and is an ordinary admin**: nothing about creation can be reused to grant again, and nothing outranks the admins.

## Why
- The tid commits to the first admin, its edge is in the walk's initial state from the start and stored nowhere, and it is removable like any other. Why not "granted in the creation commit" with a creation authority: anything that lets a node write the first grant without admin could be reused to grant again later (the record is public to every reader, the creator can always write another "creation commit", backdated): a hidden admin. Fixed by hash, there is nothing to reuse.
- Why no authority above the admins (Tess's direction; notes/disputes.md): an un-removable authority is a hidden admin users cannot change. A removed admin can backdate a removal of its remover (n1 removes n0 at 10; n0 signs "remove n1" stamped 5, which the plain walk applies first), also on an account; the walk settles the fight per node by its trust set, and a node takes a side by default when it detects the dispute: the side it held first (notes/disputes.md, Detection and sides).
- **One authority class**: admin by any path (edge admin), or an invite level. An admin of a thing's first admin is admin of the thing through the record edge like through any grant; losing that path while another keeps the class is no fall. So an admin that granted itself a direct edge on a thing below keeps it when its path above is removed, until an admin removes that edge too (one class, no "top" that outranks it; Tess accepts "a current admin Q that Y left in place voiding Y's removal silently").

## Creating and removing
- **Creation**: a record needs no authority (it is public); the creator names itself or an actor it holds write on (Tess, Q13: any writer of G may make a thing whose first admin is G; G's admins administer it, its writers write it). A thing is made either by its record alone (`Engine::create_with_admin`, or `Write::create` with nothing else: a role commit, spec/commits.md §2, so joiners fetching role commits first hold the record before the commits that need it) or inside a content commit with its first writes (`Write::create_with_admin`, trees made in one commit).
- **Removing the record edge**: no entry to reset, so the removal resets an entry of its own delta (`Mutation::fresh_resets`: a tombstone keyed by the holder at a fresh counter, spec/permissions.md §2), which every reader resolves at once, in any arrival order. A put-then-remove in one batch nets to nothing in the CRDT, so the tombstone is minted directly. An admin of the first admin removing the record edge leaves by self-removal; an admin of the thing itself removing it is an explicit demotion that audits the first admin's writes.
- **Record chain**: the chain walk (`osis_base::record_chain`) goes up first-admin links, so derivation, sync IDs, inboxes, certificates and the `MAX_CHAIN_DEPTH` cap all count through it; it says nothing about authority, which the timeline reads from the record edges as they stand.
- **Secrets**: a plain thing derives from its first admin's epochs (spec/crypto.md §3); its first grant (or `sync`) gives it secrets of its own by the usual rotation, its first admin getting its own first when plain too (`rotation::own_secrets_rot`): a plain holder has no keyset, so the rotation would box it nothing, the thing's write and admin epochs would reach no other rotator, and each rotator would find the other's epoch orphaned and rotate it again, for good (`flows::plain_first_admin_gets_secrets_before_its_thing_spec_perm_3`). The first admin is an ordinary holder of the rotation, boxed like any holder actor and delivered it by inbox, so a rotator that does not sync the first admin still reaches its sync IDs and holders (`own_secrets::` tests).
- Lowering the last admin edge of a plain thing is refused (`flows::edges::leaves_no_admin`): on a plain thing the only holder for keys is its first admin, so no "own secrets before any edge write" step is needed. Signed anyway, it stays plain and derives from the removed first admin for good (stated limit, spec/permissions.md §1). A derived epoch written under concurrently with its writer's removal is read by the first admin's holders only (spec/crypto.md §4, its limit).

## Implementation
- **Virtual record edges** (osis-perm): the walk's edge state (`Edges`) holds only edges writes set, plus the record edges writes removed (`cut`); `EdgesAt` and `View` read a record edge from the records where neither is the case (`RECORD_EDGE`, admin, no `until`). So a plain thing costs the edge state nothing, `Dense` materializes them for searches (adjacency built by one push per edge, sorted once per holder: a holder of a million things costs no scan per edge), and a write setting a record edge to exactly its record value is no explicit entry (canonical states compare equal). A record arriving late for a thing whose edges were walked: the resumed walk restores the record edge itself after rolling back (`Resume::fresh`); rejected: a full evaluation then (it is the common late-record case).
- Engine: `held.rs` names the first admin on the thing and indexes the thing under it in `first_admin_of` (`below` marks it stale when a record above it arrives); `write::role_with` gives a not-yet-held thing the first admin's role. The roster, current holders and holders for keys include the record edge while it stands (`standing_since` with `None` for the record edge: an actor grant ordered before every write, never the one left keyless), so nothing reads the record as a right. A link's K has the sharer's actor as first admin. No API call reads a thing's first admin (history, not a right): `grants` lists the record edge while it stands, and chat and the app tell accounts from teams and link keys by `grants` one level down (a key actor has no holders).
- **`sync.0` reads stop at cut record edges** (`Core::standing_chain`, `Engine::publisher`): a thing's `sync.0` and `created.0` go under the sync ID of the nearest actor with sync IDs up its record chain whose record edges up to it stand at the writer. An account's inbox is its own thing, named in the account's `keys.0` (`Engine::inbox_thing`); any other actor with own keys is its own inbox (spec/sync-inbox.md §1). **One standing-chain rule** (`Core::standing_chain`: up first-admin links while each record edge stands here, the top included): `sync.0` cross-publishing reads it, so a removed first admin has no standing on what is below. Derivation and entitlement read the records alone.

## Costs and limits
- Record edges are virtual, so a million leaves under one actor cost nothing to evaluate beyond the role commits, and one more leaf walks nothing (perm `scale::record_leaves_walk_nothing_per_leaf`). Nothing resets the `MAX_CHAIN_DEPTH` cap and chats add two links: app trees must stay far under 64.
- Within one record tree nothing moves: rights are grants, so "move this doc to team B" is a grant then a removal (notes/moves.md), and the depth of record chains should match the units that travel together. Same shape as the share-through-one-actor rule (spec/requirements.md, Generality).

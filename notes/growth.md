# Growth census
> Summary: Every known cause of permanent or unbounded growth of stored or synced data, at nodes and hosts. Each row says what it grows with, an approximate size, whether it is inherent or closable, and the issue that tracks it. Rows are ordered by how badly a "plain database, no history, frequent overwrites" workload grows. Every change that adds a new kind of permanent data adds or updates a row here.

Marks: **M** = measured, **E** = estimated from encodings or spec, **C** = the code says so.

The probe for the M rows: 400 overwrites of one register by one node, compacted after each 200. Store bytes are MemoryBackend `dump()` key+value totals, page overhead included, debug build. Measured before store rows were padded (notes/local-store.md, Row padding: about +4% on rows, small units at least 512 B), not re-measured. Results:
- Node store: 47 KB to 186 KB to 326 KB. That is about **690 B per overwrite, kept after compaction**. It is still there after 32 days, once tombstones and entry rows have gone.
- Host store: 7.5 KB to 119 KB, then 66 KB after 32 days. That was about **146 B per overwrite after tombstones expire**, the log records (row 2), which the log trim by age now drops with them.

| 2 | Host per-label log: add and delete records (33-41 B each) | Host | Per blob added and removed within the last `TOMBSTONE_LIFETIME`: about 146 B per overwrite (M, before the trim). | 3 | Receipt record `r/`: 60 B (ID, author, time) per commit whose header a receipts-only read verified without keeping it, per aspect it touches (C). | 10 | Host `T`/`Y` tombstones | Host | Per deletion, kept 30 days: 8 B + index (C) | Bounded (time) | none |

## Other workloads
| Cause | Where | Grows with, size | Kind | Issue |
|---|---|---|---|---|
| Full history (keep at least forever, or no compaction) | Both | Each commit's bodies, as written | Inherent (chosen) | none |
| Superseded bodies no one with the right has compacted (a snapshot drops a covered body only if its own commit holds the right, spec/commits.md §5) | Both | Each such body, as written. M: 90 edits of one default-retention (`author_or_admin`) aspect by 3 plain writers, 90 blobs at the host; register, text and list alike: one writer compacts 61 left (its own 30 go), two 31, all three 1 (snapshots are `writer`, so they replace each other), an admin 1. A plain writer's compaction alone removes only its own share. A device coming fresh fetches every body left. Departed writers' bodies wait for an admin; under `author` they stay for good. An admin's snapshot superseded by a plain writer's before a keep-at-least bound passes drops nothing more: the admin compacts again past the bound. A device that never held an earlier dropped body cannot cover its author's later ones (issues/atomic-wait-snapshot-gap.md), so the compacter should be a device that held the history | Inherent (chosen, no holes in purge settings). The way out: an admin compacts, or every author does. Nothing compacts by itself today (`SyncEngine::compact` has no caller in core or the apps), so a multi-writer document grows until a policy does this | none |
| Sequence tombstones and bare anchors | Both | Per deleted element: 3-4 B in a run-compressed snapshot; per reset run about 1 B (crdt.md §5.7) | Inherent (requirements Scale) | none |
| Sequence sessions (after the session design) | Both | Per session whose inserted records survive, per text or list aspect: 32 B `Sources` entry + about 4 B frontier (E) | Accepted residual. Same place as the tombstones | issues/session-sources.md |
| Value-less list `v/` and residue `w/` per expired or purged delta (C) | Node | Per expiring or purged delta: about 33 B + residue (its dots and structure, tens of B), for good. Disappearing messages and TTL caches hit this per write | Maybe closable: residue is needed for un-merge and stripping while a copy can arrive. Needs design | issues/valueless-gaps.md (related) |
| Expiring commits' headers (never covered) | Node | Per expiring commit: as row 1 | Closable with rule 8 of the session design (the `v/` list stands in for T) | issues/session-sources.md |
| Demotion (revoke) frontiers, carried as certificates under every label the successor writes, and in the ledger for good | Both | Per removed device (and each node the removal demotes with it, a cascade included): 32 B per listed commit, the device's received commits in scope the demoter's own compaction could not drop now (the tail since the last compaction plus each aspect's keep-at-least window; about none past the window if the demoter compacted first, session design step 3, not built). Measured: 200 compacted writes list 1 commit on a default aspect, 200 on a keep-at-least-1d one until the window passes (C) | Bounded by compaction cadence and keep-at-least windows (owner: accepted); permanent aspects need heads (notes/frontier-study.md F3/F4) | issues/frontier-certificate-cost.md, issues/session-sources.md |
| Tenure ledger entries (`tenures.0`) with frontiers, carried forward by every roster snapshot | Both | Per ended tenure of write or above, forever (permissions.md §6) | Inherent today | issues/frontier-certificate-cost.md |
| `roles.0` edge writes with no roster snapshot | Both | Per edge write, forever until the owner chain writes a roster snapshot; then `ROLE_KEEP` (90 days) after replaced. A holder actor's edge carries `keyset` (an edge key, about 60 B more; spec/crypto.md §4), kept by every later write of the edge, in every certificate copy and in roster snapshots | Inherent (only owner-chain can compact). Large rosters need a roster snapshot policy | none |
| An ownerless thing's `roles.0` and `tenures.0` (spec/permissions.md §1, §6) | Both | Per edge write on it, forever: nothing holds owner-chain authority on it, so it never has a roster snapshot. Grows with member churn (grants, removals, demotions; each a role commit with its rotation's boxes in `secrets.0`, which compacts as usual), not with content. Things it owns compact their rosters (its admins act through their owner chain) | Inherent (chosen: no owner). Prefer one ownerless actor owning the churning things | none |
| Role-class bodies (`secrets.0`, `keys.0`, `label.0`) | Both | Kept `ROLE_KEEP` after replaced (bounded) | Bounded | none |
| History boxes (`secrets.0` history map) | Both | Per rotation of a role: one box holding every earlier secret (about 40 B each) plus names. Never removed, so O(R²) bytes over R rotations (E, crypto.md §4) | Closable with a small trade-off: a rotation removes older history boxes of its role (the newest holds all). A holder that missed rotations then waits for a re-seal, as requirements "Out of scope" already accepts | none |
| Names in history boxes and grant boxes | Both | Per departure since its thing's epoch start (roster snapshot), over the actor and every thing below it (its current holders and owners, transitively: a group with person members names each member's device removals too), repeated in every history box of each rotation; plus one keyset name (about 55 B) per holder actor boxed and role, not growing over time; every box to a holder actor (grant, re-seal, rotation; not a bound seal's) carries that actor's closure's names, per boxed epoch (removed with the box by the next rotation; the commit's part kept `ROLE_KEEP`) | Bounded by roster snapshots of each of those actors | none |
| Held keyset epochs: `Dropped::keysets` in a dropped `keys.0` part's record (role, epoch and listed epochs, about 41 B each) and the `node/keyset epochs` index row per (actor, role, epoch) (C) | Node | Per keyset any actor ever wrote, forever (kept with the header) | Inherent while names may need them; goes with header forgetting (row 1) | none |
| Grant names of a dropped `secrets.0` part: `Dropped::names` in its record (per box to a holder the commit's edge writes put: holder, role, epoch and the sealed names, about 100 B plus 80 B per name; a rotation's or re-seal's boxes keep none) (C) | Node | Per grant or raise of a holder actor whose boxes part dropped, forever (kept with the header) | Inherent while a boxer of the holder must hold them; goes with header forgetting (row 1) | none |
| Node epoch records `k/` (C) | Node | Per epoch learned per role: about 150-250 B, forever | Inherent while old content is readable. Could fold into the newest history | none |
| `label.0` steps (about 200 B each, kept) and their claim sets with entry boxes (33 B per claim, about 1.2 KB per static entry) | Both | Steps per registration, forever. Claim sets: every admin `label.0` write drops those of steps superseded for `ROLE_KEEP` (`flows::labels::drop_old_claims`, C) | Steps inherent (the path); claim sets bounded. Old bodies carrying the sets go with role-class compaction | none |
| Host label rows: `L` meta 129 B, `S` steps about 325 B, `V`/`W` 32 B, `Q` replication position 24 B (C) | Host | Per label and per registration, forever (no label removal) | Closable: label retirement at hosts (needs a protocol op) | none |
| Host superseded claim sets | Host | Dropped after `max(claim_keep, ROLE_KEEP)` (C) | Bounded | none |
| Node-sync `y/k` certificates (label, commit), `y/s` carriers per dropped body (32 B IDs + time), `y/h` head per (host, label) about 325 B (C) | Node | `y/k` while the node holds a part of the commit (revoke and removal certificates: as long as their bodies, like the ledger); `y/s` while the body has an entry under a label, was deleted from one or set within `TOMBSTONE_LIFETIME`, or carries such a body (`State::sweep_carriers`; a commit whose `created.0` part keeps its entry keeps its carrier, row 8); `y/h` per host label | Bounded (closed); `y/h` bounded by labels | none |
| Node-sync `y/y` owed flow deliveries (an encoded delivery: tag, commit IDs and tids, keyed by its 32 B hash; C) | Node | Per role flow, from its commit's transaction until node-sync carries it out (the next step), or while a copy of it waits for a rotation; a copy whose group never becomes encryptable again (this node may not rotate it) keeps its row while this node holds the group's labels (dropped when it forgets them, or at the next start once they are gone), one per such flow | Bounded (closed) but for that stuck case | none |
| Local derived indexes (`node/metas`, `node/edges` about 2x a roster snapshot, box and epoch indexes) | Node | With their commits | Follow rows 1 and 8 | issues/session-sources.md |
| Ephemeral headers in memory | Node and host memory | About 15 MB per hour per author at presence rates, until restart | Closable: same forgetting | issues/eph-unify.md |
| Parked commits (unknown encoding), and parked parts of applied commits | Node | Whole commit or part bytes until a build understands them | Bounded by authenticated writers only | none |
| Pending commits and parts that wait alone (a record or chain that never comes) | Node | Bytes of each held part until its wait ends, kept for good if it never does; a slot holds one candidate in the pending blob; other copies live only as their label entries (`SyncEngine::redeliver`) | Bounded by what peers deliver under labels the node syncs: nothing ages these out | issues/pending-unbounded.md |
| Thin clients: `clients.0^` entry (about 50 B, tombstone kept as for any map entry), the client actor's creation record, `keys.0`, `secrets.0` and about 2.6 KB of boxes per grant (notes/permissions.md) | Both | Per client ever added and per grant; the entry and grants go at `remove_client`, the records and their history stay as for any actor (E) | Inherent | none |
| Undo buffers | Node | Capped at `UNDO_DEPTH` = 16 per aspect | Bounded | none |
| Death records (DEATH rows) | Node | Live with their body | Bounded | none |
| Suspect flags `q/` and heartbeat suspect lists (spec/permissions.md §4) | Node; host (in heartbeats) | Per suspect aspect: a flag row (8 B + 34 B per body it is about) until each body is held again or a valid snapshot listing it joins; per heartbeat about 60 B per entry (tid, AK, 16 B digest), at most `MAX_HEARTBEAT_SUSPECTS` = 32. No per-aspect digest is stored: digests are computed when a heartbeat is written or read (C). The label-level `held`/`state` set-hashes of the convergence study (16 B per aspect stored) are not built | Bounded (cap; flags clear on repair or the next compaction) | none |

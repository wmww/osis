## Decided by Tess, in the plan and the design notes, not yet in the models or spec
Written into notes/write-path-design.md, notes/account-membership-design.md and notes/terms.md as lettered rules (notes/redesign-plan.md, D1 result); the drafts carry To recut sections. One question came back: issues/owner-key-first-attach.md.
- **Owner keys replace key actors.** An **owner key** is a key a thing lists as allowed to sign as it: a concept of its own, a value with no tid, aspects or roles. Always "owner key", never "owner" alone (that reads as a role, and long ago was one: set at creation and immutable, which an owner key is not).
  - It speaks for the one thing that lists it: it is no actor and holds no role. A commit it signs is that thing acting, and the actor chain is all things, from the thing the key signs as to the target. Only things hold roles. A limited key is a thing with an owner key, granted what it should have: a node root is an ordinary thing with its node's owner key, holding a role on its account (README.md); a node wanting two accounts unlinked uses a thing and owner key for each.
  - A thing is minted with a mint admin or an owner key (a thing with no mint admin is where a chain starts). Owner keys are added and removed afterwards; the list is written only as the thing itself, by an owner key, and admins read it. A thing with none takes its first from an admin.
  - It outranks admins, which is recovery: issues/recovery-redesign.md.
  - Key actors as a kind of thing go: no grant targeting one, no sync unit carrying one, the walk never entering one, and "signer things" as an account's members (notes/account-membership-design.md §2, notes/redesign-plan.md A4). "Signer" as the design's word for a member key (notes/terms.md) becomes owner key. A thing's owner-key history is evidence wherever it signs, and a removed owner key is the ordinary removal one hop earlier.
  - The last-admin rule is unchanged: a write removing the last admin grant says so, whether or not the thing has an owner key.
  - Before the word rolls out: no reference to the old owner role survives (checked: spec, notes, issues, core, cli, libs, app). "Owner" is used loosely for an admin in comments of core/engine/src/rotation/tests_members.rs (four places): reword. A sync ID's owner (spec/sync-ids.md §4 Owner: the thing a sync ID is of) is another sense and stays.
  - Principle: notes/principles.md, Things are all made of the same stuff.
- **May-grant becomes a flag** (Tess; to be dropped if it causes problems): a grant either lets its holder add new holders up to its own role or does not, in place of a level. A lower level is an arrangement: a thing holding the lower role with the flag, the person a writer of it. Wire (`invite`), walk, API (`may_grant`) and CLI change.
- **May-grant stays** (the spec's `invite`): dropping it was weighed and rejected. It is no root cause of open bugs, and without it link joiners are either unnamed or able to evict each other.
- **Grants from outside stay gated**: a role change needs admin on the target (or may-grant, to add a new holder) and write on the holder, or the holder externally grantable and one of its writers accepting; a holder may always drop or lower its own grant. As designed (notes/write-path-design.md §4).
- **No eager delivery of removals.** Reversed: "a removal is logged where an act of the removed node could be valid, for good" (the errand, the standing duty, the record per (removal, target), holding a unit for it). A removal reaches a far thing as it does today: with the thing's next key rotation by a writer holding it, and where a node holds both it and a write it judges there. Wanted if it is simple and good (model it first): a node that only reads the thing depositing the removal there when it holds a write the removal cuts, the copy leaving with the writes it judges. If that turns out to be trouble, the gap (a removed key's write showing at readers served only by stores, in a thing no remaining member writes) is an open bug in an issue, not something to build around. The questions that existed only for the duty go with it (they are gone from notes/a3-spec/README.md).
- **A write judged invalid is dropped, as built.** A reader drops a body it judges invalid at once (spec/commits.md §5 Invalid); no node deletes one at a store, whose copy, within the store's caps, is where it is fetched from if it turns valid (issues/invalid-junk-kept.md); a write turning valid comes back from whoever still holds it, which is whoever held the evidence that made it valid, and is gone where nobody does. Nothing is kept aside for it and no drop waits for a complete pass: a kept copy helps only where every holder judged the write invalid and its writer is gone, within whatever bound it had, a heuristic for something not required (Tess). The loss is stated (notes/a3-spec/README.md Open 12 (a); notes/a2-spec/README.md Open 11 (b)).
- **The last admin is a writer's check only.** A node does not remove the last admin it sees without being told to (built: notes/permissions.md, The last admin); no rule every node judges, so two sole admins leaving at once leave a thing adminless, as a deliberate leave would. Goes: A1 brief 6, a lowering naming its remaining admin and that edge as evidence, Open 26's fix on `windlass-wiring-1`. The writer's check itself may go too if it is ever in the way (Tess: not a big deal). Settles notes/a1-spec/README.md, For Tess before the switch 1.
- **A write acts only as things on its chain**: writing "as" a thing that holds no role leading to what is written is refused (notes/a1-spec/README.md Open 16; notes/path-form.md For Tess 2).
- **Nothing vouches for a role write**: issues/role-vouch-contested.md (the rule and its To do).

# Build, test and merge workflow
> Summary: How a task goes from branch to main (warm task worktrees, one dev profile, gate in the worktree, fast-forward main), the command forms, what builds and tests should cost so you can tell when something is wrong, and a short history of the designs that were tried and dropped.

Read this if you coordinate, if a build or test run feels slow, or if disk is growing. Normal numbers on a laptop are seconds for an incremental build, under a minute for tier 1, a minute or three for the gate. If you are seeing tens of minutes, something is broken; it is not how this project builds. The numbers below are from one machine (16-thread Ryzen 7 PRO 6850U laptop, 30 GB RAM, LUKS disk); another machine scales them by a constant, and load scales them 2-5x, but the ratios between rows hold.

## Current state

**One idea:** a task is a branch in a warm worktree; the branch proves itself there; main only fast-forwards and is never built.

- **Layout**: `core/` holds the library crates in unprefixed directories with prefixed package names (`core/node` is osis-node, `core/engine` osis-engine, `core/base` osis-base); `core/test/` the test infrastructure (sim, vectors, fuzz, crdt-model, membership-model, tla); `schema/` the first-party schema files; `cli/` the CLI.
- **GUI workspace**: `kit/` (osis-kit) and `app/` (osis-app) are their own Cargo workspace, root manifest `kit/Cargo.toml` (members `.` and `../app`, which points back with `package.workspace`; `default-members` both, so a bare `cargo build` in kit/ builds the app too), with its own `Cargo.lock`, `deny.toml`, `[patch]` table and target dir `kit/target/` (one per worktree, like the core one). The root workspace excludes both. Commands run in kit/: `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo run --bin osis-app -- DIR`; `python3 tools/policy.py kit` from the root. First build about 1.5 min (wgpu, Vello, winit); the osis crates compile a second time there (another lock, other features), which is the price of keeping the GUI stack out of core's builds. Core depends on nothing in it; it depends on `osis` and `osis-schema` by path only.
- Further projects (tools) are top-level directories depending only on the `osis` crate.
- **Worktrees** (`wt`, from the reasonable-rust-builds plugin, enabled in `.claude/settings.json`): `wt claim <branch> [<base>]` prints a task worktree `.worktrees/wt<N>` (gitignored, inside the repo; the tools that scan sources use explicit roots and never see it). Each has its own in-tree `target/`, kept between tasks, so a task's first build recompiles only what its branch changed: git rewrites only the files that differ, the path is the same, incremental state survives. `wt release` when the branch is committed (it prunes the target, below, then detaches HEAD; the branch is free to merge or delete), `wt list`, `wt trim [keep]`. Policy: two stay warm per device; more are created when more agents run at once and trimmed after. A new worktree builds cold once (about 80 s, 3.6 min through clippy-net). Never share a `target/` between checkouts and never build in the main checkout.
- **One profile for all per-branch work**: dev. Cargo.toml: workspace crates `opt-level = 1`, `debug = "line-tables-only"`, incremental; dependencies and osis-crypto `opt-level = 2`, no debuginfo; no `split-debuginfo` (its per-build `.dwo` files only accumulate). Debug sections are zlib-compressed at link time (`.cargo/config.toml`, Linux target): the test binaries weigh about 0.65 GB instead of 1.7 GB and backtraces keep file:line; zstd compression is not read by Rust's symbolizer, and `strip = "debuginfo"` would save another 0.3 GB at the price of frame locations. Every new combination of profile, features, `RUSTFLAGS`, `CARGO_INCREMENTAL` or target dir is another full artifact set (a `-p` subset is not: Feature unification below), so there are exactly these command forms:
  - tier 1: `cargo test --workspace` (`--no-run` to build; narrow with `--test it <module>::` and name filters; `cargo build --workspace --all-targets` and `cargo run --bin <name>` reuse the artifacts)
  - dev loop on one crate: `cargo test -p <crate>` (narrowed the same way; builds only that crate's tree, the same artifacts the workspace build uses)
  - lint: `cargo clippy --workspace --all-targets -- -D warnings` and `cargo clippy-net -- -D warnings` (the one networking feature set, 73 extra crates built once per worktree)
  - networking tier 2: `cargo test-net -- --ignored driver:: runtime:: quic relay lan` (always with filters: unfiltered it runs every ignored test of the workspace in dev, timing budgets included, which takes far longer; 25 tests, about 20 s)
  - sim: `cargo run --bin sim-sweep -- --seeds N --budget-secs T`
  - tier 2 by name: `cargo test --workspace --tests -- --ignored <name>` (`--tests` skips the doctests, which an unnarrowed run builds and runs after the ignored test), or narrower `cargo test -p <crate> --test it -- --ignored <name>`; the whole set `PROPTEST_CASES=256 cargo test --workspace -- --include-ignored --skip scale:: --skip bench:: --skip budget --skip sweep --skip repro_`
  - harness env vars (`OSIS_*_START`/`_SEEDS`, `OSIS_PERM_SEED`, ...): read through `osis_base::testenv`, which panics on an unparsable value, zero seeds or any set `OSIS_*` variable not in `testenv::KNOWN` (a typo; policy.py keeps the list equal to what the sources name: add a new variable there). A set variable and an overridden range are echoed past libtest's capture, so they show on a passing run; the rest of a test's output (per-seed lines, summaries at default ranges) needs `-- --nocapture` (after `--ignored`/`--exact`). Failure messages carry the range. Tier-1 harness tests are not `#[ignore]`: `--ignored --exact <name>` on them runs nothing and passes, check `1 passed`.
  - old vs new: `tools/bin-at REV OUT [--release] [-p CRATE] [--test NAME]` (default osis-node `it`, dev) copies REV's test binary to OUT (the scratchpad), built in your worktree: it needs a clean tree (wip-commit), checks REV out detached, builds the standard artifact set, checks your branch out again (also on failure); the next build recompiles what REV changed back (each way: the crates the diff touches and their dependents, about a minute for an osis-engine change at load). Then run old and new side by side, or under `tools/icount` (notes/testing.md). The binary keeps your worktree's manifest dirs, so a test reading fixtures reads the checked-out ones. Not a second worktree: a fresh one builds cold (minutes, GB), and two checkouts never share a target.
  - release, timing only (`scale::`, `bench::`, `budget*`, cost repros in issues/): `cargo test --release -p <crate> --test it -- --ignored <filter>` (the crate holding the test), in your worktree; keep `target/release` (a few hundred MB), the next timing check is cheaper for it
- **Merge gate** (`tools/gate.sh [--all] [--sweep-seeds N] [--base REV] [--plan]` (REV: compare against it instead of the merge base, to time one project's steps; `--plan` prints the selection, tested on fabricated histories by `tools/gate_select_test.sh`, a gate step), in the worktree after `git rebase main`; steps per project, see Components pay for themselves): `cargo test --workspace --locked`, the unification check (Feature unification), both clippy runs, `tools/policy.py`, `tools/spec_map.py --uncited` and `--gaps`, `cargo deny check`, then the 5-seed dev sim sweep (every scenario; seed breadth is a periodic check) when the branch touches `core/test/sim/`, osis-engine, osis-node, osis-perm, osis-crdt or Cargo.toml/lock since its merge base (the crates it has caught regressions in; `--sweep-seeds N` forces, 0 skips). Each step prints its wall time. Then `git checkout main && git merge --ff-only <branch> && git push`. Task branches are never pushed: worktrees share the repo's branches, so the coordinator merges the local branch directly. `git pull --rebase` everywhere; history is linear. The generated notes/testing-map.md is gitignored, so nothing conflicts on a rebase but real edits.
- **Coordination** (worker, reviewer, fast-forward; periodic checks; the watchdog; complaints): notes/coordination.md.
- **Components pay for themselves**: with more projects in the repo (app/, kit/, cli/, core/), iterating on one must not run the others' tests or checks. The gate selects its steps by what the branch touched: a diff only under kit/ or app/ runs the GUI steps alone (`policy.py kit`, GUI test, clippy, deny in kit/); any other diff runs the core steps plus `cargo check --workspace --all-targets` of the GUI workspace (an osis API change must not silently break the app); both when both; everything on main or with `--all`; the sim sweep by crate within the core steps. policy.py and spec_map.py look at the core workspace (spec_map: core/, cli/ sources only); policy.py takes a workspace dir for the GUI one and skips vendored `patches/`. New projects extend the same pattern, per-branch oracles and periodic checks are per component (notes/coordination.md), and the dev loop on one crate is `cargo test -p <crate>`, which builds only that crate's tree (Feature unification).
- **Waiting**: a command that may pass a few minutes runs with `run_in_background` and is awaited with `claudewait ID` (CLAUDE.md). Never a shell wait loop.
- **Shell footguns met**: `pkill -f`/`pgrep -f <pattern>` also match the Bash tool's own `bash -c` wrapper (killed the caller's command); the pre-plugin `claudewait` (~/.local/bin) cannot find a background job whose shell redirects its own stdout (`for ...; done > log`, `{ ...; } > log`, `exec > log`) and reports it "finished earlier" at once: redirect per command instead; editing sources (or swapping files with `git show rev:path > path`) while a background cargo runs builds the half-edited tree: build once and run a copy of the test binary from scratch, and wip-commit before swapping files; `--test it <filter>` across the workspace prints a `0 passed` result line for every other crate's `it` binary. A background run whose `> $D/x.log` names a scratch dir not made yet fails at once and its `echo $?` reports success (three agents): make the dir in an earlier call and check the log for `test result` lines. A misspelled `--exact` name or seed env var (`OSIS_WALKS_*` vs `OSIS_WALKS_MOVES_*`), or `--ignored --exact` on a test that is not ignored (walks, deaths_never_early), runs nothing or the default seeds and still says ok (the seed helper's zero-seed panic needs the test to run, so a wrong `--exact` name still passes with `0 passed`; oracle names carry a `_spec_*` suffix, `--list --ignored` shows them): check for `1 passed` and the printed seed range, which the harnesses write with `eprintln!` and libtest shows only with `-- --nocapture` (a passing run without it, copied binary or not, prints no range). `git rebase main | tail -1 && tools/gate.sh` gated a conflicted tree (the pipe hid the failed rebase): rebase without a pipe. `git checkout <file>` to undo a temporary test edit also drops the file's uncommitted work: wip-commit first. A test run that panics on an unknown `OSIS_*` variable fails in seconds and proptest saves the panic as `proptest-regressions/*.txt`: check `git status` before committing. To reproduce a load-dependent flake, pin the test to few cores (`taskset -c 0-1 <copied binary> ...`) rather than spinning CPU burners: 16 busy shells for 15 min (redeem-flake) loaded every other agent's gate. Oracle chains: run a copied test binary (above), not `cargo test` per step; four agents broke their own chains by editing meanwhile. `rust-lld: undefined hidden symbol anon.*.llvm.*` after a build was stopped midway: delete `target/debug/incremental/<crate>-*`, then rebuild.
- **Permission prompts**: agents run unattended, so a command that needs approval stalls the owner's screen. Stay inside your worktree and the session scratchpad; use absolute paths instead of `cd` inside compound commands; no sudo, no network fetches, no writes outside the repo or scratchpad, no killing processes you did not start with `run_in_background`, no `git worktree add` outside `.worktrees` (use `wt`). Write scripts and files with the Write tool, not shell heredocs plus `chmod`/`rm` (that combination prompted). `pkill`/`kill` and `rm -f $D/*.log` in the scratchpad prompted too (one reviewer sat 83 min on an unanswered prompt): stop your own background task with the TaskStop tool, and use fresh file names instead of deleting. If a step needs approval, do it another way.
- **Pruned to what is in use.** `wt release`, for `target/` and `kit/target` each: if anything in it was used since the previous release, runs `scripts/wt-mark` there (every standard command, the gate's set; a no-op on a gated tree; marks the units to keep: cargo reads every live unit's fingerprint; add a new standard command there too), then in each profile used since then deletes every unit not used since; in `incremental/` it keeps the newest session per dir and drops dirs beyond the live units naming that crate (no cold builds: an osis-engine edit after a release costs the warm 7 s). Idle targets and profiles (an unused `target/release`) are left alone. If a target misbehaves, delete it and take the cold build. **Not on this box**: `/` is mounted `noatime`, wt detects it (`wt: this filesystem doesn't record access times (noatime): targets not pruned`, printed by every release) and prunes nothing, so targets only grow: 14-15 GB `du` in the two busy worktrees after a session, 7-8 GB in idle ones, `incremental/` 5-13.5 GB of it, of which 1-6 GB are superseded sessions (rustc keeps the previous finished session of each crate dir until that crate's next compile). Until fixed (owner: remount `relatime`, which wt supports; or a plugin change marking units from `--message-format=json`, which lists every fresh unit's files): on a released worktree (no cargo running there) whose target passes 12 GB, delete every incremental session but the newest per crate dir, which is what rustc would do next anyway and costs no rebuild: `python3 -c 'import glob,os,shutil,sys; [shutil.rmtree(s) for d in glob.glob(sys.argv[1]+"/target/*/incremental/*/") for s in sorted((x for x in glob.glob(d+"s-*") if os.path.isdir(x)),key=os.path.getmtime)[:-1]]' .worktrees/wtN`; past 20 GB delete the target.

## Feature unification
A package's features are the union of what everything in the build asks for, so `-p X` resolves differently from `--workspace` unless every crate's features are the same in both, and then rebuilds part of the tree as a second artifact set (before this was fixed, 20 of 21 packages recompiled 1-20 crates). cargo's `resolver.feature-unification = "workspace"` would do it outright but is unstable. The rules that keep it selection-invariant:
- No feature a member turns on that another build of the crate leaves off: optional features only for the networking opt-in set (osis/osis-node/osis-transport `iroh`, `lan`, `relay`, through `test-net`/`clippy-net`) and the default `driver` nobody turns off. QUIC, redb, `OsRng` and the server binary are unconditional.
- Third-party features in the `[workspace.dependencies]` table, the same for every member (tokio's set, blake3 `zeroize`, ed25519-dalek `hazmat`), not added per member; dev-dependencies add no features to a normal dependency.
- Pins: where a crate higher up enables features on a shared low dependency (quinn-proto: rand's defaults; libcrux-platform: libc's; x25519-dalek: zeroize's derive; crypto: blake3 `zeroize`), osis-base lists that dependency at the workspace's features (and crdt-model, which has no osis-base, as dev-dependencies), unused.
- Checked by the gate's `unification_check` (after the whole-workspace build, `cargo build -p <member> --all-targets` for every member from `cargo metadata` compiles nothing; 3 s when it holds). An offender: `cargo tree -e normal,build,dev --prefix none -f '{p}|{f}'` with `--workspace` and with `-p X`, diffed, names the crate and features; fix at the source by the rules above.

## What things should cost

Quiet machine, warm worktree, after the fixes this note records. If your numbers are more than about 3x these at low load, stop and find out why before doing anything else; the History section lists what it was last time.

| what | expect |
|---|---|
| no-op `cargo build --workspace` / `--all-targets` | 0.4 s / 2 s |
| one-line edit, `cargo test --workspace --no-run`: osis-node (`sync/`) / osis-engine | 2.5 s (4 crates) / 5.5 s (5 crates); before the split either was 5.5-7.5 s |
| `cargo test --workspace` tests, built | 45 s, 476 CPU-s quiet (osis-node `it`, 459 tests, 23 s of it); CPU-bound, so it scales with load (2-4x at load 25-35); notes/testing.md, Tier-1 cost |
| edit osis-crdt or osis-base (bottom of the stack), all targets | 10-16 s |
| clippy / clippy-net after a one-line edit | 3-7 s / 3.5 s |
| clean `cargo build --workspace`; then `--all-targets`; first clippy; first clippy-net | 82 s; +53 s; +17 s; +69 s |
| osis-engine and osis-node from scratch (their incremental state gone) | 27 s: osis-node starts on osis-engine's metadata at 5 s and the two codegen in parallel (one osis-node: 40 s) |
| gate, warm, without / with the 5-seed sim sweep | about 55 s / 1.5 min quiet: tier 1 47 s, sim sweep 38 s, everything else 6 s (policy, spec_map, unification 2-3 s, both clippy runs, schema check, deny), the GUI workspace's check 2 s or its steps 5 s (test 3-4 s warm; 137 s when `kit/target` is cold); 2 min at load 15; 4-9 min while a periodic run shares the box at normal priority. | `core/test/tla/run.sh small` | 95 s |
| release `cargo test --release --workspace --no-run`: clean / after an edit (thin LTO relinks every test binary) | about 5 / 4 min at load 10-16; faster quiet |
| release, one crate: `cargo test --release -p osis-node --test it --no-run` clean / after an osis-node edit | 2.9 / 1.7 min at load 20-30 (no other test binary relinks) |
| `unification_check` in the gate (after the build) | 7 s |

In a dev build the sizes default smaller (`scale.rs` `size`): a first sync of 10^4 commits there takes 9 min (`check_unchanged` re-examines every pending commit), an edge write with 10^4 commits held 0.27 s; at the dev sizes each touched test runs 10-60 s |

| tier 2 as a whole | not measured since the perm set was sharded (2.4 min) and the budgets moved to release; the remaining single-threaded tails are the crdt decoder differentials at 1024 cases; a periodic check, never per branch |
| a task worktree's `target/` | about 4-6 GB after a gate and a pruning `wt release` (+0.3-0.7 GB release); `kit/target` 1-3.5 GB more; unpruned (noatime, above) 14-15 GB |
| test executables | 53 (tests and bins), about 0.65 GB with zlib-compressed debug sections; an osis-node or osis-engine edit relinks the ten above it inside the build |

Load: three cargo invocations each asking for 16 jobs on 8 physical cores reached load 60-80 (one rustc took 15 min of wall for 2.5 min of CPU). On a shared box cap jobs per invocation at the physical core count in the user-level `~/.cargo/config.toml` (`[build] jobs = 8` on this box; it changes no artifacts, so it is not a hygiene violation; never per command). **Idle priority (this box)**: the owner disabled `system76-scheduler`, which had put every cargo/rustc running past about a minute into SCHED_IDLE (a two-file rebuild took 37 min behind a sweep). Builds now run at normal priority; if long cargo runs crawl again, check `systemctl is-active com.system76.Scheduler` and `chrt -p <pid>`.

Signs of unravelling, in the order they appeared last time: a build on a tree that was built minutes ago compiles more than the crates you touched and their dependents; `target/` dirs growing by GB per day; agents' tool calls lasting exactly 10 minutes; a "wait for X" shell loop anywhere; `--jobs`, `--release` or `--features` creeping into commands; the gate's unification check failing; a timing test running in dev.

## History (what was tried, briefly)

Three worktree designs preceded this one, all measured on a 4-core box shared with other agents:

1. **Seeded per-task worktrees**: a new worktree's `target/` hardlinked from the main checkout's by a post-checkout hook. Fast when the seed was fresh, but a changed core crate still compiled in full, the hook failed silently when main was mid-build, and a seed from a stale main rebuilt 83 crates. Dropped.
2. **One shared build checkout behind a queue** (`tools/b`, commit 691c11d): rsync the worktree's sources into one build tree with fresh mtimes on changed files, flock, run cargo there. Correct and as fast as a warm worktree, one target on the box; but the lock had to be held through test runs (tests read fixtures through the manifest dir baked in at compile time), so a sweep or tier-2 run blocked everyone, and outputs written into the tree stayed on the build side. Dropped for serialization, not correctness. Note: pointing two checkouts at one `CARGO_TARGET_DIR` is a different thing and is unsafe (cargo keys artifacts without the path and judges freshness by mtime: measured, a tree read as fresh with the other tree's code inside).
3. **Slots** (`tools/slot`, `../osis-wt/slotN`) with warm in-tree targets, plus `tools/sweep.sh` after every gate to delete orphaned artifacts: the design just before this one, and the right shape. What went wrong around it, found by measuring on a quiet box against the logs of a day's work:
   - The sweep counted a crate's build unit and its clippy check unit as one, kept the newest incremental dirs (clippy-net's, the last step) and deleted the build's. Every gate on main then compiled every changed crate from scratch: 16x the CPU, 4-7 min builds at load that should have been 10-60 s.
   - `split-debuginfo = "unpacked"` left a `.dwo` per rebuild in `deps/`, which neither cargo nor the sweep deleted: 2.7-5 GB per slot, three slots at 35 GB against 5.4 GB fresh.
   - Agents waited for background jobs in shell loops with guessed conditions (`until grep -q PATTERN log`, `until ! pgrep -f PATTERN` which matches its own shell) that hit the 10-minute Bash cap: 21-109 min per agent, orphaned loops running for hours. Replaced by `claudewait`.
   - Release timing builds ran under load (12-24 min each) and `target/release` was deleted after every one.
   - Dev-profile timing budgets sat in tier 2, so the whole set took over 40 min on one core.
   - The gate on main repeated the build the reviewer had just done in the slot.

The current design is slots with the slot renamed, moved inside the repo, the sweep and split-debuginfo gone, the gate moved to the worktree, and waiting done by one tool.

# Build
> Summary: Repo layout, task worktrees, the one dev profile and the fixed command forms, the heavy lock, footguns, and what builds and tests should cost so you can tell when something is wrong. Feature unification, disk upkeep, the scheduler and scripted renames: notes/build-internals.md; time limits: notes/time-limits.md; the merge gate: notes/gate.md.

A task is a branch in a warm worktree; main only fast-forwards and is never built. Much past What things should cost means something is broken.

## Layout
- `core/` holds the library crates in unprefixed directories with prefixed package names (`core/engine` is osis-engine); `core/test/` the test infrastructure (sim, vectors, fuzz, crdt-model, roles-model, held-model, tla); `libs/` what some but not all users of osis want (`libs/chat` osis-chat, core; `libs/kit` osis-kit, GUI); `schema/` the first-party schema files; `cli/` the CLI. Further projects are top-level directories depending only on the `osis` crate.
- **One workspace**: one `Cargo.lock`, one `target/`. `default-members` is core, so a bare `cargo build`/`test`/`clippy` never compiles the GUI (osis-kit, osis-app, osis-android), which builds only when named with `-p`; `--workspace` means core and GUI. Core depends on nothing in the GUI.

## Worktrees
`wt claim <branch> origin/main` (after a `git fetch`: it branches from the ref as last fetched; without a base it branches from the lagging local main) prints a task worktree `.worktrees/wt<N>` with its own warm `target/`. `wt release` when the branch is committed (prunes the target, detaches HEAD; run it inside the worktree or name its path), `wt list`. A claim of a branch that exists locally checks out the local copy and ignores the base: for a branch pushed from elsewhere, `git reset --hard origin/<branch>` after claiming. The first release that marks in a worktree, and the first after a manifest, lock or toolchain change, runs every standard build (1-4 min: notes/build-internals.md, Disk); later ones take seconds. A new worktree builds cold once (about 80 s). Never share a `target/` between checkouts (`CARGO_TARGET_DIR`): cargo judges freshness by mtime, so one tree reads as fresh with the other's code inside. Never build in the main checkout.

## Profile and command forms
One dev profile for all branch work (Cargo.toml; details: notes/build-internals.md, Profile). `.cargo/config.toml` sets the test env (`PROPTEST_CASES=32`, `PROPTEST_DISABLE_FAILURE_PERSISTENCE`: Footguns). Every new combination of profile, features, `RUSTFLAGS`, `CARGO_INCREMENTAL` or target dir is another full artifact set (a `-p` subset is not), so there are exactly these forms:
- **Default tests**: `cargo test --no-fail-fast` (without it cargo stops at the first failing binary); `--no-run` to build.
- **One crate**: `cargo test -p <crate>`, narrowed with `--test it -- <module>:: <name>...`: filters go after `--` (before it cargo takes one filter and refuses a second; one before and one after are OR'd, so `--lib m::tests -- --ignored repro_` also runs every ignored test in `m::tests`, `_large` properties included, outside `tools/heavy`), and `--no-fail-fast` whenever the lib binary may fail, or `it` never runs. Never `--test it <filter>` without `-p`: it prints a `0 passed` line for every other crate's `it`, hiding the one that ran.
- **Lint**: `cargo clippy --all-targets -- -D warnings`. GUI: `cargo clippy -p osis-kit -p osis-app -p osis-android --all-targets -- -D warnings`, `cargo test -p osis-kit -p osis-app --no-fail-fast` (an app failure otherwise skips kit's tests), `cargo run -p osis-app -- DIR`.
- **A property or by-hand test by name**: `cargo test -p <crate> --test it -- --ignored <name>`. Seeds and env vars: notes/test-harnesses.md.
- **Sim**: `cargo run --bin sim-sweep -- --seeds N --budget-secs T` (notes/test-sim.md).
- **Networking** (by hand): `tools/heavy --short cargo test --no-fail-fast --tests -- --ignored quic relay lan --skip repro_`, always filtered (unfiltered it runs every ignored test; a `repro_` fails by design); its runs take about 13 s, so the short lane.
- **Release**: never inside a task (scaling is checked by counting work: notes/test-scale.md), roles-model searches included (`cargo run --bin roles-model` is the dev profile). Memory checks and `cargo bench` are the coordinator's, alone.
- **Old vs new**: `tools/bin-at REV OUT (-p CRATE [--test NAME] | --lib CRATE) [--patch FILE]... [--take PATH]...` builds REV's test binary in your worktree and copies it to OUT (`--lib osis-engine`: its unit-test binary, run it from `core/engine`). A new test against an old REV: `--take core/engine/tests/it/x.rs` or `--patch FILE` (a `git diff`). Needs a clean tree (wip-commit); checks REV out detached and your branch back; the next build recompiles what REV changed. OUT is the only copy of REV's binary: what it compiled at REV is deleted from `target/` (cargo's path there is the branch's binary's, so running it later ran REV's code). A patch for a revision before a directory move needs its paths rewritten by hand. Several binaries at several revisions: one spare worktree per revision (`wt claim <name> <rev>`) and one `cargo test -p A -p B --no-run --message-format=json` there, copying every executable: one build per revision, where bin-at per binary rebuilds your worktree twice per call. Compare under `tools/icount` (notes/test-harnesses.md, Measuring).
- **Jobs** are capped in `~/.cargo/config.toml`, never per command (`--jobs`).

## Heavy lock
One large all-core run at a time per box: `tools/heavy [--limit NAME] [--log FILE] <cmd...>` runs a command under the box-wide lock: release checks, by-hand property and sim runs at size, TLC and roles-model runs; the gate takes it itself. Why: two large runs at once each take about twice the wall (CPU-s barely moves), which blurs every hold's wall limit, and two large runs' memory can exceed the box's 30 GB. `--log FILE` writes the command's output to FILE, making its directory, with a line while it waits for the lock (since when) and how long it waited: a shell redirect (`> $D/x.log`) into a directory not yet made fails before the lock is taken and runs nothing.
- **Short lane**: `tools/heavy --short [--log FILE] <cmd...>` runs at once beside any hold (gates included), one short run at a time box-wide, and stops the run (its whole process tree, exit 137) past limit `heavy.short` (115 CPU-s, 230 s wall on ostrich: `tools/limits.py table`) or 4 GB resident. For a roles-model search or mode batch, a held-model twin, a seed replay: anything under about 100 CPU-s, judged by CPU-s, not wall (a roles-model search a README times at 15 s is about 230 CPU-s). Every hold prints `fits the short lane` when it did, so a rerun of the same command knows; a stopped run says to rerun without `--short`. Not for a command that edits the tree (`tools/mutate.py`: a stop leaves the plant), and not a loop of `--short` calls doing one big job (that is a hold). It costs a gate beside it at most its CPU-s / 16 of wall, a few seconds.
- **A quiet hold yields**: a hold whose process tree used under 1.5 cores over the last 5 min (`YIELD_CORES`, `YIELD_WINDOW_S`) while another run waits for the lock, at most 4 GB resident, releases the lock and runs on beside the next holder, the log and `--report` marking it `[yielded]` (one yielded run box-wide). If it then goes over 1.5 cores or 4 GB, its whole tree is stopped (SIGSTOP) until it holds the lock again, then continues; its next binary waits for the lock too. So a one-core shrink or TLC liveness tail costs waiters at most 5 min, a holder pays at most 1.5/16 of its wall, and nothing is killed. Wall-clock timeouts inside a run that was stopped see the stop.
- Unlocked: builds and single-crate test runs (`cargo test -p osis --test it` too), and anything that cannot use every core (a one-seed replay, a one-worker TLC, `tools/icount` at a few threads). Build every variant first and take the lock only for the run: a lock wait is often 10+ min. A run over the lane's cap but only a few minutes: batch every mode and plant into one `tools/heavy sh -c '...'` hold, with no `| head` inside it (the next printing search panics on the closed pipe). Not beside your own hold: your crate tests beside your own search pushed holds to 609 and 891 s against the 598 s `heavy` wall; run them before or after, and give an exhaustive search (`custody-exh`) its own hold.
- A `cargo test`/`cargo run` (maybe behind `env VAR=VAL`) builds before queueing and the hold runs copies of its binaries (cargo's args, cwd and env, `Running` lines, `--no-fail-fast` and exit codes as cargo's): edits after invocation don't reach it and nothing compiles under the hold; a build failure exits without queueing. Not covered: doctests (run while building, unlocked), data files or `CARGO_BIN_EXE_*` binaries a test reads from the tree at run time, and cargo inside a script (`run.sh`, a python tool): that runs what is on disk when the lock frees, so build first and don't edit while it waits. A `tools/heavy` inside a hold refuses.
- Log and reports: notes/build-internals.md, Heavy lock log.

## Footguns
- **Waiting** (CLAUDE.md): `run_in_background`, then `claudewait ID` with the task ID the tool printed. `claudewait` knows Bash background tasks only. Never `timeout` around cargo: it kills a test run with a green-looking log, and a build killed mid-link leaves the crate unable to link. A foreground call past 120 s moves to the background and its later steps keep running: keep edits out of a call that may run long.
- **Exit codes**: `cmd > log; echo exit $?` ends with the echo's status, and a pipe through `tee`/`grep`/`tail` reports the pipe's: read the `test result` lines. Gate a push on the check's own code: `python3 tools/policy.py && git push`. A `&&` chain stops silently at its first failure (`git commit -qm wip && <edit>` skips the edit when there was nothing to commit): keep edits in their own call. A pipe that stops reading (`| head`) ends the call while the test binary runs on unseen: write output to a file (`> log 2>&1`; `2>&1 > log` sends stderr to the call), then grep it for `panicked` and `test result` (a `tail` of a failing differential cuts the panic line off above its dump).
- **Runs that test nothing and say ok**: a misspelled `--exact` name or seed env var, `--ignored --exact` on a test that is not ignored, `OSIS_SIM_ONLY=` set empty. Check for `1 passed` and the printed seed range; oracle names carry a `_spec_*` suffix (`--list --ignored` shows them). A `repro_` test fails by design.
- **Captured output**: libtest captures a passing test's output: an `eprintln!` probe shows nothing without `-- --nocapture`. A throwaway probe variable is named `OSIS_PROBE_*` and switched off by unsetting it (`env -u`): `X= cmd` still sets it (`var_os` is `Some`), so a `for v in 1 ""` toggle runs the probe both times. testenv refuses any other `OSIS_*` name missing from core/base/testenv-known.txt, and tools/policy.py fails while a probe is left in the sources.
- **Proptest**: `.cargo/config.toml`'s `PROPTEST_CASES=32` overrides a test's own `cases:` (deep runs pass `PROPTEST_CASES=N`). A test binary run outside cargo has neither setting: it runs 256 cases unless you set both (`tools/mutate.py` and `tools/heavy cargo test` run copies with cargo's own env).
- **Editing under a running build** builds the half-edited tree: edit and build in separate calls, one cargo test per worktree at a time. For a chain of oracle runs build once and run a copy of the test binary: `cargo test -p <crate> --test it --no-run` prints the `Executable` path; take it from each `--no-run` (a dependency change moves `it-<hash>`). bash reads a script as it runs it: don't edit `core/test/tla/run.sh` under a running `run.sh`.
- **git**: wip-commit right before each probe, edits made since the last probe included (`git checkout <file>` and `git reset --hard` drop uncommitted work: undoing a sed plant this way cost agents up to an hour of review edits to the same file), and plant faults with `tools/mutate.py`, which restores from the text it read, not from git. Squash only with `git reset --soft $(git merge-base HEAD origin/main)`, never onto a branch or remote ref (a ref that moved gives the new parent with the old tree: a silent revert). Before every push, `git diff --stat $(git merge-base HEAD origin/main)` lists only your files. `git commit --amend -- <path>` commits only that path (other staged changes stay staged). Never `git stash`; never `git checkout`/`switch` in the main checkout (read another revision with `git show REV:path`). Rebase with `git fetch && git rebase origin/main`, without a pipe, and read its result. A crate both sides changed includes a dependent of one main changed: a rebase over engine changes reruns sync's `it` for a sync branch (a push after engine tests alone carried a sync failure). A branch long behind main whose commits rewrite the same lines conflicts once per commit: squash it first (as above), then rebase once.
- **`tools/mutate.py`** (its docstring): `MUTATE_HEAVY=1` builds unlocked and runs the copies in holds; wrapped in `tools/heavy` it builds under the lock, and the crate cannot be edited until a wait of maybe 15 min and the build end. One mutation per OLD site (two plants of one expression: two runs); an OLD that is not unique, a closure's text (its `if` wraps two closure types: mutate a value inside it) or a `&&` tail does not plant: pick whole operands. Read its whole output or `MUTATE_OUT`: a `| tail` hides the first rows, and a row holds the plant's own `|` (split from the right on ` | `).
- **Short-lane stops**: `tools/heavy --short ... | grep` hides the stop line (exit 137, no partial output): check the exit. A search's CPU-s grows with its checks, so a size that fit the lane stops after a check is added: time it (`/usr/bin/time`) before trusting `--short`.
- **Broken link** after a stopped build (`rust-lld: undefined hidden symbol anon.*`): `cargo clean -p <crate>` for the crate whose rlib the error names, then rebuild.
- **`wt claim` races `wt release`**: release prunes the target (minutes on a first release) before it detaches HEAD, so the branch stays checked out there meanwhile and a claim of that branch fails with "already used by worktree" (`wt list` shows the old worktree still claimed). Wait for the release to end (`claudewait` on your own background release; another agent's: `wt list` until its worktree reads `free`), then claim again. Upstream fix wanted: notes/complaints/upstream-wt.md.
- **`wt claim` of a branch that exists locally** checks out the local copy and ignores the base (above, Worktrees): a reviewer gets the worker's local branch, which may predate the worker's last push or rebase. After claiming, `git log -1 origin/<coordinator>-<branch>` against HEAD, and `git merge --ff-only` (or `reset --hard` when the push was a rebase) onto the pushed copy before reading the diff. A new branch from `origin/main`: `git status` right after the claim says whether it is behind (a claim without a fetch first branches from the stale ref).
- **Processes**: `.claude/settings.json` denies `git stash`, `pkill`, `killall` and `pgrep` anywhere in a command (a call holding `git stash list` is denied whole); stop your own background task with TaskStop.
- **grep** in agent shells may be Claude Code's ugrep shim, which rejects bounded repeats (`.\{0,150\}`): use `command grep` or python.
- **Debuggers**: ostrich has no `gdb` (so `rust-gdb` fails) and no `perf`; `strace`, `tools/icount` and `tools/cpuprof` (a SIGPROF sampler; `--report` symbolizes against the binary as it is now, so profile a copied binary) work, and a hung test is found by its libtest "running for over 60 seconds" line, then a round counter or `eprintln!` in the suspect loop (fixpoint loops that may never end carry one: `osis_base::loop_guard`, notes/test-harnesses.md, Loop guards). Debug test builds' `std::backtrace` resolves few frames (line-tables debuginfo): find a caller with `#[track_caller]` and `Location::caller()`. Where gdb is installed, `ptrace_scope` 1 lets it debug only what it starts: `gdb --batch -ex run -ex 'thread apply all bt' --args <copied test binary> --exact <name>`.
- **`HOME`**: a test or script that overrides it breaks rustup's `rustc` (tools/heavy reads `rustc -vV`): set `RUSTUP_HOME` and `CARGO_HOME` explicitly, as tools/heavy_test.py does.
- **Stdin**: `cat > file` (or `python3 -`) with no heredoc after it waits on stdin forever.
- **`tools/icount`** needs an absolute binary path (else `INSTR 0`, exit 127).
- **Silent when clean**: `tools/dup_windows.py` and `tools/spec_map.py --gaps --uncited` print nothing on a clean run.
- **A load-dependent flake**: pin the test to few cores (`taskset -c 0-1 <copied binary> ...`); don't spin CPU burners.
- **Permission prompts** stall unattended agents: stay inside your worktree and scratch dir, absolute paths instead of `cd` in compound commands; no sudo, network fetches, killing processes you did not start, or `git worktree add`. Write files with the Write tool.
- **Scratch** (CLAUDE.md): every file, gate logs and copied binaries included, goes in your own `<scratchpad>/<task>-<random>` dir; never a file or `rm` at the scratchpad root. `mkdir -p` the dir in an earlier call, not a parallel one (a redirect into a missing dir fails a background run; `tools/heavy --log FILE` makes it). At your task's end delete copied binaries, profiles and TLC state dirs (GBs each) in your own dir.
- **Scripted edits** over-match: a `sed` pattern `a.s` meant as "a's" rewrote a whole comment line; a python `str.replace` for one test also hit a near-identical older block. Edit with the Edit tool, or assert each replacement's count is 1.
- **Renames**: a scripted sweep over-matches: notes/build-internals.md, Scripted renames. Test harness traps: notes/test-harnesses.md, Harness footguns.

## What things should cost
Warm worktree. Compare CPU-s; wall follows load. More than about 3x the CPU-s: stop and find out why (3x at low load is a bug, not load). Gate stages: notes/time-limits.md, Limits.

| what | expect |
|---|---|
| no-op `cargo build` / `cargo test --no-run` | 0.2 s / 0.3 s |
| one-line edit, `cargo test --no-run`: osis-engine | 30-70 s, about 200 CPU-s |
| edit osis-base, `cargo build --all-targets` | 40 s, 314 CPU-s |
| clippy after a one-line edit | 3-8 s, then the GUI lint 3 s |
| clean `cargo build`; then `--all-targets`; first clippy | 82 s; +53 s; +17 s |
| first GUI build on a built core | 183 s, 1240 CPU-s |
| `cargo test -p osis --test it` | about 380 CPU-s |
| `core/test/tla/run.sh <module>` | under 3 min each at one worker; `netopen` about 5 |

Signs of unravelling: a build on a tree built minutes ago compiles more than the touched crates and their dependents; tool calls lasting exactly 10 minutes; a "wait for X" shell loop; `--jobs`, `--release` or `--features` creeping into commands; a long build whose CPU-s are normal but wall is 10x (the scheduler: notes/build-internals.md, Scheduler).

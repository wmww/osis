# Build, test and merge workflow
> Summary: How a task goes from branch to main (warm task worktrees, one dev profile, gate in the worktree, fast-forward main), the command forms, the footguns, disk upkeep, and what builds and tests should cost so you can tell when something is wrong.

A task is a branch in a warm worktree; the branch proves itself there; main only fast-forwards and is never built. Normal numbers are seconds for an incremental build, minutes for the default tests and the gate; much past the cost table means something is broken. The cost table's numbers come from one 16-thread laptop (30 GB RAM); another machine scales them by a constant and load by 2-5x, but the ratios between rows hold. Process around this (worker, reviewer, release checks, watchdog): notes/coordination.md.

## Layout
- `core/` holds the library crates in unprefixed directories with prefixed package names (`core/node` is osis-node); `core/test/` the test infrastructure (sim, vectors, fuzz, crdt-model, roles-model, tla); `libs/` what some but not all users of osis want (`libs/chat` osis-chat, core; `libs/kit` osis-kit, GUI); `schema/` the first-party schema files; `cli/` the CLI. Further projects (tools) are top-level directories depending only on the `osis` crate.
- **One workspace**, root `Cargo.toml`: one `Cargo.lock`, one `deny.toml`, one `target/`, one copy of osis. `default-members` is core (everything but the GUI), so a bare `cargo build`/`test`/`clippy` never compiles the GUI. The GUI (`libs/kit/` osis-kit, `app/` osis-app, `app/android` osis-android) builds only when named: `cargo test -p osis-kit -p osis-app`, `cargo clippy -p osis-kit -p osis-app -p osis-android --all-targets -- -D warnings`, `cargo run -p osis-app -- DIR`; `--workspace` means core and GUI together. Its `[patch]` entries (libs/kit/patches/, vendored, excluded from the members) are in the root manifest. The GUI build reuses core's artifacts for every core crate (Feature unification); its own first build is about 3 min / 1250 CPU-s at load 25 (wgpu, Vello, winit). Core depends on nothing in it; it depends on `osis`, `osis-schema` and `osis-chat` only.

## Worktrees
`wt` (reasonable-rust-builds plugin): `wt claim <branch> [<base>]` prints a task worktree `.worktrees/wt<N>` (gitignored; tools that scan sources use explicit roots and never see it). Each has its own in-tree `target/`, kept between tasks, so a task's first build recompiles only what its branch changed. `wt release` when the branch is committed (prunes the target, then detaches HEAD), `wt list`, `wt trim [keep]`. Two stay warm per box; more are made when more agents run and trimmed after. A new worktree builds cold once (about 80 s).
- Never share a `target/` between checkouts (`CARGO_TARGET_DIR`): cargo keys artifacts without the path and judges freshness by mtime, so one tree read as fresh with the other tree's code inside (measured). Never build in the main checkout.
- Hardlink-seeded worktrees and one shared build checkout behind a lock were both tried and dropped: a seed from a stale main rebuilt everything, and a shared checkout must stay locked through test runs (tests read fixtures through the manifest dir baked in at compile time), serializing everyone.

## One profile, fixed command forms
Dev profile for all branch work (Cargo.toml): workspace crates `opt-level = 1`, `debug = "line-tables-only"`, incremental, `lto = "off"` (no thin-local LTO: slightly slower code, Tess's call); dependencies and osis-crypto `opt-level = 2`, no debuginfo. Build-time code (`[profile.dev.build-override]`) runs without debug assertions; that setting exists to keep build-time units apart (Feature unification). No `split-debuginfo`: its per-build `.dwo` files accumulate (2.7-5 GB per worktree). Debug sections are zlib-compressed at link time (`.cargo/config.toml`): test binaries about 0.65 GB instead of 1.7 and backtraces keep file:line; Rust's symbolizer does not read zstd. Every new combination of profile, features, `RUSTFLAGS`, `CARGO_INCREMENTAL` or target dir is another full artifact set (a `-p` subset is not: Feature unification), so there are exactly these forms:
- the default tests: `cargo test --no-fail-fast` (without it cargo stops at the first failing test binary and hides every later crate's failures behind another 5-10 min run; same artifacts); `--no-run` to build. `cargo build --all-targets` and `cargo run --bin <name>` reuse the artifacts.
- one crate: `cargo test -p <crate>`, narrowed with `--test it <module>::` and name filters after `--`. Never `--test it <filter>` without `-p`: it prints a `0 passed` line for every other crate's `it`, hiding the one that ran.
- lint: `cargo clippy --all-targets -- -D warnings`.
- networking (by hand): `tools/heavy cargo test --tests -- --ignored driver:: runtime:: quic relay lan --skip repro_`, always filtered (unfiltered it runs every ignored test in dev; a `repro_` fails by design and would stop cargo before the later crates).
- sim: `cargo run --bin sim-sweep -- --seeds N --budget-secs T`.
- a property or by-hand test by name: `cargo test -p <crate> --test it -- --ignored <name>` (or `cargo test --tests -- --ignored <name>`: `--tests` skips the doctests an unnarrowed run builds and runs after). Every property at once (release checks): `OSIS_FULL=1 PROPTEST_CASES=256 cargo test -- --include-ignored --skip sweep --skip repro_ --skip memory:: --skip multi_gb_value_streams`.
- release: never inside a task (scaling is checked by counting work in the default tests, notes/coordination.md Testing; one release bench compiled 13+ min before it was stopped). Memory checks (`memory::`, `multi_gb_value_streams`) and `cargo bench` are by hand: the coordinator runs `cargo test --release -p <crate> --test it -- --ignored <filter>` alone, keeping `target/release`.
- old vs new: `tools/bin-at REV OUT [--release] [-p CRATE] [--test NAME | --lib CRATE] [--patch FILE]... [--take PATH]...` copies REV's test binary (default osis-node `it`, dev; `--lib osis-engine`: that lib's unit-test binary, run from `core/engine`) to OUT, built in your worktree. A new test against an old REV: `--take core/node/tests/it/x.rs` (root-relative) or `--patch FILE` (a `git diff`), applied on REV and undone after. Needs a clean tree (wip-commit); checks REV out detached, builds, checks your branch out again (also on failure); the next build recompiles what REV changed back (about a minute for an osis-engine change at load). The binary keeps your worktree's manifest dirs, so a test reading fixtures reads the checked-out ones. Refuses the main checkout. Then run old and new side by side, or under `tools/icount` (notes/testing.md).
- Harness env vars (`OSIS_*_START`/`_SEEDS`, `OSIS_PERM_SEED`, ...) are read through `osis_base::testenv`, which panics on an unparsable value, zero seeds, or any set `OSIS_*` variable not in core/base/testenv-known.txt (policy.py keeps that list equal to what the sources name; add a new variable there; read at run time, so adding one rebuilds nothing). A set variable and an overridden range are echoed past libtest's capture, so they show on a passing run; other output (per-seed lines) needs `-- --nocapture`. Seed-ranged harnesses run on `testenv::run_seeds` (notes/testing.md Seed runners: a thread per core, `OSIS_SEED_THREADS`; every failing and hung seed reported with its replay line; a seed past `OSIS_SEED_TIMEOUT_SECS` CPU-seconds, default 600, is marked hung). Only a harness's `#[ignore]` `_large` twin reads its range; the default test runs fixed seeds.
- Agent shells run at nice 12 (`ps -o ni,cls -p $$`), so their builds and tests yield to anything at nice 0.
- Jobs: on a shared box cap jobs per invocation at the physical core count in the user-level `~/.cargo/config.toml` (`[build] jobs = N`; it changes no artifacts), never per command: three invocations each asking for 16 jobs on 8 cores reached load 60-80.
- Scheduler: `system76-scheduler` (Pop!_OS, `com.system76.Scheduler.service`) must be off (`sudo systemctl disable --now` and `mask` it; an OS upgrade re-enabled it once). Its `batch` rule matches the names `cargo`, `rustc`, `ld`, `lld`, `make` at its 60 s refresh and sets SCHED_IDLE, nice 19, idle I/O; every process that cargo spawns after inherits it (test binaries come out nice 19). A SCHED_IDLE task runs only on a core no normal task wants, so any cargo run that outlives a refresh then crawls beside any other test run, TLC or sweep: one osis-engine lib rebuild took 28 s (60 CPU-s) caught early and 330 s (62 CPU-s) caught, its threads 25 s running and 528 s runnable-waiting; the same work, 12x the wall. Builds under 0-60 s escape, which is why short builds look normal while long ones take 10-30x. Unprivileged processes cannot leave SCHED_IDLE (RLIMIT_NICE 0), and `nice`/`chrt` wrappers don't help (they exec, so the daemon's `descends=` exceptions never match). Check: `ps -eo pid,cls,ni,comm | grep -E 'cargo|rustc'` shows `IDL`; the gate warns while the service runs.

## Merge gate
`tools/gate.sh [--all] [--base REV] [--plan]`, in the worktree after `git rebase main` (or `git fetch && git rebase origin/main`), without a pipe and after reading the rebase's result. One command, one hold of the heavy lock. Steps, failing fast, each printing its wall time and CPU-s (compare CPU-s, wall follows load):
1. Instant checks: the lockfile is current (`cargo metadata --locked`, about 1 s; not `--offline`, where an uncached crate fails like a stale lock; the failure prints the refresh command), `tools/policy.py`, the tools' own tests (`tools/gate_select_test.sh`, `tools/test_select_test.py`), `tools/spec_map.py --uncited` and `--gaps`.
2. The selection: `tools/test_select.py` on the branch's diff (every crate on main or with `--all`) at one random offset, printed with its commands (notes/testing.md, The gate's selection).
3. Lints: core clippy, then the GUI's (Components below).
4. Builds, unlocked: `cargo test --no-run` and the selection's test binaries and `sim-sweep`, each with its run's own cargo arguments, so the hold builds nothing (doctests still compile inside it, at run time).
5. The rest unlocked: the unification check when a `Cargo.toml` (any), `Cargo.lock` or `.cargo/` changed since the merge base (`--plan` says `unify=1`), the schema check, `cargo deny check` and core's bans alone.
6. The tests, in one `tools/heavy` hold: the default tests (`cargo test --locked --no-fail-fast`), then the selected properties, then the selected sim scenarios at 15 seeds. Each prints its own wall and CPU-s and its time-limit line, and the hold's after (Time limits below; every other step checks its own too).
7. The GUI tests, when libs/kit/ or app/ changed.

`--base REV` compares against REV instead of the merge base; `--plan` prints the step selection (`core`, `gui`, `unify`, `select=all|diff|none`; tested on fabricated histories by `tools/gate_select_test.sh`, a gate step). Then the coordinator runs `git checkout main && git merge --ff-only <branch> && git push`. Task branches are never pushed; history is linear. The generated notes/testing-map.md is gitignored.

## Components pay for themselves
Iterating on one project must not run the others' tests or checks. The gate selects steps by what the branch touched:
- only libs/kit/ or app/: the GUI steps alone (GUI clippy and test, the unification check if a manifest changed, deny).
- other paths all Markdown under spec/, notes/ or issues/ (`--plan` says `core=docs`, `select=none`): only the instant Python checks, no Rust build, plus the GUI steps if libs/kit/ or app/ changed. A Rust line reading or including a path there (`git grep` in gate.sh, one-line calls only) sends the full gate and names it.
- anything else: the core steps, with the GUI's clippy (an osis API change must not silently break the app), plus the GUI tests if libs/kit/ or app/ changed; everything on main or with `--all`.
- GUI lint in core gates: `cargo clippy -p osis-kit -p osis-app -p osis-android --all-targets` right after core's clippy re-lints only kit and app, about 3 s / 5 CPU-s after an osis-engine edit at load 25 (a `cargo check` instead re-checks every osis crate in check mode, a unit set apart from clippy's: 5-18 s). Cold (a worktree that never linted the GUI) it checks the GUI stack once: about 95 s / 290 CPU-s at load 30.
policy.py covers every member (vendored libs/kit/patches/ skipped); spec_map.py core/ and cli/ sources only. A new project extends the same pattern, with its own properties and release checks (notes/coordination.md).

## Feature unification
A package's features are the union of what everything in the build asks for, so `-p X` resolves differently from `--workspace` unless every crate's features are the same in both, and then rebuilds part of the tree as a second artifact set. cargo's `resolver.feature-unification = "workspace"` would do it outright but is unstable. The rules that keep it selection-invariant:
- No feature a member turns on that another build of the crate leaves off: optional features only for the default `driver` nobody turns off. QUIC, the LAN loop, redb and `OsRng` are unconditional; osis-node's normal dependency on osis-host takes its defaults, so its `driver` is on in every build.
- Third-party features go in `[workspace.dependencies]`, the same for every member (tokio's set, blake3 `zeroize`, ed25519-dalek `hazmat`), not per member; dev-dependencies add no features to a normal dependency.
- Pins: where a crate higher up enables features on a shared low dependency (quinn-proto: rand's defaults; libcrux-platform: libc's; x25519-dalek: zeroize's derive; crypto: blake3 `zeroize`; the GUI stack: bitflags `serde`, num-traits `libm`, tracing and tracing-core defaults), osis-base lists that dependency at the workspace's features (crdt-model, which has no osis-base, as dev-dependencies), unused. The reverse for the GUI: osis-kit pins regex-syntax at proptest's defaults.
- Build-time units never share a unit with run-time ones: `[profile.dev.build-override]` gives them a profile of their own (any field the dependency profile leaves unset; `debug-assertions = false`). Without it, cargo merges a build-time and a run-time unit of the same crate when their profiles and features match, and the merged unit takes the run-time `lto = "off"` (`-C lto=off`) where a build-time-only one takes none; which crates merge depends on the selection (unicode-ident is a run-time dependency of naga, so in GUI builds only), and every build-time unit above it differs, osis-schema included, so a GUI build would compile every osis crate a second time. Dropping `lto = "off"` would also do (it is Tess's call); `[profile.dev.package."*"]` and `build-override` cannot set `lto`, and a pin of unicode-ident would hold only until the next such crate. Its cost: a crate used on both sides is built once per side, about 20 small ones in core builds (osis-schema's dependencies: blake3, rand, libc, tracing, serde_core, ...), once per target.
- The GUI is in the same rule: a GUI build compiles the GUI crates only, never a second osis. The pins cost core builds `serde_core`, `libm` and `tracing-attributes`, a few seconds once.
- Checked by the gate's `unification_check` (only when a manifest, the lock or `.cargo/` changed: nothing else changes resolution): after `cargo build --workspace --all-targets` (GUI included), `cargo build --all-targets` (the default members) and `cargo build -p <member> --all-targets` for every member compile nothing (about 15-60 s when it holds). An offender: diff `cargo tree -e normal,build,dev --prefix none -f '{p}|{f}'` with `--workspace` and with `-p X` (or bare); fix at the source by the rules above. Same features but a different fingerprint `profile` hash is a per-unit profile difference (LTO, as above): compare the unit's rustc line in `cargo build -v` of each selection.

## Heavy lock
`tools/heavy <cmd...>` runs a command under the box-wide lock (`$XDG_RUNTIME_DIR/osis-gate.lock`, flock): the gate's tests (one hold per gate, after every build, Merge gate above), release checks, by-hand property and sim runs at size, TLC and roles-model runs. Builds and single-crate test runs stay unlocked (bursty, partly using the cores). The command sees `HEAVY_HELD=1`: a `tools/heavy` inside a hold refuses (flock is per open file, so it would wait on itself), and the gate's internal `--held` runner refuses without it. It logs each run to `~/.cache/osis/heavy.log` (JSON lines: who, command, wait, hold, the command's CPU-s, the box's /proc/stat counters at each event and every 10 s held). `tools/heavy --report [--since HOURS]` lists runs (own and box utilization while held, the box while each waited, the box with the lock held or free); `tools/agent-times.py` adds each agent's lock wait, hold, CPU-s and cores used.

## Time limits
Every timed run has a CPU limit (tight: other work on the box barely moves CPU-s) and a wall limit (looser: it also catches waiting, idle cores, a demoted process), as multiples of the box's base unit `u` (notes/coordination.md, Time limits). `u` is the CPU-s of one fixed work quantum of `tools/baseunit.c` (hashing, random access over 32 MB, allocation, sorting) with every hardware thread busy: a CPU limit is `k u`, a wall limit `k u 16/threads` (the 16 quanta spread over the box's threads; on ostrich `u` seconds). Measure a box's with `tools/heavy tools/limits.py unit` (median of 5, a few seconds; it varies 2-4% with load) and add its row. The other rows are what a run takes on ostrich now plus a little, except `gate` and `gate.hold`: Tess's 5-minute cap, which every every-crate gate exceeds about 4x until issues/gate-five-minutes.md is done. ## Footguns
- Waiting: a command that may pass a few minutes runs with `run_in_background`, awaited with `claudewait ID`. Never a shell wait loop, never `timeout` around any cargo command (it kills a test run with a green-looking log, and a build killed mid-link leaves the crate unable to link until `cargo clean -p <crate>`). A foreground call past 120 s moves to the background and its later steps keep running: keep edits and reverts out of a call that may run long.
- Exit codes: `cmd > log; echo exit $?` ends with the echo's status, and a pipe through `tee`/`grep`/`tail` reports the pipe's: end a wrapper with the command's code and read `test result` / `== gate passed` lines. A background run whose `> $D/x.log` names a dir not made yet fails at once: make the dir in an earlier call. `git rebase --exec` runs under dash (no `${PIPESTATUS}`).
- Runs that test nothing and say ok: a misspelled `--exact` name or seed env var, `--ignored --exact` on a test that is not ignored, `OSIS_SIM_ONLY=` set empty (read the `N runs` line). Check for `1 passed` and the printed seed range; oracle names carry a `_spec_*` suffix (`--list --ignored` shows them). Several libtest filters go after `--`. An `#[ignore] repro_` test fails by design: read test names, not the exit code.
- libtest captures a passing test's output, threads it spawns included: an `eprintln!` probe shows nothing without `-- --nocapture` (read as "never reached" several times).
- `cargo clippy` prints `Compiling` (not `Checking`) for osis-engine, osis, osis-chat, osis-kit and osis-app after an edit that reaches their build scripts: clippy compiles a workspace member's build script and its build-dependencies (osis-schema, osis-base) with clippy-driver, so they are units apart from `cargo build`'s (own binary, own `OUT_DIR`) and run again in clippy. Once per edit, a few CPU-s; it does not repeat, and it is how build.rs gets linted.
- `pkill -f`/`pgrep -f` match the Bash tool's own `bash -c` wrapper and kill the caller: stop your own background task with TaskStop.
- Editing sources (or `git show rev:path > path`) while a background cargo runs builds the half-edited tree: for an oracle chain build once and run a copy of the test binary. `cargo test -p <crate> --test it --no-run` prints the `Executable` path, relative to the worktree root: copy from the root and `test -x` the copy before starting a chain. `--message-format=json` lists sim-sweep's executable too: pick `/deps/it-`.
- `git checkout <file>` to undo a temporary edit drops the file's uncommitted work: wip-commit first. Squash with `git reset --soft $(git merge-base HEAD main)`: `reset --soft main` after main moved stages a revert of main's newer commits. `git diff main` compares with main's tip: use `git diff $(git merge-base HEAD main)`.
- A build stopped partway can leave incremental state that fails the next link (`rust-lld: undefined hidden symbol anon.*`): `cargo clean -p <crate>` for the crate whose rlib the error names (deleting only its `target/debug/incremental/` dirs left the bad rlib in place), then rebuild.
- A test that panics on an unknown `OSIS_*` variable makes proptest save `proptest-regressions/*.txt`: check `git status` before committing. `.cargo/config.toml` sets `PROPTEST_CASES=32`, which overrides a test's own `cases:`: deep runs pass `PROPTEST_CASES=N`.
- `grep` in agent shells may be Claude Code's ugrep shim, which rejects bounded repeats (`.\{0,150\}`): use `command grep` or python.
- A load-dependent flake: pin the test to few cores (`taskset -c 0-1 <copied binary> ...`), don't spin CPU burners (they load every other agent's gate).
- Harnesses: `osis_sim::world::World::pump` panics after `STORM` (5000) rounds without settling, listing what the storm carries. Node net harness: `set_online(n, false)` drops n's `Dial` actions, so it never redials (to cut one host off use `net.blocked.insert((n, s))` with `net.drop_link(n, s)`); `set_online(n, true)` then `run()` does not reconnect until a retry tick: `advance` tens of seconds; `store.put`/`plant_inbox` notify no subscriber and skip the host's prefix check (go offline, then reconnect, or the test passes for nothing); `Net` auto-accepts requests; a 1 h `tick` closes the connection by ping timeout; `hold_blobs` holds listing pages naming the blob too; the first `advance` after a clock jump only clamps; a role commit past `grant`'s refusal needs `m.unchecked` plus `skip_writer_rules`. osis-host tests' `World::connect` keys overflow past 31 clients (`0xe0 + c as u8`).
- Permission prompts stall unattended agents: stay inside your worktree and your scratch dir, absolute paths instead of `cd` in compound commands, no sudo, network fetches, writes outside the repo or scratchpad, killing processes you did not start, or `git worktree add` (use `wt`). Write files with the Write tool, not heredocs plus `chmod`/`rm`; never `rm` in the scratchpad (use fresh names). If a step needs approval, do it another way.

## Scripted renames
Every reviewer of a scripted rename sweep found over-matches the worker's old-word hunt missed. Before running: list files holding both the old and the new word (shadowing, colliding names); protect third-party and other-sense names as exact tokens in every case (`x`, `X`, `X_Y`) with word boundaries (`/members(?!\w)`, not a prefix); filter paths with `git ls-files | grep -v`, not `':!path'` pathspecs (one silently matched nothing); print each rule's hit count, every rule must hit. After: hunt the new word as well as the old (`REHOLDERED`), census short forms (`sv`, `srv`), read the token pair table `tools/rename-table [REV | A..B | -]` (no argument: merge base to working tree; `count  old -> new  first-file`); same-token sense errors still need reading.
- TLA junction lists are indentation-sensitive: realign `/\` bullets and compare `run.sh <module>` state counts.

## Disk
- `wt release` prunes `<wt>/target` to what is in use: if anything was used since the previous release it runs `.claude/wt-mark` (every standard command; the GUI's only where the GUI was built before, so marking never builds it cold; add a new standard command there too), then deletes every unit not used since, and in `incremental/` keeps the newest session per dir and drops dead dirs beyond the live units naming that crate. No cold builds result (an osis-engine edit after a release costs the warm 7 s). Idle targets and profiles are left alone.
- It needs a filesystem that records access times: on a `noatime` mount it prints `wt: this filesystem doesn't record access times (noatime): targets not pruned` and targets only grow (14-15 GB in busy worktrees, 22-30 GB after crate-graph changes leave dead `incremental/` dirs). `relatime` works (`findmnt -T .`).
- A `libs/kit/target` in a worktree is dead (no workspace is rooted there; wt never prunes it, 1-4.5 GB): delete it once that worktree's branch has the one workspace.
- `tools/prune-incremental.sh [hours]` removes incremental sessions untouched for that long from claimed worktrees' targets.
- Bound: a worktree over 15 GB gets a cleanup between rounds: on a worktree where no cargo runs, delete every incremental session but the newest per crate dir (what rustc does next anyway, no rebuild): `python3 -c 'import glob,os,shutil,sys; [shutil.rmtree(s) for d in glob.glob(sys.argv[1]+"/target/*/incremental/*/") for s in sorted((x for x in glob.glob(d+"s-*") if os.path.isdir(x)),key=os.path.getmtime)[:-1]]' .worktrees/wtN`, plus `tools/prune-incremental.sh` for dead dirs; past 20 GB delete the target. `wt trim` is not the cure: the next claim builds cold (a 13-minute default-test run once).
- A full disk reads as a compile error (`failed to write query cache`, `failed to parse process output`): `df` before believing a build failure. A `du` of `/home/ai/*` takes over 10 minutes: use `df` and the worktrees only.

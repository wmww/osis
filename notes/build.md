# Build, test and merge workflow
> Summary: How a task goes from branch to main (warm task worktrees, one dev profile, gate in the worktree, fast-forward main), the command forms, the footguns, disk upkeep, and what builds and tests should cost so you can tell when something is wrong.

A task is a branch in a warm worktree; the branch proves itself there; main only fast-forwards and is never built. Normal numbers are seconds for an incremental build, a few minutes for tier 1 and the gate; tens of minutes means something is broken. The cost table's numbers come from one 16-thread laptop (30 GB RAM); another machine scales them by a constant and load by 2-5x, but the ratios between rows hold. Process around this (worker, reviewer, periodic checks, watchdog): notes/coordination.md.

## Layout
- `core/` holds the library crates in unprefixed directories with prefixed package names (`core/node` is osis-node); `core/test/` the test infrastructure (sim, vectors, fuzz, crdt-model, roles-model, tla); `libs/` what some but not all users of osis want (`libs/chat` osis-chat, a core-workspace member; `libs/kit` osis-kit); `schema/` the first-party schema files; `cli/` the CLI. Further projects (tools) are top-level directories depending only on the `osis` crate.
- **GUI workspace**: `libs/kit/` (osis-kit) and `app/` (osis-app) are their own Cargo workspace, root manifest `libs/kit/Cargo.toml` (members `.`, `../../app` and `../../app/android`, which points back with `package.workspace`; `default-members` both, so a bare `cargo build` in libs/kit/ builds the app too), with its own `Cargo.lock`, `deny.toml`, `[patch]` table and target dir `libs/kit/target/`. The root workspace excludes both. Commands run in libs/kit/: `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo run --bin osis-app -- DIR`; `python3 tools/policy.py kit` from the root. First build about 1.5 min (wgpu, Vello, winit); the osis crates compile a second time there (another lock, other features): the price of keeping the GUI stack out of core's builds. Core depends on nothing in it; it depends on `osis` and `osis-schema` by path only.

## Worktrees
`wt` (reasonable-rust-builds plugin): `wt claim <branch> [<base>]` prints a task worktree `.worktrees/wt<N>` (gitignored; tools that scan sources use explicit roots and never see it). Each has its own in-tree `target/`, kept between tasks, so a task's first build recompiles only what its branch changed. `wt release` when the branch is committed (prunes the target, then detaches HEAD), `wt list`, `wt trim [keep]`. Two stay warm per box; more are made when more agents run and trimmed after. A new worktree builds cold once (about 80 s, 3.6 min through clippy-net).
- Never share a `target/` between checkouts (`CARGO_TARGET_DIR`): cargo keys artifacts without the path and judges freshness by mtime, so one tree read as fresh with the other tree's code inside (measured). Never build in the main checkout.
- Hardlink-seeded worktrees and one shared build checkout behind a lock were both tried and dropped: a seed from a stale main rebuilt everything, and a shared checkout must stay locked through test runs (tests read fixtures through the manifest dir baked in at compile time), serializing everyone.

## One profile, fixed command forms
Dev profile for all per-branch work (Cargo.toml): workspace crates `opt-level = 1`, `debug = "line-tables-only"`, incremental; dependencies and osis-crypto `opt-level = 2`, no debuginfo. No `split-debuginfo`: its per-build `.dwo` files accumulate (2.7-5 GB per worktree). Debug sections are zlib-compressed at link time (`.cargo/config.toml`): test binaries about 0.65 GB instead of 1.7 and backtraces keep file:line; Rust's symbolizer does not read zstd. Every new combination of profile, features, `RUSTFLAGS`, `CARGO_INCREMENTAL` or target dir is another full artifact set (a `-p` subset is not: Feature unification), so there are exactly these forms:
- tier 1: `cargo test --workspace --no-fail-fast` in the dev loop (without it cargo stops at the first failing test binary and hides every later crate's failures behind another 5-10 min run; same artifacts); `--no-run` to build. `cargo build --workspace --all-targets` and `cargo run --bin <name>` reuse the artifacts.
- one crate: `cargo test -p <crate>`, narrowed with `--test it <module>::` and name filters after `--`. Never `--workspace --test it <filter>`: it prints a `0 passed` line for every other crate's `it`, hiding the one that ran.
- lint: `cargo clippy --workspace --all-targets -- -D warnings` and `cargo clippy-net -- -D warnings` (the one networking feature set, 73 extra crates built once per worktree).
- networking tier 2: `cargo test-net -- --ignored driver:: runtime:: quic relay lan`, always filtered (unfiltered it runs every ignored test in dev, timing budgets included).
- sim: `cargo run --bin sim-sweep -- --seeds N --budget-secs T`.
- tier 2 by name: `cargo test -p <crate> --test it -- --ignored <name>` (or `cargo test --workspace --tests -- --ignored <name>`: `--tests` skips the doctests an unnarrowed run builds and runs after). The whole set: `PROPTEST_CASES=256 cargo test --workspace -- --include-ignored --skip scale:: --skip bench:: --skip budget --skip sweep --skip repro_`.
- release, timing only (`scale::`, `bench::`, `budget*`, cost repros in issues/): never inside a task (a task checks scaling by counting work in tier 1, notes/coordination.md Testing; one release bench compiled 13+ min before it was stopped). When a measured budget is in question the coordinator runs `cargo test --release -p <crate> --test it -- --ignored <filter>` by hand, alone, keeping `target/release`.
- old vs new: `tools/bin-at REV OUT [--release] [-p CRATE] [--test NAME | --lib CRATE] [--patch FILE]... [--take PATH]...` copies REV's test binary (default osis-node `it`, dev; `--lib osis-engine`: that lib's unit-test binary, run from `core/engine`) to OUT, built in your worktree. A new test against an old REV: `--take core/node/tests/it/x.rs` (root-relative) or `--patch FILE` (a `git diff`), applied on REV and undone after. Needs a clean tree (wip-commit); checks REV out detached, builds, checks your branch out again (also on failure); the next build recompiles what REV changed back (about a minute for an osis-engine change at load). The binary keeps your worktree's manifest dirs, so a test reading fixtures reads the checked-out ones. Refuses the main checkout. Then run old and new side by side, or under `tools/icount` (notes/testing.md).
- Harness env vars (`OSIS_*_START`/`_SEEDS`, `OSIS_PERM_SEED`, ...) are read through `osis_base::testenv`, which panics on an unparsable value, zero seeds, or any set `OSIS_*` variable not in core/base/testenv-known.txt (policy.py keeps that list equal to what the sources name; add a new variable there; read at run time, so adding one rebuilds nothing). A set variable and an overridden range are echoed past libtest's capture, so they show on a passing run; other output (per-seed lines) needs `-- --nocapture`. Seed-ranged harnesses run on `testenv::run_seeds` (notes/testing.md Seed runners: a thread per core, `OSIS_SEED_THREADS`; every failing and hung seed reported with its replay line; a seed past `OSIS_SEED_TIMEOUT_SECS` CPU-seconds, default 600, is marked hung). Only a harness's `#[ignore]` `_large` twin reads its range; the tier-1 test runs fixed seeds.
- Jobs: on a shared box cap jobs per invocation at the physical core count in the user-level `~/.cargo/config.toml` (`[build] jobs = N`; it changes no artifacts), never per command: three invocations each asking for 16 jobs on 8 cores reached load 60-80. If long cargo runs crawl at low load, check that nothing puts them in SCHED_IDLE (`chrt -p <pid>`; `system76-scheduler` did, and Tess disabled it).

## Merge gate
`tools/gate.sh [--all] [--sweep-seeds N] [--base REV] [--plan]`, in the worktree after `git rebase main` (or `git fetch && git rebase origin/main`), without a pipe and after reading the rebase's result. First, every run: both workspaces' lockfiles are current (`cargo metadata --locked` in the root and libs/kit/, about 1 s; not `--offline`, where an uncached crate fails like a stale lock; the failure prints the refresh command). Core steps: `cargo test --workspace --locked`, the unification check, both clippy runs, `tools/policy.py`, `tools/spec_map.py --uncited` and `--gaps`, `cargo deny check`, then the 5-seed dev sim sweep (every scenario; seed breadth is a periodic check) when the branch touches `core/test/sim/`, osis-engine, -node, -perm, -crdt, -store, -crypto or Cargo.toml/lock since its merge base (`--sweep-seeds N` forces, 0 skips). `--base REV` compares against REV instead of the merge base; `--plan` prints the selection (tested on fabricated histories by `tools/gate_select_test.sh`, a gate step). Each step prints wall time and CPU-s; compare CPU-s, wall follows load. Then the coordinator runs `git checkout main && git merge --ff-only <branch> && git push`. Task branches are never pushed; history is linear. The generated notes/testing-map.md is gitignored.

## Components pay for themselves
Iterating on one project must not run the others' tests or checks. The gate selects steps by what the branch touched:
- only libs/kit/ or app/: the GUI steps alone (`policy.py libs/kit`, GUI test, clippy, deny in libs/kit/).
- other paths all Markdown under spec/, notes/ or issues/ (`--plan` says `core=docs`): only the instant Python checks, no Rust build, plus the GUI steps if libs/kit/ or app/ changed. A Rust line reading or including a path there (`git grep` in gate.sh, one-line calls only) sends the full gate and names it.
- anything else: the core steps plus `cargo check --workspace --all-targets` of the GUI workspace (an osis API change must not silently break the app); everything on main or with `--all`.
policy.py and spec_map.py look at the core workspace (spec_map: core/ and cli/ sources only); policy.py takes a workspace dir for the GUI one and skips vendored `patches/`. A new project extends the same pattern, with its own per-branch oracles and periodic checks (notes/coordination.md).

## Feature unification
A package's features are the union of what everything in the build asks for, so `-p X` resolves differently from `--workspace` unless every crate's features are the same in both, and then rebuilds part of the tree as a second artifact set. cargo's `resolver.feature-unification = "workspace"` would do it outright but is unstable. The rules that keep it selection-invariant:
- No feature a member turns on that another build of the crate leaves off: optional features only for the networking opt-in set (osis/osis-node/osis-transport `lan`, through `test-net`/`clippy-net`) and the default `driver` nobody turns off. QUIC, redb and `OsRng` are unconditional; osis-node's normal dependency on osis-host takes its defaults, so its `driver` is on in every build.
- Third-party features go in `[workspace.dependencies]`, the same for every member (tokio's set, blake3 `zeroize`, ed25519-dalek `hazmat`), not per member; dev-dependencies add no features to a normal dependency.
- Pins: where a crate higher up enables features on a shared low dependency (quinn-proto: rand's defaults; libcrux-platform: libc's; x25519-dalek: zeroize's derive; crypto: blake3 `zeroize`), osis-base lists that dependency at the workspace's features (crdt-model, which has no osis-base, as dev-dependencies), unused.
- Checked by the gate's `unification_check`: after the whole-workspace build, `cargo build -p <member> --all-targets` for every member compiles nothing (a few seconds when it holds). An offender: diff `cargo tree -e normal,build,dev --prefix none -f '{p}|{f}'` with `--workspace` and with `-p X`; fix at the source by the rules above.

## Footguns
- Waiting: a command that may pass a few minutes runs with `run_in_background`, awaited with `claudewait ID`. Never a shell wait loop, never `timeout` around any cargo command (it kills a test run with a green-looking log, and a build killed mid-link leaves the crate unable to link until `cargo clean -p <crate>`). A foreground call past 120 s moves to the background and its later steps keep running: keep edits and reverts out of a call that may run long.
- Exit codes: `cmd > log; echo exit $?` ends with the echo's status, and a pipe through `tee`/`grep`/`tail` reports the pipe's: end a wrapper with the command's code and read `test result` / `== gate passed` lines. A background run whose `> $D/x.log` names a dir not made yet fails at once: make the dir in an earlier call. `git rebase --exec` runs under dash (no `${PIPESTATUS}`).
- Runs that test nothing and say ok: a misspelled `--exact` name or seed env var, `--ignored --exact` on a test that is not ignored, `OSIS_SIM_ONLY=` set empty (read the `N runs` line). Check for `1 passed` and the printed seed range; oracle names carry a `_spec_*` suffix (`--list --ignored` shows them). Several libtest filters go after `--`. `-- --ignored parts::` also runs a known always-failing hole (`parts::repro_body_class_move_drops_spec_commits_5`): read test names, not the exit code.
- libtest captures a passing test's output, threads it spawns included: an `eprintln!` probe shows nothing without `-- --nocapture` (read as "never reached" several times).
- A new or changed dependency of a core crate leaves libs/kit/Cargo.lock stale too (the gate's first step says so): refresh it with `cargo metadata --offline --format-version 1 >/dev/null` in libs/kit/ and commit it with the change.
- `pkill -f`/`pgrep -f` match the Bash tool's own `bash -c` wrapper and kill the caller: stop your own background task with TaskStop.
- Editing sources (or `git show rev:path > path`) while a background cargo runs builds the half-edited tree: for an oracle chain build once and run a copy of the test binary. `cargo test -p <crate> --test it --no-run` prints the `Executable` path, relative to the worktree root: copy from the root and `test -x` the copy before starting a chain. `--message-format=json` lists sim-sweep's executable too: pick `/deps/it-`.
- `git checkout <file>` to undo a temporary edit drops the file's uncommitted work: wip-commit first. Squash with `git reset --soft $(git merge-base HEAD main)`: `reset --soft main` after main moved stages a revert of main's newer commits. `git diff main` compares with main's tip: use `git diff $(git merge-base HEAD main)`.
- A build stopped partway can leave incremental state that fails the next link (`rust-lld: undefined hidden symbol anon.*`): `cargo clean -p <crate>` for the crate whose rlib the error names (deleting only its `target/debug/incremental/` dirs left the bad rlib in place), then rebuild.
- A test that panics on an unknown `OSIS_*` variable makes proptest save `proptest-regressions/*.txt`: check `git status` before committing. `.cargo/config.toml` sets `PROPTEST_CASES=32`, which overrides a test's own `cases:`: deep runs pass `PROPTEST_CASES=N`.
- `grep` in agent shells may be Claude Code's ugrep shim, which rejects bounded repeats (`.\{0,150\}`): use `command grep` or python.
- A load-dependent flake: pin the test to few cores (`taskset -c 0-1 <copied binary> ...`), don't spin CPU burners (they load every other agent's gate).
- Harnesses: `osis_sim::world::World::pump` panics after `STORM` (5000) rounds without settling, listing what the storm carries. Node net harness: `set_online(n, false)` drops n's `Dial` actions, so it never redials (to cut one host off use `net.blocked.insert((n, s))` with `net.drop_link(n, s)`); `set_online(n, true)` then `run()` does not reconnect until a retry tick: `advance` tens of seconds; `store.put`/`plant_inbox` notify no subscriber and skip the host's prefix check (go offline, then reconnect, or the test passes for nothing); `Net` auto-accepts requests; a 1 h `tick` closes the connection by ping timeout; `hold_blobs` holds listing pages naming the blob too; the first `advance` after a clock jump only clamps; a role commit past `grant`'s refusal needs `m.unchecked` plus `skip_writer_rules`. osis-host tests' `World::connect` keys overflow past 31 clients (`0xe0 + c as u8`).
- Permission prompts stall unattended agents: stay inside your worktree and your scratch dir, absolute paths instead of `cd` in compound commands, no sudo, network fetches, writes outside the repo or scratchpad, killing processes you did not start, or `git worktree add` (use `wt`). Write files with the Write tool, not heredocs plus `chmod`/`rm`; never `rm` in the scratchpad (use fresh names). If a step needs approval, do it another way.

## Scripted renames
Every reviewer of a scripted rename sweep found over-matches the worker's old-word hunt missed. Before running: list files holding both the old and the new word (shadowing, colliding names); protect third-party and other-sense names as exact tokens in every case (`x`, `X`, `X_Y`) with word boundaries (`/members(?!\w)`, not a prefix); filter paths with `git ls-files | grep -v`, not `':!path'` pathspecs (one silently matched nothing); print each rule's hit count, every rule must hit. After: hunt the new word as well as the old (`REHOLDERED`), census short forms (`sv`, `srv`), read the token pair table `tools/rename-table [REV | A..B | -]` (no argument: merge base to working tree; `count  old -> new  first-file`); same-token sense errors still need reading.
- TLA junction lists are indentation-sensitive: realign `/\` bullets and compare `run.sh <module>` state counts.

## Disk
- `wt release` prunes each `<wt>/target` and `<wt>/*/target` to what is in use: if anything was used since the previous release it runs `scripts/wt-mark` there (every standard command; add a new standard command there too), then deletes every unit not used since, and in `incremental/` keeps the newest session per dir and drops dead dirs beyond the live units naming that crate. No cold builds result (an osis-engine edit after a release costs the warm 7 s). Idle targets and profiles are left alone.
- It needs a filesystem that records access times: on a `noatime` mount it prints `wt: this filesystem doesn't record access times (noatime): targets not pruned` and targets only grow (14-15 GB in busy worktrees, 22-30 GB after crate-graph changes leave dead `incremental/` dirs). `relatime` works (`findmnt -T .`).
- `libs/kit/target` is two levels down, past wt's `*/target` glob: it is never pruned; `tools/prune-incremental.sh [hours]` reaches it (it removes incremental sessions untouched for that long from claimed worktrees).
- Bound: a worktree over 15 GB (target plus kit) gets a cleanup between rounds: on a worktree where no cargo runs, delete every incremental session but the newest per crate dir (what rustc does next anyway, no rebuild): `python3 -c 'import glob,os,shutil,sys; [shutil.rmtree(s) for d in glob.glob(sys.argv[1]+"/target/*/incremental/*/") for s in sorted((x for x in glob.glob(d+"s-*") if os.path.isdir(x)),key=os.path.getmtime)[:-1]]' .worktrees/wtN`, plus `tools/prune-incremental.sh` for dead dirs; past 20 GB delete the target. `wt trim` is not the cure: the next claim builds cold (a 13-minute tier 1 once).
- A full disk reads as a compile error (`failed to write query cache`, `failed to parse process output`): `df` before believing a build failure. A `du` of `/home/ai/*` takes over 10 minutes: use `df` and the worktrees only.

## What things should cost
Quiet machine, warm worktree. More than about 3x at low load: stop and find out why.

| what | expect |
|---|---|
| no-op `cargo build --workspace` / `--all-targets` | 0.4 s / 2 s |
| one-line edit, `cargo test --workspace --no-run`: osis-node / osis-engine | 2.5 s (4 crates) / 5.5 s (5 crates) |
| `cargo test --workspace`, built | 152 s, 1900 CPU-s (2834 tests); osis-node `it` 65 s of it. CPU-bound, 2-4x at load 25-35, and CPU-s rise too (SMT): a built run 3000-3400 CPU-s at load 20-40. Harness failures are reported unshrunk (`OSIS_ORDER_SHRINK=1`, `OSIS_PERM_SHRINK=1` shrink; a shrinking osis-node `it` with 12 failures ran 646 s); per test: notes/testing.md Tier-1 cost |
| edit osis-crdt or osis-base, all targets | 10-16 s |
| clippy / clippy-net after a one-line edit | 3-7 s / 3.5 s |
| clean `cargo build --workspace`; then `--all-targets`; first clippy; first clippy-net | 82 s; +53 s; +17 s; +69 s |
| osis-engine and osis-node from scratch | 27 s (osis-node starts on osis-engine's metadata and the two codegen in parallel) |
| gate, warm, everything | 237 s: tier 1 143 s, sim sweep 26 s, GUI tests 46 s, clippy, unification, deny and instant checks about 20 s; 2-4x beside other all-core runs (460-1160 s at load 20-40, plus 1.5-7 min rebuilding after a rebase). The first core gate in a worktree with no `libs/kit/target` adds 2-4 min (its GUI check builds kit's dependencies, 800-1300 CPU-s) |
| sim sweep 5 / 30 / 300 seeds | 38 s, 600 CPU-s / 2.2 min / about 20 min; heaviest per seed `concurrent_writers`, `future_format`, `work_sets`, `link_race` about 2.5 CPU-s; 30 seeds 6-10 min at load 30-36 |

In dev the sizes default smaller (`scale.rs` `size`), 10-60 s per test |
| per-branch oracles at plain sizes (a tenth of full) | about 2.5 min, 950 CPU-s (alike 10 s, exhaustive 11 s / 160 CPU-s, purge 16 s, perm set 21 s / 284, crdt set 34 s single-threaded, paged 25 s, rotation 3 s, eph 5 s, sim 30 eph seeds 12 s); `OSIS_FULL=1` 13.4 min, 11,370 CPU-s |
| a task worktree's `target/` | 4-6 GB after a gate and a pruning release (+0.3-0.7 GB release); `libs/kit/target` 1-3.5 GB more; a warm one settles at 11-12 GB by `du` when not pruned |
| test executables | 53, about 0.65 GB; an osis-node or osis-engine edit relinks the ten above it |

Signs of unravelling: a build on a tree built minutes ago compiles more than the touched crates and their dependents; `target/` dirs growing by GB per day; tool calls lasting exactly 10 minutes; a "wait for X" shell loop anywhere; `--jobs`, `--release` or `--features` creeping into commands; the unification check failing; a timing test running in dev.

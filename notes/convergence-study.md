# Convergence study: retroactive validity against dropped data
> Summary: Catalogue of every known convergence hole and accepted divergence with its root-cause class; why no removal rule (give up retroactivity, key epochs, bounded reach-back) removes the class; the one rule change that makes the class convergent on delivery (a body dropped for its keep bounds counts as never received: a copy that arrives again joins); a small detection-first repair backstop (keyed state digests in heartbeats, a writer re-snapshots self-reported suspect aspects); the requirement sentences that change and need Tess's call.

## 0. The shape, stated precisely
Validity (spec/permissions.md §5.2) is a function of the held set, and that function is **non-monotone**: adding an explicit demotion D to a node's held set turns writes it had applied invalid. Every node that applies X's write before it holds D and later receives D performs an un-merge (spec/crdt.md §4.6), and un-merge is "the join of every body and residue the node holds, minus the invalid writes". A node that dropped a body or residue it would need (keep-at-most bound, purge, expiry, pending part dropped at T, a cover that itself turned invalid) computes a different join than a node that kept it. So the class is: **(a validity flip) × (a non-vouching drop under the flipped write)**.

Two facts narrow it:
- **Every flip is an explicit demotion arriving late** (a removal, a demotion, a ledger entry, a revoke of a snapshot's or cover's author; `until` and self-removals audit nothing and are judged at the write's own `ts`, so they never flip). The arrival is late at a node whenever the demoted writer's write reached that node before the demotion did: a backdated revoke (stolen device: honest and common), an unsynced or offline revoke, P2P-only edits, in-flight uploads.
- **Compaction is a vouching drop and does not cause the class.** A valid snapshot vouches for what it carries (notes/permissions.md Snapshots and history), so a write compacted before the compactor learned of the demotion stays at every node alike (spec/requirements.md Permissions already says so). Tess's Carol example as stated (Carol *compacts*) therefore converges, with Bob's write surviving everywhere. The divergent variant is Carol dropping the state under Bob's write at a **keep-at-most** bound (or losing it to expiry, purge, or a pending part dropped at T): non-vouching drops, whose content no snapshot carries.

So in honest use the class needs: an aspect with retention bounds (or expiry/purge), written by a holder who is later demoted with a frontier that does not cover the write. Rare, but real, and each new dropping mechanism (header forgetting, session-sources, eph-unify) re-opens a shape of it.

## 2. Requirement changes examined
The binding sentence is spec/requirements.md Permissions: "Whether an edit by a revoked holder counts is judged by what the revoker had received, never by the author's own timestamps. Edits the revoker had not received when it revoked are lost until re-grant, except those another writer compacted before it learned of the revocation, which stay."

### (a) Give up retroactive invalidation
Meaning "a removal stops only writes arriving after it". Two readings, both fail:
- **Arrival at the judging node.** Validity would depend on the order a node received things: Carol (got W, then D) keeps W, Dave (got D, then W) refuses it, and they never agree. This breaks Decentralization "Deterministic" and "Convergence" outright, not as an exception.
- **Arrival at a host** (the host as sequencer: stamped before the re-registration stands). Breaks "No central or trusted coordinator ... or sequencer" and "Nothing trusts a host's word"; with several hosts and P2P it is not even well defined.
- **Deterministic version: the author's claimed time** (valid iff `ts` < the removal's `ts`). This is the rejected timestamp rule, and it does **not** remove the class: Bob's honest 10:05 write accepted by Carol over LAN still flips when D (10:00) arrives, so Carol still un-merges and still needs the state under it. Any rule in which a removal ever invalidates a write some node has already applied is retroactive at that node; the only non-retroactive rules are arrival-dependent. So (a) buys no convergence. What it loses: the removed writer forges pre-T writes forever. Hosts refuse its uploads once the write key is re-registered and honest peers refuse its connections, but any *reader* can deposit its commit into a label's open budget and a writer promotes it (its chain shows a writer at `ts`, so it is valid), so a removed writer plus any reader have permanent write power into every aspect it ever had: breaks "Readers only read" and "Rights held by different parties never combine". Reject.

### (b) Bind each write to its key epoch (the secret-token idea)
A write carrying proof of the write secret of epoch e proves only that its author held that secret at some time, which a former holder does forever (history boxes, and it simply keeps the secret). Possession gives a **lower** bound on write time ("after the epoch existed"), never the **upper** bound removal needs ("before the rotation"); a removed writer backdates `ts` into any epoch it ever held. So epoch binding protects against nothing the frontier protects against, and the rule "a removal invalidates only writes of the epochs since the last rotation" would both lose more honest writes (every uncovered write of the whole epoch) and still flip at nodes that applied them. Reject. (The one thing a token proves, freshness, is useful elsewhere: it is what the host's write-key stamp already does for uploads.)

### (c) Bounded reach-back by a first witness
A witness the author cannot fake is another member's receipt: a writer's signed receipt frontier (the "writer witnesses" sketch in issues/revoke-needs-whole-tree.md) or an upload stamp under a write-key epoch the author never held (a current writer relayed it after the rotation). A host's own stamp or time is the host's word (excluded). Writer witnesses are sound (a writer vouches for what it could have written itself, the same principle as snapshots vouch) and deterministic as a least fixpoint from the demoter outward. But they are still retroactive: a witnessed write is valid, an unwitnessed one flips when D arrives, exactly as today, and the witness itself falls if the witness is later removed with a non-covering frontier. They reduce *loss* (hole 19), close no R×D hole, and add a receipt frontier to every delta plus a fixpoint. Not now; keep as the lever for hole 19 if receipts-only reads prove insufficient. No reach-back rule converges better than the frontier because convergence is not what the rule decides; what the node dropped is.

### (d) What actually closes the class: make non-vouching drops re-joinable
The spec already has the right model for one drop kind: a body dropped as covered whose cover turns invalid "counts as never received from then on ... and the body joins as a late part when it arrives again" (spec/permissions.md §5.2). Keep-at-most drops have the opposite rule, "a drop is final", enforced in `retention::takes_late` (a late copy of a part dropped other than at expiry or purge is refused). **Rule R1: a body dropped for its keep bounds counts as never received: a copy that arrives again joins (and is dropped again at once if it has no live write or its bound has passed).** With R1:
- Node N dropped U (killed by Bob's W), later gets D: W un-merged, U absent at N. Dave, who never held W valid, holds U live and uncovered, so U is must-hold and Dave uploads it where missing (spec/sync.md §7, existing rule); N fetches and joins it. N and Dave now hold the same bodies and read the same. The state is a function of the bodies held; nodes holding the same bodies agree; nodes lacking a body get it from any holder that still has it, a reader included (deposit, then promotion by a writer: the body is a verified signed commit). Only when no node holds U is it gone, and then alike.
- Privacy: U's value is live (its only replacement is invalid), so holding it is right; a body that arrives dead is dropped in the same transaction, as at-most-0 does today. Absolute bounds (T) still drop at every node, so nothing is re-uploaded past T. Expired and purged copies still arrive value-less or are stripped (`v/`, the header's T, the held purge request), unchanged.
- Transient: a node that has not yet received D sees Dave's re-upload as dead and may delete it at the host at its bound; Dave re-uploads at its next resync. Role commits are applied and placed before content, so D normally reaches the node with or before U. Same class as hole 13.
- Cost: no new wire state, no residues; `takes_late` admits keep-bound drops (the reopen path exists), node-sync's no-reupload memory (`DeletedBody`) must not refuse a body that is live again. Hole 2 is not closed by R1 (no copy exists after T); hole 4 goes with eph-unify step B; 5 and 6 heal already.
- The order oracle can then *assert* equality after the two nodes exchange their held bodies, instead of tolerating `drop_flip`: a stronger oracle for free.

Requirement sentence that changes (Tess's call): Deletion "Erasure is final: a body dropped at its keep-at-most bound stays dropped if the write that replaced it later turns invalid. This is the one place where nodes holding the same data may read differently" becomes "A body dropped at its keep-at-most bound is not recovered by the dropping node on its own; if the write that replaced it turns invalid the value is live again and the node takes it back from any holder that still has it (a copy that arrives again joins), so nodes holding the same bodies read alike. Two nodes may read differently only while one lacks a body the other holds, or when a part expired before a node could apply it." The second half of the old sentence was an admission, not a wanted property: the one place became several.

## 3. Repair backstop
What the exchange-digests-then-replace idea gets right and wrong, and the smallest version worth building.

**Replace-aspect is the wrong repair write.** A `replace` is a reset at the repairer's `ts`: it prunes every concurrent honest edit from offline nodes (list inserts, map puts, text) and makes the repairer's view win over a richer one. The right repair write already exists: an ordinary **compaction snapshot** of the aspect. A valid snapshot's copies govern held originals, two writers' snapshots join to their union (disagreeing copies under one dot by the deterministic copy order), it carries expiring writes value-less and purged ones stripped (spec/crdt.md §8, §4.7), so it never resurrects expired or purged content, and it may carry a keep-at-most-dropped value exactly when that value is live at the snapshotter, which R1 wants anyway. "Prefer the side with less" is thus wrong for keep-at-most and automatic for expiry/purge; the join is the only tiebreak needed. Attribution: content known only through a snapshot has no author or time (notes/api.md Attribution), true of compaction today. Readers cannot write snapshots: they only report.

**Detection without a drill-down protocol.** Two signals, both in the heartbeat `seen.0` (spec/permissions.md §4; a deposit, so readers send it too):
- `held`: a set-hash (XOR of BLAKE3 over commit IDs) of the commits applied under the label, and `state`: a set-hash over per-aspect digests of the label's closure, each digest `kdf("state", dedup secret of tid, ak, canonical state bytes)` (per-page hashes for paged states, so a change inside a huge value costs O(change); 16 B per aspect stored; the label set-hash updates in O(1) per change). Keyed by the thing's dedup secret, so a blind node learns nothing and a rotation recomputes nothing. Two co-readers with equal `held` and unequal `state` have diverged; unequal `held` compares nothing (false negatives are fine).
- `suspect`: up to a few dozen (tid, ak, digest) entries the node itself flagged: an un-merge or validity flip on an aspect where it holds a body dropped other than as covered (R1's re-join clears the flag when the body returns), a pending part dropped at T (hole 2), a snapshot's writes removed where their bodies are gone (hole 3). The node that cannot compute the right answer is the one that knows it.

**Action.** A writer that sees a co-reader's suspect entry whose digest differs from its own writes a compaction snapshot of that aspect (bounded: one per aspect per `HEARTBEAT_MIN_INTERVAL`); if its own view is the poorer one the snapshot changes nothing and the richer writer's snapshot, when it comes, converges everyone. A label-level `state` mismatch with no suspects raises a diagnostic only (an unknown divergence: the first field signal this project would have for the class). No negentropy over (tid, ak), no new request kinds, no repair of large labels by full re-snapshot.

**Cost.** Hashing: a 64 KiB page in tens of µs, well inside the 50 ms per-write budget (notes/testing.md); 16 B per aspect in the store, 48 B more per heartbeat. Code: digest maintenance in the engine, two heartbeat fields, the suspect flag at three sites, the writer's compare-and-snapshot: a few hundred lines, no wire change outside `seen.0`'s schema.

**Is it simple enough to be worth it?** Detection yes: cheap, and the only way to learn whether the field has holes the oracles missed. Active repair only after R1, and only on suspects: without R1 the snapshot would be fighting the drop-is-final rule; with R1 the common case repairs itself by delivery and the snapshot covers what no copy can bring back (hole 2) and unknown shapes. Risk: silent repairs hide bugs, so each repair is a diagnostic and the oracles run with repair off.

**What repair lets us delete or not build.**
- Do not build pending-past-expiry option C (checked value-less residues for pending parts): take option A (a part pending at T is dropped and counts as never received), flag the aspect suspect, and let a writer's snapshot carry the stamps. One rare case, no new residue form.
- A past-T part never decides whether its commit applies (`apply::waits_without_expired`). Cost: a stale copy of the only part a node gets, on X, beside a thing Y it does not sync, leaves the commit pending for good (it waits whole once part-less) and X's non-value writes out: an older value X's delta overwrote still reads, until a writer's snapshot repairs it or Y's part comes and another copy of X's joins. Only stale copies: hosts drop the blob at T and refuse it past T, so that node mostly never saw the commit at all and reads the same. The expired value itself never shows or stays; chat E is not exposed (an edit is a new message plus a purge, nothing overwrites a message's value). Letting a commit left with no live part apply as before fails `parts_differential` seeds 121019, 936059 and order seed 49724; making it apply needs a kept "a part came" mark that a relay's junk could set.
- The order oracle's `drop_flip` tolerance (with R1) and, if repair is on in a differential, the "deaths dated per node" tolerances stay as they are (retention, not convergence).
- Not deletable: `v/` and `w/` residues (they strip late valued copies after expiry or purge and keep un-merge order-free where no copy ever returns; dropping `w/` would make every un-merge on an aspect with expired writes a repair round), the cover-uncover rule of §5.2 (it *is* R1 for covers; unify the two into one sentence rather than delete either), `Dropped::stands_in`/`live` (atomic apply and host carriers).
- Could lean on repair instead of local rules: hole 2 (above), hole 16 (a projection pending forever: a writer's snapshot of the thing's `created.0` cannot help, `created.0` is never snapshotted; stays a liveness issue), hole 4 until eph-unify B lands.

## 4. Tricks, judged against the bar
(1) acceptable to sometimes happen, (2) common enough to be worth it, (3) no true solution.
- **Grace before a keep-at-most drop** ("keep the under-state G after the kill"): at 0 today, at infinity no deletion. Fails (3): R1 is the true solution; and (2): flips are rare.
- **Reach-back window** ("a demotion can only invalidate writes with `ts` within W of T"): fails (1): backdated vandalism is the thing being prevented, and it needs a removed writer, not a mishap.
- **Demoter compacts first, state as of after its own demotion** (session-sources step 3, with a state-size bound): converts the common honest shape at the source (the demotion arrives with the demoter's vouched view). Fails (3) once R1 exists, and the size bound would be a convergence switch, not a performance one. Not needed; revisit only if demotion frontiers measure large.
- **Repair snapshot of every aspect under a small label** on an unexplained digest mismatch: a size bound deciding whether a divergence is repaired fails (3) (a drill-down is the true solution) and (2) until the field shows mismatches. Diagnostic only.
- **Re-snapshot after a roster-snapshot residue** (hole 6): already the designed heal, no trick.

## 5. Recommendation
Keep the frontier model: no removal rule removes the class, and (a)-(c) each give up a requirement for no convergence gain. The smallest set that makes convergence robust and the implementation simpler:
1. **R1** (spec/commits.md §5, spec/permissions.md §5.2 unified with the cover rule; engine `takes_late`/`reopen`, node-sync `DeletedBody`): a body dropped for its keep bounds counts as never received; a copy that arrives again joins. Closes hole 1, Tess's example, as convergence on delivery; turns the oracle tolerance into an assertion. Needs the Deletion requirement sentence rewritten (Tess).
2. **Detection** in `seen.0` (`held`, `state`, `suspect`): a few hundred lines, no new protocol. Then **repair on suspects** by an ordinary compaction snapshot from a writer, diagnostics on every repair. Covers hole 2 and unknown shapes; nothing is replaced, nothing expired or purged comes back.
3. **pending-past-expiry: option A + suspect flag instead of C** (Tess had said "if C is good go with C"; this is simpler and C is unbuilt).
4. Already planned and consistent with this: eph-unify step B (hole 4), session-sources rules 7-9 (header forgetting replays rejoin, which is R1's model).
5. Keep fixing F-class holes only when cheap; they need a hostile writer and converge whenever nodes hold the same valid snapshots.

Honest limits: hole 2 and hole 16 stay without a local fix (repair covers 2, nothing covers 16 but a re-place of the author's commit); hole 19 (loss, not divergence) stays the designed semantics, writer witnesses being the only lever. "Keep fixing one by one" is still what remains for F and L; for R×D it is not, because R1 removes the rule that made each new drop mechanism a new hole.

Tess's sign-off needed, in plain words:
- Deletion: "a value erased at its keep-at-most bound stays erased even if its replacement turns out invalid" becomes "it stays erased only at nodes that cannot get it back; if its replacement was invalid the value is live and comes back from any device that still has it." Expired and purged content never comes back; this changes nothing there.
- Decentralization "Deterministic"/"Convergence": add "nodes holding the same bodies read alike; a node missing a body reads as if it never had it until it arrives", replacing the "one place" exception.
- pending-past-expiry: A plus suspect flag instead of the chosen C.

# Serving: hosting in osis-host and the node
> Summary: Why hosting is a node feature with its own crate and store (Tess), and how it is built: osis-host's `HostStore` (rows, shredding, sweep, log trim), `HostPolicy` with every default and why the step-past-cap rule is so, the sans-I/O `Hub` serving every connection of the node under its one key, push-only replication with echo suppression, hosting inside the node (the hub in the node driver's loop, `host^.0`, admission, the store's lifecycle), isolation, and host abuse limits. Not here: the serving engine itself (notes/sync-protocol.md), hub stall bounds and turns (notes/flow-control.md), co-reader serving (notes/peers.md), what a host learns (notes/unreadable-data.md).

## Decisions (Tess)
- **One kind of node**: same binary, run the same way, on a laptop or a rented machine, with any mix of data it reads and data it cannot. A node hosts a label by storing it and serving it to its role key holders. Reading is per label (a read secret held or not), so one node may read some groups and host others it cannot read; a machine that reads its own configuration group and hosts everything else unread is one osis instance.
- **No separate program**: hosting is part of the node, started by the one long-running command (`osis serve`), configured by `host^.0` on the node's own thing (spec/data-model.md §9). Config as osis data lets any admin of the node (the account's nodes) configure it remotely; it is never in the node card; absent means not hosting.
- **osis-host is its own crate below osis-node**, so the compiler keeps hosting away from the engine, keys and sync state; the node hands it public data only (`HostConfig`), and tools/policy.py fails closed on any new decrypting call (`host_blind`).
- **Its own `Store`, not raw `Backend` rows**: a node hosting a label it also reads holds the read secrets on the same machine, so wraps and blobs surviving a delete in freed pages would break spec/requirements.md Deletion; Store deletes shred. Not the engine's store: that would hand the host the store holding actor secrets. Every node opens it beside the engine, always (issues/net-one-peer.md step 4: the one store of ciphertext); what it keeps for others is what `host^.0` admits.
- **One serving path** (issues/net-one-peer.md step 3): every listener of a node feeds its hub, one `ServingSession` per connection under the node's one key (the dialable key; a LAN listener's per-join key, a unix socket's uid key); node sync is every session's upper layer. The hub's store is the node's one store beside the engine (`SyncEngine::hub_store`), admitting nothing while the node hosts nothing. What a node reads goes to readers by node sync's stream from the engine's store (issues/net-one-peer.md step 4 moves it into this one).

## HostStore (`core/host/src/store.rs`)
- Implements osis-proto's `LabelStore` on its own osis-store `Store`: one table, blobs in the store's blob area (bytes once per host, reference-counted).
- **The engine's blobs** (`store/engine.rs`, `osis_store::CipherHost`): the engine's ciphertext store is this one, so a blob the node reads and serves is stored once. A `B` row marks a blob the engine holds; a blob goes once no entry references it (`R`) and no `B` row is left (`Write::DeleteBlob` skips a held one, `Write::PutBlob` one present). The engine's memory blobs sit in `engine_mem`. Its writes join the store's open transaction under the lock its transaction holds; `abort` drops them. Test `engine::`. Rows: label meta (log ID, head, counters), host totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts, sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions; per-step indexes (`V`/`W`), head keys (`K`), claim index (`H`), blob prefixes (`R`).
- Every table removal is `Shred::Yes` but the engine's `B` marks (they name a blob, no secret; a release is no shredding commit) (the node log's rows: notes/local-store.md, Node log); overwrites are `Shred::No` (a promotion wraps the same blob key, and the entry's removal later shreds every earlier version on its path), so deleted wraps are unrecoverable once committed (forensic test `hygiene::deleted_wraps_unrecoverable`).
- A mutation's writes apply together to the open store transaction (`Suspended` between calls, `Store::resume`); it commits per mutation, or once per hub batch (`defer_durability`/`durable`); a failed write aborts the open transaction and fails the batch's `durable`; a failed commit recovers the store in place (`Store::reopen`). Reads take `&self` (`LabelStore`), so the store sits in a `RefCell`.
- Log ID = BLAKE3(instance seed || label)[..16], the seed random per storage instance, so a wiped host invalidates old cursors.
- **Node log** (notes/local-store.md, Node log): the store's one node-wide log beside the per-label logs the host protocol reads (both until build 3i, issues/net-one-peer.md), written in each mutation's own writes (`Write::Log*`, no extra commit): an `Added` per durable entry stored or promoted, a `Deleted` per removal (delete, replacement, expiry: the entry left the store), a `Head` per step pushed; ephemeral entries none. Cost per durable entry event: one log append (meta, slot and event rows, the replaced event dropped). The sweep runs its page of the log's sweep when due (`log_next_due`, also in `next_due`). The stream reads it (notes/peers.md, The stream): one log for what the node reads and what it keeps for others. Tests osis-host `nodelog::`.
- **Node sync's rows** (`store/reader.rs`; issues/net-one-peer.md step 4). Principle: the hub's store holds every ciphertext of the node once, the truth for it; node sync's state (the entry's kind, certificates, tombstones, records) is a cache beside it in the engine's store.
  - Node sync's sync IDs (`set_read`, the labels it syncs; durably an `n` flag) are its own: no admission, cap, budget or rate; never replicated nor dropped by `stop_hosting`. Totals count their rows too (a reader's data narrows what it takes for others: accepted until step 6 settles consent).
  - Entries: an entry node sync holds bytes of is a row (`reader_put`, in `State::flush`); an entry without bytes (announced, unvouched, a dropped chunk's salt) and tombstones stay in the engine's store only. Steps: the path node sync serves (`label.0`'s deepest recorded path, `ServedLabel`) goes in as it moves (`reader_steps`, `State::note_path`); a client's Register takes no genesis for such a sync ID (refused for now, code 4) and a valid child only.
  - Add before, remove after (one mechanism with the engine's blobs, notes/local-store.md Ciphertext store): rows are put in the engine transaction's hub transaction, committed first; node sync's removals and forgets are deferred (`osis_engine` `Cipher::defer` of `HostStore::removal`/`forgetting`), noted with the blob holds and releases, applied after the engine's commit (`finish`) or by `settle_blobs` when it committed. So a crash leaves a row with no entry (an arrival, derived again), never a removal the engine did not decide.
  - Expiry: node sync alone expires a sync ID it reads (its pass, which knows a commit's leftovers and covers); the hub keeps no expiry index for its rows, an upload from a client to such a sync ID included. The sweep expires the sync IDs it does not read.
  - Changes others make (a client's upload or delete to a sync ID node sync reads, the sweep before a label turned read) set `moved` (`take_moved`; node sync's own writes leave it): the hub hands up `HubOutput::Moved` after that batch, the driver feeds an `Event::Hub`, and node sync reads the node log past its position (`State::hub_changes`, in memory: at load a full reconcile, `State::reconcile`, sets it to the log's end): a row with no entry is derived (`Kind::Unknown`, its bytes held again, opened), an entry whose bytes are held with no row is dropped and its blob forgotten, a differing wrap or stamp taken; a row of an entry node sync tombstoned is removed.
- **What node sync reads of unread sync IDs** (`store/unread.rs`): their heads and claim sets and paths, `heads_generation`, and the ephemeral events of those its shared sets serve (`set_streamed`, `take_memory`); a change by others of a sync ID node sync reads or streams, or any head, sets `moved` (node sync wakes, stamps and serves what its streams gained). The hub hands up relay-only uploads of unread sync IDs (`Up::Relay`) and takes `Down::Changed` for a Deposit item node sync put in (notes/peers.md, Sync IDs kept unread).
- **Sweep** (`sweep(now, budget)`): at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record); tombstones after `TOMBSTONE_LIFETIME`, and with them the log up to the position the entry went at; claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`).
  - Every durable removal, expiry included, puts a `Y` row holding its log position (the Deleted record's, or the head's at an expiry) and whether it was a deletion; only a deletion's `Y` row drops the tombstone (an expired blob may be added and deleted again). The `Y` and `G` rows dropped count against the budget, a label's highest due `Y` row only once its trim is done, so a budget the due `Y` rows fill still progresses; a trim cut short keeps that row and raises the horizon to the last row dropped.
  - An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s.
- **Log trim**: also to `log_keep` records in steps of 1/8. Serving: a cursor of the label's `log_id` that `log_after` no longer reaches and not past the head is trimmed (Error 15, the client reconciles); another `log_id`, a cursor past the head, or a lost replay gets Error 10.
- Host byte totals count an entry's bytes once per label holding it. Counters (rate windows) are in memory: a restart resets them.

## Host policy (`HostPolicy`)
Every knob is settable by field name in `host^.0`'s `policy` map (`HostPolicy::set`; a bad one is a diagnostic and the defaults hold). Defaults:
- Per label: `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12, new entries only). Host-wide: `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register gets Error 12 via `LabelStore::admit_label`, which answers 14 for a label outside the admission, spec/wire.md §11.2).
- A registered step and its claim set count toward `cap_bytes` and `max_bytes` (the set until the sweep drops it). Past them `push_step` refuses a genesis step (12) but takes a child step without its set, and a child step past them even without its set once per `over_cap_step_ms` (1 h) per label, else Error 12 (`Meta::over_cap_until`, durable). Why: a refused rotation would leave a removed holder's open and write keys valid at that host, and anyone may fill a host to `max_bytes`; only a label's own admin spends that room, so outsiders cannot starve an honest label's rotation, and growth past the caps is at most `max_labels` bare steps (about 300 B) per hour. A wait past one interval (clock set back) counts as over.
  - The node keeps its open on a Register refused 4, 12 or 14 and registers again at a later pass (each resync), so the label stays synced, not stranded, while it waits; the rest of that pass waits with it (nothing goes under the old keys). Steps queued behind a refused one each wait an interval: `reregister` registers the recorded child of the host's head (the older rotation) before issuing one at the newest epochs, so k rotations at a full host take k intervals (`rotation_at_full_host_waits_spec_sync_5`).
  - Forgetting old steps instead was rejected: a path walk from genesis is how a node verifies a head it has not recorded.
- `deposit_factor` 1 × the spec minimum budget (64 + 4 per head claim slot entries of 32 KiB); `claim_keep_ms` `ROLE_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither may be less); `log_keep` 2^20.
- Fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `deposits` 600, `registers` 600 (steps pushed; a repeat of the head is free; a recorded path registered at a new host goes at that pace), `relays` 6000 and `relay_bytes` 32 MiB (relay-only pushes). Rate limits answer code 4.
- **Connection memory** (principle: what the hub holds for the connections it serves is bounded by `max_buffered_bytes` per direction, never passed; a reader that reads is never closed for it and slows only itself).
  - **No connection count limit** (Tess; spec/sync.md §10 Served connections): any node serves any number of connections and closes none for their count or for sharing nothing. A count picked from memory per connection would mislead (that memory is not a fixed amount in practice) and refused devices past it on large rosters. Stated limit: the transport's buffers per connection (up to `link::CONN_MEMORY` each) are unbounded in total, so many connections can take the node's memory. Later work, not built: a node that detects low memory sheds load (refusing or closing connections, evicting caches). `hello_ms` 10 s (no Hello: closed). `max_queued_bytes` 64 MiB unread per connection (then dropped; at least `SEND_QUEUE` + `WINDOW_QUEUE`: node sync's own requests go on served connections too).
  - `CONN_MEMORY` (2 MiB, transport tuning): a QUIC connection window of 1 MiB (one stream's: a session is a stream), the send window as large, and one 64 KiB read per stream (`MAX_STREAMS` 16): a link reads its stream only when its consumer asks, so a read waiting for its turn is the only received byte outside the window. Windows are not sized from a share of a memory bound: a connection's throughput needs its window whatever the count.
  - `max_buffered_bytes` 512 MiB per direction over all connections, in the hub: frames received and not yet run or answered (`ServingSession::buffered`: a partial frame, frames waiting for room, requests handed up; past it the connection holding the most is closed, `limit_buffered`; without the latter two, 256 connections each holding a waiting `MAX_MESSAGE` frame hold 2.3 GiB) and what connections hold for output (`Hub::held`: bytes written and not yet taken by the transport, as reported by `Hub::sent`, and reply allowances reserved).
  - **Room for output**: the hub sets each served session's room before it runs (`ServingSession::set_room`): its **share**, `max_buffered_bytes` over the active connections (holding something, `ServingSession::holding`: bytes written and not taken plus reply allowances handed up and not answered; or needing room), and the bytes the bound has left. A reply, push or own request goes only within both: within the share, or alone when the connection holds nothing, and within what is left. Requests are taken (decoded, charged against `MAX_UNANSWERED` at once) and wait in order for their reply allowance to fit (`pending`, `run_pending`); a connection with requests waiting takes no input (`Hub::waits`: the driver parks its read, the peer's next requests wait in the transport's window) and resumes at its own takes (`Taken`) or node sync's answers. A reply is never cut to fit: the allowance is reserved before the request runs, and the actual reply (at most it) is what then counts. Node sync answers what it was handed up at once and within the reservation. Push room granted (`Up::Room`) is reserved too until its pushes arrive (the stream's page, the port's Notifies) or node sync gives it back unused (an empty `Down::Notify`: `port_notify`, `stream_room_unused`). The share is judged against the connection's own output (bytes unread, room granted), not reservations for replies to come: a request waiting on pushes (a client-port settle) never holds back the room that lets them go, and "alone" (one reply or push past the share, within what is left) means no output of its own (`ServingSession::alone`).
  - **The queue**: a connection with no output of its own whose need does not fit what the bound has left (a reply past every share, a full bound) waits in the hub's queue (`queue`, arrival order); the first one's need is kept from the others (`slack`), so slack freed by any reader goes to it first and it runs when it fits (`pressure`). So the bound is never passed, a slow reader (honest or trickling) slows only itself and whoever queues behind the bytes it does not take, and a reader's request waits at most until enough readers drained its need. Shares follow the active count: one over a smaller share just waits.
  - **Bytes that do not move**: while the queue's first waits, once per `PUSH_POLL_MS` (the report period, at `tick` after the driver's `sent`) the hub closes, most held first and only until the whole queue's needs fit, connections holding output of their own that the transport took none of since the last check (`close_stuck`; a reservation alone, a reply to come such as a client-port settle, has no bytes to move). Room for the first alone would move the queue one request a period, and about 180 kept connections could then starve queued requests past their stall time. The first runs while still first, so the room kept for it is its own. Without it, readers that never read could hold the bound and queue everyone. Once the first has waited half `STALL_TIMEOUT_MS` (`first_due`), the most-holding connections go until it fits, moving or not: else readers draining slowly into a small bound (4 at 16 KiB/s) hold a request past its peer's stall time, the longer the smaller the bound. So a reader is closed for memory only when it drains too slowly for another to be answered in time.
  - Peer stalls: a request waits only while its own connection holds replies to earlier requests (which move the peer's stall clock as they arrive) or in the queue, at most half the stall time there.
  - Throughput under load: a waiting connection resumes at the driver's take reports (each `PUSH_POLL_MS` while it holds output), so with shares below its window a connection moves about a share per period. Outside the bound's room: our Hello.
  - Tests: proto `serving::tests::replies_wait_for_room_spec_sync_10`; osis-host `bounds::slow_readers_drain_their_shares`, `bounds::tricklers_slow_only_themselves` (15 tricklers fill the bound; a newcomer answered within each report period), `bounds::a_big_reply_waits_its_turn`, `bounds::shares_follow_the_active`, `bounds::granted_room_stays_within_the_bound`, `bounds::a_waiting_request_runs_within_half_the_stall_time`, `bounds::a_queue_behind_stuck_holders_runs_at_once`, `bounds::received_frames_stay_within_the_bound`, `bounds::a_reservation_is_not_output_that_stalls`; proto `serving::tests::granted_room_is_reserved_spec_sync_10`; by hand `quic::quic_unread_sessions_hold_one_window_spec_sync_10`.
- Ephemeral entries: `ephemeral_bytes` 16 MiB per label and `ephemeral_total` 1 GiB, in memory (code 12; past the total the label charged most gives way; notes/ephemeral.md).
- Reasons behind spec rules (§5 Host caps): an ephemeral upload refused for its cap reaches no holder through that host until room appears; entries deleted at a host's total cap may be brought back by nodes holding them.

## Hub, replication
- **`Hub`** (sans-I/O; osis-host has no async code): one `ServingSession` per accepted connection, its static key the listener's (`Hub::accept(now, id, key, Remote)`; `Remote`: the transport's peer and whether a relay carries it), every session serving the client port's kinds too; `Changed` to every connection and replicator; `Relay` to the label's subscribers on other connections (bytes shared, `Relayed::blob` an `Arc`). Every public call is one store transaction (one commit per input, so at most one shredding root write; on a failed commit nothing it would send goes and those connections close); `tick` commits its sweep on its own, so a failing sweep backs off. `tick(now)` runs the bounded sweep, Hello deadlines, stalls of node sync's requests (the session's `stall_at`: closed), replication work and timers; `next_due(now)`.
  - **Node sync above every session** (issues/net-one-peer.md step 3, The hub calls up for nothing): the hub judges no node kind (`Message::for_node`) and no client-port request. It hands up (`HubOutput::Up`) a session's start at its Hello (`Up::Start(Binding)`: both challenges, the listener key, the `Remote`), each node-kind message in arrival order, client-port requests (`Up::Request`, after the session's own Auth gate), push room (`Up::Room`) and the end of a started connection (`Up::End`, once its batch ends); it takes down (`Hub::down`, one batch) node sync's messages (requests within the session's window, answers at once), client-port answers and Notifies (`Reply`, `Notify`), `WantRoom` and `Close`. Node sync keeps each connection as a `Served` (`serve.rs`, `hub_up`, `hub_conns` by hub connection ID): proofs, records, the shared set, the stream and the client port; the hub keeps its Hello deadline, partial-frame budget and stalls. Test hosts are nodes too: the simulator's (`World::add_host`, `NetSim::add_host`) and osis-node tests' (`Net::add_host`) run node sync above the hub on a bare engine (no account, no group; admission open); only osis-host's own tests drop `Up`.
  - **The store is shared, locked per call**: `Hub::new` takes the node's `Arc<Mutex<HostStore>>`, the one `SyncEngine` holds; each public call locks it for its whole batch (its writes are one transaction nobody else interleaves with), so the hub runs beside the engine's holder without its lock. A guard (`Hub::store`) lives for one statement: held across another hub call, a second `store()` or a lock of `SyncEngine::hub_store` it deadlocks silently (the lock is not re-entrant), across an await it blocks the other holder. A node copy (`Net::copy`) copies the store once, through its sync engine, and its hub shares that copy (`Hub::test_copy_over`). Cost: hub batches and node sync's writes to the store take turns on that lock (counted as commits per inbound batch, issues/net-one-peer.md step 4).
  - `Hub::stop_hosting` (`host^.0` gone): the labels it kept for others go (`HostStore::drop_labels`: every row of the label, shredded; its blobs once no other label references them; its node log events, no deletion event), and the sessions that opened something and the replication sessions close; the rest stay.
  - The node driver drives the hub in its own loop (below); the simulator drives it directly (`World::host_of` runs a node's hub the same way, feeding `Up` to that node as `Event::Hub` and its `Action::Hub` back by `down`).
- **Replication** (`Replicator`, push only, since download needs an open): per dialed peer a `ClientSession` walks each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record. Deposits, deletions and pending times are not relayable (their signatures are not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with back-off 1-60 s.
  - A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks: a new peer, or one a removal's lifetime behind, of any label with a removal older than `TOMBSTONE_LIFETIME`). Entries stamped under keys older than the peer's head get code 9 there (a diagnostic only): writers re-stamp.
  - **Echo suppression**: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry, and a replicator does not send an entry to the peer key it came from, saving the upload of what the peer just sent (a held stamped entry changes nothing, so replication settles either way). It needs the dialing host to authenticate with its static key: the driver dials peers with `dial_as` and the dialable secret (an ephemeral dial key would defeat it, and then every entry goes back once).

## Hosting in the node (`sync/host.rs`, `sync/driver/`)
The only way a host runs. The node reads its own `host^.0` (any admin of the node thing may write it) once per engine change and hands its driver `Action::Host(HostConfig)` (none: stop) when it changed: the admission, replication peers, the policy (knobs over the defaults) and per-label caps (`LabelCaps`, in place of `cap_entries`/`cap_bytes`).
- **Admission**: `open` (any label) or `listed` (`labels` only), for the sync IDs the node does not read. Label IDs only, no key state. The sync IDs node sync reads are its own in the store whatever admission says (below, Node sync's rows), so a node reading its own groups serves them with no setup and no saved peer of its own; a stranger's grant, read or admin, never makes this node store a group it does not read (Tess's decision, as for the inbox accept step: spending this node's storage on someone else's data takes `open` or an explicit label).
- The node learns a new group's label by syncing the labels up its record chain, so the first registration there may come first: a registration refused for now (4, 12, 14) is `Phase::Refused`, opened again after `retry_ms` doubling per refusal by that host up to `resync_ms`, across connections (`refused_for_now`; `SyncEngine::refusals` keeps the count and last code per (host, label) until it opens there: a host that closes a connection sharing nothing does not reset the back-off), never Stranded nor reopened at once. Status: `LabelStatus::refused_by` names the hosts whose last answer was 14 (not admitted), connected now or not; osis shows `SyncState::Refused` (naming them in `GroupSync::refused_by`) when there are some and the label is open at none, `NotConnected` for 4 and 12 when open at none, and synced when it is open at another host (the data is at a host). `wait_synced` waits on a refused label (no deadline); the CLI, past `--timeout`, says which host does not admit which group. Tests `runtime::a_paired_serving_node_in_process_spec_data_model_9` (`config_mut` shortens `retry_ms`), `serving::serving_listed_then_open_spec_sync_5`, `serving::a_reader_serves_what_it_reads_with_no_setup_spec_data_model_9`, by hand `localhost::paired_serving_node_localhost`.
- **The hub in the node driver's loop** (`sync/driver/hub.rs`, `HubRun`): the node driver owns the `Hub` from its start and drives it sans-I/O on the driver's task beside the sync engine, one call at a time, each under `block_in_place` on a multi-thread runtime. Node sync and the hub meet by function call in that loop (`hub_pump`, after every pass and every host change): what the hub handed up (`HubRun::take_ups`) goes to the engine as one `Event::Hub`, the engine's `Action::Hub` go back by `HubRun::down`, until neither has more. Every listener is a hub listener group (`HubRun::listen(key, listeners)`, `unlisten(group)` closing its sessions): `Control::Reach` (the dialable key's P2P listener), `Control::Listen` (`Osis::listen`'s URLs, dialable key), `Control::Socket` (the unix socket) and the LAN loop's per-join listener; `rotate_peer_address` moves every dialable-key group to the new key (the unix socket stays: the kernel names its peers). The node's own dials of its dialable key, or of any key it listens under, are an in-process `link::pair`, no socket (`HubRun::own`, `listens_as`), so the sync engine sees an ordinary host. Hosting (`host_update`): a start or change goes in place (admission, caps, policy; replication dials restarted when the peers changed); a stop sets the default policy admitting nothing and drops what was kept for others (`Hub::stop_hosting`). Per link a reader task hands over one read at a time (notes/flow-control.md, Turns); writes go into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); a replication dial task per peer (`link::dial` with `dial_as` and the dialable secret, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`). A connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s; the hub ticks when due or 60 s after its last tick, at a deadline that moves only earlier until it runs (a due counted from now, such as a held connection's push poll, would otherwise move with every pass of the shared loop). Its tasks' events go through one unbounded channel (at most a read and an end per connection, a link per dial task, an accept per session the listeners took), a new link tagged by listener group, a replication session by its run, connection IDs never reused, so a stopped group's or run's late ones are dropped; the loop awaits no connection.
  - Tests: osis-node `hub_loop::` on `InProcess` under tokio (scripted host clients against a hosting node; one connection carrying a hosted label and the shared set and stream of a read one, `one_connection_serves_hosted_and_read_labels`; a stranger proved nothing, `a_stranger_gets_no_proof_spec_sync_10`; replication across a restart; a stop closing the opened sessions, `stopping_closes_what_opened_the_host_store`; turns; not `Sched`: the driver spawns tokio tasks); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). By hand (`hub_loop::quic_clients_and_replication`, ignored): two hosting nodes on QUIC replicating.
- **The store's lifecycle**: the holder opens it first and hands it to the engine as its ciphertext store (`osis_node::sync::hub_store`; osis: `<store>/host.redb` with key root `<store>/host.root`, or the `MemStore`'s, backed up with it); `SyncEngine::new` takes it from the engine (`Engine::blobs`), for every node, hosting or not; admitting nothing under the default policy until a host config sets them.

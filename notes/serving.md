# Serving: hosting in osis-host and the node
> Summary: Why hosting is a node feature with its own crate and store (Tess), and how it is built: osis-host's `HostStore` (rows, shredding, sweep, log trim), `HostPolicy` with every default and why the step-past-cap rule is so, the sans-I/O `Hub` serving every connection of the node under its one key, push-only replication with echo suppression, hosting inside the node (the hub in the node driver's loop, `host^.0`, admission, the run of hosting and store lifecycle), isolation, and host abuse limits. Not here: the serving engine itself (notes/sync-protocol.md), hub stall bounds and turns (notes/flow-control.md), co-reader serving (notes/peers.md), what a host learns (notes/unreadable-data.md).

## Decisions (Tess)
- **One kind of node**: same binary, run the same way, on a laptop or a rented machine, with any mix of data it reads and data it cannot. A node hosts a label by storing it and serving it to its role key holders. Reading is per label (a read secret held or not), so one node may read some groups and host others it cannot read; a machine that reads its own configuration group and hosts everything else unread is one osis instance.
- **No separate program**: hosting is part of the node, started by the one long-running command (`osis serve`), configured by `host^.0` on the node's own thing (spec/data-model.md §9). Config as osis data lets any admin of the node (the account's nodes) configure it remotely; it is never in the node card; absent means not hosting.
- **osis-host is its own crate below osis-node**, so the compiler keeps hosting away from the engine, keys and sync state; the node hands it public data only (`HostConfig`), and tools/policy.py fails closed on any new decrypting call (`host_blind`).
- **Its own `Store`, not raw `Backend` rows**: a node hosting a label it also reads holds the read secrets on the same machine, so wraps and blobs surviving a delete in freed pages would break spec/requirements.md Deletion; Store deletes shred. Not the node's store: that would hand the host the store holding actor secrets, and engine and hosting would contend on one lock. Accepted cost: a label both read and hosted is stored twice (no dedupe across the two stores).
- **One serving path** (issues/net-one-peer.md step 3): every listener of a node feeds its hub, one `ServingSession` per connection under the node's one key (the dialable key; a LAN listener's per-join key, a unix socket's uid key); node sync is every session's upper layer. The hub's store is the host store while the node hosts, else an empty one in memory admitting nothing. What a node reads still goes to readers by node sync's stream from the engine's store; the two stores become one in step 4.

## HostStore (`core/host/src/store.rs`)
- Implements osis-proto's `LabelStore` on its own osis-store `Store`: one table, blobs in the store's blob area (bytes once per host, reference-counted). Rows: label meta (log ID, head, counters), host totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts, sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions; per-step indexes (`V`/`W`), head keys (`K`), claim index (`H`), blob prefixes (`R`).
- Every removal is `Shred::Yes`; overwrites are `Shred::No` (a promotion wraps the same blob key, and the entry's removal later shreds every earlier version on its path), so deleted wraps are unrecoverable once committed (forensic test `hygiene::deleted_wraps_unrecoverable`).
- A mutation's writes apply together to the open store transaction (`Suspended` between calls, `Store::resume`); it commits per mutation, or once per hub batch (`defer_durability`/`durable`); a failed write aborts the open transaction and fails the batch's `durable`; a failed commit recovers the store in place (`Store::reopen`). Reads take `&self` (`LabelStore`), so the store sits in a `RefCell`.
- Log ID = BLAKE3(instance seed || label)[..16], the seed random per storage instance, so a wiped host invalidates old cursors.
- **Sweep** (`sweep(now, budget)`): at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record); tombstones after `TOMBSTONE_LIFETIME`, and with them the log up to the position the entry went at; claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`).
  - Every durable removal, expiry included, puts a `Y` row holding its log position (the Deleted record's, or the head's at an expiry) and whether it was a deletion; only a deletion's `Y` row drops the tombstone (an expired blob may be added and deleted again). The `Y` and `G` rows dropped count against the budget, a label's highest due `Y` row only once its trim is done, so a budget the due `Y` rows fill still progresses; a trim cut short keeps that row and raises the horizon to the last row dropped.
  - An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s.
- **Log trim**: also to `log_keep` records in steps of 1/8. Serving: a cursor of the label's `log_id` that `log_after` no longer reaches and not past the head is trimmed (Error 15, the client reconciles); another `log_id`, a cursor past the head, or a lost replay gets Error 10.
- Host byte totals count an entry's bytes once per label holding it. Counters (rate windows) are in memory: a restart resets them.

## Host policy (`HostPolicy`)
Every knob is settable by field name in `host^.0`'s `policy` map (`HostPolicy::set`; a bad one is a diagnostic and the defaults hold). Defaults:
- Per label: `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12, new entries only). Host-wide: `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register gets Error 12 via `LabelStore::admit_label`, which answers 14 for a label outside the admission, spec/wire.md §11.2).
- A registered step and its claim set count toward `cap_bytes` and `max_bytes` (the set until the sweep drops it). Past them `push_step` refuses a genesis step (12) but takes a child step without its set, and a child step past them even without its set once per `over_cap_step_ms` (1 h) per label, else Error 12 (`Meta::over_cap_until`, durable). Why: a refused rotation would leave a removed holder's open and write keys valid at that host, and anyone may fill a host to `max_bytes`; only a label's own admin spends that room, so outsiders cannot starve an honest label's rotation, and growth past the caps is at most `max_labels` bare steps (about 300 B) per hour. A wait past one interval (clock set back) counts as over.
  - The node keeps its open on a Register refused 4, 12 or 14 and registers again at a later pass (each resync), so the label stays synced, not stranded, while it waits; the rest of that pass waits with it (nothing goes under the old keys). Steps queued behind a refused one each wait an interval: `reregister` registers the recorded child of the host's head (the older rotation) before issuing one at the newest epochs, so k rotations at a full host take k intervals (`rotation_at_full_host_waits_spec_sync_5`).
  - Forgetting old steps instead was rejected: a path walk from genesis is how a node verifies a head it has not recorded.
- `deposit_factor` 1 × the spec minimum budget (64 + 4 per head claim slot entries of 32 KiB); `claim_keep_ms` `ROLE_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither may be less); `log_keep` 2^20.
- Fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `deposits` 600, `registers` 600 (steps pushed; a repeat of the head is free; a recorded path registered at a new host goes at that pace), `relays` 6000 and `relay_bytes` 32 MiB (relay-only pushes). Rate limits answer code 4.
- Connections: `max_connections` 10 000, the node's one rule over every connection it serves (node sync's, notes/peers.md Sessions; a node that hosts nothing runs the default). Each listener takes at most that many transport connections that share nothing (`link::serve`; `Link::kept`, set from node sync's `Down::Keep`, takes a connection out of the count). `hello_ms` 10 s (no Hello: closed). `max_queued_bytes` 64 MiB unread per connection (then dropped; at least `SEND_QUEUE` + `WINDOW_QUEUE`: node sync's own requests go on served connections too). `max_buffered_bytes` 512 MiB of partial frames over all connections (the connection holding the largest is closed).
- Ephemeral entries: `ephemeral_bytes` 16 MiB per label and `ephemeral_total` 1 GiB, in memory (code 12; past the total the label charged most gives way; notes/ephemeral.md).
- Reasons behind spec rules (§5 Host caps): an ephemeral upload refused for its cap reaches no holder through that host until room appears; entries deleted at a host's total cap may be brought back by nodes holding them.

## Hub, replication
- **`Hub`** (sans-I/O; osis-host has no async code): one `ServingSession` per accepted connection, its static key the listener's (`Hub::accept(now, id, key, Remote)`; `Remote`: the transport's peer, source and whether a relay carries it), every session serving the client port's kinds too; `Changed` to every connection and replicator; `Relay` to the label's subscribers on other connections (bytes shared, `Relayed::blob` an `Arc`). Every public call is one store transaction (one commit per input, so at most one shredding root write; on a failed commit nothing it would send goes and those connections close); `tick` commits its sweep on its own, so a failing sweep backs off. `tick(now)` runs the bounded sweep, Hello deadlines, stalls of node sync's requests (the session's `stall_at`: closed), replication work and timers; `next_due(now)`.
  - **Node sync above every session** (issues/net-one-peer.md step 3, The hub calls up for nothing): the hub judges no node kind (`Message::for_node`) and no client-port request. It hands up (`HubOutput::Up`) a session's start at its Hello (`Up::Start(Binding)`: both challenges, the listener key, the `Remote`), each node-kind message in arrival order, client-port requests (`Up::Request`, after the session's own Auth gate), whether the session holds an open or an answered Auth as that changes (`Up::Opened`), push room (`Up::Room`) and the end of a started connection (`Up::End`, once its batch ends); it takes down (`Hub::down`, one batch) node sync's messages (requests within the session's window, answers at once), client-port answers and Notifies (`Reply`, `Notify`), `WantRoom`, `Keep` (for the driver) and `Close`. Node sync keeps each connection as a `Served` (`serve.rs`, `hub_up`, `hub_conns` by hub connection ID): proofs, records, the shared set, the stream and the client port; it decides which connections stay (notes/peers.md, Sessions); the hub keeps its Hello deadline, partial-frame budget and stalls. Drivers without a node above (osis-host tests, the simulator's and osis-node tests' standalone hosts) drop `Up`.
  - `Hub::replace_store` (hosting starts or stops): the sessions that opened something of the old store and the replication sessions close; the rest stay.
  - The node driver drives the hub in its own loop (below); the simulator drives it directly (`World::host_of` runs a node's hub the same way, feeding `Up` to that node as `Event::Hub` and its `Action::Hub` back by `down`).
- **Replication** (`Replicator`, push only, since download needs an open): per dialed peer a `ClientSession` walks each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record. Deposits, deletions and pending times are not relayable (their signatures are not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with back-off 1-60 s.
  - A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks: a new peer, or one a removal's lifetime behind, of any label with a removal older than `TOMBSTONE_LIFETIME`). Entries stamped under keys older than the peer's head get code 9 there (a diagnostic only): writers re-stamp.
  - **Echo suppression**: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry, and a replicator does not send an entry to the peer key it came from, saving the upload of what the peer just sent (a held stamped entry changes nothing, so replication settles either way). It needs the dialing host to authenticate with its static key: the driver dials peers with `dial_as` and the dialable secret (an ephemeral dial key would defeat it, and then every entry goes back once).

## Hosting in the node (`sync/host.rs`, `sync/driver/`)
The only way a host runs. The node reads its own `host^.0` (any admin of the node thing may write it) once per engine change and hands its driver `Action::Host(HostConfig)` (none: stop) when it changed: the run of hosting (`store_id`), the admission, replication peers, the policy (knobs over the defaults) and per-label caps (`LabelCaps`, in place of `cap_entries`/`cap_bytes`). Node sync reads the policy's `max_connections` from the config it last emitted.
- **Admission**: `open` (any label) or `own`: the label IDs of its account's own groups whose hosts name the node's key (its dialable key), plus `labels`. `SyncEngine::owns`: the record chain through standing record edges (`Core::standing_chain`) reaches the node or its account, so a person removed from a group it made stops hosting it (`set_person`; osis sets `me` at start, kept by `host_restart` when the driver starts, else a node that only hosts admits nothing on a real runtime). No role grant counts: a stranger's grant, read or admin, to the account or the node, on the group or an actor above it, never admits a group (Tess's decision, as for the inbox accept step: spending this node's storage on someone else's data takes `open` or an explicit label). Label IDs only, no key state.
- **Its own address is a saved peer** (osis `upkeep_serving_peer`, notes/api.md Serving): while it hosts and listens (`Osis::listen`), its first address is in the saved peers, so its home and the groups that follow the list name its key and it syncs them from its own hub like any node. Without that an `own` node with no other route admits nothing for good: it learns which groups name its key only from labels it syncs, and it syncs none. Rejected: the host judging `own` from its own store (a second source for the node's decision), or a diagnostic for a missing self-peer (a setup step whose only correct value the node knows).
- The node learns a new group's label by syncing the labels up its record chain, so the first registration there may come first: a registration refused for now (4, 12, 14) is `Phase::Refused`, opened again after `retry_ms` doubling per refusal by that host up to `resync_ms`, across connections (`refused_for_now`; `SyncEngine::refusals` keeps the count and last code per (host, label) until it opens there: a host that closes a connection sharing nothing does not reset the back-off), never Stranded nor reopened at once. Status: `LabelStatus::refused_by` names the hosts whose last answer was 14 (not admitted), connected now or not; osis shows `SyncState::Refused` (naming them in `GroupSync::refused_by`) when there are some and the label is open at none, `NotConnected` for 4 and 12 when open at none, and synced when it is open at another host (the data is at a host). `wait_synced` waits on a refused label (no deadline); the CLI, past `--timeout`, says which host does not admit which group. Tests `runtime::own_serving_node_in_process_spec_data_model_9` (`config_mut` shortens `retry_ms`), `serving::own_admits_only_owned_groups_*` (a `host_restart`), by hand `localhost::own_serving_node_localhost`.
- **The run of hosting** is a local record (`y/z`, 32 random bytes, `HostConfig::store_id`), drawn when hosting starts and dropped when `host^.0` goes; the host store belongs to it. A config of a run that is over (hosting stopped, maybe started again, since it was emitted) is skipped (`host_current`; test `driver::a_stale_host_config_is_not_current_spec_sync_10`).
- **The hub in the node driver's loop** (`sync/driver/hub.rs`, `HubRun`): the node driver owns the `Hub` from its start and drives it sans-I/O on the driver's task beside the sync engine, one call at a time, each under `block_in_place` on a multi-thread runtime. Node sync and the hub meet by function call in that loop (`hub_pump`, after every pass and every host change): what the hub handed up (`HubRun::take_ups`) goes to the engine as one `Event::Hub`, the engine's `Action::Hub` go back by `HubRun::down` (a `Keep` sets its link's `kept`), until neither has more. Every listener is a hub listener group (`HubRun::listen(key, listeners)`, `unlisten(group)` closing its sessions): `Control::Reach` (the dialable key's P2P listener), `Control::Listen` (`Osis::listen`'s URLs, dialable key), `Control::Socket` (the unix socket) and the LAN loop's per-join listener; `rotate_peer_address` moves every dialable-key group to the new key (the unix socket stays: the kernel names its peers). The node's own dials of its dialable key, or of any key it listens under, are an in-process `link::pair`, no socket (`HubRun::own`, `listens_as`), so the sync engine sees an ordinary host. Hosting (`host_update`): a new run opens the host store of its run and puts it in place of the empty one (`Hub::replace_store`); a change goes in place (admission, caps, policy; replication dials restarted when the peers changed); a stop puts an empty store back and erases the host store when the engine no longer hosts. Per link a reader task hands over one read at a time (notes/flow-control.md, Turns); writes go into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); a replication dial task per peer (`link::dial` with `dial_as` and the dialable secret, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`). A connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s; the hub ticks when due or 60 s after its last tick, at a deadline that moves only earlier until it runs (a due counted from now, such as a held connection's push poll, would otherwise move with every pass of the shared loop). Its tasks' events go through one unbounded channel (at most a read and an end per connection, a link per dial task, the listeners' accepts within their slots), a new link tagged by listener group, a replication session by its run, connection IDs never reused, so a stopped group's or run's late ones are dropped; the loop awaits no connection.
  - Tests: osis-node `hub_loop::` on `InProcess` under tokio (scripted host clients against a hosting node; one connection carrying a hosted label and the shared set and stream of a read one, `one_connection_serves_hosted_and_read_labels`; a stranger proved nothing, `a_stranger_gets_no_proof_spec_sync_10`; replication across a restart; a stop closing the opened sessions, `stopping_closes_what_opened_the_host_store`; turns; not `Sched`: the driver spawns tokio tasks); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). By hand (`hub_loop::quic_clients_and_replication`, ignored): two hosting nodes on QUIC replicating.
- **The host store's lifecycle**: opened by the holder (`Shared::host_store`: `<store>/host.redb` with key root `<store>/host.root`, or the `MemStore`'s); erased when hosting stops (spec/requirements.md Deletion; `Shared::erase_host_store`: the root erased first, `RootStorage::erase`, which crypto-shreds the rest, then the files). The driver erases after the store is out of the hub (dropped) when the engine holds no run of hosting, so a driver shutdown never erases; a driver start with no run erases what a stop no driver carried out left; a node that never runs a driver (`Runtime::None`) keeps the files until one runs. The store records its run (local record `host run`, written before any entry), and opening one that records another run, or none, erases it first (another: stopped and started again with no driver between; none: new, or half erased by a crash, such as `host.redb` left without `host.root`). Test `serving::stop_serving_erases_its_store_spec_data_model_9`.
- **Isolation**: osis-host depends only on base, crypto, label, proto, store and transport, and names only allowlisted osis-crypto and osis-label items (tools/policy.py `host_blind`, fail-closed: a new `open*`, `kdf*` or secret type fails policy); osis-node names only `osis_host::{Hub, HubOutput, ConnId, Up, Down, Remote, HostStore, HostConfig, HostPolicy, Admission, LabelCaps}`.
- Builds: P2P is on in every build; the LAN loop (`lan`, `Config::lan`) too (issues/net-connect.md).

## Abuse (open; deferred until a real problem, Tess)
- Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-label rate limits on deletes, deposits, registers and relays, per-label ephemeral caps, admin delete. Anyone may register a label up to the host-wide label cap (then Error 12, so squatters can exhaust it), and any writer can fill a label's cap with junk the host cannot tell from data. Inbox-specific limits: notes/inbox.md.
- Per-holder limits would need pseudonymous holder keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one host bound to (host, label), never into the relayed `label.0` chain.
- Abuse limits for relaying: issues/p2p-own.md.

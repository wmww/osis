# Serving: hosting in osis-host and the node
> Summary: Why hosting is a node feature with its own crate and store (Tess), and how it is built: osis-host's `HostStore` (rows, shredding, sweep, log trim), `HostPolicy` with every default and why the step-past-cap rule is so, the sans-I/O `Hub`, push-only replication with echo suppression, the tokio driver, hosting inside the node (`host.0^`, admission, the host secret and store lifecycle), isolation, and host abuse limits. Not here: the serving engine itself (notes/sync-protocol.md), hub stall bounds and turns (notes/flow-control.md), co-reader serving (notes/peers.md), what a host learns (notes/unreadable-data.md).

## Decisions (Tess)
- **One kind of node**: same binary, run the same way, on a laptop or a rented machine, with any mix of data it reads and data it cannot. A node hosts a label by storing it and serving it to its role key holders. Reading is per label (a read secret held or not), so one node may read some groups and host others it cannot read; a machine that reads its own configuration group and hosts everything else unread is one osis instance.
- **No separate program**: hosting is part of the node, started by the one long-running command (`osis serve`), configured by `host.0^` on the node's own thing (spec/data-model.md §9). Config as osis data lets any admin of the node (the account's nodes) configure it remotely; it is never in the node card; absent means not hosting.
- **osis-host is its own crate below osis-node**, so the compiler keeps hosting away from the engine, keys and sync state; the node hands it public data only (`HostConfig`), and tools/policy.py fails closed on any new decrypting call (`host_blind`).
- **Its own `Store`, not raw `Backend` rows**: a node hosting a label it also reads holds the read secrets on the same machine, so wraps and blobs surviving a delete in freed pages would break spec/requirements.md Deletion; Store deletes shred. Not the node's store: that would hand the host the store holding actor secrets, and engine and hosting would contend on one lock. Accepted cost: a label both read and hosted is stored twice (no dedupe across the two stores).
- Host and co-reader serving share osis-proto's serving engine but not a store, chosen by listener: serving entries the node can read and entries it cannot from one store would make hosting depend on key state, or make co-reader serving durable and authoritative.

## HostStore (`core/host/src/store.rs`)
- Implements osis-proto's `LabelStore` on its own osis-store `Store`: one table, blobs in the store's blob area (bytes once per host, reference-counted). Rows: label meta (log ID, head, counters), host totals (labels, entries, bytes), steps, claim sets, entries (wrap, stamp, size, add seq, pending time, expiry), tombstones, log records by sequence number, blob reference counts, sweep indexes by time (expiry, pending deletion, tombstone drop, claim-set drop), replication positions; per-step indexes (`V`/`W`), head keys (`K`), claim index (`H`), blob prefixes (`R`).
- Every removal is `Shred::Yes`; overwrites are `Shred::No` (a promotion wraps the same blob key, and the entry's removal later shreds every earlier version on its path), so deleted wraps are unrecoverable once committed (forensic test `hygiene::deleted_wraps_unrecoverable`).
- A mutation's writes apply together to the open store transaction (`Suspended` between calls, `Store::resume`); it commits per mutation, or once per hub batch (`defer_durability`/`durable`); a failed write aborts the open transaction and fails the batch's `durable`; a failed commit recovers the store in place (`Store::reopen`). Reads take `&self` (`LabelStore`), so the store sits in a `RefCell`.
- Log ID = BLAKE3(instance seed || label)[..16], the seed random per storage instance, so a wiped host invalidates old cursors.
- **Sweep** (`sweep(now, budget)`): at most `budget` index rows (the hub uses 1024 and asks for another tick at once while work remains), one commit per label: expiry (no tombstone, no record); due timed deletes in time order (tombstone, Deleted record); tombstones after `TOMBSTONE_LIFETIME`, and with them the log up to the position the entry went at; claim sets `claim_keep_ms` after their step was superseded (time from the store's `Clock`).
  - Every durable removal, expiry included, puts a `Y` row holding its log position (the Deleted record's, or the head's at an expiry) and whether it was a deletion; only a deletion's `Y` row drops the tombstone (an expired blob may be added and deleted again). The `Y` and `G` rows dropped count against the budget, a label's highest due `Y` row only once its trim is done, so a budget the due `Y` rows fill still progresses; a trim cut short keeps that row and raises the horizon to the last row dropped.
  - An index row that does not parse or names no held label is dropped; a failing sweep (storage) backs off 1 s.
- **Log trim**: also to `log_keep` records in steps of 1/8. Serving: a cursor of the label's `log_id` that `log_after` no longer reaches and not past the head is trimmed (Error 15, the client reconciles); another `log_id`, a cursor past the head, or a lost replay gets Error 10.
- Host byte totals count an entry's bytes once per label holding it. Counters (rate windows) are in memory: a restart resets them.

## Host policy (`HostPolicy`)
Every knob is settable by field name in `host.0^`'s `policy` map (`HostPolicy::set`; a bad one is a diagnostic and the defaults hold). Defaults:
- Per label: `cap_entries` 2^20 and `cap_bytes` 16 GiB (code 12, new entries only). Host-wide: `max_labels` 2^20, `max_entries` 2^26, `max_bytes` 256 GiB (new entries code 12; a new label's genesis Register gets Error 12 via `LabelStore::admit_label`, which answers 14 for a label outside the admission, spec/wire.md §11.2).
- A registered step and its claim set count toward `cap_bytes` and `max_bytes` (the set until the sweep drops it). Past them `push_step` refuses a genesis step (12) but takes a child step without its set, and a child step past them even without its set once per `over_cap_step_ms` (1 h) per label, else Error 12 (`Meta::over_cap_until`, durable). Why: a refused rotation would leave a removed holder's open and write keys valid at that host, and anyone may fill a host to `max_bytes`; only a label's own admin spends that room, so outsiders cannot starve an honest label's rotation, and growth past the caps is at most `max_labels` bare steps (about 300 B) per hour. A wait past one interval (clock set back) counts as over.
  - The node keeps its open on a Register refused 4, 12 or 14 and registers again at a later pass (each resync), so the label stays synced, not stranded, while it waits; the rest of that pass waits with it (nothing goes under the old keys). Steps queued behind a refused one each wait an interval: `reregister` registers the recorded child of the host's head (the older rotation) before issuing one at the newest epochs, so k rotations at a full host take k intervals (`rotation_at_full_host_waits_spec_sync_5`).
  - Forgetting old steps instead was rejected: a path walk from genesis is how a node verifies a head it has not recorded.
- `deposit_factor` 1 × the spec minimum budget (64 + 4 per head claim slot entries of 32 KiB); `claim_keep_ms` `ROLE_KEEP` and `tombstone_ms` `TOMBSTONE_LIFETIME` (neither may be less); `log_keep` 2^20.
- Fixed one-minute windows per label: `deletes` 20 000 (timed ones count), `deposits` 600, `registers` 600 (steps pushed; a repeat of the head is free; a recorded path registered at a new host goes at that pace), `relays` 6000 and `relay_bytes` 32 MiB (relay-only pushes). Rate limits answer code 4.
- Connections: `max_connections` 10 000; when full they are shared by source (`Hub::accept_from` closes the newest connection of the source holding the most if it holds two more than the newcomer's, else the newcomer; `osis_transport::evict_for`; sources from `Connection::source`: IP, IPv6 /64, unknown = one source); the listener takes at most `max_connections` transport connections (`link::serve`, shared by source the same way). `hello_ms` 10 s (no Hello: closed). `max_queued_bytes` 48 MiB unread per connection (then dropped; at least `SEND_QUEUE`). `max_buffered_bytes` 512 MiB of partial frames over all connections (the connection holding the largest is closed).
- Ephemeral entries: `ephemeral_bytes` 16 MiB per label and `ephemeral_total` 1 GiB, in memory (code 12; past the total the label charged most gives way; notes/ephemeral.md).
- Reasons behind spec rules (§5 Host caps): an ephemeral upload refused for its cap reaches no holder through that host until room appears; entries deleted at a host's total cap may be brought back by nodes holding them.

## Hub, replication, driver
- **`Hub`** (sans-I/O, tokio-free with `--no-default-features`): one `ServingSession` per accepted connection; `Changed` to every connection and replicator; `Relay` to the label's subscribers on other connections (bytes shared, `Relayed::blob` an `Arc`). Every public call is one store transaction (one commit per input, so at most one shredding root write; on a failed commit nothing it would send goes and those connections close); `tick` commits its sweep on its own, so a failing sweep backs off. `tick(now)` runs the bounded sweep, Hello deadlines, replication work and timers; `next_due(now)`. The simulator drives it directly (`World::host_of` runs a node's hub the same way).
- **Replication** (`Replicator`, push only, since download needs an open): per dialed peer a `ClientSession` walks each label's log (labels enumerated 256 at a time, at most 64 labels examined per call) from the position the peer acknowledged (stored per peer key and label with the log ID): Register per Head record (with the claim set while held), Upload of stamped entries whose latest add is the record. Deposits, deletions and pending times are not relayable (their signatures are not kept). One batch (256 records or 4 MiB) in flight; its position is stored when the session has no outstanding request and no reply refused for now (codes 4, 12); otherwise the label is retried from the same position with back-off 1-60 s.
  - A log trimmed past the position replays per run of steps sharing a write key: the run's steps, then the live entries whose stamp verifies under that key (O(entries × runs) signature checks: a new peer, or one a removal's lifetime behind, of any label with a removal older than `TOMBSTONE_LIFETIME`). Entries stamped under keys older than the peer's head get code 9 there (a diagnostic only): writers re-stamp.
  - **Echo suppression**: the store remembers in memory (up to 2^20 entries) which connection's peer key last added or replaced each entry, and a replicator does not send an entry to the peer key it came from, saving the upload of what the peer just sent (a held stamped entry changes nothing, so replication settles either way). It needs the dialing host to authenticate with its static key: the driver dials peers with `dial_as` and its listen secret (an ephemeral dial key would defeat it, and then every entry goes back once).
- **Driver** (`driver::run(hub, Endpoint { transport, listeners, secret }, peers, clock, control, log)`, tokio, feature `driver`, default; generic over `T: Transport`): sessions are osis-transport `link` sessions (notes/networking.md): `link::serve` turns every stream a dialer opens into a `Link` (peer key = the transport's), each a hub connection. The hub task owns hub and store, its calls in `block_in_place` on a multi-thread runtime; a reader task per link hands over one read at a time (notes/flow-control.md, Turns); writes go into an unbounded queue with a byte count (`LinkTx::send` refuses above `max_queued_bytes` not yet taken by the transport; one run always fits an empty queue); a dial task per peer (`link::dial` with `dial_as`, seeded `Backoff` 1-60 s; stops on `BadUrl`/`UnknownScheme`). A connection without sessions for `hello_ms` is closed; session ends wait at most `FINISH_WAIT` 10 s for the finish; ticks when due or every 60 s; `Control::{Tick, Admit, Accept, Shutdown}`.
  - Tests: tier 1 runs it on `InProcess` under tokio (a perfect network; not `Sched`: the driver spawns tokio tasks, and the sim drives sans-I/O engines, not drivers); the slow-reader cap is a `link` unit test (`InProcess` never stalls a writer). Tier 2 (tests/it/quic.rs, ignored): two drivers on QUIC replicating.

## Hosting in the node (`sync/host.rs`, `sync/driver.rs`)
The only way a host runs. The node reads its own `host.0^` (any admin of the node thing may write it) once per engine change and hands its driver `Action::Host(HostConfig)` (none: stop) when it changed: the host key, listen URLs, the admission, replication peers, the policy (knobs over the defaults) and per-label caps (`LabelCaps`, in place of `cap_entries`/`cap_bytes`).
- **Admission**: `open` (any label) or `own`: the label IDs of its account's own groups whose hosts name the host key, plus `labels`. `SyncEngine::owns`: the record chain reaches the node or its account (`set_person`; osis sets `me` at start, kept by `host_restart` when the driver starts, else a node that only hosts admits nothing on a real runtime). No role grant counts: a stranger's grant, read or admin, to the account or the node, on the group or an actor above it, never admits a group (Tess's decision, as for the inbox accept step: spending this node's storage on someone else's data takes `open` or an explicit label). Label IDs only, no key state.
- The node learns a new group's label by syncing the labels up its record chain, so the first registration there may come first: a registration refused for now (4, 12, 14) is `Phase::Refused`, opened again after `retry_ms` doubling per refusal up to `resync_ms` (`refused_for_now`; `Requests::refusals` keeps the last code until it opens), never Stranded nor reopened at once. Status: `LabelStatus::not_admitted` names the hosts that answered 14 (not admitted); osis shows `SyncState::Refused` (naming them in `GroupSync::refused_by`) when there are some and the label is open at none, `Unreachable` for 4 and 12 when open at none, and synced when it is open at another host (the data is at a host). `wait_synced` waits on a refused label (no deadline); the CLI, past `--timeout`, says which host does not admit which group. Tests `runtime::own_serving_node_in_process_spec_data_model_9` (`config_mut` shortens `retry_ms`), `serving::own_admits_only_owned_groups_*` (a `host_restart`), tier 2 `localhost::own_serving_node_localhost`.
- **The host secret** is a local record (`y/z`, shredded), made when hosting starts and shredded when `host.0^` goes. It is not the dialable key, so a `label.0` host list never links to `reach.0`. A config whose key is no longer the host secret's (hosting stopped since it was emitted) is skipped, never making a secret (`host_secret_for`, test `host_secret_not_revived_by_stale_config_*`).
- The driver runs osis-host's driver as a task over its own transport (`Arc<T>`), listening at each URL with the host secret and reporting `HostStatus` (`Listening(addresses)`, `Failed`). A change of admission or caps goes in place (`Control::Admit`); anything else restarts the task with its hub kept. The node's own dials of the host key go over an in-process `link::pair` (`Control::Accept`), no socket, so the sync engine sees an ordinary host; dials made before the host listens wait in its control channel. Host sessions get the hub over the host store whatever the node reads; dialable and LAN listeners get co-reader serving over the node's own entries.
- **The host store's lifecycle**: opened by the holder (`Shared::host_store`: `<store>/host.redb` with key root `<store>/host.root`, or the `MemStore`'s); erased when hosting stops (spec/requirements.md Deletion; `Shared::erase_host_store`: the root erased first, `RootStorage::erase`, which crypto-shreds the rest, then the files). The driver erases after the host task ended (the hub, and the store, dropped) when the engine holds no host secret, so a driver shutdown never erases; a driver start with no host secret erases what a stop no driver carried out left; a node that never runs a driver (`Runtime::None`) keeps the files until one runs. The store records its host key (local record `host key`, written before any entry), and opening one that records another key, or none, erases it first (another key: stopped and started again with no driver between; none: new, or half erased by a crash, such as `host.redb` left without `host.root`). Test `serving::stop_serving_erases_its_store_spec_data_model_9`.
- **Isolation**: osis-host depends only on base, crypto, label, proto, store, transport and tokio, and names only allowlisted osis-crypto and osis-label items (tools/policy.py `host_blind`, fail-closed: a new `open*`, `kdf*` or secret type fails policy); osis-node names only `osis_host::{driver, Hub, HostStore, HostConfig, HostPolicy, Admission, LabelCaps}`.
- Builds: P2P is on in every build; the LAN loop (`lan`) only in `cargo test-net`, no shipped manifest enables it (issues/node-host-unify.md).

## Abuse (open; deferred until a real problem, Tess)
- Today: stamps (only writers add content), a deposit budget per label, per-label storage caps, per-label rate limits on deletes, deposits, registers and relays, per-label ephemeral caps, admin delete. Anyone may register a label up to the host-wide label cap (then Error 12, so squatters can exhaust it), and any writer can fill a label's cap with junk the host cannot tell from data. Inbox-specific limits: notes/inbox.md.
- Per-holder limits would need pseudonymous holder keys (linkable uploads, forbidden) or anonymous credentials (zkgroup-class crypto). If paying accounts come, the credential goes to one host bound to (host, label), never into the relayed `label.0` chain.
- Abuse limits for relaying: issues/p2p-own.md.

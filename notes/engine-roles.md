# Engine: role commits, keys and rotation
> Summary: How the engine reads and writes role-class data: edge writes from `roles.0` deltas, addenda written by the state rule, `secrets.0` ingestion and established epochs, the roles `secrets.0`/`keys.0` deltas need, may-grant grant boxes, flows hooks, the flows' readings (departures, finalizes, the cascade), the role flows (accounts, pairing, own secrets again, grants, lowering writes, epoch introduction), the rotation and secrets invariants, the cover check's own self-removals, head keys. Rules: spec/permissions.md, spec/crypto.md §4; reasons: notes/permissions.md, notes/keys.md. Not here: dropping lost access (notes/engine-lost-access.md), writer-side role rules (notes/engine-apply.md, Writer side).

## Principle
Role-class data is held data like any other: perm reads `roles.0` as edge writes from the held set, epochs are established only from held valid role commits, and everything the node owes because of roles (addenda, finalizes, rotations, re-seals) is derived from what it holds, never queued by arrival. Every encrypting path runs the rotation cascade first, so nothing is encrypted to a holder the timeline has removed.

## Edge writes from `roles.0` deltas (spec/permissions.md §2)
- An entry the delta creates (it carries the entry's dot) sets the grant it reads; a reset of a known entry dot removes it (keys learned from the creating deltas, `ix.holder_keys`); a delta writing inside an entry it did not create is bad input (`check_holders_parts`, in `examine`, so the writer refuses it too).
- A reset whose key is unknown (its creation not held) names no holder: the commit's other writes go to perm and the commit stays in `unresolved`, derived again when keys arrive (`resolve_unresolved`) and once after an open has read every commit (it reads them in `ts` order).
- A grant writes a new entry (`flows::put_edge`, `Op::Put`: crdt `put_new`) beside the reset of the holder's current entry (`edges::reset_current`), never into a held entry: nested field writes would compose two changes wrongly (a role raise losing an `until`), and one into an entry the walk dropped (still live in the state) left the grantee unresolved for good. Entries the walk dropped stay live in the state; nothing reads it.
- Perm consumes these as abstract edge-write records (`validity::add_role_commit`, `PermParts`), persisted per commit in `node/perm` (notes/engine-store.md).

## Addenda (spec/permissions.md §5.2 Addenda, Writing)
- **Write** (`flows/addenda.rs`, state-based, unasked, at each durable transaction's end, at R's own node too): addenda owed per (R, N) as the module doc says (`gather`, `unvouched`, `decide`, notes/addenda.md Rules). Nothing vouches for a role write (issues/role-vouch-contested.md): a role write of a removed party its remover's list does not name is dropped at every node. A judgement gathers (whether R applies, its candidates) and then decides (`decide`: this node's roles, its own counting addenda, the node closure, whether it may write there).
- **The decide is followed by construction**: `Core::addenda_owed` (`Decides`: a `memo::Effects` keyed per gathered removal), settled at each transaction's end exactly where a read moved, so none of its inputs has a trigger to keep. Its reads: the kept gathering (`Indexes::addenda_gathered`, rewritten only when it changes), R held, its own addenda by R first, then this node's role now on each thing where a candidate is left unvouched, as a row (`Core::own_roles`, a `memo::Cutoff` per thing over `Core::role_now`: a role change on the thing leaving this node's role as it was decides nothing, `tests_addenda::a_role_change_elsewhere_rescans_no_candidates`) (own addenda through `Indexes::addenda_keyed`, their bodies and validity: the epoch rule closing one included), the candidates still held, and for a thing owed: the node closure holding it (`Closure::holds`), the record-chain depth and `may_write_on` (minting, delete keys, setting). So entering the closure, a later grant of write (`a_witness_granted_write_after_the_removal_writes_its_addendum_then`), an own addendum ceasing to count, keys arriving each decide again with nothing written for them; time is read through the memo clock (an `until` passing). Another removal's addenda move nothing; one keyed by R decides R once. A write moves R's decide (its own addendum keyed by R), which `write_owed` settles again at once to nothing; owing again right after its own write is a debug panic. A write that fails (`OwnWriteFailed`) is decided again at the next call. The rows are refreshed before each `due`, so a role row derived again to the same value decides nothing (`Cutoff`: a row not refreshed moves its readers). A row is held while a followed decide's last settle read it (`Decides` counts its readers) and goes with the last: a removal answered (every candidate vouched for by its own addendum) or no longer held reads none, so the rows follow the removals still needing a role read (`tests_addenda::answered_removals_hold_no_role_rows`).
- **The gathering** is due again (`Indexes::addenda_due`: every held one at an open, a removal on arrival or its late parts) only when what it reads moves:
  - R's own status in the walk moves (`note_changed`, from the timeline's `Changed.ops`): the only input of a removal not applying, so a removed party's never-applying removals cost no other write anything. A replay changing whether R cuts with its status unmoved changes its edge's history before it: `wake` below;
  - the walk's change naming an edge R writes (`wake`, from the same `Changed`; `Indexes::addenda_wake`, one entry per (edge, R)): its history changing at or before R's `ts` (`Changed.edges`: whether R's write is a cut reads the edge as restored before it; a record of its target coming or going, `created`), or a delta new in the walk stated through it (`Changed.parts`, `Paths::rests`), stamped no later than R and received before it (a candidate applying late, in its window). These are all a gathering reads besides R's status: under stated paths a member joining a holder or another path of a member moving changes neither a cut nor a candidate. A commit's wake costs a lookup per edge and hop it names, whatever its author reaches (`scale::addenda_wake_is_flat_in_the_removed_partys_reach_spec_permissions_5_2`: a removed party's backdated edits and grants, 18 lookups and no removal woken at 10 and 100 things held); a removed party's backdated content judges nothing.
  The gathering is no `Effects` value: it reads the walk before R (edge histories, stated paths), which perm stamps per thing, not per (edge, point); the wake reads perm's own change report (`Changed`) instead, never a list of call sites.
  R's window closes at its arrival (`addenda::window`: received by R's `ts` and before R itself, by the wall clock, strictly earlier milliseconds), so receipts are final once R is held and a commit arriving after R is in no window. Debug builds check, after every durable transaction and at each engine drop, that every removal not due to gather has a kept gathering equal to a fresh one and, unless its decide is due, owes nothing it may write now by a fresh judgement reading roles whole and `writable_split` in full (`addenda::missed`, `Engine::check_missed_wakes`: a missed wake or a read the decide made unstamped; reading the role row unrecorded fails `a_witness_granted_write_after_the_removal_writes_its_addendum_then`). An addendum is positioned after R (applying R moved the clock past its `ts`). Nothing durable: an open re-derives all, gathering each removal once. Tests: `apply::tests_addenda` (counts: `a_role_change_elsewhere_rescans_no_candidates`); the order harness writes none, held-model judges none.

## `secrets.0`, `keys.0` and established epochs
- **Genesis seed** (spec/crypto.md §3; `EpochInfo::genesis`, `ActorEpochs::genesis`): set from the admin history entries opened under a checked secret (the least where entries differ), derived down a derived view (`ActorEpochs::derived`: `kdf("sync genesis", g(base), tid)` per derived admin epoch), persisted with the epochs. A rotation writes it in its admin history box (`osis_keys::rotate`: the one held, else, rotating from none, its new admin secret); `HistoryBox::adds` makes a history add of an admin entry lacking it. Making a thing independent writes the genesis step and its first child (`flows::sync_ids::independent_steps`) as one put of the sync ID's `sync.0` entry (`Op::Put`), so concurrent promotions' entries both stand, read as their join.
- **Pending pieces read together** (`apply::keys::pending_boxes`): a pending role commit's `secrets.0` pieces on one actor are read as one write, so a history box opens with the secret a box in another piece gives whatever order the pieces have (a fresh load and a live ingest read alike).
- **Ingestion** (`atomic::observe_touched`, `Core::ingest_keyed`): a join reads only the box and history-box entries its delta touched (`secrets::touched_keys`; a reset of the value, a field or a map reads the whole state), then the history box of every epoch with a secret held, repeatedly (what `open_histories` reaches over the whole state). One derivation, live and rebuilt: a moved state, a retake, the open's sweep and a rebuild read an actor's whole state by one function (`flows::observe_secrets`; a rebuild runs the open's `reopen_all`), and an actor whose secrets grew by any input (a state, an invalid or pending commit's boxes, a take-up) has everything they may open read again (`flows::reopen_dependents`: `reread` of the actor itself, its applied history boxes and invalid deltas, then of each actor with a box keyed to one that learned, `ix.boxes_to`), so the live index holds what reading every state whole afterwards gives (`apply::keys::tests::a_reading_only_secret_opens_the_applied_history_spec_crypto_4`). Pending boxes stay outside it: a pending commit's boxes are read at its arrival and at each reexamine (`read_pending_boxes`), not when an opener of theirs grows.
- **Established epochs** (`apply/keys.rs`, spec/crypto.md §4): a held valid role commit's `secrets.0` write is recorded with its `keys.0` write (`SecretsWrite::rotated`, whole keysets: flows replace the field); an invalid commit's epochs count for nothing and are never recorded as rotations; its boxes open for reading only (`keys::read_invalid`, spec/crypto.md §4 Reading-only secrets). A held `secrets.0` compaction snapshot keys its epochs (`snapshot_keyed`). A delta found invalid stops counting (`keys::invalidated`, which unsets only the rotations that commit made, never every epoch its history boxes name: else another commit's epoch goes unapplied and a later removal rotation never establishes); valid again it is recorded again (`revalidated`, the keysets before taken as the current `keys.0`). `Core::own_epochs` establishes from these and the held commits. A removal is a keyless reset, so box keys come from an index of held keyed entries, and a write whose removed keys are unknown waits until they arrive, so a rotation received before the one it supersedes is not established. Epochs persist (`k/`), never re-inferred. A `secrets.0` snapshot carries only records at epochs verified here (`vouched_only`, `osis_keys::unvouched`). `Engine::epochs(actor)` exposes the view.
- Late parts (`join_late`, `with_held`): late `secrets.0` parts establish epochs with the commit's held `keys.0` like a whole commit's; a late `keys.0` part applies the held `secrets.0` of its thing again. `note_required` judges a late `secrets.0` part with every held part of the commit and clears the mark when the whole commit fits; the late parts' validity is recomputed before they join (`judge_late`; other aspects' flips go through the re-judge). Judging a late part alone makes a redemption's `secrets.0` overreach (no grantee) when its `roles.0` part came first by a certificate copy.
- **Roles they need**: `secrets.0` and `keys.0` deltas need the highest role they rotate or box (at least write): admin for an admin box, history key or keyset, and for any delta that is not a plain struct (`Fragment::is_plain_struct`: a register write or root reset replaces every field); such a `secrets.0` delta gets no may-grant exemption.
- **May-grant grants** (spec/permissions.md §2) may reset nothing: `put_secrets(.., new_only)` writes fresh puts (`Op::Put`, spec/crdt.md §5.6 `put_new`), and `validity::grantee_boxes_only` accepts its one `secrets.0` delta only when every box and history map is `Fragment::is_put_only_map` over the delta's own dots (`Owned::owns`: no record at another's dot) with keys fitting its grantees; the header must list one delta for the aspect, so a node missing a part judges alike. All from the commit alone: looking up reset dots in an index of held boxes would make validity depend on arrival order. Fresh puts stack live entries per key, so only may-grant grants use them; two puts of one key in one commit do not net out like two commits (same stamp), which no writer does.

## Flows hooks in the engine
- `Core::link_keys` (held link keys, in memory only): derived, each held exactly while `hold_link_key` (until `drop_link_key`) or a followed link names it (`Engine::settle_link_key`), so a link key goes with its followed link, whatever order links are followed, followed again under another seed, or let go. `Mutation::sign_as` signs as one in commit form, `Core::epochs` derives from its seed's secrets (`Core::link_key_epochs`), `ingest_secrets` opens its boxes.
- `DiagnosticKind::Removed` when the node drops a thing's secrets.
- Re-seal is a pull hook for sync (`pass_end`, `own_secrets_candidates` at the end of a complete pass); flows only return what they committed.
- Steps: `Engine::due_step(s)` (derived: this node an admin, an epoch newer than the recorded head registers or a refreshed seed, `flows::sync_ids::due_at`; a deposit-only one not while `keys_write_unapplied`; with the rotations the step registers and whether it is deposit-only, `DueStep`) and `issue_due_step(s)` (`issue_step`: a child of the recorded head in `sync.0`; `None` while a role is blocked). Sync's read module issues it once those rotations are logged under S in its own store, so they are stamped under the old head: issuing in the rotation's own transaction stamped them under the new step's write key, which a store at the old head refuses, while Register waits for them there (a deadlock). Nothing is marked or persisted: a restart re-derives what is due.
- `pass_end` makes the rotations and finalizes due on the thing (`ensure_rotated`) before reading its candidates when any are due: a rotation or a finalize going alone can box or leave out a candidate, and a list read before it named a holder its re-seal could no longer seal, failing the whole pass (`reseal_candidates_follow_the_finalize_before_them_spec_permissions_3`).

## Flows readings
- Departures are recomputed from the timeline (applied lowering edge writes, a finalized timed edge counting as its role's departure) and from state (a box at a current epoch whose holder holds less than that role now), holders re-granted since dropping out, from the thing alone (a holder actor's departures reach it as stale boxes, notes/holder-actors.md). Keys read no clock: an edge past its `until` is no key departure until finalized.
- **Finalize** (spec/permissions.md §2): a node with write about to encrypt under a thing first writes the finalize of each edge there past its `until` of role at most its own (`rotation::finalize_due`, `flows::edges::finalizable`, `finalize_in`): a removal with no frontier carrying the rotation. A departure's commit (a finalize, an explicit removal) rotates only what it can make now (`rotation::departure_rotates`: the roles left that it may rotate, where `wrappable`, the question `rotation_due` asks, which also gives a sync keyset its claim epoch); otherwise it goes alone, the departure uncovered, and the roles stay blocked until a re-seal lets a rotation cover it (`a_finalize_rotates_only_what_its_writer_can_wrap_spec_permissions_2`). A renewal of an ended edge is not finalized first: the grant writes it anew.
- Rotation authority is that of the key signing the rotation (`who`: the node thing, or a link key it holds). A self-removal carries no rotation and the leaver drops what it lost; an explicit demotion runs the cascade on the target, then carries the target's rotation.
- Every encrypting path runs the cascade first (`ensure_rotated`: depth first, the holder actors with key access `who` may rotate, then the thing; each gets its finalizes first): grants, re-seals, own secrets (the mint admin's epochs, with the sync ID). It returns the roles still blocked; nothing may encrypt under those (uncovered, stale, notes/holder-actors.md).
- A rotation boxes the timeline's current holders whose keys are held. A rotation or re-seal boxing a holder travels under the thing's sync IDs (later removals reset their box entries). A holder left out of a rotation (its rotator did not yet hold its grant, or a concurrent one) opens its re-seal only from that piece: the copy under the thing's sync IDs is wrapped under the epoch it lacks. That is the path its grant took, so it reaches the holder wherever a grant would; an inbox no reachable node keeps takes both only over a direct connection, which nothing dials across accounts. Rejected: wrapping that copy under an epoch the holder holds (shows the commit to parties the rotation left out); holding the pass-end rotation until every entry opens (an entry that never opens stalls it, and a concurrent grant leaves the holder out anyway).
- `put_secrets` writes boxes and history boxes as remove + put, so a grant or re-seal re-writing them unchanged (spec/crypto.md §4) still carries them and one live entry per key stays (a nested write into a rotation's entry the holder never held would be unreadable to it); an inbox grantee reads pre-grant content, from the pending grant already (`read_pending_boxes`).

## Role flows
`flows/` and `rotation/`; tests `core/engine/tests/it/flows.rs`; API and engine hooks: notes/engine.md (Public surface).
- A node signs as its node thing (`Core::me`); making an account, pairing and removing a node are the account library's, over the `osis` API (notes/accounts-switch-brief.md). Held link keys (`link_keys`, in memory only) sign in commit form and open their boxes.
- **Own secrets again**: a dependent thing (including one left dependent by its only keyset part turning invalid) with a current holder other than its mint admin, or holding a role with key access on an independent thing, gets secrets of its own again (`own_secrets`, the rotation delivered by inbox to the holders it boxes) from every admin node at the end of a complete pass of its independent's sync IDs (`Engine::pass_end`, `rotation::own_secrets_candidates`). A role commit from elsewhere on a dependent thing, or writing an edge to one (a holding of an independent thing, granted by a node that could not make it independent first), wants that pass: its arrival is noted on the dependent thing's actor (`held::note_arrival`, `reader_of`). A candidate left by a keyset part turning invalid through a commit on neither the thing nor its independent waits for the next pass end of its independent something else wants (issues/own-secrets-waits.md). Admins acting concurrently fork the thing's secrets on its one sync ID (each records the same genesis step, `osis_blob::genesis`, and a first step of its own: concurrent rotations, settled by re-seals and the next rotation); no wait (`SETTLE_MS`) leaves it to one. Candidates come from a scan of `ix.holder_keys` targets per pass end (a measured cost would justify an incremental set). One that cannot be made (a holder's `keys.0` not held, an intermediate uncovered) is undone alone (`Step::OwnSecrets`), reported (`OwnWriteFailed`) and decided again at the next pass end. Until then such a holder actor is boxed by no rotation: its members read nothing new through it, and rotators whose only path at a role runs through it hold no epoch of that role there and stall rather than trade rotations (notes/keys-establishment.md, Uncovered forks rotate). A dependent thing's holding of its dependent record children is derivation, no candidate.
- A grant first gives the target, and a dependent holder, secrets of their own, makes the rotations it may on the holder and the target first (sealing to a holder actor's keyset is encrypting under it) and boxes every granted role's current epochs. Authority: admin on the target, else a may-grant grant (no current grant, its role at most what the granter's paths give may-grant at), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own grant or the author's authority on the target comes only through the holder (admin on it); otherwise it is an explicit demotion with its frontier. A removal of an absent grant (finalizing a used single-use link) resets the holder's current entry, or one of its own delta, and audits the holder's writes on the target.
- Departures are a memo per thing (`rotation::departures`; notes/engine.md Derived values) and read no clock.
- An epoch's introducing commit (`Indexes::epoch_intro`) is the earliest valid commit writing its keyset in `keys.0` (only a rotation does; a box introduces nothing): what a box naming the keyset carries and a certificate of a thing's current keys. Noted from valid role-commit parts at apply; a flip of a `keys.0` part rebuilds the thing's entries and held keysets, so an invalid (backdated, forged) write never introduces or holds a keyset. A dropped `keys.0` body's keysets, `rotation_role` and `overreach` stay, so a compactor keeps knowing them and re-judging needs no body; `uncover` (never received again) forgets them, and a forgotten commit (`unindex_commit`) takes them with it: its parts' judgment rows go through `unjudge_part` and its `keys.0` things' keysets, `epoch_intro` and own keys are re-derived from the parts still held. `boxes_to` is noted from held `secrets.0` deltas of any validity (a lookup for `reopen_dependents`) and goes with a dropped body. Epochs are persisted whenever they change.
- A demotion frontier above `CHUNK_THRESHOLD` is a chunked large value the header links. `Engine::certificates` returns the parts to carry per commit; sync logs a copy's linked blobs (header lists, linked frontiers) under the sync ID with it.
- A rotation's step is issued by sync once its rotations are logged (Flows hooks in the engine).

## Rotation and secrets invariants
- A rotation also goes by inbox to every holder it boxes that held no box at a current read epoch (`rotation::unreached`): a holder with no box at the epoch the commit is wrapped under (a single-use link race's winner, boxed by the sharer's second rotation) could not reach its box, while the re-seal trigger sees it boxed.
- A rotation that boxes nobody writes no boxes field: `engine::secrets::secrets_value` (used by `flows::secrets_in`, apply's observe and the `apply/keys.rs` snapshot keying and `vouched_only`) reads a never-written map field as empty.
- Forgetting on lost access drops plaintext states, `c/` records, wraps and blob keys of unreadable things, not only `k/`, from the derived drop with its pending-grant guard (notes/engine-lost-access.md).

## Own self-removals in the cover check (`rotation::departures_with_own`, spec/crypto.md §4)
- A departure that is the node's own blocks no epoch (spec/crypto.md §4 Encrypting under, Exception): its account's or its own node's always; one whose newest edge write is its own self-removal of another holder (a thing it administers, a link key; `departures::own_leaving`) while that commit waits in `held_wait`. `rotation::others` leaves both out of every walk (encrypting and placing), so the leaver can still seal its removal under the sync IDs it leaves; counted, a removal carrying no rotation blocked its own logging, the verdict fell to may-hold and status judged it held at once. The lost-access trigger leaves such a thing until sync is done waiting (notes/engine-lost-access.md Self-removal drops). Derived from stored commits, so a restart keeps it.
- The node's own departures (its account's, its node's) count nowhere, placed or not (`rotation::others`, inside `blocked_epoch`): the departed party is the node itself. This bullet's rule is for the other holders a self-removal departs.
- A self-removal on things with no sync ID here counts as logged at once (its copies elsewhere are then held back: rare). Other departures (a removal the node did not know of) hold back what it logs.
- An independent thing read through the lost thing is listed, heard out and dropped on its own (`LostScope::Only` takes exactly what it names), so its unsent writes wait for its sync IDs, not the lost thing's (notes/engine-lost-access.md, The drop, Self-removal drops).

## Head keys
- Head keys (`sync_ids/blobs.rs` `matching`): a reading-only secret finds the head's epoch (open, walk) but never yields the write or delete key (stamps and deletes are encrypting under, spec/crypto.md §4).

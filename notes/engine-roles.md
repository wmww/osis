# Engine: role commits, keys and rotation
> Summary: How the engine reads and writes role-class data: edge writes from `roles.0` deltas, `secrets.0` ingestion and established epochs, the roles `secrets.0`/`keys.0` deltas need, invite-grant boxes, key actors and other flows hooks, the flows' readings (departures, finalizes, the cascade), the role flows (accounts, pairing, own secrets again, grants, lowering writes, epoch introduction), the rotation and secrets invariants, the cover check's own self-removals, head keys. Rules: spec/permissions.md, spec/crypto.md §4; reasons: notes/permissions.md, notes/keys.md. Not here: dropping lost access (notes/engine-lost-access.md), writer-side role rules (notes/engine-apply.md, Writer side).

## Edge writes from `roles.0` deltas (spec/permissions.md §2)
- An entry the delta creates (it carries the entry's dot) sets the grant it reads; a reset of a known entry dot removes it (keys learned from the creating deltas, `ix.holder_keys`); a delta writing inside an entry it did not create is bad input (`check_holders_parts`, in `examine`, so the writer refuses it too).
- A reset whose key is unknown (its creation not held) names no holder: the commit's other writes go to perm and the commit stays in `unresolved`, derived again when keys arrive (`resolve_unresolved`) and once after an open has read every commit (it reads them in `ts` order).
- A grant writes a new entry (`flows::put_edge`, `Op::Put`: crdt `put_new`) beside the reset of the holder's current entry (`edges::reset_current`), never into a held entry: nested field writes would compose two changes wrongly (a role raise losing an `until`), and one into an entry the walk dropped (still live in the state) left the grantee unresolved for good. Entries the walk dropped stay live in the state; nothing reads it.
- Perm consumes these as abstract edge-write records (`validity::add_role_commit`, `EdgeParts`), persisted per commit in `node/edges` (notes/engine-store.md).

## `secrets.0`, `keys.0` and established epochs
- **Ingestion** (`atomic::observe_touched`, `Core::ingest_keyed`): a join reads only the box and history-box entries its delta touched (`secrets::touched_keys`; a reset of the value, a field or a map reads the whole state), then the history box of every epoch with a secret held, repeatedly (what `open_histories` reaches over the whole state). An opener's new secrets reopen only the boxes keyed to it (`ix.boxes_to`, `flows::reopen_dependents`).
- **Established epochs** (`apply/keys.rs`, spec/crypto.md §4): a held valid role commit's `secrets.0` write is recorded with its `keys.0` write (`SecretsWrite::rotated`, whole keysets: flows replace the field); an invalid commit's epochs count for nothing and are never recorded as rotations; its boxes open for reading only (`keys::read_invalid`, spec/crypto.md §4 Reading-only secrets). A held `secrets.0` compaction snapshot keys its epochs (`snapshot_keyed`). A delta found invalid stops counting (`keys::invalidated`, which unsets only the rotations that commit made, never every epoch its history boxes name: else another commit's epoch goes unapplied and a later removal rotation never establishes); valid again it is recorded again (`revalidated`, the keysets before taken as the current `keys.0`). `Core::own_epochs` establishes from these and the held commits. A removal is a keyless reset, so box keys come from an index of held keyed entries, and a write whose removed keys are unknown waits until they arrive, so a rotation received before the one it supersedes is not established. Epochs persist (`k/`), never re-inferred. A `secrets.0` snapshot carries only records at epochs verified here (`vouched_only`, `osis_keys::unvouched`). `Engine::epochs(actor)` exposes the view.
- Late parts (`join_late`, `with_held`): late `secrets.0` parts establish epochs with the commit's held `keys.0` like a whole commit's; a late `keys.0` part applies the held `secrets.0` of its thing again. `note_required` judges a late `secrets.0` part with every held part of the commit and clears the mark when the whole commit fits; the late parts' validity is recomputed before they join (`judge_late`; other aspects' flips go through the re-judge). Judging a late part alone makes a redemption's `secrets.0` overreach (no grantee) when its `roles.0` part came first by a certificate copy.
- **Roles they need**: `secrets.0` and `keys.0` deltas need the highest role they rotate or box (at least write): admin for an admin box, history key or keyset, and for any delta that is not a plain struct (`Fragment::is_plain_struct`: a register write or root reset replaces every field); such a `secrets.0` delta gets no invite-grant exemption.
- **Invite grants** (spec/permissions.md §2) may reset nothing: `put_secrets(.., invite)` writes fresh puts (`Op::Put`, spec/crdt.md §5.6 `put_new`), and `validity::grantee_boxes_only` accepts its one `secrets.0` delta only when every box and history map is `Fragment::is_put_only_map` over the delta's own dots (`Owned::owns`: no record at another's dot) with keys fitting its grantees; the header must list one delta for the aspect, so a node missing a part judges alike. All from the commit alone: looking up reset dots in an index of held boxes would make validity depend on arrival order. Fresh puts stack live entries per key, so only invite grants use them; two puts of one key in one commit do not net out like two commits (same stamp), which no writer does.

## Flows hooks in the engine
- `Core::key_actors` (held link keys, in memory only): derived, each held exactly while `hold_key_actor` (until `drop_key_actor`) or a followed link names it (`Engine::settle_key_actor`), so a link key goes with the last followed link naming it, whatever order links are followed, followed again under another seed, or let go. `Mutation::sign_as` signs as one in commit form, `Core::epochs` derives from it, `ingest_secrets` opens its boxes.
- `observe_state` calls `flows::reopen_dependents` when secrets of a thing are learned (boxes sealed to it in other things' `secrets.0` open then; things found through `boxes_to`).
- `DiagnosticKind::Removed` when the node drops a thing's secrets.
- Re-seal is a pull hook for sync (`pass_end`, `own_secrets_candidates` at the end of a complete pass); flows only return what they committed.
- Steps: `Engine::due_step(s)` (derived: this node an admin, an epoch newer than the recorded head registers or a refreshed seed, `flows::sync_ids::due_at`; a deposit-only one not while `keys_write_unapplied`; with the rotations the step registers and whether it is deposit-only, `DueStep`) and `issue_due_step(s)` (`issue_step`: a child of the recorded head in `sync.0`; `None` while a role is blocked). Sync's read module issues it once those rotations are logged under S in its own store, so they are stamped under the old head: issuing in the rotation's own transaction stamped them under the new step's write key, which a store at the old head refuses, while Register waits for them there (a deadlock). Nothing is marked or persisted: a restart re-derives what is due.
- `pass_end` makes the rotations and finalizes due on the thing (`ensure_rotated`) before reading its candidates when any are due: a rotation or a finalize going alone can box or leave out a candidate, and a list read before it named a holder its re-seal could no longer seal, failing the whole pass (`reseal_candidates_follow_the_finalize_before_them_spec_permissions_3`).

## Flows readings
- Departures are recomputed from the timeline (applied lowering edge writes, a finalized timed edge counting as its role's departure) and from state (a box at a current epoch whose holder holds less than that role now), holders re-granted since dropping out, from the thing alone (a holder actor's departures reach it as stale boxes, notes/holder-actors.md). Keys read no clock: an edge past its `until` is no key departure until finalized.
- **Finalize** (spec/permissions.md §2): a node with write about to encrypt under a thing first writes the finalize of each edge there past its `until` of role at most its own (`rotation::finalize_due`, `flows::edges::finalizable`, `finalize_in`): a removal with no frontier carrying the rotation. While it cannot (it lacks a current secret the rotation needs) every encrypting under the thing waits for a re-seal. A renewal of an ended edge is not finalized first: the grant writes it anew.
- Rotation authority is that of the key signing the rotation (`who`: the node, or a held key actor). A self-removal carries no rotation and the leaver drops what it lost; an explicit demotion runs the cascade on the target, then carries the target's rotation.
- Every encrypting path runs the cascade first (`ensure_rotated`: depth first, the holder actors with key access `who` may rotate, then the thing; each gets its finalizes first): grants, re-seals, own secrets (the mint admin's epochs, with the sync ID). It returns the roles still blocked; nothing may encrypt under those (uncovered, stale, notes/holder-actors.md).
- A rotation boxes the timeline's current holders whose keys are held; a removal fires a removal notice on the removed holder's inbox (spec/sync-inbox.md §5 Removal notice); re-seal commits go by a ticket on the holder's inbox and under the thing's sync IDs (later removals reset their box entries). A holder left out of a rotation (its rotator did not yet hold its grant, or a concurrent one) opens its re-seal only from the ticket: the copy under the thing's sync IDs is wrapped under the epoch it lacks. That is the path its grant took, so it reaches the holder wherever a grant would; an inbox no reachable node keeps takes both only over a direct connection, which nothing dials across accounts. Rejected: wrapping that copy under an epoch the holder holds (shows the commit to parties the rotation left out); holding the pass-end rotation until every entry opens (an entry that never opens stalls it, and a concurrent grant leaves the holder out anyway).
- `put_secrets` writes boxes and history boxes as remove + put, so a grant or re-seal re-writing them unchanged (spec/crypto.md §4) still carries them and one live entry per key stays (a nested write into a rotation's entry the holder never held would be unreadable to it); an inbox grantee reads pre-grant content, from the pending grant already (`read_pending_boxes`).

## Role flows
`flows/` and `rotation/`; tests `core/engine/tests/it/flows.rs`; API and engine hooks: notes/engine.md (Public surface).
- An account is created by its node (`Engine::create_account`) in one commit signed as the account: the account at its first epoch (a key actor, admin on itself; its epoch's signing key in `account.0` on its account root D, spec/data-model.md), D (minted with the account as admin, its secrets boxed to the node, its sync ID), the profile and the inbox. Held key actors sign in commit form and open their boxes; nothing persists them. `Engine::certificates` names the account's and the node's own cards for every sync ID.
- Pairing a node not on D's roster is a rotation of the account adding it (`Engine::pair`, notes/engine-validity-epochs.md Writing); one on the roster (stranded) is re-sealed. Either goes as one direct send with the account's and D's certificates and D's `sync.0` commits.
- **Own secrets again**: a dependent thing with a current holder other than its mint admin, or holding a role with key access on an independent thing (its only keyset part turned invalid), gets secrets of its own again from an admin node at the end of a complete pass of its independent's sync IDs (`Engine::own_secrets_candidates`, `give_own_secrets_again`), the rotation delivered by inbox to the holders it boxes. Each candidate may be left for `SETTLE_MS` after the newest role write on it arrived to that write's author (not built: issues/sync-unbuilt.md), so one admin acts rather than all at once; admins acting concurrently fork the thing's secrets and sync IDs (a sync ID each, which every node then syncs and prunes). Candidates come from a scan of `ix.holder_keys` targets per sync ID pass (a measured cost would justify an incremental set). One that cannot be rotated (a holder's `keys.0` not held, an intermediate uncovered) is retried, with a diagnostic, each pass. Until then such a holder actor is boxed by no rotation: its members read nothing new through it, and rotators whose only path at a role runs through it hold no epoch of that role there and stall rather than trade rotations (notes/keys-establishment.md, Uncovered forks rotate). A dependent thing's holding of its dependent record children is derivation, no candidate.
- A grant first gives the target, and a dependent holder, secrets of their own, makes the rotations it may on the holder and the target first (sealing to a holder actor's keyset is encrypting under it) and boxes every granted role's current epochs. Authority: admin on the target, else an invite grant (no current grant, role and invite at most the effective invite), unchecked locally and judged by perm.
- A lowering write is a self-removal when it lowers the author's own grant or the author's authority on the target comes only through the holder (admin on it); otherwise it is an explicit demotion with its frontier. A removal of an absent grant (finalizing a used single-use link) resets the holder's current entry, or one of its own delta, and audits the holder's writes on the target.
- Departures are cached per thing, cleared on any role-class state write, timeline update, held-epoch change or key-actor hold/drop, with no clock horizon.
- An epoch's introducing commit (`Core::epoch_intro`) is the earliest valid commit writing its keyset in `keys.0` (only a rotation does; a box introduces nothing): what a box naming the keyset carries and a certificate of a thing's current keys. Noted from valid role-commit parts at apply; a flip of a `keys.0` part rebuilds the thing's entries and held keysets, so an invalid (backdated, forged) write never introduces or holds a keyset. A dropped `keys.0` body's keysets, `rotation_role` and `grant_overreach` stay, so a compactor keeps knowing them and re-judging needs no body; `uncover` (never received again) forgets them, and a forgotten commit (`unindex_commit`) takes them with it: its parts' judgment rows go through `unjudge_part` and its `keys.0` things' keysets, `epoch_intro` and own keys are re-derived from the parts still held. `boxes_to` is noted from held `secrets.0` deltas of any validity (a lookup for `reopen_dependents`) and goes with a dropped body. Epochs are persisted whenever they change.
- A demotion frontier above `CHUNK_THRESHOLD` is a chunked large value the header links. `Engine::certificates` returns the parts to carry per commit; sync logs a copy's linked blobs (header lists, linked frontiers) under the sync ID with it.
- Contact cards stay in the osis API (`contact_card`): the card composes calls flows already has (an independent thing, a sync ID, certificate placements, a read link) plus the API's local record of the card; a flows call would only move that orchestration below the layer that owns membership and sync.
- A rotation's step is issued by sync once its rotations are logged (Flows hooks in the engine).

## Rotation and secrets invariants
- A rotation also goes by inbox to every holder it boxes that held no box at a current read epoch (`rotation::unreached`): a holder with no box at the epoch the commit is wrapped under (a single-use link race's winner, boxed by the sharer's second rotation) could not reach its box, while the re-seal trigger sees it boxed.
- A rotation that boxes nobody writes no boxes field: `engine::secrets::secrets_value` (used by `flows::secrets_in`, apply's observe and the `apply/keys.rs` snapshot keying and `vouched_only`) reads a never-written map field as empty.
- Forgetting on lost access drops plaintext states, `c/` records, wraps and blob keys of unreadable things, not only `k/`; it runs from the derived drop (`lost_due`) with the pending-grant guard, since a naive "role none now" test counts secrets read from a not-yet-applied grant as lost (notes/engine-lost-access.md).

## Own self-removals in the cover check (`rotation::departures_placing`, spec/crypto.md §4)
- A departure that is the node's own blocks no epoch (spec/crypto.md §4 Encrypting under, Exception): its account's or its own node's always; one whose newest edge write is its own self-removal of another holder (a thing it administers, a link key; `departures::own_leaving`) while that commit waits in `held_wait`. `rotation::others` leaves both out of every walk (encrypting and placing), so the leaver can still seal its removal under the sync IDs it leaves; counted, a removal carrying no rotation blocked its own logging, the verdict fell to may-hold and status judged it held at once. The lost-access trigger leaves such a thing until sync is done waiting (notes/engine-lost-access.md Self-removal drops). Derived from stored commits, so a restart keeps it.
- The node's own departures (its account's, its node's) count nowhere, placed or not (`rotation::others`, inside `blocked_epoch`): the departed party is the node itself. This bullet's rule is for the other holders a self-removal departs.
- A self-removal on things with no sync ID here counts as logged at once (its copies elsewhere are then held back: rare). Other departures (a removal the node did not know of) hold back what it logs.
- sync's `drop_lost` (`life.rs`) drops each thing heard out, and `Engine::removal_done` each whose self-removal is placed (`LostScope::Only` takes exactly what it names): an independent thing read through the lost thing is listed, heard out and dropped on its own, so its unsent writes wait for its sync IDs, not the lost thing's (notes/engine-lost-access.md).

## Head keys
- Head keys (`sync_ids/blobs.rs` `matching`): a reading-only secret finds the head's epoch (open, walk) but never yields the write or delete key (stamps and deletes are encrypting under, spec/crypto.md §4).

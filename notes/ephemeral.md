# Ephemeral data
> Summary: Design (proposal, owner direction of round 13 and its review) for ephemeral data: in-memory things and schema-declared aspects, an axis independent of sync. Ephemeral state is ordinary CRDT state held in memory by every node syncing it: it merges on reconnect, outlives contact with its author and is lost only when no node holds it. The `presence` lifetime ties values to a reachable author instead. Every thing starts ephemeral and is persisted with its owner chain at its first durable write, keeping its tid; ephemeral placements are the ephemeral side of `/group`. Signals become `event` aspects. Covers the API delta, engine, wire (verbatim forwarding, reconnect digests, answers from any holder, reachability for presence), bounds, deletions, spec edits and a five-step plan; also kept: expiry and the all-nodes predicate. Tracking: issues/ephemeral-data.md.

## Owner direction (decided)
- Ephemeral = cheap and disposable, no never-touches-disk promise. Independent of sync: durable or ephemeral, local or synced. All of an app's state lives in osis; the UI drives and is driven by it.
- Both units: ephemeral things (creation record only in memory, same tid derivation and rights) and ephemeral aspects on durable things, declared in the schema. Flags `ephemeral` (a value) and `event` (no lasting value) both kept.
- `create` takes no placement; group ops set groups (same batch for atomic create-and-place). Every thing starts ephemeral and is persisted at its first durable write together with its owner chain's creation records, keeping its tid. No persist call. A thing never given durable data vanishes when every node holding it forgets it.
- Local ephemeral writes: no signing, hashing, encryption or journaling; typed reads, writes, watches, merge, undo alike, in memory. Synced ephemeral writes are signed.
- Ephemeral synced state is ordinary CRDT state in memory at every holder: it survives while any holder keeps it, merges on reconnect (two people keep using a shared ephemeral window while one is offline; the states merge when they reconnect), and a new subscriber gets current state from any holder, ideally sent to it alone. Dying with the author is an optional per-aspect lifetime for presence-like data, not the default.
- No exception to convergence: ephemeral state converges among the nodes holding it; author-tied values converge once every holder notices the departure (like expiry).
- Lease only as a backstop: `MAX_LEASE` 20 min, keep-alive 15 min; no chatter while a path to the author exists; act at once when it drops.
- Ephemeral placements of ephemeral things approved (side effects below). Signals folded in, fewest concepts.

## Model
**Kinds of aspect.** The key decides, by schema flag: durable (default); `ephemeral` (a value held in memory); `presence` (an `ephemeral` value whose writes live only while their author's session is reachable); `event` (an ephemeral write with no lasting value: the former signal). The writer's key decides the path; merge needs no schema. Core aspects are durable, `/group` aside (placements). Retention does not apply to ephemeral aspects; expiry does.

**Holders.** A node holds the ephemeral state of the things it writes or receives: every node syncing a label whose closure holds the thing, while it runs. Holders keep it until they restart, stop syncing the label or lose read access. State is lost only when no holder keeps it; a restarted node gets it back from holders when it reconnects.

**Ephemeral thing.** A thing whose creation record no durable commit holds at this node. Tid derivation, creation record and owner are as for any thing. `create(owner)` mints the record and keeps it in memory; nothing is written; holders keep the records the state they hold names. Invariant: **the durable set is closed under owner**, so a durable thing never has an ephemeral owner.

**Persistence (promotion).** The first commit with a durable delta on an ephemeral thing T (a durable aspect of T, by any node that holds T's record and may write T) also carries `/created` of T and of each ephemeral thing on T's owner chain, top down, and makes T's ephemeral placements durable (below). Same tid; ephemeral aspects stay ephemeral; ephemeral values never become durable: the app copies a draft's content into a durable aspect in the same batch (`set`). Reason: a durable write anchored at an ephemeral dot hides once no holder has it, and a durable writer delta cannot carry foreign stamps. Two nodes persisting T concurrently both carry the same record (idempotent). A membership operation on an ephemeral thing first persists it by its own content commit (membership commits cannot carry `/group`), then runs. A durable thing never becomes ephemeral again.

**Ephemeral placements.** `/group` is the one durable aspect with an ephemeral side: a group op (`place`, `unplace`, subgroup add or remove) whose item is ephemeral is an ephemeral write into the group's `/group`, held and merged like any ephemeral state, needing write on the group. The `/group` read is the join of both sides (below), so the item shows in the group and in its `/groups` and its ephemeral data routes under the group's labels. When the item persists, the persisting commit adds it durably (with the placement's expiry) and an ephemeral reset removes the ephemeral element. An ephemeral thing can thus be a group of ephemeral items, a draft placed in a folder lands there at save, and nothing durable names a thing that never persisted. A group op on a durable item is a durable write and persists the group. Side effects, all minor: an ephemeral `unplace` concurrent with the item's persistence loses to the durable add (add wins, as for any concurrent add); a persisting node without write on the group cannot make that placement durable, so it stays ephemeral and a `PlacementNotPersisted` diagnostic names it (a writer of the group fixes it with `place`); a durable `/group` naming an ephemeral tid (a raw path op) is a reference that may dangle.

**Rights.** An ephemeral thing has no membership-class aspects (writing one persists it), so a node's role on it is its role on a new thing owned by the nearest durable thing on its chain: the rule already used for things created in the same batch. Ephemeral writes need what the durable write would need. Readers cannot write ephemeral data, presence included (spec/requirements.md: readers only read). Remote ephemeral parts are judged by the sender's current roles (no timeline: no history); a roster change re-judges presence contributions by author and drops those no longer allowed. Merged state a holder sends on behalf of others is judged by that holder's rights, as a compaction snapshot is by its author's (spec/permissions.md §5.2): a writer can forge others' ephemeral writes, the same class as snapshots today.

**Reads and merge.** An aspect reads the join of its durable state and its ephemeral state (spec/crdt.md §4.1); normally one side is empty (both: `/group`, or schemas that disagree; the join is defined). `ephemeral` state is one joined state per expiry class: own writes and every received part join into it. `presence` state is kept per author session (each holding only that session's stamps); the read is their join, and dropping a session is un-merge of that author (spec/crdt.md §4.6: its writes go, its sequence records stay as hidden anchors). `event` aspects always read absent. Expiring ephemeral writes follow spec/crdt.md §4.7 in memory. So ephemeral state converges among holders under any delivery order; presence converges once every holder has seen the author's departure.

**Deletion.** `delete(T)` on an ephemeral thing writes the usual resets. A thing in no labeled closure is then freed at once (record, state, undo entries, the ephemeral things it owns; the tid reads unknown), so short-lived UI things cost nothing. A synced one keeps its record and tombstones while holders run, since dropping them would let a holder's older copy revive the values.

## API delta (notes/api.md, applied with step 1)
- `w.create(owner) -> Tid`; `Place`, `create_expiring` go (expiring placements stay `place_expiring`).
- Schema DSL: `aspect /win/notes: list<tid> [ephemeral];` `aspect /doc/cursor: map<tid, Cursor> [presence];` `aspect /call/ring: Ring [event];` (`flag` cases 4 `ephemeral`, 5 `presence`, 6 `event`; `signal` items, `signal_def` and schema field 4 go). `AspectDefaults` gains `ephemeral: Durable | Ephemeral | Presence | Event`; untyped `Ak::ephemeral()`, `Ak::presence()`, `Ak::event()` for generic tools and the CLI.
- Writes: unchanged calls. One `Write` may mix durable and ephemeral ops: validated as a whole, applied locally at once (one dispatch); the commit and the envelope travel separately, so a peer may see one without the other. `retention(..)` on an ephemeral write and any op but `set` on an event aspect are `Invalid`. `commit()` returns `Committed { id: ChangeId, ts }`, `ChangeId = Commit(CommitId) | Ephemeral(EphemeralId)`; a batch with both halves is one change (one `ts`; revert of either reverts both).
- Watches: unchanged. Each event reaches every `on_change` callback once (never coalesced, never in state; a `Watch` on an event aspect stays `None`). `CommitInfo.id` becomes `ChangeId`; a remote ephemeral change names the node whose body delivered it (verifiable authorship only, notes/api.md Attribution); a presence value dropped at its author's departure fires `Remote` naming that author's last known node.
- `created(t)`: `Created.commit: Option<CommitId>`, `None` while ephemeral (`ts`, `node`, `actor` from the creating batch or body, `received` from its arrival).
- Undo, redo, revert, query: own ephemeral batches of this session are changes (`CommitKind::Ephemeral`). Thing and Group scopes cover durable aspects and ephemeral things; an ephemeral aspect of a durable thing (cursor, selection) is in scope only when named by `Scope::Aspects`, so document undo never steps through cursor moves. Remote ephemeral changes and own ones from before a restart have no log: revert is `Invalid`. `Config.ephemeral_history` (default 16 MiB) bounds the log; older batches are `NotUndoable{Compacted}`.
- Gone: `send_signal`, `on_signal`, `on_signal_in`, `Target`, `SignalEvent`, `Signal<T>`/`SignalKey`. Device targeting is dropped (no user; a value can name a device). A group-wide event goes on the group thing.
- Errors: none new; `UnknownThing` for a vanished tid. Diagnostics: `EphemeralTooLarge { tid, ak }` (a part not sent), `EphemeralRefused { label, node }` (incoming growth over a cap), `PlacementNotPersisted { item, group }`. `NotSynced` stays only for a durable placement into a closure with no label.
- Text sessions on an ephemeral `text` aspect apply each edit at once (no idle commit).

## Local engine
- Module `osis-engine` `ephemeral/`, owned by `Engine` beside `Core`, never in the store or the journaled indexes; under the handle's one lock. `Eph { session: [u8; 32] random per open, next counter, things: Tid → record, aspects: (Tid, Ak) → { classes: expiry → state | sessions: session → classes (presence) }, reach (presence, below), growth accounting per label and sender, log, timers }`.
- Stamps: `ts` from the engine's HLC (an accepted body advances it like a commit); dots of source `Commit(session)` (spec/crdt.md §2.1; no new source kind) with counters from the session counter. Node-form counters are never used (they must stay contiguous and survive restarts). Ops resolve against the read view with the same `osis_crdt` code as durable writes. A local ephemeral write is an HLC tick, an op, a join and a watch event: no store transaction, signature, hash or encryption.
- `Write` splits ops by key: durable ops into the `Mutation` (plus chain records and placement conversions of the ephemeral things it persists), ephemeral ops into an `EphBatch`. The mutation commits first; if it fails, nothing applies. Then the batch applies (cannot fail after validation) and the engine queues `Event::Ephemeral { changes, info, events }` (replaces `Event::Signal`), dispatched like commit events.
- Reads (`read.rs`): join the durable state with the ephemeral state when both exist; synthetic aspects and `groups_of` include ephemeral data; `created` reports records without a commit. Perm: an ephemeral thing's role through its nearest durable owner.
- Undo: the log keeps per own batch its deltas and the undo buffer of the positions it touched, captured at write time (register values, removed content, presence at the "absent before" position): O(change), never a copy of the aspect. Inverse writes follow spec/crdt.md §4.6 against the current state and apply as a new batch. Past `ephemeral_history` the oldest entries go.
- Restart: everything ephemeral is gone locally and the next open draws a new session; on reconnect the node merges back what holders kept. Own writes from the old session come back as other nodes' state.

## Synced ephemeral data
### Envelope (replaces the signal envelope)
- Same framing as today: a blob with no expiry and no commitments, at most `MAX_EPHEMERAL` = 64 KiB, wrapped under the label; publish auth under the label's write or deposit key (domain renamed `"osis v1 ephemeral publish"`). Plaintext: padded canonical `[EphemeralBody, signature]` by the sender node (domain `"osis v1 ephemeral"`).
- `EphemeralBody := [node, actor, ts, session, records, parts, reach, digest, want, flags]`:
  - `records`: creation records of the ephemeral things the parts name and of their ephemeral chains, plus durable ones whose creation commit the sender has not seen placed under the label.
  - `parts`: `[0, tid, ak, Opt(schema), Opt(expires), fragment]`, a state-form fragment (spec/crdt.md §3 with the Commits table; any sources; a `presence` part holds one session's stamps), or `[1, tid, ak, Opt(schema), ctr, value]`, an event.
  - `reach`: presence reachability, `[session, Opt([session*])]` (a path, or none: a withdrawal).
  - `digest`: in a join request, `[tid, hash16]*` over the sender's ephemeral state for the label (hash: BLAKE3 of the thing's (AK, canonical state) list, first 16 bytes; equal states encode equal). `want`: in an answer, the tids whose state the answerer lacks or differs from the digest. `flags`: `done` (last body of an answer), `skipped` (the answerer left out parts it may not vouch for).
- Entitlement as for blobs (spec/sync.md §3): one envelope per label holding the parts whose things are in its closure (durable plus ephemeral `/group` sides) and readable by its actor. A part too big for one envelope is not sent (`EphemeralTooLarge`).
- Receiver: decrypt, verify the node signature and its chain like a commit (drop the body when the chain is missing), check records hash to their tids, judge each part by the sender's rights and drop failures, then join.

### Messages and server role
- `Ephemeral [24, 0, label_id, blob, wrap, auth, to, from, pick, via]` (replaces `Signal`; `Poke` is not needed): `to` `Opt(handle)`, deliver only to that subscriber; `from` `Opt(handle)`, set by a serving node to the publishing connection's handle; `pick` `Opt([handle*])`, deliver to one subscriber the serving node picks outside the list (needs the label opened); `via` up to `MAX_HOPS` 8-byte route tags (below). `Left [26, 0, label_id, handle]`: a serving node tells subscribers that a connection which published under the label closed or unsubscribed.
- A serving node (server or member peer) keeps per (connection, label) a random handle, unique per label, whether it published under the write key, and its subscription age. It forwards a body to every other subscriber, or as `to` or `pick` say; for `pick` it prefers the oldest subscriber that published under the write key. It stores and merges nothing (blind): its memory is the handles.

### Propagation, reconnect, joiners
- **Writes.** A writer sends each body to every connection holding the label open, with `via` = the route tags of those connections. Route tag = `kdf("ephemeral route", label read secret, server static key | peer node tid)`, first 8 bytes: opaque to servers. Per label at most one body waits per connection: new batches join into it until the connection takes it (latest wins); events queue beside it, at most `EVENT_QUEUE`.
- **Forwarding.** A holder that receives a body whose parts changed its state forwards it verbatim (same blob and wrap, its own publish auth) to its connections holding the label whose tag is not in `via`, adding their tags; a body that changed nothing, or whose `via` is full, goes no further. It also forwards it under other labels it syncs whose closure holds the parts' things, as a new envelope of the same body. So partitions bridged by a holder (two servers, a member peer) converge, and a group on two servers that every member uses carries no duplicate forwards. Verbatim forwarding keeps the author's signature, so a reader can bridge.
- **Reconnect and join.** After (re)subscribing a label, a node sends a join request: a body with its `digest`, routed by `pick` (paged over several bodies if large). The picked holder answers addressed to it (`to`): the parts whose hash differs or that the requester lacks, of things the answerer may write, then a `done` body with `want`. The requester joins them and broadcasts its own state of the `want` things (now merged) to every connection; everyone joins and forwards on change. If the answer is `skipped`, or no `done` arrives before the picked handle leaves, the requester asks again with that handle in `pick`'s list (at most once per subscriber). Alone on the label, nothing answers and nothing is lost. So the two-person window merges on reconnect, a restarted node gets its state back, and a joiner's cost is one holder's answer, not one per holder.

### Presence lifetime: reachability
- For `presence` aspects a holder tracks, per label, which author sessions it can reach: path-vector over its neighbors (a peer connection, or a server handle with the session publishing from it). It announces in `reach`, on change only, its own session (empty path) and each session it reaches with the path through it; a path containing the receiver is ignored, so no loops and no count to infinity. Paths longer than `MAX_HOPS` are not announced. `Left`, a lost connection or a withdrawal removes routes; a session left with none is unreachable at once: its contributions are dropped (un-merge) and the holder withdraws it from its neighbors.
- Backstop against a path that never reports (a hostile server, a half-open connection): a session's contributions also die at `min(ts, arrival) + MAX_LEASE` (20 min) of its newest body, and an author with live presence values sends a keep-alive (an empty body, forwarded like any) every `KEEPALIVE` (15 min). No other periodic traffic.
- The author's own presence state lives in its memory regardless; reconnecting re-announces it.

### Ordering, duplicates, replay
- A body is accepted when its `ts` is within `MAX_DRIFT` of the receiver's corrected clock. Fragments join idempotently, so duplicates and reordering are harmless; replaying an old body re-adds only writes its stamps already lose to or that holders still have. Events are delivered once per (session, counter), in counter order per session (a lower counter after a higher one is dropped). A wrong local clock harms only its own writes.

### Bounds (notes/arbitrary-values.md)
| value | class | at 0 / at infinity |
|---|---|---|
| `MAX_EPHEMERAL` 64 KiB | resource bound (existing) | nothing sent / unbounded frames |
| `MAX_LEASE` 20 min, `KEEPALIVE` 15 min | owner-agreed protocol constants (presence only) | constant keep-alives / a hostile path keeps a departed author's presence forever |
| `MAX_HOPS` 16 (`via`, reach paths) | resource bound: farther holders are not reached by forwarding and farther authors count as unreachable | no forwarding / unbounded lists |
| ephemeral growth per label (config, default 16 MiB) and per sender node per label (4 MiB) | resource bound: a part that would grow past it is refused with `EphemeralRefused` (deduped); that label stops converging at this node until restart or unsync, other labels and senders unaffected | no remote ephemeral data / a hostile writer fills memory |
| event dedup: 64 sessions per sender node | resource bound: the oldest session's counter is forgotten, so its late duplicates may fire again | no dedup / unbounded sessions minted by a hostile writer |
| `EVENT_QUEUE` 256 per label | resource bound: oldest dropped, diagnostic | no events / unbounded queue on a slow link |
| `ephemeral_history` 16 MiB (config) | resource bound: older batches not undoable | no ephemeral undo / log grows with edits |
| server rates for 24 per label (renamed `signals` knob) and for `pick` bodies | resource bound: over-rate bodies dropped; a join retries | best effort anyway / flooding |
Local ephemeral memory is the app's; no cap. State grows with edits and removals while holders run (tombstones), as durable state does.

### Leaks
A blind server sees ephemeral traffic size and timing per label (as for signals), which subscriber is picked, and nothing new: route tags and digests are opaque or encrypted. Co-readers see handles join and leave, reachability paths (which member nodes bridge which), and a node's session change at restart.

## Expiry
- Expiry is death by timer (spec/crdt.md §4.8): the values die at T and the body follows, whatever the deltas' keep bounds. "Keep at least until T" is a retention bound (spec/commits.md §5), a different thing.
- Covers disappearing messages (write-based timer in core; read-based timers and earlier deletion are app writes; core expiry is the hard upper bound and lets a server wipe them unattended) and buffered events (a list aspect with a one-hour default). Cheaper than keep-at-most 0: nothing has to be deleted by hand, and the server does it unattended.
- Leak accepted by owner: a blind node learns which entries expire and when.
- Not provided: server-enforced minimum retention (legal hold). Keep-at-least binds honest nodes; a blind node deletes whatever a delete key or its label delete key tells it to.
- On ephemeral writes expiry runs in memory (typing indicators: `expires_in(5 s).set(true)`); presence needs none: the `presence` lifetime covers it.
- Nothing is kept "until every receiver has seen it": the receiver set is open and nodes die. What must survive every holder forgetting it (restarts) is durable state: the inbox pattern (receiver-owned list, senders append, owner deletes, expiry as backstop) or a list with expiry.

## The all-nodes predicate
"All nodes a thing syncs to" is a state predicate computable at trusted nodes, never a protocol condition. Per label: the nodes with a valid chain that published `/node` under the thing's label (not "every node of every member", which needs rosters readers never see).
- Recency: each node places an expiring `/seen` heartbeat under each label it tracks (spec/permissions.md §4); the live one's value is its last sync of L, absent means unknown. `/seen` is one aspect of the node thing, so its joined read is "last seen anywhere"; the per-label answer comes from the sync layer's record of which heartbeat commits arrived under L, not from the aspect. (A `map<label ID, timestamp>` would give aspect semantics but leave a value-less entry record per expired heartbeat forever.) The heartbeat also carries `stranded`, the one signal a device that cannot open a label's current epoch, or cannot walk to the head because a claim set was dropped, can still send (it deposits without opening the label, under the newest established read secret it holds, which co-members open by history boxes), and what triggers a re-seal; it is placed only after a complete pass at that server (the rotation commits are uploaded before the step, notes/sync.md, so "cannot open" means not boxed, never "not fetched yet"); it fails only when the deposit key changed under it (issues/reseal-triggers.md). Membership (the node card) and recency are separate aspects because an expired register winner reads as absent and the older write does not show through: an expiring re-put of `/node` would drop the node from the membership view when it lapsed.
- Why a durable heartbeat and not a node-card re-put or ephemeral data: a reader's re-put is a deposit that sits in the label's budget until a writer promotes it, so readers × cadence × promotion delay had to fit a budget the spec never sized, and a full budget refuses the deposits that matter (grants into the group, a reader's self-removal, a revoke only readers hold). Expiry frees the budget unattended (no tombstone, no delete, no writer), so a reader holds at most ceil(lifetime / interval) entries at once and the budget is sized from the claim set (spec/sync.md §5). Rejected: deposit new card plus token-delete the old one (a delete and a 30-day tombstone per refresh, reader-side delete flows, rate-limited deletes); ephemeral writes (the asker is rarely online with the reader, and readers cannot write ephemeral data); server arrival times (untrusted, per server).
- Leak accepted by owner: a blind node sees each reader's heartbeat rhythm per label (same class as deposit and expiry times it already sees). Clock skew between the heartbeat's writer and the asker shifts the reading by the skew; lifetimes are days, so no coarse policy notices.
- A trusted node keeps its own local record of the last heartbeat it saw per node, for policies wanting a longer memory than the lifetime; it is a lower bound, not knowledge of the gap.
- Uses: write a new schema form once every node reads it (fixes the read-only old app the header heuristic cannot see), drop old-form history after that, clean up an inbox once every own device has acked.
- Dead nodes: a lost phone's heartbeat lapses and it drops out of "all nodes seen recently" on its own; a policy that needs it gone from membership too waits for an explicit node removal. Never gates deletion at blind nodes.
- "Buffer until all have seen it" = inbox pattern plus this predicate plus expiry as backstop. Fine as a core helper later; not sync machinery.

## Implementation plan
Each step merges alone and passes the gate; notes/api.md and the spec follow each.
1. **Local ephemeral things and aspects.** Schema flags and `AspectDefaults.ephemeral`, `Ak` builders; engine `ephemeral/` (session source, records, joined states, expiry classes, timers); reads joined; `Write` split; persistence with chain records; `create(owner)` (Place gone at every call site); `created().commit: Option`; rights through the nearest durable owner; ephemeral `delete`; event aspects to callbacks; `Event::Ephemeral`. `presence` acts as `ephemeral` until step 5. Interim: a group op on an ephemeral item is a durable group write. Signals untouched. Tests (osis `tests/it/ephemeral`): write and watch with no commit and no store write; the first durable write persists T and its ephemeral owner chain in one commit, same tid; restart on a `Dir` store: T unknown, durable data intact, a durable thing's ephemeral aspect gone; permission on another actor's ephemeral thing; ephemeral expiry under `ManualClock`; events once each, never in state, path op `Invalid`; a mixed batch whose durable half fails applies nothing. Release bench by hand: 10^5 local ephemeral sets against a `BTreeMap` baseline.
2. **Ephemeral placements and undo** (both local). The ephemeral side of `/group`, conversion at persistence (with expiry, `PlacementNotPersisted`), membership ops persisting first; the undo log, `CommitKind::Ephemeral`, `ChangeId`, the scope rule, mixed batches as one change, history cap.

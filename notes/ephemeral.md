# Ephemeral data
> Summary: Ephemeral data as built: `~` aspects on durable things, an axis independent of sync, as much like ordinary data as possible. Local ephemeral writes are memory commits through Core; synced ephemeral data is ordinary signed commits marked ephemeral, held in memory instead of the store at every node holding them and carried by node-sync's ordinary passes: it merges on reconnect, outlives contact with its author and is lost only when no node holds it. A value that should die with its author is an expiring write its author renews (`osis::KeepAlive`); `*` signal aspects reach only connected nodes and hold nothing. Every thing is durable from its creation. Covers the API, engine, wire, bounds, deletion, undo, expiry and the all-nodes predicate.

Terms: **ephemeral** is for `~` aspects: shared with others, never stored.

## Principle (Tess)
Ephemeral data has the same semantics as durable data, just held in memory, with no exceptions. Every ephemeral rule is the durable rule, or follows from "held in memory": lost on a restart (so sessions, counters and spent commits' headers live in memory and go with it, and a restarted node gets state back from holders like a joiner), bounded by memory caps per label (node and host, with a defined refusal), never in a store or bundle, and not kept at hosts past a restart. A rule that follows from neither is a divergence to remove; the ones left are listed under Divergences left.

## Divergences left
- **Demotion frontiers list no ephemeral commit** (spec/permissions.md §5.1), so an explicit demotion invalidates every ephemeral commit of the demoted node, its snapshots included. Downstream of it: the covered drop rule's own-author exception (Memory commits) and the reconcile on a fallen snapshot (`take_memory_invalidated`). Removing it means frontiers listing the ephemeral commits a demoter holds (a permissions change, raised with Tess).
- **Superseded expiring writes** (spec/sync.md §9, six conditions): an ad hoc keep-nothing-after-replacement. Purge on replace cannot take its place as decided: an expiring delta is not covered (so not dropped) before its T, and this rule exists exactly for expiring writes (a moving cursor would hold every move until it expires). A question for Tess in issues/retention-modes.md. The second session for expiring writes exists only for it (a superseded commit is forgotten whole, leaving a counter gap no frontier passes).
- **Delete writes nothing ephemeral** (Deletion): the deleter drops the thing's ephemeral state locally; other holders keep it until restart or expiry.
- **Purge and suspect flags**: a purge request's fall restores no ephemeral delta, a waiting ephemeral part a request names is dropped as never received, and ephemeral aspects are never flagged suspect (`rejudge_purges`, `pending.rs`, `suspect::raise`). Small; nothing writes purge requests on ephemeral aspects today.
- **Never paged** (spec/crdt.md §8): an ephemeral delta and snapshot must fit one blob (issues/eph-unpaged-cover.md).
- **Retention shape fixed** to `writer` with no history given: keeping history cannot hold across a restart (follows from memory); purge on replace and purge are not offered. The redesign's history modes decide what ephemeral gets (issues/retention-modes.md).

## Tess's direction
- Ephemeral = cheap and disposable, no never-touches-disk promise. Independent of sync: durable or ephemeral, local or synced. All of an app's state lives in osis; the UI drives and is driven by it.
- Like ordinary osis data in most ways; its history is "don't care" (neither purged nor kept). On one node it must be very cheap; some overhead is fine when synced, and anywhere when the alternative is special cases or API complexity. Reuse the ordinary commit, delta, validity, sync and host paths unless clearly worse.
- The unit is the ephemeral aspect on a durable thing, declared in the schema.
- `create` takes no membership; group ops set groups (same write for atomic create-and-add). A thing is durable from its creation commit.
- Synced ephemeral state is ordinary CRDT state held in memory by every holder: it survives while any holder keeps it, merges on reconnect (two people keep using a shared ephemeral window while one is offline; it merges when they reconnect), and a joiner gets it from any holder.
- Presence is not a lifetime of its own: a value that should die with its author is an expiring write its author renews (Values that live while their author is there).
- No exception to convergence: ephemeral state converges among the nodes holding it; author-tied values converge once their last write expires.
- Principle C (above): durable semantics, held in memory, no exceptions.

## Model
**Kinds of aspect.** The key's lifetime marker decides (spec/data-model.md §2): durable (none); `~` ephemeral (a value held in memory); `*` signal (an ephemeral write with no lasting value, delivered only to currently connected nodes; anything a late joiner should see is ephemeral state, not a signal). The writer's key decides the path; merge needs no schema. Core aspects are durable. Ephemeral deltas carry the fixed retention `writer` without bounds (Divergences left); expiry applies as to durable data.

**New things are durable.** `create()` puts the creation record in the write's durable commit. Rejected: drafts (a new thing held in memory until its first durable write): nothing needs them (every create in app, chat and CLI writes durable data at once) and no requirement asks for them, while they cost a membership split, records in memory parts, a persistence fixpoint, freeing and draft undo.

**Holders.** A node holds the ephemeral state of the things it writes or receives: every node syncing a label whose closure holds the thing (spec/sync.md §3, as for durable data; a thing no group lists syncs no more), and that label's hosts, while they run. They keep it until they restart, stop syncing the label or lose read access. State is lost only when nobody keeps it; a restarted node gets it back by syncing.

**Rights and validity.** Ephemeral writes need what the durable write would need; readers cannot write ephemeral data. Synced ephemeral commits are judged like compaction snapshots (spec/permissions.md §5.2: a part is valid iff its author could write the aspect at its `ts`, through the ordinary timeline), and un-merged like any commit on revocation. Parts on core aspects are invalid. A part on a thing whose record is not held waits for it (its creation commit, durable).

**Reads and merge.** An aspect reads the join of its durable state and its ephemeral state (spec/crdt.md §4.1); normally one side is empty (both: schemas that disagree; the join is defined). Own writes and every applied ephemeral commit join into the ephemeral state. `signal` aspects always read absent. So ephemeral state converges among holders as any CRDT state does.

**Deletion.** `delete(T)` is one durable commit: T's durable resets and its group removals. T's ephemeral state is dropped at the deleting node with no commit (`Mutation::deleting`; `retention::memory::drop_things`: every held memory part on T's `~` aspects vanishes, spent commits are forgotten, node-sync deletes their entries as `MemoryDrop::Gone`). Limit: other holders keep T's ephemeral values in memory until they restart or the values' own lifetimes end (expiry, `KeepAlive`); T is in none of the groups the delete took it out of, so apps reading those groups do not show it. A copy of a dropped commit arriving at the deleter again applies again (as any forgotten memory commit's does, `forget_if_spent`): only through a label whose closure still holds T (a membership the delete could not remove, a concurrent add). A delete has no wire marker (resets plus removals look like any clearing write) and the per-dot resets only the deleter could write, so a receiver-side clear is not plain; a durable floor aspect or `~` resets in the durable commit would be design changes to the wire. Undoing a delete restores T's durable state only. Undoing a creation does the same as a delete (`Engine::revert_batch`). Tests: `deleted_thing_stays_deleted_at_holders_spec_sync_9`, `undo_of_creation_reaches_holders_spec_crdt_4_6`, osis `delete_resets_ephemeral_aspects_spec_data_model_1`.

## API
- `w.create() -> Tid`; an expiring membership is `w.group(g).expires(e).add(m)`.
- Schema DSL: the key's marker is the lifetime: `aspect win:notes.0~: list<tid>;` `aspect doc:cursor.0~: map<tid, Cursor> [expires: 30s];` `aspect call:ring.0*: Ring;`. `AspectKey::lifetime()` reads it from any key, typed or untyped.
- A `Write` is one commit (notes/api.md Writes), so durable beside ephemeral writes is refused (`Clash`): a peer could see one without the other. A new thing's record is durable, so a `~` write on a thing created in the same `Write` is `Clash` too (write it in a second write). A `delete` writes nothing ephemeral (Deletion). `retention(..)` on an ephemeral write and any op but `set` on a signal aspect are `Invalid`. In the engine `BatchId = Commit(CommitId) | Ephemeral(EphemeralId)`; the API's opaque `CommitId` wraps it.
- Watches: each signal reaches every `on_change` callback once (never coalesced, never in state). A remote ephemeral change's `Origin::Remote(Stamp)` names the ephemeral commit that carried it (its author, verifiable, notes/api.md Attribution). No node targeting (a value can name a node); a group-wide signal goes on the group thing.
- `created(t)`: the creating commit (`ThingStamp.id`), always durable.
- Undo, redo, revert, query: own ephemeral writes of this session are entries (`CommitKind::Ephemeral`); ephemeral commits are transport, not listed (own memory commits and own compaction snapshots never show as commits). Thing and Group scopes cover durable aspects; an ephemeral aspect (cursor, selection) is in scope only when named by `Scope::Aspects`, so document undo never steps through cursor moves. Remote ephemeral changes and own ones from before a restart have no log: revert is `Invalid`. `Config.ephemeral_undo_bytes` (default 16 MiB; the engine's `ephemeral_history`) bounds the log; older batches are `NotUndoable{Compacted}`.
- Errors: none of their own. Diagnostics: `EphemeralRefused { things }` (a cap was hit, Bounds).
- Text sessions on an ephemeral `text` aspect idle-commit like durable ones (harmless; committing each edit at once is not built).

## Local engine
- Module `osis-engine` `ephemeral/`, owned by `Engine` beside `Core`, under the handle's one lock. Ephemeral writes are memory commits in Core (Memory commits below); `Eph` keeps only the undo log, batch counter, unsent signals and delivered relay-only commits.
- Local stamps: `ts` from the engine's HLC; dots of source `Session(node, nonce)` (spec/crdt.md §2.1) with counters per aspect from the store's memory overlay (`counter(tid, ak, nonce)`), contiguous from 1 in each session. Two sessions per open: `Core::session` for plain writes, `Core::expiring` for expiring ones, its nonce the plain one's with the first bit flipped (one rng draw per open: a second draw would move every later tid and blind, and seed-pinned order tests and the judgment vectors depend on commit-ID ties). Why two: an expired delta's range is forgotten, and under the plain session it would leave a gap no snapshot frontier passes, so nothing later of the session would be covered.
- Fresh sessions within an open (`Core::fresh_session`, from the validity pass in `apply/validity.rs` when an own session-form write of the current sessions falls, the `OwnWriteInvalid` case): the plain nonce's last 8 bytes step by one as a big-endian count (no rng draw), the expiring one follows by the flip; `later_sessions` counts them, so `own_plain`/`own_session` recognise every session of the open (batch IDs, `copied_expiry`, `own_memory_commit`) without a list. Why: a write invalid for good (explicit demotion, no re-grant after it, spec/permissions.md §5.2) stops every snapshot frontier of its session below it, and later writes behind it would be held uncovered at every holder until a restart (`memory_regranted_writer_covered_spec_sync_9`). A plain demote-then-grant re-grants (§5.2: the earlier writes turn valid again), so the hole needs a grant with `until` or similar; a fall that rises again still begins a session, harmlessly. Bound: a step needs a fallen write under the current sessions, so an admin flapping the node's role adds at most one session per write the node makes, and holders pay per session only through its writes (frontier entries, `ix.ranges`: as for a restart). Residual (spec/sync.md §9): writes made under the old session after the grant's key but before the node learned of its demotion. The undo log's `restored` matches a stamp to the logged write by its source alone (the log holds own writes only).
- `Engine::write` sorts ops by key lifetime and refuses what asks for two kinds (`Error::Clash`; creates and deletes count as durable): durable ops go to `commit_in` (a delete's things' ephemeral state dropped in the same transaction, Deletion), ephemeral ops into one memory commit per expiry class (refused when there would be two). The memory `commit_in` runs in `Tx::in_class(true)`: session form, ephemeral marker, retention `writer` without bounds, no records, no chunks or pages: a delta past a blob is `Misuse` and nothing of the batch applies; `delta_past_a_blob_refused_spec_commits_2`). Then the undo log is fed from Core (`log_aspects`: the written aspects' fragments and `undo::remembered` footprints) and one `Event::Ephemeral` goes with the batch's `BatchId::Ephemeral`; a delete's dropped aspects go in an `Event::Ephemeral` with its `BatchId::Commit`. Own memory commits fire no event of their own; received ones do (`apply_verified`, origin not `Local`).
- Reads (`read.rs`) come from Core state as for any aspect.
- Restart: everything ephemeral is gone locally and the next open draws new sessions; syncing brings back what holders kept, own old-session writes included (held like others' commits, compacted by the ordinary trigger). Nothing per session is kept across restarts.
- Node-sync subscribes with `subscribe_durable` (no `Event::Ephemeral`) and the osis handle shows it `SyncEvent::Local` after ephemeral-only events only when `has_memory_changes()`.
- Cost (release, `tools/icount`, `ephemeral::bench_ephemeral_sets`, setup subtracted): a local ephemeral set through a `write()` batch on one aspect about 19.8k instructions (undo log footprint, delta copy and log entry about 4k of it; rights check about 4.6k, the largest part, trivially cacheable per (thing, roster generation) if a budget needs it), against a `BTreeMap` insert 316 and a durable set 5.3M.

## Undo
- Undo log (`Eph.log`, `ephemeral/log.rs`): per own ephemeral batch (durable batches log nothing) its id, `reverts`, actor, ts, and per aspect delta, counter range, `footprint` of the pre-write state, schema: O(change). Byte size = `Fragment::approx_bytes` of delta and footprint plus the entry's own size (`approx_bytes` counts heap structure, within a few percent of measured RSS growth per logged write: an int set about 1.9 KB, a two-entry map set about 12.5 KB; counting stamps and values only is 6-16x low). Past `ephemeral_history` the oldest entries go, each remembered per aspect (newest ts and id, and whether it was a revert), bounded by the aspects held. At 0 nothing is undoable. Replacing the log with undo over held bodies is step D of issues/eph-unify.md.
- `Engine::revert_batch(id, actor)`: a commit by its durable undo commit (`revert_commit`, `undo_in`); an ephemeral batch by the log entry's inverse writes (`osis_crdt::undo` against the current state, the footprint as buffer, `restored` judged over the log) as one memory commit logged with `reverts` (`revert_ephemeral`). Returns `Reverted::{Written, Superseded, Compacted}`; an ephemeral id from another session or node is `Misuse` (osis `Invalid`).
- Commit query: entries keyed by `BatchId`; a logged batch is `CommitKind::Ephemeral` (changes and reverts alike; `reverts` tells). Relations (`reverted_by`, in effect, depth) over the related commits plus the whole log. Redo's "no newer change" test uses depth > 0. An own write covered by a snapshot is still an own write for undo (`own_gone` judges by the state, `copied_expiry` by the write's session: a plain-session write never expires).
- Scope: `Thing`/`Group` cover held durable aspects (`scope_aspects` filters by key). Undo first checks the newest dropped ephemeral batch in scope: newer than the chosen target is `NotUndoable{Compacted}` (redo: a dropped change gives `None`).
- Undoing a creation deletes (spec/crdt.md §4.6): `revert_batch` of a commit carrying `created.0` deletes those things, durably in `undo_in` (`undo::unmake_ops`: durable aspects reset, memberships removed in groups the writers may write), their ephemeral state dropped locally as a delete drops it (Deletion, with its limit). Redo brings back the durable state only.
- Rules found by `ephemeral::ephemeral_reverts_within_rights_alike_*`: a revert's writes on several things are one memory commit (every batch's memory commit spans its things; the pass places a commit's bodies under a label holding any of its things, each body the label's actor may read).
- A commit on things in no labeled closure is held and goes nowhere until a closure holds one of them (the passes judge the closure's commits again when it moves, spec/sync.md §3).

## Synced ephemeral data: ordinary commits in memory
- **Ephemeral commit.** A commit with the header marker `ephemeral` (header field 14, `EphClass::Plain` or `Relay`), a content commit or content snapshot in the form a durable one would use (spec/commits.md §3: session form for a node's own writes, commit form for snapshots and for a key actor used from several nodes, `commit_form_ephemeral_commit_spec_commits_3`), no `created.0` part and no records (a part on a thing whose record is not held waits), signed, encrypted, projected and wrapped as any commit. A batch's ephemeral writes are one commit per expiry class. Every node keeps ephemeral commits in memory only (the store's memory overlay and Core's indexes, `Engine::holds_memory`); never persisted, never in bundles. Memory parts decode with `osis_crdt::Unpaged` everywhere (`judge_part`, `stream_stored`, `examine_stored`, pending strip, relay), so a value of any size up to a blob is inline; `MAX_PAGE_ITEMS` binds durable deltas only (spec/crdt.md §8). Ephemeral deltas are never paged and must fit a blob (8 MiB; a larger one is not sent, `EphemeralRefused`; issues/eph-unpaged-cover.md).
- **On the durable sync path** (`core/node/src/sync/memory.rs`): node-sync's passes judge, place, upload, relay and delete memory bodies exactly as durable ones (`label_bodies_meta` lists memory commits; `place` seals with the header's class and stores the blob in the overlay; `Entry::memory`/`BlobRec::memory` keep every sync record about them out of `y/`). `Engine::closure(g)` is the durable closure. Node-sync routes by the blob's prefix class in one place. What stays particular (`memory.rs`):
  - the node cap at the one ingest site (`ingest_memory_entry`: room, `PENDING_SHARE`, `unfit`; refused entries fetched again once the label's bytes drop below what they were at refusal);
  - the restart reconcile (`Memory::reconciled`): the first sync of a label at a host after a start reconciles the live sets and keeps the cursor, so entries the persisted cursor passed come back as `need`; marked done when the reply arrives (a connection ending first, or with any of the reply's fetches unanswered or refused, reconciles again: nothing else names an entry the cursor passed); not after a cursor-less replay, not on reconnects within one run; a Push during it keeps no cursor;
  - presence of memory entries dropped when a connection ends (a restarted host lost them) and learned again by the first Sync's `gained` list (`memory_gained`/`memory_synced`: what the host does not want is present there);
  - hold-back and coalescing before a send (`coalesce_own`, Memory commits below);
  - carriers of a dropped memory part read from the engine (`carrier_of` follows `Dropped::covered_by` via `Engine::coverers_of` and forgotten coverers, since `drop_covered` sets no carrier row; without it a deleter snapshots the aspect anew every pass);
  - the headers of forgotten memory commits kept while their entries are known (`Memory::forgotten`: deletes at hosts are judged by them; a coverer forgotten before it was placed stands for what covers it, `carriers_of_forgotten`; a coverer a host refused for its cap goes up again replacing the covered entries);
  - a memory entry's tombstone at `MAX_DRIFT` (an announcement of a tombstoned blob is nothing);
  - an upload a host refused for its cap tried again once per resync while the body is held (`SyncEngine::capped` dirties the label at `timers`; durable too);
  - relay-only commits (`relay_in`, `send_relay`, `RelaySeen`).
- The compaction trigger compacts every aspect it weighs, local-only ones too (else a rewritten UI value keeps every body). An entry is deleted for being outside the closure only by a node that judged or placed it inside (`State::memory_in_closure`): a restarted node's closure is what has arrived so far, and deleting window bodies while the membership waits its relay delay is a storm.
- Only commits the engine verified and holds are kept, served and spread (far-future dropped; unknown authors wait apart within `PENDING_SHARE`); pending commits are retried only when a record they wait for arrives; another blob of a held commit has its signature and delta hashes checked before it is kept; a replay of a covered commit is not held again and a writer deletes it.
- **At hosts.** The blob prefix has a class field (byte 25, osis-label `Class`): durable, `ephemeral` or `relay` (signals), from the commit's marker (spec/sync.md §3). A host keeps ephemeral entries (blob, wrap, stamp, log event, tombstone) in memory only (`Ephemeral` in `HostStore`), under a per-label byte cap (`HostPolicy::ephemeral_bytes` 16 MiB) and a total (`ephemeral_total` 1 GiB), code 12 past them; deposits of ephemeral or relay-only blobs are code 1; unstamped ephemeral and relay-only blobs are refused for every store. Log sequence numbers are shared with the durable log, reserved on disk in blocks of `SEQ_BLOCK` in the label meta's `reserved`, so a restart never reuses one (a cursor ahead of the durable log stays valid). The in-memory log is trimmed at `EPH_LOG_KEEP` records per label; the durable log is trimmed by its own record count, so ephemeral churn never sends durable cursors to reconciliation. Ephemeral deletes and replacements are rate-limited, due times are indexed (sweep budgeted), the label using most gives way at the total cap. A restart loses everything ephemeral. The rest is the ordinary path: upload by stamp, cursor sync, range reconciliation, subscriptions pushing new entries, expiry, delete keys.
- **Convergence and reconnect.** Ordinary (spec/sync.md §6): a holder bridging two hosts or a co-reader peer serving its own label carries ephemeral state across. A joiner or restarted node gets the state by its ordinary first sync from any host or peer that holds it; if every host restarted, holders upload again (presence is per connection). Residual (spec/sync.md §9, as durable's spec/permissions.md §5.2): a write covered by a snapshot that fell invalid comes back only from a writer still holding it; readers lose their entry of it with the host's deletion.
- **Signals.** A write's signal writes become one relay-only commit (`ephemeral/signal.rs` `take_signals`: one commit per write, grouped by the write's `ts`, snapshot deltas; grouping per actor would make two writes of one aspect before a pass one refused commit). A host, or a co-reader peer serving the label, accepts it by stamp like any upload, pushes it to the label's current subscribers (`ServingOutput::Relay`, a `Push` of one add event at the subscription's cursor) and holds nothing: no entry, log event, tombstone or expiry, so it never reaches a later sync. A co-reader peer passes a verified new relay-only commit on (from a host to its sessions, from a session to its other sessions and the label's hosts), each blob once, so a node reachable only through it gets the signals. `ingest_relay` verifies, judges the author's write role through the thing's timeline (a relay on a thing whose record is not held is dropped), delivers each valid signal part to callbacks once and holds nothing (no state, no body, never re-uploaded). Dedup (`Delivered`) is per (commit, part): a commit whose parts have different readers goes as several blobs. A node remembers delivered relay-only commits until their `ts` is `MAX_DRIFT` old, with a floor per author past `MAX_DELIVERED` (a floor shared by all would let one flooding writer drop every group's signals), and drops relay-only commits older than that. The blob's prefix expires at `ts + MAX_DRIFT`: hosts and peers admit relays through `osis_proto::RelayGate` (expiry window, `MAX_RELAY_BLOB`, per-label rate, push once per blob); receivers drop relay blobs unopened when oversized, outside the window or seen (`RelaySeen`, checked before opening but recorded only once verified, so keyless junk cannot raise the floor). Within that window a signal can arrive late (a delayed push), and a restarted node can see one again if a replayer uploads it to a host that forgot it. A node's own signals fire locally.
- **Validity, ordering, replay**: ordinary commit rules (chains, parking past `MAX_DRIFT`, idempotent apply). A replayed old ephemeral commit only re-adds writes its stamps already lose to, or that holders still have.
- Leak: a host learns which entries are ephemeral. Nothing else.
- Open, deliberately not built: a node that stops syncing a label or loses read access keeps that label's ephemeral state until restart; relays are not delayed, so every bridging holder uploads a duplicate (answered OK).
- Tests: osis-node `tests/it/ephemeral.rs` (with `random_window_converges_*`: four writers, two hosts, random writes, partitions, restarts, a random host cap on odd seeds; tier 2 `random_window_converges_large`, `random_window_one_capped_host_*`, `OSIS_EPH_START`/`OSIS_EPH_SEEDS`, about 11 min for 300 seeds together), `memory_*` differentials, `random_churn_converges*`, `sync::signals_relay_only_spec_sync_5`, `hostile_host::replayed_signal_dropped_spec_sync_9`; osis `sync::remote_signal_spec_sync_5`, `tests/it/ephemeral.rs`, `ephemeral_undo.rs`; osis-host `hub::subscriptions_and_relays`, `hub::ephemeral_entries_in_memory`; proto `loopback::subscribe_push_and_relays`; vectors (ephemeral and relay-only commits, prefix classes); sim `ephemeral*`.

## Memory commits
Ephemeral data is Core's memory class end to end. What is special: memory storage (the overlay), forgetting spent commits, the second session for expiring writes and superseding (Superseded expiring writes), signals, the restart reconcile, the caps.
- **Receiving**: every ephemeral blob goes to `Engine::ingest_memory(bytes, room)`, routed on `Ingested`: `Applied` kept as an entry, `Duplicate` kept once `parts_genuine` (a copy carrying the held parts' bytes), `Pending` kept apart within the share (else `forget_pending_memory`), `TooLarge` refused and reported, `Parked` dropped. Charge per entry `memory_charge`, bound before decode `memory_bound`; parts are judged like durable ones (spec/permissions.md §5.2), applied atomically, un-merged by demotion.
- **Each step** node-sync drains the engine: `take_memory_invalidated` (aspects a held memory snapshot turned invalid on: a writer still holding a valid part writes a fresh snapshot of what it holds, uploaded as a new commit, and the label is reconciled so holders' copies of what it covered come back; the authors' own writes, kept under others' snapshots, return to hosts and readers this way, since a re-upload of the covered entries would meet the host's delete tombstone; `compacted_write_of_removed_holder_stays_spec_permissions_5_2`. Gated on a valid-to-invalid flip of a held snapshot, so only a role change triggers it, at most one snapshot per writer and aspect per step; an author that restarted or never held the fallen snapshot valid does not, and its covered write stays gone at readers until it writes again, spec/sync.md §9), then `memory_compactions`, then `take_memory_drops` (commits forgotten, `MemoryDrop::{Covered { by }, Superseded { by }, Gone}`: the lane forgets their entries and, as a writer, deletes them per label once a coverer or superseder is held there; `Gone` deletes at once).
- **Snapshots and covering** (`retention/memory.rs` `drop_covered`, `retention/snapshot.rs`): a memory compaction snapshot is commit form, ephemeral marker, the aspect's whole state at that node (every author's writes, frontiers over every session, expiring deltas' values value-less, covering such a delta only as its leftover past T, as for durable, `retention::snapshot_state`; `Absorbed` for by-ID commits), retention `writer` without bounds. **Covered drop rule** (code comment in `drop_covered`): a body whose author is this node is dropped as covered only by this node's own snapshots; any other author's body drops under any valid held snapshot covering it. So a demoted compactor's snapshot falling invalid (its demotion lists no memory commit) loses at most the demoted author's own writes: every other author still holds its own bodies and re-uploads them when the label is reconciled (`memory_compactor_demoted_keeps_others_writes_spec_permissions_5_2`, `snapshot_invalidated_by_self_removal_reads_alike_spec_permissions_5_2`). Of covered-equal snapshots the higher ID goes. The own-author exception follows from demotion frontiers listing no ephemeral commit, a divergence (Divergences left). `covered` checks the frontier before decoding. No receipts for memory commits. A forgotten body not held elsewhere is gone, as durable's residual (spec/permissions.md §5.2).
- **Trigger** (`Engine::memory_compactions(force)`): per memory aspect changed since last weighed (`MemorySync::dirty`), with two or more held non-snapshot bodies a snapshot may cover (no expiry, or leftovers past it) costing (`held_cost`: `part_weight` plus `ENTRY_CHARGE` each; a leftover has no delta bytes) more than `FACTOR` times the snapshot's cost (`snapshot_cost`, measured by encoding), `snapshot` if this node may write the aspect; weighed only when the held cost passes the factor times the cost last weighed (Bounds). Counted are only the bodies a snapshot built now would cover (`retention::frontiers_now`, the snapshot build's own frontier walk): a session's bodies behind an invalid or missing one stay held uncovered, and counting them makes the trigger fire on every step; one invalid for good makes its author begin fresh sessions (Local engine), so nothing later piles up behind it. Snapshots are not counted as bodies (two writers each keeping their own snapshot under the covered drop rule would otherwise re-snapshot each other forever). Any writer compacts: concurrent snapshots are covered-equal duplicates, dropped by rule. `force` (`compact_ephemeral_now`, tests) snapshots every memory aspect with a body. A host's cap refusal triggers nothing.
- **Coalescing** (`coalesce_own`, before a pass sends under a label): own memory bodies not yet placed under the label wait while an own memory upload under it is unanswered on the connection; then two or more on one aspect go as one snapshot: of their join alone when all are this session's plain writes (`Engine::coalesce`: frontier `{own session: up to the last of their counters}`), of the whole state when a snapshot is among them (`Engine::snapshot`), covering them at every holder; a body the snapshot cannot cover goes as it is. One delayed plain commit instead is impossible without restamping: a writer delta's commit-level writes must carry the delta's stamp (spec/crdt.md §3.3 rule 7), and several commits' writes have several; a snapshot carries foreign stamps, and its frontier makes it exact. Expiring writes are not coalesced: no snapshot carries an expiring value (spec/crdt.md §8, durable alike); superseding thins them. Signals are not held back. Measured: one entry per aspect per round trip.
- A memory part answers to no `required.0^` rule (`validity::under_required`, spec/commits.md §5).
- **Growth**: `MemorySync`'s sets drain each step; `weighed` keeps an entry per memory aspect weighed, bounded by the aspects held; memory commits are bounded by the caps and forgotten once spent (`forget_if_spent`).

## Expiry
- Expiry is death by timer (spec/crdt.md §4.8): the values die at T and the body follows, whatever the deltas' keep bounds. "Keep at least until T" is a retention bound (spec/commits.md §5), a different thing.
- Covers disappearing messages (write-based timer in core; read-based timers and earlier deletion are app writes; core expiry is the hard upper bound and lets a host wipe them unattended) and buffered events (a list aspect with a one-hour default). Cheaper than purge on replace: nothing has to be deleted by hand, and the host does it unattended.
- Leak accepted by Tess: a host learns which entries expire and when.
- Not provided: host-enforced minimum retention (legal hold). Keep-at-least binds honest nodes; a host deletes whatever a delete key or its label delete key tells it to.
- **Ephemeral expiry is durable expiry** (spec/crdt.md §4.7): at T an ephemeral delta's value-carrying writes go value-less and its other writes (resets, removals) stay; the body is held as its leftover (`make_leftover`, the memory overlay's `w/` row) until a later write of its author supersedes it (`superseded_rest`, Superseded expiring writes) or a held valid snapshot covers it (spec/commits.md §5: before T no snapshot covers an expiring delta, after it the join judges the leftover like any body); then it drops and its commit is forgotten (`unindex_commit` also takes its writes off the value-less list, so a copy arriving later applies as new and goes again). A copy arriving after T joins value-less as the leftover. A snapshot carries the leftover's writes value-less, so a node that missed the delta (offline at T, restarted) gets its resets from the next compaction; until a writer compacts it may read what the delta removed, as for durable data (`expired_removal_stays_spec_crdt_4_7`).
  - Copy expiry (spec/crdt.md §4.7) binds ephemeral writes too: a write into an entry an expiring write created takes that expiry, or is `Clash` beside writes that must outlast it (`set_into_expired_entry_reads_alike_spec_crdt_4_7`).
  - Undo of an expired batch writes its inverse as usual. An undo copies back no expired content: `undo_expiring` strips everything expired by the undo's `ts` from the pre-state before it runs (`undo_of_set_past_expiry_restores_no_shadowed_entry_spec_crdt_4_6`). A revert copying back an expiring value writes all its inverse under the expiring session at that expiry; one copying back values of different expiries (or expiring beside lasting) is `Clash` (`undo::copy_expiry`).
  - **Memory cost**: one held leftover commit (header, meta, leftover row, value-less list entry, about 3 KiB charged by the trigger) per expired ephemeral commit until a snapshot covers it. Leftovers count in the compaction trigger (Memory commits), so a writer holding them compacts: any writer of the aspect does, the author included, and a holder that may not write drops them under a writer's snapshot. Measured (`scale::eph_leftover_memory`, release, one expiring list element per commit, never superseded): 2000 commits held at B, 2001 commits after expiry (charge 0: the trigger, not the cap, bounds them), 1 after X's snapshot (B's commits back to baseline; the snapshot keeps each element's value-less anchor, charged about 1.15 KB per element, the list's tombstones as durable state keeps them; never collected, so they bound an expiring list's lifetime elements at a holder by its cap, issues/eph-expired-anchors-fill-cap.md). RSS above baseline +7.5 MB ingested, +11.5 MB expired, +18 MB covered at 2000 (+20, +37, +59 MB at 6000): RSS does not shrink as the heap frees. Expiry 0.16 s for 2000, 0.6 s for 6000; writing them costs more (5 s, 27 s: each write re-encodes the aspect's unpaged state).
  - **Expiry cost**: a round of expiries (`tick_round`) rebuilds each aspect once (`apply::run_batched`), not once per expiry; the value-less list is looked up per dot by binary search (`retention::sorted_owns`), a forgotten commit's timers by key; each leftover is judged for superseding alone (its author's later commits newest first) and for cover against the held snapshots. A new snapshot's part is read once for all the bodies it is judged against (`Core::cover_cache`), and its covered drops rebuild once. A journaled index keeps one old value per key per transaction (`JMap`), so the value-less list growing per expiry is copied once. Linear in the expiries (`ephemeral::expiry_round_work_linear`).
- **Expiry never waits for a Tick** (durable too): a Tick comes late (`MIN_WAKE_MS` throttle, a suspended process; in the node test net an offline node gets no events at all), so the osis handle runs `SyncEngine::expire_due` before every call under its lock: when `Engine::timers_due` (in-memory: `Core::timer_floor`, a lower bound of the earliest durable timer, and the ephemeral timer map) it runs the Tick's engine part (live-drop snapshots and `tick_round`, in rounds, `tick_ephemeral`); every sync step starts the same way when a timer is due. Pushed change events still come with the Tick (up to `MIN_WAKE_MS` late) or the next call: a subscriber's last value can show past T until then. Tests reading through the engine directly call `expire_due` first (`random_churn_run` checks every step that no value is read at or past its expiry).
- Nothing is kept "until every receiver has seen it": the receiver set is open and nodes die. What must survive every holder forgetting it (restarts) is durable state: the inbox pattern (a list the receiver holds, senders append, the receiver deletes, expiry as backstop) or a list with expiry.

## Values that live while their author is there
Tess's decision: a value that should live only while its author is there (a cursor, a selection, an "online" mark) is an ephemeral aspect with a short default expiry (`~` key, `[expires: 30s]`) whose author rewrites it before it expires; when the author's node goes away the rewrites stop and the value is gone at every node holding it by its last write's expiry. Nobody needs to notice the departure: no connection tie at hosts, no source tracking or un-merge at holders, no lease or keep-alive constant.
- **Helper**: `db.at(t, k).path(p).keep_alive(&value) -> KeepAlive` writes the value and rewrites it every `expiry / REFRESH_DIVISOR` (2) of the key's default expiry on the handle's runtime until the `KeepAlive` is dropped; `KeepAlive::set` writes a new value at once. The key must be ephemeral with a default expiry. A rewrite is a `Put` (a fresh entry at a map key, a fresh register write elsewhere): a `set` of an equal value writes nothing, and a write into an entry an expiring write created outlives that entry (Expiry) unless it expires no later. `Replace` would not: at a live key it writes into the old entry and goes at that entry's expiry.
- **Cost**: each rewrite or `set` supersedes the write before it (below), so a holder and a host hold about one commit and entry per kept value, and one upload goes per value per half expiry or per round trip while it changes (`ephemeral::moving_cursor_one_entry_per_author_spec_sync_9`: 60 moves, one entry). Left: an expiry under the sync tick (1 s) still rewrites every half expiry, one upload per rewrite, while expiry is applied only per tick.
- Two nodes keeping one path alive overwrite each other at every rewrite: key by node (`Osis::node`), not account. Nothing survives a restart: the app calls `keep_alive` again.
- **Choosing the expiry** (the schema's, per aspect): how long a departed author's value lingers against the rewrite traffic. 30 s suits cursors.
- Rejected: write-level "until the author disconnects" (Tess's idea, evaluated). It needs a host tie per connection, holders tracking which host or peer still has the author's entry, un-merge when none does and a lease backstop for half-open connections, and "disconnected" is per path, so holders behind different hosts disagree.
- Tests: osis-node `ephemeral::refreshed_value_lives_while_author_present_spec_crdt_4_7`; osis `runtime::keep_alive_rewrites_until_dropped`; sim `ephemeral`/`ephemeral_capped` (random expiring cursors; `author_leaves`: a refreshed cursor at every connected holder before each refresh, gone past its expiry once the author is down).

## Superseded expiring writes
No snapshot covers an expiring write before it expires, so without this rule a cursor kept alive with `KeepAlive::set` (a fresh map entry per move, `Op::Put`) costs one commit, upload and entry per move until each expires.
- **Rule** (spec/sync.md §9, `retention/memory.rs` `supersedes`, `drop_superseded`): a held plain commit whose parts all expire and carry no reset is dropped once each part is superseded by a valid held part of another plain commit of its author on the aspect: that part expires too, no earlier, carries no reset, each of its writes is stamped later than every write of the old part and none is a write into a record it did not create (a `Set` into the entry a move created goes with that entry), and the old part joined into it reads as it alone.  Checked at every node when a commit is held (own builds included: `drop_superseded_by`, judging the new commit and only the author's commits it supersedes a part of, since nothing held before was superseded), when a commit's part goes value-less at its expiry (that commit alone, `superseded_rest`) and when parts turn valid (every candidate, `drop_superseded`). A candidate costs a join and two reads of two small deltas; a new commit decodes each held expiring commit of its author on its aspects expiring no later, unless it is a sequence, a bag or carries a reset (so a burst of `n` expiring map puts by one author costs `n²/2` small decodes; lists cost none). A received commit superseded on arrival is not held (`Dropped`).
- **Not death, but convergent** (spec/crdt.md §4.8): an older `put_new` entry at a key stays live in the CRDT, only shadowed in the read; the rule makes it expire early instead. Convergent because the drop is a function of the commits held, never of later writes: every node holding the newer part valid drops the older (at its arrival, at the newer one's, or when the newer turns valid, `rejudge_ephemeral`), and a later removal or undo of the newer entry kills only that entry everywhere. The conditions each close an order dependence:
  - the author drops the superseded writes from its own state and unsent writes too, else after a holder removes the newer entry only the author reads the old one again (`superseded_stays_gone_when_newer_removed_spec_sync_9`);
  - neither part carries any reset (`Fragment::has_any_reset`): a superseder with a reset makes the relation intransitive (q replaces the aspect over p, r later puts without it: r supersedes q but not p, so p is dropped or held by arrival order), and a superseded part with a reset takes its tombstones with it at holders but not at the author;
  - the superseder expires, so no cover ever absorbs it (a cover carries older writes and supersedes nothing; a node that got only the cover would read the move again once the plain entry is removed; `superseding_part_expires_spec_sync_9`);
  - the ts order and the expiry guard: a later write expiring sooner, or an older write with an equal value, supersedes nothing (`superseding_needs_later_stamps_and_no_reset_spec_sync_9`).
- Rejected: real death. Each move would have to tombstone every own entry of the key not yet expired (about expiry / round trip of them per commit, 450 at 30 s and 66 ms), since dropping a commit drops its tombstones too.
- Left: a superseder turning invalid later does not bring the dropped commit back (a memory part's late copy is refused, `retention::takes_late`; durable keep-bound drops join again, spec/commits.md §5).
- **Holders and the author** forget the superseded commit whole (`unindex_commit`, reported as `MemoryDrop::Superseded { by }`) and rebuild the aspect without it (`memory::vanish`). An own commit superseded before it was placed is forgotten the same way, never sent: a burst of moves during one upload goes up as the last one. The lane deletes a superseded entry where a superseder is held, else at its expiry.
- Measured (tier-1 `Net`, 66 ms round trip, 10 authors moving every 33 ms for 1 s): 160 uploads, 0 deletes, the host's peak 43 KB of a cap scaled to 560 KB, one entry per author at the end; without the rule 224 entries. A simulated minute at the default policy (tier 2, 17 min dev at load 6-12): 9100 uploads, 0 deletes, peak 1.76 MB of the 16 MB cap.
- Tests: osis-node `ephemeral::{moving_cursor_one_entry_per_author, superseded_unsent_moves_one_commit, superseding_needs_later_expiry_and_own_records, superseding_needs_later_stamps_and_no_reset, superseding_part_expires, superseded_stays_gone_when_newer_removed, many_authors_under_host_rates}_spec_sync_9` (4 authors), `many_authors_under_host_rates_large` (tier 2: 10 authors for 1 s, then a simulated minute). `random_churn_converges_spec_sync_9` (4 seeds) and `random_churn_converges_large` (tier 2, `OSIS_EPH_START`/`OSIS_EPH_SEEDS`): random expiring and plain puts, removals, replaces, undos, demotions, partitions and restarts; every holder reads alike, a once-demoted author included (no rule lets an author read its refused writes apart).

## The all-nodes predicate
"All nodes a thing syncs to" is a state predicate computable at nodes that read the label, never a protocol condition. Per label: the nodes with a valid chain that published `node.0` under the thing's label (not "every node of every holder", which needs rosters readers never see).
- Recency: each node places an expiring `seen.0` heartbeat under each label it tracks (spec/permissions.md §4); the live one's value is its last sync of L, absent means unknown. `seen.0` is one aspect of the node thing, so its joined read is "last seen anywhere"; the per-label answer comes from the sync layer's record of which heartbeat commits arrived under L, not from the aspect. (A `map<label ID, timestamp>` would give aspect semantics but leave a value-less entry record per expired heartbeat forever.) The heartbeat also carries `stranded`, the one signal a node that cannot open a label's current epoch, or cannot walk to the head because a claim set was dropped, can still send (it deposits without opening the label, under the newest established read secret it holds, which co-readers open by history boxes), and what triggers a re-seal; it is placed only after a complete pass at that host (the rotation commits are uploaded before the step, notes/label-access.md, so "cannot open" means not boxed, never "not fetched yet"); it fails only when the deposit key changed under it (a manual re-share, notes/label-access.md). The node list (the node card) and recency are separate aspects because an expired register winner reads as absent and the older write does not show through: an expiring re-put of `node.0` would drop the node from the node list when it lapsed.
- Why a durable heartbeat and not a node-card re-put or ephemeral data: a reader's re-put is a deposit that sits in the label's budget until a writer promotes it, so readers × cadence × promotion delay would have to fit a budget the spec never sized, and a full budget refuses the deposits that matter (grants into the group, a reader's self-removal, a revoke only readers hold). Expiry frees the budget unattended (no tombstone, no delete, no writer), so a reader holds at most ceil(lifetime / interval) entries at once and the budget is sized from the claim set (spec/sync.md §5). Rejected: deposit new card plus token-delete the old one (a delete and a 30-day tombstone per refresh, reader-side delete flows, rate-limited deletes); ephemeral writes (the asker is rarely online with the reader, and readers cannot write ephemeral data); host arrival times (untrusted, per host).
- Leak accepted by Tess: a host sees each reader's heartbeat rhythm per label (same class as deposit and expiry times it already sees). Clock skew between the heartbeat's writer and the asker shifts the reading by the skew; lifetimes are days, so no coarse policy notices.
- A node reading the label keeps its own local record of the last heartbeat it saw per node, for policies wanting a longer memory than the lifetime; it is a lower bound, not knowledge of the gap.
- Uses: write a new schema form once every node reads it (fixes the read-only old app the header heuristic cannot see), drop old-form history after that, clean up an inbox once every own node has acked.
- Dead nodes: a lost phone's heartbeat lapses and it drops out of "all nodes seen recently" on its own; a policy that needs it gone from the node list too waits for an explicit node removal. Never gates deletion at hosts.
- "Buffer until all have seen it" = inbox pattern plus this predicate plus expiry as backstop. Fine as a core helper later; not sync machinery.

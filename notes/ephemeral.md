# Ephemeral data
> Summary: Ephemeral data as built: drafts and `~` aspects, an axis independent of sync, as much like ordinary data as possible. Local ephemeral writes are memory commits through Core; synced ephemeral data is ordinary signed commits marked ephemeral, held in memory instead of the store at every node holding them and carried by node-sync's ordinary passes: it merges on reconnect, outlives contact with its author and is lost only when no node holds it. A value that should die with its author is an expiring write its author renews (`osis::KeepAlive`); `*` signal aspects reach only connected nodes and hold nothing. Every thing starts as a draft and persists with its owner chain at its first durable write, keeping its tid; draft memberships are `ephemeral_group.0~`. Covers the API, engine, wire, bounds, deletion, undo, expiry and the all-nodes predicate.

Terms: a new thing not yet durably written is a **draft**. **Ephemeral** is for `~` aspects: shared with others, never stored. A draft has only ephemeral aspects, so it syncs like them once added to a synced group: shared or not, it is a draft.

## Tess's direction
- Ephemeral = cheap and disposable, no never-touches-disk promise. Independent of sync: durable or ephemeral, local or synced. All of an app's state lives in osis; the UI drives and is driven by it.
- Like ordinary osis data in most ways; its history is "don't care" (neither purged nor kept). On one node it must be very cheap; some overhead is fine when synced, and anywhere when the alternative is special cases or API complexity. Reuse the ordinary commit, delta, validity, sync and host paths unless clearly worse.
- Both units: drafts (creation record only in memory, same tid derivation and rights) and ephemeral aspects on durable things, declared in the schema.
- `create` takes no membership; group ops set groups (same write for atomic create-and-add). Every thing starts as a draft and is persisted at its first durable write together with its owner chain's creation records, keeping its tid. No persist call. A thing never given durable data vanishes when every node holding it forgets it.
- Synced ephemeral state is ordinary CRDT state held in memory by every holder: it survives while any holder keeps it, merges on reconnect (two people keep using a shared ephemeral window while one is offline; it merges when they reconnect), and a joiner gets it from any holder.
- Presence is not a lifetime of its own: a value that should die with its author is an expiring write its author renews (Values that live while their author is there).
- No exception to convergence: ephemeral state converges among the nodes holding it; author-tied values converge once their last write expires.

## Model
**Kinds of aspect.** The key's lifetime marker decides (spec/data-model.md §2): durable (none); `~` ephemeral (a value held in memory); `*` signal (an ephemeral write with no lasting value, delivered only to currently connected nodes; anything a late joiner should see is ephemeral state, not a signal). The writer's key decides the path; merge needs no schema. Core aspects are durable, `ephemeral_group.0~` aside. Retention does not apply to ephemeral data; expiry does.

**Holders.** A node holds the ephemeral state of the things it writes or receives: every node syncing a label whose closure holds the thing (spec/sync.md §3: `group.0` and `ephemeral_group.0~`, as for durable data; a thing no group lists syncs no more), and that label's hosts, while they run. They keep it until they restart, stop syncing the label or lose read access. State is lost only when nobody keeps it; a restarted node gets it back by syncing.

**Draft.** A thing whose creation record no durable commit holds at this node. Tid derivation, creation record and owner are as for any thing. `create()` mints the record and keeps it in memory; nothing is written. Invariant: **the durable set is closed under owner**, so a durable thing never has a draft owner.

**Persistence.** The first durable commit with a delta on a draft T (a durable aspect of T, by any node that holds T's record and may write T) also carries `created.0` of T and of each draft on T's owner chain, top down, and makes T's draft memberships durable (below). Same tid; ephemeral aspects stay ephemeral; ephemeral values never become durable: the app copies a draft's content into a durable aspect in the same batch (`set`). Reason: a durable write anchored at an ephemeral dot hides once nobody holds it, and a durable writer delta cannot carry foreign stamps. Two nodes persisting T concurrently both carry the same record (idempotent). `grant`, `make_link`, `sync` and other role ops on a draft first persist it by a content commit of its own (`Osis::persist`; role commits cannot carry `group.0`), which also converts its memberships, then run. A durable thing never becomes a draft again. The CLI refuses `create --in G`/`--group` without durable data (the thing would vanish at exit).

**Draft memberships.** `ephemeral_group.0~` (of `group.0`'s type) is the one ephemeral core aspect: a group op (`w.group(g).add`/`remove` of an item or subgroup) whose item is a draft is a write into the group's `ephemeral_group.0~`, held and synced like any ephemeral state, needing write on the group; raw writes of `ephemeral_group.0~`, and ephemeral-keyed raw writes of `group.0`, are `Invalid`. `group.0` reads its durable state alone; `ephemeral_group.0~` reads as the group its items and subgroups make (its adds carry no struct presence); the group index (`groups_of`, `groups.0`, `listed_in`) reads both, so the item shows in the group's members and in its `groups.0`, and the closure (spec/sync.md §3) includes it, so its ephemeral commits go under the group's labels.
- When the item persists, the persisting commit adds it durably and a reset removes it from `ephemeral_group.0~`. An expiring membership refuses that commit (`Clash`: a commit has one expiry, and a record has none), so the app removes it first and adds it back in an expiring commit.
- A draft can be a group of drafts, a draft added to a folder lands there at save, and nothing durable names a thing that never persisted. A group op on a durable item is a durable write and persists the group. Any later durable write of a durable thing converts its remaining draft memberships the same way, and a durable removal from the group also removes it from `ephemeral_group.0~`.
- Side effects, all minor: an ephemeral removal concurrent with the item's persistence loses to the durable add (add wins); a persisting node without write on the group cannot make that membership durable, so it stays ephemeral and a `MembershipNotSaved` diagnostic names it (a writer of the group fixes it by adding it again); a durable `group.0` naming an ephemeral tid (a raw path op) is a reference that may dangle; an ephemeral reset of a durable element (raw path op only) is not reflected in `groups_of`.

**Rights and validity.** A draft has no role-class aspects (writing one persists it), so a node's role on it is its role on a new thing owned by the nearest durable thing on its chain: the rule used for things created in the same batch. A new draft needs the role its creation would need (checked at write). Ephemeral writes need what the durable write would need; readers cannot write ephemeral data. Synced ephemeral commits are judged like compaction snapshots (spec/permissions.md §5.2: a part is valid iff its author could write the aspect at its `ts`, through the ordinary timeline; depth counts the whole chain, durable and memory records), and un-merged like any commit on revocation. Parts on core aspects other than `ephemeral_group.0~` are invalid.

**Reads and merge.** An aspect reads the join of its durable state and its ephemeral state (spec/crdt.md §4.1); normally one side is empty (both: schemas that disagree; the join is defined). Own writes and every applied ephemeral commit join into the ephemeral state. `signal` aspects always read absent. So ephemeral state converges among holders as any CRDT state does.

**Deletion.** `delete(T)` writes per aspect a durable remove when a durable delta is held, else an ephemeral reset. A thing no commit on which was a label entry here (`MemorySync::synced`, set at `place` and at ingest) and in no labeled closure is freed at once (record, state, undo entries, the drafts it owns, its draft memberships by resets; the tid reads unknown), so short-lived UI things cost nothing. One that was a label entry is deleted as a durable thing is: its resets go to the holders and it keeps its record and tombstone commits, marked deleted (`Eph::deleted`, reads unknown; an undo of the batch brings it back), until restart; dropping them would let a holder's copy revive the values (`deleted_synced_thing_keeps_tombstones_until_restart_spec_sync_9`, `deleted_thing_stays_deleted_at_holders_spec_sync_9`). A holder's later write on it shows alone, as after a durable delete. Received memory things no commit is on any more are freed (`free_unused_memory`).

## API
- `w.create() -> Tid`; an expiring membership is `w.group(g).expires(e).add(m)`.
- Schema DSL: the key's marker is the lifetime: `aspect win:notes.0~: list<tid>;` `aspect doc:cursor.0~: map<tid, Cursor> [expires: 30s];` `aspect call:ring.0*: Ring;`. `AspectKey::lifetime()` reads it from any key, typed or untyped.
- A `Write` is one commit (notes/api.md Writes), so durable beside ephemeral writes is refused (`Clash`): a peer could see one without the other. The exception, with no write of its own asked: what a durable commit does in memory (a persisted thing's memberships leaving `ephemeral_group.0~`, a durable removal's `ephemeral_group.0~` entry, `delete`'s ephemeral resets) is a second commit, a memory one under the durable one's `ts`, one entry in the undo log (engine `BatchId::Commit`; revert takes both). Two commits on the wire: issues/commit-memory-half.md. `retention(..)` on an ephemeral write and any op but `set` on a signal aspect are `Invalid`. In the engine `BatchId = Commit(CommitId) | Ephemeral(EphemeralId)`; the API's opaque `CommitId` wraps it.
- Watches: each signal reaches every `on_change` callback once (never coalesced, never in state). A remote ephemeral change's `Origin::Remote(Stamp)` names the ephemeral commit that carried it (its author, verifiable, notes/api.md Attribution). No node targeting (a value can name a node); a group-wide signal goes on the group thing.
- `created(t)`: `Stamp.commit: Option<CommitId>`, `None` while a draft (`ts`, `node`, `actor` from the creating batch or ephemeral commit, `received` from its arrival).
- Undo, redo, revert, query: own ephemeral writes of this session are entries (`CommitKind::Ephemeral`); ephemeral commits are transport, not listed (own memory commits and own compaction snapshots never show as commits). Thing and Group scopes cover durable aspects and drafts; an ephemeral aspect of a durable thing (cursor, selection) is in scope only when named by `Scope::Aspects`, so document undo never steps through cursor moves. Remote ephemeral changes and own ones from before a restart have no log: revert is `Invalid`. `Config.ephemeral_undo_bytes` (default 16 MiB; the engine's `ephemeral_history`) bounds the log; older batches are `NotUndoable{Compacted}`.
- Errors: none of their own; `UnknownThing` for a vanished tid. Diagnostics: `EphemeralRefused { things }` (a cap was hit, Bounds), `MembershipNotSaved { item, group }`. `NotSynced` is only for a durable membership in a closure with no sync ID, never for drafts.
- Text sessions on an ephemeral `text` aspect idle-commit like durable ones (harmless; committing each edit at once is not built).

## Local engine
- Module `osis-engine` `ephemeral/`, owned by `Engine` beside `Core`, under the handle's one lock. Ephemeral writes are memory commits in Core (Memory commits below); `Eph` keeps only the undo log, batch counter, undone saves (`drafts`), deleted things, unsent signals and delivered relay-only commits.
- Local stamps: `ts` from the engine's HLC; dots of source `Session(node, nonce)` (spec/crdt.md §2.1) with counters per aspect from the store's memory overlay (`counter(tid, ak, nonce)`), contiguous from 1 in each session. Two sessions per open: `Core::session` for plain writes, `Core::expiring` for expiring ones, its nonce the plain one's with the first bit flipped (one rng draw per open: a second draw would move every later tid and blind, and seed-pinned order tests and the judgment vectors depend on commit-ID ties). Why two: an expired delta's range is forgotten, and under the plain session it would leave a gap no snapshot frontier passes, so nothing later of the session would be covered.
- Fresh sessions within an open (`Core::fresh_session`, from the validity pass in `apply/validity.rs` when an own session-form write of the current sessions falls, the `OwnWriteInvalid` case): the plain nonce's last 8 bytes step by one as a big-endian count (no rng draw), the expiring one follows by the flip; `later_sessions` counts them, so `own_plain`/`own_session` recognise every session of the open (batch IDs, `copied_expiry`, `own_memory_commit`) without a list. Why: a write invalid for good (explicit demotion, no re-grant after it, spec/permissions.md §5.2) stops every snapshot frontier of its session below it, and later writes behind it would be held uncovered at every holder until a restart (`memory_regranted_writer_covered_spec_sync_9`). A plain demote-then-grant re-grants (§5.2: the earlier writes turn valid again), so the hole needs a grant with `until` or similar; a fall that rises again still begins a session, harmlessly. Bound: a step needs a fallen write under the current sessions, so an admin flapping the node's role adds at most one session per write the node makes, and holders pay per session only through its writes (frontier entries, `ix.ranges`: as for a restart). Residual (spec/sync.md §9): writes made under the old session after the grant's key but before the node learned of its demotion. The undo log's `restored` matches a stamp to the logged write by its source alone (the log holds own writes only).
- `Engine::write` sorts ops by key lifetime and refuses what asks for two kinds (`Error::Clash`): durable ops into the `Mutation` (plus chain records and membership conversions of the drafts it persists), ephemeral ops into one memory commit per expiry class. One `Engine::run` transaction does the durable `commit_in`, the memory `commit_in`s (`Tx::in_class(true)`: session form, ephemeral marker, retention `writer` without bounds, the records beside each part, no chunks or pages: a delta past a blob is `Misuse` and nothing of the batch applies; `delta_past_a_blob_refused_spec_commits_2`) and the frees (`free::free` of things the batch deletes that nothing places, `freeable`). A batch's creation-only memory commits apply before the rest, so a commit adding a new thing carries its record. A batch touching a durable aspect and failing on its ephemeral half fails inside its transaction (rolled back; the engine generation moves, so tests mark "nothing durable changed" by the commit count). Then the undo log is fed from Core (`log_aspects`: the written aspects' fragments and `undo::remembered` footprints) and one `Event::Ephemeral` goes with `BatchId::Commit` (a batch with a durable half) or `BatchId::Ephemeral` (ephemeral only). Own memory commits fire no event of their own; received ones do (`apply_verified`, origin not `Local`).
- Split of group ops (`Engine::membership_plan`): durable-keyed `group.0` writes are taken out of the batch and split per op. A member add is durable iff the member is durable after the batch; a member remove iff member and group both are; any other op (a raw root op) iff the group is; an op that is not durable goes to `ephemeral_group.0~`. What persists is a fixpoint: owner-chain closure of the things with durable aspects or `persist`, plus groups getting a durable add, plus groups the persisted things' draft memberships convert into (when the node may write them), until nothing grows. `membership_plan` converts the draft memberships of every durable thing a batch writes durably, not only persisting ones (a restored draft gets its draft membership back from the host; a membership made ephemerally while the thing persisted elsewhere). Conversion per membership: a durable add into the group's durable `group.0` delta and an `ephemeral_group.0~` remove (the memory half). An expiring membership is found by stripping the aspect's expiry classes in turn until the element goes (a class already past its time skips the conversion). A removal of the item from that group in the persisting write wins: only the ephemeral reset is written. A persisting thing that is a group ephemerally gets `Set(Group::default())` first in its durable `group.0` ops (groupness persists, its drafts do not). A membership that does not convert (removed by the write, expired) persists no group. `ephemeral_memberships` scans `defs` per written thing, skipped when `defs` is empty.
- Reads (`read.rs`) come from Core state (`ephemeral_core_value`, `ephemeral_group_value`); synthetic aspects and `groups_of` (over `Indexes::ephemeral_group`, kept by `observe_state` of `ephemeral_group.0~` and following every write of it, `Tx::derive`, so an un-merge rebuild keeps it) include ephemeral data; `durable_groups_of` is the durable side. `created` reports memory records. A freed thing's aspects go out as changed (watches see `None`).
- Restart: everything ephemeral is gone locally and the next open draws new sessions; syncing brings back what holders kept, own old-session writes included (held like others' commits, compacted by the ordinary trigger). Nothing per session is kept across restarts.
- Node-sync subscribes with `subscribe_durable` (no `Event::Ephemeral`) and the osis handle shows it `SyncEvent::Local` after ephemeral-only events only when `has_memory_changes()`. Open: node-sync treats an ephemeral expiry on a durable group's `group.0` as a durable change (`only_ephemeral` is false there); harmless, a wasted check.
- Cost (release, `tools/icount`, `ephemeral::bench_ephemeral_sets`, setup subtracted): a local ephemeral set through a `write()` batch on one aspect about 19.8k instructions (undo log footprint, delta copy and log entry about 4k of it; rights check about 4.6k, the largest part, trivially cacheable per (thing, roster generation) if a budget needs it), against a `BTreeMap` insert 316 and a durable set 5.3M.

## Undo
- Undo log (`Eph.log`, `ephemeral/log.rs`): per own batch with ephemeral writes (fast-path durable batches log nothing) its id (the commit, when it follows one), `reverts`, actor, ts, and per aspect delta, counter range, `footprint` of the pre-write state, schema: O(change). Byte size = `Fragment::approx_bytes` of delta and footprint plus the entry's own size (`approx_bytes` counts heap structure, within a few percent of measured RSS growth per logged write: an int set about 1.9 KB, a two-entry map set about 12.5 KB; counting stamps and values only is 6-16x low). Past `ephemeral_history` the oldest entries go; an ephemeral-only one is remembered per aspect (newest ts and id, and whether it was a revert), bounded by the aspects held. At 0 nothing is undoable. Replacing the log with undo over held bodies is step D of issues/eph-unify.md.
- `Engine::revert_batch(id, actor)`: the log entry's inverse writes (`osis_crdt::undo` against the current state, the footprint as buffer, `restored` judged over the log), then for a commit the durable undo commit at the same `ts` (`undo_in`), then one ephemeral batch logged with `reverts`, applied in one transaction (`revert_inner`). Returns `Reverted::{Written, Superseded, Compacted}`; an ephemeral id from another session or node is `Misuse` (osis `Invalid`). A commit whose following memory commit left the log reverts the durable part only (as after a restart).
- Commit query: entries keyed by `BatchId`; a logged change joins its commit's entry or, ephemeral-only, is `CommitKind::Ephemeral` (changes and reverts alike; `reverts` tells). Relations (`reverted_by`, in effect, depth) over the related commits plus the whole log. Redo's "no newer change" test uses depth > 0. An own write covered by a snapshot is still an own write for undo (`own_gone` judges by the state, `copied_expiry` by the write's session: a plain-session write never expires).
- Scope: `Thing`/`Group` cover held durable aspects plus `Engine::ephemeral_scope_keys` (every ephemeral key of a draft; a durable thing's `ephemeral_group.0~`); `scope_aspects` filters a durable thing's aspects to durable keys. Undo first checks the newest dropped ephemeral batch in scope: newer than the chosen target is `NotUndoable{Compacted}` (redo: a dropped change gives `None`).
- Undoing a creation deletes (spec/crdt.md §4.6): log entries record the drafts a batch made and deleted (`log::Making`); `revert_batch` deletes what the change made (a commit's `created.0` things via `undo::unmake` in `undo_in`; their ephemeral side and a logged batch's things still drafts via `unmake_ephemeral`: aspects reset, entries removed from `ephemeral_group.0~`) and brings back what it deleted (`EphThing.deleted` cleared; it is never freed meanwhile, so redo can restore it). `ephemeral_log` lists `(t, created.0)` for made and deleted drafts, so a Thing scope sees the creation.
- Undoing a save returns the draft (exact undo: the draft existed before it). `Making.saved` records the drafts a batch saved and `undo_in` gets them as `Mutation::undo_keep` (not deleted). The conversion's draft membership reset is logged, so the undo puts the draft membership back. The record stays durable: the thing goes in `Eph::drafts` (memory only, one entry per own undone save, with a deleted flag), which makes it known, counts as a draft for the Thing scope and for deleting it by undoing its ephemeral creation. Its next durable write saves it again (`Placed.saved`); redo, a new save or `delete` takes it out of `drafts`. With no log entry for the save (another node, compacted, restarted) its undo deletes instead. After a restart a restored draft reads like a deleted thing unless its group synced (then its ephemeral content and membership come back).
- Rules found by `ephemeral::ephemeral_reverts_within_rights_alike_*`: a revert's writes on several things are one memory commit (every batch's memory commit spans its things; the pass places a commit's bodies under a label holding any of its things, each body the label's actor may read); `ephemeral_group.0~` never takes "Absent before" (a root reset of it, reverted later, would be a `replace` throwing out every item added since, which then synced no more); an undo whose deletion also writes the `ephemeral_group.0~` its inverse writes continues that delta (`Writer::resume`: one delta stamp per delta, spec/crdt.md §3.3 rule 7); a revert flips a thing's deleted mark only if it changes it (reverting a second undo of a creation does not bring the thing back while the first stays in effect).
- A commit on things in no labeled closure is held and goes nowhere until a closure holds one of them (the passes judge the closure's commits again when it moves, spec/sync.md §3).

## Synced ephemeral data: ordinary commits in memory
- **Ephemeral commit.** A commit with the header marker `ephemeral` (header field 14, `EphClass::Plain` or `Relay`), session form for a writer's own writes or commit form for a memory compaction snapshot (spec/commits.md §2), no `created.0` part: each part carries beside its delta the creation records of the drafts it is on or its `ephemeral_group.0~` delta places, with their draft chains (self-certifying, unsigned, per blob), signed, encrypted, projected and wrapped as any commit. A batch's ephemeral writes are one commit per expiry class (a deletion's resets ride with the removal from the group). Every node keeps ephemeral commits in memory only (the store's memory overlay and Core's indexes, `Engine::holds_memory`); never persisted, never in bundles. Memory parts decode with `osis_crdt::Unpaged` everywhere (`judge_part`, `stream_stored`, `examine_stored`, pending strip, relay), so a value of any size up to a blob is inline; `MAX_PAGE_ITEMS` binds durable deltas only (spec/crdt.md §8). Ephemeral deltas are never paged and must fit a blob (8 MiB; a larger one is not sent, `EphemeralRefused`; issues/eph-unpaged-cover.md).
- **On the durable sync path** (`core/node/src/sync/memory.rs`): node-sync's passes judge, place, upload, relay and delete memory bodies exactly as durable ones (`label_bodies_meta` lists memory commits; `place` seals with the header's class and stores the blob in the overlay; `Entry::memory`/`BlobRec::memory` keep every sync record about them out of `y/`). `Engine::closure(g)` is the closure through `group.0` and `ephemeral_group.0~` (cached by `Core::ephemeral_group_gen`). Node-sync routes by the blob's prefix class in one place. What stays particular (`memory.rs`):
  - the node cap at the one ingest site (`ingest_memory_entry`: room, `PENDING_SHARE`, `unfit`; refused entries fetched again once the label's bytes drop below what they were at refusal);
  - the restart reconcile (`Memory::reconciled`): the first sync of a label at a host after a start reconciles the live sets and keeps the cursor, so entries the persisted cursor passed come back as `need`; marked done when the reply arrives (a connection ending first, or with any of the reply's fetches unanswered or refused, reconciles again: nothing else names an entry the cursor passed); not after a cursor-less replay, not on reconnects within one run; a Push during it keeps no cursor;
  - presence of memory entries dropped when a connection ends (a restarted host lost them) and learned again by the first Sync's `gained` list (`memory_gained`/`memory_synced`: what the host does not want is present there);
  - hold-back and coalescing before a send (`coalesce_own`, Memory commits below);
  - carriers of a dropped memory part read from the engine (`carrier_of` follows `Dropped::covered_by` via `Engine::coverers_of` and forgotten coverers, since `drop_covered` sets no carrier row; without it a deleter snapshots the aspect anew every pass);
  - the headers of forgotten memory commits kept while their entries are known (`Memory::forgotten`: deletes at hosts are judged by them; a coverer forgotten before it was placed stands for what covers it, `carriers_of_forgotten`; a coverer a host refused for its cap goes up again replacing the covered entries);
  - a memory entry's tombstone at `MAX_DRIFT` (an announcement of a tombstoned blob is nothing);
  - an upload a host refused for its cap tried again once per resync while the body is held (`SyncEngine::capped` dirties the label at `timers`; durable too);
  - relay-only commits (`relay_in`, `send_relay`, `RelaySeen`).
- The compaction trigger skips only a thing that was a label entry here and left every closure (a snapshot of it would go nowhere while the covered commit may still travel beside a removal from the group); local-only things compact, else a rewritten UI value keeps every body. An entry is deleted for being outside the closure only by a node that judged or placed it inside (`State::memory_in_closure`): a restarted node's closure is what has arrived so far, and deleting window bodies while the membership waits its relay delay is a storm.
- Only commits the engine verified and holds are kept, served and spread (far-future dropped; unknown authors wait apart within `PENDING_SHARE`); pending commits are retried only when a record they wait for arrives; another blob of a held commit has its signature and delta hashes checked before it is kept; a replay of a covered commit is not held again and a writer deletes it.
- **At hosts.** The blob prefix has a class field (byte 25, osis-label `Class`): durable, `ephemeral` or `relay` (signals), from the commit's marker (spec/sync.md §3). A host keeps ephemeral entries (blob, wrap, stamp, log event, tombstone) in memory only (`Ephemeral` in `HostStore`), under a per-label byte cap (`HostPolicy::ephemeral_bytes` 16 MiB) and a total (`ephemeral_total` 1 GiB), code 12 past them; deposits of ephemeral or relay-only blobs are code 1; unstamped ephemeral and relay-only blobs are refused for every store. Log sequence numbers are shared with the durable log, reserved on disk in blocks of `SEQ_BLOCK` in the label meta's `reserved`, so a restart never reuses one (a cursor ahead of the durable log stays valid). The in-memory log is trimmed at `EPH_LOG_KEEP` records per label; the durable log is trimmed by its own record count, so ephemeral churn never sends durable cursors to reconciliation. Ephemeral deletes and replacements are rate-limited, due times are indexed (sweep budgeted), the label using most gives way at the total cap. A restart loses everything ephemeral. The rest is the ordinary path: upload by stamp, cursor sync, range reconciliation, subscriptions pushing new entries, expiry, delete keys.
- **Convergence and reconnect.** Ordinary (spec/sync.md §6): a holder bridging two hosts or a co-reader peer serving its own label carries ephemeral state across. A joiner or restarted node gets the state by its ordinary first sync from any host or peer that holds it; if every host restarted, holders upload again (presence is per connection). Residual (spec/sync.md §9, as durable's spec/permissions.md §5.2): a write covered by a snapshot that fell invalid comes back only from a writer still holding it; readers lose their entry of it with the host's deletion.
- **Signals.** A write's signal writes become one relay-only commit (`ephemeral/signal.rs` `take_signals`: one commit per write, grouped by the write's `ts`, snapshot deltas, records of the drafts beside; grouping per actor would make two writes of one aspect before a pass one refused commit). A host, or a co-reader peer serving the label, accepts it by stamp like any upload, pushes it to the label's current subscribers (`ServingOutput::Relay`, a `Push` of one add event at the subscription's cursor) and holds nothing: no entry, log event, tombstone or expiry, so it never reaches a later sync. A co-reader peer passes a verified new relay-only commit on (from a host to its sessions, from a session to its other sessions and the label's hosts), each blob once, so a node reachable only through it gets the signals. `ingest_relay` verifies, judges the author's write role through carried or held memory records and the durable thing's timeline, delivers each valid signal part to callbacks once and holds nothing (no state, no body, never re-uploaded). Dedup (`Delivered`) is per (commit, part): a commit whose parts have different readers goes as several blobs. A node remembers delivered relay-only commits until their `ts` is `MAX_DRIFT` old, with a floor per author past `MAX_DELIVERED` (a floor shared by all would let one flooding writer drop every group's signals), and drops relay-only commits older than that. The blob's prefix expires at `ts + MAX_DRIFT`: hosts and peers admit relays through `osis_proto::RelayGate` (expiry window, `MAX_RELAY_BLOB`, per-label rate, push once per blob); receivers drop relay blobs unopened when oversized, outside the window or seen (`RelaySeen`, checked before opening but recorded only once verified, so keyless junk cannot raise the floor). Within that window a signal can arrive late (a delayed push), and a restarted node can see one again if a replayer uploads it to a host that forgot it. A node's own signals fire locally.
- **Validity, ordering, replay**: ordinary commit rules (chains, parking past `MAX_DRIFT`, idempotent apply). A replayed old ephemeral commit only re-adds writes its stamps already lose to, or that holders still have.
- Leak: a host learns which entries are ephemeral. Nothing else.
- Open, deliberately not built: a node that stops syncing a label or loses read access keeps that label's ephemeral state until restart; relays are not delayed, so every bridging holder uploads a duplicate (answered OK).
- Tests: osis-node `tests/it/ephemeral.rs` (with `random_window_converges_*`: four writers, two hosts, random writes, partitions, restarts, a random host cap on odd seeds; tier 2 `random_window_converges_large`, `random_window_one_capped_host_*`, `OSIS_EPH_START`/`OSIS_EPH_SEEDS`, about 11 min for 300 seeds together), `memory_*` differentials, `random_churn_converges*`, `sync::signals_relay_only_spec_sync_5`, `hostile_host::replayed_signal_dropped_spec_sync_9`; osis `sync::remote_signal_spec_sync_5`, `tests/it/ephemeral.rs`, `ephemeral_undo.rs`; osis-host `hub::subscriptions_and_relays`, `hub::ephemeral_entries_in_memory`; proto `loopback::subscribe_push_and_relays`; vectors (ephemeral and relay-only commits, prefix classes); sim `ephemeral*`.

## Memory commits
Ephemeral data is Core's memory class end to end. What is special: memory storage (the overlay), the second session for expiring writes, vanish-whole expiry and superseding (Expiry, Superseded expiring writes), signals, the restart reconcile, the caps.
- **Receiving**: every ephemeral blob goes to `Engine::ingest_memory(bytes, room)`, routed on `Ingested`: `Applied` kept as an entry, `Duplicate` kept once `parts_genuine` (a copy carrying the held parts' bytes), `Pending` kept apart within the share (else `forget_pending_memory`), `TooLarge` refused and reported, `Parked` dropped. Charge per entry `memory_charge`, bound before decode `memory_bound`; parts are judged like durable ones (spec/permissions.md §5.2), applied atomically, un-merged by demotion.
- **Each step** node-sync drains the engine: `take_memory_invalidated` (aspects a held memory snapshot turned invalid on: a writer still holding a valid part writes a fresh snapshot of what it holds, uploaded as a new commit, and the label is reconciled so holders' copies of what it covered come back; the authors' own writes, kept under others' snapshots, return to hosts and readers this way, since a re-upload of the covered entries would meet the host's delete tombstone; `compacted_write_of_removed_holder_stays_spec_permissions_5_2`. Gated on a valid-to-invalid flip of a held snapshot, so only a role change triggers it, at most one snapshot per writer and aspect per step; an author that restarted or never held the fallen snapshot valid does not, and its covered write stays gone at readers until it writes again, spec/sync.md §9), then `memory_compactions`, then `take_memory_drops` (commits forgotten, `MemoryDrop::{Covered { by }, Superseded { by }, Gone}`: the lane forgets their entries and, as a writer, deletes them per label once a coverer or superseder is held there; `Gone` deletes at once).
- **Snapshots and covering** (`retention/memory.rs` `drop_covered`, `retention/snapshot.rs`): a memory compaction snapshot is commit form, ephemeral marker, the aspect's whole state at that node (every author's writes, frontiers over every session, expiring deltas neither carried nor covered, `Absorbed` for by-ID commits), retention `writer` without bounds, records of its thing and the things it adds beside it. **Covered drop rule** (code comment in `drop_covered`): a body whose author is this node is dropped as covered only by this node's own snapshots; any other author's body drops under any valid held snapshot covering it. So a demoted compactor's snapshot falling invalid (its demotion lists no memory commit) loses at most the demoted author's own writes: every other author still holds its own bodies and re-uploads them when the label is reconciled (`memory_compactor_demoted_keeps_others_writes_spec_permissions_5_2`, `snapshot_invalidated_by_self_removal_reads_alike_spec_permissions_5_2`). Of covered-equal snapshots the higher ID goes. `covered` checks the frontier before decoding. No receipts for memory commits. A forgotten body not held elsewhere is gone, as durable's residual (spec/permissions.md §5.2).
- **Trigger** (`Engine::memory_compactions(force)`): per memory aspect changed since last weighed (`MemorySync::dirty`), with two or more held non-snapshot, non-expiring bodies costing (`held_cost`: `part_weight` plus `ENTRY_CHARGE` each) more than `FACTOR` times the snapshot's cost (`snapshot_cost`, measured by encoding), `compaction_snapshot` if this node may write the aspect; weighed only when the held cost passes the factor times the cost last weighed (Bounds). Counted are only the bodies a snapshot built now would cover (`retention::frontiers_now`, the snapshot build's own frontier walk): a session's bodies behind an invalid or missing one stay held uncovered, and counting them makes the trigger fire on every step; one invalid for good makes its author begin fresh sessions (Local engine), so nothing later piles up behind it. Snapshots are not counted as bodies (two writers each keeping their own snapshot under the covered drop rule would otherwise re-snapshot each other forever). Any writer compacts: concurrent snapshots are covered-equal duplicates, dropped by rule. `force` (`compact_ephemeral_now`, tests) snapshots every memory aspect with a body. A host's cap refusal triggers nothing.
- **Coalescing** (`coalesce_own`, before a pass sends under a label): own memory bodies not yet placed under the label wait while an own memory upload under it is unanswered on the connection; then two or more on one aspect go as one snapshot: of their join alone when all are this session's plain writes (`Engine::coalesce`: frontier `{own session: up to the last of their counters}`), of the whole state when a snapshot is among them (`Engine::snapshot`), covering them at every holder; a body the snapshot cannot cover goes as it is. One delayed plain commit instead is impossible without restamping: a writer delta's commit-level writes must carry the delta's stamp (spec/crdt.md §3.3 rule 7), and several commits' writes have several; a snapshot carries foreign stamps, and its frontier makes it exact. Expiring writes are never coalesced (superseding thins them). Signals are not held back. Measured: one entry per aspect per round trip.
- A memory part answers to no `required.0^` rule (`validity::under_required`, spec/commits.md §5).
- **Growth**: `MemorySync`'s sets drain each step; `weighed`/`dirty` entries go with their thing (`free`); memory things and commits are bounded by the caps and forgotten once spent (`forget_if_spent`).

## Expiry
- Expiry is death by timer (spec/crdt.md §4.8): the values die at T and the body follows, whatever the deltas' keep bounds. "Keep at least until T" is a retention bound (spec/commits.md §5), a different thing.
- Covers disappearing messages (write-based timer in core; read-based timers and earlier deletion are app writes; core expiry is the hard upper bound and lets a host wipe them unattended) and buffered events (a list aspect with a one-hour default). Cheaper than keep-at-most 0: nothing has to be deleted by hand, and the host does it unattended.
- Leak accepted by Tess: a host learns which entries expire and when.
- Not provided: host-enforced minimum retention (legal hold). Keep-at-least binds honest nodes; a host deletes whatever a delete key or its label delete key tells it to.
- **Ephemeral expiry vanishes whole** (spec/crdt.md §4.7 Ephemeral data): at T an ephemeral delta's writes all go, resets and removals included, at every node and for its author, as if never applied; an expiring removal stops removing at T. Durable data keeps its value-less records. Why: value-less leftovers would live only in the state of nodes that held the commit at T (a rebuild, a late joiner or the author's own copy differ), and ephemeral data has no carrier for them (only an author covers, never expiring writes, and nobody may re-serve the body after T). Built in Core (`retention/memory.rs` `vanish`): a memory delta at T drops its body and the aspect is rebuilt without its writes (`rebuild_without`), its commit forgotten once spent. **Invariant** (module doc): a memory aspect's state is the join of its valid held parts, so two nodes holding the same ephemeral commits read the same, whatever expired when. Superseded writes vanish the same way.
  - Consequence: a write into an entry an expiring write created outlives that entry (the entry's record repeats the key, and a map record lives by its content, spec/crdt.md §5.6), so a writer gives such a write an expiry no later than T; it then reads alone everywhere, as at a node that never held the entry (`set_into_expired_entry_reads_alike_spec_crdt_4_7`).
  - Undo of an expired batch writes its inverse as usual (a removal re-added with a fresh dot, a register untouched since its write is not the winner): convergent. An undo copies back no expired content: `undo_expiring` strips it from the pre-state and reruns until none is copied (a single strip lets a `Set`'s undo restore a shadowed older entry's expired value, `undo_of_set_past_expiry_restores_no_shadowed_entry_spec_crdt_4_6`). Test `ephemeral::expired_removal_vanishes_everywhere_spec_crdt_4_7`.
- **Expiry never waits for a Tick** (durable too): a Tick comes late (`MIN_WAKE_MS` throttle, a suspended process; in the node test net an offline node gets no events at all), so the osis handle runs `SyncEngine::expire_due` before every call under its lock: when `Engine::timers_due` (in-memory: `Core::timer_floor`, a lower bound of the earliest durable timer, and the ephemeral timer map) it runs the Tick's engine part (live-drop snapshots and `tick_round`, in rounds, `tick_ephemeral`); every sync step starts the same way when a timer is due. Pushed change events still come with the Tick (up to `MIN_WAKE_MS` late) or the next call: a subscriber's last value can show past T until then. Tests reading through the engine directly call `expire_due` first (`random_churn_run` checks every step that no value is read at or past its expiry).
- Nothing is kept "until every receiver has seen it": the receiver set is open and nodes die. What must survive every holder forgetting it (restarts) is durable state: the inbox pattern (receiver-owned list, senders append, owner deletes, expiry as backstop) or a list with expiry.

## Values that live while their author is there
Tess's decision: a value that should live only while its author is there (a cursor, a selection, an "online" mark) is an ephemeral aspect with a short default expiry (`~` key, `[expires: 30s]`) whose author rewrites it before it expires; when the author's node goes away the rewrites stop and the value is gone at every node holding it by its last write's expiry. Nobody needs to notice the departure: no connection tie at hosts, no source tracking or un-merge at holders, no lease or keep-alive constant.
- **Helper**: `db.at(t, k).path(p).keep_alive(&value) -> KeepAlive` writes the value and rewrites it every `expiry / REFRESH_DIVISOR` (2) of the key's default expiry on the handle's runtime until the `KeepAlive` is dropped; `KeepAlive::set` writes a new value at once. The key must be ephemeral with a default expiry. A rewrite is a `Put` (a fresh entry at a map key, a fresh register write elsewhere): a `set` of an equal value writes nothing, and a write into an entry an expiring write created outlives that entry (Expiry) unless it expires no later. `Replace` would not: at a live key it writes into the old entry and goes at that entry's expiry.
- **Cost**: each rewrite or `set` supersedes the write before it (below), so a holder and a host hold about one commit and entry per kept value, and one upload goes per value per half expiry or per round trip while it changes (`ephemeral::moving_cursor_one_entry_per_author_spec_sync_9`: 60 moves, one entry). Left: an expiry under the sync tick (1 s) still rewrites every half expiry, one upload per rewrite, while expiry is applied only per tick.
- Two nodes keeping one path alive overwrite each other at every rewrite: key by node (`Osis::node`), not account. Nothing survives a restart: the app calls `keep_alive` again.
- **Choosing the expiry** (the schema's, per aspect): how long a departed author's value lingers against the rewrite traffic. 30 s suits cursors.
- Rejected: write-level "until the author disconnects" (Tess's idea, evaluated). It needs a host tie per connection, holders tracking which host or peer still has the author's entry, un-merge when none does and a lease backstop for half-open connections, and "disconnected" is per path, so holders behind different hosts disagree.
- Tests: osis-node `ephemeral::refreshed_value_lives_while_author_present_spec_crdt_4_7`; osis `runtime::keep_alive_rewrites_until_dropped`; sim `ephemeral`/`ephemeral_capped` (random expiring cursors; `author_leaves`: a refreshed cursor at every connected holder before each refresh, gone past its expiry once the author is down).

## Superseded expiring writes
Snapshots never carry expiring writes, so without this rule a cursor kept alive with `KeepAlive::set` (a fresh map entry per move, `Op::Put`) costs one commit, upload and entry per move until each expires.
- **Rule** (spec/sync.md §9, `retention/memory.rs` `supersedes`, `drop_superseded`): a held plain commit whose parts all expire and carry no reset is dropped once each part is superseded by a valid held part of another plain commit of its author on the aspect: that part expires too, no earlier, carries no reset, each of its writes is stamped later than every write of the old part and none is a write into a record it did not create (a `Set` into the entry a move created goes with that entry), and the old part joined into it reads as it alone. Core keys alike: an `ephemeral_group.0~` part is superseded as any (`membership_superseded_like_any_write_spec_sync_9`). Checked at every node when a commit is held (own builds included), each candidate costing a join and two reads of two small deltas; a received commit superseded on arrival is not held (`Dropped`).
- **Not death, but convergent** (spec/crdt.md §4.8): an older `put_new` entry at a key stays live in the CRDT, only shadowed in the read; the rule makes it expire early instead. Convergent because the drop is a function of the commits held, never of later writes: every node holding the newer part valid drops the older (at its arrival, at the newer one's, or when the newer turns valid, `rejudge_ephemeral`), and a later removal or undo of the newer entry kills only that entry everywhere. The conditions each close an order dependence:
  - the author drops the superseded writes from its own state and unsent writes too, else after a holder removes the newer entry only the author reads the old one again (`superseded_stays_gone_when_newer_removed_spec_sync_9`);
  - neither part carries any reset (`Fragment::has_any_reset`): a superseder with a reset makes the relation intransitive (q replaces the aspect over p, r later puts without it: r supersedes q but not p, so p is dropped or held by arrival order), and a superseded part with a reset takes its tombstones with it at holders but not at the author;
  - the superseder expires, so no cover ever absorbs it (a cover carries older writes and supersedes nothing; a node that got only the cover would read the move again once the plain entry is removed; `superseding_part_expires_spec_sync_9`);
  - the ts order and the expiry guard: a later write expiring sooner, or an older write with an equal value, supersedes nothing (`superseding_needs_later_stamps_and_no_reset_spec_sync_9`).
- Rejected: real death. Each move would have to tombstone every own entry of the key not yet expired (about expiry / round trip of them per commit, 450 at 30 s and 66 ms), since dropping a commit drops its tombstones too.
- Left: a superseder turning invalid later does not bring the dropped commit back (a memory part's late copy is refused, `retention::takes_late`; durable keep-bound drops join again, spec/commits.md §5).
- **Holders and the author** forget the superseded commit whole (`unindex_commit`, reported as `MemoryDrop::Superseded { by }`) and rebuild the aspect without it (as at expiry). An own commit superseded before it was placed is forgotten the same way, never sent: a burst of moves during one upload goes up as the last one. The lane deletes a superseded entry where a superseder is held, else at its expiry.
- Measured (tier-1 `Net`, 66 ms round trip, 10 authors moving every 33 ms for 1 s): 160 uploads, 0 deletes, the host's peak 43 KB of a cap scaled to 560 KB, one entry per author at the end; without the rule 224 entries. A simulated minute at the default policy (tier 2, 17 min dev at load 6-12): 9100 uploads, 0 deletes, peak 1.76 MB of the 16 MB cap.
- Tests: osis-node `ephemeral::{moving_cursor_one_entry_per_author, superseded_unsent_moves_one_commit, superseding_needs_later_expiry_and_own_records, superseding_needs_later_stamps_and_no_reset, superseding_part_expires, superseded_stays_gone_when_newer_removed, many_authors_under_host_rates}_spec_sync_9` (4 authors), `many_authors_under_host_rates_large` (tier 2: 10 authors for 1 s, then a simulated minute). `random_churn_converges_spec_sync_9` (4 seeds) and `random_churn_converges_large` (tier 2, `OSIS_EPH_START`/`OSIS_EPH_SEEDS`): random expiring and plain puts, removals, replaces, undos, demotions, partitions and restarts; holders never demoted read alike.

## The all-nodes predicate
"All nodes a thing syncs to" is a state predicate computable at nodes that read the label, never a protocol condition. Per label: the nodes with a valid chain that published `node.0` under the thing's label (not "every node of every holder", which needs rosters readers never see).
- Recency: each node places an expiring `seen.0` heartbeat under each label it tracks (spec/permissions.md §4); the live one's value is its last sync of L, absent means unknown. `seen.0` is one aspect of the node thing, so its joined read is "last seen anywhere"; the per-label answer comes from the sync layer's record of which heartbeat commits arrived under L, not from the aspect. (A `map<label ID, timestamp>` would give aspect semantics but leave a value-less entry record per expired heartbeat forever.) The heartbeat also carries `stranded`, the one signal a node that cannot open a label's current epoch, or cannot walk to the head because a claim set was dropped, can still send (it deposits without opening the label, under the newest established read secret it holds, which co-readers open by history boxes), and what triggers a re-seal; it is placed only after a complete pass at that host (the rotation commits are uploaded before the step, notes/label-access.md, so "cannot open" means not boxed, never "not fetched yet"); it fails only when the deposit key changed under it (a manual re-share, notes/label-access.md). The node list (the node card) and recency are separate aspects because an expired register winner reads as absent and the older write does not show through: an expiring re-put of `node.0` would drop the node from the node list when it lapsed.
- Why a durable heartbeat and not a node-card re-put or ephemeral data: a reader's re-put is a deposit that sits in the label's budget until a writer promotes it, so readers × cadence × promotion delay would have to fit a budget the spec never sized, and a full budget refuses the deposits that matter (grants into the group, a reader's self-removal, a revoke only readers hold). Expiry frees the budget unattended (no tombstone, no delete, no writer), so a reader holds at most ceil(lifetime / interval) entries at once and the budget is sized from the claim set (spec/sync.md §5). Rejected: deposit new card plus token-delete the old one (a delete and a 30-day tombstone per refresh, reader-side delete flows, rate-limited deletes); ephemeral writes (the asker is rarely online with the reader, and readers cannot write ephemeral data); host arrival times (untrusted, per host).
- Leak accepted by Tess: a host sees each reader's heartbeat rhythm per label (same class as deposit and expiry times it already sees). Clock skew between the heartbeat's writer and the asker shifts the reading by the skew; lifetimes are days, so no coarse policy notices.
- A node reading the label keeps its own local record of the last heartbeat it saw per node, for policies wanting a longer memory than the lifetime; it is a lower bound, not knowledge of the gap.
- Uses: write a new schema form once every node reads it (fixes the read-only old app the header heuristic cannot see), drop old-form history after that, clean up an inbox once every own node has acked.
- Dead nodes: a lost phone's heartbeat lapses and it drops out of "all nodes seen recently" on its own; a policy that needs it gone from the node list too waits for an explicit node removal. Never gates deletion at hosts.
- "Buffer until all have seen it" = inbox pattern plus this predicate plus expiry as backstop. Fine as a core helper later; not sync machinery.

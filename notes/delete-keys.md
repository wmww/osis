# Delete keys
> Summary: Why deletes are signatures under blinded keys (spec/crypto.md §7): the per-blob blind, linked blobs' link and thing blinds and why the thing is bound, the sync ID key signature, delete bases, one level-2 key per commit, measured costs, rejected designs.

Principle (Tess's decision, over hashed tokens): one mechanism at every level, signatures under blinded keys, so a writer that is no admin lists the thing's published admin key, and a thing admin who is no admin of S's thing deletes a writer's data at nodes keeping S unread (hashed tokens needed the admin secret to list level 1).

## Blinds
- **The blob blind**: each blob commits to A' = h·A, h from A, the prefix salt and a 16-byte random blind in the encrypted header (Tor v3 style). Without the blind h would be computable from A alone, and A is widely known (level-2 keys travel in chain certificates and contact profiles, a key actor's is its signing key, a thing's admin key is known to its readers), so a node keeping S unread colluding with any contact could link an author's blobs across sync IDs (spec/requirements.md, Data a node cannot read). Only header readers compute A'; only the holder of a signs; a delete reveals nothing. Blinded signing derives the nonce prefix from the seed, salt and blind, so two blinded keys never share a nonce.
- **Linked blobs carry their own blind** (chunks, tree nodes, pages, header-list blobs): the link blind, from the blob key (`osis_crypto::link_blind`), bound to the blob's thing by the thing blind (`osis_crypto::thing_blind`; a header list's thing is the header's actor). A link carries the blob's prefix salt and its Del (spec/data-model.md §6); reuse copies a link verbatim only when the prefix bears its salt and Del (`Framing::keeps`, `tree::bears`). So reuse needs no header: a node that never received the commit introducing a value's chunks (dropped under a compaction, or forgotten under its author's own replaces) reuses them instead of logging every one again per edit. Deleting goes by link too: a dropping node keeps its body's links in a freed set (spec/sync-compaction.md §1 freed links), so the delete needs no header either.
  - What it protects is unchanged: a node keeping S unread or a contact knowing A still cannot link blobs to keys (the blob key never leaves link holders and is random per encryption, so no confirmation by content either), and the right to delete is still the holder of a. A reader holding a link can test which author chain a chunk commits to, also one that never held the introducing header: that is the author of an earlier edit, which readers may learn (spec/requirements.md, Confidentiality between readers).
  - **Why the thing is bound**: anyone reading a value holds its links, so a writer of t1 who reads t2 can set a t1 value to t2's link verbatim. The deleter's "still linked" check walks the trees of the link's thing only (walking every thing a node holds per freed link scales with the wrong thing, and an admin of the sync ID's thing may hold none of t2). With the thing in the blind, a link judged under another thing names commitments the blob does not bear: a node keeping S unread refuses a delete by level, and a node holding the blob checks the link against the prefix before deleting by the sync ID's delete key, walking it or dropping its copy (`retention::freed`, `freed::lost`). The judgment is per thing, so t1's link keeps nothing of t2 alive either. Without it, dependent things with one independent (one delete base) would still let a copied link through. A node not holding the blob deletes by level only, so a lazy admin without the delta's delete keys leaves the delete to the delta's right holders.
  - Rejected: a blind from the thing's dedup secret and the salt (no link needed): the dedup secret never rotates, so a removed reader colluding with a node keeping S unread would link every later chunk to its thing and author. Keeping the introducing header at every holder while its chunks are linked: must-hold header-only blobs and forget rules per chunk, and nothing for a commit forgotten under own replaces. A snapshot listing chunks with their introducer's blind: a reuser holding neither snapshot nor introducer still re-encrypts; every delta listing what it reuses is O(value) per edit.

## Keys
- The sync ID key signature stays: every past holder of an epoch's secret can sign with its delete key, so only the sync ID's key proves current roles.
- A dependent thing uses its delete base's keys (its mint admin's admins are its admins while nothing is granted on it, so the right holders are the same and nothing per thing is published); a key-actor base uses its signing key (public through the creation record; key actors never rotate). The base is the thing's independent, so a thing whose `keys.0` has not arrived is not writable rather than wrongly listing its mint admin's key. Residue: a planted reading-only box for a dependent thing creates a `secrets` entry with no keyset, so the thing is its own delete base and unwritable until its `keys.0` arrives.
- A grantee gets a role before the target's delete keys where the target's `keys.0` is not held yet: until they are here a content write is `Permission` and `role_on` reports `Read` (`Engine::holds_delete_keys`), and `redeem` returns once `role_on` reports its role.
- One level-2 key per commit (the author chain), checked at receivers: header-list chunks and tree nodes commit to it alone (Tess: one uniform rule, no cutoff). At nodes keeping S unread the author chain deletes them by its delete key, else the sync ID's delete key, so a thing admin who is no admin of S's thing waits for one there (accepted). A commit listing no level-2 key (every delta admin-only, the default) leaves that group empty: its header-list blobs go by the sync ID's delete key or at expiry alone.
- Engine: `delete_key(level, base, author)` (newest held), `delete_candidates` (every held epoch); keysets carry `delete_key`.

## Costs
Measured (`budget_minimal_commit` and arithmetic; a minimal `author_or_admin` commit, two levels): header 322 bytes plaintext (two `[level, 32-byte key]`, the 16-byte blind), prefix 33-byte commitments, commit blob 444 bytes after Padmé and tag (Padmé steps at 320 bytes; with three levels, `writer`: 17 more in the header, 16 more in the prefix); a chunk's prefix carries the same 33-byte commitments; an inbox payload names a target's two delete keys (about 70 bytes per independent thing); a delete by delete key carries a 64-byte signature per item; `keys.0` about 34 bytes per keyset for its delete key. Compute (`cargo bench --bench crypto`, release, shared box): derive a delete key ~12 µs, a blinded commitment ~27 µs per level per blob framed or prefix checked, blinded sign ~36 µs, verify ~36 µs; a node keeping S unread checks two signatures per delete (~66 µs).

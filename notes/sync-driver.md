# Sync: driver
> Summary: osis-sync's `driver` (core/sync/src/driver/): `Node`, the one sans-IO step (`handle`: route, settle loop, dials, keep or close, outputs), `apply` and `Links`, store-failure restarts, dial candidates and the retry rule, the tokio `TransportLinks`, and why the step is shaped so.

Spec: spec/sync-opens.md §1, spec/sync-transport.md. Overview: notes/sync.md. The harness that drives `Node` in tests: notes/sync-test-harness.md.

## The step
```rust
impl Node {
    pub fn open(engine: Engine, store: Store, cfg: SyncConfig, rng: Box<dyn NodeRng>) -> Result<Node>;
    #[must_use] pub fn handle(&mut self, input: Input) -> Vec<Out>;   // Up, Bytes, Taken, Closed, Down, Tick, Wrote, Discovered
    pub fn engine(&mut self) -> &mut Engine;   // the osis handle's writes and reads; then handle(Wrote)
    pub fn status(&self) / status_of(s) / idle() / wait(scope) / redeem(link);
}
pub fn apply(out: Vec<Out>, links: &mut impl Links);   // Out: Send, Dial, Close, Read (stop or go on reading a connection), Wake
```
`handle`, in order: the engine's reload check; the input routed to its module (bytes: `Session::receive`, then each message to the module `Incoming::to` names, notes/sync-session.md); the compaction trigger (`Engine::compactions`, spec/sync-compaction.md §1); **settle**; `Opens::flush`; the reload check again; dials; keep or close; closes; sessions' bytes; one `Wake`, the earliest of every module's `next_wake`, `Engine::next_timer` and the memo clock's next `until`.

- **Settle**: first the requests that waited for room and fit now (`Sessions::admit`, notes/sync-session.md Hostile peers), then every module's `settle` (each returns whether it acted) in the order leave, store, unread, opens, read, inbox, streams, status, life, again while one acted. Opens comes before the other sending modules so they act on this round's shared set; status's complete passes ask `Streams::pull_again` at the end of a round.
- **The loop ends** because "acted" means only that a module changed something another reads (a store row, an engine write, a member moved), each an `Effects` value moving to a new settled value; a round runs again only while values move. Two modules undoing each other would loop forever: nothing in the product bounds it; the harness fails a step past `ROUND_CAP` (16) rounds (`Node::rounds`, tests only).
- **Pass ends**: status tells each complete pass to the engine and calls `Engine::pass_end` on S's owner: re-seals, history adds, withdraws and, for the account root D, the account's owed rotations (`signing_due`, spec/permissions.md §3, §5.5). The engine's `signing_due` flag is set by an account commit from elsewhere and at open; a restart judges it only at D's next pass, which only a new role commit on D wants.
- **Members moving**: opens' `Moved` values go at once to status, read, inbox, the dials (`sharing`) and streams; streams' `Reported` go back to opens (`reports`) until nothing is left.
- **No engine events as input.** After the osis handle writes it calls `handle(Wrote)`, which only settles: what the write changed reaches sync through the memos it moved. `Engine::subscribe_durable` serves the API's listeners only.
- **Two clocks, one rule** (spec/sync-streams.md §1 Waits): every wait a module keeps in memory (dials' pauses, session deadlines, opens' resync and retries, streams' retries and asks, inbox back-offs, a pass's `PASS_WAIT_MS`, the failure stretch) runs on the monotonic clock (`osis_base::Mono`, `Engine::mono`, `Cx::mono`); the wall clock (`Cx::now`, the latest reading, never back) only stamps and judges stamped values, and dates what a restart keeps (the store's rows and its memory twins, a link's follow time, the engine's timers and memo clock). `Out::Wake` is on the monotonic clock: `next_wake` turns each wall-dated time into a monotonic one at its distance from the wall reading now, so a wall clock moved while the node is quiet is followed at its next step (an early wake costs an idle `Tick`). `Input::Tick` carries no time: the node reads both clocks at every step. Rejected: one wall clock with a cut (a deadline more than its wait ahead counts as due): every timer site needs the cut, and a forward jump still fires every wait at once.
- `apply` carries out sends and dials in the order made, then closes (a closing node's owed Applied goes first, spec/sync-streams.md §4 Reports), then one `Links::wake`, the earliest given. A step gives at most one `Wake`, last, and `Links::wake` replaces the node's earlier one, so no older wake overwrites a newer (an early wake costs one idle `Tick`). Only `handle` makes outputs: `status` and `wait` read.
- The client port's messages are carried as `PortEvent`s for the owner (`Node::port`); sync judges none of them (notes/client-port.md).

## Duties
Engine work sync drives, one `Effects` hook per kind over what makes it due, never polled (`life`, the last module of each settle round; spec rule per duty):
- **Role duties** (spec/permissions.md §2 Finalize, §3 Required rotation, Lost access): first, per actor the engine holds secrets of, one `Effects` key over `Engine::role_duty_due` (derived from the state, notes/engine-lost-access.md Owed role commits): `Engine::ensure_rotated` writes what this node owes before it next encrypts there (the finalize of a grant past its `until`, a departure's rotation, a stale box's), logged as own commits by the next round. Then, per held actor, a second key: the lost-access drop (`Engine::drop_lost`) once `lost_due` and `lost_passed` settle true (notes/engine-lost-access.md, The drop: a complete pass of its sync IDs after the cause first, the memo clock read up to the next `until`, so an `until` passing with nothing written wakes the node), and one key over `copies_due`. The wrap gate (`Engine::wrap_secret`) refuses to encrypt meanwhile: under a blocked epoch, or while a grant this node may finalize is past its `until`, so a write made before the duty ran waits for the rotation. A loss by an `until` alone (`Engine::lost_timed`, on the same per-actor key) drops once each sync ID of the actor read here is heard out for it (`life::Hears::timed_heard`: a source of it, a complete pass begun after the loss (`Cause::Lost`, whose pass the engine wants) and every own commit there held elsewhere; or no peer to wait for on S, `Opens::waited`: a peer that refused S acknowledged it and holds no member of it, so it is none), or at `LOST_HEARD_WAIT_MS` after it was first judged (read on the memo clock).
- **Joiner's leave** (spec/permissions.md §7): per thing named a holder (`Engine::role_things`, then its feed), `Engine::joined_link_ended`: a link this account joined whose K's edge on its target is removed or past `until` (the clock read up to the next `until` of K's and the target's components). One that becomes so is left (`Engine::leave_link`, a self-removal; idempotent across the account's nodes).
- A leave or untie refused for anything but a store failure writes nothing and is tried again when what its value read moves (acted on at every judgment, not only on a change). A thing named a holder no more (`Engine::named_a_holder`; `untie_due` reads its holders, so it is due then) is followed no more: the state is one value per duty per thing named a holder here.

## Failures
- A step that fails (a store failure) sends nothing it queued, closes every connection and restarts the modules from the store, once per stretch until a durable commit of either store lands; the next wakes back off from `RETRY_FIRST_MS` (1 s) doubling to `RETRY_MAX_MS` (60 s). The store's memory part (ephemeral entries) stays. A frame of the failed step might tell of what the failure undid (an Applied of a cursor not stored, a record answered but not written), so none goes; peers see a dropped connection, which every rule survives.
- The engine reading its store again (`Engine::loads` moved: a write of unknown outcome) replaces every index the modules follow (memo stamps, feeds). One rule for each: the settle ends after the round it happened in, and the step closes every connection and restarts the modules as at an open. Leave finds a sync ID still waiting to stop at a restart as at a start (out of the sync set, its entry still synced).
- Modules' effects are not durable (but opens' `changed_at`), so a start or restart settles every key once. Forgetting (lost access, a self-removal placed, a release) moves the engine's indexes in place: the modules follow the facade values it moved, with no restart (spec/sync-judgement.md §3 Restart and forgetting).

## Dials (`driver/dials.rs`)
Candidates, reasons as priorities (a candidate known at several addresses dials its best reason's, then after a failed dial the next of its others at once; a turn where each failed waits `REDIAL_MS`, so a stale dial list never hides a configured address; `Cand::addrs` counts reasons per distinct address so picking one is O(distinct addresses), not O(reasons)), the one retry rule (`REDIAL_MS` 30 s, quiet candidates waiting for a change), `max_peers` (`MAX_PEERS` 32 by default), `DISCOVERED_KEEP` (1024) and the pair rule's held dials: the module doc. Sources of candidates: `Engine::dial_peers(s)` per S this node syncs (`set::SyncsFollow`, then `Effects`, notes/sync-facade.md), `Inbox::dial_hints` (read whole each step, O(hints)), `SyncConfig::dial`, discovery (`Input::Discovered`). Unbounded candidate counts from hostile dial lists: issues/dial-candidates.md.

**Keep or close**: a dialed connection closes when `Opens::idle` (no member, nothing of opens under way), `!Inbox::may_deposit` and `Session::quiet` all hold; its candidate is dialed again after a change. A served connection is never closed for sharing nothing (spec/sync-transport.md §5). Each step reads the dialed connections, at most `max_peers` sharing ones plus those about to close.

## Links
`Links { dial, send, close, wake }` is all a node needs of the world. `TransportLinks<T: osis_transport::Transport>` (`driver/links.rs`, behind the default `driver` feature, tokio) is the product's: dials, listeners, discovery, each link's bytes and what the transport took, turned into `Input`s (`TransportLinks::next`); the osis handle's driver task steps the node on them. Tests use a `Links` per node over an in-memory fabric (the harness; `internals::ManualNet` in the osis tests). Sync never learns how a peer is reached: a connection is its key, its rank and its bytes.
- Listener sets (`Listening`: direct sync's dialable listener, `Osis::listen`'s URLs, the client socket): `listen(set, ..)` replaces that set alone: its listeners come back from their tasks, and a URL one of them is bound at keeps it under the new secret (`Listener::relisten`: QUIC swaps the endpoint's server config, `peer://` also re-registers at its relays); the rest close before any fresh listen. Sessions the set took under a key none of its listeners has any more close (`Input::Closed`): a key change serves nobody under the old key (its point: a removed contact or ended link holder knowing it must not keep a live channel), while the same key's sessions go on. Closing and rebinding a QUIC socket is not an option: quinn keeps the UDP socket while any connection or stream handle lives, and a closed connection's handles go only when the node drops them, so the port stays held.
- **Connection diagnostics**: the driver reports each connection up (dialed address, or accepted) and ended, and each failed dial (address, the transport's error or `dial timed out`), as `DiagnosticKind::Connection` (`osis::Diagnostic::Connection`, printed by `serve`, `-v`, `diag --follow`). Rate-limited per remote (`Engine::report_from`, 64 a minute each): each address dialed, all accepted connections together, all client ones together; an accepted connection is unproven when it comes up, so one remote opening and dropping them floods only that bucket, never a dial failure (osis-sync `driver::a_connection_flood_leaves_a_dial_failure_reported`). A bucket whose window passed goes as a new one comes. Dedup is of the same report (detail included), and each names its connection number, so none repeats.

## Reasons
- One sans-IO step with one place outputs are carried out: an older wake overwriting a newer nested one once left a node that never ticked after a restart; with `apply` alone carrying out outputs, in order, no call path can reorder them.
- No hook, callback or queue from the engine to sync: a queue sync must drain is state two owners write; memos and `Effects` give the same change-driven work with one owner per value.

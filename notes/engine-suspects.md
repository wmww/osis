# Engine: suspect flags and repair
> Summary: Where the engine flags an aspect it may have computed from less than another holder (`retention/suspect.rs`, `q/`), what clears a flag (bodies back, dormant under a later valid snapshot, never for pending expiry), how suspect lists carry flags with state digests over connections and a writer re-snapshots once per state per reporter, the accepted limits, the rejected settling rules with their seeds, and how the order oracle treats flagged aspects. Rules: spec/permissions.md §4, spec/sync-compaction.md §1, spec/commits.md §5; reasons: notes/convergence-study.md §3. Not here: what drops the data (notes/engine-retention.md, notes/engine-validity.md).

## The limit it backstops
Every writer dropped what a reader kept, so no writer can mend it and the reader's relay meets the tombstone: they read apart until the next write of that data (spec/requirements.md Deterministic). Rejected: a reader deposit, a new rule that lets a reader put back a value a writer deleted. The flag only asks for a repair; no read or state depends on it.

## Raising (`suspect::raise`)
- `Why::Uncovered`: `retention::uncover` with parts lost; a part never received again on its purge's fall (`purge::rejudge_purges`); a waiting part gone for a purge with a page away (`retention::strip_purged`). The aspect reads the value the purged write superseded until a copy or a snapshot repairs it.
- `Why::PendingExpiry`: a part pending at its expiry (`pending_drops` at pend, parked copies included; `strip_pending` from the T timer, or before the stored copy is read past T, `expire_waiting`). Only that aspect is flagged.
- A flag lists the bodies it is about ((commit, ai, `Why`) entries in the `q/` record). Each entry goes when that body is held again (`body_back` from `late_parts`); the flag goes with its last entry.
- Kept as rows `q/` mirrored in `Indexes::suspects` (a journaled map, loaded at open), so a read of one aspect's flag reads that key and that aspect's held snapshots alone. Sync follows them per key (`Engine::suspect(t, ak)`: `(at, why)`, why 0 while dormant, `None` once gone; new keys from `suspect_feed`): a follower is due when the flag is raised or cleared or a snapshot of the aspect comes, goes or flips validity, never for other engine changes. Counted: `shred::a_flag_moving_rejudges_that_flag_alone_spec_perm_4` (one flag re-judged per move at n and 10n flags), `a_suspect_flag_is_followed_per_aspect_spec_perm_4`.

## Settling
- A Flip or Uncovered entry is dormant while a held snapshot valid here is stamped after its commit, judged when `suspects` is read (`suspect::dormant`, `receipt::settled`), so a settling snapshot that turns invalid shows the flag again (alike seed 4208). No frontier test: pruned sessions leave nothing to test, and it was never exact (a writer that applied the delta, then dropped it, reached it carrying nothing).
- Limit, accepted (Tess: simple and consistent over rare shapes): a snapshot whose author never received the delta settles the flag too, so a node holding the delta reads richer, unreported, until a writer holding it compacts (it is uncovered there, and a live write leaves only with a carrier) or a copy arrives and joins (`takes_late`).
- A PendingExpiry entry is never dormant (it goes only with its thing, `forget`): its part's writes reach this node only as a snapshot's copies, and no test on held snapshots tells whether one repaired it. It yields to any flag raised after it (`suspects_under`: most recent first).
- Rejected settling rules:
  - clearing on any later-stamped snapshot (alike seed 4108: a writer's ordinary compaction carrying nothing of the part cleared it, leaving the divergence silent);
  - a listing valid snapshot, even one carrying a write of the part (seed 5288 with a second put in the same commit: the snapshot held the part's write value-less in a key-erased record, spec/crdt.md §4.7, outside the entry it wrote, and the reads still differed; also commit-level writes of one delta share a dot, so no dot test sees a partial carry).

## Repair (sync)
Per sync ID S, flagged aspects of the things in S's closure S's actor may read (`Engine::suspect_under`) with `Engine::state_digest` (16 B) go to reader sources of S (osis-sync `inbox/suspect.rs`, notes/sync-inbox.md), except while a source's stream shows under S a body the flag names (`Engine::suspect_bodies`): that body is being fetched, and a digest taken meanwhile would have a writer repair a state about to heal (a lowered writer reconnecting, its snapshots turned invalid, made node 0 snapshot or not by which of its lists arrived first: `growth::a_lowered_writers...`). A writer judges each entry by `Engine::repair_suspect` (`suspect_under`, `may_snapshot`, state held, digest differs, not already snapshotted from this state for that reporter account; each judged entry a `DiagnosticKind::Repair`); sync keeps the per-reporter state digest durably, so a report no snapshot can settle (order seed 5288, a PendingExpiry flag) costs one snapshot per state per reporter, across restarts. `Engine::state_digest` is a memo per aspect (stamped by the thing's creation record and the aspect's state), so judging an entry again costs a lookup unless its aspect moved, not work in the aspect's size. Not built: the sync-ID-level `held`/`state` set-hash digests (notes/convergence-study.md §3, detection of unknown divergence).

## Oracles
The order oracle excuses the reads of an aspect a commit expired by the history's end lists (Tess: a part expired before a node could apply it), decided from the history, never from the node's flags: `order::expired_by_now`. Everything else is compared exactly.
